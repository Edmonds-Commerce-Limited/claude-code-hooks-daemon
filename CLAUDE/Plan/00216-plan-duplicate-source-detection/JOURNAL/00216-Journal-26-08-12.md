## 19:25 · finding · P2 — the scout's INPUT substrate has a hole

A stop-hook advisory flagged me for hedging: I had written that the agent's
judgement was "unproven" and left it there. Part of that claim is verifiable
without dispatching anything — the design rests on live plans HAVING an
`## Overview` to read, and that is a measurable fact about this tree, not a
matter of opinion. So I measured it instead of asserting it.

| measure                       | value                                |
| ----------------------------- | ------------------------------------ |
| live plans                    | 36                                   |
| with a usable `## Overview`   | 31 (mean 1,378 chars — substantial)  |
| **with NO Overview at all**   | **5** — 00007, 00034, 00035, 00085, 00102 |
| Overview under 120 chars      | 0                                    |
| approx total ingest           | ~11.4k tokens                        |

The design assumption holds for 86% of the tree and FAILS silently for the
rest: for those five, the scout had only a folder name, and nothing in the
prompt told it to say so. A name says what a plan is CALLED, not what it
covers — scoring one silently is precisely how a confident wrong answer gets
produced, and this agent's whole calibration argument is that a wrong
candidate is more expensive than a missed one.

Fixed in the prompt: fall back to `## Goals`, and if there is neither, either
leave the plan out or name it and state plainly that only its title was
visible. Two tests pin it, so the instruction cannot be edited away later
without the guard noticing.

Killed the in-flight QA run to fold this in rather than running two full
cycles — the same call as earlier today with the pgrep whitelist, and for the
same reason.

Worth noting the shape: this was found by verifying a claim I had already
made, not by testing the code. The unit tests were all green before and after;
what was wrong was an assumption about the DATA the agent would meet.

## Namespacing and ownership banner

Two requests, both about the same underlying property: `.claude/agents/` is a
FLAT directory the client owns and fills with its own agents. This project's
own copy holds six of them. A name collision there does not error — one
definition silently wins and the other is never dispatched — so a bare
`plan-dedupe-scout` was a real hazard, not a stylistic one.

Renamed to `hooks-daemon-plan-dedupe-scout` everywhere: the template filename,
the frontmatter `name:`, `DEDUPE_AGENT_NAME`, the manifest entry, the asset
checker, `mkplan.bash`, the `plan_number_helper` guidance and the post-upgrade
task. The rename had to be swept rather than pointed at one constant, because
the name appears in prose the daemon writes into a client's CLAUDE.md as well
as in code.

Added an HTML-comment banner at the top of the deployed file carrying the
exact `OWNERSHIP_MARKER` string, plus the namespacing rationale and — the part
that matters more than "do not edit" — the customisation route: copy it to a
name of your own, do not edit in place. A banner that only forbids leaves the
reader with no way to get what they wanted, and they edit it anyway.

### Two guards caught this, which is the point

Registering the agent in `CLIENT_OWNED_ASSETS` immediately failed two Plan
00217 guards: the file was not enumerated in `CLAUDE/LLM-INSTALL.md`, and it
was not clean under the markdown check. Both were the guards working. The
agent definition is exactly the shape Plan 00217 exists for — daemon-owned
source, deployed into client-owned space, committed and linted by them.

The markdown half needed care. `AssetLanguage` documents that a language the
guard cannot lint passes by OMISSION, so MARKDOWN had to arrive together with
its check, never ahead of it. My first attempt ran bare `mdformat`, which does
not understand YAML frontmatter: it rewrote the leading `---` block into a
thematic break plus a setext heading and destroyed the definition — Claude
Code resolves an agent by exactly that block. The naive check "fixed" the
asset by breaking it.

The daemon already solves this. `markdown_table_formatter` strips and
re-attaches frontmatter byte-for-byte, so the guard now checks the asset is a
FIXED POINT of `format_markdown_text()` — the only question that matters,
since that is what will actually run over the file in a client project. A
second test pins frontmatter survival directly, so removing the mitigation
fails here rather than in the field.

### The dogfood run, and the input that misled me

Three probes, on haiku, following the deployed definition:

| probe                                       | result                                    |
| ------------------------------------------- | ----------------------------------------- |
| novel work (Dockerfile `:latest` handler)   | PASS — exact output string, count given   |
| un-built planned work (matches Plan 00205)  | PASS — named the number, correct verdict  |
| work already fully built, phrased as new    | FAIL — answered "already shipped"         |

The 00205 probe is the one worth keeping: my description shared almost no
vocabulary with the plan ("alternative git verbs" vs "synonym respellings")
and it still matched on subject, named the number and the status, and
recommended merging. That is the behaviour the whole design rests on.

The failing probe I initially read as a prompt defect and hardened against —
fencing the evidence to `PLAN.md` files, naming the forbidden verdict
phrasings, requiring a plan number per candidate. Three tests pin those words.
Re-running the probe after redeploying did NOT flip it, which is the useful
part: it means my first diagnosis was too confident.

Two things were actually going on. The input was pathological — nobody runs a
duplicate check on work they have just finished — and the harness is not a
faithful test. Inlining a definition as a user message to a general-purpose
agent leaves that agent's own system prompt ("explore the codebase, complete
the task") competing with it. Under real dispatch the definition IS the system
prompt. So the hardening is defensible on its own terms but is NOT verified,
and I have recorded it as Task 4.4 rather than ticking it.

## Task 4.4 under real dispatch — and a claim of mine that was wrong

The agent became dispatchable, so the probe that could not be run fairly
yesterday ran properly today.

**The hardening works.** The pathological case — work already fully built,
phrased as a proposal — now names Plan 00216 by number instead of replying
"already shipped, no additional work required". The true-positive control
still names Plan 00205. So the earlier inline harness WAS the confound: a
general-purpose agent's own system prompt competes with a definition handed to
it as a user message, where real dispatch makes the definition the system
prompt. Worth remembering as a general limit on testing agent definitions.

**A second defect the harness had masked.** Both real-dispatch runs produced
the right finding and the right plan number, then flattened the report into a
single sentence, dropping the `Overlap:` and `Relationship:` lines. Losing
`Relationship` is the costly one: merge and supersede are opposite actions and
it is the only field that says which applies. A format shown only as an
example reads as illustrative, and a small model compresses it away.
Strengthened to state the format is mandatory, with a test pinning the words.

**I was wrong about needing a session restart.** I wrote in the post-upgrade
task that a newly deployed agent is not dispatchable until a NEW session,
because Claude Code enumerates `.claude/agents/` at session start. The
recovery cron disproves it: `cae1a725` is session-only and non-durable, and it
is still alive — so this session never restarted, and the agent appeared
anyway. Enumeration re-scans during a session.

That mattered because the claim was already in a client-facing document,
telling people to restart when they only need to wait. Corrected there: check
the file exists, and treat a restart as the way to FORCE the re-scan rather
than a requirement. The same delay applies to edits, which matters for anyone
forking the definition.

It also explains why the format strengthening still showed old behaviour when
probed two minutes after redeploying — consistent with the re-scan delay, not
evidence the instruction is insufficient. Left as Task 4.5 to retest rather
than iterating on the prompt blind, which would be guessing dressed up as
work.

## Task 4.5 — position beat emphasis, and the count paid for itself immediately

Three real dispatches dropped the output contract entirely: correct finding,
correct plan number, then a conversational sentence with no checked-count and
no Relationship line. I had already restated the format as "mandatory" further
down the document, and it changed nothing.

The decisive evidence was that the CHECKED-COUNT requirement predates that
wording — it was in the body at session start and was still dropped. So this
was never the re-scan delay I hedged about earlier; a contract stated ~100
lines down simply loses to the pull of answering conversationally. I was wrong
to attribute the first miss to propagation, and the third run is what showed
it.

Fixed by hoisting the contract to the TOP and cutting it to three fields — the
count, the plan number, the Relationship — chosen because they are the only
things a caller cannot reconstruct from prose. Everything else can be brief.
Designing to what the model reliably does is better than demanding compliance
a fourth time.

That worked: the next dispatch opened with "Checked 17 active plans."

### And the count immediately found something

17. Earlier runs reported 34 and 32, against a tree that has not changed and
holds 34 live plans. So coverage swings by half between runs.

This is the best possible argument for having insisted on the field. Without
it, a scout that read half the tree and found nothing produces output
identical to one that read all of it — same reassuring sentence, same silent
gap, and the caller files the duplicate anyway. Requiring a number made an
invisible failure visible on the very first run that complied.

Logged as Task 4.6 rather than fixed on the spot. The likely remedy is to have
the procedure enumerate the plan folders FIRST and reconcile its reported
total against that list, instead of reading until it feels finished — but that
is a hypothesis, and each verification round costs a full dispatch, so it
wants a deliberate decision rather than another blind iteration.
