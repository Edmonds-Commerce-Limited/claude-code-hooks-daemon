## 18:50 · finding · T1.4 — 153 would-be denials in the first session, which is itself the Phase 2 question

The handler went live at the merge-day daemon restart and recorded 153 would-be
main-thread denials before this session ended. That number IS the evidence Phase
2 needs, and it points the opposite way from the plan's founding assumption: if
orchestrator-only mode blocked today, the main thread would have been stopped
153 times in a single session of ordinary work.

Two readings, and Phase 2 has to pick one rather than average them:

1. The coordination-tool boundary is drawn far too tight. Reading a file,
   running a test, committing — none of that is delegation-worthy on its own,
   and a mode that forbids it would make the main thread useless rather than
   focused.
2. The main thread genuinely is doing work it should have delegated, and 153 is
   the measurement of the problem the plan was opened to solve.

The record cannot distinguish them on its own — a count is not a judgement.
Phase 2's Task 2.1 needs the BREAKDOWN by tool, not the total: a mode that fires
mostly on `Read` argues (1), and one firing mostly on multi-step implementation
work argues (2). Recorded now so the next agent starts from the number rather
than re-deriving it, and does not mistake a big number for a settled answer.

## 19:15 · finding · T2.1 — the per-tool breakdown, and why it cannot finish the job

437 would-be denials across one session, by tool:

```
277  Bash
122  Write
 33  Edit
  4  Artifact
  1  CronList
  1  ToolSearch
```

`Read` appears ZERO times. That kills the first of the two readings offered in
the earlier entry: the boundary is not drawn so tight that it forbids looking
at things. Every flagged call MUTATES or EXECUTES, which is implementation
work, which is what the plan set out to catch. So far the evidence favours
reading (2).

**But the record cannot actually settle it, and that is the real finding.**
Bash is 63% of the total, and Bash spans both sides of the line this plan
exists to draw. A coordination-only main thread still has to run `git status`,
start a QA run and read its JSON — none of that is delegation-worthy, and all
of it is Bash. Today's own 277 are visibly a mixture: git plumbing and `jq`
queries alongside genuine implementation.

The verdict record carries `tool` but not the command, so the mixture cannot be
separated from what is on disk. Task 2.1 as written — "settle the boundary from
that evidence" — cannot be completed against this record.

Two ways forward, for the owner rather than for me:

1. Record enough to split Bash (the command head, or a coarse verb class —
   never the full command, which would put arbitrary text into a log this
   project treats as reviewable).
2. Accept that Bash is unclassifiable at this layer and draw the boundary on
   the OTHER tools, where the signal is already clean: `Write` (122) and `Edit`
   (33) are unambiguous implementation, 155 calls with no interpretation needed.

Option 2 is available immediately and needs no new capture. It is also the more
honest shape: a mode that blocks `Write`/`Edit` on the main thread says exactly
what it means, where one that blocks "some Bash" would need a classifier that
is itself a source of wrong answers.

Not deciding this myself — promoting anything to blocking is Task 2.2 and
explicitly the owner's call.
