## 16:40 · decision · T1.2 — precedence placement and its trade-off

Placed the operator-signal branch in `decide_once` right after the
DROP-ANCHOR + coupled-effort corrections and *before* the manual
model-switch override, satisfying the literal instruction ("ahead of the
goal and model injections"). Consequence: it sits ahead of the "own line"
resolution block (which computes `own_line_blocks_text`), so the operator
branch cannot reuse that shared variable. Fixed by gating on the raw
`machine.own_line_pending` flag instead — slightly more conservative (a
line a *later* tick would have resolved this same tick still reads as
pending from here), which is the safe direction for "don't paste text over
a possibly-unconfirmed line."

## 16:45 · decision · T1.2 — status-line deadline is anchored to the signal's own `ts`

The status-line countdown (Task 1.5) must count down to a fixed deadline,
not "N minutes from whichever tick happens to render it" — recomputing
`now + minutes * 60` on every ~2s tick would push the deadline forward
every tick and never converge. `load_operator_signal` therefore computes
`deadline = ts + minutes * 60` once, from the signal file's own `ts`, and
returns it as a fourth tuple element (widening the 3-tuple shape every
other signal loader here uses to a 4-tuple). The status message is
(re)posted every tick a valid signal remains unconsumed, independent of
`can_inject` — mirroring the audit banner's rationale that a file write
cannot disturb what the user is typing.

## 16:50 · decision · T1.3 — where the wording lives

The rendering (`_render_operator_message`) lives entirely in
`.claude/ccy/claude-supervise.py`, not in the daemon package, even though
this repo is self-install (the daemon *could* import itself). Reason: the
daemon-side `operator_signal.write_operator_signal` only ever carries a
`kind` + `minutes` on disk — an attacker with filesystem access to the
context-sidecar directory writes a JSON file, not a Python call, so the
real trust boundary is the supervisor's read of untyped JSON, not the
writer's type-checked Python signature. Keeping the templates supervisor-side
means the ONLY thing ever built from file bytes is a number substituted into
a literal string; the daemon module is a thin, independently-validating
sensor with no rendering responsibility at all. `kind` string constants are
duplicated (unavoidable — the supervisor is stdlib-only and cannot import
the daemon package) and pinned together by
`tests/unit/supervise/test_operator_signal.py::TestKindsPinnedToTheDaemonWriter`
plus a round-trip test that writes via the real daemon function and reads
via the real supervisor function.

## 16:55 · decision · T1.4 — `--all-sessions` discovery mechanism

`--all-sessions` does not require `CLAUDE_CODE_SESSION_ID` at all (the
whole point — the intended caller is host-side tooling that may run outside
any container). It discovers targets by listing `<session>.json` context
sidecars already present in the project's own shared, bind-mounted
`context-sidecar/` directory (Plan 00166: two terminals of one project
already share this one directory) — this is what scopes it to "every
session of this project and no other" without needing any new host-visible
session registry.
