## 01:20 · finding · P1 — the "old default" baseline is the NEW default on the documented path

Found while fixing the six v3.62.0 field defects, not reported by the client.
`scripts/install/config_preserve.sh` Step 5 carries the comment "Save the old
example config before checkout (for diff baseline)" and copies
`$EXAMPLE_CONFIG` (`$DAEMON_DIR/.claude/hooks-daemon.yaml.example`) into
`$OLD_DEFAULT_CONFIG`. On the Layer 1 path that comment is false: `upgrade.sh`
checks the target out first and never preserves the pre-checkout example, so
the "old" default is the NEW one.

Verified only that Layer 1 does no such copy:

```
$ grep -n "hooks-daemon.yaml.example\|EXAMPLE_CONFIG\|OLD_DEFAULT" scripts/upgrade.sh
(no output)
```

The consequence is REASONED, not yet measured, and Task 1.2 exists to measure
it before anything is changed. Expected: with `OLD_DEFAULT == NEW_DEFAULT`, a
user value equal to the old default differs from the new one and is therefore
classified as a customisation and preserved — so a changed default never
propagates. The direction is the safe one (preserve rather than silently
change), which is likely why it has gone unnoticed.

## 01:38 · finding · T1.2 — measured: a changed default does NOT propagate

Correcting the 01:20 entry, which recorded the consequence as reasoned rather
than measured and hedged it as "expected". It is now measured, and the
reasoning held. Task 1.2 is complete.

Drove `ConfigDiffer` + `ConfigMerger` directly with a default that changed
between versions and a user who simply accepted the old one:

```python
OLD_DEFAULT = {"version": "1.0", "daemon": {"log_level": "INFO",    "timeout": 30}}
NEW_DEFAULT = {"version": "2.0", "daemon": {"log_level": "WARNING", "timeout": 30}}
USER        = {"version": "1.0", "daemon": {"log_level": "INFO",    "timeout": 30}}

diff   = ConfigDiffer().diff(USER, baseline)
merged = ConfigMerger().merge(NEW_DEFAULT, diff).merged_config
```

```
TRUE old default (intended):
   custom_daemon_settings = {}
   merged log_level       = WARNING
   new default propagated = True
NEW default as baseline (Layer 1 path):
   custom_daemon_settings = {'log_level': 'INFO'}
   merged log_level       = INFO
   new default propagated = False
```

So the effect is exactly as predicted: a user value equal to the OLD default
is misread as a deliberate customisation and pinned, and the new default never
arrives. Note the trap for whoever writes the fix — this is indistinguishable,
at the data level, from a user who genuinely set `INFO` on purpose. The
baseline is the ONLY thing that separates "accepted the default" from "chose
this value", which is why restoring a true old-version baseline (Task 1.3) is
the fix rather than any heuristic applied at merge time.

## 08:12 · decision · T1.3 — handover, not `git show`

Two candidate fixes were on the table in PLAN.md. Chose Layer 1 preserving the
file and exporting a path, and rejected having Layer 2 read the old default out
of git (`git show <previous-ref>:.claude/hooks-daemon.yaml.example`).

Reason: on the Layer 1 path Layer 2 no longer knows the previous ref — its own
`ROLLBACK_REF` resolves to the TARGET, because the checkout already happened.
So the git approach would need Layer 1 to hand over the ref, which is the same
handover with an extra step and an extra failure mode. One mechanism, used by
both entry points.

Placement detail worth keeping: the preserved copy goes OUTSIDE `DAEMON_DIR`.
Layer 1's checkout is `git reset --hard` for a normal (non-self-install)
install, which would discard anything staged inside the tree.

The resolver is a CAPTURED function (`VAR=$(resolve_old_default_config ...)`),
so every progress line in it is `>&2`. This repo's v3.10.0 SEV-1 was one
missing `>&2` in exactly that shape, and there is a QA gate for it —
`audit_capture_corruption.py` reports no violations, and a test asserts stdout
is a single usable path.

## 09:00 · finding · T1.3 — CORRECTION to the 08:20 entry and commit c85d5e90

The Phase 1 commit message says the baseline "on the documented upgrade path

Precise conditions, which the fix still covers:

## 09:20 · decision · T2.5 — owner ruling: leave config untouched on upgrade

Asked the owner whether the fast path skipping the config merge was design or
accident. Ruling: **leave it** — "because post upgrade we are supposed to
handle the config optimisation". Upgrading must not rewrite a user's config
file; `/optimise` is the adoption path. Task 2.5 closed as not-a-bug.

The owner's follow-up is what makes the ruling safe, and it deserved proof
rather than agreement: if a handler is enabled by default but absent from the
project config, is it enabled? Their understanding was that absent = enabled,
and that disabling requires an explicit `enabled: false`.

Confirmed, three independent ways.

Executed against the real models:

```
EventHandlersConfig().get_handler('absent')      -> enabled = True
model_validate({'h': {'enabled': False}})        -> enabled = False
same config, a different absent handler          -> enabled = True
```

Code: `EventHandlersConfig.get_handler()` (models.py:87) returns a bare
`HandlerConfig()` for anything not present, and `HandlerConfig.enabled`
defaults to `True` (models.py:61). A comment at models.py:214 states the rule
outright: "Not in config = use defaults (enabled)".

Field evidence: the v3.62.0 defect report recorded five handlers new in that
release as registered and firing in a client project whose config predated the
release — and one of them denied a write — all before `/optimise` ran.

Two dead ends worth recording so they are not repeated. First, comparing the
`handlers` CLI listing against config keys suggested "56 active but
undeclared"; that was a naming artefact (the listing shows handler NAMES,
the config uses handler CONFIG KEYS) and was discarded rather than reported.
Second, this repo is a poor sample for the question at all — its own config
declares every handler explicitly, so nothing here is absent.

Consequence worth stating plainly: leaving config untouched does NOT disable
new handlers. The real gap `/optimise` fills is the inverse — a handler
shipping default-DISABLED stays off, and only the review surfaces it.

## 09:44 · decision · T4.2 — the two cases were assessed apart and want the same answer

The task said to handle install and update separately rather than with one
compromise. Doing so, the premise behind the split turned out to be wrong:

- **Update** — daemon installed and enforcing, so `/tmp` is denied every time.
  `untracked/scratch/` already exists via `ensure_scratch_dir` (Plan 00333).
- **Install** — the stated worry was "may have no repository yet".
  `LLM-INSTALL.md` opens with "From your project root (must have `.git/`)" and
  its first act is a clone into `.claude/`. There IS a repository. No daemon is
  running, so nothing blocks it either way, but the in-repo destination is
  still better: `untracked/` is gitignored the moment the installer runs and
  survives a container restart, which `/tmp` does not.

So one destination is correct for both — arrived at by separating them, not by
declining to. `mkdir -p untracked/scratch` precedes each fetch so the install
case does not depend on the daemon having run first. The
download-inspect-run sequence is untouched: no `curl | bash` introduced, and a
test asserts that.
