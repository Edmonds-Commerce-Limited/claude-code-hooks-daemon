## The report is accurate, and I checked rather than assumed

The report quotes git's refusal but says plainly that the manual could not be
re-read on the reporting machine, so the quoted runtime warning is the evidence
it relies on. That is honest, and it is also exactly the kind of claim worth
re-deriving before building a fix on it — a paraphrase of git's rule could be
subtly wrong in a way that sends the fix in the wrong direction.

So I built the shape from first principles: a bare repo as the "remote", a clone,
a branch pushed with `-u` so it genuinely has an upstream, one further commit NOT
pushed, then `git merge --no-ff` into main locally. Result, verbatim:

    warning: not deleting branch 'feature' that is not yet merged to
             'refs/remotes/origin/feature', even though it is merged to HEAD.
    error: The branch 'feature' is not fully merged.

`git merge-base --is-ancestor feature main` succeeds at the same time. Both
halves of the report confirmed on this machine.

## Which proof is actually stronger

Worth being precise, because it decides the fix. The daemon proves *the tip is an
ancestor of the protected ref*, so every commit on the branch is reachable from
`main` and nothing can be lost. Git's `-d` enforces *merged into its upstream if
it has one* — a statement about whether a PUSH happened, which is not a fact
about preservation at all.

And the combination cannot hide a loss: a commit that is ahead of the upstream
AND absent from `main` would fail the ancestry test, so the branch would never be
classified `merged` in the first place. Within this tier, ahead-of-upstream
commits are necessarily also in `main`.

That is why a distinct tier is defensible where widening `merged` is not. The
proof does not change at all — only the flag does, and the tier name records why.

## Phases 1–3 delivered

The precondition test earned its keep on its first run. My first fixture pushed
to a bare repo by PATH and then hand-wrote `branch.<name>.remote`,
`branch.<name>.merge` and the remote-tracking ref — which looks equivalent and is
not: without `remote.origin.url` git cannot resolve `<name>@{upstream}` at all,
so it falls back to comparing against HEAD and ALLOWS the delete. The fixture
therefore built a shape where the bug does not exist, and every assertion after
it would have been about nothing.

`test_the_fixture_reproduces_gits_refusal` failed with "fixture no longer
reproduces git's refusal", which is exactly what it is for. Replaced the
hand-written config with a real `git remote add origin` plus `push -u`.

That is worth remembering as a general point: a fixture that synthesises the
STATE around a git feature, rather than exercising the feature, can produce a
shape git treats completely differently. Same lesson as Plan 00248's F4, where a
test that looked like it covered a function could not see the call under review.

## What each phase changed

**Phase 2, the substantive fix.** `_is_merged_into_its_upstream` asks git the
question directly — `rev-parse --abbrev-ref --symbolic-full-name <name>@{upstream}`
then `merge-base --is-ancestor <name> <tracking>` — and returns True when there
is no upstream at all, because git then falls back to HEAD, which the ancestry
proof already covers. So the common case keeps delegating to git's battle-tested
`-d` and is NOT escalated to a force delete for a condition that does not apply
to it. Two negative tests pin that: a branch with no upstream, and a branch level
with its upstream, both stay plain `merged`.

**Phase 3, the reporting.** The delete loop now runs with `check=False` and
collects failures instead of raising, so git can refuse on any grounds — today's
or a future git's — and the user gets git's own sentence plus the tier that was
proven. The docstring's all-or-nothing promise was corrected rather than
defended: classification-before-mutation is a real guarantee and is stated as
one, but a ref already removed cannot be un-removed, so the report now lists
exactly what went and sets `refused`.

The refusal is provoked in the tests with REAL git, by patching
`delete_argv_for_tier` back to the safe delete for a merged-unpushed branch. That
reproduces the pre-fix argv exactly, so the test exercises git's actual refusal
rather than a mock's idea of one.

**The bundle.** First attempt logged the unlink failure and continued — and the
`error_hiding` QA check flagged it as `log-and-continue`, correctly. The fix was
not an exclusion: this module already reports outcomes through
`DeletionReport.blockers`, so the failure goes there, in front of the person
running the command, rather than into a log they have no reason to open. The
guard pointed at a better design than the one I reached for first.
