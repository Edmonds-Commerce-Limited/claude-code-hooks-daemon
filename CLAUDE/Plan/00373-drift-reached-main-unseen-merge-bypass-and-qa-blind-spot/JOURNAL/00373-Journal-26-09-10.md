## 14:32 · finding · P1 — how the drift got in, and why nothing said so

Found while surveying state after the release slate came back green on every
axis but worktrees. `CLAUDE/Plan/00372-worktree-reap-two-defects/` existed at
the ACTIVE location holding only `subagent-reports/build-report.md`, while
the README row for 00372 pointed at `Completed/`.

Sequence, from `git log -- CLAUDE/Plan/00372-worktree-reap-two-defects/`:

```
a85e00e8 Merge branch 'worktree-plan-00372': the plan's build report
7c315045 Plan 00372: subagent build report
69803a2c Plan 00372: Complete — archived to Completed/
```

The worktree branch was cut before `69803a2c`, so it wrote the report to the
path the plan no longer occupied, and the merge landed it. Four plan-QA
findings resulted — `no-new-collisions`, `row-folder-bijection`,
`location-status-coherence`, `stats-recount`.

Two independent gates were missing, either of which would have caught it:

1. `plan_qa_commit_gate.matches()` calls `is_git_commit(tokenise(command))`.
   `git merge` auto-commits without invoking `git commit`, so the gate never
   ran. Same for `docs_qa_commit_gate` and `staged_lint_gate`.
2. `scripts/qa/llm_qa.py`'s `TOOL_REGISTRY` has no `plan_qa` or `docs_qa`
   entry, though both are shipped CLI verbs that exit 1 on findings and
   support `--json`. So the drift survived `27/27 PASSED`, green CI, and
   `release-slate-check`.

## 15:00 · decision · P2 — any finding fails QA, at either severity

The sweeps exit non-zero on ANY finding, and the QA tools mirror that rather
than reinterpreting it. The tension is real and worth recording: the
advise/block split exists so an inherited inconsistency does not deny every
later commit (`commit_scoped_level`, Plan 00343). Promoting advisories to
blockers would undo that.

It does not, because QA is a different surface asking a different question.
`commit_scoped_level` decides who gets BLAMED for a commit; QA decides
whether the tree is clean right now. The whole corpus was four findings and
all four were fixable in minutes, every check that can legitimately fire has
its own configured allowlist, and the project's own pyright gate already
sets this precedent ("ANY error-severity diagnostic fails QA, so every
diagnostic the agent sees is one worth reading"). Ratcheting while it is
cheap is the moment to do it. If this proves too noisy it is a one-line
change.

## 15:15 · finding · P2 — the two sweep CLIs disagree on a key name

`plan-qa --json` emits `"level"`; `docs-qa --json` emits `"severity"`, for
the same concept, on two sibling verbs. Found while writing the wrapper's
severity split — it counted `severity` and would have silently reported
`0 block, 0 advise` for every plan finding while the total was right.

Not fixed here: changing a shipped `--json` key is a breaking change that
belongs in a release note, not smuggled into a QA plan. The wrapper does not
paper over it either — it reads the findings the CLI prints and the
divergence is recorded here for whoever reconciles the two surfaces.

## 16:00 · finding · P2 — the replay found a defect in my own gate

That first replay printed `3 findings (0 block, 0 advise)` — a summary line
contradicting its own total. Cause: the 15:15 key divergence, which I had
recorded as "not fixed here". Recording it was the wrong call. The wrapper
counted `severity` only, so every plan finding fell out of the split while
still counting toward the total, and the report told a reader there was
nothing to place.

Fixed at the reading end (`_severity_of` tries `severity` then `level`),
not by changing a shipped `--json` key — that remains a breaking change for
a release note. Added a class guard asserting the split always sums to the
total, so a THIRD key name cannot reintroduce this quietly; the failure was
never about `level` specifically.
