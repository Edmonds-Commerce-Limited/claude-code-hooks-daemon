Worth stating plainly: neither bug was on this plan's task list, and neither

Queried the verdict log (`hooks-daemon verdicts`) rather than arguing from

274 fires, `allow=274`. Not one of them restricted anything. It is the single
most active behavioural handler in the daemon by a factor of 2.7 over the next

The mechanism, read from source: `handle()` lowercases stdout+stderr and does a
substring test for `error`, `failed`, `failure`, `fatal`, `warning`, `warn`,
`deprecated`, plus "stderr was non-empty". Substring, not word — so
`error_hiding_exclusions.json` in an `ls` listing trips it. It then echoes the
FULL command back into context and asks the agent to "review the output
carefully".

The corroboration is first-hand and unusually direct: it fired on the `grep`
that listed the removals, on `git status --porcelain`, on the `jq` that read
the QA report, and — best of all — on the very command that produced the table
above, because the string `bash-error-detector` contains "error". The output it
asks me to re-read is output I requested one line earlier and can see.

Confirms REMOVE for Task 2.5 rather than narrow+rate-limit. A rate limit would
reduce the volume of an advisory whose content is "look at the thing you are
looking at"; the defect is not the frequency.

Two figures with a caveat attached, since the report says so itself: this is a
bounded rolling window, not a lifetime total, and "never fired" in it is not
evidence a handler is pointless. Neither claim above rests on an absence — both
rest on a handler firing 274 times and allowing every one.

## 21:40 · finding · T2.4 — post_clear_auto_execute breaks when sessions share a daemon

The audit's case was "its originating plan is Cancelled as unachievable and
rates the surviving code marginal". Reading the code, there is a firmer reason.

Its whole contract is "fires once per session". It implements that with ONE
slot of instance state:

```python
self._last_session_id: str | None = None
...
if session_id != self._last_session_id:
    return True
```

The daemon is explicitly designed for multiple Claude Code processes with the
same (hostname, project root) to SHARE one daemon instance — CLAUDE.md's
"Parallel sessions share one daemon (Plan 00127)". Two concurrent sessions
alternating prompts flip `_last_session_id` on every dispatch, so `matches()`
returns True for every prompt of both, and each is told "the user has just
started a fresh session (likely after /clear)" when they did not.

So the failure mode is not "marginal value" — it is guidance that becomes
FALSE exactly in the configuration this project encourages (the
`agent_isolation_advisor` and the `multithread_indicator` status segment both
exist because several threads at once is normal here). A one-slot cache cannot
express per-session state in a multi-session process.

Fixable in principle — a bounded per-session map, as `command_hints` already
does for its TTL — but that is repair, and repair was Plan 00236's remit. The
verdict stands at REMOVE: it fired once in the retained window, and the thing
it exists to prevent (an agent idling after /clear instead of executing) is
already covered by the resident instruction set.
