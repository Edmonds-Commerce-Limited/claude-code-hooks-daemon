# Plan 00317 Task 1.1: host-tier responsibility audit

`claude-supervise.py` runs two tiers: the PTY **host** (`supervise()` /
`_forward_io()`, spawned once, never reloads because it owns the live
`claude` child) and the **`--worker`** subprocess (`run_worker()`, owns
`CompactStateMachine`, respawned from current on-disk code whenever
`PolicyWorker.reload_if_stale()` detects a content-hash change). Everything
below is host-tier code found beyond raw byte forwarding and
child/worker-lifecycle management, classified **MOVE** or **MUST STAY**.

## Summary of moves

Only item 1 (typed-command recognition) is moved, per Task 2.1. Every other
audited item has a hard reason to stay host-side: either it must act on a
byte before that byte is forwarded (items 2, 5), it configures a byte-level
primitive once per session rather than deciding per-tick (items 3, 4), it is
inherently process-local (item 6), or it is pre-existing "host injects /
adopts state" plumbing from the Plan 00164 Phase 4 split that this plan's
Non-Goals explicitly preserve (items 8, 9, 10). Item 7 is recorded as a minor
inconsistency (a threshold comparison lives host-side) but is out of this
plan's scope and left alone — flagged for a future plan if it ever matters in
practice.

## Task 2.1 design (typed-command recognition)

- New `RawInputTap` (bounded, fail-open byte buffer) lives host-side
  alongside `InputActivity`, fed the same forwarded bytes inside
  `_forward_io()`. `drain()` returns and clears the buffer; overflow drops
  the OLDEST bytes so a stalled drain can never grow memory or block
  forwarding.
- `TickFacts` gains `human_raw_input: str` (base64 of the bytes forwarded
  since the last tick). Host still populates the legacy
  `human_compact_submitted` / `human_model_command` / `human_effort_command`
  / `input_line_empty` fields from its own `InputActivity.line` as before —
  unchanged, so every existing host-side test keeps passing — but those
  fields are now consumed ONLY by the in-process fallback path
  (`_poll_once`, used when the worker is unavailable). This is an
  intentional, pre-existing degradation pattern (the fallback already
  doesn't get worker hot-reload for `decide_once` itself), not a new gap.
- `run_worker()` gains its OWN persistent `HumanInputLine` instance (same
  class, same lifetime as `CompactStateMachine` — reset on worker
  restart/reload, which is the same risk profile the state-machine export/
  import already manages for state). Each tick, it feeds
  `facts.human_raw_input` into that instance and RECOMPUTES
  `human_compact_submitted` / `human_model_command` / `human_effort_command`
  / `input_line_empty` from it, overriding whatever the host sent, before
  calling `decide_once`. This is the piece that now hot-reloads: a code
  change to `HumanInputLine` takes effect the moment the worker restarts,
  with no host-side change and no session restart.
- Fail-open: if `human_raw_input` is empty/missing (old host build, or the
  worker restarted mid-line so its recognizer buffer is fresh/empty), the
  worker's recognizer simply reports "no command yet" for that tick — never
  raises, never blocks. A worker restart mid-typed-line loses at most that
  in-flight (not yet submitted) line state, which self-heals the moment the
  human keeps typing or presses Enter again.
