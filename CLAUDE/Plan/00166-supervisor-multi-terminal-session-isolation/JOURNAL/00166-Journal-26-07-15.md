## 14:10 · finding · T2.1/T2.2 — identity-binding feasibility spike (live)

Ran a live `/proc` probe against the two-terminal setup (A=`7ef60468`,
B=`e7247afe`). Decisive results reshaping Decision 1:

- **H4 (open transcript fd) FAILS.** claude does NOT keep its
  `~/.claude/projects/<slug>/<session>.jsonl` transcript continuously open —
  the probe found NO process (in the whole container) holding ANY `.jsonl`
  open. So `/proc/<child>/fd → transcript → session_id` is not viable.
- **Env-var route WORKS.** `CLAUDE_CODE_SESSION_ID=7ef60468…` is present in
  claude's DESCENDANT process environs (e.g. pid 65776, a `bash -c` tool-call
  child of claude pid 76). Not in the claude process's OWN environ (set after
  exec), but reliably in its children while it works. Learnable + cacheable.
- **Containers are the clean separator.** Each `ccy` terminal is a SEPARATE
  podman container / PID namespace. The env scan surfaced ONLY A's own
  `7ef60468` — NOT B's `e7247afe` — even though B's sidecar AND B's transcript
  are BOTH visible on disk (shared bind-mounted `untracked/` and
  `~/.claude/projects/`). So process-env identity is container-local and
  excludes foreign sessions by construction; only the on-DISK shared surfaces
  leak across, which is exactly what the actuator must filter.

### Revised Decision 1 (identity source)

Bind the supervisor to its OWN session-id set by scanning its container's
processes for `CLAUDE_CODE_SESSION_ID` (its child claude's descendants),
CACHE the set (ids are stable per claude process), and FILTER the shared
sidecar/signal dir to act only on files whose `session_id` ∈ that set.
Fail-safe: until the main id is learned, act on NOTHING (never resume/compact
off an unidentified signal). Minimal viable fix for the reported bug =
filter `load_compaction_signal` to the learned id set (compaction is a
main-session event), which alone stops A resuming on B's compaction.

Open design fork for Phase 3 (needs a steer): (a) precise —
walk the direct-child claude's process subtree/descendants for the id set
(handles subagents that stay in-tree; misses ones reparented to pid 1);
vs (b) namespace-broad — treat EVERY `CLAUDE_CODE_SESSION_ID` found in the
container as "mine" (correct under one-container-per-terminal; over-broad
only if a deployment shares a PID namespace across terminals, e.g.
`--pid=host`). Leaning (b) with a documented caveat + `CLAUDE_HOOKS_*`
socket-isolation escape hatch for shared-namespace setups.

## 16:45 · blocker · P5 — LIVE FLOOD: worker crash tracebacks spammed both PTYs

While committing the identity fix, BOTH live Claude sessions were flooded with
supervisor stack traces (`_redirect_worker_stderr_to_log is not defined`, etc.).
Root cause — a dogfooding self-inflicted wound from live-editing the shared
supervisor file:

- The PTY **host** process never hot-reloads itself; only the policy **worker**
  subprocess reloads (`PolicyWorker.reload_if_stale`, fingerprint change). The
  host also **restarts a dead worker every tick** (`if not worker.alive():
  worker.restart()`, ~line 2485).
- The OLD host spawns the worker via `Popen(..., stdin=PIPE, stdout=PIPE)` with
  **no `stderr`** → the worker inherits the host's stderr = the **PTY**.
- During my edits there was a window where the worker's `main()` **called**
  `_redirect_worker_stderr_to_log()` before I had **defined** it. Every worker
  the host respawned `NameError`'d on startup → traceback to the inherited PTY →
  crash-loop flood (~every 2s), in BOTH containers sharing the bind-mounted file.

### Safety net (the durable fix the user demanded: errors → file, NEVER stderr)

Added to `.claude/ccy/claude-supervise.py` (Plan 00166 Phase 5):

- `worker_error_log_path()` / `open_worker_error_log()` / `append_worker_error()`
  — the worker's diagnostics land in
  `untracked/claude-supervise-worker.err.log`, never a tty. `open_*` returns
  None → caller uses `subprocess.DEVNULL`; the worker's stderr is NEVER left
  inheriting the terminal.
- `PolicyWorker.start()` now passes `stderr=<error log | DEVNULL>` to Popen
  (host-side redirect once the host runs new code), and closes the handle in
  `close()`. The host-side `sys.stderr.write` worker-lifecycle noise in
  `close()` was rerouted to `append_worker_error` too.
- `_redirect_worker_stderr_to_log()` — the worker's FIRST action in its
  `--worker` branch dup2's fd 2 onto the log file, so it self-contains even
  under an OLD host that inherited the PTY (defence in depth).
- `run_worker` per-tick guard: `decide_once` wrapped in `except Exception` →
  full traceback to the FILE + a safe `_worker_error_noop()` emitted so the host
  still gets a reply and the worker never dies (no crash-loop).

Verified: forcing `decide_once` to raise on 3 ticks → worker rc 0, 3 NOOPs
emitted, error log holds the tracebacks, **zero** bytes to stderr. mypy clean;
278 supervise tests pass (9 new in `test_worker_error_safety_net.py`). Live
worker PID 172235 healthy since 14:44, error log empty. **Lesson**: never
live-edit the shared supervisor incrementally while ccy sessions run it — an
incomplete intermediate state crash-loops every session. The safety net makes
this class of failure non-fatal (file, not PTY) forever after.

**Follow-up owed**: host adopts the Popen-stderr redirect + the decision fix
