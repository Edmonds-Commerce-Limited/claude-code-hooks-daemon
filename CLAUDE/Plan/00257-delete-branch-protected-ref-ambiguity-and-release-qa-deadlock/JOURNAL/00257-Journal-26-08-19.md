# Plan 00257 Journal — 2026-08-19

## 09:35 · finding · `sed -n 'Np' file` is blocked, and it modifies nothing

Fourth guard misfire of this release cycle. Recording it; not fixing it yet,
for the same reason as the previous three — v3.54.0 is prepped and unpushed to
`refs/tags`, and a source change would move HEAD under the tag.

**What happened**: I ran `sed -n '1,20p;140,157p' PLAN.md` to read two ranges
of a file. `sed_blocker` denied it.

**Why this is arguable rather than obviously wrong**: `CLAUDE.md` states the
rule as "sed is blocked for FILE MODIFICATION", and lists read-only use as
allowed — but the example given is a PIPELINE (`cat f | sed 's/x/y/' | grep z`).
`sed -n '1,20p' file` takes the path as an argument instead. It has no `-i`, so
it cannot write to the file; it prints to stdout and exits. By the stated
rationale — "a single error can silently destroy hundreds of files" — there is
nothing here to destroy.

**Why I am not simply calling it a bug**: a deliberately blunt rule has real
value. `sed -i` and `sed -n` differ by one character, and an agent that has
built the habit of reaching for `sed` to read is one typo from reaching for it
to write. The block also costs almost nothing: `Read` with `offset`/`limit` did
the same job on the next call. So the question is a policy one — is the
blockiness intentional? — not a defect report, and it should be answered by
whoever set the policy rather than assumed by me.

**What makes it worth recording at all**: a *system-level* instruction in this
same session actively told me to prefer `sed -n`, heredocs and short scripts
over the dedicated Read/Edit/Write tools. That instruction and this project's
rule are in direct conflict. I followed the project rule, which I think is
right — the project's hard guard is the more specific and more local authority,
and it is dogfooded. But an agent that followed the generic instruction instead
would hit this wall repeatedly and might "work around" it by disabling the
handler, which is the failure mode worth heading off.

**Concrete options if this is taken up** (none applied):

1. Leave as-is, and correct `CLAUDE.md` so the allowed-read example is not
   pipeline-specific — i.e. say plainly that ALL `sed` is blocked, pipeline
   read-only use excepted, so the doc stops implying reads are generally fine.
2. Allow `sed -n` with no `-i`/`-e`/`-f` and a file argument, on the grounds
   that it provably cannot write.

Option 1 is the smaller change and keeps the guard blunt; option 2 is the more
accurate one and is what the stated rationale actually implies. My preference
is 1, because the doc is currently the thing that is wrong: it describes a
narrower block than the handler implements, and that gap is what surprised me.

Running tally of guards that misfired on their own author during this release:
the `release_blocker` step threshold (twice), the `STOPPING BECAUSE:` matcher
versus markdown emphasis, and now this. None was a false alarm about DANGER —
all four are cases where the guard's *stated* contract and its *implemented*
contract differ.
