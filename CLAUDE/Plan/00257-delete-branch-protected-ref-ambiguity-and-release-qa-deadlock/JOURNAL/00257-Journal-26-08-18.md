## 14:05 · decision · P1 — why this was latent for a release and is not now

Worth recording because it changes how the severity reads. The ambiguous base
is not new. What is new is that a mis-verdict can now reach a force delete.

Before: bad base -> tier `merged` -> `delete_argv_for_tier` returns
`git branch -d` -> git re-runs its OWN ancestry check -> refuses. The bug was
real and fully contained by a tool we did not write.

After Plans 00249/00253: the same bad base can land on `merged-unpushed` or
`merged-not-in-head`, which return `--force` precisely so git's refusal is
bypassed. The tiers are correct; they simply removed the net.

This is the LESSONS.md entry from earlier this cycle ("the battle-tested tool's
checks compose with yours") arriving from the other direction — that entry
observed git's delete-time check catching what our proof missed. Here we
switched that check off for two tiers and immediately lost a real defence.

## 14:05 · finding · P2 — a fixture that neutralised an input nobody reads any more

The three QA failures had one cause, and it is a better lesson than the fix.

`test_stop_chain_terminal_shadowing` stubbed `subprocess.run` to feign a clean
working tree, and its docstring said so, because `release_blocker` inferred a
release from modified version files. That handler was changed THIS CYCLE to
read `untracked/release-state.json` instead — correctly, since a working tree
cannot express intent. Nothing updated the fixture, and nothing could notice:
the stub still ran, still succeeded, and isolated nothing.

The failure surfaced at the worst possible moment — QA went red the instant a
real release wrote the state file, which is exactly when RELEASING.md requires
it green. Fixed by rooting the walk at an empty `tmp_path` and patching
`ProjectContext.project_root`, so it isolates against what the handler now
reads. It passes with a release in flight, which is the only proof worth having.

## 14:05 · finding · P2 — chasing it found a production defect, not just a test one

The two acceptance failures were not the same fixture problem. `release_blocker`
is terminal at priority 8, so it shadows `auto_continue_stop` at 10 entirely —
and during a release an agent that hit a `tool_use_error` was told "a release is
in progress", which says nothing about the error it just hit. The specific,
actionable directive (Read the file, then retry) was replaced by an unrelated
one.

Stood the guard down for that case only, reusing `get_transcript_reader` rather
than re-parsing the transcript so the two handlers cannot drift apart on what "a
tool error" means. Both handlers DENY, so the release loses nothing: the session
continues either way and the guard fires again on the next stop attempt, which
by then carries no tool error.

The remaining negative-control test now skips during a release with a full
explanation. That is deliberate and narrow: its real assertion — Branch 2.5 must
not fire on a clean turn — still executes, and only the question of WHICH branch
answered is unobservable while a terminal guard sits ahead of it.

## 16:40 · finding · P4 — the guard had a hiding place, and something was in it

Three sub-agents dispatched to re-derive the review findings all terminated
without reporting, so I did the review in the main thread. One of the three
lost labels was real, and it was the one about the guard rather than about the
code it guards.

`test_git_spawns_are_bounded` read only `["git", ...]` literals. Its docstring
defends that: argv assembled elsewhere would mean guessing, and a checker that
guesses is untrustworthy. Right principle, drawn one step too wide —
`[_GIT_BINARY, "-C", ...]` beside `_GIT_BINARY = "git"` in the SAME file needs
no guess, the value is an assignment two screens up.

`plan_qa/gitfacts.py:132` sat in that gap, and it was not a harmless one:

```
result = subprocess.run(
    [_GIT_BINARY, "-C", str(self._repo_root), *args],
    capture_output=True, text=True, timeout=Timeout.GIT_CONTEXT, check=False,
)
```

It carried a timeout but no `GIT_OPTIONAL_LOCKS=0`, and one of the commands it
runs is `git diff --cached`, which refreshes and rewrites `.git/index`. The
module is the plan-QA fact source, so that spawn happens at the COMMIT GATE —
the daemon taking the index lock at the precise moment the agent needs it for
the commit being gated. That is the exact failure Plan 00246 existed to remove,
surviving inside the release that claims to have removed it.

The file predates this release (Plan 00144) and was untouched by 00246's sweep,
because the sweep could only fix what the guard could see. So the changelog
sentence "an AST guard now covers all of `src/`" was false when written.

## 16:40 · decision · P4 — resolve constants, do not evaluate expressions

Widened the scanner to resolve module-level string constants only, from the
module BODY, including the annotated `Final[str]` form this codebase actually
uses. Deliberately NOT resolving an imported name or one assigned inside a
function: following either would mean crossing a file boundary or control flow,
which is where reading really does become guessing.

Proof it is calibrated rather than merely wider: run against all of `src/` it
returns exactly one spawn — the real one — and no false positives.

Task 4.4 left open: an import-graph check ("does this module import subprocess
at all?") would be strictly stronger than matching call shapes, and would not
need a constant resolver. Not rushed into a release.
