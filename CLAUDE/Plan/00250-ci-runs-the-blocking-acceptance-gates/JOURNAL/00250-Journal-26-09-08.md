## 04:25 · finding · T2.1 — a CI install must not pass `--force`, and the reason is this plan's own subject

Went to measure the remaining unknown from the entry above: the footprint of a
full `--self-install`, as opposed to `regenerate-docs`. Ran it in a disposable
worktree with `--force`, which is the flag that looks obviously right for an
unattended CI step. Two things came out of it, and the second is the important
one.

**The worktree could not run it, for a reason CI will not hit.**
`validate_installation_target` walks `project_root.parents` looking for
`<parent>/.claude/hooks-daemon` and refuses if it finds one. A worktree under
`/workspace/untracked/` has `/workspace` as a parent, so it refused. A runner
checking out to `/home/runner/work/X/X` has no such parent and passes. So this
is a local-probe artefact, not a CI blocker — but it does mean the install
cannot be rehearsed from inside this repo, and that is worth knowing before
someone else tries the same thing.

**`--force` would silently replace this project's configuration.** Reading the
call sites instead: `create_settings_json` (line 690) and `create_daemon_config`
(line 768) both begin `if <file>.exists() and not force: return`. So the
existence check is the whole protection, and `--force` removes it. Both files
are tracked here, and both carry far more than the installer's template writes:

- `.claude/settings.json` — the template emits only `statusLine` and `hooks`.
  The tracked file also carries `plansDirectory` (required by
  `R-MARKDOWN-PLAN-SYNC`), a `permissions.deny` block guarding `/tmp`,
  `/var/tmp` and `/dev/shm`, `enableArtifact: false`, and the statusLine's
  `refreshInterval`. All four would be dropped.
- `.claude/hooks-daemon.yaml` — 1188 lines with 128 `enabled: true` handlers,
  replaced by the default template.

The last one lands directly on this plan's thesis. Plan 00250 exists to stop
blocking acceptance gates from passing invisibly without a daemon. An install
step with `--force` would give them a daemon — running a DIFFERENT handler set
from the one the project ships. The gates would go green against a
configuration nobody uses. That is a worse failure than the skip this plan is
fixing, because a skip at least leaves a trace in the output.

Without `--force`, both files already exist in a CI checkout, both writes are
skipped, and the tree stays clean. So the constraint for Task 2.1 is specific
and easy to state: **install without `--force`**, and it is precisely the flag
an unattended workflow step invites you to add.

Separable from this plan, and being checked for an existing plan before
anything is filed: `--force` discards project configuration with no warning, no
diff and no backup, and the `/hooks-daemon install` skill documents it only as
"Force reinstall over existing".

## 05:10 · finding · T2.4b — the `nc -U` hypothesis was wrong, and the task's own caution is what caught it

Task 2.4b carried an explicitly flagged **unverified hypothesis**: that
`test_relay_guard_fail_open.py` fails on a runner because the runner's `nc`
lacks `-U`. It also carried an instruction to confirm before fixing. That
instruction earned its keep — the hypothesis was wrong on both counts. Not a
provisioning gap, and nothing to do with `nc`.

**What the failure actually said.** Pulled the log from the last CI run that
completed rather than reasoning about it. `assert result.returncode == 0`
passed and `elapsed < 5.0` passed; only `server.received is not None` failed.
So the forwarder ran fine and fast — nothing timed out, nothing errored. A
missing `nc -U` would have looked similar, but so would a socket bound in the
wrong place, and the test's own comment names the second possibility.

**The cause.** The test computed its socket suffix as:

```python
hostname_suffix = "-" + os.environ.get("HOSTNAME", "localhost").lower().replace(" ", "-")
```

Both real implementations resolve in three rungs — `$HOSTNAME` →
`socket.gethostname()` → `"localhost"` (`init.sh:345-357`,
`paths.py:_resolve_hostname_from_env`). The test has only the first and last.
And **bash populates `$HOSTNAME` as a shell variable without exporting it**, so
on a runner `init.sh` resolved a real OS hostname via its `hostname` rung while
the test's Python saw no `HOSTNAME` at all and fell to `"localhost"`. The server
bound `events-localhost/`, the nc rung dialled `events-fv-az…/`, and the
assertion that failed mentioned no hostname anywhere.

Invisible in every dev environment here, because Docker exports `HOSTNAME`.
Checked: locally `os.environ["HOSTNAME"]` and `socket.gethostname()` are both
`199aeb5410ac`, so the two paths agree by accident.

**Reproduced locally in one command**, which is the part worth carrying
forward — the plan assumed this needed a runner:

```
env -u HOSTNAME pytest tests/integration/test_relay_guard_fail_open.py
→ 1 failed, 10 passed   (same assertion, same file)
```

Same shape as Task 1.1's `git worktree` trick: name the one property of the
runner that differs and reproduce just that, instead of buying an 11-minute
round trip. Two for two now.

**Fixed** by calling `paths._get_hostname_suffix()` — the helper whose own
docstring says every site that needs "what host am I" MUST call it so bash and
Python agree. Passes with `HOSTNAME` set and unset. The run also drops 10.4s →
0.4s, because the nc rung now connects instead of waiting out a timeout; the
old duration was itself evidence nobody read.

**Guarded the class, because the near-miss is instructive.**
`test_hostname_suffix_parity.py` already existed and already pinned bash against
