## 04:30 · action · T2.4a — two of the three were never about the daemon

Corrects my 04:07 entry, which lumped all three files under "the same missing
dependency". Two of them turned out to need no daemon at all, and both were
fixed with a test that reproduces the CI condition HERE rather than requiring a
push to observe.

**`test_deployed_skill_trees.py`** — the mechanism, reproduced in a scratch
repo before touching anything:

```
pattern: /hooks-daemon/          (trailing slash = DIRECTORY-ONLY)

A) git check-ignore .claude/hooks-daemon             (absent)  -> NOT ignored
B) git check-ignore .claude/hooks-daemon/README.md   (absent)  -> IGNORED
C) git check-ignore .claude/hooks-daemon             (present) -> IGNORED
```

(A) is CI. (C) is this container. The assertion passed here for the single
reason that a deployed install happens to exist, so the guard was testing its
own environment rather than the pattern it names. (B) is the fix: ask about a
path INSIDE the directory and the answer stops depending on the directory being
there.

**`test_forwarder_socket_stdin.py`** — `HOOKS_DIR = Path("/workspace/.claude/hooks")`.
The forwarders are tracked and not gitignored, so they exist on every checkout,
just not at `/workspace`. Now derived from `__file__`. The status-line payload
also carried a literal `/workspace` as `workspace.current_dir`; that is now the
real checkout root, which is closer to what Claude Code actually sends.

Both fixes ship with a test that would FAIL on the old code for CI's reason —
the skill-trees one builds a throwaway repo with the real `.claude/.gitignore`
and no deployed clone, so the runner condition is reproducible on a laptop.

That is 6 of the 9 CI failures (3 files x 3 interpreters -> 2 files x 3).

## 04:07 · finding · T2.1 — the regenerated doc does go dirty, by one date line

(Later than the 06:27 entry above despite the smaller number: the container
clock moved backwards between them. `date` reads 04:07 as this is written.
Ordering in this file is by position, not by the timestamps.)

The 05:52 entry justified deferring Task 2.1 partly on this: a CI self-install
"regenerates `.claude/HOOKS-DAEMON.md` and the `<hooksdaemon>` block in
`CLAUDE.md` — both tracked — inside a job that also runs `black`, `ruff` and
the docs checks over the same tree." I wrote that as a fact without measuring
it. Measured now, and the answer is neither what I asserted nor what I first
"corrected" it to.

Three measurements:

1. **Neither artefact carries environment-specific content.** `grep -c
   /workspace` is **0** in both `.claude/HOOKS-DAEMON.md` and `CLAUDE.md`. So
   the machine that generates them does not leak into them, which was the
   mechanism I originally had in mind. That part was wrong.

2. **`.claude/HOOKS-DAEMON.md` still regenerates dirty**, because its header
   carries a generation DATE:

   ```
   -> Generated on 2026-09-07 (v3.62.1) by `generate-docs`
   +> Generated on 2026-09-08 (v3.62.1) by `generate-docs`
   ```

   One line, deterministically, on any day after the file was last committed.
   `CLAUDE.md` is byte-identical — the `<hooksdaemon>` block carries no date.
   So the OUTCOME I flagged is real; I had just named the wrong cause.

3. **The dirty line is inert.** `qa.yml` has no `git diff --exit-code` or
   `git status --porcelain` cleanliness assertion anywhere, and its
   `black --check src/ tests/` does not cover `.claude/`. The three QA scripts
   that read the generated doc — `check_doc_truth.py`,
   `check_handler_reference.py`, `measure_instruction_footprint.py` — parse
   handler content, not the header.

So Task 2.1's dirty-tree question resolves to: yes it goes dirty, no it does
not currently break anything, and the fix if that ever changes is a one-line
exclusion rather than a redesign of where the install lives.

Scope limit worth stating, because it is the part still unmeasured: this
measures `regenerate-docs`, not a full `--self-install`. An install deploys
files and creates a symlink as well, and may dirty more than one line. What is
settled is the specific hazard the 05:52 entry named; the install's own
footprint is not.

The tell, both times, was asserting a mechanism in confident detail without
running the command that would confirm it. The first correction repeated the
mistake in the opposite direction — "byte-identical" was also a guess, and
`sha256sum` before/after refuted it in one shot.
