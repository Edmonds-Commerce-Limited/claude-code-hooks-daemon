### N1 — `hookEventName: "Unknown"` is not a valid event name (fixed at `48a9ff74`)

`init.sh`'s `emit_hook_error()` takes an event name as `$1` and embeds it
verbatim in `{"hookSpecificOutput": {"hookEventName": $event, ...}}`. Three
call sites pass the literal string `Unknown`, and the function's own default is
`${1:-Unknown}`:

| line | error type                   |
| ---- | ---------------------------- |
| 265  | `init_path_error`            |
| 285  | `nested_installation`        |
| 323  | `hooks_daemon_repo_detected` |

Claude Code validates `hookEventName` against a closed enum (`PreToolUse`,
`UserPromptSubmit`, `UserPromptExpansion`, `SessionStart`, `Setup`,
`PreModelSwitch`, …). `Unknown` is not in it, so the response fails schema
validation and is thrown away wholesale.

The consequence is the inverse of what the code intends. `emit_hook_error` is
documented as **CRITICAL: This ensures the agent sees errors and can take
action** — and on these three paths it guarantees the agent sees nothing. The
carefully-worded remedy text is discarded along with the envelope. What the
human gets instead is a raw JSON blob in the status-line area and a
`SessionStart:startup hook error` banner, neither of which names a cause.

Reproduction: clone this repository fresh and start an agent in it.

The fix must supply a REAL event name rather than substituting a valid-looking
one — mislabelling a `PreToolUse` failure as `SessionStart` would trade a
visible error for a silent misroute. The wrappers already know their own event
(`.claude/hooks/session-start` passes `"SessionStart"` correctly to its own
`emit_hook_error` call); only the guards that run at `source` time, before the
wrapper reaches its body, lack it.

### N4 — the remedy names an interpreter that is not installed (fixed at `48a9ff74`)

The `hooks_daemon_repo_detected` message ends with:

> To install for development, run: `python install.py --self-install`

The flag is correct — `install.py --help` confirms `--self-install`. The
interpreter is not. Bare `python` is absent from this container's `PATH`
(`python3` is present), and it is absent by default on modern Fedora, Debian 12+
and Ubuntu, none of which ship an unversioned `python` without an explicit
compatibility package. `install.py`'s own shebang is `#!/usr/bin/env python3`.

So a reader who follows the instruction verbatim gets `command not found`, which
reads as a broken repository rather than a wrong instruction.

Minor in isolation and compounding badly in sequence: N2 sends the reader here,
N1 stops them ever seeing the sentence, and if N1 is fixed so they finally read
it, N4 is what they hit next. Swept for the same `python ` spelling elsewhere in
user-facing output rather than fixing just the one line.

## 13:20 · finding · N12 — a CONDITIONAL input field is invisible in the vendored contract, and it produced a wrong answer

Found by getting it wrong. Asked whether `PreToolUse` carries agent identity —
the fact that decides whether GitHub issue #14 is buildable — I checked
`contracts/claude-code-hooks/PreToolUse.json`'s `input_example` keys and
grepped every contract file for `agent_id`. Both said no. I reported "still
blocked" to the owner. A sub-agent said the opposite, and the sub-agent was
right.

**The raw upstream docs say `PreToolUse` DOES carry it** (`untracked/hooks-raw.md`,
the v2.1.272 body this session's refresh verified by sha256):

- line 267: "tool events such as `PreToolUse` and `PostToolUse` fire the same
  configured hooks as in the main conversation, and the input carries the
  `agent_id` and `agent_type` common input fields that identify the subagent";
- line 767: "`agent_id` — Present only when the hook fires inside a subagent
  call. Use this to distinguish subagent hook calls from main-thread calls."

**Why the contract could not show it, and why that is nobody's mistake.**
These two fields sit in their own table, introduced by "When running with
`--agent` or inside a subagent, two additional fields are included" — separate
from the main common-input-fields table. They are CONDITIONAL. A vendored
`input_example` for `PreToolUse` depicts a main-thread call, where `agent_id`
is absent *by definition*. So the example is correct and complete for the case
it shows, and silent about a field that exists.

**The trap is the project's own reading convention.** `Elicitation.json`
records, correctly, that "the common-fields table makes the per-event example
authoritative ('Not all events receive this field. Check the JSON example in
each hook event section')." That rule is right for an UNCONDITIONAL field —
absent from the example means not delivered. Applied to a CONDITIONAL field it
produces a confident false negative, which is exactly what it produced here.

The contract has no way to express "may arrive, under this condition". It has
`input_example` and nothing else, so a field that is real but situational
cannot be distinguished from one that is not delivered at all. That is the
gap: not a wrong fact recorded, but a true fact with no slot to live in.

Worth fixing because the failure mode is silent and confident. Options, in
rough order of cost: a `conditional_input_fields` block per event naming the
field and its condition; or a note on the events that receive one. The first is
checkable, the second is not.

Scope note: `agent_id`/`agent_type` are the known instance, but the fix should
be the SLOT, not a special case for these two — `permission_mode` and
`scratchpad_dir` are also documented as conditionally absent, and the same
reading convention would mislead about them in the other direction.

### N12 — what the slot is, and what it deliberately omits (Task 1.15)

`conditional_input_fields` maps a field name to the CONDITION under which it
arrives. Two kinds of entry live there, and the condition text says which: a
field ABSENT from the example that may arrive (`agent_id`, `agent_type`), and
a field PRESENT in it that may be absent at runtime (`prompt_id`,
`scratchpad_dir`, `effort`). Both mislead a reader treating the example as a
schema, in opposite directions.

Three properties are enforced by `check_input_contract.py` rather than left to
convention:

- A name with no condition is REJECTED. "May arrive" without "when" is not a
  contract and leaves the next reader guessing, which is the entire failure.
- The declaration is PER-EVENT. Upstream says outright that not all events
  receive `permission_mode`, so a field declared conditional on one event must
  not become known on every other — `Elicitation` would stop reporting a read
  of a field its own notes record as undelivered.
- A declared field counts as KNOWN, so a legitimate read needs no
  `INPUT-ALLOWLIST.yaml` entry. An allowlist entry records a known GAP; a
  documented conditional field is not a gap, and filing it as one would
  misrecord a fact as a deficiency.

`permission_mode` got no entry, contrary to the task's original wording.
Upstream resolves it by telling you to check each event's JSON example, so the
existing per-event-example convention already gives the right answer there.
The slot exists for what the example CANNOT say; adding a field the example
CAN say would dilute it.

An event with an EMPTY example stays empty even if it declares conditional
fields. Such an event has no substrate and is skipped by the superset rule;
synthesising a known-set from the conditional slot alone would start checking
its reads against a fragment, which is worse than not checking them.

`SubagentStop` was the case that clarified the boundary: it carries `agent_id`
and `agent_type` UNCONDITIONALLY — the event only ever fires for a subagent —
so they belong in its `input_example`, not in the slot. `Stop` is the mirror
image, and its entry records why: a session-wide `--agent` makes `agent_type`
present on a MAIN-THREAD stop, so `agent_type` alone does not mean "in a
subagent". `agent_id` does. That distinction is the one an orchestrator-only
handler (GitHub issue #14) would be built on, and it is exactly the kind of
thing the old contract shape had nowhere to record.

### N13 — how the false verdict was found, and why the suite could not find it (Task 1.16)

Found while reading `untracked/qa/sensitive_content.json` to check on an
in-flight QA run. It said `passed: false, total_violations: 1,
files_scanned: 1`, naming a file under `/tmp/pytest-of-root/pytest-25/` whose
NAME matched the secret word list. I reported that the repository had a
sensitive-content violation. It does not: running the scanner directly gives
`No sensitive-content violations found (3514 files scanned)`.

The mechanism is one line. `--json` wrote `_OUTPUT_FILE` — a module constant
pointing at the repo artefact — regardless of `--path`. So a scoped scan's
verdict was published as the repository's verdict. Twenty tests in
`test_check_sensitive_content.py` run the real script with `--json --path
<tmp_path>`, and one deliberately creates a file named with a blocked term to
exercise exactly that detection. A plain `pytest` run therefore leaves the
artefact asserting a violation that does not exist, with no error anywhere.

Two harms, and the second is the one that bit:

1. The tests read the shared repo path BACK to get their own result, so every
   one of them depended on a file the whole QA suite also writes. Concurrent
   runs would cross-contaminate.
2. The artefact is what `llm_qa.py` exists to produce for an agent to consume.
   A wrong verdict there is not noticed as wrong — it is read as fact. It was.

Why the suite never caught it: every check passed. `sensitive_content` reported
green on its own run, and nothing compares a verdict against the SCOPE that
produced it, so "1 file scanned" sitting in a repository-wide artefact raised
nothing. This is the class of defect the dogfooding rule exists for — it
surfaced by using the tool, not by testing it.

The fix keeps the scoped verdict (the caller did ask for `--json`) but writes
it beside what was scanned. The RED test pins both halves: the repo artefact is
byte-identical across a scoped run, AND the scoped verdict still lands. Pinning
only the first would be satisfied by silently dropping the output.

### N14 — the playbook generator ignored configured options (Task 1.17)

Surfaced by the full QA run: 19 acceptance failures and 3 smoke probes, all but
one traced to a STALE DAEMON (the freshness guard doing exactly its job after a
session of `src/` edits). The restart cleared 18. The survivor was real:

    #155 AskUserQuestionBlockerHandler: denied, but for a reason that does not
         match ['ASKING BECAUSE:']
    #156 AskUserQuestionBlockerHandler: expected allow, observed deny

First read, that looks like the handler misbehaving. It was not. The daemon was
right — `mode: unattended` denies every question, which is the mode's entire
purpose — and the PLAYBOOK was wrong, still declaring the strict-mode probes.

`PlaybookGenerator._collect...` did `instance = handler_class()` and read
`handler_config` only for `enabled` and `priority`. The configured `options`
never reached the instance, so `get_acceptance_tests()` always answered for
DEFAULT options. The registry applies them at dispatch time via
`setattr(instance, f"_{key}", value)`; the generator simply did not.

Two fixes, because there were two defects stacked:

1. `get_acceptance_tests()` was not mode-aware, though `get_rules()` already
   was. Same reasoning, sharper consequence: `get_rules()` publishes prose into
   CLAUDE.md, where being wrong misleads a reader; `get_acceptance_tests()` is
   DISPATCHED against the live daemon, where being wrong fails a test and
   accuses the handler.
2. The generator did not apply configured options at all — the general defect.
   Fixing only (1) would have left every future option-switched handler with
   the same trap, and fixing only (2) would still have declared strict probes,
   because the handler had no unattended declarations to give.

Scope held deliberately: option INHERITANCE (`shares_options_with`) is not
reproduced in the generator. It needs the registry's two-pass collection across
every handler, and no handler today both inherits options and varies its
declared tests by one. Recorded here rather than silently omitted.

Worth noting what did NOT find this. Every unit test passed throughout; the
handler's own tests cover unattended mode thoroughly. The gap was between two
declarations of the same behaviour, and only a live dispatch of one against the
other could see it. That is the argument for the acceptance harness existing.
