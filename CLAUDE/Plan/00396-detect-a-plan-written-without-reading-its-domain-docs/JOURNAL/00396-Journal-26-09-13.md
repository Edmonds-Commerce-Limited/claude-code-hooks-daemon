## 15:40 · finding · — — the read-tracking primitive already exists

Checked feasibility BEFORE designing, deliberately, given that this plan is
about designing before checking.

`write_clobber_guard` already keeps `session id -> paths whose contents this
session has seen`, bounded by explicit caps, with an `<no-session-id>` bucket
for payloads carrying no id. So the hard part of the proposed handler — knowing
what a session has read — is shipped and proven.

One subtlety to carry over rather than rediscover: that handler deliberately does
NOT record a `Read` that was DENIED. The agent never saw those bytes, so it must
not count as grounding.

## 15:41 · thought · — — what is NOT detectable, recorded so it is not re-attempted

The sharpest description of the real failure is "generalised from one sample" —
probing one deployment mode and treating it as the model. There is no mechanical
signature for that: a probe that samples the environment looks identical whether
or not its result is being over-generalised.

Likewise "disproportionate design" needs the right answer in order to spot the
wrong one, which is the thing being got wrong.

So the plan targets the narrow, mechanical proxy — an unread DOMAIN — and says
plainly in its Non-Goals that it detects ungrounded plans, not wrong ones. A plan
can cite every relevant document and still be wrong, and an agent can `Read` a
file without absorbing it. Overclaiming here would make the handler feel like a
guarantee it cannot provide.

Also rejected: the zero-config option of inferring owning docs from paths the
plan mentions. It is the tempting answer and it would have failed on the actual
incident — the first revision of Plan 00395 cited `controller.py` and
`metadata.py` accurately while never naming an install doc at all.
