# Hooks Daemon Upgrade Issue Report

**Date**: 2026-05-01
**Upgrade**: v2.26.0 → v3.9.1
**Environment**: Container (Podman/YOLO mode), Fedora Linux 6.19.14, Python 3.11.2, uv installed
**Project**: example-org/ai-tools (`/workspace`)
**Outcome**: Eventually succeeded via workaround (direct `install_version.sh` invocation)

---

## Executive Summary

Upgrading the hooks daemon from v2.26.0 to v3.9.1 via `/hooks-daemon upgrade` failed through
multiple cascading failure modes. The primary root cause is **stale skill wrapper scripts**:
the skill scripts deployed at v2.26.0 hardcode the legacy venv path
(`untracked/venv/bin/python`) which was retired in v3.7.0 in favour of fingerprint-keyed
venvs (`untracked/venv-py311-XXXXXXXX/`). This made the upgrade's venv resolution fail before
any real work could begin, and the fallback force-reinstall path had a separate
`verify_venv` failure on this container's overlay filesystem.

**User's hypothesis (correct)**: The skill scripts should fetch the LATEST versions from
upstream GitHub before orchestrating the upgrade, rather than running whatever version was
deployed at install time.

## Root Cause Analysis

### Problem 1: Stale skill scripts hardcode retired venv path

**Files affected (old content)**:

- `.claude/skills/hooks-daemon/scripts/daemon-cli.sh` — `PYTHON="$DAEMON_DIR/untracked/venv/bin/python"`
- `.claude/skills/hooks-daemon/scripts/health-check.sh` — same hardcoded path

**Timeline**:

- v3.7.0: Daemon migrated to fingerprint-keyed venvs (`venv-py311-XXXXXXXX`)
- v2.26.0: This project was still running — skill scripts shipped at that time still
  used the old path
- v3.9.1: Skill scripts updated to use new `_resolve-venv.sh` helper

**Effect**: Any skill script operation (including the health check) would fail with
"Python not found" on any install ≥ v3.7.0 that had been set up fresh (no legacy venv).
The upgrade flow did NOT fail due to this directly, but the health-check script was
broken the whole time we were on the old version.

**New v3.9.1 skill scripts** use `_resolve-venv.sh`:

```bash
# shellcheck source=_resolve-venv.sh
source "$(dirname "$0")/_resolve-venv.sh"
```

This dynamically resolves the venv Python by scanning `untracked/venv-*/bin/python`.

### Problem 2: upgrade_version.sh requires a valid existing venv

The Layer 2 upgrader (`upgrade_version.sh`) calls `resolve_existing_venv_python`
at the very start (before `UPGRADE_STARTED=true`). This function requires one of:

- A `venv-*/` directory with `.daemon-metadata.json` (v3.7.0+ format)
- The legacy `untracked/venv/` path (exact legacy path)

Upgrading from v2.26.0 had a plain `untracked/venv/` but it had `.daemon-version`
(the v2.x stamp format) and lacked `.daemon-metadata.json`. The resolver skips
these as "legacy-stamped but needs rebuild via ensure_venv".

This creates a **bootstrapping paradox**: you need a valid venv to run the upgrade
that would create the valid venv.

### Problem 3: verify_venv race condition on overlay-fs

When `--force` install creates the venv via `uv sync` with `UV_LINK_MODE=copy`
(the hardlink retry fallback used on container overlay-fs), `verify_venv` fails
immediately after. The `sync -f "$venv_path"` call is intended to flush but appears
insufficient on this Podman overlay-fs.

This is a separate issue from Problems 1 and 2. It was bypassed by the workaround
(venv already existed from a previous attempt).

### Problem 4: write-venv-metadata stores wrong python_path

After installation, `ensure_venv` calls `write-venv-metadata` to write
`.daemon-metadata.json` into the venv directory. This file is the source of truth
for `paths.py resolve-venv` (used by `_resolve-venv.sh` in skill scripts).

The metadata written contained:

```json
{"python_path":"/usr/bin/python3.11", ...}
```

But the correct venv Python is:
`/workspace/.claude/hooks-daemon/untracked/venv-py311-66bbc57c/bin/python`

`sys.executable` inside the venv correctly returns the venv path — so
`write-venv-metadata` is not using `sys.executable` to populate `python_path`.
It appears to store the system Python used to invoke the `write-venv-metadata` CLI
command rather than the venv's own Python.

**Effect**: `paths.py resolve-venv` reads `python_path` from metadata and returns
`/usr/bin/python3.11`. `_resolve-venv.sh` sets `PYTHON=/usr/bin/python3.11`.
`daemon-cli.sh` then fails with `ModuleNotFoundError: No module named 'claude_code_hooks_daemon'` because the system Python has no venv packages.

**Fix applied**: Manually edited `.daemon-metadata.json` to set the correct
`python_path`:

```json
{"python_path":"/workspace/.claude/hooks-daemon/untracked/venv-py311-66bbc57c/bin/python", ...}
```

After this fix, `paths.py resolve-venv` returns the correct path, `daemon-cli.sh`
works, and the `/hooks-daemon restart` skill command functions correctly.

### User Hypothesis Validation

> "I wonder if the problem is in using skill scripts which are not up to date instead
> of pulling latest stuff from remote, then using those remote scripts?"

**Confirmed correct for Problem 1**. The skill scripts in `.claude/skills/hooks-daemon/`
are deployed ONCE at install time and only updated when the daemon successfully upgrades.
If the upgrade fails, the skill scripts remain stale indefinitely.

A safer design would be for the skill `upgrade.sh` to:

1. First fetch the LATEST `upgrade.sh` from GitHub (the daemon does this for `install.sh`)
2. Use that fresh script to orchestrate the upgrade

This is similar to how the daemon's own `install.sh` downloads the latest installer
script from main before running. The upgrade wrapper does NOT do this — it delegates
directly to the already-deployed `$DAEMON_DIR/scripts/upgrade.sh` which is versioned
alongside the installed code.

## Recommendations for Upstream

### High priority

1. **Skill wrapper should fetch latest upgrade.sh from GitHub before running**
   (mirrors how install.sh works — downloads fresh from main first). This ensures
   stale skill scripts cannot block upgrades.

2. **upgrade_version.sh bootstrap paradox**: When no valid venv exists (e.g., upgrading
   from a major version that used a different venv format), `upgrade_version.sh` should
   fall back to `ensure_venv` to CREATE a fresh venv rather than aborting. The current
   design assumes a valid venv always exists for the upgrade bootstrap.

3. **uv.lock cleanup**: The installer should ensure `uv.lock` is either in `.gitignore`
   for the daemon directory, or is explicitly cleaned up before git checkout operations.

### Lower priority

4. **write-venv-metadata stores wrong python_path**: The `write-venv-metadata` CLI
   command writes `python_path` as the system Python (`/usr/bin/python3.11`) rather
   than the venv Python. Since `paths.py resolve-venv` reads this field to determine
   which interpreter to return, skill scripts end up using the system Python and fail
   with `ModuleNotFoundError`. The fix: `write-venv-metadata` should store
   `sys.executable` (the calling interpreter's path) as `python_path`, or `paths.py`
   should construct the venv Python path from `venv_path/bin/python` rather than
   relying on the stored `python_path` field.

5. **verify_venv race on overlay-fs**: The `sync -f` call after `uv sync` with
   `UV_LINK_MODE=copy` may not be sufficient on Podman overlay-fs. Adding a small retry
   loop or an alternative flush mechanism would improve reliability.

6. **health-check.sh bug**: The health check script does not consistently use `$PYTHON`
   (the resolved venv Python) for all daemon CLI invocations.
