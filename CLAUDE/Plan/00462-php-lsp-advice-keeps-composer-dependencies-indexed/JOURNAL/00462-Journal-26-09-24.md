## 13:46 · finding · —   — Task 1.1: only PHP is affected

Task 1.1 conclusion, per-language, each verified against the tool's own docs
(fetched live, not assumed):

- **Python (pyright)**: `exclude` only changes which files are treated as
  project ROOT files for checking. Verbatim from
  `microsoft/pyright` `docs/configuration.md`: "Note that files in the
  exclude paths may still be included in the analysis if they are referenced
  (imported) by source files that are not excluded." So excluding
  `**/.venv`/`**/venv`/`**/vendor` never removes import resolution - not
  affected.
- **TypeScript/JavaScript (tsserver)**: identical shape. Verbatim from the
  TypeScript website's `tsconfig-reference` `exclude.md`: "exclude only
  changes which files are included as a result of the include setting... It
  is not a mechanism that prevents a file from being included in the
  codebase - it simply changes what the include setting finds." `node_modules`
  resolution via `import` is unaffected by `exclude` - not affected.
- **PHP (intelephense)**: verified against `bmewburn/intelephense-docs`
  `gettingStarted.md`: `files.exclude` "configure glob patterns to exclude
  certain files and folders from all language server features" and the
  surrounding prose says these are files you "do not want [] indexed by
  Intelephense" - this is the INDEX, the structure intelephense resolves
  types from, not a diagnostics-only filter. Its own default list proves the
  point: it excludes only `**/vendor/**/{Tests,tests}/**` and
  `**/vendor/**/vendor/**`, never the whole of `**/vendor/**` - Composer's
  own maintainer-authored defaults keep the dependency tree indexed. This is
  the one language genuinely affected - confirmed root cause, in scope.
- **Go (gopls)** and **Rust (rust-analyzer)**: neither strategy ever asks for
  an any-depth (`**/name`) entry at all - `exclude_finding()` in both
  `go_strategy.py` and `rust_strategy.py` filters `required` down to
  `plain_trees` (`not r.startswith("**/")`) before using it, so
  `CORE_VENDORED_BUILD_DIR_NAMES` (including `vendor`) never reaches either
  language's finding. Not affected - confirmed no equivalent defect exists,
  by reading the source rather than assuming symmetry with PHP.

Scope conclusion: only `php_strategy.py` needs the fix. Sources fetched into
`untracked/scratch/` this session (gitignored, not committed):

## 14:29 · decision · —   — Task 1.3/1.4: table-driven substitution, full QA green

Implementation (Task 1.3): `php_strategy.py` gained a table-driven
substitution, kept entirely inside the PHP strategy (the handler and
`required_excludes()` stayed language-free, per the module's CLAUDE.md edit
guards):

- `_DEPENDENCY_ROOT_REPLACEMENTS`: `{"vendor": (nested test glob, nested vendor glob)}` - PHP's declaration of which shared required name is a
  dependency root, and what to ask for in its place.
- `_substitute_dependency_roots(required, replacements)`: swaps a bare
  `**/<name>` for its replacements when `<name>` is a key in `replacements`;
  everything else in `required` passes through unchanged.
- `_harmful_root_excludes(present, replacements)`: flags a present override
  entry that excludes an entire declared root outright (`vendor`,
  `**/vendor`, `**/vendor/**`), keyed off the same table.
- `exclude_finding()` now reports two independent things: entries still
  missing (as before) and entries that are harmful (new) - both can appear
  together, since a harmful blanket exclude also happens to satisfy the
  nested-entry coverage check via prefix matching.

Both functions take the replacements table as an explicit parameter (not a
closed-over module global) specifically so a test could prove the mechanism
is table-driven rather than a `"vendor"` string special case, by calling
them directly with a fabricated table (Task 1.2's fourth RED test).
