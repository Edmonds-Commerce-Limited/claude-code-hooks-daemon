### Why the folder is archived rather than deleted

`PROPOSAL-ASSESSMENT.md` is the durable output. 00213's owner reviewed it and
reported it "matches my own read almost exactly", adopting every integration
finding:

- mode `0644`, not `0755` — the library is **sourced**, not executed, so
  reusing `_MKPLAN_MODE` (`install/plan_workflow.py:24`) would ship a
  misleading execute bit
- add the library to `_EXPECTED_ROOT_FILES` (`plan_qa/model.py:306-314`), or
  the SessionStart sweep flags the deployed file as a stray root file in every
  client project, every session
- daemon-owned, overwritten every upgrade — a client-owned copy re-creates the
  per-copy divergence the proposal exists to eliminate
- no default for `root_marker`; neutral config examples instead of the
  proposal's Ansible/`shellscripts/` flavour
- assert **empty stderr** from `bash -n`, which exits 0 while printing
  diagnostics
- defer `plan_script_qa` — nothing here to gate

They also accepted §7.1's objection: this repo has no orchestrator scripts, so
the library cannot be genuinely dogfooded here. Their stated response is to say
so plainly rather than fabricate a use — which is the right answer, and better
than the mitigation this plan proposed.

### Process note for the plan system

Two plans covering one proposal, five days apart, neither aware of the other,
is not an agent mistake — it is a **gap in the plan workflow**. Nothing warns
an author that an existing plan already targets the same source document.

The daemon already has the machinery: `plan_qa` parses every `PLAN.md` in the
tree at sweep time. A check for "two active plans citing the same source
document or proposal file" would have caught this on the day 00213 was created.
Worth raising as a candidate `plan_qa` rule; not opening a plan for it from
inside a plan being closed.
