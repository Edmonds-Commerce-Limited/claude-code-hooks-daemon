## 21:10 · finding · N1/N2 — the reported symptom and the real defect are two different things

The owner reported that supervisor compacts had stopped working, and asked
whether moving ccy into tmux had caused it. Investigated rather than answered
from the shape of the question, and the two parts came apart.

**tmux is not in the path.** Process ancestry INSIDE the container:

```text
1       tini -- entrypoint.sh claude --dangerously-skip-permissions --continue
2       python3 .claude/ccy/claude-supervise.py --arm -- claude …   <- PTY host
83      claude --dangerously-skip-permissions --continue            <- its child
940924  bash (tool shell)
```

`TMUX`/`TMUX_PANE` unset, no tmux server socket. Any tmux wraps the container's
stdio from OUTSIDE, so it never sits between the PTY host and its child.

**Auto-compaction is healthy, and the threshold explains the symptom.** The host
runs `--arm`, the worker is alive, and the sidecar is being written
continuously (`seq 16387`, ts moving). Its reading:

```json
{"red": false, "critical": false, "compact_urgent": false, "tier": "yellow",
 "pct": 24.0, "window_size": 1000000}
```

RED for a 1M window is 40% (`context_tiers.py:51`); the session is at 24%.
Nothing to fire on. On a 200k window red is 76% — 152k tokens of context —
against 400k here, so a session now runs roughly 2.6x longer between automatic
compactions with nothing having been misconfigured.

**The real defect is the opposite failure, and it is in the other direction.**
Reading the worker diagnostic log to check the above surfaced N1: a
Tab-completed `/compact` is never recognised, because autocomplete expands
inside Claude Code and emits no keystrokes, so the tap holds `/comp`.

Worth stating plainly, because the tempting write-up is wrong: N1 cannot cause
a MISSED compaction. Recognition exists so the supervisor DEFERS to a human
compact instead of stacking its own. Failing to recognise risks a duplicate
injection, not a suppressed one. Reporting it as the cause of the owner's
symptom would have been a satisfying answer that happened to be backwards.

## 21:11 · blocker · N1 — the fix needs a ruling, and here is why it is not obvious

The naive fix — match a `/comp` prefix — is wrong in a way worth recording so it
is not re-proposed:

- The tap sees the bytes the human typed, so it cannot know WHICH entry
  autocomplete resolved to. `/comp` + Tab is `/compact` today only because no
  other `/comp…` command exists; that is a fact about Claude Code's current
  command set, not an invariant this repository controls.
- Widening the match trades a false negative for a false positive, and the two
  costs are not symmetric. A missed recognition risks one duplicate `/compact`.
  A false recognition makes the supervisor DEFER to a compaction that is never
  coming, which suppresses real auto-compaction until the state clears.

Options, recorded without a recommendation being acted on:

1. Match the typed prefix against a list of known completions, treating an
   unambiguous single match as that command. Fixes Tab, keeps the ambiguity
   question explicit, needs maintaining when Claude Code's command set changes.
2. Stop inferring from keystrokes entirely and read the compaction fact from
   the daemon's own `PreCompact`/`PostCompact` hook record, the way Plan 00328
   made `/model` restore arm on the daemon's `.model-downgrade` signal rather
   than on typed text. Authoritative, no ambiguity, but a larger change.
3. Accept it. The cost is a possible duplicate `/compact`, which is visible and
   self-limiting, and option 2 may subsume it anyway.

Option 2 is the same shape as a ruling this project already made once, which is
an argument for it — but it is a design change, not a niggle fix, so it
graduates rather than being decided here.
