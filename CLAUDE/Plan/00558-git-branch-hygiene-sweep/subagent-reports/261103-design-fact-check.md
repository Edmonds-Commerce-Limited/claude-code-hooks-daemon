## REFUTED (most consequential first)

R1. Section 6, "Interaction with the existing stop handlers": "after `usage_pause_stop_gate` (6), `cron_stop_enforcer` (7), the release-in-progress gate and `subagent_handoff_gate` (11), and before `auto_continue_stop` (15, 10 here)".

- `subagent_handoff_gate` is a SubagentStop handler (`handlers/subagent_stop/subagent_handoff_gate.py:72`, priority 11 in `.claude/hooks-daemon.yaml:1250`), not a Stop handler. Priorities only order handlers within one event.
- For one event, "after 11 and before 10" cannot hold. On Stop in this repository the order is idle_workable_issue_stop_gate 4, goal_loop_detector 5, usage_pause_stop_gate 6, cron_stop_enforcer 7, release_blocker 8 (`.claude/project-handlers/stop/release_blocker.py:138`), teammate_reap_advisor 9, background_task_recorder 9, auto_continue_stop 10 (`.claude/hooks-daemon.yaml:1353-1377`). The only free slot before auto_continue_stop is 9.
- Defaults: USAGE_PAUSE_STOP_GATE 6, CRON_STOP_ENFORCER 7, SUBAGENT_HANDOFF_GATE 11, AUTO_CONTINUE_STOP 15 (`constants/priority.py:154,142,213,226`), which matches the numbers quoted.
- Also: the "release-in-progress gate" is a project handler in `.claude/project-handlers/stop/`, not a shipped daemon handler. A client project does not have it.
- Plan change: give the Stop guard and the SubagentStop guard separate priorities. SubagentStop: after handoff gate 11, before size blocker 15. Stop: between 8 and 10 here, and below auto_continue_stop's default 15 for clients. State that the release gate is project-local.

R2. Section 4, "The configuration optimiser (`bin/hooks-daemon optimise-checklist`, which already checks the top-level `plan_workflow` section beside the handlers)", and the proposed OPTIONAL line.

- `grep plan_workflow|OPTIONAL|optional` over `config_optimisation/areas.py`, `checklist.py` and `state.py` returns nothing. `cmd_optimise_checklist` (`daemon/cli.py:7780`) reads only `config_dict["daemon"]["languages"]` (cli.py:7817) and calls `build_checklist`.
- The only verdict tokens are PASS, WARN and FAIL (`config_optimisation/checklist.py:52-53,245-250`). There is no OPTIONAL level and no top-level-section check.
- Plan change: the optimiser needs a new section check and a new verdict level, so list it as new work. Do not describe it as an existing precedent.

R3. Section 3 route table: the git-argv parser "`sensitive_content` already uses to extract branch names (`handlers/pre_tool_use/sensitive_content.py:1496`, `:1834`)".

- Line 1496 is a docstring sentence ("denied a `git switch -c` that carried none"). Line 1834 is a user-facing guidance string. Neither is a parser.
- The handler's machinery is `_writes_git_metadata` (1457), `_metadata_commands` (1491), `_is_metadata_command` (1522) and `_GIT_METADATA_WRITE_SUBCOMMANDS` (187). It decides whether a command records metadata, then scans the text for terms. I found no function that returns the created branch name. The imports are `utils/git_commit_parsing` and `utils/git_facts`; `git_commit_parsing.py:61` lists `-c` only as a flag.
- Plan change: the creation-route parser is new work, or move something like `git_invocations` (used in `destructive_git.py:644`) into a shared utility. Fix the citation.

R4. Section 1 migration table: "`worktree-reap --base-branch` default `main` (`daemon/cli.py:12426`)".

- The `--base-branch` argument is at `daemon/cli.py:12437-12442`, with `default="main"` at 12440. Line 12426 is not it. The `--protected-ref` citation (12807) is correct (default at 12809).
- Plan change: cite 12437-12442.

R5. Section 4 and 2 wording on `%(trailers)` is correct (see V-table), but one inventory detail is wrong. Step 3's `for-each-ref --merged=<ref> refs/heads ...` also lists the default branch itself (probe output: `refs/heads/main` appears with `--merged=main`). The design's state order puts "default / integration line" first, so classification survives, but the bulk step must drop the target ref from its own result. Minor; no plan change beyond a note.
