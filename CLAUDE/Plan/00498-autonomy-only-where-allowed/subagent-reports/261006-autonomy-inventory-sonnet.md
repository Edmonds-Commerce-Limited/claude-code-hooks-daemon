# Plan 00498 Task 1.1: what DRIVES work, and what only protects

Method: searched `src/` for `CronCreate`, `cron`, `goal`, `goal-intent`, `stand-in`, `resume`, `recovery`, `rebrief` and read every handler that surfaced. A handler is a DRIVER when its output asks the session to schedule something, set or defend a goal, resume or recover work, or take on work nobody asked for in this conversation. A handler that only records, restricts, reports a fact, or asks for an explanation is a guard and is not gated.

## Settled design

- Config: top-level `autonomy:` with `environments` (any of `host`, `docker`, `podman`, `lxc`, `generic`) and `hosts` (role aliases or fnmatch globs). Default is every environment, so a project with no block is unchanged.
- Rule: autonomy runs when the session's environment is listed OR its effective hostname (`HOOKS_DAEMON_HOSTNAME`, `CCY_HOST_HOSTNAME`, system hostname, payload stamp) matches `hosts`. `host` is `detect_container_runtime()` returning None. An unrecognised runtime label counts as `generic`, never as `host`.
- An unloadable config or no `ProjectContext` keeps the default (autonomy on).
- Mechanism: `Handler.drives_autonomy` (class attribute, False for every guard). One gate in `HandlerChain`, beside the scope gate, skips a driver before `matches()`. Handlers that mix a protective part with a driving part are gated inside instead.
- Helper: `src/claude_code_hooks_daemon/utils/autonomy.py` (`autonomy_allowed`, `autonomy_verdict`, `environment_label`).
