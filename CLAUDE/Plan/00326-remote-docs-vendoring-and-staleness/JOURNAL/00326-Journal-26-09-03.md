## 11:53 · finding · T1.3/T1.6 — the tree name collided with a latent bug

Task 1.3 registered the remote tree: `documentation.trees.remote` (default
`remote-docs`), a `remote_docs_dir` axis and `is_remote_docs_path()` on
`ProjectLayout`, and a config-derived allowance in `markdown_organization`
beside the agent and human trees. `is_docs_path()` deliberately does NOT
claim the tree (D1/D12) — a test pins that, because if it did, every consumer
keyed on "is this our documentation?" would treat vendored upstream prose as
project-authored.

The axis is **defaulted and declared last** on the frozen dataclass. Making
it required broke collection across ~20 unrelated test modules that construct
`ProjectLayout` directly; defaulting it keeps the addition additive. The
default is stated in both `_DEFAULT_REMOTE_DOCS_DIR` and the pydantic model,
which is the same two-layer pattern `_DEFAULT_HUMAN_DOCS_DIR`/`default="docs"`
already uses.

**Then the interesting part.** The first allowance test PASSED, and it was
WRONG to. Two compounding causes:

1. The test wrote under `tmp_path` while `ProjectContext.project_root` was
   mocked to `/tmp/test`. `matches()` allows anything outside the project
   root, so every path was allowed and the assertion proved nothing. Fixed by
   pinning both to one root, and by adding an explicit CONTROL test
   (`test_an_unregistered_top_level_tree_is_blocked`) so a future vacuous
   pass is caught by its neighbour.
2. Underneath that sat a genuine defect. `normalize_path` matched its project
   markers as **bare substrings**, so `remote-docs/x/p.md` was rewritten to
   `docs/x/p.md` — the remote tree silently classified as the HUMAN DOCS
   TREE, which is precisely the inheritance D12 exists to prevent. The same
   flaw would fold `my-src/` into `src/`, `old-untracked/` into `untracked/`.

Fixed at root cause: markers now match only at a path-segment boundary
(position 0 or straight after `/`), via `_segment_aligned_index`, and the
remote tree is itself a marker so its absolute prefix strips correctly.
Reproduction test written first and confirmed RED
(`assert 'docs/x.com/p.md' == 'remote-docs/x.com/p.md'`), plus a companion
test that a genuine marker prefix is still stripped, so the fix cannot
regress into doing nothing. Full suite green: 14,480 passed.

Worth recording the irony for whoever revisits the naming: the tree name we
chose, `remote-docs`, is the one name that collides with the `docs/` marker.
A name like `docs_remote` would have dodged the bug by accident and left it
latent for the next person. Finding it was luck; fixing it at root cause was
not, and the fix is what makes the D12 separation real rather than nominal.

## 12:09 · action · P2 — Phase 2 complete: capture, store and CLI

Three new modules and a CLI subcommand; 103 remote-docs tests, full suite
14,536 passed. `bin/hooks-daemon remote-docs {add,list,check,refresh}` smoke-
tested against this repo for real.

`capture.py` (Tasks 2.1/2.2) is pure — URL and bytes in, content out, no
filesystem — so path derivation and provenance rendering are testable without
a tmpdir. `store.py` (2.3/2.4) owns the disk. The CLI owns argv and the only
real network call. That split is deliberate: it keeps the network at the
outermost layer, where the Non-Goal "no network I/O in any hook handler"
becomes structural rather than a rule someone has to remember.

Decisions worth recording:

- **The hash is of the RAW upstream bytes, never the written file.** Hashing
  the file would fold our own frontmatter into the digest, so every refresh
  would look like an upstream change and D4's cheap no-op path would never
  fire. There is a test naming this reasoning.
- **Refresh reads the URL out of the document.** A refresh never needs the
  caller to remember where a file came from — the provenance is the input.
  It also carries the recorded `licence` across rather than re-deriving it:
  a licence is a human judgement, and silently discarding one on refresh
  would be the same class of error as `check` writing banners.
- **`check` exits 1 for unreadable provenance as well as staleness.**
  Reporting a corpus clean while part of it cannot be parsed is the
  silence-as-success failure the whole staleness system exists to avoid.
- **An implied `index` is not "lossy".** `/docs` derives to `docs.md` and
  `/docs/` to `docs/index.md`, which cannot collide, so neither needs a hash
  disambiguator. A query or fragment does: `?v=1` and `?v=2` would otherwise
  overwrite each other silently.
- **`_stale_window_days` preserves the document's own window** across a
  refresh rather than resetting to the default, so a project that widened or
  narrowed one keeps its choice.

Deferred deliberately: `known_sources` domain→licence pre-fill (D13) needs
the `documentation.remote` config block, which is Task 3.7's work. Capture
records `unreviewed` until then and the CLI says so on every capture, so the
gap is visible rather than silent. Task 2.5 (routing captured content past
the secret-scanning surface) is still open and is the last of Phase 2.

## 12:13 · action · T2.5 — capture is scanned; Phase 2 done

A capture writes to disk from a CLI, so the `Write`-tool hook that normally
inspects content never fires. Without a guard, `remote-docs add` against an
authenticated page would vendor its secrets into the repository with no check
at all — a gap the daemon's own CLAUDE.md warns about in general terms ("a
file written through Bash is not seen by the content guards").

`SensitiveContentHandler.scan_text` is now PUBLIC and returns a reason or
None. Making it public rather than re-implementing the matching is the point:
a second copy of "what counts as sensitive" would drift from the first, and
the weaker copy would be the one guarding the newer surface. The secret-word
arm keeps the handler's own disclosure rule — it reports only an INDEX, never
the term.

`write_capture` takes the guard as an INJECTED `content_guard`, so
`remote_docs` gains no dependency on the handler package and the rejection
path is testable without any config. The CLI supplies the real one. A
rejected capture writes nothing — verified by a test asserting the tree is
still empty afterwards, because "raised but wrote anyway" is the failure that
would matter.

The guard degrades to None if the handler cannot be built, matching how the
daemon fails elsewhere; capture then proceeds unscanned. That is a deliberate
soft edge rather than an oversight — worth revisiting if it ever masks a real
misconfiguration.

Two are worth recording because the tempting answer was the wrong one. The
ratchet test is explicitly a "must not grow" list, so the fix was to write a
real near-miss ALLOW acceptance case (a markdown write OUTSIDE the tree),
not to add a line to the allowlist. And the bash-blindness register is
answered honestly as BLIND: a heredoc into `remote-docs/**` really does
bypass the gate, and the Phase 4 session sweep that would mitigate it does
not exist yet, so claiming PARTIAL would have been a lie in a file whose
whole purpose is to stop exactly that.

CLAUDE.md turned out to already contain the guidance when I went to check —
the daemon regenerates and auto-commits that block on restart, which is why
`git status` looked clean. Verified through the injector's own reader rather
than a grep, since my first grep used underscores and the marker uses
hyphens; a wrong grep reading as "absent" is how a green test gets believed
for the wrong reason.

## Agent-browser capture, and two corrections

Asked to default to agent-browser, I built it against `agent-browser read`
and justified it in code comments and a commit message by saying it renders
JavaScript. It does not. `read <url>` is an HTTP fetch plus extraction;
rendering needs `open` first. I had verified the command WORKED and inferred
WHY from its name, which is exactly the inference that should have been a
check.

The real justification is better than the one I invented: `read` negotiates
`Accept: text/markdown`, retries with `.md`, and walks ancestor `llms.txt`
paths. For vendoring documentation as markdown that beats a raw GET
outright — a docs page captured 317 KB of structured markdown where the GET
would have stored raw HTML. So the default stands; the reasoning behind it
was replaced.

The second correction came from the human: I had begun hardcoding this
container's wrapper names and pointing the fallback warning at
`.claude/ccy/Dockerfile`. This daemon installs into arbitrary projects. One
environment's container layout is not a fact about the product, and a
warning naming it is wrong everywhere else. Fixed by probing a candidate
list with `--version` — the bare name is on PATH here and exits 2, so
presence never decided usability — and by writing the warning in terms of
`agent-browser` and `PATH` only. A test now asserts the warning mentions no
specific container.

Also found by measurement rather than assumption: a `read` leaves a browser
session running, so capture must `close --all` or leak a process per fetch.
The D4 hash short-circuit survives the switch — two consecutive captures of
the same page produced an identical `source_sha256`, so `refresh` still
no-ops on unchanged upstream.

Fidelity is `converted` for every browser capture, including when upstream
served markdown and the text looks untouched: the content is extracted and
normalised, not the response body, and D3's whole point is not to overclaim
on another component's behalf.

Full suite green: 16,991 passed.

## Phase 3 closed, Phase 4 mostly already built

Task 3.7's config block was the last of Phase 3. Writing it surfaced a small
API question worth recording: `known_sources` is keyed by domain, but every
caller holds a URL. Making each call site parse the host is how two parsers
drift, so `licence_for` accepts either and lowercases, since host names are
case-insensitive. A blank licence is rejected rather than stored — an empty
string satisfies a required field while saying nothing, which is the same
failure mode `fidelity` guards against.

Phase 4 turned out to be largely done already, which is worth stating
plainly rather than re-implementing: `stale_after` is written by `add` and
`refresh` (4.2), and the TTL/pinned policies plus hash revalidation already
resolve through capture and the refresh short-circuit (4.1). The honest gap
in 4.1 is the version pin: `upstream_version` sits in the schema but nothing
populates or compares it, because no source vendored here publishes a
version to pin to. Recorded as schema-ready rather than built on
speculation.

Task 4.3 is the one that changes behaviour. It also closes, partly, the
bash-write blindness I registered as BLIND: a heredoc into `remote-docs/**`
still bypasses the write-time gate, but the sweep now reports the resulting
document as having provenance that does not parse. I deliberately did NOT
copy `contract_staleness`'s version cache — that handler caches an external
`claude --version` subprocess, whereas this one reads local files that are
cheap, and a cache there would serve a stale answer about staleness.

The report is capped at ten entries plus a total. A corpus of forty stale
documents would otherwise push every other session-start advisory out of
view, which is how an advisory system trains people to skim past it.

Full suite green: 17,023 passed.

## Phase 5: routing, and a scoping correction from the human

The lookup compares normalised `source_url` values rather than derived
paths. That was a deliberate reversal of my first instinct: deriving the
path from the URL is one stat instead of a walk, but the derivation is
LOSSY by design — it appends a digest for query strings — so two URLs that
ought to match can derive different paths. The document's own recorded
`source_url` is the authoritative answer to "where did this come from?",
and normalising both sides is the only comparison that respects that.

Normalisation is deliberately asymmetric about queries: fragments and known
tracking parameters are dropped, but an unknown query parameter is kept,
because `?version=3` is a different page. Dropping it would route someone
to the WRONG document, which is worse than not routing them at all.

Then the human corrected the scope, and the correction was right. I had the
capture hint firing on every unvendored URL once a tree existed. Most
`WebFetch` calls are not documentation — an issue, a status page, a blog
post — so that hint would have been wrong most of the time, and an advisory
that is usually wrong is one people learn to skim past. Their suggestion
(the project declares which domains are doc sources) fixes it exactly.

I reused `known_sources` rather than adding a parallel domain list. A
domain you recorded a licence for IS a domain you vendor from, and two
lists meaning nearly the same thing drift — the failure the SSoT rules
exist to prevent. Declaring a source before reviewing its licence is
already expressible: record the `unreviewed` sentinel.

One distinction worth keeping straight, and now pinned by a test:
declaration governs NUDGING, not ROUTING. A page we already hold a fresh
copy of is still denied even on an undeclared domain — we demonstrably have
the document, so the declaration adds nothing there.

A test of mine was wrong and the code was right: "reading a fresh document
is silent" failed because the capture default licence IS the `unreviewed`
sentinel, which is itself an advisory trigger. Fixed the fixture to seed a
reviewed licence, and added the case I had actually been missing — a fresh
but unreviewed document DOES advise, because an unreviewed licence is a
standing fact rather than a staleness symptom.

The `_EXEMPT_DESPITE_DENYING` guard earned its keep. It refuses to let a
deny-capable handler claim another section covers it without naming that
section, and its docstring records a case where exactly that claim was
false twice over. My exemption was initially in that shape: I claimed the
provenance section covered the routing deny, but that section only said
"check whether it is already vendored" — it never said a fetch would be
DENIED. Rather than argue the exemption, I made the section state the deny
explicitly, which is what the guard was asking for.

Full suite green: 17,072 passed.

## The index, and where it must NOT live

Task 5.2's index looked trivial until the placement question. The obvious
home is `remote-docs/INDEX.md` — and that file would have no `source_url`
of its own, so the provenance gate would deny writing it. The tempting fix
(exempt the filename) would punch a hole straight through the invariant the
whole tree exists to hold: anyone could then write arbitrary unattributed
content to that one path.

So it generates to `.claude/REMOTE-DOCS.md`, outside the tree, as an
ordinary generated artefact. A test asserts it is not written inside the
tree, so the tempting version cannot come back by accident.

Regeneration happens on `add` and `refresh` rather than on demand. An index
that silently goes stale is worse than no index — it answers "no, we don't
have that" confidently and wrongly. It renders from the TREE rather than
from what the command was asked to do, so a failed capture cannot leave the
index claiming a document that was never written; there is a test for that
too, because it is exactly the kind of bug that only shows up on a bad
network day.

Unreadable documents are LISTED with their unknown fields marked, not
omitted. An index that quietly disagrees with the tree it describes is a
second source of truth.

Full suite green: 17,087 passed.

## Phase 6 reassessed, and the gap the Success Criteria caught

Phase 6 wanted the vendored hook contract migrated onto this subsystem.
Reading the actual artefacts rather than the plan's description of them
changed the answer: the contract is 33 hand-derived JSON schemas, and
META.json records the provenance of the SOURCE DOC, which the refresh
procedure deliberately fetches to `untracked/` rather than storing. There
is nothing for this subsystem to manage.

Two things did fall out of the assessment, and both were worth having.

The refresh procedure's non-negotiable rule — RAW fetch only — is there
because a summarising fetch of that exact URL fabricated a
`permissionDecision: "escalate"` value. My D18 default records `converted`,
so the corpus never lied, but there was no way to DEMAND raw bytes.
`--verbatim` now exists.

And building it exposed that the raw GET was simply broken against real
documentation hosts: default `Python-urllib/3.x` gets 403 from
code.claude.com. The documented procedure worked because it uses curl. So
the fallback path had never been exercised against a host that cares. Fixed
with an honest identifying User-Agent — deliberately not a browser
impersonation, because a host that wants to refuse automated capture should
be able to.

Then re-reading the Success Criteria caught a real gap I had not noticed
while working phase by phase: "cannot pass the commit gate". I had only the
Write/Edit gate. That criterion is the entire answer to the bash-write hole
I had registered as BLIND and moved on from — a heredoc into the tree
reaches disk unexamined, and without a commit gate an unattributed document
enters history, where removing it needs a rewrite.

`remote_docs_commit_gate` judges the git INDEX, so the route a file took to
disk is irrelevant by construction.

Two guards corrected me while I registered it. The blindness register
refused the new handler outright — it is only for Write/Edit-keyed handlers,
and mine keys on Bash. And when I tried to upgrade the provenance handler's
verdict to PARTIAL, the precedent (`docs_qa_edit`, mitigated by its sweep)
says the verdict stays BLIND with the mitigation NAMED. That is the more
honest shape: the Write/Edit surface really is blind, and saying otherwise
because something else covers it would misdescribe this handler.

I also repeated my earlier mistake once, and caught it the same way: the
`_EXEMPT_DESPITE_DENYING` entry claimed the provenance section warns about
Bash-authored files. It did not. Rather than argue the exemption, I made
the section say it — which also makes the guidance better, since an agent
now learns there is no gap to exploit rather than inferring one exists.

Full suite green: 17,114 passed. Four handlers live and verified in the
running daemon.
