## 09:38 · decision · P1 — design as it will be built

**One driver in the clone: `scripts/venv_bootstrap.sh`.** `init.sh` is a
COPY in client projects (`.claude/init.sh`), while the clone is what
builds. So the logic lives in the clone and `init.sh` only calls it. It
has three verbs:

- `hook <daemon_dir>` runs on the hook path, only in init.sh's
  VENV_MISSING branch for a real clone with a readable version. It never
  blocks and prints `key=value` lines for init.sh to render.
- `build <daemon_dir> <python> <fingerprint> <inputs>` is the detached
  child.
- `repair <daemon_dir>` is the foreground build for `bin/hooks-daemon
  repair`.

**Gate (decision 3).** `find_latest_python` (bash, no venv needed) picks
the interpreter, which runs `paths.py bootstrap-decision --daemon-dir D`
BY FILE PATH, with no package import and no PYTHONPATH. One spawn returns
the five-condition decision, the venv fingerprint for that interpreter
and this daemon dir, and an inputs signature. When no 3.11+ interpreter
exists at all, nothing can run the gate, and the answer is the one
failed condition that makes it so (`compatible-python`). The gate is
evaluated only in the VENV_MISSING branch.

**Build (decision 1).** It is detached (`setsid` where present, else
`nohup`) with stdin, stdout and stderr redirected, so the hook's stdout
pipe closes at once. The existing venv lock is taken NON-BLOCKING, using
a new `try_acquire_venv_lock` in `venv.sh` that shares the backends of
`acquire_venv_lock`. The hook checks whether the lock is held before it
spawns anything. The child takes the lock itself, and a child that loses
the race exits without writing anything. Under the lock the child
re-checks freshness before truncating the log, so a late child never
clobbers a finished build's log. Success is judged by the RESOLVER
resolving afterwards, not by `ensure_venv`'s exit code: a venv whose
metadata write failed is stamp-only, and the resolver refuses it.

**State files** go under `untracked/`, dot-prefixed so no `venv-*` glob
can ever match them:

- `.venv-bootstrap-<fp>.log`: the build log.
- `.venv-bootstrap-<fp>.failed`: the failed marker. It holds the inputs
  signature.
- `.venv-bootstrap.current`: the log of the build holding the lock, used
  to name the log when the holder is another environment.

They are keyed by the fingerprint, which is exactly the venv's own key.
So environment A's failure never blocks environment B.

**Retry policy.** A failed marker stops respawning. A retry is allowed
when the inputs signature changes (`pyproject.toml` or `uv.lock`
content, the chosen interpreter, the resolved `uv` path) or on an
explicit `bin/hooks-daemon repair`, which clears the marker. An
environmental failure that changes no input (network down, disk full)
therefore waits for `repair`, and the message names it.

**Opt-out.** `HOOKS_DAEMON_SKIP_VENV_BOOTSTRAP=1` is honoured on the hook
path, as it already is in `ensure_venv`. The message names it as the
reason no build was started.

**Skill (decision 5).** The in-place repair runs the clone's own
`bin/hooks-daemon repair`, not the same-version upgrade. The upgrade
fetches `scripts/upgrade.sh` from GitHub, rewrites tracked project files
(`settings.json`, `HOOKS-DAEMON.md`, the skills themselves) and restarts
the daemon, which is far more than "build the missing venv". `repair` is
local, offline, and takes the same lock. The upgrade stays the documented
manual fallback.

## 09:52 · finding · T1.2 — the lock can be handed to a detached child with no gap

Before relying on it, I checked that a `flock` the hook takes survives
being handed to a `setsid`-detached child after the parent closes its own
descriptor:

```
parent-got-lock
parent-closed
held-by-child: ok
free-after-child-exit: ok
```

So the HOOK takes the lock (non-blocking), the child inherits the
descriptor, and the lock is never free in between. Exactly one hook can
ever start a build; a second never even spawns a child. The mkdir backend
hands over its lock directory the same way (`adopt_venv_lock`).

## 10:16 · decision · T1.4 — how the skill decides, and how `--force` keeps venvs

With no `--force`, an existing directory takes one of four branches:

- **Healthy**: nothing to do (unchanged).
- **Only the hooks' runtime shell**: no entry but `untracked/`, and no
  `venv*` inside it. Removed, then a normal install without `FORCE`.
  This case needs its own branch: init.sh `mkdir -p`s that directory on
  every hook, and until now the auto-force was what let a fresh checkout
  install at all.
- **A whole clone** (`scripts/lib/resolve_venv.sh`, `bin/hooks-daemon`
  and a version that reads): the clone's own `bin/hooks-daemon repair`
  runs, then the probe runs again. If it still fails, exit 1, "Nothing
  was deleted", with next steps in order: `repair`, then the
  same-version upgrade, then `--force` as a last resort (now safe).
- **Anything else** (a damaged clone, a lone leftover venv): exit 1,
  change nothing, explain.

`repair` was chosen over the 00454 same-version upgrade for the in-place
path: it is local and offline and touches only the venv. The upgrade
fetches from GitHub and rewrites tracked project files.

An explicit `--force` MOVES every `untracked/venv-*` aside before the
installer runs. The aside directory is `.claude/.hooks-daemon-venvs.XXXXXX`,
a sibling of the daemon dir, so the move is a same-filesystem rename,
byte-for-byte. The venvs are moved back to the same path from the EXIT
trap, so a failed install restores too. I chose this over "delete
everything except them" because the installer's `git clone` needs the
target directory absent. A name the fresh install rebuilt belongs to
this environment, so the new one wins and the old copy is dropped. The
root installer's own `FORCE=true` path (`install.sh:72`) still wipes
everything when run directly. The skill is the route agents use, so that
is recorded as out of scope rather than changed. `upgrade.sh` is a
fetch-and-exec shim with no force shape. The other skill scripts only
`exit 5` with advice when no venv resolves, and none of them forces.
