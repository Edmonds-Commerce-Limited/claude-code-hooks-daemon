## 07:12 · decision · T1.3 — 0o007, not the report's 0o077

The report's preferred Option A is `os.umask(0o077)`. That is wrong for this
project, and the report flags the exact caveat without being able to resolve it
from outside ("if any deployment genuinely relies on a second user reading
daemon runtime files"). It does. Three independent pieces of evidence:

- `server.py:657` — the socket is `chmod(0o660)` AFTER bind. Group, not
  owner-only. A mode chosen deliberately so a second process can connect.
- `CLAUDE.md` — a host and a container sharing a bind-mounted `untracked/`
  resolve the same `(hostname, project root)` and **deliberately share one
  daemon**. Those two contexts routinely run as different UIDs.
- `.claude/init.sh` — the forwarder, running as whoever launched Claude Code,
  reads `PID_PATH` (line 575, `cat "$PID_PATH"`) and the `.socket-path`
  discovery file (478–482).

Under `0o077` the PID file and `.socket-path` become `0600` and the shared-daemon
setup breaks for the non-owning UID. `0o007` keeps group and strips other:
files `0660`, dirs `0770`. Both explicit-mode sites are unaffected —
`0o600 & ~0o007 == 0o600` for the lock, and the socket's mode is a post-bind
`chmod` that no umask touches.

The exposure the report is actually about — "any local user can read every
archive" — is *other*-access, and `0o007` removes it completely.

## 07:18 · finding · T1.2 — 1 of 98 create sites passes an explicit mode

Enumerated every runtime create under `src/claude_code_hooks_daemon/` (mkdir,
makedirs, write_text, write_bytes, os.open, open-for-write, tempfile, replace),
excluding `install/` and `skills/`:

- **98 sites total**, of which **35** are directory creates (all `0777` today).
- **Exactly one** passes an explicit mode: `server.py:727`,
  `os.open(str(lock_path), os.O_RDWR | os.O_CREAT, 0o600)`.

The heaviest concentrations with no explicit mode: `daemon/cli.py` (19),
`daemon/paths.py` (8), then `thread_registry.py`, `context_sidecar.py` and
`markdown_organization.py` at 4 each.

**This settles the A-vs-B design question the report leaves open.** Its Option B
is "keep `umask(0)` and pass explicit modes at every sensitive create". At 97
unguarded sites that is not a fix, it is a permanent audit obligation — and one
the codebase has already failed once, since the `umask(0)` contract requires
exactly that discipline and got it in a single place out of 98. The umask is the
one choke point that fixes every current and future create at once, which is the
SINGLE SOURCE OF TRUTH principle applied to permissions.

Option C's explicit modes therefore stay deliberately narrow — defence in depth
on `payload-capture/` only, the one artefact whose contents are known-sensitive,
so the posture survives someone later "restoring" the textbook `umask(0)` line.
Not a sweep of 97 sites.

## 07:55 · decision · T1.3 — REVERSED: 0o077, not 0o007. I was wrong.

Sent an adversarial reviewer at the 07:12 decision with instructions to refute
it rather than confirm it, and worktree isolation so it could not touch the
index. It refuted it, and I verified every load-bearing claim myself before
accepting.

The three premises of the `0o007` argument, each checked:

- **"The socket's 0o660 proves group access is deliberate."** `server.py:655`,
  the comment immediately above the chmod, reads *"owner read/write, group read,
  world none"* — which describes `0o640`. The code writes `0o660`. An author
  reasoning about group WRITE on an IPC socket does not write "group read" above
  it. It is a typed-from-memory idiom. Confirmed further: `grep -rE
  "chown|chgrp|SO_PEERCRED|getpeereid"` over `src/`, `scripts/` and `init.sh`
  returns exactly ONE hit, and it is a config-comment string. Group access to a
  file whose group is never set is not a design.
- **"A host and a container share one daemon at different UIDs."** Documented,
  but already impossible today: `server.py:727` opens the start-lock
  `os.open(..., 0o600)` and leaves it on disk for reuse, so a second UID's
  `start` gets EACCES regardless of umask. The daemon is also a descendant of
  every process that reads its files, and nothing setuids.
- **"init.sh reads PID_PATH and .socket-path as the launching user."** True —
  and same-UID, for the reason above.

So the premise I was most confident in — the one I told the user I had
"independently established" — was the weakest of the three. It was real
evidence read correctly and reasoned from wrongly: `0o660` is a fact about the
code, not a fact about intent, and I promoted it to intent because it fit.

`0o007` is never safer than `0o077`, and on a host with a shared primary group
(`staff`, `users`, a service account) it leaves the verdict log,
`stop-events.jsonl` and `payload-capture/` group-readable AND group-writable.
`0o077` is deployment-invariant. Both explicit-mode sites survive it.

## 08:00 · finding · T2.4 — the daemon world-writables entire SOURCE CHECKOUTS

The review surfaced something neither the field report nor Phase 1 caught, and
the proof was sitting in the reviewer's own isolation worktree:

```
777 .claude/worktrees/agent-<id>/
666 .claude/worktrees/agent-<id>/README.md
666 .claude/worktrees/agent-<id>/pyproject.toml
666 .claude/worktrees/agent-<id>/.claude/settings.json
--- same files in the main repo ---
644 /workspace/README.md
644 /workspace/pyproject.toml
644 /workspace/.claude/settings.json
```

`worktree_create` runs `git worktree add` as a child of the umask-0 daemon, so
git creates the whole checkout under umask 0. This is not a runtime-file
problem, it is a SOURCE TREE problem, and it inverts the fix: a checkout should
be `0644`/`0755`, so under a bare `0o077` it would become `0600`/`0700` —
functional for one user but wrong for source, and it would surface as spurious
mode churn wherever `core.fileMode` is true. That subprocess needs a
*permissive* `0o022`, making it the one place the daemon needs a LOOSER umask
and the one place it currently exercises none.

Two further umask-governed sites, both the same tmp-then-replace shape:

- `settings_repair.py:105-106` replaces the **git-tracked**
  `.claude/settings.json` with a temp file, so the tracked file inherits the
  temp's mode. Its sibling `hook_command_migration.py:178` rewrites in place and
  is immune; the two differ for no reason.
- `retention.py:62-64` does the same to `verdicts.jsonl` and
  `stop-events.jsonl`, so a manual `chmod` is undone at the next trim.

**One correction to the reviewer**, checked rather than accepted: it stated
`settings_repair` resets the mode "on essentially every SessionStart". Live,
`.claude/settings.json` is `0644`, so that path has not been firing here. The
mechanism is real; the claimed frequency is not evidenced. Taking that at face
value would have put a false frequency claim into the plan.
