## Overview

Owner request (7 November 2026): at release time, do we create or update a comprehensive catalogue of all the handlers, each linked to its source file, and is that catalogue validated for correctness at release? This is post-release work and must not delay the current release.

What exists today (surveyed before filing; `find-plan` for "handler reference", "catalogue", "handler catalogue" found nothing, and "generate-docs" found only the completed Plan 00282, a null-priority crash fix, so this is a new plan):

- `.claude/HOOKS-DAEMON.md` is GENERATED by `bin/hooks-daemon generate-docs` (`src/claude_code_hooks_daemon/daemon/docs_generator.py`). It lists handlers per event with priority, BLOCKING/advisory and a one-line purpose, but it is titled "Active Configuration", so a handler disabled in this project is absent. It contains no links to source files. Drift is guarded in QA by `scripts/qa/check_generated_doc_drift.py` (regenerates and diffs), wired in `scripts/qa/run_all.sh`; RELEASING.md (line 465) has a manual "regenerate after the version bump" step.
- `docs/guides/HANDLER_REFERENCE.md` (about 5,300 lines, about 130 `####` sections) is HAND-WRITTEN. Its own scope note says it covers every PreToolUse blocking handler plus handlers with configurable options, NOT every handler. It has no source-file links. `scripts/qa/check_handler_reference.py` (tests: `tests/integration/test_handler_reference_check.py`) validates section names against the registry and `constants/handlers.py`, priorities against `constants/priority.py`, and that every PreToolUse blocking handler has a section; it runs in `run_all.sh`.
- `bin/hooks-daemon handlers` prints the registered handlers per event (mode, priority, kebab name), with no purpose, rule IDs, config key or links.
- README.md has only prose about handlers; no inventory. The CLAUDE.md `<hooksdaemon>` block is a separate generated, partial digest.
- Release process: `CLAUDE/development/RELEASING.md` runs the QA gate (which includes the two checks above) and has the regenerate step, but no step or test asserts "every registered handler is in one catalogue with a resolving source link and test link".

Gap: there is no single complete catalogue (advisory and non-PreToolUse handlers are only in the Active-Configuration view or the CLI), nothing links a handler to its source or test file, and nothing at release or in CI fails when a handler is missing from a catalogue or a link is dead.

## Goals

- One comprehensive handler catalogue, GENERATED from the handler registry (not hand-maintained), listing EVERY registered handler regardless of the project's config: name, event, priority, blocking or advisory, purpose, rule IDs, config key, and a relative link to its source file and to its test file.
- A CI test that fails when the committed catalogue is stale, a registered handler is missing from it, or any source or test link does not resolve to an existing file.
- A release-time gate in `CLAUDE/development/RELEASING.md` that regenerates the catalogue and runs that validation before tagging.
- No overlap left behind: the new catalogue is the single inventory; `HANDLER_REFERENCE.md` stays the options reference and points to it, and `HOOKS-DAEMON.md` keeps its per-project role.

## Non-Goals

- Delaying or changing the current release.
- Rewriting the hand-written options in `HANDLER_REFERENCE.md`.
- Documenting project-local (client) handlers beyond what the registry already discovers.
