## 09:00 · action · T2.5+T3.5 — markdown_organization resolves declared `projects:` first

`_declared_subproject_relative()` resolves a normalized markdown path
through the injected `_project_registry` via the same `resolve_workspace()`
helper `npm_command`/`lint_on_edit`/`tdd_enforcement` use — a declared
`projects:` root that CONTAINS the path is stripped to a sub-project-relative
path exactly like `strip_monorepo_prefix()` already did for
`monorepo_subproject_patterns`. `matches()` now tries the declared registry
FIRST and falls back to the deprecated pattern alias
(`self._declared_subproject_relative(normalized) or
self.strip_monorepo_prefix(normalized)`), so both mechanisms are unioned —
neither shadows the other (pinned by
`test_declared_projects_and_pattern_alias_are_unioned`).

No inference: when `_project_registry` is `None` or resolves the path to the
repository root (nothing declared covers it), `_declared_subproject_relative`
returns `None` and behaviour is identical to before this task — pinned by
`test_no_registry_injected_is_byte_identical_to_before` and the anti-inference
pin `test_anti_inference_undeclared_subproject_runs_from_repository_root`
(a manifest-shaped-looking sibling directory that was never declared still
gets repo-root treatment, i.e. blocked).

New test class `TestDeclaredProjectsSubprojects` in
`tests/unit/handlers/pre_tool_use/test_markdown_organization.py` deliberately
exercises `RELEASES/` paths rather than `CLAUDE/Plan/...` ones: `normalize_path`
already strips anything containing a `CLAUDE/` marker regardless of any
monorepo mechanism (see the pre-existing
`test_subproject_without_monorepo_config_falls_through_to_normalize`), so a
`CLAUDE/`-shaped path would not isolate the declared-`projects:` behaviour
under test. `RELEASES/` has no such marker.

`strip_monorepo_prefix()`'s docstring all now point at `projects:` as the
primary mechanism and name `monorepo_subproject_patterns` as a deprecated

## 06:46 · decision · T4.1 — degradation surfaced via a concrete `Handler` hook, wired only into `check`

Added `Handler.get_enforcement_status(project_root: Path) -> list[str]`
(`core/handler.py`) — concrete, default `[]`, so the vast majority of
handlers with no on-disk-dependent posture need no change. A handler whose
strictness is decided by a cheap on-disk probe overrides it to report the
degraded condition at a given root.

**Scope chosen deliberately narrow**, per the plan's "smallest design that
satisfies the success criterion" steer: implemented for the three handlers
the survey named, wired into `check` output ONLY (not `handlers`):

- `npm_command` / `validate_eslint_on_write`: both already probe
  `has_llm_commands_in_package_json()` per invocation (Plan 00296 Task 2.1/2.3)
  — `get_enforcement_status()` just re-runs that same cheap read at the
  requested root. `validate_eslint_on_write` honours its pinned
  `workspace_root` test seam over the passed root, matching `_workspace_for`'s
  own precedence.
- `lint_on_edit`: probes only each active strategy's EXTENDED lint command
  (the one that "may or may not be installed" — the built-in default, e.g.
  `bash -n`, is always available, so its absence is not a degradation worth
  reporting). Reuses `_resolve_executable`'s existing filesystem checks
  (`is_file`/`shutil.which`) — no subprocess run. Required a small addition,
  `LintStrategyRegistry.strategies()` (dedup by identity), since the registry
  previously only exposed lookup-by-file and a bare language-name list.

**Why `check` only, not `handlers`**: `handlers` lists every registered
handler on every invocation, including from scripts that parse it — adding a
filesystem probe per handler there would slow the common case for a
diagnostic nobody asked for on that call. `check` is already the on-demand,
deliberately verbose audit (Plan 00128) that reads config and runs several
probes per invocation, so one more line-item fits its existing cost profile.

**CLI wiring** (`_collect_enforcement_status_lines` in `daemon/cli.py`):
loads `.claude/hooks-daemon.yaml` best-effort (falls back to
`ProjectRegistry.single_project()` on any load/validation error — `check` is
also how a broken config gets diagnosed, so it must not raise), builds a
`ProjectRegistry`, and evaluates all three handlers at the repository root
AND every declared `projects:` root. Handlers are constructed directly
(mirroring the existing `OptimalConfigCheckerHandler()` /
`GitFilemodeCheckerHandler()` pattern in `cmd_check`), bypassing the registry/
daemon lifecycle entirely — deliberate, since a `handlers`-wide sweep was
explicitly out of scope. `npm_command`/`validate_eslint_on_write`
construction probes `ProjectContext.project_root()` for state this function
never reads (their per-root posture comes from `get_enforcement_status()`,
not the constructor default); `ProjectContext` is patched to `project_path`
for the duration of construction only, matching those handlers' own test
suites (e.g. `test_validate_eslint_on_write.py`'s `mock_project_context`
fixture) rather than depending on a live daemon-initialised singleton.

**Known limitation, accepted**: a pure-non-Node repository with no
`package.json` anywhere reports `npm_command`/`validate_eslint_on_write` as
"degraded" at every root, which is technically true (raw npm/npx commands
would only get an advisory) but is noise for a repository that never runs
npm at all. This mirrors those handlers' own existing advisory-mode
semantics (`get_claude_md()` already documents "operates in advisory mode"
for exactly this case) — `check` is reporting the same fact the handler
already discloses per-invocation, just proactively. Not fixed here: doing so
would need `check` to know whether npm is even relevant to the repo, which
is exactly the kind of inference this plan's Goals reject.
