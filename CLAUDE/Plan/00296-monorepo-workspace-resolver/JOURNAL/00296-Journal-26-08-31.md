## 15:24 · decision · T1.2 — no workspace override knob, and why

Reviewed every existing config surface that encodes "which sub-tree am I in".
**Decision: add no new override knob.** Resolution stays derived from the
edited file's own path; `_MANIFEST_KINDS` is the sole extension point.

Rationale — a knob naming each workspace is the same bodge as a root-level
manifest existing purely to satisfy tooling, which the field report rules out
explicitly. It would also be dead surface: the automatic answer is correct
wherever a manifest exists, and where none exists, declaring the location does
not conjure a toolchain.

The four surviving knobs are **not** workspace overrides and none is replaced:

| Surface                                          | What it actually is                                            |
| ------------------------------------------------ | -------------------------------------------------------------- |
| `markdown_organization.monorepo_subproject_patterns` | Documentation-layout sub-project; need not have a manifest |
| `tdd_enforcement.test_path_map`                  | Where tests live for a glob — orthogonal to which workspace    |
| `validate_eslint_on_write(workspace_root=…)`     | Test seam, constructor-only, never read from YAML              |
| `layout.source_dirs` etc.                        | Roles *within* a workspace — a different axis                  |

The `monorepo_subproject_patterns` finding is the load-bearing one: a docs site
with its own `docs/` and `CLAUDE/` and no `package.json` is a real layout, so
automatic manifest resolution **cannot** subsume that option. Task 2.5 makes it
an override of automatic resolution, not a replacement for it.

## 15:24 · finding · T2.2 — Ansible has a marker that is not a manifest

`lint_on_edit._MODULE_ROOT_MARKERS` maps Go→`go.mod` and Ansible→`ansible.cfg`.
`go.mod` is in `_MANIFEST_KINDS` so Go routes through the resolver unchanged,

supplementary marker lookup alongside the resolver. Recorded as a known limit
in the new doc.

## 15:31 · finding · T2.1 — cwd alone would NOT have fixed the reported bug

Started Task 2.1 intending the obvious change (pass a workspace root to
`has_llm_commands_in_package_json`, evaluate per invocation). Resolving the
workspace from the hook's `cwd` alone turns out to be insufficient, and would
have shipped a fix that does nothing for the reporter.

An npm command in a monorepo is shaped `cd apps/web && npm run build`. The
Bash tool's `cwd` stays at the **repo root** for that invocation, so cwd-only
resolution finds no manifest, falls back to the root, and leaves enforcement
off — the exact reported symptom, preserved. So the resolver consults a
leading `cd <dir> &&` first and `cwd` second. Only a LEADING cd counts; a cd
later in a chain does not describe where the npm command ran.

`test_leading_cd_selects_the_workspace` is the regression pin for this.

## 15:31 · finding · T2.1 — per-invocation mode broke 31 tests, correctly

Moving the decision out of `__init__` made `handle()` call
`has_llm_commands_in_package_json` for the first time, which surfaced two
things worth recording:

1. **31 existing tests patched the detector at CONSTRUCTION only** — the patch
   context exited before `handle()` ran, so they silently fell through to the
   real repo root. Fixed by turning those fixtures into `yield` fixtures so the
   patch spans the test body. The failure was correct: the contract genuinely
   changed from decided-once to decided-per-invocation.
2. **`handle()` must not require an initialised `ProjectContext`.** Calling
   `ProjectContext.project_root()` directly raised `RuntimeError` in every unit
   test that only exercised message formatting. Switched to the project's
   existing `resolve_project_root()` helper, which returns `None` when
   ProjectContext is not initialised precisely for this case; the walk is then
   bounded at the base directory instead of raising.

## 15:47 · action · T2.3 — validate_eslint_on_write resolves per authored file

`_workspace_for(file_path)` returns `(root, bin_dirs)`; `handle()` uses it for
the subprocess cwd, for the PATH prefix, and for the mode probe — the last of
which previously ignored `self.workspace_root` entirely and read the repo root,
the internal inconsistency the report called out.

Two deliberate preservations:

- **The `workspace_root` test seam still wins outright.** An explicit root pins
  every file, which is what makes it usable for test isolation. Per-file
  resolution only applies when it is unset.
- **`node_modules/.bin` is a FALLBACK when the resolver yields no bin dirs.**
  Routing purely through `workspace.bin_dirs` would have regressed a pinned
  root that has no `package.json`: the resolver returns empty bin dirs there,
  so `tsx` would have dropped off PATH. Caught while writing the code, not by
  a test — worth stating because the same trap applies to Task 2.2.

## 16:02 · action · T2.2 — lint_on_edit searches workspace bin dirs first

`_resolve_executable(name, workspace_bin_dirs)` now searches the file's own
`vendor/bin` / `node_modules/.bin` BEFORE the daemon venv and PATH, and the
working directory falls back to the workspace root for any language without a
module-root marker. The "tool not found" advisory names the bin dirs it
searched, so the message can no longer claim a tool is absent without saying
where it looked.

Workspace-first is deliberate rather than last-resort: a project pins a linter
VERSION in its own manifest, so a global copy that happens to be on PATH is the
wrong tool even when one exists.

The Ansible hazard recorded at 15:24 was real and is now closed by ordering:
`_MODULE_ROOT_MARKERS` is consulted first, the workspace root only as fallback.
`test_ansible_cfg_marker_still_selects_the_working_dir` is the non-regression
pin, and `test_go_mod_marker_is_unaffected` covers the case where both
mechanisms agree.

## 16:20 · decision · T1.2 — CORRECTION: the no-knob decision was wrong

Owner ruling: a top-level config object must track projects as a first-class
concept — single project / repo root as the default, monorepo supported by
changing config structure rather than by deriving everything.

This **supersedes the 15:24 decision entry**, which concluded "add no new
override knob". That conclusion does not survive its own evidence. The field
report's own layout sketch lists a third workspace:

```
infra/     # a third toolchain again (config-driven, no manifest)
```

A manifest walk-up **structurally cannot resolve `infra/`** — there is no
manifest to find, so `Workspace.for_path()` falls through to the project-root
fallback, which is precisely the silent degradation this plan exists to remove.
Derivation handles two of the reporter's three workspaces and quietly fails the
third. I read past that line while writing the Non-Goals.

I also over-read the report's "bodge" objection. Re-read at line 30: it is
specifically about adding a manifest to the REPOSITORY — "it would exist purely
to satisfy a tool, declaring dependencies the repository does not have and
creating a lockfile nobody installs". A `projects:` block in
`.claude/hooks-daemon.yaml` is not that: it declares to the daemon without
putting a fake manifest in the repo. The Non-Goal conflated the two, and the
`monorepo_subproject_patterns` finding in the same entry — a docs sub-project
with no manifest — was already the same counter-example staring back.

**Resolution: three precedence layers, not two competing designs.**

| Layer                          | Source          | Covers                                            |
| ------------------------------ | --------------- | ------------------------------------------------- |
| `projects:` config             | declared        | manifest-less workspaces, docs sub-projects       |
| `Workspace.for_path()`         | manifest walk-up | the zero-config default                          |
| project root                   | git root        | single-project repos, unchanged                   |

Phase 2 is NOT invalidated: `Workspace` stays the runtime type every handler
consumes, so the three handlers already routed through it gain a declaration
source ahead of the walk rather than being rewritten.

Design constraint carried forward: `projects:` is a PRECEDENCE layer, never a
requirement. Making declaration mandatory would charge every single-project
repo config cost for a monorepo feature, and a stale `projects:` list would
silently disable enforcement for a workspace nobody remembered to add — the
same class of silent failure as the original bug.
