# Report 4 — Prior Art: How Other Ecosystems Handle the Hook Exec-Bit Problem

## 1. Summary

Every git-hook manager that survives in user repos has hit the exec-bit failure mode (Windows clones, `core.fileMode=false`, tarballs, IDE rewrites). The convergent industry answer is **"don't put the executable in the user's tree"**: install a small auto-generated shim *outside* version control (`.git/hooks/` or `.husky/_/`), keep it gitignored, and re-create it on every install/run so a missing or stripped exec bit just gets fixed automatically. The most opinionated example is husky v9, which deleted its old shebang+chmod approach in favour of `.husky/_/` shims regenerated by `husky` (run from `prepare` after every `npm install`). Pre-commit and lefthook do the same: generated shims under `.git/hooks/`, `chmod 0755` applied at install, regenerated on every `install` invocation. Tools that ship as a binary on `PATH` (lefthook, mise) sidestep half the problem because the shim only needs to invoke a known binary, not a tracked script.

## 2. Per-tool findings

### husky v9 ([typicode/husky](https://github.com/typicode/husky))

- **Install location**: shims live in `.husky/_/`, gitignored. User-authored hooks live in `.husky/<name>` and are *sourced*, not exec'd.
- **Invocation**: husky sets `git config core.hooksPath .husky/_`; each shim shells `. "$(dirname "$0")/h"` which `sh`-sources the user file. Because the user file is sourced, **its exec bit is irrelevant**.
- **Public bug history**: [#1177](https://github.com/typicode/husky/issues/1177) — Windows-created hooks lost exec bit when pulled on macOS/Linux ("hook was ignored because it's not set as executable"). Tracked across [#934](https://github.com/typicode/husky/issues/934) and [#1241](https://github.com/typicode/husky/issues/1241).
- **Resolution**: v9 [migration notes](https://typicode.github.io/husky/how-to.html) eliminated the requirement entirely by switching from `git → user-script` (needs +x) to `git → generated shim → source user-script` (no +x needed on user file). Also dropped the auto-shebang.

### pre-commit ([pre-commit/pre-commit](https://github.com/pre-commit/pre-commit))

- **Install location**: generated `.git/hooks/<name>` from `hook-tmpl`. Backs up any existing hook to `<name>.legacy`.
- **Invocation**: shim is direct-exec'd by git; calls `pre-commit hook-impl` with the user's config.
- **Exec-bit handling**: `_install_hook_script()` in [`install_uninstall.py`](https://github.com/pre-commit/pre-commit/blob/main/pre_commit/commands/install_uninstall.py) calls `make_executable(hook_path)` unconditionally after writing.
- **Public bugs**: [#413](https://github.com/pre-commit/pre-commit/issues/413), [#1042](https://github.com/pre-commit/pre-commit/issues/1042), [#2077](https://github.com/pre-commit/pre-commit/issues/2077) — all permission-denied, all resolved by re-running `pre-commit install` which re-applies the chmod. Pattern: idempotent re-install, not detection.

### lefthook ([evilmartians/lefthook](https://github.com/evilmartians/lefthook))

- **Install location**: shims in `.git/hooks/`, written by the `lefthook` Go binary.
- **Invocation**: shim runs `lefthook run <hook-name>`. Because the user's logic lives in `lefthook.yml` (data, not script), the only file that ever needs +x is the *generated* shim — never anything tracked.
- **Public bugs**: [#161](https://github.com/evilmartians/lefthook/issues/161) (snap install permissions), [#1398](https://github.com/evilmartians/lefthook/issues/1398) (absolute paths baked into shim break worktrees). Mitigation: the binary regenerates shims on `lefthook install`, and an `auto_install` flag re-runs install when `lefthook run` detects drift.

### direnv ([direnv.net](https://direnv.net/))

- **Install location**: `.envrc` is in the user's tree but **never executed via exec()** — direnv spawns `bash` and sources the file, then captures the env diff.
- **Trust model**: `.envrc` requires explicit `direnv allow` keyed on content hash; permission bits are ignored entirely. Edits invalidate trust.
- **Relevance**: confirms the *source-don't-exec* pattern eliminates exec-bit dependence, and adds a content-hash trust gate as security backstop.

### git's own `core.hooksPath` ([git-scm docs](https://git-scm.com/docs/githooks/2.24.0))

- **Contract**: git `exec()`s files in the hooks dir; **no exec bit = silently ignored**. This is the root cause of every other tool's chmod gymnastics.
- **Implication**: any approach that has Claude Code directly invoke a tracked file inherits this trap. Husky/lefthook/pre-commit all work around it by pointing the hook path at a *generated* directory they control.

### simple-git-hooks ([toplenboren/simple-git-hooks](https://github.com/toplenboren/simple-git-hooks))

- Minimalist counter-example: writes commands directly into `.git/hooks/<name>` and chmods once at `npx simple-git-hooks` time. No regeneration. Failure mode is **exactly ours**: anything that strips the bit kills hooks silently. Demonstrates that *one-shot* chmod is insufficient.

## 3. Patterns we should steal

1. **Generated-shim layer outside the tracked tree** (husky, lefthook, pre-commit unanimous). Put the executable wrappers in `.claude/hooks-daemon/untracked/hooks/` (gitignored, regenerated). Tracked content in `.claude/hooks/` becomes *data sourced by the shim*, not a direct exec target. This single architectural change makes the bug class structurally impossible.
2. **Source-don't-exec the user-tracked file** (husky v9, direnv). If the wrapper is `sh -c '. "$REAL_HOOK"'`, the user file's exec bit is irrelevant.
3. **Idempotent re-install on every daemon start / hook invocation** (lefthook `auto_install`, husky `prepare` after every `npm install`). Cheap to hash-check and rewrite-with-chmod; converts "broken once, broken forever" into "broken until next event".
4. **Self-healing shim** that runs `chmod +x` on its peers if it detects damage and continues. Costs one `stat()` per event, recovers silently from `cp`/tarball damage.
5. **Single binary on `PATH` for the heavy lifting** (lefthook). Our daemon CLI already plays this role; hook wrappers should be the thinnest possible bash that locates and execs the daemon entry.

## 4. Patterns we should NOT copy

1. **Husky's "just gitignore the wrappers entirely" approach.** If we hide `.claude/hooks/*` we lose the audit trail and project-level customisation central to this project. Steal the *shim layer*; keep the user-facing files tracked and sourced rather than exec'd.
2. **simple-git-hooks' one-shot chmod at install.** Already proven insufficient by Issue #29 — install runs once, the bit gets stripped later, no recovery path.
3. **direnv's content-hash trust prompt on every change.** Hostile UX for hooks the user explicitly wants to run on every event. Our trust boundary is the daemon config, not per-file approval.

---

**Key findings for the plan**: convergent answer is `core.hooksPath`-style indirection — point the host (Claude Code) at a regeneratable shim directory and source the tracked user files. Husky v9's evolution from "chmod the tracked hook" to "source the tracked hook from a regenerated shim" is the single most relevant precedent and worth reading their migration guide closely.
