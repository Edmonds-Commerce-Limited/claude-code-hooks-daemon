## BLOCKER

### B1. On macOS the wait primitive returns at once, so a hanging candidate is never killed (Confidence 75%)

**Location:** `scripts/lib/resolve_venv.sh:163-166` (`_rv_wait_secs`)

**Problem:** Main used `sleep` whenever PATH had one. It fell back to `read -r -t "$1" <> <(:)` only on a stripped PATH. The branch makes `read -t` the only path. That primitive blocks for the bound only because Linux re-opens `/proc/self/fd/N` as a new read-write handle on the pipe, so the shell becomes a writer of the pipe itself.

On macOS, `/dev/fd/N` is a dup of the existing read-only fd. Two outcomes are possible, and both are bad:
- XNU refuses the read-write open (EACCES).
- Or it hands back the read end whose only writer, `:`, has already exited, so the read sees EOF at once.

Either way `_rv_wait_secs` returns 1 straight away. `[ 1 -gt 128 ]` is false, so the watchdog never sends the kill, and `wait "$pid"` blocks for as long as the candidate runs. The bound this function exists to provide is gone.

There is a second break on bash 3.2 (macOS's default `/bin/bash`): `read -t` takes whole seconds only. A fractional `HOOKS_DAEMON_VENV_PROBE_TIMEOUT` makes the read fail at once with the same effect. Main handled fractions through `sleep`.

**Why it counts:** macOS is supported. The README says "Linux or macOS", and `portable_time.sh` documents bash 3.2 handling for exactly this script family. There is no macOS CI runner, so nothing in the suite can catch this.

**Evidence:** `/workspace/untracked/scratch/review-00500-r1/dup_semantics.bash`. On Linux:
- A dup of the read end returns `rc=1 waited=0s`, which is what macOS's dup behaviour would produce.
- The Linux re-open returns `rc=142 waited=3s`.

I could not run macOS here. The EACCES half rests on XNU's `dupfdopen` mode-subset check.

**Fix (verified on Linux):**
1. Fix the pipe hold where it actually happens. Detach the watchdog's fds with `( … ) < /dev/null > /dev/null 2>&1 &`. The watchdog writes nothing anyone reads, because its kill output is already captured.
   - I patched main's resolver with only that change (`/workspace/untracked/scratch/review-00500-r1/lib_alt/resolve_venv.sh`).
   - A good candidate answered in 0.014 s against a 6 s bound.
   - A hanging candidate was still killed at 2.02 s against a 2 s bound.
2. Keep `sleep` as the main wait and `read -t` as the no-`sleep` fallback. With that, macOS and fractional bounds work again.
   - Trade-off: an orphaned `sleep` still lives out the bound, reparented to pid 1, but it holds no pipe. The branch's Linux-only path does avoid that orphan.
   - If you also want to avoid that orphan on Linux, choose `read -t` only where `/proc/self` exists.
3. When the wait primitive returns early without timing out, treat it as an error and fall back to `sleep`, rather than silently dropping the bound.
4. Add a test that stubs `_rv_wait_secs` to return 1 at once and asserts that a hanging candidate is still bounded.

**Other answers to question 1 on Linux:** this is fine.
- The watchdog is still killed and waited on.
- The builtin `read` dies with its subshell, and the `<(:)` child exits at once and is reaped, so there is no leaked `sleep` and no lasting zombie.
- `_rv_wait_secs` runs in an `if` condition, so callers using `set -e` or pipefail are unaffected.
