## Findings

- Released-tree test: its 25 readers include the layer-1 upgrade file (about 280 s of it). Running them as one process serialised everything. The same files now run in the same copy in four groups chosen by file size (`partition_readers`, unit-tested). No reader is dropped.
- Layer-1 file: `origin` was function-scoped, so each of 15 tests snapshotted the working tree and made three commits. Tests only clone and fetch from it, so it is module-scoped.
- Resolver latency: not a timeout in the test. `_rv_wait_secs` used an external `sleep`; when the candidate answered, the watchdog subshell was killed but its `sleep` lived on holding the pipe of `$(...)`, so every resolver cache miss cost the full 5 s probe bound. Real hook cost, not only test cost. RED test added in `test_resolve_venv_runnability_probe.py` (failed at 20.01 s of a 20 s bound), then `_rv_wait_secs` uses the `read -t` builtin always, which dies with its subshell. The PATH-without-sleep tests still pass.
- Glob readers: `_glob_reader_files()` (an AST parse of every test file, 14 s) and the mapper corpus were rebuilt per test; both are now `functools.cache`d (immutable inputs).

## Declined, with reasons

- Signal-target checker: pure CPU AST scan of 2,254 files. 17 s without coverage, 91 s under the 3.11 coverage leg. The cost is coverage tracing of the detector, which cannot be removed without lowering coverage. Parallelising it would need fork pools inside the test. Not done.
- `test_llm_qa_main_moved`: the 58 s is the one shared corpus fixture under coverage and load (12.7 s here); 136 tests run in 34.6 s. Nothing left to share.
- Hostile-input performance: each case times the handler under test on 100,000-character inputs; the time is the measurement. Running cases concurrently would distort the ratios, and `_regime` is a correctness check on a separate call. Declined.
