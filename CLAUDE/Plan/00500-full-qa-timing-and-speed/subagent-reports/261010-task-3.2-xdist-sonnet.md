# Task 3.2: pytest-xdist evaluation

Verdict: **DECLINE WITH EVIDENCE.** No code, config or dependency changed. pytest-xdist is not added to the dev group.

Host: 8 CPUs, load average 12 to 21 throughout (other agents' QA). Trial venv: a new venv under this worktree's
`untracked/scratch/` that borrows the shared venv's site-packages through a `.pth` and has `pytest-xdist 3.8.0`
installed from PyPI. The shared venv was not touched. No coverage unless stated; no whole-suite run.

## Measured

| Subset                                                     | Serial                  | `-n 4`                    | Notes                                                                             |
| ---------------------------------------------------------- | ----------------------- | ------------------------- | --------------------------------------------------------------------------------- |
| `tests/unit/utils` (129 files, 6,770 tests)                | 311 s, 226 s            | 135, 129, 164, 118, 117 s | 5 of 5 parallel runs green; about 2x                                              |
| `tests/unit/handlers` (263 files, 15,060 tests)            | 1,907 s (load 12 to 21) | 1,457 s (load about 19)   | 1.31x; one serial and one parallel run only, each takes 25 to 30 min at this load |
| `tests/unit/core` with coverage (`--cov`, `COVERAGE_FILE`) | 126 s                   | 131 s                     | no gain; total coverage 26.96 serial vs 26.93 parallel                            |

The gate always runs with coverage, so the figure that matters is the last row: no wall-clock gain, and a
different coverage total from the same tests (0.03 points here; the 95% threshold is judged on the combined number).
The handlers and utils gains were measured without coverage and on an oversubscribed host, so they are the best
case for xdist's benefit only on an idle host that the gate does not have.

## New flakiness and cost

- Parallel handlers run: 7 failures against 5 serial. The 2 extra are `test_safety_handlers_hostile_input_performance.py`
  (`test_no_handler_grows_superlinearly_on_a_deep_write_path[.py]`, `test_bash_command[digit_sequences]`), timing tests that
  measure scaling and which more workers on the same cores perturb. A third (`[brace_pairs]`) failed serially too under
  load 20. These need a truly serial lane, not an `xdist_group` (a group pins tests to one worker, it does not stop
  the other workers loading the host). A serial lane means every shard becomes two pytest runs and two coverage data files.
- Merely installing xdist breaks two pins that read the running pytest's parser:
  `test_every_boolean_option_of_the_running_pytest_is_known` (`--loadscope-reorder`, `-d`, ...) and
  `test_every_value_option_of_the_running_pytest_is_known` (`--px`, `--testrunuid`). The sub-agent full-QA blocker
  grammar (`PYTEST_FLAG_OPTIONS`, `PYTEST_VALUE_OPTIONS`) would need xdist's options.
- Two `test_lint_on_edit_tool_resolution.py` failures are an artefact of the trial venv (no `ruff` in it), not xdist.

## Phase A static audit (classification)

- **Full-QA lock sink: must change if xdist is installed.** `qa/full_qa_gate.py` exempts workers
  (`_is_xdist_worker`) and the xdist controller never collects, so `pytest_collection_modifyitems` never sees the
  items. Verified with a fixture suite whose one file is 100% of the suite: serial run refused (rc=1, REFUSED), the same
  run with `-n 2` passes (rc=0). So with xdist installed a direct `pytest -n N tests/` bypasses the lock. Today, without
  xdist, `-n` gives rc=4 (safe). A fix would use an `optionalhook` on `pytest_xdist_node_collection_finished`.
  `scripts/qa/run_tests.sh` itself holds the lock before pytest starts, so the gate path is covered; the backstop is not.
- **Shard checkpoints (Task 2.4): safe.** Each shard has its own `COVERAGE_FILE`; pytest-cov combines worker data
  internally, so `parallel = true` in `pyproject.toml` (disabled for a fork bomb) is not needed and not reintroduced.
  Coverage under `-n 4` ran cleanly on `tests/unit/core` with no process explosion.
- **Isolated daemons: safe.** `tests/isolated_daemon.py` keys socket, pid and log by a hash of `tmp_path`, which
  xdist makes unique per worker (`popen-gwN`).
- **Live daemon in this checkout: safe with care.** Acceptance and some integration tests read the shared socket under
  `untracked/` and write per-session usage-exemption markers (`tests/usage_ceiling.py`); read-mostly, session ids differ.
  Not exercised in parallel here (those directories were not run).
- **Environment mutation:** only `tests/daemon/test_paths.py` pops `CLAUDE_HOOKS_*` from `os.environ`, inside
  per-process patch contexts; per-process in xdist, so safe.
- **Fixed ports:** none found. **`os.chdir`:** 15 uses across 26 files, per-process, safe.
- **Session fixtures with side effects:** `signal_safety_net` (per process, installs per worker, safe),
  `fresh_relay_build` (read-only check of `untracked/relay-build`, safe).
- **Timing tests** (33 files use clocks; `tests/load_scaling.py` scales bounds by host load): the hostile-input
  scaling tests are the demonstrated failures above; they must run serially.
- **Not audited by a parallel run:** `tests/integration` and `tests/acceptance` (spawn daemons, installs, nested
  pytest runs); the plan names them the slow, process-spawning files, so they are where parallel risk is highest.

## Why decline

The speedup is real only without coverage and on spare cores, neither of which the gate has. With coverage on a mixed
subset it was nil. Adoption would add a fail-open fix to the lock sink, new grammar entries, a serial lane for the
timing tests (doubling pytest runs per shard) and a new coverage-total variance, for a gain the measurements do not
show where the gate runs. Revisit if the full gate moves to a dedicated host with idle cores.
