# Plan 00260 Journal — 2026-08-20

## Differential testing against a real shell — four more defects, after "done"

Continues from `00260-Journal-26-08-19.md`, which closed with Phase 4 verified
and everything committed. This entry is what happened next, and it is the most
useful thing in either file.

A background code review was dispatched twice for a second opinion and stalled
both times without producing findings. Rather than try a third, I did something
stronger: ran each command through an actual bash and compared the files that
really changed against what the accessor predicted.

This was AFTER the work was committed, QA-green at 23/23, and verified live over
the socket. It found four discrepancies in one pass:

| finding                              | class             |
| ------------------------------------ | ----------------- |
| `cp -t DEST src` reported the SOURCE  | OVERCLAIM         |
| `cp a.py somedir` reported nothing    | MISS              |
| heredoc prose yielded a phantom path  | OVERCLAIM         |
| `mv two operands` mismatch            | my TEST was wrong |

The first is the worst class available here: a file the command READS, reported
as one it writes. A path-keyed guard would judge a file that was never touched
while the real destination went unmentioned.

The second was a live bypass. `cp note.md <memory-dir>` writes
`<memory-dir>/note.md` — the shell told me the exact path — so declining it
meant copying a file INTO a guarded directory reached it without ever naming
the file. Now resolved to the file actually written, which also disposes of
`cp -t <dir> src` and the three-or-more-operand form. `-t` needed one extra
piece of state (`directory_only`), because a `-t` naming a directory that does
not exist must yield nothing rather than be reported as a written file.

The fourth was not a code defect at all, and is worth recording as such: my case
was `cp src -> mv0 && mv mv0 -> mv1`, and the `mv` renamed `mv0` away before the
snapshot. `cp` really did write it. **The test destroyed its own evidence.** A
differential harness is only as good as its observation window, and it is very
easy to read a measurement artefact as a defect — which is why the case is now
a single `mv` and the reason is in a comment.

The third is now a documented contract rather than a bug. Nothing distinguishes
a script being authored from prose containing a redirect — both are data in a
heredoc body — so `include_heredoc_bodies=True` is inherently a SUPERSET. The
old unit test had "passed" while missing this, because it supplied no `cwd` and
the relative target was declined for an unrelated reason. The test agreed with
the code and both were wrong about the contract. It now asserts the phantom
APPEARS, with a cwd, so the next caller meets the cost instead of discovering
it. Recorded as Decisions 5d and 5e.

**The harness is now tracked**, at
`tests/integration/test_bash_write_targets_vs_real_shell.py`: 28 cases, 28/28
exact under the strict contract, ~0.4s. Fixing four defects by hand and leaving
the method blind is precisely what defence-before-fix exists to prevent — and
the method that missed them was "hand-written tests encode what the author
already believes".

Three of my own documentation claims became false the moment the directory
expansion landed — the handler guidance, the staged truth-changes entry, and
the plan all said a directory destination was NOT detected. All three corrected
in the same change. Shipping a guidance claim that the code contradicts is the
exact defect this plan was opened to fix, so leaving one behind would have been
the worst possible ending.

The honest summary across both days: this code was called done three times —
after QA, after the live socket probe, and after the commit — and was wrong
each time in a way only execution could reveal.

## Task 3.5 — the decision came back "get it done", and what that required

The human answered the open product question, so the linters are now wired to
Bash-authored files. The implementation was the easy half; the boundaries were
the work.

**The design question that decided whether this is safe on by default.** A
denying content guard must not act on everything `get_bash_write_targets`
returns. `cp broken.py copy.py` writes a file — the memory-path guard has to
see that, since copying INTO a guarded directory is a real bypass — but a
linter denying it reports a defect the command did not introduce, and leaves
the agent repairing a file it never chose to write. So the split is by what the
guard's premise is ABOUT: a LOCATION guard asks "did a file reach this path?",
which every route can violate; a CONTENT guard asks "is the content this
command produced well-formed?", which a relocation cannot violate because it
produced none. Hence `get_written_file_paths()` — authoring routes only —
recorded as Decision 5f.

**The census had gone stale, and every test still passed.** Wiring the two
handlers should have contradicted
`test_bash_write_blindness_coverage.py`, which recorded both as BLIND. It
did not: 37 tests passed with both rows now false. The table was
hand-maintained and only ever checked for internal consistency — valid verdict
string, argued reason — never against the code it describes. That is the same
defect the file exists to catch, one level up, and it is the second time in
this plan that a green test has agreed with stale documentation (the first was
the heredoc-phantom unit test in Decision 5e). Each verdict is now checked
against the handler's SOURCE: COVERED must show an accessor call, BLIND must
show none. 37 tests became 54, and both directions are exercised, so it cannot
pass vacuously.

**A test defect surfaced by making `handle()` honest.** `handle()` previously
skipped the scope filter `matches()` applies; it had to stop, because a Bash
command can author several files and each needs filtering on its own. Two
ESLint tests then failed — and for a real reason. pytest derives `tmp_path`
from the test FUNCTION NAME, `SKIP_PATHS` is a naive substring test over the
whole path, and the tests were called `test_node_modules_bin_*`. They were
asking the handler to lint a path it is configured to ignore, and had only ever
passed because `handle()` was unguarded. Renamed, with the reason recorded on
the class so the next person does not rediscover it. Worth noting separately:
the substring check means any project directory containing `dist`, `coverage`
or `node_modules` as a SUBSTRING is silently skipped — left alone as out of
scope here, but it is a real sharp edge.

**Three documentation claims falsified by the change, again.** The class-wide
guidance intro said flatly that Bash writes are not seen by the content guards;
that is now false for the linters and still true for the PreToolUse guards, so
it had to state the split rather than pick a side. The staged truth-changes
entry said the linters were "deliberately NOT wired". Both corrected in the
same change, plus a new truth-changes entry and a config-changes manifest so
the new denial surface is announced on upgrade instead of arriving unexplained.

The pattern is now consistent enough to name: **every time this plan changed
behaviour, it falsified something it had itself written down one commit
earlier.** That is not carelessness so much as the nature of a plan whose
subject IS the gap between what the daemon does and what it says — but it means
"update the docs" is not a closing step here, it is part of every step.
