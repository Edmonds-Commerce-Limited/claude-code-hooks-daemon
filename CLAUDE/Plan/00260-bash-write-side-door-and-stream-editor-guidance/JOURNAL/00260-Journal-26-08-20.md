# Plan 00260 Journal — 2026-08-20

## Differential testing against a real shell — four more defects, after "done"

Continues from `00260-Journal-26-08-19.md`, which closed with Phase 4 verified
and everything committed. This entry is what happened next, and it is the most
useful thing in either file.

A background code review was dispatched twice for a second opinion and stalled
both times without producing findings. Rather than try a third, I did something
stronger: ran each command through an actual bash and compared the files that
really changed against what the accessor predicted.

This was AFTER the work was committed, QA-green at 23/23, and verified live over
the socket. It found four discrepancies in one pass:

| finding                              | class             |
| ------------------------------------ | ----------------- |
| `cp -t DEST src` reported the SOURCE  | OVERCLAIM         |
| `cp a.py somedir` reported nothing    | MISS              |
| heredoc prose yielded a phantom path  | OVERCLAIM         |
| `mv two operands` mismatch            | my TEST was wrong |

The first is the worst class available here: a file the command READS, reported
as one it writes. A path-keyed guard would judge a file that was never touched
while the real destination went unmentioned.

The second was a live bypass. `cp note.md <memory-dir>` writes
`<memory-dir>/note.md` — the shell told me the exact path — so declining it
meant copying a file INTO a guarded directory reached it without ever naming
the file. Now resolved to the file actually written, which also disposes of
`cp -t <dir> src` and the three-or-more-operand form. `-t` needed one extra
piece of state (`directory_only`), because a `-t` naming a directory that does
not exist must yield nothing rather than be reported as a written file.

The fourth was not a code defect at all, and is worth recording as such: my case
was `cp src -> mv0 && mv mv0 -> mv1`, and the `mv` renamed `mv0` away before the
snapshot. `cp` really did write it. **The test destroyed its own evidence.** A
differential harness is only as good as its observation window, and it is very
easy to read a measurement artefact as a defect — which is why the case is now
a single `mv` and the reason is in a comment.

The third is now a documented contract rather than a bug. Nothing distinguishes
a script being authored from prose containing a redirect — both are data in a
heredoc body — so `include_heredoc_bodies=True` is inherently a SUPERSET. The
old unit test had "passed" while missing this, because it supplied no `cwd` and
the relative target was declined for an unrelated reason. The test agreed with
the code and both were wrong about the contract. It now asserts the phantom
APPEARS, with a cwd, so the next caller meets the cost instead of discovering
it. Recorded as Decisions 5d and 5e.

**The harness is now tracked**, at
`tests/integration/test_bash_write_targets_vs_real_shell.py`: 28 cases, 28/28
exact under the strict contract, ~0.4s. Fixing four defects by hand and leaving
the method blind is precisely what defence-before-fix exists to prevent — and
the method that missed them was "hand-written tests encode what the author
already believes".

Three of my own documentation claims became false the moment the directory
expansion landed — the handler guidance, the staged truth-changes entry, and
the plan all said a directory destination was NOT detected. All three corrected
in the same change. Shipping a guidance claim that the code contradicts is the
exact defect this plan was opened to fix, so leaving one behind would have been
the worst possible ending.

The honest summary across both days: this code was called done three times —
after QA, after the live socket probe, and after the commit — and was wrong
each time in a way only execution could reveal.
