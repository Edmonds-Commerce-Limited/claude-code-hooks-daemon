## N15: `remote-docs` scans captures with the configured handler

**RED.** Three tests in `TestCaptureScanUsesTheConfiguredHandler` failed on the merged base:

- **Public pattern:** `remote-docs add` of a page carrying a match for a configured `public_patterns` entry exited 0 and wrote the file.
- **Word list:** a page carrying a term from a word list at a non-default path (`config/private/terms.txt`) was also written.
- **Refresh:** `refresh` rewrote a stored copy with a matching body.

All three now refuse. The refusal names the pattern, or `entry 1 of 1 in the secret word list`, never the term itself. My first fixture used a UUID, and this repository's own `session-uuid` public pattern blocked the Write, so the tests use a `ZZQX-CAPTURE-MARKER-NN` pattern of their own.

**Fix.** `_sensitive_content_guard(project_root)` in `daemon/cli.py`:

- loads the project's config;
- reads the handler's options through `handler_options`;
- builds `SensitiveContentHandler()` and gives it those options through a new `handlers.registry.apply_handler_options(instance, options)`.

`apply_handler_options` is the registry's own `setattr(instance, f"_{key}", value)` loop, now shared. `register_all` pass 2 and `playbook_generator._apply_configured_options` both call it, so there is one "apply options like the registry" routine.

The word list path is resolved to an absolute path against `project_root` before it is applied. Otherwise the handler resolves a relative path against `ProjectContext`, which this CLI never initialises. When no path is configured it falls back to `get_active_secret_terms()`, which returns `()` without that context. So before this fix, even the default list was found only by accident.

The guard also catches `ValueError` and `yaml.YAMLError`, so an unreadable config still takes the existing loud "NOT being scanned" path instead of crashing the capture. `_remote_docs_add` and `_remote_docs_refresh` now take `project_root`.

**Class audit: handlers constructed without their config.** I searched `src/` by AST for bare `SomethingHandler()` constructions outside the registry:

## N17: handlers read the options the registry delivers (`bcd9bf61`)

**The class.** The registry delivers options only as `self._<key>` attributes. `configure()` fills a `self.config` dict, but nothing in `src/` calls it, so a handler that reads its options from `self.config` always runs on its defaults. Its unit tests still pass, because they call `configure()` directly.

**RED.** I wrote the class pins first, in `tests/unit/handlers/test_registry_option_injection.py`:

- **`test_every_declared_option_is_delivered_and_read`** builds every handler through the real `register_all` from a config that gives each option a non-default value. The option inventory is the `**Options:**` table of each handler's `HANDLER_REFERENCE.md` section. The test fails if the value did not arrive as `self._<key>`, or if the handler's source never reads that attribute outside `__init__`. "Delivered" means the value differs from a bare-constructed handler's default. `bash_safe_mode` validates its options, so it gets a valid non-default from `_VALID_NON_DEFAULTS` instead of a sentinel. `secret_file_guard`'s `allow_plain_hash` is read outside the handler, and `_READ_OUTSIDE_THE_HANDLER` records why.
- **`test_no_handler_reads_an_option_from_a_configure_dict`** is an AST scan for a read of any key other than `enabled` from `self.config`. It catches handlers that have no reference section. A companion test exercises the scan on both read shapes.

On the base both pins failed on exactly three handlers, and nowhere else.

**Fix.**

- **`skill_opportunity_detector`:** N17 itself. `__init__` declares the five option attributes, and `_options()` builds `SkillScanOptions` from them. `check_interval_days` was ignored.
- **`hook_registration_checker`:** same class, found by the pin. It read `auto_migrate_settings` and `auto_repair_registrations` from `self.config`, so `auto_migrate_settings: false` did not stop it rewriting `settings.json`. That includes this repository's own `.claude/hooks-daemon.yaml`, which sets it. `configure()` and the dict are gone, and both options are `self._` attributes defaulting to `True`.
- **`version_check`:** same class, found by the pin. `cache_ttl_hours` was ignored. It is now `self._cache_ttl_hours`. A value that is not a number or a string falls back to 24 hours, and a string that does not parse as a number takes the existing "cache invalid" path. The option was undocumented, so `HANDLER_REFERENCE.md` gained an Options table and an example for it.

The existing unit tests for all three now go through `apply_handler_options` rather than `configure()`, so they exercise the production path. `version_check` gained `test_configured_cache_ttl_hours_is_honoured`.

**Left alone.** `config_optimisation_reminder`, `contract_staleness`, `remote_docs_staleness` and `version_check` still have a `configure()` that reads only `enabled`. That code is dead in production but harmless, and the pin allows it.

## N19: an options-collection failure is loud (`4bb2a733`)

**RED.** `tests/unit/handlers/test_registry_option_collection_failure.py` patches `registry.handler_options` to raise for one configured handler (`destructive_git`). Seven of the nine tests failed on the base:

- no ERROR record named the handler;
- the registry had no failure record;
- `get_health()` had no `option_failures`;
- `health` exited 0 and printed nothing about it.

The two tests that passed on the base are guards that must stay true: the other handlers still get their options, and the failed handler still registers on its defaults.

**Fix.**

- **The catch.** The pass-1 `try` now covers only the `handler_options(handler_config)` call. The registry key, the `workspace_root` addition and the write into `options_registry` all moved outside it.
- **What a failure does.** It is logged at ERROR with the registry key (`PreToolUse.destructive_git`) and a traceback. It is recorded in `HandlerRegistry.option_failures` as `{key: "ExcType: message"}`, and the loop moves on to the next handler. The failed handler registers on its defaults.
- **A second bug.** The old debug call had two `%s` placeholders and one argument, so even the debug line would have failed to format.
- **Health.** `DaemonController.get_health()` adds `option_failures` when any exist. `hooks-daemon health` prints a "Handler options" section, either `OK` or a DEGRADED list naming each handler and reason, and exits 1 when any exist.
- **Docs.** Both copies of the `hooks-daemon` skill's `health.md` describe the new section.
- **Unchanged.** `status` stays `healthy`/`degraded` for config validation only. Setting it would have made `status` and `check` print the config-degraded block with no config errors under it.

**A judgement call for the coordinator.** The ledger asked me to narrow the catch "to the exceptions that option collection can legitimately raise". After N14, `handler_options` reads every block shape without raising. So there is no exception class that collection can legitimately raise, and nothing narrower to name in the `except` clause. I narrowed the `try` to that one call and kept `except Exception`. Anything it catches is a daemon defect, and it is now reported at error level and in `health` rather than hidden. The alternative is to let it propagate and crash `register_all`. That matches the fail-fast contract of the module import just above it, and it would have made the N14 regression fail every registry test outright. I chose not to. A crash turns one handler on its defaults into a daemon with no protection at all, and the controller's own config-validation path already prefers degraded-and-visible over a crash. If you prefer fail-fast, it is a one-line change, and the error-log and health tests would be replaced by a raise test.
