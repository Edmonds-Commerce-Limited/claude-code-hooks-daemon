**One implementation.** `plan_qa/checks/stats_arithmetic.py` holds the patterns, the pure `stats_arithmetic_disagreements(text)` function, which returns `(line, message)` records with the line number inside the message, and the remediation text. `scripts/qa/check_repo_hygiene.py` keeps its `plan_stats_arithmetic(root)` only as a thin adapter, and imports `CHECK_ID` and `REMEDIATION`. `test_there_is_exactly_one_implementation` fails if the folderless-clause regex appears in any other `src/` or `scripts/` file.

**Registration.** The check carries `sins=("B5",)`, the statistics-drift sin that `stats-recount` also carries.

- **COMMIT** blocks only when the commit stages the plan index AND the disagreement is not already present in HEAD's index (`commit_scoped_level`). A commit that does not touch the index gets an advisory, so inherited drift cannot trap unrelated commits (Plan 00343's rule).
- **SWEEP** blocks, which puts it in `plan-qa --sweep`.
- **EDIT** is advisory only. Updating the bullet takes more than one edit, so a block would deny the first half of a correct update. This is the same reasoning `index-retention-window` documents for having no EDIT registration at all.

## N15: `remote-docs` scans captures with the configured handler

**RED.** Three tests in `TestCaptureScanUsesTheConfiguredHandler` failed on the merged base:

- **Public pattern:** `remote-docs add` of a page carrying a match for a configured `public_patterns` entry exited 0 and wrote the file.
- **Word list:** a page carrying a term from a word list at a non-default path (`config/private/terms.txt`) was also written.
- **Refresh:** `refresh` rewrote a stored copy with a matching body.

All three now refuse. The refusal names the pattern, or `entry 1 of 1 in the secret word list`, never the term itself. My first fixture used a UUID, and this repository's own `session-uuid` public pattern blocked the Write, so the tests use a `ZZQX-CAPTURE-MARKER-NN` pattern of their own.

**Fix.** `_sensitive_content_guard(project_root)` in `daemon/cli.py`:

- loads the project's config;
- reads the handler's options through `handler_options`;
- builds `SensitiveContentHandler()` and gives it those options through a new `handlers.registry.apply_handler_options(instance, options)`.

`apply_handler_options` is the registry's own `setattr(instance, f"_{key}", value)` loop, now shared. `register_all` pass 2 and `playbook_generator._apply_configured_options` both call it, so there is one "apply options like the registry" routine.

The word list path is resolved to an absolute path against `project_root` before it is applied. Otherwise the handler resolves a relative path against `ProjectContext`, which this CLI never initialises. When no path is configured it falls back to `get_active_secret_terms()`, which returns `()` without that context. So before this fix, even the default list was found only by accident.

The guard also catches `ValueError` and `yaml.YAMLError`, so an unreadable config still takes the existing loud "NOT being scanned" path instead of crashing the capture. `_remote_docs_add` and `_remote_docs_refresh` now take `project_root`.

**Class audit: handlers constructed without their config.** I searched `src/` by AST for bare `SomethingHandler()` constructions outside the registry:

- `daemon/cli.py` `_sensitive_content_guard`: **N15 itself, fixed.**
- `daemon/cli.py` `_collect_enforcement_status_lines` (`hooks-daemon check`): **same class, fixed.** `LintOnEditHandler` was built bare, so its enforcement probe ignored the configured `languages` option and `daemon.languages`. That made it report missing extended linters for languages the project does not lint. RED: both parametrised cases failed with a `lint_on_edit: Shell ...` line under a Python-only config. The three probe handlers now get their options and `_project_languages` the way the registry sets them.
- `daemon/controller.py` `DestructiveGitHandler()`: **intended.** This is the degraded-mode guard, and the config is invalid by definition in degraded mode.
- `daemon/cli.py` `OptimalConfigCheckerHandler()` and `GitFilemodeCheckerHandler()` in `check`: **intended.** Neither declares options.
- **Dynamic `handler_class()` constructions** read only static metadata: tags, priority, default-enabled, rules, CLAUDE.md text, tier and relevance. They are in `config/models.py:326`, `config_optimisation/checklist.py`, `daemon/docs_generator.py`, `rule_explain/lookup.py`, `utils/session_action_items.py` and `daemon/cli.py` status-line-explained. **Not affected.** `plugins/loader.py` and `handlers/project_loader.py` build plugin and project handlers, and those config blocks have no `options` field, so there is nothing to miss.

**Pin.** The new test in `test_handler_options_accessor.py` walks every `src/` function. It fails on any construction of a built-in hook handler class (the names come from `iter_builtin_handler_classes()`) in a function that never calls `apply_handler_options`. Constructions whose defaults are intended sit in an allowlist, each with its reason. Run against the pre-fix `cli.py`, it flagged exactly the four sites fixed above. A companion test exercises the detector itself.
