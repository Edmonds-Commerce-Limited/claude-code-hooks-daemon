## 1. BLOCKER: Fable is raised above low by the new floor, then anchored back

**Where:** `.claude/ccy/claude-supervise.py:4289` (`target = self._resolve_effort_for_family(family, now_wall=now_wall)`), fed by `_resolve_family_effort` at `:1684-1686`.

The top-level `effortLevel` fallback applies to every family, fable included. The floor path has no anchor ceiling. The clamp exists only in `_coupled_effort_target` (`:3818-3823`).

**Repro:** probe sections 3 and 3b, using the OWNER settings.json.
```
[S3 fable low under owner settings] live=claude-fable-5-1@low -> would-effort payload='/effort medium'
  tick 0 t=+0s   live=low    -> would-effort '/effort medium'
  tick 1 t=+200s live=medium -> would-effort '/effort low'      (DROP ANCHOR)
```
On the owner's own machine, the first idle tick of a Fable spell types `/effort medium`, which breaks the Plan 00297 invariant that Fable never runs above low. DROP ANCHOR then has to undo it. Plan 00297 exists because exactly this kind of correction was once swallowed by a busy session, and Fable then ran above low for about an hour.

NIGGLES.md N47 requires: "The fable anchor clamp (Plan 00297) stays as a ceiling." Before this change, the Fable floor came from `fable=low` in ccy.env, so this path could not fire.

**Direction:** apply the anchor ceiling inside `_resolve_effort_for_family`, so every consumer (floor, coupled, restore) gets the clamp. That means `min(configured, _ANCHOR_TARGET_EFFORT)` for the top-rank family. Add a RED test using the owner-shaped settings (top-level medium, no Fable entry, live Fable at low) that asserts no `/effort` is sent.

## 2. MAJOR: only the user settings file is resolved

**Where:** `.claude/ccy/claude-supervise.py:1657-1660` (`_main_settings_path`) and `:1703` (`SettingsEffortCache` reads a single path).

**Evidence from the vendored docs:**
- `remote-docs/docs.claude.com/en/docs/claude-code/settings-reference.md:1189`: "Across files, Claude Code resolves each model separately: the highest-precedence settings file that sets either an `effortLevel` for that model or a top-level `effortLevel` that applies to that model decides."
- `settings.md:640-646`: precedence is managed > command line (`--settings`) > project local > shared project > user.
- `settings-reference.md:668` and `:709`: both keys have Scope "Any file". Effort does not ignore project scope.

The plan's own remedy says: "in its precedence order: per-model `modelSettings` over `effortLevel`, project over user".

**Repro:** put `{"effortLevel": "low"}` in `<project>/.claude/settings.json`, keep `medium` in the user file, and run Opus 5 at low. Claude Code runs low. The supervisor resolves `medium` from the user file and types `/effort medium`. The fight is back. (This is not in the probe because the supervisor has no project-path input at all, so there is nothing to drive.)

**Direction:** resolve over the list [managed `managed-settings.json`, `<cwd>/.claude/settings.local.json`, `<cwd>/.claude/settings.json`, user], taking the first file that sets a value applying to the model. The project root is the supervisor's cwd, which is the ccy launch dir. Cache each file by mtime. `--settings` cannot be seen and can be documented as a known gap.

## 3. MAJOR: resolution is per family, not per model id

**Where:** `.claude/ccy/claude-supervise.py:1677-1683`. The loop walks `sorted(model_settings)` and returns the first entry whose id maps to the same family.

The docs (`settings-reference.md:1197`) say Claude Code keys the entry by canonical model name and matches alias, date-suffixed and `[1m]` ids to that one entry. It never matches a sibling model.

**Repro:** probe section 4.
```
modelSettings: claude-opus-5 -> xhigh, claude-opus-5-5 -> medium
[S4 live opus-5-5 @medium] -> would-effort payload='/effort xhigh'
```
`"claude-opus-5"` sorts before `"claude-opus-5-5"`, so the Opus 5 entry wins for an Opus 5.5 session. The owner's own file already has both keys, so this is one `/effort` in the Opus 5 picker away from firing live.

Alias, `[1m]` and unknown ids currently behave (probe section 7: an `opus` alias key matched `claude-opus-5-5[1m]`, and `gpt-9` produced no action). That works only because matching is by family.

**Direction:** pass the reading's `model_id` into the resolver. Normalise it by stripping `[1m]`, a date suffix and a provider prefix. Match `modelSettings` keys by exact canonical id first, then by alias key (`opus`, `fable`, …), and never by a sibling version.

## 4. MAJOR: a user-file top-level `effortLevel` is wrongly applied to Opus 5.5

**Where:** `.claude/ccy/claude-supervise.py:1684-1686`.

**Evidence:**
- `model-config.md:550`: "a top-level `effortLevel` in your user settings file doesn't count for Opus 5.5 … Opus 5.5 and models released after it start at their own default."
- `settings-reference.md:921` says the same.

**Repro:** probe section 5. With a user file of `{"effortLevel":"xhigh"}` and live Opus 5.5 at medium (Claude Code's own default there), the result is `/effort xhigh`.

**Direction:** apply the user-file top-level key only to models released before Opus 5.5, per the docs list (Opus 5, Fable 5.1 and earlier). Apply a project, local or managed top-level key to every model. This needs the model id from finding 3.

## 5. MAJOR: when nothing is configured, the defaults still fight Claude Code

**Where:** `.claude/ccy/claude-supervise.py:1418-1423` (`opus: high`) and `:3767`.

**Evidence:** `model-config.md:548`: the default is "`high` on every model that supports effort, except that Opus 5.5 defaults to `medium`, Opus 4.7 defaults to `xhigh`". The owner's requirement was "we need a SSoT and defaults and claude main settings.json should be it". The defaults should be Claude Code's, not a second table.

**Repro:** probe section 6. With no settings file and live Opus 5.5 at medium, the result is `/effort high`. This is the same `/effort high` over medium that N47 was filed for, and it now reaches any user without a `modelSettings` entry (for example, after `/effort auto` clears one).

**Direction:** when settings configures nothing for the model, do nothing, because Claude Code already applied its own default. Alternatively, encode Claude Code's per-model defaults keyed by model id, not family. Fable stays pinned by the anchor.

## 6. MAJOR: the new `is_restore` branch cannot be reached, and the xhigh path it was meant to fix remains

**Where:** `.claude/ccy/claude-supervise.py:3824-3825` (`if is_restore: return self._resolve_effort_for_family(family)`) and `:6492`.

**Why it cannot be reached:**
- An episode opens only when `_family_rank(prev_family) == _TOP_FAMILY_RANK` (`:4248`).
- `_downgrade_from_family` is set only there (`:4277`).
- So `model_restore_due` always returns the top family (fable), which takes the earlier top-rank branch.
- A restore to a non-top family never reaches `is_restore`.

**Repro:** probe section 11 shows a Fable→Opus attributed downgrade, then the restore. The restore is `/model fable`, and the pending coupled effort is `probe-sess:fable:low`, which is the pre-existing path. Probe section 12 shows that a switch back to Opus via `--emit-model-switch opus` still arms `probe-sess:opus:xhigh`.

The only test of the new branch, `tests/unit/supervise/test_effort_restore.py:636-647`, calls `arm_coupled_effort(family="opus", is_restore=True)` directly. It tests an input that production never produces, so it is TDD theatre for the claimed fix.

NIGGLES.md's remedy asks for "A switch back to a configured model sets that model's configured effort. `xhigh` compensation applies only while a downgrade leaves the session on a fallback model." A manual switch to Opus with no open episode is not "a downgrade leaving the session on a fallback", yet it still gets xhigh.

**Direction:** decide the xhigh compensation from whether a downgrade episode is open for the destination, not from which injector typed `/model`. Drive the RED test through `_poll_once` or `decide_once` from a real sidecar sequence, not through `arm_coupled_effort` directly. If the owner's reported "restore back to Opus" was really the manual switch path, name that path in the test.

## 7. MAJOR: a degraded settings.json is never logged

**Where:** `.claude/ccy/claude-supervise.py:3769` (`take_settings_error_note`) has no caller. `grep -c take_settings_error_note` on the supervisor returns 1, which is the definition only. It is exercised only by `tests/unit/supervise/test_settings_effort.py:176-204`.

In addition, a missing file is deliberately silent (`:1720`: `last_error` is set only when a previously-loaded file disappears).

**Repro:** probe section 9. Malformed, list-shaped and null files set `last_error`, but the outcome's `deferred_log` and `noop_reason_log` are both `None`, and nothing reaches the decision log. A `modelSettings` that is not a dict, or an integer `effortLevel`, does not even set `last_error`.

The N47 RED test list requires "a missing or unreadable settings file degrades to the current defaults with a logged reason".

**Direction:** wire the note into `decide_once` (or the host's per-tick log flush), the same way the other consume-once notes are (for example `_unattributed_downgrade_note`). Report a missing file once at startup. Add a test that asserts the decision-log line.

## 9. MINOR: hot reload of the coupled-target change needs a full relaunch

**Where:**
- `.claude/ccy/claude-supervise.py:6427` (`_apply_post_injection_bookkeeping`) runs in the HOST loop (`:7440`), and that is what calls `arm_coupled_effort` → `_coupled_effort_target`.
- `CLAUDE/development/CcySupervisor.md:114-124` (new section) says only a code edit needs the reload procedure, and that settings.json needs none.

A worker reload picks up the new floor path, because `decide_once` runs in the worker and the worker builds its own `CompactPolicy()`. The coupled target, however, is armed by the never-reloading host with its launch-time code, and the host's in-process fallback also runs old code.

Mixed versions do not crash:
- Old host with new worker: no policy crosses the wire, the `TickOutcome` fields are unchanged, and `model_switch_is_auto_restore` already existed on main.
- New host with old worker: the old worker builds its own `CompactPolicy(min_effort_levels=…)`.

**Direction:** say in CcySupervisor.md (and in the release note, for the dogfood session) that the coupled-target and fallback parts need a ccy relaunch. Alternatively, move target resolution to decision time in the worker: arm with family only, and resolve the target when the coupled `/effort` is decided at `:5704`.

## 10. MINOR: explicit effort sources are ignored

**Evidence:** `model-config.md:546` gives the resolution order. An explicit choice comes first: the `CLAUDE_CODE_EFFORT_LEVEL` env var, `--effort` at launch, or `/effort`. The supervisor inherits the claude env (it wraps the process) but never reads `CLAUDE_CODE_EFFORT_LEVEL`.

**Direction:** if `CLAUDE_CODE_EFFORT_LEVEL` is set in the supervisor's env, treat it as the configured level for every model, or stand the floor down.
