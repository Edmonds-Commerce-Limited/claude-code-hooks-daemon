## BLOCKER

### BLOCKER-1: the Agent-terminated-early signal never fires on the documented or observed PostToolUse:Agent shape

**Where:**

- `src/claude_code_hooks_daemon/handlers/post_tool_use/budget_exhaustion_detector.py:367-374` (`_stringify_tool_response`)
- `tests/unit/handlers/post_tool_use/test_budget_exhaustion_detector.py:427-446`

**The real shape.** A completed foreground Agent call gives PostToolUse a
`tool_response` object whose `content` is an ARRAY of text blocks:
`[{"type": "text", "text": ...}]`. The vendored
`remote-docs/code.claude.com/docs/en/hooks.md:1775-1786` says so. Every real
record in the transcripts agrees (`probe_n46r2_shapes.py`, output in
`probe_n46r2_shapes_out.txt`). The three real `completed` occurrences all have
the keys `agentId, agentType, content(list), ..., status, totalDurationMs, usage`.

**Why it misses.** `_stringify_tool_response` returns `content` directly only
when it is a `str`. A list falls through to `json.dumps` of the whole dict. That
string begins `{"agentId": ...`, so the `\A\s*Agent terminated early` anchor can
never match. It also matches nothing else, because the anchor is the whole
point of the pattern.

**The tests.** Every Agent test passes `{"content": "<string>"}`. That shape
does not occur in any of the 351 real Agent/Task results in the corpus.

**The is_error variant is not reachable through PostToolUse either:**

- A failed tool call goes to `PostToolUseFailure`, not `PostToolUse`
  (hooks.md:2014: PostToolUse fires "after a tool has already executed
  successfully"), and this is a PostToolUse handler.
- Even as a string, the real `toolUseResult` for that record begins
  `"Error: Agent terminated early..."`, so the anchor fails on it too.
- `test_the_is_error_variant_fires` (line 444) therefore tests a payload that
  cannot reach the handler.

**Reproduction.** Run `probe_n46r2_replay.py`, output in
`probe_n46r2_replay_out.txt`. It replays every real Agent/Task result through
the branch handler.

| Replayed as                                                                  | Real occurrences that fire        |
| ---------------------------------------------------------------------------- | --------------------------------- |
| `toolUseResult` (what PostToolUse carries)                                   | **0 of 4**                        |
| tool_result block content (what the model sees, not the PostToolUse payload) | 1 of 4 (only the is_error string) |

`probe_n46r2_edges.py` section 2 checks the synthetic shapes:

| Shape                                           | Fires |
| ----------------------------------------------- | ----- |
| dict with string `content` (what the tests use) | True  |
| dict with list `content` (the documented shape) | False |
| bare list of blocks                             | False |

**The false-positive count is 0 of 347 ordinary Agent/Task results.** That is
vacuous: the handler cannot fire on any real dispatch shape at all.

**Direction:**

- In `_stringify_tool_response`, when `content` is a list, join the `text` of
  its `type == "text"` blocks, or at minimum use the first text block. Do this
  for dispatch tools at least, so the anchor sees the sub-agent's own first
  text.
- Rewrite the Agent tests to use the documented object: `status`, `agentId`,
  `content` as a list of blocks, and the telemetry keys. Better still, use a
  fixture copied from one of the redacted real records.
- Delete or re-scope the is_error test. Either register the signal on
  `PostToolUseFailure` with that event's real payload (`error` field, text
  prefixed `Error: `), or drop the "one is_error: true" occurrence from the
  claims at handler line 36 and test line 396. As written, those lines claim
  coverage of four occurrences, and the handler covers none.

## MAJOR

### MAJOR-1: the migration note tells operators to do the opposite of what restores their alert

**Where:** `CLAUDE/UPGRADES/UNRELEASED/config-changes/v3.67.0.yaml:116-117`

The note says: "Add `Bash` back to `excluded_tools` explicitly to restore
matching for that tool." Adding Bash to `excluded_tools` *excludes* it, and Bash
is already in the new default. The operator needs to set `excluded_tools`
explicitly to a list WITHOUT `Bash`. As written, an operator who follows the
note keeps the alert silenced and believes they restored it. The release note
(34, "can re-include it via `excluded_tools`") and HANDLER_REFERENCE.md:3171
("requires removing `Bash`") both have it the right way round, so the manifest
contradicts the two docs beside it.

**Reproduction:** read line 116, then compare it with `_prepared_response_text`
(handler line 563), which returns None for any tool in the list.

**Direction:** reword the note to "set `excluded_tools` explicitly to the new
default minus `Bash`, e.g. `[Read, Grep, Glob, Edit, Write, NotebookEdit]`".

### MAJOR-2: the session UUID is still in branch history, and no gate would catch it on merge

**Where:** the blob of
`CLAUDE/Plan/00466-niggles-ledger-sixteen/subagent-reports/260925-n46-review1-opus-5-5.md`
at commit `3da8c1ed`. HEAD `f41ff342` replaces it with the all-zero
placeholder.

- `git log -S<uuid>` over `merge-base..HEAD` lists both `3da8c1ed` (which
  introduced it) and `f41ff342` (which removed it). Neither the main tree nor
  main's history holds it.
- `scripts/qa/check_sensitive_content.py` exits 0 at HEAD. It scans only
  `git ls-files` content, and the current blob is clean.
- `scripts/qa/check_git_history.py` exits 0. It sweeps commit messages,
  identities, ref names and tag messages, but not historical blob contents.
  Its own docstring confines it to metadata.
- **Nothing flags it.** The project's `session-uuid` public pattern DOES match
  the historical blob (1 hit when replayed against that blob). No gate that
  runs at merge or push scans old blobs.
- **Merging publishes it.** Squash merges are denied (R-GIT-MERGE-SQUASH), so a
  `--no-ff` merge carries `3da8c1ed` into main's ancestry. `origin` is the
  GitHub repository, and a push of main publishes the blob permanently. The
  branch is not on any remote yet (`git ls-remote` finds no match), so it can
  still be fixed without a force-push.
- **The commit gate should have denied `3da8c1ed` and did not.** The
  sensitive_content commit gate scans the ADDED lines of staged files. The
  pattern matches, and no `exclude_paths` entry covers `CLAUDE/Plan/`. I did
  not find why it let the commit through. One untested hypothesis: the commit
  ran with a cwd or `-C` target that differed from the checkout the gate
  diffed.

**Direction:**

- Before merging, rebuild the branch so no commit carries the UUID. For
  example, recreate it on the merge-base by cherry-picking with `3da8c1ed`'s
  report blob already redacted. This is a history rewrite of an unpushed
  branch, so the owner must approve it. Do not paper over it with a follow-up
  commit.
- File a niggle for the commit-gate miss, with a reproduction in a scratch
  repo.
- Optionally add a merge-time check that runs the public patterns over
  `git log -p main..<branch>` added lines, because that is exactly the window
  in which this leak survives.

## MINOR

### MINOR-3: un-excluding Task/Agent routes `extra_patterns` over the dispatch brief and telemetry

**Where:** handler lines 141-175 (the default exclusion) and 371-372 (the
`json.dumps` fallback)

Before this change, Task/Agent were excluded, so `extra_patterns` never saw
them. Now:

- Every non-string `content` falls back to `json.dumps(tool_response)`, and
  that dump includes `prompt`, which is the orchestrator's own brief.
- The same goes for the `teammate_spawned` (188) and `async_launched` (76)
  shapes, which have no `content` at all.

**Result:** an `extra_patterns` entry fires whenever the brief *mentions* its
term. In `probe_n46r2_edges.py` section 3, `extra_patterns: ["budget"]` fires
on a dispatch whose sub-agent replied only "done", because the prompt was
"Review the budget detector". A sub-agent report quoting the term fires too.
The manifest entry does not tell `extra_patterns` users about this new
surface.

On timing, no regression was measurable. A 1 MB Agent result costs about 124
ms for matches and handle together, and about 85 ms with one extra pattern;
most of that is the ledger-strip scanner. The worst real result was 1.7 ms.

**Direction:**

- For dispatch tools, scan only the joined text blocks of `content`. This is
  the same function as the BLOCKER fix. Never scan `prompt` or the telemetry.
- Add one line to the manifest `migration_note`: `extra_patterns` now also
  applies to Task/Agent results.

### MINOR-4: the advisory ignores `name`, and the signal is structurally foreground-only

**Where:** handler `_dispatch_identity`, lines 449-463

**Identity.** All 351 real Agent/Task calls carry `description`, so the
"missing description" path never occurs in the corpus. When it is missing, the
fallback is `subagent_type` (e.g. `'Explore'`). It ignores `name`, which 243
of the 351 calls set, and which is the handle SendMessage needs for a re-brief.
It also ignores `tool_response.agentId`. Output from `probe_n46r2_edges.py`
section 5:

| Payload                        | Advisory names          |
| ------------------------------ | ----------------------- |
| description present            | `'review N23'`          |
| no description                 | `'Explore'`             |
| `name` present, no description | `'an unnamed dispatch'` |
| empty dict                     | `'an unnamed dispatch'` |
| `None`                         | `'an unnamed dispatch'` |

**Foreground only.** Only `status: completed` results carry `content`. The
async and teammate dispatches (264 of 351 in the corpus) return at launch, so
a limit that kills them later never arrives through PostToolUse:Agent. The
docstrings and release note 34 read as if every dead sub-agent is surfaced.

**Direction:**

- Include `name` alongside `description`, falling back to `agentId`.
- State the foreground-only scope in the docstring, the HANDLER_REFERENCE
  entry and release note 34.

## NIT

### NIT-6: a report that opens with an unquoted copy would fire once BLOCKER-1 is fixed

With string content today, a sub-agent whose first line is the bare phrase
fires. A quoted, blockquoted or fenced copy does not. See
`probe_n46r2_edges.py` section 1:

| Report text                   | Fires    |
| ----------------------------- | -------- |
| mid-text quote                | False    |
| begins with a `'`-quoted copy | False    |
| begins with a blockquote      | False    |
| begins with a fenced copy     | False    |
| begins with the bare phrase   | **True** |

The risk is low, but the harness text has a stable tail, `(error type rate_limit, HTTP 429`.

**Direction:** extend the anchor to require that tail on the first line.
