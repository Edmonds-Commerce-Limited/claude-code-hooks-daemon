## What the exemption is now

`shell_expansion.brace_expansion_view` neutralises braces only in the program text of a top-level simple command, and only when all of the following hold:

- The command word is `python`, `python3` or `python3.X`, named bare or from `/usr/bin`, `/bin` or `/usr/local/bin`.
- Nothing precedes it except `NAME=value` words. A wrapper is not allowed.
- The program text is either the single-quoted word right after `-c`, or the one quoted-delimiter heredoc (not `<<-`) that is Python's stdin program (`python3 - <<'EOF'` or `python3 <<'EOF'`).
- Only Python options the scanner knows come before the program.

The whole line must also pass these checks:

- No pipe stage follows the command.
- No process substitution appears anywhere in the line.
- The command is not inside a subshell, group, compound command or substitution.
- No top-level `exec`, `eval`, `coproc`, `builtin` or `command` appears.
- Nothing redefines the name: no function, `alias`, `hash`, `enable`, `PATH` word, `source` or `.`.
- There is no input redirect or here-string.
- Output goes to the terminal, a 1/2 dup or `/dev/null`. The one exception is an output file, and only when every other command in the line is one of `set`, `cd`, `pushd`, `popd`, `echo`, `printf`, `pwd`, `true`, `false`, `:` or `mkdir`.
- The program must parse, or it is not exempted.

The new `utils/python_program_reach.py` decides whether a program "reaches beyond stdout". It is an allowlist. A program reaches if it imports anything outside a small stdlib list, names a spawn, write, fd or dynamic-code name (even as a string, as `getattr` would), touches a dunder outside a short list, or calls `open` in a mode that is not read-only. When any exempted program in the line reaches, or its output goes to a file, the string literals of every exempted program in the line are returned in `view.literals`. `_brace_expansion_tokens` then enumerates them, so a brace-spelled protected path still denies, and an over-cap literal still fails closed.

## N102, N103, N104, N105

- **N102** (grep regex denied in compound commands): not fixed. The remedy widens `is_grep_pattern_only_mention` to compound commands and to patterns containing `*`, which that exemption refuses today. That is a design choice that widens an allow, so it is for the owner. Open questions: may a quoted `*` count as regex rather than glob once the grep is identified, given `grep --include`, `find -name` and git pathspecs? And how is each grep's argument position found inside a compound command without the unparsed-fallback risk?
- **N103** (`**` walk past cap): not fixed. The ledger entry already states the choice the owner has to make: what a walk past the cap means for a word no receiver expands. Deciding "judge by spelling only" is a widening.
- **N104** stays pinned. The NIGGLES entry now says why it cannot be narrowed safely. A written `.py` file is text a later command can run, so it is always a program that passes its text on. Narrowing it would need the same reach analysis over the whole file, and would also have to accept that the module can be imported by code the guard never sees.
- **N105** (new): the data-sink heredoc exemption ignores redefinitions in the same command. For example, `cat() { bash; }; cat <<'EOF'` has its body blanked for every consumer. This was confirmed with `strip_quoted_heredoc_bodies`, and it is present on main too. It is recorded in NIGGLES.md and PLAN.md. The fix is to withhold the exemption when the line's shell-level text redefines a name, which needs quote-and-body masking in `shell_segmentation`.

## Residual

A value assembled at runtime (`'id_' + 'rsa'`, `str({1,2}).replace(' ', '')`) is outside every spelling-based scan. That is the same precedent both reviews accepted. It is stated in `python_program_reach`'s module docstring.
