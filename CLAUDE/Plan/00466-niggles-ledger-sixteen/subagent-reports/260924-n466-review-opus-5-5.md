## Major

### M1 — guard-defects (N6): `enforce_llm_qa` became allow-by-default, and 16 real invocations of the runner now pass

- **Where:** `.claude/project-handlers/pre_tool_use/enforce_llm_qa.py:35`, and `:114-151`, in particular `:143` `if head not in _WRAPPER_COMMANDS: return False`.

- **Cause:** The fix deleted the inspection/VCS allowlists and now denies only when the script is at a segment's head or is an argument to one of six named wrappers. Anything else that executes the script is allowed.

- **Failure scenario:** In `probe_n466review_llmqa_branch.txt`, each of these is DENY on main and ALLOW on the branch:

  - `source scripts/qa/run_all.sh`, `. scripts/qa/run_all.sh`
  - `time ./scripts/qa/run_all.sh`, `CI=1 ./scripts/qa/run_all.sh`
  - `(cd scripts/qa && ./run_all.sh)`, `(./scripts/qa/run_all.sh)`, `{ ./scripts/qa/run_all.sh; }`, `! ./scripts/qa/run_all.sh`
  - `if true; then ./scripts/qa/run_all.sh; fi`, `for …; do ./scripts/qa/run_all.sh; done`
  - `nohup …`, `sudo …`, `command …`, `setsid …`, `stdbuf -oL …`
  - `echo scripts/qa/run_all.sh | xargs bash`

  The subshell form `(cd scripts/qa && ./run_all.sh)` and the `time` and `VAR=1` prefixes are everyday agent shapes.

- **What the tests pin:** the new tests cover only shapes that were already denied on main (`cd && ./run_all.sh`, `sh -c`, `$(…)`), so nothing guards against these.

- **What the ledger claims:** "a command whose head is not a wrapper and does not itself name the script now correctly can't execute it". That is false.

- **Fix direction:** Keep deny-by-default and fix only the tokenisation, which is the real cause of the false positive:

  - deny when any shlex word *is* the script (equal to `run_all.sh`, or ending in `/run_all.sh` with no whitespace in the word);
  - tokenise with `punctuation_chars=True` so `(`, `)` and `{` split off;
  - skip leading `VAR=value` words;
  - restore the inspection/VCS head allowlist for data consumers.

  A quoted multi-word `--title "... run_all.sh ..."` is one shlex word that is not the script, so the reported false positive is still fixed. Add RED tests for the shapes above.

### M2 — goal-flip (N3): after a daemon restart, completing a plan no longer retracts it from the combined `/goal` signal

- **Where:** `src/claude_code_hooks_daemon/handlers/post_tool_use/goal_injection.py:686` (new gate) together with `:736` (`_maybe_refresh_on_retirement` requires the in-memory `self._fired` latch).

- **Cause:** The retirement refresh runs only for a plan this daemon process latched. On main, any later Write/Edit of the still-In-Progress plan re-fired and re-latched after a restart, for example a task tick. Under N3 a non-flip write never re-latches. A daemon restart between the flip and the completion therefore silently disables the refresh that Plan 00299 added.

- **Failure scenario:** `probe_n466review_goal.py` scenario A:

  1. Plans 00296 and 00298 flip.
  2. The daemon restarts (a new handler instance).
  3. The agent ticks a task in 00296, then flips it to Complete.
  4. Main's signal then names only `00298`. The branch's signal still names `00296,00298`, so the completed plan keeps its `/goal`.

  Daemon restarts happen routinely here, because `daemon_restart_verifier` requires one before a commit.

- **Fix direction:** In `_maybe_refresh_on_retirement`, decide "this session ledgered the plan" from the persistent `GoalLedger` rather than from `self._fired`. Alternatively, restore the latch, without re-emitting, when a non-flip write lands on a plan the ledger already holds for this session. Add a restart test: a fresh handler instance, then a terminal flip, then the signal no longer names the plan.

### M3 — goal-flip (N3): the Plan 00269 design that made the goal survive a session restart is removed without a replacement or a disclosure

- **Where:**
  - `goal_injection.py:26-39` (module docstring) and `:686`;
  - `CLAUDE/UPGRADES/UNRELEASED/release-notes/13-goal-injection-no-longer-fires-on-any-edit-of-an-already-in-progress-plan.md`;
  - `CLAUDE/Plan/Completed/00269-supervisor-goal-message-injection/PLAN.md:118-128`.
- **Cause:** Plan 00269 Task 2.1 chose STATE semantics on purpose: "the first edit to an already-In-Progress plan in a NEW session re-fires. That is intended: it is what makes the goal survive session restarts". N3 reverses that decision. Nothing in the daemon re-asserts the goal on a new session: no SessionStart consumer reads `GoalLedger`. The only paths left are a real flip and the manual `inject-goal`.
- **What the documentation says:**
  - The module docstring says "a genuine flip re-fires in a new session exactly as before". That is misleading, because before, any touch re-fired.
  - The release note says "No action is needed — this only removes false triggers".
  - The subagent report's trade-off section does not mention the loss.
- **Failure scenario:** A session restarts mid-plan, and the agent keeps editing the In Progress plan. On main the `/goal` was re-established on the first edit. On this branch the new session has no goal at all until someone runs `inject-goal`.
- **Fix direction:** Decide explicitly, and either:
  - (a) re-assert from the persistent ledger on the first touch, or at SessionStart, when the ledger shows the plan was already this workspace's live goal (no displacement advisory); or
  - (b) accept the loss and say so in the release note ("after a session restart run `bin/hooks-daemon inject-goal NNNNN`"), in the docstring, and as a superseding note on 00269's decision.

### M4 — guard-defects (N5): the exception class stays open, and `secret_file_guard.matches()` still fails open

- **Where:**

  - `src/claude_code_hooks_daemon/core/chain.py:512-516` (non-strict: log and continue);
  - `src/claude_code_hooks_daemon/utils/secret_file_matching.py:264-275` (`path_is_protected` catches only `OSError` around `os.path.realpath`).

- **Cause:** N5 fixed one way the guard could raise. The general property it exposed still holds: an exception anywhere in this SAFETY/BLOCKING handler's `matches()` means "no match", and the tool call proceeds. That is the default for every client install, where `daemon.strict_mode` is `false` by default. This is at least the second time the class has shipped. `_expand_glob_token`'s Plan 00357 comment records the same fail-open from a `Path.glob` `ValueError`.

- **Failure scenario:**

  - A remaining raise path exists today: `sfm.path_is_protected('/tmp/a\x00b', DEFAULT_PROTECTED_PATTERNS)` raises `ValueError: embedded null byte` (probed). It is not exploitable for disclosure, because no tool can open a NUL path.
  - Any future `ValueError`, `RuntimeError` or `re.error` anywhere in the mention scan would silently disable the guard for that call. The Bash route is included, and pre-fix it was triggered by nothing more than a bare `~/` word.
  - The ledger and release note 14 say the guard is now "total on this input shape at two independent layers". That is true of the shape, not of the class.

- **Fix direction:** Make the guard fail closed structurally. Either:

  - wrap `_matched_pattern_and_route` so any exception yields a DENY with a "guard could not evaluate this call" reason; or
  - give the chain a policy: a handler tagged `SAFETY` + `BLOCKING` denies on exception whatever `strict_mode` says.

  Pin the class with a test that monkeypatches a raise into the mention scan and asserts DENY. Separately, widen `path_is_protected`'s catch to `(OSError, ValueError)`.

## Minor

### m1 — guard-defects (N4): the new gate also drops real internal-wildcard truncations, and the "never the sole route" claim is false

- **Where:**

  - `secret_file_matching.py:753-757`;
  - the docstring at `:729-732`;
  - release note `13-secret-file-guard-no-longer-flags-a-python-unpacking-splat…` ("A real truncation of any protected file is still denied exactly as before").

- **Failure scenario:** Each of these is DENY on main and ALLOW on the branch, and each can glob-expand to a protected name:

  - `cat *rd*rd` → `rd.vault-password`
  - `cat *word*word` → `word.vault-password`
  - `cat *on*.json` under a project `*secret*.json` pattern → `on-secret.json`

  Only this overlap branch caught them before. The threat is modest, because `cat *d` (a one-character residue) is an accepted residual that already expands to the vault file. But the stated invariant is wrong.

- **Is the "full literal suffix" rule right?**

  - For a leading-wildcard-only pattern with a *literal* stem (`*.vault-password`, `*.env`, `*.pem`) it is correct for tokens with no internal wildcard. Every full-suffix case is also caught by the substring+fnmatch check.
  - For a project pattern with an internal wildcard (`*secret*.json`), the stem `secret.json` is a concatenation and not a real suffix, so `endswith` is only a heuristic there.

- **Fix direction:** Apply the new condition only when the token's basename has no wildcard after its leading one, which is exactly the splat shape (`*identifier`, `*words[position`). Otherwise keep the old overlap behaviour. Correct the docstring and the release note.

### m2 — guard-defects (N5): the ledger entry and release note 14 misstate the trigger, the surface and the severity

- **Where:**
  - `NIGGLES.md`, the N5 entry ("Severity" paragraph);
  - `CLAUDE/UPGRADES/UNRELEASED/release-notes/14-secret-file-guard-no-longer-fails-open-on-an-empty-path-mention-token.md`.
- **What is wrong:**
  - **The trigger.** Only a bare `~/` crashed. `$` is a tokeniser delimiter (`_TOKEN_DELIMITERS`), so `"$PWD/"` and `"${PWD}/"` tokenise to `PWD/` and `{PWD}/` and never matched a prefix. The release note names `$PWD/` and `${PWD}/` as triggers.
  - **The surface.** The Bash surface was affected too (`ls ~/ && cat <protected>` crashed on main; probed). The release note describes Write/Edit only.
  - **The severity.** "An agent could not have engineered this" is wrong: appending ` ~/` to any command was enough.
  - **strict_mode.** The severity depends on `strict_mode`. This repository runs `strict_mode: true` (`.claude/hooks-daemon.yaml:8`), so here the crash was a fail-closed SYSTEM ERROR deny. The fail-open applies to client installs on the default `false`.
- **Fix direction:** Correct the trigger list, add the Bash surface, state the `strict_mode` dependence, and drop the "could not have been engineered" sentence.

### m5 — goal-flip (N3): a Write reads HEAD from the project root's repo, not the repo that contains the file

- **Where:** `src/claude_code_hooks_daemon/utils/git_facts.py:168-196`.
- **Cause:** A PLAN.md in a worktree or nested repo under the project root (`untracked/worktrees/<wt>/CLAUDE/Plan/...`) passes `_is_inside_project`. The code then runs `git show HEAD:untracked/worktrees/...` in the main repository, which never tracks that path. The answer is `None`, and `None` is read as "genuine flip".
- **Failure scenario:** `probe_n466review_goal.py` scenario C. A Write that only appends to a plan already committed as In Progress in the nested repo still emits a signal, so N3's defect survives for Writes in worktrees. The same applies to `recovery_cron_advisor`'s COMPLETION check.
- **Fix direction:** Resolve the file's own toplevel (`git -C <file-dir> rev-parse --show-toplevel`) and read `HEAD:` relative to that.

## Pre-existing (not introduced by either branch; recommend new ledger entries)

  - `cat .vault-pas?word` and `cat .vault-p?ss`
