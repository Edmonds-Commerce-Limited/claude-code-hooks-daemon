## 1. BLOCKER: the supervisor's `/effort` injections are persisted into the user settings.json

**Evidence from the vendored docs:**

- `remote-docs/docs.claude.com/en/docs/claude-code/model-config.md:554`: "`Enter` in the `/effort` slider or the `/model` picker, or a level typed after `/effort`: save the level as your default and apply it in later sessions".
- `settings-reference.md:900`: "When you run `/effort low`, `medium`, `high`, or `xhigh` in an interactive session on your machine, Claude Code saves the level for the active model under `modelSettings`".
- `settings-reference.md:1185` says the same for `modelSettings`. The installed CLI is 2.1.282, which is at or above the documented v2.1.251 behaviour.

The supervisor types exactly that, `/effort xhigh` (`.claude/ccy/claude-supervise.py:6205-6213`), into an interactive session.

**Consequence (probe S7b):** the owner's settings are `effortLevel: medium` plus `modelSettings.claude-opus-5-5: medium`.

1. An automatic Fable → Opus 5.5 downgrade makes the supervisor inject `/effort xhigh`.
2. Claude Code saves `modelSettings.claude-opus-5-5.effortLevel = "xhigh"` into `~/.claude/settings.json`.
3. After the restore, the user settings end as `{"effortLevel": "medium", "modelSettings": {"claude-opus-5-5": {"effortLevel": "xhigh"}}}`.
4. Every later Opus 5.5 session starts at xhigh, and the resolver now reads that xhigh as "configured", so nothing ever corrects it.

That is the original N47 report ("the restore path still lands on xhigh … for good"), now written into the single source of truth.

The claim is stated as fact in `NIGGLES.md:60` ("injects a plain `/effort <value>`, never touching disk") and in release note `33-…md:37` ("which never touches disk"). It is false. The reasoning that rejected `/effort auto` "because it writes" applies equally to the plain `/effort <level>` that replaced it.

It also applies to every settings correction from finding 2. When a PROJECT or LOCAL file resolves the value, the supervisor's `/effort <value>` makes Claude Code copy that project value into the owner's USER file under `modelSettings`. That is a cross-scope write the owner never made.

The DROP ANCHOR's `/effort low` on Fable persists the same way. It is owner-sanctioned, but the docs should say so.

**Direction:** needs an owner decision. Options:

- Make the compensation session-only. Claude Code offers this only interactively (`s` in the slider, v2.1.257+; `model-config.md:555`), so it would mean driving the slider rather than typing a level.
- Drop the xhigh compensation.
- Accept persistence explicitly, and on restore type the value that was resolved BEFORE the episode (captured at episode open), not the value read after it.

Whichever is chosen, correct the NIGGLES and release-note claim, and add a test that simulates Claude Code's documented save (as probe S7b does) and asserts the pre-episode level survives a cycle.

## 2. BLOCKER: a third, bidirectional settings-enforcement intervention remains

**Where:**

- `.claude/ccy/claude-supervise.py:4449-4461`: the `else:` branch of `note_model_reading`.
- `:3954-4002`: `resolve_coupled_effort_target`, which returns `configured` whenever it differs from live.

The redesign asked for exactly two interventions (downgrade compensation and the Fable anchor), plus restoring the resolved value on return. The branch instead corrects ANY non-Fable reading, at any time, whenever live effort differs from what the resolver computes, in either direction. The ledger itself says so ("corrected (in either direction) toward whatever settings.json resolves").

The resolver cannot see or model most of the things that legitimately make live effort differ from settings (`model-config.md:546`, `:555`, `:559`, `:623`, `settings-reference.md:1018-1024`). So the supervisor fights all of them.

On main, the floor was raise-only, so a human's raise was never reverted (`probe_n47r2_more_main.out` scenario A). This is a regression the branch introduces.

The unattributed-drop latch (`_latch_unattributed_effort_drop`, `:4200`, raise check at `:4242`) only covers DROPS, so every raise is reverted.

**Direction:**

- Delete the steady-state correction.
- Outside an open episode, the supervisor should inject NOTHING for non-Fable families.
- "Restore on return" should fire only on the transition out of an episode it opened itself (compensation → restore), and only if it cannot be avoided at all (see finding 1).
- The coupled path's "honours settings" branch (`test_manual_switch_to_opus_with_no_episode_open_honours_settings`) should go too, because Claude Code already applies its own resolution on every `/model` switch.

## 4. MAJOR: a manual switch to Opus is treated as an automatic downgrade after any earlier downgrade in the session

**Where:**

- `.claude/ccy/claude-supervise.py:3278-3315`: `load_model_downgrade_signal` is "deliberately NOT time-windowed", because the recorder republishes the fact for the whole session.
- `:4267-4269`: `_downgrade_is_attributed` compares only `session:from:to`.

**Repro** (probes B and B2 on both trees, and S7b):

1. An automatic downgrade happens.
2. The supervisor's own `/model fable` restore LANDS.
3. 15 minutes later, the owner picks Opus 5.5 from `/model`, and Claude Code applies its saved medium.
4. The episode reopens (`downgrade_episode=probe-sess:opus`), and the supervisor types `/effort xhigh` twice.
5. In S7b it also types `/model fable` at the human.

The result is identical on main, so this is pre-existing. But the review brief requires the compensation to be triggered "never by a manual switch". The ledger claims xhigh is "decided purely from 'an episode is open for this exact destination'", and here the episode itself is opened by a manual switch. `HANDLER_REFERENCE.md:3195` ("a model you pick yourself is never overridden") is also untrue in this case.

**Direction:**

- Open an episode only when the attribution record is NEWER than the last observed recovery. Alternatively, make it consume-once per record `record_ts`.
- Add a RED test: downgrade → restore lands → manual switch to Opus → no `/effort`, no `/model`.
- If this is out of N47's scope, ledger it as its own entry.

**Direction:** if finding 2 is fixed by deleting the steady-state correction, these gaps can no longer cause a fight. Otherwise, resolve all five scopes and the flags.

## 6. MAJOR: "force the worker reload" is not a safe alternative to a relaunch

**Where:**

- `CLAUDE/development/CcySupervisor.md:134-137`: "relaunch it (or force the worker reload above)".
- The release note's last paragraph: "needs a relaunch (or a forced worker reload …)".

A forced worker reload yields an old (main) HOST driving a new WORKER. Code the HOST owns changed:

- `arm_coupled_effort`'s key format: main arms `session:family:target` (`probe_n47r2_main_supervise.py:3697`).
- `_apply_decision` and `_outcome_from_json`: they carry and write `settings_status_log`.
- `CompactPolicy`.
- `_poll_once`: the in-process fallback, which still runs main's floor using `CCY_MIN_EFFORT_LEVELS` from the old ccy env.

The new worker splits the old 3-part key with `partition(":")`, so `family` becomes `"opus:xhigh"`. That never matches a reading, so the key is never resolved and never cleared (`:3976-3994`).

The old host's bookkeeping (`:6645`, the same on main) then credits the next ordinary `/effort` injection to the stuck coupled key (`mark_coupled_effort_injection`) instead of calling `mark_effort_injection`. That records no cooldown and no cap.

**Repro:** `probe_n47r2_mixed.out`, second scenario. After a `/model opus` test-trigger, `/effort medium` is injected at t+33 and again at t+35: a duplicate 2 s apart, with `effort_injections` still 0 after the first. The old host also drops `settings_status_log`, so the new decision.log note never appears.

No test covers importing a legacy 3-part `coupled_effort_pending`. The existing "legacy state" test (`test_manual_model_choice.py:410`) only covers deleted manual fields.

**Direction:**

- Make the owner action "relaunch ccy" only, and remove the worker-reload alternative from both docs.
- Have `import_state` drop (or split) a 3-part coupled key.
- Add a legacy-import test.
