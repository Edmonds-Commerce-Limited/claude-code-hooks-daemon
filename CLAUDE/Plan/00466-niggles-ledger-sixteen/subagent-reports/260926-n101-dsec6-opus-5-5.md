### MAJOR (not a regression): `$"…"` quoting keeps its `$` after quote removal

- **Citation:** `src/claude_code_hooks_daemon/utils/shell_expansion.py:2664` (`_consume_dollar`), whose fall-through is `return "$", start + 1`. The `"…"` is then read as an ordinary double-quoted span, so `normalise_word('$"abc"')` gives `$abc`.
- **What it allows:** bash drops the `$` from `$"…"`.
  - `cat $".vault-"pass` reads `.vault-pass`, and both trees allow it. The guard sees the token `$.vault-pass`. The all-in-one `cat $".vault-pass"` is denied only because the raw text holds the name.
  - The N107 shape `cat $".vault-"{"}",pass}` is also allowed on both. The new mask handles `$"` correctly (`shell_expansion.py:192`), but every spelling is then normalised to `$.vault-pass`.
- **Class:** a quote-removal model that leaves any character bash removes, or removes one bash keeps. The removed or kept character then shields a spelling from the name match.
- **Why the tests miss it:** the N107 guard tests use `$"}"` only inside a group (`§{$"}",pass}`), where the `$` lands mid-token and the prefix still matches. No test puts `$"` before the protected text.
- **Detector hypothesis:** a differential test. Build words from quoting primitives (`'`, `"`, `$'`, `$"`, `\`) around a harmless name. For each, compare bash's `printf '%s\n' WORD` with `normalise_word(WORD)` and require them to be equal. It only prints, so it runs nothing dangerous. It has no false positives, since any mismatch is a real misparse.
- **Confidence:** high. Probed on both trees, with bash ground truth. It belongs to the quote-removal model more than to N101. It is worth a new niggle, or a note on N107 if N107 is meant to cover every quoting form.

### MAJOR (not a regression): braces produced by decoding `$'\x7b'`, run by `eval` or `bash -c`, are never expanded

- **Citation:** `shell_expansion.py:653-665`. `_nested_command_words` re-reads the decoded text only when `_holds_quoted_braces(code)` is true, which needs a `{`, a `}` **and** a quoting character that survives decoding. Its docstring says "A brace may come from quote removal itself (`$'\\x7b'`)". That holds only when a quote survives too.
- **What it allows:** `bash -c $'cat .vault-\x7bpass,q\x7d'` and `eval $'cat .vault-\x7bpass,q\x7d'` are both allowed on both trees. Bash runs `cat .vault-{pass,q}` and reads `.vault-pass`. The quote-blind stream never sees a brace, because the raw text holds only `\x7b`. The branch does catch the form where a quote survives (`$'…\x7b"\x7d",pass\x7d'`).
- **Class:** brace syntax that exists only after one layer of decoding, when the decoded text is handed to a shell. That covers `$'\x7b'`, `$'\173'`, `$'{'`, and `printf`/`echo -e` output that is `eval`'d.
- **Why the tests miss it:** `TestIterShellBraceWords` covers `bash -c` in ANSI-C quoting only with literal braces, or with a quote that survives.
- **Detector hypothesis:** for any word handed to a nested shell, re-read the decoded value whenever decoding changed it and the value holds a `{`, whether or not a quote survives. That work is bounded by the existing depth limit. The likely false positives are `bash -c` scripts containing `{ …; }` command groups, which expand to themselves and name nothing. It is worth measuring on the fixer's 140-program corpus.
- **Confidence:** high. Probed on both trees, with bash ground truth.

### minor (not a regression): the new "no group left" early exit looks only for a literal `{`

- **Citation:** `shell_expansion.py:683-703` (`_checked_word_end`, `_may_hold_a_group`) and `:773` (`_heredoc_body_words`). When a span cannot be resolved and `_may_hold_a_group` finds no `{` other than `${`, the rest of the text is not scanned.
- **What it allows:** alone, `bash -c $'cat .vault-\x7b"\x7d",pass\x7d'` is **denied** on the branch. After a prefix, as in `: ${x:-'a'} ; bash -c …` or `: ${x:-'a'} ; eval $'…'`, it is **allowed**, because the unresolvable `${x:-'a'}` ends the scan. `main` allows it either way, so this is not a regression. But the branch's own N107 coverage can be switched off by an unrelated prefix.
- **Class:** a fail-open early exit whose premise ("nothing left to find") is checked on raw text, while the finder also works on decoded text.
- **Why the tests miss it:** `test_quoting_that_cannot_be_resolved_fails_closed` puts a literal brace after the unresolvable span. No test puts a decoded brace there.
- **Detector hypothesis:** make `_may_hold_a_group` also return true when the rest of the text holds `\x7b`, `\173`, `{` or `\U0000007b` inside `$'…'`. Better, fail closed whenever the rest holds `$'`. The likely false positives are rare, since `$'` after an unresolvable `${…'…'}` is uncommon.
- **Confidence:** high. Probed on the branch in both forms.
