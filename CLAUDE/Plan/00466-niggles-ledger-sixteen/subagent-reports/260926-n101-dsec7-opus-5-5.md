## Shared MAJOR 1: a `}` before the first comma is missed in an unquoted word

**Citation:** `shell_expansion.py:232-233`, together with the yield gate at `:757`:

```python
    if _QUOTING_CHARS.isdisjoint(word):
        return spellings
```

and

```python
if "{" in word and "}" in word and (every_word or not _QUOTING_CHARS.isdisjoint(word)):
```

**What it allows:** `cat /proj/.vault-{},pass}` is allowed on both trees. So is the same line in a Write of a `.sh` file. Bash prints `/proj/.vault-}` and `/proj/.vault-pass` (confirmed with a harmless name).

- Of 167 fuzzed quote-free words that bash expands to the path, 31 are allowed on both trees. Examples: `{},pass}`, `{q},pass}`, `{a}b,pass}`, `{..}a,pass}`, `{{}},pass}`.
- Adding any quoting character makes the branch deny, for example `cat "N/"{},pass}` and `bash -c '…'`. `_BashBraces` reads the rule correctly (`shell_word_spellings('.qq-{},pass}')` gives `.qq-pass`), but it is never run on a word without quoting.

**The class:** a word with no quoting character whose group bash accepts differently from the quote-blind regex. Round 7 names three such rules: a `}` before any comma is text, a comma-less group that is not a sequence is text, and `${` opens a level. Only quoted words reach the port that knows them.

**Why the tests miss it:**

- `test_every_spelling_bash_prints_is_one_the_guard_reads` draws 19 of its 26 primitives from quoting forms. At seed 107, only 14 of the 2,000 words are quote-free with braces, and none has this shape.
- The program-stream differential uses `every_word=True` and the ungated `shell_word_spellings`, so the gate is never exercised.

**Detector hypothesis:** run `_BashBraces` on every brace word; that is, drop the gate at `:232`, and yield every brace word at `:757`. The budget already bounds the cost. Alternatively, add a differential run over the quote-free primitives alone (`{`, `}`, `,`, `..`, text). Likely false-positive cost: some added budget fail-closes on long quote-free brace runs. It is not noisy.

**Confidence:** high. Probed on both trees, with bash ground truth.

## Shared MAJOR 2: a here-string word is read as a heredoc delimiter, so `bash <<< $'…'` is never re-parsed

**Citation:** `shell_expansion.py:731` and `:745-747`.

- At the first `<` of `<<<`, the heredoc test fails correctly, and `<` is skipped as a stop character.
- At the second `<`, `text.startswith("<<", i)` sees `<< ` and not `<<<`, so it reads a heredoc. The here-string word becomes a delimiter (`:736-742`) and is never scanned as a word.
- `iter_shell_brace_words` returns 0 words for each of these commands.

**What it allows (all allowed on both trees):**

- `bash <<< $'cat /proj/.vault-\x7bpass,q\x7d'`
- `bash <<<$'…'`
- `sh -s <<< $'…'`
- `bash <<< $'cat /proj/.vault-\x7b\x7d,pass\x7d'`
- `xargs -0 bash -c <<< $'…'`

Bash runs `cat /proj/.vault-{pass,q}` (confirmed with a harmless name). Quoted-brace forms (`bash <<< "…{'}',pass}"`) still deny, through the quote-blind word finder feeding `expand_braces`.

**The class:** a redirection operator mis-tokenised by a scanner that reads one character at a time, so the word after it is dropped from every stream that needs bash's word split. That covers N107's quoted whitespace and N112's decoded braces reaching a shell through stdin.

**Why the tests miss it:** the N112 tests put the `$'…'` word in argument position (`-c`, `eval`, `su`, `ssh`). No test feeds it through `<<<`.

**Detector hypothesis:** at `:731`, test for `<<<` first and step over all three characters, then scan the next word as an ordinary word. It will already be decoded and re-read, because it holds `$'`. More generally, a differential that runs each generated word through `bash <<< WORD` with `printf` would catch the whole class. Expected false positives: none, since the word is then scanned like any other argument.

**Confidence:** high. Probed on both trees; the scanner behaviour was confirmed by the zero-word count.
