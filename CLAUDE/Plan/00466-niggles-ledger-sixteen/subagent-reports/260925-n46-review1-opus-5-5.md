## Central question: did the fix drop a real signal?

Evidence examined:

1. **Occurrence ledger** (`/workspace/untracked/budget-exhaustion-events.jsonl`,
   18 records, all `tool_name: Bash`). Every one is a false positive. Most are
   this repo's own vocabulary (`exceeded its N dispatch budget`, `exceeded its byte budget`, `exceeded the 30s budget`, `budget already exhausted`). The last
   two were raised DURING THIS REVIEW by the live, pre-fix daemon on a `grep`
   of Plan 00315's docs, which is N46 reproducing itself. No record came from a
   real harness limit.
2. **Transcript corpus** (291 jsonl files under
   `/root/.claude/projects/-workspace`, including sub-agent transcripts). Scanned
   by `probe_n46r1_transcript_scan.py`, with redacted context from
   `probe_n46r1_transcript_context.py` (output in `probe_n46r1_context_out.txt`).
   - Zero WebSearch tool_results carry the refusal. The 6 WebSearch results in
     the corpus are ordinary results.
   - WebFetch hits (7 rate_limit, 1 maxTurns) are all documentation page
     content, not a harness limit.
   - Bash hits for `quota_exceeded`, `budget_limit_reached` and
     `budget_exhausted` are all this repo's source or plan prose.
   - **The only real harness limit found in a tool channel is on Agent**. See
     MINOR-5. Main excluded Agent too, and main's generic family does not match
     that wording, so this is not a regression.
3. **Payload capture** (`/workspace/untracked/payload-capture`) holds no
   PostToolUse payloads, so it gives no evidence either way.
4. **Vendored docs** (`remote-docs/code.claude.com/docs/en/`).
   - `tools-reference.md:599-603` ("Session search limit") documents that
     capped WebSearch calls "return a notice". That supports WebSearch as the
     channel for the web-search budget.
   - `sub-agents.md:314,1092` and `tools-reference.md:111` document a maxTurns
     cap that marks the returned Agent output as partial. That is an Agent
     channel. Main did not catch it either.
   - 529s, usage limits and `quotaLimits` never enter the tool layer
     (BUDGETS.md:23-24, miner report section 2). Neither version could catch them.

**Result:** no signal that main caught is missed by the fix. The generic family's
true-positive count in the available evidence is zero. Its false-positive count
is 18 of 18.

### MAJOR-3: no config-changes manifest entry for the default flip

**Reproduction:** `grep -n budget CLAUDE/UPGRADES/UNRELEASED/config-changes/v3.67.0.yaml` finds nothing.
`CLAUDE/UPGRADES/config-changes/v3.60.0.yaml:44-47` is the migration note that

**Direction:** add a `changed:` entry keyed
`handlers.post_tool_use.budget_exhaustion_detector.options.excluded_tools`. It
should state that the default now includes Bash and that the generic family is
removed. The `migration_note` should say that a config setting `extra_patterns`

### MINOR-5: the Agent/Task channel carries real harness-written limit signals, contradicting the exclusion rationale

**Where:** handler `budget_exhaustion_detector.py:44-49, 107-116, 576-580`. The
same text was on main; the fix carries it forward.

Transcript
`/root/.claude/projects/-workspace/00000000-0000-0000-0000-000000000000/subagents/agent-areview-00421-a34e78b1154713ac.jsonl`
holds Agent tool_results whose content OPENS with the harness's own text:
"Agent terminated early due to an API error: You've hit your weekly limit ·
resets Sep 27, 8am (UTC) (error type rate_limit, HTTP 429, request id ...)",
followed by "Everything below is PARTIAL output recovered from the agent before
it was cut off". `toolUseResult.status` is `"completed"`, so PostToolUse:Agent
fires with this response. There are four occurrences, two weekly-limit and one
session-limit, plus one `is_error: true` variant.

This falsifies two claims in the code:

- "never a field the Task/Agent tool machinery itself populates from a budget
  check"
- "a genuine hit ... already fires directly in the sub-agent's own session"

An API-stream limit never produces a tool event in the sub-agent (BUDGETS.md:24).

The documented maxTurns cap (`sub-agents.md:314`) is a second harness-marked
Agent signal of the same kind. There is also a related over-claim at lines
41-44, 127-133 and 571-574: "nothing Bash prints is ever this handler's
confirmed channel". It is right in effect, but BUDGETS.md:25 lists a harness
output cap, `<persisted-output>`, that arrives in the Bash tool_result.

This is NOT a regression. Main excluded Agent and Task, and its generic family
does not match "You've hit your weekly limit".

**Reproduction:** `probe_n46r1_transcript_context.py` (lines 46-62 of
`probe_n46r1_context_out.txt`). The inline python in this review printed
`is_error`, `content` and `toolUseResult` for those records.

**Direction:**

- Now: correct the rationale text at the three sites. The honest reason for
  excluding Agent is that the free-text body is the sub-agent's own prose. It
  is not that the harness never writes there.
- Follow-up plan: add
  `_Signal(frozenset(SUBAGENT_DISPATCH_TOOL_NAMES), re.compile(r"\A\s*Agent terminated early due to an API error: You've hit your (session|weekly) limit"))`,
  anchored at the start of the response so a sub-agent's prose quoting it
  cannot match. Consider a maxTurns partial-output marker once its verbatim
  shape is captured.
- The follow-up requires built-in channel signals to be evaluated even for
  tools in `excluded_tools`, or requires Task/Agent to leave the default
  exclusion now that channel-scoping gives the precision. The exclusion check
  at line 455 runs first today.
