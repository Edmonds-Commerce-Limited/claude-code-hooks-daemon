# N110: the full gate's tests stage covers CI's Python matrix (Opus 5.5)

Branch `worktree-n466-n110`, work commit `411430ed1`.

## Design

- **`scripts/qa/run_test_matrix.py`** is the tests stage for both
  `llm_qa.py` (the `tests` registry entry) and `run_all.sh` (step 5).
- It reads `jobs.qa.strategy.matrix.python-version` out of
  `.github/workflows/qa.yml` **at run time**, so a version added to CI widens
  the gate with no second edit. The stage FAILS on any of these: an
  unreadable or empty matrix, a non-string entry (an unquoted `3.10` is the
  YAML float 3.1), or an entry that is not `X.Y`.
- **Primary** = the interpreter running the script, which is the checkout's
  venv. It runs `run_tests.sh` unchanged: all of `tests/`, with coverage.
- **Extras** = every other matrix version. Each is provisioned as follows:
  - `uv python find --no-project X.Y`, falling back to `uv python install X.Y`.
  - A probe checks that the interpreter really is X.Y.
  - `uv sync --frozen --all-extras --python <interp>` builds the venv at
    `untracked/qa-interpreters/pyX.Y/`.
  - A probe checks that the venv imports pytest and this checkout's `src/`.
  - The venvs sit outside the `untracked/venv-*` glob that `resolve_venv.sh`
    scans. That glob takes the FIRST candidate, so a `py312` venv beside
    `py311` could otherwise become the daemon's interpreter.
- **Phase 1 (parallel):** the primary starts first, before any
  provisioning. Each extra's `tests/unit` then runs at the same time as the
  primary.
- **Phase 2 (serial):** once phase 1 is done, the daemon is started if it
  idled out. Then each extra runs `tests --ignore=tests/unit`, one version
  at a time. Those directories drive the checkout's single live daemon
  (acceptance tests toggle its transport), so running them concurrently
  would contend.
- **Fail closed:** if a version cannot be provisioned (no network, no uv, a
  version mismatch or a failed sync), nothing is launched for it. Each of its
  runs is recorded as `NOT RUN - <reason>`. `passed_all` goes false, and the
  top-level `error` names the version. The stage never passes on fewer
  versions than CI. Checked for real: `provision("3.99")` raises
  `` `uv python install 3.99` failed (exit 2): No download found ``.
- **Report:** `tests.json` keeps the primary's schema and coverage.
  - Counts are summed across every run.
  - Each extra's failures are named `[py3.13 unit] <nodeid>`.
  - A red run that names no test still gets an entry pointing at its log.
  - A new `interpreters` array records version, scope, counts, duration, exit
    code, log path and error for each run, plus `wall_seconds`.
  - `llm_qa`'s tests summary prints one line per run.
- Extras' logs are at `untracked/qa/tests-pyX.Y-<scope>.log`.
- Lint, format, mypy, pyright and the other stages stay on the primary.
- Documented in `CLAUDE/QA.md` (the Automated Checks list and Quick
  Reference). The satellite updates are `CONTRIBUTING.md`,
  `.claude/agents/qa-runner.md` (which now runs `llm_qa.py tests` instead of
  `run_tests.sh`) and `.claude/agents/qa-fixer.md`.
- No release note: `scripts/qa/` is repository QA tooling and does not ship
  to clients.

## Tests (RED, then GREEN)

`tests/unit/qa/test_run_test_matrix.py` has 31 tests.

- **The central guard** reads CI's matrix with its own `yaml.safe_load`. For
  a primary of 3.11, 3.12, 3.13 or 3.14 it asserts that every CI version gets
  all of `tests/`. It also asserts that `TOOL_REGISTRY["tests"]` and
  `run_all.sh` both run the matrix runner.
- **RED on the branch base (main `937a4c772`):** `llm_qa.py's tests stage runs [.../run_tests.sh], which is one interpreter; CI runs ['3.11', '3.12', '3.13']`. The `run_all.sh` assertion also failed, and the module did not
  exist.
- **Mutation-proven** on a `git archive` scratch copy
  (`untracked/scratch/n110-mutate.bash`). Each of these goes RED:
  1. extras run only `tests/unit` (4 failures);
  2. a provisioning failure is skipped silently;
  3. phase 1 waits on each run before starting the next;
  4. the `llm_qa` tests stage is reverted to `run_tests.sh`.
- **Narrowed end-to-end run with real interpreters**
  (`untracked/scratch/n110-e2e.py`, two small files, not the suite). It
  covered provisioning, both phases, log parsing, the daemon start before
  phase 2 and the merged report. The result was py3.11/3.12/3.13 all PASSED
  in 13.3s wall. It also found a real gap: `_ExtraJob` did not create
  `untracked/qa/`. That is fixed.
- **Targeted runs:** `tests/unit/qa` plus the QA integration tests
  (`test_qa_*`, `test_blocking_gate_skip_guard`) plus the project handlers
  gave 1248 passed. The `llm_qa` tools `magic_values`, `format`, `lint`,
  `type_check`, `pyright`, `shell_check`, `error_hiding`, `shell_audit`,
  `python_var_guidance`, `doc_truth`, `doc_snippets`, `docs_qa`, `plan_qa`,
  `british_english`, `repo_hygiene`, `sensitive_content`,
  `canonical_callers` and `skill_refs` all passed (18/18).
- `mypy --strict` and `pyright` are clean on the touched Python.
- The daemon was restarted and reports RUNNING.

## Timing

**I have not measured it.** The only full run allowed is the gate, and the
brief says not to wait for it.

- **Before:** in four earlier worktree gates, the file timestamps from the
  first tool's JSON to `tests.json` span about 1,900 to 2,600 seconds. Most
  of that is the serial 29,317-test run.
- **After (expected):** the tests stage takes max(primary, the two unit runs
  under CPU contention), plus two serial non-unit runs. Unit is 958 of 1,187
  test files. The non-unit remainder is integration/acceptance-heavy, and
  those files are slower per test.
- **Where to read the real number:** the queued gate
  (`/workspace/untracked/scratch/gate-worktree-n466-n110.out`) prints each
  run's duration on the tests line. `tests.json` records `wall_seconds`.
- **If phase 2 turns out too slow:** the lever is to run phase 2 in parallel
  with an isolated daemon per interpreter. That was not done here, because
  it needs a per-version checkout.

## Open items for team-lead

1. **Subprocess boundary.** Tests that spawn `bin/hooks-daemon`, and the
   live daemon itself, resolve the checkout's primary venv. Only in-process
   code runs under the extra interpreter. This matches where N24 lived
   (in-process stdlib path code), but it is not full parity with CI's
   per-version jobs. Closing it needs a per-version isolated checkout with
   its own venv and daemon. That is documented in QA.md as a boundary; you
   decide whether it becomes a ledger item.
2. **N111 (recorded in NIGGLES/PLAN).** `setup_worktree.sh`'s `uv sync` has
   no `--python`, so uv swaps the `py311` venv's interpreter for its
   preferred Python. The venvs for n101 and n105 are named `py311` but are
   3.13.15. Replaying the script's steps for this worktree gave 3.12. I
   rebuilt this worktree's venv on `/usr/bin/python3.11` to match main. This
   also means N110's premise ("the gate runs 3.11") was false for every
   worktree gate built by the script.
3. Extras do not collect coverage. CI enforces `--cov-fail-under=95` per
   version, while the local primary reports coverage without enforcing a
   threshold, which is pre-existing and unchanged.
