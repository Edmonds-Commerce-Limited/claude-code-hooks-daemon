# N110: the full gate's tests stage covers CI's Python matrix (Opus 5.5)

Branch `worktree-n466-n110`, work commit `411430ed1`.

## Design

- **`scripts/qa/run_test_matrix.py`** is the tests stage for both
  `llm_qa.py` (the `tests` registry entry) and `run_all.sh` (step 5).
- It reads `jobs.qa.strategy.matrix.python-version` out of
  `.github/workflows/qa.yml` **at run time**, so a version added to CI widens
  the gate with no second edit. The stage FAILS on any of these: an
  unreadable or empty matrix, a non-string entry (an unquoted `3.10` is the
  YAML float 3.1), or an entry that is not `X.Y`.
- **Primary** = the interpreter running the script, which is the checkout's
  venv. It runs `run_tests.sh` unchanged: all of `tests/`, with coverage.
- **Extras** = every other matrix version. Each is provisioned as follows:
  - `uv python find --no-project X.Y`, falling back to `uv python install X.Y`.
  - A probe checks that the interpreter really is X.Y.
  - `uv sync --frozen --all-extras --python <interp>` builds the venv at
    `untracked/qa-interpreters/pyX.Y/`.
  - A probe checks that the venv imports pytest and this checkout's `src/`.
  - The venvs sit outside the `untracked/venv-*` glob that `resolve_venv.sh`
    scans. That glob takes the FIRST candidate, so a `py312` venv beside
    `py311` could otherwise become the daemon's interpreter.
- **Phase 1 (parallel):** the primary starts first, before any
  provisioning. Each extra's `tests/unit` then runs at the same time as the
  primary.
- **Phase 2 (serial):** once phase 1 is done, the daemon is started if it
  idled out. Then each extra runs `tests --ignore=tests/unit`, one version
  at a time. Those directories drive the checkout's single live daemon
  (acceptance tests toggle its transport), so running them concurrently
  would contend.
- **Fail closed:** if a version cannot be provisioned (no network, no uv, a
  version mismatch or a failed sync), nothing is launched for it. Each of its
  runs is recorded as `NOT RUN - <reason>`. `passed_all` goes false, and the
  top-level `error` names the version. The stage never passes on fewer
  versions than CI. Checked for real: `provision("3.99")` raises
  `` `uv python install 3.99` failed (exit 2): No download found ``.
- **Report:** `tests.json` keeps the primary's schema and coverage.
  - Counts are summed across every run.
  - Each extra's failures are named `[py3.13 unit] <nodeid>`.
  - A red run that names no test still gets an entry pointing at its log.
  - A new `interpreters` array records version, scope, counts, duration, exit
    code, log path and error for each run, plus `wall_seconds`.
  - `llm_qa`'s tests summary prints one line per run.
- Extras' logs are at `untracked/qa/tests-pyX.Y-<scope>.log`.
- Lint, format, mypy, pyright and the other stages stay on the primary.
- Documented in `CLAUDE/QA.md` (the Automated Checks list and Quick
  Reference). The satellite updates are `CONTRIBUTING.md`,
  `.claude/agents/qa-runner.md` (which now runs `llm_qa.py tests` instead of
  `run_tests.sh`) and `.claude/agents/qa-fixer.md`.
- No release note: `scripts/qa/` is repository QA tooling and does not ship
  to clients.

## Rulings and follow-up

1. **Subprocess boundary: accepted by team-lead** as a documented boundary.
   Tests that spawn `bin/hooks-daemon`, and the live daemon itself, resolve
   the checkout's primary venv. Only in-process code runs under the extra
   interpreter. The QA.md text stays.
2. **N114 (renumbered from N111, which the N101 branch already holds):
   fixed on this branch.**
   - **Root cause.** It is not `setup_worktree.sh`'s dev-extras sync; a sync
     into an existing venv was measured not to swap. `ensure_venv` names the
     venv from PATH's `python3`, then `create_venv_at_path` passed the bare
     name to `uv sync --python python3`. uv reads that as "any 3.x" and
     builds on its preferred interpreter. On a toy project, the bare name
     built 3.12; the resolved `/usr/bin/python3` built 3.11.
   - **Fix, in `scripts/install/venv.sh`.** `create_venv_at_path` resolves
     the interpreter with `command -v` and hands uv the path. It fails before
     uv runs if the interpreter is missing. After the sync it compares the
     built venv's X.Y with the requested interpreter's. A mismatch fails
     loudly and the venv is removed, so the resolver's glob cannot pick it
     up.
   - **`setup_worktree.sh`** pins its dev-extras sync with `--python` for the
     venv's own interpreter, and refuses a venv whose Python differs from the
     `pyMM` in its name. That `pyMM` is parsed from the right end of the
     name, because the slug is a path.
   - **Real uv check:** the fixed function built 3.11 from a bare `python3`
     where main's built 3.12.
   - **Tests:** `tests/integration/test_venv_sh_builds_on_the_fingerprinted_python.py`
     gave 4 RED on main's `venv.sh` and 5 GREEN here. The two new checks in
     `test_worktree_daemon_env_provisioning.py` were RED on main.
     `test_ensure_venv_lock.py`'s stub `uv` wrote an empty `bin/python`,
     which the new version check correctly refuses. The stub now links
     `bin/python` to the requested interpreter, and the file is back to 9/9.
     All 68 test modules that touch venv creation pass, apart from those six
     stub failures, which are now fixed.
   - **Release note:** `99-the-daemon-venv-is-now-built-on-the-python-its-name-declares.md`,
     because `venv.sh` ships to clients.
   - **Not done:** existing mislabelled venvs (n101, n105) are not rewritten.
     Each rebuilds correctly once deleted.
3. Extras do not collect coverage. CI enforces `--cov-fail-under=95` per
   version, while the local primary reports coverage without enforcing a
   threshold, which is pre-existing and unchanged.
4. The first queued gate was stopped before it started, as instructed. It
   was still waiting on the gate lock and had written no output. I killed
   only `gate.sh` and its `flock` child, after checking both command lines
   and the parent link. The gate is re-queued on the final HEAD.

## N122: the ensure_venv-lock flake was a test defect, fixed before landing

team-lead cancelled the first queued gate: N110/N114 are exactly the
`ensure_venv` branch, so a flake in an `ensure_venv` test could not ride
along unexplained.

- **Test and assertion:**
  `tests/integration/test_ensure_venv_lock.py::TestConcurrentStartersBuildOnce::test_second_starter_waits_then_reuses_the_finished_venv`,
  `assert WAITING_FRAGMENT in err2` ("the second starter must say it is
  waiting on the lock").
- **Failure rates measured** (30 copies of this one test run concurrently
  per batch, 8 cores, two batches each = 60 runs):
  - This branch, before the fix: **5/60 failed** (~8%).
  - `git archive` of main `fe14348e7`, same test, same contention, its own
    `uv sync`-built venv: **0/60 failed**.
  - This branch, after the fix below: **0/60 failed**.
- **Cause: the test, not the lock.** `_run_two_starters` started the second
  `ensure_venv` subprocess a fixed `time.sleep(0.3)` after the first,
  assuming the first would always reach `acquire_venv_lock` inside that
  window. Under real CPU contention the first bash subprocess's own
  scheduling — not `venv.sh`'s locking — can exceed 0.3s before it gets
  there, so the second's non-blocking `flock -n` sometimes wins
  uncontended. `acquire_venv_lock`, `WAITING_FRAGMENT` and
  `TIMEOUT_FRAGMENT` in `scripts/install/venv.sh` are unchanged.
- **Fix (test only):** `tests/integration/test_ensure_venv_lock.py` adds a
  `_StderrWatcher` that reads the first starter's stderr on a background
  thread and releases the second starter only once it has seen `"creating venv at"` — printed by `_ensure_venv_build` (venv.sh) immediately after
  `acquire_venv_lock` returns holding the lock. This is a barrier on a real
  production event, not a guessed delay; no sleep-based ordering and no
  widened timeout remain (`_TIMEOUT_SECONDS`, 60s, is unchanged and now
  bounds the marker wait too).
- **Logged:** ledger N122 in `NIGGLES.md` and `PLAN.md`, marked ✅ Remedied.
- **Release note renumber:** the branch's note moved 120 → 121 (main's
  `superlinear` work holds 120).
- **Verification:** `tests/integration/test_ensure_venv_lock.py` +
  `test_venv_sh_builds_on_the_fingerprinted_python.py` +
  `test_worktree_daemon_env_provisioning.py` — 22 passed. `ruff`,
  `black --check`, `mypy`, `pyright` clean on the touched test file. Daemon
  restarted, `RUNNING` (PID 2132441).
