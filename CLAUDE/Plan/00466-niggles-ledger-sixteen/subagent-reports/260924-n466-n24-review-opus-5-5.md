## Blockers

### B1: a lone surrogate in `tool_input` crashes the chain before any handler runs, so every guard ALLOWs (a regression)

- **Where**: `src/claude_code_hooks_daemon/core/chain.py:76`, `total += len(value.encode("utf-8"))` inside `_safety_payload_size`. It is called at `chain.py:653`, before the handler loop and outside every `try`. The exception escapes `HandlerChain.execute` and reaches `daemon/controller.py:1034` (`except Exception` → `HookResult.error(internal_error)`), which serialises with no `permissionDecision`. That is an ALLOW.
- **Why it is reachable**: the daemon's `json.loads` turns a JSON `"\ud800"` escape into a Python `str` holding a lone surrogate. `init.sh` re-emits one with `json.dumps` (ensure_ascii), and a model's JSON tool arguments can carry one. `str.encode("utf-8")` raises `UnicodeEncodeError` on it. The cap is on by default (`max_safety_input_bytes` = 2 MiB), so every PreToolUse carrying `command` / `content` / `new_string` / `old_string` goes through it.
- **Reproducer**: `probe_n24r_p1_deadline.py` over the real socket, and `probe_n24r_surrogate.py <root>` in process.
  - Branch: `git reset --hard HEAD # \ud800` → `ALLOW(no decision)`, context `internal_error: UnicodeEncodeError`. Same for `curl … | bash # \ud800`, and for `Write .env` with content `AKIA\ud800`.
  - **Base 3104434b, same probe**: both Bash commands are **denied** (R-GIT-RESET-HARD, R-CURL-PIPE-SHELL). The fail-open is new with this branch.
- **Direction**:
  - Measure without a strict encode, e.g. `len(value.encode("utf-8", "surrogatepass"))`, or bound by `4 * len(value)`.
  - Move the measurement inside a fail-closed path: any exception while computing the cap denies when the chain holds a SAFETY+BLOCKING handler.
  - More generally, anything `HandlerChain.execute` does outside the per-handler `try` should fail closed for PreToolUse rather than reach the controller's fail-open `except`.
  - Add a RED test: a lone surrogate in each of the four measured fields, plus `file_path`, through `controller.process_request`, must deny.

### B2: one Write with a ~90 KB `file_path` freezes the whole daemon; N34's thread-based bound cannot fire, so every concurrent call from every session fails open (pre-existing root cause, but it defeats N34's core claim)

- **Where**:
  - The root cause is `src/claude_code_hooks_daemon/utils/path_exclusion.py:274`, `compiled.fullmatch(candidate)` on a glob-derived regex. It is reached from `error_hiding_blocker.py:163` → `_is_excluded` → `handler_excludes_path` → `is_path_excluded` → `path_matches_globs`, and the same path serves `comment_changelog` and `comment_size`.
  - The cost is quadratic in path length (`probe_n24r_p9_pathhang.py`): 1 KB 0.13 s, 2 KB 0.49 s, 4 KB 1.9 s, 8 KB 6.7 s. That extrapolates to many minutes at 90 KB.
  - The work happens inside **one C-level `re` call that never releases the GIL**. Nothing else in the process runs: not the `Future.result(timeout=…)` waiter in `bounded_dispatch.py:163`, not the asyncio loop, not the other executor threads, not signal handlers.
- **Reproducer**: `probe_n24r_p11_gil.py`, real socket, default config, no probe handler involved.
  - Branch: `git reset --hard` before the Write → deny in 0.19 s. `git reset --hard` 2 s after the Write started → **30.03 s CLIENT_TIMEOUT, which `init.sh` treats as fail-open for PreToolUse**. The Write itself also times out on the client.
  - Base: identical, so the root cause predates the branch.
  - `probe_n24r_p10_path_saturation.py` runs 16 such Writes. All 16, then `git status`, `ls`, `git reset --hard HEAD` and an ordinary Write, **all hit the client timeout (fail open)**.
  - `hooks-daemon stop` returned after about 6 s, but the daemons were still alive at 99% CPU minutes later. SIGTERM was ignored for 5 s, because Python signal handlers only run between bytecodes. The three probe daemons had to be SIGKILLed.
- **Why it is a blocker for this branch**: N34 exists to close exactly this class. From NIGGLES.md N34 and `bounded_dispatch.py:11-17`: a handler slow within its own call reaching the client's 30 s timeout "reproduces the exact failure mode N25 set out to close". The chosen mechanism, a daemon thread plus a timed wait on the calling thread, only bounds handlers that yield the GIL. Any handler stuck in C-level regex, which is how most handlers here scan text, is unbounded. The shape is model-reachable: a Write tool call with a long path. The size cap does not measure `file_path` (see m5), and the hostile-input harness only sweeps `file_path` with shapes under 300 bytes.
- **Direction**, several are needed:
  1. Make judging preemptible. Run the chain, or each SAFETY call, in a **worker process** the daemon can kill at the deadline, with a pre-forked pool to keep latency low. Alternatively, have a separate watchdog process answer deny once a request's absolute deadline passes.
  2. Defence in depth in the client: `init.sh` should fail **closed** for PreToolUse on `socket_timeout` (today only Stop/SubagentStop are special-cased, and they fail open). The daemon's deadline already sits well under 30 s, so a client timeout now means "the daemon could not judge", not "a slow advisory".
  3. Fix the root cause. Use a linear, non-backtracking glob matcher in `path_matches_globs`, or cap the path length judged there and deny above it.
  4. Extend the size cap to every string field in `tool_input`, including `file_path`, and add long-path shapes (1–100 KB) to the hostile-input harness.

## Majors

### M1: the deadline clock starts at `chain.execute`, not when the request arrives; executor queueing pushes judged requests past the client's 30 s timeout (fail open)

- **Where**: `core/chain.py:486` (`start_time = time.perf_counter()` inside `execute`). The request waits beforehand in asyncio's default executor (`daemon/server.py:1435`, `run_in_executor(None, …)`, min(32, cpu+4) = 12 workers on this 8-core host). That wait is not counted. Post-chain work is not counted either: pseudo-events (`controller.py:1016-1027`, `nitpick` fires on 1 in 5 PreToolUse events), verdict logging and history.
- **Reproducer**: `probe_n24r_p6_queue.py 24`, default config, 24 concurrent requests whose SAFETY+BLOCKING probe sleeps 25 s. Twenty were correctly denied at 20.1 s, and **4 hit CLIENT_TIMEOUT (fail open)** at 30.0 s. Those 4 were queued behind the first 12 workers, started about 20 s late, got a fresh 20 s budget, and the client gave up at 30 s. A destructive command shaped to be slow, sent behind parallel slow calls, fails open the same way. Claude Code runs PreToolUse hooks for parallel tool calls concurrently, and one daemon serves every session and subagent in the project.
- **Direction**: stamp the arrival time in `_handle_client` / `_handle_event_client` and pass an absolute deadline down (`controller.process_request` → `router.route` → `chain.execute`). If the budget is already spent when the chain starts, deny when a SAFETY+BLOCKING handler is registered for the event. Keep pseudo-events and logging inside the same budget, or run them after the response is written. B2's client-side fail-closed also backstops this.

### M2: abandoned stragglers are unbounded in time and cost; CPU-bound ones slow every event down, and 16 of them deny every PreToolUse permanently, with no recovery short of a restart

- **Where**: `core/bounded_dispatch.py:151`. The semaphore is released only when the straggler **finishes**, not when its caller abandons it. `DISPATCH_MAX_INFLIGHT = 16` (`:52`). Nothing tracks straggler age, and no health signal or watchdog exists.

- **Reproducer**: `probe_n24r_p2_saturation.py`, real socket, deadline set to 2 s only to shorten the run, the rest shipped defaults, stragglers that spin in pure Python.

  | Stragglers | Median latency for an ordinary `git status` PreToolUse | Outcome                                                                                                                                                                                                                    |
  | ---------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | 0          | 12 ms                                                  | allow                                                                                                                                                                                                                      |
  | 1          | 775 ms                                                 | allow                                                                                                                                                                                                                      |
  | 4          | 2.3 s                                                  | the chain overran its deadline; the BLOCKING-only handlers after the last SAFETY+BLOCKING handler (`block-comment-changelog`, `plan-journal-guard`, `block-comment-size`, …) were **skipped, so their checks failed open** |
  | 8          | 3.0 s                                                  | every event denied: "chain deadline exceeded"                                                                                                                                                                              |
  | 16         | —                                                      | every PreToolUse denied: "dispatch pool saturated"                                                                                                                                                                         |

  After 16, the state was still present 30 s later, and it lasts until the stragglers exit, which is never for an infinite loop. The Bash command an agent would use to restart the daemon is itself a PreToolUse and is denied.

- **Real handlers produce such stragglers.** From the hostile sweep (`probe_n24r_p5_hostile.py`, inputs under 100 KB):

  - `enforce-lsp-usage`: 48.6 s on 99 KB of newlines;
  - `plan-number-helper`: 21.7 s / 23.1 s / 12.0 s on quote runs;
  - `error-hiding-blocker`, `block-comment-changelog`, `block-comment-size`: over 90 s on a 90 KB `file_path` (the GIL-holding case, B2).

- **Inferred, not verified** (the synthetic marker excludes scoped handlers): when saturated, `cron-stop-enforcer` would block every main-session Stop, because it is SAFETY+BLOCKING.

- **Judgement**: denying while saturated is correct fail-closed behaviour. The lack of any way out is an availability defect, and the graded slowdown before saturation (1 to 15 stragglers) is itself a fail-open path for the BLOCKING-only guards.

- **Direction**:

  - Track the count and age of stragglers. When more than N are alive, or one is older than T, have the daemon report unhealthy and re-exec itself; the client already respawns a dead daemon.
  - Surface the saturation state in `status`.
  - Process isolation (B2 direction 1) solves this class outright, because a worker process can be killed.

### M3: fail-closed depends on tags, and several obviously security-critical deniers carry neither tag, so they still fail open on a raise, a timeout or saturation

- **Where**: `core/chain.py` checks `HandlerTag.SAFETY in handler.tags and HandlerTag.BLOCKING in handler.tags` in `_record_unjudged` and in the `except` branch (`:765`).
  - Untagged but denying: `block-curl-pipe-shell` (`curl_pipe_shell.py:136`, no `tags=`), `block-dangerous-permissions` (`dangerous_permissions.py:80`, no `tags=`), `block-sudo-pip`, `block-pip-break-system`, `lock-file-edit-blocker`, plus 14 more that deny (see `probe_n24r_enum.py`).
  - 22 handlers are BLOCKING without SAFETY (for example `enforce-tdd`, `qa-suppression-blocker`, `plan-*`).
- **Reproducer**: `probe_n24r_p3_failclosed.py`, real controller, `strict_mode` False, which is the client default (`config/models.py:1720`). A forced raise in `block-curl-pipe-shell`, `block-dangerous-permissions`, `lock-file-edit-blocker`, `block-pip-break-system` or `block-sudo-pip` gives **ALLOW(no decision)**. On a timeout or saturation, `_apply_deadline_exceeded` only "skips" these handlers. In the real chain, `block-sudo-pip` / `block-pip-break-system` (priority 21/22) and every BLOCKING-only handler come after the last SAFETY+BLOCKING handler (`block-git-message-backtick`, priority 20). If the deadline runs out there, nothing later can deny.
- **Direction**:
  - Tag `curl_pipe_shell` and `dangerous_permissions` SAFETY+BLOCKING, and audit the other 17 untagged deniers.
  - Add a registry test: every PreToolUse handler whose `Rule` can deny carries SAFETY+BLOCKING, or explicitly declares itself fail-open. That makes the predicate opt-out instead of opt-in.
  - State plainly in the docs that BLOCKING-only means fail-open under deadline pressure.

## Minors

### m1: thread-per-handler dispatch adds about 12 ms to every event

- **Where**: `chain.py:722-727` creates one `threading.Thread` per handler per event (69 PreToolUse handlers with this repository's config).

- **Measurement** (`probe_n24r_p4_latency.py`, in-process `controller.process_request`, 150 samples, median):

  | Build  | Mode                     | `ls -la` | `echo hello world` |
  | ------ | ------------------------ | -------- | ------------------ |
  | Branch | shipped deadline         | 13.97 ms | 14.15 ms           |
  | Branch | `deadline_seconds: None` | 1.66 ms  | 1.81 ms            |
  | Base   | —                        | 0.81 ms  | 1.14 ms            |

  The p90 in deadline mode is 24–29 ms.

- **Direction**: one watchdog-bounded worker per **event**, running the whole chain inline, instead of one thread per **handler**. With process isolation, use a pre-forked worker.

### m2: stragglers keep mutating shared state after the verdict has been returned

- The `on_matched` closure (`chain.py:646`) appends to `handlers_matched` after `execute` has moved on or returned. `chain.py:829` iterates the same list.
- A timed-out `sensitive_content.matches()` can re-populate `_cached_dispatch` after the chain's `commit_side_effects` cleared it (`sensitive_content.py:730`, `:759`). That retains secret-bearing haystack text in a process-lifetime instance, which is exactly what the clear exists to prevent.
- A straggling `handle()` can call `mark_disclosed` (for example `github_auto_close_keywords.py:282`) and spend `lsp_enforcement`'s block-once, although its verdict was never delivered.
- **Direction**: give each dispatch a cancellation token that the handler base checks before side effects; or snapshot the lists, and have `commit_side_effects` run again when a straggler finishes.

### m3: `BoundedDispatcher.run` edge cases

- If `thread.start()` raises (`RuntimeError: can't start new thread`, `bounded_dispatch.py:160`), the permit acquired at `:129` and the `_threads` entry leak for good. Saturation creeps up.
- `except Exception` at `:143` does not capture `BaseException` (`SystemExit`, `KeyboardInterrupt`). The future is never resolved, so the caller waits the whole remaining budget.
- **Direction**: wrap acquire → start in `try`/`except` and release on failure; catch `BaseException` on the worker and set it on the future.

### m4: the fail-open inventory does not see the new fail-open paths

- `scripts/qa/check_fail_open_inventory.py:66` scans `chain.py`, `front_controller.py` and `controller.py`, but not the new `core/bounded_dispatch.py`.
- The new "skip on timeout / saturation / oversize" branches for non-SAFETY+BLOCKING handlers are fail-open boundaries a caller can trigger. They are written as `isinstance` checks, not `except` constructs, so the scanner cannot see them and no inventory row exists.
- B1's route into `controller.py:process_event`'s `except` is a new way to induce an existing row.
- **Direction**: add the surface and rows, or teach the scanner to recognise these branches.

### m5: the size cap measures 4 fields; it is non-monotonic, and it misattributes the deny

- **Where**: `chain.py:60` `_SIZED_TOOL_INPUT_FIELDS`. Results from `probe_n24r_p7_size.py`, real socket:
  - Not measured: MultiEdit with 6 MiB in `edits[]` → allow in 0.14 s; NotebookEdit with 3 MiB `new_source` → allow in 0.09 s; `file_path` (B2's vector).
  - A Bash command of 1.9 MiB → deny by rule (0.34 s). 2.1 MiB → deny by the cap. **17 MiB → the server closes the connection** (`SocketLimit.REQUEST_BUFFER_BYTES` = 16 MiB, `readline` overrun) → BrokenPipe on the client → `init.sh` `fail()` → PreToolUse **fail-open**. So 2–16 MiB denies and more than 16 MiB allows. The transport part predates the branch; a model cannot realistically produce 16 MiB.
  - A legitimate 3 MiB Write is denied. The deny names whichever SAFETY+BLOCKING handler comes first, whether or not it applies to Write, because the size check runs before scope and `matches()`. In the real chain that is `prevent-destructive-git`.
- **Direction**:
  - Measure the whole serialised `tool_input` with `surrogatepass`.
  - Deny an oversized request with a chain-level reason, not a handler's name.
  - Fail closed in the server when the payload exceeds the buffer for PreToolUse.

### m6: nothing ties `deadline_seconds` to the client timeout

`config/models.py`, the `ChainConfig.deadline_seconds` field: only `gt=0` is enforced. A configured 40 s is accepted, and every slow chain then fails open on the client. **Direction**: validate it below `Timeout.SOCKET_DISPATCH_ROUNDTRIP` minus a margin.

## Nits

1. **n1**: `bounded_dispatch.py:73` says "Runs callables on a small, bounded, shared thread pool", and `chain.py`'s comments say "shared pool". There is no pool: each call gets a fresh thread and a semaphore.

2. **n2**: `chain.py:747` puts `assert isinstance(outcome, HookResult)` on the production path. It sits inside the `try`, so a failure would deny, but `-O` strips it. Prefer an explicit check.

3. **n3**: two SAFETY+BLOCKING handlers are above the brief's 1 s threshold, though under the harness's own 5 s bound, on inputs under 100 KB (`probe_n24r_p5.out`):

   - `block-sensitive-content`: 3.7 s on `true;` × 20 k, 2.6 s on 20 k nested `$(`.
   - `block-secret-file-read`: 1.0–2.5 s across 10 shapes. **Owned by the guard-defects branch.**

   No shape made a SAFETY handler raise. `enforce_llm_qa` and `subagent_full_qa_blocker` did not stand out in this sweep; they are owned elsewhere.

4. **n4**: the new tests exercise the synchronous path almost everywhere (`deadline_seconds=None`). Only the dispatch-specific cases and the controller-level tests take the production threaded path. A parametrised run of the chain suite under the shipped default would catch threading-only divergence.

## Pre-existing defects found (not introduced by this branch; record as niggles)

- **P1 (bypass)**: `github_auto_close_keywords.py:241-249` caches its verdict by **command text alone**. `git commit -F msg.txt` is judged clean; the file then gains `Closes #12`; the identical command is still allowed, because the cache hits. A fresh instance denies (`probe_n24r_p8_autoclose_cache.py`: False / False / True). The two-attribute cache write is also not atomic across the concurrent threads that N34 makes routine. Key the cache on the message-file content, or drop it.
- **P2**: the quadratic `utils/path_exclusion.path_matches_globs` behind B2 affects every handler that uses `handler_excludes_path`.

## Direction summary, in order

1. Fix B1: a surrogate-safe measurement, with every pre-loop step inside a fail-closed path. Add the RED test.
2. For B2 and M2, move judgement into killable worker processes, or add an out-of-process deadline watchdog; make `init.sh` fail closed on a PreToolUse `socket_timeout`; fix `path_matches_globs`; cap `file_path`; add long-path shapes to the hostile harness.
3. For M1, base the deadline on request arrival and put pseudo-events inside the budget.
4. For M3, tag the untagged security deniers, and add a registry test that makes fail-open an explicit opt-out.
