## N115: a `}` before the first comma in a quote-free word (shared MAJOR 1)

- **What was wrong:** `expand_braces` returned early for a word with no quoting character. `_shell_brace_words` also yielded only quoted words unless `every_word` was set. So bash's grouping rules (`_BashBraces`) never ran on `cat /proj/.vault-{},pass}`.
- **Fix:**
  - `expand_braces` now reads every word both ways.
  - `iter_shell_brace_words` reports every word that holds a brace, whatever its quoting.
  - `iter_every_shell_brace_word` and the `every_word` switch are removed, because nothing was left for them to select. `python_program_streams` now calls `iter_shell_brace_words`.
  - A word's value after quote removal is re-read as a command whenever it holds a brace. Before, this happened only when a quoted brace survived, so `bash -c 'cat …{},pass}'` now reaches the reader too.
- **Differential test:**
  - A quarter of the generated words now have a `}` or `{}` leading the first alternative.
  - A new run of 2,000 words draws from quote-free primitives only (`{`, `}`, `{}`, `,`, `..`, text).
  - Both runs are RED on the pre-fix branch (`git archive` of d2775367d) and green after.
- **Tests through `HandlerChain`, RED on main 01827942b:**
  - `test_a_close_brace_before_the_first_comma_is_text_n115`, with 5 shapes.
  - The Write `.sh` case.
- **Updated expectations:** three primitive and view tests now also list the re-read value's words (`{a,b}`, `.p-{}`). These add spellings and never remove any.

## N116: a here-string word read as a heredoc delimiter (shared MAJOR 2)

- **Guard fix:**
  - `_shell_brace_words` steps over the whole `<<<` before the `<<` test.
  - So does `_command_substitution_end`. There, `echo "$(cat <<< hi)" {a,b}` used to fail closed as "a heredoc inside".
- **The other `<<` sites, the same class in main's own code:**
  - `shell_segmentation._QUOTED_HEREDOC_BODY_PATTERN` blanked the line after `cat <<<'EOF'` as a quoted heredoc body.
    - Bash runs that line.
    - `destructive_git` and `pipe_blocker` allowed `cat <<<'EOF'` followed by a force-push line on main (probed through `HandlerChain`).
  - `core.utils._HEREDOC_RE` (`split_heredocs`) had the same flaw.
  - So did `background_process_tracker._HEREDOC_OPEN_RE`. Its comment claimed `<<<` could not match.
  - All three regexes now carry `(?<!<)`.
- **Sites checked and found sound:**
  - The view scanner already consumes `<<<` first.
  - `_REDIRECT_RE` lists `<<<` first.
  - Main's normalised-word scan matches `<<<` on accumulated operators.
  - `bash_file_writes` works from `split_heredocs` output.
  - The two `cat\s+<<` regexes cannot match at the second `<`.
- **Tests, each RED on main 01827942b:**
  - `test_a_here_string_word_is_read_as_a_word_n116` through `HandlerChain`, with 5 shapes: `bash <<< $'…'`, unspaced `<<<$'…'`, `sh -s <<<`, `xargs -0 bash -c <<<`, and the decoded `{},pass}` form.
  - `TestAHereStringIsNotAHeredoc` through `HandlerChain` for `destructive_git`.
  - Primitive tests for `strip_quoted_heredoc_bodies`, `split_heredocs` and `_command_is_backgrounded`.
  - Pins that must stay allowed: `echo "$(cat <<< hi)" {a,b}`, `bash <<< $'echo \x7ba,b\x7d'`, `cat <<< '{a,b}' && echo {c,d}`, and a plain heredoc.

## N117: ENAMETOOLONG failed the guard closed (new, found this round)

- **How it was found:** after the merge, the 140-program corpus had 6 allow verdicts turn into `R-SECRET-EVALUATION-ERROR`. Three mention verdicts also turned into evaluation errors.
- **Cause:**
  - Main's `_expand_glob_token` expands, on disk, a glob that shares text with `*.secret*`.
  - A quoted multi-line heredoc chunk read as one word has a component longer than `NAME_MAX`, so `os.stat` raised ENAMETOOLONG.
  - Only ENOENT counted as proof of absence, so the error propagated.
- **Main has the same defect:**
  - `ls <300 a's>/*.rest` is denied there with `OSError`.
  - The live main daemon also denied this round's first commit command the same way.
- **Fix:** ENAMETOOLONG joins ENOENT in `_PROOF_OF_ABSENCE_ERRNOS`. No entry can have that name, and a shell naming the path fails the same way. Every other `OSError` still propagates.
- **Tests, RED on main 01827942b:** one expander test on a real too-long name, with no monkeypatch, and two `HandlerChain` tests.
- **Corpus:** now byte-identical to round 7 (`n101f7/fp-3.txt`): 85 allowed, 54 `R-SECRET-BASH-MENTION`, 1 `R-SECRET-EVALUATION-ERROR`.
- **Ledger:** I took the number N117. Please renumber it if it collides with a number used elsewhere.
