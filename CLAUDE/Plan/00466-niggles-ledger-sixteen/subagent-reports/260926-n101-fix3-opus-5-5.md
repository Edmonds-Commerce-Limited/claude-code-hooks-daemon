## What changed

### 1. Only a Python literal can spell a path

`shell_expansion.python_string_literals` finds literal boundaries with Python's own `tokenize` and `ast`. It reports:

- every `str` and `bytes` token on its own, with escapes decoded;
- every constant in the parsed tree, which adds implicit concatenations, the literal text of f-strings, and strings nested inside f-string fields;
- every comment.

A program that does not tokenise or parse returns `None` and is not exempted.

`brace_expansion_view` neutralises every brace in the exempted program text and always returns the literals. `_brace_expansion_tokens` then enumerates each literal on its own, with the normal caps.

Comments are a deliberate addition to the brief's rule. A program can read its own command line back (`/proc/self/cmdline`) and write or print a comment verbatim. So "only a literal can spell a path" holds only if comments count as literals. A chain row pins this.

### 2. `python_program_reach.py` is deleted

Its tests are deleted too. Nothing depends on reach any more.

The extended spawn-API scan is **kept**, because it adds denials that rule 1 does not. It judges a shell-exec literal as a full shell command: quote assembly, backslashes and `$VAR` collapse, not just braces. A probe with a synthetic pattern showed the difference for a heredoc program calling `os.system` or `subprocess.getoutput`:

- `n'a'me`, `n"a"me`, `n\ame` and `na$X` are caught **only** by that scan.
- A brace spelling is caught by both.

The probe is at `untracked/scratch/n101fix3_probe.py`.

### 3. The scope conditions are kept, and one is added

- A bare top-level `(` now withdraws the exemption. This covers a subshell or a function definition, however the name is spelled.
- Any `PYTHON*` setting outside a small allowlist also withdraws it. The allowlist is `DONTWRITEBYTECODE`, `UNBUFFERED`, `IOENCODING`, `HASHSEED`, `UTF8`, `FAULTHANDLER`, `NOUSERSITE` and `SAFEPATH`.
- Both changes only narrow the exemption.

### 4. Name comparisons are quote-aware

- **New helpers.** `shell_segmentation.iter_shell_words` is a quote-aware splitter. It stops with `None` at the first word whose extent is uncertain: an unterminated quote, `$(`, `${` or a backtick. `resolve_shell_word` removes quotes and backslashes. It returns `None` for any expansion, glob, brace group, `$'…'` or unterminated quote.
- **Heads.** In the view scanner, each segment's head is found past `NAME=value` words and redirections, so `>gen.sh exec` and `X=1 exec >f` are both `exec`. The head is judged after quote removal. An unresolvable head withdraws the exemption.
- **Redefinition words.** Every top-level word is resolved, except the exempted `-c` program word. A word that resolves to `alias`, `hash`, `enable` or `function` withdraws the exemption, and so does a word naming PATH or a non-allowlisted `PYTHON*` setting. An unresolvable argument to a name-assigning builtin also withdraws it (`export $v` sets PATH when `v=PATH=…`). The round-2 regex on masked text is kept as well.
- **Data-sink resolver.** `_segment_command_word` now uses the new splitter and resolver:
  - `sudo -p 'x cat' bash` names `bash`.
  - `$cat`, `` `echo cat` ``, `c*` and `{cat,bash}` name nothing. Main resolved `$cat` to `cat`, a sink.
  - A word after the command word may still contain an expansion: `cat > "$(pwd)/f" <<'EOF'` still names `cat`.

### 5. The view applies only to Bash tool command lines

- A new keyword, `bash_tool_command`, is threaded through `find_protected_mention`, `find_protected_mention_detail`, `iter_protected_mentions` and `_brace_expansion_tokens`.
- Only the guard's Bash route and payload capture set it. Payload capture also receives the Bash tool's whole command.
- Script Write/Edit content, command segments (`flaggable_content_channel_guard`) and `"content"` are enumerated exactly as on main.
- The docstring now says this.

### 6. The data-sink widening is recorded (D-RULE m1)

It is recorded in three places: NIGGLES N101, the `_WRAPPER_GRAMMARS` comment, and the corrected `quoted_heredoc_command_words` docstring. Each entry names every wrapper and gives the reason it is sound. The interior-backslash resolution (`c\at` is `cat`) is named as part of the widening.

### 7. The branch's N105 is removed

It is gone from NIGGLES and from the PLAN table. Its content (source, `hash`, `enable`, `.`, PATH, and quoted spellings) is folded into main's N89. N104's text is also updated: both surfaces now follow one rule, which is to enumerate literals.

## Behaviour changes to flag

**1. A literal with a real over-bound brace group now fails closed.** Examples are `print('{a,b}…×9')` and the same inside `-c`. This follows from the ruling ("every literal … with the guard's normal caps"), and D-SEC predicted it.

- Two round-1 "allowed" pins were converted to fail-closed pins: `test_an_over_bound_brace_string_literal_still_fails_closed`.
- In the round-1 false-positive table, those two rows are replaced by a code-brace `-c` program and by a code-brace program that imports and runs `subprocess`. The second was denied in round 2 and is now allowed.
- The N101 field-report shape, which is dicts and f-strings, stays allowed.

**2. Other rows were changed:**

- `test_python_heredoc_piped_on_to_any_stage_still_fails_closed` now uses the code-brace program, so it pins the pipe withdrawal and not literal enumeration.
- `test_shell_segmentation.py::test_an_expansion_built_command_word_names_no_command` was renamed and now expects `[]` for `$SHELL`. Main returned `["SHELL"]`.
- The `PYTHONPATH=src python3` "neutralised" row became `PYTHONDONTWRITEBYTECODE=1`.

**3. Python 3.12 and later tokenise f-strings as separate tokens.** On those versions, per-token extraction covers only plain `STRING` tokens. The whole-tree `ast` walk still reports every f-string constant, so no literal is lost. I checked `python_string_literals` against the unit cases under both 3.11 and 3.13.
