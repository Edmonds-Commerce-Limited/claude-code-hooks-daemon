## Part 1 — `daemon.strict_mode` plumbing

`DaemonController.process_event` read `self._config.strict_mode`, and
`self._config` is never populated by the real daemon startup path
(`get_controller()` builds a bare `DaemonController()`;
`_build_initialised_controller` in `daemon/cli.py` threads individual config
slices into `initialise()` instead). So `strict_mode` was always `False` on
every real install, whatever `hooks-daemon.yaml` declared.

`DaemonController` gained a narrow-slice `_strict_mode` attribute, following
the exact DI idiom `_chain_config`/`_verdict_log_config` already use:
`initialise(strict_mode: bool | None = None, ...)` sets it (`None` keeps the
default `False`); `process_event` reads `self._strict_mode` instead of
`self._config`. `_build_initialised_controller` now passes
`strict_mode=config.daemon.strict_mode`.

- `src/claude_code_hooks_daemon/daemon/controller.py`
- `src/claude_code_hooks_daemon/daemon/cli.py`

  `test_cli_verdict_log_wiring.py`: patches `initialise` and asserts

## Part 2 — SAFETY+BLOCKING handlers fail closed regardless of `strict_mode`

`HandlerChain.execute`'s per-handler `except Exception` now checks whether
the raising handler carries both `HandlerTag.SAFETY` and `HandlerTag.BLOCKING`
(24 built-in handlers do, including `secret_file_guard` and
`project_containment`, the two the review's m1/m2 findings were about). If
so, it denies unconditionally — whatever `strict_mode` says — with a reason
naming the handler and the underlying exception ("evaluation error, denied
for safety"), distinct from strict_mode's own "SYSTEM ERROR" wording so a
verdict log can tell the two paths apart. A non-`SAFETY`+`BLOCKING` handler's
behaviour is unchanged. The try/except this lives in already spans both
`handler.matches()` and `handler.handle()`, so this closes the class for a
raise from either — the review's m1 (`handle()`'s tail outside a guard's own
fail-closed wrapper) and m2 (`matches()`/`handle()` re-evaluating differently)
are both covered structurally at the chain level, for every SAFETY+BLOCKING
guard at once, not just the two N11 hardened by hand.

- `src/claude_code_hooks_daemon/core/chain.py`

RED/GREEN — `tests/unit/core/test_chain.py` (5 new cases):

- a SAFETY+BLOCKING handler raising in `handle()` denies with `strict_mode=False`
- the same, raising in `matches()` instead (never reaches `handle()`)
- a non-SAFETY-tagged advisory handler raising still fails open (unchanged)
- SAFETY without BLOCKING does NOT trigger the new path (still fails open) —
  pins the predicate is the SAFETY+BLOCKING *combination*, not SAFETY alone
- with `strict_mode=True` AND SAFETY+BLOCKING both true, strict_mode's own
  wording ("SYSTEM ERROR") still wins — the two mechanisms don't silently
  swap messages

`MockHandler` gained `tags` and `raise_in_matches` parameters to support
these.

## N25 — a slow handler runs out the client's 30s budget, and a timeout ALLOWs the whole chain

Added to this branch after N24 landed. Three candidate remedies, all three
implemented:

### 1. Daemon-side per-event chain deadline

`ChainConfig.deadline_seconds` (`config/models.py`), default
`Timeout.CHAIN_DEADLINE_DEFAULT = 20` (seconds, `constants/timeout.py`),
threaded through `DaemonController.initialise()` -> `process_event()` ->
`EventRouter.route()` -> `HandlerChain.execute()` — the same narrow-slice DI
idiom N24 used for `strict_mode`. Inside `execute()`'s per-handler loop, a
deadline check runs before each not-yet-run handler: once exceeded, every
remaining `SAFETY`+`BLOCKING` handler is denied under N24's fail-closed rule
with a "not judged in time" reason naming the handler; every other remaining
handler is skipped instead, with an advisory note. `deadline_seconds: null`
disables enforcement.

- `src/claude_code_hooks_daemon/config/models.py`,
  `constants/timeout.py`, `core/chain.py`, `core/router.py`,
  `daemon/controller.py`

RED/GREEN: `tests/unit/core/test_chain.py` (4 new deadline cases),
`tests/unit/core/test_router.py` (deadline passed through to the chain),
`tests/unit/config/test_chain_config.py` (4 new cases: default value under
the client timeout, parsing, `null` disables, rejects non-positive),
`tests/unit/daemon/test_controller.py` (`test_deadline_seconds_reaches_the_router`,
patches `EventRouter.route` to capture the kwarg end to end from a real
`ChainConfig`).

### 2. `strip_inert_spans` made linear

Reproduced the review's two 200 KB repros directly against `main`'s code
first, confirming both (`git commit ` + `-m x ` × 40000: 99.179s;
`git commit -F - <<'EOF'...EOF` × 5000: 98.342s) — RED. Root cause was the
same shape in three places inside `shell_segmentation.py`:
`strip_message_bodies`'s segment/binary/subcommand resolution and
`strip_quoted_heredoc_bodies`'s substitution-depth and receiving-segment
lookups all re-derived prefix-dependent state from scratch
(`command[:match_start]` slicing/rescanning) for every regex match, instead
of advancing incrementally in the guaranteed left-to-right match order that
`re.finditer`/`re.sub` provide. Replaced with three stateful tracker classes
(`_SegmentTracker`, `_SubstitutionDepthTracker`, `_LastNewlineTracker`), each
bounding its per-match cost to the gap since the previous query rather than
the absolute position — total cost across a whole scan is now O(n). Same two
repros after the fix: 0.139s and 0.453s respectively (>200x speedup each).

- `src/claude_code_hooks_daemon/utils/shell_segmentation.py`

RED/GREEN: `tests/unit/utils/test_shell_segmentation_performance.py` (new) —
5 tests pinning both shapes plus the combined `strip_inert_spans` case at
200 KB under a 3s bound, plus correctness checks that a protected string at
the END of a 40000/5000-repetition command is still blanked (the position
quadratic cost would hide worst). Full regression across
`destructive_git`/`curl_pipe_shell`/`shell_segmentation` suites: 2433
passed, 1 pre-existing unrelated xfail.

### 3. Hostile-input harness across every SAFETY handler

`tests/unit/handlers/test_safety_handlers_hostile_input_performance.py`
(new) discovers every `HandlerTag.SAFETY` `pre_tool_use` handler via
`iter_builtin_handler_classes()` (23 handlers, never a hardcoded list — the
same enumeration `register_all` uses, Plan 00330) and drives each with four
hostile shapes against both a `Bash` command payload and a `Write`
file-content payload: many small quoted/backslashed/wildcarded tokens (the
shape that actually caused #2's bug — many MATCHES, not one giant token) and
deep `$(...)` command-substitution nesting, all under a 5s bound at 100 KB.
Found no other super-linear handler (9/9 sub-tests pass in ~6s combined).
One handler, `SecretFileGuardHandler`, stood out as markedly slower than its
peers (~1.3s at 100 KB vs \<0.25s for everything else); measured its scaling
separately up to 800 KB and confirmed it is LINEAR (doubling the input
roughly doubles the time) — a high constant factor, not a superlinearity
bug, so it is noted in NIGGLES.md rather than "fixed": out of this niggle's
scope, which is specifically superlinear paths, but worth a follow-up look
if it ever becomes a real bottleneck.
