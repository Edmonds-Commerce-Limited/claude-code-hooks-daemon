## MAJOR 1: an f-string's source text is no longer brace-enumerated as a whole

**Citation:** `shell_expansion.py`, `python_string_literals` (around line 561, the docstring's bullet on "the literal text of an f-string").

**What it allows:** For `f"…p{a,x}ss"`, only the literal parts (`"…p"` and `"ss"`) and the field's contents are reported. The raw text that crosses the literal/field boundary is neutralised and never enumerated.

- Probe with an inert placeholder: main's raw stream yields `/tmp/demo-pass`; the branch yields no brace tokens at all.
- None of the other token streams expands braces, so this is a deny that became an allow.

**Class:** Program text that is neither a literal nor a comment but still spells a path, because it sits right next to literal text. The fixer's own reason for enumerating comments ("a program can read its own command line back") applies to this text in the same way. So the invariant "only a literal can spell a path" is incomplete as implemented.

**Why the tests miss it:** No test has a brace group in an f-string field placed right next to literal text. A grep of the view and guard tests finds no `JoinedStr` or `get_source_segment` case.

**Detector hypothesis:**

- Also report the source segment of every `JoinedStr` node (`ast.get_source_segment`), or each raw STRING token on Python 3.11 and earlier.
- Likely false positive: an f-string field holding a comma tuple or a dict display, which could hit the over-bound cap. The coordinator has already ruled that this fails closed, so it is acceptable.

**Confidence:** high for the difference between main and the branch (probed at the token level).

## MAJOR 2: some builtins that run shell text in the current shell do not withdraw the exemption

**Citation:** `shell_expansion.py`, `_EXEMPTION_WITHDRAWING_HEADS` (around lines 336–362). `mapfile` appears only in `_NAME_ASSIGNING_BUILTINS` (line 433).

**What it allows:** In my probe the view neutralised a Python program sitting next to `trap '…' DEBUG` and next to `mapfile -C '…'`. Both builtins evaluate their string argument as shell code in the current shell. That is the same property that put `eval` and `exec` on the list. So the view's claim that nothing on the line can turn the program back into shell text does not hold for these two builtins.

**Class:** The same class as round-2 B1: a deny-list of heads that execute shell text, where some members are missing. `trap` and `mapfile -C` are the members I found.

**Why the tests miss it:** No test in the view or guard suites mentions `trap` or `mapfile -C`.

**Detector hypothesis:**

- Add `trap` as a withdrawing head, and treat `mapfile`/`readarray` with `-C` the same way.
- A sturdier fix is to invert the rule: allow only an explicit list of inert heads next to an exempted program.
- False positives: very few. `trap` next to an inline Python program is rare.

**Confidence:** high that the view is neutralised (probed). I did not check how much this matters in practice, and I would route that check to the quarantine executor.

## Minor 1: the stated reason for skipping `sudo` does not cover `-R`/`--chroot`

**Citation:** `shell_segmentation.py`, `_WRAPPER_GRAMMARS["sudo"]`: `R` is in `value_flags` and `chroot` is in `long_value_flags`.

**What it allows:** The comment argues each wrapper is sound because it runs the named command unchanged, and it says the modes that change PATH are refused. A chroot changes which binary the name resolves to, more thoroughly than a PATH change does, yet it is accepted. The bar is the same as a planted binary.

**Detector hypothesis:** Refuse `-R`/`--chroot`, which returns no command. No realistic false positive.

**Confidence:** high, from reading. The other wrappers' stated reasons (env, nice, nohup, timeout, command) are sound.
