## B1: BLOCKER. A quoted or escaped withdrawing head does not withdraw the exemption

**Citation.** `shell_expansion.py:545–546`:

```python
heads = [self.word(segment.words[0]) for segment in self.segments if segment.words]
if any(head in _EXEMPTION_WITHDRAWING_HEADS for head in heads):
```

`self.word` returns the raw source text, quotes and backslashes included. The probe results:

- Bare `exec >out.txt; python3 -c '…'` is **kept**.
- `\exec`, `'exec'`, `e\xec`, `'source'`, `"."` and `\eval` in the same position are **neutralised**.

**What it allows.** Bash does quote removal before it looks up a builtin, so `'exec' >f` still redirects the shell's own stdout for the rest of the line. The Python segment then carries no redirect of its own. So `writes_a_file` is False, sibling commands are never checked, and literals are not enumerated. A later sibling that runs `f` executes a brace-spelled protected path that no stream expanded. Main denies this; the branch allows it.

This is F2's `> gen.sh` then `bash gen.sh` route with the redirect moved onto a spelled-differently `exec`. A quoted `source` or `.` likewise reopens F5. No planted file and no polyglot is needed.

**Class.** A withdrawal rule keyed on a command name, compared against the word as written rather than the word bash resolves. It belongs to the class if some quoting or escaping of the name still runs the same builtin or keyword-equivalent, but fails the string comparison.

**Why the tests miss it.** Every withdrawal pin (`TestTheInterpreterMustBePython`, `…d_rule_f5`) and the fix report's list use the bare spelling. No test quotes or escapes a head. Round 1 pinned only bare spellings too, so the mutation proof could not see this.

**Detector hypothesis.** Property test: for every head in `_EXEMPTION_WITHDRAWING_HEADS`, generate `'h'`, `"h"`, `\h`, and `h` with an interior backslash. Assert that `brace_expansion_view` returns the command unchanged.

- Structural rule: never compare a shell word to a name list without full quote removal.
- `command_word()` strips surrounding quotes and a leading `\`, but not an interior backslash, so on its own it is not enough.
- Simpler rule: any head containing a quote or a backslash withdraws the exemption.
- False positives: near zero, because quoting a builtin name is rare in real commands.

**Confidence.** High at view level (probed). High for the handler verdict, because only the brace stream expands braces.

**What would settle it:** a chain row in `test_a_program_whose_output_a_shell_reads_is_judged` using `\exec >gen.sh` and the existing `_BRACE_PATH` fixture, and a quoted `source` row in the F5 test, each asserting DENY.

## B2: BLOCKER. The view is applied to authored shell-script content, whose stdout the view cannot see

**Citation.**

- `secret_file_matching.py:1497–1504`: every non-`"content"` context goes through `brace_expansion_view`.
- `secret_file_guard.py:1494–1507`: `.sh`, `.bash`, Makefile, `.mk`, CI YAML and shell-shebang files are scanned with `context="bash"`.

The docstring at `secret_file_matching.py:1487–1489` says: *"`"content"` (a file being authored) is enumerated whole, as before: the view models a COMMAND line, not a source file."* That is false for exactly the files this surface exists to guard.

The probe returned `NEUTRALISED`, with 0 brace tokens, for both of these:

- `#!/bin/bash\nset -euo pipefail\npython3 -c '…'\n`
- `#!/bin/bash\npython3 - <<'EOF'\n…\nEOF\n`

**What it allows.** Take a Write of `gen.sh` whose Python step only prints a brace-spelled protected path. Main denies it, because the raw brace stream enumerates the path. The branch allows it.

The view's safety argument is "the program's stdout reaches no shell". In a script, that stdout goes to whoever runs the script later, in a separate call such as `bash gen.sh | sh`. That later command names nothing protected, so nothing denies it either. This is the write-then-execute gap the guard's docstring at `:1459–1466` says `context="bash"` exists to close. N104 keeps `.py` files fully enumerated for this very reason, and the same reasoning applies here.

**Class.** An exemption justified by a property of the Bash tool's command line (stdout is the model's terminal) and applied to text with a different execution context. It belongs to the class if the text is not run as the tool's own command line: a file, a recipe, a CI step.

**Why the tests miss it.** The only Write-route test (`test_writing_shell_source_with_an_over_bound_word_still_fails_closed`, `:2055`) has an `echo` body. No test writes a Python program into a script file.

**Detector hypothesis.** Make the view opt-in rather than opt-out: an explicit `route="bash_command"` argument, which only the Bash-tool route passes. Every file-authoring caller then keeps raw enumeration. A test that Writes `gen.sh` containing `python3 -c 'print("cat /proj/.vault-p{a,x}ss")'` would assert DENY.

False positive: the N101 cap failure returns for over-bound Python inside authored shell scripts. That is main's behaviour today, and it is a separate niggle if wanted.

**Confidence.** High. The view behaviour is probed; the context routing is read directly from the guard.

## M1: MAJOR. The name-redefinition regex runs on quote-masked text, so quoted `hash` / `PATH` spellings pass

**Citation.** `shell_expansion.py:379` (`_NAME_REDEFINITION_RE`) is applied to `shell_level_text()` (`:543`), which blanks every quoted span. The prefix class `(?:^|[\s;&|(\`\])\` also misses a leading backslash.

The probe results:

- `'hash' -p /bin/true python3; python3 -c '…'` is neutralised.
- `\hash -p …` is neutralised.
- `export "PATH=/opt/x"; …` is neutralised.
- `export P\ATH=/opt/x; …` is neutralised.
- The bare `hash` and `export PATH=` forms are kept.

**What it allows.**

- A quoted `hash -p <existing binary> python3` makes the exempted text run under another interpreter, with no planted file. Turning that into a mention needs text that parses as Python and also means something to the substitute binary: a polyglot, which is a known construction. That constraint is why this is MAJOR rather than BLOCKER.
- A quoted `PATH` export needs a planted binary, which is the same bar as round-1 F5.

**Class.** Same root as B1: a deny-list of redefinition spellings, matched before quote removal.

**Why the tests miss it.** `TestTheInterpreterMustBePython` lists only unquoted forms.

**Detector hypothesis.** Search the raw text, not the masked text, for `hash`, `alias`, `enable`, `PATH`, `declare`, `typeset`, `readonly`, `printf -v` and `read`, after removing quotes and backslashes. Or withdraw the exemption when any segment head contains a quote or backslash, which also closes B1.

Noise: `PATH` appearing in a quoted `echo` or `grep` argument would withdraw the exemption, which only means a return to main's behaviour.

**Confidence.** High at view level. The polyglot step is unconfirmed, and I deliberately did not attempt it.

## m1: minor. The wrapper resolver widens the data-sink heredoc exemption for seven handlers, and this is not named

**Citation.** `shell_segmentation.py:190–244` (`_WRAPPER_GRAMMARS`), consumed by `_receiver_is_data_sink` and `_downstream_is_all_data_sinks`. Their callers are `strip_quoted_heredoc_bodies` / `strip_inert_spans`: destructive_git, pipe_blocker, curl_pipe_shell, merge_to_main_approval, reference_repo_freshness, bash_flags and process_probe.

I ran the same inputs on both trees. The heredoc body is **kept on main and blanked on the branch** for:

- `env cat`, `nohup cat`, `timeout 5 cat`, `nice cat`, `command cat`
- `sudo -u root tee f`
- `cat <<'EOF' | env cat`

**What it allows.** A heredoc body that a destructive_git, pipe or curl rule used to judge is now treated as prose when a wrapper sits in front of a sink.

In each case I checked, the wrapper execs the named command with the same stdin, so the widening looks sound. `command` and `env` even bypass shell functions, which makes them safer than a bare `cat` given N105. But it is a deny-to-allow change, and the D-RULE check requires a stated reason for each one.

The fix report and NIGGLES frame this only as a tightening. NIGGLES `:21–22` says "changed only how wrapper options are skipped". The `quoted_heredoc_command_words` docstring (`:808–811`) still says only `sudo` is skipped. One test, `("sudo env nice -n 5", "tee")`, pins the widening without naming it.

**Why the tests miss it.** They are all phrased as "a wrapper option's value is not the command", which is the tightening direction.

**Detector hypothesis.** Any change to a shared allowlist resolver ships with a differential test on main vs branch over a fixed corpus of receiver shapes. It reports every flip from kept to blanked, and each flip needs a written reason. It has no false positives, because it reports flips rather than judging them.

**Confidence.** High (both trees probed).

## m2: minor. The reach analysis's name deny-list can be passed by a computed attribute lookup

**Citation.** `python_program_reach.py:37` includes `os`, `operator` and `types` in `_STDOUT_ONLY_MODULES`. `:102` `_REACHING_NAMES` lists `getattr`, `vars` and friends, but not `dir`, `operator.attrgetter`/`methodcaller`, or `types.CodeType`/`FunctionType`.

**What it allows.** A program can reach `os.system` through a name computed from `dir(os)`, or through a hand-built code object, without naming anything on the list. Its brace-spelled literal is then not enumerated. The module docstring's promise, "an unknown name costs a false positive … never a bypass", does not hold.

It is minor because an author who can do that can equally assemble the path at runtime, which is the accepted residual.

**Class.** An allowlist of modules combined with a deny-list of names: complete only if the deny-list covers every dynamic-dispatch primitive in the allowed modules.

**Why the tests miss it.** `test_python_program_reach.py` tests listed names only.

**Detector hypothesis.** Move `operator` and `types` off the allowlist, and add `dir`, `attrgetter` and `methodcaller` to `_REACHING_NAMES`. Or accept this residual and fix the docstring. The false-positive cost is small, since neither module is common in one-liners.

**Confidence.** Medium-high, from reading. I did not probe it, to avoid constructing the bypass.

## m3: minor. Code the interpreter loads before the program runs is outside the analysis

**Citation.** `python_program_reach.py` module docstring; `_PYTHON_VALUE_FLAG_LETTERS` = `WX` (`shell_expansion.py`).

- `-c` and `-` put the working directory first on `sys.path`, so a `json.py` there shadows an allowlisted stdlib module.
- `PYTHONPATH=` is allowed as a prefix assignment.
- `-W …::mod.Cat` imports `mod` to resolve the warning category.

**What it allows.** A module the analysis cannot see into receives the program's strings. This needs a separately authored file, the same bar as round-1 F5, which was ranked minor.

**Detector hypothesis.** Withdraw the exemption on any `PYTHON*=` assignment and on `-W`/`-X`. `-I` isolation cannot be required, because it breaks ordinary use.

**Confidence.** Medium, from reading.
