## Finding 1 (MAJOR) — episode survived a human's move to a lower family

`note_model_reading`'s episode-close check compared family RANK
(`_family_rank(family) > _family_rank(ep_family)`), so a human picking Sonnet
while the open episode's fallback was Opus never closed it (`rank(sonnet) < rank(opus)`) — the episode rode out the flip-flop backoff and `/model fable`
was typed over the pick once it expired.

Fixed: close (and spend the record) on `family != ep_family` — ANY change
away from the fallback, not only a rise. Deleted the now-provably-dead
"further drop follows the session down" `else` branch (confirmed unreachable:
reaching it requires `prev_family` to be the top family, but any fable
reading always closes an open episode before that branch is reached).

Tests (`tests/unit/supervise/test_manual_model_choice.py`):
`test_a_human_pick_of_a_lower_family_closes_the_open_episode`,
`test_a_human_pick_of_a_lower_family_is_never_reverted_once_backoff_expires`.
RED-verified against a `git archive` copy of the pre-fix source (both failed
with `assert '...:opus' is None` before the fix).

Also reran the reviewer's own probes
(`/workspace/untracked/scratch/probe_n47r5r_scenarios_test.py`) against the
fixed worktree: all 12 scenarios (S1, S1b, S2, S3/S3b window edges, S4, S5,
S6) now pass with no `/model` command typed where the human's pick should
win.

## Finding 2 — a record attributed after a later Fable sighting superseded it

Added `_last_top_family_seen_session` / `_last_top_family_seen_ts`: updated
on every reading that shows the top family (fable), EXCEPT the very first
reading this process has ever seen for the session (that one IS the origin
of whatever drop follows it, not a later confirmation — needed to keep the
existing attribution-window tests green, since those deliberately date a
record up to 300s before the very reading that starts the drop).
`_downgrade_is_attributed` now also refuses when that last-seen time postdates
the record's own event time by more than a 30s render-skew
(`_DOWNGRADE_SUPERSEDE_SKEW_SECONDS`).

Verified via the reviewer's S2/S4/S5 probes (unwatched downgrade + manual
fable + manual opus; unpaired standalone after a spent block; keyless legacy
record) — all three now type nothing.

## Finding 3 — Effort Source's env-object and null/auto gaps

- `_check_effort_source` now also reads `env.CLAUDE_CODE_EFFORT_LEVEL` from
  the user, project and local settings files (Claude Code applies a
  settings file's `env` object exactly like the shell).
- A top-level `effortLevel` of `null`/`"auto"`/`"unset"`/`""` no longer
  counts as a pin (same non-pinning values as the env var).
- Managed settings and `--settings` are NOT read — this project vendors no
  confirmed on-disk managed-settings path, and `--settings` cannot be seen
  from a running session. Chose the "correct the doc" branch of the
  finding rather than guess a path: `_EFFORT_CHECK_WHERE`, the truth-change,
  the release note and `CcySupervisor.md` now name this as an explicit gap
  instead of claiming coverage.

Tests: `test_an_env_object_pin_in_project_or_local_settings_is_a_warning`,
`test_an_env_object_pin_in_user_settings_is_a_warning`,
`test_a_non_pinning_env_object_value_is_not_a_pin`,
`test_a_non_pinning_top_level_effort_level_is_not_a_pin`. RED-verified
against pre-fix source (8 failures, all the expected shape).
