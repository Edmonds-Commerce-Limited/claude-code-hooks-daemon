## started_event

- **Set on every successful start: yes.** `server.py:732` runs after both binds. Partial per-event binds and transport-off still reach it (tests at `test_event_socket_listeners.py:906-936`). A restart is a new process with a new instance, so it gets a fresh event. `server.py` has no separate degraded-start path; degraded mode lives in the controller, and `start()` is unchanged by it.
- **Never set on a failed bind: yes.** My probe patched `_acquire_socket_and_bind` to raise. The event stayed unset.
- **Every wait has a timeout: yes.** All converted sites use `asyncio.wait_for(..., timeout=Timeout.SOCKET_CONNECT)` (5 s).
- **Converted tests still assert what they did: yes.** Each change is a one-line swap of the sync point, and no assertion was altered.
- **Leftover fixed startup sleeps: none.** `grep -A2 'create_task(.*\.start())' | grep sleep` finds only a docstring.
- **Flakes:** 5 serial runs of all 9 touched test files passed (153 each), and so did 4 concurrent copies of the three socket-heavy files (56 each). No flakes seen.

### MEDIUM-1: a failed start is reported as a 5 s TimeoutError, not the real exception

When `start()` raises before it reaches `started_event.set()`, every converted test blocks for the full 5 s. It then fails with `TimeoutError`, and the real `OSError`/`DaemonAlreadyRunningError` sits unretrieved on `server_task`. My probe printed: `waiter got TimeoutError; event set? False task done: True exc: bind boom`. Before this change the old sleep let the next `open_unix_connection` fail quickly, with the error close to the cause.

Direction: add a tiny shared test helper that races `started_event.wait()` against `server_task` and re-raises the task's exception if the task finishes first. Alternatively, have `start()` store the failure so the helper can surface it. This touches roughly 60 sites, so a helper is also cheaper than repeating the call everywhere.

### MEDIUM-2: "reset on stop" is not implemented

`shutdown()` (`server.py:1182-1243`) never clears `started_event`. My probe printed `after clean stop, started_event still set: True`. In practice the impact is nil: `_shutdown_requested` is never cleared either, so a `HooksDaemon` instance is already single-use. It is still a stated requirement, and it matters to an embedder that polls `started_event.is_set()` as "is live".

Direction: either call `self.started_event.clear()` in `shutdown()` and add a test, or document in the attribute comment and release note 33 that the event means "has started at least once", not "is currently live".

## LOW

- **LOW-1: CI ordering.** The `GITHUB_ENV` line comes after `restart` and `status` (`qa.yml:192-201`). If either fails, `bash -e` stops the step before the variable is written, and the `!cancelled()` test step then runs without escalation. The job is still red because the start step failed, so this is not silent. Writing the variable first would make the acceptance tests fail loudly as well, and the step's own comment says that is the intent.
- **LOW-2: the conftest culprit note can blame an innocent restart.** The note at `tests/conftest.py:647-656` fires on any pid-file mtime change. The daemon's own `_touch_daemon_files_periodically` also touches `daemon*.` files, hourly (`server.py:1138`, `paths.py:2254-2258`). A real test-caused rewrite that coincides with that touch would be labelled "almost certainly the real cause". Direction: soften the wording to "likely", or compare the pid file's inode or content instead of its mtime. Otherwise the change is correct: it is additive, the generic text is kept, and the restore happens before the raise.
- **LOW-3: remaining sleep-then-assert shapes in `test_server.py`.** These are not startup-related, so they are outside N39's stated scope, but they are the same class. At `:724`/`:732`, `sleep(0.05)` is followed by `assert daemon._active_requests == 0`. At `:433`, `sleep(0.05)` is followed by the shutdown, on the assumption that the slow request is already in flight. Worth a ledger entry.
