## F1 — BLOCKER: a single-quoted interpreter argument is neutralised however the interpreter's output is consumed

**Citation.** `shell_expansion.py:486` (and the same at `:494` for `$'…'`):

```python
if not in_substitution and self.owner_is_interpreter(command_start, index):
    self.neutralise(index + 1, end)
```

The heredoc branch has a pipe-stage check (`body_is_inert`, `:741`). This branch has none. The probe returned NEUTRALISED for:

- `python3 -c '…x{a,b}{c,d}…' | bash`
- `… | xargs sh -c`
- `… > >(bash)`
- `… | while read l; do bash -c "$l"; done`

**What it allows.** Take a command where the interpreter prints text containing a brace-spelled protected path, and the same command line pipes that output into a shell. Before N101 it was denied (the raw brace stream expanded it, and an over-cap one failed closed). Now it is allowed, because no stream sees the brace spelling. This is the `-c` twin of the heredoc case the diff pins as still denied, so the fixer's own rule already classifies it as a deny.

**Class.** An exemption keyed on who receives the text, with no check on who reads what the receiver emits. A case belongs to the class if the exempted text can reach a shell through the receiver's stdout, or through a file the receiver writes, and that shell is named on the same command line.

**Why the tests miss it.** `TestSingleQuotedArguments` (`test_shell_expansion_brace_view.py:301–332`) has no pipe, redirect or process-substitution case. `test_interpreter_body_piped_on_to_a_shell_is_kept` exists only for heredocs. The mutation proof in the report mutated "pipe stages", but those exist only in the heredoc path, so no mutation could reveal that the single-quote path lacks them.

**Detector hypothesis.** A property test over the view's allowed shapes. Take every input where `brace_expansion_view(S).text != S` and wrap it as `S | bash`, `S | xargs sh -c`, `S > >(bash)`, `( S ) | bash` and `{ S; } | bash`. Assert that each wrapped form comes back unchanged. False positives should be near zero, because every wrapped form really does feed a shell. The structural twin: every call to `neutralise(` must sit under a guard that includes an output-consumer predicate. That can be a grep-level lint over `shell_expansion.py`, and it would have fired here.

**Confidence.** High at view level (probed). High that the handler now allows the mention, because the brace stream is the only route that expands braces. **What would settle it:** a `HandlerChain` test mirroring `test_over_bound_python_heredoc_piped_to_a_shell_still_fails_closed`, but using `-c` and the existing `/proj/.vault-p{a,x}ss` fixture, asserting DENY.

## F2 — BLOCKER: the heredoc consumer check sees only `|` stages in the same scan context

**Citation.** The rules sit in `extend_pipelines` (`:699`), `end_pipelines` and `body_is_inert` (`:741`). The subshell branch at `:522` recurses into a fresh `scan`, which has its own `pending` list. So a `)` or `}` followed by `| bash` is never added to the inner heredoc's stages. Redirections and process substitutions are never stages at all. The probe returned NEUTRALISED for:

- `( python3 - <<'EOF' … EOF ) | bash`
- `{ python3 - <<'EOF' … EOF } | bash`
- `python3 - <<'EOF' > >(bash)`
- `python3 - <<'EOF' | tee >(bash)` (`tee` is a data sink, but its argument is a process substitution feeding a shell)
- `python3 - <<'EOF' > gen.sh` followed by `bash gen.sh`

**What it allows.** The case the diff pins as denied (`python3 - <<'EOF' | bash`) is allowed once it is wrapped in a subshell or group, or written as an output process substitution. For `> gen.sh` followed by a run, the result contradicts the diff's own rationale. At `:741–747`, `cat > gen.sh <<'EOF'` is not inert because it "authors a file a later command can run". An interpreter printing that same text into `gen.sh` is treated as inert.

**Class.** Same root as F1: the consumer test is modelled as the pipeline stages of the heredoc's own simple command, not as every route from the receiver's output to a shell.

**Why the tests miss it.** The pipe tests (`:256–274`) use only a bare `| stage` on the opener line. None wraps the receiver in `( )` or `{ }`, and none uses `>(…)` or `> file`.

**Detector hypothesis.** The same property test as F1, applied to heredoc shapes, plus a `tee >(bash)` wrap. Its noisy point: the `> file` then later-run form cannot be decided in general. A detector that keeps every heredoc body whose receiver has an output redirect would fire on ordinary `python3 - <<'EOF' > out.json`. Report that part as noisy. Cheaper option: keep the body only when the same command also executes the redirect target (the command word or first argument after `bash`, `sh`, `.` or `source` equals the target).

**Confidence.** High at view level (probed). **What would settle it:** chain-level DENY tests for the subshell, group and `>(bash)` forms using the existing fixture.

## F3 — MAJOR: every single-quoted argument of an interpreter is neutralised, not only its code argument

**Citation.** At `shell_expansion.py:486` the only question is whether the segment's command word is an interpreter. The argument's position is never checked. The docstring at `:387` says "argument of a simple command", but its example and the report both describe the code argument. Probe `sq_argv`: `python3 script.py '…x{a,b}{c,d}'` is NEUTRALISED. The same holds for `python3 -m mod '…'` and for extra arguments after `-c CODE`.

**What it allows.** With `python3 script.py '…'`, the script's source is not on the command line. So the guard's compensating defence cannot apply: the shell-exec literal scan has no code to read. If the script hands its argv to a shell, a brace-spelled argument reaches the shell unexpanded by the guard. Before N101 it was denied. An identical call through an unrecognised wrapper name (`mytool '…'`) is still enumerated, so the exemption depends on the interpreter's name, not on anything about the text.

**Class.** An exemption granted for "this text is code in language L" and applied to text that is not the code: data arguments, module arguments, and arguments to a script file.

**Why the tests miss it.** Every single-quoted test puts the quoted text in the `-c` position. No test has a script path or `-m` before the quoted argument.

**Detector hypothesis.** Limit the exemption to the family's code flag, reusing `_OneLinerFamily`'s `code_flags` and `value_flags` that the guard already has. The check: a unit test that the quoted argument following a script path or `-m MOD` comes back unchanged. False positive: an over-cap brace string passed as data to a Python script fails closed again, which is the pre-N101 behaviour. That is an acceptable cost; if not, it is a separate niggle.

**Confidence.** High (probed). This is a real widening past the named case. Whether it is acceptable is the lead's call, but it needs a stated reason.

## F4 — MAJOR: the compensating literal scan is a fixed list of call shapes, so a brace-spelled literal in any unlisted call form now passes

**Citation.** The compensating control is `_shell_exec_literal_mention`, now also applied to heredocs at `secret_file_guard.py:1080`. It depends on per-language regexes that only recognise listed call names. For example:

- Perl: `system` and backticks/`qx` only (`:363`, `:777–786`);
- PHP: `shell_exec`, `exec`, `system`, `proc_open` and backticks (`:362`, `:371`);
- Ruby: `system`, `exec`, `IO.popen`, `Open3.*`, backticks, `%x` (`:361`, `:369`);
- Node: `exec`, `execSync`, and `spawn` with a `shell` option (`:364–376`).

Python's AST route is much broader (`:532–545`).

**What it allows.** The fixer's self-review says a brace-spelled path "inside a direct call … still denies". That is true only for listed calls. In a direct call through a listed language's other shell-reaching APIs, a brace-spelled **literal** now passes; before N101 the raw brace stream denied it. Examples: Perl's `exec`, a piped `open`, `readpipe`; Ruby's `spawn`, or `open` with a leading pipe; PHP's `passthru`, `popen`; Node's `spawnSync` or `execFileSync` with a shell. That is not the named case: there is no variable, the literal is right there in the code.

**Class.** An exemption whose soundness depends on a separate enumerating detector being complete, where that detector is a known-shapes list. Everything missing from the list becomes an allow at the moment the exemption lands, even if it was previously caught by accident.

**Why the tests miss it.** The only chain-level pin for this route is Python `os`-dot-`system`. No test enumerates each language's shell-reaching APIs against the extractor.

**Detector hypothesis.** A table-driven test with one row per (language, shell-reaching API) taken from each runtime's documented process APIs. Each row asserts that a brace-spelled fixture path inside that call in an interpreter heredoc is denied. Expected noise: rows that change nothing, since the list only grows, so the cost is upkeep rather than false positives.

**Confidence.** Medium-high. I read the regexes, but I did not confirm through the handler that no other stream catches any of these forms. **What would settle it:** one chain test per missing API, or a short written decision that these forms fall inside the accepted residual.

## F5 — minor: `_NAME_REDEFINITION_RE` misses a redefinition made by sourcing a file

**Citation.** `shell_expansion.py:330`. The regex covers `alias`, `hash`, `enable`, `function`, `name()` and `PATH=`. It does not cover `source` or `.`. The probe returned NEUTRALISED for `. ./defs.sh; python3 -c '…'` and `source defs.sh; python3 -c '…'`.

**What it allows.** A sourced file can define a shell function named after the interpreter, and that function then hands its argument to a shell. The report already accepts shims from earlier tool calls. This case is in the same command, so it sits inside the scope the hardening commit claimed to close.

**Class.** A name-redefinition deny list that leaves out a redefinition route.

**Why the tests miss it.** `TestTheInterpreterNameMustBeTheRealInterpreter` lists the inline forms only.

**Detector hypothesis.** Add `source` and `.` as command words to the regex, or (sounder) withdraw neutralisation whenever any command word in the line is outside a small allowlist of builtins known not to change name resolution. The allowlist form will fire on ordinary `source .venv/bin/activate && python3 -c '…'`, which is a common shape. That is noisy, and the noise costs only a return to pre-N101 behaviour.

**Confidence.** High (probed). Ranked minor because it needs a separately authored helper file.
