> **Append-only activity log** for plan 00466. One file per day
> (`00466-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM; NEVER edit earlier
> entries (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 17:50 · action · N1   — N1 remedied: run-probe every venv-fallback acceptance site

Fixed N1: `resolve_venv_python`'s fallback accepted a venv interpreter that
cannot run on this host, on executable-bit alone (`[ -x ]` / `os.access(X_OK)`).

Found every implementation that trusted a venv interpreter's executable bit:
the bash canonical library `scripts/lib/resolve_venv.sh::_rv_pick_python`
(the only bash site not delegating to it, per `check_canonical_callers.sh`'s
own static enforcement) and the Python SSOT
`resolve_existing_venv_python_with_diagnostics` in
`src/claude_code_hooks_daemon/daemon/paths.py` (steps 2 metadata, 3
fingerprint-keyed, 4 scan-fallback, 5 legacy, via a shared `_pick_interpreter`
closure). `resolve_existing_venv_python` (the simpler, no-diagnostics
function) was deliberately left un-probed: it runs on the per-user-turn hot
path (`daemon_upgrade_detector`) and neither of its current callers execute
the returned interpreter -- `daemon_upgrade_detector` only reads
`.daemon-metadata.json`, and `client_validator.py::validate_daemon_can_start`
already runs its own `subprocess.run(..., timeout=...)` probe before
executing.

TDD: RED tests confirmed failing against the pre-fix code first, in
`tests/unit/daemon/test_paths_resolve_venv_diagnostics.py::TestRunnabilityProbe`
(7 new tests) and a new `tests/integration/test_resolve_venv_runnability_probe.py`
(7 tests exercising `_rv_pick_python`/`resolve_venv_python` directly in
bash). Both cover: a fake executable that exits non-zero, a dangling
symlink, a hanging candidate with the bound respected, fall-through to a
good second candidate, all-candidates-bad reaching the venv-free path, and
the slug-exact/fingerprint-keyed venv unaffected when it genuinely works.

GREEN: both new test files pass in full, plus the full existing
venv-resolution regression surface (239 tests: parity matrix, hot-path
latency/cache, pipefail cascade, bin-wrapper, skill-scripts, install
resolver, client validator, daemon_upgrade_detector, multi-host NFS
fail-fast) -- no regressions.

Probe cost measured directly against this worktree's own real venv
`bin/python`: an early sleep-1-poll-loop draft cost ~1005ms per candidate
(the loop always sleeps a full second even for a candidate that exits in
milliseconds, since the first poll almost always lands before the process
has exited). Replaced with a watchdog subprocess
(`( sleep N; kill -KILL "$pid" ) &` + a blocking `wait "$pid"`, no polling):
measured ~15-40ms per candidate. Only reached on a resolver-cache MISS (the
bash hot-path cache in `_rv_resolve_python_impl` is checked before
`_rv_pick_python` is ever called), so none of this lands on the
steady-state per-hook path.

Verified the bash implementation's -e safety directly: `_rv_candidate_runs`
is always called as the condition of an `if` inside `_rv_pick_python`
(`if _rv_candidate_runs "$candidate"; then ...`), and bash suspends
`set -e` for the ENTIRE body of a function called in that position --
confirmed empirically both for the direct case and for the full nested
`resolve_venv_python` -> `$(...)` -> `_rv_pick_python` -> `_rv_candidate_runs`
chain used in production. A candidate's output is captured to a private
temp file (not `/dev/null`, not the caller's inherited stdout/stderr) so an
orphaned descendant of a killed candidate (this script has no job control,
so `kill -KILL "$pid"` reaches only the immediate process) cannot hold the
caller's own pipe open past the bound.
