>   down the file. A file with no sentinel line above predates this system —

>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry

## 17:07 · finding · N5   — secret_file_guard security fail-open on empty path-mention token

N5 reproduced via the coordinator's saved triggering payloads
(`untracked/scratch/n5_triggering_edits.jsonl`), replayed through the real
daemon with a full traceback. Root cause pinned:
`_normalised_token_forms` (`secret_file_matching.py`) strips a token equal
to a home/pwd prefix (e.g. a quoted `"~/"` literal) down to an empty
string, which reaches `path_matches_globs("")` → `_candidate_paths` →
`os.path.relpath("", root)` → `ValueError: no path specified`.

Severity: the crash is inside `secret_file_guard.matches()`, and the
daemon's non-strict per-handler catch treats the exception as "did not
match" — so the WHOLE secret-file guard is skipped for that write. Fixed
at both layers per the coordinator's instruction: (a)
`_normalised_token_forms` never emits an empty form (guard on
`len(token) > len(prefix)`), (b) `_candidate_paths` is now total on an
empty `file_path` (returns early, no `os.path.relpath` call at all — a
second line of defence for any other caller). Fail-safe pinned with a RED
test: content with BOTH a home-prefix token and a genuine protected
mention (`id_rsa`) still denies. A corpus test over every operand shape
from the live payloads confirms the mention scan never raises.

RED confirmed failing pre-fix (`test_path_exclusion.py ::test_empty_file_path_with_a_project_root_does_not_raise`,
`test_secret_file_matching.py::TestBareHomePrefixTokenDoesNotCrash`, 6
tests), GREEN after. Full `test_secret_file_matching.py` (196),
`test_path_exclusion.py` (55) and `test_secret_file_guard.py` (76) pass —
327 total. Replayed all three original triggering payloads through a real

## 17:20 · finding · N6   — enforce_llm_qa denies a prose mention of the denied full-suite runner in an unrelated argument

N6 reproduced from the coordinator's live report: `enforce_llm_qa`'s
substring-plus-leading-word-allowlist check (`_is_inspection_only`) denied a
`mkplan.bash --journal ... --title "... run_all.sh ..."` journal entry
because `run_all.sh` appeared only as prose inside the quoted `--title`
argument, and the segment's own leading word (`mkplan.bash`) wasn't on the
inspection/VCS allowlist.

Replaced the check with a `shlex`-based real-invocation detector
(`_has_real_invocation`/`_segment_executes_script`/`_word_names_the_script`),
reusing this project's established `shlex.split()` + `try/except ValueError`
pattern (`project_containment.py::_tokenise`) rather than a third parser. A
segment now matches only when the script is named at the command's own head,
or as an argument to a wrapper (bash/sh/env/timeout/nice/exec) — recursing
into a `-c` subshell argument and into `$(...)`/backtick substitution inner
text. A prose token merely containing the name (a whole quoted `--title`
phrase is one shlex token) no longer counts. `_INSPECTION_COMMANDS`/
`_VCS_COMMANDS` allowlists deleted (YAGNI): with no wrapper match and no
script-name match, nothing can execute regardless of what the head verb is.
A segment that fails to tokenise falls back to the old conservative
substring check (still denies) — no bypass opened.

Found and fixed a second instance of the same false-positive class in the
handler's own acceptance-test fixture: `echo "./scripts/qa/run_all.sh"` was
denied only because `echo` was absent from the allowlist, not because it
invoked anything. Replaced with `bash -n scripts/qa/run_all.sh` (a genuine
wrapper-invocation shape; `-n` keeps it parse-only and harmless if the block
ever regresses).

RED tests confirmed failing pre-fix:
`test_does_not_match_a_prose_mention_in_a_quoted_title_flag` (the exact live
shape) and `test_does_not_match_an_unrelated_wrapper_invocation`. Four
