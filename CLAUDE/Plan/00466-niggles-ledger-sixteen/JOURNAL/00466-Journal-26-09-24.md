## 22:28 · finding · —   — N34 remedied: bounded per-handler dispatch + SAFETY size cap

N34 remedied: an externally enforced per-handler chain deadline plus a
SAFETY input-size cap, closing the gap where `HandlerChain`'s own deadline
check only ran BETWEEN handlers and could not bound a handler slow within
its own `matches()`/`handle()` call.

New module `core/bounded_dispatch.py` (`BoundedDispatcher`): runs a
handler's combined `matches()`+`handle()` call on its own daemon thread and
waits on it via `Future.result(timeout=remaining)`, where `remaining` is
whatever is left of the chain's `deadline_seconds` budget. On expiry the
same N25 fail-closed verdict applies (SAFETY+BLOCKING denies "not judged in
time"; anything else is skipped with an advisory), now shared between the
pre-check and this new post-dispatch-timeout case via one `_record_unjudged`
helper in `chain.py`. The overrunning call is abandoned, never killed
(Python cannot force-stop a thread), and logged again at WARNING with its
real elapsed time whenever it finishes. Concurrency is bounded via a
semaphore (16 calls at once by default); beyond that, `DispatchSaturated` is
returned immediately and treated the same as a timeout.

Found live during this work: the FIRST implementation used
`concurrent.futures.ThreadPoolExecutor`, whose worker threads are
non-daemon and get JOINED by a CPython `atexit` hook before the interpreter
may exit -- so a single abandoned straggler hung the daemon's own `stop`
command for the length of its sleep. Caught by the new end-to-end test
(`tests/integration/test_n34_deadline_probe_isolated_daemon.py`, which
starts a real isolated daemon and stops it after a call). Fixed by
rewriting the dispatcher onto plain `threading.Thread(daemon=True)` per
call, which is never waited on at interpreter exit.

Remedy 3 (defence in depth, explicitly requested alongside remedy 2): new
`daemon.chain.max_safety_input_bytes` config key (default 2 MiB), checked
once per chain execution against a handler's bulk-text `tool_input` fields
(Bash `command`, Write `content`, Edit `old_string`/`new_string`). A SAFETY
handler over the limit is denied/skipped BEFORE dispatch is even attempted.
Not the only guarantee -- the per-handler deadline bound already caps
worst-case wall clock regardless of size -- so raising or disabling it
(`null`) stays safe as long as `deadline_seconds` is enforced.
`secret_file_guard`'s own constant factor was deliberately left alone per
the coordinator: guard-defects is rewriting `secret_file_matching` onto a
shared bounded expander and will profile that cost there.

RED tests: `tests/unit/core/test_bounded_dispatch.py` (5 tests: completes
within budget, propagates an exception, times out without waiting for
completion, the stray worker still finishes in the background, saturation
