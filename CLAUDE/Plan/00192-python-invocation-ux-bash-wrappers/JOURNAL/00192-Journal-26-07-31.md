## 19:28 · finding · — — three structural gaps

1. `skills/hooks-daemon/scripts/daemon-cli.sh` is ALREADY a fully general
   forwarder (`"$PYTHON" -m …cli "$@"`), so `daemon-cli.sh plan-qa --sweep`
   would work today. But it is not deployed in self-install mode
   (`.claude/skills/` has no `hooks-daemon/`), it resolves the venv via
   `$DAEMON_DIR/scripts/lib/resolve_venv.sh` which does not exist under
   `.claude/hooks-daemon/` here, and it performs a network self-bootstrap per
   invocation — unacceptable for a hot-path command like `plan-qa --lint`.
2. Root `daemon.sh` is stale: hardcodes the legacy `untracked/venv/bin/python`
   instead of the fingerprint-keyed venv `CLAUDE.md` declares canonical,
   exposes a curated subcommand list rather than forwarding, mode `rwx--x--x`.
3. Deployed skill has zero plan-QA coverage — `rg 'plan-qa' src/…/skills/`
   returns nothing.

## 19:28 · decision · — — emit resolved absolute paths, never a shell variable

The correct pattern already exists here: `pipe_blocker` does not tell the agent
to run `echd-capture`, it resolves and prints the ABSOLUTE path
`/workspace/scripts/echd-capture`. Every `$PYTHON` site should do the same.
The daemon knows its own interpreter; the agent should never have to.

Rejected alternative: document how to set `$PYTHON`. That pushes venv
complexity onto every agent and every client project's docs, and still breaks
whenever the fingerprint changes.
