## 12:05 · finding · T1.1 — the blind Enter DOES confirm a modal's default

Reproduced rather than reasoned about, per Task 1.1. Drove a real Claude Code
v2.1.263 over a PTY (`untracked/scratch/tui_modal_probe.py`, gitignored) with
the `/model` picker open. The picker states its own bindings, which is why it
was chosen as the modal: "Enter to set as default · s to use this session
only · Esc to cancel".

Two presses, two answers:

```
after a bare Enter   -> "Set model to Opus 5 and saved as your default for new sessions"
after ESC            -> "Kept model as Opus 5"
```

So the risk is real — `Decision.WOULD_RESUBMIT` presses Enter whenever the
machine is in AWAIT_COMPACTING, the session is keystroke-idle and the input
line is modelled empty, and a modal satisfies all three: empty box, nothing
streaming. It would persist a model change nobody asked for. The mitigation is
equally real: ESC dismisses, and ESC is already flush attempt 1.

## 12:12 · finding · T1.3 — the gap was PROXIMITY, not ordering

Chasing the mitigation to its edge. ESC being attempt 1 covers a dialog that
was already open when the AWAIT episode began. It does NOT cover a dialog that
opens *after* that escape: the remedies alternate at `escape_after_seconds`, so
that dialog is still on screen a full minute later when the Enter fires.

That reframes the fix. Nothing needs to detect the dialog — the pairing just
has to be tight enough that an Enter is always closely preceded by an ESC that
would have dismissed one.

Checked the three conditions that pairing depends on, on the same rig
(`untracked/scratch/tui_esc_enter_probe.py`):

1. Enter on an empty box — no-op.
2. Text in the box → ESC, pause, Enter — still SUBMITS. One ESC does not clear
   the box (the TUI answers "Esc again to clear"), so the unsubmitted-line case
   still gets its fix.
3. Modal open → ESC, pause, Enter — default NOT confirmed.

All three hold.

## 12:20 · decision · T1.3 — shorten an interval, do not extend the protocol

The obvious-looking implementation is a single new "escape then enter"
decision. Rejected, and the reason is the two-tier design rather than taste:
decision names and payloads ARE the worker→host protocol, and **the host never
hot-reloads**. A freshly reloaded worker talks to the Sep-4 host until the
whole ccy session restarts — that host would hit
`Decision(outcome.decision_value)` on an unknown name, or paste a raw ESC
through as literal text.

So the change is confined to the worker: `_RESUBMIT_FOLLOW_SECONDS = 2.0` plus
`_flush_interval()`, which returns the short interval before an even-numbered
attempt (the resubmits) and the configured `escape_after_seconds` before an
odd one (the escapes). Escalation stays paced by policy; only the Enter is
pulled in behind its own ESC. Exposure window: 60s → ~2s. The floor is the
poll interval — anything shorter and the tick that would fire the resubmit
never lands, which is now pinned by a test.

`_walk_into` was the reported duplication, but `_OWN_EXCLUDED_DIR_NAMES` sits
directly above it in both check modules with the same three entries and two

The only real difference was `module_doc_budget`'s `scope_exclude_globs`

already made, which is pinned by a test so a future caller cannot use it as an
un-prune hatch.

## 13:01 · decision · T2.1 — test the RULE once, test the WIRING per caller

The two check test files each had an identical
`TestVendorExceptionWildcardNeverUnprunesOwnExcludedDirs` that called the
private `_walk_into` directly. Copying that a third time into `test_corpus.py`
would have kept the duplication, just moved it.

Instead the rule's semantics are unit-tested once against `walk_into`, and
each check's own class now drives its REAL walk — `_iter_module_doc_paths` /
`_iter_markdown_paths` — over a `tmp_path` with `.git/`, `untracked/`,
`worktrees/` and a `node_modules/ours/` exception on disk. That is a stronger
test than the one it replaces: it fails if a check quietly stops calling the
shared function, which the old test could not see.

## 13:18 · finding · T2.2 — a `.pyc` is not a plan document

QA went red on a rule that had nothing to do with the refactor:

```
repo_hygiene: ignored-plan-document
  CLAUDE/Plan/Completed/00335-…/probes/__pycache__/probe_walk.cpython-311.pyc
```

Fixing the archived probe's import made something import it, which wrote
bytecode beside it. That file is gitignored and untracked, so it lands exactly
in `ignored_plan_documents`' set — but it is generated, not authored, and the
rule's own remediation ("anchor the pattern so the file gets tracked") is
actively wrong for bytecode. Any checkout where someone ran a plan's probe
would go red, which is what a probe is for.

Excluded `__pycache__/`, `.pyc` and `.pyo` only. An ignored `.py` probe is a
genuine silent loss and stays flagged — a second test pins that, because the
carve-out's only danger is widening into "ignore Python under a plan".
