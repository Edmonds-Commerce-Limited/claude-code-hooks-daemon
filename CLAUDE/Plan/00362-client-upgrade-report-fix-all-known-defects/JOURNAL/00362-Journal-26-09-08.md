## 15:14 · action · T1.1 — pipeline step + local-copy fallback

- New `scripts/release/publish_bootstrap_assets.sh vX.Y.Z [--build-only]`:
  stages the four skill scripts from `src/.../skills/hooks-daemon/scripts/`
  in a fixed order, builds the manifest via `build_bootstrap_checksums.sh`,
  refuses to build if any script in the skill tree carries a
  `SELF-BOOTSTRAP BEGIN` stanza that is not in the bundle, runs
  `gh release upload <tag> ... --clobber`, then reads the release back and
  fails unless every asset is listed. `HOOKS_DAEMON_GH_BIN` and
  `HOOKS_DAEMON_RELEASE_ARTIFACTS_DIR` make it testable without GitHub.
- `tests/integration/test_publish_bootstrap_assets.py` pins the manifest
  coverage (by scanning the skill tree for the stanza), determinism,
  `--build-only` never calling gh, the upload/read-back contract, and that
  all three procedure documents invoke the script AFTER `gh release create`.
- RELEASING.md Step 14, `invoke.sh` Stage 4 and `release-agent.md` Stage 3
  now all run the script; the relay-asset block no longer offers a second
  `gh release create` form.
- The shared bootstrap stanza (identical in daemon-cli.sh, health-check.sh,
  init-handlers.sh, and their deployed `.claude/` copies) now falls back to
  the installed local copy on a manifest or fresh-script download failure:
  one `Warning:` line naming the URL and curl exit code, no cache marker
  written (so the next run retries). Checksum mismatch and a manifest with
  no entry still abort. `tests/acceptance/test_diagnostic_scripts.py`
  replaces the abort-pinning case with three fallback cases plus a
  stanza-parity check across the three scripts.
- Not done here by design: attaching assets to the real v3.62.1 release.
