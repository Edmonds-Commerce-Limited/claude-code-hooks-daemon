## 06:05 · finding · T3.5 — variant 4: the scripts PRINT the defect at runtime

Provisioning the client fixture surfaced a fourth spelling immediately, in the

```
  Status:   /workspace/untracked/dummy-client-repo/.claude/hooks-daemon/untracked/venv-…/bin/python -m claude_code_hooks_daemon.daemon.cli status
```

Docs are not the only thing that instructs. `install_version.sh`,
`upgrade_version.sh`, `setup_worktree.sh` and `run_smoke_test.sh` all echo
commands to the operator, and `.sh` was outside `_SCANNED_SUFFIXES` entirely —
so none had ever been checked. Nine real sites.

Two were especially bad:

- `setup_worktree.sh:173-174` printed the LITERAL `\$PYTHON -m …` — variant 1,
  unrunnable as printed — in the very script this plan had just made the
  documented way to create a worktree.
- `upgrade_version.sh` prints its four sites on the "daemon failed to start after
  upgrade" path: the exact moment an operator is most likely to copy a command
  and least able to debug why it fails.

`run_smoke_test.sh:53` also embedded it in the JSON `error` field, which is what
an LLM reads from QA output — invisible to the shell-output rule because it sits
inside a heredoc.

### The rule needed a real distinction, not just a wider net

First attempt flagged any banned pattern on any output line: 28 findings, of
which 5 were false positives. Shell scripts legitimately PRINT a resolved
interpreter as a **value** — `print_error "Venv Python not found: $VENV_PYTHON"`
names the path it just failed to find, and flagging that would force scripts to
suppress the one detail that makes the error actionable.

So a `.sh` line is guidance only when BOTH hold: it is an output statement, AND
it shows a **command** — either `-m …daemon.cli`, or an ESCAPED `\$PYTHON`
(deliberately unexpanded, so the reader really does see the literal variable).
An unescaped `$PYTHON` in an echo expands to whatever the script resolved, so it
is a value, not an instruction.

That refinement took 28 → exactly the 9 real defects, with all 5 diagnostics
cleared and no exemptions needed for them. Verified case by case against
`debug_hooks.sh`, `detect_location.sh`, `project_detection.sh`,
`test_validation_manual.sh` and `run_strategy_pattern_check.sh`.

### The one I could see in my own scrollback

`restart` had been printing

```
Sent SIGTERM to daemon (PID: 1316846)
Daemon stopped
Sent SIGTERM to daemon (PID: 1316846)
Daemon stopped
```

all session. Same pid twice — which reads as two daemons killed, and is exactly
what made me nervous about stray daemons earlier in this plan. `cmd_restart`
calls `cmd_stop` once, and a genuine second stop would say "Daemon not running",
so it was not double execution. It was `cmd_start` forking with an unflushed

It only reproduces when stdout is a file or pipe, so it is invisible at an
interactive terminal and corrupts **only** captured output — i.e. exactly what
tooling and agents parse. I had been reading duplicated output for an entire
session and treating it as cosmetic.

## 2026-08-01 — Task 6.7: teardown reported success while orphaning a daemon

Found this by doing the boring thing: after the final client verification I ran
`destroy`, then checked `ps` anyway rather than trusting the script's own
"removed /workspace/untracked/dummy-client-repo". The fixture daemon was still
alive, its cwd pointing at a directory that no longer existed.

The teardown had printed:

```
Daemon not running
  dummy daemon stopped
  worktree removed
  removed /workspace/untracked/dummy-client-repo
```

"Daemon not running" and "dummy daemon stopped" in consecutive lines, about a
daemon that was running and did not stop.

Root cause is **Plan 00194's bug, biting for real**. `stop_dummy_daemon`
invoked the CLI with neither a `cd` nor `--project-root`. The CLI resolves the
daemon it MANAGES from the project root derived from the CURRENT WORKING
DIRECTORY — the interpreter's own location does not select it. Run from
`/workspace`, the stop resolved the DOGFOOD project, looked for
`/workspace/untracked/daemon-dummy-client-repo.pid`, found nothing, and honestly
reported "Daemon not running". Teardown believed it and deleted the tree.

`cmd_cli` in the same script does `cd "$DUMMY_ROOT"` first — which is exactly
why every `cli` invocation I made all session worked correctly, and why the bug
stayed hidden until teardown. Two functions, one anchored, one not.

The near-miss worth recording: this is one bind-mount away from being much
worse. A `stop` that resolves the WRONG project is only harmless because no
`daemon-dummy-client-repo.pid` happened to exist under `/workspace`. Given a
host and container sharing `untracked/`, the same call stops a daemon belonging
to a different project while reporting success.

Two fixes, because the anchoring bug and the silent-success bug are separable:

1. `--project-root "$DUMMY_ROOT"` — an explicit anchor beats relying on cwd,
   which is the whole Plan 00194 lesson.
2. `verify_dummy_daemon_stopped` — a post-condition. "stop exited 0" is NOT
   evidence the daemon is gone when the stop may have targeted elsewhere. It
   matches on the dummy venv path (unique to the fixture, so it can never match
   the dogfood daemon), reaps survivors by process GROUP, and `fail`s rather
   than deleting a live daemon's directory.

The contract test is source-level rather than behavioural: it asserts every
daemon-CLI invocation in the script is anchored, by `--project-root` or by a
`cd "$DUMMY_ROOT"` in the same or a preceding line. Two of my own test bugs
along the way, both worth noting because they are the same species as the code
bug — a check that looks at the wrong thing:

- it read raw lines, so my `--project-root` on a backslash continuation read as
  unanchored;
- it only looked at PRECEDING lines for a `cd`, so an inline
  `$(cd "$DUMMY_ROOT" && … cli status)` read as unanchored too.

Both were the test being narrower than the contract, exactly like the gate in
Phase 3. Fixed by joining logical lines and accepting either anchor position.

Verified by reproducing the original scenario end to end: create, confirm the
daemon is live, then `destroy` **from `/workspace`** — the cwd that caused the
orphan. The stop now reports `Sent SIGTERM to daemon (PID: 1483482) / Daemon
stopped` where it previously said "Daemon not running", and no survivors remain.
The `error_hiding_blocker` also correctly blocked my first draft for `|| true`;
rewrote it to handle the pgrep-found-nothing and kill-failed cases explicitly.

QA 14/14 (10,786 passed, 5 skipped, 95.2%); shellcheck clean; exactly one daemon
on the host throughout — the dogfood one, PID unchanged.
