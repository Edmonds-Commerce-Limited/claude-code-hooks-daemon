## 10:29 · action · —   — Phases 3, 4 and Task 5.1 built: one staleness rule, UNPROVEN evidence, start-time cleanup, dead-set sweep

Phases 3 (3.1-3.3), 4 (4.1-4.3) and Task 5.1 built in the staleness worktree.

Decisions:

- The one rule lives in `paths.py` (stdlib-only, because `list-stale-venvs` runs under the host `python3`): `classify_venv` returns `stale`, `unproven` or `keep`. `live_venv_realpaths` moved there from `cli.py` and is keyed on the daemon dir, which is what the resolver and `ensure_venv` key on. In a client install `project_root` is a different directory, so the old call asked the resolver about the wrong path.
- The current fingerprint's venv is never judged (`keep`): its metadata is written after the sync, so a venv mid-build would otherwise read as UNPROVEN.
- Process evidence reads `/proc/<pid>/{exe,cwd,cmdline}`. A venv's `bin/python` is a symlink, so `exe` shows the system interpreter and only `argv[0]` names the venv. Later arguments are deliberately not read: `prune-venvs --unproven <path>` itself names the venv and would refuse itself. Processes whose three sources are all unreadable are counted and disclosed in the evidence, not guessed at.
- Restart, provision and plain start all reach `cmd_start`, so the cleanup (4.1) and the dead-set sweep (4.3) live in `_reap_stale_runtime_files`. No shell change was needed for provision. The venv cleanup holds the build lock for at most 5 seconds, skips any stale venv a process still uses, and is fail-open.
- 4.3 deviates from the brief in one place: the pid check is `read_pid_file(verify_daemon=True)`, "alive and a daemon server", not "alive". After a container restart old pids are reused by unrelated processes, and a plain liveness test would keep most dead sets forever. A set with any member written in the last 60 seconds is also left, because a peer's start writes its lock before its pid and sockets.
- The resolver serves a metadata-less venv as a last resort, so a lone UNPROVEN venv can be the live one. Tests that need a venv to be UNPROVEN patch the resolver to find none.

## 12:18 · decision · —   — Automatic stale-venv removal fails closed while a peer host is not proven dead

Review round 1, decision: the automatic stale-venv removal fails closed.

`/proc` in this container cannot see a process in a peer container that shares the checkout through a bind mount, so the in-use check proves nothing about a peer. The automatic cleanup at daemon start, restart and provision therefore removes nothing while any other host's runtime set is not PROVEN dead, and nothing when the `/proc` scan has unreadable processes. "Proven dead" is one predicate (`paths._runtime_set_is_dead`), shared with the dead-set sweep: every socket in the set lies under the untracked dir and is refused or absent, nothing was written in the last 60 seconds, and the pid file does not name a verified daemon. A socket or discovery path outside the untracked dir (a fallback runtime dir) cannot be checked from here, so it keeps the set. Manual `prune-venvs --stale --force` is unaffected, but it now also skips any venv a process on this host uses, as `--unproven` and the automatic cleanup do.

Alternative rejected: trusting the `/proc` scan alone. It is right for this host and silently wrong for a peer, and the cost of a wrong removal is a venv under a running daemon.
