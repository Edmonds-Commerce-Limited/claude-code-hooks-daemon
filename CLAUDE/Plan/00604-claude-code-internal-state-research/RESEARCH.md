# Plan 00604 research: how Claude Code 2.1.322 tracks its own session state

All observations are from one container running Claude Code **2.1.322** (`claude --version`), an interactive ccy session, on 11 November 2026. Identifiers in examples are shortened or replaced; prompts, file contents, names and tokens are redacted.

## The answer to the true-idle question

**Not from one documented source.** The closest single signal is the `status` field of `~/.claude/sessions/<pid>.json`. `claude agents --json` reports it as `busy | waiting | idle`, and that output is documented. In this session the field stayed `busy` through three turn ends while background sub-agents were running. The input box is not part of it, and this research did not observe whether background Bash commands or monitors hold it at `busy`.

A reliable true idle can be built from three internal sources plus the supervisor's own input tracking:

1. `status == "idle"` in `sessions/<pid>.json`
2. no sub-agent `.meta.json` without `"finished": true`
3. every `b*.output` file in the session's tasks directory ends with `[exited with code N]`
4. the supervisor's own empty-input and quiet-output gates

Only the first of these is documented, and only through `claude agents --json`.

Inspection used `ls`, `stat`, `find -newer <marker>` and `jq` with key-only or redacting filters.
- `claude --help`, `claude agents --help`, and `claude agents --json`. The last one is refused while `CLAUDE_CODE_DISABLE_AGENT_VIEW` is set; it was run once with that variable unset for the one command, and it started no process.
- The environment: variable names only.
- The vendored docs under `remote-docs/code.claude.com/docs/en/`: hooks, statusline, settings-reference, scheduled-tasks, tools-reference, sub-agents, and `plugins/mods/*`. One page that is not vendored, `agent-view.md`, was read with WebFetch. It was not captured, because `remote-docs add` from this worktree has no venv and the vendored tree belongs to the main checkout.
- Controlled experiments in this session:
  - a `sleep 20` run with `run_in_background`
  - an 11-second `Monitor`
  - `find -newer` snapshots before, during and after each
- Not done:
  - no decompiling and no reading of the program bundle
  - no `.credentials*` file and no `.claude.json` values; only the top-level key names of `.claude.json` were listed
  - no cron experiment, because a sub-agent has no CronCreate
  - no daemon payload capture: `daemon.payload_capture.enabled` is false, and switching it on means restarting the shared daemon

## Evidence for the `status` claim (Experiment 1)

- The last `statusUpdatedAt` was 13:15:48.5. The turn that ended at 13:16:11.531 lasted 23,041 ms, so it began at 13:15:48.49. The idle→busy flip is written at turn start.
- That flip implies the field was not `busy` before 13:15:48. The turn before it ended at 13:14:35 with `pendingBackgroundAgentCount: null`.
- Later turns ended at 13:16:11 (pending 1), 13:18:10 (pending 2) and 13:21:52 (pending 3). The field was still `busy` at 13:26 with the main thread at its prompt.
- So a turn end with background agents pending does not write `idle`.

Two things were **not observed**: the flip back to `idle`, and whether background Bash, monitors or a pending cron hold `busy`. agent-view.md says that for background sessions "a running subagent, workflow, or monitor counts as working, and so does a pending session-scoped scheduled task". That sentence is about `state`, not `status`, so it is not proof for `status`.

## Experiments 2 and 3: background Bash and Monitor

- **Start.** The only files that changed were `tasks/<id>.output` (created) and the `tasks/` directory. `sessions/<pid>.json`, the team config and the job files did not change. A `bash -c …` child of pid 111 appeared, with its own process group.
- **End.** The trailer `[exited with code 0]` was appended and the process was gone. The task-notification went through the main transcript's queue (`enqueue`, then `remove` with reason `absorbed_mid_turn`), and the sub-agent transcript recorded it.
- **Monitor.** It behaved the same way: a `b…` task id, the same output file and trailer, and a shell child of the CLI.
- **Every 60 s.** `.claude.json` is rewritten and backed up into `backups/`. This holds no task state.

## Ranked hook points for "is the session truly idle?"

1. **`claude agents --json` → `status` for `$CLAUDE_PID`** (or the same field read from `sessions/<pid>.json`).
   - Reliability: high for the turn and for background agents, and the field is documented.
   - Failure modes: the docs do not say what it means for background Bash, monitors or crons; agent view must not be disabled (`CLAUDE_CODE_DISABLE_AGENT_VIEW` is set in ccy, so the command is refused unless that variable is unset); reading the raw file skips the stale-pid filtering; a crash leaves a stale `busy`. Check the pid is alive and `procStart` matches.
2. **Unfinished sub-agent metas** (`subagents/*.meta.json` without `"finished": true`), restricted to the current session id.
   - Reliability: high on 2.1.322; it matched the live set exactly.
   - Failure modes: internal; the field is absent on older versions; an agent killed with its session never gets `finished` (so restrict to the live session and to metas newer than `startedAt`).
3. **Running background shells and monitors**: any `b*.output` in the session's tasks directory without the exit trailer, cross-checked against the children of `$CLAUDE_PID`.
   - Reliability: medium.
   - Failure modes: internal; a running foreground command also has an untrailered file (harmless, because the session is then busy anyway); a command killed by TaskStop or a crash was not tested, so it may never get a trailer; the trailer text may change.
4. **`Notification` `idle_prompt` hook** (the daemon already receives it).
   - Reliability: documented and it accounts for background agents.
   - Failure modes: about 60 s late; in a terminal it is gated on "appears away", which is untested under the ccy PTY; it says nothing documented about background Bash or monitors; and it is an edge, not a level (typing afterwards does not un-fire it).
5. **Transcript `turn_duration.pendingBackgroundAgentCount`** at the last turn end.
   - Reliability: medium.
   - Failure modes: internal; written only at turn end, so it goes stale as agents finish later (the turn that absorbs their notifications rewrites it); counts agents only.
6. **A mod (`$.agent.list()`, `$.prompt.read()`, `turn.complete`, `AbovePrompt.isWorking`)** that writes its own sidecar.
   - Reliability: high and documented, and the only documented source that also covers the input box.
   - Cost: a new shipped component (a plugin mod), so it is a build, not a read; `$.agent.list` does not cover shells or monitors either.
7. **The supervisor's current screen and output gates** (`_is_idle`, `_is_work_idle`, `input_line_empty`).
   - What it sees: the human and the turn.
   - What it misses: blind to everything in the background.

## Gaps: no readable source found

- **Background Bash and monitors through a documented API.** The only sources are internal files and the process tree. The mods docs refuse background work through `$.tool.call`; they do not list it.
- **The list of live session crons.** It is in memory. On disk it appears only as tool calls, fire records and a carry record at compaction or resume. The daemon's own `session_crons` record (`cron_record_keeper`) is still the practical source.
- **The `status` transition table.** When it returns to `idle`, and the meaning of the undocumented `shell` value, were not observed.
- **The input box**, without the supervisor's keystroke tap or a mod.
- **The `notify_idle` peer message on the messaging socket.** The protocol was not inspected.

## Recommendations per consumer

**Plan 00603 (idle compaction at 30%).**

- Gate the compaction on all of these together:
  - the existing supervisor gates (empty input, quiet output, human idle)
  - `sessions/$CLAUDE_PID.json` status `idle`, after validating `pid` and `procStart`
  - zero unfinished sub-agent metas for the session
  - zero untrailered `b*.output` files
- Fail closed: if any source is missing, unreadable or unknown, do not compact.
- The worker runs in the same container, so the paths are local. Derive the tasks directory from `/tmp/claude-$(id -u)/<cwd slugged with "-">/<sessionId>/tasks`.
- Treat every source except status as internal, and pin it with a version-gated test fixture.
- Note that Claude Code's own `idleCompaction` is `true` in this user's settings. Per the docs it fires about an hour idle and over its threshold, on the 1-hour cache, so the two must not double-fire. Watch for the notice that starts `Compacted while idle`.

**Plan 00501 (session modes).** Use the same composite, read-only, for any "session is idle" or "blocked" display. Do not drive a guard from it. The hook-level facts (`SubagentStart`/`SubagentStop` counts, `idle_prompt`) are the documented fallback.

**Screen-inferring code (supervisor work-idle, cron watchdog).** Add the composite as an extra veto: "background work alive → not idle". Do not replace the screen gates, because only they see the input box.

**Follow-up (Task 4.2).** It is worth filing one plan: a single `true_idle()` reader in the daemon's utils, covering sources 1 to 3 above with version fixtures, consumed by the supervisor worker. A mod-based sidecar is the documented long-term alternative. Filing the plan is left to the coordinator.
