## 14:13 · decision · T1.1   — empty shipped default, opt-in; no orchestrator deadlock

Two Task 1.1 decisions that do not wait on the Workflow probe.

**1. Shipped default: `full_qa_patterns: []`, handler OFF by default (opt-in).**
A client's full-QA commands cannot be known from here: `llm_qa.py all` is this
repo's, and `npm test` or `make check` are other projects'. A shipped default
built from this repo's commands could never fire in a client, which is the
plan's own warning. The precedent is `flaggable_content_channel_guard`, which
also ships an empty seed and is off until configured.

The handler does not treat "enabled with zero patterns" as silence.
`get_enforcement_status` reports it, so `hooks-daemon check` shows a guard that
cannot fire instead of one that looks like it is working. With no shipped
defaults there is nothing to merge, so there is no `mode: additive|replace`
key. The HANDLER_DEVELOPMENT standard applies to lists the handler ships
defaults for.

No machine-wide scheduler is needed for clients either. The guard works per
session: each coordinator serialises its own full runs. Two separate sessions
in one checkout are already handled by the per-checkout run lock (Plan 00262).

**2. Orchestrator-only mode (00418) does not deadlock the gate.** Plan 00418
Task 2.1 fixed that mode's denial surface as `Write`/`Edit`/`NotebookEdit` on
the main thread, and ruled out denying `Bash` on arithmetic: 93% of real calls
are compound, and 22% straddle the boundary. So the coordinator's full-QA run
is a Bash call that mode never denies, and the two features cannot deadlock.
Pinned by a new test in `test_orchestrator_simulate.py`: in BLOCKING mode, a
main-thread `llm_qa.py all` is allowed. If that mode ever grows a Bash denial,
the test fails and names this plan, and that is the moment to add the full
gate to its allowlist.

## 14:58 · finding · T1.1   — Correction: the simulate record said Bash would be denied; the policy never did

Correction to the 14:13 T1.1 decision on orchestrator-only mode. The conclusion was right
but the evidence was too thin, and the simulate record contradicted it.

**What the lead saw.** On every main-thread Bash call, including `llm_qa.py all`, the
PreToolUse context said: "SIMULATED orchestrator-only mode (Plan 00418 — record only, never
blocks): main thread would have been denied — Bash: <command>". Read at face value, arming
the mode would deny the coordinator's full gate. That is the deadlock this plan must rule
out.

**Where it came from.** The message comes from
`.claude/project-handlers/pre_tool_use/orchestrator_simulate.py`, `handle()`. It printed
"would have been denied" for every call that `matches()` flags, meaning any main-thread call
to a tool outside the coordination set, Bash included. The blocking policy was a different
function (`_would_deny`), which refuses only Write, Edit and NotebookEdit outside
`CLAUDE/Plan/`, and never Bash. So the record claimed denials that the armed gate would
never make. The simulated TEXT was false; the policy was not.

**Why the old pin was not enough.** `test_the_coordinators_full_qa_gate_is_never_denied` ran
the handler on its own, with `blocking=True`. That is the right policy code, but a deny can
come from anywhere in the chain, and the test never checked the record the lead was reading.

**Fixes:**

- The blocking policy is now `_policy_denies()`, and `_would_deny()` is that policy gated by
  the switch. Simulate mode prints "would have been denied" only when `_policy_denies()` is
  true. Any other matched call reads "recorded, not a would-be denial", and Bash calls add
  "Bash is never denied by this mode".
- `TestTheSimulatedRecordTellsTheTruth` pins the record and the armed verdict together across
  the tool surface: the claim appears exactly when the armed handler DENIES.
- `tests/integration/test_full_qa_gate_is_never_deadlocked.py` drives the REAL PreToolUse
  chain: library handlers via `register_all()` on this repo's config, plus every discovered
  project handler, with orchestrator-simulate ARMED. The main thread's
  `./scripts/qa/llm_qa.py all` gets ALLOW, and the orchestrator's own verdict on it is ALLOW.
  Two controls in the same chain show it is live: a main-thread Edit is denied with
  R-ORCHESTRATOR-MAIN-THREAD-WRITE, and a sub-agent's `llm_qa.py all` is denied by
  subagent-full-qa-blocker. Before the message fix, the chain-level ALLOW already held and
  only the "would have been denied" assertion failed. That confirms the policy never blocked
  the gate, and only the record said it would.

**No allowlist entry was added.** Bash is outside the policy's blocked-tool set, so an
allowance for `llm_qa.py all` would be code that never runs. The integration test is the
explicit pin. If the policy ever gains a Bash branch, that test fails, and the allowance
goes in then.
