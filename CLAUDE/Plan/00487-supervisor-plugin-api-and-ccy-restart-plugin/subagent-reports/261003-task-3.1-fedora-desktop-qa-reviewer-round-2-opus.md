**Verdict**: FIX-BEFORE-MERGE

Twelve of the thirteen round-1 findings are fixed. Finding 2 is only partly fixed. The
unattended relaunch is well designed: it closes stdin, names every prompt it can reach, and
refuses loudly. But the `exec` carries the first launch's exported state into the relaunch.
One piece of that state, `CCY_KEY_STAGE_DIR`, makes the relaunch fail on an SELinux-enforcing
host whenever the session used a key file. That is Fedora's default posture, so it is the
main path this feature exists for (new finding A). The branch also no longer merges cleanly:
F44 has moved and now ships its own ccy 3.74.0 (new finding B).

## New findings in the fix diff

### Should fix (FIX-BEFORE-MERGE)

**A. The relaunch inherits the first launch's exported state, and on an SELinux-enforcing host a key-file session fails to relaunch.**
`files/var/local/claude-yolo/claude-yolo:3446-3451`; `lib/ssh-handling.bash:1087-1096`; `claude-yolo:2110-2111`

- `build_ssh_mounts_and_validate` stages key files into a tmpfs directory. It does this only
  when `CCY_SELINUX_MODE` is not `off`, which is the case on Fedora's default enforcing
  posture. It creates the directory and adds its `-v …:/root/.ssh/ccy-keys:ro,Z` mount only
  when `CCY_KEY_STAGE_DIR` is empty (`ssh-handling.bash:1087`), and it **exports** the
  variable (`:1092`).
- The handler calls `cleanup` before the `exec` (`claude-yolo:3448-3449`). `cleanup`
  `rm -rf`s that directory (`:2110-2111`) but never unsets the variable. So the exec'd
  relaunch starts with `CCY_KEY_STAGE_DIR` naming a deleted directory.
- In the relaunch, the `-z` guard is false. That skips `mktemp` and the mount. The `install`
  into the deleted directory then fails with "Could not stage SSH key …", and
  `build_ssh_mounts_and_validate … || exit 1` (`claude-yolo:1143`) ends the restart. It fails
  loudly, and the marker banner has already printed `ccy --resume <id>`. But every `--max-age`
  session that used a key file (typed, picked at the menu, or the GitHub alias key) cannot
  restart on an enforcing host.
- The handler's own comment says the opposite: "the relaunch stages its own copies"
  (`:3446-3447`).
- Before this fix the directory survived, so the mount would have been silently missing
  instead. Neither version works.
- The tests cannot see this. `cleanup` is stubbed in both suites (`test-ccy-restart-request.bash:327`,
  `test-ccy-lifecycle.bash:305`), and nothing asserts what environment the relaunch starts with.

The same mechanism carries other state, all confirmed by `grep -n '^\s*export'`:

- **The token values.** `CLAUDE_CODE_OAUTH_TOKEN` and `GH_TOKEN` are exported at
  `claude-yolo:3261-3262`. In the first launch they reach only the container step. In the
  relaunch they are in the environ of every child from the first line: ssh probes, git,
  podman, the image update path. This is not argv and not a log, but it widens where the
  secret lives.
- **The compose state.** `CCY_COMPOSE_WAS_STARTED` and `CCY_COMPOSE_CMD`
  (`network-management.bash:974-975`, `claude-yolo:2582-2583`) are inherited. The fix
  report's claim that compose-stop "only fires when this launch started compose, which a
  restart never does" is therefore wrong: the relaunched session offers to stop compose when
  it ends. That outcome is arguably right, but it should be a decision rather than an
  accident.
- `SSH_AGENT_FORWARDED`, `SSH_CONFIG_EXTRA_B64`, `SSH_KNOWN_HOSTS_PINS` and `PROBE_LOG_DIR`
  are re-initialised by the relaunch, so they are harmless today.

**Fix:** exec with an explicit environment. Before the `exec`, `unset` the launch-state
exports the relaunch must rebuild itself: at least `CCY_KEY_STAGE_DIR`,
`CLAUDE_CODE_OAUTH_TOKEN` and `GH_TOKEN`, plus the compose pair if the owner decides the
relaunch should not inherit it. Also make `cleanup` unset `CCY_KEY_STAGE_DIR` after removing
the directory. Then add a test that runs the real handler with an exported
`CCY_KEY_STAGE_DIR` and a stub launcher that records its environment, and asserts that none of
those variables reach it.

`OWNER-LIVE-TEST.md:31` would catch this only if the owner picks a key **file** without a
passphrase on an enforcing host. F44's key menu now defaults to the agent when it holds the
key (finding B), so a default answer would miss it. Add "pick a key file, not the agent" to
that step.

**B. F44 has moved: version collision and four conflicting files.**
`git merge-tree --write-tree origin/F44 HEAD` exits 1 with conflicts in `CLAUDE/QA.md`,
`docs/ccy-changelog.md`, `files/var/local/claude-yolo/claude-yolo` and `scripts/qa-all.bash`.
origin/F44 is 27 commits ahead. Among them are 64cdd47d and cc774bb1 (PR #64, the key menu
defaulting to the agent), and origin/F44's launcher is now `CCY_VERSION="3.74.0"`.

This branch also has a 3.74.0 changelog entry, followed by 3.75.0 and 3.76.0, so two
different releases are both called 3.74.0. Round 1 reported a clean merge and no collision.
That was true at the time and is no longer.

**Fix:** merge origin/F44 into the branch, then renumber the branch's releases above F44's
3.74.0. Renumber the `CCY_VERSION` line and each changelog heading together. The container
version is unaffected, since F44 is still at 2.40. Then re-run the targeted tests. Check that
the restart path still holds with the new key-menu default: if the menu selects the agent,
`SSH_KEYS` holds the sentinel and the relaunch passes `--ssh-agent`, which is the intended
unattended route.

**C. The container-version pre-commit check covers only three of the image's in-repo inputs, and its comment says it covers everything.**
`scripts/git-hooks/pre-commit:213-221`; `files/var/local/claude-yolo/Dockerfile:264-265,414`
The comment says: "Everything else the image bakes in (the entrypoint, the supervisor
plugins) reaches a running container ONLY through a version bump". But the Dockerfile also
`COPY`s these in-repo sources:

- `agent-browser-mode-required`
- `agent-browser-session-guard`
- `plugins/phpantom-lsp/`

None of them is in the hook's `case`, so an edit there ships a stale image with no error.
This is AgentNotes' "a check that names files by path where the program has grown" case once
more. The play-generated `COPY` sources (`ccy-startup-info.txt`, `docs/`, `skills/browsing/`,
`optional/`) do not exist in the repo and are out of scope.

**Fix:** derive the guarded set from the Dockerfile's `COPY` sources that exist under
`files/var/local/claude-yolo/`. Or add a test in `test-ccy-container-version-hook.bash` that
fails when an in-repo `COPY` source is not covered. Correct the comment either way.

### Nits

**D. The structural prompt-window test reads only the launcher.** `test-ccy-restart-request.bash:534`
The test greps `read -r?p ` in `$LAUNCHER` and finds 19 prompts. The library prompts use
`read -r -p` (`token-management.bash:741-1499`), and the library files are not read. The
closed stdin still covers them, because they are called from inside the window, so nothing
can hang. But the stated population ("all prompts on the launch path") is larger than the one
measured. Either state the scope in the test's label, or count the library call sites too.

**E. The deploy test misses `common-pure.bash`.** `test-ccy-lifecycle.bash:478-489`
The test reads `CCY_LIBS`, which omits `common-pure.bash`. `common.bash:12` sources that file
transitively, and the play deploys it (`play-claude-yolo.yml:382`), so it is fine today, but
unguarded. Deriving the list from `lib/*.bash` would cover it.

## Finding 2, reviewed as hard as the original

**Prompts still reachable.** None found that can wait:

- stdin is `/dev/null` from `claude-yolo:139-141`, which runs before the tmux insulation
  (that returns early on a non-tty stdin), until `:3230`. The only prompt after that point is
  compose-stop (`:3557`), which runs after the session ends.
- The only `/dev/tty` reader in the tree is `_confirm_clear_saved_network`
  (`network-management.bash:639`), on the `--disconnect` path. The walk drops that flag.
- OpenSSH's own `/dev/tty` prompts:
  - Host-key confirmation: `ssh -T` uses `StrictHostKeyChecking=no` (`ssh-handling.bash:729`).
  - Passphrases: `ccy_restart_keys_unattended` (`ssh-keygen -y -P ''`, never asks) runs once
    before the budget is spent and again before `build_ssh_mounts_and_validate`.
    `_probe_unlock_keys` returns early on a non-tty stdin (`ssh-handling.bash:924`).
- `DEBUG_CCY`'s "Press Enter" (`:2191`) can only be reached from the `--debug` chooser
  (`:858`), and the walk drops that flag.

**Secrets in argv or logs.** None found:

- argv carries the token file **path** (accepted by the `=~ /` branch at `claude-yolo:1233`),
  key paths, the network name and the session id.
- The passphrase file travels as a path in the environment only. Its content never leaves
  the file.
- The refusal text includes `ssh-keygen`'s stderr, which is an error string, not key
  material.
- The one widening is the inherited token environment (finding A).

**Fail-open.** None found. Every builder failure, empty argv, history-directory failure,
spent budget, key needing a passphrase, expired token and failed validation goes through
`ccy_restart_refuse` and `exit 1`. A malformed `CCY_RESTART_RELAUNCH` is refused, not
ignored (`restart-request.bash:563-566`). An unaccounted `read` under the closed stdin gets
EOF, so the launch ends rather than waits.

**Is widening the passphrase-file acceptance to restarts (`CCY_UNATTENDED_LAUNCH`) safe?**
Yes:

- `ccy_restore_passphrase_take` still runs `ccy_restore_passphrase_check` (regular file,
  owned by this uid, mode 600/400, non-empty).
- The handler exports the file only when the first launch already held a validated one
  (`claude-yolo:3443-3444`), and an ordinary session never had one.
- The marker must be a UUID and is unset on read. Only the host user can set it, and that
  user could already set `CCY_SESSION_RESTORE=1`.
- The path sits in the relaunch's environment between `:139` and `:1029`, which is a path,
  not the secret.
- `ccy_restart_keys_unattended` passes every key when a passphrase file is in force. A key
  that passphrase does not open then fails loudly in `_probe_unlock_keys`' restore branch
  (`ssh-handling.bash:944-952`) rather than waiting.
