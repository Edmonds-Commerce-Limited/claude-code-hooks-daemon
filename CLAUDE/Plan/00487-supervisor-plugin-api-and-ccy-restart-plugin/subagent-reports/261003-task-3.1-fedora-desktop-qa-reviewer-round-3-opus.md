## F44 3.76.0 askpass unlock vs. the unattended relaunch

**The relaunch never runs the user's `SSH_ASKPASS` helper, so the refusal is not
over-cautious. It is the only correct answer that never waits.**

1. The relaunch sets stdin to `/dev/null` at `claude-yolo:139-141`, before anything below.
2. `ccy_askpass_passphrase_supply` (`claude-yolo:1134`) returns 0 without running the helper
   unless `ccy_has_terminal`, which is `[ -t 0 ]` (`ssh-handling.bash:935,942`). On the
   relaunch that is false. `RESTORE_SSH_PASSPHRASE_FILE` therefore stays as whatever
   `ccy_restore_passphrase_take` set (`:1029`), which is non-empty only for a server restore.
3. The refusal at `claude-yolo:1139-1143` then stops any key that does not open with an
   empty passphrase.
4. The first launch cannot hand an askpass answer on either.
   `ccy_askpass_passphrase_discard` (`claude-yolo:2161`, before the container runs) deletes
   the file and clears `RESTORE_SSH_PASSPHRASE_FILE` when it was the helper's
   (`ssh-handling.bash:974-984`).
   - So the restart handler's pre-check (`claude-yolo:3393`) sees an empty passphrase
     file. It refuses before the budget and the image update are spent.
   - The `export CCY_RESTORE_SSH_PASSPHRASE_FILE` at `:3451-3453` never names a deleted
     askpass file.
5. Removing the refusal would not make askpass work, because the helper is gated on a
   terminal. Relaxing that gate would be wrong for a restart: the helper is
   `SSH_ASKPASS_REQUIRE=force "$SSH_ASKPASS" …` (`ssh-handling.bash:962`), which for a GUI
   helper is a dialog on the desk and for a gpg-backed one a pinentry. Both wait for a
   person.
6. The user's helper is not reachable through ssh-add either:
   - `_probe_unlock_keys` returns before any `ssh-add` when stdin is not a tty and no
     restore file is in force (`ssh-handling.bash:995-997`).
   - With a restore file, `ssh-add` runs with ccy's own stage helper forced
     (`:818-820`), not the user's.

**Is there any path where the relaunch now waits? One, and it is not new with F44 (G
below).** It is the forwarded agent. `ccy_restart_keys_unattended` skips the sentinel as
"unlocked already" (`restart-request.bash:395`). The relaunch's GitHub probe then signs
through the user's `$SSH_AUTH_SOCK` (`ssh-handling.bash:729-739`), with only
`ConnectTimeout=10`, which bounds the TCP connect and nothing after it.

Some agents put up a dialog before they sign:

- a key added with `ssh-add -c`;
- gpg-agent's ssh support once its cache TTL has passed (pinentry);
- a keyring agent that unlocks keys on first use.

In those cases `ssh -T` blocks on the agent's reply. Nobody is at the desk, and GitHub
dropping the connection after its login grace does not unblock it.

This is inferred from the code plus OpenSSH and agent behaviour. It was not run live.

## New findings

### Should fix (FIX-BEFORE-MERGE)

**F. Neither the 3.77.0 entry, the docs nor the refusal message says that a key unlocked
through 3.76.0's askpass route cannot restart unattended. The suggested fix points at the
route 3.76.0 just demoted.**
`docs/ccy-changelog.md` (3.77.0, "for an SSH key that needs a passphrase (unless a server
restore's passphrase file is in force)"), `docs/ccy.md` (the "relaunch asks nothing"
paragraph), `claude-yolo:3394`.

- The 3.76.0 entry directly below says one encrypted key "unlocks with no prompt" through
  the user's helper. An owner using that route will reasonably expect `--max-age` to work.
  It is refused at the first restart (mechanism above).
- The refusal text and `docs/ccy.md` recommend `--ssh-agent`. F44's 3.76.0 now labels that
  route as exposing every key the agent holds and running the container without SELinux
  confinement (`ssh-handling.bash:565`), and stopped defaulting to it.

**Fix:**

- Add one clause to the changelog bullet, the `docs/ccy.md` paragraph and the `:3394`
  message. The clause says a key your `SSH_ASKPASS` helper unlocked at launch is refused
  too, because the helper is only asked with a terminal. Then name the trade-off: a
  passphrase-less key file (confined), or `--ssh-agent` (every key, unconfined).
- Add a restart-request case asserting that a first launch whose passphrase came from the
  helper is refused at `ccy_handle_restart_exit`. Today the "relaunch never runs the user's
  helper" property rests on two separate mechanisms, `[ -t 0 ]` and the closed stdin at
  `:140`. No test joins them.

**G. The forwarded-agent probe is the one unbounded wait left on the relaunch.**
`restart-request.bash:395`; `ssh-handling.bash:726-739,1201,1210`.

The design promise is "stops instead of waiting". An agent that asks before signing breaks
it, and the launch hangs at the probe with the resume banner already printed.

**Fix:** on a relaunch (`CCY_RESTART_RELAUNCH_SESSION` set), run the sentinel probe under
`timeout` (for example 60 s). On expiry, refuse through `ccy_restart_refuse` with "the
forwarded agent did not sign without confirmation". If the owner prefers to accept the
risk, state it in the restart paragraph of `docs/ccy.md` instead. Either way it should be a
decision, not an omission.
