## Finding 4: the state file was per project, so concurrent sessions reset each other's clock

RED first. Fifteen tests failed or errored against the old plugin. Among them was
`ConcurrentSessionTests.test_two_sessions_keep_their_own_clocks_across_interleaved_reloads`:
A starts, then B starts with another launch id, then A reloads, then B reloads, all against
one `state_dir`.

The new layout in the plugin's shared `state_dir`:

- `lifecycle-<launch id>.json` holds this container's `started_at`, `restart_warned` and
  `deadline_notified`. The launch id is already validated by `_LAUNCH_ID`, so it is safe as a
  file name. A hot reload finds the file again, while a new container never sees it, so the
  max-age clock and the warning start over. This matches OWNER-LIVE-TEST.md line 30. If the
  file's contents name a different launch than its file name, the plugin raises ValueError
  instead of adopting it.
- `deadline-<epoch>-<sha256(session id)[:32]>.json` records "this deadline was announced to
  this Claude session". Keying by the deadline epoch alone, as the review suggested, would
  still collide: two sessions launched with the same `--until 17:00` get the same epoch, so
  the second would never be told. The relaunch resumes the same session id
  (`--resume <same session id>`, OWNER-LIVE-TEST.md line 27). So the session id is what a
  relaunch shares and a concurrent session does not. The id is hashed, so no session id is
  written to disk. When the marker is found, the new container records `deadline_notified`,
  which also keeps the max-age restart stood down (new test
  `test_a_relaunch_after_the_notice_does_not_restart_for_max_age`).
- `tick.session_id` can be None, meaning no session or several. In that case only the
  per-container record applies: no repeat across a hot reload, but a relaunch could announce
  once more. This is commented in the code and covered by a test.
- Pruning happens on every `on_start`. It removes only files whose name matches the plugin's
  own patterns (including `*.tmp.<pid>` leftovers) and that have not been modified for
  `PRUNE_AFTER_SECONDS` (2 x the 30-day max-age cap). The plugin's own file is skipped. Other
  writers' files, including a legacy `lifecycle.json`, are never touched. A
  FileNotFoundError race with a concurrent prune is skipped; any other OSError raises.
- Temporary save files carry the target's unique name. Two containers can have the same pid
  across pid namespaces, but they still never share a temporary file.

## Finding 8

(a) I reworded the `Config` docstring. The supervisor's loader DOES register the module in
sys.modules (claude-supervise.py:4193). The real constraint is the unit tests'
`load_plugin_module`, which imports a fresh copy per test without registering it.

(b) I added `SupervisorHarnessContractTests` to `test_plugin.py`. It loads the plugin through
the real `PluginTestHarness`: the real loader, vetting, API-major check and budgeted calls.
It covers loader acceptance, the warning then the exit as `PluginNotification` /
`PluginExitRequest`, the deadline notice plus a hot reload over the same `work_dir`, and a
bad value raising `PluginHarnessError`. How it finds a supervisor:

- If `CCY_SUPERVISOR_PATH` is set, it uses that file. A path that does not exist, or a
  supervisor without the harness, FAILS the run instead of skipping.
- Otherwise it uses the repo's own `.claude/ccy/claude-supervise.py`. The copy in this clone
  predates the harness, so the class SKIPS. The reason goes to stderr (the runner is
  non-verbose and its stdout must stay empty) and is also the `SkipTest` message. Once the
  daemon upgrade deploys a supervisor with the harness, the class runs with no configuration.
- File ownership and mode: `check_plugin_file` accepts files owned by the caller's uid or
  root that are not group- or world-writable. The test copies the plugin into a private tmp
  dir (dir 0700, file 0600, owned by the test's uid), the same way the daemon's
  `_plugin_helpers.write_plugin` does. Nothing in the check is weakened.
