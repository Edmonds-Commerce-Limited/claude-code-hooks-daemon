# Fact check: Plan 00502 merge requires approval

Scope: the whole PLAN.md (the diff file lists the same new plan). Judged against the current tree only.

Tally: 22 claims, 18 verified, 2 refuted, 2 unverifiable-here.

## REFUTED (most consequential first)

### R1. "The daemon already receives SubagentStart/SubagentStop with the sub-agent type, model and final report" (Option B)

The event does not carry a model.

- `contracts/claude-code-hooks/SubagentStop.json` `input_example` fields: session_id, transcript_path, cwd, permission_mode, effort, hook_event_name, stop_hook_active, agent_id, agent_type, agent_transcript_path, last_assistant_message, background_tasks, session_crons. There is no `model`.
- `SubagentStart.json` carries only agent_id and agent_type.
- `src/claude_code_hooks_daemon/constants/protocol.py:83-85` defines only AGENT_ID, AGENT_TYPE and AGENT_TRANSCRIPT_PATH.
- The only `"model"` in the contracts is SessionStart's own session model (`SessionStart.json:29`).

Type, id and final report are verified. The model is not.

What this changes in the plan:

- The fallback the plan hedges with ("if the event does not carry it, fall back to the agent definition's declared model") is the ONLY route. It is not a contingency.
- `min_model: opus` cannot be checked from the event. A built-in sub-agent type, or a definition with no declared model, has no model source at all.
- The model could be read from the sub-agent transcript at `agent_transcript_path`, but that needs a separate check that the transcript records a model.
- Task 2.2 and the Option B text need rewriting. The "ordered model ladder" enforcement is only as strong as the declared-model source.

### R2. "the human-only property is a convention plus the handler guard on the command" (What exists to compare)

No handler guards `approve-merge`.

- `grep approve-merge` over `src` (`.py`) finds only `cli.py` (`cmd_approve_merge`, around line 4980, and the parser at line 11363), `merge_to_main_approval.py` (the deny route and docs) and docstrings in `constants/handlers.py` and `config/models.py`.
- `upgrade_approval_guard.py` matches only `approve-upgrade`/`approve` and `upgrade-approvals/`.
- `merge_to_main_approval.matches()` only matches merges.
- `merge-approvals` appears only as `APPROVAL_SUBDIR` in the handler (`merge_to_main_approval.py:55`) and in a `cmd_approve_merge` docstring. Nothing protects the directory.
- `cmd_approve_merge` does not check `isatty` (compare `_stdin_is_a_terminal`, `cli.py:5607`).

Today it is a pure convention, so an agent can run `approve-merge` or `touch untracked/merge-approvals/<branch>.approved` unchallenged.

What this changes in the plan:

- Phase 2 Task 2.3 ("same family as the upgrade-approvals guard") is NEW work, not an extension.
- Phase 4 Task 4.1 ("TTY-gated ... consistent with the upgrade gate") adds a gate that does not exist today.
- Even `approver: human` needs both for the human gate to be real. The migration table row "key `true` maps to `human` (unchanged behaviour)" preserves an agent-forgeable gate.
- The plan should state this gap and decide whether the guard and TTY gate apply to the human path as well.
