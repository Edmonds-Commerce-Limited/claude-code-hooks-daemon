## 07:40 · decision · — — scope demarcation is a first-class requirement, not a detail

User requirement: journalling rules must be explicitly and *only* about
journalling; plan rules explicitly and *only* about `PLAN.md` and other
plan-type files. This reframes the root cause — the two rule-sets are near
**opposites**, so rule-bleed in either direction is a failure mode:

| Axis                 | `JOURNAL/*.md`                  | plan-type files (`PLAN.md`, …)   |
| -------------------- | ------------------------------- | -------------------------------- |
| Mutation             | append-only, never rewritten    | freely rewritten / curated       |
| Growth               | unbounded **by design**         | bounded — lean, surgical         |
| Size enforcement     | **never** size-limited          | tiered advise → warn → block     |
| History lives in     | the file itself                 | **git**, not the file body       |

Bleed direction A (journal rules → PLAN.md) produces the observed failure: an
append-only, ever-growing plan. Bleed direction B (plan rules → journal) is the
inverse hazard: an agent "curating"/trimming an append-only log, destroying the
record. The design must guard both directions.

Two consequences recorded now so they are not lost:

1. **Naive size enforcement is dangerous on its own.** Telling an agent only
   "your plan is too big" invites it to *delete* content rather than *relocate*
   it. Every size message must name the destination (`JOURNAL/`) in the same
   breath, and state that the journal grows freely.
2. **Content-shape signals are scope-dependent.** Dated headings, past-tense
   narrative and pasted tracebacks are *correct* journal content and *only*
   ever a defect signal when found in a plan document. Any shape detector must
   carry an explicit file-scope predicate.

Follow-up dispatched to all five agents: audit the file-scope predicates in
every `plan_qa` check for mis-scoping, find a shared path classifier (or
propose one as SSoT), define what counts as a "plan-type file"
(`PLAN.md`, `PLAN-v1.md`, `CRITIQUE-v1.md`, supporting docs, templates), and
make config key names encode their scope unambiguously.

## 07:55 · decision · — — the READ contract completes the model and anchors the thresholds

User requirement: the journal is not to be read whole — it is grepped, tailed,
or mined by a sub-agent for "plan archeology". The plan, by contrast, IS read
whole for grounding. This is the mirror of the write contract:

| Axis  | `JOURNAL/*.md`                                | plan-type files            |
| ----- | --------------------------------------------- | -------------------------- |
| WRITE | append-only, unbounded by design              | curated, LEAN and bounded  |
| READ  | **never whole** — grep / tail / sub-agent     | **read in full** for grounding |

The causal link is the important part, and makes both rules self-justifying
rather than arbitrary hygiene:

- `PLAN.md` must stay lean **because** it is the artefact read in full every
  session. The size limit is *derived from its read cost*.
- `JOURNAL/` may grow forever **because** it is never read whole. Unbounded
  growth is only safe under a bounded read discipline.

Consequence for threshold design: express tiers in **tokens**, not just bytes —
the operative question per tier is "what does it cost to re-read this every
session?". Re-briefed `bloat-forensics` to re-derive boundaries from read cost
and reconcile against the percentile-derived numbers.

**Consistency trap flagged to the agents**: this repo's own `pipe_blocker`
handler blocks piping to `tail`/`head`. Guidance that naively says "tail the
journal" would contradict an active handler and get an agent blocked. The
drafted wording must only recommend mechanisms the project's own handlers
permit (direct `tail -n N <file>` if unpiped, `Read` with `offset`/`limit`,
whitelisted `grep`/`rg`, or sub-agent delegation) — verification requested
with file:line before anything is written down.

**Possible new enforcement surface** (feasibility under assessment by
`planqa-arch`, honest verdict requested — it may not be worth building): a
PreToolUse advisory on `Read` of a large `JOURNAL/*.md` day-file with no
`offset`/`limit`. Precedent exists in `daemon_docs_guard`, which already warns
on reads of a specific docs directory. Must be rate-limited and must never fire
on `PLAN.md`, where full reads are the desired behaviour.

## 08:30 · finding · P1 — pipe_blocker does NOT block unpiped `tail`; read guidance is safe

Verified directly (agent delivery has been unreliable, and this fact gates every
message we draft, so redundancy was warranted):

- `handlers/pre_tool_use/pipe_blocker.py:94` —
  `_pipe_pattern = re.compile(r"\|\s*(tail|head)\b", re.IGNORECASE)`.
  The handler matches **only on a pipe INTO** tail/head.
- `pipe_blocker.py:107-119` — `matches()` requires a pipe to tail/head; "No pipe
  to tail/head" is listed as an explicit non-match condition.
- `pipe_blocker.py:130-134` — `tail -f` and `head -c` are allowed even when piped.
- `strategies/pipe_blocker/common.py:12-22` — universal whitelist includes
  `^grep\b`, `^rg\b`, `^awk\b`, `^sed\b`, `^jq\b`, `^cat\b`, so even
  `grep … | tail` is allowed.

**Conclusion**: a direct, unpiped `tail -n 50 <journal>` is NOT blocked. The
read-contract guidance may safely recommend all four mechanisms:

1. `Read` with `offset`/`limit` — tool-level, no handler involvement (cleanest)
2. `tail -n N <journal-file>` — direct and unpiped
3. `grep -n "pattern" <journal-file>` — whitelisted, and `grep … | tail` too
4. sub-agent delegation for deep archaeology

No self-contradiction risk. This removes the blocker on Task 4.1 wording and on
the drafted enforcement messages.

## 09:30 · decision · P1 — design fixed from the five agent reports

**Tier mapping** — tiers are wording, not new machinery. `Level` stays two-valued;
tier 1 → ADVISE, tier 2 → ADVISE with escalated wording, tier 3 → BLOCK. Adding a
third `Level` would break `report.py:46-47`, whose header count knows only BLOCK
and ADVISE.

**Thresholds** (`bloat-forensics`, measured with tiktoken, not estimated; density
3.97 B/token, p25-p75 3.82-4.14 — bytes are a faithful runtime proxy). Canonical
unit is **tokens**; bytes/lines are the runtime proxy. Rule shape `bytes > B OR
lines > L` — both axes needed, since 00110 is byte-heavy/line-light and 00008 the
inverse.

| tier     | bytes   | lines | ~tokens | corpus hit  |
| -------- | ------- | ----- | ------- | ----------- |
| advisory | >18,000 | >350  | ~4,500  | 31/183 (17%) |
| warning  | >25,000 | >500  | ~6,300  | 20/183 (11%) |
| block    | >35,000 | >900  | ~8,800  | 6/183 (3.3%) |

Derived from **read cost**, not percentiles — percentiles are a property of *this*
repo and would be meaningless in a client project with 100 KB plans. The
independent anchor: `src/**/*.py` median is 761 tokens, p95 4,643, largest handler
10,817. A plan is grounding, not the work, so it should cost no more than the
source it describes. Resident context is already **42,466 tokens (21%)** before any
read, so the real working budget is ~123,500 — the tiers are calibrated against
that, not a notional 200k.

**Escape hatch is mandatory** — `MUST_EXCEED_PLAN_SIZE_BECAUSE="reason"`. And
**shrinking edits must never be blocked**, or a 57 KB plan can never be refactored
down.

**The finding that reframes the block message**: only ONE of the six worst
offenders is a journalling failure. 00101 collapses 45.2 KB → 9.5 KB (corpus
median) once its dated incident blocks move out. The other five are **over-scoped,
not journal-polluted** — after perfect curation 00100 is still 45.8 KB because its
task tree alone is 28.5 KB. So the block message must name **two** remedies:
relocate narrative to `JOURNAL/`, **or** split an over-scoped plan. Naming only
the first to a 00100-class plan is actively harmful — with no narrative left to
move, the only remaining lever is deleting genuine task content.

**Journalling amputates the tail, it does not shrink the median.** Mature plans
with a JOURNAL: median 16.6 KB vs 17.3 KB without (indistinguishable), but p90
23.4 vs 36.4 KB and max 25.8 vs 57.2 KB. Zero journal-era plans exceed 35 KB or
500 lines. A plan's irreducible content is ~10-20 KB and journalling neither can
nor should touch it. Size enforcement and journalling are complementary.

**Read-time journal advisory: DO NOT BUILD.** `planqa-arch`'s honest verdict, and
I accept it. An `ALLOW`-with-context advisory does not prevent the flood — the
journal is read anyway and you pay the advisory tokens on top. Documentation plus
the size check's own remediation text reaches the agent at the moment of
relevance, at zero marginal cost. Revisit only with measured data.

**Churn ratio: sweep-only, never blocking.** An agent cannot fix a low historical
ratio in the edit in hand, so a block would be unactionable. Also
`bloat-forensics` corrected my methodology — see the next entry.

## 10:35 · finding · P0 — Task 0.5 re-diagnosed: NOT a wrong-string bug, do not patch hastily

My earlier note called this "the block reason names the wrong handler". Having
read `core/chain.py:199-202`, the real mechanism is different and the original
framing was wrong:

```python
# First restrictive decision wins attribution: this is the
# handler the "To disable:" footer must name.
if decided_by is None and _is_restrictive(result.decision):
    decided_by = handler.name
```

In my probe BOTH handlers denied: `plan_qa_edit` (priority 44) fired first because
the probe content had no `**Status**:` line, then `plan_time_estimates` (45) fired
on the duration. Attribution went to the first denier while the *displayed reason*
came from the second — so the footer names a handler whose message you are not
reading.

So it is an **attribution-vs-reason mismatch when two handlers deny the same
call**, not a mislabelled constant. It only manifests on multi-deny, and the fix
touches shared chain logic carrying deliberate Plan 00144 semantics (*"a laxer
terminal result must not wash out an earlier non-terminal deny"*). Patching that
hastily risks a real regression to fix a cosmetic footer.

**Decision: leave tracked, do not fix in Phase 0.** Reclassified as low severity,
needs its own TDD cycle against the chain's attribution tests.
