> **Append-only activity log** for plan 00190. One file per day
> (`00190-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM; NEVER edit earlier
> entries (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` local 24h (the date is in the filename); times increase down the file.
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 07:20 · finding · — — PLAN.md churn is ~90% additive: plans are edited as journals

Measured git churn (`git log --numstat`) on PLAN.md files. A "lean, surgical,
always-correct" spec should show substantial deletions as resolved material is
condensed away. Instead deletions are near zero — these files are appended to,
never curated. This is the mechanical proof of the PLAN-vs-JOURNAL confusion.

```
plan                                              added  deleted  del/add
00104-v3.10.0-venv-resolver-dry-consolidation       885        0     0.00
00188-hook-event-semantic-response-audit            205        0     0.00
00135-event-driven-send-keys-injection              751       37     0.05
00144-plan-qa-system                                480       39     0.08
00100-venv-ssot-consolidation                       723      130     0.18
00163-plan-journalling                              525       94     0.18
00101-recap-stoppage-investigation                 2214     1319     0.60   <- the outlier that WAS curated
```

Size distribution in this repo tops out at 57 KB (00100); the user reports
100 KB+ in client projects, so thresholds must be designed for the general
client case, not calibrated to this repo's current worst offender.

Corollary for the design: **raw size is a lagging indicator**. A low del/add
ratio over a plan's history is the *leading* indicator of journal-drift. Worth
considering whether the sweep can surface that ratio, not just byte count.

## 07:40 · decision · — — scope demarcation is a first-class requirement, not a detail

User requirement: journalling rules must be explicitly and *only* about
journalling; plan rules explicitly and *only* about `PLAN.md` and other
plan-type files. This reframes the root cause — the two rule-sets are near
**opposites**, so rule-bleed in either direction is a failure mode:

| Axis                 | `JOURNAL/*.md`                  | plan-type files (`PLAN.md`, …)   |
| -------------------- | ------------------------------- | -------------------------------- |
| Mutation             | append-only, never rewritten    | freely rewritten / curated       |
| Growth               | unbounded **by design**         | bounded — lean, surgical         |
| Size enforcement     | **never** size-limited          | tiered advise → warn → block     |
| History lives in     | the file itself                 | **git**, not the file body       |

Bleed direction A (journal rules → PLAN.md) produces the observed failure: an
append-only, ever-growing plan. Bleed direction B (plan rules → journal) is the
inverse hazard: an agent "curating"/trimming an append-only log, destroying the
record. The design must guard both directions.

Two consequences recorded now so they are not lost:

1. **Naive size enforcement is dangerous on its own.** Telling an agent only
   "your plan is too big" invites it to *delete* content rather than *relocate*
   it. Every size message must name the destination (`JOURNAL/`) in the same
   breath, and state that the journal grows freely.
2. **Content-shape signals are scope-dependent.** Dated headings, past-tense
   narrative and pasted tracebacks are *correct* journal content and *only*
   ever a defect signal when found in a plan document. Any shape detector must
   carry an explicit file-scope predicate.

Follow-up dispatched to all five agents: audit the file-scope predicates in
every `plan_qa` check for mis-scoping, find a shared path classifier (or
propose one as SSoT), define what counts as a "plan-type file"
(`PLAN.md`, `PLAN-v1.md`, `CRITIQUE-v1.md`, supporting docs, templates), and
make config key names encode their scope unambiguously.

## 07:55 · decision · — — the READ contract completes the model and anchors the thresholds

User requirement: the journal is not to be read whole — it is grepped, tailed,
or mined by a sub-agent for "plan archeology". The plan, by contrast, IS read
whole for grounding. This is the mirror of the write contract:

| Axis  | `JOURNAL/*.md`                                | plan-type files            |
| ----- | --------------------------------------------- | -------------------------- |
| WRITE | append-only, unbounded by design              | curated, LEAN and bounded  |
| READ  | **never whole** — grep / tail / sub-agent     | **read in full** for grounding |

The causal link is the important part, and makes both rules self-justifying
rather than arbitrary hygiene:

- `PLAN.md` must stay lean **because** it is the artefact read in full every
  session. The size limit is *derived from its read cost*.
- `JOURNAL/` may grow forever **because** it is never read whole. Unbounded
  growth is only safe under a bounded read discipline.

Consequence for threshold design: express tiers in **tokens**, not just bytes —
the operative question per tier is "what does it cost to re-read this every
session?". Re-briefed `bloat-forensics` to re-derive boundaries from read cost
and reconcile against the percentile-derived numbers.

**Consistency trap flagged to the agents**: this repo's own `pipe_blocker`
handler blocks piping to `tail`/`head`. Guidance that naively says "tail the
journal" would contradict an active handler and get an agent blocked. The
drafted wording must only recommend mechanisms the project's own handlers
permit (direct `tail -n N <file>` if unpiped, `Read` with `offset`/`limit`,
whitelisted `grep`/`rg`, or sub-agent delegation) — verification requested
with file:line before anything is written down.

**Possible new enforcement surface** (feasibility under assessment by
`planqa-arch`, honest verdict requested — it may not be worth building): a
PreToolUse advisory on `Read` of a large `JOURNAL/*.md` day-file with no
`offset`/`limit`. Precedent exists in `daemon_docs_guard`, which already warns
on reads of a specific docs directory. Must be rate-limited and must never fire
on `PLAN.md`, where full reads are the desired behaviour.
