## 18:35 · finding · — — N3 opened, N2's fork closed, and N1's fix had a defect of its own

Three ledger movements, all found by running the full QA on merged main rather
than by reasoning:

**N1's fix was itself broken.** The replacement used `mapfile`, bash 4+, which
fails this project's own macOS `/bin/bash` 3.2.57 gate. The targeted tests all
passed — they run in the container's bash 5 — so only the separate shell
portability sweep caught it. Replaced with a `read` loop over the same process
substitution, which keeps the assignment in the calling shell and still avoids
the SIGPIPE. Worth holding on to: fixing one defect inside a block is precisely
when the next one is introduced, and a passing targeted test says nothing about
the sweeps that were not run.

**N2's fork is closed by constraint.** Repointing an inbound link inside a
JOURNAL day-file trips `journal-append-only`; leaving it dead trips
`pointer-resolves` at BLOCK. Both observed as real handler output. So
"repoint at archival time" cannot be the remedy — a journal structurally cannot
accept it — and teaching the resolver about `Completed/` is the only option
left standing. The decision the ledger was holding open for an owner is made by
the constraint instead.

**N3 is new**: the two plan-close gates are mutually exclusive on the legal
close path. Each refuses the state the other's change produces, so no sequence
of single edits closes a plan. The only working move is one whole-file `Write`
carrying both changes, which nothing documents — it is learned by being blocked
twice. That has now happened three times in this session alone.

## 18:45 · blocker · — — N4: the teeth merged this morning wedged this session

`cron_stop_enforcer` blocked every Stop reporting `issue-sdlc` missing while
`CronList` showed it present. Resisted the obvious move of disabling the
handler or creating a duplicate cron — the block message asks for exactly that,
and obeying it would have created a second never-matching cron costing an
hourly model turn, while hiding the defect.

Captured a real `Stop` payload instead (`payload_capture`, scoped to Stop, one
daemon restart, reverted after). Diagnosis took one look at it: schedule
byte-identical, prompt 580 delivered against 576 declared, the difference being
blank lines inserted between paragraphs. No truncation involved, so the cap
normalisation the module was designed around was never going to help.

The capture also answered the design question it raised. The three live crons
disagree with each other about whitespace — the failsafe job kept single
newlines, the other two did not — so this is not one renderer to special-case,
it is that delivered layout is not stable at all and cannot be part of an
identity test.

RED first: 5 failing, 3 passing. The 3 that passed were deliberate — the guards
that a different prompt, a dropped paragraph and a different schedule still do
not match. Without them the "fix" could have been `return True`.

Two things I got wrong earlier in the day that this exposes:

- I verified `TestAbsentSessionCronsNeverBlocks` before merging and treated
  that as having checked the safety property. It was one safety property. The
  dangerous case was not absence, it was a PRESENT cron that fails to match,
  which is the case the handler exists to judge and the one I never exercised
  against real data.
- I read the module's three documented contract constraints as thorough, and
  they are — but all three concern what the WIRE does to a field. The defect
  is in the round trip through a rendered advisory and an agent retyping it,
  which is the only way this field is ever populated. Reasoning about a
  delivery mechanism is not reasoning about a delivery path.
