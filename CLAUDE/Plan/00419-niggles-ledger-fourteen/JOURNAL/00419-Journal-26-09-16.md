## 10:40 · finding · T1.7 — the `background_tasks` shape, read off a real payload

**The `/goal` evaluator IS a Stop hook, so its own records quote the payload
the daemon is handed.** That is what made the capture possible at all, and it
is the whole evidential basis for the advisory built below.

The canonical route — `daemon.payload_capture` plus a daemon restart — was not
available: three agents were working concurrently against the shared daemon, a
restart was out of scope for this branch, and a `Stop` event only fires when
the PARENT session ends its turn, which a subagent can neither trigger nor read
back within its own turn. So the capture used instead is the session's own
transcript, where Claude Code records each `/goal` evaluation as a
`goal_status` attachment carrying the evaluator's reading of its ARGUMENTS —
i.e. the Stop payload. Five such records cite `background_tasks`
(`9679b063-…jsonl` lines 13487, 13507, 13552, 13724, 14032), and they straddle
the reap N5 describes.

Before the reap, verbatim from line 13487:

```
the ARGUMENTS field shows 7 background_tasks with status 'running' — these are
'teammate' type tasks (sub-agents or parallel work), not OS processes.
```

And line 13552, on the same seven:

```
The assistant verified via harvest-background, ps, and ListAgents that no
OS-level processes are running and that agent teammates are idle, but the
ARGUMENTS field represents the actual state the stop hook evaluates against.
```

After `TaskStop` on each of the seven, line 14032:

```
The ARGUMENTS field now shows 'background_tasks: []' (empty), confirming no
work is in flight.
```

**Both halves are therefore established, not assumed:** a registered-but-idle
teammate DOES occupy `background_tasks` (with `status: "running"`, and a `type`
the evaluator reads as `teammate`), and reaping it DOES empty the list. Entry
field names are the contract's (`Stop.json` `input_example`:
`id`/`type`/`status`/`description`/`command`).

Two negative checks, so the advisory cannot be grounded in a field the daemon
never sees: the Stop forwarder pipes stdin verbatim (`.claude/init.sh`,
`forward_stop_event` — "`send_request_stdin` wraps the raw stdin hook_input"),
and `handlers.stop.*` config is a free-form dict, so nothing strips the field
on the way in.

**What this capture is NOT.** It is not a `payload-capture/Stop.jsonl` written
by the daemon itself, so it cannot show a key the evaluator's prose did not
mention. It was sufficient here because the advisory needs only the LIST and
its LENGTH — the message is deliberately conditional ("if these are finished
teammates"), so it never asserts a `type` or a `status` it has not verified.

## 11:05 · action · T1.7 — teammate reaping documented, and a Stop advisory built

**Documentation (unconditional half).** `CLAUDE/AgentTeam.md` gains "Reaping
Teammates (`TaskStop`)" as the canonical home, stating the rule (reap once the
work is harvested, confirm with `ListAgents`) and the reason (an idle teammate
still reads as background work to `/goal`, so the natural end state of a
CORRECT parallel workflow is a session `/goal` can never release — and it holds
context meanwhile). Per `CLAUDE/DocumentationStrategy.md` the satellites point
rather than duplicate: the Cleanup Phase "Do"/"Don't" lists, the Team Lead
Checklist, and `CLAUDE/Worktree.md`'s See Also, which is where the
worktree-versus-teammate distinction is most likely to be missed.

**The advisory (evidence-gated half, and the evidence permitted it).**
`handlers/stop/teammate_reap_advisor.py`, priority 9, `terminal=False`.
Priority 9 is the last free slot below `auto_continue_stop`'s 10 — a Stop
handler above it is shadowed on every stop lacking a `STOPPING BECAUSE:` line,
which `tests/integration/test_stop_chain_terminal_shadowing.py` denies outright
— and 9 rather than 6 because a handler that never denies has no claim to run
ahead of the two that do (`cron_stop_enforcer` at 7, `release_blocker` at 8).

One deviation from the decision document worth recording, because it reads as a
contradiction and is not. The document says the handler must return an
`AdvisoryResult`. It cannot: `StopHandlerBase` IS `BlockingHandler` (Stop can
refuse, so its tier base narrows `handle()` to `BlockingResult`), and
`AdvisoryResult` is a SIBLING of `BlockingResult`, not a subtype — declaring
the narrower return would be an `[override]` error, and the only way to silence
that is a `type: ignore`, which this project blocks. The requirement behind the
wording is "can never construct a deny", and that is met structurally instead:
every path returns `Decision.ALLOW`, and a unit test reads the module's own
source to assert it contains neither `Decision.DENY` nor `.deny(` — so a deny
branch added later fails the suite rather than reaching a client. An assertion
about one call would not have done: it is satisfied by a handler that denies on
some other input.

RED first, against the captured shape rather than an invented fixture: 13 tests,
clean RED of 1 collection error (`No module named
'…handlers.stop.teammate_reap_advisor'` — nothing could pass), then 13 passed.
The first three tests pin the capture directly: seven teammate entries →
advise; `[]` → silent; field absent → silent, because `Stop.json` says an
absent list means *unknown* and never *empty*.
