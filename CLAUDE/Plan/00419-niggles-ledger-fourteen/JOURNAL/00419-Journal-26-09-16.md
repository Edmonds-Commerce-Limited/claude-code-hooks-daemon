## 10:29 · finding · N9 — every WorktreeCreate in this repo was failing

Four `isolation: "worktree"` agents were dispatched at once to clear the
remaining WIP in parallel. All four came back with the same line:

```
WorktreeCreate hook failed: HOOKS DAEMON: WorktreeCreate produced no
worktree path (is the worktree_create handler enabled?)
```

The owner spotted it immediately for what it was — "dogfooding alert right
there" — and the dogfooding rule took priority over the parallel dispatch.

The handler WAS enabled, at priority 50, and `hooks-daemon handlers` confirmed
it. Checking that was the wasted step, and the message is what caused it. The
daemon log had the real answer:

```
Handler worktree-create raised exception
  ...
  File ".../handlers/worktree_create/worktree_create_handler.py", line 104
    validate_seed_sources(Path(root), entries)
  File ".../utils/worktree_seeding.py", line 97, in validate_seed_sources
WorktreeSeedError: Cannot seed worktree — 1 configured entry is unusable:
  '.claude/block-words.secret': no such file or directory at the repository root
```

`secret-meta` confirms `exists: false` (read via the CLI — the path is
protected and was never opened).

## 10:31 · finding · N9 — the config comment already said why this was wrong

The seed entry that killed it carries this comment, directly above it:

> The secret word list. Gitignored, so a worktree lacks it — and
> `sensitive_content` does not fail without it, it goes silently INERT.

So one subsystem's *legitimately absent* was another subsystem's *fatal*. The
author of that config knew the file was optional and wrote it down; the seed
config simply had no vocabulary to express it.

The fail-fast rationale in `worktree_seeding.py` is sound for the case it was
written for — a typo'd path that silently seeds nothing is exactly the failure
the feature exists to prevent. What was missing is that **"seed this" and
"seed this if it exists" are two different intentions, and only one of them
was expressible.**

## 10:38 · action · N9 — fixed, RED first

`SeedEntry` gains `optional`, defaulting to `False` so an unmarked entry keeps
today's contract. Clean RED was **9 failed / 24 passed** — the 24 are the
guards that had to hold before AND after, including every existing fail-fast
case, or the fix would have been indistinguishable from "stop checking".

`optional` excuses ABSENCE ONLY. An optional entry that is absolute, traverses
upwards, or resolves outside the repository is still fatal, each pinned by its
own test. A non-boolean `optional:` is warned about and treated as REQUIRED,
because loose coercion of a string like `"false"` could only ever fail in the
weakening direction.

Validation and placement both had to learn it: `validate_seed_sources` passes
an absent optional entry, so `seed_worktree` had to skip the same entry rather
than dying on it. Splitting that judgement across the two functions is how the
pair would fall out of step, and the docstring now says so.

Verified live: daemon restarted, `config-validate` clean, and all four worktree
agents launched successfully on the retry.

## 10:52 · decision · T1.5 — N3 is a defect fix, not a policy relaxation

Task 1.5 was recorded as owner-gated because "(1) and (2) both relax a gate
that currently blocks". The ruling rejected all three candidates and took a
fourth option, and in doing so dissolved the gate: **the premise that this
relaxes anything is wrong.**

Closing a plan needs two changes to one `PLAN.md` — tick the last Success
Criterion, flip the status header. `Edit` replaces ONE contiguous span, and
line 3 and the end of the document are never one span. So:

- tick first → all-ticked under `In Progress` → denied by `header-body-coherence`
- flip first → `Complete` with the holding-area criterion unticked → denied by
  `plan_done_requires_holding_area`

The only single-call move left was a whole-file `Write` — the operation
`R-WRITE-CLOBBER` exists to discourage on exactly this kind of document. The
all-ticked-under-`In Progress` state is the MANDATORY intermediate on the legal
path, and **a gate no legal sequence of moves can satisfy is a defect.**

## 10:58 · action · T1.5 — built, and it is a net tightening

The completion branch is now ADVISE at EDIT; the check gains a COMMIT
registration at BLOCK; SWEEP is unchanged. The `Not Started`-with-boxes-ticked
branch is untouched and still blocks at EDIT — it has a legal one-call fix
(flip the header; no box is ticked in that same edit), so it was never part of
the sequencing problem.

This ENFORCES MORE than before, not less. `header-body-coherence` had no COMMIT
registration at all, so a plan committed in the violating state reached history
unchallenged and was caught only by the next session's sweep. The invariant
moves off the surface that sees a half-written document and onto the two that
see a settled one.

The commit gate is scoped by Plan 00343's rule — BLOCK for what this commit
introduces, ADVISE for what it inherited — so an already-incoherent plan cannot
deny every later commit that touches the file for an unrelated reason. Pinned
by `test_inherited_incoherence_advises_rather_than_traps`.

The registry catalogue guard caught the new registration on its own
(`Stage.COMMIT` 17 → 18) before any of my own tests ran. That is the guard
doing precisely its job, and the count is updated with the reason rather than
the number alone.
