## 00:52 · finding · — — the premise this plan was filed on was wrong

Filed as "pin qa toolchain versions", on the reading that `pyproject.toml`'s
lower bounds are the only thing controlling which tools run. They are not, and
the real problem is both narrower and worse.

**This repository already has a lockfile.** `uv.lock` is committed, CI-gates
itself through `uv lock --check` in `scripts/qa/run_dependency_check.sh`, and
`CONTRIBUTING.md:73` names it as one of the files "the same ones `scripts/qa/`
uses".

`scripts/qa/` does not use it:

```
run_tests.sh:19   source "${PROJECT_ROOT}/scripts/venv-include.bash"
run_tests.sh:24   ensure_venv || exit 1
run_tests.sh:25   if ! "${VENV_PYTHON}" -c "import pytest"; then   # auto-provisions
run_tests.sh:39   venv_tool pytest ...

venv-include.bash:148   "${VENV_PIP}" install -e ".[dev]" --quiet
```

`pip install -e ".[dev]"` never reads `uv.lock`. It resolves the lower bounds
against PyPI, so the toolchain that decides whether this project passes is
whatever was newest when the venv happened to be built.

Measured, not inferred — two venvs, two toolchains, and the one that runs the
tests is the off-lock one:

| Tool   | `uv.lock` | `.venv` | workspace venv (runs QA) |
| ------ | --------- | ------- | ------------------------ |
| black  | 26.3.1    | 26.3.1  | **26.5.1**               |
| mypy   | 1.20.2    | 1.20.2  | **2.3.0**                |
| pytest | 9.0.3     | 9.0.3   | **9.1.1**                |
| ruff   | 0.15.11   | 0.15.11 | **0.15.22**              |

`.venv` matches the lock on every tool. The workspace venv is adrift on four,
mypy by a whole major.

**The repository has already diagnosed this exact bug once.**
`.pre-commit-config.yaml`'s header explains that pinning tools in pre-commit
mirror repos created "a SECOND version source that drifts from `uv.lock`", that
it drifted for "two years of silent rot", and that the fix was to delete the
second source rather than keep it synchronised. That fix was applied to
pre-commit. The QA venv path still has the second source — and it is the more
consequential one, because it is what the gate actually runs.

Why this matters more than the pins: a plan that added upper bounds to
`pyproject.toml` would have been treating the symptom. Bounds express
compatibility; the lockfile expresses reproducibility. Tightening bounds while
the lock stays bypassed leaves a second source in place and makes it look
addressed. `PLAN.md` is rewritten around the bypass.

## 01:06 · action · T1.1 T1.2 — the QA venv now installs from the lock, and passes on it

`install_deps` now runs `uv sync --frozen --all-extras` with
`UV_PROJECT_ENVIRONMENT` pointed at the resolved venv (`2de920a3`). Absent
`uv` it fails and names both remedies; `HOOKS_DAEMON_ALLOW_UNLOCKED_VENV=1`
opts back into pip with a warning that says what it costs. A silent fallback
was the one shape ruled out — it restores the bypass in full while looking
fixed.

`--frozen` carries the weight. A bare `uv sync` *updates* the lock to satisfy
`pyproject.toml` when they disagree, which re-resolves against PyPI; without
the flag the change would look applied and reintroduce the drift.

T1.2's question was what happens to the venv that already exists, since it is
what `venv_tool` selects and therefore what the change has to reach. Answer:
synced it. `uv sync --dry-run` first showed the drift was repo-wide — about
**100 packages** differ from the lock, not the six tools the evidence table
tabulated.

Then the whole suite on the locked toolchain, which is the actual proof:

```
✅ format 0 · lint 0 · type_check 0 · security 0 · semgrep 0
✅ tests: 18507 passed, 0 failed, 6 skipped | coverage: 95.2%
QA: 25/25 PASSED
```

Checked before switching that obeying the lock changes no verdicts — the
locked `.venv` passed the same tree independently (black 1383 files unchanged,
ruff clean, mypy 520 files 0 issues). Both toolchains pass; this was only ever
about which one is authoritative.

Blast radius confirmed by reading every caller: the eight are `scripts/test.bash`,
six `scripts/qa/run_*.sh`, and `venv_tool`'s own auto-provision. All dev-facing.
No client install path now requires `uv` that did not already.

## 01:06 · finding · P2 — CI has the same bypass, and it couples the remaining work

`.github/workflows/qa.yml:46` and `:179` both run `pip install -e ".[dev]"`.
The workflow that gates merges resolves its toolchain against PyPI on every
run, across a 3.11/3.12/3.13 matrix — then runs `uv lock --check` a few steps
later and certifies a lockfile it never installed from.

This is Success Criterion 3 ("no provisioning path installs QA tools without
consulting the lock"), and the plan had no task for it. Added as Task 2.2.

It also **sequences Phase 2**: the T2.1 gate would fail CI the moment it
landed, because CI's venv is off-lock by construction. The gate and the CI fix
have to be one commit.

`uv.lock` is universal (`requires-python = ">=3.11"`, resolution markers
splitting at 3.15), so one lock serves all three matrix interpreters.

## 01:06 · finding · T2.1 — the gate mechanism, and proof it is not vacuous

`uv sync --frozen --all-extras --check` exits 0 against the synced QA venv
(136 packages, "Would make no changes"). The half that matters is the negative:
against a venv with a single deliberately-downgraded package it exits 1 and
names both versions.

```
$ uv pip install 'ruff==0.15.22' && uv sync --frozen --all-extras --check
 - ruff==0.15.22
 + ruff==0.15.11
The environment is outdated; run `uv sync` to update the environment
exit=1
```

Tested the empty-venv case too (exit 1, "Would install 136 packages"). Checking
only that shape would have been the weaker test — a gate that catches a missing
package but not a wrong version would pass this plan's own evidence table.

## 01:06 · finding · — — a factual error in this plan's Non-Goals

Non-Goals says the client install path is excluded because
`scripts/install/venv.sh` runs `uv pip install -e <dir>`. That file has **two**
provisioning functions and the primary one, `create_venv_at_path`, runs
`uv sync --project`. The conclusion survives — no `--all-extras`, so a client
gets no QA tools — but the stated reason is wrong. Corrected in `PLAN.md`.

Reading it surfaced a real gap: `create_venv_at_path` calls `uv sync` **without
`--frozen`**, so a checkout whose `pyproject.toml` and `uv.lock` disagree has
its lockfile silently rewritten and re-resolved against PyPI. Same defect as
T1.1, one function over.

I first recorded this as "file it, do not fix it — client-facing behaviour is
the owner's call". That was deflection, and two parts of it were wrong. It is
testable here: `tests/integration/test_ensure_venv.py` already drives
`create_venv_at_path` against real venv builds. And the trade-off I invented
does not exist — without `--frozen`, uv re-locks *only* when pyproject and the
lock disagree, which in a tagged checkout is already a defect that CI gates.
The flag does not make a working install fail; it converts a silent wrong
install into a legible error. Added as Task 2.3 with a RED test first.
