## 16:30 · finding · P1 — root cause of the "already upgraded" confusion

Client upgrades ALWAYS print `Already at version vX.Y.Z` and take the idempotent
fast path, even on a genuine version jump. Chain:

- `scripts/upgrade.sh` (Layer 1) checks out the target tag at Step 6 (line ~359)
  BEFORE delegating to Layer 2 — it must, because Layer 2 (`upgrade_version.sh`)
  only exists in the target checkout.
- Layer 2 then computes `ROLLBACK_REF = git describe --tags --exact-match`
  (line ~189) which now ALWAYS equals `TARGET_VERSION`, so
  `if [ "$ROLLBACK_REF" = "$TARGET_VERSION" ]` (line ~197) is always true.

Consequences: (a) misleading message on every upgrade; (b) the full-upgrade path
(config preservation/merge, breaking-change detection, snapshot/rollback,
upgrade-guide enforcement — Layer 2 Steps 3–17) is DEAD for client installs;
(c) `CURRENT_VERSION` (venv/source) vs the venv `.daemon-version` stamp disagree,
producing "already at 3.40 but venv stamped 3.38, rebuilding".

Fix direction: Layer 1 already captures `FROM_VERSION` before checkout
(line ~271); pass it to Layer 2 and base idempotency + messaging on
from-vs-target (+ venv-stamp health), not the post-checkout git ref.
