## 16:30 · finding · P1 — root cause of the "already upgraded" confusion

Client upgrades ALWAYS print `Already at version vX.Y.Z` and take the idempotent
fast path, even on a genuine version jump. Chain:

- `scripts/upgrade.sh` (Layer 1) checks out the target tag at Step 6 (line ~359)
  BEFORE delegating to Layer 2 — it must, because Layer 2 (`upgrade_version.sh`)
  only exists in the target checkout.
- Layer 2 then computes `ROLLBACK_REF = git describe --tags --exact-match`
  (line ~189) which now ALWAYS equals `TARGET_VERSION`, so
  `if [ "$ROLLBACK_REF" = "$TARGET_VERSION" ]` (line ~197) is always true.

Consequences: (a) misleading message on every upgrade; (b) the full-upgrade path
(config preservation/merge, breaking-change detection, snapshot/rollback,
upgrade-guide enforcement — Layer 2 Steps 3–17) is DEAD for client installs;
(c) `CURRENT_VERSION` (venv/source) vs the venv `.daemon-version` stamp disagree,
producing "already at 3.40 but venv stamped 3.38, rebuilding".

Fix direction: Layer 1 already captures `FROM_VERSION` before checkout
(line ~271); pass it to Layer 2 and base idempotency + messaging on
from-vs-target (+ venv-stamp health), not the post-checkout git ref.

## 20:10 · finding · P4 — live dogfooding: compact-injection LOOP (4-5 stacked /compact)

While running this plan under ccy, the supervisor injected `/compact` 4 then 5
times and Claude Code queued+ignored every one. Root cause in
`CompactStateMachine.AWAIT_COMPACTING`: the ESC flush fired ONCE and only for the
CRITICAL band (Plan 00152 `_await_escalate` latch). An ELEVATED-band queued
`/compact` therefore never got an `[esc]`; `await_timeout` returned the machine to
MONITOR, which promptly re-injected `/compact` — a loop. User: "should not inject
another if one is already queued … if we want it to take effect you have to fire
in escape until it does." Also noted: ESC (or ↑+↵) interrupts the in-flight turn,
which is what actually lets the queued `/compact` run.

## 21:45 · finding · P4 — release code-review caught a duplicate-compact path

Running the release Code Review Gate over `v3.40.0..HEAD`, the reviewer flagged a
REAL bug in the Phase 4 host/worker split: TWO independent `CompactStateMachine`
instances. The host's in-process fallback (fired on a mere worker `select`
timeout, not just a crash) used a machine whose cooldown/AWAIT state never
advanced while the worker handled ticks — so a worker stall or hot-reload right
after a `/compact` could inject a DUPLICATE `/compact`. That is the exact bug
class this release exists to kill, in a default-on subsystem. Per RELEASING.md
"prefer reviewing early", fixed now rather than shipped.
