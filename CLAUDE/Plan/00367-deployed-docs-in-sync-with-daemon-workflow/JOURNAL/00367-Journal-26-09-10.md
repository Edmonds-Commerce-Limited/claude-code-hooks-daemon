## 07:58 · decision · P2 — a new handler, not an extension of plan_qa_edit

`plan_qa_edit` is a lint whose findings are level-driven by the
`plan_workflow.qa` policy; the closing gate is a project toggle with a
human-side artefact (the approval marker), so it is its own handler,
`plan_close_approval` (`R-PLAN-CLOSE-APPROVAL`, priority 43, terminal,
PLANNING-tagged so the registry injects the key alongside the plan dir).
What the two share is "the content the file WOULD have", now one helper
(`handlers/utils/would_be_content.py`) both call. The gate is on the FLIP
(before-status differs from a terminal after-status), not on the terminal
state, so a plan a human already closed stays editable. The project handler
that emits "PLAN NOT DONE" (`plan_done_requires_holding_area`) reads the
status the same way and was the reference for the detection.

## 08:00 · decision · T2.2 — the marker is one-shot, untracked, keyed by number

`hooks-daemon approve-plan-close NNNNN` writes
`untracked/plan-close-approvals/NNNNN.approved` under the daemon's untracked
directory; the next terminal flip of THAT plan consumes it (unlinks). It
refuses a number with no active plan folder (an approval for a typo would
sit waiting to close the wrong plan) and prints a note when the key is off
(nothing would consume it). Human edits made outside Claude never reach the
hook, so that route needs no daemon support.

## 08:05 · decision · P1 — the owner caught a baseline

The first cut of the check blocked only an instance NEW in the edit or
commit and advised on the rest, copying this repo's `pointer-resolves`
convention. The owner asked whether that was a baseline. It was: a rule
that only warns on what is already there is a baseline by another name,
and DBF section 4 makes that the owner's decision, not the agent's. The
check now blocks every instance at edit and at commit, and the project
config sets `unenforced-approval-gate: block` under
`documentation.qa.check_modes`, because this repo's commit gate and edit
mode are `warn` by default and a block-eligible finding would otherwise
still only warn at the real entry point. Consequence, stated plainly: any
commit that stages `Worktree.core.md` fails until its 11 instances are
fixed, and the same held for `PlanWorkflow.core.md` until Phase 3.
