## 18:14 · decision · — — why this plan exists at all

Follows a direct user decision on a trade-off I had previously deferred. My
earlier position was that recursing into `$( )` would block
`$(cmd | head -1)` — ordinary shell idiom for extracting one value — and so
traded a real gap for a noisy handler. The user weighed it and chose to fail
closed: friction has a config remedy, a silent bypass has none.

Implementation showed why that call was better than mine. Correct attribution
is not blanket blocking: classifying the INNER producer against the whitelist
that already exists leaves `echo $(git log --format=%H | head -1)` allowed.
The noise I feared largely does not exist.

Recovery cron `cae1a725` was already live from earlier in this session, so no
new one was created.

## 18:16 · finding · P1 — the defect, measured before any code changed

Probed through the production forwarder against the live daemon rather than by
importing the handler — hand-rolled probes have given false results here
before.

| command                                         | decision |
| ----------------------------------------------- | -------- |
| `echo $(pytest tests/ \| head -1)`              | allow    |
| `ps -o etime= -p $(pgrep -f claude \| head -1)` | allow    |
| `echo $(echo $(pytest tests/ \| head -1))`      | allow    |
| `FOO="$(pytest tests/ \| head -1)"`             | deny     |

This corrects my own earlier description of the gap. I had said pipes nested
in `$( )` were "invisible". They are not — the pipe is always detected. What
fails is ATTRIBUTION: the producer is read from the text left of the pipe,
which inside a substitution begins with the OUTER command. `echo` is
whitelisted because echoing is cheap, so the wrapper laundered the producer.

The two shapes that already denied did so by accident, not by understanding:
`FOO="$(pytest` matches no whitelist entry. Right decision, wrong reported
producer — the block told the agent to whitelist a variable assignment.

## 18:20 · decision · P3 — scope widened mid-implementation

While implementing I checked whether the same "ask the question of the whole
command" shape appeared elsewhere. It did, twice:

- `_pipe_pattern.search` returns the FIRST match only, so exactly one pipe per
  command was ever classified. `git log | head -2 && pytest tests/ | head -1`
  was ALLOWED. Prefixing any command with a whitelisted pipe laundered it —
  cheaper to exploit than the substitution route, and needing no substitution.
- the `tail -f` / `head -c` exemptions were searched across the WHOLE command,
  so `&& tail -f /dev/null` appended anywhere disabled the handler entirely.

One root cause, so one plan. A guard covering substitution but not shadowing
would have left the cheaper bypass open while looking complete — the exact
failure mode DBF exists to prevent.

`matches()` is now built on `_find_offending_producer()`, which iterates every
pipe and judges each on its own producer and its own consumer. `handle()`
reports the OFFENDING producer instead of the first pipe's.

## 18:31 · decision · T5.3 — pgrep whitelisted on the user's call

User authorised it directly ("whitelisting pgrep is fine"), so `^pgrep\b` was
added to `UNIVERSAL_WHITELIST_PATTERNS` with a failing test first. The plan's
Non-Goal was narrowed rather than ignored: no broad whitelist review, one
entry, because correcting the attribution is precisely what made its absence
observable.

That is the interesting part. `pgrep` was never deliberately excluded — the
canonical idiom `ps -o etime= -p $(pgrep -f x | head -1)` had been passing
under the OUTER `ps` all along, so nothing ever asked whether `pgrep` itself
was classified. The misattribution was concealing a second, unrelated gap.
Fixing it surfaced the omission rather than creating it.

Checked before claiming friction either way: `grep -rn pgrep scripts/ bin/`
finds 8 occurrences, none of them a `pgrep | head` pipe, so no project script
changed behaviour in either direction.

QA11 was killed mid-run rather than left to finish — the pgrep change would
have invalidated it, so one run over the whole change set is cheaper than two.
