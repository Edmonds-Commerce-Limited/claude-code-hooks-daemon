## N1 (decision 1): the template ships the Priority constants

**Test**: `tests/integration/test_template_priorities_match_the_constants.py`.
It covers the whole `ConfigTemplate.generate_full()`, so every handler the
template lists with a priority (more than 100) is compared against its
handler class default, which comes from `priority.py`. It has no allow-list.
Two controls stop it from passing vacuously. The parse must find more than
100 entries, and every template entry must resolve to exactly one handler
class.

**RED first, and it found four divergences, not three**:

```
pre_tool_use.security_antipattern: template ships 15, the constant says 14
status_line.account_display:       template ships 6,  the constant says 5
status_line.git_repo_name:         template ships 5,  the constant says 3
status_line.host_hostname:         template ships 7,  the constant says 6
```

**The ledger's premise was wrong. Relative order was NOT preserved.**
`environment_indicator` is not in the template, so it runs at its constant of
4\. I built a router from the generated template and measured the status-line
order on a fresh install:

```
before: 2 multithread  4 environment  5 git-repo-name  6 account  10 model ...
after:  2 multithread  3 git-repo-name  4 environment  5 account  10 model ...
```

The environment indicator rendered before the repository name. That
contradicts `ENVIRONMENT_INDICATOR`'s own comment ("After repo name, before
account display"). So a user could see the defect.

**Which side won, and why.** The constants won all four.

- Status line: the constants hold the documented intent, and the measured
  order proves the template breaks it. `docs/guides/HANDLER_REFERENCE.md`
  already said 3 and 5.
- `security_antipattern`: `SECURITY_ANTIPATTERN = 14` has not changed since
  the handler shipped (v2.20.0, same commit as the template's 15). It sits in
  the documented content-leaving band with `sensitive_content`,
  `secret_file_guard` and `project_containment`. `HANDLER_REFERENCE.md`,
  `CLAUDE/LLM-INSTALL.md` and this repository's own config all say 14. The
  template was the only surface that disagreed. The one behaviour change on a
  fresh install: this handler now runs before `tdd_enforcement` and
  `pipe_blocker` (15). When one tool call trips both and the chain stops at
  the first deny, the security deny is the one reported. That is the order
  the band documents.

**Also fixed in the same change**:

- `CLAUDE/Architecture/StatusLine.md`'s execution-order table put
  `environment_indicator` at 11. That is this repository's override, not the
  shipped value. It now says 4.
- The `HOST_HOSTNAME` comment claimed it sits "beside" the environment
  indicator. `account_display` sits between them, so the comment now says "in
  the environment cluster after".

**Band docs and the Plan 00435 test**:
`tests/integration/test_priority_bands_match_the_code.py` still passes. No
constant changed value, so no band moved.

**Existing configs are not rewritten.** The config-changes entries are
documentation-only (no `recommended_value`). A project that set its own
priority chose it, and the advisory must not tell it to change. This
repository's own config (`git_repo_name: 25`, etc.) is one example.

## N3 (decision 5): the `correction` category

**Grammar**: `## HH:MM · correction · REF`, where REF names the corrected
entry. It is `HH:MM` for an entry in the same day-file, or `YY-MM-DD/HH:MM`
for an entry in an earlier day-file of the same plan. The corrected entry is
never edited or moved.

- `mkplan.bash --journal` (both copies): accepts `correction` and requires
  `--ref`. It refuses a malformed ref (`T2.1`, `9:50`, `—`, a space-separated
  date) and a ref that names no entry. Both refusals happen before any
  mutation, and a refused call does not even create `JOURNAL/` (D5). The entry
  lookup skips fenced blocks using the same marker-matching rule as
  `utils/markdown_fences.py`, so a heading quoted in a fenced log is not taken
  as an entry. To make that check possible, the clock read moved above the
  "validation complete" line. It is still one `date` call, so the midnight
  straddle guard is unchanged. Shellcheck is clean.
- `journal-entry-ordering`: it collects the same-file labels named by
  `correction` entries (`corrected_entry_labels` in `plan_qa/model.py`, which
  is still the only heading parser). Those entries set no high-water mark.
  Every other entry is judged as before, including entries between the wrong
  one and its correction. A `--ref` on any other category voids nothing, and
  a cross-day ref voids nothing in the file that carries it. Both have
  tests.
- `journal-append-only` and `journal-entry-ordering` remediations name the
  exact command, `mkplan.bash --journal N correction <body-file> --ref <HH:MM of the entry it corrects>`. The ordering remediation still leads with
  appending, not moving.
- Both copies of each of `_JOURNAL_TEMPLATE_.md`, `mkplan.bash` and
  `PlanJournalling.md` changed. `PlanJournalling.md` also ships under
  `install/templates/`, which the original N3 write-up did not mention.
  `JOURNAL_CATEGORIES` now has seven entries, and
  `test_journal_category_sync.py` pins all five copies.

**The N3 regression case**: the 00419 day-file is archived, and its
correction is a `finding` entry that cannot be rewritten. So nothing changes
there, and nothing can. The new category applies to journals written from now
on.

## N5 (decision 6 = remedy 2): the tracked default

- The contract text (advisory and strict deny) and `get_claude_md` now call
  the dispatching plan's `subagent-reports/` the DEFAULT. They say it is
  tracked and should be committed with the plan. They describe the
  gitignored `fallback_report_dir` as "only when no plan applies".
- New advisory, never a deny, in strict mode too: a dispatch that names a
  plan folder but declares a destination under `fallback_report_dir` is
  told to use `<plan-folder>/subagent-reports/…`. This is the exact shape of
  the v3.65.0 loss. Only a declared destination (verb + to/in/under/into +
  path) counts, so a bare mention such as "the daemon keeps a copy under
  `untracked/agent-reports/auto/`" draws nothing. The configured fallback
  directory is the one checked. A new acceptance probe covers it, and the
  playbook harness passed against the restarted worktree daemon.
- Docs: `HANDLER_REFERENCE.md` and both `PlanWorkflow.core.md` copies.
  `CLAUDE/development/IssueSdlc.md` already follows the rule (fallback only
  for the plan-less dedupe scout, plan folder once one exists), so it was not
  changed.
- `fallback_report_dir` keeps its default, so no config key changes. The
  truth-change reuses id `subagent-report-destination`, back-filled onto the
  v3.59.0 handoff entry per the truth-changes README. Its `now` restates the
  whole current truth, so an upgrading agent sees one statement.
