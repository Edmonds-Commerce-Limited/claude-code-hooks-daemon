# N27 — a worktree daemon idles out in the middle of a full QA run

**Branch**: `worktree-n422-n27`
**Commits**: `d5e08ca0` (RED test), `76dd6c8a` (fix, docs, release note),
then this report.

## Decision

**`llm_qa.py` starts the checkout's daemon, if it is not running, just before
each tool that probes it.** `ToolConfig` gains `live_daemon: bool = False`.
`smoke_test` and `tests` set it. Before running a flagged tool (not in
`--read-only`), `ensure_live_daemon()` runs `bin/hooks-daemon status`. Only
when that reports not running does it run `bin/hooks-daemon start`, and then
it prints one line: `DAEMON STARTED: ...` or `DAEMON START FAILED: ... (exit N): <output>`.

Why this one over the other candidates:

- **It is the daemon's own contract.** A stopped daemon is a normal state.
  Every real hook forwarder calls `ensure_daemon` (`.claude/init.sh`) and
  starts it on demand. The QA consumers were the only callers that treated
  "not running" as a defect. Making them behave like a hook fixes the
  assumption without adding a new mechanism.
- **It is correct for clients.** Nothing changes in the daemon, its idle
  clock or its protocol, so client daemons still idle out exactly as before.
  An idle clock that counted QA activity, or a daemon-side lease, would add
  runtime surface that every client ships only to serve this repo's QA.
- **It never restarts a running daemon.** A stale daemon (source edited, no
  restart) still fails `check-source-fresh` inside `smoke_test`, so this
  does not hide the dogfooding failure that `smoke_test` exists to catch.
  A daemon it has just started is fresh by construction.
- **It is not a heartbeat.** The daemon is checked at the moment each
  consumer starts. After that the consumer's own traffic resets the idle
  clock: `_handle_client` sets `last_activity` on every request, including
  the `_system health` query that `check-source-fresh` sends.

## Why `tests` is flagged too (a second instance of the class)

The defect class is **a QA consumer of the live daemon that assumes a
daemon started earlier in the run is still alive**. I searched two ways:
for the live-daemon markers in `scripts/qa/*` (`.claude/hooks/`,
`daemon-*.sock`, `check-source-fresh`), and for callers that report or skip
on "not running" across `scripts/`, `tests/integration` and `.claude/skills`.
That found two instances:

1. `smoke_test` (`scripts/qa/run_smoke_test.sh`), the one observed.
2. `tests`: pytest runs `tests/acceptance/` first, and its
   `daemon_running`/`daemon_socket` fixtures skip when there is no socket.
   `tests/acceptance/blocking_gate_guard.py` turns a skip in a RELEASING.md
   Step 12.0 gate into a FAILURE. Today it is safe only because of timing:
   acceptance runs about two minutes after a restart. It fails whenever a
   run starts more than `idle_timeout_seconds` after the last restart.

`check_project_handler_tests.py` runs `test-project-handlers`, which does
not use the live daemon, so it is not flagged.

**Detector.** `tests/unit/qa/test_llm_qa_live_daemon.py` reads every
registered tool's script. It fails when a script that carries a live-daemon
marker is not flagged `live_daemon`, or when a flagged one carries no
marker. It also pins the consumer set to exactly `{smoke_test, tests}`, so a
new consumer must be declared. `tests` is exempt from the marker scan,
because it reaches the daemon through pytest fixtures, not its script. That
case is covered by the explicit set pin. The detector runs in the normal
`tests` gate. No stronger detector is practical: "reaches the daemon"
becomes a runtime property as soon as a script delegates to pytest.

## Evidence

- **RED, live.** I set the worktree's `idle_timeout_seconds` to 5 (reverted,
  never committed), restarted, and waited for the PID to exit.
  `llm_qa.py smoke_test` failed with `0/3 probes passed`, `TOOL ERROR: Daemon not running — no socket found`.
- **RED, unit.** The new test file before the fix: 42 failed, 2 errors
  (`ToolConfig` has no `live_daemon`, no `ensure_live_daemon`). Committed as
  `d5e08ca0`.
- **GREEN, live.** Same setup, daemon idled out. `llm_qa.py smoke_test`
  printed `DAEMON STARTED: no daemon was running before smoke_test ...` and
  `smoke_test: 3/3 probes passed`, exit 0.
- **Targeted QA:** format, lint, type_check, pyright, magic_values,
  error_hiding and smoke_test all pass. docs_qa, british_english and
  doc_truth pass. `pytest tests/unit/qa`: 695 passed, 1 skipped. The
  release-notes holding-area tests pass. I did not run `llm_qa.py all`, as
  instructed. I also did not run the `tests` tool: the new flag on `tests`
  goes through the same `ensure_live_daemon` code path that the live
  smoke_test run exercised.
- I also used this finding while working: polling `bin/hooks-daemon status`
  keeps a daemon alive, because `read_pid_file(verify_daemon=True)` talks to
  it. To watch for an idle-out, poll the PID (`kill -0`), not `status`.

## 00464's effect on the picture

None. `worktree-plan-464-commit-gate-repo` makes the commit gates judge the
checkout named by the command (`git_command_target.py`). It does not change
where hook traffic goes: a teammate's payload `cwd` is still the main
checkout, and the hook scripts invoked are still main's. So the worktree
daemon still gets no traffic, which is exactly the case this fix handles.
The fix does not depend on the payload `cwd`: it only runs this checkout's
`bin/hooks-daemon`.
