## 11:14 · finding · — — how the real cause was found

00422 N20 was first filed as "the acceptance probes cannot pass in a
worktree whose daemon is running". It rested on the Plan 00456 agent's A/B
and on the coordinator's own run, which passed on main and failed in that
worktree. The contradiction came from `worktree-n18-n19`, which reported
35/35 QA with its daemon running. A direct run of the same two tests there
passed too (2 passed, 14.3s). So what distinguished the failing worktree
was not being a worktree. It was its name, `worktree-issue-53-venv`.

Searching the guards' skip lists for `venv` found `"venv/"` matched with
`skip_dir in file_path` in `qa_suppression.py:162` and
`comment_changelog.py:316`. Those are the two handlers behind the 14
failing probes. A wider search found four more sites with the same shape.
`strategies/lint/common.py`'s `matches_skip_path` docstring already
describes this failure ("`venv/` inside `myvenv/`"), so it was fixed once,
in one sibling.

Lesson: the first diagnosis was accepted because two runs agreed with it.
A third data point, which had been available the whole time, disproved
it.

Dedupe: no live plan touches handler skip lists. The two nearest are
00422 N11 (probe fixture location) and the lint fix that introduced
`matches_skip_path`. Recovery cron: `3c3c53c3`.

## 11:22 · finding · T1.1 — audit beyond the six named sites

Searched `src/claude_code_hooks_daemon` for `in file_path`/`in path` tests.
Confirmed the six named sites. Found six more `in file_path` sites and
classified each:

- `strategies/tdd/common.py:26` (`matches_directory`) — used by every
  per-language TDD strategy's `_SOURCE_DIRECTORIES`/`_SKIP_DIRECTORIES`
  (11 languages, ~22 call sites). Already both-side segment-bounded (it
  builds `/{directory}/` itself), so it does NOT have the substring-collision
  half of the defect — only the project-relativity half. Converting it
  touches far more call sites than this plan scoped, with no existing
  regression coverage for the venv-style collision there. Left as a
  documented follow-up, not fixed here.
- `handlers/post_tool_use/validate_eslint_on_write.py:328-331` (`is_worktree`,
  iterating `(WORKTREES_DIR, CLAUDE_WORKTREES_DIR)`) — same bare-`in` shape
  over a 2-tuple, but the result only feeds a log line
  ("Detected worktree file..."), never a skip/gating decision. No behavioural
  fail-open, so out of scope.
- `handlers/pre_tool_use/daemon_docs_guard.py:67`, `plan_qa_edit.py:117`,
  `plan_time_estimates.py:117`, `markdown_organization.py:902` — each tests
  ONE fixed, already both-side-slash-bounded pattern (e.g. `f"/{plan_dir_rel}/"`),
  not a directory LIST. Not the class this plan targets (Goals: "every
  skip-list and directory-classification site"); single-pattern containment
  checks are a narrower, different shape.

Decision: fix scope stays at the six named sites. The detector (T1.2) is
written broad enough to catch a NEW list-shaped site if one appears, but
does not retroactively demand fixing `matches_directory` or the single-
pattern sites above.

Also settled the matcher's project-root-resolution source: reuse
`utils.path_exclusion.resolve_project_root()` (best-effort, returns `None`
when `ProjectContext` is uninitialised — exactly the existing idiom
`handler_excludes_path` already uses for `daemon.exclude_paths`), rather
than inventing a second way to ask "what project is this". `project_root=None`
falls back to matching the raw `file_path` unchanged — preserves lint's
current behaviour and every existing unit test for the six handlers that
constructs them directly without initialising `ProjectContext`.
