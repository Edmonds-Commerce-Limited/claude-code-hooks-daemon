## 15:10 · finding · N1 — the new check was wrong, and only the real tree said so

`index-retention-window` landed with 20 green unit tests and then reported
**340 completed rows against a window of 30** on its first real sweep — on a
tree that was correctly AT 30. It is a BLOCK at COMMIT, so shipping it would
have denied every commit in the repository.

The cause: `plan_qa/context.py` appends the ARCHIVE index's rows to the
`ReadmeIndex` it hands checks, so `row-folder-bijection` still resolves a plan
whose row has aged out, while leaving `lines` sourced from the primary file
alone. 30 primary + 310 archived = the 340 reported. The constraint WAS
documented — in a comment on the producer, not on the dataclass a check author
reads. Recorded as N5 and fixed there.

Two things worth keeping from this. Every synthetic fixture passed: they each
built one `ReadmeIndex` from one string, so `rows` and `lines` always agreed —
a shape the real context never produces. The regression test now constructs
the divergent shape explicitly.

And the end-to-end proof earned its two extra edits. After fixing, I put a
31st row back into the real index and swept: `31 completed rows ... 1 row
overdue`; removing it returned the sweep to clean. Watching a guard fire on
real data is the only thing that would have caught the first version, because
the unit tests were green the whole way through.

## 15:25 · decision · N4 — where the rule belongs, and what it must check

Two choices worth recording, because both could reasonably have gone the other
way.

WHAT it checks. The obvious rule — "a sum written in the index must add up" —
would NOT have caught this defect. `364 + 13 = 377` is arithmetically true.
What was wrong is that both operands contradicted figures stated inches above
them (365 distinct, 378 allocated), under a ✅ asserting the check had been
done. So the rule has to be a cross-reference one: the closing self-check's
operands must match the distinct / folderless / allocated figures the same
bullet states, the folder sum must add up, and the folderless count must match
the numbers actually listed.

WHERE it lives. Not plan_qa, which ships to client projects whose plan index
has no reconciliation bullet at all — a check for one repository's prose
convention does not belong in a linter every consumer runs.
`scripts/qa/check_repo_hygiene.py` is this repository's own hygiene scan and
already owns rules of exactly that shape (`post-upgrade-index-drift`).

Proved against the real defect, not just fixtures: restoring
`364 + 13 = 377. ✅` produced two findings naming both wrong operands
("starts from 364, but the bullet states 366"; "totals 377, but the bullet
states 379"), and reverting returned the scan to clean.
