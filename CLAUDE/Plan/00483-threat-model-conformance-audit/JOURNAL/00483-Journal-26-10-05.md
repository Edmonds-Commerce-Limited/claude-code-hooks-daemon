# Plan 00483 — Journal 26-10-05

_Scaffolded by `mkplan.bash`; timestamps in this file are UTC._

> **Append-only activity log** for plan 00483. One file per day
> (`00483-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM, ONLY with
> `mkplan.bash --journal <plan-number> <category> <body-file>` (it stamps the
> real UTC time; a hand-written entry is denied); NEVER edit earlier entries
> (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff` | `correction`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - A `correction` corrects an earlier entry without touching it. Its `REF`
>   (`--ref`, required) names that entry: `HH:MM` in this file, or
>   `YY-MM-DD/HH:MM` in an earlier one. An entry a correction names in this
>   file no longer counts for time order, so a future-dated stamp can be
>   corrected at the honest time.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 21:10 · decision · —   — Task 2.2: owner ruling A6 implemented

Task 2.2 implemented from owner ruling A6.

Where each row went:

- `git push --delete` / `-d` / `git push <remote> :<name>`: an extra pattern in `destructive_git` (index-aligned rule id R-GIT-PUSH-DELETE-REMOTE), scoped to the push segment like the force-push pattern and judged on the whitespace-delimited token, so a branch named `my-delete-branch` or `main:feature` is untouched. Its own verbose text says to stop and ask the human; no hatch.
- `docker run -v /:/host`, `gh auth token`, a non-PyPI pip index, `crontab -r`: one new handler, `host_command_guard` (priority 10, on by default), because no existing handler fits and one handler beats four. It reads commands with the shared `simple_commands` reader and judges only the program in command position, past assignments and wrappers (`peel_command_wrappers`), so `echo 'crontab -r'`, a commit message and a grep pattern are data.
- Allowed rows (`git tag -d`, `git reset --keep`, `truncate -s 0`, `rm -rf`): no code; pinned as allowed in unit tests, the ordinary-command gate (`a6-` ids) and the dangerous-invocation corpus (UNCOVERED-accepted).

Decisions the ruling left open:

- PyPI means `https://pypi.org/...` or `https://files.pythonhosted.org/...` and nothing else. `test.pypi.org`, plain `http://`, `file://` and a lookalike host such as `pypi.org.example` are not PyPI. A value with `$` or a backtick is allowed (unreadable, owner ruling A1).
- `gh auth token` piped on or substituted into another command (`| docker login --password-stdin`, `TOKEN=$(gh auth token)`) is allowed, because the ruling's reason is the transcript. Inside `echo`/`printf` it is denied. A redirect to a file is not visible to the reader and is denied.
- Docker: `-v`, `--volume` and `--mount` after `run`/`create` (also `container run`); host root is a source of `/` or `//` with a target, so `-v /data` (an anonymous volume) and `-v /` are not findings.
- `pip install` only; `pip download`, `pip config` and `uv pip` are not covered.

Corpus: the nine UNCOVERED-open rows are now five COVERED and four UNCOVERED-accepted.
