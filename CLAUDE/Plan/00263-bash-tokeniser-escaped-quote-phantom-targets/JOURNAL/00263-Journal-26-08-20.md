## 15:10 · finding · P1 — the filed diagnosis was wrong; measurement corrected it

Before writing tests I ran eight candidate shapes through a real `bash` in a
sandbox and diffed what it WROTE against what the accessor PREDICTED. Three
claims in the filed plan did not survive.

Takeaway: five overclaiming shapes, not one, and the stated discriminator was
the wrong variable.

```
=== [OVERCLAIM] escaped-quote json payload, path followed by space
    phantom : ['phantom.py']
=== [OVERCLAIM] escaped-quote json payload, path at end of value
    phantom : ['phantom.py\\"}']
=== [ok]        multi-line double-quoted arg mentioning a redirect
=== [ok]        multi-line double-quoted arg with escaped quotes
=== [OVERCLAIM] escaped quote then tee
    phantom : ['loudly', 'phantom.py\\']
=== [OVERCLAIM] escaped quote then cp
    phantom : ['next']
=== [OVERCLAIM] backslash-escaped space in a real path
    phantom : ['sp\\']
    missed  : ['sp ace.txt']
```

1. **Line breaks are irrelevant.** The plan said the damaging shape needed a
   line break inside the quoted argument and that the single-line variant was
   inert. Both multi-line shapes came back clean, and a single-line one produced
   the clean phantom. The real discriminator is only whether the phantom token
   happens to be followed by whitespace.
2. **Not just redirects.** Once the quote breaks, `tee` and the copy verbs
   consume trailing operands, so prose words become "written files" — `loudly`
   is an adverb, `next` a preposition. These are *worse* than a malformed path,
   because `Path.exists()` filters the malformed one and may not filter these.
3. **Both failure directions, one defect.** `> sp\ ace.txt` overclaimed the
   fragment `sp\` AND missed `sp ace.txt`, which bash really wrote.

The filed diagnosis was an inference from two hand-built examples. Recording the
correction in `PLAN.md` rather than silently replacing the table — the point of
the differential harness is that the shell settles these questions, and it did.

## 15:20 · decision · T2.1 — `posix=True` over targeted pre-processing

The plan left this open, warning that POSIX mode changes token content (strips
quotes, processes escapes) and would ripple into `_write_target_tokens`. It
does, and the ripple is an improvement rather than a cost:

- POSIX mode is what bash itself does with `\"`, so the fix is "parse the shell
  correctly" rather than "special-case the shape that bit us". The alternative
  meant hand-rolling escape rules `shlex` already implements.
- Quotes now arrive stripped by the lexer, which knows which ones were syntax.
  That made the `strip("'\"")` in `_resolve_write_target` redundant AND latently
  wrong — it would corrupt a path whose name genuinely contains a quote — so it
  was removed (T2.3) rather than left as harmless-looking dead defence.
- Comparisons like `token == "tee"` get *more* correct, since a quoted `"tee"`
  no longer fails to match.

One behaviour is traded away, in the fail-safe direction: POSIX mode rejects a
trailing lone backslash ("No escaped character") where non-POSIX tolerated it,
so such a segment yields no targets instead of a wrong one. That command is
unterminated to bash as well. Recorded in the `_tokenise` docstring rather than
left for someone to rediscover.
