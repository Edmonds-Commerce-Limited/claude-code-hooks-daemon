## 15:53 · finding · P3 — what the dogfood actually exposed

The runbook was written from design, then run against the live backlog. Four
of its rules exist because the run found them, not because they seemed wise.
Recording the evidence so nobody later "simplifies" them back out.

**#14 — work that was already done and deliberately REVERTED.** The body
carries a detailed, plausible "Proposed Solution" with config examples. The
comment thread says it was implemented (Plan 00019, merged `915aa4c`) and then
REMOVED (`a3b5035`), because Claude Code's hooks expose no way to tell which
agent fired a `PreToolUse` event, so enabling it blocked every agent equally
and made agent teams unusable.

A loop reading only the body would have re-implemented a handler this project
chose to delete. That is the single most damaging thing this loop could do, and
nothing in the original design prevented it. Hence check 1, and the new
`blocked on upstream/external` outcome — no work here clears that blocker.

**#22 / #23 / #32 — a stale report, and a remediation that would now hurt.**
#22 and #23 report that SessionStart handler output never reaches the model.
It reached the model in the session that triaged them: this agent received the
repo's dogfooding advisory and `tool_disable_advisor`'s output as `SessionStart
hook additional context`. Both are SessionStart handlers.

The dangerous part is #32, which proposes the REMEDIATION — reframe SessionStart
messages as human-only "because the LLM ignores them". Acting on that today
would rewrite guidance the agent demonstrably does read into a form addressed
only to humans. A loop processing issues oldest-first, one at a time, would
have hit #32 with no idea #22 had just been contradicted by evidence.

So: re-verify old reports against current behaviour, and triage interacting
issues as a cluster. Neither rule was in the first draft.

**#34 — half the report had already shipped.** It made two suggestions. The
second (a declarable source-root → test-root mapping) exists as
`test_path_map`, and the handler's own guidance uses the reporter's exact
`qaConfig/Tests` layout as its worked example. The first (casing) is still a
real defect: `_TEST_DIR = "tests"` is hardcoded lowercase.

Treating an issue as one indivisible unit would have got this wrong in either
direction — closing it as done, or rebuilding something that exists.

**#30 / #31 — the clean case.** Genuine duplicates, same title two hours apart.
Closed the thinner one (1681 chars) in favour of the fuller (2961). This is the
only branch where the loop acted decisively and irreversibly, and it is the
branch where certainty was highest.

## 16:54 · finding · P1 — I shipped a red tree twice, and neither was caught by me

Both Phase 1 defects were found by someone else's run, not mine, and they share
one cause.

1. `persistent_cron_assertor` was registered in `handlers/session_start/__init__.py`
   and `init_config.py` but not in `.claude/hooks-daemon.yaml.example`, failing
   `test_every_registered_handler_is_listed_for_its_event` and
   `test_example_config_includes_all_library_handlers`. Found by the issue-34
   sub-agent's regression sweep.
2. `handler._workspace_root = str(tmp_path)` in my own test is a pyright error:
   the handler reads that attribute via `getattr` and never declares it. Found
   by the worktree's full QA run.

I ran the handler's own tests and the guidance-coverage suite before pushing
Phase 1. Neither runs pyright, and neither reads the reference config. A
targeted run answers "does my change work"; only the full suite answers "did my
change break something else" — and a newly REGISTERED handler is precisely the
change whose blast radius lies entirely outside the files it touches.

The reference-config test exists to catch exactly this, so the gate worked and
I pushed past it by not running it.

## 16:54 · finding · P3 — the full SDLC, end to end on a real issue

#34 went the whole way: triage → dedupe scout → worktree → sub-agent → QA →
review → merge → CI → comment → close. Four things are worth keeping.

**The sub-agent disagreed with my brief, twice, and was right both times.**
I proposed rewriting finished `Path` objects to swap the `tests` segment; it
pointed out that post-hoc surgery picks the wrong segment for a repo checked
out under a directory literally named `tests`, and parametrised the three
mappers instead. It also reported that "all existing tests still pass" was not
achievable as I had stated it, because one of them was pinning the defect.
Briefing a sub-agent with explicit permission to disagree is now in the runbook
because of this.

**The fix was smaller than the report asked for, and better.** The reporter
asked for casing support AND a declarable mapping. The mapping already existed;
and once the casing was fixed, their exact layout resolves with no declaration
at all. They never needed config — they needed the other casing.

**`QA_EXIT` earned its place in the runbook.** The worktree QA run reported
wrapper exit 0 while `QA_EXIT=1` and 3/29 failing. Reading the wrapper's status
would have merged a red tree.

**A `cancelled` CI run is not a failure.** The first watch returned
`completed cancelled` because a later push superseded it. The runbook already
said to re-check the newer run, which is what made that a non-event.
