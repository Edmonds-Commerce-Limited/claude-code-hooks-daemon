## 15:55 · finding · T1.1 — why ruff sees the file at all

Built the client fixture (`scripts/dummy-client-repo.sh create`, production
installer, isolated hostname; its own daemon came up RUNNING). The installer
writes:

```
# Claude Code Hooks Daemon
.claude/hooks-daemon/
.CLAUDE.md.pre-inject
```

Ruff respects `.gitignore` by default, so **nobody ever wrote the vendor
exclusion** — git did it. `install/ccy_supervisor.py::_ensure_ccy_gitignore_allows()`
then whitelists `!claude-supervise.py` back out of the ccy ignore so the file
can be committed (Plan 00147/00148 intent). That single act is what puts
daemon-owned source into every Python tool's discovery.

Which also kills option (b): a symlink into the git-ignored vendor dir dangles
for every teammate who clones, breaks the launcher `exec`, makes
`ccy_supervisor_integrity`'s "not executable → chmod +x" advice wrong, and
permanently disables Plan 00164 stale detection (a symlinked file can never
diverge from the fingerprint it is compared against).

## 16:05 · decision · T1.3 — chose (c), upgraded; considered and rejected a rename

Own proposal (e): deploy as extensionless `claude-supervise`, the Unix
convention for an executable program, which leaves ruff/black/mypy/flake8/pylint
discovery in one tool-agnostic move. Rejected: `_arm_ccy_supervisor()` never
overwrites an existing `CCY_CLAUDE_WRAPPER` and `_is_armed()` matches the
literal `claude-supervise.py`, so armed clients would point at a filename we
stopped deploying. The reporter's own `ccy.env` is hand-edited to `--dry-run`,
so a "rewrite only lines we generated" migration would not match it — the
rename bricks the client who filed the report. That was the deciding fact.

Also noted but NOT acted on: the committed copy may be redundant altogether —
a teammate with the daemon gets it deployed by their own install/upgrade, and a
teammate without the daemon has no context sidecar for it to read. Unwinding
the gitignore whitelist would reverse two completed plans and invert
`ccy_supervisor_integrity`'s git-ignored check, on the strength of an inference
about ccy workflows I cannot verify from here. Recording it as a question for
the humans rather than implementing it.

Chosen: banner in the deployed artifact + one manifest of daemon-owned assets
deployed into client space + a guard that each stays clean under its language's
DEFAULT rule set. Five such assets exist (31 hook forwarders, 6 skill scripts,
`mkplan.bash`, `bin/hooks-daemon`, the supervisor); all measure clean today and
nothing asserted that.
