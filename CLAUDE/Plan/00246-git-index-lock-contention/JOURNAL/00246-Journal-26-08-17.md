## How this plan came to exist

A dogfooding report: the daemon's CLAUDE.md auto-commit is causing stale
`.git/index.lock` problems, and the question asked was whether something funny is
going on in how the auto-commit is done.

Worth noting that I had hit the same symptom earlier in this session — a 0-byte
`.git/index.lock`, ~11 minutes old, with `pgrep -cx git` returning 0 — and
treated it as a one-off stale file to remove rather than a signal. The report is
what turned it into an investigation.

## What the investigation found

The auto-commit is real but the smallest of three paths.

### The proof that matters

`git status` is not a read. It refreshes the index and writes it back, taking
`.git/index.lock`. Rather than assert that from memory I proved it in a throwaway
repo: `touch` the tracked file to make the cached stat info stale, record
`.git/index` inode+mtime, run `git status --porcelain f.txt` exactly as the
injector runs it, compare.

    git status, as the injector runs it: index REWRITTEN -> it took index.lock
    git status, GIT_OPTIONAL_LOCKS=0:    index NOT rewritten

git 2.39.5. `GIT_OPTIONAL_LOCKS` appears **zero** times across `src/` and
`scripts/`.

### Three paths, ordered by how often they fire

Startup frequency is not the driver. `git_context_injector` takes the lock on
every user prompt and `git_branch` on every status refresh; the auto-commit only
fires per daemon start. The report blamed the auto-commit because that is the one
that leaves a *stale* file — it is the only one holding the lock long enough, and
across a `git add` plus a `git commit`, to be caught mid-flight.

### The auto-commit's own defects

Four, all in `_auto_commit_if_dirty`:

1. `git add` before `git commit --only <file>` is redundant — `--only` already
   scopes the commit to that path irrespective of the index. A second lock
   acquisition for nothing.
2. No `timeout=` on any of the four subprocess calls. Grep count: 0. Every other
   git caller in `src/` uses the `Timeout` constants, so this is the odd one out
   rather than a house style.
3. Failures logged at `debug`, so contention never surfaces.
4. It runs synchronously inside `DaemonController.__init__` — the startup path —
   and restart is mandated after every handler change, which is exactly when an
   agent is also running git in the same tree.

### The structural finding

`utils/git_repo.py` (Plan 00113) already declares the fix: *"new git operations
are added as methods on `GitRepo`, not by re-implementing
`subprocess.run(["git", ...])` in each caller"*. Fifteen files bypass it, across
~30 call sites. Had the principle held, both the env var and the timeout would be
one line in one place. The declared architecture was right and unenforced — which
is why Phase 3 (the guard) is the actual deliverable and the migration is a
consequence of it, not the point.

## A hypothesis that did not survive

First guess for the stale file was the container single-daemon enforcement
SIGKILLing a daemon mid-`git add`. Checked: `process_verification.py` and
`cli.py` both signal a single pid, not a process group, so a `git` child outlives
the daemon and cleans up its own lock. Not impossible via some other
process-group kill, but not demonstrated — so the plan claims contention (proven)
and does not claim to have identified which process orphaned the lock I saw.

## Phases 1 and 2 — what actually got fixed

`run_git` in `utils/git_repo.py` is now the single spawn point, setting
`GIT_OPTIONAL_LOCKS=0` and a timeout by construction. All three paths route
through it.

Verified on the REAL repository rather than only in tests, through the production
hook wrappers: a daemon restart rewrites `.git/index` zero times, and so does a
status render plus a user prompt driven through `.claude/hooks/status` and
`.claude/hooks/user-prompt-submit`. No lock left behind in either case.

### Two assumptions that testing overturned

1. **"The `git add` is redundant."** Filed as fact, from reading what `--only`
   does. `commit --only` on an UNTRACKED path fails outright, so the call is
   load-bearing on first install. Deleting it would have silently stopped
   committing a brand-new CLAUDE.md — and no existing test would have caught it,
   because every fixture commits a CLAUDE.md before exercising the injector. It
   is now gated on the porcelain `??` prefix, and the untracked case has a test.
2. **"A read-only runner must refuse write verbs."** The premise was that
   `GIT_OPTIONAL_LOCKS=0` might be unsafe on a write. It is not — `add`,
   `commit`, `commit --only` and `config --local` all behave normally with it
   exported. Verb classification was also unsound (`config --get` reads,
   `config k v` writes), so dropping it deleted a risk rather than mitigating
   one.

Both were caught the same way: running the thing instead of reasoning about the
documentation. Worth recording because the first one was already written into a
tracked plan as an assertion.

### An own goal avoided

Adding a timeout to the commit is not free: `subprocess` KILLS the child when a
timeout expires, and git killed mid-commit is exactly how `.git/index.lock` gets
orphaned. A tight bound would have manufactured the reported symptom while
claiming to fix it. Hence `Timeout.GIT_COMMIT = 30`, deliberately generous, with
the reasoning recorded at the constant.

### A test-authoring trap, now closed centrally

Every "took no lock" assertion is vacuous unless the index is stale first: if git
has no reason to refresh, "not rewritten" is true of any implementation. That is
invisible in a passing test. It now lives in one place — the `GitIndexWatch`
fixture in `tests/conftest.py`, whose `expect_none`/`expect_one` pair makes the
index stale on entry — so a future test cannot forget it. Every `expect_none` in
this plan is paired with an `expect_one` control on bare git.

### A self-inflicted detour

The first per-prompt test failed with `tmp_path` arriving as a MagicMock. The
cause was my own edit: the insertion point sat directly beneath a
`@_MOCK_PROJECT_ROOT` class decorator, so the new class inherited it (and the
class it belonged to lost it). `patch` used on a class injects the mock as the
first positional argument, which pytest then filled `tmp_path` with. Recorded
because the symptom pointed nowhere near the cause, and I spent several tool
calls hunting a phantom fixture override before reading the file.

## Phase 3 — the guard, and what it cannot see

The guard is `tests/integration/test_git_spawns_are_bounded.py`: an AST scan for
a `subprocess` spawn whose argv literal starts with `"git"`, anywhere under
`src/`, with an `_EXEMPT` dict whose VALUE is the reason, so an entry cannot be
added without justifying itself. It found 17 spawns across 10 files.

It carries two control tests. `assert violations == []` is indistinguishable from
the output of a scanner that silently matches nothing, so one control feeds it a
known offender and one feeds it a non-git subprocess.

### Scope checked rather than assumed

- **Shell side**: the guard only sees Python. Checked `init.sh`,
  `bin/hooks-daemon` and `scripts/*.sh` — the only `git status` is in
  `scripts/upgrade.sh`, a one-off human-initiated upgrade, not a hot path. So the
  `src/`-only scope is not hiding a live contention source.
- **Argv built in a variable** escapes the scan. Accepted deliberately, the same
  trade-off `check_magic_values.py` documents: a check that fires only on
  unambiguous shapes stays enabled; one that guesses gets disabled.

### The stale-exclusion guard earned its keep

Removing the now-dead `try/except` blocks made two entries in
`scripts/qa/error_hiding_exclusions.json` stale, and `test_audit_error_hiding.py`
failed naming both. One had genuinely been fixed (`git_branch._run_status`) and
was deleted. The other (`git_repo._git_output`) I first tried to REALIGN onto
`run_git`, and the test failed again — the auditor flags nothing there now,
because `run_git` reports the failure in its return value rather than swallowing
it, so the entry had to go entirely. Two attempts, and the guard was right both
times.

### A risk retired by measurement, not mitigation

The plan's highest-severity risk was that declining the refresh might change what
`git status` REPORTS — worse than the original bug, since a false "modified"
would make the daemon commit CLAUDE.md on every start. Measured across the three
shapes the daemon parses (stat-dirty-but-content-identical, genuinely modified,
and `--porcelain=v2 --branch` with an untracked file): byte-identical every time.
Git still does the comparison in memory; the variable only stops it PERSISTING
the refreshed index.

## The migration — delegated, and why that shape

Seventeen call sites across ten files is mechanical work with a single pattern,
so it went to three parallel `python-developer` agents split by directory. Each
was given the same explicit contract for `run_git` (it already prepends
`git -C <cwd>`; it runs in TEXT mode so drop `.decode()`; it never raises so the
`try/except` around the spawn becomes dead code; `env=` ADDS rather than
replaces) plus hard rules: no git commands, no commits, no daemon restart.

Withholding git from them was deliberate and slightly funny given the subject:
peers sharing one `.git/index` is exactly the contention this plan is about, and
`agent_isolation_advisor` warns about it. Only the main thread commits.

Two things went right that are worth naming:

- The `project_context.py` migration is the one I flagged as risky, because it
  bootstraps before most of the package. The agent used a DEFERRED import inside
  the function and documented the cycle it avoids, matching the existing comment
  two functions above. That was the correct call, unprompted.
- `git_branch.py` carries tests asserting exact `subprocess.run` call COUNTS and
  `side_effect` ORDER (Plan 00238 tuned this handler from 192 spawns per 115
  renders down to 44). It came back 419 passed with those assertions intact.

`git_sync.py` turned out to hold a private `_run_git` that was a near-duplicate
of the real one, with a subtly different failure contract (None vs a non-zero
returncode) — the DRY violation this plan describes, in its most literal form.

## What the guard cost to satisfy, and what that says

Nine entries in `error_hiding_exclusions.json` went stale, because removing a
dead `try/except` removes the finding its exclusion covered. Every one was named
by `test_audit_error_hiding.py` with the right remediation, and one of them
corrected me mid-fix: I tried to REALIGN the `git_repo` entry onto `run_git`
rather than delete it, and the test failed again because the auditor flags
nothing there — `run_git` reports failure in its return value instead of
swallowing it, so there is no finding left to exclude.

That is two independent guards in this repo catching real drift caused by a fix,
within minutes, with actionable messages. Worth recording as evidence that the
DBF investment pays: the guards were not in the way of the work, they were the
only reason the work stayed correct.
