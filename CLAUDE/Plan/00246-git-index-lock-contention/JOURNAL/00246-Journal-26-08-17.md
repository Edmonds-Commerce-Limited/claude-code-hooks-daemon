## How this plan came to exist

A dogfooding report: the daemon's CLAUDE.md auto-commit is causing stale
`.git/index.lock` problems, and the question asked was whether something funny is
going on in how the auto-commit is done.

Worth noting that I had hit the same symptom earlier in this session — a 0-byte
`.git/index.lock`, ~11 minutes old, with `pgrep -cx git` returning 0 — and
treated it as a one-off stale file to remove rather than a signal. The report is
what turned it into an investigation.

## What the investigation found

The auto-commit is real but the smallest of three paths.

### The proof that matters

`git status` is not a read. It refreshes the index and writes it back, taking
`.git/index.lock`. Rather than assert that from memory I proved it in a throwaway
repo: `touch` the tracked file to make the cached stat info stale, record
`.git/index` inode+mtime, run `git status --porcelain f.txt` exactly as the
injector runs it, compare.

    git status, as the injector runs it: index REWRITTEN -> it took index.lock
    git status, GIT_OPTIONAL_LOCKS=0:    index NOT rewritten

git 2.39.5. `GIT_OPTIONAL_LOCKS` appears **zero** times across `src/` and
`scripts/`.

### Three paths, ordered by how often they fire

Startup frequency is not the driver. `git_context_injector` takes the lock on
every user prompt and `git_branch` on every status refresh; the auto-commit only
fires per daemon start. The report blamed the auto-commit because that is the one
that leaves a *stale* file — it is the only one holding the lock long enough, and
across a `git add` plus a `git commit`, to be caught mid-flight.

### The auto-commit's own defects

Four, all in `_auto_commit_if_dirty`:

1. `git add` before `git commit --only <file>` is redundant — `--only` already
   scopes the commit to that path irrespective of the index. A second lock
   acquisition for nothing.
2. No `timeout=` on any of the four subprocess calls. Grep count: 0. Every other
   git caller in `src/` uses the `Timeout` constants, so this is the odd one out
   rather than a house style.
3. Failures logged at `debug`, so contention never surfaces.
4. It runs synchronously inside `DaemonController.__init__` — the startup path —
   and restart is mandated after every handler change, which is exactly when an
   agent is also running git in the same tree.

### The structural finding

`utils/git_repo.py` (Plan 00113) already declares the fix: *"new git operations
are added as methods on `GitRepo`, not by re-implementing
`subprocess.run(["git", ...])` in each caller"*. Fifteen files bypass it, across
~30 call sites. Had the principle held, both the env var and the timeout would be
one line in one place. The declared architecture was right and unenforced — which
is why Phase 3 (the guard) is the actual deliverable and the migration is a
consequence of it, not the point.

## A hypothesis that did not survive

First guess for the stale file was the container single-daemon enforcement
SIGKILLing a daemon mid-`git add`. Checked: `process_verification.py` and
`cli.py` both signal a single pid, not a process group, so a `git` child outlives
the daemon and cleans up its own lock. Not impossible via some other
process-group kill, but not demonstrated — so the plan claims contention (proven)
and does not claim to have identified which process orphaned the lock I saw.
