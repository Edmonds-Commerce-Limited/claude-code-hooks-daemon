## 11:06 · finding · T2.1 — the contract already answers it, and names a trap

Starting the dogfooding from what is already written down rather than
capturing blind. `contracts/claude-code-hooks/Stop.json` records:

```
agent_id:   Present ONLY when the hook fires inside a subagent call. A
            main-thread Stop carries no agent identity, which is what makes
            its ABSENCE the usable signal.
agent_type: Present when the session uses --agent or the hook fires inside a
            subagent. Note a session-wide --agent makes this present on a
            MAIN-THREAD stop too, so agent_type alone does not mean 'in a
            subagent' -- agent_id does.
```

Two things follow:

1. The discriminator is the ABSENCE of `agent_id`, not its value. Any
   implementation that tests truthiness of `agent_type` is wrong.
2. `agent_type` is a live trap, not a theoretical one: a session started with
   `--agent` sets it on the MAIN thread, so a handler keying on it would treat
   the coordinator as a subagent and suppress exactly the nudges this plan
   exists to keep firing on the main thread.

**This is documentation, not yet a measurement.** It is the right starting
point but does not discharge the owner's condition: the next step is capturing
real Stop and SubagentStop payloads and confirming the absence/presence split
holds at the moment the handlers actually run. A contract can be stale in the
same way the examples in issue #44 were.

## 11:09 · finding · — — the payload carries `effort`, which closes N7's class

Unplanned, and it belongs to niggle N7 rather than to this plan, so it is
recorded here only as provenance and copied there.

N7 says the supervisor's effort floor cannot see an effort set from Claude
Code's own selector, because a bare `/effort` names nothing its stdin tap can
read. The captured payload carries:

```
"effort": {"level": "medium"}
```

The daemon is handed the EFFECTIVE effort level on every Stop/SubagentStop,
regardless of how it was set. That is a remedy N7 never considered — it reads
the state rather than trying to observe the act of setting it, so the selector
path and the typed-argument path become indistinguishable, which is exactly
what "closes the class rather than the instance" means there.

## 11:16 · finding · T2.1 — MEASURED both halves; the condition is discharged

The main-thread `Stop` could not be produced on demand, so it was captured by
stopping. Both halves now measured from real payloads in this session:

```
=== every SubagentStop row (5) ===
agent_id_present=true   agent_id_len=17
agent_id_present=true   agent_id_len=17
agent_id_present=true   agent_id_len=17
agent_id_present=true   agent_id_len=17
agent_id_present=true   agent_id_len=17

=== every Stop row (1, main thread) ===
agent_id_present=false  agent_type_present=false
```

**The contract holds.** `agent_id` is present in every subagent stop and absent
on the main thread, so its ABSENCE is a sound MAIN discriminator. The owner's
condition — dogfood it, do not assume it — is discharged for this case.

**And the measurement found something the contract does not say.**
`agent_type` is present but EMPTY in 4 of the 5 subagent stops:

```
has_agent_type=true  value="general-purpose"
has_agent_type=true  value=""
has_agent_type=true  value=""
has_agent_type=true  value=""
has_agent_type=true  value=""
```

Only the plain `general-purpose` dispatch carried a type; the named and
worktree-isolated agents did not. So `agent_type` is worse than the contract's
warning suggested. The contract says it over-reports (present on a main-thread
stop under a session-wide `--agent`); measurement says it ALSO under-reports,
empty for most real subagents here. A handler keying on its truthiness would
have misclassified **4 of 5** subagents as main-thread — failing in the
direction that fires nudges where they were meant to be suppressed.

`agent_id` was a 17-character string in all five, never empty.

**Limit of this measurement, stated rather than glossed**: the one case NOT
covered is a session started with `--agent`, where the contract says
`agent_type` appears on a MAIN-thread stop. That needs a differently-launched
session and cannot be produced from inside this one. It does not affect the
conclusion — the discriminator is `agent_id`, and nothing here reads
`agent_type` — but the `--agent` main-thread case remains unverified by direct
observation, and Task 3.1 must not quietly assume it.

## 11:20 · finding · P3 — a synthetic event is indistinguishable from main-thread

Before building Phase 3, read the prior art:
`.claude/project-handlers/pre_tool_use/orchestrator_simulate.py` has been
discriminating on `agent_id` in simulate mode for a while, and it guards
something this plan had not recorded.

The acceptance playbook FABRICATES hook events, and a fabricated event carries
no `agent_id` — so it looks exactly like a main-thread call. That handler
checks `is_synthetic_event()` (`daemon/synthetic_traffic.py`) and its docstring
says what happens without it: the suite goes red "with hundreds of denied
probes AND, under most-restrictive-wins, other handlers' expected ALLOWs turned
into failures — on the day blocking was first enabled".

A `scope: MAIN` handler inherits that failure mode exactly, because `MAIN` is
the same predicate. So **`MAIN` cannot mean "no `agent_id`"; it must mean "no
`agent_id` AND not synthetic"**. Recorded in PLAN.md Phase 3 with a required
test that fabricates an event.

This is the cheap kind of finding — it cost one read of an existing handler and
would otherwise have surfaced as a broad, confusing QA failure on the day the
key shipped, in tests that have nothing to do with scope.
