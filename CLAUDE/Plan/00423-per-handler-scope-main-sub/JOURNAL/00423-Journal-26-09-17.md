## 11:06 · finding · T2.1 — the contract already answers it, and names a trap

Starting the dogfooding from what is already written down rather than
capturing blind. `contracts/claude-code-hooks/Stop.json` records:

```
agent_id:   Present ONLY when the hook fires inside a subagent call. A
            main-thread Stop carries no agent identity, which is what makes
            its ABSENCE the usable signal.
agent_type: Present when the session uses --agent or the hook fires inside a
            subagent. Note a session-wide --agent makes this present on a
            MAIN-THREAD stop too, so agent_type alone does not mean 'in a
            subagent' -- agent_id does.
```

Two things follow:

1. The discriminator is the ABSENCE of `agent_id`, not its value. Any
   implementation that tests truthiness of `agent_type` is wrong.
2. `agent_type` is a live trap, not a theoretical one: a session started with
   `--agent` sets it on the MAIN thread, so a handler keying on it would treat
   the coordinator as a subagent and suppress exactly the nudges this plan
   exists to keep firing on the main thread.

**This is documentation, not yet a measurement.** It is the right starting
point but does not discharge the owner's condition: the next step is capturing
real Stop and SubagentStop payloads and confirming the absence/presence split
holds at the moment the handlers actually run. A contract can be stale in the
same way the examples in issue #44 were.

## 11:16 · finding · T2.1 — MEASURED both halves; the condition is discharged

The main-thread `Stop` could not be produced on demand, so it was captured by

```

**The contract holds.** `agent_id` is present in every subagent stop and absent
on the main thread, so its ABSENCE is a sound MAIN discriminator. The owner's
condition — dogfood it, do not assume it — is discharged for this case.

**And the measurement found something the contract does not say.**
`agent_type` is present but EMPTY in 4 of the 5 subagent stops:

```
has_agent_type=true  value="general-purpose"
has_agent_type=true  value=""
has_agent_type=true  value=""
has_agent_type=true  value=""
has_agent_type=true  value=""
```

Only the plain `general-purpose` dispatch carried a type; the named and
worktree-isolated agents did not. So `agent_type` is worse than the contract's
warning suggested. The contract says it over-reports (present on a main-thread
stop under a session-wide `--agent`); measurement says it ALSO under-reports,
empty for most real subagents here. A handler keying on its truthiness would
have misclassified **4 of 5** subagents as main-thread — failing in the
direction that fires nudges where they were meant to be suppressed.

`agent_id` was a 17-character string in all five, never empty.

**Limit of this measurement, stated rather than glossed**: the one case NOT
covered is a session started with `--agent`, where the contract says
`agent_type` appears on a MAIN-thread stop. That needs a differently-launched
session and cannot be produced from inside this one. It does not affect the
conclusion — the discriminator is `agent_id`, and nothing here reads
`agent_type` — but the `--agent` main-thread case remains unverified by direct
observation, and Task 3.1 must not quietly assume it.

## 11:20 · finding · P3 — a synthetic event is indistinguishable from main-thread

Before building Phase 3, read the prior art:
`.claude/project-handlers/pre_tool_use/orchestrator_simulate.py` has been
discriminating on `agent_id` in simulate mode for a while, and it guards
something this plan had not recorded.

The acceptance playbook FABRICATES hook events, and a fabricated event carries
no `agent_id` — so it looks exactly like a main-thread call. That handler
checks `is_synthetic_event()` (`daemon/synthetic_traffic.py`) and its docstring
says what happens without it: the suite goes red "with hundreds of denied
probes AND, under most-restrictive-wins, other handlers' expected ALLOWs turned
into failures — on the day blocking was first enabled".

A `scope: MAIN` handler inherits that failure mode exactly, because `MAIN` is
the same predicate. So **`MAIN` cannot mean "no `agent_id`"; it must mean "no
`agent_id` AND not synthetic"**. Recorded in PLAN.md Phase 3 with a required
test that fabricates an event.

This is the cheap kind of finding — it cost one read of an existing handler and
would otherwise have surfaced as a broad, confusing QA failure on the day the
key shipped, in tests that have nothing to do with scope.

So 85 handlers need a real per-handler safety decision, not 142. The other 57

event whose contract has no `agent_id`, not accepted and quietly ignored —
a scope silently doing nothing is the same failure class as a guard that
matches nothing.

**A premise I could not confirm, and am recording rather than assuming
either way.** `auto_continue_stop` is registered on `Stop` alone (priority 10,
terminal); `SubagentStop` has a separate two-handler chain. That made me think
a subagent's stop can never reach it, which would make scoping it a no-op for
Agent-tool subagents. `Stop.json` says otherwise — `agent_id` is "present ONLY
when the hook fires inside a subagent call", which means a `Stop` CAN carry
one. Task 2.1's measurement saw exactly one `Stop`, main-thread, no `agent_id`:
consistent with both readings and decisive for neither. Not a blocker for
3.1 — the mechanism is worth having for the 79 PreToolUse/PostToolUse handlers
regardless — but #40's motivating symptom should not be cited as fixed by it
until a subagent-context `Stop` has actually been observed.

**Where the key lives.** `HandlerConfig` (`config/models.py`) already carries
`enabled`, `priority` and `options`; `scope` belongs beside them. The gate
cannot be applied at registration the way `enabled` is, because it depends on
the payload — it has to sit in `ChainExecutor.execute`, before
`handler.matches(hook_input)` (`core/chain.py:409`).

**The trap, from the plan and confirmed in the prior art.**
`orchestrator_simulate._would_deny` guards with `is_synthetic_event()` because
the acceptance playbook fabricates events with no `agent_id`, making them
indistinguishable from main-thread ones. `MAIN` must mean "no `agent_id` AND
not synthetic", with a test that fabricates one.

Phase 3's note says a `MAIN` handler inherits `orchestrator_simulate`'s failure
mode: a synthetic event carries no `agent_id`, so `MAIN` must mean "no
`agent_id` AND not synthetic" or the acceptance suite goes red. `scope_admits`
does exclude synthetic events — for `MAIN` and `SUB` alike — which raised the
opposite question: does that exclusion silently turn a DENY probe into an
ALLOW?

Measured rather than reasoned about. `daemon/playbook_harness.build_event`
stamps `SYNTHETIC_SOURCE_FIELD` on every probe, so the concern was real. But
partitioning this repository's own 351-block playbook reports 224 executable
and 127 skipped, and **all five** probes belonging to the three newly-scoped
handlers are in the skipped half:

```
SKIP: cron stop enforcer - blocks when session_crons is present but empty
      | Stop carries no tool call for a payload to drive
SKIP: cron stop enforcer - allows when session_crons is absent
SKIP: teammate reap advisor - reports the background_tasks count
SKIP: teammate reap advisor - silent when background_tasks is absent

The harness cannot dispatch a `Stop` probe at all. `tests/acceptance/test_playbook_harness.py`
is green (5 passed), and it is green for a reason that holds rather than by

That immunity is an accident of the event, though, and it does not extend to

## Task 3.2: coordinator-only failsafe-cron deletion

Two facts decided the shape, and both were measured before anything was
written.

**`PreToolUse` does fire for `CronDelete`.** Counting event/tool pairs in this
project's own `verdicts.jsonl`: 4 `PreToolUse`/`CronDelete` records (and 4
`PostToolUse`), alongside 16 `CronList` and 7 `CronCreate`. The mechanism is
real and the tool name is exactly `CronDelete`; it was not inferred from the
tool's existence.

**The rule has to be wider than "the failsafe cron".** `session_crons` is
delivered to `Stop`, not to `PreToolUse`, so at the moment a deletion is judged
the daemon holds an opaque cron id and nothing that maps it to a schedule or a
prompt. A handler claiming to protect one named cron would in fact be guessing
at which one it had. "A subagent deletes no cron" is the rule this event can
support, and it costs nothing real — a session cron belongs to the
coordinator's session, which is the session that created it. The deny reason
says this outright rather than letting a reader assume a precision the payload
does not carry.

`SubagentCronDeleteBlockerHandler` is therefore `scope=SUB`, `terminal=True`,
priority 14, on by default, and it **never reads `agent_id` itself** — the
scope key is the whole role test. A second copy of a safety rule drifts from
the first in exactly the direction nobody notices, the one where the guard
stops firing.

Its acceptance test declares `harness_cannot_produce` naming the synthetic
marker, and a unit test asserts that every acceptance test it returns does so.
The alternative was a probe that observes ALLOW forever and passes or fails for
reasons unrelated to the handler — a green run that means nothing, which is the
failure shape this plan's own Phase 3 note and three separate incidents earlier
in this work have already cost.

`test_handler_scope_defaults.py` had to be amended: `test_nothing_is_scoped_to_sub`
was true when it was written and is now false. That is the test working — the
set is exact so that adding to it is a deliberate edit with a justification
beside it, and the justification is that `PreToolUse` reaches both roles. The
line it draws: `SUB` is for a handler on an event BOTH roles reach, never for a
`SubagentStop` handler where it would be true but redundant.
