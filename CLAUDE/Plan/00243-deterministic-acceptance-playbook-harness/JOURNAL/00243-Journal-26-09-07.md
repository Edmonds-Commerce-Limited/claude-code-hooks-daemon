## 21:50 · decision · T1.2/T1.3 — the plan's task order was backwards

Task 1.2 says "convert to a literal command every prose test that can be one —
the Write/Edit tests are the bulk". Attempting it first would have been wrong,
and the reason is this project's own rule.

A file written through **Bash** bypasses the content guards that run BEFORE a
`Write`. That is the documented behaviour of `error_hiding_blocker`,
`qa_suppression`, `security_antipattern`, `comment_changelog` and
`sensitive_content` — they key on the `Write`/`Edit` tools, so a `>`, `tee` or
heredoc reaches disk unexamined. So converting

    Use the Write tool to create /repo/x.py with content '<guarded content>'

into

    echo '<guarded content>' > /repo/x.py

does not produce a harness-executable version of that test. It produces a test
that asserts DENY against a path the handler deliberately does not judge — a
guaranteed failure, asserting the opposite of the handler's contract.

The audit already pointed here: its bottom line calls the structured field
"Task 1.3's instinct is correct". So Task 1.3 shipped first, and Task 1.2 is
re-scoped from "regex prose into shell" to "populate the declared field".

## 21:56 · decision · T1.3 — mutual exclusion rather than a precedence rule

`harness_cannot_produce` and `tool_payload` could have been given a precedence
("skip wins"), which is what `_skip_block` does for its two skip reasons. They
are not analogous. Those two are both reasons NOT to run, and one genuinely
dominates — no tool install makes an unproducible test runnable.

These two point in opposite directions: one says the input cannot be produced
at all, the other says exactly how to produce it. There is no correct
precedence because one of them is simply false whenever both are set. So
`__post_init__` raises. A silent precedence would have let the wrong one sit
in the tree indefinitely.

## 22:10 · decision · T1.2 — render the prose FROM the payload, not beside it

The audit counted five grammars for one Write payload and framed Task 1.2 as
normalising them. Converting 125 sites by hand would have written the payload
AND a sentence at each one — which is what created five grammars in the first
place, just with a sixth added.

So `ToolPayload.as_instruction()` renders the sentence from the payload. A site
states the payload once; the prose is derived. The two cannot disagree, because
there is no longer a second copy to disagree with.

Arguments are sorted on the way out. Without that, dict insertion order would
let the same probe written by two authors render two ways — reintroducing
exactly the variation being collapsed. Values go through `repr` so a newline
inside file content stays inside the sentence rather than splitting the
playbook's `**Command**` block in two.

## 22:14 · finding · T1.2 — the field ADDS a risk, in the opposite direction

Fifteen converted payloads targeted the real working tree —
`$CLAUDE_PROJECT_DIR/src/config.ts`, `tests/fixtures/`, a resolved
`/workspace/random-notes.md`.

Those paths were harmless as PROSE. A human tester reads "write to
`src/config.ts`" and balks, or quietly substitutes a scratch path. They are not
harmless as a declared payload, because a harness dispatches them verbatim.

And it bites exactly where it matters. These are DENY tests: in the healthy
case the handler blocks the write and nothing lands. The case a deny test
exists for is the one where the handler has REGRESSED — and then the write
succeeds. The probe that catches a broken guard becomes the probe that drops a
credential-shaped string into `src/`, at the one moment nothing is there to
stop it.

Fixed as two invariants over the real generator rather than as fifteen edits,
because the edits do not stop the sixteenth: every declared write must land in
`untracked/scratch/`, and no payload may hardcode a resolved repo root.

## 22:18 · decision · T1.2 — two exemptions, each recorded with its reason

The scratch rule has two genuine exceptions, and they are opposite failures.

`ProjectContainmentHandler` denies writes OUTSIDE the repository, so a scratch
path cannot exercise it at all. `MarkdownOrganizationHandler` denies markdown
in an UNRECOGNISED location — and `untracked/` is a recognised one, so a
scratch path would leave that probe silently proving nothing.

Both are named individually in `_OUTSIDE_SCRATCH_BY_CONTRACT`, not
pattern-matched. An exemption that cannot be read off a list is one nobody
audits. The reason each is safe is recorded beside it: a stray
`random-notes.md` at the repo root carries no code and no credential and
`git status` names it immediately, which is categorically unlike a fake AWS key
appearing under `src/`.

## 22:22 · finding · T1.2 — a resolved project root is not a portable one

The agent converting `markdown_organization` correctly refused a scratch path

## 22:30 · finding · T1.2 — verifying the payloads found a Phase 2 requirement

A declared payload that does not actually trigger its handler is a test passing
for the wrong reason, so all 97 were dispatched in-process against their own
handlers. First run reported 29 failures. Twenty-nine was wrong.

Two artefacts of the checker, not defects in the payloads:

1. **ALLOW-by-not-matching read as failure.** A handler that correctly declines
   to match an allowed input returns no decision at all. Eighteen of the 29.
2. **PostToolUse handlers need the file to EXIST.** `lint_on_edit._is_lintable`
   ends with `Path(file_path).exists()` — load-bearing, and documented as such.
   A synthetic dispatch that never performs the write can never match it. Ten
   more, plus one `sensitive_content` probe that needs `public_patterns`
   configured, which the audit already flagged as borderline.

Corrected: **59 DENY confirmed, 27 ALLOW correct, 11 explained.** Zero payload
defects.

The correction is the useful output. Task 2.1's harness must expand
`$CLAUDE_PROJECT_DIR`, and must PERFORM the write before dispatching a
PostToolUse probe — otherwise it will report the same 10 lint tests as failures
on its first run, which is precisely the false-failure mode this plan exists to
avoid.

## 22:44 · finding · T2.1 — building the harness found two more of its own traps

The two requirements carried into Phase 2 were the ones Task 1.2 measured.
Building it surfaced two MORE, and both were invisible until the thing actually
ran — which is the argument for building the harness rather than reasoning
about it.

**A rejected event is not an allow.** The first run sent all 26 PostToolUse
probes without the `tool_response` that `POST_TOOL_USE_INPUT_SCHEMA` requires.
The daemon refused each event before any handler ran, and a refusal carries no
decision. Folded into "no decision means allow", every ALLOW probe passed while
testing precisely nothing, and only the DENY half complained — which reads like
a scatter of handler bugs rather than the one harness bug it was. `daemon_error`
now separates the two, because this is the failure mode that would have made
the whole gate ceremonial.

**A harness that only works once is worse than none.** With `session_id` fixed
per test number, `lsp_enforcement` — `block_once` by default — passed on the
first run and failed on the second, the daemon having already spent that
session's single block. Nobody re-reads a green harness, so this would have
surfaced as a mystery failure during a release. The session is now unique per
(run, probe): per probe because disclosure ladders would otherwise let one
probe mute another's message, per run because of this.

## 22:45 · decision · T2.3 — patterns are asserted on a deny, not on an allow

Task 2.3 asks for `expected_message_patterns` to be asserted so a deny for the
wrong reason stops passing. Applying it symmetrically to ALLOW probes would
have been wrong.

A deny always carries its own reason, so requiring the reason costs nothing and
catches exactly the defect named. An allow's patterns describe ADVISORY text,
and this project's handlers carry disclosure ladders that deliberately go terse
on a later fire. Asserting that text makes the verdict depend on session state
rather than on handler behaviour, and a harness that reports defects which are
not there is one nobody leaves switched on.

So the asymmetry is deliberate and recorded in `verdict`'s docstring rather
than left for a reader to infer from the code.

## 22:46 · finding · T2.1 — four real declaration defects, found by running them

Ten first-run mismatches survived the harness fixes. Three were genuine, and
none was reachable by reading the code:

- **Two `sensitive_content` payloads named a RELATIVE `file_path`**, so
  `absolute_path` denied the write before the handler under test was reached.
  The DENY one passed for the wrong reason and the ALLOW one failed outright.
  The scratch invariant could not see it, because `untracked/scratch/...`
  contains the marker whether or not it is rooted — so that invariant now has a
  sibling requiring absolute-or-`$CLAUDE_PROJECT_DIR`.
- **The Ansible lint test declared no `required_tools`** while every sibling
  strategy declares one. With no Ansible installed the strategy correctly
  declines to lint, and the probe reported a missing toolchain as a handler
  failure.
- **`plan_time_estimates` declared the pattern `time estimate`** against a
  message that opens "Time estimates not allowed". A human ticks that off
  without noticing; a case-sensitive regex cannot. `[Pp]lan` elsewhere in the
  same field shows the convention was always case-sensitive.

The fourth group was the PostToolUse deny SPELLING: one `Decision.DENY`
serialises as `permissionDecision: deny` on PreToolUse and `decision: block` on
PostToolUse, which the daemon's own `REFUSAL_CAPABLE_EVENTS` table records
against the same enum member. Normalising the two is correct rather than
lenient.

## 22:46 · decision · T2.4 — isolate the cwd even though it changes nothing

Measured both ways across all 94 probes: identical verdicts. The isolation is
kept anyway, which needs justifying since it is not fixing an observed failure.

Plan 00241's trap is silent by construction. A terminal handler shadowing a
probe can return the SAME decision the probe expected, so the substitution
leaves no trace in a pass/fail report — the probe goes green while testing a
different handler. That is not a risk a measurement showing "no difference
today" can retire, because the failure mode is precisely that it looks like no
difference. `release_blocker` matches on a modified release file whenever the
tree is dirty, which during a release it is by definition.
