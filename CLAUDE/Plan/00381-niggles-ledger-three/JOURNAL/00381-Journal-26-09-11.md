## 16:15 · finding · N1 — a test class that cannot pass alone

Found sideways, which is worth recording because it is how these usually
surface. While verifying Plan 00380 I narrowed a run with
`-k "worktree or cli"`; `cli` matched `TestFreshClientConfig` by substring, so
that class ran without its module siblings and
`test_transport_on_with_absent_binary_and_null_source_refuses_untouched`
failed.

My first instinct was that I had broken it, so I checked instead of assuming:

- the relay binary it depends on was built at 06:58, hours BEFORE the full QA
  run at 15:02 that passed 22,371 tests with zero failures — so its presence is
  not new and not mine;
- the whole module passes: 11/11;
- the class alone fails: 1 failed, 2 passed.

So it is neither my change nor flakiness — the class depends on state a sibling
leaves behind. These tests drive the real CLI, and `transport on` regenerates
forwarders and restarts the daemon, so the shared state is genuinely mutable.
Two runs gave two DIFFERENT failures from the same command — `assert 0 != 0` on
the return code, then `assert 'relay hot path' not in ...` on the generated
hook — which is the signature of reading whatever the previous test left rather
than a fixed missing precondition.

Recorded rather than fixed here: the suite as normally run is green, so this
costs nothing today. It costs the next person who runs a single failing class
while debugging — precisely when a misleading failure is most expensive.

## 16:34 · finding · N1 — the real mechanism, and why the first record was too shallow

"Depends on a sibling class" was true but unhelpful, and I went back for the
actual mechanism rather than leaving it.

The module-scoped `client_project` fixture seeds `relay_enabled: false` via
`_fixture_config`, then copies the forwarders from THIS repository's live
`.claude/hooks/` (line 160, deliberately "real deployed forwarders"). This repo
runs with `relay_enabled: true`, and its `pre-tool-use` forwarder carries the
relay hot path twice. So the fixture starts INTERNALLY INCONSISTENT — config
says relay off, forwarders say relay on.

`TestFreshClientConfig`'s first test then runs `transport off`, which reports
"already" (the config already says false) and regenerates nothing, so the
contradiction survives into the next test and its `assert "relay hot path" not
in ...` fails. The full module hides this because the earlier classes toggle
transport for real and regenerate the forwarders as a side effect.

The precondition is therefore the HOST repository's transport setting,
normalised incidentally by unrelated tests. On a checkout with
`relay_enabled: false` the class would pass alone. A fixture that inherits the
developing machine's mutable config is the defect; the ordering is just how it
shows.

Not fixed in this pass, and deliberately not rushed. The obvious repair —
making `transport off` reconcile drifted forwarders instead of short-circuiting
on "already" — is a change to production behaviour of a toggle, not a test fix,
and whether that gap matters outside the fixture is unverified. Recorded inside
N1 as the thing to check rather than asserted as a second entry, because this
ledger takes VERIFIED defects only.
