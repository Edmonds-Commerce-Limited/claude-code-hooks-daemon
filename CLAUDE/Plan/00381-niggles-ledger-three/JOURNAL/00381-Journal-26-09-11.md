## 16:15 · finding · N1 — a test class that cannot pass alone

Found sideways, which is worth recording because it is how these usually
surface. While verifying Plan 00380 I narrowed a run with
`-k "worktree or cli"`; `cli` matched `TestFreshClientConfig` by substring, so
that class ran without its module siblings and
`test_transport_on_with_absent_binary_and_null_source_refuses_untouched`
failed.

My first instinct was that I had broken it, so I checked instead of assuming:

- the relay binary it depends on was built at 06:58, hours BEFORE the full QA
  run at 15:02 that passed 22,371 tests with zero failures — so its presence is
  not new and not mine;
- the whole module passes: 11/11;
- the class alone fails: 1 failed, 2 passed.

So it is neither my change nor flakiness — the class depends on state a sibling
leaves behind. These tests drive the real CLI, and `transport on` regenerates
forwarders and restarts the daemon, so the shared state is genuinely mutable.
Two runs gave two DIFFERENT failures from the same command — `assert 0 != 0` on
the return code, then `assert 'relay hot path' not in ...` on the generated
hook — which is the signature of reading whatever the previous test left rather
than a fixed missing precondition.

Recorded rather than fixed here: the suite as normally run is green, so this
costs nothing today. It costs the next person who runs a single failing class
while debugging — precisely when a misleading failure is most expensive.
