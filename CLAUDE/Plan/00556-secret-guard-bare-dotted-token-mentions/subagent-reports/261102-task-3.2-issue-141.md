# Task 3.2 report: issue 141, awk operators read as writes

## Diagnosis

Fault 1 (awk): confirmed. `_AWK_WRITING_PROGRAM_RE = r">|\|&?|system\s*\("` matched any `>` and any `|` in the program, so `>=`, a comparison `>`, a regex alternation, `||` and a quoted `|` all counted as a write. Under a wildcard-only glob `_text_naming` returns the glob for any text, so the read-only awk was denied.

Fault 2 (`_text_naming` returns the glob when `_name_pattern` is None): confirmed from the code, NOT changed. It is the deliberate fail-closed answer for "unreadable text with a wildcard-only glob": once the awk check is exact, a real awk write with an unknown target must still deny through it. Narrowing it makes every fail-closed caller allow more and is an owner decision (N555 in Plan 00474). The heredoc/brace-enumeration fault (third) is likewise untouched: out of this brief's awk scope.

## Fix

`write_protected_paths.py`: the regex is replaced by `_awk_program_writes`. It blanks string literals, regex literals (a `/` after an opener such as `{ ( , ; ! ~ & | = < > ? :` or newline) and `#` comments, then denies if it finds:

- `system(`;
- a lone `|` or `|&` (print pipe, `cmd | getline`), but not `||`;
- inside a `print`/`printf` statement, a `>` or `>>` at paren depth 0 (not `>=`).

A `>` in a pattern, an `if (...)` or a parenthesised print is a comparison. An unterminated literal is blanked to the end (awk refuses to run it). `-i inplace` handling and shell redirects are unchanged code paths.
