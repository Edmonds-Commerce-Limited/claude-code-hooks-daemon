# Why the session-start relay repair left no state or log (read-only investigation)

Question from the peer: on the affected aarch64 box the status command shows the missing-binary WARNING, but there is no relay-repair state file, no relay log and no untracked/bin, although github.com is reachable.

What the code does, read in full (relay_binary_checker.py, relay_repair.py):

- `start_relay_repair` creates the state file FIRST (`O_EXCL` under `<untracked>/relay-repair/<key>.state`, `mkdir` included) and only then spawns. Every outcome after that is recorded: a spawn failure is written as `failed`, a pid-record failure is returned as a failure notice. An unwritable state directory is returned as a failure notice shown in the hook answer. So any call to `start_relay_repair` that reaches the claim leaves a state file, or a visible failure line. An absent state dir therefore means the handler never reached that call on this box.
- The untracked directory both the repair and the relay binary default path use is the same function (`get_untracked_dir`), so "state written to a different dir" would move `untracked/bin` the same way; it does not explain the absence by itself. It would, however, explain it if the box's daemon runs with a different project root (container path) than the one inspected.
- The status command's WARNING comes from `_print_transport_status_warnings` in the daemon CLI, which does not involve the checker, so the status warning is not evidence the checker ran.
- The checker returns silently (no warning, no repair) when `ProjectContext` is not initialised, when `.claude/hooks-daemon.yaml` is absent at the daemon's project root, or when the handler is not registered. It runs on SessionStart events only: a session whose SessionStart never reached the daemon (hooks not delivered, or delivered to a daemon of another root) never starts it.
- v3.74.0 contains the repair (`relay_repair.py` has been in every release since v3.71.0), so a version gap is ruled out.

Not reproduced: no combination in this checkout makes `start_relay_repair` skip its claim. The existing tests cover the claim, the once-per-cause rule, the spawn failure and the failed-record report.

Open question for whoever can reach the box: did a SessionStart event reach the daemon there at all (daemon log for `relay_binary_checker`, or `hooks-daemon probe` of the handler with a SessionStart payload), and which project root does that daemon report? If the daemon was started for a different root (a container mount), the state is under that root's untracked/, not the one that was listed.

No code change made for this: nothing reproduces, and adding speculative handling would hide the real cause.
