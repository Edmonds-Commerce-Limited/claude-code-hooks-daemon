## BLOCKER

### B1. A holder that has exited stays the holder: the crons are lost (confidence 90)

**Location:** `src/claude_code_hooks_daemon/utils/session_thread_group.py:193-218`
(`ThreadGroupRegistry.claim`) and `:274`.

`claim` returns any recorded holder unconditionally (`existing = holders.get(group.key)`,
`if existing is not None: return existing`). The holder is stored as a bare
`session_id`, with nothing that could be checked for liveness. Thread 1 can close
while thread 2 (or a thread opened later) lives on under the same
`claude daemon run`. In that case every remaining and future thread of the session
is exempt. The assertor tells each one "Create no CronCreate job for them here",
the Stop and SubagentStop enforcers never ask, and the session runs with no
declared crons until the front end exits. The registry is persisted, so a daemon
restart does not clear the stale holder either. The probe's `holder-exit` case
reproduces this through the real `CronStopEnforcerHandler`.

The same root cause covers `/clear` in the initial thread. It produces a new
`session_id` (SessionStart `source: clear`) in the same worker, and that session is
then exempted as a "later thread". Whether that is right depends on whether
session crons survive `/clear`, which no probe has established. Today the outcome
is an accident of keying on `session_id`.

**Fix:** store the holder as a live process, not a session id. The walk already
passes through it: the process directly below `claude daemon run` (the thread's
`bg-pty-host`) or the worker below that. Record `{holder_session, holder_pid,
holder_start_time}`. In `claim`, re-read `/proc/<holder_pid>/stat`. If it is gone
or its start time differs, the claimant takes over and is recorded as the new
holder (logged at INFO). Compare thread identity by worker pid+start time rather
than `session_id`, so a `/clear` in the holder's own worker stays the holder.
Add handler-level tests:
(a) holder's worker removed from the fake `/proc` -> the next thread's Stop is
DENY and the assertor states the jobs;
(b) a new `session_id` from the holder's own worker is still demanded.

### B2. "First `session_id` seen" is not "the initial thread", and the tests assume the order (confidence 75)

**Location:** `session_thread_group.py:263-274` (`initial_thread_holder_elsewhere`),
`tests/unit/handlers/test_initial_thread_only_crons.py:120` ("the initial thread is
seen first"), and the release note `004-...md`.

RESEARCH.md "Probe results (Task 6.3)", lines 230-233, says there is no
`claude daemon run` at all until a second thread is opened. "Once threads exist,
the first thread also runs as a worker (`--fork-session --resume`)". So the initial
thread's events before the second thread produce no group and no claim. The first
hook that CAN claim the new group is a race between two events:

- the new thread's SessionStart, which fires the moment it is opened (finding 4);
- the migrated initial thread's next hook, which is usually its next Stop, after the
  user next prompts it.

The new thread usually wins. Then the new thread is told to create every declared
job and is enforced at Stop. The initial thread, which already holds the jobs from
its single-thread phase, is exempted. The result is the duplicate firing this task
exists to remove, and the initial thread's jobs are no longer refreshed under
`refresh_after` (Task 2.2). The probe's `arrival-order` case reproduces this.
The implementer's own report says the logic was "Verified only against synthetic
/proc trees".

**Fix:** decide holder by thread identity, not arrival order. The walk already
visits the worker. The initial thread's worker carries `--resume`/`--fork-session`
(RESEARCH.md line 220), and later threads are `bg-spare` workers (line 224). Claim
the group only for the session whose worker is the resumed/forked one, and treat a
`bg-spare` worker as a non-holder. If neither shape is recognised, fall back to "holds"
(fail-safe). Put the argv markers in named constants beside `_SPAWNED_BY_FLAG`.
Add a test where the second thread's SessionStart arrives BEFORE any event from
the initial thread, and assert the initial thread is still the holder. Correct the
release note, IssueSdlc.md, the assertor and Stop guidance, and the yaml example:
they all state "the first `session_id` seen under it is the initial thread" as fact.
If the ordering cannot be settled from the walk, the shape needs a live probe
(Task 6.3 style) before this ships as default-on.

### B3. `audit_error_hiding.py` fails on four new sites (confidence 95)

**Location:** `session_thread_group.py` audit lines 96 and 107 (`_read_stat`'s
`except OSError` / `except ValueError` -> `return None`), 176 (`_load`'s
`except (OSError, ValueError)` log-and-return-`{}`), and 214 (`claim`'s write
failure, which only logs).

On main the audit exits 0. The two `plan_fact_check.py` hits it also reports in
the worktree are only because of the older merge base (fixed on main in
`06ab3658e`). The four above belong to this branch, so the QA gate is red.

**Fix:** route each deliberate swallow through
`utils.deliberate_swallow.log_and_continue(logger, exc, reason=...)` with a specific
reason (for example "a process that exited mid-walk ends the walk; the session
then holds the crons"). For `_read_stat`, either return a sentinel through a
non-`except` path or use `log_and_continue` before `return None`, whichever the
audit accepts (see how `06ab3658e` resolved the same pattern). Keep the
"unwritable registry -> caller holds" behaviour.

## SHOULD-FIX

### S1. A caller-supplied `hooks_daemon_peer_pid` is trusted on both transports (confidence 85)

**Location:** `src/claude_code_hooks_daemon/daemon/server.py:255` (`... or
HookInputField.PEER_PID in hook_input: return`), the legacy `_handle_client` /
`_process_request` path (`server.py:2188`, which neither strips nor stamps the field),
and the test `tests/unit/daemon/test_event_socket_session_hostname.py:189`
(`test_an_existing_value_is_kept`), which locks in the wrong contract.

Claude Code does not send this field, so under the careless-not-hostile threat model
this is not an attack path. Still, the only thing a forged value can do is EXEMPT a
session, which is the dangerous direction. A hand-built `probe` or replayed
capture payload carrying the field (captures now contain it) would walk an
arbitrary pid's ancestry and could claim or join a real group. The hostname stamp's
"never overwrite" rule exists because `init.sh` legitimately stamps the hostname.
Nothing legitimately pre-stamps a pid. The probe's `forged-pid` case confirms the
value is kept.

**Fix:** in `_stamp_peer_pid`, `hook_input.pop(HookInputField.PEER_PID, None)`
unconditionally, then stamp the SO_PEERCRED value. On the legacy socket, strip the
key from `hook_input` in `_handle_client` before dispatch. Better, stamp it there
too: the peer is `init.sh`'s inline python3, a descendant of the hook, so this
would also make the feature work on the `init.sh` transport instead of silently
staying off there (S2). Replace `test_an_existing_value_is_kept` with
`test_a_caller_supplied_value_is_replaced` (and `..._is_removed_when_unknown`).

### S2. The feature is silently inert on the `init.sh` transport (confidence 75)

**Location:** `server.py:2188` onward. This is documented only in the release note's
last sentence and the implementer report. IssueSdlc.md, the yaml example and both
handlers' guidance say "With no such ancestor every session holds them", with no
mention that the transport matters.

**Fix:** stamp in `_handle_client` as in S1, or state the limit in the guidance
and the yaml example comment as well as the release note.

### S3. `usage_pause_gate` still tells a later thread to re-create the jobs (confidence 80)

**Location:** `src/claude_code_hooks_daemon/handlers/user_prompt_submit/usage_pause_gate.py:240`.

The implementer listed this as "Open" in the journal and report, but it is filed
nowhere. A later thread whose pause lifts gets the declared jobs in its lift
directive, which recreates exactly the duplicate this task removes.

**Fix:** mix in `InitialThreadExemption` there and drop the job list for a
non-holder, with a handler test. At minimum, file it as a plan task, not a journal
line.

### S4. Any `claude daemon run --spawned-by` counts as a session front end, whatever its origin (confidence 70)

**Location:** `session_thread_group.py:116-127` (`_is_daemon_run`).

The single observed shape is `claude daemon run --origin transient --spawned-by
{"pid": <front end>}` (RESEARCH.md line 222). `--origin` implies other origins
exist. A longer-lived daemon that hosts threads for more than one front end would
merge unrelated sessions into one group, and every session after the first would
lose its crons (the B1 failure, across sessions).

**Fix:** also require `--origin transient`, and/or parse the `--spawned-by` JSON
`pid` and require it to equal the daemon's own ppid. Otherwise return "no group"
(fail-safe). Add named constants for `"daemon"`, `"run"`, `"--origin"` and
`"transient"` (`:125` currently has bare `"daemon"`/`"run"` literals), and add a
test for a non-transient origin.

## NIT

  identical `_active_jobs` bodies, and each Stop walks `/proc` and reads the

  `getsockopt(SO_PEERCRED)`, so every event on the hot path does it twice. Query

  `assert path is None or path.name == THREAD_GROUPS_FILENAME` passes in either

  `test_event_socket_session_hostname.py:197` (`test_a_non_dict_payload_is_ignored`)
  has no assertion. Assert the list is unchanged.
- **N4** `tests/unit/handlers/test_initial_thread_only_crons.py:15` imports helpers

- **N5** `session_thread_group.py:180`: a corrupt registry is logged at WARNING on

## Checked and fine

- Bounded walk (depth 32, 0.25 s budget, cycle-safe), `/proc` read only, no shell,
  no signals. Bandit is clean.
- No work when the option is off (early return before any read), when no job is
  declared (`if jobs and ...`), or where scope or autonomy skip the handler.
- Concurrency: load-modify-write under a module lock, with an atomic write. A

- pid reuse is handled by keying on start time. Corrupt or unwritable map, no pid,
  unreadable `/proc` and no ancestor all mean the session holds (tested).
- Sensitivity: removing the exemption fails
  `test_a_second_thread_is_not_required_to_hold_them` (both enforcers) and the
  assertor's `holds none` test. Option-off and no-ancestor behaviour is pinned.

  The INPUT-ALLOWLIST entry, the config-changes manifest, the yaml example and
