## Design decisions (all minimal; none irreversible)

- One JSON file, `work-queue.json`, in the daemon's untracked dir (beside `limit-events.json`). Shape `{"version": 1, "records": [...]}`. Written with the existing `blockage_marker.write_json_atomically` (owner-only, rename).
- Record: `name`, `worktree`, `branch`, `brief` (inline, capped at 4000 characters), `brief_file` (path), `last_sha`, `status` (`running`/`done`/`abandoned`), `created_at`, `updated_at`. At least one of brief / brief file is required.
- Project-wide, not session-keyed: a restart is a new session id, so a per-session key would hide exactly the records the new session needs.
- `add` on an existing name re-dispatches it in place (status back to `running`, `created_at` kept). `--sha` defaults to the worktree's HEAD via `run_git`; if that cannot be read the command fails and asks for `--sha`.
- Strict writer, honest reader: `read_queue` raises on a corrupt file or a version it does not know. A writer therefore never overwrites a file it cannot read, and the re-brief says "WORK QUEUE UNREADABLE" instead of implying an empty queue.
- Writers (CLI processes and daemon threads) serialise on `flock` of a sidecar `.work-queue.json.lock`; a 12-thread test loses no record.
- The re-brief lists only `running` records, each with worktree (flagged `[MISSING on disk]`), branch, last sha, age and the brief clipped to 500 characters; `work-queue list --json` has the full text. It states that agents are not respawned. `work_queue_rebrief` and `limit_rebrief` share `queue_briefing`, so they cannot disagree.
- No QA suppression, no allowlist or exclusion entry was added.

## Owner questions (not decided; the advisory path only is implemented)

1. Auto-respawn: should a resumed session ever re-dispatch queued agents itself, instead of listing them? Today it never does.
2. Retention: finished (`done`/`abandoned`) records are kept forever and only hidden from the default listing. Should they be pruned, and after how long or how many? Task 4.1 (growth measurement) may be the place.
3. A `running` record whose agent died and whose coordinator is also gone stays `running` until someone closes it. Should the re-brief age such records out (for example after N days) rather than list them indefinitely?
4. Several coordinators in one project share the queue. If that is a real case, should a record carry the dispatching session so each coordinator sees only its own by default?
