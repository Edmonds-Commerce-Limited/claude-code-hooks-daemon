# Task 6.4 report: only the initial thread holds the declared crons

## Which pid the daemon can learn

The daemon CAN learn the calling pid on the per-event socket (relay) path. `SO_PEERCRED` was already queried there for the hostname override, so `_peer_pid` was split out of `_peer_hostname` and `_stamp_peer_pid` stamps `hooks_daemon_peer_pid` on the payload (`daemon/server.py`). The pid is of the connected hook process (the relay), a descendant of the thread's worker.

The legacy `init.sh` envelope socket (`_handle_client` -> `_process_request`) parses its request after the connection step and stamps nothing. `init.sh` was not changed, so a payload from that path carries no pid and behaves as today (every session holds the crons). That is the fail-safe direction, but it means the feature is live only on the relay path.

## What was built

- `utils/session_thread_group.py`: `find_thread_group` walks `/proc/<pid>/stat` (ppid, start time) and `/proc/<pid>/cmdline` up to 32 hops and 0.25 s, no shell, never signals, to the nearest `claude daemon run ... --spawned-by` ancestor. `ThreadGroupRegistry.claim` persists group key (`pid:starttime`) to holder `session_id` in `session-thread-groups.json` under the daemon untracked dir (atomic write, 256 groups kept, first-inserted evicted). A corrupt or unwritable file means the caller holds.
- `handlers/utils/initial_thread_exemption.py`: mixin shared by `persistent_cron_assertor`, `cron_stop_enforcer`, `cron_subagent_stop_enforcer`. The walk is lazy (only when a job is active and the option is on). A non-holder gets no active jobs at the two enforcers; the assertor says it holds none, names the initial thread's session and the option.
- `persistent_crons.initial_thread_only` (strict bool, default true) in `config/models.py`.
- Docs: yaml example and this repo's config, handler guidance (`get_claude_md`) for the assertor and Stop enforcer, `IssueSdlc.md`, release note `004-...`, config-changes entry in `v3.70.0.yaml`, `INPUT-ALLOWLIST.yaml` entry for the stamped field. HANDLER_REFERENCE.md is generated and does not list these two handlers' guidance, so it was not edited.
