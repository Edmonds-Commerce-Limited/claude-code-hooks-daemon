## Design

A Notification cannot speak to the model, so the work splits in two.

- `handlers/notification/quota_resume_recorder.py` (priority 50): records `quota_auto_resume_*` notifications (session, type, time; not the text) in `limit-events.json` under the daemon untracked dir. `utils/limit_events.py` mirrors `stop_failure_records.py`: atomic write, lock, fail open, bounded to 50, malformed entries skipped. It reuses the 3.1 time validator, which I made public (`epoch_seconds`) rather than copy.
- `handlers/user_prompt_submit/limit_rebrief.py` (priority 39): one handler, two jobs.
  - A prompt that OPENS with `<task-notification` and quotes the limit sentence, or with `<teammate-message` carrying a failed `idle_notification` that quotes it, gets an advisory naming the agent and demanding a re-brief once the limit resets. It is also recorded as `agent_killed`. A human prompt that merely quotes the sentence is ignored (the marker must open the prompt).
  - Any prompt while a resume event is undelivered gets the one-shot re-brief, worded per type (`fired`: resumed; `stale`: waiting for Enter; `disabled`: did NOT continue), then the events (and the agents recorded as killed) are marked delivered.

I extended nothing existing for the handler itself: `agent_terminated_early_failure_detector` is PostToolUseFailure on a tool `error` field and `stop_failure_resolver` is deliberately silent, so neither is the natural host. `stop_failure_*` and `limit_events` stay separate files because the records mean different things (an API failure versus how a wait ended or who died).

The re-brief points at what exists: `git worktree list` with `git status` and `git log -1` per worktree, the active plan's JOURNAL day-file, the last recorded limit hit for the session (read from `stop-failures.json`, resolved or not, so it does not depend on the resolver's priority), and any recorded dead agents. It does not mention a queue. `_REBRIEF_PLACES` in `limit_rebrief.py` is a tuple; Task 3.3 adds the queue at its head.

Also fixed: `NOTIFICATION_INPUT_SCHEMA` enumerated three `notification_type` values, so `hooks-daemon probe` and input validation would have rejected the new types. It now lists the twelve in hooks.md (test widened).

Both handlers return `None` from `get_claude_md()` with reasoned `_EXEMPT_FROM_GUIDANCE` entries; each declares an acceptance test with `harness_cannot_produce` (the triggers are harness-sent turns and a real limit).

## Decisions

- Status line: no chip. The record is for the model, which is the party that can re-dispatch; the 3.1 chip already tells the human about the limit.
- A death noticed in the same prompt as a pending resume is recorded after the pending set is read, so the re-brief does not repeat the notice, and is then marked delivered by the same pass.
- Duplicate undelivered events (same session, kind, detail) are recorded once.
- Resume events are not aged out; a re-brief hours late is still correct, and the 50-record bound caps growth.

## Limits

- Not verified live: whether Claude Code fires UserPromptSubmit for a `<task-notification>` turn or for the auto-continuation. If it does not, the death notice is not seen here, and the resume re-brief still lists the worktrees (it says no agent was recorded, and that this does not mean none died). A live probe is the follow-up; the daemon was not restarted.
- The text inside `<task-notification>` is undocumented, so a notification that does not quote the exact limit sentence is not recognised.
- No agent assignment (worktree, brief, sha) is stored; that is Task 3.3's queue.
