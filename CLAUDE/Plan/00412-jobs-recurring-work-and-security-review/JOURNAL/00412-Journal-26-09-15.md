## 09:05 · decision · P1 — the design decisions, and why

Full reasoning in `DESIGN.md`. The load-bearing ones:

**Coverage is an INTERVAL, not a pointer** (from `cargo-vet`). Each run records
`from -> to`. Intervals compose, so a gap between runs is arithmetic; a mutable
"last reviewed" pointer bumped wrongly once is silently wrong forever and
undetectable afterwards. This is the single most important decision here.

**A delta run is structurally blind** (CodeQL says so of its own diff mode), so
the periodic full sweep is a compensating control rather than thoroughness
theatre — and a delta run MUST record which checks it did NOT run. "Clean"
without "clean under a delta scope" is the expensive kind of wrong, because it
gets cited later as coverage.

**Missed runs widen the next interval, never replay** (systemd `Persistent=`
semantics, Airflow's `catchup=False` default).

**Absence of a run is invisible from the run records** — something outside them
must assert overdue-ness.

**Two-level logging split by PORTABILITY, not verbosity.** The owner corrected
me here: `untracked/` is bind-mounted and survives container restarts; I had
confused it with paths outside the repo. The real limitation is that it is
per-checkout — invisible to CI, another machine, a fresh clone. So the interval
must be in-repo; raw output need not be.

## 09:12 · decision · D9 — the owner's last input before shutdown: triggers are kinds, not clocks

Recorded because it arrived at the end and would otherwise be lost, and because
it is the best structural idea in the design so far.

A job declares a trigger KIND — `schedule` or `session_start` (and plausibly
`release` later) — rather than always a cron expression. Three consequences,
written up as D9 in `DESIGN.md`:

1. The six existing session-start sweeps become REAL consumers. Under a
   clock-only model they could never migrate, and the whole abstraction would
   rest on one hypothetical consumer instead of six shipped ones.
2. It inverts the delivery-guarantee argument. A Claude Code cron lives in
   session memory and the daemon cannot see it; a SessionStart hook is executed
   by the daemon itself. So the clock is the WEAKEST trigger and the one the
   daemon already owns is the strongest — a design leading with cron has it
   backwards.
3. A monthly job may need no cron at all: a `session_start` trigger that reads
   the interval and stays silent unless a run is overdue gives the same cadence
   with none of the delivery risk. The clock becomes an optimisation for jobs
   that must fire with no human present.

This should be the first thing the re-dispatched fable review is asked to
attack, since it materially changes the architecture it was originally briefed
on.

The ones that change the design rather than decorate it:

**Run states — `clean` must never mean `absent`** (D10). PCI DSS requires four
PASSING scans over four quarters, not four scans. So "is this job in good
standing?" is a query over OUTCOMES, not existence, and five states are needed:
no-record, clean, findings, failed, skipped-with-reason. Collapsing the first
two is named as the default mistake.

**Falling behind must be loud** (D11). A Kubernetes CronJob past 100 missed
schedules stops scheduling ENTIRELY and only logs it — a recurring job that
silently stops recurring, permanently. Also: a dead man's switch needs period
PLUS grace, or a monthly cadence nags on day 31.

**The owner's delta instinct has a reason** (D12): a NEW RULE makes UNCHANGED
code newly reviewable. That is precisely the failure a naive delta cannot
self-detect, because nothing in the diff points at it. It is why "changed code
and changed security rules" was the right scoping all along.

**Two traps inherited from the Plan machinery** (D13), both silent:
`staleness-nag`, `dormant-honesty` and `journal-freshness` all assume quiet
means neglected — for a recurring job quiet between runs is CORRECT, so copied
unchanged they nag daily about a job behaving perfectly. And the goal ledger
retires an entry on terminal status: a Job has none, so it would enter the
ledger once and challenge every stop for the rest of the session, forever.

**Share, do not fork** (D14). `plan_qa/paths.py`, the journal subsystem and the
numbering layer are structurally generic and only textually plan-named.
`docs_qa` already duplicated `plan_qa`'s type layer instead of sharing it;
Jobs would make three copies. Worth a deliberate ruling now rather than a
discovery later.

**Where we already conform to DBF** (D15) — `handlers`, `explain-rule`, stable
`R-*` identifiers and the generated CLAUDE.md block satisfy much of the
Toolchain spec by convergent design. Two real gaps: `exclude_paths` are
exceptions with no recorded hazard-naming justification, and there is no
red-commit discipline.

**Squash bans are load-bearing here** (D16). `R-GIT-MERGE-SQUASH` and
`R-GH-PR-MERGE-SQUASH` exist for unrelated reasons, but they are what keeps a
stored baseline ref resolvable. Relaxing them later would break job coverage
retroactively — every stored `from` pointing into a squashed branch becomes
unresolvable at once.

Two claims were checked and REJECTED, which matters because both are the kind

## Task 2.1 — the interval algebra, and why it was never blocked

I had this plan recorded as owner-gated on three rulings, one of them
"whether Task 2.1's interval algebra survives". Re-reading D2, which is marked
DECIDED, that was wrong. The open questions (D18, D22) decide WHERE run
records live — tracked pointer, untracked ledger, per-checkout. The
composition arithmetic is identical either way, so the algebra never depended
on the answer. Doing everything that does not depend on an open question is
the rule I had not applied here.

Four outcomes, not three. The task asks for gap, overlap and full coverage;
building it surfaced a fourth that the task text does not name and that
matters more than any of them. A rebase or a diverged branch leaves two refs
where NEITHER is an ancestor of the other, and with only three outcomes that
case has to be forced into one of them. Forcing it into `MEETS` is the
pointer bug wearing an interval's clothes — silently claiming coverage nobody
established — so `UNRELATED` is its own answer.

**Detection needs no oracle; classification does.** This is the split that
made the module pure. Whether two runs are discontinuous is
`current.from != previous.to`: string inequality, no git, and precisely what
"detectable without consulting anything mutable" comes to. Telling a GAP from
an OVERLAP is a different question — it needs to know which ref came first —
so ancestry arrives as an injected protocol rather than a subprocess called
from inside the algebra. Two benefits fell out of that rather than being
designed for: the whole thing tests against a list of strings, and the healthy
case short-circuits on equality, so a QA sweep composing every adjacent pair
never shells out for a chain with no breaks.

Two properties are pinned as tests rather than left as prose, because both are
the kind of thing a later reader would "fix":

- **D5, missed runs widen.** A skipped run leaves no hole: the next run's
  `from` is still the last COMPLETED run's `to`, so the pair composes as
  `MEETS`. The record does not need to know a run was skipped, only what was
  looked at.
- **D6, absence is not a gap.** `discontinuities([])` is empty, and a comment
  says why: a Routine that never ran has no runs to compose. Conflating the
  two would let an unrun Routine report as continuous, which is the one
  failure this whole area exists to prevent. The overdue assertion is Task
  2.5's job and belongs outside the algebra.

sends the pair to UNRELATED — a finding a sweep reports. Raising instead would
abort the sweep, and a sweep that reports nothing looks exactly like a sweep
that found nothing.

## Task 3.1 — the first real routine, and the question it forced

The task reads as one routine with two modes: a full sweep on a calendar, a
narrower per-release sweep, one check inventory. I built it as two routines,
and the reason is a mechanism, not a preference.

If a delta run writes into the same ledger as the full sweep, it resets the
overdue clock. A project that releases often would then defer its full sweep
for ever, and every record would read as healthy the whole time. That is the
exact failure this plan exists to prevent, reintroduced by the plan's own first
routine — so the two obligations need two clocks, which means two ledgers,
which means two routines.

The deeper reason is that coverage is per CHECK SET, not per routine. A delta
run covers the delta-able checks over its interval and covers NOTHING over that
same interval for the full-only ones. One ledger cannot express two coverage
timelines without the interval arithmetic quietly lying, and the interval
arithmetic is the part of this design that was supposed to make lying
impossible.

Naming the full-only column was the useful work. Two shapes account for almost
all of it: the world moved while the file did not (a pinned dependency acquires
a CVE), and the nth item was the one too many (every exemption was defensible
on the day it was added; no single diff hollows the guard out). Both are
invisible to a diff by construction, which is what makes the full sweep a
compensating control rather than belt-and-braces — the phrase the task used,
and which I could not have justified before writing the table.

`Trigger: release` had to become a real value first. Left out of the closed
set, "each release" parses as UNKNOWN, and an UNKNOWN trigger removes the
routine from every check in the sweep while still reading as configured to a
human. A check a typo can switch off is worse than no check; a check a MISSING
ENUM VALUE switches off is the same thing with better manners.

It carries no clock, deliberately, and I pinned that with a test rather than
leaving it to `due_after_days`'s existing SCHEDULE guard. A release routine's
backstop is the full sweep beside it — a missed delta run widens the next full
run's interval (D5) — so a due date would be a second nag about a cadence
nobody keeps. The behaviour was already correct by accident of the earlier
guard; a test makes it correct on purpose.

`routine-qa` now reports two findings, both `routine-never-run`, both true.
That is the system working: the first thing the machinery says about its first
real routines is that nobody has run them yet.

## Task 3.2 — the register found its first entry by being written

The register was meant to ship with an empty table and a contract. It shipped
with one category, because writing it hit a bug in the project's own docs gate:
`CLAUDE/Security/README.md` would not write. `pointer-resolves` reported both
its `../Routine/...` links as dead while both files were on disk.

`Path.exists()` stats the path as written, so `..` is walked through the
filesystem and `CLAUDE/Security/` had to exist for the join to stat at all —
and it did not, because the write that would create it was the one being
judged. A new dead link is BLOCK, so the write was denied, and no retry could
have succeeded. The denial named a dead link, which would have sent me hunting
for a typo in a path that was correct.

The dogfooding rule says stop and fix with a TDD reproduction. Defence Before
Fix says the Defence lands first. Both, then.

Attributing the class is where I learned something. I predicted 4 instances and
the sweep found 7: `README_FILENAME` and two config-derived directory names are
`Name` nodes, not string literals, so the SYNTAX does not tell you whether a
value can carry a `..`. Deciding that needs data flow. A rule that guesses is a
rule that argues with its reader, so it became a chokepoint instead — in the
two trees whose job is resolving what an author wrote, normalise before you
stat, always. Seven sites, no exemption marker, nothing to weigh.

Scoping is what keeps it credible rather than what weakens it. All of `src/`
has 17 sites of the shape, mostly daemon-chosen paths where `..` cannot arise.
A rule firing on 17 to catch 7 gets suppressed, and a suppressed rule protects
nothing. The inline-string-literal exclusion is the same argument in miniature.

The Defence went in red, deliberately, in its own commit. That felt wrong to do
— pushing a failing gate to main — right up until the fix commit made the pair
read as exactly what happened: here is the net, here is the proof it catches
the thing, here is the thing removed.

Worth recording what the Defence does NOT catch, because the register asks
every category for it and this one has five. Only two trees; only inline
literals excluded; only three predicates, so `os.stat` or an `open()` in a
`try` is invisible; it is a syntax rule, so a join built over two statements
slips past; and containment is a different question entirely — normalising
makes `src/../../etc/passwd` resolve faithfully to a real file, and this
Defence has nothing to say about that.

documentation asserting it is what makes the absence read as presence.

cross-references every "blocked" claim in the agent docs against the live rule

## G9, and why it is upstream of the other fifty-two

F-GAP's method is the reason it found this and a cheaper pass would not have.
It evaluated every candidate against the real handler classes in TWO passes,
`matches()` then `handle()`. The second was load-bearing: `verification_result_gate`
MATCHES almost every git command and then allows it, so a `matches()`-only
survey would have scored 24 git candidates as covered while nothing denied them.

Its headline: **guard self-disablement is watched by nothing.** Setting

`.claude` — no deny, across Write, Edit and Bash. I confirmed the handler set

config-adjacent handlers are advisories. `write_clobber_guard` looks like it

## The chain: three defensible decisions that compose into one

F-BYPS came back and its top finding meets G9 head on. Taken alone, none of
these three is a mistake. I checked each.

1. **A config validation failure fails open.** `daemon/controller.py:915-926`:
   in degraded mode the destructive-git safety net runs, and if it returns
   nothing the result is `HookResult.configuration_error(...)` — an ALLOW. This
   is deliberate and reasoned; Plan 00304 NARROWED it, adding the destructive-git
   net after a real-repo canary caught `git reset --hard` sailing through. The
   comment states the remaining position outright: "fail-open remains the design
   for ordinary handlers". A daemon that hard-denies on its own config error
   bricks the session, so fail-open is a real trade-off honestly made.

2. **Nothing guards writes to that config.** Verified: no handler gates
   `.claude/hooks-daemon.yaml`, `.claude/settings.json` or the agent
   definitions. Also defensible — the config is the operator's, and a tool that
   refuses to let you configure it is a tool people work around.

3. **Every deny message names the key that switches the handler off.** Good
   operator ergonomics, and the honest thing to print when a guard fires on
   something legitimate.

Compose them and the picture changes. A single malformed line in a file nothing
guards — a line every deny message in the system effectively teaches an agent
how to write — reduces the entire PreToolUse guard set to one handler, silently,
with an advisory nobody has to read. Not a disable that anyone decided: a
VALIDATION ERROR gets there too, which means a typo and an attack have the same
blast radius.

This is the F-EXPT insight on a different axis — each entry was fine alone —
and it is precisely what F-BYPS was created to catch: "a bypass is created by
the INTERACTION of files, and both can be unchanged." Here all three are
unchanged and each has a plan behind it.

F-BYPS-8 removes the last floor: the forwarder `exec`s `untracked/bin/hooks-relay`
after only an `-x` test. Gitignored, agent-writable, unverified, and consulted
BEFORE the daemon — so it sits underneath even the degraded-mode safety net.

And F-BYPS-4 is a fifth instance of the class named above: four handlers assert
"NO escape hatch, only a human may lift this", nothing enforces it, and the
tests assert the claim is PRINTED rather than that it is true. A test that
pins the text of a promise, and not the promise.
