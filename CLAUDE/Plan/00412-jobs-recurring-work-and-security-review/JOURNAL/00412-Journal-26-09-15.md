## 09:05 · decision · P1 — the design decisions, and why

Full reasoning in `DESIGN.md`. The load-bearing ones:

**Coverage is an INTERVAL, not a pointer** (from `cargo-vet`). Each run records
`from -> to`. Intervals compose, so a gap between runs is arithmetic; a mutable
"last reviewed" pointer bumped wrongly once is silently wrong forever and
undetectable afterwards. This is the single most important decision here.

**A delta run is structurally blind** (CodeQL says so of its own diff mode), so
the periodic full sweep is a compensating control rather than thoroughness
theatre — and a delta run MUST record which checks it did NOT run. "Clean"
without "clean under a delta scope" is the expensive kind of wrong, because it
gets cited later as coverage.

**Missed runs widen the next interval, never replay** (systemd `Persistent=`
semantics, Airflow's `catchup=False` default).

**Absence of a run is invisible from the run records** — something outside them
must assert overdue-ness.

**Two-level logging split by PORTABILITY, not verbosity.** The owner corrected
me here: `untracked/` is bind-mounted and survives container restarts; I had
confused it with paths outside the repo. The real limitation is that it is
per-checkout — invisible to CI, another machine, a fresh clone. So the interval
must be in-repo; raw output need not be.

## 09:12 · decision · D9 — the owner's last input before shutdown: triggers are kinds, not clocks

Recorded because it arrived at the end and would otherwise be lost, and because
it is the best structural idea in the design so far.

A job declares a trigger KIND — `schedule` or `session_start` (and plausibly
`release` later) — rather than always a cron expression. Three consequences,
written up as D9 in `DESIGN.md`:

1. The six existing session-start sweeps become REAL consumers. Under a
   clock-only model they could never migrate, and the whole abstraction would
   rest on one hypothetical consumer instead of six shipped ones.
2. It inverts the delivery-guarantee argument. A Claude Code cron lives in
   session memory and the daemon cannot see it; a SessionStart hook is executed
   by the daemon itself. So the clock is the WEAKEST trigger and the one the
   daemon already owns is the strongest — a design leading with cron has it
   backwards.
3. A monthly job may need no cron at all: a `session_start` trigger that reads
   the interval and stays silent unless a run is overdue gives the same cadence
   with none of the delivery risk. The clock becomes an optimisation for jobs
   that must fire with no human present.

This should be the first thing the re-dispatched fable review is asked to
attack, since it materially changes the architecture it was originally briefed
on.

## 09:16 · finding · P1 — the agents' closing summaries arrived AFTER the handoff, and carried more than the reports' openings did

Three agents sent final summaries after the handoff entry was already
committed. They were not restatements: each carried findings the report
introductions had not surfaced. Captured as D10–D16 in `DESIGN.md` rather than
left in a chat message nobody will re-read.

The ones that change the design rather than decorate it:

**Run states — `clean` must never mean `absent`** (D10). PCI DSS requires four
PASSING scans over four quarters, not four scans. So "is this job in good
standing?" is a query over OUTCOMES, not existence, and five states are needed:
no-record, clean, findings, failed, skipped-with-reason. Collapsing the first
two is named as the default mistake.

**Falling behind must be loud** (D11). A Kubernetes CronJob past 100 missed
schedules stops scheduling ENTIRELY and only logs it — a recurring job that
silently stops recurring, permanently. Also: a dead man's switch needs period
PLUS grace, or a monthly cadence nags on day 31.

**The owner's delta instinct has a reason** (D12): a NEW RULE makes UNCHANGED
code newly reviewable. That is precisely the failure a naive delta cannot
self-detect, because nothing in the diff points at it. It is why "changed code
and changed security rules" was the right scoping all along.

**Two traps inherited from the Plan machinery** (D13), both silent:
`staleness-nag`, `dormant-honesty` and `journal-freshness` all assume quiet
means neglected — for a recurring job quiet between runs is CORRECT, so copied
unchanged they nag daily about a job behaving perfectly. And the goal ledger
retires an entry on terminal status: a Job has none, so it would enter the
ledger once and challenge every stop for the rest of the session, forever.

**Share, do not fork** (D14). `plan_qa/paths.py`, the journal subsystem and the
numbering layer are structurally generic and only textually plan-named.
`docs_qa` already duplicated `plan_qa`'s type layer instead of sharing it;
Jobs would make three copies. Worth a deliberate ruling now rather than a
discovery later.

**Where we already conform to DBF** (D15) — `handlers`, `explain-rule`, stable
`R-*` identifiers and the generated CLAUDE.md block satisfy much of the
Toolchain spec by convergent design. Two real gaps: `exclude_paths` are
exceptions with no recorded hazard-naming justification, and there is no
red-commit discipline.

**Squash bans are load-bearing here** (D16). `R-GIT-MERGE-SQUASH` and
`R-GH-PR-MERGE-SQUASH` exist for unrelated reasons, but they are what keeps a
stored baseline ref resolvable. Relaxing them later would break job coverage
retroactively — every stored `from` pointing into a squashed branch becomes
unresolvable at once.

Two claims were checked and REJECTED, which matters because both are the kind
of thing a later plan would cite as precedent: the widely-repeated "Django
requires a test with every security fix" appears to be folklore with no written
policy behind it, and an annual Kubernetes/CNCF audit cadence could not be
verified (observed intervals are roughly triennial). Each report also carries
its own "could not verify" section — the prior-art one flags seven items,
including the `cargo-vet` 500-LOC convention, where the principle is sound but
