## 09:05 · decision · P1 — the design decisions, and why

Full reasoning in `DESIGN.md`. The load-bearing ones:

**Coverage is an INTERVAL, not a pointer** (from `cargo-vet`). Each run records
`from -> to`. Intervals compose, so a gap between runs is arithmetic; a mutable
"last reviewed" pointer bumped wrongly once is silently wrong forever and
undetectable afterwards. This is the single most important decision here.

**A delta run is structurally blind** (CodeQL says so of its own diff mode), so
the periodic full sweep is a compensating control rather than thoroughness
theatre — and a delta run MUST record which checks it did NOT run. "Clean"
without "clean under a delta scope" is the expensive kind of wrong, because it
gets cited later as coverage.

**Missed runs widen the next interval, never replay** (systemd `Persistent=`
semantics, Airflow's `catchup=False` default).

**Absence of a run is invisible from the run records** — something outside them
must assert overdue-ness.

**Two-level logging split by PORTABILITY, not verbosity.** The owner corrected
me here: `untracked/` is bind-mounted and survives container restarts; I had
confused it with paths outside the repo. The real limitation is that it is
per-checkout — invisible to CI, another machine, a fresh clone. So the interval
must be in-repo; raw output need not be.

## 09:12 · decision · D9 — the owner's last input before shutdown: triggers are kinds, not clocks

Recorded because it arrived at the end and would otherwise be lost, and because
it is the best structural idea in the design so far.

A job declares a trigger KIND — `schedule` or `session_start` (and plausibly
`release` later) — rather than always a cron expression. Three consequences,
written up as D9 in `DESIGN.md`:

1. The six existing session-start sweeps become REAL consumers. Under a
   clock-only model they could never migrate, and the whole abstraction would
   rest on one hypothetical consumer instead of six shipped ones.
2. It inverts the delivery-guarantee argument. A Claude Code cron lives in
   session memory and the daemon cannot see it; a SessionStart hook is executed
   by the daemon itself. So the clock is the WEAKEST trigger and the one the
   daemon already owns is the strongest — a design leading with cron has it
   backwards.
3. A monthly job may need no cron at all: a `session_start` trigger that reads
   the interval and stays silent unless a run is overdue gives the same cadence
   with none of the delivery risk. The clock becomes an optimisation for jobs
   that must fire with no human present.

This should be the first thing the re-dispatched fable review is asked to
attack, since it materially changes the architecture it was originally briefed
on.
