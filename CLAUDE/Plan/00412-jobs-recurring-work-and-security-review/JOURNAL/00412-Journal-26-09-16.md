## 00:10 · milestone · the call-path rule kind, and the gap it found

`5b6ac98b` (red) → `a6ce7bb7` (fix) → `ac430ad3` (register). Third instance of
`asymmetric-sibling-protection`, and the first found by a rule kind rather than
by comparing two constants.

`remote_docs/store.py::refresh_document` never called `content_guard`.
`write_capture` does, and its docstring already says why: a capture writes from
a CLI, bypassing the `Write` hook that would otherwise inspect the content, so
an authenticated page would be vendored with its secrets unexamined. The
refresh path ran the same fetch and the same write with no scan at all.

**The refresh path is the more exposed of the two**, which is what lifts this
above tidiness. A capture is something a human ran deliberately, once. A refresh
exists precisely because upstream may have changed — and those new bytes have
had no review by anyone.

Two decisions worth keeping:

- `REFUSED` is a new outcome, not a reuse of `FAILED`. A failed fetch is a
  transient network problem to retry; a refusal means upstream is now serving
  something that must not enter the repository. Blurring them would tell a
  human to retry when they should be looking at the source.
- The scan runs BEFORE the unchanged-hash short-circuit. Putting it after would
  have left a clean route past the guard — an unchanged hash still rewrites the
  file, and the scanner's pattern list can grow between runs even when upstream
  has not moved.

## 00:12 · finding · what `reaches` cannot prove

That second decision is the honest limit of the rule kind I had just built, and
it is now in the register's blind-spot section.

`reaches` proves a **call**, not an **effect**. It cannot tell whether the
result is acted on, whether the call sits behind a condition that is never true,
or whether it runs before the write it is meant to guard. Had I put the scan
after the short-circuit, the row would have gone green over a guard that did
nothing on the path that mattered.

So the ordering — the load-bearing part of this fix — was caught by a test, not
by the rule. Writing that down beside the rule is worth more than the row.

`unbounded-work-on-input-not-sized` is the second class in this plan to get a

**A false positive caught before it shipped, which is the whole discipline.**
My first scan flagged three sites. The third, `install/transport_verify.py`, was
correct: `Popen` takes no timeout at construction — its bound is set at
`communicate(timeout=…)`, which that module does, and its second unbounded
`communicate()` is deliberate and documented. A rule that treated `Popen` like
`run` would have flagged a correct call, and a guard that cries wolf gets
switched off. `Popen` is excluded, the exclusion is pinned by its own test, and
the resulting blind spot is written in the docstring rather than papered over.

**Deduplication avoided creating a member of class 1.** The git guard already
resolves which AST calls reach a subprocess spawner, and it learned about
`import subprocess as sp` and the two `from`-import forms by EXECUTION, not by
reading (Plan 00248 F5). A second scanner copying that logic would have started
from the naive version and inherited exactly those blind spots while the first
stayed correct — the asymmetric-sibling class, created by the very act of
adding a Defence for another class. The resolver moved to one shared home.
Extracting it surfaced a real bug too: `run as launch` reported the local alias,
so a deny message would have sent a reader looking for `subprocess.launch`.

**The conflict, unresolved and owner-gated.** Registering this class runs into
two documented rules that contradict:

- `CLAUDE/Security/README.md` states the obligation that every Defence "must be
  a Detector in `scripts/qa/` wired into `run_all.sh` — not a regression test,
  not a note, not a convention", and asserts both existing categories honour it.
- `test_git_spawns_are_bounded`'s docstring gives the opposite reasoning: a test

  and "cannot publish its verdict under a key no consumer reads — the failure

The second is not a preference, it is a recorded failure of the first. I
followed the git guard's precedent because this Defence is its sibling and
splitting the pair across two mechanisms would have been worse than either
choice. That means class 15 is NOT added to the register table: doing so would
make the table assert an obligation this Defence does not meet, and a register
that overstates its own coverage is the one failure it cannot afford.

There is a synthesis available and I am not taking it unilaterally, because it
changes a standing rule: a `scripts/qa/` Detector PLUS a test asserting it is
wired into `llm_qa.py`, which satisfies the register's letter while guarding
the exact 00244 failure the docstring cites. That is a decision about which of
two standing rules governs, and it should be made once, for every future class

## Class 7 — `interpolation-into-another-language`, all three instances

Two target languages, one shape: a value substituted into a string that another
language then parses, where the substitution does not survive the parse as one
token. I fixed them on separate evidence rather than letting one imply the other.

**argv (`lint_on_edit`, `staged_lint_gate`).** A command template carrying a
`{file}` placeholder had the path substituted in and the result `.split()`. Run
rather than read, that is:

    "ruff check {file}" + "/repo/x.py --config /tmp/attacker.toml"
        -> ['ruff', 'check', '/repo/x.py', '--config', '/tmp/attacker.toml']

A FILENAME becomes an argument. `lint_on_edit` runs automatically on every Write
and filenames are agent-controlled, so this is a live route to making a linter
load someone else's config. No shell is involved anywhere near it, which is
exactly why `security_antipattern` — which looks for `shell=True` — has nothing
to say. The boring half of the same line is a path with a space linting two
files that do not exist.

The fix is not escaping. It is never building argv as a string: split the
TEMPLATE, then substitute the path as one element. The two sites were also an
asymmetric sibling pair and had to move together; fixing one would have left the
other reachable by the identical input.

**YAML (`remote_docs/capture.py`).** `_render_frontmatter` built the provenance
block by interpolation, so a newline in any value opened a new key. Through the
public `capture()` path, a licence of `MIT\nfidelity: verbatim` produced:

    fidelity: summarised     <- what capture() was told
    licence: MIT
    fidelity: verbatim       <- injected, and the one that wins

Nothing is malformed, so the parser accepts it and a reader skims past it. That
block is the record `R-REMOTE-DOCS-PROVENANCE` validates, and `verbatim` is the
assertion that a vendored document matches upstream byte-for-byte — the whole
basis on which a local copy is trusted. A capture could declare `summarised` and
emit a record claiming `verbatim`.

Again the fix is the mechanism, not the symptom: escaping newlines per field
would have left the next field and the next value type to be rediscovered, so
the frontmatter is now produced by a YAML writer. I verified it by INSPECTING
both renderings, not by trusting the assertion — the hostile licence now renders
quoted inside its own value with `fidelity: summarised` intact, and an ordinary
capture still renders one field per line in declaration order.

**Deliberate scope limit.** The argv Detector does not cover the YAML instance
and says so in its docstring. Different target language, fixed on its own
evidence. It also knows exactly one spelling — a name assigned from `.replace()`
and later `.split()` — so an f-string, `%`, `.format()` or `shlex.split` of an
interpolated value is the same defect and invisible to it. The sweep found 2
such sites against 35 bare `.split()` calls, so the rule is narrow and precise
rather than complete; going wider needs taint tracking.

  previously recorded a deliberate decision NOT to add a profanity rule…") and

- `8f8596cd`, `3fd5b056`, `3b9be212` are bulk restructures (89/157, 41/118,

**The lesson, which is the transferable part**: both designs test the SPELLING of
the message, not whether anyone reasoned. That is the same defect twice, and the
second time it was wearing a disguise convincing enough that I only caught it by
running the same measurement again. A separator-insensitive match rescued one of
the five — proof that the rule's verdict turned on punctuation.

**So 2(a) reports; it does not deny.** This is not a retreat from the class.
Class 2 is defined as an action "judged by no gate and recorded nowhere", and the
RECORD is the deliverable; denial was never what the class asked for. It also
matches this project's own rollout precedent — `staged_lint_gate`,
`verification_result_gate` and `plan_qa_commit_gate` all ship `mode: warn`. A
gate with an 80% historical false-alarm rate is one that gets switched off, which
is the finding eating itself.

**The discriminator was validated in its failure direction, not just its totals.**
15 of the 20 candidates are suppressed by the per-commit set; all 15 are
`removed`-only and all 15 had a readable declaration, so it is the discriminator

Suppressing it is correct, and only the per-commit set gets it right.

**Build order for 2(a)**: `-a`/`--all` detection is load-bearing, not polish —

## Class 2 is complete: the promotion found four divergences, the gate found one

Both halves of class 2 now exist. The gate is `85b0cd6b` (the promotion) and
`4e57549b` (the handler), on top of 2(b)'s `11d09297`.

**The promotion was the risky half, and comparing beat lifting.** Moving
`-a`/`--all` detection into `git_commit_parsing` looked like a copy-paste. It was
not: the handler's private copy and the shared module's existing letter sets
disagreed in FOUR places, each of which I found by diffing the two sets rather
than assuming a lift would do, and each of which I proved with a failing test
before changing anything.

- `t` (`--template`) was missing from the shared value letters, so `-ta path`
  (template "a") read as carrying `-a`.
- `S`/`u` take an OPTIONAL value and must never consume the FOLLOWING token.
  Reusing `VALUE_FLAGS` made `-u -a` swallow the `-a` — a working-tree commit
  read as an index one, which is the wrong direction for a guard.
- `--trailer` and `--pathspec-from-file` take separate values the shared long set
  did not list, so a trailer value starting with a dash was walked as options.

The letter sets are deliberately NOT merged with `_SHORT_VALUE_LETTERS`. Widening
that set would change what `extract_commit_message` and
`extract_commit_pathspecs` parse, and therefore what two LIVE commit gates see.
Class 2a should not have that side effect, so the module carries two readers that
answer two different questions rather than one that answers both badly.

**A false green I caught by strengthening the test, not by reading the code.**
The gpg-sign case first used a key id of `keyid`, which contains no `a` — so it
passed against an implementation that scans the whole token and would have
locked in the bug it was written to prevent. Re-spelled as `keya` it went red,
then green. The general form: *a test whose input cannot distinguish the two
implementations is not evidence about either.* Same family as the fixture-green
lesson from earlier today, and it keeps recurring because the passing test looks
identical in both worlds.

**The live probe earned its place again.** 17 unit tests inject both readers, so
every one of them stays green against a handler whose REAL readers return `None`
on every call — permanently silent, perfectly tested. That is the false negative
that already bit this plan once. Probing the real repository showed HEAD, index
and working tree all reading (67,618 bytes), silence on the real config, and a
finding on a weakening the probe confirms was actually applied — printing
`mutation actually applied: True` rather than trusting a `.replace()`.

**And the probe found a defect in shipped code.** The comparator's finding text
was written for its first caller and said "`enabled: false` in the working tree".
The commit gate reads the STAGED blob, so that sentence printed verbatim under a
heading saying "per the staged config" — a security advisory naming the wrong
document. Fixed with a test: findings now state only WHAT changed, because each
caller already states which document it read. **A message written when there was
one caller becomes a false statement when a second arrives, and nothing fails —
the text is not type-checked and no test asserted it.**

## Class 2 verified 32/32 — and what my targeted test runs structurally cannot see

The suite after the class 2a commit came back **28/32**, and all four failures
were mine. The fix commit is `81bccf69`; the verifying run is **32/32** at that
commit. Class 2 is done.

**The useful part is WHY the pre-commit checks missed them.** I had run the new

changed files — and still shipped four failures. Two of the four were
unreachable by any test selection I would have thought to make:

| Failure | Why my selection could not find it |
| --- | --- |
| `type_check`, `pyright` | I ran pytest on the changed files, and mypy only on `git_commit_parsing.py` — not on the new handler |
| `error_hiding` + its self-scan | a repo-WIDE audit script, not a test of my module |
| `test_blocking_handler_evasion` | a registry in `tests/unit/`, and I had run `tests/integration/` |

The pattern: **a new file must satisfy repo-wide registries and repo-wide audits
that no test in its own directory mentions.** Choosing what to run from the diff
finds the first kind of failure and never the second. The full suite is the only
selection that is not a guess about where the couplings are.

**I declined the cheap fix on `error_hiding`, deliberately.** The violation was a
`return None` inside an `except OSError` body. Moving the return out of the
except body passes the AST check and changes nothing about the behaviour — that
is class 6 (`outcome-reachable-by-an-unenumerated-spelling`) and it would be
invisible in the diff. I refused the same respelling earlier in this plan and the
reasoning has not changed. The real fix is a typed result that carries the
reason, which the sibling handler already had; with a second caller it moved to
`utils/path_predicates.py` — whose stated thesis is "predicates that cannot raise
and cannot silently pick a side", and a text read is the same idea.

Its new tests include the case that would otherwise bite a caller: `text == ""`
is falsy, so an empty file and an unreadable one are indistinguishable to anyone
testing truthiness. The `reason` field is what separates them.

**The evasion registry deserved substance, not bookkeeping.** The failing test
says "silence is not a classification". The gate never denies, so there is no
block to respell around — but a respelling that made it SILENT hides a weakening
just as effectively, so I asserted the respellings rather than only registering
the handler. `git -C <path> commit`, `git --no-pager commit` and an absolute
`/usr/bin/git commit` all pass, because the subcommand is located with the same
evasion-hardened locator `destructive_git` uses. Registering without testing
would have recorded a judgement I had not actually made.

**A vacuous check I caught mid-fix.** I ran the error-hiding audit with a flag it
does not take, got a zero-byte file, and read that silence as "no violations".
An empty output file is not a passing check — the script reports on stdout, and
run properly it named the violation at once. Third instance today of the same
shape: *the absence of a complaint is only evidence if the checker actually
ran.*

## Class 3, instance 1: the fix I did NOT write, and the scope I cut mid-build

Detector RED at `2420e74c`, fix at `296204e5`, verified **32/32**. 584 modules
scanned, one violation, now zero.

The defect: `validate_eslint_on_write` prepended the GUARDED PROJECT's
`node_modules/.bin` to `PATH` and spawned bare `tsx`. Any package able to drop a
`tsx` shim into that directory got code execution in a daemon subprocess on the
next TypeScript write — inside the process that enforces every other guard — and
afterwards the daemon could not say which file it had run.

**The fix the worklist suggested, which I declined.** It offers two: "ship the
wrapper, or resolve `tsx` from a fixed path". Taken literally, the second means
pinning `tsx` to its absolute path inside the client's `node_modules/.bin` —
which turns the Detector green and leaves the exposure **exactly** where it was,
because that directory is still the client's. It would have been the third
appearance today of the same move I refused on `error_hiding` twice: changing
the SPELLING so a check stops firing. The defect is not "argv[0] is bare"; the
Detector uses that as a *symptom*. The defect is that a directory belonging to
the tree under review was prepended to PATH, so that is what came out.

**A fallback that looks like the defect and is not.** With no local `tsx`, the
command still goes out as a bare name — resolved from the environment the DAEMON
was started in, which the reviewed tree does not supply. Dropping that branch
would have silently stopped linting every project relying on a global `tsx`: a
regression wearing a security fix's clothes. Worth stating because the Detector
reads it as clean for a *reason* (its docstring says a bare name on the daemon's
own PATH is ordinary), not by oversight.

**I cut scope mid-build, and 15 failing tests were the signal.** My first draft
also pre-checked that `scripts/eslint-wrapper.ts` exists, so a missing wrapper
would deny by name instead of surfacing as a generic "Failed to run ESLint".
That is a real improvement and it is NOT class 3 — it changed behaviour for every
caller, and fifteen unrelated tests went red. **The temptation was to read those
fifteen as work to do rather than as evidence.** They were evidence: a security
fix that forces fifteen unrelated tests to be rewritten has stopped being a
security fix. Dropped and recorded as a follow-up.

**What the fix does not buy, written into the code rather than implied.** The
interpreter and the wrapper still come from the tree under review. That is class
3's general form and it stays open. Saying otherwise would be the cross-cutting
candidate this worklist already names — "the project asserts a control it does
not have" — committed by the very plan that catalogued it.

**Three old tests re-expressed, not deleted.** They asserted the PATH-prepending
contract. The property they protect is unchanged and still worth pinning — in a
monorepo a file must be linted by its OWN workspace's `tsx`, not the repo root's
— so they now assert argv[0]. A test deleted because the mechanism changed takes
its property with it silently.

## Class 4: the corpus's "single most valuable follow-up", measured — and the question was wrong

The worklist names one measurement as **the single most valuable follow-up in
the corpus**, to precede the owner's decision on F-BYPS-5 (the forwarder allows
any tool call the daemon takes longer than 30,000 ms to judge): *"if a
5,000-file commit judges in a couple of seconds the finding is theoretical; if
it judges in forty it is live."* Measured through `.claude/hooks/pre-tool-use`,
the real forwarder path the budget applies to, against throwaway repositories
under `untracked/`.

**By its own test, the answer is "theoretical".**

| staged files | median ms | % of 30 s budget |
| --- | --- | --- |
| 0 | 168 | 0.6% |
| 1,000 | 440 | 1.5% |
| 5,000 | 1,629 | 5.4% |

Linear, ~0.29 ms per file. Crossing 30 s by file count needs on the order of a
hundred thousand files.

**But file count is not the only input the caller chooses, and the other axis
answers differently.** `sensitive_content` scans added LINES, so cost follows
BYTES — and there the growth is superlinear:

| added text | median ms | % of budget |
| --- | --- | --- |
| 2 MiB | 421 | 1.4% |
| 4 MiB | 959 | 3.2% |
| 8 MiB | 3,509 | 11.7% |
| 16 MiB | 17,804 | **59.3%** |

Doubling 8 → 16 MiB cost 5.1x the time, not 2x. 16 MiB of added text is an
ordinary commit — vendored data, a generated fixture set, a lockfile dump.

**So the framing, not just the answer, needed correcting.** F-BYPS sized the
finding in FILES; the daemon's cost is driven by BYTES, and on that axis the
finding is within the same order of magnitude as the budget at realistic sizes.
A "5,000 files in 1.6 s, therefore theoretical" conclusion would have been true,
measured, and misleading — the right reading of my own first table only became
visible once I measured the axis the question did not ask about.

**What I will NOT claim.** During a sequential sweep, two runs landed at 30,069
and 30,072 ms — pinned to the budget, which is what an expiring 30,000 ms clock
looks like. A standalone 20 MiB run then judged in 6,223 ms. So a crossing is
OBSERVED but not reliably reproducible in isolation, and I am not asserting a
crossing point. Re-measuring at 8 MiB with the index rebuilt between every run
gave 3,420 / 3,469 / 3,557 / 3,526 / 3,401 ms — tight, and identical to the
repeat-without-restaging figures, which rules out a cross-call cache inflating
or deflating the table above. The sequential-sweep variance is unexplained and
is recorded as unexplained.

**A second finding, incidental but concrete**: the documented 4 MiB total
stand-down does NOT cap the cost. Cost keeps climbing steeply past 4 MiB, so
either the bound does not apply on this path or another component dominates.
Attribution to a specific handler is not done — the daemon's in-memory log had
already rolled past the probe events — and it is the obvious next step, because
it decides whether the remedy is a bound that works or a budget that is raised.

**Method note worth keeping**: both probes assert a CONTROL before printing a
conclusion — wall time must respond to the input being varied, or the figures
are noise from a repository the daemon never looked at. The file-count probe
reported 9.70x growth and the content probe 113x, so both earned their tables.
Without that, a probe pointed at the wrong repository produces a beautifully
formatted "the finding is theoretical".

**Standing**: unchanged — class 4's Detector and fix are both still to build,
and the fix stays owner-gated. What has changed is that the owner now has the
number the worklist said should precede the decision, and the axis it should be
measured on.
