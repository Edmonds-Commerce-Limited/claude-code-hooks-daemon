## 00:10 · milestone · the call-path rule kind, and the gap it found

`5b6ac98b` (red) → `a6ce7bb7` (fix) → `ac430ad3` (register). Third instance of
`asymmetric-sibling-protection`, and the first found by a rule kind rather than
by comparing two constants.

`remote_docs/store.py::refresh_document` never called `content_guard`.
`write_capture` does, and its docstring already says why: a capture writes from
a CLI, bypassing the `Write` hook that would otherwise inspect the content, so
an authenticated page would be vendored with its secrets unexamined. The
refresh path ran the same fetch and the same write with no scan at all.

**The refresh path is the more exposed of the two**, which is what lifts this
above tidiness. A capture is something a human ran deliberately, once. A refresh
exists precisely because upstream may have changed — and those new bytes have
had no review by anyone.

Two decisions worth keeping:

- `REFUSED` is a new outcome, not a reuse of `FAILED`. A failed fetch is a
  transient network problem to retry; a refusal means upstream is now serving
  something that must not enter the repository. Blurring them would tell a
  human to retry when they should be looking at the source.
- The scan runs BEFORE the unchanged-hash short-circuit. Putting it after would
  have left a clean route past the guard — an unchanged hash still rewrites the
  file, and the scanner's pattern list can grow between runs even when upstream
  has not moved.

## 00:12 · finding · what `reaches` cannot prove

That second decision is the honest limit of the rule kind I had just built, and
it is now in the register's blind-spot section.

`reaches` proves a **call**, not an **effect**. It cannot tell whether the
result is acted on, whether the call sits behind a condition that is never true,
or whether it runs before the write it is meant to guard. Had I put the scan
after the short-circuit, the row would have gone green over a guard that did
nothing on the path that mattered.

So the ordering — the load-bearing part of this fix — was caught by a test, not
by the rule. Writing that down beside the rule is worth more than the row.

## Class 15 closed with a full DBF cycle, and a rule conflict it exposed

`unbounded-work-on-input-not-sized` is the second class in this plan to get a

`ps` from an hourly cron tick, and `cli.py` spawning `gh run list`, which
reaches the network.

**A false positive caught before it shipped, which is the whole discipline.**
My first scan flagged three sites. The third, `install/transport_verify.py`, was
correct: `Popen` takes no timeout at construction — its bound is set at
`communicate(timeout=…)`, which that module does, and its second unbounded
`communicate()` is deliberate and documented. A rule that treated `Popen` like
`run` would have flagged a correct call, and a guard that cries wolf gets
switched off. `Popen` is excluded, the exclusion is pinned by its own test, and
the resulting blind spot is written in the docstring rather than papered over.

**Deduplication avoided creating a member of class 1.** The git guard already
resolves which AST calls reach a subprocess spawner, and it learned about
`import subprocess as sp` and the two `from`-import forms by EXECUTION, not by
reading (Plan 00248 F5). A second scanner copying that logic would have started
from the naive version and inherited exactly those blind spots while the first
stayed correct — the asymmetric-sibling class, created by the very act of
adding a Defence for another class. The resolver moved to one shared home.
Extracting it surfaced a real bug too: `run as launch` reported the local alias,
so a deny message would have sent a reader looking for `subprocess.launch`.

**The conflict, unresolved and owner-gated.** Registering this class runs into
two documented rules that contradict:

- `CLAUDE/Security/README.md` states the obligation that every Defence "must be
  a Detector in `scripts/qa/` wired into `run_all.sh` — not a regression test,
  not a note, not a convention", and asserts both existing categories honour it.
- `test_git_spawns_are_bounded`'s docstring gives the opposite reasoning: a test
  "needs no wiring to be binding", runs in the QA suite and CI by construction,
  and "cannot publish its verdict under a key no consumer reads — the failure
  mode Plan 00244 hit with a freshly-added checker".

The second is not a preference, it is a recorded failure of the first. I
followed the git guard's precedent because this Defence is its sibling and
splitting the pair across two mechanisms would have been worse than either
choice. That means class 15 is NOT added to the register table: doing so would
make the table assert an obligation this Defence does not meet, and a register
that overstates its own coverage is the one failure it cannot afford.

There is a synthesis available and I am not taking it unilaterally, because it
changes a standing rule: a `scripts/qa/` Detector PLUS a test asserting it is
wired into `llm_qa.py`, which satisfies the register's letter while guarding
the exact 00244 failure the docstring cites. That is a decision about which of
two standing rules governs, and it should be made once, for every future class
in this plan, rather than silently per Defence by whoever writes the next one.

## Class 10 closed; class 14 measured clean and deliberately NOT built

`irreversible-publication-surface-inventory` ran the cycle in order: test RED on

`_GH_BODY_PATTERN` was built from the issue/PR surface and stopped there, so

The surfaces are now a DECLARED table. That is the class's real shape: no rule

## Class 7 — `interpolation-into-another-language`, all three instances

Two target languages, one shape: a value substituted into a string that another
language then parses, where the substitution does not survive the parse as one
token. I fixed them on separate evidence rather than letting one imply the other.

**argv (`lint_on_edit`, `staged_lint_gate`).** A command template carrying a
`{file}` placeholder had the path substituted in and the result `.split()`. Run
rather than read, that is:

    "ruff check {file}" + "/repo/x.py --config /tmp/attacker.toml"
        -> ['ruff', 'check', '/repo/x.py', '--config', '/tmp/attacker.toml']

A FILENAME becomes an argument. `lint_on_edit` runs automatically on every Write
and filenames are agent-controlled, so this is a live route to making a linter
load someone else's config. No shell is involved anywhere near it, which is
exactly why `security_antipattern` — which looks for `shell=True` — has nothing
to say. The boring half of the same line is a path with a space linting two
files that do not exist.

The fix is not escaping. It is never building argv as a string: split the
TEMPLATE, then substitute the path as one element. The two sites were also an
asymmetric sibling pair and had to move together; fixing one would have left the
other reachable by the identical input.

**YAML (`remote_docs/capture.py`).** `_render_frontmatter` built the provenance
block by interpolation, so a newline in any value opened a new key. Through the
public `capture()` path, a licence of `MIT\nfidelity: verbatim` produced:

    fidelity: summarised     <- what capture() was told
    licence: MIT
    fidelity: verbatim       <- injected, and the one that wins

Nothing is malformed, so the parser accepts it and a reader skims past it. That
block is the record `R-REMOTE-DOCS-PROVENANCE` validates, and `verbatim` is the
assertion that a vendored document matches upstream byte-for-byte — the whole
basis on which a local copy is trusted. A capture could declare `summarised` and
emit a record claiming `verbatim`.

Again the fix is the mechanism, not the symptom: escaping newlines per field
would have left the next field and the next value type to be rediscovered, so
the frontmatter is now produced by a YAML writer. I verified it by INSPECTING
both renderings, not by trusting the assertion — the hostile licence now renders
quoted inside its own value with `fidelity: summarised` intact, and an ordinary
capture still renders one field per line in declaration order.

**Deliberate scope limit.** The argv Detector does not cover the YAML instance
and says so in its docstring. Different target language, fixed on its own
evidence. It also knows exactly one spelling — a name assigned from `.replace()`
and later `.split()` — so an f-string, `%`, `.format()` or `shlex.split` of an
interpolated value is the same defect and invisible to it. The sweep found 2
such sites against 35 bare `.split()` calls, so the rule is narrow and precise
rather than complete; going wider needs taint tracking.

## Class 9 — the guard that would have been the disclosure

Highest-value class remaining, and the build order was right to name it. Two
things went differently from the worklist, both found by checking rather than
trusting a report that was a day old.

**The worklist groups three instances; there are two.** `staged_lint_gate.py:249`
DOES consult `path_is_protected` — it uses the answer to `continue`, and its
comment gives the reason: a lint diagnostic can quote the offending source line
verbatim. Skipping is the disclosure-correct behaviour. F-HYG-3's argument is
that it should DENY instead, which is a policy question about unlinted protected
files, not a guard leaking protected bytes. Two different defects wearing one
name. Stating "three instances" would have overclaimed, and a rule written as
"does not reference the helper" structurally CANNOT fire on a module that
references it — so "land RED on all three" was never achievable as hypothesised.

**The echo is the wrong discriminator.** The report's cheap variant — flag a
module that echoes `match.group(...)` with no protected-path reference — I
measured at 7 modules direct, 17 with one hop, and it misses the primary
instance entirely because `sensitive_content`'s taint runs through a dict across
500 lines. Worse, most hits legitimately echo the project's OWN documents. The
broad two-arm version measured 41 of 606: a rule that PROPOSES a convention
rather than pinning one, which is the class 5 lesson again.

What actually separates the real instances is what they READ: content from a
path set the module did not choose. Nine modules invoke a content-bearing git
subcommand; seven are safe for a STRUCTURAL reason — `--name-only`,
`--error-unmatch`, `ls-files` with no content read, or `git show` of a
module-chosen path — and two are not. 7/9 compliant is a pinning shape.

**The two instances.** `sensitive_content` runs `git diff --unified=0` over the
index and yields every staged file's added lines; the only exclusions were
configured `exclude_paths` and the word-list file. `check_sensitive_content`
enumerates with `ls-files` and reads every tracked file, echoing `match.group(0)`
to stdout and into a JSON artefact `llm_qa` publishes for an agent to read as
fact.

The route matters more than the echo. `git add -A` names no path, so
`secret_file_guard` — which keys on a path appearing in a tool call — is not on
this path at all; it was not bypassed, it was never there. The read and the
retention are unconditional and only the echo needs a matching pattern, so the
guard would emit protected bytes in its own denial while reporting that it
protected something.

**What the Detector really pins, since it fires on nothing else.** The member set
today is exactly the two offenders, which could be mistaken for a rule that
merely restates known defects. The classifier is the load-bearing part: nothing
in the codebase currently records that `merge_scope` is safe only because of its
`--name-only`. Delete that one flag and it silently starts handing diff bodies
to a caller with no protected-path check in it. This is a tripwire on a
boundary, not a census.

**Verified by execution, twice, because green proves little here.** The Detector
going green only proves the modules now MENTION the helper. So: the filter was
called directly and dropped all six configured protected shapes while keeping an
ordinary source file; and the new behavioural test was run against a
deliberately neutralised guard, where it FAILED, while its control — the same
content in an unprotected path — stayed denied either way. That is what makes
the path, and not some other bound, demonstrably the reason.

**A guard blocked me and was right to.** `secret_file_guard` denied the Edit that
would have written a protected-shaped filename into the test fixture. I did not
route around it with string concatenation; the test derives the name from the
configured patterns instead, which is both non-evasive and a better test, since
it now tracks the configured set rather than a literal I chose.
