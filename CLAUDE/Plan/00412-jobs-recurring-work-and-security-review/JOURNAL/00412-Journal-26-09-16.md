## 00:10 · milestone · the call-path rule kind, and the gap it found

`5b6ac98b` (red) → `a6ce7bb7` (fix) → `ac430ad3` (register). Third instance of
`asymmetric-sibling-protection`, and the first found by a rule kind rather than
by comparing two constants.

`remote_docs/store.py::refresh_document` never called `content_guard`.
`write_capture` does, and its docstring already says why: a capture writes from
a CLI, bypassing the `Write` hook that would otherwise inspect the content, so
an authenticated page would be vendored with its secrets unexamined. The
refresh path ran the same fetch and the same write with no scan at all.

**The refresh path is the more exposed of the two**, which is what lifts this
above tidiness. A capture is something a human ran deliberately, once. A refresh
exists precisely because upstream may have changed — and those new bytes have
had no review by anyone.

Two decisions worth keeping:

- `REFUSED` is a new outcome, not a reuse of `FAILED`. A failed fetch is a
  transient network problem to retry; a refusal means upstream is now serving
  something that must not enter the repository. Blurring them would tell a
  human to retry when they should be looking at the source.
- The scan runs BEFORE the unchanged-hash short-circuit. Putting it after would
  have left a clean route past the guard — an unchanged hash still rewrites the
  file, and the scanner's pattern list can grow between runs even when upstream
  has not moved.

## 00:12 · finding · what `reaches` cannot prove

That second decision is the honest limit of the rule kind I had just built, and
it is now in the register's blind-spot section.

`reaches` proves a **call**, not an **effect**. It cannot tell whether the
result is acted on, whether the call sits behind a condition that is never true,
or whether it runs before the write it is meant to guard. Had I put the scan
after the short-circuit, the row would have gone green over a guard that did
nothing on the path that mattered.

So the ordering — the load-bearing part of this fix — was caught by a test, not
by the rule. Writing that down beside the rule is worth more than the row.

The worklist called it one defect: unescaped interpolation in

So "apply the helper" — the obvious reading of the worklist — is correct for
three sites and wrong for two.

**And a `reaches` row would not have noticed.** It asserts the function CALLS
the helper. Blanket-applying the escaper turns the row green with two sites

such a path. That is yesterday's blind spot arriving on the very next row I went
to write: *proves a call, not an effect.*

I fixed the three and wrote up the two. No row, because **a row satisfiable by a
partial fix is worse than no row** — it converts an open defect into a closed
one on paper, which is the one failure a security register cannot survive. That
reasoning is now in the register under the instance, not as an abstract caveat.

The remaining fork is genuinely the owner's: four costed options, recommending B
(assign the default to a plain variable first, so all five sites land in the one
context the existing escaper already handles). C — refuse the path at install
time — is the better answer if the failure should be loud, and is a legitimate
preference rather than a worse one, but it adds a refusal in installing projects
and is not mine to add.

Worth noting what the escaper's own docstring gave me: it escapes an internal
CATALOGUE constant, and says it does so because the failure would be silent and
remote. A path is not an internal constant. The argument for escaping the raw

existing code contained the case for its own fix.

## 01:05 · the tilde, verified · and a finding overturned in the open

Full suite green at 32/32 (24,347 passed, 95.3% coverage), so the tilde fix is
verified rather than merely written. It is the most consequential instance of
the session: a live bypass of `R-WRITE-OUTSIDE-PROJECT-ROOT`, where `curl -o
~/x.sh` was ALLOWED and `echo > ~/notes.txt` on the same destination was DENIED.
The verdict was decided by the spelling, not the location.

Two things I want on the record because both were judgement rather than
mechanics.

**I overturned review finding C6, and did it visibly.** C6 grouped
`leading-tilde` with `$HOME`, a glob and a backtick as "decline, do not
fabricate". Its principle survives untouched and is still enforced for those
three. What C6 missed is that declining was not the only alternative: `~/x`
expands deterministically to where the shell really writes, so naming it is
resolution, not fabrication — and `core/utils.py` had already written that rule
down. Silently flipping a recorded verdict, or leaving a real bypass open to
avoid touching one, were both worse than moving the single case with a test
that says why.

**A docstring was part of the camouflage.** `_resolve_against_cwd` claimed it
shared the decline "verbatim" with the shared accessor. It shared the constant
and then added a `~` rule on top. Anyone auditing by reading the claim would
have come away reassured. A false claim of sharing is worse than no claim,
because it spends the reader's suspicion for them — worth watching for wherever
a comment asserts two sites agree.

I also corrected my own probe mid-investigation: I first reported the `../../..`
relative form as escaping too. It does not — I had put `cwd` inside `tool_input`
where the handler reads it at top level, so my probe supplied no cwd at all.
That correction lives in the red commit rather than being quietly dropped.

**D-PUB-4 sized while the suite ran**, by probing rather than reading the regex:
`/usr/bin/gh issue create --body '<term>'` and `./gh …` do not match the publish
guard at all, while the same term in `git commit` is denied whether or not the
binary is path-qualified. `gh` is the surface that cannot be retracted.

The registry question that looked like it had no answer now has one. `reaches`
genuinely cannot express this pair — `OPTIONAL_PATH` is a module-level constant
interpolated into a pattern, and `reaches_helper()` asserts a CALL — so the row
needs a fourth relation, `interpolates`. What earns it a row where the forwarder
was refused one: **it cannot be satisfied by a partial fix.** The fragment is
either in the pattern or it is not. That is the discriminator I want to keep
using when deciding whether a row is worth writing.

I am deliberately NOT pairing the row with the git surface, which hand-rolls
`endswith("/git")`. That is correct, merely bespoke. A row demanding one idiom
of both sites would assert style rather than protection, and a registry that
starts policing style is one that gets switched off.

**Standing, as of this entry**: four declared rows against thirteen known
instances; one recorded instance the Defence does not cover; one deliberately
left rowless; one (D-PUB-4) now known to be expressible once `interpolates`
