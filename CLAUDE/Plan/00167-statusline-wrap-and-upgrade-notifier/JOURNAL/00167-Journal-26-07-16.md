## 08:05 · finding · — — status-line investigation (pre-plan research)

Root-caused the four status-line questions from two research agents +
direct code reading:

- **Assembly**: `core/hook_result.py:164-185` joins enabled `status_line`
  fragments with `" | "` and returns `{"text": text}`. ZERO width /
  truncation / wrapping logic — narrow terminals lose right-hand segments
  off the edge.
- **Wrap is feasible**: Claude Code officially renders multi-line status
  (one terminal row per `\n`), and exposes terminal size via `COLUMNS`/
  `LINES` **environment variables** (v2.1.153+), NOT in the JSON payload.
- **Transport gap**: the daemon is a separate process and does not inherit
  `COLUMNS`. The jq-free transport (`init.sh` `send_request_stdin`, Status
  branch ~L960) runs in the wrapper's env and already rewrites the Status
  payload — the correct single injection point to forward width/height.
- **Cron**: NO scheduled-cron data reaches the status line — not in Claude
  Code's Status JSON, and nothing daemon-side is reachable. Non-Goal.
- **Unused Status-input fields**: top-level `version`, `cwd`,
  `output_style`, `exceeds_200k_tokens`, `rate_limits.*`, `prompt_id`, plus
  nested `agent.*`/`pr.*`/`worktree.*`/`vim.*`. `rate_limits` + `version`
  are the highest-value unused fields.
