## 07:56 · finding · P1 — the mechanism, proven rather than reasoned

The owner reported the pattern and diagnosed it correctly in the report: the
folder name is not anchored to `.claude/`, so it matches any folder with that
name. Confirmed in a scratch repository before reading any daemon code, because
gitignore anchoring is exactly the kind of rule that is easy to recite and easy
to get backwards.

Method: a throwaway git repo containing both `.claude/skills/hooks-daemon/` and
`.claude/hooks-daemon/`, then `git check-ignore -v` against each, under the two
spellings of the pattern.

| pattern          | deployed skill tree | installed clone |
| ---------------- | ------------------- | --------------- |
| `hooks-daemon/`  | IGNORED — defect    | ignored — right |
| `/hooks-daemon/` | not ignored — right | ignored — right |

`check-ignore -v` prints the deciding `file:line:pattern`, which is why the
check this plan builds should ask git rather than parse patterns: git hands
over the remediation detail for free, and it is right about every spelling
rather than only the one we thought of.

## 07:56 · finding · P2 — where the bug is NOT

Three things had to be ruled out before filing, and each would have changed the
plan:

1. **This repository.** `.claude/.gitignore:9` is already `/hooks-daemon/`,
   anchored, with a comment saying why. `git check-ignore` confirms the skill
   tree is visible here. So the reported text is not from this tree.
2. **The installer.** `scripts/install/gitignore.sh` writes
   `hooks-daemon/untracked/` into `.claude/.gitignore` and
   `.claude/hooks-daemon/` into the root file. Both carry an INTERNAL slash,
   which anchors a pattern exactly as a leading one does, so neither is the
   source. A fix aimed at the installer would have been aimed at nothing.
3. **The existing handler.** `gitignore_safety_checker` runs on SessionStart
   and checks that required paths ARE ignored. It has no notion of a path that
   must NOT be — the reverse direction does not exist anywhere in the codebase.

So the defect reaches a client by being hand-written, or by predating Plan
00336 Task 4.3, and nothing announces it afterwards. That is the gap this plan
fills: not the pattern, the DETECTION.

## 07:56 · decision · — — detection reports, it does not edit

The plan will not auto-fix a project's `.gitignore`. An ignore file is the
project's own, and a wrong auto-fix un-ignores something deliberately hidden —
a strictly worse failure than the one being fixed, and a silent one. Naming the
file, the line, the pattern and the anchored replacement is the whole of what a
check can safely do.

One distinction to keep in the implementation: a deployed path that is ignored
BUT already tracked is a weaker finding than one ignored and untracked. Git
tracks what it already tracks, so the first is latent — it bites on a fresh
clone, or when an upgrade writes a NEW file beside the tracked one. Reporting
them identically would either cry wolf about a working checkout or understate a
live hole.
