## 10:20 · finding · — — live-session design burst (joseph driving)

A long live-debugging session on THIS opus-flagged session produced several
findings and a new wave of scope. Recording before compaction risk.

- **Detector recovered-vs-active fix** (agent, uncommitted pending QA):
  `model_fallback_detector` fired a LOUD alert at session start even though the
  fallback had recovered post-compaction. Root cause: it never checked whether a
  LATER assistant turn returned to the original model. Fix: `_scan_transcript`
  also collects `(line_index, model)` per assistant message; `_is_recovered`
  ⇒ soft no-🚨 notice for a recovered fallback, loud alert only for an active
  one (unknown original model stays ACTIVE, conservative). QA running (bsqnkx1lu).
- **Stale-worker myth debunked.** The `/model` flip-back was NOT firing, and I
  first mis-diagnosed the running `--worker` as stale (started 07:17, /model code
  committed 07:41). WRONG: 07:41 was a COMMIT time, not a DEPLOY time. The
  deployed file's mtime was 07:17:02 and its content (incl. the flip-back) never
  changed after, so the 07:17 worker already had the code. Proof: the host calls
  `reload_if_stale()` (content-hash) every ~5s on ticks; a `touch` (mtime-only)
  did NOT respawn it, but my later comment EDIT (content change) DID respawn it
  (pid 2946311 → 3487039). Two-tier hot-reload works. Committed dogfooding docs
  (comment + `.claude/rules/ccy-supervisor-dogfooding.md`, 649f7f7d).
- **Confirm-Enter = 1, VALIDATED.** joseph typed `/model fable` manually: it
  switched with exactly ONE confirming Enter. So a `/model` injection needs
  `payload + \r + <one more \r>`. This is why the flip-back never completed —
  the injection sent only one Enter. Building `confirm_enters` (default 1, env
  `CCY_MODEL_CONFIRM_ENTERS`) into `_perform_injection`.
- **xhigh-fable is wasteful — reset-to-floor is right.** joseph's manual
  `/model fable` KEPT xhigh (Claude Code does not touch effort on model switch);
  he had to `/effort low` by hand. Confirms the design: the supervisor's
  post-flip effort reset (`recovered_from_restore` → `/effort <floor>`, fable
  floor = low) is the sanctioned lowering. Automated path already bundles it.
- **Effort raise IS the supervisor, invisibly.** After the user set `/effort
  low`, effort went to xhigh on a fresh fable→opus flip. Claude Code never
  raises effort on a fallback → it was the supervisor's `/effort xhigh`
  (`_DOWNGRADE_TARGET_EFFORT`). Working, but with NO on-screen sign — the core
  observability gap.
- **SessionStart-only detection critique (joseph).** The detector scans only at
  SessionStart, so it catches a fallback CARRIED INTO a resumed session but is
  BLIND to mid-session flips (the common, actionable case). Fix planned: add a
  `UserPromptSubmit` live-scan sharing the scanner, so mid-session flips get the
  authoritative record + snapshot promptly. (Blocked on landing the recovery-fix
  commit first — it refactors the scanner.)
