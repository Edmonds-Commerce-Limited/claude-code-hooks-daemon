## 11:29 · decision · P1 — `explain_segment()` is read-only; the CLI icon
line is a labelled reference, not a live replay

Several handlers mutate on-disk state inside `handle()` (`ContextSidecarHandler`
writes a sidecar file, `MultithreadIndicatorHandler` upserts a heartbeat,
`DowngradeIndicatorHandler` persists per-session counters) — calling `handle()`
from a one-shot introspection CLI would pollute the REAL daemon's on-disk
state with synthetic CLI-session entries (e.g. inflating the live `🧵 Y/X`
thread count). `explain_segment()` is therefore a separate, explicitly
read-only method: each handler computes `current_value` from a read-only
peek at the same on-disk/live state `handle()` would read, without ever
calling `handle()` itself from the CLI path. Consequence: the CLI's rendered
"icon line" is a REFERENCE line built from each handler's own glyphs, labelled
as such — not a byte-identical replay of a live status-line render, which is
impossible anyway for model/context/effort/workspace-diff segments that only
exist inside a live Claude Code render payload. Recorded as a Non-Goal in
PLAN.md.

## 13:05 · action · T2.1 — explain_segment() implemented on all 14 handlers

Each read-only by construction (see the 11:29 decision above). Reused the
handler's OWN existing read-only internals where one exists, rather than
reimplementing detection logic a second time:
- `SupervisorIndicatorHandler`: calls its own `_detect_state()` /
  `_safe_active_message()` (status-file + /proc reads only, never a write;
  a throwaway instance's caches are discarded when the CLI exits).
- `UpgradeNotifierHandler`: calls its own `_detect_upgrade_segment()`
  (MtimeCachedFile-gated cache read).
- `MultithreadIndicatorHandler`: calls `thread_registry.read_live_entries()`
  directly — deliberately does NOT call `upsert_heartbeat`, which would
  inflate the live `🧵 Y/X` count real sessions see with a synthetic
  CLI-session heartbeat.
- `DowngradeIndicatorHandler`: no live session id exists outside a hook
  payload, so it glob-scans its state directory read-only and reports how
  many sessions currently show an open downgrade episode, rather than
  answering a specific-session question it cannot ask.
- `GitBranchHandler`: a single `run_git(cwd, "branch", "--show-current")`
  (the project's one blessed no-lock git wrapper) — deliberately bypasses
  `_render_git_context`'s render-TTL cache and the background auto-fetch
  scheduler, since the fetch thread genuinely mutates remote-tracking refs
  and must never run as a side effect of an introspection command.
- `ContextSidecarHandler`: `glyphs=()` — it never renders a visible icon by
  design, so `explain_segment()` says so and only counts (never reads the
  content of) existing sidecar files.
- `DaemonStatsHandler`: deliberately does NOT call `get_controller()` —
  that returns an in-process controller scoped to the one-shot CLI, whose
  uptime would misleadingly read near-zero instead of the real,
  separately-running daemon's. Points at `bin/hooks-daemon status` instead.
- The remaining 7 (`AccountDisplayHandler`, `CurrentTimeHandler`,
  `EnvironmentIndicatorHandler`, `GitRepoNameHandler`, `ModelContextHandler`,
  `StartupCleanupHandler`, `WorkingDirectoryHandler`): direct read-only
  peeks (MtimeCachedFile readers, `ProjectContext` accessors, or pure
  computation), each wrapped so `ProjectContext` not being initialised
  degrades to a "not shown now" message rather than raising —
  `EnvironmentIndicatorHandler` was caught missing this guard by the new
  completeness sweep below and fixed.

One new perf-guard allowlist entry was needed:
`tests/unit/handlers/status_line/test_no_ungated_render_reads.py`'s
`_ALLOWED_DIRECT_READS` gained `downgrade_indicator.py`, documented as never
running on the render path (`handle()` never calls the new code) — a
stronger justification than the two pre-existing entries, which admit a
real per-render cost this one simply doesn't have.
