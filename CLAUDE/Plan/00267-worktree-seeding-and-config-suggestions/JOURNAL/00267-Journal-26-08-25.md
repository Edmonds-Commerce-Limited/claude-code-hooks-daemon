## 09:44 · finding · P1 — the handler never resolves the repo root

Code-map findings that shaped the design:

- **`configure()` is a dead end.** Options are applied by
  `setattr(instance, f"_{key}", value)` *after* `__init__`. The two
  `configure()` methods in the tree are vestigial and the registry never calls
  them. Parse lazily into a memo field instead.
- **The handler takes the raw `cwd` from the payload** and never asks git for
  the top-level. So a session whose cwd is a subdirectory already creates
  worktrees in the wrong place, today, before this plan adds anything. That is
  a pre-existing bug and became Phase 1 — seeding cannot be built on it,
  because seeding must know the main checkout root to find its sources.
- **A version-independent "is my config good now" diff does not exist.**
  `check-config-migrations` is version-range gated; `/optimise` is an LLM skill
  with no code behind it. The dotted-path lookup helpers, the `UNSET` sentinel
  and the advisory dataclasses are all reusable as-is.
- **Live drift example**: this repo's own daemon config has no
  `worktree_create` block at all, while the shipped example config has one.
  That is precisely what the Phase 5 reporter should catch, and makes a natural
  first real-world test of it.

## 09:55 · decision · P1 — fall back to cwd, do not raise, when the root is unresolvable

FAIL FAST would argue for raising when `resolve_for` returns nothing. Rejected:
the resolver can return nothing for reasons other than "not a repo", and
raising would newly break worktree creation in environments that work today.
Falling back to the raw cwd makes the change strictly narrowing — behaviour
moves *only* in the case where a root resolves and differs — and a genuinely
non-repo cwd still fails loudly, because `git worktree add` refuses it anyway.
The warning log names the path so the degraded case is visible rather than
silent.

## 10:20 · decision · P2 — reject the two shapes a project will actually mistype

`parse_seed_config` refuses any non-mapping at the top level. The two likely
mistakes are a bare path string (`seed: .env.local`) and a bare list
(`seed: [.env.local]`), and NEITHER may be iterated — a string yields one
entry per character, which is exactly the silent no-op that made the
predecessor's misconfiguration undiagnosable. `entries:` given a string is
rejected for the same reason, with a test asserting no single-character paths
come back.

Unrecognised keys are reported rather than ignored, at both levels: a typo
like `mode:` where `default_mode:` was meant would otherwise be silently
dropped and the project would never learn its override did nothing.

## 10:55 · decision · P3 — validate and place are two functions, not one

`git worktree add` runs BETWEEN them. That ordering is the whole point: a
content error has to surface while there is still nothing to clean up. A
half-seeded worktree is worse than an unseeded one, because the agent working
inside it cannot tell which of its files are missing — it just behaves oddly.

The handler therefore calls `validate_seed_sources` before `mkdir`, and
`seed_worktree` after `git worktree add`. Both no-op on an empty list, so the
unconfigured path needs no special-casing. A handler test asserts the worktree
directory does NOT exist after a validation failure.

## 10:55 · decision · P3 — report every bad entry, not just the first

`validate_seed_sources` collects all problems and names them in one message.
Raising on the first would make fixing a misconfigured list an iterative
guessing game: fix one path, re-run, discover the next. A test pins that two
distinct offenders both appear.

## 10:55 · finding · P3 — the never-clobber check must test is_symlink FIRST

`exists()` follows links, so it is False for a *dangling* symlink. A check
written as `if dest.exists()` would therefore treat a broken link as "nothing
there" and clobber it. The predecessor's review had already credited this
ordering as a good instinct; it is preserved here with a test that plants a
dangling link at the destination and asserts it survives untouched.

## 10:55 · finding · P3 — the path guard bounds the LINK, not the TARGET

Rejecting absolute paths and `..` only constrains where a link is WRITTEN.
A path traversing a symlinked directory component inside the repo — a repo-root
`linkdir` pointing at somewhere outside — has no `..` and is not absolute, yet
still resolves outside the tree. Task 3.6 adds a `resolve()`-under-root
containment check, with a test that plants exactly that shape. This closes the
LOW finding the predecessor's review raised but did not act on, and it matters
more here than it did there because directories are now in scope.
