## 16:58 · decision · — — why this is a plan and not a ledger fix

Graduated from Plan 00381 N1. Worth recording WHY it moved rather than being
fixed in the ledger, because "it looked big" is not a reason.

The dedupe scout checked all 16 live plans plus the archived transport prior
art and found no overlap: 00294 built the toggle, its verification and its
auto-revert, and 00290 built the relay itself, but neither covers the case
where the toggle believes it has nothing to do. So this is new work on an
existing command, not a duplicate.

It earns a plan because the repair changes what a production command DOES in a
path that currently has zero side effects, and that path is the fast one. Three
decisions have to be made rather than assumed, and each can be got wrong
quietly:

- a reconcile that fails verification must NOT auto-revert, because the only
  state to revert to is the drift being repaired;
- `transport on` reconciling with no relay binary present would deploy a hot
  path pointing at nothing, so provisioning has to gate that direction;
- `changed` already means "the config flipped" and existing tests asserts it,
  so a reconcile cannot borrow it.

## 16:58 · finding · P2 — the drift detector already exists

Checked before designing one, and it is already built.
`regenerate_deployed_hooks` (`install/forwarder_generator.py:645`) scans EVERY
forwarder unconditionally, writes only when the generated content differs from
what is on disk, and returns the basenames it actually rewrote.

That is precisely the signal this plan needs, with the property that makes it
safe to call on the fast path: byte-identical-by-default. A converged project
gets an empty list back and nothing was written, so the clean no-op stays free.
Non-empty means drift, and names it.

So Phase 2 is a wiring change, not a new comparison. The docstring already
states the guarantee this plan will lean on, which is a good sign the guarantee
is intended rather than incidental.

## 17:04 · decision · T2.3 — provisioning gates the enable direction

Not obvious, and worth writing down because the wrong choice is silent.

A regenerated relay hot path NAMES the relay binary. So if a reconcile in the
`on` direction ran before provisioning, repairing drift would deploy a
forwarder pointing at a binary that is not there — re-creating the exact "green
enable with no relay engaged" failure that made provisioning a precondition of
the flip path in the first place (Plan 00294 defect D2).

Checked the cost before putting it on the fast path: `ensure_relay_binary`
returns immediately when the binary is present and executable, so a converged
project pays nothing. The only case where it does real work is binary absent
with a `relay_source` set — and there the forwarders reference a missing
binary, so provisioning is the right thing to do rather than waste.

The disable direction gets no such gate, deliberately: turning the relay off
never references the binary.

Pinned by a test that asserts the refusal leaves the forwarder without a hot
path AND restarts nothing — a refusal that still restarted would be a worse
bug than the one being fixed.

## 17:04 · finding · — — a test that was passing for the wrong reason

`test_on_when_on_is_a_clean_no_op` kept passing after the change, which was
suspicious rather than reassuring. It sets the config ON while the fixture's
forwarder carries no relay guard — so that project is DRIFTED, and the test now
exercises the reconcile path while its name claims a clean no-op.

Renamed to `test_on_when_on_leaves_the_config_alone` and tightened to assert
the config text is byte-identical before and after, which is what it can
honestly pin. The genuine no-op case is covered separately, with `calls == []`
proving nothing was restarted or probed.

Left as-is it would have been a trap: the next person to change this path would
read "clean no-op" and believe the fast path was covered when it was not.
