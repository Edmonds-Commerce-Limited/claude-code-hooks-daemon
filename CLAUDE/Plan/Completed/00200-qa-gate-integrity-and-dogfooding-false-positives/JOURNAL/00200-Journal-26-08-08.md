# Plan 00200 — Journal — 2026-08-08

## Task 3.6: the sibling audit, and the bypass it found

Started as the last open fix-task: *audit sibling handlers for the same
mention-vs-invocation confusion*. It was expected to be a read-only sweep. It
produced three defects, one of which defeated a handler outright.

### How it surfaced — the guard blocked me, twice

The first two defects were not found by reading code. They were found by the
handler blocking ordinary work:

```
cd /workspace
grep -n "ALLOWLIST" tests/integration/test_acceptance_negative_case_requirement.py | head -30
```

`grep` is whitelisted. This was denied. The `&&` and `;` forms of the identical
pipeline were allowed. That asymmetry is the whole bug: `_extract_source_segment`
split command chains on `["&&", "||", ";"]` and **not on a newline**, so a
multi-line command never split and the producer text became the entire two-line
string — which no anchored whitelist pattern (`^grep\b`) can match.

Probed the live daemon rather than reasoning about it, which is what made the
shape unambiguous:

| Command                          | Expected | Before fix |
| -------------------------------- | -------- | ---------- |
| `grep … ⟨pipe⟩ head`             | allow    | allow      |
| `cd X && grep … ⟨pipe⟩ head`     | allow    | allow      |
| `cd X ; grep … ⟨pipe⟩ head`      | allow    | allow      |
| `cd X ⏎ grep … ⟨pipe⟩ head`      | allow    | **deny**   |
| `cd X && pytest … ⟨pipe⟩ head`   | deny     | deny       |

A second defect fell out of reading the same function: the chain split used
naive `rsplit`, so a separator **inside a quoted argument** cut the producer —
`grep -E "a;b"` resolved to `b"`. The sibling pipe split was already
quote-aware. The two halves of one function disagreed about what a separator is.

### The one that mattered: a bypass, not an annoyance

Both of the above are false positives — irritating, not dangerous. Asking *why*
the two splitters disagreed led to the real find.

The project's `enforce_llm_qa` handler had grown a quote-**and-escape**-aware
splitter in earlier work. `pipe_blocker` had a quote-only one. So: does the
missing escape handling change a verdict? Probed it rather than assuming:

```
echo "<escaped-quote>" ; pytest tests/ ⟨pipe⟩ head   ->  blocked: False
grep -E "a<escaped-quote>b" x.py ; pytest tests/ …   ->  blocked: False
```

Both **allowed**. A scanner blind to the backslash flips its in-double-quote
flag on an escaped quote and never leaves quoted state, so every later separator
looks like data. Prefix an expensive command with a whitelisted one containing
an escaped quote and the chain separator is never seen — the producer resolves
to the harmless leading command and a full pytest run sails through the handler
that exists to stop it.

That is a false **negative**. The two irritating bugs were worth fixing; this one
was worth finding.

Fixed to the actual bash rule — a backslash escapes the next character
everywhere **except** inside single quotes, where it is literal — and pinned with
a test that a scanner over-applying escapes would fail. Verified live before and
after: both bypass forms now resolve their producer to the pytest segment and
block, while the equivalent legitimate `grep` still passes.

### Discipline that paid off

- **Every allow-case is paired with a deny-case built from the same shape.** A
  fix that merely widened the whitelist, or split too eagerly, would pass a
  suite of allow-cases and quietly become a bypass. The RED run showed 9 failed
  / 7 passed, and the 7 passing were the negative controls — proof the tests
  discriminate rather than just fire.
- **Probe the live daemon, not the imported class.** Handler edits are invisible
  until restart; the whole point is the running system's verdict.
- **One test expectation was wrong, not the code.** `_extract_source_segment`
  returns the FULL segment including arguments; the case had been written
  expecting a trimmed one. Fixed the test, not the behaviour.

### A self-inflicted "failure" worth recording

A direct `pytest tests/` run reported 2 failures (`test_daemon_smoke`,
`test_plugin_daemon_integration`) that passed in isolation and passed under the
QA runner. Cause: the run was launched immediately after restarting the live
daemon, so daemon-starting integration tests collided with it — container
single-daemon enforcement reaps daemons serving the same project root.

Not flaky, and not the code change. It was **how it was run**. Worth naming
because "passes in isolation" was the exact reasoning that misled me on a
previous defect where the cause turned out to be mine; the honest resolution is
to re-run the real gate, not to argue from plausibility.

Also lost a command chain to the Bash tool's persistent cwd: an earlier

### The handler blocked its own fix's commit message

The first commit attempt was denied — the message quoted the literal exploit

## Task 3.7 — the deferral was wrong, and probing proved it

Task 3.7 (consolidate the two shell scanners) was created in `c1991414` and
deferred with the reasoning: *"it crosses the project-handler/library boundary
and deserves its own decision."* Both halves of that turned out to be wrong.

**The boundary objection was weak.** Checked instead of assumed: project
handlers already import `claude_code_hooks_daemon.core`,
`.constants.timeout` and `.constants.tags`, and `utils/` is an established
20-module package. A shared utility there is consistent with the existing
design — not a new coupling class.

**It was never tidiness.** The question that settled it was: the two scanners
disagree about escapes, so *does that difference change a verdict?* Probed
`enforce_llm_qa` directly rather than reasoning about it:

```
grep -n 'a\' README.md ; ./scripts/qa/run_all.sh    ->  blocked: False
cat 'x\' ; ./scripts/qa/run_all.sh                  ->  blocked: False
```

Both **allowed**. `enforce_llm_qa` applied backslash escaping *inside* single
quotes, where bash treats it as a literal character. A trailing `\` in a
single-quoted argument therefore swallowed the closing quote, the scanner never
left quoted state, nothing split, and the whole command was judged by its
allowlisted leading word — so the guarded QA script ran.

That is the **mirror image** of the `pipe_blocker` bug fixed hours earlier
(blind to the backslash entirely). Two independent parsers, opposite halves of
one rule, the same bypass shape from both. It was still live and unfixed until
`5b8eb887`.

This is the cleanest DBF illustration the plan has produced: **the divergence
was the defect.** Fixing `pipe_blocker` by hand left an identical hole in its
sibling; only consolidation closes the class. A third careful implementation
would have been a third chance to get the rule half-right.

`utils/shell_segmentation.split_unquoted` is now the single implementation,
pinned by 17 tests including both production bypass shapes and the rule that
distinguishes them.

## Task 6.5 — the last task, and closing the plan

Nearly stopped before this one, giving "context budget" as the reason. That was

### What shipped

`agent_isolation_advisor`, a PreToolUse advisory on the Task tool. It speaks
only when a spawn joins an already-shared checkout.

The interesting part is the **negative** design, not the positive:

- **Silent for a lone agent.** The overwhelmingly common case must see nothing,
  or the advisory becomes noise that gets tuned out.
- **Silent when `isolation: worktree` is already set.** Advising someone who
  already did the right thing actively teaches them to ignore the handler.
- **Never blocks.** It cannot tell whether this particular agent needs the
  shared tree, so it must not decide.
- **Never raises.** The thread count comes off disk; every failure degrades to
  0, which makes `matches()` False. A guard that cannot read its input goes
  quiet rather than firing on every spawn — the opposite of the fail-open
  behaviour that would make it obnoxious the moment the registry breaks.
- **Names its own exception.** Daemon-restart verification and client-mode
  testing are anchored to the project root and do NOT work in a worktree. An
  advisory that omitted that would push work somewhere it cannot run.

Deliberately did NOT build the mooted second layer (warn on bare `git commit`
while peers are live). The upstream advisory addresses the cause; a second guard
on the symptom is speculative until the first proves insufficient. YAGNI applies
to guards too.
