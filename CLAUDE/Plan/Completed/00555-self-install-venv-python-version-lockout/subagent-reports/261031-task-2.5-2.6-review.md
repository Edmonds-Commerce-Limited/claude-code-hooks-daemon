## CRITICAL

### C1. Project-configured protected globs that contain a `/` are not enforced (Confidence 95%)

**Location:** `init.sh:362-369` (`_is_protected`, specifically `fnmatch.fnmatchcase(base, glob) or fnmatch.fnmatchcase(norm, glob)`).

**Problem:** The snapshot holds the globs that `secret_file_guard` enforces in the daemon's own dialect (`utils/path_exclusion.py`). In that dialect a glob is matched against the path relative to the project root and is unanchored: `config/creds.yml` matches at any depth, `secrets/**` matches a whole directory, and a leading `/` anchors the glob to the project root. init.sh instead tests each glob with `fnmatchcase` against the basename and the absolute path. As a result, any configured glob that contains a `/` (other than a leading `**/`) never matches.

**Bypass (confirmed by probe):** the snapshot holds `config/credentials.yml`, `secrets/**` and `/deploy/key.json`. The daemon matcher protects all three (see `probe_daemon_matcher.py`). The daemon-down judge allows every one of these:

- `cat config/credentials.yml`
- `cat secrets/db.txt`
- `cat deploy/key.json`
- `Read <proj>/config/credentials.yml`
- `Read <proj>/secrets/db.txt`

The same gap applies to `head`/`tail`. It also applies whenever the snapshot is missing: the ruling accepts defaults plus the `.claude/` lockdown in that case, but then no configured glob outside `.claude/` is enforced at all.

**Why it matters:** A project that protects a credential file by path, which is the normal way to protect a path that is not a basename pattern, has that file readable by a plain `cat` or `Read` whenever the daemon is down. This is exactly what the ruling's matcher clause 4 forbids ("or when it matches the project's configured `protected_paths`"). The tests miss it because the only custom-glob test uses `*.pem`, a basename glob (`test_a_custom_snapshot_glob_is_honoured`).

**Fix:** Implement the daemon dialect in the stdlib-only string:

- Compute the project-relative form of both the spelled path and the realpath.
- Treat a leading `/` as anchored to the project root.
- Otherwise allow any number of leading directories.
- `**` matches across segments; `*` and `?` match within one segment.

`path_exclusion.py` is already stdlib-only and documents this dialect. Copy `_tokenize_glob` and `_glob_fullmatch`, then pin parity with a test that runs both matchers over a shared table of globs × paths: anchored, directory `/**`, mid-path `**/`, and basename globs. Add red tests for the three shapes above.

## IMPORTANT

### I1. `..` after a symlinked directory escapes the containment check: the judge normalises before it resolves (Confidence 90%)

**Location:** `init.sh:399-402` (`absolute = os.path.normpath(os.path.join(cwd, raw))`, then `real = os.path.realpath(absolute)`).

**Problem:** `normpath` collapses `x/..` lexically before `realpath` runs, so the realpath is taken of a path the kernel will never open. The shell resolves `lnk/..` physically, to the parent of the link's target. The docstring's claim that "a symlink or .. cannot launder it" is false for Bash heads. Read is unaffected, because Claude Code's Read normalises lexically too.

**Bypass (confirmed):** `lnk` is a symlink inside the project to `/elsewhere/inner`, and `<proj>/README.md` exists. The judge allows `cat lnk/../README.md`, and the command prints `/elsewhere/README.md` ("OUTSIDE CONTENT" in the probe). That breaks the "inside the project or daemon root" rule. The same route also defeats full-path and configured globs, because the judge checks a different file from the one `cat` opens. A basename default still catches a protected basename, since the basename does not change.

Under the careless-agent threat model this spelling is unlikely, so the severity is IMPORTANT rather than CRITICAL. It is still a real gap in a function whose only job is containment.

**Fix:** Resolve the raw spelling directly with `real = os.path.realpath(os.path.join(cwd, raw))`, without `normpath` first, and apply both `_is_protected` and the root-containment test to that value. Keep the lexical check as a second check. Add `cat lnk/../README.md` with an outside target as a red test.

### I2. The stop-bound reset after `start_daemon` can make the bound unreachable (Confidence 80%)

**Location:** `init.sh:3364` (`_hooks_daemon_reset_stop_bound` in `ensure_daemon`) and `init.sh:3302-3315`.

**Problem:** `start_daemon` returns 0 once a pid is alive and the socket exists (`init.sh:2616-2635`), or immediately if `is_daemon_running` succeeds (`init.sh:2523`). Neither proves the daemon served a request.

Consider a daemon that binds and then dies, for example on handler load after the bind, or a crash-on-first-request loop. Each Stop then runs:

1. `ensure_daemon` starts the daemon, so the counters are deleted.
2. `forward_stop_event` gets `socket_not_found` or `connection_refused`, so the count goes to 1 and the stop blocks.

The count never reaches 3. That reproduces the unbounded block from the incident, which is the failure Task 2.6 exists to remove.

The reset is also redundant: a daemon that really serves resets the count through the transport (`init.sh:4221-4222`). On top of that, it wipes the counters of every session, not just the caller's. No test exercises this path; there is no grep hit for `reset_stop_bound` or `start_daemon` in either new test file.

**Fix:** Delete the `ensure_daemon` reset and rely on the per-session transport reset, which only fires on a parsed daemon response. Add a red test where the start appears to succeed but the socket refuses every connection, and assert that the third Stop is allowed.

### I3. Quarantined `*-opus-security-DETAIL*` artefacts are readable while the daemon is down (Confidence 85%)

**Location:** `init.sh:362-389` (`_is_protected` knows only the secret globs, plus the `.claude/hooks-daemon/`, events and `.sock` rules).

**Problem:** `quarantine_artefact_read_guard` normally denies Read, `cat`, `head` and `tail` of `*-opus-security-DETAIL*` in the coordinator. The daemon-down set has no equivalent rule, so the guard simply disappears during an outage.

**Bypass (confirmed):** `cat CLAUDE/reports/x-opus-security-DETAIL.md` and `Read <proj>/CLAUDE/reports/x-opus-security-DETAIL.md` are both allowed.

The ruling's wording ("must NOT match the protected-path matcher") did not list this guard, but its principle does cover it: nothing in the set may reveal content that a running daemon refuses to reveal.

**Fix:** Write the quarantine guard's effective globs into the snapshot, either as a second section or as a second file. Add `*-opus-security-DETAIL*` to the built-in defaults so a missing snapshot still protects. Test both.

### I4. The log-reading rationale does not hold, and the daemon-runtime rule depends on install mode (Confidence 80%)

**Location:** `init.sh:379-381`.

**Problem:** In a client install, everything under `.claude/hooks-daemon/` except `bin/` is denied, including the logs:

- `cat .claude/hooks-daemon/untracked/logs/daemon.log` and `tail -n 50 ...` are denied (confirmed by probe).
- The venv bootstrap log, `.venv-bootstrap-*.log` in the daemon's `untracked/`, is denied too.

So `head`/`tail`, which the ruling added because "the build log and daemon log are large", cannot read either log in a client project. The build report acknowledges this.

In self-install mode the daemon root is the project root, so the rule never applies. There, the daemon-runtime artefacts that `utils/private_io.py` calls known-sensitive are readable:

- `untracked/payload-capture/` (raw Write/Edit bodies)
- the verdict log
- the stop-event log

The same artefact is protected or exposed depending only on the layout.

**Fix:** State the rule in terms of the daemon untracked directory, in both modes:

- Allow only a named log allowlist: `logs/`, `.venv-bootstrap*.log`, `.venv-bootstrap.result`.
- Deny `payload-capture/`, the verdict and stop-event logs, `events*` and `*.sock`.
- Keep the rest of `.claude/hooks-daemon/` denied.

The ruling itself is contradictory here, since clause 4 denies `.claude/hooks-daemon/**` while the rationale wants the logs readable. Raise that with the owner rather than resolving it silently.

## SUGGESTIONS

### S1. The snapshot goes stale in exactly the outage case

**Location:** `src/claude_code_hooks_daemon/daemon/server.py:1483` and `utils/secret_file_matching.py:241`.

The snapshot is written only at start. If a human adds a protected glob and the restart then fails, for example because that config edit broke the daemon, init.sh keeps using the old snapshot, and the new glob is never enforced. The ruling asked for a write "at startup and on config reload".

**Fix:** In `_snapshot_globs`, treat the snapshot as absent (which triggers the lockdown) when `.claude/hooks-daemon.yaml` has a newer mtime than the snapshot.

### S2. SubagentStop shares one counter across concurrent sub-agents and reads the parent's transcript

**Location:** `init.sh:538-540` and `init.sh:599-616`.

The key is the parent `session_id` plus the event name, so three concurrent sub-agents each stopping once release the third one without it ever being blocked. Also, `transcript_path` on SubagentStop is the parent's transcript, so a sub-agent's own `[awaiting-human]` is never seen. The ruling specified this key, so this is not a deviation.

**Fix:** When `agent_id` and `agent_transcript_path` are present, use them.

### S3. An uncaught non-OSError in `_stop_bound` fails open on the transport path

**Location:** `init.sh:599-650`.

Two cases escape the handlers:

- `int(text)` at `init.sh:628` raises `ValueError` for a counter with more than 4300 digits, and only `OSError` is caught there.
- `json.loads` in `_last_assistant_text` can raise `RecursionError` on a deeply nested line, and only `OSError` and `ValueError` are caught around it.

Either exception crashes the transport python. `forward_stop_event` (`init.sh:4350-4364`) then treats the unparseable output as allow. Neither input is controllable by the agent while the daemon is down, so the impact is low.

**Fix:** Wrap the whole body of `_stop_bound` in `except Exception`, returning `None` (keep blocking) with a message on stderr.

### S4. `git status` is not strictly read-only

`git status` opportunistically rewrites `.git/index` when it refreshes the index. It also runs a repo-configured `core.fsmonitor` program if one is set. The ruling says "Nothing in this list may write, exec".

**Fix:** Either drop `git status`, or record this as an accepted residual in the plan.

### S5. A daemon that is reached but broken still wedges Stop without a bound

`connection_lost` and `malformed_response` on Stop set `daemon_reached`, so they never count (`init.sh:3967`). A daemon that accepts a connection and then crashes on every request therefore blocks every stop indefinitely. That is the incident's cost in a different shape.

**Fix:** Count the classes that were reached but returned no verdict, under their own `reason_class`. Keep `socket_timeout` and `invalid_hook_input` excluded.

## Verified not bypassable (probed or traced)

The shell-metacharacter rule holds. Each of these is denied:

- NBSP, U+2028 and vertical tab, through the `isprintable` check
- `#` comments
- `KEY=value` env prefixes
- `cat --`
- `ls -R`
- `git log -p`
- `git log --output=`
- `git log --ext-diff`
- `git -c ...`

Symlinks are handled correctly for Read and `cat` alike: a symlink to a protected file and `sub/../<protected basename>` are both denied. Paths outside the roots are denied, `/proc/self/environ` included; the only `/proc` path that gets through, `/proc/self/root/<proj>/...`, resolves to the same project file.

Errors do not fail open on the PreToolUse paths:

- A python crash in the emit_hook_error judge exits 1, which denies.
- A crash in the transport goes to `_hooks_daemon_static_deny`.
- A missing, unreadable, non-UTF-8 or directory snapshot gives the lockdown.

A relay hand-off stays limited to recovery commands only. While the daemon is down the agent cannot write the counter, so it cannot reset or inflate it; the only lever the agent has is `hooks-daemon stop`, which the ruling accepts.
