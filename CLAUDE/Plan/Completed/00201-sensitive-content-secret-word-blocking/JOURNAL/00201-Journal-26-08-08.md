## Task 4.5 — the live dogfood, done under 5.4's rule

This is the one that actually needed doing, and it is the security property the
entire plan exists for. Executed against a **temp** word list, never the
operational one, exactly as Task 5.4 prescribes:

1. temp list at `untracked/dogfood-words.secret` with one sentinel term
2. `secret_word_list_path` repointed at it, daemon restarted
3. a real `Write` containing the term sent through the deployed forwarder
4. every file under `untracked/` scanned for the term
5. config restored, daemon restarted, operational list verified intact

Result — both halves of the contract hold:

```
decision            : deny
term in deny reason : False
reason excerpt      : 'SENSITIVE CONTENT BLOCKED: ... (entry 1 of 1 in the secret word list).'
leaked into         : NOTHING
```

The second half is the whole point. A handler that blocks the term but then
writes it into a log has **moved** the leak, not closed it. The deny reason
names only an index, which is meaningless without the gitignored file it refers
to.

Afterwards: real list confirmed at 12 entries, still gitignored, still
untracked, working tree clean.

## Task 5.4 — putting the rule where it will be read

The recorded incident: a previous dogfood overwrote the operational
`.claude/block-words.secret` with a throwaway term, and **nothing failed**. The
guard silently stopped guarding and the QA scanner started reporting a cleaner
tree than reality — the precise failure mode that lets a redaction be declared
finished with identifiers still in it.

The plan described the durable fix but never applied it anywhere enforceable.
It now lives in the `safety_notes` of the very acceptance test that tempts an
agent to touch the real list, together with *why* — because the failure is
silent, nothing else will tell you.

Being explicit about the limit: no stronger guard is available here. The file
is deliberately untracked and gitignored, so git cannot detect an overwrite,
and it must stay hand-editable, so it cannot be made read-only. Guidance at the
point of use is the honest ceiling, not a placeholder for something better.

## A correction to the plan's own scope

The success criteria listed **four** leak vectors. There were five: the
daemon's blocking-response debug log in `server.py` was missed, and found only
by re-reading the log sites instead of trusting the list. Closed in `ceddf020`.

The follow-up `60412be2` matters more than the redaction: the log predicate was
a substring test over the serialised response, so anything whose text contained
"deny"/"block" was logged as a block. The status line reports `🛡️ N blocks`, so
every render — roughly three a second — was written under a "BLOCKING RESPONSE"
label. That is *how* an account name reached a log about blocking decisions.
Redaction stopped the leak; the structural predicate stopped the mislabelling.
