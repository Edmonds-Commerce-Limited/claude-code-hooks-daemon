## 13:20 · finding · T2.1–T2.3 — the plan's own "test doesn't exist" premise was wrong

`tests/unit/daemon/test_default_enabled_template_consistency.py` already
exists and already passes (7/7). It is a generic cross-handler drift guard:
it fails if ANY handler either (a) overrides `get_default_enabled()` to
`False` without the template marking it `enabled: false` to match, or (b) the
template marks a handler `enabled: false` without a matching override.
`ask_user_question_blocker` overrides neither, so both directions are already
covered for it. Added a direct per-handler pin anyway
(`test_default_enabled_is_true` in `test_ask_user_question_blocker.py`),
matching the convention already used by ~12 other opt-out handlers
(`test_command_hints.py`, `test_secret_file_guard.py`, etc.) — a readable,
single-handler failure message alongside the generic guard, not a
replacement for it.

## 13:40 · finding · T2.2 — but the RUNTIME default was never actually off

Traced the real registration path (not the Pydantic `HandlerConfig` model,
which turned out to be a parallel/validation-only path):
`HandlerRegistry.discover()` in `handlers/registry.py` resolves each
handler's config as `event_config.get(config_key, {})` then skips only when
`not handler_config.get(ConfigKey.ENABLED, True)`. For a handler key absent
from a project's `hooks-daemon.yaml` entirely (true for every fresh install
before today's template fix, AND for any pre-existing project's config
written before this handler existed), that resolves to `enabled=True` by the
hardcoded literal default. `git log -S` on that exact line shows it predates
even Plan 00012 — it goes back to the initial commit, long before
`ask_user_question_blocker` shipped in Plan 00108 (commit `15211df5`,
2026-05-15, CHANGELOG v3.14.0). So: this handler has been functionally
enabled-by-default since the day it shipped. Today's template/doc/test edits
make that already-true fact visible and protected — they change no runtime
behaviour for any existing install.
