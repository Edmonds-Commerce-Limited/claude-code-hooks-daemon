Claim "git remote get-url, stat, /proc checks" verified.

## 2. send_request_stdin (init.sh:2925-3660)

- Rungs: (1) the Rust relay guard is NOT in send_request_stdin; it is a generated block at the top of each forwarder, and status-line has none. (2) nc rung, init.sh:2980-3020: needs `-z "$response_mode"`, a per-event sock name, HOOKS_DAEMON_NC_UNIX_CAPABLE=1 and nc present. (3) python3 rung, init.sh:3041-3645.
- Claim verified: response_mode "status" skips nc (2968-2970 comment, 2980 condition). Stated reason: render_status/print_worktree logic (init.sh:3451-3496) is not to be duplicated in bash. Real constraints behind it: the reply is JSON `{"text": "...🧵...\u001b[..."}` with surrogate-pair and \\u001b escapes, so extracting .text needs a JSON decoder (bash printf %b cannot do surrogate pairs; the project is deliberately jq-free, Plan 00156); the `.error` -> "ERROR: ..." and empty -> "NO STATUS DATA" fallbacks; and the python rung injects hook_event_name=Status and COLUMNS/LINES -> terminal_columns/terminal_lines (init.sh:3512-3521, Plan 00167), which a byte pump cannot do. nc half-close is NOT the constraint: `nc -U -N` works (see 3).
- python3 resolution: bare `python3` on PATH (init.sh:3041), not the venv. Same in \_detect_unsupported_python (:1379,1394). Venv path is resolved only by \_resolve_python_cmd (:1415, sources scripts/lib/resolve_venv.sh) and used by cli helpers, not by this call. Here PATH python3 = /usr/bin/python3 -> /usr/bin/python3.11; no pyenv shim in this container, so the issue's 0.4 CPU-s shim cost is NOT reproducible here (it is plausible on a pyenv host; unverified).

## 5. Cheapest no-new-toolchain options (RECOMMENDATIONS, ranked by estimated saving)

1. Status-only fast path at the TOP of .claude/hooks/status-line, before `source init.sh` (saves ~25 ms source + ~30 ms forks, up to ~55 of ~80 ms): if the status socket exists, send via the relay binary if executable else `nc -U -N`, extract text, print; on any failure, fall through to the existing full path unchanged. Needs: (a) text extraction without python: options are a server-side change so the status socket replies raw text (daemon already knows it is Status; the status socket is already special-cased), or a bash/awk unescape of `"text"` (surrogate pairs make this fragile); (b) terminal size: the python rung forwards COLUMNS/LINES, a byte pump cannot, so either the daemon reads them from a client-added JSON field (bash can splice with printf into the payload only by parsing, fragile) or accept losing Plan 00167 behaviour on the fast path; (c) the fast path skips is_daemon_running proof, ensure_daemon, "venv building"/DAEMON FAILED/VERSION_MISMATCH texts (Plan 00488, issue #72, init.sh:2866-2904) - these must remain on the fall-through path, which is naturally triggered because the socket would be absent or refuse. Risk: a hung (not dead) daemon makes a socket client wait; needs a short -w (nc) / --timeout-ms and fall-through.
2. Move the 3 dirname calls, git remote get-url (init.sh:1303), tr lower-casing to bash builtins/parameter expansion, or cache them: saves ~10-20 ms on every hook, not only status; low risk, but touches an install-wide file with extensive tests.
3. Resolve interpreter once to an absolute path: ~0 saving here (venv python 28 ms vs system 24 ms), but avoids pyenv shim cost (issue's 0.4 s) on hosts that have it; cheap, but the python rung is stdlib-only by design so a bare system python3 is deliberate; an absolute path cached under untracked/ risks staleness.
4. nc for status (drop `-z "$response_mode"` for status): saves ~20 ms of python startup but still needs JSON text extraction (see 1a); nc -U -N verified here (OpenBSD nc, `-N` present). socat is not installed; other nc variants (traditional/GNU) may lack -U/-N, hence the existing HOOKS_DAEMON_NC_UNIX_CAPABLE probe (transport_probe.py).
5. Daemon caches rendered text: already done (15.75 ms render, TTL cache). No client-side saving.
6. Reduce refreshInterval from 1 (settings.json:12; Plan 00175 made it first-class): the biggest lever per second (halving ticks halves cost) at the price of staler display; trivial.
7. Enable relay for status by making the daemon's status socket return raw text and removing Status from the exclusion: smallest code change that makes the existing Rust relay serve status (~7 ms), requires relay_enabled and the binary present (build needs rustc+musl target or relay_source: download), and the guard still falls back to the bash forwarder when the socket or binary is missing.

## 6. A compiled client (Go/Rust) would need

Connect to <untracked>/events-<host>/status-line.sock (or legacy daemon-<host>.sock with envelope {"event":"Status","hook_input":...}); send stdin; half-close; read to EOF; JSON-decode .text/.error and print (std-only Rust has no JSON parser: hand-rolled unescape, or daemon emits raw text); forward COLUMNS/LINES; timeout; on connect failure exec the bash forwarder (relay already does this). Distribution: the daemon installs from a git clone plus Python venv with no compiler assumed; the existing relay answers this with source-built (rustc+musl, relay_source: build) or digest-verified download (relay_source: download) and always falls back to bash; a Go client would add a second toolchain (go 1.19 here) and a second distribution path for no gain over extending hooks_relay.rs. The assessment's Rule 3 (distribution cost vs saving) applies; status is the highest-frequency hook (1/s), which that assessment did not count.
