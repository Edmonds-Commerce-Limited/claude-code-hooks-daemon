# Plan 00238 Journal — 2026-08-14

## Phase 3 complete: the uncached-read family

### The gate is now one implementation, not four

Follow-up H named `account_display` alone. The research named four handlers
with the same shape, and `settings_reader.py` already had a working mtime gate
for a fifth file. Copying that gate into three more handlers would have left
four places to fix one bug, so it was **extracted** into
`handlers/status_line/mtime_cache.py` (`MtimeCachedFile[T]`) and
`settings_reader` rewritten as its first caller. `settings_reader` is now just
the settings-specific parts: where the file is, and what counts as a valid
document.

Two deliberate properties of the extracted gate:

- **A parse failure is NOT cached.** These files are written by other processes
  (the ccy supervisor among them), so a failed parse is usually a half-written
  file. Caching the failure would keep showing nothing until the mtime happened
  to move again.
- **The stat() stays.** The gate never latches. That matters for
  `startup_cleanup`: a second `hooks-daemon start` against a live daemon
  rewrites `cleanup_status.json`, and a handler that had stopped looking would
  silently never show 🧹 again — a display change, which this plan forbids.

### Gated: account_display, upgrade_notifier, startup_cleanup

`account_display` also surfaced a near-miss worth recording. The port initially
read `if not username: return []`, which quietly turned an EMPTY token from
`👤  |` into no segment at all. Its own test caught it. The plan's Non-Goals say
a tuning change that alters output is a bug, and the fix was one word:
`if username is None`.

`startup_cleanup` gained a real robustness fix on the way. Its guard caught
`OSError/JSONDecodeError/KeyError`, but a valid-JSON-but-not-an-object document
(`[1,2,3]`) parses fine and then raises `AttributeError` on `.get` — none of
the three. That would have escaped `handle()` and taken the whole status line
with it, against this directory's fail-silent contract. Validating the document
shape inside the parse function turns it into the fail-silent default.

### Not gated: multithread_indicator, with a reason

The gate **cannot** apply, and the reason is structural rather than a judgement
call: the handler WRITES its own heartbeat into the registry immediately before
reading it, so the directory's mtime has always just moved and every render
would miss. Its read is also bounded by the number of live sessions (normally
one), not by the render rate.

### DBF: the fifth instance cannot appear silently

Four handlers independently grew the same shape and nothing reported it — the
line renders correctly, nothing is logged, and a stat-per-render is
indistinguishable from a read-per-render without measuring. Fixing four by hand
is the "95 instances" failure this project has a rule against.

`tests/unit/handlers/status_line/test_no_ungated_render_reads.py` parses every
module in the package and fails on any direct `read_text`/`read_bytes`/`open`
unless the module is allowlisted with a written reason. Three entries survive
(`thread_registry`, `git_branch`, `supervisor_indicator`), each explaining why
its read is correct. A companion test fails if an allowlisted module STOPS
reading, so a stale licence cannot sit there covering a future re-introduction
— the same failure mode the error-hiding exclusions file has.

The guard carries its own anti-vacuity checks: the scanner must find the reads
inside the gate implementation itself, must find every allowlisted reader, and
must come back clean for the three handlers just fixed. Without those, a broken
scanner and a clean codebase produce the same green tick.

## Incident: CLAUDE.md lost both nitpick sections on a daemon restart

Unrelated to this plan's changes, and worth recording because it is the exact
failure Plan 00237 already fixed once.

**What happened.** The Task 3.3 daemon restart rewrote `CLAUDE.md` and DELETED
the `nitpick.dismissive_language` and `nitpick.hedging_language` guidance
sections — 42 lines, the last two sections before `</hooksdaemon>`. Both
handlers were live and firing throughout (their dispatch lines are in the
daemon log), and both are enabled in `hooks-daemon.yaml`.

**What caught it.** `tests/integration/test_claude_md_guidance_coverage.py::
TestGuidanceActuallyReachesClaudeMd::test_every_earning_handler_has_a_section_in_claude_md`
— the Plan 00203 guard, doing precisely its job. Nothing else would have: the
daemon reported HEALTHY, `.claude/HOOKS-DAEMON.md` still listed both handlers,
and the deletion sat in the working tree looking like an ordinary regeneration.
The asymmetry between the two generated docs is what made it visible at all.

**What the diagnostic established.** Building a controller from the live config
and instrumenting the injector shows the pipeline is correct as it stands: the
injector receives 85 handlers INCLUDING both nitpick handlers,
`_collect_sections` returns 56 sections including both, `_build_section`
emits them, the block replacement keeps them, mdformat keeps them, and the
content-loss guard passes. So the bug is not reproducible from the current
code — the restart must have run against a handler set that lacked the
pseudo-event handlers, and the mechanism for that is not yet established.

**What was done.** Restored via the daemon's own `regenerate-docs` path (not by
hand), which brought `CLAUDE.md` back to byte-identical with HEAD, and the
guidance test passes again. Recorded as Plan 00234 Task 4.11 rather than
closed, because an unexplained mechanism that silently deletes resident agent
guidance will recur.

**It is not the restart — it is the QA run.** The damage recurred later in the
session, and the correlation is now clean in both directions: three daemon
restarts left `CLAUDE.md` byte-identical, and both deletions appeared across a
full `llm_qa.py all` run. So the suspect is a TEST that initialises a
controller against the REAL `/workspace` root with `pseudo_events_config=None`
— which would rewrite the live file with every section EXCEPT the pseudo-event
ones, which is precisely the damage: 42 lines, both nitpick handlers, nothing
else touched.

`test_cli_regenerate_docs.py` and `test_cli_verdict_log_wiring.py` were checked
and are clean (they use `tmp_path`, or stub `initialise`). The specific test is
not identified yet, and I am not going to name a culprit I have not caught —
but "a test writes the developer's tracked CLAUDE.md" is a much sharper thing
to hunt than "a restart sometimes drops sections", and it is a real defect in
its own right whatever the section content turns out to be.

## Task 2.2: the /proc walk, and a plan premise that turned out to be wrong

The plan predicted `supervisor_indicator`'s 5s negative-cache TTL had "the same
resonance shape" as `git_branch`'s. It does not, and Task 2.3's own guard is
what settled it: at the measured 1.043s interval, `ceil(5/1.043) = 5` renders
per cache miss — above the bar of 3, so the TTL is fine. Worth recording as a
small vindication of building the arithmetic into a test rather than reasoning
about resonance by eye, since eyeballing is exactly what produced the wrong
prediction.

The real cost is the WALK. Measured directly: ~20µs per pid (17 pids in this
container, so 0.35ms here — which is why this repo feels nothing). On a
500-process desktop that is ~10ms, repeated every ~5s forever, i.e. **~360,000
`/proc` reads an hour** for a project that will never run the supervisor. That
is an order of magnitude larger than the uncached-read family this plan started
with.

The fix is a split rather than a bigger number. The two detectors were tied to
one TTL, which priced the cheap one at the expensive one's rate:

- The **status file** is the fast, precise detector — two stats — and a
  supervisor that starts normally writes one. It stays at the 5s rate.
- The **/proc walk** is the slow fallback for the rare case of a live
  supervisor whose status file has gone missing. It now runs at most once a
  minute — a 12× cut.

The trade is explicit: a supervisor that never wrote a status file can take up
to a minute to appear. A test pins the other half of that trade (a
status-file-writing supervisor is still found within the short TTL), because if
that ever stopped being true this would be a latency bug rather than a cost
fix. Another pins that a dead cached supervisor forces an immediate walk — the
walk throttle must not suppress the replacement scan, the same trap the
negative cache already had to be cleared for.

## Phase 4: both FIX verdicts, and neither fix was a rate limiter

The plan called Task 4.2 "rate-limit per session". Looking at what was actually
being repeated made a limiter the wrong instrument.

`daemon_restart_verifier` sent the same advice by two routes on every commit: a
one-line `context` nudge, and a multi-paragraph `guidance` block restating —
almost verbatim, same commands, same rationale, same 5-handler anecdote — what
`get_claude_md()` already keeps RESIDENT in CLAUDE.md for the whole session.
The right rate limit for the long version is not "say it less often" but "say it
once, where it already lives". So `handle()` now returns the single line and
nothing else. An anti-vacuity test asserts the full instructions still exist in
the resident guidance, because deleting the per-commit copy is only correct
while the first copy is there to point at.

`git_context_injector` (Task 4.1) needed the opposite care. Change-detection is
obviously right — a second identical copy of a ~460-token payload teaches the
agent nothing it did not have from the previous prompt — but the plan warned
that a too-strict definition silently stops informing, and there are two
distinct ways to get that wrong:

- **Keying globally.** Sessions share one daemon (Plan 00127), so a single
  "last payload" would let whichever session prompted first mute every other
  session's git context entirely. Keyed by `session_id`, with a test.
- **No ceiling.** Context gets compacted. If suppression never expired, an
  agent that lost the earlier injection would have no git context at all until
  the repository happened to change — indefinitely, on a quiet repo. Capped at
  900s, with a test that says why.

Per-session state is bounded at 32 entries, oldest-evicted. That is the same
"a daemon runs for days" discipline the `MtimeCachedFile` tests insisted on
earlier today; unbounded per-session maps are easy to write and invisible until
they are not.

## Caught it: the CLAUDE.md writer was my own test

The narrowing held — it was a test, not the daemon. `test_stop_chain_terminal_shadowing.py::TestThisProjectHasNotFallenIntoTheTrap`
builds its fixture by initialising a real `DaemonController` against
`self._project_root()`, deliberately, so it sees this project's own handlers.
`initialise()` runs `ClaudeMdInjector` as a SIDE EFFECT. The fixture does not
pass `pseudo_events_config`, so the injector rewrote the tracked `CLAUDE.md`
from a handler set with no pseudo-event handlers in it — deleting exactly the
two nitpick sections, 42 lines, and nothing else.

Reproduced deterministically: sha before, run that one file, sha after. Five
tests pass, file silently rewritten. I wrote that fixture in `c5584c67`
earlier in this same work.

Two things make it worth more than a one-line fix:

**It passes green while damaging tracked source.** The injector even
auto-commits. The only surface that ever objected was an unrelated coverage
test on a LATER run, which is why it read as a daemon fault for two rounds of
investigation.

**Nothing stopped it, and nothing would stop the next one.** DBF: the fix is a
conftest autouse fixture that stats `CLAUDE.md` and `.claude/HOOKS-DAEMON.md`
around every test, fails the specific test that moved either, names the
likely cause (a controller initialised against the real root), and restores
the file. One stat per file per test.

Restoring is from a session-scoped BYTE SNAPSHOT, not `git checkout --`. Two
reasons, both about not making the cure worse: a developer may have legitimate
uncommitted edits in these files when the suite runs, and this project blocks
agents from running that git command at all — a fixture should not do quietly
what the repo forbids explicitly.

The guard's own anti-vacuity check took two attempts, which is the lesson
repeating itself. The first throwaway computed its repo root with

that silence as "the guard works". The second attempt, with an absolute path,
fired three times and restored the file byte-identical. A guard that has not
been watched failing is not yet a guard.

Picked this back up on a fresh context window, which was the whole reason it

**The earlier note here was wrong and worth correcting rather than quietly

**The change.** Four spawns per cache miss became two. `rev-parse
--show-toplevel` is memoised per cwd (a directory's repo root does not move for
the life of a process), and the branch name now comes from the `# branch.head`

running for the icons — so `branch --show-current` was spending a fork asking
git something it had just been told.

**Measured, not modelled**, with the same shim instrument as Task 1.2: a `git`
shim first on the DAEMON's PATH that logs argv and execs the real git. Over
120s: **112 renders, 44 spawns — 22 `status`, 22 `stash list`, nothing else.**
Zero `rev-parse`, zero `branch`, zero `symbolic-ref`. Exactly 2 per miss.
Against the original 192 spawns / 115 renders that is **77% fewer**, and the
breakdown is itself the proof the two calls are genuinely gone rather than
merely rarer.

**One thing the tests caught that the plan did not.**
`test_status_silent_fail_keeps_branch` exists because a `git status` failure

right answer was not to update the test's expectation but to keep the

before. The happy path is still two forks.

That is the second time in this plan a test defended an output the tuning would

## Correction: the delegated agent did not fail to start — I raced it

The earlier delegation note in this file is wrong, and wrong in the direction
that would teach the wrong lesson, so it gets a correction entry rather than a
silent edit.

I recorded that the sub-agent "never became reachable and the file was
untouched some minutes later, so I did the work directly", and drew from that:
"a silent non-start is indistinguishable from slow progress unless you check
the artefact rather than the agent."

The agent has since reported back, and that is not what happened. It was alive
the whole time — reading both files and deriving the new mock ordering by hand.
`ListAgents` returning nothing and the file being unmodified at the moment I
looked were both true, and both misleading: I sampled a slow worker early and
read it as a dead one. It then watched `git_branch.py` change under it
mid-analysis (my `_run_branch_name` fallback appearing between two of its
reads) and the test file get rewritten with helpers it had not written. It
correctly declined to touch anything and verified instead.

**The real lesson is the opposite of the one I wrote.** The hazard was not an
unreliable agent; it was me editing files a live agent was reasoning about, in
a shared checkout. That is precisely what this repo's own
`agent_isolation_advisor` warns about, and the remedy it names —
`isolation: "worktree"` — was available and I did not use it. Two agents in one
working tree share a `.git/index` and a filesystem; here it cost nothing
because the peer was disciplined enough not to write, but the failure mode it
avoided was a merge of two independent migrations of the same file.

Practical corrections for next time, in order of usefulness:

1. Give a file-editing sub-agent `isolation: "worktree"`, or accept that its
   files are off-limits to me until it reports.
2. Do not infer "dead" from one `ListAgents` miss plus one unchanged file.
   Absence of an artefact a few minutes in is the expected state of work in
   progress, not evidence of failure.
3. If I do decide to take the work back, say so — a peer discovering its
   subject rewritten underneath it is a worse outcome than a wasted agent.

The code is unaffected: the peer made zero edits, and the state that shipped in
`b245a6c9` is the one I wrote and verified (454 tests here, QA 21/21, measured
spawn counts). Its independent run — 62 passed in this file, 417 across the
directory, clean black/ruff/mypy — agrees with mine.
