**Two new instruments, both re-runnable:**

1. *Render interval* — poll `context-sidecar/<session>.json`'s mtime and count
   distinct writes. That file is written once per render, so distinct mtimes
   are renders. 86 renders in 90s: min 0.939s, median 1.039s, max 1.833s.
2. *git spawns* — a `git` shim placed on the DAEMON's PATH only (exported for
   the restart command, not installed anywhere persistent), which appends its
   argv to a log and `exec`s the real git. Counts real spawns rather than
   modelling them, and works identically before and after.

**Baseline, 120s window:** 115 renders, 192 git spawns, 1.67 spawns/render →
~5,760 spawns/hour. Breakdown: 59 `rev-parse --show-toplevel`, 57 each of
`status --porcelain=v2 --branch`, `stash list`, `branch --show-current`. That
is **57 cache misses in 115 renders — 49.6%**, the exact alternating steady
state Plan 00234 predicted analytically, now observed directly.

**After (identical method):** 116 renders, 84 spawns, 26 misses → **22.4% miss

measured 22.4%. The model held.

### The guard I wrote first would have passed the bug it was written to catch

Task 2.3 asked for a check that fails when a render TTL sits in the resonance
band. I wrote it against the FASTEST observed interval (0.939s), reasoning that
the fastest rate is the most demanding. It is the opposite. For a fixed TTL, a
LONGER interval covers FEWER renders, so the fastest rate flatters the result:

```
ttl=2.0s (the value that shipped)
  at 0.939s (fastest) -> ceil(2.13) = 3 renders/miss -> my guard PASSED it
  at 1.043s (median)  -> ceil(1.92) = 2 renders/miss -> resonant
```

I only caught it because I ran the anti-vacuity check — feed the guard the
pre-fix value and confirm it rejects it — rather than shipping a green test.
Without that step this plan would have delivered a resonance guard that could
not detect resonance, in a plan whose entire subject is guards that report
clean because they have stopped looking. Rebased on the median, with the trap
itself pinned as a test (`test_sizing_against_the_fastest_interval_would_have_missed_it`)
so a future simplification back to the minimum fails and explains why.

### The TTL is now derived, not chosen

`_DEFAULT_RENDER_TTL_SECONDS = round(5 × 1.043, 1) = 5.2`. The constants are
live — a test asserts the value equals the arithmetic — so the number cannot
drift back to a round guess without the derivation drifting with it. The
original 2.0s was not careless; it was reasonable when written and became wrong
silently when the render rate moved underneath it. That is why the answer is a
guard plus a derivation rather than a better constant.

### Still open on git_branch, deliberately not done here

Four git calls per miss, and two look avoidable with ZERO staleness cost:
`rev-parse --show-toplevel` (the repo root for a given cwd effectively never
changes — cacheable far longer than the render TTL) and `branch --show-current`
(subsumed by `status --porcelain=v2 --branch`, which already emits
`# branch.head <name>`). Cutting 4 calls to 2 would roughly halve what remains
on top of today's 57%. Left as a task rather than folded in silently: it is a
parse change to the porcelain-v2 handling, which is a different risk profile
from editing one constant, and it deserves its own RED test.
