## 12:05 · finding · T1.1 — the blind Enter DOES confirm a modal's default

Reproduced rather than reasoned about, per Task 1.1. Drove a real Claude Code
v2.1.263 over a PTY (`untracked/scratch/tui_modal_probe.py`, gitignored) with
the `/model` picker open. The picker states its own bindings, which is why it
was chosen as the modal: "Enter to set as default · s to use this session
only · Esc to cancel".

Two presses, two answers:

```
after a bare Enter   -> "Set model to Opus 5 and saved as your default for new sessions"
after ESC            -> "Kept model as Opus 5"
```

So the risk is real — `Decision.WOULD_RESUBMIT` presses Enter whenever the
machine is in AWAIT_COMPACTING, the session is keystroke-idle and the input
line is modelled empty, and a modal satisfies all three: empty box, nothing
streaming. It would persist a model change nobody asked for. The mitigation is
equally real: ESC dismisses, and ESC is already flush attempt 1.

## 12:12 · finding · T1.3 — the gap was PROXIMITY, not ordering

Chasing the mitigation to its edge. ESC being attempt 1 covers a dialog that
was already open when the AWAIT episode began. It does NOT cover a dialog that
opens *after* that escape: the remedies alternate at `escape_after_seconds`, so
that dialog is still on screen a full minute later when the Enter fires.

That reframes the fix. Nothing needs to detect the dialog — the pairing just
has to be tight enough that an Enter is always closely preceded by an ESC that
would have dismissed one.

Checked the three conditions that pairing depends on, on the same rig
(`untracked/scratch/tui_esc_enter_probe.py`):

1. Enter on an empty box — no-op.
2. Text in the box → ESC, pause, Enter — still SUBMITS. One ESC does not clear
   the box (the TUI answers "Esc again to clear"), so the unsubmitted-line case
   still gets its fix.
3. Modal open → ESC, pause, Enter — default NOT confirmed.

All three hold.

## 12:20 · decision · T1.3 — shorten an interval, do not extend the protocol

The obvious-looking implementation is a single new "escape then enter"
decision. Rejected, and the reason is the two-tier design rather than taste:
decision names and payloads ARE the worker→host protocol, and **the host never
hot-reloads**. A freshly reloaded worker talks to the Sep-4 host until the
whole ccy session restarts — that host would hit
`Decision(outcome.decision_value)` on an unknown name, or paste a raw ESC
through as literal text.

So the change is confined to the worker: `_RESUBMIT_FOLLOW_SECONDS = 2.0` plus
`_flush_interval()`, which returns the short interval before an even-numbered
attempt (the resubmits) and the configured `escape_after_seconds` before an
odd one (the escapes). Escalation stays paced by policy; only the Enter is
pulled in behind its own ESC. Exposure window: 60s → ~2s. The floor is the
poll interval — anything shorter and the tick that would fire the resubmit
never lands, which is now pinned by a test.

## 14:05 · finding · T3.1 — the leak is conditional, and the cleanup was reaching into the caller

The report said `resolve_old_default_config` leaks a temp file per run. Reading
it, Step 10 of `upgrade_version.sh` already carried:

```bash
# Clean up temp file
if [ -n "$OLD_DEFAULT_CONFIG" ] && [ -f "$OLD_DEFAULT_CONFIG" ]; then
    rm -f "$OLD_DEFAULT_CONFIG"
fi
```

So the leak is not every run — it is every run that exits between Step 5 and
Step 10, which is most of the upgrade and all of its failure paths.

The same three lines hide a second problem. `$OLD_DEFAULT_CONFIG` is whatever
the resolver returned, and on the DOCUMENTED path that is Layer 1's handover,
not a copy Layer 2 made. Layer 2 was deleting a file belonging to its caller.

Both come from the same missing idea: nobody owned the file. Fixed by giving
the temp copy a recognisable mktemp prefix and putting the ownership rule in
`cleanup_old_default_config`, which declines anything it did not create — then
calling it from Layer 2's EXIT trap (covers every exit) while Layer 1 removes
its own preserved baseline in its own EXIT trap.

## 14:12 · decision · T3.1 — stamp the OWNING PROCESS, not a version

The plan said "record a version or timestamp in the handover and warn on a
mismatch". A version cannot actually be checked: after the checkout, Layer 2
has no independent idea which version it is upgrading FROM, so it has nothing
to compare against — and a stale export plus its own stale stamp is perfectly
self-consistent. A timestamp only turns into a threshold, and a slow upgrade
then warns for no reason.

What a leftover export cannot fake is a LIVE OWNER. Layer 1 waits for Layer 2,
so on the documented path the process that made the handover is running for the
whole of Layer 2's life; a leftover in someone's shell names a process that
exited. `HOOKS_DAEMON_OLD_DEFAULT_PID` plus `ps -p` is the whole check.

It stays advisory. The resolver's stated contract is to fail open, and a false
negative — no `ps`, a recycled PID — must not break a real upgrade. The
requirement was that a stale baseline cannot be used SILENTLY, not that it be
refused.

## 15:02 · finding · T4.1 — the closer had no anchor, and widening the delimiter made that matter

Two spellings of the same command disagreed:

```
cat > doc.md <<'EOF'    # recognised as a heredoc
cat <<'EOF' > doc.md    # NOT recognised: body scanned as shell
```

A heredoc opener and an output redirect are independent redirections, so bash
cares about neither order. `_QUOTED_HEREDOC_BODY_PATTERN` demanded a newline
immediately after the delimiter, so anything trailing on that line meant no
match — and an unrecognised heredoc is not a near miss, the whole body gets
split on newlines and judged command by command.

Widening the delimiter to `[\w.\-]+` for `'EOF-1'`/`'END.MD'` then exposed a
second, older gap: the closer `[ \t]*(?P=delim)` has no right-hand anchor, so
a body line reading `EOFDATA` closes an `EOF` heredoc and everything after it
is scanned. Added `(?![\w.\-])`.

## 15:14 · finding · T4.1 — the fix nearly opened a hole of its own

`strip_quoted_heredoc_bodies` rebuilds the command from the groups it
captured, so anything the pattern matched but did not capture is DELETED. With
the opener line widened, the trailing text — usually the redirect — was
matched by a bare `[^\n]*` and silently dropped:

```
cat <<'EOF' > /etc/hosts   ->   cat <<'EOF'
```

That would have hidden the destination from `project_containment`, which is
the check that exists to catch exactly that write. Captured as `opener_tail`
and re-emitted, with a test stating the rule directly: blanking a body must
remove no evidence except the body.

Worth recording because of the shape rather than the detail — the widening and
the deletion are the same edit, and the second effect is invisible unless you
go and read what the substitution rebuilds.
