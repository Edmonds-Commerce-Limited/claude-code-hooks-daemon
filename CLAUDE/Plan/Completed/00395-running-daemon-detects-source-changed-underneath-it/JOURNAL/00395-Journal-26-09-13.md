## 15:10 · finding · — — the capability exists; only the caller is missing

The owner's report was that the daemon detects being out of date but not being
updated underneath it. Reading the code before designing anything changed the
shape of the work: Plan 00371 already shipped the entire comparison, including a

So the daemon cannot notice its own source moving, and the only automatic

## 15:11 · finding · — — the cheap gate fails exactly when it is needed

Any live check needs a gate; hashing every `.py` per dispatch is not viable. The
obvious gate is mtime. Tested it rather than trusting it, with a `cp -p` over
changed content:

```text
before:  mtime=1789311874  ctime=1789311874  ino=425451172
after:   mtime=1789311874  ctime=1789311875  ino=425451172   content: changed
```

mtime unchanged, INODE unchanged, ctime advanced. So both obvious cheap gates
miss an installer-style redeploy, which is precisely the shape of "another
session upgraded it". A check that reports freshness it did not verify is worse
than no check.

The ccy supervisor contract already documents this same trap for its worker
reload, so it is one root cause solved twice — hence Task 2.5.

One small JSON read answers the question. The earlier entries designed a

## 15:33 · finding · — — grounding properly surfaced something the sweep design missed

Reading `SELF_INSTALL.md`, `metadata.py` and `scripts/upgrade.sh` produced a
constraint the earlier design never had: the venv is fingerprint-keyed
(`untracked/venv-{slug}-py{MM}-{fingerprint}/`), so an upgrade that changes the
fingerprint inputs writes a NEW venv directory rather than rewriting the old
one.

A check that re-reads the path it remembered at startup would therefore find an
untouched file and report fresh — the exact failure it exists to prevent. The
check has to re-RESOLVE the venv, not just re-read a path. That is now Task 2.1,
as the first failing test.

Recorded because it cuts against a comfortable reading of this correction: the
lesson is not merely "the simple answer was simpler". Grounding also found a
real trap that the elaborate design had no idea about.

## 15:56 · finding · T2.3 — the dormancy polarity trap was avoided, and the version shapes do match

Reviewing the implementation while it is still in flight. Two things were worth
checking rather than assuming, because both would have been silent failures.

**The inverted-sense trap did not land.** `CanBeDormant`'s two existing entries
are dormant-when-FALSE (a capability is missing). This handler is
dormant-when-TRUE — self-install mode is a reason NOT to run. A reader copied
from either existing entry would have inverted it, and the symptom would be the
handler advertising itself as policy in exactly the repository where it is
meaningless. The implementation returns `self_install_reader()` directly and
fails toward dormant on `RuntimeError`, which is the correct bias: an advisory
that cannot establish its own precondition must not announce itself.

**The two compared version strings are the same shape.** Checked rather than
eyeballed, because a prefix mismatch would make the handler fire on EVERY turn —
strictly worse than the defect it reports:

```text
version.py       __version__ = "3.63.0"                  bare
_STAMP_RE        ^v(?P<version>\d+\.\d+\.\d+)(?:\+...)?$  the `v` is OUTSIDE the group
parse_install_stamp("v3.63.0").version -> "3.63.0"       bare
```

So `installed == running` compares like with like, and the advisory re-adds the
`v` only for display. The guarded-branch form `vX.Y.Z+<ref>.<sha>` narrows to
its release version, which is right for this comparison: a branch install and a
release install of the same version are the same CODE for this purpose.

## 16:22 · finding · T2.5 — fail-open has a narrow blind spot, and it should be on the record now

Verifying the error-hiding exclusion the implementation added, rather than
waving it through because the file is a sanctioned mechanism. Its stated reason
claims the two version regexes disagree, and they do:

```text
metadata.py       ^v\d+\.\d+\.\d+(\+[0-9A-Za-z._-]+)?$              accepts  v1.0.0+main
install_stamp.py  ^v(\d+\.\d+\.\d+)(?:\+(ref)\.(sha 7-40 hex))?$    rejects  v1.0.0+main
```

So the `ValueError` branch is genuinely reachable and the exclusion is earned,
not defensive padding.

**But the consequence is a real blind spot, and naming it is the point of this
entry.** A `daemon_version` in that gap — accepted by the metadata schema,
rejected by the stamp parser — makes the handler return `None` and stay SILENT,
even though the installed version really did change underneath the process.
Fail-open is the owner's ruling and this obeys it; the cost is that the one
shape that is malformed-but-plausible is also the one shape that reports
nothing.

Judged acceptable and NOT graduated to a niggle, with the reasoning recorded so
it can be overruled: `scripts/upgrade.sh` writes the stamp, and it always emits
`<ref>.<sha>` together, so the gap is not reachable through the supported
upgrade path — only by hand-editing the file. Blocking a prompt over a
hand-edited installer artefact would be strictly worse. Recorded rather than
left silent because "the check said nothing" and "the check could not tell" are
indistinguishable to a reader, which is the same conflation this whole plan
exists to fix one level up.
