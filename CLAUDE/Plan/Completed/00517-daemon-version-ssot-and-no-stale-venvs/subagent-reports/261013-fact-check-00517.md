# Fact check: Plan 00517 (and the Plan 00474 ledger diff N453-N455)

Checked 2026-10-13 against the current tree. Dry-run only; no --force run.

## REFUTED (most consequential first)

1. **The "never removes the venv the running daemon uses" protection does not work, so the plan's premise is understated.**
   The task asked whether `prune-venvs --all-except-current` protects the live venv (Plan 00184). It does not here.

   - `bin/hooks-daemon prune-venvs --all-except-current --dry-run` prints: `Pruning 1 venv(s): - workspace-py311-81c29529 461.4 MB /workspace/untracked/venv-workspace-py311-81c29529`.
   - The same output comes from running the CLI under that venv's own interpreter.
   - The daemon uses this venv: `ps` shows pid 110597 running `/workspace/untracked/venv-workspace-py311-81c29529/bin/python -m claude_code_hooks_daemon.daemon.cli --project-root /workspace restart`.
   - Root cause: `_resolver_active_venv_realpath` (cli.py:2897-2919) returns `python_path.resolve().parent.parent`.
   - `resolve()` follows `bin/python`, which is a symlink to `/usr/bin/python3` and resolves to `/usr/bin/python3.11`.
   - Called from the venv interpreter it returns `/usr`, not the venv directory.
   - So `is_current` (cli.py:2974-2976) and the skip at cli.py:3335-3340 never match.
   - Protection therefore rests on the fingerprint match alone, and that fails when the fingerprint has drifted (current `2a519198` against the venv's `81c29529`).
   - Plan 00184 only covered a symlinked venv directory name, not the symlinked interpreter.
   - What it changes in the plan:
     - The Overview should say the live venv is removable today, not merely that definitions differ.
     - Task 3.1 must fix the resolver-realpath bug, with a test using a real venv whose `bin/python` is a symlink. This is a precondition for the Goal "never removes the venv the running daemon uses".
     - It should also say the daemon-start advisory (item 2 below) shares `is_current`.
   - Related: `--stale` compares against the current env's stamp (cli.py:3319-3353) and prints "Nothing to prune" here only because no current-fingerprint venv exists. That is a fourth behaviour, not a refutation.

2. **"Nothing runs at restart, provision or session start" is partly wrong.**

   - Daemon start already runs `_stale_venv_advisory` (cli.py:605-611, 3039-3074). It surfaces a "stale/legacy venv" message and points at `prune-venvs --stale --force`.
   - It deletes nothing, by Plan 00181 Decision 1. So "Nothing removes those later" holds, but the plan's "Cleanup runs only on upgrade" skips an existing advisory.
   - That advisory uses a fourth staleness predicate, `_reclaimable_venv_entries` (cli.py:3009-3036): the legacy venv, or a stamped version that differs. It is a mirror of `--legacy`/`--stale`, not of the other two definitions.
   - Task 4.2 and Task 3.1 must account for it. Extend or replace it rather than adding a second advisory, and unify it too.
   - It also never flags a venv with no `.daemon-version` stamp. The venv on disk has no stamp (the list-venvs Stamp column is "-"). It is also missing `.daemon-metadata.json`, which the plan's UNPROVEN class covers.

3. Minor, plan text: the path in line 18 reads `handlers/user_prompt_submit/ daemon_upgrade_detector.py`, with a stray space. The file exists without it.

4. Minor, task wording: the task brief places `eager_cleanup_stale_venvs` in `scripts/upgrade_version.sh`. It is defined in `scripts/install/venv.sh:1623` and only called from `scripts/upgrade_version.sh:1072` and `:1608`. PLAN.md itself does not make that mistake.
