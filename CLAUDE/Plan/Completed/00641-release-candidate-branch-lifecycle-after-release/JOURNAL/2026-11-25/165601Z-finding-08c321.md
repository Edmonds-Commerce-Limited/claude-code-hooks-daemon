## 16:56 · finding · — — Tasks 1.1 and 1.2 answered: the guard reads a snapshot the sweep's fetch never updates

Tasks 1.1 and 1.2 answered, with the evidence.

**Task 1.1, why preflight and the sweep disagreed.** Two different readers of keep state. `branch-sweep --clean --remote` calls `branch_keep.fetch_keeps` first, so a keep note written in another clone reaches the local tracking ref and the sweep honours it. `branch-preflight` and the creation guard instead read the labels snapshot (`untracked/branch-inventory/labels.json`), which only the SessionStart sweep handler writes, and the only code that clears a stale mark in it is `branch-keep` run in this clone (`daemon/cli.py`, `clear_label_stale` and `clear_label_stale_at_tips`). A keep that arrives by fetch never reaches the snapshot, so the guard kept refusing on a branch the sweep reported kept. The reviewer's guess that preflight does not read fetched notes was close: the inventory reads them, but the creation guard does not use the inventory, it uses the snapshot.

Reproduced by `test_a_keep_fetched_by_the_sweep_lifts_the_stale_mark_preflight_reads` in `tests/unit/daemon/test_cli_branch_preflight.py`, with a control test showing the same setup refuses when there is no keep. Four fixture facts were needed before the guard counted the branch at all, and are worth knowing for any future guard test: `branches.wip.count_remote` must be on for a remote-only branch to be seen; the snapshot is keyed by ref name (`rc/1.0`, not `origin/rc/1.0`) and trusted only while the label's tip equals the ref's tip; a remote-only branch counts only when its tip author equals the clone's `user.email`; and under pytest the session pins `GIT_AUTHOR_EMAIL`, which beats a `-c user.email` given to `git commit`.
