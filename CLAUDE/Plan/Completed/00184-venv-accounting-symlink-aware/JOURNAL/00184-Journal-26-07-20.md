## 19:30 · finding · — — data-loss incident + root cause

While dogfooding the Plan 00181 disk cleanup, `prune-venvs --legacy --force`
deleted the LIVE venv. `untracked/venv-py311-66bbc57c` was a SYMLINK to the real
`untracked/venv`; the resolver (`resolve_existing_venv_python`, scan fallback)
picked the symlink, so the daemon+forwarders ran via it — but `_enumerate_venvs`
keyed protection on `python_venv_fingerprint` (slug scheme
`workspace-py311-81c29529`), which matched NEITHER on-disk name, so `venv` was
flagged legacy-reclaimable and pruned, orphaning the symlink. Also: symlink +
target were double-counted (341.6 MB shown for one 170.8 MB dir).

Recovered live: removed the dangling symlink, `install_deps` rebuilt the correct
`venv-workspace-py311-81c29529`, daemon RUNNING (PID 1197510→1258396), Stop-hook
forwarder probe returns the proper block (exit 2) → forwarders serving.

## 19:52 · decision · T1.2 — dropped a needless error-hiding suppression

The agent had wrapped `resolve_existing_venv_python` in `try/except (OSError,
ValueError): return None` and added a `daemon/cli.py` entry to
`error_hiding_exclusions.json` to sanction it. Verified in `paths.py:735` that
`resolve_existing_venv_python` **never raises** — it returns a best-effort path
(override/legacy branches return WITHOUT an existence check). So the try/except
was dead code and the exclusion was sanctioning a non-existent error path. Root-
cause fix instead: removed the try/except (the `if not python_path.exists():
return None` guard is the real "no venv" signal) and reverted the exclusions
entry. `error_hiding` QA now passes with NO suppression. 35 venv tests green.

v7.2.2.20260518; `uv lock --check` green). mypy → 0 errors. Folding into the
00184 commit since it is part of making the rebuilt/fresh venv pass QA.
