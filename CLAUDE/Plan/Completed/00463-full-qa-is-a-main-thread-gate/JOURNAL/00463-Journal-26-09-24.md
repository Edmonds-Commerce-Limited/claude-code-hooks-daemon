## 16:39 · finding · —   — Gate lock inherited by a daemon started under it; 00463 ships no lock

The coordinator's serial full-QA gate (an flock around `hooks-daemon restart` plus `llm_qa.py all`) deadlocked the queue.

- The daemon that `restart` started inherited the lock's file descriptor. It outlives the gate, so it held the lock after its gate finished. The next gate waited on `flock` until that worktree daemon was stopped by hand.
- The keepalive subshell's `sleep` inherited the descriptor too, and outlived `kill $KEEPALIVE` by up to 120s.
- The fix is to close the descriptor for anything that outlives the gate: `restart ... 9>&-`, and `exec 9>&-` inside the keepalive subshell.

**What 00463 ships.** No gate lock and no gate tooling of its own. The lock that deadlocked was the coordinator's shell script, not code in this branch. The only lock 00463's code path touches is `llm_qa.py`'s existing run lock (Plan 00262). It is opened with `os.open`, which is non-inheritable (PEP 446), so a daemon a QA tool starts during the run cannot keep it.

**Pinned.** `tests/unit/qa/test_llm_qa_run_lock.py::TestADaemonStartedUnderTheRunDoesNotHoldTheLock`. A child process takes the lock through `llm_qa`'s own `_open_lock_fd`, then starts a long-lived grandchild the way a daemon restart does: its own session, `close_fds=False`. The child exits, and another process then probes the lock while the grandchild is still alive. `real`: the lock is free. `control`: the same run with the descriptor marked inheritable, and the probe finds it held, so the test can see a leak.

**Design rule, recorded in `CLAUDE/QA.md` ("The Batched Integration Gate").** Any lock held around the gate must be released when the run exits, even while a daemon started under it lives on. A shell flock closes its fd for every long-lived child (`9>&-`, and `exec 9>&-` before a keepalive). Tooling that later ships a gate lock needs a release test of this shape.
