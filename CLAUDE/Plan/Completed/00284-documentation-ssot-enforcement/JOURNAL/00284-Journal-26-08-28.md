**Task 3.5 — `docs-qa --lint` stale-cache root cause and fix.**
Reproduced with a synthetic corpus (not the real HooksSystem.md/
PROJECT_HANDLERS.md pair, since a later sweep had already re-indexed
that pair by the time this was investigated): `load_or_cold_corpus`
performs NO staleness check at all — it is a raw cache read, no
mtime/size comparison (that logic lives only in `build_and_save_corpus`,
which never runs on the lint path). `checks.duplicate_block`'s own file
content is always read fresh (`context.file_content`), so removing a
duplicate from the linted file and re-linting it was already correct —
that direction never reproduced. The real bug is the opposite
direction: `_hash_index` only counts a shared block hash once it
appears in TWO DISTINCT corpus entries; when a lint target's fresh
content GAINS a block that duplicates an existing partner, the corpus's
stale record for the lint target itself never carries that hash, so the
pair never reaches the 2-entry threshold and the finding is silently
dropped — a false negative, not the over-reporting the field
observation described, but the same underlying defect (the linted
file's own corpus record can lag its real content) and the only
mechanism in this check that a stale self-record can actually corrupt.
