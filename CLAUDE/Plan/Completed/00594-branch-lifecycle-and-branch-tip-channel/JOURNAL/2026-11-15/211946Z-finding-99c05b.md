## 21:19 · finding · — — Relay binary missing on a provisioned aarch64 install: provision.sh never provisions it

Peer request (lts-infra.1, no authority; read-only): why does the provisioned install on VM 170 (daemon 3.74.0, aarch64, built by the project's `.claude/provision.sh`) have no relay binary and run on the fallback transport?

Finding, from this repository (the VM was not inspected):

1. The relay IS built for arm64. The v3.74.0 release carries `hooks-relay-aarch64-unknown-linux-musl` and `SHA256SUMS`; `PUBLISHED_RELAY_TARGETS` in `install/relay_deploy.py` names aarch64; `relay_source: auto` builds with a musl `rustc` or downloads the digest-verified asset.
2. `provision.sh` never provisions it. The only callers of `provision_relay_binary` (`scripts/install/relay_provision.sh`, which runs `relay_deploy`) are `scripts/install_version.sh` and `scripts/upgrade_version.sh`. `.claude/provision.sh` builds the venv through `scripts/venv_bootstrap.sh repair` and starts the daemon, and neither mentions the relay. `init.sh` only consumes a relay (the guard, the hand-off); it builds nothing. So a clone made by `provision.sh` has the relay enabled by default (Plan 00529: `relay_enabled` on, `relay_source: auto`) but no binary: a daemon gap, not an arm64 or release gap.
3. The only automatic remedy is the SessionStart `relay_binary_checker`, which starts a detached `transport on` once per cause. It does not run in the provision step, and on that box it either did not run, or it failed (no github.com egress, or no musl rustc). Its log and state file under the project's `untracked/` say which.

Fix, and where it belongs:

- Daemon repo (the real fix): `.claude/provision.sh` runs the same relay step as install and upgrade, with the same warn-never-abort policy (the relay is a performance path; every rule is still enforced on the bash transport). A foreground run provisions it and prints the banner; a `--background` run reports it, as it already does for a stale venv. Needs a plan, a test and a release note; not started, since the request was read-only.
- lts-infra, for now, and not a substitute: after provision, run `/workspace/.claude/hooks-daemon/bin/hooks-daemon transport on` as the dev user (needs github.com egress or a rust toolchain with the musl target for aarch64).
- Their third question: an unattended provision should run the relay step and WARN when it fails, not fail the provision, matching install and upgrade.

Not verified: whether the box can reach github.com, and what the session-start repair logged.
