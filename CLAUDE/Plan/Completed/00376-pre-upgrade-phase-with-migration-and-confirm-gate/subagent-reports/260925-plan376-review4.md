## BLOCKER 1: `env -i` drops Layer 1's data handover to Layer 2, so config and settings preservation regress on every upgrade

The allowlist at `scripts/upgrade.sh:759-777` forwards PATH, the handoff,
`UPGRADE_FLAGS`, HOME/LANG/proxy/TLS, three `HOOKS_DAEMON_*` names and
`UV_*`/`PIP_*`. It leaves out four variables that Layer 1 exports for Layer 2
itself:

| Variable                                                 | Exported at      | Read by Layer 2 at               |
| -------------------------------------------------------- | ---------------- | -------------------------------- |
| `HOOKS_DAEMON_UPGRADE_PREVIOUS_VERSION`                  | `upgrade.sh:434` | `upgrade_version.sh:785`         |
| `HOOKS_DAEMON_OLD_DEFAULT_CONFIG` and `_OLD_DEFAULT_PID` | `upgrade.sh:461` | `config_preserve.sh:168`/`:221`  |
| `HOOKS_DAEMON_OLD_DEFAULT_SETTINGS`                      | `upgrade.sh:479` | `upgrade_version.sh:868`/`:1262` |

**Observed** (`probe_376r4_layer1_out.txt`). The fixture's example config is
`old_default: true` at v1.0.0 and `new_default: true` at v1.1.0.

- **Control, main's `upgrade.sh`:** all four arrive, and
  `resolve_old_default_config` returns `old_default: true` (correct).
- **Branch:** all four are `<unset>` in Layer 2, and the baseline is
  `new_default: true`. That is the target's example: the exact silent failure
  documented at `upgrade.sh:438-447`, where every accepted default reads as a
  customisation and a new default never reaches the user.
- The settings merge likewise loses its baseline, so it "preserves every
  client value and upgrades none".
- Real e2e (`probe_376_e2e/runs/patch/patch.log:41`): a v3.66.0 to v3.66.1
  run prints `Current version: 3.66.1`. Layer 2 falls back to the checked-out
  target's `version.py`. The old version drives the compatibility check
  (`run_config_compatibility_check`, which compares target to target) and the
  transition headline.
- Layer 1 still prints `OK Preserved pre-upgrade config baseline for diffing`
  and the settings equivalent, so the log claims a handover that no longer
  happens.

**Why the suite missed it:**

- `test_upgrade_old_default_baseline.py:80` and
  `test_upgrade_settings_baseline.py:53` assert the `export` text.
- The resolver tests call it directly.
- No test runs the real Layer 1 into a Layer 2 that reads the handover.

**Direction:**

- Add the four names to the allowlist.
- Add a real-Layer-1 integration test that has a stub Layer 2 print each
  handover variable. It must be RED today; this probe is the template.
- Audit the rest of Layer 2's environment reads against the allowlist. The
  full list is in "Dropped operator knobs" below.

## MAJOR 1: the guard's steering detection has other spellings, and a direct Layer 2 call then bypasses the gate end to end

`_STEERING_ASSIGN_RE` (`upgrade_approval_guard.py:175-180`) matches `NAME=`,
`export NAME` and `declare/typeset -x NAME`. It also matches the `-f…x` flag
cluster. `probe_376r4_guard_out.txt`: all of the following are **allow** in
front of `bash <clone>/scripts/upgrade_version.sh <proj> <clone> v4.0.0`.

- `read -r BASH_ENV <<< f; declare -gx BASH_ENV; …`
- `printf -v BASH_ENV %s f; export -- BASH_ENV; …`
- `set -a; read -r BASH_ENV <<< f; …`
- `n=BASH_ENV; export "$n=f"; …`
- `unset() {…}; declare -f -x unset; …` (`declare -fx` is DENY)

**End to end** (`probe_376r4_direct_bashenv_out.txt`, v3.66.0 clone, target
v4.0.0, a MAJOR):

- **Control:** exit 3, `UPGRADE STOPPED`, nothing deployed, rolled back.

- **With `BASH_ENV`:** exit 0, `head=v4.0.0`, `deployed=True`, no approval
  marker. The `BASH_ENV` file:

  - defines an `unset` that ignores `-f unset`/`-f source`;
  - defines a `source` that redefines `find_latest_python` after
    `python_discovery.sh` loads.

  The log reads `Pre-deploy gate: … (run by …/fakepy)`. The fake interpreter
  received `--verdict-file … --nonce …` on argv and wrote the nonce-headed
  `verdict=proceed`.

**Scope:**

- The Layer 1 route is now immune: `env -i` holds, and
  `probe_376r4_r3layer1_rerun_out.txt` shows `BASH_ENV` and every
  `BASH_FUNC_*` running only in Layer 1.
- The direct Layer 2 route is still a supported entry point
  (`upgrade_version.sh:657-660`). No in-process defence is possible there, so
  the guard is its only barrier.
- The steered3 shapes review 3 asked for are closed. This is the same class,
  one spelling over.

**Direction:**

- On a command that runs the upgrade, treat any occurrence of a steering NAME
  as steering, not only `NAME=`/`export NAME`: `BASH_ENV`, `ENV`,
  `BASH_FUNC_`, `PATH`, `LD_`, `PYTHON`.
- Treat `set -a`/`set -o allexport` and any `declare`/`typeset` flag cluster
  containing `x` the same way.
- Alternatively, make a direct Layer 2 call refuse to proceed past the gate
  unless the handoff is valid, and document direct calls as unsupported for
  an agent.

## MAJOR 2: Layer 2's PATH is not the fixed trusted list: `venv.sh` prepends `$HOME/.local/bin` after sanitisation, and HOME is allowlisted

`scripts/install/venv.sh:26-28` runs `export PATH="$HOME/.local/bin:$PATH"`
at source time. Layer 2 sources it (`upgrade_version.sh:57`) twelve lines
after `_sanitise_layer2_env`. Review 3's probe stub stopped at
`_sanitise_layer2_env`, so it could not see this.

`probe_376r4_layer1_out.txt`:

- **baseline:** Layer 2's `PATH=/root/.local/bin:/usr/bin:…`.
- **`home_local_bin_planted`:** HOME's `.local/bin` holds a logging `git`,
  `cksum`, `uv` and `python3`. `git`, `uv` and `python3` all resolve there in
  Layer 2. The planted `git` ran for `rev-parse --show-prefix` (the shape of
  `upgrade_version.sh:759`) and the planted `cksum` ran (`:665`), both BEFORE
  the gate.

Every gate-feeding function uses `local PATH=$(_gate_trusted_path)`, so the
gate's own tools are safe. Everything else before the gate is not:

- the Step 1/2 `git` calls (`:759`, `:800`, `:822-823`);
- `cksum` (`:665`);
- `resolve_existing_venv_python` (`:592`).

A planted tool there can edit the checked-out target's `CLAUDE/UPGRADES/`
before the gate reads it, or simply write the approval marker.

- The guard allows `printf … > ~/.local/bin/git` and `cp … ~/.local/bin/cksum`.
- `~/.local/bin` exists wherever the uv installer ran, and it needs no
  profile edit or new shell.
- This is the same persistent-PATH class review 3 put outside the guard
  (`~/.bashrc`), with a lower bar.

What is wrong regardless of threat model:

- LLM-UPDATE (`:261-281`, "resets `PATH` to the same fixed…") and PLAN
  decision (e) say Layer 2 runs on the trusted PATH. It does not.
- HOME is on the guard's own forbidden list (`_UPGRADE_STEERING_VARS`,
  `:153`), yet Layer 2 honours it silently: it steers PATH here and is passed
  into the gate's `env -i` (`upgrade_version.sh:460`). That is inert there
  under `-I -S`.

**Direction:**

- Re-apply `PATH="$(_gate_trusted_path)"` after the last library `source`.
- Better, drop the source-time PATH mutation in `venv.sh` and resolve `uv`
  explicitly (`$HOME/.local/bin/uv` as a named fallback, not a PATH prefix).
- Add a test that asserts Layer 2's PATH AFTER all sources, not after
  `_sanitise_layer2_env`.

## MAJOR 3: the git config isolation breaks a legitimate setup and does not cover the routes still open

`upgrade.sh:548-550` exports `GIT_CONFIG_GLOBAL=/dev/null` and
`GIT_CONFIG_NOSYSTEM=1` for every later git call in Layer 1.
`probe_376r4_gitconfig_out.txt`:

| Route                                                                  | Fetched and launched                                                                             | Guard                                                      |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| global `url.insteadOf`                                                 | GOOD (closed)                                                                                    | allow (no longer matters)                                  |
| global `includeIf`/`include.path`                                      | GOOD (closed)                                                                                    | allow                                                      |
| `GIT_CONFIG_COUNT`/`KEY_0`/`VALUE_0` in env                            | **EVIL**                                                                                         | DENY on same command                                       |
| `GIT_CONFIG_PARAMETERS` in env                                         | **EVIL**                                                                                         | DENY on same command (`GIT_*`)                             |
| clone `.git/config` `url.insteadOf` appended by redirect               | **EVIL**                                                                                         | **allow** (review-3 m2 part 2, unchanged)                  |
| clone `.git/config` `include.path` to an outside file                  | **EVIL**                                                                                         | allow by redirect; `git -C clone config include.path` DENY |
| clone `core.sshCommand`                                                | read from `file:.git/config` under the isolation; the fixture remote is a path, so not exercised | `git -C … config` DENY                                     |
| **clone owned by another uid, `safe.directory = *` in `~/.gitconfig`** | **exit 128, "dubious ownership"**                                                                | n/a                                                        |

**Scope of the regression:**

- The last row passes on main (`probe_376r4_gitconfig_main_control_out.txt`:
  exit 0, GOOD).
- A bind-mounted `.claude/hooks-daemon` owned by the host uid, with
  `safe.directory` set globally, is the usual devcontainer shape. Such a user
  can no longer upgrade at all.
- The same goes for any `credential.helper`, `http.proxy` or
  `http.sslCAInfo` that lives only in `~/.gitconfig`, for a private or
  corporate remote. That was reasoned, not probed (no network here).

**Direction:**

- Do not drop the user's global config wholesale. Instead:
  1. before the fetch, `unset GIT_CONFIG_COUNT GIT_CONFIG_PARAMETERS` and the
     `GIT_CONFIG_KEY_*`/`VALUE_*` families;
  2. reject the fetch when
     `git config --show-origin --get-regexp '^(url\..*\.insteadof|url\..*\.pushinsteadof|include\.|includeif\.|core\.sshcommand)'`
     returns anything, from any scope;
  3. add the clone's `.git/config` to the guard's path predicates, which
     closes review-3 m2's residual.
- Or pin the fetch to the verified canonical URL and check the remote's
  identity.
