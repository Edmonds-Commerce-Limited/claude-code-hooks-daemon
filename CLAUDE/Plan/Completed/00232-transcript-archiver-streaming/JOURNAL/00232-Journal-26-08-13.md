## 14:10 · the guard was BLIND, and that is the story of this plan

Task 4.2 asked for proof the new semgrep rule fires. **It fired on zero of
four planted defects.** It loaded fine, ran fine, reported a clean tree.

Diagnosed rather than guessed, with a minimal probe: a `pattern-either` nested
inside a `patterns` block does not bind its metavariables. Individually every
piece worked — direct+regex, deferred+regex, nested-in-either — so only the
combination was broken. Rewritten with one `pattern` per branch: 4/4 planted
defects caught, both negative controls silent.

This is the whole justification for Decision 5. A semgrep rule has no compiler
and no type checker; a structural typo degrades it to silence, and silence is
indistinguishable from success. So the probe became a permanent fixture plus a
test (`tests/unit/qa/test_semgrep_unbounded_source_reads.py`), with
expectations as `# EXPECT-HIT` / `# EXPECT-CLEAN` markers IN the fixture — a
duplicated list in the test would drift, and drift is how it goes quiet again.
The rule file now carries a comment saying its branch structure is
load-bearing, at the point where a future tidy-up would be tempted.

The test caught one more thing immediately: my marker scanner matched the
fixture's own docstring EXPLAINING the markers. Fixed to require a marker to be
a trailing comment on a line of code.

## 14:20 · real-world verification, and two wrong conclusions of mine

Measured against this project's live 74.9 MB transcript:

| | peak | ratio |
| ---------------------- | -------- | ------- |
| before (`read_text()`) | 673.5 MB | 8.99x |
| after (streaming) | 0.7 MB | 0.0097x |

**922x lower**, bounded by the longest line (0.1 MB).

Two corrections worth recording, because both were mine and both looked
convincing:

1. My first "after" number was 112.7 MB — 1.5x the file, nothing like O(line).
   The handler was fine; my harness streamed into an `io.StringIO`, which
   accumulates everything. Re-measured against a real file handle.
2. Driving the production hook end to end, my verifier printed **"REAL
   CORRUPTION"** — 264 lines differing. Twice wrong: it first assumed a verbatim
   copy, then "disproved" redaction by calling `get_active_secret_terms()` in a
   standalone process where `ProjectContext` is uninitialised, so it silently
   got zero terms. Loading the 12 terms from the file directly: 264 differing,
   **264 explained by redaction, 0 unexplained**. Faithful.

Worth keeping: a verifier is as capable of being wrong as the code it checks,
and both of mine failed in the direction of a confident-looking wrong answer. A
"CORRUPTION" verdict from a tool I wrote five minutes ago deserved the same
scepticism as a green one.

Side benefit: this live-proved the Plan 00201 redaction path end to end through
the real daemon on a real transcript with real secrets.
