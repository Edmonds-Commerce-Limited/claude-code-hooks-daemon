## 14:37 · Phase 0 — what the three real defects were

**0.1 — project handler tests reached no playbook, ever.** `cmd_generate_docs`
loads project handlers; `cmd_generate_playbook`, five lines away, never did. The
generator's branch for them is fully unit-tested — and a unit test cannot catch
this, because the test supplies the argument that was missing. Only running the
command finds it. Measured before: 0 matches for either project handler in a
6,439-line playbook. After: +82 lines, both present. In this repo that had
hidden the two most repo-specific guardrails there are.

Fixed by extracting ONE `_load_project_handlers` helper used by both commands,
rather than pasting the five lines a second time. Two copies is how they drifted
in the first place; a third would drift again.

**0.2 — `generate_json` dropped `harness_cannot_produce`.** Every other field of
the dataclass is emitted; that one was not. It is the harness's only signal to
SKIP rather than execute, so without it a must-skip test is run, fails, and is
reported as a daemon defect. Guarded by deriving the expectation from
`dataclasses.fields(AcceptanceTest)`, so the next field added to the dataclass
fails on the same commit instead of being silently dropped the same way.

**0.3 — the sed_blocker test, and the class behind it.** Its `command` was a
bare file path with the real instruction buried in `description`: it looks like
a literal shell test, is not one, and cannot produce the deny it declares.
Rewritten into the dominant Write-payload grammar so Task 1.2 converts it
mechanically with the other 76.

Fixing the `/workspace` in it raised the real question — how many others? Grep
of `handlers/` said 4. Collecting through the actual generator with
`ProjectContext` initialised said **17**. The 13 extra live in
`strategies/security/*.py`, reachable only through the five handlers that
delegate their entire test set, exactly the trap the audit had already flagged
for the converter. A hand-search undercounted by a factor of four; this is the
same shape as the tokeniser phantom in 00263, where the guard found 15 and the
cross-reference found 10.

The guard for this **already existed and did not cover this surface.**
`test_generated_docs_are_path_agnostic.py` (Plan 00244) asserts exactly this
property for `get_claude_md()` and for `.claude/HOOKS-DAEMON.md` — two of the
three artifacts rendered from handler code. The playbook is the third and was
never checked. Extended there rather than in a new file, so the property keeps
one home. Added a third test asserting the sweep actually reaches 100+ tests,
because the two portability assertions are both satisfied by an empty sweep.

## 14:40 · Task 0.4 — the fourth claim did not survive

The audit flagged, marked "verify, not confirmed", that `plan_number_helper`'s
piped test is answered by `pipe_blocker` at priority 17 and so passes for the
wrong reason. It is **refuted**. All four of that handler's tests were driven
through the production forwarder against the live daemon: every one matches its
declared decision, and both denies carry `plan_number_helper`'s own reason with
both declared patterns present. `sort` is whitelisted, so the `| tail -1` never
trips `pipe_blocker`.

Recorded as struck-through in the audit rather than deleted. An unverified but
plausible claim that survives into a plan becomes work someone does later for
no reason, and the fact that a sub-agent's finding needed checking is itself
worth leaving visible.
