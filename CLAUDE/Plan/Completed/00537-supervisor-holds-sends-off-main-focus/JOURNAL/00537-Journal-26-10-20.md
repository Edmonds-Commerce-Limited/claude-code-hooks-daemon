## 00:40 · finding · —

Task 2.1 finding: the daemon's live sub-agent snapshot CAN under-report a started agent, so it must not become a second way to clear the focus hold. No clearing signal was built from it.

The snapshot is `utils/session_load.py` `live_snapshot_path` (`live.json`), written by `refresh_live_snapshot`, whose only callers are the Stop handler `background_task_recorder.py` and the SubagentStop handler `subagent_cache_aggregator.py`. Ways a started agent goes uncounted:

1. Freshness: nothing recounts at SubagentStart or PreToolUse, so an agent started after the last Stop/SubagentStop is absent from the snapshot until the next one fires. A snapshot is a reading of an earlier moment, not "fresher than the latch".
2. Liveness window: `live_agents` counts an agent only if its transcript was written within `DEFAULT_LIVENESS_SECONDS` (120 s). An agent blocked in a long tool call, or waiting on a permission prompt, writes nothing and drops out while still running. An agent whose transcript file does not exist yet is not counted either.
3. Turn ended: a transcript whose last record is `end_turn` is skipped, but a background agent or teammate between turns is still a thread. Its panel row still exists, and focus can sit on it.
4. Name collision: `finished` holds task ids AND descriptions, and an agent is excluded when its name matches either. So a new agent that reuses the description of an earlier finished task is treated as finished.
5. Category mismatch: the count measures agents that are RUNNING. The hold needs to know that no panel row or transcript exists that focus could be on. A finished agent's row and transcript can still be selected and viewed, so even a correct zero does not prove focus is on the main prompt.

The module's own docstring scopes the count as advisory-only ("a stale count must never lock anyone out"). Its failure direction is under-counting, which is the unsafe direction for a clearing signal.

Ruling: only a bare Esc clears the hold. A history-recall Up in a session with no panel therefore holds until Esc. That is the accepted cost: a banner, never a send. A positive signal would need to come from a source that reports panel or view state, which is the non-screen focus-signal spike already listed for the Task 3.2 follow-up plan (`subagentStatusLine` input or a hook payload). This finding goes into that follow-up. Nothing is implemented here.

Also recorded: ruling task 0 (does Esc close an OPEN transcript, state B?) was NOT verified live. The brief forbids touching the running supervisor or session, and the vendored docs (`sub-agents.md:1230`, `interactive-mode.md:46`) document Esc only for a selected row. The implementation clears on one bare Esc, as the brief requires. If Esc does not close an open transcript, an Esc pressed while a transcript is open releases the hold while focus is still off main. The follow-up plan should verify this live and, if needed, switch to the ruling's two-Escs-within-2-s variant.
