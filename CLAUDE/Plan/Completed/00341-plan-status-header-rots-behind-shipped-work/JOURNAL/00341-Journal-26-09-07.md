## 17:55 · finding · P2 — the detection already exists, and it already fired

Task 2.3 said to check `same-commit-plan-doc` before designing anything. Doing
so collapses most of Phase 2, and produces the sharpest fact in this plan.

The check runs at `Stage.COMMIT`, pulls plan numbers out of the commit message
with `[Pp]lan\s+0*(\d{1,5})`, and emits a finding when the commit also stages
`src/`/`tests/`/`config/` changes without touching that plan's `PLAN.md`.

Applied to `923fd583` — the 00314 commit this whole line of work started from:

```
Plan 00314 Tasks 1.1-1.3: marker-write observability and pattern widening

CLAUDE/Plan/00314-.../JOURNAL/00314-Journal-26-09-02.md
CLAUDE/Plan/00314-.../subagent-reports/260902-python-developer-sonnet-5.md
scripts/qa/error_hiding_exclusions.json
src/claude_code_hooks_daemon/handlers/stop/auto_continue_stop.py
src/claude_code_hooks_daemon/utils/blockage_marker.py
tests/unit/handlers/stop/test_auto_continue_stop.py
tests/unit/utils/test_blockage_marker.py
```

Message names Plan 00314; `src/` and `tests/` are staged; the JOURNAL is
touched but `PLAN.md` is NOT — the check's path regex requires `PLAN.md`
directly under the plan folder. So the finding fired, at `Level.ADVISE`, and
the plan stayed `Not Started` for five days anyway.

**So the failure was never detection. It was the level.** An advisory is a
suggestion an agent mid-commit is free to scroll past, and one did.

That changes Phase 2 from "build a git-informed check" to two much smaller
questions:

- Should `same-commit-plan-doc` be BLOCK rather than ADVISE? It has a real
  false-positive shape — a first commit that scaffolds a plan and starts work
  legitimately may not touch PLAN.md — so this is a judgement, not an
  obvious yes.
- Touching `PLAN.md` is a weak proxy. The check is satisfied by ANY edit to
  that file, so a commit that adds a paragraph and leaves the header at
  `Not Started` passes. Asserting on the staged CONTENT (status not
  `Not Started` when code ships) is the stronger property and costs nothing
  extra, because the staged blob is already in hand.

And the `git log` dependency Task 2.1 worried about disappears entirely: the
commit stage already has the facts, so nothing needs to walk history over 45
plans.

## 21:30 · action · P1 — the cheap half shipped, and the ordering was the catch

`header_body_coherence` now has a second branch: `Not Started` plus any ticked
box. No history needed to see that — a single tick falsifies "not started" on
the document's own terms.

**The part that was not obvious until it was written down: the two branches
need different REMEDIATIONS, not just different messages.** The existing one
says "flip to Complete and archive". Given to the author of a plan that is 8
boxes into 60, that is not a clumsy message, it is wrong advice. So there are
two constants, and the split is load-bearing rather than cosmetic.

**And they overlap.** A `Not Started` plan with EVERY box ticked satisfies both
conditions. "You finished this" is the more useful correction than "you
started this", so completion is evaluated first — pinned by its own test,
because an ordering left incidental is an ordering that flips during a later
refactor and nobody notices the advice got worse.

**Task 1.3 confirmed the pre-measurement rather than upsetting it.** The sweep
produced exactly one BLOCK finding — 00110, "8 of 60 boxes ticked" — and
nothing else moved. That is the answer the plan predicted, so BLOCK ships with

## 22:00 · thought · P3 — BLOCK-level is not the same as blocking

Nearly shipped a subtly false claim. The plan's whole argument is that the
ADVISE fired on `923fd583` and changed nothing, so the fix is BLOCK. I made
the finding BLOCK — and then checked what the gate actually does with it.

`plan_workflow.qa.commit_gate_mode` is `warn` in this project, and in warn mode
`PlanQaCommitGateHandler` renders EVERY finding as advisory regardless of
level; only `_MODE_BLOCK` turns blockers into a DENY. So a BLOCK-level finding
today reaches the author as `[block] same-commit-plan-doc: …` inside the
advisory block. More prominent than `[advise]`. Still not a denial.

Writing "Phase 3 makes it block" would have been exactly the failure this plan
exists to name: a document claiming a state the artefact does not have.

The remaining lever is one config flip, and it is deliberately staged — the
config comment reads "warn-first rollout; flip to block after clean
dogfooding". Flipping it would change the behaviour of EVERY plan QA commit
check, not just this one, so doing it as a side effect of this plan would be
the over-reach the rollout exists to prevent. Recorded as a named follow-up
with the evidence attached instead.

## 17:50 · action · — — Phase 2 shipped; plan complete

Full QA green, 25/25: 18,332 tests, 0 failed, 95.2% coverage. Three earlier
runs were discarded before this one and each taught something worth keeping:

- One scored a tree that was edited while it ran. A QA verdict is a statement
  about the tree as of the run's START, so the check now is to compare
  `ps -o lstart=` against the mtime of every file the commit will carry. All
  six were last touched before 17:37; the verdict covers what is shipping.
- One refused to start because the previous run's python child was still
  alive. The watchdog reports the `bash -c` wrapper's pgid, but the python
  child runs in its OWN process group, so `kill -- -<wrapper-pgid>` misses it.
  Reap the pid the QA LOCK message names, not the one the watchdog names.
- Two rounds of `error_hiding` failures, both on `_plan_status`'s
  `return None` paths. Fixed by a reasoned entry in
  `error_hiding_exclusions.json` rather than an in-code suppression: `None`
  there means "this plan has no readable status", which is a distinct answer
  from any `PlanStatus`, and the gate runs inside a PreToolUse handler on
  every `git commit` — raising would turn one unreadable PLAN.md into a
  blocked commit for unrelated work.
