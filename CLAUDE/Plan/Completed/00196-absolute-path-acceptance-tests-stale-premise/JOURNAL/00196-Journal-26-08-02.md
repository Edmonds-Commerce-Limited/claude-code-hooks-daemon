## 08:40 · finding · T1.1 — both offered routes are dead ends

Task 1.1 offered two routes. Investigation killed both, so the task became a
design decision rather than a pick.

**Route A — retarget at a surviving path form: DEAD.** The v3.51.0 evidence
already showed the plain relative form is normalised. Probed the remaining
candidate this session: `Read` on `~/.claude/settings.json` returned the file
contents rather than a block, so Claude Code expands `~` before dispatch too.
No non-absolute form survives to the daemon.

**Route B — reclassify as VERIFIED_BY_LOAD: DEAD.** VERIFIED_BY_LOAD is not a
`TestType` value. `playbook_generator` derives OBSERVABLE vs VERIFIED_BY_LOAD
from the EVENT TYPE:

```python
observable_events = {"SessionStart", "UserPromptSubmit", "PostToolUse"}
if event_type in observable_events:
    test_type_str = f"{test_type_str} (OBSERVABLE - check system-reminders)"
else:
    test_type_str = f"{test_type_str} (VERIFIED_BY_LOAD - skip test)"
```

A PreToolUse handler is therefore unable to declare itself untriggerable, and
marking it `TestType.CONTEXT` would render "OBSERVABLE — check
system-reminders", which is actively wrong.

**Route C — delete the two tests: FORBIDDEN.** `Handler.get_acceptance_tests()`
states: "Every handler MUST define at least one acceptance test. Returning an
empty list is NOT ALLOWED and will be rejected during validation."

## 08:45 · decision · T1.2 — add `harness_cannot_produce`

Took the third path: an `AcceptanceTest.harness_cannot_produce` field carrying
the reason. When set, the playbook renders SKIP with that reason instead of
asking a tester to run something impossible. This is the VERIFIED_BY_LOAD *idea*
generalised so it can reach a handler whose event type locks it out of the
existing bucket, and it puts the explanation where the release tester actually
looks rather than in a code comment nobody opens mid-gate.

Guard-rail wired into the field docstring so it does not become an escape hatch:
use ONLY when the harness rewrites the input so the assertion is unreachable by
construction — never for a test that is merely awkward — and state WHAT rewrites
it so the claim can be re-checked when Claude Code changes.

Rendering is shared with the existing `required_tools` skip through one
`_skip_block()` helper, so a test can never be skipped in the built-in section
and demanded in the project-handler section. `harness_cannot_produce` is checked
FIRST: no tool install can make such a test runnable.

## 08:58 · finding · — — two stale `$PYTHON` skip messages fixed en route

Noticed while working in `tests/acceptance/`: two `pytest.skip()` messages told
the reader to run `$PYTHON -m claude_code_hooks_daemon.daemon.cli restart` —
the exact unrunnable-guidance defect Plan 00192/00193 removed everywhere else
(`$PYTHON` is never set in an agent's shell). Fixed both to
`./bin/hooks-daemon restart`:

- `tests/acceptance/test_stop_hook_hard_block.py`
- `tests/acceptance/test_tool_use_error_recovery.py`

They survived the sweep because `tests/` is not in
`check_python_var_guidance.py`'s `_DEFAULT_SCAN_ROOTS`.

**Deliberately did NOT extend the gate to `tests/`.** ~30 `$PYTHON` occurrences
live there and most are regression guards that quote the banned pattern in
order to assert against it (`assert "$PYTHON" not in result.guidance`). Adding
the root would need roughly ten whole-file path exemptions, and the checker's
own design notes argue against exactly that: "A path exemption silences a whole
file; prefer a rule that can tell the two apart." Widening the gate that way
would make it weaker, not stronger. Recorded here rather than actioned
unilaterally — the open question is whether a narrower rule (guidance strings
only, e.g. `pytest.skip`/`print` bodies) could cover `tests/` without the
exemption sprawl.
