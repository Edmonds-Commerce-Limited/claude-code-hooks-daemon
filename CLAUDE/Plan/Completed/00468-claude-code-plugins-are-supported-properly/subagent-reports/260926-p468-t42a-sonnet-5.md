## What G7 was

The audit ([260924-plugin-audit-opus-5-5.md](../../00467-recommend-the-defence-before-fix-plugin-to-client-projects/subagent-reports/260924-plugin-audit-opus-5-5.md)
G7) found that `utils/settings_repair.py:78-107` read `settings.json` once
and wrote its merged result unconditionally, with no re-read before the
replace. Claude Code's own `/plugin` and `claude plugin install/enable/disable`
CLI commands are a fifth, previously-uncounted writer of `settings.json` (the
existing "four unlocked writers" reasoning in `settings_merge.py` did not
count them), so a plugin install landing at the same moment as a repair could
be silently lost.

## RED test and proof it failed before the change

Added two tests to `tests/unit/utils/test_settings_repair.py`:

- `test_concurrent_write_survives_the_repair`: monkeypatches `Path.read_text`
  so that, on the FIRST read of `settings.json` inside
  `repair_settings_registrations`, a concurrent writer lands an
  `enabledPlugins` change (simulating the plugin CLI). Asserts the repair
  still adds the missing hook keys AND the concurrent `enabledPlugins` value
  survives on disk, and that the function actually issued a second
  (re-)read.
- `test_concurrent_corruption_aborts_loudly_without_clobbering`: same
  monkeypatch shape, but the concurrent writer leaves invalid JSON
  (`"{ not json"`). Asserts the repair aborts (`repaired=False`) and the
  broken content is left exactly as the concurrent writer left it — not
  overwritten by our own valid JSON.

Ran both against the pre-fix code and confirmed RED:

- `test_concurrent_write_survives_the_repair` failed with
  `AssertionError: repair must re-read before replacing / assert 1 >= 2` —
  the function never issued a second read, so it could not have noticed the
  concurrent change.
- `test_concurrent_corruption_aborts_loudly_without_clobbering` failed with
  `AssertionError: assert True is False` — the pre-fix code happily wrote its
  stale merge over the concurrent writer's (broken) content, i.e. exactly the
  clobber this task exists to prevent.

Both pass after the fix; all 13 tests in the file pass (11 pre-existing + 2
new).

## Concurrent-writer semantics chosen

Compare-and-swap, per the brief: `repair_settings_registrations` now
re-reads `settings.json` immediately before the atomic
`tmp_path.replace(settings_path)`:

- **Unchanged** since the first read → writes the already-computed merge, as
  before.
- **Changed** → recomputes `reconcile_settings_hooks` against the freshly
  read content and writes that result instead, so the concurrent writer's
  change (e.g. a newly enabled plugin) is folded in rather than lost. If the
  fresh content already carries every wired hook event, the repair is now a
  no-op (`repaired=False`, nothing written) — the concurrent writer already
  made it unnecessary.
- **Unparseable / non-dict** on re-read → aborts without writing
  (`repaired=False`, logged at `warning`); a result we cannot understand is
  never overwritten.

This mirrors the pattern `run_settings_merge` in `settings_merge.py` already
used (re-read, compare, recompute-or-abort) rather than inventing a new
scheme.

## Writer-count correction

`settings_merge.py` had two docstring comments claiming "four unlocked
writers" of `settings.json` (the module-level rationale on
`_write_atomically`, and the re-read comment inside `run_settings_merge`).
Both are corrected to five, naming: this merge, the legacy-command migrator
(`hook_command_migration.py`), the upgrade deploy
(`scripts/install/settings_deploy.sh`), `install.py`, and Claude Code's own
plugin CLI (`/plugin`, `claude plugin install|enable|disable`) as the
previously-uncounted fifth.
