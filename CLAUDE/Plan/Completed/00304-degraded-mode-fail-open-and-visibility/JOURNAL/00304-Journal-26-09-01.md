## 09:10 · finding · T1.1 — canary evidence reviewed

Read `/tmp/canary-*.txt|json`. Confirmed all five findings from the task
brief against the actual daemon source:

- `config/validator.py::_validate_removed_monorepo_patterns_option` hard-
  errors on the mere PRESENCE of `monorepo_subproject_patterns`, including
  `null` — the exact shape an older daemon's own default template writes.
- `DaemonController._validate_config` enters `_degraded = True` on any
  config error; `process_event` then returns `HookResult.configuration_error`
  (always `Decision.ALLOW`) for EVERY request while degraded — confirmed by
  reproducing a `git reset --hard` PreToolUse event against a degraded
  controller in a unit test: it returned ALLOW before any fix.
- `install.config_validator.ConfigValidator` (the `config-validate` CLI) only
  ever calls `Config.model_validate()` — it never runs
  `config.validator.ConfigValidator.validate()`'s business-rule checks
  (including the monorepo one), which is the actual daemon-startup path. Two
  different validators, same class name, genuinely different verdicts.
- `HandlerConfig.options: dict[str, Any]` rejects `None` outright (Pydantic
  `dict_type` error); the reported loc drops the handler name because the
  error is raised inside `HandlersConfig.coerce_handler_configs`'s
  `field_validator`, which pydantic-core cannot annotate with the dict key
  that was being iterated in plain Python.
- `LLM-UPDATE.md` line 788 used `config-validate --config PATH`; the CLI
  (`cli.py` parser) only accepts a positional `config_path`.

Session's existing failsafe recovery cron `2494b387` is reused — not
re-created for this plan.

## 09:35 · action · T2.1 — degraded-mode safety net

Reproduced first: `test_degraded_mode_still_blocks_destructive_git` in
`tests/unit/daemon/test_controller_degraded_mode.py` asserted DENY on a
degraded controller processing `git reset --hard HEAD`; confirmed RED
(ALLOW) against the unmodified controller. Fix:
`DaemonController._degraded_mode_safety_net` instantiates
`DestructiveGitHandler` directly (no config dependency) and runs it against
every `PreToolUse` event while degraded, ahead of the fail-open
`configuration_error` advisory; a DENY from the guard is returned as-is
(with a DEGRADED-MODE context line appended), otherwise falls through to the
existing advisory. See PLAN.md "Design Decision" section for the fail-open-
vs-fail-closed rationale.
