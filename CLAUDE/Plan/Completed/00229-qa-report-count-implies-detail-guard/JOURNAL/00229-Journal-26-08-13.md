## 05:52 · finding · P1 — the promise is already printed, and one report breaks it

Grounded the plan in the registry BEFORE writing the task tree rather than
after — the lesson from Plan 00228, where the filed proposal turned out to be
inverted for most of its own evidence. Two things came out of it.

**The contract already exists in the code.** Every `TOOL_REGISTRY` entry
carries a `jq_hint` printed to the operator beneath the summary line:

```
✅ magic_values: 0 violations
   magic_values.json | jq '.violations[] | {file, line, rule, message}'
```

So the guard needs no new table mapping report → detail array. It can verify
the hint the tool ALREADY prints, keeping one source of truth and covering a
newly added report without anyone remembering to extend a list — the same
default-in-scope reasoning Plan 00228 settled on.

**`tests` is the exception, and that is the whole story of Plan 00226.** Its
hint points at the COUNT, not at a detail array:

```python
"tests": ToolConfig(
    command=_bash("run_tests.sh"),
    json_file="tests.json",
    jq_hint="jq '.summary'",
),
```

Every other report sends the reader to `.violations[]`, `.errors[]`,
`.issues[]` or `.probes[]`. The one report whose detail went missing is the one
whose printed hint sends the reader back to the number they already had — so
there was no surface on which the absent `.tests[]` detail could look wrong.

Consequence recorded in PLAN.md: a guard checking only the array the HINT names
would pass `tests` trivially and reproduce the exact blind spot it exists to
close. It must also check the array the SUMMARIZER READS.

Of the twenty reports only `tests` renders detail inline; the other nineteen
delegate to the hint. That delegation is deliberate — it keeps the artifact
small enough to be read in full on every run — so it is listed as a Non-Goal.
The guard is about detail being REACHABLE, not inline.

So the detail array is DERIVABLE from the printed hint by reading its leading

`tests` is the single entry where the derivation yields nothing. It is also the
single report with a proven history of losing its detail. That is not a
coincidence worth shrugging at: the hint is the surface on which missing detail
would have looked wrong, and for `tests` that surface pointed at the count.

## 06:06 · decision · T1.2 — fix the exception rather than exempt it

Two options for `tests`: exempt it from the guard, or fix its hint to point at
`.tests[]`.

Exempting would have preserved exactly the blindness this plan exists to
remove. `tests` is not a report that legitimately lacks detail — the
`.tests[]` array is where Plan 00226's missing names lived the whole time; the
hint just never pointed there. An exemption would assert something false and
would leave the one report with a history of losing detail as the one report
the guard skips.

Verified the change is safe before committing to it: `findReferences` on
`jq_hint` returns 22 hits, all inside `llm_qa.py` — 20 registry definitions,
the NamedTuple field, and one render site. No test asserts a hint value.

Deliberately NOT applying the fix yet. The guard comes first and the fix
arrives as the failing test it produces (Core Standard 15), which is the
sequencing Plan 00228 validated an hour ago — its guard caught a real defect,
a bug in itself, and one piece of correct behaviour, none of which would have
been distinguishable if the fix had gone first.

## 05:56 · finding · P2 — I nearly shipped a test that could not fail

The guard went RED exactly where Decision 1 said it would: 2 failed / 46
passed, both failures on `tests`. The 46 matter as much as the 2 — they show
the guard is not red for some unrelated structural reason.

```
FAILED test_every_report_hint_names_a_detail_array[tests]
  - tests's jq_hint ("jq '.summary'") names no detail array
FAILED test_summarizer_detail_agrees_with_the_hint[tests]
```

**The part worth recording is a mistake I caught in my own draft.** The second
test was first written as:

```python
if summarizer(populated) != summarizer(empty):
    return
assert summarizer(populated) == summarizer(empty)
```

That can never fail. Either branch passes. I had written a vacuity guard into
a plan whose entire subject is tests that pass while checking nothing — and it
would have sat in the suite looking like coverage. It is the same defect class
as the one this plan exists to close, one layer up: an artifact that reports a
result without anything behind it.

Rewritten to probe which arrays a summariser's output actually varies with,
then assert that set is a subset of the array its hint names. That version can
fail, and states a real contract: a summariser must never render detail from
somewhere the operator is never sent.

GREEN after fixing the hint: 56 passed, including Plan 00226's own regression
tests, so the fix does not disturb the behaviour 00226 established.

## 06:10 · finding · P4 — the guard did not yet do what the plan's title says

Stopped before ticking the goal and asked what the structural guard actually
proves. It proves WHERE detail lives: every hint names a real array, and no
summariser renders from an array its hint does not name. That is genuinely the
Plan 00226 defect class — producer and consumer disagreeing about location.

It does NOT prove a tool emitted any detail. `total_violations: 3` beside
`violations: []` satisfies every structural rule and tells the reader nothing.
Checked whether per-tool tests cover that instead: 6 of 20 tool test files
mention `total_violations`, and 2 assert the array's length. They do not.

So ticking "a non-zero count implies operator-reachable detail" on the
structural half alone would have been over-claiming — the plan title would
have outrun the code, which is the same species of defect as a report whose
count outruns its detail. Recorded rather than quietly narrowed.

Rejected a test over the real `untracked/qa/*.json`: `llm_qa` writes each
report as it runs, in registry order, so mid-run the early reports are current
and the late ones stale from the previous run. Order-dependent, and it would
only fire when QA was already red. Put the check at render time instead
(Decision 2) — every report, no per-tool opt-in, fires when someone is reading.

## 06:30 · finding · P5 — the bug is already in the shipped scripts

While waiting on the gate I turned this plan's lens on the QA scripts
themselves, checking whether the new warning could fire spuriously. It found
two LIVE instances of the defect instead.

`run_smoke_test.sh`, when no daemon socket exists:

```python
"summary": {"total_probes": 3, "passed_probes": 0, "failed_probes": 3, "passed": False},
"probes": [],
"error": "Daemon not running — no socket found. Run: ./bin/hooks-daemon restart",
```

`failed_probes: 3` with an empty `probes` array — the exact shape. Run QA with
the daemon down and you get "0/3 probes passed (3 failed)" and a jq command
that prints nothing.

`run_shell_check.sh`, when shellcheck is absent: `total_issues: 0`,
`passed: false`, and `"error": "shellcheck not installed"` inside `summary`.
That renders as a RED "0 issues" with no cause given.

**Both scripts DO print the reason** — to their own stdout, which `run_tool`
sends to `DEVNULL`. So the console copy is destroyed and the JSON copy is
never read. The one fact needed to act exists on disk and reaches nobody.

Also worth noting: I checked the other producers and most derive their count
as `len(violations)`, so `total_violations: 3` with an empty array is
structurally impossible for them. The residual risk lives exactly where count
and array come from DIFFERENT sources — which is what `tests` did, and what
these two error paths do.

## 06:33 · decision · T5.2 — candidate, not verdict, again

My first instinct was that smoke_test was a clean hit for the generic warning.
It is not. That warning says the detail "was dropped, not absent" — untrue
when no probes ran. There was nothing to drop, and the tool said so.

The shell_check case settles the design: its count is ZERO, so a guard keyed
on counts cannot see it at all. The real invariant is broader than the one
this plan was filed on — an artifact must not withhold a reason it holds.

So a recorded `error` is surfaced whenever present and takes precedence.

RED first this time (4 failed / 52 passed), correcting the Phase 4 slip where
I wrote code before tests and had to prove teeth by mutation afterwards.

Also bound the fixtures to the PRODUCERS: a test reads both scripts and
asserts they still emit these shapes. Without it, the scripts could change,
my hand-written fixtures would not, and the tests would keep passing against
a shape nothing produces — an unreachable premise, the Plan 00196 class, and
the third time today that pattern has come up.

Dogfooded: `--read-only all` across the twenty real reports adds ZERO extra
lines on a healthy run.
