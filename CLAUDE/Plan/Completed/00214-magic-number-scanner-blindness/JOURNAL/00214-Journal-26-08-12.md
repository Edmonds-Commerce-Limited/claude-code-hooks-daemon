## 13:20 · finding · P1 — measured numeric literal surface (src/ + tests/)

Wrote a throwaway AST scanner (scratchpad, not shipped) over every `.py`
file in `src/` and `tests/`, bucketing every numeric literal (int/float,
excluding bool) by syntactic context: kwarg, call-positional, compare,
subscript, assign, binop, param-default. Total: **7,144 numeric literals**.

- 61.4% (4,389) are in `{0, 1, -1, 2}` — indices, sentinels, arithmetic
  identities. Confirms the plan's Non-Goal: a blanket "every literal is
  magic" rule would be almost entirely noise.
- Stratified hand sample (~50 entries across all 7 context buckets) found
  every non-trivial value was either (a) already named via the assignment
  that defines it (`assign` context — assignment IS how you name a
  constant), (b) test-local fixture data with no cross-file significance,
  or (c) domain values (percentages, byte thresholds) needing semantic
  judgement a regex/AST rule can't safely make.
- The `timeout=`/`settimeout()` family stood out as the one shape with a
  crisp, mechanically-checkable "should be a named constant" signal AND an
  existing `Timeout` constants class to point at. Isolated it:
  `call-pos:settimeout` = 5 hits, `kwarg:timeout` (raw literal, not already
  `Timeout.XXX`) = 4 hits (all 4 in `tests/integration/test_daemon_smoke.py`,
  which is already globally exempted from the whole-file scan for an
  unrelated reason — mock-handler fixtures tripping the string rules — so
  out of scope for this plan; noted as a residual batch-gap, not fixed here).

## 13:35 · finding · P1 — the settimeout() split confirms the trap in the brief

Of the 5 raw `settimeout(<literal>)` call sites (all in `tests/acceptance/`):
3 are `1.0` guarding a connect-only liveness probe (`_socket_is_alive`,
Plan 00127 shape — correct by design, has a docstring saying so) and 2 are
`10.0` guarding a full `sendall()`+`recv()` dispatch round trip — the exact
defect class this plan exists to catch (commit `90ef405f`'s sibling bugs).

Measured two candidate rules against these 5:
- **Naive** ("flag every raw literal to settimeout()/timeout=, regardless of
  context"): 3/5 flagged incorrectly = **60% measured false-positive rate**.
  Rejected outright — not shipped even as advisory; the brief is explicit
  that flagging the connect-probe would get the rule switched off, and 60%
  noise on its own natural test population is well past that threshold.
- **Context-aware** ("flag only when the enclosing function ALSO calls
  `sendall`/`recv`"): 0/5 misclassified = **0% measured false-positive
  rate** across every real instance in this repo. Shipped as the Task 2.1
  rule.

## 13:50 · decision · P2 — implementation shape

Extended `MagicValueChecker` in `scripts/qa/check_magic_values.py`:
- `_DISPATCH_CALL_METHODS = frozenset({"sendall", "recv"})` — the two method
  names that mark a function as doing a full round trip, not just connecting.
- `_contains_dispatch_call(node)` — `ast.walk`s a FunctionDef/AsyncFunctionDef
  body for a call to either method. Documented limitation: walks into nested
  function bodies too (would only ever cause a missed catch in a shape that
  does not exist in this codebase today, never a new false positive).
- `visit_FunctionDef`/`visit_AsyncFunctionDef` merged into one
  `_visit_function_scope` helper that pushes/pops both the existing
  `_in_handler_init` flag AND a new `_dispatch_call_stack` boolean per scope
  — necessary because the literal `sock.settimeout(10.0)` line appears
  BEFORE the `sendall()`/`recv()` calls in every real instance, so the
  decision can't be made online during a single top-down walk; the whole
  function body is inspected up front when the scope is entered.
- `visit_Call` gained a `.settimeout(<literal>)` check reusing the existing
  `magic-timeout` rule ID (same remediation: use a named `Timeout.XXX`), so
  it aggregates with the pre-existing `timeout=` keyword rule rather than
  forking a new rule name.
- Ships BLOCKING (contributes to the script's exit code), matching the
  existing `magic-timeout` rule's severity — justified by the 0% measured
  FP rate above (Task 2.4: only a non-zero-FP rule would be demoted to
  advisory, and none was shipped).

## 14:15 · finding · handoff — worktree venv gap (not a source bug)

`scripts/qa/llm_qa.py` hardcodes `PROJECT_ROOT/untracked/venv/bin/python`
(the pre-fingerprint legacy path) rather than going through
`scripts/lib/resolve_venv.sh`. In the main checkout this works because
`untracked/venv` is a symlink to the fingerprinted venv
(`venv-workspace-py311-81c29529`) that was set up once outside git tracking.

so `git worktree add` never populates it), so `llm_qa.py all` failed with
`FileNotFoundError` until I created the equivalent symlink
(`ln -s /workspace/untracked/venv-workspace-py311-81c29529 untracked/venv`)
inside this worktree. This is a local, untracked, gitignored convenience
link — no tracked file touched — not a fix to `llm_qa.py` itself (out of
scope for this plan; flagging in case it recurs for other worktree agents).
