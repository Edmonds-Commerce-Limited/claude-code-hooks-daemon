## 16:06 · finding · — — the hooks were never the problem

The owner asked why stale worktrees accumulate, said requiring human pruning
is not acceptable, and asked directly whether the project's own hooks were
blocking correct cleanup. Worth recording the answer precisely, because I had
been asserting the opposite for several turns without checking.

`git worktree remove --force` is blocked by NOTHING. It is the worked example
in `destructive_git.py:46` of a `--force` that deliberately does not match the
push-force pattern. I removed all five worktrees and no hook objected. The
claim that this was "reserved to the user" was never verified and was wrong.

What actually jams the reaper is `reap_refusal_reason` counting ANY uncommitted
path as work. Measured on the five:

- four held by exactly one untracked path,
  `.claude/reports/v2.2.0-to-v2.15.2/ADVISORY.md` — the daemon's OWN generated
  config-migration advisory;
- one (00372) held by a 15-line black-formatting churn in
  `tests/unit/core/test_claude_md_injector.py` that `main` had already settled
  in `cbc44c58`.

All five had **zero** commits unmerged to main, so every one was safe the whole
time.

The advisory reads as untracked in those worktrees because of a second defect:
it reached `main` in `41391a66` ("WIP handoff before shutdown … not QA'd"), an
accidental commit of generated output, and `.claude/reports/` was never
gitignored. A worktree pinned to a commit predating `41391a66` therefore sees
the daemon's artefact as an untracked file the agent might care about.

And a third, which is the one that cost the most: the refusal text says
"remove it by hand" and the summary says "N need a human". Neither is true —
an agent can inspect and remove. That wording is what routed this to the owner
across several turns. A message that misroutes the work is a defect in the
message, not a cosmetic issue.

## 16:10 · decision · P2 — why only UNTRACKED paths may be dropped

The obvious implementation is "drop any uncommitted path main would ignore".
That is too broad and would have been a real hazard.

`git check-ignore` answers about a PATH. It cannot see that the same path is
tracked and modified inside the worktree. Ignore rules do not apply to tracked
files, but this query is asked of MAIN, whose tracked set is not the worktree's
— so a file untracked-and-ignored in main but tracked-and-modified in the
worktree would have been filtered out, and a genuine modification discarded on
reap. Narrowing the filter to the `??` status code removes that case entirely:
a staged, modified or deleted tracked file always still refuses, whatever its
path matches. Three tests pin exactly that.

Failure handling follows the module's existing doctrine rather than inventing
one: `_ignored_in_main` returns an empty set when the query fails, so an
unanswerable question can never WIDEN what gets reaped — the same reasoning as
`UNKNOWN_COUNT` being negative. And the `<git status failed…>` sentinel is a
message, not a path, so it is never handed to git; a test asserts
`check-ignore` is not called at all in that case.

## 16:10 · finding · T2.2 — proved on a real worktree, not just fixtures

Unit fixtures are what gave false confidence on the last plan, so this was
verified against a real worktree reproducing the exact original condition:
`git worktree add --detach untracked/worktrees/probe-00380 1e78c5eb` — pinned

`?? .claude/reports/v9.9.9/`, which is the original failure exactly.

Before: that path was an uncommitted path and the worktree was refused for it.
After: the only refusal left is the age rule —

```
KEEP  probe-00380 is not safe to reap: created 6s ago, under the 900s minimum
```

Then the safety direction, on the same real worktree: adding an ordinary
untracked file brought the refusal straight back, naming it —
`uncommitted path(s): genuinely-new-work`. Probe worktree removed afterwards;
`git worktree list` is back to the main checkout alone.

That run also made the Phase 3 problem obvious in a way reading the code had
not: the 6-second-old probe was reported as "1 need a human". Nothing about a
worktree being young needs a human — it needs fifteen minutes.
