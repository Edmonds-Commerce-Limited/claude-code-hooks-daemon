# Plan 00194 Journal — 2026-08-01

## Phase 1: enumerating callers retired the plan's biggest risk

The plan's risk table rated "hook forwarders depend on CWD resolution" as
High/Medium, and Task 1.1 existed to enumerate caller shapes BEFORE choosing a
rule. Doing that first paid for itself immediately: **the hook forwarders do not
use `bin/hooks-daemon` at all.** They source `init.sh` and talk to the socket
directly. So the highest-traffic, highest-risk path is untouched by this change,
and the wrapper's blast radius is limited to agents, humans and scripts.

Caller shapes and the daemon each should target:

| Shape                                        | DAEMON_DIR                   | Correct target |
| -------------------------------------------- | ---------------------------- | -------------- |
| self-install `<proj>/bin/`                   | `<proj>`                     | `<proj>`       |
| client `<proj>/.claude/hooks-daemon/bin/`    | `<proj>/.claude/hooks-daemon`| `<proj>`       |
| worktree `<wt>/bin/`                         | `<wt>`                       | `<wt>`         |
| skill `daemon-cli.sh`                        | n/a — separate resolver      | unchanged      |
| hook forwarders                              | n/a — socket direct          | unchanged      |

The layout alone distinguishes client from self-install (`hooks-daemon` under a
`.claude` parent), so no mode flag or config read is needed.

## Precedence: verified, not assumed

The rule injects `--project-root <derived>` *before* the caller's arguments and
relies on argparse taking the LAST occurrence, so an explicit `--project-root`
still wins. I did not take that on trust — checked it against the live CLI first:

```
hooks-daemon --project-root /tmp/pr_a --project-root /workspace status
# resolved /workspace  → last wins, confirmed
hooks-daemon --project-root /tmp/pr_a status
# ERROR: hooks-daemon not installed at: /tmp/pr_a  → control, proves the first
#                                                     value is genuinely parsed
```

This is why the anchor goes first rather than last: precedence falls out of
argparse's own semantics instead of needing the wrapper to scan `$@` for a
user-supplied flag. Less code, and no parsing bug to get wrong.

## Fail-safe, not fail-shut

The anchor is only injected when the derived root actually contains `.claude`.
Injecting one that fails validation would convert a currently-working
invocation into a hard error — a regression traded for a fix. An unanchorable
layout defers to the CLI's existing CWD walk-up and its existing diagnostics.
There is a test for exactly this ("stray" daemon tree with no `.claude`).

## Testing the shell honestly

The tests run the REAL wrapper against a stub `resolve_venv.sh` and a stub
interpreter that echoes its argv, then assert on the argv actually built. That
beats asserting on the wrapper's source text, which would pass just as happily
if the shell logic were wrong. Covers client, self-install, worktree,
explicit-override, argv-preservation, and the unanchorable fail-safe.

## Phase 3: the original regression, reproduced and killed

Rebuilt the fixture and ran the exact scenario from Plan 00193 Phase 4 — the
FIXTURE's wrapper, invoked while standing in `/workspace`:

```
=== BEFORE: dogfood PID ===       PID: 1629099
=== restart FIXTURE daemon, standing in /workspace ===
Sent SIGTERM to daemon (PID: 1629953)
Daemon started successfully (PID: 1631197)
=== AFTER: dogfood PID ===        PID: 1629099   ← UNCHANGED
```

Before this fix that same command restarted the dogfood daemon (1186876 →
1203331). Now it restarts the fixture's, and the dogfood daemon is untouched.
Both daemons RUNNING and independently controllable.

One nuance worth recording so it is not mistaken for a bug later: running the
fixture wrapper WITHOUT `HOSTNAME=dummy-client-repo` reports "NOT RUNNING". That
is correct — hostname isolation is a SEPARATE axis from project root. The
wrapper now gets the project right; the hostname suffix is still the caller's to
supply. Documented in `CLIENT-MODE-TESTING.md` rather than left as a trap.

## 2026-08-02 — The fallback was the bug wearing a safety label

Caught during the v3.50.1 release review, by the user, before the tag went out.

My first cut of the anchoring kept a fallback: when the wrapper could not derive
a project root, it exec'd the CLI unanchored and let it walk up from `$PWD`. I
justified that in a code comment as "Fail-safe, not fail-shut" — the reasoning
being that injecting a `--project-root` which then fails validation would turn
a currently-working invocation into a hard error.

That reasoning was wrong, and wrong in an instructive way. **The CWD walk-up is
the defect this plan exists to remove.** Keeping it as the fallback preserved
the exact silent-wrong-target behaviour in the one situation where no other
check could catch it. Worse, it was the situation most likely to be unusual and
therefore least likely to be noticed.

The label did the damage. Calling it "fail-safe" made it read as the cautious
option, when the two outcomes are:

- refuse: the caller sees an error and fixes their layout;
- fall back: the caller's *other* project's daemon gets restarted, exit 0, no
  signal at all.

A wrong action that reports success is not the safe side of that trade.

Changed to fail loud: an unanchorable layout exits 5 and prints the root it
derived plus the two layouts it expects. The user's framing was that CWD should
never take part in resolution at all, and that self-install can absorb whatever
pain that costs. As it turns out it costs nothing — the layout check is
`$0`-derived, not CWD-derived, so self-install keeps working from any directory;
only the fallback had to go.

Test changed from asserting the fallback to asserting the refusal:
`TestDoesNotBreakUnanchorableLayouts` became `TestUnanchorableLayoutFailsLoud`,
three cases — non-zero exit with the CLI never reached, a diagnostic that names
the derived root, and a pin that the caller's own project never leaks in as the
target. Confirmed RED against the old wrapper (2 failures, both the fallback
path) before implementing.

399 install tests pass. Live check: `./bin/hooks-daemon status` from
`/workspace` and from `/root` both report the same dogfood daemon, PID
unchanged.

Note for the record: this is the second time in two plans that a "defensive
fallback" turned out to be a branch that could only ever produce a worse
message or a wrong result — the other being the seven retired-venv-path
fallbacks in Plan 00193 Task 7.1. Same shape, same fix, same lesson: a fallback
whose success case is impossible or harmful is not a safety net, it is a
silencer.
