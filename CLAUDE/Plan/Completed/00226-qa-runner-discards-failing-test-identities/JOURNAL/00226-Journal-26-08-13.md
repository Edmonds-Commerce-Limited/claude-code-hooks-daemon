## 03:44 · finding · T1.2 — the real fixture earned its keep immediately

Captured actual pytest output instead of writing the format from memory, and
the first line showed why that mattered:

```
'\x1b[31mFAILED\x1b[0m untracked/.../test_sample_failures.py::\x1b[1mtest_one_that_fails\x1b[0m - assert 1 == 2'
```

pytest colours its short summary EVEN WHEN REDIRECTED TO A FILE, and the escape
codes sit INSIDE the node id, not around it. A parser built on `^FAILED (\S+)`
against a remembered format would have captured
`test_sample_failures.py::\x1b[1mtest_one_that_fails\x1b[0m` as the test name —
and would have passed its own tests, because those tests would have used the
same remembered format.

The count regexes survive uncoloured because `2 failed` stays contiguous inside
`\x1b[1m2 failed\x1b[0m`, which is why the existing code never noticed.

## 03:48 · decision · T3.1 — the question's premise was wrong

Task 3.1 asked which OTHER QA checks report a count without the identities.
The premise was that the others derive their summary FROM their detail array,
so they cannot disagree, making pytest the odd one out.

Read every summariser in `llm_qa.py`. All of them —
`_summarize_magic_values`, `_summarize_lint`, `_summarize_security` and the
rest — read a `summary.total_*` COUNT FIELD, and not one reads the detail
array. So any producer that fills its count but not its list reproduces the
pytest failure exactly, and the reporting layer prints a non-zero count beside
a `jq` hint pointing into an empty array.

Verified: the mechanism, by reading the code. NOT verified: whether each
producer populates its array, which needs a red run per check. Recorded as a
limit rather than an all-clear, with the class-level guard named as follow-up.

## 04:05 · finding · T3.2 — the tested half was not the half that gets read

Went to confirm `_summarize_tests` was covered before committing, and it was
not. Both of this plan's verifications stop one layer short of the output an
LLM actually reads:

| verification                 | proves                        | does not prove          |
| ---------------------------- | ----------------------------- | ----------------------- |
| 9 parser unit tests          | node ids extracted from text  | they reach the summary  |
| heredoc against a red file   | node ids land in `tests.json` | they are ever displayed |

So a break in the rendering layer would have passed everything I had already
called sufficient — while `tests.json` sat there holding the right answer.

The specific fragility: `_summarize_tests` selects records whose `outcome`
equals the literal `"failed"`, and nothing bound that to the token
`run_tests.sh` writes. Change one side and the summary keeps printing an
accurate count beside nothing at all. That is this plan's own bug re-entering
through a different door, which is why it was worth stopping to fix rather
than filing.

Guard added: reads the token out of `run_tests.sh` and asserts the summariser
renders it, plus a vacuity check (the extraction found something) and an
inverse test (a different token renders nothing). Confirmed it reads the real
token `failed`, so the coupling is genuine and not a test that agrees with
itself.
