## 12:15 · finding · T1.1 — the format, from the spec and the source

Vendored two captures with `remote-docs add`:
`remote-docs/docs.ansible.com/projects/ansible/latest/vault_guide/vault_using_encrypted_content.md`
(converted) and
`remote-docs/raw.githubusercontent.com/ansible/ansible/devel/lib/ansible/parsing/vault/__init__.py.md`
(verbatim). What the detector relies on:

- Header: `$ANSIBLE_VAULT;1.1;AES256`, or `;1.2;AES256;<label>` when a vault
  id is given (`format_vaulttext_envelope`: 1.2 is chosen only for a
  non-default id, and only 1.2 carries the label). `1.0;AES` is read-only
  legacy and is NOT accepted: it fails closed, so such a file stays protected.
- Body: hex, 80 columns, trailing newline (`[b_ciphertext[i:i + 80] ...]`,
  then `b''` joined with `\n`). The parser uses `splitlines()`, so CRLF is
  tolerated there, and the detector tolerates it too.
- Inside the armour: `hexlify(salt) \n hexlify(hmac) \n hexlify(ciphertext)`
  (`encrypt`: `b'\n'.join([hexlify(b_salt), b_hmac, b_ciphertext])`, then
  hexlified again). HMAC is SHA-256, so 64 hex chars. Ciphertext is
  PKCS7-padded to the AES block, so a multiple of 32 hex chars. Salt is 32
  random bytes by default, but `VAULT_ENCRYPT_SALT` can set any length (so
  salt is only required to be non-empty, even-length hex).
- `write_data` REMOVES the file and recreates it (`O_CREAT | O_EXCL`), so
  `ansible-vault decrypt` gives the plaintext a new inode. A hardlink made to
  the ciphertext keeps ciphertext. Relevant to the residual-risk analysis.

That inner structure is the strong check: a plaintext secret that happens to
be hex (API tokens often are) does not unhexlify to `hex\nhex(64)\nhex(32k)`.

## 12:15 · decision · T1.1–T1.4 — design

**One detector**, `utils/encrypted_at_rest.py`: `classify_at_rest(path,
project_root)` returns a format enum (`ansible-vault`,
`ansible-vault-inline`, `none`) and `is_encrypted_at_rest()` is True only for
the whole-file format. It reads at most `MAX_INSPECTED_BYTES` (4 MiB; the
armour is hex of hex, so about 1 MiB of plaintext) and verifies the WHOLE
file, not a prefix: a file over the bound is not confirmed. Fails closed on:
a relative path, no project root, a realpath outside the project root, not a
regular file (checked by `lstat` before open, and `fstat` after open against
the same device and inode, with `O_NOFOLLOW | O_NONBLOCK` so a FIFO swapped in
cannot block the daemon), any `OSError`, a malformed header, a non-hex or
blank body line, or armour that does not decode to the inner structure. No
cache: every call re-reads, so a file decrypted in place is protected at the
very next check. Nothing but the enum leaves the module; nothing is logged
except an exception class name.

**Guard, path tools** (Read/Write/Edit/NotebookEdit/Grep): a protected path
that is confirmed encrypted is let through. A relative path is resolved
against the event's `cwd`; with no `cwd` it is not confirmed. A Grep rooted at
a directory is allowed only if every protected file under it is confirmed.

**Guard, Bash.** The lead's rule (every mentioned protected path confirmed)
is necessary but not sufficient, for two reasons found while designing:

1. Ciphertext is only harmless while the reader cannot decrypt it, and
   Ansible finds the password WITHOUT the command naming it
   (`DEFAULT_VAULT_PASSWORD_FILE`, `ANSIBLE_VAULT_PASSWORD_FILE`, see the
   vendored guide). So `ansible localhost -m debug -e @<vault file>`,
   `EDITOR=cat ansible-vault edit <vault file>`, `ansible-inventory`, and
   `git diff`/`log -p`/`show`/`blame` under the common
   `diff=ansible-vault` textconv setup all print plaintext while naming only
   the encrypted file. Before this plan every one of those was denied by the
   mention rule. A denylist of "commands that decrypt" cannot be complete.
2. A token resolving to an encrypted file under `cwd` says nothing about the
   file the SHELL opens after `cd other &&`, `git -C other`, `tar -C`,
   `find -execdir`, a `$VAR` prefix or a quoted concatenation. Several
   inventories with the same `group_vars/all/<name>` layout, one of them
   decrypted for editing, is a realistic shape for exactly that divergence.

So the Bash exemption is deny-by-default in the guard's own style: the
command must be ONE simple command (shlex words; no `;`, `&&`, `||`, `|`,
background `&`, subshell or process substitution; redirections only), with
no expansion characters anywhere (`$`, backtick, backslash, newline, glob or
brace characters, `~`), whose head is on a short allowlist of commands that
cannot decrypt: `git add|commit|status|mv|rm|ls-files|check-ignore` (with
`git` global options refused, and patch/interactive/edit/verbose flags
refused because they render diffs), plus `cat head tail wc ls stat file grep
cp mv`. Every protected mention must then be a complete literal shell word
that resolves (against `cwd`) to a confirmed encrypted file. Anything else
keeps the existing verdict, so the consumer allowlist, `secret-meta` and
`git rm --cached` behave exactly as before, and `ansible-vault view|decrypt`
stay denied.

**Guard, script authoring**: NOT exempted. A script is used later, by a
Bash call that does not name the file, so no check can happen at the time
of use, and the file may have been decrypted by then.

**Hygiene checker**: an encrypted file gets no gitignore, untrack or
permissions finding (ciphertext that is tracked is world-readable to the
repository's readers by design). It is listed as "encrypted at rest --
tracking is correct" only when the advisory prints anyway. The owner's
report is that the warning should stop, so a project whose only matches are
encrypted gets no output at all.

**Flaggable/quarantine guards**: checked, they match their own glob sets
(`flaggable_path_globs`, the DETAIL artefact globs), not the secret globs,
so they do not re-block a vault file by name. Nothing to change.

## 12:29 · decision · T1.2 — inline `!vault` values: advice changes, protection stays

Adopted the plan's recommendation. A YAML file whose values are tagged
`!vault |` carries plaintext KEYS always and may carry plaintext VALUES
beside the vaulted ones; nothing in the file says whether every secret was
vaulted, so the daemon cannot prove the file is safe to read. So:

- `secret_file_guard`: unchanged, still protected (the detector returns
  `ansible-vault-inline`, and only `ansible-vault` counts as encrypted).
- `secret_file_hygiene_checker`: when such a file is tracked or not
  gitignored, the gitignore/untrack findings are REPLACED by one statement:
  tracking it is correct only if every secret value in it is vaulted, which
  the daemon cannot verify, so reads stay denied. The permissions finding is
  kept (the file is partly plaintext). A gitignored, untracked, 0600 inline
  file is silent.

Detection is `!vault |` (any block indicator) followed by an indented
`$ANSIBLE_VAULT;` line, within the same 4 MiB bound. It only changes advice
TEXT, never a verdict, so a miss falls back to the ordinary advice.

## 12:29 · decision · T1.2 — SOPS: NOT included

Evidence from the vendored SOPS reference
(`remote-docs/raw.githubusercontent.com/getsops/docs/main/content/en/docs/reference/_index.md`):

- "key names are concatenated into a byte string that is used as AEAD
  additional data ... We expect that keys do not carry sensitive information,
  and keeping them in cleartext" (Encryption Protocol). Keys are plaintext by
  design.
- `encrypted_suffix`, `encrypted_regex` and `encrypted_comment_regex`: "All
  other values are **not encrypted**"; `unencrypted_suffix`,
  `unencrypted_regex` and `unencrypted_comment_regex` leave the matching
  values in cleartext (Settings). A SOPS file can hold plaintext values by
  configuration, and which rule applied is recorded only in its own `sops`
  metadata.
- `mac_only_encrypted`: the MAC can cover only the encrypted values, so the
  presence of `sops.mac` does not even vouch for the unencrypted ones.
- The `sops` metadata is a top-level key of a YAML/JSON tree (Top-level
  arrays: "SOPS needs a top-level `sops` key to store its metadata"), and ENV
  and INI files are also trees of key/values. Proving "no plaintext secret"
  means parsing the whole structure of a possibly-plaintext secret file
  inside the daemon and re-implementing each store's leaf rules.

So `sops:` with `mac` and `lastmodified` is unambiguous about the file being
SOPS-MANAGED, but not about the file being safe to read: it is the inline
`!vault` situation again, with more configuration. A SOPS file matching a
protected glob stays protected and keeps the ordinary hygiene advice. A
project that tracks SOPS files under a protected name can narrow the globs
(`mode: replace`); that is a human config decision, as Plan 00272 intends.

## 13:19 · decision · T1.3 — lead's follow-up: no half measures on the two open ends

The lead asked for both out-of-scope items to be fixed on this branch.

**(a) `gitignore_safety_checker` is content-aware.** It asked for one
`.gitignore` line per protected glob, and that line would silently ignore
every NEW encrypted vars file at a matching name: the owner's complaint
again. It now uses the same detector over the protected files git knows
about, every session and UNCACHED (the existing cache is keyed on the
`.gitignore` content, and a file can be encrypted or decrypted without that
changing):
- A protected glob it advises is followed by a `!/<path>` negation for every
  existing ciphertext file that glob would catch. The last match wins in
  gitignore, so the negation goes after the glob. It never advises a glob
  that swallows ciphertext.
- Ciphertext that a present rule already ignores (tracked or not) is
  reported under its own heading with the negation that re-includes it.
- Plaintext protected files must stay ignored, exactly as before.
- With no such file yet, the advice carries a one-line caveat that an
  encrypted file matching the glob needs a `!/<path>` line.

**(b) Recovery.** `secret_file_hygiene_checker` gives ciphertext that is
untracked and/or ignored positive advice: it SHOULD be tracked; remove the
ignore rule or add `!/<path>` after it, then `git add <path>` (the `git add`
step is left out when it is already tracked). The release note now tells a
project that followed the old advice to do exactly this.

**Shared code.** Both handlers read file states from a new
`utils/git_file_states.py` (lifted out of the hygiene checker, plus the
state it lacked: TRACKED files an ignore rule matches, from `git ls-files
--cached --ignored --exclude-standard`). `gitignore_negation()` builds the
line: anchored with `/` so it cannot re-include a same-named file elsewhere,
with `\*?[` escaped. `unignore_advice()` is the one wording both use,
including git's limit that a file under an ignored DIRECTORY cannot be
re-included. The hygiene checker keeps its old `--others`-only notion of
"ignored" for PLAINTEXT files, so their findings are unchanged, as Task 1.3
requires.

**(c) Truth-change filename: kept as `v3.67.0.yaml`, per the README.**
`UNRELEASED/truth-changes/README.md` says to stage "per-version" files, and
`RELEASING.md` moves `v*.yaml` "keeping their version-named filenames". The
loader enforces it: `_VERSION_PATTERN = ^\d+\.\d+\.\d+$` on the file stem,
so a `vUNRELEASED.yaml` would be silently SKIPPED by `check-truth-changes`.
Precedent: Plan 00427 staged `v3.66.0.yaml` on 2026-09-17 (`c631d4dc`), four
days before `Release v3.66.0` (`4daba1d1`, 2026-09-21). If the release
