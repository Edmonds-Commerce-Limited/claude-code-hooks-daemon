# Plan 00257 Journal — 2026-08-19

## 09:35 · finding · `sed -n 'Np' file` is blocked, and it modifies nothing

Fourth guard misfire of this release cycle. Recording it; not fixing it yet,
for the same reason as the previous three — v3.54.0 is prepped and unpushed to
`refs/tags`, and a source change would move HEAD under the tag.

**What happened**: I ran `sed -n '1,20p;140,157p' PLAN.md` to read two ranges
of a file. `sed_blocker` denied it.

**Why this is arguable rather than obviously wrong**: `CLAUDE.md` states the
rule as "sed is blocked for FILE MODIFICATION", and lists read-only use as
allowed — but the example given is a PIPELINE (`cat f | sed 's/x/y/' | grep z`).
`sed -n '1,20p' file` takes the path as an argument instead. It has no `-i`, so
it cannot write to the file; it prints to stdout and exits. By the stated
rationale — "a single error can silently destroy hundreds of files" — there is
nothing here to destroy.

**Why I am not simply calling it a bug**: a deliberately blunt rule has real
value. `sed -i` and `sed -n` differ by one character, and an agent that has
built the habit of reaching for `sed` to read is one typo from reaching for it
to write. The block also costs almost nothing: `Read` with `offset`/`limit` did
the same job on the next call. So the question is a policy one — is the
blockiness intentional? — not a defect report, and it should be answered by
whoever set the policy rather than assumed by me.

**What makes it worth recording at all**: a *system-level* instruction in this
same session actively told me to prefer `sed -n`, heredocs and short scripts
over the dedicated Read/Edit/Write tools. That instruction and this project's
rule are in direct conflict. I followed the project rule, which I think is
right — the project's hard guard is the more specific and more local authority,
and it is dogfooded. But an agent that followed the generic instruction instead
would hit this wall repeatedly and might "work around" it by disabling the
handler, which is the failure mode worth heading off.

**Concrete options if this is taken up** (none applied):

1. Leave as-is, and correct `CLAUDE.md` so the allowed-read example is not
   pipeline-specific — i.e. say plainly that ALL `sed` is blocked, pipeline
   read-only use excepted, so the doc stops implying reads are generally fine.
2. Allow `sed -n` with no `-i`/`-e`/`-f` and a file argument, on the grounds
   that it provably cannot write.

Option 1 is the smaller change and keeps the guard blunt; option 2 is the more
accurate one and is what the stated rationale actually implies. My preference
is 1, because the doc is currently the thing that is wrong: it describes a
narrower block than the handler implements, and that gap is what surprised me.

Running tally of guards that misfired on their own author during this release:
the `release_blocker` step threshold (twice), the `STOPPING BECAUSE:` matcher
versus markdown emphasis, and now this. None was a false alarm about DANGER —
all four are cases where the guard's *stated* contract and its *implemented*
contract differ.

## 13:40 · action · Phase 3 closed — the abort deadlock was a documentation bug

Task 3.1. `release_blocker` only stands down at `last_completed_step >= 13`,
but RELEASING.md mandates ABORT on any failed BLOCKING gate and those gates are
Steps 8-12. So on an abort the guard denied the Stop the agent needed in order
to REPORT it.

Diagnosis changed the fix. The mechanism out already existed — no state file
means no release in flight, so deleting it releases the guard — and a test now
proves that end to end. What was missing was any STATEMENT of it. An
undocumented escape hatch is, to the agent hitting it, indistinguishable from
one that does not exist: it retries, is denied again, and burns turns.

Fixed the deny TEXT, not `matches()`, and the reason matters. No signal in a
Stop event distinguishes "aborting a failed gate" from "avoiding the acceptance
suite", and this handler exists specifically to stop the latter — its own deny
text cites `example-context.md` on acceptance-test avoidance. Detecting an abort
would mean trusting the agent's own account of the one thing it is most
motivated to misreport. A second test asserts the message warns against deleting
the file merely to end the session, so making the exit discoverable does not
make it attractive.

Verified live over the socket in both directions: state file present -> denied
WITH the abort instructions; file deleted -> guard stands down and
`auto_continue_stop` answers instead. The synthetic state file was removed
immediately after — a fabricated release authorisation must not outlive the
probe that needed it.

## 14:05 · finding · Task 4.4 audit found a live git spawn the guard could not see

Task 4.4 asked whether `run_git` should be the only IMPORTABLE path to git.
Gathering evidence to answer it turned up something better than the answer.

Five handler modules import `subprocess`. Three do so legitimately
(`lint_on_edit`, `validate_eslint_on_write` spawn linters, not git) and two
import it only for exception TYPES while already using `run_git`. So an
import-graph check would need an allowlist covering most of its own hits —
precisely the "list of whatever failed last" that `_EXEMPT`'s docstring warns
against. Declined.

But the fifth was real. `git_hooks_executable_fixer.py:85` spawns
`subprocess.run(list(_GIT_HOOKS_PATH_CMD))` where
`_GIT_HOOKS_PATH_CMD = ("git", "rev-parse", "--git-path", "hooks")`. Ran the
guard against the real tree before touching anything: it reported **"NO direct
git spawns"** while that call sat in it.

This is the Plan 00246 escape recurring one container out. Task 4.2 accepted
that resolving a module-level STRING constant is reading rather than guessing;
a module-level SEQUENCE constant is the identical claim about the identical
kind of assignment, and `list(...)` around it changes the container and nothing
else. Declining to look inside was not caution, it was the same blind spot with
a different spelling.

Fixed both halves. The guard gained `_module_sequence_constants` and
`_argv_words` (bare NAME, `list`/`tuple` wrapper, existing literal); three
negative controls — another tool, an unbound name, a mixed-type sequence —
passed from the start, which is what keeps a widening from becoming guessing.
Then the handler itself moved onto `run_git`.

Two things fell out of that move rather than being looked for:

- `import subprocess` and its `# nosec B404` left the module entirely, because
  `run_git` never raises and the exception handling existed only for that.
- It passed `cwd=None` when the event carried no cwd, which inherits the
  DAEMON's working directory — `/`, never the project. That is the Plan 00237
  scoping shape: git failed in a non-repository and the handler silently did
  nothing, which reads exactly like a repo with nothing to fix. `_repo_root`
  now falls back to `ProjectContext.project_root()` and reports visibly when
  neither resolves.
