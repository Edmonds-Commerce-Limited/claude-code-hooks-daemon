## 10:41 · finding · — — why this plan exists: 00201 guarded 2 of 7 surfaces

Plan 00201 shipped believing "sensitive content" meant file *content*. It does
not. The evidence was already sitting in the rewrite built to clean this repo's
own history: `git-filter-repo --replace-text` alone was nowhere near enough —
four distinct mechanisms plus two manual steps were needed, across seven
surfaces. Two are now guarded. Five are not, and all five enter through
`Bash`, which `matches()` rejects before it looks at anything:

```
def matches(self, hook_input):
    tool_name = hook_input.get(HookInputField.TOOL_NAME)
    if tool_name not in (ToolName.WRITE, ToolName.EDIT):
        return False
```

The concrete failure: force-push the cleaned history, then make one
`git commit -m "<term>"`. The repo is contaminated again and BOTH guards
report all-clear — the scanner because it reads `git ls-files` blob contents,
the handler because it never saw the call.

That is the DBF question answered honestly. The defect was never "165 places
carried the term". It was "nothing could see them", and that fix is only
finished when the guard sees every surface the rewrite had to touch.

## 10:41 · decision · — — extend the handler, do not add a second one

## 11:08 · decision · P1 — gate on a git invocation, match the whole command

Two candidate designs for the Bash haystack:

1. **Parse the metadata operands** — extract just the `-m` message, the tag
   name, the branch name, the config value, and match only those. Precise, but
   needs shell-aware parsing (quoting, `--message=`, compound commands), and a
   parser is exactly the sort of thing that is wrong in a way nobody notices.
2. **Gate on the git subcommand, then match the whole command string.**

Chose 2. The gate is a `git` invocation whose NEXT token is a metadata
subcommand — token-based, not substring, so `untracked/git-notes` and a
sentence mentioning a branch do not qualify. `commit`, `tag` and `branch` are
ordinary English words; matching them bare would have been a disaster.

Cost of 2: a compound command where the term is in an unrelated part
(`grep <term> f && git commit -m 'clean'`) is denied. Accepted, and named in
`get_claude_md` with the remedy (split it into two calls). That is a rare and
loud false positive; a subtly wrong parser is a quiet false negative, and this
is a guard.

## 11:08 · finding · P1 — the read exemption is what keeps the guard alive

The sharpest constraint on this design is not the leak — it is that a term
legitimately appears on the command line whenever you SEARCH for it or REMOVE
it. `grep -rn <term>`, `git log --grep=<term>`, `git branch --list '<term>*'`,
and this project's own `refresh.sh` all name a term while writing nothing.

Denying those would block the remedy. 00201's own lesson applies directly: an
unfixable false positive does not make people careful, it makes them switch the
handler off — which costs more than the leak it was meant to prevent. Hence
`_GIT_READ_ONLY_FLAGS` (`--grep`, `--list`, `-l`, `--get`), and hence the
metadata-write gate rather than "any Bash command".

Encoded as its own test class with 9 allowed-cases, because this is the
property most likely to be broken by a future well-meaning widening.

## 11:42 · decision · P2 — grandfathering that cannot rot into an amnesty

The gate must be green before the force-push or nobody will trust it, but a
grandfather that outlives its reason is worse than no gate. Two mechanisms,
each with its own expiry:

- **`history_baseline: <sha>`** exempts commits reachable from it. It needs no
  manual removal: the rewrite gives every commit a NEW sha, so this one stops
  resolving — and an unresolvable baseline exempts NOTHING (fail-safe). The
  gate therefore tightens to full-history coverage by itself the moment the
  rewrite lands. Encoded in `test_unknown_baseline_ref_sweeps_everything`.
- **`history_grandfathered_refs: [...]`** for the three tags. This one does NOT
  auto-expire — the same tag names survive a rewrite with cleaned messages — so
  the checker reports a `stale-grandfather` violation the moment an entry stops
  being needed (ref gone, or ref now clean). The escape hatch polices its own
  obsolescence instead of trusting anyone to remember.

Refs are deliberately never covered by the commit baseline: a ref has no
ancestry, so exempting by the tagged commit would let a tag created TODAY on an
ancient commit sail through an all-grandfathered history.

## 11:42 · finding · P2 — `%(contents)` on a branch head is a trap

`git for-each-ref --format=%(contents)` returns the TIP COMMIT's message for a
branch head, and for a lightweight tag. Scanning it blindly re-reported every
commit message a second time under the `tag-message` surface — and worse,
laundered it straight past the baseline, because refs are never grandfathered.

Surfaced by the baseline test failing on a repo whose only contamination was
already exempt: it reported `[tag-message] main`, which is not a thing that
exists. Fixed by requiring `%(objecttype) == "tag"` (an annotated tag is the
only ref with a message of its own) and pinned with two regression tests.

## 12:06 · decision · P3 — exercise the coverage matrix, never declare it

Phase 3's job was "a test that proves no surface is unguarded". The obvious
implementation is a list of surface names plus an assertion that each appears
in some registry — and that is worthless. A declaration of coverage is exactly
the kind of artifact that stays green while the thing it describes rots.

`tests/unit/qa/test_leak_surface_coverage.py` instead exercises all 14 cells of
a 7-surface × 2-guard matrix: for each surface it actually contaminates
something and asserts a real guard catches it. Both guards, because each is
blind where the other sees — a PreToolUse handler cannot see what is already
committed, and a batch scanner cannot stop the next write. A surface with only
one of them is half-covered, which is what every one of these was before this
plan.

Two extra tests keep the LIST honest as well as the guards:

- adding a surface row without a contamination fixture raises rather than
  silently contaminating nothing and "passing"
- the row count is pinned, so a silently-dropped row fails
