# Plan 00247 Journal — 2026-08-17

## Failsafe recovery cron

Not created for this plan, which is the plan's own subject: cron `8326de0b`
(hourly at :23, non-durable) is already live for this session, and its prompt is

## How this plan came to exist

A dogfooding report from the user: the daemon's own handler is what prompts these
crons to be created, and they must never stack — one only, updated or
dropped-and-recreated, never accumulated.

I had already hit it without recognising it. `CronList` showed TWO identical
hourly crons at :23 (`8326de0b` and `f12d9c0d`), and I deleted the duplicate by
hand as a tidy-up rather than treating it as a signal. Same failure as the
`.git/index.lock` file in Plan 00246: I cleaned up the symptom and moved on.

Then it happened a third time, live, mid-investigation: running `mkplan.bash` for
THIS plan fired the creation advisory telling me to create a cron "NOW" while one
was already running. Hard to ask for better evidence.

## The defect

`_CREATION_GUIDANCE` said "Create a non-durable hourly failsafe recovery cron
NOW" with no instruction to look first. It fires per PLAN.md creation, so a
session that creates two plans gets two crons, at the same minute, both firing on
the same session.

The part worth recording is that the handler's own module docstring already
claimed the fix:

    Decision D2 (PLAN.md): ... The agent uses CronList to avoid duplicate creates.

Plan 00139 decided it. The handler cites it. `CronList` then appears only in the
PROGRESS guidance, and even there only as "recreate if missing" — nothing about
one already existing, and nothing at all in the text read at creation time. So
this was never a design gap; it was a decision recorded and not implemented,
which is the same shape as Plan 00246's finding that `utils/git_repo.py` declared
an invariant nothing enforced.

The dedupe scout confirmed no live plan covered it and pointed at 00139 as the
origin.

## Why one cron is sufficient — not merely tidier

The canonical prompt is plan-agnostic: "your most recent work on the active
plan/task". It never names a plan, so one cron already covers every plan in the
session. A second is not extra safety, it is a duplicate wake-up on the same
session — and the advisory explicitly warns against treating the cron as a
heartbeat, which stacking quietly does by doubling the tick rate.

## What changed

Creation guidance now leads with `CronList`, reuses what is running (recording
THAT id in the plan's journal), deletes extras, and creates only when none is
listed. Progress guidance is now a three-way repair — exactly one, more than one
(delete extras), none (create) — which matters because progress is the phase that
fires repeatedly, so it is where an already-stacked session gets fixed.

`get_claude_md()`'s lifecycle table said "Create a non-durable hourly cron now",
so it would have contradicted the advisory and won by being resident. Updated in
the same change, with a test asserting the two agree.

## The sibling had the same bug

`background_process_tracker` said "Create a non-durable recurring watchdog cron"
unconditionally, and it fires on EVERY backgrounded process. This session
launched several — QA runs, CI waiters, a 3.12 test sweep — so following that
advice literally would have produced one identical watchdog cron each, all
running the same `harvest-background` command. One covers the session because the
harvest is global, not per-process. Fixed the same way, tests first.

## Guarding a text-only fix

There is no mechanism to fix here: `CronList`/`CronCreate`/`CronDelete` are
Claude Code tools, so the handler can only advise. That makes the guidance text
itself the deliverable, and guidance text is exactly what erodes silently under
later rewording — which is how D2 came to be claimed but not done for however
long.

So the tests assert the four separable instructions rather than the wording: that
`CronList` is named, that the create step is CONDITIONAL, that reuse is
mentioned, and that the one-per-session invariant is stated. Plus one asserting
the resident CLAUDE.md table agrees with the injected advisory, since a
contradiction between them is worse than either being wrong alone.

## Verified against the running daemon, not just the unit tests

Restarted the daemon and probed the live socket through the production wrapper
`.claude/hooks/post-tool-use` with a synthetic plan-creation event: the emitted
advisory contains "CronList FIRST" and "EXACTLY ONE". The same restart
regenerated CLAUDE.md and the daemon auto-committed it (`ca4b0599`) before the
source was committed — the generated-artifact-ahead-of-source shape RELEASING.md
Step 13 warns about. Harmless here because the source commit follows immediately,
but worth noting that it happens automatically and would be easy to leave behind.

The plan README edit landed mid-QA-run, so the doc checks that scan markdown were

doc_truth, doc_snippets, british_english, sensitive_content, repo_hygiene — all

Recounting the plan tree for the statistics turned up something unrelated and
worth recording: an empty `CLAUDE/Plan/CLAUDE/Plan/` directory, the residue of a
`mkdir -p CLAUDE/Plan/...` run from inside `CLAUDE/Plan` itself. Git does not
track empty directories, so `git status` never showed it and it survived
indefinitely — but it sits in the plan root, so a naive folder count reads 35
where the README says 34. That is the failure mode: a silent discrepancy between
two counts, where the discrepancy is not a plan at all. Removed with `rmdir`
(which refuses non-empty directories, so it could not take anything real).

`git mv` refused the archive move — "source directory is empty" — because the
whole folder was still untracked. Nothing to preserve history for, so a plain
`mv` is correct here; `git mv` only earns its keep when there are tracked paths
whose history should follow.

The best evidence the fix works is not a test: closing this plan tripped the
progress advisory, it told me to run `CronList` first, I did, exactly one cron
(`8326de0b`) was listed, and nothing was created. Before the fix that same edit
would have read "create a non-durable hourly cron NOW".
