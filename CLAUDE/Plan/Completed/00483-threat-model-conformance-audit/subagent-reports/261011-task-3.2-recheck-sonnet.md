Characterisation (in-process, same chain, `untracked/scratch/extra_inproc.py`):

- P2: `git commit -F - <<'EOF'` with `git reset --hard` in the body allows; `git -c core.x=1 commit -F - <<'EOF'` and
  `git -c user.email=a@b.c commit -F - <<'EOF'` deny by destructive_git. `git -c k=v commit -m "$(cat <<'EOF'...)"`,
  `git -C /tmp commit -F -` and `git -c k=v commit -m '...git reset --hard...'` allow (the `-C` form is denied by the
  conflict gate for the unplaceable directory, which is correct). So the `-F -` heredoc body is read as code only when a
  `-c` global option precedes `commit`. N383 covers a quoted global-option value, not this.
- P1: `gh pr create --title x --body "$(cat <<'EOF'\nblocks git reset --hard\nEOF\n)"` and
  `gh issue comment 5 --body "$(cat <<'EOF' ... )"` deny (destructive_git for `reset --hard`, git_stash for `stash`).
  `--body-file - <<'EOF'` and plain-text bodies allow; `git commit -m "$(cat <<'EOF'...)"` allows. This is the standard
  PR-body idiom and the ordinary shape of any PR or comment that describes a blocked command.
- P3: `cd "$(git rev-parse --show-toplevel)" && git commit ...` and `cd $PROJ && git commit ...` deny with "this commit was
  NOT checked ... the directory needs an expansion the daemon cannot perform". `cd /tmp && git commit` also denies
  (not a repository), correctly. The one-level `$(git rev-parse --show-toplevel)` already resolves for path judgement
  since fp-batch2; the commit gates did not take it. A commit gate that cannot place the repository fails closed, which
  the owner's R3 ruling (deny only on a positive finding) dropped for the secret guards; it was not applied here.

### Proposed new ledger entries (NOT added; for the coordinator)

- **P1. destructive_git and git_stash read a quoted heredoc inside `gh ... --body "$(cat <<'EOF' ... EOF)"` as a command.**
  Evidence: probes d-j2, j2a, j2b above; `--body-file -` and `git commit -m "$(cat <<'EOF'` are already data. Remedy:
  treat the quoted-delimiter heredoc body of a `$(cat <<'EOF'...)` substitution as data when the receiver is a `gh`
  `--body`/`-b` value (the same sink rule as the `gh` body heredoc batch (b) added), gate row `a8-*`.
- **P2. destructive_git reads the quoted-heredoc commit message of `git -c k=v commit -F - <<'EOF'` as a command.**
  Evidence: probes d-j1, j1a, j1b versus allow rows cA, cG. Remedy: the git-global-option reader (`GIT_INVOCATION`,
  N383) hands the heredoc-sink decision the same segment it uses without `-c`; add the `-c` form to the gate.
- **P3. conflict_marker_commit_gate denies `cd "$(git rev-parse --show-toplevel)" && git commit` and `cd $PROJ && git commit`.**
  Evidence: probes d-h1, d-h4; control d-h2 allows. Remedy: resolve the one-level `git rev-parse --show-toplevel` the way
  path judgement does, and for any other unresolvable directory allow with an advisory instead of denying (owner R3
  applied to the commit gates). This needs a 00483 R3 check: if the owner wants this gate to stay fail-closed, record that
  and dismiss P3 as a correct deny.
