## What changed

- New `utils/recursive_search.py` finds the trees a search command reads and asks the existing
  `directory_contains_protected` walk (same 5000-entry cap, same answer past it) whether a protected
  file is under them. It adds no walk of its own, so ledger 00474 N348 is neither worsened nor fixed.
  The only walk change is an optional `skip(path, is_dir)` hook on `directory_contains_protected`.
- Shapes covered: `grep -r` family, `ugrep -r`, `rg`, `ag`, `ack`, `find ... | xargs <search>`,
  `find ... -exec|-execdir <search>`, literal `bash -c`/`sh -c`/`eval`, `sudo`/`env`/`timeout`
  prefixes, and `git grep` (tracked files via one `git ls-files`; `--no-index` walks the tree).
  The obfuscated spellings (`g\rep`, `"grep"`, `$G`) are dismissed and not handled.
- Tool behaviour is modelled: `rg` and `ag` skip hidden entries and gitignored files (decided with
  `git check-ignore`, so a failure reads the file) unless `--hidden`, `-.`, `-u`, `-uu`,
  `--no-ignore*`, `--unrestricted`; `grep` and `ack` read everything. Exclusions that remove the
  protected path allow the search: `--exclude-dir`, `--exclude`, and `rg -g '!glob'` (only while every
  `-g` glob is negated).
- `secret_file_guard` runs the check after the text scan clears a command and where an exemption
  clears it, on a new `search` route: the `read` rule plus a remedy line, never the file name.
  `quarantine_artefact_read_guard._bash_mention` runs the same check (N144). Its deny reason has no
  remedy line, because the matcher returns only the glob.
- The option parser and command splitter moved out of `flaggable_content_channel_guard` into the new
  module so the two guards read one grammar. That guard's behaviour is unchanged.
