## 03:50 · finding · — — how this was found, and what it cost to attribute

Not filed from a review. It surfaced while regression-testing Plan 00347's
11-site commit: `tests/unit/core/test_project_context.py` failed two tests, in
a file that plan had not touched.

The first hypothesis was that Plan 00347 had broken something. Disproving that
took a clean `git worktree` at the previous commit and a re-run — which is the
strongest argument for fixing this rather than noting it. **The failure accuses
innocent code**, and the next agent to trip it will pay the same cost, or worse,
will "fix" the file that is already correct.

Bisected to a single pair:

```bash
pytest tests/unit/handlers/post_tool_use/test_goal_injection.py \
       tests/unit/core/test_project_context.py
# 2 failed, 84 passed
```

Either file alone passes. `tests/unit/handlers/pre_tool_use` and
`session_start` are both clean against `test_project_context.py`;
`post_tool_use` and `stop` are not, and within `post_tool_use` the bisect
landed on `test_goal_injection.py`. **`stop` was not bisected** — it may be the
same file reached transitively, or a second leaker. Task 2.1's success
criterion is deliberately written to require sweeping every handler test file,
not just this one.

The leaked value is unambiguous — a `tmp_path` from a goal-injection test
appearing inside a project-context assertion:

```
assert PosixPath('.../test_ledger_failure_never_bloc0/untracked')
    == PosixPath('.../test_initialize_with_valid_con0/project/.claude/hooks-daemon/untracked')
```

## 03:51 · thought · T1.2 — do not skip straight to the fix

`test_goal_injection.py` patches `ProjectContext.daemon_untracked_dir` two
ways: an autouse fixture using `pytest.MonkeyPatch.context()`, and the
function-scoped `monkeypatch` fixture, sometimes on the same attribute. The
obvious suspect is restore ORDER — an outer manager restoring the original
first, then an inner one restoring what IT captured (the outer's patched value)
leaves the patch installed for good.

That is a hypothesis, not a diagnosis, and it is written into the plan as one.
A second candidate exists: `monkeypatch.setattr` on a CLASSMETHOD captures the
original via `getattr`, which yields a bound method rather than the descriptor,
so "restoring" installs something subtly different from what was there.

Both produce the same symptom. They do not have the same fix. Confirm before
changing anything.

Session crons: failsafe recovery `5398b3f9` (hourly :23) and background
watchdog `ef8543f1` (hourly :17) were both already live — CronList confirmed
exactly one of each, so this plan REUSES them and created none.

## 05:10 · finding · T1.2 — measured the class, and the measurement killed one theory

Task 1.2 named two candidate mechanisms and said to confirm rather than assume.
The confirmation took one probe: print `ProjectContext.__dict__` after the
offending test.

```
baseline:            classmethod(<function ProjectContext.daemon_untracked_dir>)
after the leaker:    classmethod(<function TestGoalLedgerIntegration.
                                 mock_project_context.<locals>.<lambda>>)
```

What survives is the FIXTURE's lambda. That is decisive, and it eliminates the
classmethod-descriptor theory outright: pytest already reads `target.__dict__`
for classes precisely to avoid the bound-method trap, so the descriptor was
never the problem.

What is left is restore ORDER. A test-level `monkeypatch` patches an attribute
the class's autouse fixture has already patched. The fixture's context exits
first and restores the original; the test-level undo then runs and faithfully
restores what IT recorded as previous — the fixture's lambda — which then stays
on the class for the rest of the process.

It also explains the puzzle from the bisect: why one test out of four in that
class leaked. The others patch `write_goal_signal`, a DIFFERENT attribute, so
their unwind never collides with the fixture's.

## 05:12 · finding · T2.1 — the sweep found three more, and they are an idiom

Fixing the one file found by the bisect would have felt complete. The success
criterion demanded sweeping every handler test file against the victim anyway,
and that turned up three more, all outside the directory the bisect landed in:

```
tests/unit/handlers/pre_compact/test_compaction_signal.py
tests/unit/handlers/status_line/test_context_sidecar.py
tests/unit/handlers/stop/test_goal_ledger_stop_defence.py
```

All four are the same shape, and it is a deliberate, sensible idiom rather than
an accident: patch `ProjectContext.daemon_untracked_dir` to RAISE, to prove the
handler fails open. Four authors reached for it independently. That is why this
got a check rather than four corrections — the next person writing a fail-open
test will reach for it too.

Sweep widened past the criterion to every `tests/unit/*` directory and
`tests/integration`, on the reasoning that a process-wide singleton is not
leaked only by handler tests. Nothing further found, but three of four leakers
being outside the original directory is the argument for having looked.

## 05:14 · decision · T2.2 T3.1 — two things deliberately NOT built

**No backstop in `tests/conftest.py`.** It was the obvious move: the
`reset_project_context` autouse fixture already runs for every test, so
restoring the class's attributes there would catch every future leak. Rejected
because it would MASK the next one, and being masked is this defect's entire
cost — it survived because nothing ever reported it. A backstop here buys
tidiness and sells the signal.

**No per-module attribute fingerprint.** It would run across all 18,627 tests
to catch a defect with four known instances, and the subprocess pair-check
gives the same signal exactly where the risk is. Rejected on cost, recorded so
the option is not re-derived from scratch later.
