## 18:14 · finding · P1 — I misread a CI run as green, exactly the way the runbook warns about

Worth recording because it happened to me while writing the rule against it.

I backgrounded `timeout 900 gh run watch <id> --exit-status` followed by a
`gh run view`. The task reported exit code 0 and I nearly took that as CI green.
The watch had actually hit its timeout and exited 124; the 0 was the LAST
command in the chain. The run was still `in_progress` with one of five jobs
unfinished.

This is the `QA_EXIT` trap in different clothing — a wrapper's status standing in
for the thing it wrapped — and the runbook already warned about it in Step 5
without generalising to Step 8. It does now. The general form: **when a command
exists to observe something, never read the observer's exit code as the
observation.** Ask the thing itself.

What caught it was reading `gh run view --json status,conclusion` out of habit
rather than trusting the exit code. Per-job status was the confirmation: four
green, one still running.

`sensitive_content` denied my draft comment on #36 because I had quoted the
reporter's concrete vendor path back at them. The reporter had filed that path
publicly themselves, so nothing was being protected from them — but the guard is
right anyway, and the reasoning is worth keeping.
