## 07:05 · decision · Task 3.1 · guard the reason, in CI, not the release scope

The task suggested adding these files to `RELEASING.md` Step 12.0 so the
existing declaration-driven guard picks them up. I did not, for two reasons.

**That declaration is the RELEASE-blocking set.** Adding files to it changes
what a release gates on, which is a decision about release scope rather than CI
visibility. Plan 00250 Task 1.2 hit the same fork and left it as a
recommendation to the owner; making the opposite call here would be
inconsistent for no reason but convenience.

**A file list is the wrong key anyway.** The two files spell their skip
differently and sit in different directories (`acceptance/` and `integration/`),
so the existing guard's `tests/acceptance/...` path regex would not have found
one of them. What they share is the artefact, not a path.

So `tests/relay_gate_guard.py` keys on the skip REASON and fires only when `CI`
is set. That last part is what makes not touching `RELEASING.md` sufficient: on
a runner the binary is now guaranteed, so a skip for its absence means the
provisioning broke; on a developer's machine with no Rust toolchain the skip is
honest and stays a skip. Proven both directions by nested pytest runs.

The residual coupling worth naming: the CI step's two paths and the two the
tests read are related by nothing but matching string literals.
`test_ci_provisions_the_relay.py` asserts the workflow still names both.

## A correction I should make before someone relies on it

I wrote in the commit message that the CI step "reproduces the deployed binary
byte-for-byte (same sha256)". That was measured locally and it is true *there*.
It is **not** true across machines:

| Where | size | sha256 |
| --- | --- | --- |
| `/workspace` | 570056 | `f6484c23…` |
| the runner | 570056 | `79bc27ac…` |

Same size, different hash. rustc embeds absolute paths in the binary, and the
build directory differs — so the reproducibility claim is scoped to a fixed
build path, not to the artefact in general. Nothing depends on the hash today,
which is exactly why it is worth writing down now: the next person to add a
"cache the relay by content hash" step would otherwise discover this the
expensive way.

The same shape as this week's other errors — a fact measured on one machine,
stated as a fact about the class. Here I caught it from the runner's own log
rather than from a failure, which is the cheap way round.
