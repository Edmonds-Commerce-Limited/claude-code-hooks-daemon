## finding · P1 — why the docstring's "fable switch already drives effort
down" claim didn't save the incident

`.claude/ccy/claude-supervise.py`'s module docstring (lines 52-62 before this
plan) already claimed every `/model fable` injection unconditionally drives
effort down to fable's floor via the "coupled effort" mechanism
(`arm_coupled_effort`/`_coupled_effort_target`, Plan 00278 continuation). That
claim is TRUE as far as it goes — the coupled correction did fire and did
inject `/effort low` at 16:01:35. The incident happened anyway because of
TWO compounding gaps, not one:

1. **The one everyone expected**: `mark_coupled_effort_injection()` is called
   by the HOST the moment the PTY `write()` syscall succeeds
   (`_apply_post_injection_bookkeeping`, gated only on `injected`). A
   successful write proves the bytes reached the pty; it proves NOTHING
   about whether the busy session actually applied them as a command. The
   session swallowed the keystrokes; the supervisor's bookkeeping closed the
   episode anyway. Classic inject-and-assume.
2. **The one that would have re-broken any naive "just check the sidecar
   again" fix**: the ONLY other mechanism that watches effort
   (`note_model_reading`'s floor logic, feeding `_effort_pending`) is
   explicitly documented as raise-only ("INVARIANT: this family only ever
   RAISES effort... a session already at or above its floor... is never
   touched"). Once the coupled correction (wrongly) marked itself done,
   fable sitting at xhigh is NOT "below its floor" from that mechanism's
   point of view — it's above it — so it structurally could never re-fire
   even on a fresh reading. There was no continuously-reasserted invariant
   anywhere in the file; only a one-shot post-switch nudge with no
   read-back.

So the fix needed BOTH a genuine read-back verification primitive (closing
gap 1) AND a standalone, continuously-checked invariant independent of the
raise-only floor machinery (closing gap 2) — a bolt-on read-back check on
the EXISTING coupled-effort pending state would not have been enough, because
that state is exactly what gets cleared the moment the (unverified) write
succeeds. DROP ANCHOR (`_evaluate_anchor`/`anchor_active`) is built as that
separate mechanism: it reads the same sidecar `SidecarReading.model_id`/
`.effort` fields already written by the daemon (Plan 00278), never trusts
`mark_*_injection` bookkeeping, and re-evaluates from scratch on every fresh
non-stale reading regardless of what any other mechanism believes it already
fixed.

No other gap was found — `_downgrade_episode` correctly closes the instant a
switch reaches fable (`_family_rank(family) > _family_rank(ep_family)`), so
the xhigh downgrade-episode target never outranks the fable floor in
practice; the risk there is only a `CCY_MIN_EFFORT_LEVELS` misconfiguration
setting fable's OWN floor above low, which `_coupled_effort_target` now
clamps defensively (Task 2.3) even though the anchor would correct it within
one retry cycle regardless.

## decision · P2 — ESC interrupt NOT implemented (deviation from the brief)

Task 2.2 asked for an ESC interrupt on escalation. Implemented instead:
suppression of continue/goal (work-continuing) injections while anchored,
plus a loud rate-limited owner alert — but no ESC send. Rationale: an ESC
mid-turn interrupts whatever the session is doing, which for an in-flight
`/compact`/escape sequence the state machine is managing could leave the
AWAIT_COMPACTING lifecycle in a worse state than the effort misconfiguration
it was meant to protect against, and the anchor's own retry-until-verified
`/effort low` already IS the corrective action the incident needed — the ESC
was a belt-and-braces stronger stop, not the primary fix. Left for a
follow-up given the added complexity of getting ESC-during-compaction right
without a live incident forcing the tradeoff. `PLAN.md`'s Task 2.2 and the
matching Success Criterion are marked partial, not complete, to keep this
visible.
