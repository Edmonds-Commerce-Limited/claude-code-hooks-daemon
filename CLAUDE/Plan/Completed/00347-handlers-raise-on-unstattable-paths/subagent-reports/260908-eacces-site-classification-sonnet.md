## Key findings for whoever implements Task 2.1

1. **`markdown_table_formatter.py:233` is caller-supplied and is NOT in the
   Task 2.1 list**, even though its sibling at line 224 (same `file_path`,
   same handler) is. Line 224 gates `matches()`; line 233 is a second,
   independent `Path(file_path).exists()` inside `handle()`. Fixing only 224
   leaves 233 raising if `handle()` is ever reached without `matches()`
   having run first (e.g. direct unit-test invocation, or a future dispatch
   change). Low stakes either way — this handler never denies — but it
   should get the same fix in the same pass.

2. **`plan_qa_edit.py:165` and `docs_qa_edit.py:140` need more care than "false
   is safe."** Both compute `exists_before = file_path.is_file()` and pass it
   downstream as `file_exists_before` into the plan-QA / docs-QA check
   context (`docs_qa/types.py:66` and the plan-QA equivalent already type it
   `bool | None`, i.e. the consumers already expect a tri-state). Three
   consumers read it three different ways:

   - `plan_qa/checks/archive_immutability.py:30`:
     `if target is None or not target.in_archive or context.file_exists_before is not True: return []`
     — this DENY-class protection (plans in `Completed/`/archive must not be
     edited) fires **only when `file_exists_before is True`**. Both `False`
     and `None` skip it.
   - `plan_qa/checks/task_grammar.py:42`: fires only when
     `file_exists_before is False` (scoped to brand-new documents).
   - `plan_qa/checks/template_metadata.py:29`: fires when `file_exists_before is not False`
     (i.e. True or None).

   So if `is_file()` raises `EACCES` on an archived plan file sitting behind
   an unreadable ancestor directory, and the fallback is the pathlib-mimicking
   "not known → False," `archive_immutability` silently stops protecting that
   file — a DENY-class guard exempted exactly the way the plan's Overview
   warns about for `write_clobber_guard`. Unlike `comment_size.py:226` (next
   point), there is no fallback boolean that is safe for every consumer here:
   `True` satisfies `archive_immutability` but would wrongly exempt
   `task_grammar`'s new-document leniency; `False`/`None` satisfies
   `task_grammar` but defeats `archive_immutability`. The safe choice is to
   bias toward `True` (assume it exists) when the answer is genuinely unknown,
   because `archive_immutability` is the one DENY-class protection in the set
   (the other two are advisory grammar/metadata checks, not immutability
   guards) — but this needs its own RED test against `archive_immutability`
   specifically, not a blanket boolean flip, and likely needs the read at
   `content_before = file_path.read_text(...) if exists_before else None`
   (line 151/176) guarded too, since assuming `True` on an unreadable path
   sends execution straight into a `read_text()` that will raise the same way.

3. **`write_clobber_guard.py:155` — confirmed, and the naive fallback is the
   dangerous direction.** `if not Path(path).is_file(): return False` (skip
   the guard) is the "new file, nothing to clobber" branch. If `is_file()`
   raises and the fallback is the pathlib-mimicking "not known → False" (i.e.
   `not Path(path).is_file()` becomes `not False` = `True` → "treat as new" →
   `matches()` returns `False` → guard never fires), a file this session never
   read, sitting behind an unreadable directory, gets silently exempted from
   the clobber check — precisely the scenario the plan's Overview names this
   handler for. The safe fallback is the opposite of pathlib's convention:
   treat an unstattable path as **an existing file** (`is_file()` → `True`),
   which sends control to `return not self._is_known(...)` — almost certainly
   `True` (an unreadable path was never "read" this session) — so the guard
   denies. Denying a write to a path the daemon cannot even stat is the
   correct conservative outcome for a clobber guard.

4. **`comment_size.py:226` — confirmed, and here the naive "false" fallback
   IS safe**, unlike case 2/3 above. Contrast matters: `handle()` (line 309)
   computes `grows = chars_before is None or chars_after > chars_before` —
   `content_before is None` (which is what falling back to `is_file() → False`
   produces, per `_region_before`'s own docstring "which always counts as
   growth") makes `grows` `True`, which is the branch that can DENY. So
   defaulting to "not a file" here biases toward the DENY, not away from it —
   the opposite risk profile from `write_clobber_guard` even though both are
   `Path(...).is_file()` calls feeding a `PreToolUse` DENY handler. This is
   the concrete illustration of the plan's point that "the correct fallback
   VALUE differs by site."

5. **`github_auto_close_keywords.py:242`** (newly identified as
   caller-supplied, not in Task 2.1's list): `path.is_file()` on a path parsed
   out of a `git commit -F <file>` / `gh pr create --body-file <file>`
   argument. The existing code already treats "missing/unreadable" as
   "skip this file's content" (`continue`), which is a DENY-class scanner
   (closing-keyword detector) silently not-scanning content it cannot read.
   An `EACCES` here reproduces an existing design choice rather than
   inverting it, but it is the same shape of risk as case 2: a message file
   the daemon cannot stat is treated exactly like a message file that does
   not exist, and its content (which might carry the banned pattern) never
   enters the scan. Worth a RED test even though the direction is "matches
   existing (arguably already loose) behaviour" rather than "a new inversion."

6. **`worktree_remove_handler.py:57`** (newly identified as caller-supplied):
   `path.exists()` where `path` is read straight from the `WorktreeRemove`
   event payload (`worktree_path`/`path` key) with **no containment check**
   at all (unlike `WorktreeCreateHandler`, which only ever builds a path from
   a slugified name under a fixed `.claude/worktrees/` prefix). This handler
   never denies — "WorktreeRemove is a side-effect-only event... always
   returns an empty allow" — so an `EACCES` here has no security
   consequence; the safe fallback is simply `False` (skip the optional
   `git worktree remove --force`), since `git worktree prune` still runs
   unconditionally right after (line 61) as the fallback cleanup path.

## Borderline cases (classified, not "uncertain," but worth a second look)

These are not marked UNCERTAIN — I traced each to a definite origin and have a
reasoned position — but they don't fit the plan's daemon-controlled examples
("config files, install directories, caches") as cleanly as the rest, so I'm
flagging the reasoning explicitly rather than letting it hide inside a table
cell:

- **`HookInputField.CWD` / StatusLine `workspace.current_dir"` sites**
  (`git_hooks_executable_fixer.py:104/188`, `git_branch.py:177/282`,
  `worktree_create_handler.py:96`). The daemon's own `project_containment.py`
  (lines 254-267) explicitly treats the event's `cwd` as the trusted anchor it
  resolves *untrusted* Bash-relative targets against — it is session/
  environment context Claude Code supplies, not a string the LLM writes into
  a tool-call argument for this event. I classified all of these
  daemon-controlled on that basis. The counter-argument: a session's `cwd`
  can itself have been changed by a prior `cd` the agent issued, so in a
  loose sense "the caller" chose it over time — but that is a different kind
  of control than "this tool call's argument names an arbitrary path," and
  none of the plan's example categories (`tool_input.file_path`, a Bash-parsed
  path, `get_file_path()`/`get_bash_write_targets()`) match it. Worth
  confirming this reading with the plan owner before treating it as settled.
- **`monorepo_detector.py:76/80`**. Classified daemon-controlled because the
  walk's root is the project root (SessionStart, no tool input involved at
  all) and the handler is advisory-only, but it is the one daemon-controlled
  site that recursively touches arbitrary depth into the repository tree
  rather than a fixed conventional name — structurally the closest of the
  "daemon-controlled" bucket to the original `core/utils.py:_written_paths`
  bug this plan is patterned on (a real filesystem walk, not a config lookup).

No site was left genuinely unclassifiable.
