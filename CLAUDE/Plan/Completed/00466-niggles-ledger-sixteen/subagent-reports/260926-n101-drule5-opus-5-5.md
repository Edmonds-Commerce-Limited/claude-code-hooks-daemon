## MAJOR 1: past the cap, a quoted brace inside the group produces a skeleton that does not cover bash's spelling

**Citation:** `src/claude_code_hooks_daemon/utils/shell_expansion.py:293-310` (`brace_skeleton`), reached from `secret_file_matching.py:1531-1546` (`_code_word_spellings`):

```python
for char in word:
    if char == "{":
        opens.append(len(out))
```

The scan does not model quotes. A `{` or `}` inside a Python string still counts as a group delimiter for the skeleton. Bash does not treat it as one.

**What it allows:** this is valid Python, a set display with 302 elements:

```
y = 0 if 1 else x .vault-{"{","pass","a0",...,"a299"}
```

Read as a shell word, bash's alternatives are `{`, `pass`, `a0`, … so it expands to `.vault-pass`. Past the 256-spelling cap, the branch builds the skeleton `.vault-{"*`, which normalises to `.vault-{*`. That glob cannot match `.vault-pass`.

| Tree             | `"{"`, heredoc                               | `"{"`, `-c`                       | `'{'`, heredoc                    |
| ---------------- | -------------------------------------------- | --------------------------------- | --------------------------------- |
| main 4f0a205b3   | deny, `R-SECRET-EVALUATION-ERROR` (over cap) | deny, `R-SECRET-EVALUATION-ERROR` | deny, `R-SECRET-EVALUATION-ERROR` |
| branch 1a11131b7 | **allow**                                    | **allow**                         | **allow**                         |

Main denies this shape and the branch allows it, which the brief defines as a defect. This is exactly the case the brief asked about: an over-cap code word that produces a protected path the wildcard form does not match.

**Class:** a fallback that stands in for a failed-closed enumeration, but parses brace structure differently from the shell it models. Anything that makes the skeleton pair braces differently from bash puts a case in this class: quoted braces, escaped braces, or `${`. The symptom is a skeleton that still holds a literal `{` or `}`, or that ends a group too early.

- **Impact:** the same read-back premise as round-4 MAJOR 1 (for example, `/proc/$PPID/cmdline`).
- **Grade:** MAJOR, to match how that finding was graded.

**Why the tests miss it:**

- `test_an_over_cap_code_word_that_could_name_a_path_denies` uses only unquoted groups.
- `TestBraceSkeleton` pins nesting and unmatched braces, but has no case with a quote-held brace.
- Nothing compares the skeleton against a real shell's expansion.

**Detector hypothesis:**

1. **Static rule:** if the skeleton still holds `{` or `}`, the fallback misparsed the word and must fail closed, as main does. Likely false positives are over-cap code words that also contain a string literal holding a lone brace. I expect these to be rare, but I have not measured it; re-running `probe_fp.py` would settle that.
2. **Stronger, differential check:** generate words with quoted and escaped braces inside groups. Compare `bash -c 'printf "%s\n" WORD'` against `fnmatch(spelling, normalise_word(brace_skeleton(WORD)))`, and require every bash spelling to match. This check prints only, so it runs nothing dangerous.

**Confidence:** high. Both trees were probed through the handler chain, in both the heredoc and the `-c` form.
