## Your two specific questions

**1. Can Python itself expand a brace-spelled name?** Not through anything the exemption allows.

- In the standard library, `glob`, `fnmatch`, `pathlib.Path.glob`, `os.path.expanduser` and `os.path.expandvars` do not expand `{a,b}`.
- Code that does expand braces needs an import outside the allowlist (`ctypes` with libc `glob`/`wordexp`, `braceexpand`, `wcmatch` with its BRACE flag). Such an import marks the program as reaching, so its literals are enumerated.
- So the real risk is not Python expanding braces. It is Python handing the text to a shell or to a file without the analysis noticing. That is what findings 1 and 2 are.

**2. Does the `_segment_command_word` change weaken main's heredoc exemption?** Yes, in one case: an option value that contains a space (finding 3).

- `secret_file_guard` and `secret_file_matching` never use that exemption; the guard scans heredoc bodies whole. So this is not a way to reach protected files, and I rank it minor for this check.
- It is a real loosening for the other handlers that do use the exemption, so it belongs under D-RULE.

## Finding 1 (MAJOR): the reach analysis misses a shell call reached through `operator`

**Citation.**

- `src/claude_code_hooks_daemon/utils/python_program_reach.py:73`, where `"operator"` is on `_STDOUT_ONLY_MODULES` (`"string"` is at :82).
- `:102`: `_REACHING_NAMES` matches only names spelled out in full.
- `src/claude_code_hooks_daemon/utils/shell_expansion.py:494`: literals are returned only when `hands_text_on` is true.

**What it allows.** Here is how such a program gets through:

- It imports only allowlisted modules: `os` and `operator`.
- It gets `os.system` by asking `operator.attrgetter` (or `operator.methodcaller`, or `string.Formatter().get_field`) for an attribute name built at runtime from pieces, such as `'sys' + 'tem'`.
- It passes a shell command whose protected path is written plainly in the program, spelled with braces.

What the checks then see:

- No reaching name appears, not even as a string constant, since the pieces are separate constants. So `reaches_beyond_stdout` is False.
- The braces in the program text are neutralised, and `view.literals` is empty.
- `_bash_interpreter_one_liner_mention` (`secret_file_guard.py:1092`) finds shell-exec calls by resolving `module.attr` names, and an `attrgetter(...)(...)` call has no such name.
- The other token streams do not expand braces.

So nothing denies the command. Bash then expands the braces and reads the protected file. On main, the same `-c` or heredoc text is brace-enumerated whole, and the command is denied.

**This is not the accepted runtime-assembly residual.** That precedent covers a *path* built at runtime (`'id_' + 'rsa'`), which no stream ever caught. Here the path is written out in the program and was caught on main. Only the *call* is built at runtime, and this branch is what stops the path being checked.

**The class.** The branch trusts a program because the dangerous names are absent, while an allowlisted module can fetch an attribute from a string built at runtime. A new case belongs to the class if an allowlisted module offers a way to fetch or call something by string name, and that way is not itself on `_REACHING_NAMES`. Known members: `operator.attrgetter`, `operator.methodcaller`, `string.Formatter.get_field`. `getattr`, `vars`, `globals` and dunders are already covered.

**Why the tests miss it.** Every reach test names what it calls in full: `os.system`, `getattr`, `__import__`, `sys.modules`, a variable holding the command. A grep of `test_python_program_reach.py`, `test_secret_file_guard.py` and `test_shell_expansion_brace_view.py` finds no `attrgetter`, `methodcaller`, `Formatter` or `get_field`.

**Detector hypothesis.** For each allowlisted module, list the public callables that take an attribute or method name as a string. Treat each as a reaching name, and pin one test per callable. That will always lag new routes. The sturdier Defence is to always enumerate the literals of an exempted program, each on its own, and neutralise only the braces outside string literals.

- This removes the need for reach analysis as a protection.
- It should not bring back the round-1 false positives: dict displays and f-string braces are code, not literals, and a format field like `{}` or `{name}` is not a brace expansion.
- Likely false positive: a literal that really contains `{a,b}` (a shell snippet held as data). That is rare, and each literal has its own cap.

**Confidence.** High, from the code path. To settle it, add a unit test on `analyse_python_program` with a program that imports only `operator` and `os` and builds the attribute name. Expect `reaches_beyond_stdout` to be False today.

## Finding 2 (MAJOR): a renamed `os.open` plus unlisted write functions writes a script that a later command in the line runs

**Citation.**

- `python_program_reach.py:236`: the `from … import` check only asks whether each imported name is a reaching name, and `open` is not one.
- `:241`: the `open` check matches only the literal name `open`.
- `:270`: `owner == "os"` checks what the object is called, not what it is.
- `_REACHING_NAMES` lists `write`, `writelines`, `write_text`, `write_bytes`, `writestr`, `fdopen`, `dup`, `dup2` and `FileIO`. It does not list `os.pwrite`, `os.pwritev`, `os.writev`, `os.sendfile` or `os.copy_file_range`.

**What it allows.**

- `from os import open as <alias>, pwrite, O_WRONLY, O_CREAT` gives a writable file descriptor. The name `open` never appears as a Name or an Attribute, and the owner check never fires.
- `pwrite` then writes a shell script containing a brace-spelled protected path.
- The program's stdout goes to the terminal, so `writes_a_file` stays False. The inert-sibling rule (`shell_expansion.py:553`) applies only when stdout goes to a file, so the same line may go on to run the script with `bash`.
- The literals are never enumerated, so nothing denies the command.

This is the same `> gen.sh; bash gen.sh` shape that D-RULE F2 pinned. Here the file is written by Python's own API instead of a redirect.

**The class.** The program writes a file that the shell or a later command executes, through a write primitive that neither the name list nor the `open`-mode rule sees.

**Why the tests miss it.** The write tests use builtin `open` with a write mode, `Path.write_text` and `.write`, all of which are caught. No test renames `open` on import, and none uses `pwrite`, `writev` or `sendfile`.

**Detector hypothesis.**

- Treat any `from os import open`, under any alias, as reaching.
- Treat every `os` function that writes through a file descriptor as reaching.
- Also apply the inert-sibling rule to every exempted program, whatever its stdout.

The Defence proposed in finding 1 (always enumerate literals) closes this too. Of the options above, the sibling rule is the noisiest: it would withdraw the exemption from `python3 … ; pytest`-style lines.

**Confidence.** High, from reading the code. To settle it, add a unit test on `analyse_python_program` for the aliased import with `pwrite` and a harmless literal.

## Finding 3 (minor for D-SEC; I suggest D-RULE re-rank it): the command-word resolver splits a quoted option value at its space and lands on a safe name

**Citation.** `src/claude_code_hooks_daemon/utils/shell_segmentation.py:868`:

```python
words = strip_reserved_word_prefix(segment).split()
```

The wrapper grammar (`_skip_wrapper_arguments`, :887) consumes exactly one whitespace-split word per value.

**What it allows.**

- In `sudo -p 'x cat' bash <<'EOF'`, `-p` consumes only `'x`. The next word, `cat'`, reaches `command_word`, which strips the quotes to `cat`.
- `cat` is on `DATA_SINKS`, so `strip_quoted_heredoc_bodies` hides the body of a heredoc that bash actually executes.
- On main, the same segment resolved to `x`, which is not a sink, so the body was scanned. This is new on this branch.
- `--prompt 'x cat'` behaves the same way. `env -C` and `sudo -D` with a quoted directory containing a space are the same shape, if that directory exists.
- It affects the handlers that use the exemption: `curl_pipe_shell`, `destructive_git`, `pipe_blocker`, `flaggable_content_channel_guard`, `quarantine_artefact_read_guard` and others.
- For `secret_file_guard`, the only effect is that a heredoc fed to Python behind such a wrapper loses the new, additional shell-exec literal scan (`secret_file_guard.py:1092`). That scan is not on main, and the wrapper already keeps the brace exemption away, so nothing is lost relative to main.

**The class.** A resolver splits on whitespace without respecting quotes, and consumes option values a fixed number of words at a time. A quoted value that contains a space moves the resolver onto a word inside that value.

**Why the tests miss it.** Every wrapper case in `test_shell_segmentation.py` (~:617) and `test_destructive_git_prose.py` (~:170) uses a single unquoted value.

**Detector hypothesis.**

- Tokenise the segment with the quote-aware splitter the module already has, not `.split()`.
- Or fail closed (return None) whenever a word consumed as a wrapper option value starts or ends a quote without closing it.

Likely false positive: none of note, because a quoted wrapper option value is rare.

**Confidence.** High, from the code path. To settle it, run `quoted_heredoc_command_words` on that shape: expect `['cat']` here and `['x']` on main.
