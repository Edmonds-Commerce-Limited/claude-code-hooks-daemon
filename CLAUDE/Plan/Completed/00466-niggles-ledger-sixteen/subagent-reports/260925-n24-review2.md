### MA2: B2's class is still reachable through shipped handlers; a 99 KB Bash command freezes the daemon for every session, and the advertised recovery command cannot recover it

- **Where**:
  - `handlers/pre_tool_use/lsp_enforcement.py:128`: `_BASH_GREP_PATTERN = re.compile(r"(?:^|\s|&&|\|\||;)\s*(?:grep|rg)\s+")`. A `\s` followed by `\s*` makes it quadratic on a run of whitespace. Measured alone (`probe_n24r2_f_regex.out`): 5k newlines 0.20 s, 10k 0.78 s, 20k 2.84 s.
  - `plan_number_helper.py`: the same kind of cost on quote runs. I did not isolate which pattern causes it.
- **Evidence** (`probe_n24r2_e_gilstarve.out`, this worktree's config). A ticker thread wakes every 10 ms beside the handler, so any long gap between wakeups means the handler held the GIL:
  - `enforce-lsp-usage` on `"true" + "\n"*99_000`: the handler took **73.5 s**, and the longest ticker gap was **73.5 s**.
  - `plan-number-helper` on `"echo " + "'"*99_000`: **37.5 s**, longest gap 37.4 s.
  - When the gap equals the handler's run time, the GIL is held throughout. The work is one C-level `re` call, and nothing else runs meanwhile: not the deadline's `Future.result(timeout=…)`, not the asyncio loop, not `_monitor_straggler_health`.
- **Real socket, shipped defaults** (`probe_n24r2_d_realslow.out`):
  - The 99 KB-newlines command ends in a **30.01 s client timeout**, not in the 20 s deadline deny.
  - A second client sending `echo benign` every 0.5 s also stalls, up to 30.03 s.
- **What each client finally emits** (`probe_n24r2_c_gil*.out`, using the probe handler's GIL-holding verb):
  - **Python rung**: DENY (`socket_timeout`) for the call and for every call that follows it. That fails closed, but it is a denial of service for every session.
  - **Relay rung**: **ALLOW** `{}` for the call and for every call that follows it.
- **Recovery does not work**:
  - `hooks-daemon stop` returns rc 1, and the process stays alive at 50–75 % CPU.
  - `cmd_stop` sends SIGTERM, waits 5 s, then gives up (`daemon/cli.py:760-806`). `cmd_restart` then aborts (`cli.py:1751-1780`).
  - Yet `init.sh:1664` tells the agent that a wedged daemon "is fixed by restarting it -- run exactly bin/hooks-daemon restart". Restart fails in exactly that state.
  - A `kill -9` sent by the agent is itself a PreToolUse call, so the same timeout denies it.
- **Why this is a major**:
  - NIGGLES marks B2 "✅ Remedied".
  - Review 1 had already named both handlers (M2: 48.6 s and 21.7 s).
  - The new hostile harness only sweeps SAFETY handlers.
  - The B2 sweep explicitly left hand-written-regex ReDoS out of scope.
- **Fix**:
  - Make that regex linear, for example `(?:^|[\s;&|])(?:grep|rg)\s+`, or tokenise instead of using a regex.
  - Isolate and fix the `plan_number_helper` pattern.
  - Extend the hostile harness to every PreToolUse handler, add whitespace-run and quote-run shapes, and assert on GIL starvation rather than on wall clock.
  - Have `stop` escalate to SIGKILL after the grace period, so the exempted recovery command actually recovers.
  - Process isolation (review-1 B2, direction 1) remains the structural fix.

### MA3: every fail-closed guarantee holds only on the python rung; the relay rung, which this repository enables, still ALLOWs on a timeout, a daemon crash or an oversized payload

## Minors

### mA1: a legacy-socket request over about 50 MiB still fails open on the python rung

- **Cause**: `_drain_oversized_request` (`server.py:1070`) gives up after `_OVERSIZED_REQUEST_DRAIN_CAP_BYTES` (`server.py:81`, 16 MiB).
- **Result**: at 64 MiB and 100 MiB, `sendall` raises `BrokenPipeError`. That reaches `init.sh:1927` as `fail('BrokenPipeError')`, which ALLOWs (`probe_n24r2_c_oversize_big.out`).
- **Impact**: no realistic model output is that large, but it disproves m5's "always".
- **Fix**: treat a broken pipe or connection reset after a successful `connect()` as "reached", and deny.

### mA2: a `SystemExit` or `KeyboardInterrupt` raised in a handler kills the daemon

- **Status**: pre-existing against main, but a regression against review 1's HEAD.
- **Cause**: m3 made the worker capture `BaseException` onto the future (`bounded_dispatch.py:264`). `future.result()` (`:294`) then re-raises it on the executor thread. Neither the chain nor the controller catch-alls (`controller.py:1043`, `:1129`) catch it, so asyncio lets it escape the event loop.
- **Evidence** (`probe_n24r2_b2_diag.out`): the process exits and the next connect is refused. Base `3104434b` behaves the same.
- **Behaviour at `d7f2c875`**: the waiter timed out and denied, and the daemon survived.
- **Effect**:
  - Python rung: this call and every in-flight call are denied.
  - Relay rung: ALLOW.
- **Fix**: convert a `BaseException` from `matches()` or `handle()` into the SAFETY+BLOCKING deny path inside `_execute_handlers_body`.

### mA3: while the dispatcher is saturated, the Stop chain blocks

`probe_n24r2_p2rerun.out`: `Stop event → block :: chain: not judged in time (dispatch pool saturated)`. This lasts until the self-restart, which by default can be up to `straggler_restart_after_seconds` plus one 10 s check interval. The agent sees an auto-continue loop. Fix: document this, or restart sooner when a Stop is refused.

### mA4: the m6 validator checks a constant, and a rejected value silently turns guards off

- **Constant comparison**: `validate_deadline_below_client_socket_timeout` (`config/models.py:1711`) compares against `Timeout.SOCKET_DISPATCH_ROUNDTRIP` (`:1726`). It ignores the client timeout actually configured (`transport.timeout_seconds`, the relay's `--timeout-ms`, `CLAUDE_HOOKS_SOCKET_TIMEOUT`). A deadline of 20 with `transport.timeout_seconds: 10` is accepted and reports healthy (`probe_n24r2_i_config.out`).
- **Degraded mode**: a rejected value (26, or 0 under N25's own `gt=0`) puts the daemon in the pre-existing DEGRADED mode (`probe_n24r2_i5_degraded.out`).
  - In that mode, `curl … | bash` and the project SAFETY handler are **ALLOWED**.
  - `config_errors` never mentions the deadline (P2).
- **Fix**: validate against the timeout actually configured, and make degraded mode deny PreToolUse, or fall back to the shipped defaults and report the real error.

### mA5: a straggler runs `commit_side_effects` with its own decision and ignores the cancellation token

- **Where**: `chain.py:1035-1043`.
- **Effect today**: harmless, because only `sensitive_content` implements this hook for PreToolUse, and all it does is clear a cache.
- **Why fix it**: the next rate-limiter-style handler would record side effects for a decision the caller never received.
- **Fix**: skip the commit when the token is cancelled.

## Nits

1. **The drain has no overall time limit.**
   - Each read is bounded at 0.5 s and the total at 16 MiB, but nothing caps elapsed time. A sender trickling 1 KiB every 0.4 s holds the coroutine far longer than any client waits.
   - It holds one fd and one coroutine. During the trickle, other clients were served in 0.13 s (`probe_n24r2_g_drain_1.out`). `readline()` has never had a timeout either, so this adds no new exposure.
   - 24 parallel 17 MiB sends all got the JSON error within 0.8 s. RSS peaked at 383 MiB and settled back to 65 MiB (`probe_n24r2_g_drain_2.out`).
   - Suggest a total drain deadline of a few seconds.
2. **Assertions loosened since review 1** (`git diff d7f2c875..HEAD -- tests`):
   - `"safety-guard" in reason` became `"chain" in reason`, in `test_chain.py` and in `test_n34_deadline_probe_isolated_daemon.py`. Prefer `startswith("chain: not judged in time")`.
   - The oversize test dropped `"100" in reason` and does not assert the new measured size.
3. **A project handler that raises at import vanishes silently** (pre-existing). The handler is simply absent while the daemon reports `status: healthy` (`probe_n24r2_j_import.out`).
4. **The 90 KB-path Write is still slow**: it now answers in 9.4 s under gate load (`probe_n24r2_p11rerun.out`). It no longer blocks other clients.
