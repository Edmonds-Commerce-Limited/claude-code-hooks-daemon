## F1: MAJOR. Interpreter code whose own file APIs expand braces now reads a brace-spelled protected path directly, with no shell involved

**Citation:** `src/claude_code_hooks_daemon/utils/shell_expansion.py:183-189` together with `:365-371` (single-quoted argument) and `:620-621` (heredoc body).

```python
#: Interpreters whose program text is not shell ... None of them brace-expands its source
NON_SHELL_INTERPRETERS = { ".py": ..., ".rb": ..., ".pl": ..., ".js": ..., ".php": ... }
```

**What it allows.** Braces are now neutralised in `ruby -e '…'`, `perl -e '…'`, `node -e '…'` and `php -r '…'` code, and in quoted heredocs fed to those interpreters. The premise is that "no shell expands this". Several of these languages expand braces themselves in their file-matching APIs:

- Ruby: `Dir.glob` and `Dir[]` always expand braces.
- Perl: core `glob` and `<…>` use File::Glob, and its default flags include `GLOB_BRACE`.
- PHP: `glob(…, GLOB_BRACE)`.
- Node: `fs.globSync` / `fs.glob` (22+) expand braces. Of the four, this is the one I am least sure of.

A brace-spelled protected name passed to one of these APIs as a string literal now reads the file inside the interpreter process. There is no variable, no subprocess and no shell-exec call. Before N101 the whole-command brace stream enumerated that literal. Now `{`/`}` become `(`/`)`, which neither the brace-group regex nor `fnmatch` treats as special. `_shell_exec_literal_mention` (`secret_file_guard.py:1078`) looks only at shell-exec calls, so it does not see a glob API.

This is not the case the fixer's self-review names ("reaches a shell only through a variable"). It is a direct literal read. The asymmetry is sharp: the same literal spelled with `*`, `?` or `[..]` still denies, because `_tokenise` reads the raw command and `_is_glob_shaped` / `_glob_intersection_mention` judge it (`secret_file_matching.py:560`, `:945`). Only the brace spelling of an interpreter-side glob lost coverage. The fixer's sweep did note that "Python's `glob` expand[s its] own quoted arguments", but applied it only to `*` globs, not to braces. Python itself is fine: its `glob` and `pathlib` do not expand braces.

**The class.** An exemption is justified by "no *shell* expands this text", but the program receiving the text has its own expander for the same syntax. To judge a new case, ask: does the receiving program itself give `{a,b}` (or `*`, `?`, `[..]`) filesystem meaning in any API reachable from a string literal? If yes, "no shell reads it" does not make the text inert.

**Why the tests miss it.** `test_shell_expansion_brace_view.py` lists ruby, perl, node and php as names to neutralise (diff line ~222). It asserts that `{` disappears, which is the behaviour this finding objects to. The deny pins in `TestTextTheShellNeverExpandsIsNotEnumerated` are Python-only and shell-exec-only. No test pairs an interpreter with a brace-expanding API of its own. The suite was written from the same model as the fix ("interpreter = not shell"), so it has the same blind spot.

**Detector hypothesis.** Any exemption keyed on `NON_SHELL_INTERPRETERS` (or any "text no shell expands" rule) should carry, per language, a declared list of that language's in-process glob/brace expanders. A parametrised test over (interpreter, expander API, brace-spelled stand-in protected name) must then deny.

- Reading-code rule: flag any docstring or comment that justifies an allow with "no shell expands" when the receiver is a program with a glob API.
- Likely false positives: Python rows would be flagged even though Python has no brace glob. The table must be allowed to say "none", or the rule will be suppressed.

**Rank and fix direction.** MAJOR: it is a direct read in 4 of the 5 trusted interpreter families, and the self-review misses it. The smallest fix within N101's intent is to neutralise only for Python, which is the interpreter N101's false-positive reproduction actually hit. Leave `.rb`, `.pl`, `.js` and `.php` enumerated as before.

**What would settle it.** Build the chain in-process on main and on this branch, with a benign stand-in protected glob such as `stand-in-secret.txt`. Run `ruby -e 'Dir.glob("stand-in-{secret,x}.txt")'` through both. I expect main to deny and the branch to allow.

## F2: MAJOR. Under `sudo`, a flag's value is read as the command, so braces in a real `bash -c` script are neutralised

**Citation:** `src/claude_code_hooks_daemon/utils/shell_expansion.py:331-342` (`owner_is_interpreter`). It relies on `shell_segmentation.py:779-786`:

```python
for word in strip_reserved_word_prefix(segment).split():
    if not word or word.startswith("-"):
        continue
    resolved = command_word(word)
    if not resolved or resolved in _COMMAND_WORD_PREFIXES:   # {"sudo"}
        continue
    return resolved
```

**What it allows.** `_segment_command_word` skips `sudo` and any word starting with `-`, but not the *value* of a flag that takes one. Take `sudo -p python3 bash -c '<script>'`. `-p` sets the prompt, accepts any string, and is never checked against users, groups or directories. The segment resolves to `python3`. `owner_is_interpreter` then looks for a raw word equal to `python3`, finds the flag value, and returns True. Line 370 neutralises the braces in the single-quoted script, and bash then brace-expands that script.

The heredoc form behaves the same way: `sudo -p python3 bash <<'EOF'` gets `receiver_is_interpreter=True`, so the body is neutralised. `_shell_exec_literal_mention` then scans that bash body as Python, finds no Python shell-exec call, and passes it. Other sudo flags that take values (`-u`, `-g`, `-D`, `-h`, `-C`, `-r`, `-t`, `-U`, `-T`) resolve the same way, but only `-p` works whatever the host's configuration.

This defeats the design's stated guarantee (`brace_expansion_view` docstring: "anything owned by a shell … kept"). The route needs `sudo` to be present and usable, which is common in dev containers running as root or with NOPASSWD.

**The class.** A command-word resolver that grants trust must know which options consume the next word. Skipping only `-*` tokens lets an option's *argument* stand in for the command. The resolver was written for a deny-direction question ("is this a data sink?"). N101 reuses it for an allow decision in `secret_file_guard`, which carries higher stakes.

**Why the tests miss it.** `test_sudo_prefixed_interpreter_is_neutralised` (diff line ~306) pins only bare `sudo python3 -c`. The shell-owner tests (`"sudo bash"`, line ~239) use no flags. Nothing puts a value-taking flag between `sudo` and the command.

**Detector hypothesis.** For every caller of `segment_command_word` / `_segment_command_word` that grants an exemption, run a test over each prefix in `_COMMAND_WORD_PREFIXES`: `<prefix> -<value-flag> <trusted-name> <shell> …` must resolve to `<shell>`.

- Reading-code rule: a resolver that skips `-*` without a per-prefix table of value-taking options is a finding.
- Likely false positives: low, since there are only a few callers.
- Note: the pre-existing DATA_SINKS heredoc exemption shares this resolver, so the same defect probably lets `sudo -p cat bash <<'EOF'` through other guards. That is outside this diff; I suggest routing it to F-BYPS.

**Fix direction.** When a prefix is present, withhold neutralisation unless the prefix's option syntax is parsed (sudo value-flag table, `--` handling). The simplest version: neutralise only when `sudo` is followed directly by the interpreter.

**What would settle it.** Call `brace_expansion_view("sudo -p python3 bash -c 'x{a,b}'")`. I expect `.text` to contain `(a,b)`. This uses no protected name.

## F3: minor. The named case (indirection through a variable), plus an argv variant the report does not name

**Citation:** `shell_expansion.py:365-371`, which neutralises *every* single-quoted argument of an interpreter command, not only the program argument. The shell-exec scan is at `secret_file_guard.py:1078-1094`.

**What it allows.**

1. **The fixer's named case.** Interpreter code builds a brace-spelled path in a variable and passes the variable to a shell-exec call. This is now allowed. Note that it needs a shell that brace-expands: Python's `os.system` uses `/bin/sh`, which is dash on Debian (no brace expansion) and bash on Fedora.
2. **Not named: argv.** `python3 script.py '<brace text>'` and `python3 -c '<code using sys.argv>' '<brace text>'` also neutralise the *data* argument. The receiving program may pass that argument to a shell or to a brace-expanding glob (combine with F1). The rationale "program text no shell expands" does not cover argv, which is data an arbitrary program consumes. The docstring does describe the behaviour, so this is a scope observation rather than a hidden change.

**The class.** Protected-name spellings that reach an expander through interpreter data flow (a variable or argv) rather than through a literal at the call site.

**Why the tests miss it.** No test covers indirection or argv. The fixer relies on precedent: `"id_" + "rsa"` concatenation was never denied, so interpreter data flow was never a guarded class. I agree the precedent holds. But this is still a deny-to-allow change that needs an owner decision, not just a self-review line, and argv is wider than the case that decision would cover.

**Detector hypothesis.** A differential corpus: run the same set of brace-spelled stand-in names, embedded in interpreter code/argv shapes, through main and the branch, and report only verdict *changes*. Checking absolute verdicts would be noisy, because every concatenation case is already allowed. The rows belong in the D-RULE record for N101.

**Rank.** Minor for D-SEC: it is consistent with an existing, accepted gap. It should be recorded as an owner-accepted allow (D-RULE), not left only in the fixer's report. If F1's fix restricts neutralisation to Python, the argv variant also stops combining with a brace-expanding glob.
