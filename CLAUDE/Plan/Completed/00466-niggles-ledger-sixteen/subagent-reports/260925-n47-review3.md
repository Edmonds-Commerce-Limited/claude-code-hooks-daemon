## Item 2: does Claude Code apply modelSettings effort on every model change?

**What the vendored docs say:**

- `model-config.md:544-548`: the resolution order is (1) an **explicit choice**, meaning `CLAUDE_CODE_EFFORT_LEVEL`, `--effort`, "or `/effort` in the session"; (2) settings, meaning "the level you saved for the model"; (3) the model default.
- `model-config.md:557`: "each model keeps its own saved level". `settings-reference.md:1189`: "Claude Code resolves each model separately".
- `model-config.md:484-491`: an automatic fallback "re-runs the request on that model", and "the session continues on the fallback model".
- The docs never say what happens to an explicit step-1 choice when the model changes. They do rank it above the per-model saved level, with no per-model qualifier.

**What the installed binary does** (Claude Code 2.1.282; `probe_n47r3_ccbin*.out`):

- The session effort is a tagged value: `{kind:"inherit"}` (the start state `W`), `{kind:"default"}` or `{kind:"level", value}`. The resolver `Ml(state, model)` returns `value` for `level` regardless of model. It returns `undefined` for `default`, which means the model's built-in default. Only for `inherit` does it look up the settings table for the model passed in. The fragment: `case"level":return r.value;case"default":return;case"inherit":…return K(e.settingsEffortTable,n??e.mainLoopModelForSession??e.mainLoopModel…)`.
- `/effort <level>` sets `sessionEffort = ZKe(level)`, which is `{kind:"level"}` (the `h1e`/`F`/`w` path). `/effort auto` sets `{kind:"default"}`.
- A `/model` picker pick with an effort level sets `sessionEffort: xN(M.level)`, also `level`. A pick with no effort level leaves `sessionEffort` untouched.
- An automatic refusal fallback sets only `mainLoopModel` and `mainLoopModelForSession:null` (the `refusal_fallback` and `swapSession` branches). It never touches `sessionEffort`.
- `--effort` initialises `sessionEffort` to `level` (`Hit`: `ne(SBn(e))`). `CLAUDE_CODE_EFFORT_LEVEL` outranks everything (`RN()` in `JS`).

**Coverage per case:**

| Case                                                                                               | Is the fallback or target model's `modelSettings` level applied?                                                                                       |
| -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Session never used `/effort`, no `--effort`, no env var; automatic fallback to Opus 5 or 4.8       | Yes. It is looked up per model (`inherit`). The docs imply this (`:557`, `settings-reference.md:1189`), but they never state it for fallback           |
| Same session; the supervisor types `/model fable`                                                  | Yes (`inherit`). The docs cover this by `:557`                                                                                                         |
| The owner typed `/effort medium` at any point this session, then an automatic fallback to Opus 4.8 | **No.** The session stays at medium on Opus 4.8. The xhigh entry is not applied. Covered by `:546` (explicit choice first), and the binary confirms it |
| The owner typed `/effort auto` this session                                                        | **No.** The session gets each model's built-in default (Opus 5 and 4.8: high). Saved levels are not consulted. Not documented                          |
| A `/model` picker pick made with the effort slider, then a fallback                                | **No** (`level`)                                                                                                                                       |
| Launched with `--effort X` or `CLAUDE_CODE_EFFORT_LEVEL=X`                                         | **No** for the whole session. Documented (`:546`, `settings-reference.md:913`)                                                                         |

This matters in practice. N47 began with the owner choosing medium, and typing `/effort medium` once pins every later fallback to medium. It also re-saves the level for the active model. The effect is the owner's own explicit choice winning, which is consistent with the SSoT requirement. What is false is the documentation:

- `CLAUDE/development/CcySupervisor.md:131-142`. It even cites the step-1 override (`:133`), then says "there is no documented case where a model change … leaves the OLD model's level attached to the new one". Step 1 is exactly that case.
- `.claude/ccy/claude-supervise.py:36-41`: "applies it itself on every `/model` switch -- automatic or manual". Also `:1325-1328`.
- `NIGGLES.md:52-55`.
- Post-upgrade task 02 `:16-17` ("applies automatically whenever that model serves a request") and `:49-52` ("whichever one an episode falls back to keeps the old compensation").

**Direction:** state the condition in all four places. The entries apply only while the session has no explicit effort (no `/effort <level>` or `/effort auto`, no slider pick, no `--effort`, no env var). An explicit choice holds across every model change, fallback included. Cite `model-config.md:546` and drop the "no documented case" sentence.

## Item 3: the recommended entries

- **Fallback ids.** `model-config.md:486`: from Fable 5.1, Fable 5 or Opus 5.5, a biology flag goes to **Opus 5** and a cyber flag to **Opus 4.8**. `claude-opus-5` and `claude-opus-4-8` are correct canonical ids. The binary's known-model set `oe` lists both, plus `claude-fable-5-1`. The supervisor's own "table" works by family (`_MODEL_FAMILY_RANKS`, `:1333`), and both targets are family `opus`, so the two agree.
- **Opus 5.5 at medium.** The entries do not touch `claude-opus-5-5`. In the binary (`pat`), a lookup skips any entry whose canonicalised key (`yme(key)`) differs from the model's, and it prefers the exact key. `claude-opus-5` does not collide with `claude-opus-5-5`. The owner's `claude-opus-5-5: medium` is left alone. (The owner's settings file was not read. Review 2 reported its content.)
- **Exact ids or aliases.** They are exact canonical ids, which is right. `settings-reference.md:1197` says entries are written under the canonical name, and alias, dated, `[1m]` and provider ids are matched to that entry. The binary canonicalises keys too (`yme(Pe)`). So a hand-written alias key such as `opus` would resolve to whatever `opus` currently points at, which is Opus 5.5 here. The docs and task 02 correctly avoid aliases.
- **Gaps (finding 8):**
  - `claude-fable-5-1` does not cover Fable 5 (`claude-fable-5`). A gateway resolves `fable` to Fable 5 (`model-config.md:83`). It also does not cover `claude-mythos-5`/`-5-1`, which the supervisor treats as fable (`:1333-1341`).
  - The xhigh entries apply wherever Opus 5 or 4.8 serve. That includes an Opus 5.5 → Opus 4.8 cyber fallback (`:486`) and a manual pick. The old compensation fired only for fable-origin drops (`_TOP_FAMILY_RANK`). State that it is now broader.

So the fix does what it claims (A, B, D). Edges:

- **C.** A downgrade whose reading renders before `model_downgrade_recorder` publishes (PostToolUse) is never attributed. The drop is judged once, on the tick `family_changed` is true (`:3545-3589`), and never looked at again. This is pre-existing for a first downgrade (C0, the same on main). On main, a LATER downgrade was rescued by the stale record, and the branch removes that accidental rescue. A robust fix: latch the unattributed drop, and attribute it if a NEW `record_ts` for the same session/from/to arrives while the family is still the fallback.
- **E.** `record_ts` falls back to `""` when the transcript record has no `timestamp` (`model_fallback_records.py:134,147`; the loader at `claude-supervise.py:2899-2901`). Once `""` is spent, every later untimestamped downgrade in the session is refused. Treat an empty `record_ts` as "cannot tell", and never spend it.
- **Hot reload.** An episode open at upgrade time has no `downgrade_episode_record_ts`, so closing it spends nothing, and the MAJOR 4 bug recurs once (`probe_n47r3_scenarios.out` S10b: a manual switch types `/model fable`). A relaunch avoids this (see finding 6).
- **Test gap.** Removing `"spent_downgrade_record_ts"` from `export_state` survives the whole branch suite (`probe_n47r3_mutate_branch.out`). In production that key must survive the host↔worker hop every tick, or MAJOR 4 comes back. Add an export/import round-trip test for both new keys.

The new tests (`test_attributed_downgrade.py:259-315`) assert only on `downgrade_episode`, never on the `/model` payload. They pass here because the restore is gated on the episode.
