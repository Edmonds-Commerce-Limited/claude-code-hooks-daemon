## Class and fix

Bash brace-expands only unquoted shell words. The new
`shell_expansion.brace_expansion_view(command)` returns a same-length copy
with `{`/`}` neutralised only in two places:

- a quoted-delimiter heredoc body whose receiver is a non-shell interpreter
  (`NON_SHELL_INTERPRETERS`: python/pypy, ruby, perl, node, php), where every
  later pipe stage is a `DATA_SINKS` command or another such interpreter;
- a single-quoted (`'…'` or `$'…'`) argument whose command is such an
  interpreter.

The interpreter must be named by a bare name or from `/usr/bin/`, `/bin/`
or `/usr/local/bin/`. Nothing is neutralised if the command's shell-level
text defines a function, or uses `alias`, `hash`, `enable`, `function` or a
`PATH=` assignment. Text inside a command or process substitution is kept.
So is a body fed to a data sink: `cat > run.sh <<'EOF'` authors a runnable
file, which is the same reason `Write` content is judged whole. The scanner
tracks comments, backslash escapes, `$'…'` escapes, double quotes with
nested substitutions, and both quoted and unquoted heredoc bodies. Any
construct outside that model returns the command unchanged: a `case`
pattern's `)`, an unterminated quote or heredoc, a quoted `${…}`, or
`$((…))` with quotes in it.

`_brace_expansion_tokens` reads the view on the `"bash"` route. The
`"content"` route (a file being authored) is unchanged. Its brace
enumeration is pinned by the existing
`test_a_script_brace_sequence_mention_still_denies_as_content`.

A heredoc fed to an interpreter now also gets the one-liner families'
shell-exec literal scan (`_shell_exec_literal_mention`). A brace-spelled
path inside a direct call such as Python's os-dot-system therefore still
denies. The families' basename regexes now come from
`shell_expansion.NON_SHELL_INTERPRETERS`, so there is one table.

## Self-review: is anything now allowed that could read a protected file?

Yes, one narrow class, and it is deliberate:

- **A brace-spelled path in interpreter code that reaches a shell only
  indirectly.** Example: a python heredoc or `-c` program doing
  `cmd = "cat …/id_rs{a..a}"` and then running `cmd` through a shell-exec
  call, or writing it into a script that it runs later. Before this change
  the raw brace stream caught it by accident. Now interpreter code is judged
  only through its DIRECT shell-exec call literals, which is what the brief
  specifies ("the guard's one-liner families cover interpreter reads"). The
  same programs spelled `"id_" + "rsa"` were never denied, so this was never
  a guarded class for interpreter code. A literal name anywhere still
  denies. N104 asks the coordinator to settle one rule for both surfaces.
- **The interpreter name as identity.** Neutralising assumes `python3` is
  Python. The hardening commit refuses relative or untrusted paths and
  same-command redefinitions. Two things remain that no per-command guard
  can see. One is a shim installed by an EARLIER tool call. The other is a
  trusted-path binary overwritten earlier in the same command
  (`cp /bin/bash /usr/bin/python3; python3 -c '…'`). The one-liner families
  already trusted interpreter names in the same way.
- Everything else is unchanged or stricter. Shell text, double-quoted text,
  unquoted heredocs, shell-fed and sink-fed bodies, substitutions and
  unparseable commands are enumerated exactly as before and still fail
  closed past the caps. Interpreter heredoc bodies gained a shell-exec
  literal scan they did not have.
