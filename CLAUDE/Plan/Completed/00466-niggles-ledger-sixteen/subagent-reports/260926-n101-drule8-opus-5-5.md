### BLOCKER 1: N117 treats a path-length ENAMETOOLONG as proof of absence, and the shell can still read the file

- **Where:** `src/claude_code_hooks_daemon/utils/secret_file_matching.py:1884` and `:2009`, `_PROOF_OF_ABSENCE_ERRNOS = frozenset({errno.ENOENT, errno.ENAMETOOLONG})`.
- **The premise is false for one of the two causes.** The fix assumes "no entry can carry that name, and a shell naming that path fails the same way". The kernel raises ENAMETOOLONG for two reasons:
  - One path component is longer than NAME_MAX. Here the premise holds.
  - The whole path is longer than PATH_MAX. Here it does not.
- **Why the second case breaks it:** `_expand_glob_token` joins a relative token onto absolute bases (project root, hook cwd, daemon cwd). Bash globs and opens the relative path, which can stay under 4,096 bytes while `base + "/" + token` goes over.
- **What it allows (demonstrated):** from `/workspace`, `cat CLAUDE/Plan/Completed/<57-char dir>/../ ×62 … untracked/*ecre*` resolves to a real on-disk file matching `*.secret*`.
  - Relative directory part: 4,081 bytes. Joined absolute path: 4,092 bytes. The expanded match is 4,069 bytes relative and `os.stat` succeeds, so `cat` would read it.
  - pathlib's `glob` raised errno 36 (`File name too long`) on the joined path.
  - Main: DENY, `R-SECRET-EVALUATION-ERROR`. Branch: ALLOW.
  - From the worktree cwd (root is 49 characters) the same shape also flips, with a 4,046-byte relative directory and a 4,069-byte expanded path.
- **Who can reach it:** the command author controls this completely. The `..` repeats only need one real directory with a long name.
- **Second failure in the same code:** one ENAMETOOLONG ends the whole `for match in matches_iter` loop. That covers pathlib's `glob` and `bounded_recursive_glob` (`shell_expansion.py:4091-4093`, which re-raises anything but ENOENT). So one over-long sibling path hides every sibling not yet visited, even ones whose paths are short enough to open.
- **Which routes are exposed:**
  - The both-edges route (`_both_edges_glob_mention`, the `*.secret*` family), where the filesystem is the only oracle.
  - `find_protected_mention_strict` (`:1871`), used by quarantine_artefact_read_guard. I checked this one by reading the code only; there was no DETAIL artefact on disk to demonstrate with.
- **Class:** a guard's filesystem oracle queries a path that is not the one the shell will query (base-joined rather than cwd-relative). It then reads a failure caused by that difference as a fact about the target. This sits next to `CLAUDE/Security/AuthoredPathResolution.md`.
- **Why the tests pass:** both N117 tests use a single 300-character component, the NAME_MAX case, so neither covers PATH_MAX. The fail-open inventory's surfaces (`check_fail_open_inventory.py:66-89`) do not include `secret_file_matching.py`.
- **Detector hypothesis:** flag any `except OSError` whose errno allowlist grows beyond ENOENT, in a function that joins a caller token onto a base path. Also run a corpus row with a relative path whose joined length is over PATH_MAX while its own length is under it. This is low noise: two sites today.
- **Fix direction:** count ENAMETOOLONG as absence only when a literal component of the pattern is longer than `os.pathconf(base, "PC_NAME_MAX")`. Otherwise propagate it. Alternatively, walk relative to a directory fd.
- **Confidence:** high for secret_file_guard (demonstrated end to end). Medium for the quarantine route (code-read only).

### MAJOR 2 (delta): project_containment flips from deny to allow when a here-string write is followed by an unbalanced quote

- **Commands:**

- **Status:** this is the only deny-to-allow flip in the 66-handler differential. Fixing Finding 3 closes it. It is MAJOR rather than BLOCKER because main is already open to the same outcome through Finding 3.
- **Confidence:** high.

### MAJOR 3 (shared, on main and branch): an unbalanced quote on any later line hides every write target

- **Where:** `core/utils.py:429` `_tokenise` catches `ValueError` and returns `[]` (around line 467).
- **The docstring's claim is false:** lines 461-462 say this "is the fail-safe direction … and such a command is unterminated to bash as well". Bash runs every complete earlier line before it fails.
- **Demonstrated, ALLOW on both trees:**
  - `echo x > /opt/o.md\nx="u`
  - `cat > /opt/o.md <<'my-notes'\nit's done\nmy-notes`
  - `cat > /opt/o.md <<'END.MD'\n…` and `<<'EOF-1'`
  - `cat > /opt/o.md <<\EOF\nit's done\nEOF`
- **Why these ordinary commands get through:** `_HEREDOC_RE` only accepts `\w+` delimiters. A `-`, `.` or `\` delimiter is not recognised as a heredoc, so a prose apostrophe in the body reaches shlex.
- **What it allows:** a write outside the project root that project_containment misses, from a heredoc with a hyphenated delimiter and prose.
- **Class:** a parse failure that returns an empty list, where the empty list means "writes nothing" to a guard that denies.
- **Why the tests pass:** the fail-open inventory does not cover handler parsers (`FailOpenBoundaries.md` §"does not catch", "outside the five surfaces").
- **Detector hypothesis:** in any function whose result feeds a deny handler, flag `except ValueError: return []` or `return None`. Expect some false positives from content-only consumers such as lint_on_edit, where empty is the safe direction; that distinction needs a consumer-aware row.
- **Fix direction:** split on unquoted newlines first and tokenise each line on its own, or fail closed for location guards.
- **Confidence:** high.
