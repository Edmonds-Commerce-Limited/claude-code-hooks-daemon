## MAJOR 1: a brace word wholly inside a Python literal is dropped even when the literal's escapes change its brace structure

**Where:** `src/claude_code_hooks_daemon/utils/shell_expansion.py:1476-1495`, which is `_code_brace_words`, the round-6 `_code_shell_words`, and `_outside_every_span`:

```python
    for word, start, end in _shell_brace_words(source, depth=0, anchor=None):
        if _outside_every_span(spans, start, end):
            yield word
```

The literal itself reaches the guard only as its escape-decoded value (`:1269`, `_constant_strings(ast.parse(token.string, …))`).

**What it allows:** this Python program in a `python3 - <<'EOF'` heredoc:

```
s = '''a' /proj/.vault-{\x7b,pass} 'b'''
```

- Python reads it as the value `a' /proj/.vault-{{,pass} 'b`, which does not spell the path.
- Bash reads the same raw text as `''` `'a'` followed by an **unquoted** word `/proj/.vault-{\x7b,pass}`. I confirmed with `bash -c "printf '%s\n' …"` (it prints and runs nothing) that this expands to `/proj/.vault-x7b` and `/proj/.vault-pass`.

| Escape used        | main (`fc2a42b25`) | branch (`0779559fa`) |
| ------------------ | ------------------ | -------------------- |
| `\x7b`             | deny, BASH-MENTION | **allow**            |
| `\x7d`             | deny               | **allow**            |
| `\173`             | deny               | **allow**            |
| `\N{LEFT CURLY …}` | deny               | **allow**            |

- The `-c "…"` form still denies. A double-quoted `-c` is not exempted.
- Impact: this is the same read-back premise the coordinator graded MAJOR in round 4 (MAJOR 1). A program reads the command text back, for example from `/proc/$PPID/cmdline`, and hands it to a shell.
- Round 6 did not introduce this. Literal decoding (round 3) and the containment rule (round 5) did. But round 6's new `_code_shell_words` splits the raw text exactly as bash does, and then applies the same containment filter. So the one stream that reads the text correctly throws this word away.

**The class:** a brace word that is wholly inside a Python literal is skipped, on the assumption that the literal's value covers it. That assumption fails when both of these hold:

1. **The literal contains an escape that adds or removes a brace or comma.** Examples are `\x7b`, `\x7d`, `\x2c`, octal, `\u`, `\N{…}`, and a line continuation.
2. **Python's quoting and bash's quoting disagree about where the literal starts and ends,** so bash sees the word unquoted. Triple quotes are one way; any embedded quote character is another.

Condition 1 alone is not a defect. `s = "/proj/.vault-{\x7b,pass}"` is main-deny/branch-allow, but no reading spells the path, because bash also treats the text as quoted. That is the exemption working as intended. I list it only because it matches the brief's literal rule.

**Why the tests miss it:**

- `test_a_shell_word_wholly_inside_a_literal_is_not_reported` asserts that the word is dropped.
- No test pairs an escape in a literal with a quote divergence between Python and bash.
- The 140-program corpus contains ordinary programs, and nothing compares the guard with bash's reading of the raw program text.

**Detector hypothesis:**

1. Drop a word under containment only when the raw text of the enclosing literal contains no backslash. Otherwise, also enumerate the raw word.
2. A stronger version: never filter `shell_words` by containment at all. The quote-aware reading already treats a brace inside a matched shell quote as text, so an ordinary literal expands nothing. Only words that bash genuinely sees unquoted would be enumerated.

Likely false positives are triple-quoted docstrings containing apostrophes near braces. Re-running the fixer's `probe_fp.py` corpus would measure it.

A differential test would catch the whole class: generate literals with escapes and quote divergence, and require that every word bash would expand (checked with `printf` only) is covered by the guard's tokens.

**Confidence:** high on the current behaviour. It was probed through the handler chain on both trees, and bash's reading was confirmed with `printf`. My claim that this is pre-existing since round 3 or 5 comes from reading the code; I did not run it against `1a11131b7`.
