## MAJOR (in branch code, but `main` allows it too): `bash <<< $'…'` is never read, because `<<<` is taken for a heredoc

- **Where:** `src/claude_code_hooks_daemon/utils/shell_expansion.py:731`
  ```python
  if text.startswith("<<", i) and not text.startswith("<<<", i):
  ```
  At the first `<` the test fails, and line 745 steps past it as a stop character. At the second `<` the text now reads `<< `, so the test passes. The here-string's word becomes a heredoc delimiter and is never read as a command.
- **What it allows:** `bash <<< $'cat /proj/.vault-\x7bpass,q\x7d'` is allowed on both trees, and `iter_shell_brace_words` returns `[]`. Bash runs the decoded script and brace-expands it: `bash <<< $'printf "%s\n" /proj/.qq-\x7bpass,q\x7d'` prints `/proj/.qq-pass`.
  - `bash -c` with the same `$'…'` word denies. So N112's "every `$'` word is read as a command" never sees this word.
  - With an N113 prefix it denies, but only as an evaluation error.
  - `bash <<<$'…'` (no spaces) splits the same way.
- **Not a regression:** the line predates round 7 (N107, round 6). `main` has no such scanner and also allows the command.
- **The class:** a multi-character operator scanned one character at a time, where a suffix of the operator matches a shorter operator. The word after it is then read with the wrong role.
- **Why the tests miss it:** N112's cases are `bash -c`, `eval`, `sh -c`, `su -c` and `ssh`, with no here-string. The differential test prints single words, so it never splits operators.
- **Detector hypothesis:** for each operator family (`<<<`/`<<-`/`<<`, `>>`/`>`, `&&`/`&`, `;;`/`;`), a test that puts a brace-carrying `$'…'` word after the operator, with `bash` as the receiver. The splitter must hand that word to `_nested_command_words`. False positives: none, since each case is a real bash reading.
- **Suggested fix:** consume the whole `<<<` before the stop-character branch, then read the word as usual.
- **Confidence:** high. Probed on both trees, bash output confirmed, and the splitter traced.
