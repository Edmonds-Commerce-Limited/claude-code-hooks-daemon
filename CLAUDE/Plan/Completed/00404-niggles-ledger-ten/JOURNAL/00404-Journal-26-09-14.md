## 16:22 · finding · N1 — `cancelled` and `failure` are not the same signal

N1 came from a CI check rather than from hitting a symptom, and the first
instinct was wrong in a way worth recording. CI runs on this repo are routinely
evicted by the next push (one pending slot), so a red run is easy to wave away.
But eviction reports `cancelled`; `acc3eb93` reported `failure`. Separating
those two before reaching for an explanation is what made the rest happen.

The second signal was the shape: 3.11 failed, 3.12 and 3.13 passed. A genuinely
version-specific defect is rare; a race that lands differently under different
interpreter timings is not. That pointed at timing rather than at a 3.11 API
difference, which is what it turned out to be.

## 16:31 · finding · N1 — the reproduction said more than the CI log did

It passed locally first time, so the reproduction had to attack the CAUSE
rather than try to lose the race on purpose: patch `Path.chmod` to fail once
for a socket under the events dir.

That immediately said something the CI log did not:

```text
E       assert 0 == (31 - 1)
```

Not "one socket lost" — all thirty-one. The per-socket `continue` sitting
immediately above the unguarded `chmod` made the blast radius LOOK like one
event, and reading the traceback alone would have left that impression.

## 16:44 · decision · N1 — skip rather than serve; unlink rather than close

Two calls worth keeping:

- **Skip, do not serve.** The tempting fix is to log the chmod failure and keep
  the socket anyway. That leaves it with umask-derived permissions instead of
  `0o660` — a security regression traded for an availability gain the legacy
  socket already provides for free.
- **Unlink, do not just close.** `asyncio` leaves the socket file on disk when
  its server closes, so closing alone would leave a path that looks like a
  working socket with nothing behind it. That is harder to diagnose than its
  absence.

The `log-and-continue` on the unlink is deliberate and recorded in
`error_hiding_exclusions.json`: it is cleanup for a socket already abandoned,
and raising there would restore the exact defect the function exists to
prevent. `wait_closed()` is deliberately NOT guarded — it has no documented
`OSError` contract, so a guard would be an unreachable branch dressed up as a
considered decision.
