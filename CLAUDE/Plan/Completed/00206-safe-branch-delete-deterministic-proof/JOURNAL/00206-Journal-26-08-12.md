## 07:52 · decision · T1.1 — dropped the path-level tier during RED

Writing the tests exposed a flaw before any implementation existed. The draft
had a `content-subsumed` tier that passed when every path on the branch also
appeared somewhere in main's history. A path existing says nothing about the
CONTENT at that path, so the branch could still hold the only copy of a file
version — the tier could approve a lossy deletion, which is not a proof.

Replaced with `content-preserved`, which compares **blob shas**. Blob sha *is*
content identity in git. `test_a_path_main_knows_but_whose_content_differs_
stays_unproven` pins the difference so the weaker form cannot creep back.

## 09:05 · finding · — — squash merges are handled without flags

Tested rather than assumed. After `git merge --squash`, the branch is NOT an
ancestor (so `git branch -d` refuses) and `git cherry` reports every commit as
unique, because squashing N commits into one changes every patch-id:

```
ancestor: NO  (so 'git branch -d' refuses)
cherry unique (+): 2
delete-branch tier: content-preserved   is_safe=True
```

`content-preserved` proves it: the squash put the branch's final tree into
main, so every blob is reachable. This is the case that tier exists for, and
another reason dropping the path-level draft tier mattered.

## 09:20 · decision · — — the MERGED tier now delegates to `git branch -d`

User's correction, and it was right: "plain -d is preferable to resorting to
this script. Your script is fallible and untested, -d is safe and clean."

Acting on it found a real defect. Deletion forced EVERY tier, including
`merged` — discarding a free second opinion, since plain `-d` does the same job
while making git re-verify our ancestry claim independently. On that tier a
classifier bug could therefore have caused a silent loss.

`delete_argv_for_tier()` now returns the safe delete for `merged` and the force
flag only for tiers where git would refuse regardless (rewrite, squash). Guidance
in `destructive_git`, `HANDLER_REFERENCE.md`, the changelog and the release notes
all reordered to put `git branch -d` first and frame this command as the
fallback for when `-d` has actually refused — not a replacement for it.

Correcting my own earlier claim to the user: I said the motivation for banning
squash merges was void because "-D is no longer needed". Half right. Squash does
not force `-D`, but it DOES force this script instead of `-d` — and preferring
`-d` is exactly the user's point. Their argument survives in that refined form,
so the squash blocker remains justified.

## 10:05 · decision · — — abandonment is now human-gated

User: "lets make true branch abandonment human gated." Implemented as a
`confirm` callback the ENGINE requires before deleting any `unproven` branch,
supplied by the CLI only when `sys.stdin.isatty()`.

The distinction the design turns on: `--allow-unproven --reason "..."` declares
**intent**, and intent is not **consent**. The party that wants a deletion
cannot grant its own permission for it, so the flags stayed necessary and
stopped being sufficient. Every provable tier is untouched — a proof can be
acted on unattended, which is what makes it a proof; `unproven` is by
definition the case where a judgement replaces evidence, and judgement is a
human's.

Deliberate detail: the CLI passes `confirm=None` rather than a
callback-that-always-declines when there is no TTY. Declining would have
reported "a human declined" when in truth none was ever asked. The engine
distinguishes the two and says which happened.

Two more choices worth recording:

- Consent requires typing `abandon`, not `y`. One keystroke is too easy to
  fat-finger for discarding the only copy of work.
- The confirmation prompt lists ONLY the `unproven` branches, never the safe
  ones in the same batch. Listing branches that are in no danger trains a human
  to skim the list, which would defeat the prompt.

Verified both directions against a throwaway repo through the real CLI, not
just unit tests: with every flag declared and no TTY, deletion is refused and
the branch survives; a `--no-ff` merged branch still deletes with no prompt and
no flags.

Guidance updated in the same pass, because a block that names a route the agent
cannot walk is a dead end. `destructive_git.get_claude_md()`,
`HANDLER_REFERENCE.md`, the changelog and the release notes now all state that
an agent cannot finish this and must hand the decision back.

## 10:40 · finding · P4 — the 4 failing tests were a release-time trap, not my changes

Tracked down the 4 failures I had been carrying as an unexplained blocker
rather than assuming they were unrelated to this work. They were unrelated —
but not benign, and NOT safe to wave through.

`tests/acceptance/` upgrade gates clone this repo at HEAD and upgrade to
`git describe --tags`, asserting idempotency in their own docstrings. That
premise holds only BETWEEN releases. Mid-release, HEAD carries 3.52.0 while the
newest tag is still v3.51.0, so "upgrade" silently becomes a DOWNGRADE, the
version-specific upgrader rebuilds the venv, and it dies inside uv:

```
→ Venv version mismatch: have v3.52.0, need v3.51.0
✗ Failed to create virtual environment at .../venv-...
error: No interpreter found at path `.claude/hooks-daemon/untracked/venv-.../bin/python`
```

Proved it rather than argued it: tagging the clone's HEAD v3.52.0 made all four
pass. So the gates were structurally unsatisfiable during EVERY version-bumping
release — red exactly when a release depends on them, which is the worst
possible moment to be reasoning about whether a red test "counts".

Fix is the premise, not the symptom: pin the clone to its tag BEFORE the
baseline install, so installed version == target version with no synthesised
state and no invented tag. `assert_clone_is_pinned` then re-checks it, so a
future drift fails by name at the fixture instead of three subprocesses deep.

Two things worth keeping:

- The clone helper was copy-pasted into all three files. That duplication is
  precisely what let one wrong assumption sit unexamined in three places; it
  now lives once in `tests/acceptance/conftest.py`.
- My own guard shipped broken for a moment: `describe --exact-match` exits
  NON-ZERO to say "HEAD is not at a tag" — the very condition it reports on —
  so under `check=True` the guard would have died with a subprocess traceback
  instead of printing its diagnosis. Caught by asking what the guard does when
  it fires, and verified against a deliberately-unpinned repo.

Durable lesson recorded in `CLAUDE/development/LESSONS.md` ("A fixture must
ESTABLISH the premise its test documents"). Release notes previously claimed
"0 failing" while 4 were failing; that number gets corrected from a measured
run, not carried forward.
