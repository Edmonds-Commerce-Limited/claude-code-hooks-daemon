# Plan 00176 Journal — 2026-09-08

## Task 2.0 shipped, and it was filed against the wrong site

The plan's backup table said the upgrade path took no backup — "**no** — bare
`cp`" — reasoning from the copy at `:865` alone. Two things turned out to be
wrong with that, and the second inverts the risk model.

**First: Step 9 is covered.** `upgrade_version.sh:544` creates a full state
snapshot at Step 3, `install/rollback.sh:162` captures `settings.json` in it,
and `cleanup_old_snapshots "$DAEMON_DIR" 3` at `:1192` keeps the last three. So
a recoverable copy survives a successful upgrade, and the "cheap mitigation" of
backing it up first would have added a second one.

**Second, and worse: the site that runs most often is the uncovered one.** The
idempotent fast path at `:307` copies `settings.json` and prints *nothing*, and
`exit 0`s at `:439` — before Step 3 at `:539` — so no snapshot stands behind it
either. The script's own comment about that branch:

> Layer 1 (upgrade.sh) ALWAYS checks out the target tag before invoking this
> script, so `ROLLBACK_REF` always equals `$TARGET_VERSION` here — this branch
> is the effective single deployment path for every client upgrade.

So the silent, unbacked, unannounced copy is the one on the effective single
deployment path, and the plan's table pointed at its safer sibling.

**The fix is one function, not two patches.** Two sites doing one job
differently is what produced the gap in the first place, so
`scripts/install/settings_deploy.sh` now serves both. Its three properties, each
chosen against a specific failure:

- Acts only when the file actually **differs**. Warning on every upgrade trains
  people to ignore the warning, and a `.bak-` per upgrade of an identical file
  is litter that makes the real one harder to find.
- Takes a backup only when nothing else holds a copy; points at the snapshot
  when one exists. One copy, never two.
- **Aborts** if the backup cannot be written, leaving the client file
  untouched. Losing it is the one outcome worth failing a deploy for.

Tested by sourcing the real library and calling it, plus assertions that both
sites go through it and that no raw `cp "$SETTINGS_JSON_SOURCE"` survives — a
helper only helps if the sites that had the bug actually call it.

I deleted `test_upgrade_sh_settings_replacement_warning.py`, written an hour
earlier against an inline version of this. It extracted the Step 9 block and
stubbed its callees; once the block called the helper, stubbing would have
tested the stub.

check is for, and it worked. Realigned rather than re-justified — same lines,
same reasons, five lines lower.

## 09:26 · implementation · Phase 2 complete

Tasks 2.1–2.4 shipped across four commits. The merge core, its file layer, the
`settings-merge` CLI, all three deploy routes, and the escalation path.

**The discriminator earned its cost immediately.** The audit's probe said a
`/.claude/hooks/` substring test was wrong in both directions; writing the tests
first turned each of its four rows into an assertion, including the false
NEGATIVE that mattered most — the relative legacy shape `.claude/hooks/<key>`,
which is precisely the stale entry the refresh exists to repair. Anchoring to
the whole command via `legacy_command_bash_key` plus membership of the wired set
handles all four.

**`install.py` could not use the merge, and saying so beat pretending.** It runs
before any venv exists, so it can neither import the daemon nor shell out to the
CLI. It gets the safety PROPERTY instead — read the client document first, then
edit the daemon-owned parts — which removes the deterministic discard of
`permissions`/`plansDirectory`/`enableArtifact` that Q6 identified as the only
genuine conflict of the four writers. The limit that buys is that a client hook
sharing an array with a daemon forwarder is not preserved there, because
separating them needs the discriminator and that file already hand-keeps a copy
of the wired set. Recorded in the code, the tests and PLAN.md rather than left
to be discovered by whoever hits it.

**One existing test asserted the defect.** `test_the_new_file_still_lands`
checked that a client's `statusLine` came out NOT equal to theirs — an accurate
description of a reinstall discarding their settings, pinned as if intended. It
now asserts the hooks block lands, with a sibling asserting the client's keys
come through.

**The plan document went over its size threshold**, so the ~100 lines of
pre-fix measurement moved verbatim into `EVIDENCE.md`. Worth keeping rather than
deleting: the corrected backup table — where the snapshot really was, and why
"back it up first" was the wrong mitigation — is the reasoning that shaped the
whole design.

## 09:26 · bug · docs QA duplicate-block reports a stale location

Found while linting the extracted `EVIDENCE.md`. `duplicate-block` reported its
Python code fence as "identical, after normalisation" to `PLAN.md:38-43`, which
by then held a prose bullet list — the two share nothing.

Not a false match: a STALE one. `untracked/docs-qa/index.json` caches each
document's `block_locations` alongside `mtime_ns` and `size`, and a single-file
`--lint` refreshes the entry for the file being linted but not for the files it
compares AGAINST. The cached PLAN.md entry read size 17360 against an actual
14841, so the checker matched against the code fence that used to live at 38-43
and cited a range whose content had changed.

Both directions are wrong, and the quiet one is worse: a finding can send you to
fix a duplication that no longer exists, and a genuinely NEW duplicate against a
stale-cached file can be missed. Filed for its own TDD reproduction rather than
folded in here.
