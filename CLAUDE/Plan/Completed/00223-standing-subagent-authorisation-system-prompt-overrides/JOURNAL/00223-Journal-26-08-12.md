## 23:34 · decision · D3 — the mechanism ships on, every authorisation ships off

Phase 2 surfaced a problem with the Goals' "default-on" wording that I had not
seen when opening the plan.

Every other default-on handler here ADDS a restriction
(`ancestry_preserving_merge`, `git_message_backtick`). This one RELAXES one,
which is different in kind. And it makes the handler's own text false: Decision
2 requires the injection to say the project owner recorded this request, and on
a fresh install nobody did. Shipping it active would have the daemon fabricate
the very consent the design rests on.

So: handler `enabled: true`, every built-in entry `enabled: false`. The default
set exists so the options are discoverable and adopting one is a single flag.
`config-changes` with `recommended: true` carries it to existing installs —
the same shape `comment_changelog` and `comment_size` used.

This converts the plan's "becomes a general ignore-your-instructions surface"
risk from a wording safeguard into a structural one, which is strictly better.
Enabled in THIS repo, where the authorisation is real and on the record.

## 23:44 · thought · T3.3 — rate limiting, and why a cooldown would be wrong

Task 3.3 needs care. The instinct is to copy `critical_thinking_advisory`'s
gates, but those exist to make an advisory OCCASIONAL, and occasional is the
one thing this must not be: Phase 1's whole finding is that a per-request
instruction is answered only by a per-prompt channel.

Cost is real though — ~640 chars ≈ 160 tokens every prompt.

So the shape is a DECAY, not a cooldown: full text for the first few
deliveries per session, then a short form that still fires every prompt. That
keeps presence at parity with the system prompt while cutting the steady-state
cost by roughly 80%. A cooldown that skips prompts entirely would rebuild the
SessionStart failure — a window where the restriction is unopposed.

## 00:04 · finding · — — an ORPHANED CLAUDE.md guidance block has no guard (DBF)

Observed while checking my own work, not reported by anything.

Restarting the daemon (mandatory after a handler change) made the daemon
regenerate and AUTO-COMMIT the root `CLAUDE.md` guidance block — commit
`a16620d0` — while `standing_authorisations.py` itself was still untracked. So
HEAD briefly carried resident guidance for a handler that did not exist in that
tree.

This is the exact hazard `CLAUDE/development/RELEASING.md` Step 13 warns about
("the GENERATED artifact lands in git while its SOURCE handler does not"), and
its documented mitigation is a MANUAL pre-staging check. It self-heals here as
soon as the source is committed.

The DBF observation is that the mitigation is a human remembering. Checked:
`scripts/qa/check_repo_hygiene.py` defines five rules
(`tracked-build-artifact`, `root-test-script`, `frozen-session-summary`,
`src-test-stub`, `ignored-plan-document`) and NONE of them checks that every
handler section in the `<hooksdaemon>` block corresponds to a handler that
exists in the tree. The ordering that produces the divergence is inherent —
restart-to-verify necessarily precedes commit — so every new handler passes
through this state; only an abandoned change leaves it permanently.

Deliberately NOT fixed inside this plan: a new hygiene rule needs its own
tests and belongs with the other repo-hygiene rules, not bolted onto a plan
about standing authorisations. Recorded here so it is not silently absorbed,
and raised with the user rather than dropped.

## 00:34 · finding · T4.1 — mypy was right about a type that lied

`redundant-expr` on `isinstance(entry, dict)` in `_enabled_ids`. The declared
option type was `list[dict[str, Any]] | None`, so mypy could see the guard as
unreachable-by-type.

The tempting fix is to delete the guard. That would be wrong — this is
arbitrary user-authored YAML, and a config typo would then take the daemon

data, and the guard stays as the validation (Core Standard 14).

Worth stating as a general rule: when mypy calls a runtime guard redundant on
external data, the guard is usually right and the annotation is usually the
lie.

## 00:37 · thought · — — do not trust a background task's reported exit code

The task notification for the QA run said "exit code 0". QA had actually
failed, 17/20, `exit=1`.

Cause is mine: the backgrounded command was
`./scripts/qa/llm_qa.py all > out 2>&1; echo "exit=$?" >> out`. With `;` the
compound command's status is `echo`'s, which is always 0, so the harness
faithfully reported 0 for a failed gate.

Had I trusted the notification I would have committed over three real
failures, including the missed registration point above. **Read the artifact,
never the reported exit code** — and prefer a wrapper that propagates status
rather than one that swallows it behind a trailing `echo`.

## 00:46 · finding · — — the guidance guard is blind because the GENERATOR discards the name

Stopped deferring the orphaned-guidance gap and designed the guard. The
investigation found the real cause, which is upstream of where I was looking.

`core/claude_md_injector.py` collects sections as `(handler.name, content)`
pairs — the name IS known — and then `_build_section` does:

```python
for _name, content in sections:
    parts.append(content.strip())
```

The name is discarded. So the `<hooksdaemon>` block carries no
machine-readable link back to the handler that produced each section, and the
headings that remain are inconsistent by convention: most are
`## <config_key> — ...` (`## destructive_git`, `## sed_blocker`), but several
are prose (`### Stop Explanation Required`, `### Pipe Blocker`). Any guard
parsing headings would be part heuristic, part false-positive generator.

So this is DBF in its exact form: the guard cannot see the problem because the
GENERATOR threw away the information the guard would need. Writing a
heading-parsing checker would be fixing the symptom with a worse tool.

Proper fix, in order:

1. `_build_section` emits a marker per section (`<!-- handler: <name> -->`),
   using the name it already has.
2. A `check_repo_hygiene` rule asserts every marker resolves to a handler that
   EXISTS in the tree.

Note the rule must be "exists", NOT "is committed". The transient divergence
(restart-to-verify necessarily precedes commit) is inherent and happens for
every new handler, so a committed-ness check would fire constantly and be
disabled within a day — precisely the failure mode Core Standard 15's own text
warns about. Only the permanent orphan is worth flagging.

Deliberately sequenced AFTER the 00223 commit rather than folded into it: it
touches the injector and the hygiene suite, which have nothing to do with
standing authorisations, and it needs its own tests. Sequencing, not deferral
— it is the next thing I do.
