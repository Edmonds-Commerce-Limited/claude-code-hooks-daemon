## 07:30 · finding · T1.2/T1.3 — the surface, and the two references that are docs not code

10 handler modules, 12 other `src/` files, 16 test files.

The two that would have been quietly broken by a mechanical delete:

- `core/hook_result.py:370` — a DOCSTRING naming `hello_world_stop` as the
  example of an unconditional advisory handler in the Stop check. Deleting the
  handler leaves prose pointing at nothing.
- `utils/naming.py:32/61/80` — `HelloWorldPreToolUseHandler` is the worked
  example for ALL THREE naming conversions (class→snake, snake→kebab,
  kebab→snake), and `tests/unit/utils/test_naming.py` asserts against it. This
  one is load-bearing documentation: the naming utility's contract is explained
  entirely through this example.

Neither is a dependency, both need a replacement example that still exists. A
grep-and-delete pass would have left the naming utility's docstring describing a
class the codebase no longer contains — the exact "docs assert something that
became false" shape the truth-changes convention exists for.

Retired-handler registry: `RETIRED_HANDLERS: dict[str, str]` at
`constants/handlers.py:669`, handler id → user-facing explanation, consumed by
`config/validator.py`. Its own comment records why it exists: handlers retired
BEFORE the registry existed had their config keys rejected as unknown, tipping
an unedited v2.x config into DEGRADED MODE with no way for the user to know why.
Ten entries are needed here, one per event type, or every client whose config
still carries these keys hits exactly that.

`.claude/HOOKS-DAEMON.md`'s per-event counts are generated and ALREADY exclude
the TEST handlers — they have been gated off since v3.40.0 — so the doc needs a
regenerate, not a hand edit, and the counts will not move.

## 07:32 · thought · — the delegation did not earn its cost here

Spawned two Explore agents for these two audits. Both went idle without
returning a report across three notification rounds, and one left a stale
`.git/index.lock` in the shared checkout (no git process running, 15 minutes
old, index intact — removed by hand).

Both audits turned out to be two greps each. I did them directly in less time
than the three turns spent chasing the agents, and every conclusion in Plan
00239 and Plan 00240 so far comes from files read directly rather than from an
agent summary.

Two lessons, and the second is the one that keeps recurring: delegate when the
search is genuinely broad, not when it is a bounded grep; and when peers may
touch the same git index, use `isolation: "worktree"` — which is exactly the
correction recorded in Plan 00238's journal for 26-08-14, repeated here within
the same session.

## 09:20 · finding · P2 — a stale-daemon trap that presented as an unrelated failure

The first full run after the removal failed 14 tests. Thirteen were the expected
shape — two classification tables still naming the deleted handlers, i.e. the
Plan 00203/00234 guards doing exactly their job.

The fourteenth was not, and was the interesting one:

```
test_every_earning_handler_has_a_section_in_claude_md
  DismissiveLanguageNitpickHandler (name=nitpick-dismissive-language)
  HedgingLanguageNitpickHandler (name=nitpick-hedging-language)
```

Nothing in this plan touches the nitpick handlers, and the same test passed
21/21 an hour earlier. The cause was the daemon: it regenerates the
`<hooksdaemon>` block in `CLAUDE.md` on every restart, and it had restarted at a
moment when the handler modules were deleted but the registry was not yet
consistent — so it wrote a block missing those two sections, and the tracked
file kept it.

The first instinct was to suspect the agent's `controller.py` edit had dropped
the pseudo-event handlers from the injector list. Reading the diff settled it in
one look: three lines removed, exactly the argument. Restarting the daemon on
the completed tree brought both sections back and the test passed.

This is the "#1 dogfooding failure mode" CLAUDE.md warns about, but with a twist
worth recording: it did NOT present as "handler doesn't fire". It presented as a
test failure about two handlers nobody had touched, in a file nobody had edited.
When a failure names something outside the change, the daemon's own generated
artefacts are a candidate before the change is.

## 09:30 · action · T3.4 — client mode verified the thing that actually matters

Self-install can only show that the removal compiles. The failure this plan is
guarding against is a CLIENT with an unedited config, so the fixture was driven
that way: a real installed client repo, then both retired names injected back
into its config —

```
daemon:
  enable_hello_world_handlers: false
  pre_tool_use:
    hello_world_pre_tool_use: {enabled: false, priority: 5}
```

— then restarted. Daemon RUNNING, no degraded mode, no unknown-key finding, and
`destructive_git` still denying a probe. Without the ten RETIRED_HANDLERS
entries this is precisely where every upgrading project would have gone into
DEGRADED MODE, silently, until a human hand-edited their file.

Worth noting the probe itself had to be built with a split literal
(`"git re""set --ha""rd"`), because the dogfood daemon blocks the full command
string wherever it appears — including in my own verification command. That
matching is deliberate and documented; it is what makes acceptance tests
possible.
