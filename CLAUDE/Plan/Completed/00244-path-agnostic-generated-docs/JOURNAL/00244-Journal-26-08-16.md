## The dogfooding blind spot is the real finding

In self-install mode the project root is `/workspace`, so the generated docs
render `/workspace/bin/hooks-daemon …` — an absolute path that happens to be
identical for everyone. Our own committed artifacts therefore look correct while
every client install writes a developer's home directory into a tracked file.

Per Core Standard 15 (DBF), the guard is the fix worth having: nothing currently
asserts that generated tracked docs are free of the rendering project's own
root, and no test renders them under a client-mode root. That is why the defect
was invisible for as long as it was.

## Decision: path form for the doc variant

The report ranked `<repo-root>/…` first (and applied it downstream by hand).
Raised the conflict with the human rather than silently overriding a stated
preference: `<repo-root>/…` is not runnable as printed, and Plan 00192 exists
because non-runnable documented commands led agents to "repair" working
installs — the same failure class.

Human chose the **project-root-relative** form:

- client install → `.claude/hooks-daemon/bin/hooks-daemon status`
- self-install → `bin/hooks-daemon status`

This is path-agnostic and still copy-paste runnable from the project root, which
the daemon's docs already name as the working directory for every daemon
command. It is also the shape `_fallback_relative_path()` already returns, so
there is one definition of a path-agnostic wrapper path rather than two.

## A second defect class the report did not identify

An exhaustive call-site map (AST scan, transitive to depth 3) confirmed the
report's 10 handlers / 11 builder call sites and the docs generator. It also
found something the report's method could not: `absolute_path` and
`root_recursion_guard` hard-code the literal `/workspace` into `get_claude_md()`.

Grepping for `daemon_cli_command` never finds those, and they are worse in kind.
An absolute path is at least true on the machine that produced it; `/workspace`
is true on no client machine at all. `absolute_path` was telling every client
install to prepend a directory that does not exist there — in its resident
guidance AND, as it turned out, in its runtime block reason
(`Example: /workspace/{file_path}`). `root_recursion_guard` had the same shape on
both surfaces.

That settled the guard's design: assert on the RENDERED TEXT, not on the call
sites. A call-site rule would have shipped the fix and left this class untouched.

## Pre-existing failure found, NOT caused by this work

`tests/integration/test_hooks_deploy_permissions.py` has 5 failures (expects
`0o755`, gets `0o744`). Verified pre-existing by running the same file in a
clean worktree at HEAD before these changes — identical 5 failures.

Cause is this container's `umask 0077`, which strips the group/other bits that
`chmod +x` would otherwise grant. Nothing in this plan touches permissions.

Left unfixed deliberately: the real question is whether the deploy should force
`0o755` regardless of umask or whether respecting the umask is correct, and that
is a decision about the permissions subsystem, not about this plan. Raised with
the human rather than folded in silently.
