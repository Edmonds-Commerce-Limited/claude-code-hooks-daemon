## 11:27 · finding · —   — superseded release-gate run was cancelled by concurrency, not by hand

Item 3 check: why did superseded Release gate run 42598705633 appear to keep running during v3.73.1?

It did not. The concurrency group cancelled it; no hand cancel was involved.

Evidence (gh api, check-run annotations on each cancelled job of the run):

- All 15 cancelled jobs of 42598705633 carry GitHub's annotation
  "Canceling since a higher priority waiting request for release-gate-188 exists".
- Timeline on release/3.73.1: 42598705633 created 10:08:43 for 7fee2b4b8; the next push
  (f53afe5f4) started run 42599128101 at 10:12:03; 42598705633's jobs completed `cancelled`
  at 10:12:18-10:12:21. That is an 18 s cancellation latency.
- The earlier pair is the same: 42598050981 (755c97baa) was superseded at 10:08:43 and
  cancelled at 10:09:01, also 18 s, with the same annotation on 14 jobs.
- No push landed between 10:08:43 and 10:12:03, so nothing could have cancelled the run
  sooner. A hand cancel in that window would show a different annotation.

What did look like the run "kept running": its `checks docs` job FAILED at 10:10:48, yet
the 15 test-shard jobs kept going until the supersede at 10:12. A failed job in a run does
not stop its sibling jobs (no fail-fast across jobs). So a run that is already red keeps
spending runner time until it finishes or is superseded. That is a separate gap, not a
concurrency defect, and it is out of scope for this plan. It is NOT yet in the niggles
ledger: Plan 00474 is linked to issue #59, which is assigned to another account, so
github_issue_assignment_guard denies edits to it from this session. Candidate niggle for
the owner to file: a release-gate job that `needs` the fast checks and runs
`gh run cancel ${{ github.run_id }}` (needs `actions: write`) when any of them fails.

Conclusion: `cancel-in-progress: true` on `release-gate-<PR or ref>` works as designed, and
TestASupersededRunIsCancelled pins it. No workflow change is needed for item 3.
