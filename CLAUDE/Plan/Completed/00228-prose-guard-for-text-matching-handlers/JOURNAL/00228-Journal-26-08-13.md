## 06:05 · finding · T1.1 — the plan's own proposed mechanism was wrong

This plan was FILED proposing that the guard be scoped by priority band —
safety handlers exempt, everything above them in scope. Plan 00227's Decision 3
proposed the same thing. Checked the actual numbers before writing any code:

| handler              | priority | band    | instance  |
| -------------------- | -------- | ------- | --------- |
| `pipe_blocker`       | 15       | safety  | 00222, #4 |
| `nitpick_dismissive` | 10       | safety  | 00225     |
| `nitpick_hedging`    | 20       | safety  | 00225     |
| `plan_number_helper` | 30       | quality | 00227     |

A band-scoped guard would have exempted THREE OF THE FOUR instances it exists
to catch. Not imprecise — inverted for most of the evidence.

The proxy fails because priority encodes DISPATCH ORDER, not consequence.
`pipe_blocker` runs at 15 so it short-circuits before expensive handlers get a
turn; nothing about 15 claims a miss is unrecoverable. That is the same
category error as reading `HandlerTag.ADVISORY` as "cannot block", which Plan
00227 fixed yesterday in a different handler. Twice in two days I have taken a
number or a tag that encodes ONE property and read it as a statement about a
DIFFERENT one.

Inverted the design: every handler in scope by default, deliberate matchers
named explicitly with reasons. That also fails closed for handlers nobody has
thought of yet, which band-scoping never would.

## 06:20 · finding · T2.2 — the guard's second hit was a trap, and I walked into it

First run surfaced three handlers. One was the predicted `pipe_blocker` heredoc
case. The other two were more interesting:

**`AutoContinueStopHandler`, on all five fixtures** — a bug in MY guard. The
first draft fed a Bash PreToolUse payload to every discovered handler including
Stop handlers, which is a category error: a Stop handler never receives that
event, so its answer is meaningless. Scoped the guard to the PreToolUse
package.

**`GitStashHandler`, on prose about the stash policy** — looked exactly like a
fifth instance. `echo "this project blocks git stash because ..."` is denied,
which is precisely the shape of the defect. I implemented the quoted-span fix
for it. Then the existing suite went red:

```
AssertionError: Should block: echo "git stash"
tests/unit/handlers/test_git_stash.py::test_matches_git_stash_in_echo_quotes
```

The behaviour is SPECIFIED. It is the CLAUDE.md-prescribed mechanism by which
the acceptance suite verifies a blocking handler — embed the command in a
string and check it is refused. My "fix" would have broken acceptance testing
while looking like a false-positive repair.

What saved it was running the existing tests before believing my own diagnosis.
Nothing else would have: the reasoning was clean, the analogy to
`plan_number_helper` was exact, and the change was small. Reverted, and
recorded in the exemption map with the test names as the justification.

**Takeaway worth keeping**: a guard finding is a CANDIDATE, not a verdict. This
one produced three hits — one real bug, one bug in the guard itself, and one
piece of correct behaviour that a confident engineer would have "fixed".

## 05:31 · finding · T2.4 — my targeted selection was narrower than my change

Full QA came back 18/20, not green: seven failures in
`test_pipe_blocker_prose_remediation.py`, none of which my earlier targeted run
had touched. I had reported "87 green / 0 red" against a selection I chose from
the files I had edited — but the change was to a SHARED helper on the scan
path, so its blast radius was every test that reaches the matcher, not every
test in the files I opened. Picking the selection by "files I edited" is what
missed them.

The notification for that QA run said **exit code 0** while the artifact said
`QA_EXIT=1`. Sixth time today. The artifact is the only thing worth reading.

**The failures were the same trap as 06:20, and the answer was the opposite.**
Every one used a QUOTED heredoc to get prose in front of the matcher — exactly
what the fix now blanks. Having just been burned by "fixing" a specified
behaviour in `git_stash`, the honest question was whether I was about to do it
again in reverse: change the tests to suit my code.

What settled it was the tests' own language, not my reading of the handler:

- the class is named `TestProseFalseTriggerGetsNoRemediationTemplate` — the
  author called the trigger FALSE
- the failing sanity test's docstring says "the detection itself is correct and
  **out of scope per Non-Goals**"

Plan 00209 identified the false positive, deferred the detection, and shipped
only the reason-shape fix. Its deliverable was the REASON, not the block. So
00228 delivers the deferred half and the plans compose — where `git_stash`'s
tests asserted a denial CLAUDE.md mandates, and there the denial WAS the
deliverable.

Verified by probe before rewriting anything, rather than assuming the retarget
target was live:

```
quoted heredoc, prose body         match=False   (now allowed)
unquoted heredoc, prose body       match=True    prose_reason=True
unquoted heredoc, $(pytest|tail)   match=True    prose_reason=False
quoted heredoc, $( ) as text       match=False
real pipe, no heredoc              match=True    prose_reason=False
```

Row 2 says the retarget lands somewhere real; row 3 is the teeth of the
quoted/unquoted boundary — bash substitutes inside an unquoted heredoc, so
extending the exemption there would be a one-character bypass.

**Two things this dragged out that I had not looked for**, both of which would
have shipped silently:

1. `get_claude_md()` still told every session "a heredoc body ... can
   false-trigger this handler". Resident guidance contradicting the handler is
   its own defect.
2. `get_acceptance_tests()` carried a `<<'EOF'` case expecting DENY — a premise
   the fix makes unreachable, so the next release's acceptance run would have
   failed on it. That is precisely the class Plan 00196 closed, recurring in a
   handler's own test definitions.

Also worth noting: the daemon auto-committed the regenerated `CLAUDE.md`
(`6f9176c3`) the moment I restarted, while `pipe_blocker.py` — the SOURCE of
that guidance — was still uncommitted. That is the exact divergence
`RELEASING.md` warns about, seen live rather than in theory.
