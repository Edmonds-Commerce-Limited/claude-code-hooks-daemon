# Plan 00390 — Journal 26-09-13

> **Append-only activity log** for plan 00390. One file per day
> (`00390-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM; NEVER edit earlier
> entries (corrections are new entries):
>
> ```
> ## HH:MM · category · REF — one-line summary
>
> Body.
> ```
>
> - `HH:MM` local 24h (the date is in the filename); times increase down the file.
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 11:30 · finding · N2 — a generated rule row asserted a gate that was switched off

`CLAUDE.md:479` carried `R-PLAN-CLOSE-APPROVAL` with a Why column reading
"This project requires a human to close a plan", while
`close_requires_human_approval` was `false` and the handler's `matches()`
returned False before anything else. An enabled-but-inert handler contributed
its rule row unconditionally.

Cost, measured rather than imagined: two finished plans (00386, 00389) sat open
across a multi-day cron run, the belief was written into both plan documents as
fact, and the owner was briefed to run two commands that would have done
nothing.

## 11:45 · decision · N2 — omit the handler, do not reword the row

A smaller fix existed: make the Why column read conditionally. Rejected. The row
would still sit under a heading reading "All other ENFORCED rules" while
enforcing nothing, and resident guidance is not free — the guidance-coverage
suite's own measurement puts this block at ~73 KB / ~18,300 tokens per session.

Implemented as an optional `CanBeDormant` protocol, default-active because most
handlers gate on their INPUT, which is undecidable at generation time.

## 11:52 · finding · N2 — the sibling gate was mis-assessed, and the config comment was right

An earlier revision of N2 claimed `R-MERGE-TO-MAIN-APPROVAL` was honest because
its key "is true here". It is not — there is no `worktree:` section in
`.claude/hooks-daemon.yaml` at all, so the key takes its default `False`. The
claim came from reading ONE grep line of a comment that continues onto the next
and says "inert here since that key is false (default)". The config comment was
correct; the reading was not.

Both rows were therefore removed, and both removals are correct.

## 12:05 · action · N2 — proved through the real registry, in both directions

The stub tests prove the injector honours `is_dormant()`. They cannot prove the
daemon's own handlers report it truthfully, because that depends on the registry
injecting config BEFORE the injector walks the chain. A test now drives the real
path with the key ON and OFF:

```text
key ON  -> R-PLAN-CLOSE-APPROVAL present
key OFF -> R-PLAN-CLOSE-APPROVAL absent
```

The ON half is the one that matters: it is what stops this fix silently deleting
a gate a project really did turn on.

Swept for other config-dormant handlers afterwards: only these two. The other
`bool = False` handler attributes (`_languages_applied`, `_timeouts_applied`)
are one-time-application latches, not dormancy switches.

## 12:20 · finding · — — this ledger's own closing rule was wrong

`PLAN.md` carried: "This ledger stays OPEN while it is the current one. It is
not 'finished' when its entries are: it closes when a successor opens."

The canonical SOP in `CLAUDE/core/PlanWorkflow.core.md` says the opposite:

```text
- **When every entry is resolved, close and archive the ledger.** Do not keep a
  ledger open as a permanent fixture.
- **The next niggle found opens a NEW ledger.** Never reopen a closed one.
```

Four precedents agree with the SOP and not with the note: ledgers 00377, 00379,
00381 and 00385 are all `Complete` and archived. 00390 was the only one sitting
open, and that note was the reason.

Same class of error as N2 itself — a document asserting a workflow rule its
canonical source contradicts — so it is corrected in the closing commit rather
than carried forward.
