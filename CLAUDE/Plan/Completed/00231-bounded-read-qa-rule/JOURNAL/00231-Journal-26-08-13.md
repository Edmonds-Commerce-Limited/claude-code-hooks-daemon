## 11:55 · finding · — — origin was a question, and it corrected me

Started as a user question: is the session transcript a hooks-daemon artefact
or a Claude Code artefact, and why does the Stop handler read it six times?
Answering required measuring, and the measurement contradicted my own earlier
claim.

**Correction on the record**: I had told the user the Stop handler "re-reads and
re-parses a 74 MB transcript up to six times per stop event". Wrong. The six
retries call `TranscriptReader.load_tail()`, a bounded 1 MiB seek — 17.5 ms
each, flat as the file grows. Plan 00177 already fixed that. The retry loop is
a defensible answer to a genuine race: Claude Code flushes the transcript
asynchronously, the Stop payload carries no assistant message text, and the
daemon cannot be notified when the write lands.

The transcript is a **Claude Code** artefact — `/root/.claude/projects/…`,
outside the project. The daemon only reads it; `transcript_archiver` copies it.

What the measurement did find:

```
load_tail (1 MiB seek)      :  17.5 ms   <- 6 retries = ~105 ms, flat
has_recent_stop_hook_block  : 162.0 ms   <- reads all 74 MB, grows forever
```

`has_recent_stop_hook_block()` wanted the last 20 lines and used
`deque(f, maxlen=20)`, which iterates every line to keep twenty. It is called
ONLY when `stop_hook_active` is set — so the repeatedly-executed path was the
expensive one.

## 11:55 · decision · P1 — DBF turn changed the deliverable

User redirected: do not fix the instance, add a QA rule so it cannot recur.
Plan 00177 fixing `load_tail` while leaving its sibling untouched is exactly
the argument for guarding the class instead of patching occurrences.

Key design realisation: the checkable signal is the **declared bound**.
`maxlen=20` is the author's own written intent sitting next to a read that
ignores it — local, explicit, no guess about file size needed. A whole-file
read with no declared bound stays legal, which is what holds false positives
at zero.

## 11:55 · finding · T3.3 — the byte-accounting test was nearly vacuous

It wrapped `read()` to tally bytes, but the ORIGINAL defect consumed the file
by ITERATING it and never called `read()`. The tally would have scored the bug
at zero bytes and passed. Added `__iter__` counting, then proved it against a
reconstruction of the old code:

```
file size          : 2,396,089 bytes
OLD (deque+iterate): 2,396,089 bytes  -> guard fires: True
NEW (bounded seek) :    65,536 bytes  -> guard fires: False
marker still found : True
```

The Plan 00230 lesson repeating: a guard that is registered, runs, and finds
nothing is indistinguishable from a guard that passes.
