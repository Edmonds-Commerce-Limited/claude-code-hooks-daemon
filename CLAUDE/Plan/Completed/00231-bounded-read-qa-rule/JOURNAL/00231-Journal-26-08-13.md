## 11:55 · finding · — — origin was a question, and it corrected me

Started as a user question: is the session transcript a hooks-daemon artefact
or a Claude Code artefact, and why does the Stop handler read it six times?
Answering required measuring, and the measurement contradicted my own earlier
claim.

**Correction on the record**: I had told the user the Stop handler "re-reads and
re-parses a 74 MB transcript up to six times per stop event". Wrong. The six
retries call `TranscriptReader.load_tail()`, a bounded 1 MiB seek — 17.5 ms
each, flat as the file grows. Plan 00177 already fixed that. The retry loop is
a defensible answer to a genuine race: Claude Code flushes the transcript
asynchronously, the Stop payload carries no assistant message text, and the
daemon cannot be notified when the write lands.

The transcript is a **Claude Code** artefact — `/root/.claude/projects/…`,
outside the project. The daemon only reads it; `transcript_archiver` copies it.

What the measurement did find:

```
load_tail (1 MiB seek)      :  17.5 ms   <- 6 retries = ~105 ms, flat
has_recent_stop_hook_block  : 162.0 ms   <- reads all 74 MB, grows forever
```

`has_recent_stop_hook_block()` wanted the last 20 lines and used
`deque(f, maxlen=20)`, which iterates every line to keep twenty. It is called
ONLY when `stop_hook_active` is set — so the repeatedly-executed path was the
expensive one.

## 11:55 · decision · P1 — DBF turn changed the deliverable

User redirected: do not fix the instance, add a QA rule so it cannot recur.
Plan 00177 fixing `load_tail` while leaving its sibling untouched is exactly
the argument for guarding the class instead of patching occurrences.

Key design realisation: the checkable signal is the **declared bound**.
`maxlen=20` is the author's own written intent sitting next to a read that
ignores it — local, explicit, no guess about file size needed. A whole-file
read with no declared bound stays legal, which is what holds false positives
at zero.

## 12:05 · decision · P5 — a NAME rule for what shape rules cannot reach

The audit's structural point is the valuable part: no AST pair rule can see
this. There is no `.read()` in the expression to key on, and the declared bound
lives in a DIFFERENT function from the read. Shape is simply the wrong handle.

So added a second rule keyed on the API name — `TranscriptReader.load()`
outside its defining module — bound to names proven to hold a reader, so the
many unrelated `Config.load()` calls are untouched. The defining module is
exempt, mirroring how `check_python_var_guidance.py` exempts `cli_command.py`.

The general lesson worth carrying: a shape rule and a name rule cover different
classes, and picking the wrong one produces a guard that is registered, runs,
and is blind — the Plan 00230 failure mode again.

## 12:05 · finding · P5 — the shape rule catches 1 of 11 spellings

## 13:35 · correction · Decision 3 reversed — semgrep adopted

Recording that the plan's Decision 3 was **wrong** and has been rewritten in
place, rather than leaving the archived plan asserting a decision the very next
commit reversed.

**What I got wrong.** Decision 3 rejected semgrep partly on "a new runtime
dependency in a daemon that clones into client projects". The user challenged
the premise directly ("can't python projects have dev deps like PHP?"), and one
file settled it: `scripts/install/venv.sh:674` provisions a client venv with
`uv pip install -e <dir>` and no `[dev]` extra. Ruff, mypy, black and bandit
have never reached a client project. Semgrep sits in exactly the same bucket.

The failure worth naming is not "chose the wrong tool" — it is that I stated a
fact about the installer's behaviour without reading the installer, in a
document whose purpose is to be trusted later. That is the same shape as the
hedging the Stop handler advises against, except it did not read as a hedge.

**How it was settled.** Not by argument — by running both engines over the SAME
11-shape probe:

| engine                   | caught | cost                                |
| ------------------------ | ------ | ----------------------------------- |
| hand-written AST checker | 1 / 11 | ~300 lines Python + 19 tests        |
| semgrep rules            | 9 / 11 | ~130 lines YAML, no tests of its own |

Strict dominance, so keeping both would only let two implementations of one
rule drift apart. Deleted `check_bounded_reads.py` and its 19 tests.

**The 2 misses are diagnosed, not hedged** (now Decision 5). A minimal 3-rule
probe: `pattern-inside` with a `...` sequence does not bind the read to the
later slice; taint mode does not propagate into a subscript sink. The only
form that matches is a bare `$X[-$N:]`, which flags every negative slice in the
repo. So 9/11 is the honest ceiling, not a tuning gap I failed to close.

**One deliberate hardening.** `run_semgrep_check.sh` exits 1 when the binary is
absent. A check that reports green while examining nothing is the vacuous-guard
failure Plan 00230 hit and the exact thing DBF exists to prevent — a missing
linter must be loud.

**Real payoff for DBF**: the next rule is a `.yaml` dropped into
`scripts/qa/semgrep/`. Picked up automatically — no wiring, no script, no tests.
