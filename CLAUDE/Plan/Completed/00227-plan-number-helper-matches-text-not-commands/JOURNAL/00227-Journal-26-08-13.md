## 04:58 · finding · P1 — one of my three defects was latent, not live

second one — the archive-coverage carve-out refusing a regex alternation — is

```

Row 1 is the point: the alternation command is allowed because NO RULE MATCHES

## 05:10 · decision · T2.1 — the global exemption was wrong, and the tests said so

First implementation blanked shell literals for EVERY rule. Three existing
tests broke immediately:

- `ls -1 CLAUDE/Plan/ | grep -E '^[0-9]+'` — the numeric grep pattern IS the
  signal for that rule, and it lives inside single quotes
- `find CLAUDE/Plan -name "00036-*"` — the `-name` argument is what separates a
  targeted find from a sweep, and it lives inside double quotes

So this handler reads quoted arguments *deliberately*, and a blanket exemption
blinds rules that were working correctly. Scoped the blanked copy to the two
rules that misread literals and left the rest on the raw command.

This is Plan 00225's Decision 2 arriving in a new setting: place an exemption
by consequence-of-a-miss, never by uniformity. Worth noting that I reached for
uniformity first and the regression suite is what stopped me — the reasoning
did not.

## 05:40 · finding · — — a FOURTH instance of the class, found while fixing the third

While probing this handler, `pipe_blocker` denied a command of mine because a
truncating pipe appeared inside a **Python string literal**, inside a heredoc
whose delimiter was quoted:

```
"$PY" - <<'PYEOF'
CASES = [("alternation + sort + trunc", "ls CLAUDE/Plan | ... | sort | tail -1")]
PYEOF
```

A QUOTED heredoc delimiter means the shell performs no expansion at all — the
body is handed verbatim to python's stdin. The shell can never execute that
pipe. So this is the same defect as 00222/00225/00227: text read as a command.

Notably `pipe_blocker` ALREADY has heredoc awareness — its documented
exemptions cover the `"$(cat <<'EOF' ... EOF)"` idiom precisely because a quoted
delimiter makes the body literal. The reasoning exists; it is scoped to git
message values and never generalised to a heredoc feeding an interpreter's
stdin. That is worth stating carefully, because it means the fix is likely to be
widening an existing, already-correct notion rather than inventing one.

Not filed yet — filing advances the plan counter, which would invalidate the
README statistics staged in this plan's own commit. Recorded here so it survives
until 00227 lands.

## 05:48 · finding · — — verified the 05:40 claim; the gap is narrower than stated

Correction and refinement of the 05:40 entry (a new entry, not an edit — the
journal-append-only check caught me rewriting that one in place, correctly).

At 05:40 I said `pipe_blocker` "already has heredoc awareness" and implied the
fix would be widening it. I had not checked how that awareness is implemented,
and "probably just needs widening" is the kind of claim that becomes a wrong
plan. Checked:

- `pipe_blocker.py:226` holds the exemption, and it is bound to ONE syntactic
  shape — `"$(cat <<'EOF' ... EOF)"`, a command substitution capturing `cat`,
  used as a git message value.
- My case had no `cat`, no `$( )` and no surrounding quotes — a heredoc on an
  interpreter's stdin.
- The handler's other escape route, prose detection by function-word density
  (`:154`), does not apply either: a Python string literal is not prose.

So the accurate framing is NOT "add heredoc awareness". The handler's own
guidance at `:968` already states the principle — a QUOTED delimiter makes the
body literal — and the implementation acts on it in exactly one instance. The
fix is to let the stated principle cover the general case, which is a smaller
and better-founded change than the one I first described.

Worth noting the shape of my own error: I reached for a plausible
characterisation of unread code, and the Stop-time hedging advisory is what sent
me to verify it. That is the handler working as designed on me — the third time
today a guardrail in this repo has corrected my reasoning rather than my typing.
