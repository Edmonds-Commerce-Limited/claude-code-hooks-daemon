## 12:15 · finding · — — a SECOND overclaim, pre-existing: conditional execution

While probing whether POSIX mode changed how `&&`/`;`/`|` terminate an operand
run — `_collect_trailing_operands` depends on them to stop consuming, so a
tokenising change could plausibly have broken it — a different overclaim
surfaced.

Takeaway: the accessor names write targets on branches a real shell never runs.

```
[ok]        echo hi | tee {S}/t.txt && echo x > {S}/b.txt
[ok]        cp {S}/src.txt {S}/c1.txt; echo x > {S}/b2.txt
[ok]        echo hi | tee {S}/t2.txt | grep hi > {S}/b3.txt
[OVERCLAIM] cp {S}/src.txt {S}/c2.txt || echo fallback > {S}/b4.txt
    over: ['b4.txt']
[ok]        for f in a b; do echo $f > {S}/loop.txt; done
```

`cp` SUCCEEDED, so the `||` branch never ran and `b4.txt` was never written —
yet the accessor names it. A defect found while fixing another one is easy to
mis-blame, so it was checked against BOTH tokenisers before being attributed:

```
cp ... || echo fallback > /s/b4.txt   legacy=['/s/c2.txt', '/s/b4.txt']
                                      posix =['/s/c2.txt', '/s/b4.txt']  identical
false && echo x > /s/never.txt        legacy=['/s/never.txt']
                                      posix =['/s/never.txt']            identical
test -f /s/x && echo y > /s/cond.txt  legacy=['/s/cond.txt']
                                      posix =['/s/cond.txt']             identical
```

**Pre-existing, NOT a regression from this plan**, and a different mechanism
entirely — no quoting is involved. The accessor reads command TEXT and cannot
model exit codes, so any branch a real shell short-circuits is still named.
`&&` has the mirror form.

Not fixed here, and the reason is not "it belongs to another plan". It is that
learning the exit code means EXECUTING the command, which an accessor running
inside a PreToolUse dispatch must never do. The honest alternatives are to
document the limit, or to drop conditional branches altogether — which trades
one overclaim for a MISS on every legitimate `&& >` write, a common and
deliberate shape. Documenting is the better trade, so it is going into the
plan's Non-Goals with this reasoning rather than being left in scrollback.

Mitigation that already exists: both denying linters check `Path.exists()`
before acting, so a named-but-unwritten path is skipped unless a file of that
name happens to exist. That is exactly the thin protection the escaped-quote
phantom also had — and there it was NOT enough, which is why this is recorded
rather than waved past. It belongs alongside the accessor's other documented
conservatism limits (the `$VAR` and glob declines).

## 12:35 · blocker · T3.1 — a SELF-INFLICTED QA failure: source edited mid-run

`llm_qa.py all` returned **22/23 PASSED, 1 FAILED** — and the wrapper exited
**0**, the third time in this project that the exit code has disagreed with the
`QA: N/M` line. The line is the authority; the exit code is not.

The failing check was coverage, not tests: `12876 passed, 0 failed` but
`coverage: 94.72%` against `fail_under = 95.0`.

Takeaway: the entire shortfall was one file, and the measurement was wrong.

```
src/claude_code_hooks_daemon/core/utils.py  175  75  82  20  46.69%
   254-255, 260->265, 268-269, 271-381, 399-400, 402-407, ... 570-576
TOTAL                                     23501 977 6894 459  94.72%
```

46.69% is implausible for a module with 123 dedicated passing tests, so the
figure was checked rather than believed. Running just its own tests:

```
src/claude_code_hooks_daemon/core/utils.py  175  3  82  4  97.28%  477, 493->495, 516, 518
123 passed
```

Arithmetic confirmed the whole gate failure sat in that one file: had utils.py
measured at its true 172/175, the total would have been **96.15%**, comfortably
over the gate.

**Cause, and it is mine.** I edited `utils.py` WHILE the QA run was in flight —
inserting a nine-line docstring paragraph at line 200 to record the
conditional-execution finding. Coverage collected execution data against the
pre-edit file and then rendered its report against the post-edit file, so every
line below the insertion point mis-mapped by nine and read as unexecuted. The
evidence is exact: `git diff -U0` shows `@@ -199,0 +200,9 @@`, and the report's
first missing line is 254 — everything BEFORE the insertion is covered,
everything after is not. Functions used by handlers across the whole suite
(`get_workspace_root`) appear unexecuted, which is what gave it away.

Ruled out first, by measurement rather than argument: a duplicate installed
package (both venvs import from `/workspace/src/`), test-order randomisation
(`pytest_randomly` is not installed), and the test files failing to collect
(they are all present in the run's own file list).

**Lesson, recorded because I had already decided this and then did it anyway:**
do not touch `src/` while a coverage run is in flight. I had deliberately
deferred two earlier edits for exactly this reason, then made this one to act
on a handler advisory without re-checking that QA was still running. A doc-only
edit felt harmless; to coverage's line mapping it is not. Journal and plan edits
are safe — coverage only measures `src/` and `.claude/ccy`.

No code change is warranted. A clean re-run on a stable tree is the remedy, and
a confirmation run started after the edit is the check.

## 12:45 · finding · T3.2 — live probe PASSES, both halves, over the real socket

Probed the running daemon through the production wrapper
(`.claude/hooks/post-tool-use`), not the library, so this exercises dispatch.

Takeaway: the daemon discriminates correctly between AUTHORING a file and
merely MENTIONING its path inside a quoted argument.

Control — a genuine redirect to the broken fixture MUST still deny:

```
command: cat > /workspace/untracked/cmp-broken.py
{"decision": "block", "reason": "Python lint FAILED for cmp-broken.py
  File \"/workspace/untracked/cmp-broken.py\", line 1
    def broken(
              ^

```

The original false-denial shape — the path only QUOTED, never written:

```
command: echo "{\"cmd\": \"cat > /workspace/untracked/cmp-broken.py <<EOF\"}"
{}
```

`{}` is allow. The control matters more than the pass: an allow on its own
would be equally consistent with the handler being disabled or broken, so a
one-sided probe would have proved nothing.

This also settles attribution, which the timestamps alone could not. The daemon
started 12:03:44 and `utils.py` was last touched 12:14:08, so "is this process
running the fix?" was genuinely open. The PRE-fix tokeniser produces a *clean*
phantom for this exact shape (path followed by whitespace), that path exists,
and it contains deliberately-invalid Python — so old code would have DENIED.
Allowing it is only possible with the fix loaded.

Two schema/tooling notes worth keeping: PostToolUse rejected a payload without
`tool_response` (`input_validation_failed`) — boundary validation doing its job
— and the fixture itself was created by a heredoc that `lint_on_edit` denied,
which is Plan 00260 Task 3.5 working: the write landed, the denial was a report,
and that is exactly the fixture this probe needed.

A deliberate `restart` + `status` still follows for T3.1, so the pass is
recorded against a known build rather than one whose provenance was inferred.
