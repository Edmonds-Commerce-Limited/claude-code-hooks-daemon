## 10:52 · action · P1 — harness behaviour re-confirmed before building

Task 1.1 was a genuine go/no-go, not a formality: if the harness had started
enforcing read-before-overwrite, this plan should have been cancelled rather
than shipped. It has not. Reproduced twice under `bypassPermissions` — once
under `/tmp`, once inside the repository to rule out a project-scope confound.
Both times `Write` replaced an unread existing file and reported "has been
updated successfully", so the tool knew the file was there.

The `Write` tool description says the opposite: "Overwriting an existing file
you haven't Read will fail." That mismatch is what makes this a restoration of
a documented contract rather than a new rule agents have to learn.

## 10:58 · action · P2 — handler implemented, 18 tests

`write_clobber_guard`, priority 16, non-terminal. Tests cover the matcher
(existing+unread → fires; new path → does not; `Edit` → does not; no
`file_path` → does not), the session state (own-path read clears it, a
different path does not, another session's read does not), the handle
decisions, and both guidance/acceptance-test surfaces.

Two implementation notes worth keeping:

- The handler reads `tool_input["file_path"]` directly instead of going through
  `core.utils.get_file_path`, because that shared accessor returns `None` for
  anything that is not Write/Edit — which would make every `Read` invisible
  here. That is exactly the centralised blindness Plan 00260 Task 3.1b is
  about; this handler works around it rather than fixing it, since fixing it
  belongs to that plan.
- An ALLOWED `Write` still records the path. Without that, creating a file and
  rewriting it later in the same session would be blocked on the second write,
  which would be absurd.

## 11:02 · decision · T3.1 — priority 16 is load-bearing, not cosmetic

Recorded as Decision 3 in `PLAN.md`. 16 puts this behind the blocking safety
handlers (10-15) so a `Read` that one of them DENIES is never recorded as
knowledge of the file. A denied read never happened; treating it as knowledge
would hand the very next `Write` a clean clobber.

Non-terminal for the Plan 00241 reason: the handler ALLOWs on its common path,
and a terminal ALLOW ends the chain and silently disables everything behind it.
Most-restrictive-wins means a non-terminal DENY still denies, so terminality
would buy nothing and cost the rest of the chain.

## 11:06 · finding · T3.3 — verified live in BOTH directions

Unit tests do not prove a handler is wired. Restarted the daemon and probed the
real socket:

- `Write` to an unread 3-line file → DENIED, message naming
  `AT RISK: 3 lines, which would be replaced wholesale`.
- `Read` that same path, then the IDENTICAL `Write` → allowed.

The second half matters as much as the first. A deny-only check cannot tell a
working guard from one that blocks every write, and it is also the only proof
that the daemon delivers `Read` as a PreToolUse event at all — which is what
Task 1.2 asked for. Probe file removed afterwards.
