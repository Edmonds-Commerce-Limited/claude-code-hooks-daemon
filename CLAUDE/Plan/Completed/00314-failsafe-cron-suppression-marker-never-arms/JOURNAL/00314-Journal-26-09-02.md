Added `TestHumanBlockedMarker::test_live_0128_shape_writes_marker` in
`tests/unit/handlers/stop/test_auto_continue_stop.py`, driving
`AutoContinueStopHandler.handle` through a real JSONL transcript file (loaded

hand-built `TranscriptMessage`) with a single, freshly-timestamped assistant
entry whose text is:

```
STOPPING BECAUSE: failsafe cron tick delivered — nothing left to resume,
blocked only on human input (Plan 00312 live Ctrl+C test).
```

This reproduces the reported shape: an em-dash earlier in the sentence, the
pattern-1 phrase inside a parenthetical aside, `session_id` present. The test
**passes against current code** — the marker file exists afterwards with the
correct `session_id`. So the four named suspects were checked in turn:

- **`_resolve_current_turn_message` freshness resolution**: the entry is
  fresh (~0s old) and is the sole/last transcript line, so `complete=True`,
  `suspect_stale=False` — the fast path returns immediately, no polling
  involved. Even in the stale-tail branch, `_resolve_current_turn_message`'s
  documented fallback (`if complete: return msg`) means a genuinely final
  message is trusted even when nothing supersedes it during the poll, so this
  path is not a plausible silent-loss route either.
- **`_message_text` block concatenation**: `_parse_message_entry` joins
  multiple text blocks with `" "` into `TranscriptMessage.content`, and
  `AutoContinueStopHandler._message_text` independently joins
  `content_blocks` with `"\n"`. Both keep the full phrase contiguous when it
  lives inside one text block, which is the common case for a single final
  answer. Not reproduced as a break with one block; a phrase split exactly
  across two block boundaries would defeat the regex, but this is not
  something the field report's evidence (a Stop verdict log showing
  `auto-continue-stop allow`) lets us confirm or deny after the fact.
- **`session_id` field name in the Stop payload**: confirmed snake_case
  `session_id` end-to-end — `HookInputField.SESSION_ID = "session_id"`
  (`constants/protocol.py`), and `_maybe_record_human_blocked_marker` reads
  `hook_input.get("session_id")` directly (a literal, not the constant — a
  minor DRY gap fixed alongside T1.2, no behavioural effect). No
  camelCase/snake_case mismatch found on this path.
- **`ProjectContext` resolution inside the daemon process**: `ProjectContext`
  is a process-wide singleton initialised once at daemon startup
  (`initialize()`), not resolved per-request — so a Stop-time misresolution
  independent of daemon startup is not architecturally possible on this path.
