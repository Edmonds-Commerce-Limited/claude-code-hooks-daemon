The parse guard is generated, not hand-edited into the stubs. The stub templates live in install.py (four shapes: generic, Stop family, WorktreeCreate, status line) and are all rewritten by forwarder_generator.generate_forwarder_content, so the guard is one apply_init_parse_guard transform that runs for every event and is idempotent (strip then reapply). The relay hot path is inserted above the guard header, so a relayed hook never pays for bash -n. Per event answer: JSON events get {"systemMessage": ...} and exit 0; the status line prints a display line and exits 0; WorktreeCreate prints nothing on stdout and exits with its catalogue daemon_down_exit_code (1), because stdout there is parsed as a path. The bash -n diagnostic is captured into a variable and sent to stderr, never discarded.

Latency, measured over 200 runs on this host against the 3799-line .claude/init.sh: bash -n init.sh takes 10.4 ms per run against a 2.8 ms bash spawn floor, so about 7.6 ms of parsing plus roughly 1-2 ms for the command substitution fork. That cost applies only to hooks that miss the relay hot path (all Stop-family, status line, and any event with the relay off or no daemon socket); relayed hooks are unchanged.

Side effect: the old guarantee that a disabled-transport generation is byte-identical to its source no longer holds, since the parse guard is always on. Six tests in test_forwarder_generator.py, two in test_forwarder_generator_cli.py and one in test_transport_toggle.py were updated to expect the guarded form.
