## 03:10 · finding · P1 — measured before designing anything

Probed the handler directly rather than reasoning about the regexes. The first
probe was WRONG and worth recording: I called `matches()` and got True for all
four cases including unrelated prose, which would have "proved" the detector
fires on everything. `matches()` only gates on event shape; the detection is
entirely in `handle()`. Re-probed through `handle()`:

| message                                                       | fires | correct           |
| ------------------------------------------------------------- | ----- | ----------------- |
| `That is out of scope for this change.`                       | yes   | genuine deflect   |
| acknowledging the advisory, quoting the phrase                | yes   | FALSE POSITIVE    |
| `I called it out of scope; that was wrong, I will fix it ...` | yes   | FALSE POSITIVE    |
| `The registry gate covers one entry today.`                   | no    | correct           |

The lesson is the same one Plan 00224 hit: a probe that returns a plausible
answer is not the same as a probe that measures the right thing.

## 03:14 · decision · T2.1 — writing the cases out is what killed option 2

The plan filed four options and leaned toward option 1 "possibly with option 3".
Writing the row-3 case out side by side eliminated option 2 on grounds stronger
than risk — it is unavailable:

```
I called it out of scope because the release is tomorrow.   <- deflection
I called it out of scope; that was wrong.                   <- acknowledgement
```

Identical up to the following clause. A reporting-verb heuristic fires on both
or neither, so it cannot separate them at all; it can only trade noise for
silence. Option 3 died to a similar counter-example: "The hook flagged the test
failure, but that is out of scope" both names the daemon AND deflects.

So option 1 alone, and row 3 stays flagged. Recorded as accepted, not missed.

## 03:22 · finding · T3.1 — the generalisation is a security regression

The obvious DBF move is to apply the new helper to every content scanner. That
would be wrong, and the reason is worth keeping: `sensitive_content` and
`security_antipattern` scan the same way, but a secret inside quotation marks
is still a secret and a dangerous construct inside a quoted string still
executes. Blanking quoted spans there is a one-character bypass.

What separates the groups is the COST OF A MISS, not the shape of the scanner —
one advisory line versus a leaked secret. Decision 2 records it so the
duplication is not "helpfully" removed later.
