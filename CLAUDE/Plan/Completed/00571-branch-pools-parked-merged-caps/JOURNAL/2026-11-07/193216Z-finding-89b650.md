## 19:32 · finding · —   — --clean would remove a live agent's worktree; fixed (Task 2.8)

Dogfooding `branch-sweep --clean --remote --dry-run` before the release turned up a destructive defect. The run planned to remove the isolation worktree `.claude/worktrees/agent-a8170e91f8de02090-f549a059`, together with its branch, while that sub-agent was still running. A freshly spawned isolation worktree sits at main's tip with a clean tree, so containment reads it as merged and `worktree_blockers` finds nothing to keep. Nothing locks it, and it has no work-queue record.

Task 2.8 adds `core/agent_ownership.py`. It skips the worktree and branch, locally and on the remote, if any of three signals holds:

- a `running` work-queue record names the branch or worktree;
- the worktree sits under `.claude/worktrees/`, which only `--clean` checks (`worktree-reap` exists to reap those itself);
- git reports the worktree locked.

`worktree-reap` had the same flaw for queue-running and locked worktrees, and it is fixed too. `delete-branch` already refuses a branch checked out in a worktree.

The fix merged to main at 4a386134e together with Plan 00572 Task 1.5, after integration QA passed 42/42. Release note 005 records the new behaviour. One follow-up was folded into Task 2.7: `branch_stop_gate` should reuse `running_holds`.
