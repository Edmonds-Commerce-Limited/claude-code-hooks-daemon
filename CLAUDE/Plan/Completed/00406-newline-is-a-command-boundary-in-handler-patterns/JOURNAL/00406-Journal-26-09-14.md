## 18:33 · finding · P1 — the &&-control is what makes these falsifiable

Worth stating once, because it separates these four sites from a tuning
argument, and it is the shape Task 3.1 should encode.

Each was confirmed by running the SAME two commands twice — joined with a
newline, and joined with `&&` — against the handler's own `matches()`. The
verdicts differ. Both spellings are the same shell structure, so no policy
can want opposite answers for them; the disagreement is an implementation
fact and settles the question without any judgement about how aggressive a
guard ought to be.

That mattered because the opposing framing was available and is wrong: "a
guard that over-blocks is erring safe". It is not erring safe when it denies
`git branch -d` — the delete this project's own rules table prescribes
INSTEAD of `-D` — nor when it denies precisely what its own deny message
tells the reader to do instead.
