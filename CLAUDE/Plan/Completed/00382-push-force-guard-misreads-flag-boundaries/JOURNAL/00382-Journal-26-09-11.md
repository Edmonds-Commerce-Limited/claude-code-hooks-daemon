The current pattern is wrong in BOTH directions, and only one direction was

command is worse than one that over-matches, so that half is the more serious
find even though nobody complained about it.

## 16:29 · decision · P2 — two flag syntaxes, two rules

The fix does NOT put one `(?<!\S)` in front of a shared group, because long and
short options need different treatment:

- LONG is forceful only when exactly `--force` / `--force-with-lease`. Matching
  a prefix would catch `--follow-tags`; dropping the leading guard would catch
  `--no-force-with-lease`, which negates the lease.
- SHORT is any single-dash token containing `f`, whatever rides with it —
  `(?<!\S)-(?!-)[A-Za-z0-9]*f[A-Za-z0-9]*\b`. The `(?!-)` keeps this branch off
  long options.

RED first, and it was worth doing: 8 failures, not the 3 the issue describes —
the extra ones were `ends-in-f` (a trailing `-f` in a branch name, which the
report does not mention) and the four grouped flags. `--no-force-with-lease`
PASSED before the fix, so that test records existing correct behaviour rather
than a repair; I had assumed it was broken and checked instead of writing that
down.

After: 134 passed in the handler's own file, 799 across the wider
destructive/safety/evasion selection, and the comparison probe reports the live
pattern at 0 wrong on all 14 cases.
