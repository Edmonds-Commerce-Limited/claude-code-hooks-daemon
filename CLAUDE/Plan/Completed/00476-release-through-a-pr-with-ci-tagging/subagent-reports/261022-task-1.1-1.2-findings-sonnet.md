### Correction to the brief: the trial workflow already started the daemon

The trial workflow already ran qa.yml's daemon step for every check (identical
text: `HOOKS_DAEMON_RELEASE_GATE=1`, `hooks-daemon.env`, `restart`, `status`).
The `tests` log shows it working at job start: `Daemon: RUNNING`, socket
`untracked/daemon-runnervmxehtw.sock (exists)`, 31/31 listeners. So "no daemon
was started" is not the cause, and copying the step again would change nothing.

### Actual cause (established from the code, not yet confirmed by a run)

- `.claude/hooks-daemon.yaml` sets `daemon.idle_timeout_seconds: 600`.
- Any connection to the socket counts as activity (`server.py` sets
  `last_activity` per accepted connection); the suite makes none until it reaches
  the acceptance tests.
- The 10 skipped gates ran when the daemon was long gone (the primary run lasted
  5814 s). `conftest._discover_socket` needs a socket that accepts a connection,
  so a stale socket file reads as "no live socket found".
- `run_test_matrix.py` already knows this: for each extra interpreter's serial
  `rest` run it restarts an idled-out daemon first. The PRIMARY interpreter's run
  has no such restart. That is why only `py3.13 full` errored, and `py3.11 rest`
  and `py3.12 rest` (0 errored) did not.

Fix made in `.github/workflows/full-gate-trial.yml`: for the `tests` check only,
a background step connects to the socket every 60 s (which defeats the idle
timeout) and runs `bin/hooks-daemon start` if no live socket answers. The re-run
will show whether it holds.

### The eleventh error, test_forwarder_socket_stdin

The failure is the doc-write jail: "tried to write a tracked generated doc of a
checkout of this repository". The daemon rewrites the generated handler guidance
in CLAUDE.md when it starts (the repo history carries "Auto: hooks daemon
regenerated CLAUDE.md" commits). The test spawns the real deployed forwarder; a
forwarder that finds no live daemon auto-starts one, and that start writes the
tracked doc, which the jail refuses. That is consistent with the idled-out
daemon, so it is PROBABLY explained by the same cause. It is not proven: I did
not find the write path in the log, and only the `py3.13` primary run (the one
that outlived the daemon) failed. If the keepalive re-run still fails this test
with the daemon alive, treat it as a separate runner-specific defect to
investigate (candidates: the venv-metadata warning below, or the forwarder
starting a second daemon).

## Task 2.1 job design proposal

Principles: one runner per leg so nothing contends; the `rest` legs need a live
daemon and relay, so each gets its own daemon step plus the keepalive; the 42
fast checks need almost nothing and should not pay 42 setup floors.

1. `static` job (one runner, one setup): the cheap code checks, one `llm_qa.py`
   call per check so each still reports its own result: magic_values, format,
   lint, type_check, security, dependencies, error_hiding, inline_suppressions,
   canonical_callers, python_var_guidance, eacces_safe, authored_path_stat,
   install_mode_marker, signal_targets, skip_list_substring,
   unreachable_handle_branch, declared_invariant_pairs, fail_open_inventory,
   dangerous_invocation_corpus, security_downgrade_flags, capture_corruption.
   About 21 checks; measured work in the table sums to roughly 600 s including
   one setup floor per check, so one shared setup lands near 300 s.
2. `pyright` job alone (118 s), so the slowest static check does not extend the
   group.
3. `docs` job: shell_check (needs apt shellcheck), shell_audit, skill_refs,
   github_urls, released_changelog, repo_hygiene, doc_truth, doc_snippets,
   plan_qa, docs_qa, sensitive_content, git_history, handler_reference,
   generated_doc_drift, british_english, semgrep. Table sum near 380 s.
4. `contracts` job (daemon plus relay): hook_contract, input_contract,
   project_handlers, smoke_test. Table sum near 106 s.
5. Tests, six runners instead of one: for each Python in {3.11, 3.12, 3.13}, a
   `unit` job (tests/unit) and a `rest` job (tests/ minus unit; needs daemon,
   relay and the keepalive). 3.13 is the coverage primary; its legs each write a
   coverage data file, uploaded as artifacts and combined in a final `coverage`
   job that applies `--cov-fail-under=95` (the shard and `LegCheckpoints` logic
   in `run_test_matrix.py` already combines per-shard data; reuse it).
6. A final `gate` job that `needs:` all of the above and is the single required
   check.

Predicted wall clock: the longest leg is `rest` at 2303 to 2392 s (measured with
the serial phase uncontended), so roughly 2400 to 2600 s with setup, against the
10544 s single job. The unit legs measured about 1800 s under contention and will
be faster alone.

Further reduction if that is still too slow: `scripts/qa/test_shards.yaml` already
defines shards. Splitting `rest` into two or three shards per Python brings the
longest leg toward 1200 s, bounded below by the single ~400 s
`test_suite_passes_on_a_released_unreleased_tree` test. Giving that test its own
shard and the hostile-input performance file its own shard lets the remaining
shards finish near 600 s.

Cost: six test runners plus four small jobs instead of 43 small ones. Total
runner time is about the same as the single job (the same tests run once per
Python), but the 42 per-check setup floors (17 to 25 s each) shrink to four.
