## 09:40 · finding · T1.3 — the field-report indicator is downgrade_indicator, not model_fallback_detector

Read the daemon source before trusting the task description's name.
`model_fallback_detector` only ever fires from the PLATFORM's own
`model_refusal_fallback` transcript record — there is no such record for a
manual `/model` command, so it could never have been the thing that fired
in the owner's field report. The actual culprit is the status-line
`downgrade_indicator` handler (`handlers/status_line/downgrade_indicator.py`
+ `downgrade_state.py`): it self-detects a rank drop purely from the model
id Claude Code reports on every render, per session, against a stored
high-water mark — with no awareness of WHY the drop happened. Redirected
Task 1.3 to that handler instead.

## 10:05 · decision · P1/P2 — design

- Host tier (`_forward_io`/`HumanInputLine`) now recognises a submitted
  `/model <family>` or `/effort <level>` line the same way it already
  recognised `/compact` (edge-triggered, consume-once).
- Worker tier (`CompactStateMachine`) tracks the last typed `/model`
  command with a 120s validity window (`_MANUAL_MODEL_WINDOW_SECONDS`). A
  rank-drop observation matching it never opens a downgrade episode (no
  auto-restore, no forced xhigh floor) and clears any stale episode already
  open for the session — the manual choice wins outright. The reason is
  logged via `noop_reason_log` ("manual change (<family>) — no restore").
- The same manual `/model` command also writes a small shared marker
  (`{daemon_untracked_dir}/manual-model-changes/<session>.json`) so the
  daemon-side `downgrade_indicator` can independently suppress itself for
  the identical choice, even though it runs in a different process with no
  visibility into the supervisor's own state.
- A manual `/effort <level>` is a latch (`_manual_effort_active`), not
  time-windowed: it suppresses both the per-model default floor and the
  post-`/model`-switch coupled effort until the user manually changes model
  again or manually re-sets effort — matching the owner's ruling that the
  coupling is a liked feature whose PRECEDENCE was wrong, not the feature
  itself.
