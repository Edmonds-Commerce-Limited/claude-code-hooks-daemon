## 01:57 · finding · P7 — "the whole phase is human-gated" was hiding a task

The goal ledger flagged this plan as still owed. My working note said Phase 7
is only `/release` and therefore blocked on a human. That was too broad, and
the plan's own preamble said the same thing — "this phase cannot be executed by
an agent".

It is true of Task 7.1 (run `/release`) and 7.2 (release notes, which the
release generates). It is NOT true of Task 7.3, which writes a document into
`CLAUDE/UPGRADES/UNRELEASED/post-upgrade-tasks/`. The release skill MOVES that
directory's contents at release time, so authoring an entry is preparation FOR
a release rather than the performing of one.

That directory contained only its README, so the task had never been done. A
blanket statement about a phase had made an authorable task invisible for as
long as the plan has been sitting in this state.

**The lesson is about the shape of the claim, not this plan.** "This phase is
blocked" is a claim about every task under it, and it only takes one task that
does not fit for the statement to start concealing work. Phase-level gating
notes should name the tasks they cover.

## 01:57 · action · T7.3 — post-upgrade task written

`01-drop-hooks-daemon-python-workaround.md`, plus the README task index.

The content follows from the host-a field report: discovery used to compare
against a hardcoded candidate list (`python3.11/12/13`), so a host with
`python3` at 3.9 alongside `python3.13` and `python3.14` aborted, and the only
way through was `HOOKS_DAEMON_PYTHON=python3.13` by hand. Discovery now
enumerates every `python3.NN` on PATH, filters to the floor and takes the
highest, so that host resolves 3.14 unaided.

**The task deliberately does not say "remove the override".** A deliberate pin
and a stale workaround look identical from the variable's value, and removing a
deliberate pin would move the venv to an interpreter the operator did not
choose. So the branch where discovery finds a DIFFERENT interpreter routes to
the user instead of acting. `HOOKS_DAEMON_PYTHON` remains supported — this is a
redundancy notice, not a deprecation.

Two smaller points that are easy to get wrong and are called out in the file: a
bare `python3` with no `.NN` suffix is deliberately not matched by the glob, so
"discovery finds nothing" is a real outcome on a host that does have a modern
interpreter under that one name; and removing the override changes which
interpreter builds the venv, so the venv wants re-provisioning rather than
being left in place.
