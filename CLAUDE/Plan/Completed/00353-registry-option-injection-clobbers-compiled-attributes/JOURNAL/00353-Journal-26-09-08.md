## 09:12 · finding · — — the incoming report's diagnosis holds in full

Verified every claim in the field report against the code before accepting it.
All of it stands: `instance = attr()` constructs bare; the per-option
`setattr(instance, f"_{option_key}", option_value)` loop runs afterwards and
overwrites; `PipeBlockerHandler.__init__` compiles `extra_whitelist` from an
`options` argument production never passes; `_matches_whitelist` then calls
`.search` on a `str`.

The one thing the report understated is which half of the constructor is the
bug. `_extra_blacklist` was initialised from the same dead `options.get(...)`
call and works fine — because it stored the value *verbatim* and its consumer
takes strings. So the fatal ingredient is not "reads options", it is
"transforms an option into an attribute the injection is about to overwrite".
Both siblings were written the same way; only one had a type mismatch waiting
for it.

## 09:20 · finding · — — the blast radius is exactly one attribute

Wrote a static audit (AST over all 121 handler modules) rather than trusting a
runtime scan. A runtime scan is useless here and it is worth recording why: an
unconfigured `[re.compile(p) for p in ...]` evaluates to `[]`, which is
indistinguishable from a raw empty list. The first attempt reported zero
findings for exactly that reason.

The static pass classifies each `self._X = <expr>` in `__init__` as verbatim
store vs transformation, and intersects with option keys harvested from the
module's own `options.get`/`getattr` reads, its `Configuration options:`
docstring block, and every key under an `options:` block in the repo's YAML.

```
handler modules scanned: 121
CLOBBERABLE TRANSFORMED ATTRIBUTES: 1
  pre_tool_use/pipe_blocker.PipeBlockerHandler: option 'extra_whitelist'
LATENT (transformed, but name is not a config key): 97
```

`pipe_blocker` is also the only constructor in the tree that reads its
`options` argument at all. `gh_issue_comments` and `gh_pr_comments` declare the
parameter and never touch it.

## 09:35 · decision · — — fix the handler, not the registry

The owner's prior was that the registry contract is what is actually broken and
a per-handler lazy compile only treats a symptom. Weighed it and landed the
other way, on evidence rather than on risk appetite.

The registry-side fix cannot be written. To "skip options the constructor
already consumed" the registry must know which *keys* a constructor reads.
Options are free-form — no per-handler schema exists anywhere — and a signature
discloses only that a `dict` is accepted. The one implementable approximation
("pass merged options to any constructor that takes them, skip the loop for
it") trades this bug for a worse one: the handler would then also swallow
`workspace_root`, `exclude_paths`, `_project_layout` and every future
cross-cutting injection it does not handle, and those would stop arriving
silently.

And the contract is not in fact broken: 120 of 121 modules honour it without
difficulty. What is broken is one handler implementing a *second*, phantom
contract the registry has never called.

So: handler-side fix, plus the generalisation the owner was really after — a
repo-wide invariant test that forbids the mechanism, so this cannot come back
quietly. That gets the "registry contract is the real problem" instinct
enforced, without changing the shared code path every handler depends on.

The report's third option (a type guard raising a clearer error) is rejected as
a destination: an actionable `TypeError` is still a handler that fails open on
every piped command. Its useful half — self-heal by compiling on the fly — is
the chosen fix, not a guard.

## 10:10 · action · T2.1–T2.4 — GREEN

`_extra_whitelist`/`_extra_blacklist` now hold raw `list[str]`; compilation
moved to a module-level cache keyed on the source string, following the
`_compiled_public_pattern` idiom already in `sensitive_content.py`. An

`re.search(pattern_str, ...)` loop from `_matches_blacklist`.

Dropped the `options` parameter entirely rather than leaving it inert: a
parameter that silently ignores what the caller passed is worse than one that
does not exist.

Seven tests in `test_pipe_blocker_comprehensive.py` and one integration test
constructed the handler with `options=`. All repointed onto the injection shape
via a `_configured(**options)` helper. Worth noting for the record: the
integration test named `test_extra_whitelist_allows_custom_command` passed green
for the entire life of this defect, because it exercised the one path
production never takes.

## 10:25 · finding · P3 — the debug_info.py bug is one guard away

`python_cmd = paths.get("PYTHON_CMD", "")`, then
`if not Path(python_cmd).exists()`. Confirmed empirically:

```
Path(empty) == PosixPath('.')
Path(empty).exists() == True
subprocess.run(['', ...]) raised: PermissionError: [Errno 13] Permission denied: ''
```

`Path("")` is the current directory, which always exists — so a blank
`PYTHON_CMD` sails past the guard and every section that shells out to the
interpreter reports `Permission denied: ''` in place of the real problem. Small
enough to fix in this plan rather than file separately. Reproduced with a real
`init.sh` that resolves no interpreter; no monkeypatching needed.
