## 12:38 · finding · — the report asserts an omission its own roster contradicts

The report's standing caveat says, unconditionally:

> Status-line renders are not recorded and status handlers are omitted from
> the roster below

and then lists thirteen `status-*` handlers at the top of that very roster,
~1,520 records each. A reader is told a fact the next paragraph disproves.

Measured rather than assumed:

- 19,750 of the 26,676 retained records (74.0%) carry `"event": "Status"`.
- Every one of them falls inside a single 30-minute window,
  2026-08-13T17:36:25 → 2026-08-13T18:06:21.
- Zero Status records since. The most recent records are ordinary PreToolUse
  decisions.

So the WRITER is correct: Plan 00234's exclusion works, and
`verdict_log.py:153` drops Status events unless `record_status_events` is set
(this project sets no `verdict_log` block at all, so it defaults off). The log
is a rolling 10 MiB window and has not yet trimmed far enough to evict records
written *before* that exclusion landed.

The defect is in the READER. Two enumeration surfaces disagree:

- `cli.py:_behavioural_handler_names` drops Status renderers from the
  **registered** side, so they cannot pollute never-fired.
- `verdict_report.aggregate_verdicts` kept them on the **fired** side.

That is the same class Plan 00237 closed in the registry and Plan 00234 closed
in the writer, reappearing in the report.

## 12:39 · finding · — the override rate is understated roughly fourfold

Not cosmetic. `override_rate` divides by every retained record, so 74% of the
denominator is renders that can never carry an override at all:

| denominator          | records | overrides | rate  |
| -------------------- | ------- | --------- | ----- |
| whole retained window | 26,676  | 19        | 0.1%  |
| behavioural only      | 6,926   | 19        | 0.3%  |

The override rate is described in this plan's own module docstring as "the
strongest available signal that a rule is mis-tuned". Reporting it ~4x low is
a defect in the one number the feature exists to produce.

## 12:39 · decision · — name what is set aside; never drop it silently

Three options considered:

1. **Make the caveat true by deleting the sentence.** Rejected: the sentence
   describes a real and correct policy; the roster is what disagrees with it.
2. **Silently exclude Status records from everything.** Rejected — this is the
   silent-narrowing failure the project rails against. Three quarters of the
   window would vanish and the remainder would read as freshly collected.
3. **Partition and SAY SO.** Chosen. Status renders leave the roster and the
   override denominator (matching the never-fired side, and correcting the
   rate), stay counted in the retained total, and the report gains an explicit
   block naming how many were set aside, over what date range, and why.

## 13:05 · decision · T3.1 — closed as superseded, not implemented

Task 3.1 asked to skip the output-keyword advisory when the trigger word also
appears in the COMMAND string. There is nothing left to skip: a scout confirmed
`bash_error_detector` was DELETED outright by Plan 00237 (commit `f782d0a28`,
handler and its 384-line test file both removed). Only a stale
`__pycache__/bash_error_detector.cpython-311.pyc` from April survives, beside
two other orphans of the same vintage — that directory is simply never pruned.

The retirement note records the evidence, and it came from the verdict log THIS
plan built: 274 fires, 45% of all behavioural handler activity, `allow=274` —
it never once restricted anything, and substring matching meant a filename
containing "error" in an `ls` listing tripped it. Removing it solved §2
completely rather than narrowing it, which is the better outcome. Recorded
rather than quietly ticked, because "done" and "no longer applicable" are
different states and the plan should say which.

Worth noting for accuracy: the scout also found the retirement note itself
slightly tangled on the mechanism — it says the handler self-triggered "because
the string `bash-error-detector` contains 'error'", but the deleted code
scanned `stdout + stderr` ONLY (`combined_output` at its line 67) and read the
command purely to echo it back. So the self-trigger was its own NAME appearing
in another tool's output, not a command-string match. The retirement stands
either way.

## 13:07 · decision · T3.5 — extend the existing guard, do not write a new one

`scripts/qa/check_handler_reference.py` already checks exactly this class —
copy-pasteable YAML naming a handler that does not exist — and was itself built
under DBF for that reason. It simply saw ONE surface. Added
`example-config-phantom-handler` so it sees both, reusing the same
`GroundTruth` (handler ids from `constants/handlers.py` UNION the live
registry).

Parsed by indentation rather than with a YAML loader, deliberately: the file is
a commented TEMPLATE and the comments are half its value. A loader discards
them, and round-tripping to report an accurate line number would mean taking a
comment-preserving parser dependency for one rule.

Scoped to the copy-pasteable surface only. Prose docs legitimately name retired
handlers — `CHANGELOG.md`, `RELEASES/`, `UPGRADES/` and archived plans are the
RECORD of the removal — so a rule that flagged every mention would be wrong and
would be switched off within a day.

## 13:20 · finding · — a stale hardcoded list was holding a false claim in place

Removing the phantoms emptied three event sections (`session_end`,
`notification`, `subagent_stop`), so those were removed too — the handler
package ships ZERO modules for each. That broke
`test_example_config_all_events_covered`, which asserted eleven hardcoded event
types must be present.

The test was not protecting anything real any more: it demanded sections the
example config could satisfy only with a phantom handler or an empty key. A
stale list was actively keeping a false claim alive.

Replaced with a derivation — event directories under `handlers/` that contain
at least one module, intersected with the declared `EventID` registry. The
intersection matters both ways: it drops `nitpick` (a pseudo-event) and `utils`
(shared code), and it cannot invent an event the registry does not declare.
Paired with a new opposite-direction test so the check discriminates rather
than merely fires. Derived set measured as exactly the ten live events.
