## Phase 1 regression found by dogfooding — length alone is not evidence of prose

Caught live in the coordinator session, not by a test. A perfectly ordinary
command was denied with the Phase 1 *prose* reason:

```
git merge-tree --write-tree --name-only main agent-ad3d35fcc36d13959-4c36fb42 2>&1
```

That producer segment is 82 characters, and
`_MAX_SOURCE_SEGMENT_CHARS_FOR_TEMPLATE` is 80, so `_looks_like_prose()`
returned True on the length trigger alone. The deny was *correct*
(`git merge-tree` is not whitelisted) but the reason shown was wrong in a way
that costs a turn:

- it withheld the matched text, so there was nothing to act on;
- it withheld the `extra_whitelist` remediation a real command deserves;
- it ended with "IF THIS WAS PROSE … no action needed beyond retrying", which
  is actively FALSE for a real command — retrying identically re-blocks.

**Why the heuristic is wrong, not merely mistuned.** The length trigger is
`>80 chars ⇒ prose`, with no corroborating evidence. In this repository an
82-char command is unremarkable: worktree branch names alone are 32 characters,
and absolute paths under `/workspace/...` are long by construction. So the
trigger fires on the *normal* case. Raising 80 to 120 would only move the
boundary and guarantee a recurrence — the defect is that length is being used
as sufficient evidence rather than supporting evidence.

Note also that the stated justification for the length trigger — not
re-quoting a huge amount of text — was **already discharged separately** by
Task 1.3's `_MAX_ECHOED_COMMAND_CHARS = 500` truncation, which is applied
uniformly on every path. So length is doing no work for context economy here;
it is only doing (bad) work for classification.

**DBF — what guard should have caught this, and why it didn't.** The Phase 1
tests exercised the length trigger only in the direction that confirms it:
long prose is classified as prose. Nothing ever asked the inverse question,
*are there long strings that are real commands?* — which in this codebase is
routine rather than exotic. A test that only confirms the intended direction
of a heuristic cannot discover that the heuristic is over-broad; it is the
same shape as the characterisation-vs-requirement failure recorded in
LESSONS.md. The fix therefore has to include the inverse-direction test, or
the next tuning of the constant re-opens the hole.

Fix is Phase 4, taken in the coordinator session with the rest of the
dogfooding queue.

## Phase 4 delivered

**The replacement signal.** Length is gone as a trigger. Prose is now
identified by function-word DENSITY: English runs 30-50% closed-class words,
argv runs 0%. The field case scores 0% across 7 tokens; the Phase 1 long-prose
fixture scores ~40% across 42. One qualifier: a token OPENING with a quote
vetoes the ratio, because that is the one place English legitimately lives
inside a real command — `echo "this is a test"` is 60% function words and
entirely executable. Tested on the opening character rather than by
containment, so an apostrophe inside a word ("doesn't") does not read as
quoting and accidentally exempt genuine prose. A minimum token count stops the
ratio being computed on samples too small to mean anything (`cat a` is 50%
function words on a sample of two).

**The Phase 1 test that pinned the false premise.**
`TestSaneLengthTriggerAlsoSkipsTemplating` asserted the right outcome for the
wrong reason: its fixture ("grep is a tool but this whole sentence…") really
is prose, so the assertion held, but the stated rule — "a very long matched
segment is still not a real shell command" — is false, and it is the rule a
future reader generalises from. The fixture is retained unchanged and only the
claimed reason corrected; the class is renamed to say what is actually being
tested. This is the second instance today of the same failure shape already in
LESSONS.md: a test that restates the implementation rather than the
requirement makes a defect look deliberate and covered.

**Verification.** Not unit tests alone: the daemon was restarted and all three
cases driven through the PRODUCTION forwarder `.claude/hooks/pre-tool-use`,
after a hand-rolled socket probe returned six false `allow` results earlier in
this session. Live results — the 82-char real command now gets remediation and
not the prose reason; the field-report heredoc still gets the prose reason;
short unknown commands are unchanged.

**A defect in the fix itself, caught by probing rather than by assuming.**
The quote veto originally tested only whether a token BEGAN with a quote.
Before asserting that in a test, the branch was probed against real
non-whitelisted producers — and the second one failed:

```
docker run --name "the box that is in the room" ubuntu     -> correct
kubectl annotate pod x note="this is the thing that broke"  -> PROSE (wrong)
```

The quote in `note="this` is mid-token, so `startswith` missed it; density
then scored the command 36% English and classified a real command as prose.
That is a narrower instance of the exact defect being fixed, and it would
have shipped had the branch been asserted instead of exercised. The veto now
matches both shapes — an opening quote and a quoted assignment — and both
cases are pinned as tests.

Two details made the probe informative rather than misleading. First, the
initial fixtures (`echo`, `grep`, `cat`, `ls`) are all WHITELISTED, so
`matches()` is False and production never routes them to `handle()` at all:
they exercised nothing, and only reporting `matches()` alongside the result
revealed it. Second, calling `handle()` directly reports `deny` for those
same whitelisted producers, which reads like a real block and is purely an
artifact of bypassing the gate. Both traps are the same one recorded in
LESSONS.md — verify through the production entry point.

**Scope note.** `get_claude_md()` carried the same false rule ("implausibly
long … the block reason is short"), so every project running this daemon was
told length decides. Corrected, with an explicit statement that a long command
is still a command and that seeing the prose reason for real command text is a
bug worth reporting rather than something to retry.
