## 18:13 · finding · T1.1/T1.2 — the filed bug, reproduced before fixing it

Built the scenario by hand before touching code: a branch `feat` tracking
`origin/feat`, plus a TAG also called `feat`. Both listings come back prefixed,
and the command the advisory hands the human is the one that fails:

```
for-each-ref %(refname:short)  -> 'heads/feat\x1forigin/feat\nmain\x1forigin/main\n'
branch --merged main %(...:short) -> 'heads/feat\nmain\n'
git branch -d heads/feat  -> 1  "error: branch 'heads/feat' not found."
git branch -d feat        -> 0  'Deleted branch feat (was b965360).'
```

So the impact is not "a slightly odd label". The advisory renders
``safe to remove: `git branch -d heads/feat` `` and that command cannot work.
Three RED tests written against this, including one that runs the offered
command rather than asserting on the string — the string is the symptom, the
failing command is the defect.

## 18:13 · finding · T1.3 — the sweep found something worse than the filed bug

Task 1.3 asked me to check the rest of the module for listings compared against
another source. The listings were fine (both sides now read `%(refname)`; the
UPSTREAM stays short on purpose because it is compared against the short refs
`git remote prune --dry-run` prints). But the BASE those listings are measured
against is a bare name from `default_branch`, and that is not a naming problem —
it is a wrong safety verdict:

```
truth: feature has a unique commit, so it is NOT merged into refs/heads/main
with a tag 'main' pointing at feature:
  branch --merged main            -> 'refs/heads/feature\nrefs/heads/main\n'   <- WRONG
                                     warning: refname 'main' is ambiguous.
  branch --merged refs/heads/main -> 'refs/heads/main\n'                       <- right
```

A branch holding commits nobody else has gets reported merged, and the advisory
then offers to delete it. Filed as Task 1.4 and fixed rather than noted: this is
the same root defect in the same function I was already editing.

The fix could not be a blind `branch_ref(base)`. Probed the case where
`default_branch` names a branch read from `origin/HEAD` that was never checked
out locally:

```
bare  'main'            -> rc=0
full  'refs/heads/main' -> rc=128 fatal: malformed object name
```

So `_merged_base_ref` qualifies only when `show-ref --verify` says the local
branch exists, and falls back otherwise — probed exactly the way
`default_branch` probes its own fallback candidates.

## 18:13 · decision · P2 — the guard question, answered on evidence

Refused the guard the plan proposed (reject bare branch names in git argv) and
built a different one. The reason is measurable rather than aesthetic: all 12
real call sites across 00254 and 00255 pass a VARIABLE (`base`, `name`, `rev`),
so a syntactic rule sees an identifier and knows nothing. That guard would have
caught zero of the defects it was written for, while firing on the hardcoded
literals that are already correct — and a guard like that is switched off within
a day.

What IS mechanically checkable is the read side: `%(refname:short)` in a git
format string, with a named replacement to point at. Written as
`scripts/qa/semgrep/short-refname.yaml` (the runner picks up any `*.yaml` there
with no wiring). Validated four ways before accepting it, because a guard nobody
tested is just a comment:

- 4/4 probe shapes flagged, including the `fmt = "..."` deferred form
- the docstrings that DESCRIBE this defect are NOT flagged — that was the whole
  reason for matching a bound metavariable instead of a raw `pattern-regex`
- both real pre-fix `git_sync.py` sites flagged, at 437 and 459
- current tree clean across 388 files

Two corrections came out of that validation. First, an early run reported zero
against the pre-fix source and I nearly concluded the rule was broken — semgrep
was applying gitignore rules to a directory walk under `untracked/`; naming the
file explicitly gave the real answer. Second, every hit was reported twice
because `$X = $STR` was binding whole multi-line call expressions whose source
text merely contained the substring. Anchoring the regex at an opening quote
makes `$STR` genuinely a string literal, and the duplicates went away.

The rule states its own scope in its header: it covers the READ side only. The
write side is covered by behaviour tests that shadow a branch with a same-named
tag, and saying so beats letting a future reader assume the gate is total.

## 18:35 · finding · T1.4 — a self-review found the fix under-tested

Before committing I asked which test would fail if someone later "simplified"
`_merged_base_ref` to a blind `branch_ref(base)`. The answer was NONE: every
real-repo test has a local `main` so the qualified path is taken, and the
`_DispatchGit` fakes stub `_run_git` wholesale. The fallback — the half of the
fix that stops it breaking repos whose default branch was read from
`origin/HEAD` — was covered only by accident.

Replaced a near-duplicate happy-path test with two direct assertions on
`_merged_base_ref`, then mutated the source to check they are load-bearing
rather than decorative:

```
fallback deleted (always qualify) -> 1 failed, 47 passed
fix removed (always bare)         -> 2 failed, 46 passed
```

Exactly the predicted counts. A first attempt at this reported "exit=1" for both
mutants and I nearly recorded it as proof — it had used `sys.executable`, the
system python, where pytest is not installed, so the failure was the harness and
not the mutant. Re-ran with the resolved venv interpreter. Worth remembering that
an exit code alone is not evidence a test failed; the summary line is.

## 18:35 · decision · T1b.1 — a comment deliberately not re-added

The extraction removed a comment on `_HEADS_PREFIX` making a point the new
`git_repo.branch_ref` docstring does not: that a bare name would leave the
moved-tip guard *silently inert*, failing in exactly the case it exists for.
Considered re-adding it at the `tip_moved_since_proof` call site and decided not

intent by name, and the rule now lives in the docstring of the function that
embodies it — a comment explaining why you called a function called `branch_ref`
is noise. Recording the decision here so it is a choice rather than a silent
loss.
