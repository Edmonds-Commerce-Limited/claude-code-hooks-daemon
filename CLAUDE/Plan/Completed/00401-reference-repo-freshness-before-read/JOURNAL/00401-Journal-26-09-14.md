## 12:24 · action · T1.1 — discovery.py, 23 tests, 100% coverage

Two boundaries carry the design, and both were written as tests first:

- A checkout is a `.git` of EITHER kind. A worktree and a submodule carry a
  `.git` FILE, so an `is_dir()` test would silently skip exactly the checkouts a
  multi-worktree workflow produces.
- The walk is depth-bounded and a non-positive bound finds NOTHING. A root is
  configuration and configuration can say `/`; failing closed on a nonsense
  value is what keeps a typo from becoming a filesystem-wide walk.

## 12:30 · decision · T1.2 — three small deviations from the drafted task, each deliberate

1. **`inspection.py`, not `inspect.py`.** The draft named it after the concept,
   but that filename shadows a standard-library module much of the ecosystem
   imports. Matching a draft filename is not worth that.
2. **`RepoState` carries no enforcement policy.** Three surfaces consume it and
   only ONE of them blocks, so a `should_block` property would bake the
   PreToolUse handler's configurable mode into a value the CLI and the sweep
   also read. It exposes facts and derived predicates; policy lives in Phase 4.
3. **`git_sync._remotes` promoted to public `remotes()`.** Needed to separate
   `NO_REMOTE` from `NO_UPSTREAM`. Both are uncomparable in an ahead/behind
   sense, so it would have been easy to collapse them — but the remedies differ
   (`git remote add` versus `git branch -u`), and a report that conflates them
   tells the reader to run the wrong command. Only two call sites, both inside
   `git_sync`, so the rename was contained; four tests cover the new contract.

## 12:33 · finding · T1.2 — the architecture is now a test, not a comment

`test_inspection_never_performs_network_io` patches `fetch_all` and
`pull_ff_only` to raise, so any future change that "helpfully" adds a fetch to
the inspection path fails there and nowhere else. A paired test asserts the
consequence honestly: a commit pushed to origin is INVISIBLE until something
fetches, so freshness means "fresh as of the last fetch". That is why the cache
feeding PreToolUse needs a TTL and why a missing or expired entry must read as
NOT VERIFIED rather than as fresh (Task 1.4).

The canary case is covered too: an origin set to `https://invalid.invalid/` still
classifies as CHECKABLE and demands no attention, because nothing contacts it.
A design that reached out would stall there for the whole fetch timeout.

## 13:40 · finding · P4-P6 — the two defects only RUNNING it could find

Both were invisible to a green test suite, and both were found by pointing the
finished thing at reality rather than at a fixture.

**1. A failed fetch read as an all-clear.** Ran the new CLI against this repo's
own canary, whose origin is `https://invalid.invalid/canary.git`. Output:

```
📚  reference repos: all 1 up to date
```

The fetch fails with exit 128. The local refs say "not behind", so the repo was
counted as fresh. `refresh_repo` already KNEW — it returns `fetched=False` with
a `_FETCH_FAILED` detail — but all three consumers keep only `.state` and drop
the outcome, so the knowledge died at the call site. Fixed by carrying it on
`RepoState` (`fetch_failed`, plus a `verified` property) so it survives into the
cache and reaches every surface.

The interesting part was where NOT to put it. Folding it into `needs_attention`
was the obvious move and is wrong: the canary is *checkable* (it has a remote
and an upstream), so every session would have opened with a complaint about a
remote that is unreachable **by design**. That is precisely what the model
docstring keeps un-checkable repos out of the way for. It belongs in the
counting, not in the nagging.

**2. The handler denied the commit that shipped its own documentation.**

```
reference repo freshness NOT VERIFIED: no in-date reading exists for untracked/repos
```

…on a `git add -A && git commit -F - <<'MSGEOF'` whose MESSAGE mentioned
`untracked/repos/php-qa-ci`. `_CHAIN_SEPARATORS` includes `"\n"`, so every line
of the heredoc body became its own "segment", and a line of prose naming a repo
parsed as a command reading it. Nothing was being read at all.

The fix was already sitting in the codebase: `strip_quoted_heredoc_bodies` and
`strip_message_bodies` in `utils/shell_segmentation.py`, which `pipe_blocker`
uses for this exact class of false positive. I segmented a raw command string
without them. Worth remembering that "is this text a command?" is a solved
problem here, and reaching for the solved version is cheaper than rediscovering
why it exists.

Both now have regression tests. Neither would have been caught by more unit
tests of the kind I was already writing — the first needed a repo with a
genuinely unreachable remote, and the second needed a real commit message.

## 14:23 · fix · three critical false positives, all from one mistake (`266b4808`)

A code review reproduced three shapes the gate denied and must never touch. I
reproduced all three myself before acting, and every one behaved exactly as
reported. They share a single cause: the handler decided from the PATH TEXT
rather than from what the path IS or what the command DOES with it.

The worst was not the noisiest. With a **perfectly fresh cache**,
`ls untracked/repos` was denied — the root is under a governed root, so the
handler invented a subject for it, and `discovery` only ever records directories
carrying a `.git`, so no sweep and no CLI run could ever put that subject in the
cache. The remedy printed beside it could not clear it. Under `mode: block` it
was a permanent dead end in this very repository.

The second: `str.split()` plus any-position matching meant merely NAMING a repo
engaged the gate — `rm -rf <repo>`, `mkdir -p <repo>-new`, `echo see <repo>`,
`gh repo clone o/x <repo>`, and a `python3 -c` whose COMMENT mentioned it.

The third was self-contradiction: `(cd <repo> && git pull)` — the remedy the
handler itself prints — was intercepted, while the deny text promised in as many
words that `git` is NEVER intercepted.

One of my own tests had also passed for the wrong reason: the quoted-path case
extracted `.../alpha/some` from `cat 'alpha/some file.md'` and matched anyway.
A test that passes for the wrong reason is worse than a missing one, because it
reports coverage it does not have.

During the rewrite the cwd fallback fired on the `HEREDOC_BODY`/`EOF`
placeholders that heredoc stripping leaves behind — they are not commands at
all. The fix was to make the inference positive (`_READING_COMMANDS`) rather
than an exclusion list: an exclusion list cannot enumerate every token that is
not a command, and an inference that fires on everything unrecognised fires on
shell noise.

All 16 reproductions verified afterwards: the 12 that must be allowed are, and
the 4 real reads still engage.

## 14:31 · fix · the silence that read like an all-clear (`76c8e8a9`)

Review finding 5, and the one I would not have found by testing what I built —
only by asking what it does NOT say.

When a fetch fails, `behind` is computed from the refs already on disk, so it
reads 0. Nothing then needs attention, so the sweep returns early and says
nothing, correctly and by its own design. But the read path was silent too. An
offline session could therefore spend hours reasoning from clones nothing had
checked, with no signal anywhere — which is the exact failure this whole plan
exists to prevent, arriving through the door marked "everything is fine".

The gate now says `COULD NOT BE CONFIRMED` once per repo per session, at the
moment the repo is read. It never denies, in any mode: there is no command that
makes an unreachable remote reachable, and under `mode: block` it would make the
canary permanently unreadable. It is tracked under its own key so a note at
09:00 cannot spend that repo's single block and let a genuine staleness at 09:05
arrive as quiet context.

Verified live rather than only in tests: `ls untracked/repos/php-qa-ci` emitted
the note and RAN; the second read in the same session was silent.

## 14:36 · fix · duplication was the mechanism, not the symptom (`ead47359`)

Findings 7 and 8 turned out to be one defect seen twice. `discover -> refresh ->
write_cache` ran in two places and the roots expression in three — and that
duplication is *how* the two surfaces came to disagree earlier in this plan: the
CLI's JSON encoder learned about `fetch_failed` while the handler's copy of the
same walk did not. I had fixed that drift without removing what produced it.

`RefreshOutcome.detail`, `.fetched` and `.pulled` had no production consumer at
all, so `_refusal_detail`'s careful dirty-vs-ahead-vs-diverged advice was
written for nobody. The shared pipeline returns outcomes rather than bare
states, and the CLI now prints and serialises them.

The package docstring claimed the re-export facade was what kept the three
surfaces from drifting. Nothing in production imports through it. `sweep` and
`report` are what actually do that — so the docstring now says what is true
rather than what was intended.

## 14:38 · fix · a test that did not test its name (`55a5adc7`)

`test_inspection_never_performs_network_io` stubbed `fetch_all` and
`pull_ff_only` and asserted they were not called. That proves `inspect_repo`
does not call those two functions BY NAME; it says nothing about the eight-odd
git commands it really spawns, and a probe added as a raw
`_run_git(cwd, "ls-remote", ...)` would have sailed straight past.

It now spies on `run_git`, the daemon's single git spawn point, and asserts no
spawned argv carries a network verb. The important part is the three guards
around it, because a test asserting an ABSENCE is exactly what a spy watching
the wrong place also reports: the spy must have recorded real probes, the
detector is asserted to fire on `fetch` and `remote prune`, and a real
`fetch_all` is driven through the same seam and must be caught.

That last one is the mutation guard. Without it, if `_run_git` ever stopped
routing through `run_git`, the invariant tests would go on passing quietly over
an unwatched spawn point — the same failure shape as the test being replaced.

## 14:49 · defect · two regressions my own critical fix introduced

Both were mine, both from `266b4808`, and I found them only because I widened
the net from "the test files I changed" to `tests/integration/` and
`tests/daemon/`. Running targeted files is how I missed them in the first
place. The narrow run is what makes a wide one feel unnecessary.

**The acceptance contract broke.** The declared acceptance test drove
`Read untracked/repos/__freshness_probe__/README.md` and claimed DENY. Fixing
finding 1 made that path correctly ungoverned — it is not inside a checkout —
so the handler now allows it and
`test_every_blocking_test_declares_a_way_to_drive_it`'s sibling failed:
`expected_decision=DENY but matches() returned False for its own declared
input`. The acceptance tests are a release gate, so this would have aborted a
release.

The DENY verdict turns out to be genuinely undrivable here: it needs a real git
checkout under `reference_repos.roots`, that root is untracked so CI has none,
and fixture commands are bounded to `untracked/scratch/` — so the harness
cannot build one under a governed root either. Declared
`harness_cannot_produce` with that reasoning written out, and replaced the slot
with three ALLOW tests that pin what actually shipped broken: listing the
governed root, `git` against a governed path, and `rm -rf <repo>`. Those are
weaker assertions than a DENY, and they are the ones that would have caught the
bug.

**A raw `.exists()` on a caller-supplied path.** `_subject`'s disk walk asks
whether each level carries a `.git` — with `Path.exists()`, which RAISES
`PermissionError` when an ancestor is not traversable. Plan 00347 has a static
checker for exactly this, and it caught it.

Worth recording how the reproduction nearly failed: I wrote the test with
`chmod 0o000` and it passed. The suite runs as root, and root traverses a
`0o000` directory regardless of mode — so the fixture proved nothing while
looking convincing. Simulating the raise at the predicate is both root-
independent and a more honest statement of the defect, which is that a raw
predicate propagates `OSError` at all.

`unreadable_means=False` is the answer at this site, and it is not the obvious
one. "I could not look" must not become "this is a governed clone": a path
whose ancestor is untraversable cannot be READ either, so denying it blocks a
call that was going to fail anyway — and hands over a `fix:` command that
cannot clear it. That is the same unclearable block that inventing a subject
produced. The cache is consulted before the disk walk, so a repo that really
was swept is still found either way.
