## 20:32 · finding · P1 — found by being blocked by my own handler

Ran a `python -m pytest` invocation piped to a pager while finishing Plan
00216. It blocked, correctly — but the reason named the producer as the
redaction placeholder, so the remediation it printed was not runnable. Small
thing; pulling on it found a real bypass underneath.

`-m` was matched anywhere, with nothing requiring the command to take a
message, so python's MODULE flag was read as git's MESSAGE flag. And the
blanking covered DOUBLE-quoted values, which bash substitutes inside. Measured
against the live handler rather than reasoned about:

| command                                        | decision                   |
| ---------------------------------------------- | -------------------------- |
| `python -m pytest tests/` piped to a pager     | blocked, producer redacted |
| `git commit -m "$(pytest … piped to a pager)"` | **not blocked**            |
| `git commit -m 'prose … piped to a pager'`     | not blocked (correct)      |

The middle row is the bug: bash expands the substitution before git ever sees
it, so pytest really runs and really gets truncated.

## 20:48 · decision · P2 — two predictions, both wrong, both caught by tests

**"Blank only single-quoted values"** died in about a minute. Plan 00200 has
two deliberate tests asserting a DOUBLE-quoted message containing the literal
characters of a pipe as PROSE is allowed, and they are right: with no `$(` and
no backtick the shell runs nothing. A quote-class rule re-breaks the exact
false positive 00200 was written to fix. The discriminator is the presence of
a substitution, not the quoting.

**"The heredoc idiom survives via producer attribution"** — I wrote into
`PLAN.md` that `"$(cat <<'EOF' … EOF)"` would be fine because Plan 00221
resolves its inner producer to the whitelisted `cat`. Two tests failed and
showed otherwise: newlines are chain separators, so the "command" before a
pipe inside the heredoc BODY is a line of English prose. What actually makes
that idiom inert is the QUOTED delimiter — bash expands nothing inside
`<<'EOF'`, so only `cat` runs. An unquoted `<<EOF` does expand and is
deliberately not exempted.

Both predictions were caught before anything shipped. That is the argument for
writing the tests first, stated more plainly than I could state it.

## 21:05 · decision · T3.1 — the fact had no home

The fix is less interesting than the reason it was needed.
`git_message_backtick` has always known bash substitutes inside double quotes
— that is the entire reason it exists — while `pipe_blocker` assumed the
opposite. Two handlers, one codebase, disagreeing about the shell.

`utils/shell_segmentation.py` already existed for the *identical* failure; its
docstring records that "two handlers grew their own scanner and each got the
opposite half of the escape rule". So `value_can_substitute` lives there now,
`pipe_blocker` consumes it, and `git_message_backtick` points at it while
keeping its own narrower scan — it answers a different question ("is a
BACKTICK the thing executing?") because its remedy is about message
corruption, not cost.
