## 07:05 · decision · — — owner chose the in-repo fix; the tracked link was rejected on evidence

The owner's direction on #54: "hooks daemon projects should expose a
standard public interface … fix this internally". Option 1, not a
consumer-side fallback.

**The issue's own proposal, a TRACKED relative symlink, was ruled out by
four checks made before this plan was filed:**

1. The wrapper already follows relative symlinks (`bin/hooks-daemon:66-80`),
   and the link was proven live. A temporary gitignored link, called from
   `untracked/scratch/`, reached this checkout's own running daemon
   (PID 581467). So the link idea itself is sound.
2. `mode_guard.sh`'s self-install test is `! -d .claude/hooks-daemon`.
   Probed on a minimal layout, `get_install_mode` went from `self-install`
   to `normal` once the link directory existed. With that, the guard that
   stops install/upgrade running in the daemon repo would stop firing.
3. Clients install by cloning this repo into `.claude/hooks-daemon/`, so a
   tracked link would appear at `.claude/hooks-daemon/.claude/hooks-daemon/`
   in every client. `init.sh:445` treats that directory as a nested install
   and exits on every hook. It has no `pyproject.toml` exemption, unlike
   `validation.py:273-281`.
4. A client's `.claude/init.sh` is a COPY refreshed at the end of an upgrade
   (`scripts/install/hooks_deploy.sh:216`). A tolerant `init.sh` therefore
   cannot be relied on to arrive before the link does.

So the link is GENERATED by the self-install daemon under the
already-gitignored `.claude/hooks-daemon/`, and never reaches a client
clone. The guard and the other "a clone is installed here" checks are
re-keyed on a real clone. Told the owner, with the two-release tracked
alternative offered.

## 08:23 · finding · T1.2 — reviewer caught a wrong exemption in init.sh; reverted

Team-lead review of commit `0bda7578` found the `init.sh:445` exemption
wrong, not merely unnecessary. The exemption (skip the nested-install
refusal when the outer `.claude/hooks-daemon/pyproject.toml` exists) is
true for EVERY real client clone, always — a client's clone always has
`pyproject.toml` at that path. So the exemption would have silenced
`init.sh`'s nested-install check for every client, permanently: it could
never fire again for a genuine nested installation either.

The framing I'd used ("true for every ordinary client install, whose clone
carries its own dogfooded `.claude/` tree") was itself the error: a
client's tracked `.claude/` tree does NOT include `.claude/hooks-daemon/`
even one level in — that path is gitignored by this repo's own
`.claude/.gitignore`, in the clone's own working tree as much as in the
outer project's. The double-nested path this check looks for therefore
never exists from cloning alone; it can only be written at runtime, which
is exactly the wrong-root pathology the check exists to catch. My
`ProjectContext` symlink change makes that pathology now produce a
link-only marker instead of daemon runtime files when it happens — a real
symptom of a real bug, correctly flagged by the ORIGINAL unconditional
check, not something to exempt.

Reverted `init.sh` to main's unconditional check (no code change needed
there after all — Task 1.2's brief listed it as a site to change under the
TRACKED-symlink design; the generated design removes the need). Replaced
`tests/integration/test_init_sh_nested_install_link_only.py`'s RED-case
test with one pinning the CORRECT behaviour: a real outer clone
(`pyproject.toml` present) with the inner nested path present (link-only
marker) is STILL refused. Also trimmed the `ensure_normal_mode_only` header
comment in `mode_guard.sh` per review — it had drifted into changelog
narrative ("Previously this parameter was accepted but silently
ignored…"); comments describe current state, that history is in the
commit message already.

**Left as a pre-existing, out-of-scope finding, not fixed here** (per
team-lead's explicit instruction — theirs to ledger): `daemon/validation.py`'s
`check_for_nested_installation` (lines 273-281) carries the IDENTICAL flaw
— its "outer has `pyproject.toml`" exemption is also always true for a
real client clone, so it too can never fire for a genuine nested
