## 09:35 · finding · P1 — the staleness is a STATED contract, not an oversight

Reading `docs_qa/corpus.py` settled the design question before any test ran.
`refresh_own_record`'s own docstring said it outright:

```
Every OTHER document's record is left exactly as loaded -- partner
staleness is accepted (that is the sweep's job); only the file actually
being linted must never lag its own content.
```

So this was never a missed case. It was a deliberate decision that turns out
to be wrong, which means the fix has to change the contract and its prose, not
just add a guard.

## 09:52 · decision · P2 — revalidate, because the alternatives measure badly

Measured against the real index (222 documents, 2833 KiB):

| pass                                    | cost      |
| --------------------------------------- | --------- |
| `stat()` all, compare `mtime_ns`+`size` | 0.73 ms   |
| re-read + re-parse all                  | 1582.3 ms |

~2000x, on a path inside a PreToolUse budget on every documentation edit. That
kills "drop the cross-file cache for single-file lint" outright.

"Invalidate the whole index when any member changed" is worse than it sounds:
detecting it costs the same full `stat()` pass, then it discards every
still-valid record — and since `duplicate-block` has a cold-index rule, the
check would go silent entirely. Trading a rare wrong finding for a silent check
is not a fix. Both are recorded as Non-Goals with these reasons.

## 10:05 · finding · P2 — the exposure is keyed to the STAGE, not the check

Audited every consumer of `context.corpus`. The dividing line is not which
check it is, but which stage it runs in: SWEEP consumers get their corpus from
`build_and_save_corpus`, which already revalidates, so `pointer-resolves`,
`quote-drift` and `at-import-census` are all clean. Two EDIT-stage consumers
read counterpart records and are both exposed — `duplicate-block`
(`block_locations`) and `quote-source-stale` (the reverse quote index).

That is why the fix went into the corpus layer. Patching `duplicate_block.py`
would have left `quote-source-stale` broken in the identical way, and would
break again for the next EDIT-stage consumer someone adds.

## 10:18 · decision · T2.2 — `load_edit_corpus`, because the two steps do not commute

`revalidate_corpus` and `refresh_own_record` must run in that order.
Revalidating AFTER refreshing would re-read the edited file from disk and throw
away the would-be content — meaning the PreToolUse handler would silently lint
the OLD content of every pending edit. That is a worse bug than the one being
fixed, and nothing in the types prevents it.

Hence one composed entry point with both callers routed through it, plus a test
pinning specifically that the own record reflects the would-be content and not
what is on disk.

## 10:41 · blocker · P3 — QA was testing the WRONG source tree

QA reported the two new test modules as collection errors while a direct
`pytest` run passed them. Cause: the worktree had no venv, so `untracked/venv`
had been symlinked to the workspace venv — whose editable install resolves the
package to `/workspace/src`, the MAIN repo:

```
$ /workspace/untracked/venv-.../bin/python -c "import claude_code_hooks_daemon as m; print(m.__file__)"
/workspace/src/claude_code_hooks_daemon/__init__.py
```

Every QA run was judging the wrong tree; the direct runs only passed because
they set `PYTHONPATH=src`. Replaced the symlink with a real `uv sync --extra
dev` venv and verified `__file__` points inside the worktree before trusting
any further number.

Takeaway worth carrying: a green QA run in a worktree means nothing until you
have checked which tree the interpreter actually resolves.
