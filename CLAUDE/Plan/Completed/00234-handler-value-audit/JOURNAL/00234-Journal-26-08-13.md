## 15:32 · finding · T1.2 — the instrument for this audit is blind

Measured `verdicts.jsonl` before dispatching anything, on the theory that the
daemon's own decision log should answer "which handlers earn their keep?" —
which is, verbatim, what Plan 00209's config docstring says it was built for.

It cannot. The log is at its 10 MiB cap with 44,180 records, of which 43,929
(99.43%) are status-line renders. Thirteen status handlers each fire ~3,383
times an hour, one render per ~1.15 s, and every record is `allow` because a
renderer has no other verdict to return. Retained window: **65 minutes**.

The dangerous part is not the blindness, it is that the report looks
authoritative. "Total recorded decisions: 44168" reads like history. Its
"Never-fired handlers (59)" list names `prevent-destructive-git` and
`block-sensitive-content` — handlers whose whole value is firing rarely.

Wrote the anti-inference warning into `RESEARCH-verdict-log-is-blind.md` and
put it in every agent brief, because the obvious misuse of that list would be
to delete 59 handlers including the safety net.

## 16:05 · thought · P3 — the removals are the small prize

Plan 00181 already found both loggers and tabulated them `Consumer: NONE`, then
**bounded** them instead of removing them. It also looked straight at `cleanup`
and certified it "the one functioning reaper" without checking the producer
side.

So this shape has now appeared four times and a prior audit walked past three of
them. Bounding an unread log gives you a fixed-size unread log — the bound
answers "will this fill the disk?", which was the question that plan asked, and
never touches "does anyone read this?", which nobody was asking at all.

That reframes the finding. The individual handlers are cheap; the defect is that
"does anything consume this?" is not a question any guard asks continuously, so
it gets answered only when a human happens to wonder. Pushed the judge to make
Phase 3 name that guard rather than list defects.

## 16:30 · finding · P1 — the cohort structure had a hole, and the hole held the best finding

The judge's closing report flagged that three handlers fell outside every
cohort's brief: two project-level handlers in `.claude/project-handlers/` and
the plugin handler. I had built the cohorts from
`src/claude_code_hooks_daemon/handlers/`, so anything outside that tree was
invisible by construction — a scoping error in my own dispatch, not an agent
failure.

Audited the three directly. `dogfooding_reminder` is fine (one line, ~30
tokens). The other two both have real defects, and one of them is the most
consequential thing this audit found:

**`enforce_llm_qa` denies `scripts/qa/run_all.sh`. Sixteen places in the
always-resident documentation instruct the agent to run it** — including
`CLAUDE.md:84` (the release QA gate) and `RELEASING.md:352`, which is **Step 8,
a documented BLOCKING GATE**, plus all three `CodeLifecycle/*.md` documents that
`CLAUDE.md` names as mandatory reading before any code change.

So an agent following the release procedure verbatim is denied by the project's
own handler, and both sides of the contradiction are resident in every session.
This is the claim-vs-mechanism drift class Cohort A found in `pipe_blocker` and
`security_antipattern` — but worse, because there the handler's guidance drifted
from its own regex, whereas here two independent sources of truth disagree and
the daemon overrules the one with authority in the reader's mind.

**`release_blocker`** has a latent trap: `RELEASE_FILES` includes `README.md`
and `CLAUDE.md`, and it DENIES every Stop on any uncommitted edit to them with
"RELEASE IN PROGRESS". `CLAUDE.md` is regenerated and auto-committed by the
daemon itself. An ordinary README edit left uncommitted would trap the session.
It also cites a plan path that has since moved to `Completed/`, and hardcodes
"89 EXECUTABLE acceptance tests" — a drifted count.

Both are FIX, not REMOVE. The `release_blocker` duty is postmortem-backed (a
v2.13.0 release where acceptance testing was repeatedly skipped, and the testing
caught a shipping bug); `enforce_llm_qa`'s mechanism is genuinely good and the
defect is in the docs, not the handler.

## 16:35 · thought · — — what the gap says about the method

Worth recording because it generalises: the cohort sweep was organised by
DIRECTORY, so it could only find defects that live inside a handler. The best
finding lives BETWEEN a handler and the documentation, and it surfaced only
because a coverage gap forced a manual pass.

A fan-out audit inherits the blind spots of its own partition. The judge
catching the gap is the reason it was found at all — which argues for keeping
the "what did this audit not cover?" question as an explicit deliverable rather
than trusting the partition to be complete.
