## Session-start context budget

In a **healthy, default-configured project** (no drift, no missing config), 10 of the 12 handlers inject **zero tokens** — confirmed live for 7 of them by inspecting this repo's actual on-disk state (cache files, `.gitignore`, `core.fileMode`, `git status`, `settings.json`). The realistic per-session tax in a clean project is:

- `plan_qa_sweep`: ~5-15 lines *only when the plan tree has drift* (currently true in this repo: ~10 lines / ~150 tokens)
- Nothing else, by design, in the common case.

The **worst case** (freshly cloned project, nothing configured yet) is materially larger: `gitignore_safety_checker` (~15 lines), `hook_registration_checker` (~10 lines, one-shot), `optimal_config_checker` (1 line, one-shot), `git_filemode_checker` (~9 lines, if misconfigured), `suggest_statusline` (~15 lines, **every session, no decay**), `git_upstream_checker` (~10 lines if behind) — roughly 300-500 tokens on the very first sessions, dropping to near-zero once fixed, **except** `suggest_statusline`, which is the only one of these that never decays on its own.

Separately from token cost: `git_upstream_checker` performs a genuine network round-trip (`git fetch --all`) on **every** new session unconditionally (`auto_fetch: true` default), which is a latency cost distinct from the context-token framing — worth flagging even though it doesn't itself bloat context.

## Cross-cutting observations

1. **Plan 00128 ("Lean SessionStart") already did most of this audit's job.** Its own `PLAN.md` (`CLAUDE/Plan/Completed/00128-lean-session-start/PLAN.md:39-57`) lists `yolo_container_detection` and (pre-fix) `optimal_config_checker`/`hook_registration_checker`/`git_filemode_checker` by name as "sources of bloat" and rewrote them to silent-unless-actionable. Verified: `optimal_config_checker`, `hook_registration_checker`, `gitignore_safety_checker`, `version_check` are now genuinely silent-when-healthy (confirmed live in this repo). `yolo_container_detection` was "fixed" by defaulting its trigger flag off rather than by being reconsidered as a handler — it is now dead weight sitting in the active-handler table with `enabled: true` while structurally incapable of firing by default.
2. **The one handler Plan 00128 explicitly certified as "already correct" (`suggest_status_line`, `PLAN.md:56-57`) is the one this cohort's brief specifically asked me to check hardest — and it's the weakest of the three named there.** `version_check` and `gitignore_safety_checker` (the other two in that same "already correct" line) both have real persistence/caching that makes them stay silent once resolved; `suggest_statusline` has none, so it is not actually in the same category as its two named siblings — it was misclassified alongside them in Plan 00128.
3. **`enabled: true` is a misleading signal for `yolo_container_detection`.** Every other "silent by default" handler in this cohort is silent because a *condition* is false (something to detect isn't present). This one is silent because a *second, nested config flag* defaults off — independent of the top-level `enabled` toggle everyone would check first. That's a discoverability trap as much as a noise problem: a reader of `.claude/hooks-daemon.yaml` or the active-handler table sees "enabled: true" and reasonably assumes it does something.
4. **Self-healing handlers in this cohort narrate correctly.** `hook_registration_checker` was called out in the brief as worth checking ("if it repairs silently, does it need to also narrate?") — it does narrate, but *only* the one-shot repair event itself, never on subsequent healthy sessions. This is the right shape and should be treated as the reference pattern, not a suspect.
