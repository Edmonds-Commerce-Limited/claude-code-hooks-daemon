## Cross-cutting observations

1. **The `background-processes.jsonl` / `read_tracked_pgids` mismatch is the cohort's most interesting finding** — it is not the "writer with zero readers" shape of the deleted `transcript_archiver`, but a subtler variant: a reader genuinely exists and genuinely runs (`cmd_harvest_background` is a real, advised-in-guidance CLI command), but the writer's record schema (`command`, `session_id`, `run_in_background`) never includes the one field (`pgid`) the reader needs. Confirmed via `tests/unit/daemon/test_background_harvester.py::test_reads_pgids_skipping_malformed_lines` (which fabricates `{"pgid": 100, ...}` records) vs. `tests/unit/handlers/post_tool_use/test_background_process_tracker.py::test_state_record_written` (which never asserts a `pgid` field, because there isn't one). Net effect: the CPU-ceiling breach (applies to ALL `ps` processes, tracked or not) still works and is the one exercised by the acceptance test; the wall-TTL-for-tracked-processes breach that Plan 00142 Task 2.3 explicitly designed can never fire from this handler's output. Worth a follow-up plan to either add `pgid` to the written record or drop the tracked-TTL code path.
2. **`cleanup_handler`/`temp/hooks/` is a second instance of the exact defect pattern this whole audit exists to find** — a directory nothing writes to, cleaned forever. It is far cheaper than `transcript_archiver` (a `glob("*")` + conditional unlink once per SessionEnd, no accumulation risk either way), so the cost of leaving it is near-zero, but Plan 00181 (`CLAUDE/Plan/Completed/00181-disk-usage-time-bomb-audit/PLAN.md:68-72`) already asserted it was "genuinely bounded" and "functioning" without checking that any producer still exists — which suggests the pattern (assume-a-writer-exists-because-a-reaper-exists) is exactly the blind spot DBF (CLAUDE.md principle 15) warns about. Two independent audits (00181 and this one) both looked at this file and only this one checked the producer side.
3. **The `lint_on_edit` / `validate_eslint_on_write` / QA-suite triple is NOT duplicative** — contrary to the brief's suspicion, the three partition cleanly: `lint_on_edit` covers 9 non-JS/TS languages at edit time, `validate_eslint_on_write` covers only `.ts`/`.tsx` at edit time (confirmed: no TypeScript/JavaScript strategy is registered in `LintStrategyRegistry`, and `lint_on_edit`'s own `get_claude_md()` says so explicitly), and the project's own `scripts/qa/run_lint.sh` only runs `ruff` (Python) as a commit-time gate. The only real overlap is Python getting both an edit-time `ruff`/`py_compile` check and a commit-time `ruff` gate — a deliberate fast-feedback-then-final-gate pattern, not redundant duplication.
4. **Rate-limiting is inconsistent across the cohort's advisories**, and `bash_error_detector` is the outlier. `background_process_tracker` (every 10th), `command_hints` (TTL 1800s default), and `recovery_cron_advisor` (every 5th progress edit) were all explicitly engineered with cooldowns after being identified as spam-prone (see their docstrings citing exactly this rationale). `bash_error_detector` — the oldest handler in the cohort, present since "Initial commit" with no plan reference — has no such gate: it matches every single Bash tool call and injects context on any stderr output or any substring hit of `error|failed|failure|fatal|warning|warn|deprecated` in combined stdout+stderr, which is a very high hit-rate against real command output (package manager warnings, verbose build tooling, etc.).
5. **The two adjacent-cohort JSONL logs the team lead measured live (`stop-events.jsonl` at 953,601 B, `background-processes.jsonl` at 68,945 B) turn out to sit on opposite ends of the same spectrum this cohort's own artefacts span.** `stop-events.jsonl` (written by `auto_continue_stop`, a Stop-event handler outside this cohort's 12, but traced per request since it parallels `background-processes.jsonl` in shape) is the healthiest artefact examined across either dossier: it has a genuine reader — not production code, but TWO independent docs (`transcript-inspector.md` and `DEBUGGING_STOP_HOOK.md`) both prescribing `tail`/`cat` on the exact path as a real diagnostic step — and it is actively bounded (Plan 00181 added a 2 MiB cap after an unbounded 644 KB was observed; live size confirms the cap is holding, not merely configured). Lined up together: `context-sidecar/*.compacting` (real reader, real bound) and `stop-events.jsonl` (real reader, real bound) are the pattern working correctly; `background-processes.jsonl` (reader exists but is schema-starved) is the pattern half-working; `temp/hooks/*` (no reader, no writer, no bound needed) is the pattern that should have been deleted like `transcript_archiver`. The measured sizes matter less than which of these four shapes each artefact is in — a small file can still be a dead reaper, and a large one can still be a correctly-functioning, actively-consumed log.
