A peer review session raised this immediately after Plan 00253 closed: the tier
00253 added uses the FORCE delete, so the concurrency guard 00253 had just
identified — git's own `-d` refusal, protecting against a peer commit the
pre-loop bundle cannot contain — does not apply to it.

Re-verified all of it by execution before accepting any of it, which is now the
standing habit in this chain, and it paid again. Two things the peer asserted
without showing both held: a pre-existing tier (`merged-unpushed`, shipped in
00249) loses work identically, so this is a latent defect across four tiers
rather than a 00253 regression; and `git update-ref -d <ref> <sha>` really is a
compare-and-swap.

But the peer's proposed remedy is the wrong change, and executing it is what
showed that. Its premise was that the force tiers give up nothing by switching to
`update-ref`, since git checks nothing there. False: the force delete REFUSES a
branch checked out in another worktree, while `update-ref -d` deletes it and
leaves that worktree with a dangling HEAD. It also leaves `branch.<name>.remote`
and `.merge` behind — the exact two keys `_safe_delete_reference` reads to choose
a tier, so a later branch of the same name would inherit a dead upstream.

In a project where agents routinely run with `isolation: "worktree"`, that guard
fires far more often than the race. So: re-read the tip, keep git's delete. The
window goes from a whole bundle pack to one git invocation, and nothing is given
up. The residual window is real and gets said out loud rather than implied away.

Second instance of 00253's Decision 1 — the battle-tested tool checks things we
did not think to check. Worth noticing that the first instance was about trusting
git over our own predicate, and this one is about trusting git over a peer's
suggested replacement for it.

## 17:02 · correct · — — my own Decision 1 was overstated; sharpened, not withdrawn

Found this while reading the imports for the RED test: `REFUSAL_WORKTREE` already
exists, and `classify_branch` refuses a branch checked out in a linked worktree at
`branch_safety.py:427`. So the version of Decision 1 I filed an hour ago —
"switching to `update-ref` loses git's other-worktree refusal" — is wrong as
stated. In the ordinary path the daemon refuses first and never reaches the
delete, so nothing would be lost.

The argument survives on narrower and better ground. What the switch would lose is
the RACING case, which is this plan's whole subject: a peer that checks out the
branch AFTER classification moves no tip, so a tip re-check is structurally blind
to it, while git's delete-time check still refuses. Verified through the real
engine with the checkout interposed during the bundle write — refused, branch
intact, peer worktree still on `done`.

So the real framing is not "atomic versus not". It is "which delete-time checks do
we keep": Option 2 closes the moved-tip window and opens a checked-out-by-a-peer
one. Keeping git's delete keeps every check it makes, including the ones nobody
here thought to enumerate — which is the actual content of 00253's Decision 1, and
the reason the two belong together.

One thing that probe does NOT show, recorded so nobody later reads it as evidence:
its attempt to emulate the CAS by swapping `delete_argv_for_tier` is invalid.
`delete_branches` appends the branch name, so it issued
`update-ref -d refs/heads/done <sha> done`, which git rejects as malformed. That
line's "refused" is an argv error, not the behaviour under test. The CAS result
stands on the direct-git run instead.

Third instance in two plans of the same failure shape, this time mine rather than
the peer's: a harness reproduced the behaviour I expected while testing something
other than what I thought.

## 18:06 · action · — — Phase 4, unplanned: the proof was reading a tag

Found this by asking what my own new line assumed, not by review. `rev-parse <name>`
looks unremarkable and the module has used bare names since Plan 00206 — but a bare
refname is AMBIGUOUS, and git resolves `refs/tags/<name>` ahead of `refs/heads/<name>`,
warning only on stderr. No fixture in the suite had ever created a tag, so nothing
could have caught it.

Three layers, each worse than the last:

1. My new guard read the tip ambiguously at both ends, so it would have compared a
   tag against itself and never seen the branch move — inert in exactly the case it
   exists for.
2. `local_branches` used `%(refname:short)`, which returns the shortest UNAMBIGUOUS
   name, so a shadowed branch came back as `heads/<name>` and `delete-branch`
   reported "does not resolve to a local branch" about a branch plainly present.
3. The PROOF itself. With a tag patch-equivalent to `main` and a branch of the same
   name holding the only copy of a file, `classify_branch` returned
   `patch-equivalent` — a verdict about the TAG — and the loop force-deleted the
   BRANCH with `refused=False`, exit 0. The only copy, gone silently. The recovery
   bundle would also have bundled the tag: a recovery route that recovers nothing.

The coupling is the thing I want to remember, and it is why this could not be a
follow-up plan (Decision 3). Layer 2 was WRONG BUT FAIL-SAFE — it refused. Fixing
just that message would have made the branch visible to a proof that still read the
tag, turning a false refusal into silent data loss. The readable-message fix alone
would have INTRODUCED the bug. Order of fixes mattered more than either fix.

Also: this is the third independent time in two plans that keeping git's own delete
paid off. Layer 3's `merged`-tier variant did not lose data, purely because that
tier uses the safe delete and git refused what our corrupted proof had approved.
Decision 1 argued for keeping git's checks on the grounds that it checks things we
did not think of. This is git catching a bug in our proof, which is exactly that,
and I did not anticipate it when I wrote the decision.

RED proven by reverting only the proof-side qualification: `patch-equivalent`
returns and the file is destroyed. And one more instance of the recurring shape —
the tag test failed at first against CORRECT production code, because the test's own
`_local_branches` helper had bug 2. I nearly went looking for a fault in the fix.
