## 18:44 · handoff · — — plan complete, delivered

`GitMessageBacktickHandler` shipped at priority 20, blocking an unescaped
backtick inside a double-quoted `-m`/`--message` on `git commit` and
`git tag`. Bash performs command substitution inside double quotes, so the
backticked span is EXECUTED and replaced by its stdout — the commit still
succeeds, so the text vanishes with no signal. Commit cc7dddc0 in this
repository lost a phrase exactly that way.

Blocking rather than advisory was a measured call, not a preference. Of 1,736
commit messages in this repository, 120 contain backticks — and every one of
them is evidence of SAFE authoring, because had they been double-quoted bash
would have consumed the span and the stored message would contain none. So
the rule fires on zero historic commits and carries no measured
false-positive cost.

Scope is the CORRUPTION case only. The execution half — a dangerous command
inside backticks — was already denied by the full-command-string matching in
`destructive_git` and friends; probed against the live daemon in both quoting
forms before writing anything, rather than assumed.

Two things this plan got wrong first and had to correct:

- `get_acceptance_tests()` was written against an INVENTED `AcceptanceTest`
  signature. All 19 unit tests still passed, because none of them called it —
  the playbook generator would have been the first thing to find out. Fixed
  to the real signature and pinned by `TestDeclaredMetadataIsReal`, so a

- The command regex was hand-rolled instead of built on the shared
