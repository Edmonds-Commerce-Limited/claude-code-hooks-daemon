## 15:05 · finding · T1.4 — the placeholder escaped four times, not two

Task 1.4 asked whether the release flow should set the manifest date, on the
evidence of one repeat. It is worse than that:

```
CLAUDE/UPGRADES/config-changes/v3.26.0.yaml
CLAUDE/UPGRADES/config-changes/v3.27.0.yaml
CLAUDE/UPGRADES/config-changes/v3.29.0.yaml
CLAUDE/UPGRADES/config-changes/v3.53.0.yaml
```

The reason it survives is the interesting part, and it is why a static check is
the ONLY guard available. `ConfigMigrationManifest.from_dict` reads `date` into
an attribute that nothing renders or compares — a `.date` grep across `src/`
returns only `plan_qa`, an unrelated module. So a wrong date breaks nothing,
surfaces nowhere, and no runtime check could ever notice it. There is no
failing behaviour to detect; only the text is wrong.

## 15:05 · decision · T1.5 — matched against the schema, not against the word

Wrote the rule against SCHEMA.md's declared contract (`date` is an ISO 8601
release date) rather than the literal `UNRELEASED` observed. A guard narrowed
to the one spelling that produced it would let `TBD` ship the identical defect,
which is the shape DBF exists to prevent. The rule therefore also catches a
missing `date:` — required by the schema, and a `KeyError` in `from_dict`.

The discriminator is LOCATION, not spelling: `UNRELEASED` is the *honest* value
while the file is staged, because the release date does not exist yet. A rule
that flagged the staging copy would fire on every in-flight release and be
switched off within a cycle. The `git mv` into the live directory is the moment
the date becomes knowable, which is why the instruction belongs at that step.

Both halves of the corollary are now closed: the batch guard sees what is
already on disk, and `RELEASING.md` Step 6 plus the staging README now say to
set the date — nothing said so before, which is why nobody did.
