## N19 — nested-install check can never fire in a real client

`check_for_nested_installation` in
`src/claude_code_hooks_daemon/daemon/validation.py` exempted an outer
`.claude/hooks-daemon/` with a `pyproject.toml` from cleaning up
`.claude/hooks-daemon/.claude/hooks-daemon/`. Every real client clone has
that file, so the exemption always held. Deleted it — cleanup is now
unconditional whenever the nested path exists.

Made the destructive branch safer while it was open:

- A nested path that is itself a symlink is `unlink()`ed, never handed to
  `shutil.rmtree` (which raises `OSError: Cannot call rmtree on a symbolic link`).
- `shutil.rmtree` does not follow symlinks it encounters while walking a
  genuine nested directory, so a symlink inside pointing outside only has
  the link removed, never its target — confirmed with a test.

**Tests added** (`tests/unit/daemon/test_validation.py`,
`TestCheckForNestedInstallation`):

- `test_cleans_up_nested_install_even_when_outer_has_pyproject` — replaces
  the old `test_returns_none_when_outer_hooks_daemon_is_the_repo`, which
  pinned the deleted exemption (asserted the inner dir survived; now asserts
  it is removed).
- `test_leaves_self_install_layout_alone` — the self-install repo layout
  (project root has `pyproject.toml` plus a
  `.claude/hooks-daemon/bin/hooks-daemon` symlink, Plan 00455) has no outer
  clone at all, so the nested path never exists there.
- `test_unlinks_nested_install_when_it_is_itself_a_symlink`
- `test_rmtree_does_not_follow_a_symlink_inside_the_nested_dir`

**Callers checked** (grep, since LSP `findReferences` was not available to
me): `daemon/cli.py::_validate_installation` and
`validation.py::validate_not_nested` are the only two callers; neither
relied on the exemption. `install.py::_validate_not_nested` (the sibling
Python pre-flight check) was read and carries **no** copy of the exemption —
it already raises unconditionally. The *other* check in
`install.py::validate_installation_target` step 1
(`_project_root_is_daemon_repo`) is a different, correct use of the same
pyproject-name detection (Plan 00455) and was left alone, per your
instruction.

## N18 — `untracked/venv` symlink LSP.md relies on but nothing creates

Added `_ensure_self_install_lsp_venv_symlink` beside
`_ensure_self_install_cli_symlink` in
`src/claude_code_hooks_daemon/core/project_context.py`, called from
`ProjectContext.initialize()`'s self-install branch. It derives the venv
from `sys.prefix`, only acts when that venv resolves to a direct child of
the project's own `untracked/`, and — unlike the CLI symlink — **repoints**
an existing symlink when it goes stale (atomic: temp symlink +
`Path.replace`). A non-symlink at the path is left untouched. Failures are
logged at WARNING and swallowed (an `error_hiding_exclusions.json` entry was
added, matching the sibling `_ensure_self_install_cli_symlink` entry).

Used the name `untracked/lsp-venv`, not `untracked/venv`: the latter is the
retired pre-v3.7.0 `LEGACY_VENV` path bound by `install_version.sh`,
`upgrade_version.sh`, `paths.py` and `llm_qa.py`, and `lsp-venv` matches
neither that exact name nor the `venv-*` prefix the skill,
`eager_cleanup_stale_venvs` (`scripts/install/venv.sh`) and
`_enumerate_venvs`/`prune-venvs` (`daemon/cli.py`) scan for — confirmed by
reading each, not just by construction. No cleanup exemption was needed
anywhere.

`pyrightconfig.json`'s `venv` key changed from `venv` to `lsp-venv`;
`tests/unit/test_pyright_config.py` updated to match.
