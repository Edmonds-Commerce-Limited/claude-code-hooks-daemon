## 22:05 · finding · — — filed from a lever Plan 00341 reached and left alone

Plan 00341's whole argument was that an ADVISE finding is not enough: one fired
on commit `923fd583` and the plan it named stayed `Not Started` for five days
anyway. So 00341 shipped a BLOCK-level finding — and then had to record that
this changes nothing today.

`PlanQaCommitGateHandler.handle()` filters `finding.level == Level.BLOCK`, but
only DENIES when `self._plan_qa.commit_gate_mode == _MODE_BLOCK`. This project
runs `warn`, and the warn path passes EVERY finding — block and advise alike —
through `format_advisory()`. So the gate's entire BLOCK tier is currently
decorative, and adding more BLOCK checks cannot change that.

The config comment says "warn-first rollout; flip to block after clean
dogfooding", which is a decision nobody has ever come back to make. That is
itself a small instance of the rot 00341 is about: a document promising a
state that does not exist.

**Filed separately rather than folded into 00341 on purpose.** The flip arms
every commit-stage check at once, not just the one 00341 added, so its blast
radius belongs to the subsystem rather than to one check — and flipping it as
a side effect is exactly the over-reach a warn-first rollout exists to prevent.

Phase 1 is deliberately a replay rather than a judgement, because the same
technique already earned its keep once: 00341 Task 2.1 replayed 250 commits
and the result CHANGED the rule (it exposed a 25% false-positive shape that
argument had missed).

Cron: reused the session's existing failsafe recovery cron `5398b3f9` — one
per session, never one per plan. Nothing created.

## 18:05 · finding · P1 — the replay says no, and says it precisely

Built `untracked/scratch/replay_commit_gate.py` and ran every commit-stage
check over the last 250 commits. **18 would have been DENIED; 8 of those are
false positives (44%), and all 8 are one shape.**

The harness matters as much as the number. Plan 00341's replay read each
plan's status as it is TODAY; this one materialises each commit's own
`CLAUDE/Plan` tree with `git archive` and answers `gitfacts` from that commit
against its parent, so every check sees the tree it would actually have seen.
On the identical rule and corpus that changes `same-commit-plan-doc` from 2
fires to 8 — the earlier count was measuring a tree that had since been
repaired. Worth remembering the next time a replay looks reassuring.

```

commits that would be DENIED: 18

     1  index-at-birth
```

The false positives are all **whole-tree** checks: `_run` walks
`context.tree` / `context.readme` and never once consults
`gitfacts.staged_changes()`. Six commits were denied over a stale README row
for `00311-v3590-release-review-followups`; they are supervisor and
venv-resolver work and not one of them touches a file mentioning 00311. Two
more were denied over plans 00304/00302 left in the active root with a
terminal header, again untouched by the commits blamed.

## 18:10 · decision · P2/P3 — not yet, because these checks are STICKY

The 44% is the smaller half of the problem. A whole-tree false positive does
not cost one retry — it denies EVERY subsequent commit until somebody repairs
the unrelated state. The 00311 row survived at least six commits, so flipping
would have wedged six pieces of ordinary work over one mistake nobody
had noticed.

So: not flipped, and the reason is a measurement rather than nerves.

The remedy was already in the repository, which is the part I did not expect.
`index-row-length._worsens` decides this exact question at EDIT stage and its
docstring states the principle outright — "an already-degraded index is never
trapped". Its own `_run_tree`, the path that runs at COMMIT, never adopted it.
Phase 3 is therefore not a new idea; it is applying the project's existing
answer to the five or six places that were written before it existed.

Phases 3 and 4 added to the plan. The bar for Phase 4 is deliberately ZERO
false positives rather than "fewer": stickiness means a low rate is not a low
cost.

## 18:40 · finding · T3.4 — the survey found no check that was already safe

Task 3.4 was written allowing for the answer "leave them, their findings
cannot be pre-existing". Not one of the four qualified.

- `no-new-collisions` was the sharpest. Its module is literally named
  `no_new_collisions`, its docstring says "catch it before it lands", and
  `_run` reported every collision in the tree with no reference to the staged
  changes at all. The name was right; the code never implemented it. That is
  worth more than the fix — a check whose name states a scope it does not have
  reads as safe to everyone who greps for it.
- `index-row-length` had the remedy in the same file. `_worsens` is used by
  `_run_edit` and ignored by `_run_tree`, so the commit path blocked on any
  over-limit row — including on the commit shortening it.
- `stats-recount` needed a DIFFERENT predicate, which is why a single generic
  helper would have been wrong. Its finding is about a COUNT, and editing a
  `PLAN.md` in place cannot change what the recount produces; only adding,
  removing or moving a folder can. Hence `commit_changes_the_folder_set`
  alongside `commit_touches_plan`.
- `structure-archive-dirs` is the one place the answer is genuinely mixed, and
  it is recorded rather than smoothed over. Its misplaced-FOLDER finding is
  attributable and now narrows; "no README index" and "no completed archive"
  do NOT, and stay unconditional. They are not about a plan, they are about
  the plan directory working at all — with no README, `context.readme` is None
  and half the suite silently no-ops. Waving that through would be worse than
  a blocked commit.

Every narrowing went RED first, and the REDs were informative rather than
ceremonial: in each file the pre-existing-state test failed while the
this-commit-caused-it test and the sweep test passed untouched. That is the
shape that proves the new tests discriminate, rather than just asserting the
new behaviour.

## 19:05 · finding · T1.3 — correction: 7 false positives, not 8

Phase 1 classified `42eb19da` as a false positive because it was denied over
the same stale 00311 README row as five other commits. It is not one. After
the narrowing it was STILL denied, which is the only reason I checked:

```
git show 42eb19da^:CLAUDE/Plan/README.md | grep -c 00311-v3590   -> 0
git show 42eb19da:CLAUDE/Plan/README.md  | grep -c 00311-v3590   -> 1
```

That commit CREATED the broken row. It is the one commit that SHOULD be denied
over it, and the five that inherited it are the ones that should not.

So the real Phase 1 figure is 7 of 18 (39%), not 8 of 44%. The commit message
for the Phase 1-2 commit carries the old number; pushed history is not
rewritten, so the correction lives here and in PLAN.md.

Worth naming the mistake rather than just the number: I grouped the six
denials by SYMPTOM (all cite the 00311 row) instead of by CAUSE (who wrote it).
The fix disagreeing with the measurement is what exposed it — which is a
decent argument for implementing a narrowing rather than only reasoning about
one.
