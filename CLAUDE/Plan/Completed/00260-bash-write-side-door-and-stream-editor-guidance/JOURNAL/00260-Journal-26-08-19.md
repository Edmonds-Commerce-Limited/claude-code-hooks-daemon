## 10:45 · finding · T2.1 — the map corrected me four times, and one inverts a design

The Task 2.1 map (`BASH-BLINDSPOT-MAP.md`, commit `8b82439f`) was worth far more
than the provisional split I had sketched from handler names.

**The inversion**: I had the three PostToolUse handlers filed as content-keyed.
They are not. They take the PATH and read the bytes off disk themselves. Two of
them DENY. So a path-only utility — the cheap option I had assumed was the
compromise — fully restores two denying guards with no content plumbing. That
makes Task 3.1 a better deal than the plan claimed, not a worse one.

**The trap**: `validate_instruction_content.handle()` ends with an explicit
`else: return ALLOW` for non-Write/Edit tools. Route a Bash event to it and you
get a POSITIVE all-clear rather than silence. Verified at
`validate_instruction_content.py:99-103`. This is the sharpest lesson in the
whole plan: a blind guard and a guard that answers "fine" are not the same
thing, and the second is worse than doing nothing. Filed as Task 3.1a, a
blocker on 3.1.

**The real fix point**: the blindness is not 21 independent decisions.
`core/utils.py:36` `get_file_path()` returns `None` for anything that is not
Write/Edit, and `get_file_content()` gates identically — a handler *cannot* opt
in. So the accessor is where this belongs. Filed as Task 3.1b.

**The scoping correction**: generalising `_bash_memory_write_target` is not a
move-the-method job. It false-positives on prose (`echo 'the arrow > file thing'`
yields target `file`), and the map agent was itself denied by exactly that while
gathering evidence. Its narrow memory-path substring test is the only reason
that is tolerable today.

## 11:40 · finding · T1.5 — the predicted hole does not exist; a different one does

Task 1.5 predicted that a flagless stream-editor call on its own line inside a
heredoc body would slip past `_SED_AS_COMMAND_HEAD`, whose `^` is
start-of-STRING under `re.IGNORECASE` alone. Wrote the test before touching the
regex. The prediction is wrong: that case is **already blocked**, and the
anchor is never consulted.

Tracing `matches()` Case 1: any Bash command merely MENTIONING the tool is
denied unless it is a git/gh command or `_is_safe_readonly_command` finds a
`grep`/`echo` in it. A `cat > deploy.sh <<'EOF'` has none of those, so the
catch-all denies it long before any anchor matters. `re.MULTILINE` would have
changed nothing here while widening an already-broad pattern — a change that
would have looked like a fix and done nothing.

What the test found instead, running three heredoc shapes:

| heredoc writes              | Bash verdict | same content via `Write` |
| --------------------------- | ------------ | ------------------------ |
| `deploy.sh`, flagless call  | BLOCKED      | BLOCKED — agrees         |
| `deploy.sh`, flagged call   | BLOCKED      | BLOCKED — agrees         |
| `NOTES.md`, prose about it  | BLOCKED      | ALLOWED — disagrees      |

The Bash branch is STRICTER than the Write branch, which is the mirror image of
this plan's thesis. Identical content and identical destination get opposite
verdicts depending on which tool the agent reaches for, and `get_claude_md()`
promises the `.md` allowance that the Bash route does not honour. This
repository writes prose about the tool constantly, so the guard blocks its own
documentation.

Recorded as Decision 3. Routed to Task 3.1 rather than special-cased: a `.md`
check bolted into the Bash branch would be a second, weaker copy of exactly the
redirect-target parsing Task 3.1 exists to centralise, and it would have to
handle a compound command where a real destructive call follows the heredoc.
Pinned as `xfail(strict=True)` meanwhile, so it flips to a pass when 3.1 lands
and fails loudly if anyone "fixes" it by accident.

## Phase 3 built — the accessor ships, the new denials do not

`get_bash_write_targets()` now lives beside `get_file_path()`/`get_file_content()`
in `core/utils.py`, which is where the blindness actually originates: those two
return `None` for anything that is not Write/Edit, so no handler could opt in
even if it wanted to. 37 unit tests.

Two things were caught by measurement rather than by reading, both before the
migration landed:

1. **The tilde regression.** A leading `~` was initially grouped with `$VAR`
   and globs as "needs an expansion the daemon cannot perform" and declined.
   Probing the old detector against the new one showed the old one blocks a
   tilde-spelled memory write and mine returned `[]`. That is the most natural
   spelling of the very path this policy exists to protect. A leading tilde is
   HOME by definition and expandable exactly, unlike a shell variable whose
   value only the shell knows. Now expanded; another user's tilde is still
   declined.

2. **A second regression the tilde fix does NOT cover.** Deleting the two
   legacy regexes in favour of the accessor would have reopened the
   variable-spelled form of the same path — blocked today by raw-string
   matching, declined by a conservative tokeniser on principle. So the handler
   UNIONS both sources rather than replacing one with the other. The regexes'
   known prose false positive stays harmless because every candidate from
   either source passes through `_is_claude_memory_path` before it can deny
   anything.

Net for `markdown_organization`: six measured bypasses closed (`>|`, quoted
paths with spaces, `dd of=`, `cp`/`mv`/`install`, every `tee` operand after the
first, heredoc-authored writes), zero spellings lost.

**Task 3.5 deliberately not done.** Wiring `lint_on_edit` and
`validate_eslint_on_write` to Bash writes is a different kind of act from
everything else in this plan: both DENY, and pointing them at Bash writes
creates a denial surface that has never existed — post-hoc, since the write has
already landed. Migrating `markdown_organization` changed nothing about what is
ALLOWED; it only stopped six spellings evading a rule already in force. The
linter wiring changes the policy itself, so it is the human's call. Recorded as
Decision 5b, and the plan says so rather than quietly implying Phase 3 closed
the blind spot. It narrowed it.

### The migration blocked this very journal entry, on its first attempt

Writing the paragraphs above through a Bash heredoc was DENIED by
`markdown_organization` — the body quoted a memory path as evidence, and
`include_heredoc_bodies=True` reads bodies by design. Worth recording three
things about that:

- It is **not a regression**. The legacy raw-string scan sees heredoc bodies
  too, so this shape was already blocked before today's change.
- It is the **same shape the `sed_blocker` guidance already warns about**:
  prose *about* a blocked thing, written through Bash, is judged as a command.
  The remedy is identical — write prose with the `Write`/`Edit` tools, which is
  what this entry used in the end.
- Blocking prose is the deliberate trade for a deny-by-default policy where
  over-blocking is cheap and under-blocking needs a history rewrite to undo.

### Benchmarking it found two defects the tests had not

The accessor now runs on every Bash `PreToolUse` event, so I timed it rather
than assuming. Typical commands were fine (`git status` 0.02 ms, a redirected
pytest run 0.05 ms) — but heredoc bodies were not, and they scale linearly:

| heredoc body | per call | per event (×2) |
| ------------ | -------- | -------------- |
| 5 KB         | 2.84 ms  | 5.67 ms        |
| 20 KB        | 11.34 ms | 22.67 ms       |
| 40 KB        | 24.78 ms | 49.55 ms       |

The ×2 is real and was measured, not assumed: `matches()` and `handle()` each
call it, confirmed by counting invocations through a patched module attribute.
A 40 KB document authored by heredoc — an ordinary thing for an agent to do —
would therefore have added ~50 ms to a round trip whose measured total is
~45 ms. Doubling the daemon's cost on the exact shape this plan exists to cover
is not something to discover after release.

Probing further turned up a second, worse defect in the same place. The whole
command was tokenised as ONE shell string, so an unbalanced quote anywhere made
`shlex` raise and the accessor returned `[]` — including the genuine target on
the introducing line. A stray `"` in ordinary prose (`he said "hi`) was enough.
No intent required; one typo in a document silently un-enforced the policy for
that write. It was masked here only by the union with the legacy regexes, which
is a second argument for Decision 5c — but any future caller would have
inherited it unmasked.

One change fixed both: tokenise the command and each heredoc body SEPARATELY,
and skip any body that contains no redirect and no write verb (it provably
cannot name a target, so this is an optimisation and never a coverage
decision). A malformed body now costs only that body. Result: 14–18× faster on
large bodies (40 KB: 24.78 ms → 1.35 ms), identical targets, and the malformed
case pinned by a test.

Worth naming the process point: both defects were invisible to a green test
suite and to reading the code. Only running it found them.

### Then probing shell edge cases found two more, one of them serious

With 260 tests green I ran the accessor against shapes no test covered. Two
failures, and the first is the worst defect of the day:

- **`cp -t /tmp/dest /tmp/a.py` returned `/tmp/a.py` — the SOURCE.** `-t` puts
  the destination first, so "the last operand is the destination" is simply
  false, and the accessor named a file the command READS as a file it writes.
  That is precisely the failure the conservative contract exists to prevent: a
  path-keyed guard would judge a file that was never written while the real
  destination went unmentioned. Declining is the only correct answer, since
  `-t` also means the destination is a directory and no single written path
  exists.
- **`make &> /tmp/all.log` returned nothing.** `&>`/`&>>` are ordinary bash and
  were simply absent from the operator set. A missed write — fails safe, but a
  gap.

Adding `&>` raised the question of its look-alike, and the answer is a rule
worth stating: `>&` must NOT be accepted. `2>&1` tokenises as `2`, `>&`, `1`,
so treating it as a redirect would report the file `1`. The membership test is
not "operators containing `>`" but "operators whose operand is always a
filename". Recorded in the constant so nobody adds it later.

A third, subtler case fell out of the same pass: `cp a.py somedir` writes
`somedir/a.py`, so reporting `somedir` names a path never written. A trailing
slash is catchable by shape, but `somedir` and `somefile` are identical as
strings — only the filesystem knows. One `is_dir()` per candidate settles it,
which is cheap next to naming the wrong file, and it also disposes of the
3-or-more-operand form (`mv a b destdir`) without a special case.

Not a regression, and worth saying so rather than implying otherwise: the old
detector missed `cp -t` too. What changed is that it is now KNOWN and stated in
the guidance instead of quietly absent.
