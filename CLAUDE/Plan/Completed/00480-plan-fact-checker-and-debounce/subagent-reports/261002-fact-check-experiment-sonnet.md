## REFUTED (most consequential first)

### R1. "Changing the ccy supervisor. It is outside this repository, and its live instance is not touched." (Non-Goals) and Task 4.5 "the ccy change lives outside this repository"

- The supervisor is in this repository: `.claude/ccy/claude-supervise.py`, `CLAUDE/development/CcySupervisor.md`, `.claude/rules/ccy-supervisor-dogfooding.md`, `src/claude_code_hooks_daemon/install/ccy_supervisor.py`, `utils/ccy_supervisor.py`, `handlers/session_start/ccy_supervisor_integrity.py`, `handlers/status_line/supervisor_indicator.py`, and tests under `tests/unit/supervise/` (about 50 files).
- The repository's own history agrees. Commit f1592f146 is titled "correct Task 4.5; the ccy supervisor is in this repository, so the pause compact is built there". CcySupervisor.md documents the `/compact` injection rules.
- The claim was a confident, unsearched negative. A search for "supervis" in `git ls-files` would have found it.
- Consequence: the Non-Goal and the Supervisor-side half of Task 4.5 (an interface spec plus an issue "for the supervisor's owner") are wrong. The compact-without-continue change is in-repo work, done TDD against tests/unit/supervise. The plan's scope and the owner's review depend on this.

### R2. Task 4.2: PreToolUse denial "with `continue: false` and a `stopReason`, so a turn already running halts at its next tool call"

- `PRE_TOOL_USE_SCHEMA` (`src/claude_code_hooks_daemon/core/response_schemas.py:23-47`) allows only `hookSpecificOutput`, with `additionalProperties: false` at the top level. Top-level `continue` and `stopReason` are not permitted there.
- `hook_result.py` routes PreToolUse to `_format_pre_tool_use_response`, not to `_format_continue_false_response`. The continue-false path is used for the `_CONTINUE_FALSE_EVENTS` set (lines 496, 638); the plan does not show PreToolUse is in that set.
- Consequence: the daemon cannot emit this today. The plan is silent on this, though it is a prerequisite: the response schema and the formatter need extending first, or the "halt the running turn" goal is unmet. Whether Claude Code honours `continue:false` from PreToolUse is external and UNVERIFIABLE-HERE.

### R3. Overview: "and nothing reads them" (the rate_limits fields)

- Mostly true for behaviour, but the claim needs qualifying. `src/claude_code_hooks_daemon/handlers/status_line/multithread_indicator.py:21,81` mentions `rate_limits` in comments only. No code reads `rate_limits`, `five_hour` or `seven_day`.
- Judged VERIFIED in substance (see the table). Listed here only because `CLAUDE/Architecture/StatusLine.md:185` already states `rate_limits.*` is "documented but currently UNUSED", which Task 1.1 would update.

### R4 (partial). Task 4.3: "unattended-mode Stop blocking, stop-explanation re-entry" as separate handlers that force continuation

- Both behaviours live in a single handler, `handlers/stop/auto_continue_stop.py`. Line 3: it intercepts all Stop events except re-entry and AskUserQuestion. Re-entry is detected with `stop_hook_active` plus a transcript marker (lines 613-640).
- The only other handlers in `handlers/stop/` are `cron_stop_enforcer.py` and `teammate_reap_advisor.py`. There is no separate "stop-explanation" handler.
- The text is loosely true, but implementers may look for two components. The pause must stand down in `auto_continue_stop` (one place), `cron_stop_enforcer` and `cron_subagent_stop_enforcer`. Also, `cron_pause.py` already exists (see below), which the plan does not mention.
