# CI wall-clock: can sharding across runners help? (plus Actions gap audit and ARM runners)

Read-only investigation, 2026-11-07. Repo is PUBLIC (`gh repo view`), so standard runners are free and unlimited minutes (concurrency capped by plan).

## Headline

Sharding is ALREADY done where it pays: `release-gate.yml` (Plan 00476) shards the whole gate across 15+ jobs. `qa.yml` is the slow path for ordinary pushes, and its slowness is almost entirely ONE serial step: the pytest run (mapped tests, or the whole suite when the mapper cannot map a file). The cheapest big win is not "4 runners each take a quarter" of llm_qa checks (they total about 9 minutes); it is reusing the shard layout release-gate already has for qa.yml's full-suite fallback and nightly matrix, and enabling `pytest-xdist` inside a shard only after proving isolation.

## 2. What each step runs

- `llm_qa.py` (scripts/qa/llm_qa.py, 3147 lines) takes check names as positional arguments (`./scripts/qa/llm_qa.py docs_qa plan_qa changed_tests --range ...`, and release-gate passes ~20 names per group), plus selectors `all` and `changed`. So YES, a subset is already supported and release-gate.yml uses it (env lists `CHECKS_STATIC`, `CHECKS_PYRIGHT`, `CHECKS_DOCS`, `CHECKS_CONTRACTS`; the `layout` job fails if the lists drift from `llm_qa.ALL_TOOL_NAMES`).
- qa.yml code tier: black, ruff, mypy, pyright invoked directly, then `llm_qa.py changed --range` (selects checks and mapped tests by `scripts/qa/changed_tests_map.yaml` via `run_changed_tests.py`), then `full_suite_if_unmapped.bash` (asks the mapper with `--select-only`; if `.unmapped` is non-empty, takes the host-wide full-QA flock, restarts the daemon, runs the entire suite serially), then bandit and deptry.
- qa.yml full tier: the same static steps, then `pytest tests/ -m "not perf_sweep" --cov=src --cov-fail-under=95` serial, then `pytest .claude/project-handlers`.
- xdist: NOT used. `pytest-xdist` is not in pyproject dev extras or uv.lock; `grep xdist` finds nothing outside a comment ("no xdist" in perf-sweep). pyproject has a comment that `coverage parallel = true` was disabled because it "causes fork bomb when running pytest with --cov". addopts forces a custom `-p claude_code_hooks_daemon_full_qa_gate_loader` plugin that refuses whole-suite-sized runs without the host-wide full-QA flock; with xdist workers the collected-count heuristics and the flock would need checking.
- Test layout: `scripts/qa/test_shards.yaml` defines 7 shards (unit-handlers, unit-daemon, unit-core, unit-features, unit-tooling, integration, acceptance-and-other), enforced by `tests/unit/qa/test_suite_shards.py` (every test file in exactly one shard). `scripts/qa/run_test_matrix.py --shard X --coverage` runs them; coverage data lands in `untracked/qa/.coverage.<shard>` and is combined by release-gate's `coverage` job (artifact download, `coverage combine`, `coverage report` with fail_under 95).
- Cores: public-repo `ubuntu-latest` has 4 vCPU, 16 GB RAM, 14 GB disk (private repos get 2 vCPU). So `-n 4` would be the ceiling for xdist per runner.

## 3. Designs and estimated savings

### (a) Matrix over llm_qa checks

Already exists in release-gate (4 groups). For qa.yml code/docs tier, the checks run is about 9 min total of which pyright (89 s) and black (53 s) dominate; splitting would save at most 2-3 min of ~9 and cost a fresh setup (Install, uv sync, Swift warm: about 1.5 min) per leg. Net saving 1-2 min, so NOT worth it on its own. Saving: low (\<2 min).

### (b) Pytest sharding (the real win)

Option b1, reuse the existing 7 shards in qa.yml's full-suite fallback and nightly. Replace the serial pytest by a matrix `include:` of shard groups, exactly as release-gate's `tests` job does (coverage legs on one Python; combine job). Estimated: full-suite fallback drops from about 30-45 min to the slowest shard, about 15-30 min on the current split (integration alone 1800-2900 s), and about 9 min static work overlaps. Nightly 3-Python matrix: wall clock from 73-116 min to about 35-50 min (already what release-gate does: 49 min).
Option b2, rebalance. Integration (about 258 files) is 2-6x the next largest shard and sets the floor. Split it by directory or with `pytest-split --splits N --group K` using a committed `.test_durations` file (`pytest --store-durations`; refresh monthly). With integration in 2-3 pieces and acceptance-and-other at 8 min, the floor becomes about 15-20 min (unit-handlers is 16-27 min with coverage, so split it too). Estimated critical path 15-20 min. Saving over b1 about 10 min.
Option b3, `pytest-xdist -n 4` inside each shard. Possible 2-3x on the unit shards (CPU-bound, 1150 files), but riskier: integration/acceptance tests spawn daemons and hit shared sockets; `perf_sweep` timing tests already fail under load; the repo-wide fork-bomb note around coverage parallel; fixtures with session-wide state; the full-QA gate plugin. Do it only for unit shards, as an experiment on one leg. Estimated: unit shards 1200-1650 s to about 500-700 s. Combined with b2, critical path would be set by integration pieces.
Coverage across runners: already solved by release-gate: each coverage leg uploads `untracked/qa/.coverage.<shard>` (`include-hidden-files: true`), a `coverage` job downloads with `merge-multiple: true`, runs `coverage combine --keep` and `coverage report` (fail_under 95 from pyproject). With pytest-split or xdist, set `coverage run parallel=true` only in CI via `COVERAGE_PROCESS_START`/`--cov` with per-process data files and `relative_files = true` so paths match across runners. Note combined-coverage with branch mode needs identical source paths; checkout path is the same on all runners.

### (c) Caching

- pip: `cache: pip` is already set, but the cache key is only `requirements*.txt`/`pyproject`-hash style; installs go through `uv sync --frozen`, so the pip cache is mostly unused. Better: cache uv (`astral-sh/setup-uv` with `enable-cache: true`, keyed on uv.lock). Saves about 30-60 s per job times 15+ jobs (minutes cost, wall time is small).
- The venv lives under `untracked/venv-<slug>-py<MM>-<hash>/`; caching that directory keyed on `hashFiles('uv.lock')` plus Python version could cut Install from about 90 s to about 15 s. Moderate.
- mypy cache (`.mypy_cache`) and pyright: mypy takes only 14 s here, pyright 70-96 s (node + analysis; not cacheable in a meaningful way). Skip.
- Relay (Rust, `relay/build.sh`): 5 s warm in qa.yml, but 471 s on the slow runner in 42051589880 (rustup target add + cargo cold). Cache `~/.cargo` and relay target dir keyed on `relay/hooks_relay.rs`+build.sh, or pre-install musl target via `dtolnay/rust-toolchain`. Saves variance more than median.
- Swift and Go "warm" steps: 22-42 s normally, 923 s in one outlier. They exist because `lint_on_edit` has a 15 s budget on a cold toolchain. Cache not applicable (runner-image toolchain); keep.
- hooks-screen Rust build: not run in CI today (no `screen/build.sh` in workflows).
  Estimated total wall-clock saving from caching: 1-2 min per job, no change to the critical path unless sharded.

### (d) Serialisation that can run concurrently

- Within `targeted`: black, ruff, mypy, pyright, bandit, deptry and `llm_qa.py changed` run strictly one after another in one job (about 9 min of mostly independent work). A static job (black/ruff/mypy/pyright/bandit/deptry, about 4 min) in parallel with the test job would cut the code-tier pre-test chain by about 3-4 min; and pyright (89 s) could be started in the background. Job-name change implications in section 7.
- Full-suite fallback runs AFTER targeted QA (6 min) inside the same job though the fallback makes the targeted pytest redundant for unmapped changes; skip the mapped run when unmapped is non-empty. Saves about 6 min on exactly the slow case. Easy win.
- Perf sweeps, shell, daemon-load already run as sibling jobs.
- release-gate: `layout` gates everything but takes 12 s; fine.
- Warm steps (Swift, Go) are serial in `targeted` (about 30 s); could be backgrounded.

### Trade-offs

- Runner minutes: public repo, free, so minutes cost is irrelevant (private-repo equivalent of the 15-job release-gate is roughly 3x the minutes of a serial run due to repeated setup). Concurrency cap on the free plan is the constraint: 20 concurrent jobs on Free, 40 on Pro, 60 Team, 500 Enterprise. A 15-job gate plus a concurrent QA run can queue.
- Flakiness from concurrency: the LOCAL collisions (daemon sockets under `untracked/daemon-*.sock`, shared `.mypy_cache`, the host-wide full-QA flock) are per-checkout/per-host. Separate runners are separate VMs with separate checkouts, filesystems, sockets and caches, so they do NOT collide across runners. They DO apply inside one runner if you add xdist or run two steps concurrently in one job (b3, d). So sharding across runners is the safe axis; xdist inside a runner is the risky one.
- Setup overhead: each extra runner repeats checkout (fetch-depth 0, up to 275 s on a slow runner), Python setup, `uv sync`, and, for daemon legs, daemon start, relay build and toolchain warm. Gains flatten after about 6-8 shards.
- Variance: runner-to-runner speed differs by 1.5x (3.12 leg 6946 s vs 3.11 4372 s same code; release-gate 3.12 rest 2845 s vs 4644 s). More shards means the max of more samples, so the tail grows.

### Required checks and branch protection

Branch protection is a repo setting: UNVERIFIABLE from files (`gh api` for it was not run). From the files: release-gate.yml deliberately funnels everything through ONE aggregator job `Release gate` (needs all others), so shard additions or renames there need no protection change. qa.yml has NO aggregator: its jobs are `Classify change`, `QA (docs or code tier)`, `QA (Python3.11/3.12/3.13)` (matrix names), `Performance sweeps`, `Shell`, `Daemon load`. If any of those are required checks, renaming or splitting them (e.g. a matrix `QA (docs or code tier)` into shards) leaves the old name pending forever and blocks merges. Also the existing skip-by-tier pattern (the targeted job vs qa job are mutually exclusive) means required checks must tolerate "skipped", which GitHub counts as passing only if the check is skipped via job `if`, not a skipped matrix. Recommendation: add a single `QA gate` aggregator job to qa.yml (`needs:` all others, `if: !cancelled()`, `jq -e 'all(.[]; .result=="success" or .result=="skipped")'`), make THAT the only required check, then freely reshape the jobs behind it.

## 4. Recommendation

Do, in this order:

1. Add the qa.yml aggregator job `QA gate` and switch branch protection to it (prerequisite for everything; low risk).
2. Skip the mapped-pytest step when the mapper reports unmapped files, so the fallback does not run after a redundant 6-min targeted run (about 6 min on the slow case).
3. Make qa.yml's full-suite fallback and nightly use the release-gate shard matrix (b1) via a reusable workflow (`workflow_call`) shared with release-gate, so one definition serves both. Expected: fallback 30-45 min to about 15-30 min; nightly 73-116 to about 40-50 min.
4. Then rebalance the `integration` shard with pytest-split (b2) to reach about 15-20 min; try xdist only on unit shards.

FIRST STEP: add the aggregator job to qa.yml (a few lines, mirroring release-gate's `release-gate` job) and change the required check to it; no timing risk, and it unlocks step 3 without branch-protection breakage. Fastest actual speed-up for the owner's pain point (the 30+ min code-tier step): step 2.

## 6. ARM runners

Sources:

- GitHub changelog, GA for public repos: https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/
- Public preview announcement (Jan 2025): https://github.blog/changelog/2025-01-16-linux-arm64-hosted-runners-now-available-for-free-in-public-repositories-public-preview/
- Runner reference: https://docs.github.com/en/actions/reference/runners/github-hosted-runners

Confirmed:

- Hosted arm64 Linux runners exist. Labels: `ubuntu-24.04-arm`, `ubuntu-22.04-arm` (also `windows-11-arm`). They are generally available (August 2025) for PUBLIC repositories.
- Cost and availability: free and unlimited minutes for public repos on these standard arm64 runners, subject to the plan's concurrency limits. The standard `-arm` labels do NOT work in private repositories (jobs stay queued); private repos need paid larger runners configured with an arm64 image, billed per minute. This repo is public, so cost is zero here; the client team's repo status decides their cost.
- Hardware per docs' table: 4 vCPU, 16 GB RAM, 14 GB SSD (same as x86_64 public `ubuntu-latest`). The image is Ubuntu 24.04 arm64. Not verified by me: Swift and Go presence on the arm image (the qa warm steps guard on `command -v swiftc/go`, so they degrade gracefully).

How this repo would use them:

1. Test-suite leg: add `runs-on: ${{ matrix.runner }}` with `runner: [ubuntu-latest, ubuntu-24.04-arm]` to a Python leg. Cheapest design: add ONE extra leg to release-gate's `tests` matrix (and the nightly qa matrix): `py3.13 arm64 unit+rest` using the `unit` then `rest` shard groups without coverage. Expect the same 25-45 min as a x86 leg; shard it like the x86 legs if on the critical path. Uses uv from uv.lock (`uv sync --frozen` resolves aarch64 wheels, which exist for pydantic, psutil, pyright's node, semgrep; `semgrep` and `pyright` wheels on aarch64 are the likeliest friction; check `uv sync` in a throwaway PR). Make the new leg non-blocking initially (`continue-on-error: true` or leave it out of the aggregator's `needs`) until stable. Note the `layout` job's by-Python shard check would need to accept an arch key. Tests that assume x86_64 (relay binary name `hooks-relay-x86_64-unknown-linux-musl`, `RELAY_TARGET` default, `rustup target add x86_64-unknown-linux-musl` in workflows lines 179 and 318) will fail or skip and must be made arch aware, exactly the area issue #174 touched.
2. Native builds, CI check: a small `native-builds` job with matrix `{runner: ubuntu-latest, target: x86_64-unknown-linux-musl}`, `{runner: ubuntu-24.04-arm, target: aarch64-unknown-linux-musl}`. Steps: `rustup target add $target`, `RELAY_TARGET=$target bash relay/build.sh` (relay/build.sh already honours `RELAY_TARGET`, default x86_64 musl), `SCREEN_TARGET`-aware `bash screen/build.sh` (default now derived from `uname -m`: `aarch64|arm64` selects `aarch64-unknown-linux-musl`, line 27), then a smoke run of each (`--version` or the relay test in `relay/test_relay.py`). On a native arm64 runner musl needs no cross toolchain beyond the target (static linking via rust-lld/musl-gcc is only needed for crates with C; vendored `screen/vendor` crates may need `musl-tools`; add `sudo apt-get install -y musl-tools` if the build asks). This replaces cross-compilation, which is the usual failure source. Today CI builds only the x86_64 relay and never builds hooks-screen, so a broken aarch64 target would currently ship undetected.
3. Release assets: today `scripts/release/build_relay_release_assets.sh` (run locally by `/release`) produces only `hooks-relay-x86_64-unknown-linux-musl` and `SHA256SUMS`. Proposed: a tag-triggered `release-assets.yml` with the same two-leg matrix producing `hooks-relay-<triple>` and `hooks-screen-<triple>`, a merged `SHA256SUMS` (a final job downloads both artifacts, `sha256sum`s, uploads to the release), and `actions/attest-build-provenance` for each binary.
