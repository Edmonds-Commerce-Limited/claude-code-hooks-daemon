## 18:01 · decision · N1 — the ownership question answered itself

N1 was recorded as an ownership call: track `.claude/ccy/CLAUDE.md`, or stop the
two tracked documents promising it. It read like a judgement, and it was not —
both branches were closed by evidence already on disk.

Tracking it is impossible. `.claude/ccy/.gitignore` says so in its own comment:
ccy's startup gate refuses to launch when anything in `.claude/ccy/` is tracked,
and prescribes `git filter-repo` plus a force push as the only remedy. The full
defect report for the ccy maintainers sits in
`untracked/fedora-desktop-ccy-CLAUDE-bug.md`, written after following that advice
caused a cascading outage.

Rewriting the file in place was ruled out for a different reason, found by
looking rather than assuming: it is 4,935 bytes at the same mtime as
`/root/.claude/CLAUDE.md` — ccy bind-mounts it as the owner's GLOBAL instructions
for every project. An edit here would have silently changed unrelated projects'
behaviour. That is the kind of side effect that is invisible until it is
expensive.

So the repo side moved: `CLAUDE/development/CcySupervisor.md`, registered in the
development routing table, with both pointers repointed. Proved the way the
defect was found — `git ls-tree HEAD` shows all three files present, so a fresh
clone now receives the target as well as the pointers.

The lesson is worth more than the fix: **a canonical home must be one the reader
actually receives.** An untracked canonical is invisible exactly where the reader
most needs it — and invisible to the checkout that would have reported it, which
is why `docs_qa` was clean on main and complained in a worktree.

## 18:01 · finding · N2 — the loop found a fix that had been silent for three days

N2 came out of the issue-SDLC loop from Plan 00384, and it is the best evidence
so far that the loop earns its cost.

Triaging issue #36 turned up a fix that already existed. The timing is exact:
the issue was filed at `16:25:38`, the fix landed in `a8111e72` at `16:43:34` the
same day, and the plan was archived at `17:02:27`. Eighteen minutes from report
to fix — then three days of silence, because Plan 00365 recorded its origin as
"the field report" and never wrote down the number. `CLAUDE/Plan/CLAUDE.md`
requires `**GitHub Issue**: #N` for exactly this reason.

What makes it a good catch rather than a lucky one: the loop re-derived from
scratch what the plan already knew, and that is precisely the redundancy that
finds an orphaned issue. A plan-header lint was considered and rejected — it
would be heuristic on prose, noisier, and would only ever fire at plan-write
time, whereas the loop catches the case however the issue was orphaned.

The same sweep closed three issues as already-fixed, each re-verified against
current `main` rather than taken on a plan's word: #27 (11 lines of probe output
showing container and host views resolving to separate venvs), #28 (14 tests),
#36 (11 tests, two of which pin that the location gate did NOT get leakier).
