## 02:10 · finding · — — found by being on the receiving end of it

Six advisories fired at Stop — three hedging categories, three dismissive — at
a message containing none of those patterns. The tempting response was to
accept the nudge and move on, which is what makes this class of bug durable: a
false advisory that sounds plausible gets absorbed rather than investigated.

Four measurements instead:

| question                                             | answer                 |

| pattern hits in the 6 most recent assistant messages | **0**                  |
| what `_get_last_assistant_message()` returns         | **zero-length string** |

| distance to the most recent genuine match            | **114 messages ago**   |

The zero-length result was the useful one: it ruled out the Stop-event

one I would have "fixed" had I trusted the label on the message.

## 02:14 · finding · P1 — the root cause was in a docstring the whole time

`nitpick/protocol.py` describes `NitpickState` as "Persisted in DaemonDataLayer
(in-memory, keyed by session_id)" with `last_byte_offset: int = 0`. A restart
drops the state, the offset returns to 0, the next fire re-audits all 2,231
messages.

This repo MANDATES a restart after every handler change, so the misfire was not
an edge case here — it was the default. I had restarted twice that session and
seen the six advisories after each.

## 02:20 · decision · T2.1 — the failing test killed two of three options

The plan filed three options. Writing the RED test eliminated two.

`TestNitpickSetupIncremental.test_only_reads_new_messages` already asserts that
a fresh `NitpickSetup` DOES return pre-existing messages — correct, for a
genuinely new session. So "skip what is already there on cold start" (Option 2)
breaks new sessions, and "cap the window" (Option 3) picks an arbitrary N
without addressing the cause.

The offset cannot separate the two situations: a new session and a restarted
daemon both present as `0`.

What separates them is the message timestamp against the daemon's own start
time — Option 4, which none of the filed options anticipated. Real entries
carry one (`2026-08-07T06:52:34.866Z`, verified on the live transcript).

Worth recording that the TEST did this, not the plan. The options table was
written from reasoning; the constraint that eliminated two of them was sitting
in an existing test I had not yet read.

## 02:30 · action · T2.2 — two things checked rather than assumed

- **That the fix is correct in production at all.** It depends entirely on
  `NitpickSetup()` being constructed once at daemon startup — if it were built
  per request, `datetime.now()` would be request time and the filter would
  suppress everything. Verified: one construction site,
  `controller._get_pseudo_event_setup_registry()`, called from startup
  registration.
- **That fixing one instance was enough.** Six other handlers hold per-session
  in-memory state. They divide by whether that state is a COUNTER or an INDEX
  into a durable record: a counter re-arms and costs at most one extra advisory
  (`command_hints` already discloses exactly this in its shipped guidance); an
  index replays, and the cost scales with the record. Nitpick was the only
  index. Recorded as Decision 2 so the discriminator survives.

## 02:32 · decision · T2.2 — fail-open, deliberately

An entry with no timestamp, or an unparseable one, is audited. That keeps the
existing fixtures meaningful, but the real reason is direction of harm: a
redundant advisory is noise, whereas a silently dropped finding is a guard that
stopped working without telling anyone.

## 02:28 · decision · T3.2 — the classification needed a guard behind it

Task 3.1 closed with Decision 2: a table classifying six per-session-state
surfaces as counters (bounded) versus indexes into a durable record
(unbounded). Re-reading it against Core Standard 15, that table is exactly the
artifact the standard warns about — it describes the surfaces that existed the
day it was written and is silent about the seventh.

What made a guard possible was finding something genuinely enumerable.
"Classes holding per-session state" is not: a source scan for it is lossy and
imprecise. But `DaemonController._get_pseudo_event_setup_registry()` IS the
authoritative list of setups the daemon runs, and the replay property is
testable against any entry in it.

So `tests/integration/test_pseudo_event_restart_safety.py` gates the registry:
every entry must accept `started_at` and return nothing for a transcript that
entirely predates it, or carry a recorded exemption with a reason. Same shape
as the Plan 00203 coverage gate — discovery, a verdict per entry, a vacuity
guard, and a stale-entry check.

Stated honestly in Decision 3: the registry holds ONE entry today, so the gate
currently covers exactly the bug just fixed. Its value is prospective. The day
pseudo-event #2 is registered, nitpick's unit test stays green while the new
setup inherits the bug silently — that is the gap this closes, and it is the
only gap it closes.

## 02:29 · finding · T3.2 — the guard was checked for teeth, not just for green

Six tests pass, which on its own proves nothing: a property test that cannot
fail passes for every implementation. So the suite includes its own inverse.
`test_the_guard_would_fail_a_setup_that_ignores_its_start_time` builds the SAME
class against the SAME transcript with only the start time moved back a day,
and asserts the messages ARE returned.

Both directions hold, so the assertion is discriminating rather than vacuous:

```
started_at = daemon_start        -> None            (backlog suppressed)
started_at = daemon_start - 1day -> 1 message       (backlog audited)
```

Had the filter been absent, both would have returned the message and the
property test would have failed.
