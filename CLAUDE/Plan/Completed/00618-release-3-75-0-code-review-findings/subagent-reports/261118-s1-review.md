## Loosening

**Secret guard: none.** Across all 163 commands, no DENY at the release tip becomes ALLOW on the fix branch. Every change is ALLOW -> DENY.

**Flaggable content channel guard: one loosening class (the FAIL driver).**

- **What changed.** `_recursive_search_reaches` now calls `recursive_search.git_search_directory`. That function returns None for any `-c core.worktree=…` or `--config-env=core.worktree=…`, because `git_placement` marks it `unplaceable`. The caller turns None into the unplaced verdict, which is ALLOW plus advisory.
- **Old behaviour.** The removed `_git_working_directory` skipped `-c` values and placed the literal `-C`, so the same command was judged from `{R}` and DENIED.
- **Real git reads the flagged directory.** `realgit.sh` ran `git -c core.worktree=.. -C <repo> grep -e SECRETRULE` and `git -C . -c core.worktree=.. grep -e SECRETRULE`. Both printed `flagdir/x/rule.txt:SECRETRULE`. A relative `core.worktree` is resolved from the git dir, so `..` is the repository root.
- **Inconsistent with the no-`-C` form.** The same command without `-C` (`git -c core.worktree=.. grep -e r`) still DENIES, because `search_command` does not count `-c` as a relocation.
  - So adding a no-op `-C .` turns a deny into an advisory allow.
- **Not reachable through the secret guard.** There, `core.worktree` correctly fails closed: it reads every indexed file and DENIES.
- **Suggested fix (for the plan owner).** In the flaggable guard, treat a git placement that is unplaceable only because of `core.worktree` (or `--git-dir`) as reaching every flagged glob, as the secret guard does, instead of reporting it as unplaced. Or keep the old behaviour for this case: place the literal `-C` and ignore the `core.worktree` move. Add a flaggable test for `git -C <root> -c core.worktree=.. grep`.

## Over-block

Ordinary non-protected use has **no over-block**. `git -C sub grep` (with tracked, `--untracked`, `--no-index`, `-n`, pathspec and `:!` exclude forms), nested `-C`, absolute `-C`, `-C <outside-dir>`, and every `git -C sub log/show/diff/status/blame/add/commit` stays ALLOW. `git log -C`, `git diff -C`, `git show -C` and `git blame -C` are untouched. The `effective_cwds` addition creates no new denial for a non-protected name (`git -C sub status; cat plain.txt` stays ALLOW).

The fix does deny some read-only shapes on purpose (fail-closed). None is ordinary `git -C` use:

- **`--work-tree`, `--git-dir`, `-c core.worktree`, `GIT_DIR` or `GIT_WORK_TREE`.**
  - Any `git grep` relocated these ways now DENIES whenever the project holds any protected file, even when the named tree has none. Examples: `git --work-tree=sub grep -e hello`, `GIT_WORK_TREE=sub git grep -e hello`, `git -c core.worktree=sub grep -e hello`.
  - `git --git-dir=.git grep -e x` is equivalent to the allowed `git grep -e x`, and also DENIES.
  - This follows from `_EVERYTHING` (`Read("/", ALL)`) and from reading the payload cwd with the ALL view when `foreign` is set.
  - It is acceptable as a documented fail-closed choice, but it is broader than needed: for `--work-tree=<literal>`, judging only the placed work tree would avoid it.
- **`git -C "~" grep …`** (a quoted, literal `~` directory). It DENIES when `$HOME` is an ancestor of the project, because the quoted `~` is treated like an unquoted one. This is a harmless edge.
- **Unknown-path tightenings** (judged closed, not an over-block of a real use): `git -C <glob>`, `git -C=deep` (git rejects that form anyway), and `-C ''`.

## Bypass attempts on the fix (secret guard)

- **The three S-1 ALLOW shapes.** All DENY now. So do `--untracked`, `| wc -l`, `;`/`&&` chains, `bash -c`, `sudo`, `sudo -u git`, `env -u git`, `timeout`, `nice`, `/usr/bin/git` and `cd sub && git -C .. grep`.
- **Unresolvable `-C` values fail closed (DENY).** This holds for `$D`, `"$HOME"`, `$(pwd)/deep`, backticks, `de*`, `dee?`, `{deep,sub}` and `-C sub -C $X`.
  - `git -C ~ grep` is judged like `grep -r x ~`: DENY when `$HOME` is an ancestor of the project, ALLOW when it is not.
- **Residual gap, not a loosening (release tip also ALLOWs).** `@sub sudo -D {O}/git git -C .. grep --no-index -e .` is ALLOWED.
  - Cause: `peel_command_wrappers` does not consume `sudo -D <dir>`, so `git_placement` starts at the first word whose basename is `git` (the `-D` value). It never sees the real `-C ..`.
  - Contrived: it needs a sudo chdir to a path ending in `/git`. Worth a test that `git_placement` starts from the command word, not the first `git`-named word.

## Test gaps

1. There is no flaggable test for `-c core.worktree`/`--config-env` combined with `-C` (the loosening above). The only flaggable relocation tests are relative `-C` inside and outside the flagged tree, and `$D`.
2. The secret guard has no deny tests for `-c core.worktree=…`, `--config-env=core.worktree=…`, or the env forms `GIT_DIR=`, `GIT_WORK_TREE=` and `env GIT_WORK_TREE=` (the `_assigns_a_relocating_variable` path). Only `--work-tree`, `--git-dir`, `--attr-source` and `$D` are in the new test corpus.
3. There is no test pinning the deliberate fail-closed over-block (`git --work-tree=<clean dir> grep` DENY), so a later narrowing would not be noticed either way.
4. There are no tests for a glob or brace `-C` value (`de*`, `{a,b}`), for `~`, or for wrappers (`sudo -u git git -C …`, `bash -c '…'`).
5. There is no test that `git_placement` ignores a wrapper argument whose basename is `git`.
