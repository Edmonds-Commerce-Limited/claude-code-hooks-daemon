## Findings (no hard-rule violation)

### F1. The flaggable guard crashes on `git -C ~+` and `git -C ~-`

- **What fails.** The fix sends `-C` values to `recursive_search._anchored`, which calls `pathlib.Path("~+").expanduser()`. That raises `RuntimeError: Could not determine home directory.` because Python reads `~+` as the home of a user named `+`.
- **Affected commands.** `git -C ~+ grep`, `git -C ~+/flagdir grep`, `git -C ~+/deep grep`, `git -C ~- grep`, `git -C ~+ -C {R} grep`, and the harmless `git -C ~+/sub grep -e hello`. All were ALLOW+adv at the tip.
- **Effect in production.** The guard fails closed, so the result is a DENY. That is an over-block, not a leak.
- **The crash predates the fix.** At the tip, `grep -r x ~+`, `rg x ~+` and `grep -r x ~-` already crash.
- **Suggested fix.** Treat `~+` and `~-` as unplaceable, or as `$PWD`/`$OLDPWD`, before calling `expanduser`, and add a test.

### F2. Flaggable guard: advisory becomes silent ALLOW where git really reads the flagged tree

At the tip, every relocated `git grep` was "unplaced", which gave ALLOW plus an advisory. The fix places a literal `-C` against the payload cwd. The guard has three properties that existed before the fix:

- It works one segment at a time and does not track `cd`.
- It skips a root that resolves above the project (`searched[:1] == [".."]`).
- It places `xargs -I%` replacement tokens literally.

So the following now pass with no advisory. `realgit.sh` prints the marker for each, which confirms git really reads the flagged tree.

| command                                                      | tip       | fix   |
| ------------------------------------------------------------ | --------- | ----- |
| `cd sub && git -C ../flagdir grep -e r` (and `--no-index`)   | ALLOW+adv | ALLOW |
| `( cd sub; git -C ../flagdir grep -e r )`                    | ALLOW+adv | ALLOW |
| `echo flagdir \| xargs -I% git -C % grep -e r` (and `-I@`)   | ALLOW+adv | ALLOW |
| `git -C .. grep --no-index -e r`, `@sub git -C ../.. grep …` | ALLOW+adv | ALLOW |

The plain forms are already ALLOW at the tip: `cd sub && grep -r r ../flagdir`, `grep -r r ..` and `xargs -I% grep -r r %` (corpus 3). So the fix lines `git -C` up with existing gaps rather than opening a new one. The secret guard, which tracks `cd` and ancestor roots, DENIES the protected-tree variants.

**Optional mitigation.** Keep the unplaced advisory when a `cd`/`pushd` comes earlier in the same command, or when the `-C` value is an `xargs -I` token.

### F3. Environment-variable relocation combined with `-C` (modelling gap, no read observed)

**The flaggable guard does not consult relocating variables.** These commands go from ALLOW+adv at the tip to ALLOW on the fix:

- `GIT_WORK_TREE=…`, `GIT_DIR=…`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `env -i GIT_WORK_TREE=…`, `export GIT_WORK_TREE=…;` and `sudo GIT_WORK_TREE=…`, each with `git -C sub grep`.

The same command without `-C` DENIES. `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT` setting `core.worktree` are not recognised by either guard. With `-C {R}/sub` they are ALLOW at both trees, and they deny with `-C .` only through the root default.

**Real git read nothing in the cases tested.** `realgit.sh` ran these with a cwd of `sub` and got rc=1 with no output:

- `GIT_WORK_TREE=<abs flagdir> git -C sub grep`, in tracked, `--untracked` and `--no-index` modes;
- `GIT_DIR+GIT_WORK_TREE=<R> git -C sub grep`, in tracked and `--untracked` modes;
- `GIT_DIR=<R>/.git git -C sub` and `git -C flagdir grep`;
- `GIT_CONFIG_COUNT … core.worktree=.. git -C sub grep`.

The cause is that git limits `git grep` to the cwd prefix, or refuses a cwd outside the work tree. Other combinations were not tested.

### F4. Secret-guard grammar gaps that predate the fix and do not depend on `-C`

The following are ALLOW at both trees:

- `{ git -C deep grep --no-index -e .; }`
- `if true; then git -C deep …; fi`
- `exec git -C deep …`
- `time git -C deep …`
- `bash -lc 'git -C deep …'`
- `sudo -D {R} git -C deep …`
- `( cd sub; git -C ../deep … )`

Each one's plain `grep -r . deep` form is also ALLOW at both trees, while the bare `grep -r . deep` DENIES. The gap is in the command grammar: brace groups, `if` bodies, `exec`/`time`, `bash -lc` and `sudo -D` are not peeled. Fixing S-1 cannot close it. It is worth filing as a separate finding.

### F5. Secret guard: `git -C ~+/deep grep --no-index -e .` gets only an advisory (an unclosed S-1 shape)

- **Verdicts.** The secret guard gives ALLOW at the tip and ALLOW+adv on the fix. The same holds for `git -C ~+ grep --no-index` and `git -C ~+ -C {R} grep`.
- **The command really reads the protected tree.** Bash expands `~+` to `$PWD`; `realgit.sh` confirms `git -C ~+/flagdir grep` prints the marker.
- **Only the F1 crash blocks it,** and only when flaggable globs are configured. With the secret guard alone, the command runs after an advisory.
- **Not a hard-rule violation.** The tip already allowed it. But it is the S-1 bypass shape, and the fix leaves it open.
- **Suggested fix.** Resolve `~+` as `$PWD`, and `~-` as `$OLDPWD`, or fail closed.
