## S-1: what changed

- **`utils/recursive_search.py`.** The `if relocated: return` skip is gone. The new `git_placement` reads git's global options.
  - Each literal `-C` moves the search directory cumulatively from the payload cwd, exactly as a `cd` does. The `-C` form and the `cd` form therefore produce identical `Read`s, and a test pins this. `-C ''` is a no-op.
  - A literal `--work-tree` is judged in full in the ALL view, placed both where it stands and where git finally runs.
  - The following fail closed as one `Read("/", ALL)`, which is every indexed protected file:
    - a `-C`/`--work-tree` value containing `$`, a backtick, a glob or a brace;
    - `--git-dir`, since a git dir's config can name `core.worktree`;
    - a `-c` or `--config-env` override of `core.worktree`;
    - a `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` or `GIT_COMMON_DIR` assignment before the command.
  - A relative `-C` with no absolute payload cwd stays unjudged, as the equivalent `cd` does today.
- **Same class, found while probing.** Git read the value of `--attr-source HEAD` and `--config-env X` as a separate word. `search_command` took that word for the subcommand, so the search was never found. Git really reads the tree in both cases (scratch probe). The separate-value set is now the shared `GIT_GLOBAL_OPTIONS_TAKING_SEPARATE_VALUE` plus `--attr-source`.
- **`utils/secret_file_matching.effective_cwds`.** It also returns each literal `git -C` directory, read from where the shell is, without moving the shell for a later `cd`. It sits behind a sound prefilter (the segment must contain both `git` and `-C`), so the no-tokenise performance tests still hold. The RED test showed the gap: with a path-anchored protected path `vault/creds.json`, `git -C vault show HEAD:creds.json` was ALLOW while `cd vault && git show HEAD:creds.json` was DENY. Both are now DENY.
- **Other searchers.**
  - `quarantine_artefact_read_guard` inherits the fix through `search_reads`, with new deny and allow rows.
  - `flaggable_content_channel_guard` now uses `git_search_directory`, the same resolver. A relative literal `-C` is placed instead of reported "unplaced" (advisory-allow). So `git -C tests grep foo` is now DENY. A truly unplaceable value, `--git-dir` or `--work-tree` stays "unplaced" (advisory). That is this guard's existing policy for every unplaceable root, and this change keeps it.
  - The guard's advisory text, `get_claude_md` text and the HANDLER_REFERENCE row now say a literal `git -C <dir>` is placed as `cd <dir>`.

**Fix.**

- The new `recursive_search.git_overrides_worktree` reads every global option of the running git, in any order. It covers `-c` and both `--config-env` spellings, and it matches the key case-insensitively.
- The flaggable guard calls it for every recursive `git grep`, whether or not the search was relocated, and DENIES. The deny text names the override. An exclusion does not help, because it is judged against a tree the override has moved.
- `git_placement` checks the override first, so an earlier unplaceable `-C $X` no longer hides it.
- Both `search_command` and `git_placement` now anchor on the git whose subcommand is `grep`, not on the first word named `git` (review test gap 5). `sudo -u git git -C .. grep` used to be missed by the flaggable guard, on the release tip too, and is now placed. Only later `git`-named words are tried, so `git log grep` is still not a search.
- `--git-dir`, `--work-tree` and an expansion-built `-C` stay ALLOW plus advisory in the flaggable guard, which is the tip's verdict and the guard's documented unplaced policy. The secret guard still denies all of them.

## Pre-existing gaps (the release tip has them too; not loosenings, not fixed here)

- **A wrapper that changes directory is not followed (the `sudo -D` gap is this class).** `COMMAND_WRAPPERS["sudo"]` (`shell_segmentation.py`) does not take `-D`/`--chdir` as a value flag, and no wrapper's chdir moves the judged cwd. So from `sub`, `env -C ../deep git grep --no-index -e .`, `sudo -D ../deep git grep --no-index -e .` and `sudo -D ../deep grep -r x .` are ALLOWED by the secret guard, on the release tip and on this branch alike. A chdir to a child of the cwd is caught only because the cwd is a superset.
  - The cause is wrapper peeling in a shared table, not git option placement, so it is reported rather than changed on this release-blocking branch.
  - The review's exact `sudo -D {O}/git git -C .. grep` shape now DENIES, as an over-block, through the running-git anchor.
  - Recommend a follow-up plan: model `env -C`/`--chdir` and `sudo -D`/`--chdir` as a directory change, or fail closed.
- **Git configuration from the environment.** `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` (and `GIT_CONFIG_PARAMETERS`) can set `core.worktree` without `-c`. Neither guard treats them as relocating. In the flaggable guard, `GIT_WORK_TREE=<flagged dir> git -C <clean dir> grep` is also judged from the `-C` directory: it was ALLOW+adv on the tip and is ALLOW here, which is not a DENY->ALLOW.

## Known limits (not loosenings)

- **Nested repository.** `git -C <nested-repo> grep x` judges in the TRACKED view using this project's index. A file that is tracked in a nested repository but untracked in the outer one is not seen. That matches the `cd <nested-repo> && git grep x` verdict at the tip.
- **Wrapped command in `effective_cwds`.** It follows `git -C` only when `git` is the segment's first word, so `sudo git -C d show HEAD:x` is not anchored. The recursive-search path does handle wrappers.
- **Unchanged out-of-scope handling.** A `-C` value carrying a command substitution is still treated as the threat model's out-of-scope class for the mention scan. For a search, it now fails closed.
