# Plan 00259 Journal — 2026-08-19

## 10:05 · delivery · the handler, and what verifying it properly cost

Built `artifact_publish_blocker` end to end. Notes worth keeping.

**Task 1.1 earned its place in the plan.** The temptation was to write the
matcher from the tool schema and move on. Instead I enabled `payload_capture`
scoped to PreToolUse, called the tool in its read-only `list` mode, and read the
real event off disk:

```
{"hook_event_name": "PreToolUse", "tool_name": "Artifact",
 "tool_input": {"action": "list", "limit": 3}}
```

That settled the one question the whole plan rested on — *does Claude Code even
send PreToolUse for this tool?* — before a line of handler code existed. If the
answer had been no, everything downstream would have been unbuildable and I
would have found out at the very end. Config reverted and the capture directory
deleted afterwards: it contained a session id and a transcript path.

**The matcher defaults unknown actions to "publishes".** `action` is optional
and an absent one means publish. An action name this handler has never heard of
is therefore treated as publishing rather than waved through. If the tool grows
a `share` or `export` action later, the guard covers it on day one and someone
has to consciously widen the allow-list — the opposite of the failure where a
new verb silently opens a hole.

**Live verification, not just unit tests.** Unit tests pass against a handler
object; they say nothing about whether the daemon loaded it. So: restarted the
daemon, probed the live socket (publish → `deny`, list → no decision), and then
actually attempted to publish a real file through the `Artifact` tool. Blocked
by the live daemon; nothing published. I used deliberately trivial content so
that even a total guard failure would have disclosed nothing — the test had to
be safe to LOSE, not merely expected to pass.

**Four registries, none of which unit tests knew about.** The QA suite failed
until the handler was recorded in: the guidance-coverage verdict table, the
blocking-handler evasion classification, `hooks-daemon.yaml.example`, and
`docs/guides/HANDLER_REFERENCE.md`. This is the daemon's own DBF principle
working on me — each of those gates exists because a handler once shipped
missing that thing, and every one of them caught me.

**One false alarm I raised and withdrew.** On finding the background-process
tracking log records no `pid`, I suspected a defect. It is not one: the
harvester matches by args against the live process table *precisely so* it can
catch processes that were never tracked at spawn, so a pid would add nothing.
Recording the retraction rather than the suspicion, because a plausible-sounding
false finding left standing is worse than no finding.

**Deliberately not done**: no `MUST_..._BECAUSE` escape hatch (Decision 2), and
no content scanning (Decision 1). Both were tempting and both would have been
wrong — the first lets an agent authorise its own disclosure, the second
duplicates `sensitive_content` and creates a second source of truth that drifts.

**Honest limitation, stated in the handler, the reference doc and the
truth-change**: this cannot stop a human publishing through the claude.ai UI.
The daemon sees tool calls, not browser clicks.
