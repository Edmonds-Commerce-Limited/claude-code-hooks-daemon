## 09:31 · decision · — — the owner overruled my backwards-compatibility objection, and was right

This plan exists because of an architecture question from the owner: should the
destructive-git and sibling guards migrate into one "dangerous" handler with
sub-config levels per concern (git, curl, gh) and per-scenario `block`/`warn`/`off`?

My first answer recommended AGAINST consolidation, on the grounds that
`handlers.pre_tool_use.destructive_git.enabled` is a config contract in every
installing project and silently renaming it is class 2
(`guard-self-disablement-unwatched`) — the very defect Plan 00412 built a
Detector for. The owner rejected the premise:

> this is backwards compat concerns that are not valid — we fix this by having a
> robust upgrade procedure and fail fast and loud on invalid config … we should
> not be scared of mutating config shape but we MUST ensure we properly advise
> on upgrade and we properly enforce with clear messaging at runtime

That is the stronger position, and the codebase already contains the evidence
for it. `constants/handlers.py:1290` states the case against its own behaviour:

```
# A key in RETIRED_HANDLERS is accepted silently at startup, which is right for
# a handler that is gone, and wrong for one that merely moved: a client who
# keeps `stop.hedging_language_detector` after the move still has a config that
# says the detector is on, while nothing runs it (Plan 00362, report §2).
```

So the failure the argument was defending against is one this project has
ALREADY SHIPPED, measured, written down — and then patched with
`RELOCATED_HANDLERS`, which still resolves to a silent accept. My reasoning was
not wrong about the class; it was wrong about which side of the trade the class
falls on. Freezing the shape does not prevent the lie. It only means the lie is
permanent instead of transitional.

The transferable form: **a compatibility shim that keeps an old key VALID
without keeping it EFFECTIVE is not compatibility — it is a config that lies
about what is protecting you.** Refusing to start is louder, cheaper and
recoverable; the silent accept is none of the three.

A third message narrowed the registry's role, and it is now Decision A:

> retired handlers is worth tracking - but only so that explicit instructions
> can be given on how to move the config to the correct new handler config

The registry survives, its purpose inverts: it is no longer the reason a stale
key is tolerated, it is the reason a refusal can name the remedy.

## 09:33 · decision · P3 — the invalid-config window, and why a boolean is the wrong shape

The owner raised the ordering problem unprompted:

> i guess we need to worry about the "invalid config window" - when upgrading -
> do you change config first (breaks current daemon) then upgrade, or upgrade
> (broken config fails fast) … maybe config can carry an "upgrade in progress"
> bool which when true handles the window and never fails fast and hard …
> something to enforce that the flag must be set to false once upgrade is
> complete and properly enforces it

Both orderings are genuinely broken, and the window exists only because they are
two separate acts — so the primary fix is to make them one transaction owned by
the upgrader. That removes the window on the supported path entirely, and a
self-install checkout gets it free because the migration lands in the same
commit as the code.

The flag is still needed for the out-of-band paths (hand-edited config, a pull
carrying someone else's config, an upgrade that died halfway). But the owner's
own follow-up names the danger precisely: something must ENFORCE that it goes
back to false. A flag whose safety depends on someone remembering is a guard
that degrades to permanently-off, which is class 2 again, this time
self-inflicted.

Decision C therefore does not rely on anyone remembering. The flag is bound to
`to_version`, so it is spent by its own terms the moment the running daemon
reaches that version — the enforcement is an observable fact, not a promise. A
TTL covers the abandoned upgrade where the target is never reached. A commit
gate makes the permissive state uncommittable, so it cannot reach history, a
teammate or a fresh clone. And it announces itself every session while live.

The property worth stating plainly: **an escape hatch should expire against a
fact, not against an intention.** "Set it back to false when you're done" is an
intention. "Honoured only while the running version differs from the target" is
a fact, and it needs no discipline from anyone.
