A peer review session raised this immediately after Plan 00253 closed: the tier
00253 added uses the FORCE delete, so the concurrency guard 00253 had just
identified — git's own `-d` refusal, protecting against a peer commit the
pre-loop bundle cannot contain — does not apply to it.

Re-verified all of it by execution before accepting any of it, which is now the
standing habit in this chain, and it paid again. Two things the peer asserted
without showing both held: a pre-existing tier (`merged-unpushed`, shipped in
00249) loses work identically, so this is a latent defect across four tiers
rather than a 00253 regression; and `git update-ref -d <ref> <sha>` really is a
compare-and-swap.

But the peer's proposed remedy is the wrong change, and executing it is what
showed that. Its premise was that the force tiers give up nothing by switching to
`update-ref`, since git checks nothing there. False: the force delete REFUSES a
branch checked out in another worktree, while `update-ref -d` deletes it and
leaves that worktree with a dangling HEAD. It also leaves `branch.<name>.remote`
and `.merge` behind — the exact two keys `_safe_delete_reference` reads to choose
a tier, so a later branch of the same name would inherit a dead upstream.

In a project where agents routinely run with `isolation: "worktree"`, that guard
fires far more often than the race. So: re-read the tip, keep git's delete. The
window goes from a whole bundle pack to one git invocation, and nothing is given
up. The residual window is real and gets said out loud rather than implied away.

Second instance of 00253's Decision 1 — the battle-tested tool checks things we
did not think to check. Worth noticing that the first instance was about trusting
git over our own predicate, and this one is about trusting git over a peer's
suggested replacement for it.
