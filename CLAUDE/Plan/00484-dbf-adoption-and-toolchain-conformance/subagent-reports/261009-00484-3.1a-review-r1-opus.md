## SHOULD-FIX

### S1. The defect-class vocabulary is not closed, and nothing stops drift

`constants/dbf.py:43` `DefectClass` is a bag of `ClassVar[str]`. `core/handler.py:108` types
`defect_class: ClassVar[str | None]`, so any string type-checks. `tests/unit/constants/test_dbf.py` only checks that
the values are unique and kebab-case. Nothing asserts that a handler's declared class is a `DefectClass` value, and
nothing pins which handlers are in the set. A typo (`"lint-falure"`) or a dropped declaration would silently change
the public `defences --json` output.

`test_cli_defences.py::test_listing_is_exactly_the_handlers_that_declare_a_defect_class` asserts only
`listed <= declared` and `len > 10`.

**Fix:** either make `DefectClass` a `StrEnum` and type the attribute `ClassVar[DefectClass | None]`, or keep the
strings and add these to `tests/unit/test_rule_parity.py`:

1. For every library handler class (the same walk the parity test already does),
   `cls.defect_class is None or cls.defect_class in DefectClass values`.
2. A pinned `frozenset` of Defence config keys (the 19), compared for equality. Adding or removing a Defence is then a
   deliberate, reviewed edit, which is what C1 being an owner ruling calls for.
3. Every class that declares `defect_class` has at least one `get_rules()` rule and a `Decision.DENY` path. A Defence
   is a Blocking Rule (SPEC "Defence"/"Blocking"), so a declared class on an advisory-only handler is a contradiction.

### S2. Client project handlers drop silently out of `defences`, and nobody is told how to opt back in

- **Before:** an enabled blocking project handler with no rules got a rule-less record.

  client project handler declares one, since the attribute is new. A client's own content gates therefore vanish from

That is the TOOLING 5.3 obligation ("the project's own defences appear alongside bundled ones"), and CONFORMANCE.md

**Fix:**

- Document `defect_class` in `CLAUDE/PROJECT_HANDLERS.md` and `CLAUDE/HANDLER_DEVELOPMENT.md`: what it means (C1),
  that it puts the handler in `defences`, and the `DefectClass` values or the rule for a project-defined class. If S1
  closes the vocabulary, say whether a project may use its own string.
- Add one sentence to release note
  `CLAUDE/UPGRADES/UNRELEASED/release-notes/006-defences-listing-identifiers-and-the-guardrail-split.md`. It should say
  that project handlers are listed only when they declare `defect_class`, and that `defences --json` no longer returns
  the action-guard rows that v3.69.0 returned (about 135 rows down to about 36 here).

### S4. G5 needs a structural test that every deny carries an ID

The implementer says no test proves this, and proposes none. The source-marker heuristic misses two things.

**Off-format IDs pass unnoticed.** `handlers/pre_tool_use/conflict_marker_commit_gate.py:474-481` `_unchecked`
denies with `R-CONFLICT-MARKER-COMMIT: this commit was NOT checked…`. That has no `BLOCKED [..]` headline, and it is
filed under the COMMIT rule although `R-CONFLICT-MARKER-SCAN-TIMED-OUT` exists for "not checked". I hit this live
during the review. The handler has rules, so the parity test passes it.

**Denies built outside the handler module are invisible.** Example: `utils/cron_refresh.py`.

**Cheap structural test:** a pytest plugin (`tests/plugins/deny_carries_rule_id.py`, loaded from `tests/conftest.py`
and the project-handler conftest).

1. At session start, wrap `handle` on every concrete `Handler` subclass, library and project. Use the parity test's
   discovery; patch the class attribute and restore it at teardown.
2. The wrapper inspects the returned result. When `decision is Decision.DENY`, it asserts:
   - the reason contains `BLOCKED [(R-[A-Z0-9-]+)]`;
   - the captured ID is in `{r.rule_id for r in self.get_rules()}`;
   - otherwise the class is in `_DENY_WITHOUT_RULES_ALLOWLIST`.
3. Violations are collected per class and fail the session in `pytest_sessionfinish`, listing class, test node id and
   the first reason line.

It costs one `isinstance` and one regex per `handle` call. It exercises every deny path that has a unit test, which
the 95% coverage gate makes nearly all of them, wherever the reason is built. It also catches an ID that the handler
prints but does not declare.

With it in place, D4.3 can move from "at least" to MET. Until then, keep CONFORMANCE.md as written. `_unchecked` can
be fixed with `RuleFormatter().headline(...)` in the same follow-up (3.1b or 3.1c).

### S5. Membership: two Defences fail the SPEC's own definition, and one content gate is left out

I checked the 19+1 declarations against C1 and against SPEC.md:109-127. A Defence is a *Blocking* Rule; a Rule is
Blocking when it "prevents a change from being accepted"; a Rule that only warns is not a Defence. Put these to the
coordinator.

**`lint_on_edit` (`post_tool_use/lint_on_edit.py:99`) and `validate_eslint_on_write` (`:144`).** Both are
PostToolUse. The write has already landed, and the project's CLAUDE.md block says so ("a failure report, not a
rollback"). They do not prevent acceptance, so by the SPEC they are Warnings. The Blocking rule for the `lint-failure`
class is `staged_lint_gate`. Either:

- (a) drop `defect_class` from the two PostToolUse linters, leaving the class defended by `staged_lint_gate`; or
- (b) keep them and record in CONFORMANCE.md why an agent-facing PostToolUse deny counts as Blocking here.

I recommend (a).

**`github_auto_close_keywords` (left out).** It judges the content of a commit, tag or `gh` message, which is the
same git-metadata surface `sensitive_content` is a Defence for. Under C1 ("commit gates are the Defence set") it reads
as a content gate. Its hazard is the auto-close, but the defect is a pattern in authored text. Either declare it
(`issue-closing-keyword`) or record why it is a guardrail.

**`tdd_enforcement` (borderline).** It does not read content. It blocks the *action* of creating a source file while
no test file exists. "Source without test" is a repository-state class rather than a pattern in content. It is
defensible either way; record the reasoning.

Everything else in the 19 is a clear content or commit gate. Among the 55 undeclared deny handlers I found no other
content gate. `markdown_organization` judges placement, and `git_message_backtick` judges shell execution of the
command; both are correctly guardrails.
