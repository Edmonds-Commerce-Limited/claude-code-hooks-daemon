## 18:20 · finding · P1 — I established git's rule by running it, before asserting it

The fix hinges on which ref `git branch -d` measures against, and the review and
the old code disagreed about it. Rather than pick a side from prose, I ran all
three cases:

```
CASE 1  upstream LEVEL with branch, HEAD elsewhere  -> -d exit 0 ("has been merged to")
CASE 2  no upstream, DETACHED HEAD not containing it -> -d exit 1 ("not fully merged")
CASE 3  no upstream, HEAD on main (common case)      -> -d exit 0
```

So the rule is exclusive, not preferential: **an upstream that resolves is used
alone** and HEAD becomes irrelevant (CASE 1 deletes a branch absent from HEAD),
and with no upstream **HEAD is the sole reference, detached or not** (CASE 2).

That third case mattered more than expected. `HEAD` resolves to a commit whether
or not it is symbolic, so one `merge-base --is-ancestor <name> HEAD` covers both
— no `symbolic-ref` special case, which is what I would have written from the
prose. There is a test pinning it, because "one expression covers both" is
exactly the sort of claim that quietly stops being true.

## 19:26 · finding · P5 — I nearly filed a self-finding produced by my own probe

While checking whether an upstream could resolve to the literal string `HEAD` and
collide with `_HEAD_REF`, I built a repo with `branch.weird.remote=.` and
`branch.weird.merge=HEAD`, and got what looked like a real residual disagreement:

```
abbrev-ref: 'main'   weird ancestor of main: True   -> my predicate: git will accept
git -d exit: 1       "The branch 'weird' is not fully merged."
```

Classifier says `merged`, real git refuses. That is the same defect shape as
finding A, apparently surviving the fix.

It is not. `merge = HEAD` means "the upstream is whatever HEAD points at RIGHT
NOW", and my probe resolved the upstream BEFORE the `checkout -b elsewhere` that
moved HEAD. Reading it at the same moment git reads it:

```
after HEAD moves:  abbrev-ref -> 'elsewhere'   for-each-ref -> 'elsewhere'
weird ancestor of elsewhere: False  -> predicate False -> merged-unpushed -> -D
git -d exit: 1                       -> agrees
```

So the code is correct, including for this pathological config, precisely BECAUSE
`_safe_delete_reference` asks git at classification time instead of caching a
reference. Also confirmed `for-each-ref --format=%(upstream:short)` agrees with
`rev-parse --abbrev-ref` in both the malformed and well-formed cases, so there was
no more faithful source of truth to switch to.

And a four-row matrix settled the case the review had listed as unfounded, for the
one combination it had not covered — a WELL-FORMED local-repo upstream
(`remote=.`, `merge=refs/heads/main`) with HEAD elsewhere:

```
HEAD_elsewhere=False local_upstream=False  anc_HEAD=True   -> -d exit 0
HEAD_elsewhere=False local_upstream=True   anc_up=True     -> -d exit 0
HEAD_elsewhere=True  local_upstream=False  anc_HEAD=False  -> -d exit 1
HEAD_elsewhere=True  local_upstream=True   anc_up=True     -> -d exit 0   <- upstream wins
```

Row 4 is the one that matters: a local-branch upstream behaves exactly like a
remote one, so the exclusive-choice rule holds regardless of where the upstream
lives.

The lesson is the one that keeps recurring this session, now in my own work rather
than in a report: **the probe has to mirror the code path, not just the
scenario**. My probe reproduced the right repository state and the wrong ORDER,
and produced a finding that would have sent me rewriting a correct function.
Pinned as `test_an_upstream_that_tracks_head_is_resolved_at_classification_time`
so the dynamic resolution is documented rather than rediscovered.

The reviewer answered my open question (should a mid-loop refusal abort the batch?)

```

  [peer advanced `victim` with an UNMERGED commit mid-loop]

report.deleted : ('first',)

Confirmed. But the interesting part is not the refusal — it is WHOSE work git

That is the one place in this module where the bundle is not a complete safety

also retroactively strengthens `delete_argv_for_tier`'s existing preference for
`-d`: deferring to git is not merely a belt-and-braces re-check of our own proof,
it is the concurrency guard.

commit.

## 19:52 · decision · — — keep the loop, change the signal

Accepted the reviewer's conclusion, having checked its load-bearing claim myself:
`delete_branches` bundles EVERY classified branch before any ref is removed, so
recovery coverage really is uniform and stopping early buys nothing. Their
order-dependence argument is the one I found most decisive — aborting would make
the surviving set depend on the order of `args.branches`, which is arbitrary user
input, so the same repository with the same proofs would leave different branches
behind for `a b c` than for `c b a`.

What changed instead is the blocker text. Post-Plan-00249/00253 the predicate
mirrors git on both axes, so a refusal at that point means our model disagreed
with git, and there are exactly two causes. The message now names both, says how to
distinguish them (re-run), warns that the bundle predates a concurrent change, and
forbids forcing past it. DBF applied to the guard's OUTPUT rather than its control
flow — a one-string change that turns each occurrence into a bug report.

Also recorded Decision 4 for the asymmetry the reviewer flagged: the exit code
marks "not what you asked for" but cannot distinguish "nothing went" from "two of
three went", so a scripted caller must parse `--format json` and must not read the
non-zero exit as "no change to the repository". The human path now says
`PARTIALLY REFUSED` and names what went, so the constraint is on machine callers
only.
