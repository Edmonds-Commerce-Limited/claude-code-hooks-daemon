that changed the fix in Plan 00251. Five held exactly as described. One did not.

**F (path miscount)** was attributed to `errors="replace"` turning raw non-UTF-8
bytes into U+FFFD. Executed, the cause is `core.quotePath`, and it is both
narrower and broader than reported — it has nothing to do with decoding, and it
bites for ANY non-ASCII path, valid UTF-8 included:

```
ls-tree            -> b'"caf\\303\\251.txt"'    (quoted AND octal-escaped)
rev-list --objects -> b'…sha caf\xc3\xa9.txt'   (raw)
the two path texts MATCH: False
```

The defect and the remedy (`-z` on both sides, or `-c core.quotePath=false`) are
unchanged, so this is a correction to the explanation rather than to the verdict.
Recorded because the wrong mechanism would have sent the fix at the decoding
layer, where there is nothing to fix.

## 18:02 · finding · — — the eight unfounded candidates, recorded so nobody redoes them

The review checked these by execution and found the code correct. Written down
here rather than left in a message, because the expensive failure mode is a later
pass re-deriving conclusions that already exist:

- upstream `gone` (`rev-parse` exit 128 → `True`): git ACCEPTS `-d`, falling back
  to HEAD when `resolve_ref` fails — agrees.
- upstream is another local branch (`remote=.`) → predicate `False` → `-D`; git
  refuses `-d` — agrees.
- upstream is itself → `True` (a commit is its own ancestor); git accepts.
- branch name containing `/` → resolves; predicate `False`; git refuses.

  `--abbrev-ref` reports the ambiguity as `remotes/origin/feat`; no

  refnames.
