## 10:05 · decision · P1 — comment-extraction architecture

Decided the shared `strategies/comments/` package layout (mirrors
`qa_suppression`/`security_antipattern`): `syntax.py` (CommentSyntax data,
one instance per DISTINCT syntax family — HASH, PYTHON w/ docstrings,
PHP, SLASH, SLASH_DOC for JSDoc/Javadoc/KDoc), `protocol.py`
(CommentStrategy Protocol — data-only, zero behaviour, same pattern as
QaSuppressionStrategy), `extractor.py` (single shared extraction algorithm,
next), `registry.py` + one thin per-language strategy file each (config
only — extension list + syntax + skip_directories + language_name), to
match the codebase's established one-file-per-language convention while
keeping the actual syntax DATA de-duplicated via the shared instances.

Language set: the 11 canonical languages from CLAUDE.md's Supported
Languages table PLUS Shell (`.sh`/`.bash`) — the field report's own
motivating example (`claude-yolo`) is a bash script, so Shell coverage is
load-bearing, not optional. HTML/XML/SQL/Lua/Lisp mentioned in the proposal
are deliberately out of scope (not in the canonical table) — logged in
PLAN.md Non-Goals.

Python docstring detection uses `doc_requires_line_start=True` (new
CommentSyntax field) so `x = """value"""` is never misread as a docstring
— only a `"""`/`'''` that is the first non-whitespace content on its line
opens a doc span.

`syntax.py` + `protocol.py` implemented TDD-first, tests green (10 passed).
Next: `extractor.py` (the load-bearing piece — line-comment runs, trailing
inline comments, block/doc delimited spans, all via one state-machine pass).

## 10:40 · finding · P1 — splitlines() not split("\n"); dead branch removed

`extract_comment_spans()` implemented and TDD'd (26 tests). Two bugs found
by the tests themselves before commit:
1. Used `content.split("\n")` instead of `content.splitlines()` — a
   trailing `\n` produced a spurious empty final "line", off-by-one on
   every unterminated-block-comment end_line. Fixed by switching to
   `splitlines()`.
2. Two test expectations were WRONG, not the implementation: contiguous
   comment-only lines using DIFFERENT markers (PHP's `#` then `//`) merge
   into one span, and a shebang line merges with the header comment below
   it when there's no blank line between them — both are correct
   "contiguous block" semantics (matches plan-doc-size's philosophy), so
   the tests were corrected rather than the code.
3. Proved (via coverage) that `_extend_comment_run`'s delimiter-vs-marker
   tie-break branch was UNREACHABLE: a delimiter start token is always
   non-whitespace, so it can never sit before a marker while everything
   before that marker is blank. Removed the dead branch instead of writing
   a test to force it — the outer loop already reprocesses the next line
   fresh once a run stops on `marker_hit is None`. 100% coverage, 36 tests.

Then built `common.py` (shared `DEFAULT_SKIP_DIRECTORIES`) plus one thin
per-language strategy file each for Python, Shell, Ruby, JS/TS, Go, PHP,
Java, Kotlin, C#, Rust, Swift, Dart (11 canonical + Shell). Each strategy

## 11:15 · finding · P1 — CommentChangelogHandler implemented, one bug found by tests

Wrote failing tests FIRST for all 5 high-precision signals, the lower-
precision advisory-only signals, the pinned must-not-flag cases (Plan 00047
rationale example verbatim; a Plan-00181-style rationale referencing a plan
number, matching this repo's own style; a bare single version mention; a

One test caught a real design gap: the "dated entry" signal (`2026-08-12:
...`) was only wired into the `max_history_entries` COUNT check, so a
SINGLE dated entry never blocked — but the proposal lists it as its own
high-precision signal, unambiguous on its own, same as `Prior X:`. Fixed by
giving it its own independent check, matching the other four signals.

Semver-token precision decision: only 3-part (`X.Y.Z`) or `v`-prefixed
tokens count as "distinct semver tokens" for the entries-count / two-token
signals. A bare two-part decimal (`3.11`) does NOT count — Python version
references ("supported on both 3.11 and 3.12") are common, legitimate
prose that would otherwise false-positive. The field report's own example
is entirely 3-part (3.27.0, 3.26.2, ...), so this restriction does not
weaken the signal that matters.
