## 10:05 · decision · P1 — comment-extraction architecture

Decided the shared `strategies/comments/` package layout (mirrors
`qa_suppression`/`security_antipattern`): `syntax.py` (CommentSyntax data,
one instance per DISTINCT syntax family — HASH, PYTHON w/ docstrings,
PHP, SLASH, SLASH_DOC for JSDoc/Javadoc/KDoc), `protocol.py`
(CommentStrategy Protocol — data-only, zero behaviour, same pattern as
QaSuppressionStrategy), `extractor.py` (single shared extraction algorithm,
next), `registry.py` + one thin per-language strategy file each (config
only — extension list + syntax + skip_directories + language_name), to
match the codebase's established one-file-per-language convention while
keeping the actual syntax DATA de-duplicated via the shared instances.

Language set: the 11 canonical languages from CLAUDE.md's Supported
Languages table PLUS Shell (`.sh`/`.bash`) — the field report's own
motivating example (`claude-yolo`) is a bash script, so Shell coverage is
load-bearing, not optional. HTML/XML/SQL/Lua/Lisp mentioned in the proposal
are deliberately out of scope (not in the canonical table) — logged in
PLAN.md Non-Goals.

Python docstring detection uses `doc_requires_line_start=True` (new
CommentSyntax field) so `x = """value"""` is never misread as a docstring
— only a `"""`/`'''` that is the first non-whitespace content on its line
opens a doc span.

`syntax.py` + `protocol.py` implemented TDD-first, tests green (10 passed).
Next: `extractor.py` (the load-bearing piece — line-comment runs, trailing

## 11:45 · decision · P2 — CommentSizeHandler growth model implemented, all tests green first try

Implemented `comment_size` following the `plan-doc-size` tiering model
exactly, but scoped to the TOUCHED REGION rather than the whole file:
`region_after` = `new_string` (Edit) or `content` (Write); `region_before`
= `old_string` (Edit, always defined) or the file's current on-disk text
(Write, `None` for a brand-new file). Growth is decided ONCE per call by
comparing AGGREGATE non-doc comment character totals between before/after
(not per-span matching — deliberately coarse, matching plan-doc-size's own
whole-file byte-count precedent), then applied uniformly to every breaching
span found in `region_after`:
- `chars_before is None` (new file) OR `chars_after > chars_before` -> GROWS
  -> DENY unless escape hatch or `mode: warn`
- `chars_after < chars_before` -> SHRINKS -> fully silent (no context)
- otherwise -> SAME-SIZE -> advisory context, never blocks

Docstrings/JSDoc (`is_doc=True`) are excluded from BOTH the breach check
and the growth aggregate — a growing docstring must never push an unrelated
regular comment's classification, and vice versa.

35 tests (including a `tmp_path`-backed pair for Write-on-existing-file, a
line-count-only breach to exercise the `_describe()` branch that doesn't
mention chars, and the bare-marker-no-reason escape-hatch rejection), 100%
file coverage on first attempt, mypy --strict / ruff / black all clean.

Next: register both handlers in `.claude/hooks-daemon.yaml`, HANDLER_REFERENCE.md
+ CHANGELOG entries, then the whole-repo self-scan and live daemon

## 12:20 · finding · P1/P3 — whole-repo self-scan REDESIGNED the blocking signal set

Ran the required self-scan (success criterion: measure `comment_changelog`
against this repo's own ~1,080 source/test files) BEFORE registering either
handler in config. Wrote a scratch scanner
(`/tmp/.../scratchpad/self_scan.py`, not committed — throwaway) that runs
`extract_comment_spans` + the handler's signal functions over every file
`CommentStrategyRegistry` resolves under `src/`, `scripts/`, `tests/`.

**First pass (original 5 blocking signals) found real false positives**,
not just theoretical risk:
- **2+ distinct semver tokens**: fired on this project's OWN version-
  processing docstrings (`breaking_changes_detector.py`,
  `upgrade_compatibility.py`, `config_migrations.py` — functions whose JOB
  is comparing/parsing versions legitimately cite 2+ example versions in
  their own docstrings) and on **`Task N.N.N`/`Phase N.N.N` numbering**
  (this project's OWN task-numbering convention collides with the 3-part
  semver shape, e.g. "Task 3.5.2").
- **Version-transition arrow**: fired on `version_check.py`'s own
  `# refs/tags/v2.7.0 -> v2.7.0` — describing a STRING TRANSFORMATION in
  code, not a migration.
- **Changelog verb + version**: fired on `project_loader.py`'s own
  rationale comment ("was added to the Handler base in v3.24.0 (Plan
  00133) ... deliberately NOT abstract") and `php_strategy.py`'s "removed
  in v4.0" (describing an EXTERNAL tool's deprecation, not this project's
  history) — even after tightening the verb-to-"in" adjacency.

**Only `Prior <version>:`/`Previously <version>:` and a dated entry showed
ZERO false positives** across the entire scan — every hit was either the
genuine field-report shape or this handler's own test fixtures.

**Decision**: redesigned from 5 blocking signals down to 2 (`Prior:`/
`Previously:`, dated entry). The other 3 are DEMOTED to advisory, not
dropped — they still surface as context. This is a real design change
driven by measurement, not a weakening for its own sake: the field
report's actual motivating example (6× `Prior 3.26.X:` occurrences) is
still caught cleanly.

**Also fixed** (systemic, not signal-specific):
- `_SEMVER_TOKEN` now excludes tokens preceded by `Task `/`Phase `
  (negative lookbehind) — fixes the task-numbering collision everywhere,
  not just in the entries-count signal.
- "used to" (retrospective phrase, advisory) now requires an immediately
  preceding pronoun subject (we/it/this/they/I) — bare "X used to Y" (the
  utility sense, "used [in order] to") was the single largest noise
  source in the scan (dozens of hits, nearly all utility-sense). "no
  longer" / "we switched from" showed no comparable ambiguity and are
  unchanged.

**Re-ran the scan after the fix**: 0 BLOCK hits anywhere in the repo
except this handler's own test fixtures (16, all in
`test_comment_changelog.py`); 100 ADVISE hits (never block), spot-checked
and none alarming. `comment_size`'s scan found 4 pre-existing large shell
script header comments (44-54 lines) — informational only, none would be
blocked since they're pre-existing (unchanged) content, not growth.

**Known, disclosed, NOT fixed**: the extractor's line-based Python
docstring detection can misread a large embedded triple-quoted STRING
TEMPLATE's closing `'''` (e.g. `daemon/cli.py`'s code-generation template)
as opening a new docstring, swallowing real code as "comment" text until
the next `'''`. This is the same class of limitation already documented
and accepted for `qa_suppression`/`security_antipattern` ("pattern
matching, not full analysis") — fixing it would need a real Python
tokenizer, out of scope for this plan. Now advisory-only in practice
(since the signals it happened to trip are the demoted ones), so the
practical impact of this specific known limitation is low.

Also noted (not acted on, low priority): `test_comment_changelog.py`
itself deliberately contains changelog-shaped fixture text, the same
self-reference class `qa_suppression`'s own test file already works
around via runtime string concatenation. Documented in a file-level
comment for future editors rather than reworked now — no current edit
path trips it.

46 tests still passing after the redesign, 99.47% file coverage, mypy
--strict / ruff / black clean. Next: register both handlers in config,
