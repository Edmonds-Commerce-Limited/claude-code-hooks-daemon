# Plan 00100 — Journal 26-10-12

_Scaffolded by `mkplan.bash`; timestamps in this file are UTC._

> **Append-only activity log** for plan 00100. One file per day
> (`00100-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM, ONLY with
> `mkplan.bash --journal <plan-number> <category> <body-file>` (it stamps the
> real UTC time; a hand-written entry is denied); NEVER edit earlier entries
> (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff` | `correction`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - A `correction` corrects an earlier entry without touching it. Its `REF`
>   (`--ref`, required) names that entry: `HH:MM` in this file, or
>   `YY-MM-DD/HH:MM` in an earlier one. An entry a correction names in this
>   file no longer counts for time order, so a future-dated stamp can be
>   corrected at the honest time.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 09:37 · decision · —   — Issue 84 tracked as ledger N434

Issue #84: the scan fallback in `resolve_existing_venv_python` and `scripts/lib/resolve_venv.sh` returns the lexically-first eligible `venv-*`. After an interpreter patch update that is often a legacy venv with stale metadata, so `daemon_upgrade_detector` reports a false downgrade.

Coordinator ruling: the fix is tracked as ledger 00474 N434, not reopened here. It ranks the scan's candidates by a metadata `lock_hash` match, with legacy venvs last. This plan keeps its goal of removing the scan fallback entirely; when that is scheduled, N434's ranking goes with the scan.

## 17:26 · thought · —   — Field evidence from #94: sys.version in the fingerprint orphans venvs

Field evidence from GitHub #94 against this plan's non-goal "Not revisiting the fingerprint *content*". `python_venv_fingerprint` hashes `sys.version`, which includes the interpreter's build string, so an OS update of the system Python changes the fingerprint and orphans the current venv's name. In the reported install, no venv matched the computed fingerprint, so every resolution went through the scan fallback that this plan's residue aims to remove. Ledger 00474 N434 made that scan pick the venv whose lock hash matches, which removes the false downgrade, but the orphaning remains. Keying the fingerprint on the interpreter version alone would need a migration. The decision stays with this plan's residue; the coordinator did not change it under #94 (ledger 00474 N441 covers only the stale-venv cleanup).
