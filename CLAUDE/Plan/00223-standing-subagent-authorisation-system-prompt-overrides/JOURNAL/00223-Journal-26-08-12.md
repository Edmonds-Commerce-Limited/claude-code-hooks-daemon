## 23:08 · finding · T1.2 — the full SessionStart payload fired exactly once

Split by `hookName`, the 18 SessionStart deliveries are not equivalent:

```
SessionStart:startup    1 delivery   1,223 chars
SessionStart:compact   17 deliveries   173 chars each, identical
```

The 173-char compact payload is only the dogfooding plugin reminder. The
1,223-char startup payload (plan-QA drift report and siblings) was delivered
once, at the very beginning, and never again across 18 compactions.

Mechanically explained, not guessed — `plan_qa_sweep.matches()` opens with
`if is_resume_session(hook_input): return False`, and that helper is a
transcript-size heuristic (`> 100` bytes ⇒ resume). At compact the transcript
is 56 MB, so the check is True and the handler is silent for the rest of the
session's life. Correct for a drift report; disqualifying for a standing
authorisation.

## 23:12 · decision · D1 — UserPromptSubmit only, no SessionStart companion

Decision 1 left the delivery hook open pending this phase. Settled:
UserPromptSubmit, and deliberately NO SessionStart belt-and-braces variant —
it would fire once, be compacted away, and its silence for the remaining
session would be invisible.

The argument is cadence, not wording. The restriction lives in the system
prompt, re-sent on **every** request; only UserPromptSubmit (198 deliveries,
one per prompt) matches that. This also promotes Task 3.3 from optional to
load-bearing, and constrains it: rate limiting must be a decay, not a fixed
cooldown, since a cooldown spanning a compaction rebuilds the exact failure
being avoided.

deterministic question with a deterministic answer. It does NOT answer whether

One honest observation of the failure mode, though: the user's delegation
authorisations from earlier this session **were** preserved by the compaction
summariser, and delegation still did not happen in the following segment. So
the original framing ("the request is gone by the next session") understates
it — the request is often still present, just relegated to quoted history while
the restriction stays structurally fresh every request. That asymmetry is the
better argument for the config surface.
