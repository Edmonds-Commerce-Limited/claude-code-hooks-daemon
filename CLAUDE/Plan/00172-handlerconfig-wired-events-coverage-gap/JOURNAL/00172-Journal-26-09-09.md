## 22:20 · decision · T3.1 — remove `ConfigSchema` rather than derive it

`config/schema.py` had exactly two consumers, both tests: its own unit file
and `tests/integration/test_config_integration.py`. The runtime path is
`ConfigLoader.load` then `ConfigValidator.validate` (controller.py), and
`ConfigValidator.VALID_EVENT_TYPES` is already derived from
`wired_event_metas()`. Deriving the JSON schema's `handlers` block from the
catalogue would have kept a third validator alive that nothing executes, and
Plan 00140's findings had already called it contradictory dead code. Removed
the module, its unit tests and the package export; the integration test now
exercises the live flow (its fixtures gained the `daemon` and `handlers`
sections the real validator requires, and the legacy `settings.logging_level`
key went with the schema). A new `tests/unit/config/test_package_exports.py`
locks the package to a single validation path. `jsonschema` stays a
dependency because input/response schema validation still uses it.

## 22:30 · action · T3.2 — generator subsets named and annotated

Both intentional subsets now live in a module constant with an intent
comment, so a future audit can rule them out on sight: `docs_generator`'s
plan-mode lookup (`_PLAN_MODE_EVENT_KEYS`, the only two events those handlers
register under) and `playbook_generator`'s OBSERVABLE context events
(`_OBSERVABLE_CONTEXT_EVENTS`, the events whose injected context surfaces as
a system-reminder). The playbook literal had been duplicated in the built-in
and project-handler renderers; one constant replaces both.
`playbook_harness.DISPATCHABLE_EVENTS` already carried its own rationale and
was left alone.
