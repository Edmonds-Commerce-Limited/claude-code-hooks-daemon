## 05:52 · finding · P1 — the promise is already printed, and one report breaks it

Grounded the plan in the registry BEFORE writing the task tree rather than
after — the lesson from Plan 00228, where the filed proposal turned out to be
inverted for most of its own evidence. Two things came out of it.

**The contract already exists in the code.** Every `TOOL_REGISTRY` entry
carries a `jq_hint` printed to the operator beneath the summary line:

```
✅ magic_values: 0 violations
   magic_values.json | jq '.violations[] | {file, line, rule, message}'
```

So the guard needs no new table mapping report → detail array. It can verify
the hint the tool ALREADY prints, keeping one source of truth and covering a
newly added report without anyone remembering to extend a list — the same
default-in-scope reasoning Plan 00228 settled on.

**`tests` is the exception, and that is the whole story of Plan 00226.** Its
hint points at the COUNT, not at a detail array:

```python
"tests": ToolConfig(
    command=_bash("run_tests.sh"),
    json_file="tests.json",
    jq_hint="jq '.summary'",
),
```

Every other report sends the reader to `.violations[]`, `.errors[]`,
`.issues[]` or `.probes[]`. The one report whose detail went missing is the one
whose printed hint sends the reader back to the number they already had — so
there was no surface on which the absent `.tests[]` detail could look wrong.

Consequence recorded in PLAN.md: a guard checking only the array the HINT names
would pass `tests` trivially and reproduce the exact blind spot it exists to
close. It must also check the array the SUMMARIZER READS.

Of the twenty reports only `tests` renders detail inline; the other nineteen
delegate to the hint. That delegation is deliberate — it keeps the artifact
small enough to be read in full on every run — so it is listed as a Non-Goal.
The guard is about detail being REACHABLE, not inline.
