## 07:05 · decision · — — owner chose the in-repo fix; the tracked link was rejected on evidence

The owner's direction on #54: "hooks daemon projects should expose a
standard public interface … fix this internally". Option 1, not a
consumer-side fallback.

**The issue's own proposal, a TRACKED relative symlink, was ruled out by
four checks made before this plan was filed:**

1. The wrapper already follows relative symlinks (`bin/hooks-daemon:66-80`),
   and the link was proven live. A temporary gitignored link, called from
   `untracked/scratch/`, reached this checkout's own running daemon
   (PID 581467). So the link idea itself is sound.
2. `mode_guard.sh`'s self-install test is `! -d .claude/hooks-daemon`.
   Probed on a minimal layout, `get_install_mode` went from `self-install`
   to `normal` once the link directory existed. With that, the guard that
   stops install/upgrade running in the daemon repo would stop firing.
3. Clients install by cloning this repo into `.claude/hooks-daemon/`, so a
   tracked link would appear at `.claude/hooks-daemon/.claude/hooks-daemon/`
   in every client. `init.sh:445` treats that directory as a nested install
   and exits on every hook. It has no `pyproject.toml` exemption, unlike
   `validation.py:273-281`.
4. A client's `.claude/init.sh` is a COPY refreshed at the end of an upgrade
   (`scripts/install/hooks_deploy.sh:216`). A tolerant `init.sh` therefore
   cannot be relied on to arrive before the link does.

So the link is GENERATED by the self-install daemon under the
already-gitignored `.claude/hooks-daemon/`, and never reaches a client
clone. The guard and the other "a clone is installed here" checks are
re-keyed on a real clone. Told the owner, with the two-release tracked
alternative offered.
