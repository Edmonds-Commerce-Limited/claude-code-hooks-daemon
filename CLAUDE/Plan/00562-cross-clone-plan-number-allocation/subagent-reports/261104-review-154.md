# Code Review: commit 513979b15 (Plan 00562, GitHub #154 read-only remote plan-number scan)

## Summary

The bash side is correct, read-only and bounded, and the collision test is a genuine red/green. The daemon side is not safe to merge. `next_plan_number_for_target` now fetches by default, and two PreToolUse handlers call it, which puts a fetch with a 30 s budget on the hook path. That path has a 20 s chain deadline and a 5 s per-handler budget, and the project has a stated rule of no network I/O in hooks. The bash and Python scans also handle a failed `ls-tree` differently.

Reviewed: 6 files, +514/-11. Issues: 1 critical, 3 important, 3 suggestions.

## Critical

### 1. A network fetch now runs inside PreToolUse hook dispatch (Confidence: 90%)

**Location:**
- `src/claude_code_hooks_daemon/handlers/utils/plan_numbering.py:279-285` (`include_remote: bool = True`) and `:318-319`
- Callers that now fetch: `src/claude_code_hooks_daemon/handlers/pre_tool_use/plan_number_helper.py:712` and `src/claude_code_hooks_daemon/handlers/pre_tool_use/markdown_organization.py:858`

**Problem:** The default is True, and only `record_new_plan_document` opts out. Both PreToolUse handlers therefore run `git fetch` with `Timeout.GIT_FETCH_SESSION` = 30 s on every call. For plan_number_helper that means every denied plan-dir listing or number-discovery command. These budgets are tighter than the fetch:
- `Timeout.CHAIN_DEADLINE_DEFAULT` = 20 s. In the chain, a slow handler causes guards behind it to be denied or skipped.
- `Timeout.HOOK_DISPATCH` = 5 s.

`reference_repo_freshness.py:8-12` documents the rule this breaks: "It performs no network I/O, ever ... 30s apiece against a 30s hook socket budget". The plan_number_helper message is advisory text, so a network round trip there buys almost nothing.

**Why it matters:** An offline machine, a slow VPN or an SSH host-key prompt turns a routine `ls CLAUDE/Plan` into a hook that can run past the chain deadline. When it does, it fails other guards open or closed. A daemon-side fetch also takes ref locks concurrently with the user's own `git fetch`/`pull`, which can produce "cannot lock ref" failures.

**Fix:**
- Default `include_remote` to False, or split the function so the hook path never fetches. Pass False at plan_number_helper.py:712.
- For markdown_organization.py:858, which actually allocates a folder, read the remote-tracking refs that already exist (`for-each-ref` + `ls-tree`, no fetch). That has zero network cost and still catches anything fetched by the SessionStart sweep or the user. Keep the fetch for `mkplan.bash` only.
- Add a test asserting that neither handler spawns `git fetch`, in the style of `test_the_handler_never_performs_network_io`.

## Important

### 2. The daemon-side "one stderr line" goes nowhere, and the fetch's own error is discarded (Confidence: 80%)

**Location:** `plan_numbering.py:270-276` (`sys.stderr.write(_REMOTE_UNCHECKED_NOTICE)`) and `plan_numbering.py:247-248`

**Problem:**
- Both callers run inside the daemon process, whose stderr is not the agent's transcript, so the fallback notice is invisible to the user the release note promises it to.
- `fetched.stderr` holds the reason for the failure, such as a timeout from run_git or an auth or DNS error. It is thrown away. Bash, by contrast, lets git's stderr through.

**Fix:**
- Log the notice with the reason (`fetched.stderr.strip()`) via `logger.warning`.
- Where the handler returns context (markdown_organization), append the notice to that context.
- Return the reason alongside None, for example as a small result type, rather than collapsing every failure to a bare None.

### 3. Bash and Python disagree when `ls-tree` fails on a ref (Confidence: 75%)

**Location:**
- `mkplan.bash:101` (both copies): `listing="$(git ... ls-tree ...)" || return 1`. Bash treats the remote as unchecked: notice, remote = 0.
- `plan_numbering.py:257-259`: `if listing.returncode == 0:`. Python silently skips the ref and returns a partial maximum with no notice.

**Problem:** The two are documented as mirrors, but on the same repository state they produce different outputs and different diagnostics. The Python branch also swallows an error silently.

**Fix:** In Python, `return None` when any `ls-tree` fails, matching bash. Add a parity test that corrupts or deletes one remote-tracking ref's object, or points a ref at a blob, and asserts both sides report "could not be checked".

### 4. The bounded-fetch and Cancelled/ behaviour is asserted by nothing (Confidence: 72%)

**Location:** `tests/unit/scripts/test_mkplan_remote_scan.py:670-679` (`TestFetchBudgetParity`) and `:562-572`

**Problem:**
- The only "timeout" test compares two constants. No test shows that a hanging fetch is cut off and falls back. Removing `timeout` from mkplan.bash:94, or the `timeout=` at plan_numbering.py:244, would leave every test green.
- Cancelled/ appears in the code but in no test, so dropping it from either tuple would also stay green.

**Fix:**
- Add a hang test: a remote URL whose transport sleeps, for example `ext::sh -c "sleep 60"` with `protocol.ext.allow=always`, or `GIT_SSH_COMMAND` pointing at a sleeping script. Run it with the budget overridden low, via an env var read by mkplan and monkeypatching `Timeout.GIT_FETCH_SESSION` in Python. Assert the fallback and the notice.
- Add a Cancelled/ case for both bash and Python.

## Suggestions

- **Files are counted as plans.** At `plan_numbering.py:213-220` and `mkplan.bash:102-108`, `ls-tree --name-only` counts FILES named like plans (e.g. `CLAUDE/Plan/00900-notes.md`), while the local scan (`highest_plan_number`, `entry.is_dir()`) counts only folders. Over-counting is safe because it only skips a number, but it is a third definition of "plan folder". Drop `--name-only` and keep only `tree` entries in both copies.
- **Nested archives.** The remote scan does not descend into nested archive folders (e.g. `Completed/2025/`), while the local scan does. None exist in this repo today, and the subagent report acknowledges the gap. Record it as a known limit in the docstring and the release note, or use `ls-tree -r -d` limited to the plan subtree.
- **Notice wording.** The bash notice (`mkplan.bash:127`, "mkplan: remote could not be checked...") and the Python notice (`plan_numbering.py:192`, "plan numbering: ...") share only the substring the tests grep. That is fine, but `_NOTICE` in the test is the only thing tying them together. Consider a shared constant comment.

## Positive observations

- The fetch runs before the lock, which is the right call given the lock's roughly 10 s give-up time.
- `--no-tags`, `GIT_TERMINAL_PROMPT=0`, and no checkout keep the bash scan read-only and quiet.
- The cross-clone tests use real bare remotes and clones rather than mocks, and the no-push assertion checks the remote's refs directly.
- `record_new_plan_document` correctly opts out, because it validates a number rather than allocating one.
