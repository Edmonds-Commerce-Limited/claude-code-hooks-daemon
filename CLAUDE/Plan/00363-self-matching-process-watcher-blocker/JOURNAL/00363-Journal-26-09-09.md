## 09:10 · decision · T1.1 — the detection test is the tool's own semantics

The obvious implementation is a table of "bad shapes": `pgrep -f` with a bare
word, `ps | grep` with no `-v`. That table has to be maintained against every
remedy anyone invents, and it still gets `run_0[3-9]` wrong.

`pgrep -f` matches an extended regular expression against a command line, and
the waiting shell's command line IS the command. So the classifier asks
exactly the tool's own question: **does the pattern, read as a regex, match
the text of the probe's own command line?** One test, and every documented
remedy falls out of it without being enumerated:

- `[p]rovision.bash` does not match `[p]rovision.bash` — the bracket trick.
- `run_0[3-9]` never matched its own spelling either, and is allowed for that
  reason rather than by a special case.
- `pgrep -x` compares the WHOLE line instead of searching within it, so it is
  answered before the regex test is reached.

The one ERE/Python divergence that bites here is anchors: ERE treats `^`/`$`
as ordinary characters anywhere but the ends, so the literal pattern
`'$PATTERN'` (single-quoted, nothing expanded) would read as "end of string,
then PATTERN" and find no match where the real tool finds one.
`_as_python_regex` re-spells those two.

## 09:50 · finding · T3.2 — Rule C must not flag its own remedy

The deny message tells you to wait on an artefact:
`until grep -q "PLAY RECAP" run.log; do sleep 10; done`. That is a
`while`/`until` loop with a sleep-only body and no cap — precisely Rule C's
shape. The discriminator is the CONDITION: Rule C fires only when the
condition contains a process probe. A loop waiting on a log marker has none,
so it stays silent, which is what makes the advice coherent.

Two consequences worth recording:

- A loop written inside a quoted `bash -c` script is deliberately NOT reported
  by `classify_liveness_loops`. Those are the shapes that BOUND a loop
  (`timeout 3600 bash -c '…'`), so reporting them would advise against the
  fix. Probes inside such a script are still classified — that recursion does
  happen.
- `done` closes a loop only in COMMAND position. As an argument it is an
  ordinary word, and `until grep -q done run.log; do sleep 5; done` was
  closing the loop on the operand and losing the loop actually open.

## 10:40 · decision · T3.1 — what a wrapper has to DO before `$!` lies

Rule B's spec names five wrappers, but they do not fail the same way, and
collapsing them would have produced a deny message that says something false.
Two hazards, and the split is the verdict:

- **`setsid` ABANDONS the pid.** It forks when it is not already a
  process-group leader and the parent exits at once, so `$!` names a pid that
  is gone in milliseconds. The wait ends on its first pass and reports
  success. Unambiguous, and denied.
- **`nohup sh -c`, `nohup bash -c`, `timeout`, `env` MIGHT own the wrong pid,
  and the command text does not say.** `timeout` keeps the pid, to enforce
  its own deadline; `sh -c` execs a single simple command but forks for
  anything longer; `env` and a bare `nohup` exec in place and hand the pid
  straight on. An unjudgeable difference is exactly what an advisory is for,
  and the message says so rather than asserting a fork that may not happen.

Two boundaries follow from that test rather than from the wrapper list, and
both are ALLOWED with a test naming why:

- **`nohup ./job.bash & pid=$!` is allowed.** `nohup` handed a COMMAND execs
  in place, so the pid it was given is the pid that runs. Only
  `nohup sh -c '…'` puts a shell in between, which is why the spec names the
  `sh -c` spelling and not `nohup` on its own.
- **`setsid -w ./job.bash & wait $!` is allowed.** `-w` makes the wrapper wait
  for its child, so the pid lives exactly as long as the job. The incident
  report calls `setsid -w` "not the fix", but that is about reaching for it
  INSTEAD of backgrounding; with `&` the job is still backgrounded and still
  gets its own session. Denying it would have printed "the parent exits at
  once" over a command where the parent does not, so the rule would have been
  teaching the wrong lesson to the one author who had already solved it.

`setsid` wins wherever it appears in a chain (`env FOO=1 setsid ./job &`
denies), because abandoning a pid is the worse fault.

## 10:55 · finding · T3.1 — the detection needs BOTH halves in one command

`classify_wrapper_pid_waits` reports nothing unless the same Bash invocation
both backgrounds a wrapped job and then asks about `$!`. That is not a
limitation being tolerated — a `$!` inherited from an earlier Bash call is
meaningless anyway (each tool call is its own `bash -c`), and a backgrounded
job nobody waits on has no bug to report. It also makes the guard free on the
overwhelming majority of commands: no `&` word, no work.

Three shapes the word scanner had to get right, each with a test:

- `pid=$!` then `$pid` — the capture binds the job backgrounded BEFORE it, so
  a later `&` rebinds `$!` without touching the variable. `$pidfile` must not
  match `$pid`, so the reference test is anchored (`\$\{?name\}?(?!\w)`).
- A pipeline's `$!` is its LAST stage, which falls out of walking back from
  the `&` to whatever last put the shell in command position.
- `while [ -d /proc/$! ]` is a loop keyed on the pid with no command this
  module recognises, so loop conditions are scanned separately — and a
  condition whose probe was already reported is skipped, or the same site
  would be billed twice.

## 11:35 · finding · — — a worktree's hook wrapper answers from the MAIN repo's daemon

`test_playbook_harness.py` failed on the new probe with "expected deny,
observed no decision at all", while the same command denied when the handler
was called directly. The handler was right; the dispatch was going somewhere
else.

`.claude/hooks/pre-tool-use` opens with a GENERATED relay hot path whose
paths are baked at deploy time, absolute:

```bash
_rl_dir="/workspace/untracked"
_rl_events_dir="${HOOKS_DAEMON_EVENTS_DIR:-$_rl_dir/events$_rl_sfx}"
_rl_bin="${HOOKS_DAEMON_RELAY_BINARY:-/workspace/untracked/bin/hooks-relay}"
```

A worktree checkout inherits that file verbatim, so its hook calls relay to
the MAIN repository's daemon — which runs main's code. Rule A denied (shipped
in v3.63.0, so main has it) and Rule B did not (it exists only on this
branch), which is precisely the shape of "the handler works but the harness
disagrees".

Proved rather than inferred: with the worktree daemon STOPPED, the wrapper
still returned a Rule A deny. Nothing local was answering.

The workaround is one environment variable, which makes the relay BINARY
unresolvable so the wrapper falls through to `init.sh` and the project-scoped
socket:

```bash
HOOKS_DAEMON_RELAY_BINARY=/nonexistent/hooks-relay ./scripts/qa/llm_qa.py all
```

Point the BINARY away, not the events directory. Overriding
`HOOKS_DAEMON_EVENTS_DIR` fixes the harness and then breaks
`test_relay_guard_fail_open.py::test_nc_rung_round_trip_completes_promptly`,
which builds its own events directory under a temp root and dials the path
`init.sh` computes — an inherited override sends it somewhere else, and it
fails with "the nc rung's own EOF-framed socket was never reached". The
binary override leaves that computation alone, and the relay test's own
generated forwarder already points at a binary that does not exist, so it
takes the same fall-through it was written to exercise.

Worth remembering for every worktree-isolated agent that has to run the
acceptance harness, not just this plan: without it the harness silently
measures a different checkout, and the failure it reports is indistinguishable
from a real defect.
