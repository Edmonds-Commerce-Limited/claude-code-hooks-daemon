## What shipped

### `utils/process_probe.py` — the classifier

Two public entry points, both pure:

- `classify_process_probes(command)` → one `ProcessProbe` per recognised probe
  (`pgrep`, `pkill`, `ps | grep`, `ps -p`, `kill -0`), each carrying its
  pattern, verdict (`SELF_MATCHING` / `UNRESOLVED` / `SAFE`), whether a match
  is SIGNALLED rather than reported, the wait construct it sits inside, and a
  `safe_rewrite`.
- `classify_liveness_loops(command)` → one `LivenessLoop` per `while`/`until`,
  with its condition, body, the probes in the CONDITION, and whether anything
  caps it.

**The detection test is the tool's own semantics, not a pattern list.**
`pgrep -f` matches an extended regular expression against a command line, and
the waiting shell's command line IS the command. So the classifier asks
exactly that question: does the pattern, read as a regex, match the text of
the probe's own command line? Every documented remedy falls out of that one
test without being enumerated — `[p]rovision.bash` does not match its own
spelling, `run_0[3-9]` never did, and `pgrep -x` compares the whole line
rather than searching within it, so it is answered before the regex test.

The one ERE/Python divergence that matters is anchors: ERE treats `^`/`$` as
ordinary characters anywhere but the ends, so a literal `'$PATTERN'` would be
read as "end of string, then PATTERN" and find no match where the real tool
finds one. `_as_python_regex` re-spells those two.

## Decisions worth review

**Rule A denies the one-shot too, against the filed plan.** The plan proposed
advisory-for-one-shot and deny-inside-a-loop. The incident report overrules it
on its own timeline: the agent ran the same `pgrep -f` BY HAND twice during
the night, was told "still running" both times, and believed it. The bug
produced a false positive in the check meant to catch the bug.

**Rule IDs renamed** from the first message's `R-PROCESS-PROBE-SELF-MATCH` /
`R-PROCESS-PROBE-ONE-SHOT` to the report's `R-PGREP-SELF-MATCH`. Nothing had
shipped under the old spellings, so the rename cost nothing. The one-shot rule
is gone (it denies now); `R-PGREP-UNRESOLVED-PATTERN` is a NEW third rule not
in the coordinator's list — it covers the variable-pattern case the report
lists as "not flagged", scoped narrowly to a wait or a kill so it stays quiet
on an ordinary `pgrep -f "$x"`. Drop it if you would rather ship two rules.

**Rule C must not flag its own remedy.** The deny message tells you to write
`until grep -q "PLAY RECAP" run.log; do sleep 10; done` — a `while`/`until`
loop with a sleep-only body and no cap, i.e. exactly Rule C's shape. The
discriminator is the CONDITION: Rule C fires only when the condition contains
a process probe. Two related choices:

- A loop inside a quoted `bash -c` script is deliberately NOT reported. Those
  are the shapes that BOUND a loop (`timeout 3600 bash -c '…'`), so reporting
  them would advise against the fix. Probes inside such a script are still
  classified — that recursion does happen.
- `done` closes a loop only in COMMAND position. As an argument it is an
  ordinary word, and `until grep -q done run.log; do sleep 5; done` was
  closing the loop on the operand.

**`get_relevance()` is NOT overridden.** Every project runs Bash through the
same `bash -c` wrapper, so nothing about a project could make this
inapplicable — which is the case `Relevance.always()` is the documented
default for. The behaviour is pinned by a test rather than by a redundant
override.

**The handler NAME is narrower than what it now carries.** It is called
`self_matching_process_probe` (as instructed) but holds the loop advisory too,
and would hold Rule B. `liveness_probe_guard` would be more honest; renaming
is free until this ships, and costs a config-key migration afterwards.

## Two scanner bugs the corpus caught

- `2>&1` was split on its `&` by the operator table, breaking the word so a
  redirect could be read as a pattern operand. Redirections are now matched
  before operators.
- `\pgrep -f run_02` resolved to the name `\pgrep` and matched nothing — a
  backslash suppresses alias expansion, but bash still runs pgrep. `_basename`
  now strips the same grouping/escape prefixes
  `shell_segmentation._command_word` does. Surfaced by adding the handler to
  the blocking-handler evasion suite, not by inspection.
