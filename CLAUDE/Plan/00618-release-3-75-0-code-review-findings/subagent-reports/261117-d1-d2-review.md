# Review: plan-618-d1-d2-stop-guard vs origin/main (D-1 / D-2)

Verdict: **PASS** (no loosening beyond D-1/D-2; two minor findings, three test gaps)

Scope: `git diff origin/main...origin/plan-618-d1-d2-stop-guard` (commits 6b51f5a0e..667913d50).
Code change is confined to `_pressure_findings` in
`src/claude_code_hooks_daemon/core/branch_stop_guard.py`; `branch_stop_gate.py`,
`branch_sweep.py` and `branch_inventory.py` are unchanged. Tests were read, not run
(read-only brief).

## 1. Does any change allow a stop main denies, beyond D-1 / D-2?

No. Checked each surface:

- **Dirty / unpushed / merged / handover**: produced in `_judge_branch` independently of
  `_pressure_findings`; untouched. Advisory filtering in the gate (`f.advisory`) is per
  finding, so an advisory OVER_CAP/DORMANT finding cannot mask a blocking UNPUSHED/DIRTY
  finding on the same branch (covered by
  `test_warn_mode_still_denies_a_blocking_finding_of_another_check`).
- **`off` modes**: identical to main (`!= "off"` guards kept).
- **`block` modes**: `advisory=False`, identical to main.
- **`stop_guard.mode`** (`off`/`warn`/`block`) and `unpushed_subagent`: gate logic unchanged.
- **Parked / merged pools**: `_pressure_findings` returns early for any non-OPEN pool on
  both sides; no change.
- **Name-prefix collapse**: impossible. `_with_same_tips` groups by exact commit
  (`local_tip or remote_tip`), not by name.
- **Dedup collapsing branches with different unpushed work**: different unpushed work means
  different tips, so they are not grouped. Even when grouped, the dedup only feeds the
  COUNT; dirty and unpushed checks still run on every touched record. `_unpushed` is
  tip-based (`git for-each-ref --contains <tip> refs/remotes/`), so a same-tip pair either
  shares "on a remote" or shares "on no remote" — "same tip, one name unpushed" cannot
  exist. Concrete attempts: (a) `a` and `a2` both at tip X, X on no remote, both touched,
  cap 1 -> count 1, no OVER_CAP, but UNPUSHED fires on both -> denied; (b) same pair, X
  pushed, `a2`'s worktree dirty -> DIRTY fires on `a2` -> denied. Both outcomes match main
  apart from the missing OVER_CAP line.
- **Monotonicity**: `open_work_count` uses the same `pool_of(...) == Pool.OPEN` membership
  as main's `sum(...)`, and grouping can only reduce the number, so the new OVER_CAP set is
  a subset of main's. The only extra allowed stops are (a) same-tip duplicates pushing the
  raw count over cap (D-2) and (b) `warn` modes (D-1).

## 2. Correctness findings

- **F-1 (minor, dead path)**: the D-1 dormancy half is unreachable in production.
  `branch_inventory.py:861` assigns `DormancyStage.BLOCK` only when
  `dormancy.mode == "block"` (it is the only producer in `src/`; `git grep` confirmed), so under `warn` no record reaches BLOCK and no DORMANT
  finding (advisory or otherwise) is ever produced. Behaviour is therefore identical to
  main for dormancy; the change is harmless but the `advisory=dormancy == "warn"` branch is
  dead code. `TestDormancyModeAtStop.test_warn_mode_advises_and_allows` only passes because
  it monkeypatches an impossible `(warn, BLOCK)` record.
- **F-2 (minor, docs)**: CONFIGURATION.md now says a branch "past the block stage ... is only
  reported in `warn` mode", and HANDLER_REFERENCE.md says `warn` "reports it". Per F-1, no
  DORMANT finding is ever produced under `warn`; the branch is still reported at an allowed
  main-thread stop, but via the rate-limited `_noisy_context` line (NOISY stage, as on main),
  not as a stop finding. Loosely true, misattributed; reword to point at the noisy line.
- No bug found where the tip dedup hides a touched branch's dirty or unpushed state (see 1).

## 3. Test gaps

- No test that a same-tip pair over the raw cap still denies when the shared tip is on no
  remote, or when one touched name's worktree is dirty (attempts (a)/(b) above); worth
  pinning since it is the obvious regression risk of D-2.
- Dormancy-warn test asserts an unreachable state (F-1); a test against a real inventory
  (no monkeypatch) asserting no DORMANT line under `warn` would document actual behaviour.
- No mixed-mode test (`wip: warn` + `dormancy: block`, or `wip: block` with
  `stop_guard.mode: warn`), and no SubagentStop/handoff case (pressure is skipped there on
  both sides, so low risk).
