## B-1: delete-branch content-preserved proof

- **Fix.** In `src/claude_code_hooks_daemon/daemon/branch_safety.py` (`classify_branch` and the new `_net_change_held`), `content-preserved` now requires two things. The first is the old blob check, unchanged. The second is `remote_branch_proof.holds_net_change`, renamed from `_holds_net_change` and now public. That second check passes when a first-parent commit of a target holds the branch's net change: every added or changed path has the same blob and mode, and every deleted path is absent.
- **Why it cannot loosen.** The tier requires both checks, so it can only be narrower than before. That is true by construction.
- **Fails closed.** `ProofUnavailableError`, a git timeout, or a failure to read the top level all give `unproven`, with the reason in `detail`. The proof runs from `git rev-parse --show-toplevel`.
- **Import cycle.** `remote_branch_proof` imports `branch_safety`, so the import is deferred.
- **Red tests** (`tests/unit/daemon/test_branch_safety.py`, `TestTheContentTierNeedsTheNetChange`). The reviewer's reproduction is tested with the branch cut both after and before main's v2 commit, in dry-run and real-run form. The real-run test asserts that the branch tip survives. Further tests cover a failed `git diff`, a timed-out `merge-base`, and a subdirectory as the repository argument. The in-suite differential test forces the net-change proof to true and checks that a branch whose content exists nowhere else on main still stays `unproven`.
- **Intentional tightening.** The old `dup` fixture copied existing bytes to a new path. It was `content-preserved` and is now `unproven`, pinned by `test_known_bytes_at_a_path_main_never_held_are_unproven`. The positive tests now use a real squash-merge fixture, and so do the two `TestCleanupKeywords` tests.
- **Cross-tree differential probe.** The probe is `untracked/scratch/b1_differential_probe.py` inside the worktree. It ran 9 synthetic scenarios against `/workspace/src` (the code before the fix) and against the worktree. Results: LOOSENED: []. Four scenarios tightened from `content-preserved` to `unproven`: copy-to-new-path, delete-before-v2, revert-after-v2 and mode-change. These scenarios were unchanged: merged, patch-equivalent, squash, squash-then-main-moves and novel.
- **Through the command.** `tests/unit/daemon/test_cli_delete_branch.py::TestADeletionMainNeverHeldIsRefused` runs the reproduction through `cmd_delete_branch`: exit 1, the tip survives, and the output names the net change. This test was written after the fix. The equivalent unit tests were red first.
- **Docs.** I updated the module docstring, `_TIER_DETAIL`, the docstrings of `restore_commands` and `content_unique_paths_of`, `_judge_offline`'s docstring, and the tier row in `docs/guides/HANDLER_REFERENCE.md`.

## B-2: stop guard handover

- **Own branches are never handed over.** `StopJudgement` (in `core/branch_stop_guard.py`) now carries `own`, the branches judged in full. `decide_stop` passes it to `_owned_branches` (in `core/branch_stop_gate.py`). That function never hands over a branch in `own`, whatever the signal, including a running queue record.
- **Liveness for other branches: the holds `worktree-reap` honours.** A running work-queue record (naming the branch or its worktree) or a git lock on the worktree hands a branch over. This is `ownership_refusal(..., harness_directory=False)`, exactly what `cmd_worktree_reap` calls (`daemon/cli.py` ~10002). A worktree that merely sits under `.claude/worktrees/` hands nothing over. The "handed over to running agents" line lists only branches that pass this check.
- **Coordinator decision needed.** I first tried a live-process signal (a process with its cwd in the worktree, read from `/proc/*/cwd`). I measured it from inside this live sub-agent's own worktree and it found nothing: a sub-agent's process does not sit in its worktree between tool calls. It would have missed live agents and counted leftover shells or daemons, so I dropped it. The cost of the reap predicate: a live background sub-agent in an unlocked harness worktree with no work-queue record is now judged at the coordinator's stop. The stop is denied up to `MAX_STOP_BLOCKS` times; after that the branch is recorded as abandoned and the stop is allowed, because `decide_stop` never resets its block count. Before, such a branch was handed over silently. To keep the handover, register the agent in the work queue or lock its worktree. The subset test cannot see the abandonment path, so the loosening review should look at it: a run of denials that ends in "abandoned" is the existing give-way rule, not new behaviour.
- **Red tests** (`tests/unit/core/test_branch_stop_gate.py`).
  - The reviewer's reproduction: a branch touched by the main thread, checked out under the harness directory, with a commit no remote holds and a dirty file. Both findings are now reported.
  - An own branch with each hold: a lock on its worktree, a running queue record, and a branch touched by both threads. All are judged.
  - A harness worktree with no hold is judged. The positive handover cases are a locked harness worktree and a locked plain worktree.
- **Differential test.** `TestHandOverOnlyNarrows` builds 9 combinations of touch, location, lock and queue record. For each, it recomputes the old handed set with the old formula verbatim and asserts that the new set is a subset of it.
- **Touch recording, checked.** Touches are written only by `branch_touch_recorder` (PostToolUse), under the caller's own agent id. The harness WorktreeCreate handler writes a creator record, not a touch. So an agent's worktree branch is in the coordinator's own set only if the main thread itself ran a touching git command in it. Ordinary handovers are not switched off. A coordinator that did touch the branch is now held on it, which is what the brief asks for.
