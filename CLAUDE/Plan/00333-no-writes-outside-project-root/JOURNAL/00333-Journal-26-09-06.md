## 13:58 · finding · P4 — a claim that did not survive checking

Reported that the 225 captures came from following `pipe_blocker`'s own snippet
(`TEMP_FILE="/tmp/output_$$.txt"`), so changing that one string would have
prevented ~99.6% of the residue. Checked it: **zero** files match
`output_<pid>.txt`, **zero** match `echd-capture`'s `command-output-*` stem —
every name is ad-hoc (`bl.txt`, `dq.txt`, `cli2.txt`).

The snippet was never being pasted. What the daemon supplied was the
*destination convention*, not the command, so the one-liner is habit-shaping
rather than a structural interception. Hence Phase 2 carries the enforcement and
Phase 4 is guidance hygiene — the reverse of the original pitch.

Incidental positive: no `command-output-*` file exists in `/tmp`, so
`echd-capture` never took its `/tmp` fallback. The convention holds where it is
implemented in code and fails only where it is left to agent judgement.

## 14:12 · finding · T1.1 — RED, and the diagnostic is sharper than expected

`tests/integration/test_out_of_root_write_containment.py` drives the FULL
discovered chain (`registry.discover()` + `register_all`), not one handler,
because the defect is that no handler owns the premise. 9 failed, 4 passed —
the four passing are the non-overreach controls, which trivially hold while no
guard exists.

The single most telling line is not an assertion message, it is the routing
result for a `Write` to `/tmp/00333-repro.md`:

```
ChainExecutionResult(result=HookResult(decision='allow'), handlers_executed=[],
                     handlers_matched=[], terminated_by=None, decisions=[])
```

`handlers_matched=[]`. Not one handler in the system **considered** the write.
This is worth stating precisely because it rules out the reading that some
handler weighed the path and allowed it: there was no decision to review, no
verdict to audit, and nothing that would appear in a block report. The file left
the coordinate system every rule is defined in, so the rules had nothing to say.

## 14:13 · finding · T1.1 — a fixture wart surfaced on the way

`tests/integration/conftest.py:32` writes `version: 1.0` into the fixture
project's `hooks-daemon.yaml`. YAML types that as a float and Pydantic rejects
it (`config/models.py:1842`) the moment a handler loads the file from disk
during registration. Existing integration tests never hit it because they pass
a hand-built config instead of letting registration read the file.

Worked around locally (the fixture rewrites the file with a quoted version)
rather than changing the shared fixture mid-plan. Left as an observation: the
fixture is emitting a config the daemon would reject in production.
