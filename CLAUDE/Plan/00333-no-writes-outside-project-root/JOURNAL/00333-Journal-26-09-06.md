done quietly.

The honest summary for the owner: the guard closes the shapes an agent
actually reaches for when writing scratch, and `curl -o` in particular is a
real remaining hole — it is how an installer gets downloaded, and it writes

## 16:20 · decision · T4.5 — owner called the deferred gap in, and corrected the shape

Two owner rulings landed together. First: catch the bashisms (`>`, `-o`, etc.)
— so the gap recorded at 15:45 is in scope after all. Second, on the Claude
Code deny list: *"listing deny paths seems like the wrong approach... surely we
need a whitelist"*. That is right, and it is the same failure shape this whole
plan is about — an enumerated blocklist means anything unlisted is permitted,
so `/var/log`, `/opt`, `/srv`, `~/anything` and a sibling checkout all sailed
through.

Checked whether Claude Code can express a whitelist for writes. It cannot:

- rules evaluate deny → ask → allow, first match wins, so
  `deny: ["Edit(//**)"]` + `allow: ["Edit(//workspace/**)"]` denies everything
  — a deny rule cannot carry allowlist exceptions
- no negation syntax (`!`, or "not under X")
- no writes counterpart to `blockReadsOutsideWorkingDirectories`
- `dontAsk` mode approximates it, but does not hold under `bypassPermissions`

So enumeration is the only shape available at that layer. The daemon handler
is already the whitelist — deny-by-default, empty `allowed_external_paths`,
one declared allowance — and it stays the control. Owner's follow-up settled
the disposition: keep the Claude Code layer as belt-and-braces *on top of* the
daemon, and keep it in sync. Pinned by test in both directions against
`ProjectPath.EPHEMERAL_ROOTS` (Task 4.6).

## 16:35 · decision · T4.5 — where the extraction lives, and why not the accessor

Did NOT widen `get_bash_write_targets`. Its premise is "content this command
AUTHORED", which is exactly why Plan 00260 excluded `cp`/`mv` from the content
linters: a copy relocates bytes it did not write, so blaming it would report a
defect it did not introduce. Containment's premise is the opposite — a file
lands outside the repository just as thoroughly whether the command authored it
or fetched it.

Two premises, two target sets. Widening the shared accessor would have made a
linter fire on `curl -o x.py`, a file it did not author, across 22 dependent
handlers. So the extraction is handler-local.

The subtle part is that `-o` is command-keyed rather than generic. `grep -o` is
only-matching and takes NO argument, so a blind "token after `-o`" rule reads
grep's PATTERN as a destination: `grep -o /tmp/foo file` would be denied as a
write, and it writes nothing. Same for `tar` — `-xf` extracts FROM a path and
is a read; only a create flag makes the archive a destination. Both are pinned
by tests that assert the NON-match.
