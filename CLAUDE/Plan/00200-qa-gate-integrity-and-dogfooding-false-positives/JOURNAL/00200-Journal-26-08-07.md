## 09:05 · finding · T6.5 — shared-checkout index race fired twice

Relocated from `PLAN.md`. Running four agents in one `/workspace` checkout
produced a defect class I created by the orchestration model itself.

Incident 1 — lost content. An agent's `git commit` landed a `git mv` as a
pure rename with **no content change**; its staged status-flip and task-ticks
never reached the commit. Caught only because the agent ran `git diff`
afterwards and looked.

Incident 2 — absorbed content. A different agent's `git commit` swept up a
third agent's staged deletion (`02de0cf7` swallowing the `00199`
`COUPLING-ANALYSIS.md` removal), committing someone else's work under its own
message.

Root cause is the same both ways: **bare `git commit` commits the entire
index**, not what the caller `git add`ed. With concurrent writers on a shared
`.git/index`, staged work is absorbed or clobbered between `add` and `commit`.
Neither agent did anything wrong by ordinary single-writer habits — which is
precisely why a guard is warranted rather than a rule nobody remembers.

Verified nothing was lost: `COUPLING-ANALYSIS.md` recoverable from
`9ffbe403`, and its intended replacement `PROPOSAL-ASSESSMENT.md` is intact
in the working tree. The deletion was deliberate; it merely landed under the
wrong commit message.

Containment: instructed all three live agents to use `git commit <pathspec>`
exclusively, and to verify with `git show --stat HEAD` rather than trusting
the exit code.

The DBF defence is cheap because the daemon **already knows**:
`handlers/status_line/thread_registry.py` + `multithread_indicator.py` track
live agent threads per project. Task 6.5 turns that into a PreToolUse
advisory on bare `git commit` when more than one thread is registered.

## 09:34 · finding · T1.6 — why the capture-corruption guard missed the lint swallow

Assigned Tasks 1.5 + 1.6. **Task 1.5 status first**: found the exact
`JSONDecodeError`-swallow fix already present, uncommitted, in
`run_dependency_check.sh`/`run_security_check.sh`/`run_smoke_test.sh` --
this is the Phase 5 agent's `audit_error_hiding.py` triage (09:05 entry
above, "the exact same JSONDecodeError-swallow shape in FOUR sibling QA
scripts"), already flagged to team-lead for dedup. Did not re-touch or
re-commit those three files -- would have duplicated/risked conflicting
with in-flight work in a shared checkout, exactly the T6.5 hazard this
same journal documents twice above. Spent the session on Task 1.6 instead.

**Root cause**: `audit_capture_corruption.py`'s two rules only recognise
`$(name ...)`/backtick command substitution as "risky stdout consumption"
(`_CAPTURE_CALL_RE`, `_BACKTICK_CAPTURE_RE`). Neither rule has ANY regex
for a plain `cmd > file` / `cmd >> file` redirect -- which is exactly the
shape that broke `run_lint.sh`: `venv_tool ruff ... > "${OUTPUT_FILE}.raw"`
is a redirect, not a substitution. `venv_tool` is never `$(...)`-captured
anywhere in the tree, so it fails BOTH rules (not captured, not
log-helper-named) and its body -- and therefore `ensure_venv`, which it
calls by bare name -- was never walked by `_audit_function_body` at all.

Secondary, reinforcing finding: `ensure_venv` (the `venv-include.bash` one)
DOES coincidentally appear in the pre-fix auditor's `all_captured` set --
not because of this bug, but because an unrelated, differently-implemented
`ensure_venv()` in `scripts/install/venv.sh` genuinely IS `$(...)`-captured
in three other scripts (`upgrade_version.sh`, `setup_worktree.sh`,
`install_version.sh`). Capture detection is NAME-based across the whole
scanned tree, with no per-file scoping, so the name collision drags the
unrelated `venv-include.bash` definition into "captured" too. But even so,
the terminal-position heuristic (rule #1) would have called the buggy
banner echo SAFE -- it sits immediately before `return 0`, textbook
"this is the function's `$(...)` return value" shape. That heuristic
correctly models single-function `$(...)` capture (nothing else shares the
stream) but does not generalise to `venv_tool`'s composition, where
`"${tool_path}" "$@"` (the real tool) ALSO writes to the same redirected
stream immediately after `ensure_venv` returns. So even a name-collision
fix alone would not have caught this: the redirect gap is necessary, not
just the name-matching gap.

**Extended, did not argue against extending** -- this is a natural
generalisation of the existing model, not a different concern:

- New `_collect_redirect_consumed_names()`: known-function-name (scoped to
  avoid misfiring on e.g. `[[ "$a" > "$b" ]]` string comparison, whose
  first token `[[` is never a function name) invoked on a line matching
  the existing `_REDIRECT_FILE_RE` (already used elsewhere in the file to
  detect an echo's OWN redirect; reused here for a caller's redirect of a
  whole command).
- New `_propagate_redirect_consumption()`: fixed-point closure over the
  bare-call graph -- a function invoked by bare name (not `$(...)`) from
  within an already redirect-consumed function's body inherits the same
  requirement, since its output shares the caller's redirected stream.
  This is what's needed to reach `ensure_venv` from `venv_tool`.
- Redirect consumption enforces ZERO TOLERANCE (no terminal-position
  exemption, same strictness as the log-helper rule) -- a redirect
  concatenates the entire stream for the block's lifetime, so there is no
  privileged "last echo is the payload" position the way there is for a
  single `$(...)` capture.

**Two real correctness bugs found and fixed while building this, both by
running against the ACTUAL repo, not just synthetic fixtures**:

1. Naive name-based propagation reintroduced the exact name-collision
   problem for the NEW rule: `venv_tool` correctly entered the
   redirect-consumed set, but propagation resolved "ensure_venv" (the bare
   call inside `venv_tool`'s body) against a GLOBAL `{name: FunctionDef}`
   dict, which the unrelated `scripts/install/venv.sh:ensure_venv`
   silently won by iteration order -- flagging 3 false positives against
   a function that was never at risk. Fixed by resolving every
   redirect-consumed function as a `(file, name)` pair, not a bare name,
   with the propagation step preferring a same-file definition for the
   callee before falling back to a global-unambiguous match, and
   declining to guess (no flag) when neither resolves cleanly. Pinned
   with `test_name_collision_across_files_does_not_leak_risk_to_the_other_definition`.
2. The pre-existing function-level marker on `venv-include.bash`'s
   `ensure_venv` (`capture-audit: allow -- legacy ensure_venv... never via
   $(...) capture`) was blanket-suppressing BOTH `is_captured` and my new
   `is_redirect_consumed` -- even though its stated reason only rebuts the
   FIRST. A marker written to silence one false-positive category should
   not silently exempt a function from an unrelated, later-added rule;
   that is precisely "guard exists but doesn't cover it" for a second,
   subtler reason (an over-broad suppression, not a missing regex).
   Re-scoped the marker to `is_captured` only. Re-running against the
   REAL repo with that fix live immediately surfaced a genuine, currently
   -shipping latent bug: `venv-include.bash:106` (the "Venv not found,
   creating..." banner on the fresh-clone/first-run path) was still
   missing `>&2` -- Task 1.2's original fix covered the "venv already
   exists" banner and its siblings but not this one, presumably because
   it's a rarer code path. Fixed (added `>&2` + an explanatory comment).

**Known, documented scope limit** (not fixed, judged out of scope for a
regex-line auditor): bare-call detection only looks at the FIRST WORD of
a line, so a callee named after a `&&`/`||` chain on the same line (e.g.
`mkdir -p "$X" && ensure_venv`) would not propagate. Not currently present
anywhere in the scanned tree; documented in the code and here rather than
silently assumed away.

**Left un-generalised, deliberately**: did not also propagate the
EXISTING `$(...)`-captured set through the bare-call graph (a captured
function's bare-called helper could equally corrupt its return value).
Same fix shape would apply, but widening rule #1's blast radius across
the whole tree was not this task's scope and risks overlapping the
Phase 5 agent's concurrent `scripts/` sweep. Noted as a reasonable
follow-up, not done here.
