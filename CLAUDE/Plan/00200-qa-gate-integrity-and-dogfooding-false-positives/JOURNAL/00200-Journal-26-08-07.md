## 08:45 · finding · P5 — why BOTH error-hiding defences missed the lint swallow

Relocated here from `PLAN.md` to keep that document lean; the task statements
remain there.

The Phase 1 bug was textbook error hiding in a repo shipping two defences
against exactly that, and neither fired. Two independent reasons for the
batch auditor, either sufficient on its own:

- `scripts/qa/audit_error_hiding.py:298-299` scans `workspace / "src"` only,
  commented *"production code only"*. The QA scripts that **implement the
  gates** are therefore exempt from the gate — the tooling sits outside its
  own jurisdiction.
- `:182` globs `*.py` only. The swallow lived in Python embedded in a bash
  heredoc inside a `.sh` file, so it was invisible a second time over.

And for the write-time handler: `error_hiding_blocker` and its
`shell_strategy` (`strategies/error_hiding/shell_strategy.py`) genuinely do
know `.sh`/`.bash` and do match `|| true` — but they only fire on Write/Edit.
Nothing sweeps files already on disk, so everything predating the handler, or
written outside a Claude session, is permanently unexamined.

That last point generalised into `CLAUDE.md` Core Standard 15's corollary:
**a write-time guard needs a batch equivalent, or it only ever protects the
future.**

## 09:05 · finding · T6.5 — shared-checkout index race fired twice

Relocated from `PLAN.md`. Running four agents in one `/workspace` checkout
produced a defect class I created by the orchestration model itself.

Incident 1 — lost content. An agent's `git commit` landed a `git mv` as a
pure rename with **no content change**; its staged status-flip and task-ticks
never reached the commit. Caught only because the agent ran `git diff`
afterwards and looked.

Incident 2 — absorbed content. A different agent's `git commit` swept up a
third agent's staged deletion (`02de0cf7` swallowing the `00199`
`COUPLING-ANALYSIS.md` removal), committing someone else's work under its own
message.

Root cause is the same both ways: **bare `git commit` commits the entire
index**, not what the caller `git add`ed. With concurrent writers on a shared
`.git/index`, staged work is absorbed or clobbered between `add` and `commit`.
Neither agent did anything wrong by ordinary single-writer habits — which is
precisely why a guard is warranted rather than a rule nobody remembers.

Verified nothing was lost: `COUPLING-ANALYSIS.md` recoverable from
`9ffbe403`, and its intended replacement `PROPOSAL-ASSESSMENT.md` is intact
in the working tree. The deletion was deliberate; it merely landed under the
wrong commit message.

Containment: instructed all three live agents to use `git commit <pathspec>`
exclusively, and to verify with `git show --stat HEAD` rather than trusting
the exit code.

The DBF defence is cheap because the daemon **already knows**:
`handlers/status_line/thread_registry.py` + `multithread_indicator.py` track
live agent threads per project. Task 6.5 turns that into a PreToolUse
advisory on bare `git commit` when more than one thread is registered.

## 10:02 · action · T6.4 — negative-case requirement built; six handlers fixed

Executed in an isolated worktree
(`.claude/worktrees/agent-aac9d627ef861e2b0-45cd43b6`), dispatched
separately from the four agents in incident T6.5 above — deliberately, to
avoid adding a fifth writer to the shared `/workspace` index.

**The requirement.** `find_deny_capable_handlers_without_allow_case()`
(`src/claude_code_hooks_daemon/daemon/playbook_generator.py`) takes the
same dict shape `generate_json()` already produces (source/event_type/
handler_name/expected_decision) and flags any handler that declares a
`deny`-expecting acceptance test but no `allow`-expecting one. Pure
function, unit-tested in isolation
(`tests/unit/daemon/test_playbook_generator_negative_case.py`, 8 cases).
Enforced end-to-end in
`tests/integration/test_acceptance_negative_case_requirement.py` against
the REAL production handler set — `HandlerRegistry.discover()` for
library handlers plus `ProjectHandlerLoader.discover_handlers()` against
`.claude/project-handlers/` for project handlers (`EnforceLlmQaHandler`,
`ReleaseBlockerHandler`) — so a project handler's false positive is caught
by the same gate as a built-in one, not a second bespoke check.

Considered the `harness_cannot_produce` / `_skip_block()` precedent (Plan
00196) — a per-test declarative exemption field on `AcceptanceTest`.
Chose a **centralised, dated allowlist** in the integration test instead:
touching 16+ handler files just to add an exemption marker was
disproportionate to today's scope, and the user's own scope-discipline
guidance explicitly sanctioned "a tracked allowlist, then ratcheting" for
the deferred set. The allowlist test asserts EXACT set equality in both
directions — a handler added without a matching removal fails as loudly as
a handler fixed without shrinking the list — specifically so it cannot
quietly become permanent cover.

**Measurement before fixing.** A one-off probe (immediately deleted, never
committed) walked the full production `PlaybookGenerator.generate_json()`
output before any fix landed: 20 DENY-capable handlers had no ALLOW case
(19 library + `EnforceLlmQaHandler`). `lsp_enforcement` already had an
ALLOW case (a different near-miss shape: regex-vs-literal, not
single-file scoping) — it satisfied the generic requirement already, but
not the SPECIFIC false positive being fixed, which is exactly why "add the
specific regression, not just satisfy the generic rule" mattered.

**The six fixes** (each: failing test first, then the minimal correct
change, each independently commit-checkpointed):

1. `EnforceLlmQaHandler` (`.claude/project-handlers/pre_tool_use/
   enforce_llm_qa.py`) — `cat scripts/qa/run_all.sh` was blocked.
   `_is_inspection_only()` recognises cat/less/more/head/tail/grep/rg/wc/bat
   as read-only per shell segment; `echo` deliberately stays in the
   "execution" bucket unchanged — that's this project's own
   echo-as-safe-test-stand-in convention (CLAUDE.md), not a bug.
2. `destructive_git` — `git tag -f v1.0.0 <sha>` turned out to be
   ALREADY correctly unmatched (verified via direct probe against the
   worktree source before writing any test); the force-push pattern was
   already segment-scoped to `git push`. Added a permanent regression
   test class pinning that plus a guardrail asserting a real forced push
   still blocks — no source change to the matcher itself.
3. `pipe_blocker` — a `git commit -m` (including the canonical
   heredoc-embedded `-m "$(cat <<'EOF' ... EOF)"` idiom used throughout
   this repo's own CLAUDE.md) whose message quoted a `| tail` example as
   prose was scanned as a real pipe. New `_strip_message_bodies()`
   blanks `-m`/`--message`/`-F`/`--file` VALUES (heredoc-aware) before
   pipe detection; deliberately scoped to those flags rather than generic
   heredoc-stripping, because a heredoc fed to a live interpreter (`bash
   <<EOF ... | tail ... EOF`) must stay detected and a message-only fix
   can't accidentally swallow that case.
4. `lsp_enforcement` — `grep -n "hook_input" <one file>` was blocked as a
   workspace-wide symbol lookup. `_is_single_file_bash_grep()` exempts a
   Bash grep/rg with no recursive flag and exactly one non-directory,
   non-glob positional target; a directory target, `-r`/`-R`, multiple
   targets, or no target at all still enforce. Scoped to the Bash grep
   path only (not the `Grep` tool's `path` field) per the reported bug's
   shape — documented as an explicit non-goal in a test, not silently
   left inconsistent.
5. `plan_number_helper` — `find CLAUDE/Plan -maxdepth 1 -type d -name
   '[0-9]*' | wc -l` (a plan COUNT for a stats line) was blocked as
   number DISCOVERY. `wc` counts; it can never be part of a
   sort+tail "find the latest" idiom, so a command piped to `wc` is
   excluded from every discovery pattern up front, regardless of which
   other pattern it also happens to match.
6. `plan_qa_commit_gate` (Task 3.5) — `git commit <pathspec>...` commits
   the WORKING TREE content of exactly the named paths regardless of
   staging, and excludes anything else staged; `GitFacts.staged_changes()`
   only ever read the INDEX (`git diff --cached`), so `same-commit-plan-doc`
   advised "does not update its PLAN.md" on a commit that demonstrably
   did. `GitFacts` gained an optional `pathspecs` constructor arg — when
   set, diffs HEAD against the WORKING TREE scoped to those paths instead
   of `--cached`. Threaded through `staged_context()` and the handler's
   own tokeniser (which already extracted `-m` the same way). Every
   check reading `gitfacts.staged_changes()` benefits, not just this one;
   a bare commit (no pathspecs) is byte-identical to the old behaviour.
