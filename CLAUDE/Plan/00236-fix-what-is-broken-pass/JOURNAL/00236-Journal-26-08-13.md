## 17:45 · finding · T4.1 — what the daemon can actually observe

Before choosing between "emit pgid" and "drop the dead path" I checked what is
observable. Backgrounded `sleep 90; echo done`, then `ps`:

```
667222  667222  /bin/bash -c … eval 'sleep 90; echo done' …
667224  667224  sleep 90
```

Two things settled the design. The recorded command text appears verbatim in
the wrapper's args, so read-time correlation works. And the child sits in its
OWN process group (667224 ≠ 667222), so even a captured parent pgid would have
missed it.

## 17:50 · decision · T4.1 — correlate by command text

`read_tracked_pgids` → `read_tracked_commands`;

seam, and rewrote the two fabricating unit tests to use the production shape.

Also updated the entry in `scripts/qa/error_hiding_exclusions.json`: it keys on

## 17:52 · action · T4.2 — lsp_enforcement multi-line

`_SEGMENT_TERMINATOR` listed `&&`, `||`, `;`, `|` but not `\n`, so every
following LINE of a multi-line script counted as another positional argument to
the grep; the target count exceeded one and a single-file grep lost its
exemption. It held only for one-liners.

While writing that test I noticed the exemption inspected only the FIRST grep,
so `grep -n x a.py` on line one bought cover for `grep -rn x src/` on line two.
Fixed both. 79 tests green.

Separately: twice this session the handler fired on a legitimate content grep
of a JSON directory (`grep -rl 'run_in_background' untracked/payload-capture`).
That one is by design — recursive flag plus a snake_case pattern. Logged so it
is not re-investigated as a bug.
