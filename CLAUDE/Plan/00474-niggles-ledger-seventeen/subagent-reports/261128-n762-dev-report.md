## Job 1: what the relay and transport do when the daemon answers after the limit

### Probe

`tests/integration/test_hook_transport_slow_daemon_probe.py` (7 tests, about 7 s). The stand-in
daemon (`_SlowDaemon`) is an AF_UNIX socket in a short temporary directory. It reads the request
to EOF, sleeps 4 s, and then sends a verdict: an allow for PreToolUse, a block for the other
events. The client limits are shortened: `--timeout-ms 500` on the relay and
`CLAUDE_HOOKS_SOCKET_TIMEOUT=1` on the python3 transport. The real daemon is never contacted.
The forwarders are generated by `generate_forwarder_content` in a tmp project, with a real copy
of `init.sh`.

| Transport                                | Event                                                                             | Result                                                                 | Test                                                                           |
| ---------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| relay (`relay/hooks_relay.rs`)           | PreToolUse (`pre-tool-use.sock`, `--fallback` = the generated forwarder)          | **deny**. The late allow is never used.                                | `TestTheRelay::test_a_pre_tool_use_answer_after_the_limit_is_denied`           |
| relay                                    | user-prompt-submit, post-tool-use                                                 | **`{}`, fail open**. The late block is never used.                     | `TestTheRelay::test_any_other_event_after_the_limit_fails_open`                |
| relay                                    | a PreToolUse payload on a socket NOT named `pre-tool-use.sock`                    | `{}`, fail open: the event comes from the socket name, not the payload | `TestTheRelay::test_the_event_is_read_from_the_socket_name_not_the_payload`    |
| python3 (`init.sh` `send_request_stdin`) | PreToolUse                                                                        | **deny** (`socket_timeout`)                                            | `TestThePythonTransport::test_a_pre_tool_use_answer_after_the_limit_is_denied` |
| python3                                  | Stop, SubagentStop (these never use the relay: `RELAY_EXCLUDED_EVENT_FILE_NAMES`) | **`{}`, exit 0, fail open**. The late block is never used.             | `TestThePythonTransport::test_a_stop_block_after_the_limit_fails_open`         |

How each path works:

- **Relay, PreToolUse.** `mid_exchange_fail` calls `judge_via_fallback`, which runs the
  forwarder with `--no-relay` and `HOOKS_DAEMON_RELAY_FAILED`. `init.sh` then denies every call
  except the exact recovery command. If the hand-off fails, the relay writes its own deny
  (`fail_body`). The budget is 30 s for the relay plus 10 s for the hand-off, which is under
  Claude Code's 60 s PreToolUse hook timeout (`.claude/settings.json`).
- **Daemon side.** Before either client limit is reached, the chain deadline applies
  (`daemon.chain.deadline_seconds`, 20 s by default, in `core/chain.py:840-872`). It ends every
  chain still running. A chain that has any SAFETY+BLOCKING handler, finished or not, gets a
  `HookResult.deny` from the daemon with the reason "chain: not judged in time"; on Stop that
  is a block. A chain with none is answered with what its finished handlers decided, and the
  unfinished handlers' output is dropped. So the client-side timeout decides the outcome only
  for a daemon that cannot answer at all (wedged, the GIL-hang shape).

### Owner decision (behaviour NOT changed)

A guard that must block fails open on a client timeout for two event classes:

1. **Stop / SubagentStop.** A wedged daemon has two outcomes:
   - While connects still succeed, the error is `socket_timeout`, and `emit_error_json`
     returns `{}`. This was a deliberate choice in Plan 00177, made so that a reached-but-slow
     daemon does not wedge the session in a 30 s stall loop. The stop is therefore allowed even
     though the branch stop guard (R-BRANCH-STOP-GUARD), the QA-failure stop or the
     goal-ledger stop would have blocked it.
   - Once the daemon's accept backlog is full, the error is `connect_backlog_full`, and
     `init.sh:4169-4182` blocks the stop, bounded by `_stop_bound` (Plan 00555). A daemon that
     cannot be reached at all also blocks, with the same bound.
2. **UserPromptSubmit on every transport.** On the relay `fail_body` gives `{}`. On the python3
   transport (relay off, or after the relay's connect-fail fallback), `init.sh:4232-4248` gives
   context only. In both cases, a prompt the usage-pause gate (R-USAGE-PAUSE-PROMPT) would
   block goes through when the daemon is wedged.

The options for the owner: keep the current behaviour (availability over enforcement for
non-tool events); make a Stop `socket_timeout` block, using the Plan 00555 bound that a down
daemon already uses so the session cannot loop forever; or extend the fail-closed carve-out to
UserPromptSubmit on both the relay and the python3 transport. The probe pins today's answer, so whichever is
chosen will turn the matching test red, and that test is the one to change deliberately.

### Found and fixed

- `tests/integration/test_relay_mid_exchange_timeout_fails_open.py` is **removed**. Its
  docstring said a PreToolUse mid-exchange timeout fails open "today" and that the pin should
  go red once N24 landed. N24 did land, but the test stayed green because its socket was named
  `daemon.sock`, not `pre-tool-use.sock`. It was pinning the non-PreToolUse path under a
  PreToolUse label, which suggests a fail-open bypass of the full-QA guard that does not exist.
  The probe's socket-name test covers the same property and labels it correctly. The
  `pre-tool-use.sock` name in every generated forwarder is pinned in
  `tests/unit/install/test_forwarder_generator.py:417`.
- `src/claude_code_hooks_daemon/core/force_removal.py`: two comments said the relay "may then
  let the command through" or would "fail open". That is false for PreToolUse. They now say
  that the budget stays under the chain deadline, and that refusing the removal here gives this
  guard's own reason rather than the deadline's unjudged deny. Only comments changed.

## Job 2: a test that fails without `git_deadline`

`TestPatchHeldProofIsBounded::test_no_git_is_spawned_once_the_budget_is_spent_midway_through_a_proof`
in `tests/unit/handlers/pre_tool_use/test_destructive_git_force_removal.py`:

- It wraps `branch_safety.patch_equivalent`. When the answer is `(True, 0)`, meaning the ref
  will go on to the net-change step, it moves the fake clock past the budget.
- It records every `subprocess.run` call. It asserts that some git ran in time (so the test is
  real), that no git was spawned after the deadline, and that nothing is held.
- The clock moves only on the passing ref. A first version moved it on any ref, and then even
  the mutated code stopped at the next loop-top clock check, so that version did not isolate
  the deadline.

Mutation check: `with git_deadline(deadline, clock):` was replaced by
`with contextlib.nullcontext():`. Result: the new test failed with
`git spawned after the deadline: [[... 'merge-base', 'refs/heads/other', ...], [... 'diff', '--raw', ...]]`
and the six other tests in the class still passed, which confirms the old overrun test does not
cover the deadline. After restoring the original line, all 54 tests in the file pass.

## Review follow-up

The independent review (`/workspace/untracked/agent-reports/auto/261128-085347-code-reviewer-a70e74af9b5972bcb.md`)
APPROVED the branch with 4 minors. All four are fixed:

1. **The relay hand-off was not asserted.** The relay PreToolUse test now asserts that the
   deny reason contains `relay_exchange_failed` and does not contain `transport-fail-closed`.
   Mutation check: I made `judge_via_fallback` return at once and rebuilt the relay. The test
   went red on the relay's own `transport-fail-closed` deny. With the source restored and the
   relay rebuilt, all 7 pass (commit `3efe3a6db`).
2. **The chain-deadline wording was wrong.** The probe docstring, this report and N762 now say
   that a chain with any SAFETY+BLOCKING handler is denied, finished or not. They also state
   the case of a chain with none: it is answered with what its finished handlers decided, and
   the rest is dropped. The earlier docstring had said the client timeout decides for such a
   chain, which was wrong: the daemon answers it at the deadline.
3. **UserPromptSubmit was described as failing open on the relay only.** It fails open on every
   transport, and the docstring, this report and N762 now say so.
4. **Only one outcome of a wedged daemon was given.** Both are now stated: `socket_timeout`
   allows the stop, and `connect_backlog_full` blocks it, bounded by `_stop_bound`.
