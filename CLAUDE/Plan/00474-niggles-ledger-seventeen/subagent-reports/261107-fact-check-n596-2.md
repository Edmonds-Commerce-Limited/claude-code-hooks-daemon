## REFUTED (most consequential first)

**R1. "the background sync's state write leaves a window with no file (a remove then write, or a replace that is not one atomic rename)" and the Proposal "make every write a temp file plus one rename".**
The state write is ALREADY temp file plus rename, and never removes the path.

- `.claude/provision.sh:917-926` `_provision_background_record`: writes `$SYNC_STATE_FILE.tmp.$$`, then `mv -f "$tmp" "$SYNC_STATE_FILE"`. Called at 1005 (running) and from the EXIT trap `_provision_background_finish` (969-977).
- `.claude/provision.sh:300-306` `_provision_record_interrupted`: also tmp plus `mv -f`.
- `src/claude_code_hooks_daemon/install/background_sync.py`: no write_text, open, rename or unlink; it only reads state back (provision.sh:171-172 says so).
- No other writer of `v<version>.state` in `.claude`, `src` or `scripts`. I did not read `tests/fixtures/cyber-flag` (guard-blocked).
  So the write is not remove-then-write, not truncate, and not non-atomic. The proposed fix is already in place.

**What the plan should say instead (the real window, found in the same file).** The path vanishes because of the directory SWITCH, not the write:

- `_provision_switch`, `provision.sh:772-784`: moves every entry of the live `$DAEMON_DIR/untracked/` (except stage, marker and old venv) into `$SYNC_STAGE_DIR/untracked/`. That includes `background-sync/` and so `v<version>.state`.
- `provision.sh:786-788`: renames `$DAEMON_DIR` aside, renames the staged clone onto `$DAEMON_DIR` (`_provision_rename_onto_live`, 213-220), then renames aside to previous.
- Between the entry move and the final rename onto the live path, `.../untracked/background-sync/v9.9.9.state` does not exist at its live path. `_provision_uncarry` (265-274) puts entries back on a failed switch.
  This matches the failure: `_outcome` sees the file (status running), then `_state` runs and finds it gone. The fix is in the switch (or a reader that tolerates the swap), not in the record write. The "test first" idea (reader polls while the sync rewrites repeatedly) would not reproduce it.
