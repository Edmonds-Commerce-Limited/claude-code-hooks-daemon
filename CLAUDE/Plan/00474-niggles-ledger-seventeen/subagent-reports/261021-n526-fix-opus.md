# N526: full-QA script scan, fail-open check and per-line cost

Branch `worktree-n526-scan-cost`. Commits: `b7d2275fd` (N526c), `a75f800cc` (N526a/b), followed by the docs commit.

## N526c: why a 4000-line script returns at once

A 4000-pair probe script is about 112 KB, which is past `_MAX_PARSED_BYTES` (96 KiB). `_full_run_in_code_file` passes
such a file to `_scanned_verdict` instead of parsing it. That function does a linear raw scan for any declared program
name.

The verdicts the probe measured for 4000 filler pairs:

| tail                                                           | verdict                                                  |
| -------------------------------------------------------------- | -------------------------------------------------------- |
| none                                                           | None (no declared program is named)                      |
| `subprocess.run(['./scripts/qa/llm_qa.py','all'])`             | `llm-qa-whole-suite`, fail_closed=`_SCANNED_FILE_REASON` |
| `subprocess.run(['pytest'])`                                   | `pytest-whole-suite`, fail_closed=`_SCANNED_FILE_REASON` |
| `b=['./scripts/qa/llm_qa.py']; b=b+['all']; subprocess.run(b)` | `llm-qa-whole-suite`, fail_closed=`_SCANNED_FILE_REASON` |

The oversized path is not silent. Its verdict is `fail_closed` with a reason, and `unseen_policy` decides what happens
next. The default, `advisory`, allows the run and prints the reason in a loud advisory. That default is a deliberate,
documented ruling: the handler class docstring and the comment above `_UNSEEN_POLICY_ADVISORY` record it as review
10 M1, kept by the coordinator in rounds 9d/10. I left it unchanged. If the owner wants a scanned file that names a
full-suite program to be DENIED by default, that is a policy decision for the owner.

## The fail-open that was real (below the size cap)

At 2000 pairs, the variable-built tail (the last row of the table above) returned `None`. Bisecting found that it is
caught at 1088 pairs and missed from 1089 pairs on. `_grown_argvs` charges each grown argv to the parse meter. Once the
meter was spent, it skipped every remaining call. Its docstring describes this ("past it the lists are left to be judged
as they are written"), but it contradicts the meter's own contract (`_MAX_PARSED_BYTES`: "Past it the command is
DENIED"; review 8 B1). It was an implementation choice made for cost in batch X round 2, not an owner or coordinator
ruling. I fixed it on the owner's no-silent-fallback rule.

The coordinator should confirm this reading. If the drop was meant to be deliberate, revert `b7d2275fd`.

RED (`test_a_grown_list_past_the_parse_meter_is_judged_over_budget`, before the fix):

```
E       assert None is not None
1 failed, 1 passed, 1473 deselected in 2.11s
```

The fix: the first call the meter cannot afford ends the sweep. `_PythonStrings.over_budget` carries that out to
`_python_commands`, which yields `_OVER_BUDGET` after every other invocation. The match is `too-much-code-to-judge` with
`_OVER_BUDGET_REASON`, and a run that is seen positively still wins (the second test covers this).

## N526a/b: per-line cost

cProfile at 2000 lines showed about a dozen whole-tree passes, each one re-walking with `ast.walk` or
`iter_child_nodes`: 682k `iter_child_nodes` calls for one file. `_tree_index` now sweeps each parsed tree once per
judgement. It stores the nodes in `ast.walk` order plus each node's children, keyed by the node itself, and lives in a
ContextVar set beside the parse meter. The whole-tree walks and the four hand-rolled traversals read from it. Marker
leaves (Load, Store, operators) are left out. No pass dispatches on them, and they make up about a third of the tree.

CPU time, best of 5, measured back to back on the same host against a `b8fff2363` checkout, at 2000 lines:

| shape              | before | after |
| ------------------ | ------ | ----- |
| a.insert(0,'x{i}') | 0.348  | 0.147 |
| a.insert(1,'x{i}') | 0.351  | 0.165 |
| a.pop()            | 0.212  | 0.109 |
| a=a+['x{i}']       | 0.325  | 0.196 |
| a=['y']+a          | 0.415  | 0.179 |

The ledger's 0.8-0.9 s figures are wall-clock times on a loaded host. Wall time on this host swings by about 2x between
runs. The 1.5 s bound is unchanged, and the whole handler test file passes (1475).

## Not done: a scaling-ratio assertion

I did not add the optional assertion that time(2N)/time(N) stays below 3. On this host the per-shape CPU ratio ranged
from 1.2 to 2.5 between runs, so a guard set at 3 would have little margin under parallel CI load. I judged it not
robust enough to add.
