## REFUTED (most consequential first)

R1. N594 "the handler resolves ruff differently from the session ... most likely with the daemon process's PATH rather than the project's pinned tool location" and the proposal "make the lookup also try the project's declared or venv tool locations".

- The handler already tries those locations first.
- `lint_on_edit._resolve_executable` (handlers/post_tool_use/lint_on_edit.py:360-383) delegates to `resolve_lint_executable` (strategies/lint/common.py:39-73).
- The search order there is workspace `bin_dirs`, then `INTERPRETER_BIN_DIR` (the daemon interpreter's own bin), then `shutil.which`.
- For a `pyproject.toml` workspace, `bin_dirs` defaults to `.venv/bin` and `venv/bin` (core/workspace.py:48), and a project can declare `bin_dirs` explicitly (workspace.py:127-153).
- So the stated hypothesis ("PATH only") is wrong for the current code. The real gap is narrower: a tool pinned somewhere other than `.venv/bin` or `venv/bin` with no declared `bin_dirs` (for example uv tool dirs, `~/.local/bin`, or a `scripts/` pin).
- Plan change: reword the Evidence and Proposal. "Add venv lookup" is already done. The proposal should be "reproduce, then find which location the project's ruff lives in that `bin_dirs` omits".

R2. N594 "The message should name the PATH that was searched".

- The message already names the searched directories: lint_on_edit.py:437-446 reads "looked in \<bin_dirs>, \<INTERPRETER_BIN_DIR> and on PATH".
- It does not print the PATH value, so this is partly true. The proposal should say "print the PATH value", not "name the PATH searched".
