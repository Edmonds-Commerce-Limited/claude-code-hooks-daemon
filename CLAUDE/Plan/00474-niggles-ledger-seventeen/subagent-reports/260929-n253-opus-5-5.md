## N253: every exemption now reads options from a closed list

### grep (`is_grep_pattern_only_mention`)

- **Known options only.** The exemption knows the GNU grep 3.8 long options, minus `--group-separator`, whose arity ugrep reads differently. It knows the short letters `EFGPiwxzsvVbnHhoqaIrRLlcTZU`, the digits, and `e f m A B C d D`. Anything else, including a prefix abbreviation, is not exempt.
- **A long option's value must be attached** (`--max-count=3`). I checked the embedded ugrep 7.8.4: it rejects a separate-word value (`missing argument for --max-count`), while GNU grep accepts one. So the two programs disagree on which word is the value.
- **Include and exclude values are judged.** The values of `--include`, `--exclude` and `--exclude-dir` are now judged like file targets. This closes `grep -rn --include <key> . .`, which main allowed and GNU grep prints.

### Encrypted-target git

- `_renders_a_diff`'s denylist is replaced by a closed grammar for each subcommand (`_OptionGrammar`).
- On a decoy repo, git accepted `--verb`, `--ed` and `--dry-run --verb` and showed the diff. Note that `git add --pat` is *ambiguous* (git refuses it), but `--patc` works.

### `git rm --cached`

- The global options and the options after `rm` now come from closed lists. The `rm` list has no `--pathspec-from-file`, so its abbreviation (`--pathspec-from`) is closed too.
- Each global-option word must be plain text and must not mention a protected path.
- **A new bypass, found and closed.** `git -c "core.fsmonitor=tee<PROTECTED>&2" rm --cached foo` was exempt on main. On a decoy repo, the fsmonitor hook really printed the file.

### Consumers (ansible)

- Option words are now judged for protected mentions. This closes `--inventory=<path>` and `-i<path>`.
- A denied subcommand (`view`, `decrypt`) anywhere in the command voids the exemption. Before, only the first non-flag word was checked.

### Tests

The tests are in `tests/unit/utils/test_secret_file_matching.py` (end of file):

- **Static verdicts.** Every bypass is asserted not exempt, and every legitimate form is asserted to stay exempt.
- **Differential tests.** These run real GNU grep, ugrep (skipped when it is absent) and git on decoy files in `tmp_path`. They prove that each bypass in the corpus really prints the decoy, and that each exempt search prints nothing.

## N255: the cause is not stdin

- **Reproduction.** I ran 2000 real commit messages through `_evaluate` as `git commit -F - <<'EOF'`. On the daemon's Python 3.11, 4 raised `OSError [Errno 36]`. On 3.14, none did.
- **Cause.** Two apostrophes (`someone's` ... `N5's`) quote the prose between them into one shell word. That word holds `CLAUDE/core/*.core.md` behind a component longer than NAME_MAX. On 3.11, `Path.glob` raises ENAMETOOLONG for it (from `is_dir` or `exists`), and `_expand_glob_token` re-raised every errno except ENOENT.
- **Fix.** ENAMETOOLONG is now a proof of absence alongside ENOENT (`_PROOF_OF_ABSENCE_ERRNOS`). No such name can exist, and bash's own glob matches nothing there either.
- **Tests.**
  - A monkeypatched unit test. It is RED before the fix on every Python version.
  - A handler test using the shortened real message. It is RED before the fix on 3.11 (`n255red311.txt`).
  - After the fix, both test files pass on 3.14 and on 3.11: 639 passed each.

## N256 (added by team-lead): a text-fed heredoc is data; a hit enumeration cap names its cause

Commit `019212893`.

- **Cause of the commit-message denies.** Markdown bold (`**Task**`, `**Status**:`) in the message body made the guard glob-walk the tree. `**Task` could match `x.secretTask`, so the guard walked to find out, and the walk hit its 2000-entry cap. That was 33 of 2000 real messages.
- **Heredocs.** `strip_quoted_heredoc_bodies` now takes an `is_data_sink` predicate; its default behaviour is unchanged. The guard passes `reads_heredoc_as_text`, so a quoted-delimiter body is blanked before the scan when every command it reaches only reads it as text:
  - `git commit`/`git tag` with `-F -` or `--file=-`, and no `--pathspec*`;
  - or the new `TEXT_READING_SINKS`: cat, tee, grep and the other filters.
  - Any `<(`, `>(`, `$(` or backtick in the segment keeps the body.
- **Why a narrower list than `DATA_SINKS`.** `DATA_SINKS` answers "does it execute the body?", and it holds git, patch, ftp and mailx. Git plumbing reads paths and object names from stdin, patch edits the files a body names, ftp runs `get`, and mailx honours tilde escapes. None of those only reads the body as text.
- **The cap.** `TooManyToEnumerateError` is now a verdict, UNKNOWN. It denies under the route's own rule (R-SECRET-BASH-MENTION for Bash) with a cause line: "more spellings or files than this guard will enumerate ... narrow the word". Before, it was reported as R-SECRET-EVALUATION-ERROR. The exception text is not echoed, because it can name a directory the walk visited.
- **The N23 pipeline.** The report has no exact command. Probing grep/awk/find pipelines over `src`, the raising shapes were a quoted glob (`find src -path '**Task'`, `grep -rn '**Task' src`) and a brace word past the cap. Both now deny with the cause.
- **No "harmless word" allowance.** I decided against one, and the reasoning is in the test docstring. The guard's heuristics match a word that shares only PART of a protected stem, so no test on the unexpanded word proves that none of its spellings is a mention.
- **Tests.** In `tests/unit/handlers/pre_tool_use/test_secret_file_guard.py`, 11 of the new tests failed before the fix. With a patched glob expansion, the tests also assert that a text-fed body is never glob-walked. Cases that still deny include:
  - `bash <<'EOF'` and `cat <<'EOF' | bash`;
  - `tee >(bash)` and `xargs cat`;
  - `git update-index --stdin` and `git commit --pathspec-from-file=-`;
  - an unquoted `<<EOF` with `$(cat ...)`;
  - `-m "$(cat <<'EOF' ...)"`.
- **Corpus.** Over 2000 real messages, as `git commit -F - <<'EOF'` with and without `-C`, there are now 0 denies on Python 3.14 and on 3.11.
- **The coordinator's N255 wording.** The coordinator asked for N255 to be recorded as "not reproducible on main". I recorded what I found instead: it IS reproducible on main under Python 3.11 (4 of 2000), and I fixed it. The row also says it was seen on the N53 branch, to recheck at landing.

## Ledger candidates (new, not fixed: out of this round's scope)

1. **URGENT (security, shared with main): `git show HEAD:<protected>` is allowed.** A protected file at the repository root, named in git's `rev:path` syntax, is not recognised as a mention. `git show HEAD:.vault-pass` and `git cat-file -p HEAD:.vault-pass` are both allowed on main, while `git show HEAD:config/.vault-pass` is denied. The token keeps its `HEAD:` prefix, so its basename never matches. This prints a committed protected file.
2. **The `-m "$(cat <<'EOF' ... EOF)"` idiom is still scanned.** The body sits inside a command substitution, so it is judged and glob-walked. Markdown bold there can still hit the cap. It now denies with a named cause rather than an evaluation error, but it is still a false-positive deny.
3. **Possible ENAMETOOLONG on the Grep-tool route (hypothesis, not probed).** `directory_contains_protected`'s `Path(directory).is_dir()` on 3.11 would raise ENAMETOOLONG for an over-long Grep `path`. That becomes an evaluation-error deny, which is fail-closed.
4. **Behaviour costs of N253, by design.** These now lose the grep exemption: `grep --regexp id_rsa f` (value in a separate word), `grep -y ...`, and any grep option outside the GNU/ugrep common set. The `git status -v`/`--verbose` and `git check-ignore -v` forms stay denied, as before.
