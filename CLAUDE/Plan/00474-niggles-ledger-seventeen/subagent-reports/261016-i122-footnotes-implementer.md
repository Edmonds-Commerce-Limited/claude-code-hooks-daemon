# N468 / GitHub #122: markdown formatter escapes footnotes

## Assumptions and flags

- **New dependency**: `mdformat-footnote>=0.1.1` (resolved 0.1.3; pulls only mdformat and mdit-py-plugins, both already
  locked). Added with `uv add --no-sync`, so `pyproject.toml` and `uv.lock` were regenerated by the package manager. It
  is called out in release note 076.
- No PLAN.md checkbox exists for niggles (N466 has none either), so PLAN.md is unchanged; NIGGLES.md and STATUS-INDEX.md
  carry N468.
- `llm_qa.py changed` without `--allow-unmapped` exits 1 only because `pyproject.toml`, `uv.lock` and
  `utils/markdown_format.py` are reported `[too-broad]` unmapped (788 tests passed, 0 failed). Re-run with
  `--allow-unmapped` per the handover: 40/40 passed, exit 0.

## Reproduction

`format_markdown_text("A claim.[^one]\n\n[^one]: The source.\n")` returned `'A claim.[^one]\n\n\\[^one\\]: The source.\n'`.
The only mdformat call is `format_markdown_text` in `src/claude_code_hooks_daemon/utils/markdown_format.py`
(extensions were `{"gfm"}`); the handler, `format-markdown` and the CLAUDE.md injector all go through it, so the fix is
shared.

## Red output (before the fix)

New tests in `tests/unit/utils/test_markdown_format.py` (`test_footnote_reference_and_definition_unchanged`,
`test_footnote_reference_at_line_start_after_soft_wrap_unchanged`, `test_multiple_footnotes_round_trip_idempotent`):
`3 failed, 24 passed`. After the fix the file plus the handler, `format-markdown` and injector tests: 201 passed.

## Fix

`_MDFORMAT_EXTENSIONS = {"gfm", "footnote"}`.

## Repo round-trip

Every tracked `.md` containing `[^...]` text (56 files): formatting with and without the `footnote` extension gives
identical output for all of them. 11 files change under the formatter either way (they were already unformatted):
the plan reports and journals under `CLAUDE/Plan/` and three `remote-docs/` pages. The extension changes none of them.

## Review round 1: degrade gracefully without the plugin

- `markdown_format.py` now builds the extension set in `_mdformat_extensions()` (functools.cache). It adds `footnote`
  only when `importlib.metadata.entry_points(group="mdformat.parser_extension")` lists it (no plugin import), and
  otherwise logs one WARNING and keeps `gfm`. Tests: plugin absent (tables align, footnote escaped as before, exactly
  one WARNING across two calls) and plugin present (no warning); the three footnote round-trip tests cover presence.
- How a client venv picks up a new dependency: the venv name is a fingerprint built in
  `src/claude_code_hooks_daemon/daemon/paths.py:850` from `_compute_project_lock_hash_stdlib(daemon_dir)`, which hashes
  `pyproject.toml` plus `uv.lock` bytes (`paths.py:576-597`). Changing either selects a different venv. Resolution
  skips a candidate whose metadata `lock_hash` differs from the current one (`paths.py:1212`), so `ensure_venv`
  rebuilds. So yes, a changed `uv.lock` triggers a rebuild, but only once the new source is checked out; before then
  (or if the sync fails) the fallback above applies.
