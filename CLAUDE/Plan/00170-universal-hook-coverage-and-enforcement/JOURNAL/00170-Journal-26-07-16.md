## 13:10 · finding · P1 — architecture map (runtime side, read directly)

Established the wiring architecture before editing (blast-radius due diligence):

- **TWO event enumerations that must agree** (the core duplication to unify):
  - `constants/events.py::EventID` — 11 `EventIDMeta` entries (enum/config/bash/json
    name forms) + `EventKey` Literal.
  - `core/event.py::EventType` (StrEnum, value = json_key) — 11 members; StatusLine
    value is `"Status"`. This is the DISPATCH enum: `EventRouter._chains` is keyed by
    every `EventType` member (`router.py:72`).
- **`EventType.from_string()` RAISES `ValueError` on an unknown event**
  (`event.py:58`). And `HookEvent.event_type: EventType` (Pydantic) rejects unknown
  values. So an event absent from `EventType` cannot be dispatched — fail-CLOSED-ish.
  ⇒ Enrolling all 31 in `EventType` is what makes new events dispatch to an (empty)
  chain instead of erroring.
- **Empty chain → `HookResult.allow()`** (`chain.py:263-264`). So zero-handler
  passthrough ALREADY works cleanly for any enrolled event — the fail-open primitive
  exists; we just need events enrolled + forwarders/settings present. (Per-event
  do-nothing response contract for non-PreToolUse events still to be verified in
  `hook_result.to_json`.)
- **Settings wiring is EventID-derived**: `utils/hook_registration.py:34-48`
  `_build_hook_events_map()` iterates `EventID` (excl. StatusLine) →
  `HOOK_EVENTS_IN_SETTINGS`, consumed by `validate_settings_hooks` /
  `validate_hook_commands`, which back the `hook_registration_checker` SessionStart
  handler. ⇒ **Adding an event to `EventID` immediately makes the live checker (and
  likely dogfooding tests) demand its forwarder + settings entry.** Therefore
  registry expansion and forwarder/settings wiring MUST land together per batch —
  expanding `EventID` alone would red the existing checker + QA. Confirms the plan's
  staged-rollout stance (§G).

## 16:35 · finding · P4 — forwarders gate runtime visibility; re-scope Phase 4

Design finding that reshapes Phase 4 before it starts. **Claude Code only invokes
a forwarder that exists in `settings.json`.** So the daemon can NEVER observe a
truly-new upstream event at runtime — there is no forwarder for it, so the socket
is never called. That makes Task 4.1's "runtime unknown-`hook_event_name` logger"
near-dead weight: it would only fire during a self-inflicted discovery→wire gap
(new forwarder+settings added but EventType member forgotten), which our atomic
per-event recipe already prevents. Keep a cheap defensive JSONL capture on the
`HookEvent`-validation-reject path if it's ~free, but do not build it up as the
primary drift detector.

**The real drift detectors** (reprioritise Phase 4 around these):
1. **Spec-audit** (Task 4.2, highest value): compare our `EventID` catalogue /
   `CLAUDE_CODE_HOOK_EVENTS` against the authoritative spec. Two layers — a
   version-pinned static assertion (already the completeness test) and an
   *advisory* that fetches the live CC hooks doc and reports any event we don't
   catalogue. This is the only thing that catches a genuinely-new upstream event.
2. **Coverage-degraded SessionStart alert**: extend beyond
   `hook_registration_checker` (which checks settings.json entries) to also
   assert each wired event's forwarder exists + is executable on disk — catches a
   deleted/cp-without-p forwarder that would make a hook silently error.
3. **`add-hook-event` scaffolder** (Task 4.3): now cheap thanks to the Phase-3a
   DRY foundation — a new event needs EventID + EventType + EVENT_TYPE_MAPPING +
   one `_DAEMON_FORWARDER_HOOKS` append + generated forwarder + settings entry.
   A CLI that does all of it (and the settings-rebuild-from-SSoT trick used this
   session) makes "we wire it for sure" a one-command operation.
