## 13:10 · finding · P1 — architecture map (runtime side, read directly)

Established the wiring architecture before editing (blast-radius due diligence):

- **TWO event enumerations that must agree** (the core duplication to unify):
  - `constants/events.py::EventID` — 11 `EventIDMeta` entries (enum/config/bash/json
    name forms) + `EventKey` Literal.
  - `core/event.py::EventType` (StrEnum, value = json_key) — 11 members; StatusLine
    value is `"Status"`. This is the DISPATCH enum: `EventRouter._chains` is keyed by
    every `EventType` member (`router.py:72`).
- **`EventType.from_string()` RAISES `ValueError` on an unknown event**
  (`event.py:58`). And `HookEvent.event_type: EventType` (Pydantic) rejects unknown
  values. So an event absent from `EventType` cannot be dispatched — fail-CLOSED-ish.
  ⇒ Enrolling all 31 in `EventType` is what makes new events dispatch to an (empty)
  chain instead of erroring.
- **Empty chain → `HookResult.allow()`** (`chain.py:263-264`). So zero-handler
  passthrough ALREADY works cleanly for any enrolled event — the fail-open primitive
  exists; we just need events enrolled + forwarders/settings present. (Per-event
  do-nothing response contract for non-PreToolUse events still to be verified in
  `hook_result.to_json`.)
- **Settings wiring is EventID-derived**: `utils/hook_registration.py:34-48`
  `_build_hook_events_map()` iterates `EventID` (excl. StatusLine) →
  `HOOK_EVENTS_IN_SETTINGS`, consumed by `validate_settings_hooks` /
  `validate_hook_commands`, which back the `hook_registration_checker` SessionStart
  handler. ⇒ **Adding an event to `EventID` immediately makes the live checker (and
  likely dogfooding tests) demand its forwarder + settings entry.** Therefore
  registry expansion and forwarder/settings wiring MUST land together per batch —
  expanding `EventID` alone would red the existing checker + QA. Confirms the plan's
  staged-rollout stance (§G).

Awaiting `map-hooks` Explore agent for the remaining pieces: installer forwarder-
script generation (registry-driven or hardcoded?), existing coverage tests
(`test_dogfooding_hook_scripts.py`, `test_all_handlers_response_validation.py`),
per-event response contracts in `to_json`, input-schema lookup, and how to add a QA
check. Will start TDD Phase 1 once that lands.
