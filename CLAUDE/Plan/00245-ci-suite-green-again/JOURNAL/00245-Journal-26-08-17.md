# Plan 00245 Journal — 2026-08-17

## Failsafe recovery cron

Cron ID `8326de0b`, hourly at :23, non-durable and session-only (auto-expires
after 7 days). Safety net only — never paced against, never waited for.

## How this plan came to exist

Not from a bug report. While verifying the CI step added by the project-handler
QA gate work, I ran `gh run list` rather than assuming the push was fine, and
found the workflow had failed. Widening the query showed it had failed on
**every push for at least 25 consecutive runs**, back through 2026-08-14.

Worth recording, because the earlier claim in that same session — that the
project-handler blind spot was now covered "in CI too" — was weaker than stated.
A step added to a permanently-red workflow cannot be the thing that turns CI red
or green. The coverage is wired in but not load-bearing until this plan lands.

## Root cause 1 — diagnosis trail

The failing job was `QA (Python 3.11/3.12/3.13)` → "Tests + coverage", identical
across all three interpreters. `Shell` and `Daemon load` passed.

`gh run view --log-failed` gave the decisive string: the forwarder returned

    Error: hooks_daemon_repo_detected - This is the hooks-daemon repository.

instead of entering CI passthrough. Two searches for that error code were
blocked by `lsp_enforcement` (it reads as a symbol lookup); searching for the
message text instead found `init.sh:246-265`.

The guard runs at SOURCE time using `PROJECT_PATH` derived from `BASH_SOURCE` —
the real repo — and clears only if `HOOKS_DAEMON_ROOT_DIR == PROJECT_PATH` or
`.claude/hooks-daemon.env` exists. `git check-ignore` confirmed that `.env` is
gitignored (`.claude/.gitignore:10`) and `git ls-files` confirmed it is
untracked.

So the tests passed locally purely because this tree is self-installed.

### Reproduction

Built a temp directory with a `.claude/init.sh` copy and a git remote pointing at
`claude-code-hooks-daemon`, no `.env`. Sourcing it emitted the byte-identical
JSON the CI assertion had diffed against. Adding a `.env` made it source
cleanly. Then confirmed the fix lever directly: with no `.env` but
`HOOKS_DAEMON_ROOT_DIR` set to the project root, sourcing succeeded.

### An earlier hypothesis that was wrong

First guess was ambient `CI=true` leaking into the test environment in the
runner. Disproved by reading `_build_clean_env` in `test_ci_passthrough.py`: it
constructs its environment from scratch, so ambient `CI` cannot leak. Recorded
because the wrong hypothesis was plausible and cost a detour — the log line was
what settled it, not reasoning about the environment.

## Fix applied

Three sites now establish the premise explicitly. `test_init_hot_path.py` got a
small local helper (`_self_install_premise`) because it has two sites; the other
two set it inline, which is three similar lines rather than a shared abstraction
— the ratio `CLAUDE.md` prefers.

While there, `_build_clean_env`'s `project_path` parameter became unused (the
generated script re-sets every path after sourcing), so it was removed rather
than left as a decorative argument.

### Verification

The decisive check was running the three files with `.claude/hooks-daemon.env`
moved aside — the exact CI condition. All 74 passed. The move and restore sat
entirely inside one Bash call, so no hook fired while the file was absent, and
the restore was asserted afterwards.

Then ran the eight remaining CI-failing files under the same condition: all 91
passed. So those failures are a different cause and need diagnosis against the
runner, which is Phase 3.

## Phase 2 — the guard, and why it is not a scanner

Task 2.1 landed as `tests/integration/test_init_sh_repo_guard.py`: five tests
over a THROWAWAY repo (a copy of `init.sh` plus a git remote), so they assert the
contract rather than inheriting whichever half of it this tree satisfies. Both
ways through the guard are pinned separately, and there is a control asserting an
unrelated remote is never refused — without it, the "guard fires" assertions
could all pass while the guard was hopelessly broad and every client install
bricked.

Task 2.2 turned out to be a decision rather than an implementation. Enumerating
first was what settled it: 30 test files mention `init.sh`, only five run it, and
two of those five already establish the premise the sandbox way (copy + their own
`.env`) — which is why they never appeared in the CI failure set. So the
population needing a guard is three files, and the discriminator that separates
them from the other 27 is not textual.

Recorded as Decision 2 with three rejected options. The one worth remembering is
the autouse `conftest.py` fixture: it looks like the tidy single-place fix and is
the worst of the three, because it would make the tests pass for a reason
invisible at the test site — the same ambient-dependency defect, relocated.

The honest conclusion is that the blind guard was never a missing scanner. CI
caught this on every push, 25 times, and nothing depended on the result. A third
partial guard on top of an unread second one is symptom-treatment, so Phase 4 is
the actual remedy.

## Phase 3, cluster 1 — the venv trio (Task 3.2)

Six of the ~14 per-interpreter failures, and all six turned out to be the same
mistake wearing three costumes: **a test asserting a property about a pair, while
letting the environment supply one half of the pair.**

### `test_ensure_venv` (4 failures) — a gate nobody had measured

`ensure_venv` skips its entire body when `CI=true`, which GitHub Actions exports
for every step. So on the runner the four creation tests asserted against a
function that had returned at line 343 without doing anything.

Reproduced locally before touching code — `CI=true pytest ...` gave the identical
assertion, down to the venv directory name in the message. That is the whole
diagnosis; everything after it was mechanical.

The part worth recording is what else the same gate was doing. `TestEnsureVenvCIGate`
already existed and asserted "HOOKS_DAEMON_SKIP_VENV_BOOTSTRAP=1 skips the
bootstrap" — and it PASSED in CI, because ambient `CI=true` was already causing
the skip before the test set its variable. A test that passes whether or not its
subject works. The `CI=true` half of the gate had no coverage at all.

Stripping both gate vars in `_run_bash` fixes both problems with one change: the
creation tests get a real premise, and the existing gate test becomes non-vacuous
because the only thing that can cause the skip is now the variable it sets. Added
the missing `CI=true` case, plus a `CI=1` control — without it, both skip
assertions are equally satisfied by a gate that skips unconditionally, which is
the exact failure mode being fixed.

CI now installs `uv`, because the honest version of these tests builds real
venvs (~15s for the file). Recorded as Decision 3 along with what that buys and
what it costs: PyPI is now in CI's path for this file, so an outage can redden
it. A truthful red beats a false green on the code path behind two field SEVs.

### `test_fingerprint_parity` (1) — a guard that was never a guard

The test compared `/usr/bin/python3` against `sys.executable`, gated on:

    if sysconfig.get_config_var("prefix") != sysconfig.get_config_var("base_prefix"):

`sysconfig.get_config_var("base_prefix")` is **always `None`** — checked, not
recalled: it prints `None` while `get_config_var("prefix")` prints `/usr`. So the
guard was permanently true and gated nothing. The test passed locally only
because this repo's venv genuinely descends from `/usr`; on the runner
`sys.executable` is a hostedtoolcache python that no more descends from
`/usr/bin/python3` than any unrelated interpreter, so the fingerprints differed
CORRECTLY and the test failed for a property it was never testing.

Rewrote it to CONSTRUCT the pair — create a venv from the running interpreter,
assert base and venv fingerprint identically. Verified the property holds first
(`/usr/bin/python3` and a venv built from it both give `py311-81c29529`). It now
runs everywhere instead of depending on the box, and the runner's own shape (two
unrelated interpreters sharing a major.minor) became its own test asserting they
must NOT collide — which is what fingerprinting is for.

### `test_venv_include_resolution` (1) — discovery vs the running process

Same shape: the test computed `python_venv_fingerprint(project)` in-process, then
compared it against the bash resolver, which runs its own glob-and-sort discovery
and picks the newest `python3.X` on the box. On the 3.11 job that is `/usr`'s
3.12, so `py311-...` was compared against `py312-...`. It failed on 3.11 only,
which fits: on 3.12/3.13 discovery happened to land on the running interpreter.

Fixed by pinning `HOOKS_DAEMON_PYTHON` — the resolver's own documented first
precedence, not a test-only hack.

Its sibling `test_fingerprint_keyed_wins_over_legacy` passed in CI throughout,
and would have kept passing: with a mismatched key the resolver falls through to
"scan for any existing venv" and finds the directory the test created anyway. So
one of the two tests was already immune to the bug for a reason unrelated to
correctness.

### The guard, per DBF

The premise `_run` now sets is invisible at the assertion site, so removing it
would restore exactly the old behaviour: green locally, red on any box with two
interpreters. `test_the_resolved_key_follows_the_pinned_interpreter` points the
resolver at a NAMED interpreter and asserts the key tracks it, so the pin cannot
be deleted without a local failure. Both parity fixes carry a matching
non-vacuity check (the constructed interpreter must really BE a venv —
`sys.prefix != sys.base_prefix`, which is the check the broken guard above was
fumbling for).

Verified green under BOTH conditions — plain, and with `CI=true` to emulate the
runner: 27 passed, 1 skipped, and the skip states which pair it lacked.

## Phase 3, clusters 2-4 — and the shape they all share

With the venv trio done, the remaining eight failures split three ways. Writing
them up together because the interesting part is that they are ONE defect wearing
six costumes, which is now Decision 6.

### `test_server_modes` + `test_server_validation` (6) — a 3.12 language change

`server.py` guards both mode actions with `isinstance(self.controller, Controller)`,
where `Controller` is a `@runtime_checkable` Protocol. Python 3.12 changed
protocol isinstance checks to look attributes up with `inspect.getattr_static()`
instead of `hasattr()`, and `getattr_static` deliberately does not fire
`Mock.__getattr__`. So a bare `Mock()` satisfies the protocol on 3.11 and fails
it on 3.12+.

I did not want to assert that from memory, and `uv python install 3.12` fetches
the exact CPython the runner used (3.12.13) in four seconds, so I checked:

    3.12.13   isinstance(Mock(), Controller)          False
              isinstance(Mock(spec=Controller), ...)  True
    3.11.2    both                                    True

That local 3.12 turned out to be the single most useful thing in this phase — it
converts "push and wait for CI" into a loop measured in seconds.

The failures were only the visible half. On 3.12 the server fell through to its
no-controller fallback, so three tests failed on 'default'/'unchanged' while the
REST of the file passed for the wrong reason: the fallback happens to return what
they assert. `test_server_validation` was stranger still — its fixture assigned
`dispatch` explicitly, which is a real attribute `getattr_static` CAN see, so on
3.12 the mock stopped being a `Controller` and became a `LegacyController`. Same
double, opposite code path, decided purely by interpreter version. Its
`dispatch.assert_not_called()` had been vacuously true on 3.11 all along, since
3.11 took the `process_request` branch.

Fixed with `spec=`, which sets `__class__` and satisfies the check on every
supported interpreter (and stops the double doubling as a `LegacyController`).
The guard is an assertion that `process_request` was actually called: the tests
otherwise assert only that validation let the request through, so they pass
whichever branch handled it. That fails on ANY interpreter where the double stops
being seen as a Controller, instead of waiting for the branch it lands in to
raise.

`test_paths_stale_cleanup` passes on 3.12, so it is not this cause. It failed
once, on one interpreter. Left for the next CI read rather than guessed at.

### `test_git_sync_rewrite_detection` (3) — three repos configured, four built

`git commit-tree` exited 128 in the bare remote. The fixtures set
`user.email`/`user.name` on the seed, the clone and the pusher — but
`_rewrite_remote` runs `commit-tree` in the BARE remote, which was never
configured. Every developer machine has a global identity that quietly lends
itself; a fresh runner does not.

My first reproduction attempt was junk: I hand-built a bare repo and a tree in
two unrelated repos, so `commit-tree` failed with "not a valid object" — 128 for
an entirely different reason. Proving nothing while looking like proof is the
worst kind of result, so I switched to neutering the real thing:
`GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null`, verified that state
really is identity-less ("Please tell me who you are"), then ran the actual file.
9 passed.

Supplied the identity through `GIT_*_NAME`/`EMAIL` in the fixture environment
rather than per-repo `git config`, and deleted the three config calls. The
environment covers repos that do not exist yet, which is the property worth
having: the failure mode here was a helper that forgot, and you cannot forget an
environment.

### `test_client_owned_asset_lint` (3) — a moving target, and a stale promise

This is the one where I was wrong twice, and where the CI-only framing broke down
entirely.

First I read the failure as "CI has a newer ruff" — right, but I then "confirmed"
it by running ruff locally and getting the SAME three findings, which looked like
a refutation. It was not: creating `untracked/venv-py312-verify/` had silently
hijacked `resolve_venv_python`, which globs `untracked/venv-*`. So `$PY` was the
3.12 venv and its freshly-installed ruff 0.16.3, not the dogfood 0.15.22. I had
committed this plan's own defect — ambient state deciding which tool runs — while
diagnosing it. Renamed the directory out of that namespace.

With that fixed the measurement is clean:

    ruff 0.15.22 (uv.lock)  --isolated  ->  clean
    ruff 0.16.3  (fresh)    --isolated  ->  DTZ005, DTZ006, BLE001

ruff 0.16 promoted DTZ and BLE into its DEFAULTS. So the asset had not changed;
the definition of "default rule set" had. The client boundary document promises
every deployed asset is clean under defaults, which quietly became false.

Then the second correction. `CLAUDE/LLM-INSTALL.md` already told clients to
ignore exactly `["BLE001", "DTZ005", "DTZ006"]` for this file — so the test was
contradicting its own remediation advice, which points at that very exclusion.
But reading the doc properly, its claim is "ships clean under DEFAULT rules, and
here is what to exclude if you select STRICTER ones". Under 0.16 those rules ARE
the defaults, so the doc's premise had expired rather than the test being wrong.

Resolved by splitting the three on their merits:

- `DTZ005`/`DTZ006` have a behaviour-preserving fix. `datetime.now(UTC).astimezone()`
  renders a byte-identical local wall-clock string to naive `datetime.now()`
  (verified, both branches), and states the "local, deliberately" intent in code
  rather than only in the docstring above it. Fixing beats excluding whenever
  behaviour is preserved: it removes a line from every client's lint config
  instead of justifying one.
- `BLE001` flags a documented safety net — one tick's exception must not kill the
  worker, so it logs the full traceback and replies NOOP. Narrowing it defeats
  the point. That one is now DECLARED in the manifest with its reason, honoured
  by the guard per FILE as well as per rule, and pinned to the client doc by a
  new test.

Two guards, because a declared exception is a promise that decays. One fails if a
declared rule no longer fires — the two DTZ codes sat in the client doc after the
asset was fixed, and a guard that only asserts the ABSENCE of findings cannot see
an exclusion it no longer needs. It selects the declared codes EXPLICITLY rather
than reading a default-rule run, because otherwise an older ruff calls a live
exception stale and a newer one is right by accident. The other pins the doc's
`per-file-ignores` snippet to the manifest, read out of the snippet rather than
the whole document so the prose explaining why DTZ was dropped is not mistaken
for an instruction.

That last one needed its own non-vacuity check, so I fed the extractor a stale
list, a missing snippet and a prose-only mention: all three detected.

### One more ambient dependency, found by accident

The stale-rule guard kept reporting nothing when ruff plainly reported something.
Cause: this container exports `FORCE_COLOR=1`, which OVERRIDES `NO_COLOR`, so
ruff emitted ANSI escapes into a captured pipe and the `path:line:col:` parser
never matched. `_run` now drops `FORCE_COLOR`/`CLICOLOR_FORCE` and sets
`NO_COLOR`. Worth noting that this one would have behaved differently in CI than
locally in the OPPOSITE direction from everything else in this plan — green here,
and green there, but only by luck about who exports what.
