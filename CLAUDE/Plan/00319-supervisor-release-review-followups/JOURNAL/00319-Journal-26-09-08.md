# Plan 00319 Journal — 2026-09-08

## F9 shipped, out of order, because Plan 00355 made it urgent

F9 was the lowest-value item on this ledger while the audit banner fired a
handful of times per session. Plan 00355 then gave every injected keystroke its
own banner — ~122 escapes in the session that prompted it — which turned "can
clobber a live Ctrl+C hint" from a theoretical race into a routine one. I had
also just seen it happen: a Ctrl+C hint sitting in `status-message.json` where a
banner had been.

So F9 jumped the queue. The other fifteen items are untouched.

## Both remedies the finding proposed were wrong

This is the part worth keeping, because the finding reads as though it offers a
choice between two acceptable outcomes and neither is available.

**"Route it through `StatusMessagePoster`."** The poster serialises with a
`threading.Lock` and rate-limits on an instance attribute. Both are
process-local. The two writers are in different PROCESSES: the audit banner is
written by `decide_once` inside the `--worker` subprocess (Plan 00164 Phase 4),
every keystroke notice by the PTY host. A worker-side poster would rate-limit
the worker against itself and leave the host/worker clobber — the thing F9
actually names — completely untouched. I only noticed because I went looking for
where the poster was instantiated (line ~5813, in `supervise()`, the host) and
where `decide_once` is called from (line ~5396, the worker loop).

**"State in the code why the bypass is correct."** It is not correct. The
clobber is real and now routine.

## What replaced them

The message FILE is the only thing the two processes share, so it is what has to
arbitrate. Every host notice posts at WARNING (Ctrl+C, Ctrl+Z, Ctrl+`\`, DROP
ANCHOR) and the audit banner is the only INFO writer — I checked all six call
sites before relying on that. So the rule needs no new state: an INFO write does
not replace a WARNING that has not expired.

`_live_warning_present` fails OPEN — absent, unreadable or unparseable counts as
no warning. Deliberate: treating corrupt state as live would wedge the channel
shut until the TTL of a value we cannot even read elapsed.

The read-then-write is not atomic across processes, so a race can still clobber.
Worth stating rather than hiding: losing that race reproduces exactly the old
behaviour, so there is no new failure mode.

## The bug I nearly shipped

Wiring the keystroke families through the existing flush block reused its
`reason` assignment — and `reason` is what reaches `decision.log`. That would
have overwritten `queued /compact stalled -> would inject [esc]` with
`audit trail flush (1 item(s))`, destroying the exact log line that made the 122
escapes diagnosable in the first place. A keystroke tick now keeps its own
`decision_value`, `reason` and `noop_reason_log`; only the banner write and the
pending-clear are shared. Pinned by a regression test.

## A second-order consequence

The flush cleared pending items unconditionally, which was fine when a failed
write was exceptional. With suppression now routine, that would silently drop
notices — so items are retained when the banner does not land. This also turns
out to be what lets a stack accumulate into Plan 00355's `esc (20)` rather than
vanishing one at a time. `arm_audit` caps the list, so it cannot grow unbounded.

## Live check

The on-disk status message at the time of writing is a Ctrl+C warning that
expired on 2026-09-04 — four days stale. The rule correctly allows a banner to
overwrite it, which is the `test_info_replaces_a_warning_that_has_expired` case
confirmed against real state rather than a fixture. Nothing reaps that file, but
the reader auto-omits expired messages, so it is inert rather than a leak.
