# Brainstorm: candidate AI-assisted handler use-cases

16 candidates, mined mostly from places this codebase's own handler guidance
already admits a regex is approximating a judgement call
(`comment_changelog`'s "rationale vs changelog" test, `security_antipattern`'s
"this is pattern matching, not analysis" disclaimer,
`validate_instruction_content`'s semantic content categories, `nitpick`'s
phrase lists) — plus two that surfaced live, as real false positives, while
this plan was being written (#1 and #16; see `DECISIONS.md` §0 for the full
account). Mechanism key: **A** = native Claude Code `prompt`/`agent` hook,
**B** = daemon handler calling a model itself, **C** = daemon advisory that
asks the *current* agent session to self-judge (see `DECISIONS.md` §3b for
when C is right vs. wrong). Within B, two shapes recur enough to name:
**B-confirm** = confirm-the-positive (model runs only after an existing regex
match, can only ever downgrade a block, never issue one — `DECISIONS.md`
§3c), **B-2nd** = second-opinion (model runs independently, can only ever
*add* an advisory flag, never block).

## Mechanism mapping, and why

The table above already carries a per-idea mechanism column; this section
states the reasoning pattern once instead of repeating it fifteen times.

- **Forced to daemon-side (B / B-confirm / B-2nd), not native-eligible**:
  #1 (needs `NitpickSetup`'s incremental transcript-cursor state, which a
  native hook has no equivalent for), #2 and #16 (confirm-the-positive
  fundamentally needs to see *this daemon's own regex match* — a native hook
  only sees raw event JSON, so reproducing this would mean duplicating the
  regex inside a prompt or running unconditionally, both defeating the
  design — see `DECISIONS.md` §4), #5 (needs subprocess output `agent` hooks
  cannot fetch, having no Bash tool access), #9 (must stay a supplementary
  advisory layered on the daemon's own deterministic block, per §3c's
  recall/precision asymmetry), #15 (self-policing; B keeps consistency with
  the rest of this project's independent-judge handlers, though A would also
  satisfy independence in principle).
- **Native-eligible (A), cheaper to try first**: #3, #4, #11, #13 — each is
  a standalone whole-event judgement over content already present in
  `tool_input` (or reachable via `agent` hooks' Read/Grep/Glob), with no
  dependency on daemon-side matcher state. Prototyping these as a native
  `prompt`/`agent` hook costs nothing to try; only adopt daemon-side
  infrastructure for one of these if the native version proves genuinely
  useful and the project decides to resolve the `hook_registration_checker`
  policy tension (`RESEARCH-...md`) rather than route around it.
- **Mechanism C (self-audit, no independent judge needed)**: #6, #7, #12,
  #14 — all already served, or trivially extendable, from
  `idle_housekeeping_advisory`'s existing report-first pattern. No hook
  event, native or daemon-side, is the right shape for any of these.
- **Rejected regardless of mechanism**: #8 (wrong filter shape for the
  stakes — needs recall, not precision, on the hottest and most
  security-sensitive surface in the codebase), #10 (no evidenced problem).
- **Adjacent, hand off rather than build**: #11 to Plan 00264.

## Ranking and recommendation

**Build first — #1 (nitpick semantic upgrade) and #16 (qa_suppression
confirm-the-positive filter), together, not in sequence.** Both are now
grounded in a *live* false positive from this exact session (`DECISIONS.md`
§0), not a hypothetical, which is the strongest evidence this brainstorm
produced. They are complementary rather than redundant: #1 proves the
deferred, advisory, `Stop`-triggered design (the safest possible shape —
nothing it does can ever wrongly block, per `DECISIONS.md` §1b/§3); #16
proves the confirm-the-positive design (the safest possible way to let AI
influence a shipping *blocking* handler, per §3c, and the one directly
motivated by a documented, intentional project constraint —
`CLAUDE.md`'s false-positive-tolerant acceptance-test strategy — that any
design here has to respect explicitly, not accidentally satisfy). Building
both validates two different safety patterns this plan identified, on two
handlers with independently-observed real failures. #2 (`comment_changelog`)
is the same design as #16 and should ship alongside it once the
confirm-the-positive infrastructure exists — it is not separate work, just a
second application of it.

**Try natively first, before building — #3, #4, #13.** `DECISIONS.md` §4's
sharpest conclusion is that native `prompt`/`agent` hooks are not a
consolation prize for ideas the daemon can't reach cheaply — for these three,
native hooks are *the cheaper option*, full stop, because nothing about them
depends on daemon-side state. Prototype via a native hook in `settings.json`
first; only justify daemon infrastructure if that proves the judgement is
valuable and the project decides native hooks are worth adopting more
broadly (which requires resolving the `hook_registration_checker` tension
`RESEARCH-...md` documents, a decision for a human, not this plan).

**Not a new handler at all — #6, #7, #12, #14.** All four are better served
by pointing the *existing* `idle_housekeeping_advisory` mechanism at them —
adding "deny-reason actionability" and "guidance context-cost" to its
suggested audit topics — than by building new live infrastructure. This
remains the honest ruthless conclusion the brainstorm keeps arriving at:
**most of the value on this list is already reachable through a mechanism
this project has built and trusts (Mechanism C) or through Claude Code's own
native hooks (Mechanism A), and the handful of ideas that genuinely need the
daemon to build something new are exactly the ones with a state dependency
or a self-policing conflict-of-interest that neither C nor A can reach.**

**Explicitly rejected, with reasons already given in the table**: #8
(security flow analysis — wrong filter shape for the stakes, defer to Plan
00204's regex-signal question instead), #10 (tone drift — no evidence the
cheap existing check is failing at anything), #11 (defer to Plan 00264,
which already owns this surface). #5, #9, #15 are plausible future
additions once #1/#16 have proven the daemon-side pattern works in
production, not candidates for a first build.
