## 16:55 — Four of the five open questions settled, and a doc bug in our own tree

Re-fetched `code.claude.com/docs/en/hooks` asking the five gaps directly, after
two `claude-code-guide` agents went idle without their reports reaching this
session. A targeted second fetch answered four of them, which is worth noting
as method: the first pass read the page, the second pass INTERROGATED it.

**`.claude/hooks.json` does not exist.** Hooks live in the `settings.json`
family (`~/.claude/`, `.claude/settings.json`, `.claude/settings.local.json`),
plus managed policy settings and skill/subagent frontmatter. There IS a
`hooks/hooks.json` — but it belongs to PLUGINS, which is almost certainly where
our filename came from.

That makes it a doc-truth bug in THIS repo, not a gap in the plan:
`CLAUDE/ARCHITECTURE.md` had it in a configuration-locations table and in a
worked example, and `CLAUDE/HANDLER_DEVELOPMENT.md` told contributors to "use
`.claude/hooks.json` with agent-based hooks". Anyone following that guidance
would have created a file Claude Code never reads and concluded their hook
silently did not fire. Fixed in both.

**Coexistence: "All matching hooks run in parallel."** A native `prompt`/`agent`
hook and the daemon's `command` hook both run, concurrently. Combined with the
code reading earlier today — the legacy detector skips entries with no
`command` key, and reconcile leaves existing event keys untouched — native
LLM hooks are adoptable here today with no code change.

**The nuance I nearly published wrong.** My first draft of the fix said the
parallelism means a slow agent hook "does not serialise behind the daemon's
~1.8ms dispatch", which is true and reads as though the latency problem had
gone away. It has not. Parallel means the hooks do not COMPOUND — the cost is
the slowest hook, not the sum — while the tool call still blocks on that
slowest one. A `prompt` hook on `PreToolUse` still turns a 45ms round trip into
a multi-second one. I killed the QA run to correct it before it landed, because
a half-true performance claim in ARCHITECTURE.md is exactly the kind of thing
someone builds on.

**Still unanswered, and it is the one that matters most**: the page says
NOTHING about cost, billing or rate-limit consumption for `prompt`/`agent`
hooks. A design that fires a model call per event cannot be costed from the
documentation. Any proposal must treat per-invocation cost as an unknown to be
MEASURED, not estimated. Nor is an introduction version annotated, so no
minimum Claude Code version can be asserted.

Also unconfirmed: there is no documented precedence rule for hooks that
DISAGREE — only that they all run in parallel. The `deny > defer > ask > allow`
ladder is the general multi-hook rule; whether a `prompt` hook's verdict folds
into it identically remains inference.

## 2026-08-24 — A committed claim was too strong; measured it and corrected

After committing 9cb8b9f0 I noticed `PLAN.md` on disk was 17,961 bytes when I
had reviewed 17,546. The planner's final pass had landed between my review and

helped either, since the path was the directory. The real fix is to confirm the
peer is idle BEFORE staging, not to trust a "done" message that raced my read.

Reviewing what had shipped turned up a genuinely over-strong claim, which the
document asserted as code-verified:

> "`hook_registration_checker` does NOT flag a native hook — that claim was
> checked against the code and is false."

True of `detect_legacy_hook_commands`. But the handler also calls
`validate_hook_commands` (`hook_registration_checker.py:186`), which nobody had
checked. I ran both validators directly against the three ways you might add a
native hook alongside the daemon wrapper rather than reasoning about the code:

| Layout | `validate_hook_commands` |
| --- | --- |
| A — separate matcher entry | ❌ "2 hook entries (expected 1) — likely duplicate registration" |
| B — appended after the daemon command, same entry | ✅ clean |
| C — placed before the daemon command | ❌ "command does not end with /.claude/hooks/pre-tool-use: got ''" |

Two causes: `len(event_hooks) > 1` is treated as a duplicate registration, and
only `inner_hooks[0]` is ever inspected, so a native entry sitting first yields
an empty `command` that fails the suffix check.

That makes Layout B the only clean way in today, and turns a "documentation-only
clarification" into a real prerequisite: Task 4.0 is now the validator fix, with
the wording clarification demoted to 4.0b. It also cascaded — "adoptable with no
code change" appeared in the Overview twice and was now false, so both were
corrected. That cascade is the point: the plan's value is that its claims are
measured, and one unmeasured claim had propagated into three places.

Also relocated the "two claims did not survive" block out of `PLAN.md`. It was
historical narrative, which the plan-workflow contract puts in JOURNAL/, and it
was carrying the now-false "no code change" line. Replaced with a current-truth
statement of the two constraints. Side effect: `PLAN.md` went 18,716 → 17,676
bytes, back under the advisory threshold — the size rule and the content rule
wanted the same edit, which is usually the sign the content rule is the real one.

**Lesson**: "checked against the code" is only as good as the set of call sites
checked. I verified the function the earlier draft named and stopped there,
without asking what else the handler calls. One `grep` for the handler's imports
would have found it — the same fix-what-I-am-looking-at failure as the doc-scope
misses earlier in this session, and now the third instance today.

## 2026-08-24 — Ran it for real, and locked myself out

Branch `plan/00266-ai-assisted-hooks`. The user asked to experiment, so I stopped
reasoning about native hooks and registered one. Full write-up in
`EXPERIMENTS.md`; this records what it was like to run, which the findings table
does not convey.

The first probe was designed to be safe: deny one sentinel string, stay neutral
otherwise, so it could sit on `PreToolUse` without consequences. I registered it
in Layout B, ran a `Bash` call carrying the sentinel, and it went straight
through. I assumed the config was not loaded — hooks snapshotted at session
start — and dispatched a `claude-code-guide` agent to check.

Then the next tool call, a `Write`, came back:

> `PreToolUse:Write hook error: [...]: The tool_name is 'Write', not 'Bash',
> so the condition ... is not met`

The hook had been live all along; there is just a propagation delay of a few
seconds. And it had not stayed neutral: instead of emitting `{}` it *explained
itself in prose*, that prose failed to parse, and the call was DENIED. So
unparseable prompt-hook output fails CLOSED — which the official docs do not
document, and which the guide agent independently confirmed is a genuine gap.

Then it got interesting. The hook had no `matcher`, so it fired on every tool.
It was now denying `Edit` and `Write` — the two tools needed to remove it from
`settings.json`. My own guard had taken away the means of disarming it. `Bash`
still worked (for a `Bash` call the prompt's condition was directly answerable,
so the model complied), and I recovered with a Python round-trip over the JSON.
Had the model been marginally chattier on that call too, the session would have
had no tool left to repair itself.

Two things I got wrong, both mine rather than the mechanism's:

- I used the `hookSpecificOutput` shape — the `command`-hook contract. Prompt
  hooks use `{"ok": bool, "reason": str}`. Instructing the model to emit a shape
  that is not the contract is probably why it reasoned in prose instead.
- I put an unscoped hook on the hot path *because* I had convinced myself it was
  neutral-by-construction. It was neutral by *instruction*, which is not the same
  thing when the executor is a language model. That distinction is the whole risk
  of this plan in one sentence, and I walked into it in the first five minutes.

Experiment 3 fixed both — correct schema, `matcher: Bash` so `Edit`/`Write`
stayed reachable — and the denial worked exactly as intended, carrying my reason
verbatim. But it surfaced two more problems: a correct denial is presented as a
`hook error` identically to a broken one, and the ENTIRE prompt is echoed into
the message every time. A real judge needs a long prompt; that prompt would be
reprinted on every denial.

**Net effect on the plan**: the native-vs-daemon question, which Phase 1 left
open, is now settled for blocking judgements. A native hook cannot deliver a
readable block — its error mode IS a block, and a real block is indistinguishable
from an error. Blocking candidates (#2, #16) belong daemon-side; native
prototypes should be advisory only. Task 4.1 said "use Layout B" and that is now
actively dangerous guidance, since Layout B cannot carry a matcher here —
corrected, and Task 4.0 is confirmed load-bearing rather than tidy-up.

`settings.json` was restored byte-identical to HEAD after each run; verified with
`git diff` both times rather than by assuming the edit was symmetrical.

## 2026-08-24 — Two things I said were impossible, weren't

### Latency, which I had declared unmeasurable

I told the user latency "isn't cleanly measurable from inside the session — the
confound is my own generation time between turns", and offered it as future work.
That was wrong, and the error was lazy rather than subtle: the confound only
exists if the measurement spans two turns. Inside ONE tool call there is no
generation time at all. A `command` hook stamps the start of the hook phase; the
Bash command stamps its own start; the difference is the hook phase.

Baseline 53/51/48 ms — which matches the ~45 ms this project documents for the
forwarder path, so the method validates itself. With one `prompt` hook:
1230/1330/1007 ms. **~24× the daemon's entire round trip**, and that is a FLOOR:
the measured hook had a constant response with nothing to reason about.

### Dynamic prompting — the user's idea, and it works

The user asked whether the daemon could respond first, compose its own prompt,
key it by a UUID, and have the native hook fetch the real prompt by that key.

It does not even need a minted UUID. The `PreToolUse` payload already carries
`tool_use_id`, and BOTH hooks receive the same payload — so each side derives
the same key independently and no coordination channel exists to go wrong. I
confirmed the payload fields by capturing one with a `cat > file` command hook
rather than assuming.

Prototyped it: a `command` hook writes `untracked/prompts/<tool_use_id>.txt`
with a per-event instruction; an `agent` hook reads the file named after the
`tool_use_id` in its own input. Both paths worked first time — the sentinel
command was denied carrying a string that existed only in a file written
milliseconds earlier, and the non-sentinel command ran.

This overturns a conclusion I had committed twice: that native hooks see only
raw event JSON, therefore cannot see a prior daemon-side regex match, therefore
confirm-the-positive must be daemon-side. With dynamic prompting the daemon runs
its regex FIRST and only asks the model to adjudicate an existing match. And it
inverts the economics — Claude Code makes the model call on the user's own auth,
so the daemon never needs API credentials, a deployment burden this project has
never taken on.

Two incidental findings: `agent` hooks present denials cleanly
(`Agent hook condition was not met: <reason>`) without echoing the whole prompt,
unlike `prompt` hooks. And the ordering race never materialised — the daemon
side finishes in ~51 ms against an agent hook's seconds — but it IS a race, so
the design must make a missing file mean ALLOW.

**Lesson, and it is the same one twice in one session**: I twice declared
something impossible from an armchair — the doc claim I had "code-verified"
across one call site, and latency being unmeasurable — and both took under ten
minutes to settle once I actually tried. The user's idea landed in the same
category: I had written the limitation into the plan as settled fact, and it
took one experiment to overturn. Prefer the experiment.
