REAL config file (mode: replace + custom protected_paths), and writing it
surfaced a genuine bug -- `Config`'s `coerce_handler_configs` validator turns
every handler entry into a `HandlerConfig` instance, not a plain dict, so
`resolve_configured_patterns`'s `isinstance(handler_cfg, dict)` guard always

config in the first place, only ever fallen through to the shipped

`.options`. This is exactly the DBF principle in miniature: the review asking
for a specific class of test (real config, not mocked patterns) is what

**Follow-up fix (isolated worktree, same day): closed the class-(c) glob gap
found above.** Root cause: the existing glob-token heuristic required a
command token's literal residue to be a substring of the protected pattern's
literal stem (`fnmatch(stem, token)`), which only catches a token whose fixed
part is anchored at the SAME edge as the pattern's fixed part. A
trailing-wildcard truncation of a real protected basename
(`dummy.vault-p*` truncating `dummy.vault-password`, matched by
`*.vault-password`) has an arbitrary `dummy` prefix the pattern's stem never
sees, so the substring test failed while the real read still succeeded.

Fixed with a new literal-edge-overlap test (`_glob_token_overlaps_stem` /
`_suffix_prefix_overlap_length` in `secret_file_matching.py`, min overlap 2
chars) added ALONGSIDE the original fnmatch check, not replacing it — see
Decision 12 in PLAN.md for why a full two-glob language intersection was
rejected (it would have flagged the required-allowed unrelated negative
control by splicing arbitrary filler between two unrelated literal
fragments). TDD: 8 new tests added to
`tests/unit/utils/test_secret_file_matching.py` covering three
trailing-wildcard truncation lengths (all denied), a synthetic
reverse-direction-only case, the single-character generic-glob accepted
residual (`d*`, stays allowed), and the genuinely-unrelated negative control
(stays allowed) — all RED before the fix, all GREEN after; full existing
suite (59 -> 68 cases in that file) stayed green throughout. Per-file
ruff/black/mypy --strict/bandit clean; touched-file coverage 91.49% (three

**Same-day coordinator review found an over-blocking regression in the fix
above, fixed in the same worktree branch.** The overlap test ran against
EVERY literal stem, including the EXACT-FILENAME stems `id_rsa`/
`id_ed25519`. Their edge characters coincidentally overlapped extremely
common tokens — `sample*`, `grid*`, `valid*`, `android*`, `raid*`,
`hybrid*`, `id*` were all wrongly denied, which would have broken ordinary
commands repository-wide. Root cause: the overlap heuristic is only
meaningful for a pattern with a LEADING wildcard (the real filename's
arbitrary prefix has no counterpart in the fixed stem); an exact-filename or
start-anchored pattern (`.vault-pass*`) has no such arbitrary prefix, so a
genuine truncation of those is already a literal prefix of the stem and was
already caught by the pre-existing substring+fnmatch check — the overlap
test added nothing there but false positives.

`find_protected_mention` (`secret_file_matching.py`) — exact-filename and
trailing-wildcard-only stems never reach `_glob_token_overlaps_stem` at all.
