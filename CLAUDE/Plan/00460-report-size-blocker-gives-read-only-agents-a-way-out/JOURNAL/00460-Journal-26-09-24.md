## 12:16 · decision · T1.2 — option (b), not (a): daemon-side content-guard
replication is not cheaply/reliably available

Condition (1) — is the full final reply reliably available to the
daemon: YES. `SubagentStop`'s vendored contract (already cited in this
handler's own docstring, v2.1.252) delivers `last_assistant_message`
directly on `hook_input`, no transcript parse needed.

Condition (2) — can the daemon run the SAME content checks a `Write` to
that path would get: NO, not reliably. Read
`sensitive_content.py`/`secret_file_guard.py`/`markdown_organization.py`
end to end. Each exposes real per-call logic (`scan_text()`,
`_matched_pattern_and_route()`, `matches()`/`handle()`), but every one of
them is driven by INSTANCE options the registry injects by `setattr`
from the project's loaded `.claude/hooks-daemon.yaml`
(`registry.py:592-593`, PASS 2) — `public_patterns`, `secret_word_list_path`,
`protected_paths`/`mode`, `exclude_paths`, the injected `_project_layout`
facade, etc. `sensitive_content.public_patterns` in particular defaults
to an EMPTY list with no baked-in defaults ("config is truth; no
hardcoded patterns ship" — its own docstring) — a freshly-constructed
`SensitiveContentHandler()` with no options applied would silently skip
every project-configured pattern, which is worse than not attempting the
check at all: a false sense of "already scanned."

Getting the LIVE, already-configured instances is not available either:
`get_registry()` (`registry.py:827`) and
`rule_explain/lookup.py:discover_handler_rules()` (what
`explain-handler` uses) both work over handler CLASSES / static
rule/CLAUDE.md metadata, never the live per-project-configured instances
the running router holds. Reaching into the router's live instances from
inside a SubagentStop handler would be a novel coupling with no existing
precedent anywhere in this codebase (handlers never cross-call each
other's live instances), and re-deriving the config-load +
option-injection slice of `register_all()` PASS 1/2 here would DUPLICATE
that logic rather than reuse it — the DRY violation the task explicitly
warned against ("call their pure checking functions rather than
re-implementing" -- reimplementing the INJECTION is the same mistake one
layer up).

So condition (2) fails on the evidence, and per the task's own fallback
rule ("If any fails, choose (b)"), the decision is **(b): the agent
condenses its reply under the threshold**. The read-only deny message
(Task 1.3) explicitly forbids a Bash write-around (heredoc/redirect/tee)
per the plan's requirement, independent of (a) vs (b).

## 13:09 · decision · T1.6 — scope widened: the daemon persists EVERY reply

The owner asked directly: "is there a hook we can use at main agent
level to ensure sub agent reports are persisted to file?" Team-lead's
read of the Task 1.2 evidence: the (b)-over-(a) reasoning (the daemon
cannot cheaply replicate the live per-project content-guard checks a
`Write` would get) holds for a TRACKED destination, but does NOT apply
to an UNTRACKED one — `last_assistant_message` already reaches the
coordinator's context and Claude Code's own on-disk transcript, so
saving it to a gitignored path (`untracked/`, confirmed at `.gitignore`
line 200) discloses nothing new to git and needs no Write-time content
check. Sent facts on SubagentStop/PostToolUse payload reliability
(`last_assistant_message` and `agent_transcript_path` both unconditional
per `contracts/claude-code-hooks/SubagentStop.json`'s own
`conditional_input_fields` list; PostToolUse:Agent's `tool_response` is
the sub-agent's composed final message per
`budget_exhaustion_detector.py`'s established-fact docstring, for a
FOREGROUND dispatch — background reliability is inference from docs +
this daemon's existing uniform SubagentStop handling, not an empirical
live test).

**New goal**: every sub-agent's final reply is persisted to a
gitignored, bounded location by the daemon itself, regardless of agent
type or Write access.

**Scope decision on "coordinator-declared report path" (own call,
recorded here for review):** team-lead's spec says route to the
declared path "when there is one". Re-reading their own opening
qualifier ("(b) reasoning holds for a TRACKED destination, but not an
UNTRACKED one") settles which declared path that can mean: `dispatch_declaration`'s
PLAN-FOLDER declaration (`<plan-folder>/subagent-reports/...`) is a
TRACKED, committed destination — auto-writing there without a Write-time
content check is exactly what (b) still forbids. Only the OTHER declared
form ("not plan work" + an explicit untracked destination) is safe to
honour automatically. Recovering that from a SubagentStop requires
parsing the SUBAGENT's own transcript for its first prompt (the
coordinator's dispatch text is not otherwise visible at this surface) —
real, safety-relevant new parsing surface for comparatively small
benefit over always using the daemon's own generated path (which is
already logged with agent_type/agent_id/timestamp and trivially
greppable). **Decision: v1 always uses the daemon-generated path only**
(`untracked/agent-reports/<yymmdd>-<HHMMSS>-<agent_type>-<agent_id>.md`);
routing to a coordinator-declared untracked destination is deferred, not
built. Flagged to team-lead in the reply; happy to add it as a follow-up
if still wanted.

**Cross-handler design**: the persister (new SubagentStop handler,
priority 10 — after path_verifier(8)/cache_aggregator(9), before the
terminal size blocker(15)) and the size blocker do NOT share in-memory
state (no precedent anywhere in this codebase for one handler mutating
`hook_input` for a sibling to read, and a shared timestamp computed
twice in the same dispatch can straddle a second boundary anyway). The
size blocker instead GLOBS the report directory for
`*-{agent_type}-{agent_id}*.md` — robust to the collision-suffix and to
any timestamp drift between the two handlers' own `datetime.now()`
calls.
