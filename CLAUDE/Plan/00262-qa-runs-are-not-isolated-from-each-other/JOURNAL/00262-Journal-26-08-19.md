## 11:55 · finding · — — filed from a self-inflicted incident

Provenance matters here, so recording it plainly: this plan exists because I
caused the problem, not because anyone audited for it.

Resuming after a compaction during Plan 00261, I started a QA run without
checking whether one was already in flight. There was — the pre-compaction run
was still going. Two suites raced for about seven minutes, both driving the same
`tests/` tree and both writing `untracked/qa/coverage.json`. I killed both and
re-ran one clean.

The worse half is what happened EARLIER in the same session: a
`test_install_sh_end_to_end` failure from the same cause was written off as
interference and moved past. That is the real damage a contended run does — not
the wasted minutes, but that it teaches you to discount failures on a gating
check.

Two details that shape the fix, both verified rather than assumed:

- `--read-only` does not run tools (`llm_qa.py:604`, the loop is guarded by
  `if not read_only`), so the lock belongs on the executing path only. Locking
  read-only too would block the one command useful for inspecting a live run.
- `pyproject.toml:114` records coverage `parallel` mode as disabled because it
  "causes fork bomb when running pytest with --cov". So concurrency was never
  supported at the coverage layer — this is not a small overlap to tidy.

Killing the runs also had a wrinkle worth remembering: `kill -- -<pgid>` on the
bash wrapper's group did NOT reap the suite. `llm_qa.py` runs in its own process
group, so the wrapper died and the QA kept going. Needed a second pass against
the python process groups.

## 12:20 · finding · — — the self-matching footgun is broader than the guidance names

The background-process watchdog advisory warns about one shape:

    until ! pgrep -f 'X'; do sleep N; done

...which matches its OWN command line and can therefore never exit. One such
waiter ran for 1d15h in this repository.

Hit the same root cause today in a DIFFERENT shape, which that wording does not
cover:

    pkill -f "flock -n /workspace/untracked/qa"

This is not a waiter and does not hang — it matched its own command line and
killed its own shell (exit 144). The target died too, so the effect looked like
success; the shell dying is the only visible symptom, and in a longer command
everything after the pkill would simply not run.

The class is: ANY `-f` full-command-line match run from a shell whose own
command line contains the pattern. `pgrep -f` in a loop is one instance;
`pkill -f` is another and is worse, because it acts rather than merely waiting.

Also hit a third instance earlier in this session: `kill -- -<pgid>` against a
QA wrapper's process group did NOT reap the suite, because `llm_qa.py` runs in
its OWN process group — the wrapper died and the QA kept running. Related but
distinct: the pgid you have is not always the pgid you want.

Not acting on this mid-gate. Candidate follow-up: widen the
`background_process_tracker` advisory from the one named shape to the class,
and mention that a wrapper's process group may not contain the real work.
Recorded here so it is not lost.

## 12:34 · action · P1 — implemented, verified live in four directions

Phase 1 landed. Unit tests alone would not have been enough here: the failure
mode IS a second concurrent process, so every claim was checked against real
ones.

- Python holder -> shell runner refused (exit 3), holder pid named
- Shell holder -> `llm_qa.py` refused (exit 3), holder pid named
- Lock held -> `--read-only` still succeeded (exit 0)
- Holder SIGKILLed -> next run proceeded, though the lock file was still on disk

The cross-language pair matters most: the two entry points do not share code
(the shell runner invokes the per-tool scripts directly rather than delegating),
so they can only exclude each other by sharing one lock FILE. `flock(1)` and
`fcntl.flock` sit on the same kernel lock, which is why that works — but it is
the kind of claim that deserves an experiment rather than a citation, so both
directions were run.

Bug found in my own bash before any test touched it: `exec {FD}> file`
truncates at OPEN time, before `flock` is attempted. A contending run would
have wiped the holder's pid stamp and then printed `pid=unknown` in the very
message that needs it. Opening append and truncating after acquiring fixes it,
and the live contention test then confirmed the stamp survives.

## 12:36 · finding · — — three handler blocks during implementation, all correct

`error_hiding_blocker` denied an `except OSError: pass` in the pid reader. Fair:
it was genuine error hiding. Rewrote it to return the reason in the string it
produces, so an unreadable lock file degrades the MESSAGE and never the
DECISION.

`qa_suppression` denied `# noqa: SIM115` on the deliberately-unclosed lock
handle. This was the most useful of the three, because suppressing would have
hidden a design smell rather than a lint quibble: the right answer was that a
lock is a file DESCRIPTOR, so `os.open` is the correct API and SIM115 never
applies. The suppression would have preserved the wrong abstraction.

`lint_on_edit` denied twice on unused imports mid-edit — an artefact of adding
imports before the code that uses them. Worth noting the PostToolUse denial is a
failure REPORT, not a rollback: the write had already landed, so the fix is
always another Edit, never a re-Write from memory.

## 12:38 · decision · — — checked for an existing lock utility before writing one

`Timeout.FILE_LOCK` hinted the codebase already had one. It does not, quite:
`daemon/server.py` (Plan 00127) uses `flock` inline, in async code, to protect
the socket-bind critical section. Not a public utility, and the shell entry
point could not call a Python helper anyway.

Reusing it would have meant extracting a utility into the daemon package and
importing it from QA tooling that currently imports nothing from the package —
coupling the tests' scaffolding to the thing under test, for ~15 lines that must
exist twice across a language boundary regardless. Left as is.

That read did surface something worth inheriting, now Decision 5: server.py
documents that `flock` is a no-op on older NFS and some 9p configs. This guard
degrades SILENTLY there, unlike server.py which degrades loudly. Acceptable for
a QA runner — the failure mode is no worse than today's status quo — but it
means "the lock is in place" must not be read as "concurrent runs are impossible
on every filesystem".
