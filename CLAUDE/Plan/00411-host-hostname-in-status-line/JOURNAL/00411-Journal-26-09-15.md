## 08:02 · finding · P1 — why the loopback hint worked THERE and not HERE

A field report resolved a host name from a loopback alias. The temptation was
to treat that as the mechanism and build on it. It is a real effect, but its
cause makes it unreliable.

Podman genuinely inherits the host's `/etc/hosts` — proven here rather than
assumed: this container's copy carries a set of the host's own private LAN
entries, which nothing inside the container could have invented.

What varies is whether the host's `/etc/hosts` names the host at all:

- **Debian / Ubuntu** write `127.0.1.1 <hostname>` at install time — the alias
  exists, and the read works.
- **Fedora** does not; `systemd-hostnamed` owns the hostname and `/etc/hosts`
  stays generic — the read returns nothing.

The reporting host was Debian-flavoured. This one is Fedora. Same podman, same
inheritance, opposite result — so the read is a HINT whose availability turns
on a property of the host that cannot be seen from inside, which is exactly why
it cannot be the mechanism.

The heuristic, as run here:

```
awk '$1 ~ /^127\./ {for(i=2;i<=NF;i++) if ($i !~ /^localhost/) print $i}' /etc/hosts
# → prints nothing
```

## 08:02 · decision · — — an inferred name must not look like a read one

The ladder is env var → config → `gethostname()` (only when not containerised)
→ `/etc/hosts` hint → nothing.

The last two rungs need different rendering. A status-line segment exists to
answer "which machine am I on?" at a glance, and a confidently-wrong name is
worse than a blank: the reader acts on it without re-checking. An inferred
value is therefore marked, and `explain_segment()` names the rung that produced
it, so provenance is inspectable rather than folklore.

Nothing resolvable renders NOTHING — not "unknown", not the container ID.

## 08:20 · finding · T2.1 — the explainer lies about its own daemon, and I believed it briefly

Restarting the daemon with `HOOKS_DAEMON_HOST_HOSTNAME` set and then running
`bin/hooks-daemon status-line-explained` reported "no host name could be
resolved". I read that as the export failing to reach the daemon — which would
have meant the primary mechanism did not work at all.

Checking the daemon's actual environment instead of trusting the report
disproved it: `/proc/<pid>/environ` carried the variable. The explainer is a
CLI command that constructs handlers in its OWN process, so it was faithfully
reporting ITS environment, which did not have the export.

The real path confirms the feature works — feeding a status event to
`.claude/hooks/status-line`, which goes to the daemon, renders the name.

Two things worth keeping from this. First, an explainer that resolves in the
wrong process is a trap for anyone verifying this feature, so the caveat is now
written into `StatusLine.md` next to the contract rather than left to be
rediscovered. Second, the near-miss: the "evidence" of failure was one command's
output, and one more probe turned it into evidence of success. Believing the
first reading would have produced a confident, wrong bug report about my own
code.

## 08:30 · finding · T1.2 — QA found two real defects the targeted tests could not

Full QA came back 28/30 with tests fully green (23,505 passed, 95.4% coverage).
Both failures were mine, and neither was cosmetic:

1. **pyright**: `handler._host_name = ...` — the config override was reaching
   the handler only through the registry's untyped `setattr`, so the attribute
   was undeclared. Fixed in the HANDLER rather than the test: the option is now
   a declared, typed attribute, which is also the only way someone reading the
   class can see the knob exists.
2. **pyright**: `resolved.inferred` on a `HostName | None`. A missing
   None-narrow in a test — small, but it is the assertion that pins the safety
   property, so a latent `AttributeError` there would have failed for the wrong
   reason.

Following the first one out led somewhere better than the fix. Since config
values arrive from user-authored YAML through an untyped `setattr`, nothing
upstream guarantees the value is text, and `host_name: 12345` is an entirely
plausible thing to write. `.strip()` on an int raises — inside a status-line
render, which repeats once per second, so the cost is a permanently broken
status line rather than one bad frame. `_non_blank` now takes `object` and
answers None for anything that is not text, with a parametrised test over five
non-string shapes.

`# type: ignore` was the obvious way to make the original version of that test
compile, and `qa_suppression` denied it — correctly. The suppression would have
hidden the fact that the public parameter is honestly typed for its real
caller; testing the private helper, where the defence actually lives, is the
better shape.
