## 18:08 · finding · P1 — N6: the fix that was already made, defeated one character earlier

`plan_number_helper` denied a three-line command listing ONE named plan's
documents. The interesting part is not that a regex over-matched; it is that
this exact failure had already been found and fixed once, and the comment above
the rule describes it: an `echo` on one line reaching forward to borrow a glob
from the next line's unrelated command. The earlier fix added `\n` to a negated
character class. It was correct and it did nothing, because the `\s+` sitting
immediately before that class matches a newline itself — the pattern had
already crossed into the next line before the exclusion applied.

So the guard was in the right place and read as working. What made the bug
findable was the `;` spelling: `echo X; wc -l <plan>/*.md` was allowed while
`echo X\nwc -l <plan>/*.md` was denied. Two spellings of one shell structure
disagreeing is a fact about the implementation, never about the policy, and it
is what turned "this block seems wrong" into a located defect.

Fixing it then exposed a second, opposite gap. A bare `[ \t]+` would have been
wrong: `\<newline>` JOINS two lines into one command, and `echo \<newline>
CLAUDE/Plan/0*` really does expand the glob. That case was never covered — the
handler read the raw command off `tool_input` instead of through
`get_bash_command`, which normalises continuations at the daemon's single entry
point, and it had been matching only by the same accident that caused the false
positive. Tightening the whitespace alone would have converted a false positive
into a silent hole, which is the worse of the two.

Both halves have a test, including the continuation case that was red before
the fix for a different reason than the one I was chasing.

## 18:30 · finding · P0 — chasing a false positive found a hole in every guard

N6 was a handler denying something harmless. Asking whether its shape recurred
turned up four more of those (N8), and then one of the opposite kind, which is
the one that matters.

The route there is worth recording because it was not deduction. N8's fourth
site, `daemon_location_guard`, reads `tool_input` directly instead of through
`get_bash_command`, so I checked what normalisation it was missing — and read
`normalise_line_continuations`. Its docstring says "the shell removes it and
joins the lines", and the line under it substitutes a space. I did not trust
either, and ran bash: `ec\<newline>ho joined` prints `joined`. The shell joins.
The daemon split.

So `git pu\<newline>sh --force` reached every blocking handler as
`git pu sh --force` and matched nothing, while bash ran the force push. The
same for `reset --hard`, and for every guard built on `get_bash_command`.

**Why it survived.** Every existing test wrote the continuation BETWEEN tokens
— `git \<newline> reset` — where the author has already typed the separating
space, so joining and substituting produce the same string and the wrong one
was indistinguishable from the right one. The helper's framing, stated in its
own class docstring, is "a line continuation is whitespace". That is true in
the tested position and exactly backwards in the untested one: inside a word it
is glue. The tests were written from the framing, so they could only ever
confirm it.

Two lessons, and the second is the transferable one. First: a docstring that
disagrees with the line beneath it is evidence, not noise — this one stated the
correct rule the whole time. Second: when a test suite covers one position of a
construct, ask what the OTHER position would prove, because a property that
holds in the tested case for an accidental reason looks identical to one that
holds for the right reason.

Ordering matters for N8 and is recorded there: `daemon_location_guard` must be
routed through `get_bash_command` before its gap is tightened. Tightening first
converts its false positive into the hole N7 just closed.
