## 11:00 · action · — — extension: {REPO_ROOT} token (owner ruling)

Owner ruling: "for docs and relative paths - can we have a single canonical
way of reference {REPO_ROOT} so that abs paths are clear?" Implemented as an
extension to the completed Plan 00302 audit rather than a new plan, since it
is additive sugar on the same validator this plan already built.

`utils/repo_relative_path.REPO_ROOT_TOKEN` (`"{REPO_ROOT}"`) added.
`normalise_repo_relative_path` now strips a leading `{REPO_ROOT}/` (or bare
`{REPO_ROOT}`) before its existing checks, so `{REPO_ROOT}/web` and `web`
normalise identically — TDD'd first in
`tests/unit/utils/test_repo_relative_path.py`. Token appearing anywhere but
the very start (e.g. `web/{REPO_ROOT}/x`, `{REPO_ROOT}suffix`) is a
`ValueError`; `{REPO_ROOT}/../x` still escapes and is rejected.

New `expand_repo_root_token(value, project_root)` for the two path fields
that are EXEMPT from the repo-relative-only rule and resolve against a known
project root at load time: `PluginConfig.path`/`PluginsConfig.paths`
(`plugins/loader.py::PluginLoader.load_from_plugins_config`) and
`ProjectHandlersConfig.path` (`daemon/controller.py::_load_project_handlers`
and the three matching `Path(config.project_handlers.path)` call sites in
`daemon/cli.py`). Semantics: token prefix expands to an absolute path
against `project_root`; a leading `/` is returned unchanged (still the
deliberate machine-specific override); a plain relative value is returned
unchanged (each loader's own existing relative-resolution logic is
untouched). A token used with no `workspace_root`/`project_root` available
raises `RuntimeError` naming the token — there is no silent no-op.

`config/models.py` field descriptions for `PluginConfig.path`,
`PluginsConfig.paths`, `ProjectHandlersConfig.path` updated to mention the
token as the portable alternative to an absolute override.
