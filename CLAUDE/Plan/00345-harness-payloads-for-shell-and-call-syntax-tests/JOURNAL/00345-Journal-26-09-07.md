## 23:17 · decision · T3.1 — the human route must not get worse

For the prose tests, Plan 00243 rendered `command` FROM the payload, which
collapsed five grammars into one and removed any possibility of drift.

The same move would be a regression here. For a shell test the bare command is
already the best thing a human can be handed; `as_instruction()` would render
`Use the Bash tool with command='echo "git reset --hard ..."'`, strictly harder
to paste than the command itself.

So shell blocks keep `command` byte-identical and gain a payload alongside it —
and because that reintroduces the two-copies problem the derivation was meant to
solve, Task 3.2 adds the invariant that closes it: a Bash payload's `command`
must EQUAL the block's `command`. The Write half of that file already checks
`file_path` appears in the command; this is the same guarantee for the other
tool.

Call-syntax blocks are the opposite case and get `as_instruction()`:
`Write(\n  file_path=...)` is not pasteable into anything, so there is no human
route to preserve.

Two things worth keeping from HOW it was done.

**The payload is derived from the command, not written beside it.**
`dispatch_as_bash=True` builds `ToolPayload(Bash, {"command": self.command})` at
construction. That makes success criterion 4 structural rather than reviewable:
there is one copy, so the human's command and the harness's cannot drift. It is
still a per-site DECLARATION — nothing inspects a command's shape — and
declaring it alongside an explicit `tool_payload` raises, which is what keeps
the shell-shaped-but-another-tool blocks honest.

It is an `InitVar`, not a field, and `test_playbook_generator_json_field_coverage`
is why: that guard requires every dataclass field to reach the JSON. Emitting
the flag would invite a harness to read it instead of the payload, reopening the
very split the derivation closes. A pre-existing test caught a design mistake
before it shipped.

**The conversion script had to be `ast`-based, and two failures forced it.** A
literal `git clean -fd` inside a transform script is denied by
`destructive_git` — the commands being converted are exactly the commands this
repo blocks, so they cannot be typed into a shell in order to convert them.
Then matching on the command text alone proved both ambiguous (several handlers
declare two tests with an IDENTICAL command, differing only in expected
decision) and insufficient (several build `command` with an f-string, so there
is no literal in the source at all). Keyed on title, with the command as
confirmation. Its `ast.parse` guard then caught a real bug in the inserter: a
multi-line `command=(...)` ends its VALUE a line before the `)` that closes the

## 00:21 · decision · T1.2 — the fixture commands are translated, never shelled

Running `setup_commands` meant the harness would, for the first time, do
something that is not inert. Everywhere else a command is DATA placed in
`tool_input` and answered by the daemon; setup would really change the tree.

First shape was `subprocess.run(command, shell=True)` behind a regex allowlist
plus a containment check. `qa_suppression` refused the `# noqa: S602` that
would have been needed to quiet bandit — and being forced to drop the
suppression produced a strictly better design rather than a workaround.

Since the permitted list is CLOSED, every entry can be mapped to a filesystem
operation instead of a command line. `vet_probe_commands` now TRANSLATES each
command into a `FixtureAction` (`mkdir` / `remove` / `write`) that the harness
performs with `Path.mkdir`, `shutil.rmtree` and `Path.write_text`. **There is
no shell anywhere in this path**, so there is no injection surface to reason
about — and the closed list gains a second justification: a shape nobody has
translated is a shape nobody runs.

Two details that would have been bugs:

- Containment is checked on the RESOLVED path. `untracked/scratch/../../etc`
  starts with the sanctioned prefix and is not inside it.
- `printf 'def broken(\n'` writes a REAL newline and `echo` does not interpret
  the escape. Getting that backwards would author a fixture whose content is
  not what the playbook shows — the same class of defect as a payload
  disagreeing with its prose.

Vetting happens while PLANNING, so a block carrying one unacceptable command
becomes a SKIP rather than being half-executed.

## 00:38 · finding · T3.1 — I shipped Decision 1's exact failure, in my own classifier

Auditing the converted set found **eight blocks that are PROSE, converted to
Bash payloads and reporting PASS while testing nothing**. This is the failure
Decision 1 is written about, arriving through my conversion script rather than
through an inference in the harness, and it was live in `7668ac41`.

The eight: #189 `goal_injection`, #190/#191 `budget_exhaustion_detector`, #199
`model_downgrade_recorder`, #218 `remote_docs_routing`, #232
`plan_qa_commit_gate`, #238 `agent_isolation_advisor`, #241
`docs_qa_commit_gate`. They open `With`, `Simulate`, `Run any`, `Stage`,
`WebFetch` — English describing a scenario a human performs.

**The cause is that my classifier was a BLACKLIST.** It decided "this is shell"
by checking the command did not start with a known prose opener, so anything
phrased in a way it had not seen fell through to shell by default. Every
mechanism in this plan for catching a bad payload then failed in the same
direction:

- The DRY RUN cleared them, because all eight expect **ALLOW**. A prose string
  dispatched as a Bash command matches no handler, returns no decision, and
  `verdict` correctly reads that absence as an allow.
- The DENY siblings of the very same handlers — #217 and #245 — failed loudly
  and were held back for Phase 5. So the dry run exposes prose **only when the
  test expects a refusal**; the allow half is silent by construction.
- The agreement invariant passed too: the payload's command genuinely equals
  the command shown. Both are the same prose.

Worth being precise about what that means: converting a DENY test wrongly is
self-correcting, because it fails. Converting an ALLOW test wrongly is
invisible. Decision 1 argues inference is dangerous because a wrong classifier
produces vacuous passes; what this adds is that the danger is **concentrated
entirely in the allow half**, and that a dry run over both halves can look like
it has cleared everything while only ever having tested the deny half.

Fixed by reverting all eight, and by adding
`test_every_bash_payload_is_a_command_a_shell_could_run` — asked as a
**whitelist**: the first token must be executable (on PATH or in the repo), or
the command must carry a shell construct. Unrecognised shapes are reported for
a human rather than assumed fine. It passes #53
(`bin/hooks-daemon secret-meta ...`, a real repo-relative command), #200
(`yamllint --version` + newline) and #214 (`set -euo pipefail` prelude), which
are the three legitimate cases with unexecutable-looking heads.

Executable therefore settles at **187, not 195**. The lower number is the true
one; the 195 included eight tests that asserted nothing.
