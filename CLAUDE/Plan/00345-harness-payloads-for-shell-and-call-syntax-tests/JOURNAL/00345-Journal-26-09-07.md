## 23:16 · finding · — — this plan exists because a number outlived its scope

Plan 00243 closed with 94 of 228 dispatchable blocks automated and 129 skipped
for want of a `tool_payload`. That looked like a far smaller residual than it
was, because Task 1.2's audit had counted **prose** tests — 119 of them — and
prose was genuinely where the problem lived: five English grammars expressing
one Write payload.

A test whose `command` was already a literal shell string was never in that
count, and the reason was sound at the time: a human could paste it as-is, so
there was nothing to disambiguate. Building the harness in Phase 2 removed that
ground without anyone re-deriving the residual. A harness needs a declared
payload just as much for `echo "git reset --hard ..."` as for a sentence.

Recorded as a shape rather than an instance: a scoping number computed under
one set of constraints was carried, unexamined, into a phase that changed those
constraints. The measurement was right when taken and wrong when used.

## 23:17 · finding · T1.1 — the first classification was wrong, and it argues Decision 1

Sizing the work with a quick filter — "not starting with `Use the`, `Create` or
`Write` " — reported all 104 remaining blocks as shell commands. It was wrong:
the filter tested `Write ` with a trailing space, and `ErrorHidingBlockerHandler`'s
probes start `Write(`. Ten call-syntax blocks were sitting in the shell bucket.

Corrected split of the 129: **79 shell**, **18 shell-shaped but unusual**
(`python3 -c "..."`, `[[ "..." == 0 ]]`), **10 `Write(...)` call syntax**, **22
English prose** (Plan 00243's documented deliberate skips — and that 22 matches
its recorded count exactly, a useful consistency check on both).

The mistake was cheap here and would not have been in the code. It is now the
evidence for Decision 1: a Bash payload is an identity mapping and so looks free
to infer, but the CLASSIFIER is what would be inferred, and this is a measured
instance of that classifier being wrong on 10 blocks. Under inference those 10
become Bash probes that no file-write handler matches; the deny test then sees
ALLOW-by-not-matching, which the harness correctly reads as a pass. Ten tests
would go green while testing nothing, with nothing in the report saying so.

## 23:17 · decision · T3.1 — the human route must not get worse

For the prose tests, Plan 00243 rendered `command` FROM the payload, which
collapsed five grammars into one and removed any possibility of drift.

The same move would be a regression here. For a shell test the bare command is
already the best thing a human can be handed; `as_instruction()` would render
`Use the Bash tool with command='echo "git reset --hard ..."'`, strictly harder
to paste than the command itself.

So shell blocks keep `command` byte-identical and gain a payload alongside it —
and because that reintroduces the two-copies problem the derivation was meant to
solve, Task 3.2 adds the invariant that closes it: a Bash payload's `command`
must EQUAL the block's `command`. The Write half of that file already checks
`file_path` appears in the command; this is the same guarantee for the other
tool.

Call-syntax blocks are the opposite case and get `as_instruction()`:
`Write(\n  file_path=...)` is not pasteable into anything, so there is no human
route to preserve.

## 23:09 · finding · T1.2 — reading the setup commands reversed the answer

PLAN.md initially proposed SKIPPING the blocks that carry `setup_commands`,
reasoning that the harness establishes file preconditions but not command ones,
so such a block would probe a state that never existed. That reasoning is sound
in the abstract and wrong here, and reading all 17 was enough to show it.

**16 of the 17 are `mkdir -p <untracked/scratch/...>`** with an `rm -rf`
cleanup. The remaining two are `echo "test content" >` (#20 `sed_blocker`) and
`printf 'def broken(\n' >` (#149 `lint_on_edit`) — also into scratch. There is
no command among them that reaches outside the sanctioned probe directory.

The `mkdir` majority is very nearly redundant with what the harness already
does: `_run_probe` calls `target.parent.mkdir(parents=True, exist_ok=True)`
before a PostToolUse write. So running setup is not a new execution surface, it
is a slightly more general form of an action the harness already performs on the
same directory — which is the argument for doing it rather than against.

Skipping would have parked 17 convertible blocks over a precondition that turns
out to be one `mkdir` the harness performs anyway.

Also corrects a number: **17, not the 14** first recorded. The 14 was counted
inside Task 1.1's buggy shell-shaped filter and inherited the same defect — the
second consequence of that one filter bug, which is worth noting because it
shows how a bad classifier propagates into every figure derived from it.
