# Plan 00555 Task 2.4: start-failure diagnosis

## What changed

- `src/claude_code_hooks_daemon/daemon/paths.py` (stdlib only, runs by file path):
  - `diagnose_venv_start(venv_dir, daemon_dir) -> VenvStartDiagnosis(healthy, lines)`. It runs the venv's own interpreter and reports the interpreter version, `pyvenv.cfg` `version_info`, whether `lib/pythonX.Y/site-packages` (X.Y from the cfg) is on that interpreter's `sys.path`, whether `claude_code_hooks_daemon` is findable, and a `no_site` note. It adds a "cause: interpreter changed under the venv" line on a minor mismatch. Unhealthy venvs end with `fix: <daemon_dir>/bin/hooks-daemon repair`.
  - CLI verb `paths.py diagnose-venv --daemon-dir D [--venv-dir V ...]`. With no `--venv-dir` it diagnoses every `untracked/venv-*`, or says "no venv found". Exit 0 only when all are healthy. This is the reusable core for the Task 2.5 `diagnose` verb.
- `init.sh`: new `_venv_start_diagnosis` (system `python3` runs paths.py, so it works with a broken venv). `validate_venv` now puts the diagnosis in `VENV_ERROR` for all four failure branches (unresolved, missing, not executable, cannot import). Every `uv sync` hint is gone from that function. The `start_daemon` timeout path also prints the diagnosis.
- Not done: the wrapper `bin/hooks-daemon` and its template. They are 2.3's pre-exec block, so I left them alone to avoid a conflict. 2.3 can call `paths.py diagnose-venv` from its import probe.
