# Plan 00555 Task 2.2: hot-path cache no longer serves a drifted venv

## Change

`scripts/lib/resolve_venv.sh` (the cache lives in `_rv_resolve_python_impl`):
a cache hit now also requires `_rv_cached_venv_current <cached_path>`. It compares
two cheap facts:

- `_rv_cfg_major_minor`: the venv's `pyvenv.cfg` major.minor (existing helper).
- `_rv_link_major_minor` (new): the deepest `pythonX.Y`-named hop in the
  `bin/python` symlink chain, followed one `readlink` at a time.

A mismatch is a cache miss, so `_rv_pick_python` runs and its probe-based drift
check (previous commit) refuses the venv. If either side is unknown the hit
passes, the same "cannot tell" rule as before.

The real incident (system Python 3.11 -> 3.13, `untracked/` untouched) is covered by
the symlink side: `pyvenv.cfg` keeps recording 3.11 while the chain ends at
`python3.13`. A changed `pyvenv.cfg` is covered by the cfg side.

## Cost

One file read of `pyvenv.cfg` (bash `read` loop) plus one `readlink` per symlink
hop (typically 1 to 3). Three small command substitutions, so a few forks. No
Python is spawned, which keeps the hot path near its previous cost.

## Limits

A chain with no `pythonX.Y` name (a plain `python3` copy, or a link to an
unversioned binary) is "cannot tell" on the hot path and passes. The miss path's
probe still catches it whenever the cache is rebuilt.
