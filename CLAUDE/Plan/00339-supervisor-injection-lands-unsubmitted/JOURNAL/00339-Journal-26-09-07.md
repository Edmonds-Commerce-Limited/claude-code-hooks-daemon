## 09:45 · finding · P1 — the evidence, and what is inferred rather than observed

Owner report: the compaction message sitting in the input box with a newline
after it, unsubmitted.

CONFIRMED from code and the live `decision.log`:

- `_perform_injection` separates payload from `\r` by a 0.2s SENDER-side sleep
  only. Nothing on the reader side is coordinated with it.
- The supervisor's own injections bypass `HumanInputLine` by design, so it
  cannot observe its own text in the box — the one signal that separates
  "queued" from "never submitted".
- `[esc]` was the only stall remedy. It flushes a queued command; it cannot
  submit a line sitting in the box.
- Each escape sets `_last_action_ts = now`, and BOTH `_escape_due` and
  `_await_timed_out` measure from that field. So the await timeout can never
  interrupt the escape sequence: all `max_escapes` attempts always burn.
- After giving up the machine returns to MONITOR; still red, so once the 300s
  cooldown elapses it can inject a SECOND `/compact` with no guard against the
  first still being in the box.

The live log shows the escape path WORKING for the queued cause — escape 1/5 at
00:03:29, `compaction detected` at 00:03:31 — which is why the fix had to be
additive:

```
00:02:29 would-compact: red at 42% + idle -> injected '/compact ...'
00:03:29 would-escape: queued /compact stalled -> would inject [esc] (1/5)
00:03:31 noop: compaction detected but session busy -> awaiting idle to resume
```

INFERRED, not observed: that read-side coalescing absorbed the CR on the
reported episode specifically. The mechanism is certain; which occurrence hit
it is not, because nothing logs it. Recorded honestly rather than asserted.

## 09:47 · decision · T1.2 — alternate the remedies, do not reorder them

Considered making the FIRST flush an Enter, since the box was visibly stuck.
Rejected: the queued cause is the one with field evidence of being fixed by
ESC, and reordering would trade a confirmed remedy for a hypothesis. Two
existing tests asserted "second attempt is also ESC"; their real invariant is
"a flush keeps firing at intervals" and "the sequence terminates", both of
which survive — so they were updated to the new alternation rather than
deleted.

Also rejected: retrying the CR inside `_perform_injection` a moment later. It
is subject to the SAME coalescing — a reader blocked for 500ms swallows both
carriage returns. A retry is only meaningful on a timescale where coalescing is
impossible, which is the 60s stall interval, i.e. the state machine.

Also rejected as a fix in itself: raising `_SUBMIT_DELAY_SECONDS`. It narrows
the window without closing it, and would read as a fix while leaving the defect
in place.

Both remedies share the ONE `max_escapes` budget deliberately: adding a remedy
must not double how long a wedged session escalates before giving up.

## 09:52 · handoff · P2/P3 — what is deliberately left open

Phase 1 ships. Phase 2 (a second `/compact` stacking on the first) is left
unfixed ON PURPOSE: it is only reachable when BOTH remedies fail, so guarding
it now would be building for a case that may no longer occur. Measure first.

Phase 3 (explicit bracketed-paste framing) is the only fix that removes the
timing dependence rather than compensating for it — the supervisor owns the PTY
master, so it IS the terminal, and Claude Code enables bracketed paste (the
proof being that `HumanInputLine` already parses the markers out of the
forwarded human stream). It is NOT shipped because Claude Code may render a
bracketed paste as a `[Pasted text]` placeholder, which would stop `/compact`
being recognised as a slash command and break compaction outright. That needs a
scratch-session experiment, not reasoning.
