## How opencode is hooked at all

There is no out-of-process command hook in opencode V2: `Config.Info` has no `hooks` key
(`packages/schema/src/config.ts:26-114`; SURFACE §3). Every row below therefore assumes the bridge SURFACE §3
recommends: a thin in-process **V2 Promise plugin** (`@opencode/plugin`, `{ id, setup }`) that forwards each hook
or event to the daemon socket and applies the verdict by **mutating the hook's event object** or **throwing**.
Three hook properties shape every verdict:

1. **Only `tool.execute.before` can fail.** Every other hook's failure type is `never`
   (`packages/core/src/plugin/hooks.ts:13-30`). Outside that one hook, "block" has to be built from a rewrite, a
   permission effect, or an after-the-fact API call.
2. **No per-hook timeout.** A hung hook stalls the operation indefinitely (SURFACE §5). The bridge must impose its
   own socket timeout and pick fail-open or fail-closed per event, the job `relay/hooks_relay.rs` does today.
3. **The server is shared and long-lived.** One plugin instance can serve many projects. The bridge must route by
   `ctx.location` to the right project's daemon (ARCH §8.1 point 2).

The bus events (`ctx.event.subscribe()`, or SSE `GET /api/event`) are observe-only. Acting on one needs a call back
into the API: `session.prompt`, `session.synthetic` or `session.interrupt` (SURFACE §2.3, §3).

**Verdict legend** (relative to what the daemon does on Claude Code today):

- **FULL**: everything the daemon uses on this event can be expressed. The bridge still has to translate the
  payload; that alone does not reduce the verdict.
- **PARTIAL**: some of it can be expressed. The row says what is lost.
- **OBSERVE-ONLY**: the daemon can see the moment but cannot change its outcome synchronously.
- **NONE**: no counterpart.

Where Claude Code's own event is non-blocking (`can_block=False`), an observe-only counterpart is **FULL** parity.

## Summary: how much of the daemon could run at full fidelity

Counted per event from the handler registry (`bin/hooks-daemon handlers`, 187 handlers on real events; the 2
`nitpick` pseudo-event handlers ride on the stop path and fall with Stop):

| Verdict          | Events (handler count)                                                                                              | Handlers | Share |
| ---------------- | ------------------------------------------------------------------------------------------------------------------- | -------- | ----- |
| **FULL**         | PreToolUse (87), PostToolUse (16), PreCompact (2), PermissionRequest (1), PostToolUseFailure (1), StopFailure (1)   | 108      | 58%   |
| **PARTIAL**      | SessionStart (36), UserPromptSubmit (9), SubagentStop (6), Notification (1), WorktreeCreate (1), WorktreeRemove (1) | 54       | 29%   |
| **OBSERVE-ONLY** | Stop (7)                                                                                                            | 7        | 4%    |
| **NONE**         | StatusLine (18)                                                                                                     | 18       | 10%   |

The 20 wired events with **zero** handlers include 10 at FULL parity (mostly observe-only on both hosts) and most of
the rest at PARTIAL. They cost nothing today.

**Reading the 58% honestly.** It measures whether the *event mechanism* exists. It does not measure whether each
handler works unchanged.

- **It overstates in two ways.**
  - Inside PreToolUse, roughly 7 handlers are keyed on tools opencode lacks (Table 3, last row), plus
    `block-ask-user-question`, `subagent-context-budget` and `usage-pause-tool-gate`, which need transcript, Claude
    usage or presence inputs. That is about 10 of the 87, by inspection and not by a per-handler trace.
  - Every write guard needs the `patch` parser before it covers all of opencode's file mutations.
- **It understates in one way.** Most SessionStart (36) and UserPromptSubmit (9) handlers only inject context, which
  opencode does *better* through `session.context`. Their PARTIAL verdict comes from the lost user-visible
  `systemMessage`, the lost start source, and, for UserPromptSubmit, the lost block.

**Where this leaves the two halves of the daemon.** This confirms the split in COUPLINGS ("the daemon's two halves
are unequally portable"):

- **Safety-guard layer** (PreToolUse/PostToolUse on shell and file tools, plus permission): ports at full fidelity
  through one in-process plugin. That is about 104 handlers (PreToolUse and PostToolUse) once the name, field and
  patch adapter exists.
- **Autonomy layer** (the Stop/SubagentStop gates, crons, usage pause, status line): degrades to after-the-fact
  re-driving or disappears. That is 7 Stop, 6 SubagentStop, 18 status-line handlers, and parts of SessionStart and
  UserPromptSubmit.

**opencode is also stronger than Claude Code in four places**:

- `session.context`: per-step context and tool-list editing.
- `shell.create.before`: rewriting the command and environment.
- `session.compaction`: replacing the summary.
- Code Mode inner calls stay visible to the guards.
