## 19:17 · finding · P2 — Round 1: concurrency reviewer = Option A, scope-keyed

Second of three. VERDICT: option **(A) lazy per-segment TTL, pull-on-render,
scope-keyed, monotonic in-daemon clock, + (C) event-invalidation for git only**.
Two decisive findings that reshape the plan:

1. **The payload-vs-system taxonomy draws the safety boundary in the WRONG
   place.** "System-derived" was implicitly equated with "globally shareable",
   but `git_branch`, `git_repo_name`, `working_directory`, multithread rank, and
   terminal width are disk/system-derived yet **per-session**. Caching any of
   them to a project-scoped shared file LEAKS one session's value into another
   under Plan 00127 (shared daemon). #1 correctness risk. Required rule: cache key
   = `(segment, scope)`, `scope ∈ {global, session_id, working_dir}`. Genuinely
   global: container, time, daemon_stats, upgrade, account, supervisor-state.
2. **Background threads (B) can't refresh the per-session facts that motivate
   them.** One daemon = single owner (no election race), but a timer thread owns
   NO session payload, so it can only refresh already-cheap global facts — the
   costly per-session fact (git) can only be warmed by the render itself. So
   pull-on-render (A) is the ONLY mechanism that refreshes per-session facts
   without leakage. B is self-defeating here.

OQ answers: Q2 → A sidesteps ownership; Q3 → monotonic in-daemon TTL, wall only
for cross-process stamps (never mix — Plan 00173's exact lesson), low git TTL +
event-invalidation, per-segment files OK (no cross-segment invariant) with
pid+tid tmp names + `.*.tmp` skip + orphan GC in startup_cleanup; Q4 → TTL-refresh
vs event lost-update race → per-segment monotonic seq + one in-process write lock.

LATENT BUG flagged (dogfooding follow-up candidate): `context_sidecar` tmp path
is `.{stem}.{pid}.tmp` — missing the `tid` the supervisor uses
(`.{name}.{pid}.{tid}.tmp`); a gap if the sidecar ever goes multi-threaded. Also
Plan 00173's `status-message.json` is not session-keyed (tolerable now; the
artefact must not institutionalise the shared path).

Convergence so far (2/3): AWAY from the big artefact-store-+-background-threads,
TOWARD a minimal scope-aware lazy-TTL cache pulled on render + git
event-invalidation + the existing Ctrl+Z push. Awaiting the arch lens.

## 19:35 · finding · P2 — measured: artefact store optimises the wrong layer

User self-corrected: "I mentally jumped from *increase refresh rate* onto *add a
performance optimisation to enable faster refresh without penalty*." Grounded the
LAG/COST reframe with a real measurement (30 warm renders of
`.claude/hooks/status-line`): **~39 ms/render**, stable, no spikes — git shows
`↑4` yet render time stays flat, confirming the `git_branch` TTL cache (Plan
00155) already absorbs the one expensive segment. Traced the cost:
`send_request_stdin` (init.sh L853) spawns a fresh `python3 -c` stdlib client
PER render to reach the socket. So the ~39 ms floor is **client
python-interpreter spawn + socket round-trip**, NOT daemon-side segment assembly.

Decisive consequence: an artefact store optimises daemon-side segment
*generation* — already the cheap slice, and already cached — so it CANNOT lower
the ~39 ms floor a faster refresh pays (that floor is the client spawn, before
the daemon runs). The user's "need a perf optimisation to refresh faster without
penalty" instinct has a real kernel (faster refresh IS ~1 python spawn each), but
the lever that touches it is a **lighter client transport** (persistent/pooled
connection) — a different optimisation, and likely not worth it above ~150 ms
refresh. Reinforces Decision 4 (defer store) and adds a third cost layer to the
LAG-vs-COST split: (1) lag → refreshInterval + event-push; (2) client-spawn floor
→ lighter transport (separate, deferred); (3) segment generation → the
scope-keyed TTL helper, kept for CORRECTNESS (shared-daemon leakage), not as a
refresh enabler.

## 19:40 · finding · P2 — ROOT CAUSE: lag is real seconds, and it's `refreshInterval: 10`

User corrected the lag magnitude: NOT microseconds — **multiple real seconds,
~5**. That instantly falsifies the render-cost framing (39 ms can't sum to 5 s)
and pointed at cadence. Researched Claude Code's status-line refresh contract
(official docs, code.claude.com/docs/en/statusline):

- The status command re-runs ONLY on these events: new assistant message,
  `/compact` finishes, permission-mode change, vim-mode toggle (debounced
  300 ms). **Ctrl+Z is NOT a trigger** — and we cannot add triggers.
- Docs verbatim: "These triggers can go quiet when the main session is idle. To
  keep time-based or externally-sourced segments current during idle periods,
  set `refreshInterval` to also re-run the command on a fixed timer." Our Ctrl+Z
  message file IS exactly an "externally-sourced segment updated during idle".
- `refreshInterval`: "re-runs your command every N seconds. The minimum is 1."

Checked this project's config — **`.claude/settings.json` had
`"refreshInterval": 10`** (10 seconds). So an idle Ctrl+Z waits for the next 10 s
timer tick; random phase → average ~5 s. Exactly the measured lag, and it also
empirically confirms the unit is SECONDS (10 → ~5–10 s observed). Fixed:
`refreshInterval: 10 → 1`. Worst-case idle lag ~1 s, avg ~0.5 s. Cost of 1 s
ticks: ~39 ms/render ≈ 4 % of one core during idle, git already cached — trivial.
(Takes effect next session; settings read at launch.)

DECISIVE for the plan: the LAG has a one-line config fix and NO redesign. And
Claude Code caps periodic refresh at 1 s regardless of how cheap our render is,
so there is **no faster-refresh headroom for an artefact store to unlock** — it
would optimise a render cost that has no consumer. Plan 00174's artefact-store
redesign is therefore not merely deferred but **provably unnecessary for the
stated goal**. The only sub-1-s path for Ctrl+Z is the supervisor writing to the
terminal directly on suspend (bypassing the status line) — a Plan-00173-class
mechanism, out of scope here. Remaining salvage from 00174: the scope-keyed cache
is a genuine CORRECTNESS item (shared-daemon per-session leakage) but is
unrelated to lag. Recommend superseding 00174; awaiting user steer.
