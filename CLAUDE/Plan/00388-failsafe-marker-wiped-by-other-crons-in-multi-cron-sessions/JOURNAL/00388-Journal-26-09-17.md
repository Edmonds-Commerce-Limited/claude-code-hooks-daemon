VERIFIED — the arm/disarm asymmetry, which is the report's best finding:

```
src/.../handlers/stop/auto_continue_stop.py:52
from claude_code_hooks_daemon.utils.blockage_marker import MARKER_FILENAME, write_marker
```

`write_marker` only. The Stop handler can ARM the marker and has no way to
disarm it, so clearing can only ever happen at `UserPromptSubmit` — and THAT is
why the "was this prompt a human?" question exists at all. It is an unbuilt
lever rather than a constraint, and it yields an option none of PLAN.md's three
candidates considered: disarm at any `Stop` that does not declare blockage, and
never classify a prompt.

NOT REPRODUCED — the character count:

```
_CANONICAL_CRON_PROMPT:       980 chars
CANONICAL_CRON_PROMPT_MARKER:  23 chars
```

The report states "986 characters, not 980". Measured here against the constant
it is **980**, the figure the report was correcting. The argument it supports —
thin headroom under a 1000-character delivery cap, so whole-text equality is
fragile — is unaffected either way, and the recommendation does not rest on the
exact number. Recorded so the number is not propagated as measured fact.

The lesson is the ordinary one: a sub-agent's reasoning can be excellent and its
arithmetic still wrong, and the two have to be checked separately.

## 11:22 · finding · — — the reframe is the valuable part

Independent of any ruling: the code answers three different questions with one
boolean — *is this prompt a human* (clear the marker), *should this tick be
delivered* (allow), *should this job exist right now* (allow the stop). Three
subjects, one flag.

That reframing makes today's behaviour a PRECISION failure in the safe
direction rather than a safety failure, which in turn sets the risk budget:
recognition must be positive evidence, and absence must resolve to "human".
Approach 3 (treat unrecognised prompts as automated unless they look human) is
disqualified on that principle regardless of how much coverage it would buy.
