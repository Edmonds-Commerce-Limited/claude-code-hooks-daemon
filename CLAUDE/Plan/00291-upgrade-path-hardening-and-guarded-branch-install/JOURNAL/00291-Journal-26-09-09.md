## 22:20 · decision · T3.1 — gate shape (design note written)

`GUARDED-BRANCH-INSTALL.md` in the plan folder is the SSoT. Summary of the
choices and why:

- Two env vars, `HOOKS_DAEMON_UNSAFE_TRACK_REF` and
  `HOOKS_DAEMON_UNSAFE_TRACK_REF_BECAUSE`, BOTH required. Exactly one set is
  a hard refusal naming the missing one, never "off": a half-typed gate is a
  mistake, and silently ignoring it would be the non-obvious-in-the-wrong-
  direction the ruling warns about. Gate plus a positional version is also
  refused (two spellings of the target contradict each other).
- Layer 1 owns the fetch (`git fetch origin <ref>`) and hands Layer 2 the
  RESOLVED COMMIT, not the ref name. A bare ref passed down would be
  rev-parsed against the LOCAL branch, which lags origin after a fetch.
- Layer 1 cannot source `scripts/install/` (it may be a curl-fetched copy in
  /tmp), so it carries its own copy of the ~15-line gate check; Layer 2
  sources the shared `branch_install.sh`. The two are kept in step by tests
  on both.
- Stamp `vX.Y.Z+<ref>.<shortsha>` where X.Y.Z is the target commit's
  pyproject version. Stored in the venv's `.daemon-version` and
  `.daemon-metadata.json` (validator regex widened to accept the `+` suffix).
  `install_stamp.read_install_stamp()` reads it from `sys.prefix`, so
  `status` and `version_check` read the install they are RUNNING from.
- `version_check`: a branch install short-circuits before the cache and the
  network. It structurally cannot say "up to date" because it never compares.
- Layer 2's fast-path guard was a NAME comparison (`describe --exact-match`
  vs TARGET_VERSION). A branch install's target is a commit no tag names, so
  it would have taken the slow path while every tag takes the fast one. The
  guard now also accepts commit equality; a second tag on the same commit is
  the same case for a release.
- UNRELEASED manifests: loaders take `include_unreleased`; `None` asks the
  stamp. The staging dir is always `<released>/../UNRELEASED/<name>`, so a
  test override carries its own twin. `--include-unreleased` on both CLI
  commands for explicit use. upgrade.sh does NOT pass the flag: an older
  branch target would not know it, and the auto-detection in the target's
  own CLI does the job when the target has it.

## 22:35 · decision · T1.2 — the boundary is "does a config exist"

A project with `.claude/hooks-daemon.yaml` is an existing install, whatever
else is missing. So the fresh-clone client state (config + forwarders, no
checkout, no venv) belongs to the UPDATE guide, and the update route must
work there without a manual step. Rather than document "clone the daemon
first by hand", `upgrade.sh` now clones it (Step 3) when the config exists
and the checkout does not; a project with neither is sent to LLM-INSTALL.
`HOOKS_DAEMON_CLONE_URL` overrides the clone source for tests and offline
canaries. LLM-UPDATE.md gets one subsection under "Where You Should Be".

## 23:02 · finding · T4.1 — canary run 2: hooks could not reach the daemon

Reclone, rerun from the canary root with `4b77b327` pushed. Daemon now
correctly the canary's (`status` RUNNING + the `Install: NON-RELEASE` line),
but every forwarder failed: "A live daemon owns the socket but is not ours
... refusing to steal it". The canary path in the worktree is long enough
that the daemon fell back to `/run/user/<uid>/hooks-daemon-<hash>.{sock,pid}`
and left a `.socket-path` discovery file; `init.sh` followed the discovery
file for the SOCKET but left `PID_PATH` at the long default, so
`is_daemon_running` said no and `cli start` refused the live socket. Proved
with a pre-fix probe (old init.sh, bound socket, discovery file: SOCKET_PATH
followed, PID_PATH did not). Fix (`03eef02f`): the PID path follows the
discovered socket's stem unless `CLAUDE_HOOKS_PID_PATH` is explicit;
behavioural test `test_init_sh_discovery_pid_path.py` sources the real
init.sh against a bound socket. Any client deep enough in the filesystem
had dead hooks after an install or upgrade until this.
