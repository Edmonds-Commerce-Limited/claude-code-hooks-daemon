## 14:32 · decision · T2.3 — the raise is scoped to the RELOCATION path, not the sweep

`_fill_block_defaults` is called from two places, and making it raise
unconditionally would have been wrong. `migrate_relocated_handler_keys`
passes a `RELOCATED_HANDLERS` target: an unknown one there IS a bug, and the
old `{enabled: True}` fallback silently retired the moved handler a second
time. But `scaffold_pseudo_event_blocks` walks every pseudo-event block in a
merged config, which may legitimately include one this constant never had to
scaffold — raising there would abort an upgrade over a user's own config.

So the sweep now SKIPS a block it has no defaults for (leaving it exactly as
written, since there is nothing to complete it from), and the raise only
fires on the relocation path. The new "every relocation target has a default
block" test makes the raise unreachable in shipped code, which is the review's
other suggested remedy; both are in, because the test is the guard and the
raise is the backstop.

## 14:34 · finding · P2 — the QA runner cannot find this worktree's venv

`scripts/qa/llm_qa.py` hardcodes `untracked/venv/bin/python`, which
`scripts/install/venv_resolver.sh` documents as the *retired* pre-v3.7.0
layout it deliberately refuses to fall back to. In a worktree the resolver
answers `untracked/venv-<hash>/bin/python`, so `llm_qa.py all` dies with
`FileNotFoundError` before running anything (`lint` alone survives because it
does not go through `VENV_PYTHON`).

Worked around locally with a gitignored symlink
`untracked/venv -> venv-<hash>`; the canonical venv also needed
`uv sync --extra dev` because it had no pytest/ruff/mypy. **Not fixed here** —
it is a QA-tooling defect outside Phase 2's scope, and the other three phase
worktrees will hit it identically. Worth its own task: `llm_qa.py` should
source `venv_resolver.sh` like everything else does.

Also note: `uv sync --active` WITHOUT `--extra dev` strips the dev tools out
of the venv. Use `--extra dev`.
