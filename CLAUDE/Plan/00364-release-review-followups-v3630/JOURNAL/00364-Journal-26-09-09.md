Worktree `worktree-plan-00364-p1-core`, branch of the same name. Every task

- **T1.1** `venv_lock._mkdir_lock` now catches `FileNotFoundError` around the
  stale-age `stat()` and retakes the lock: the holder's `rmtree` landing
  between our `mkdir` and our `stat` means the lock is FREE, not that
  anything is broken. The retry is bounded by the same deadline, and only
  the first one is immediate, so a lock NAME that can never be stat'ed (a

  second new test builds exactly that. `cmd_repair`'s "'uv' not found"

Not a Phase 1 regression, and worth a plan of its own. Both audit scripts
exclude any path containing `untracked`, and this worktree's absolute path is
`/workspace/untracked/worktrees/…`, so every file in it is excluded:

```
scripts/qa/audit_capture_corruption.py:  _EXCLUDE_DIR_PARTS = {"untracked", ...}
                                         _is_excluded -> any(part in ... for part in path.parts)
scripts/qa/audit_error_hiding.py:        _DEFAULT_EXCLUDE_PATTERNS = ("untracked/", ...)
                                         any(pattern in str(py_file) ...)
```

Takeaway: `test_default_scan_dirs_clean` fails its `len(files) > 0` guard,
and every one of the 127 live error-hiding exclusions reads as stale because
zero violations are collected to match them against. Both fail identically
with no Phase 1 change applied. The capture-corruption script at least prints
"no shell files found" on its CLI path; the audit consumed by the test does
not. Worth filing: a worktree is the project's own supported layout
(`WORKTREE_DIR_PATTERNS` names `untracked/worktrees/`), so the audits should
exclude the repo-relative segment, not any occurrence in the absolute path.
