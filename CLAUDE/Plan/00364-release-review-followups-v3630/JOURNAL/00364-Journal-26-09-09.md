## 15:05 · action · T4.1 — the staged-content bounds now cap the peak, not just the scan

`_staged_content_haystacks` asks git two questions instead of one.
`--numstat -z` first (one added-line count per path, no content at all), then
a patch call restricted to the paths that survived selection. A binary blob,
an excluded path, the secret list itself, a file the per-file bound already
excludes and everything past the whole-commit budget are all dropped before
git is asked for a byte of them.

Both stand-down log lines keep their wording, and each file is logged at most
once — a file dropped by the sizing pass never reaches the exact byte check.
The whole-commit stand-down fires once and names the first path left
unjudged, whichever pass stopped the walk; `_StagedSelection.stood_down_at`
carries the sizing pass's stop point into the scan so the two cannot each
name a different file for one truncation.

Two things the fix needed that the finding did not mention. Pathspec
chunking (`_MAX_PATHSPEC_ARGV_BYTES`, 64 KiB): a commit staging thousands of
files would build an argv past `ARG_MAX`, `run_git` reports the `OSError` as
a non-zero return code, and this handler reads that as "no staged diff" —
the change would have stood the guard down silently on exactly the large
commit it most needs to judge. And an unrestricted fallback for a path that
cannot round-trip: `run_git` decodes with `errors="replace"`, so a name
carrying a byte that is not valid UTF-8 comes back bearing U+FFFD and would
match no pathspec, so such a commit asks the broad question and every staged
path is still judged.

## 15:06 · thought · T4.1 — what the numstat bound does NOT bound, stated up front

`--numstat` counts LINES; the constants are BYTES. An added line costs at
least its own newline, so the count is a sound LOWER bound: a file whose line
count alone passes the byte bound cannot fit and is dropped unread. The
converse does not hold, so a file with few but very long lines (a minified
bundle on one line) still gets fetched before the exact byte count rejects
it. git offers no per-path byte figure in a diff; closing that would need a
second object-size query (`--raw -z` plus `cat-file --batch-check`, which
needs stdin support in `run_git`). Not done — the finding was about a
generated artefact being pulled in whole, and that case is closed.
