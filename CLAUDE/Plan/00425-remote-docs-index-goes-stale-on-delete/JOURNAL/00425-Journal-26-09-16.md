## 17:40 · finding · — — the issue's "Where" is wrong, and it changes the fix

Issue #43 says `_regenerate_remote_docs_index` "is called from the `add` path
only". It is not — it sits after the action dispatch in `cmd_remote_docs` and
runs for `add` **and** `refresh`. Reproduced: `refresh --all` cleared the stale
row.

That cuts both ways. It narrows the gap to `list` and `check`, but it also means
the only existing repair is a full network re-fetch of the whole corpus to
correct a purely local rendering — which strengthens the reporter's "no supported
way to bring the index back into line" point rather than weakening it.

Reproduction script: `untracked/scratch/repro43.py`. Output with one of two
captures deleted:

```
after list, index still names a: True
running `remote-docs check`:
remote-docs: all vendored documents are fresh
check exit code: 0
after check, index still names a: True

after `refresh --all`, index still names a: False
```

The middle three lines are the sharpest form of the defect: the command whose
job is to report problems asserts health while the index is demonstrably wrong.

## 17:41 · finding · — — root cause is the assumption, not the call sites

`remote_docs/index.py` records the original decision at the source: regenerate on
`add` and `refresh` "rather than on demand, because an index that silently goes
stale is worse than no index". That reasoning holds and is not what failed.

What failed is its assumption that every change to the tree arrives through the
CLI. Deletion is the one mutation that does not — `rm` runs no command — so no
regeneration hook can fire, whichever commands carry one. Adding regeneration to
more commands cannot fix this, because the project may never run one afterwards.
Detection is the load-bearing half.

## 17:42 · decision · P1/P2 — the issue's two suggestions are incompatible

#43 offers (a) regenerate at the end of `list`/`check`/`refresh`, or (b) a
`remote-docs index` command plus `check` reporting staleness, as alternatives.
They are not: taking (a) forecloses (b). A `check` that regenerates the index can
never *report* it as stale, because it would have just repaired it — and a
read-only reporting command would start writing files as a side effect, which
matters to anything running `check` in CI.

Going with (b). Recorded (a) as a Non-Goal with this reasoning.

## 17:43 · decision · P2 — simplicity check before adding CLI surface

Looked for an existing home for "re-render a generated artefact" before adding a
verb; there is none (`repair` is venv-specific). So `index` is a fourth verb on a
subcommand that already has four, and its body is the existing
`_regenerate_remote_docs_index` call.

Two things that check surfaced for the implementer:

- `_remote_docs_check` receives `tree` only, but the index lives at
  `<project_root>/.claude/REMOTE-DOCS.md` — the signature has to widen.
- `render_index` is pure and path-ordered with no generation timestamp
  (`test_rewriting_is_idempotent` already pins this), so staleness detection is
  an exact string comparison with nothing to churn.

Flagged the new-verb judgement call on the issue itself, so the owner can object
before merge rather than after.
