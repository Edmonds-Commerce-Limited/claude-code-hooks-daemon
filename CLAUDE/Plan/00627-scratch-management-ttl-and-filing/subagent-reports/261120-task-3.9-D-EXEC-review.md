## Finding 1 (confirmed): nested git still sees git settings inherited from the caller's environment

- **Citation:** `core/scratch_repos.py:86-94` and `:565`. The call is `project.runner(..., env=NESTED_GIT_ENV)`, which goes through `run_git`. `run_git` (`utils/git_repo.py:207-213`, unchanged in this interval) lays these variables on top of the whole inherited `os.environ` and removes only `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and `GIT_COMMON_DIR`. The comment says this is "The environment of every git run inside a nested repository".
- **Proven two ways:**
  - Calling the real `_child_environment(NESTED_GIT_ENV)` with these set: `GIT_CONFIG_PARAMETERS`, `GIT_EXEC_PATH`, `GIT_ALTERNATE_OBJECT_DIRECTORIES` and `GIT_NAMESPACE` all come out unchanged.
  - A throwaway nested repo with `* filter=x` in `.gitattributes`, run with the exact flags and environment of the nested `status --porcelain=v1 ... --ignore-submodules=all` call, plus `GIT_CONFIG_PARAMETERS="'filter.x.clean'='touch …/PWNED; cat'"`. The sentinel file was created. Probe removed; no `dexec-probe*` directory remains.
- **What it allows:** a command-valued setting (a clean filter, `core.sshCommand`, and so on) bypasses the nested-config allowlist and runs during classification. That covers the dry run as well as `--apply`. The other inherited variables can change which objects or refs the nested git sees, and therefore the verdict.
- **Threat model:** the mechanism is in scope, because the daemon can see the variable when it makes the call. **I could not place a trigger:** git only sets `GIT_CONFIG_PARAMETERS` for its children when run as `git -c …` (an alias, `rebase -x`, a hook), and the value would also have to name a driver the nested repo's attributes use. I'm reporting it as a broken invariant, not as an exploit route.
- **Class:** asymmetric sibling protection (already in the register). The sibling `_TAR_ENV` replaces the environment outright; `NESTED_GIT_ENV` only adds to it, and `GIT_CONFIG_COUNT=0` shows the environment channel was considered and only half closed.
- **Why the tests miss it:** `test_scratch_repos.py:194-228` puts filters and fsmonitor only in the nested repo's own config, which the allowlist catches. No test sets a variable in the process environment.
- **Detector hypothesis:** any `env=` constant passed to `run_git` whose docstring or comment claims isolation must either pair with a denylist that removes every inherited `GIT_*` except a named few, or be declared as an overlay. Likely false positives: the project-root calls that deliberately inherit the environment, such as `remote_git_env` for ssh.
- **Fix:** add `scrub_inherited_git=True` (or similar) to `run_git`, which drops every inherited `GIT_*` other than the ones passed in, and use it for `_nested` and `_config`.

## Finding 2 (confirmed): the printed restore command is quoted with Python's `repr`, not `shlex.quote`

- **Citation:** `core/scratch_archive_batch.py:278-281`, `f"--entry {f'{directory}/{name}'!r}"`.
- **What it allows:** `check_name` permits `'`, `$` and backticks. For a name containing `'`, `repr` switches to double quotes, so `it's $(id).txt` is printed as `"it's $(id).txt"`. An agent pasting that runs the substitution. With only `$var` in the name, the variable expands, the wrong entry is named, and the restore is refused.
- **Threat model:** apostrophes in file names are ordinary, so this is in scope. Real command execution also needs `$(` or a backtick in the name, which is rare.
- **Class:** asymmetric sibling protection. `scratch_filing.py` quotes its printed `mv` with `shlex.quote` and refuses unprintable names; this sibling does neither.
- **Why the tests miss it:** I found no test with `'` in a batch name.
- **Detector hypothesis:** an f-string that builds a `hooks-daemon`/shell command and uses `!r` or `repr(` on a path. It should be low noise.

## Finding 3 (not confirmed): `find_gnu_tar` looks up `tar` on the caller's `PATH`

- **Citation:** `core/scratch_archive_pack.py:100`, `shutil.which("tar")`.
- **The problem:** this uses the caller's `PATH`, while `require_decompressor` (`:538`) and every tar run use the pinned `/usr/bin:/bin`. The result must be an absolute path whose version line says "GNU tar", so a bsdtar or a relative entry is refused. A GNU tar earlier on `PATH` (venv or `node_modules/.bin`) would still be trusted. I found no realistic careless-agent shape that does this.
- **Fix:** look it up with `path=_TAR_ENV["PATH"]`.

**Related robustness problem (not a security finding):** `:104` does not catch `subprocess.TimeoutExpired`, and the CLI catches only `PackRefused`. A hung `tar --version` crashes the command with a traceback, and nothing is changed.

## Checked and clean

- **How tar is called:** always an argv list, no shell, environment replaced by `{LC_ALL=C, PATH=/usr/bin:/bin}`, so `TAR_OPTIONS`, `POSIXLY_CORRECT`, `TMPDIR` and `HOME` are gone. Working directory is `/proc/self/fd/N` with `pass_fds`. Every call has a timeout (600s; 30s for `--version`).
- **Create:** members are read NUL-separated from stdin (`--verbatim-files-from --no-recursion --one-file-system --format=gnu`), every name prefixed `./`, never `-h`.
- **Compare and extract operands:** always `--no-wildcards --no-unquote --`.
- **Options that run commands:** none of `--to-command`, `--checkpoint-action`, `--use-compress-program` or `--absolute-names` appears. Compression is set explicitly (`--gzip`/`--xz`) from the archive's first bytes, and the decompressor is found on the pinned `PATH`.
- **Member types:** only directory, regular file and symlink pass. Hard links, devices, FIFOs and GNU sparse members are refused, and `nlink>1` refuses the whole entry.
- **Restore headers:** a member under a symlink member, `..`, an absolute path or a duplicate is refused. Extraction goes into a fresh 0700 staging directory with `--keep-old-files --no-same-owner`.
- **Decompression bombs:** a restored archive matches its recorded SHA-256 and counts, and was compared against a real tree. The in-process `tarfile` header read has no time limit; that only matters for adopted, agent-made tarballs, which is a hostile shape and out of scope, and adopt is not called from the CLI.
- **git calls:** all go through `run_git` (scratch modules and `cli.py:6832/7087`). The nested runs add `-c core.fsmonitor=false`, `core.hooksPath=/dev/null`, `protocol.allow=never`, `submodule.recurse=false` and `GIT_CONFIG_GLOBAL=/dev/null`/`NOSYSTEM`. The config allowlist is read with `--no-includes`, so `include.path`/`includeIf` are refused, and so is `core.worktree`. `ls-remote` runs only at the project root against the project's remote. `git grep` takes its pattern via `-e` and only shas as revisions.
- **Small unconfirmed note (D-PATH more than D-EXEC):** `scratch_sweep.py:473` passes `-- <relative_root>` to `ls-files` as a glob pathspec. A root directory whose name contains glob characters could miss a tracked file. The suggested fix is `GIT_LITERAL_PATHSPECS=1`.
