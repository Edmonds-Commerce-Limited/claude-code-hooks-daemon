## Verdict

**Safe to merge with `--apply` reachable, as far as D-PATH goes.** No
confirmed path from a careless agent's ordinary actions to a write, rename,
chmod or delete outside the validated sweep root or the archive store.

Every write and delete goes through a held directory descriptor:
- `renameat2(RENAME_NOREPLACE)`, with no fallback. When the libc has no
  renameat2, or the filesystem returns EINVAL, the result is ClaimRefused or
  OSError. It never falls back to a replacing rename.
- `unlinkat`/`rmdirat` on names that were listed. Before each removal the
  inode is re-checked (`_require_listed`), and every directory is re-checked
  for its mount id. That mount-id check closes the same-filesystem bind-mount
  hole on the removal path.
- `fchmod`, only on descriptors opened `O_NOFOLLOW|O_DIRECTORY`.

Other properties confirmed:
- The store refuses a link, a foreign owner or a wrong mode, and the store's
  parent is opened `O_NOFOLLOW`.
- `resolve_sweep_root` checks both the literal and the resolved form of the
  root, so a `..` or a symlinked component cannot carry the root out of
  `untracked/`.
- Archive ids are regex-checked before they become file names.
- Restore refuses member names with an empty, `.` or `..` component, any
  member beneath a symlink member, hardlink members and special members. It
  extracts with `--keep-old-files` into a 0700 staging directory and moves the
  result with a no-replace rename.

The findings below are low severity. None of them blocks the merge.

## Findings

### F1 (CONFIRMED, low): an agent-named `.sweeping-<x>` directory is renamed to `<x>` by `--apply`

1. **Citation.** `core/scratch_archive_apply.py:169-173` resumes every name
   with the `.sweeping-` prefix. `core/scratch_archive_remove.py:485-491`
   then does `rename_noreplace(parent_fd, claimed_name, name)` when no record
   names the entry.
2. **What it allows.** An agent creates `untracked/scratch/.sweeping-notes/`
   (say, for an output directory of its own). The next `--apply` renames it to
   `notes`, whatever its age and whatever the classifier would say. The probe
   returned `Resumed(name='notes', outcome='renamed-back', reason='no record
   names the entry')`, and the directory now lists as `['notes']`. A process
   still writing under the old path then fails. No content is lost: when
   `notes` already exists the rename is refused (`stuck`). Removal still
   needs an archive that verifies.
3. **Threat-model test.** In scope. The name is ordinary, there is no race and
   no parser-defeating shape, and the daemon sees it at call time. It is
   unlikely, but a careless agent can type it.
4. **The class.** A sweep treats a reserved-prefix name as its own crash
   leftover without proof that the sweep created it. A defect belongs to the
   class when a name pattern alone (`.sweeping-`, `.restoring-`) authorises a
   mutation. `reclaim_staging` is NOT a member: it also requires the exact
   generated shape, ownership and the device. `resume_claimed`'s
   rename-back IS a member: it requires only the prefix.
5. **Why tests miss it.** They do not miss it: they pin it as designed.
   `tests/unit/core/test_scratch_archive_apply.py:349-356`
   (`test_a_leftover_claim_is_resumed_then_judged_in_the_same_run`) plants
   `.sweeping-e1` by hand and asserts `renamed-back`. That is the intended
   path for a crash between claim and record append. The tests cannot tell a
   real crash leftover from a name an agent chose, because nothing records
   that a claim was made. So a fix MUST keep that crash path working.
6. **Detector hypothesis.** A rename or unlink whose source name was selected
   by `startswith(<RESERVED_PREFIX>)` with no matching record, event or
   journal entry of its creation. Candidate fix: record a `claim` event (or
   a marker) before the claim rename, and rename back only names that such an
   event covers. Leave unrecorded prefixed names alone and report them as
   `foreign`, the way reclaim_staging does. Likely false positives: low. Only
   the two prefixes exist.
7. **Confidence: high** (reproduced).

### F2 (UNCONFIRMED, low): restore lands in the `--root` given, not in the root the record came from

- **Citation.** `daemon/cli.py` `_scratch_restore` opens `sweep_root.path`,
  which defaults to `untracked/scratch`. `restore()` uses only
  `basename(record.original_path)` and never checks the record's directory
  against the destination.
- **What it allows.** Restoring a record packed from
  `--root untracked/briefs` without repeating that `--root` puts the entry in
  `untracked/scratch/` under a different TTL. It is still inside a validated
  root, so nothing escapes. The entry is misplaced, not exposed.
- **Threat-model test.** In scope: running `restore <id>` without repeating
  `--root` is an ordinary careless omission.
- **Class.** The destination is chosen by the caller and not checked against
  the record.
- **What would settle it.** A CLI test that restores a `--root untracked/<d>`
  record with the default root and asserts a refusal (or a correct
  placement).
- **Why tests miss it.** The CLI restore tests use the default root only.
- **Detector hypothesis.** A restore whose destination directory is not
  compared with `dirname(record.original_path)`.
- **Confidence: medium.** This is from reading the code; I did not run it.

### Dismissed (threat model): same-filesystem bind mount is caught at removal but not at pack

- **Citation.** `scratch_archive_claim.py:224` (walk checks `st_dev` only);
  `scratch_archive_pack.py:64` (`--one-file-system` is also `st_dev`).
- **What it allows.** A bind mount inside an entry is walked and packed, so
  the archive copies content the entry does not own. `_remove`'s mount-id
  check then refuses, which leaves the entry claimed and stuck. Expiry holds
  the archive while the claim exists. Nothing is deleted, but the copy
  persists in the store.
- **Threat-model test.** Probably out of scope (`Dismissed (threat model)`
  candidate). Making a bind mount needs CAP_SYS_ADMIN, which is not an
  ordinary agent action.
- **Fix if wanted.** Compare the mount id in `walk_tree` too.
- **Confidence: medium.** I could not test it, because a bind mount needs
  privileges this session does not have.

## Dismissed (threat model)

Note: the store being 0700 and owned by this user is NOT the ground for these
dismissals, because the careless agent IS that user. Each is dismissed under
the two-part test instead.

- **Removing a "stale" lock file** is an ordinary action, so it is in scope.
  Its effect is two sweeps holding locks on two different inodes:
  - The claims stay atomic (a no-replace rename), so two sweeps can never
    claim the same entry.
  - `_append_line` does a seek-to-size and truncate rather than `O_APPEND`.
    Two concurrent appends could therefore cut a line that is half written.
  - A record lost that way only makes `remove_claimed` refuse
    (`record not in records`). The entry is then left claimed, and the next
    resume renames it back.
  - The cost is an unrecorded archive (reported by the audit), never lost
    content. Low; worth a note, not a blocker.
- **A FIFO planted as `index.jsonl`, `events.jsonl` or `<id>.tar` in the
  store** blocks `_open_file`, because the `O_RDONLY` open has no
  `O_NONBLOCK` and the regular-file check comes after the open
  (`scratch_archive.py:426-431`). The store is 0700 and owned by the user. The
  shape has no working purpose. A one-line hardening is available: add
  `O_NONBLOCK` and keep the fstat check.
- **Intermediate path components followed on the first `open`** of the sweep
  root and the store parent (only the last component is `O_NOFOLLOW`). The
  root is validated in both its literal and its resolved form just before.
  Exploiting this needs a concurrent swap: a race, not a careless action.
- **tar resolves `./a/b` by path inside the claimed tree.** A swap of `a` for
  a link would need a writer inside `.sweeping-<x>`. The fingerprint and inode
  re-checks around pack and remove catch it, and removal never follows it.

## Restore chmod (asked explicitly)

- `_move` fchmods only the staged root, through an `O_NOFOLLOW|O_DIRECTORY`
  descriptor. It cannot reach outside the tree.
- The mode applied is the archived root's mode, which for a packed entry is
  the original's own mode. Inner members get their archived modes through
  `--preserve-permissions`.
- Restore can recreate a world-writable or setgid mode only if the original
  had it. For a P6 (adopted) archive the mode comes from a user tarball, but
  adopt is unreachable today.
- `_empty_dir` and `_delete` only ADD owner bits (u+rwx / u+wx). They never
  make anything group- or world-writable.

## The caller's remaining items, one line each

- **Overlong names** (from reading the code, not run). A name whose
  `.sweeping-` form exceeds NAME_MAX makes renameat2 fail with ENAMETOOLONG,
  which becomes `ClaimRefused` (`scratch_archive_claim.py:327-330`). The
  outcome is `refused` and the entry is left in place.
- **`..`, `/`, NUL and absolute names.** `check_name` refuses each one. Names
  read from a directory listing cannot contain them anyway.
- **Newline and unicode names.** Names stay `str` with surrogateescape and
  are `fsencode`d back for every syscall and tar operand. tar reads them
  NUL-separated with `--verbatim-files-from`, `--no-wildcards` and
  `--no-unquote`. Side note (D-PUB/hygiene, not D-PATH): `_scratch_apply`
  prints `outcome.name` raw, so a newline in a name can forge a status line
  in the text output. `--json` is unaffected.
- **Spoofed `.restoring-` names.** `reclaim_staging` requires the exact
  `.restoring-<16 hex>` shape, a directory that is not a link, this user as
  owner and the store's device. Any other `.restoring-` name is `foreign` and
  untouched. Clean.
- **Spoofed `.sweeping-` names.** See F1.
- **The renameat2 fallback.** None. It refuses (see Verdict).
- **O_NOFOLLOW and O_NONBLOCK on FIFOs.**
  - The walkers' content reads (`read_small_regular_file`, the
    `scratch_repos.py` hash read) open with `O_NOFOLLOW|O_NONBLOCK` and
    require a regular file.
  - Pointer targets (`gitdir:`, `commondir`, alternates) are only mapped,
    lexically and by `realpath`; they are never opened
    (`scratch_sweep.py:409-415`).
  - The store's own files lack `O_NONBLOCK` (dismissed above).
  - adopt has `O_NONBLOCK`, but adopt is unreachable today.
- **flock on a replaceable path.** See the lock dismissal above.
- **Not checked:** whether the classifier's git subprocesses (`scratch_repos.py`)
  WRITE inside an entry (for example, an index refresh by `git status`). Any
  such write would land inside scratch, not outside it.
