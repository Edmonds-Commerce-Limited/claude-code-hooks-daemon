## Findings

### MAJOR 1: the gate's FROM version comes from the clone's checkout, so on three real routes it passes silently, even for a MAJOR target

`run_pre_deploy_phase` uses `CURRENT_VERSION`. That is Layer 1's `FROM_VERSION`
(the clone's `pyproject.toml`, preferring `HOOKS-DAEMON.md` only when that
marker is newer), or on a direct call the editable venv's import of the
checked-out source. Wherever the clone already sits on or past the target, the
range is empty and the gate says nothing. Task 1.2's own ruling calls this
exact failure ("the re-run would see an empty range and skip the gate that
stopped it") the reason for the restore, but the restore does not cover these
routes.

- **Fresh-clone client** (config committed, no checkout; origin `main` on the
  latest release). The first run exits 3, but `HOOKS_DAEMON_UPGRADE_PREVIOUS_REF`
  is the fresh clone's HEAD, which is already the target ("still on the previous
  ref"). The re-run with no flag reads FROM = `v3.67.0`, passes and deploys.
  Probe: `runs/freshclone/fresh1-noflag.log` (exit 3), `fresh2-noflag-rerun.log`
  (exit 0, "upgrading from v3.67.0 to v3.67.0"). With a MAJOR target the same
  sequence skips the owner's approval.
- **LLM-UPDATE "Manual Update"** (step 2 `git checkout "$LATEST_TAG"` in the
  clone, step 3 run the local Layer 1). A MAJOR upgrade with no flag and no
  approval exits 0 and deploys. Probe: `runs/manual/manual1-major-noflag-noapproval.log`
  ("Pre-deploy gate: what upgrading from v4.0.0 to v4.0.0 changes").
- **Direct Layer 2 on a clone already moved to the target** (the "just run it
  again" recovery). `CURRENT_VERSION` comes from the editable venv, which imports
  the target's `version.py`. Probe: `runs/direct/direct2-already-at-target.log`
  (exit 0, "from 3.67.0 to v3.67.0").

Fix direction: take the gate's FROM from what is actually INSTALLED rather than
from what is checked out. That is the venv's `.daemon-version` stamp
(`INSTALLED_VERSION`, already read before `ensure_venv`), then the
`HOOKS-DAEMON.md` marker, then `CURRENT_VERSION`. On all three routes the venv
stamp (or, for a fresh clone, the marker) still names the old release. For a
fresh clone, "restore" should mean removing the clone that Layer 1 created, or
resetting it to `v{marker}`, rather than resetting to the clone's own HEAD. Add
e2e cases for the fresh-clone and manual routes.

### MAJOR 2: under a pre-gate Layer 1, a stop exits 0, restores nothing and leaves a partial install

The shim's offline-recovery message runs the installed daemon's
`scripts/upgrade.sh`, and so does a pinned `HOOKS_DAEMON_UPGRADE_REF`. That Layer
1 still has the `if ! bash …; then LAYER2_EXIT=$?` bug and exports no
`PREVIOUS_REF`. Probe `runs/oldlayer1/`:

- `old1-noflag.log`: Layer 2 prints `UPGRADE STOPPED`, and Layer 1 **exits 0**.
  The clone is left on `v3.67.0` with the old editable venv and the old deployed
  hooks. The next hook event starts NEW source on OLD dependencies. The message
  claims "the daemon dir was already on v3.67.0 when this run started" and "the
  previous daemon starts again", and both are false.
- `old2-flag.log`: `ERR Unknown option: --skip-reading-confirmation`. The old
  Layer 1 cannot acknowledge.
- `old3-noflag-rerun.log`: the re-run passes silently (MAJOR 1).

Before this change the same route simply completed the upgrade, so this is a
regression on that route. Fix direction: when `PREVIOUS_REF` is absent but
`HOOKS_DAEMON_UPGRADE_PREVIOUS_VERSION` is present (the signature of an old
Layer 1), Layer 2 should restore on its own. The target is the venv stamp's tag,
or `v$HOOKS_DAEMON_UPGRADE_PREVIOUS_VERSION`. Layer 2 should also say plainly
that the caller's exit status will read 0. The shim's recovery text should
stop recommending the installed Layer 1 for a gated target.

### MAJOR 3: two already-published `breaking: true` manifests escalate every client on v3.64.x or earlier to exit 4, affected or not

`breaking_manifests` counts any crossed `config-changes/v*.yaml` with
`breaking: true`. The published tree has two: `v3.58.0.yaml` and `v3.65.0.yaml`.
The v3.65.0 one declares `removed: []`, `renamed: []`, `changed: []`. Those flags
were written before the flag meant "the owner must approve". Probe
(`probe_376_standalone`, project with no call sites, `--acknowledged`):
`3.64.1 -> 3.66.0` gives exit 4 on v3.65.0, `3.57.0 -> 3.66.0` gives exit 4 on
both, and `3.65.0 -> 3.66.0` gives exit 0.

On the first release that carries the gate, every agent-driven upgrade from
v3.64.x or earlier therefore stops for the owner. Those clients' installed
daemons have no `approve-upgrade`, so the owner must create the marker file by
hand. Neither the plan, notes 60/62 nor RELEASING.md mention this. Fix direction
is the owner's call before release. The options are: re-audit v3.65.0's flag;
key escalation on a new field that only manifests written from now on carry
(for example `requires_owner_approval: true`); or keep it and disclose it in the
release notes with the hand-marker procedure. Either way, RELEASING.md should
warn the release agent that `breaking: true` now halts fleet upgrades.

### MAJOR 4: nothing stops an agent from granting the owner's approval, or from skipping the gate entirely

Synthetic PreToolUse payloads against the worktree daemon (`payload.json`, all
**allowed**; the only output was the unrelated orchestrator-simulate notice):

- `.claude/hooks-daemon/bin/hooks-daemon approve-upgrade 4.0.0`
- `mkdir -p …/upgrade-approvals && touch …/upgrade-approvals/4.0.0.approved`
- `HOOKS_DAEMON_PRE_DEPLOY_PHASE_DONE=1 bash untracked/scratch/upgrade.sh …`

The third is the worst. The exported re-exec sentinel is also an undocumented
switch that turns the whole gate off. Probe
`runs/envbypass/envbypass-major-noflag-noapproval.log` shows a MAJOR upgrade
with no flag and no approval exiting 0 and deploying. "Human-only" is enforced
only by prose. `approve-merge` and `approve-plan-close` share the first two
properties (no handler denies the approve command itself), so this is the house
idiom, but the brief asked for it as a finding. Fix direction:

- Make the sentinel unforgeable: a nonce written to a file by the pass that ran
  the gate, checked by the second pass. Or drop it in favour of
  `HOOKS_DAEMON_UPGRADE_SECOND_PASS` plus that check.
- Add a PreToolUse guard that denies Bash running `approve-upgrade`, writing
  under `upgrade-approvals/`, or setting `HOOKS_DAEMON_PRE_DEPLOY_PHASE_DONE`.

### MINOR 1: a pre-gate Layer 2 run directly stops AFTER a full deploy and reports "Nothing was deployed"

`runs/oldlayer2/oldl2-direct-noflag.log` uses main's `upgrade_version.sh` as the
installed Layer 2, called directly. That is the route "older skill shims and
existing runbooks" use, per the script's own comment. The old first pass deploys
everything and restarts the daemon (lines 54 and 121). The re-exec'd second pass
runs the gate, which prints "UPGRADE STOPPED before anything was deployed … Nothing
was deployed" and exits 3 on a completed install. Fix: on
`HOOKS_DAEMON_UPGRADE_SECOND_PASS` without `HOOKS_DAEMON_PRE_DEPLOY_PHASE_DONE`
(the first pass had no gate), report rather than stop, or word the stop
truthfully.

### MINOR 2: an unknown range skips all detection and every escalation

When `release_tuple` fails (FROM `unknown`, for example a fresh clone with no
marker), the verdict is acknowledgement only. There is no scan for pre-upgrade
tasks, and neither a MAJOR target nor a `critical` task escalates. Probe: the
standalone run with `--from unknown --to 4.0.0 --acknowledged` exits 0. Fix: with
an unknown FROM, evaluate every pre-upgrade task up to the target, and require
approval (or treat the target's major as crossed).

### MINOR 3: the gate has no timeout, and a catastrophic Detect regex passes the schema

`schema_errors` only compiles the pattern. `(x+x+)+y` against one 29-character
line took 14.8 s (`probe_tasks.py` section 3), and each extra character doubles
that. `run_pre_deploy_phase` runs the gate with no `timeout`, so one bad pattern
and one long line in a client file hang every upgrade. The authors are daemon
maintainers, hence minor. Fix: wrap the gate in `timeout` (a timeout is a crash,
so it still stops), cap the scanned line length, and lint nested quantifiers
in the schema test.

### MINOR 4: the scanner's skip list is keyed on bare names, and the loader is laxer than the README

`_SKIP_DIR_NAMES` skips any directory named `venv` or `untracked` at any depth,
so `src/venv/x.sh` is never scanned. `vendor/`, `dist/`, `build/` and `target/`
ARE scanned, and a vendored copy that matches a `critical` task triggers owner
approval (`probe_tasks.py` sections 4 and 5). A `**Detect**` written without
backticks passes `schema_errors` and is used raw (section 2, case 03), although
the README says "one Python regular expression in backticks". Fix: anchor the
venv and untracked skips to known locations, skip common vendored/build roots
(or honour `.gitignore`), and make the schema require the backticks.

### MINOR 5: the shipped 00375 critical pattern is broader than the README's own example

`plan[-_]qa[^\n]*json` also matches `plan_qa.json` file names, as in this
repository's `scripts/qa/llm_qa.py:443`. The pre-upgrade README holds up
`plan-qa[^\n]*--json` as the good, narrow shape. Every false positive of a
`critical` task costs an owner approval. Fix: narrow the pattern to the
invocation (`plan[-_]qa\b[^\n]*--json`) unless there is a known caller that
needs the wider one.

### MINOR 6: the acknowledgement is not bound to what was listed

`--skip-reading-confirmation` on the FIRST run proceeds without ever stopping.
The skill's usage block lists it next to `--skip-config-optimisation` as an
ordinary flag. An agent that learns to always pass it turns the reading stop
back into the fall-through this plan removed. Escalations still hold. Fix
direction: have the stop print a short digest of the listing, and accept only
`--skip-reading-confirmation=<digest>`, or record an acknowledgement file on
the stop that the flag consumes.

### MINOR 7: the docs claim more than the code delivers

- Release note 60: "Every upgrade now runs a pre-deploy gate … It puts the
  daemon checkout back on your previous version". This is false on the MAJOR 1
  and 2 routes.
- Release note 56: "Both now run on every route". This is false on the Manual
  Update route.
- Release note 62: names only `hooks-daemon approve-upgrade <version>`. That is
  the command every client's installed daemon lacks on its first gated upgrade,
  because the stop restores the old daemon. The hand-created marker fallback
  (which LLM-UPDATE and the stop message do give) belongs here. MAJOR 3's blast
  radius belongs here too.
- `CLAUDE/LLM-UPDATE.md` still says Layer 1 "Delegates to Layer 2 via `exec`".
  Layer 2 is a child process, and that is exactly why the exit-code fix was
  needed.

RELEASING.md step 6 (the pre-upgrade move, checklist and summary) is accurate.

### NIT 1

`upgrade.md` advertises `/hooks-daemon upgrade --force # reinstall current`, and
the new step 6 says "skip only on a `--force` reinstall". Layer 1 rejects
`--force` (`ERR Unknown option: --force`, exit 1, checked against the worktree's
`scripts/upgrade.sh`). The flag line is older than this change, but the new text
relies on it.

### NIT 2

Layer 1's `ERR Unknown option` usage line and the skill shim's `--help` still
list only `VERSION`, without `--skip-reading-confirmation`.

### NIT 3

A branch install re-run on the same commit always stops with exit 3
(`runs/branch/branch-flag-rerun-same-commit.log`). Ruling (a) implies this, but
an idempotent re-run (the install stamp equals the venv stamp) could pass.

### NIT 4

A task whose scan could not run (missing or invalid `**Detect**`) is listed as
applicable, correctly failing closed, but with no line saying the scan did not
run (`format_findings_line` prints nothing for `applies is None`).

### NIT 5

The approval is consumed before `ensure_venv`. A later failure on the direct
slow path rolls back, and the owner has to approve again.

### NIT 6

`_BREAKING_RE` matches only a lowercase `true` at column 0. The YAML spellings
`breaking: yes` and `breaking: True` are missed, although no current manifest
uses them.

## Verdict

**Not ready to merge.** The main Layer 1 route works as specified, and I
verified it end to end: stops, restore, re-run, TTY independence, approval
consumed once, crash stops the upgrade, exit codes propagate, stdlib-only on
3.11. The four majors are the problem. The gate fails open on three documented
or recovery routes, and the Task 1.2 decision exists to prevent exactly that. A
pre-gate Layer 1 turns a stop into an exit-0 partial install. Published
manifests make the first gated release stop every client on v3.64.x or earlier
for the owner, and nobody has disclosed that. The owner's approval, and the
whole gate, can be bypassed by an agent with one environment variable. MAJOR 1,
2 and 4 are code fixes with a shared root (derive FROM from the installed
version; make the sentinel unforgeable). MAJOR 3 needs an owner decision before
this ships in a release.
