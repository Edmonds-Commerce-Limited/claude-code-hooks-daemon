## BLOCKER 1: missing stamp + edited `HOOKS-DAEMON.md` makes FROM == TO, and a MAJOR deploys with no approval

**Observed** (`probe_376r2_e2e_rerun.txt`, scenario `docmarker`; log
`probe_376r_runs/docmarker/1-major-noflag-doc-forged.log`). Setup: v3.66.0
installed; the venv's `.daemon-version` removed; the project's
`.claude/HOOKS-DAEMON.md` marker changed to `(v4.0.0)`; then a plain
`upgrade … v4.0.0`. Result: `exit=0`, `head=v4.0.0`, `deployed=True`, no stop,
no reading, no approval. Log `:34`: `Installed version: 4.0.0 (from the .claude/HOOKS-DAEMON.md)`. Log `:6`: Layer 1 knew better (`Installed clone is v3.66.0 but this project's tracked assets were deployed from v4.0.0; using the tracked version as the upgrade FROM side`).

**Not a regression.** Review-1's own `probe_376r_e2e_out.txt:16-19` shows the
same exit 0 and deploy. Review-1 then filed it under "What holds" as "makes the
gate STRICTER". That was a misread, so the defect has been live since before
review-1.

**Root cause.**

- `installed_version()` (`upgrade_gate.py:198-205`) falls back to the doc
  marker whenever the stamp is missing.
- The new receipt check (`upgrade_gate.py:566-583`) is guarded by
  `installed_stamp == target_stamp`, so it never sees a doc-derived FROM.
- FROM == TO gives an empty range: no guides, no tasks, no MAJOR escalation,
  so the gate proceeds.
- Layer 1 prefers the tracked doc over the clone's pre-checkout version
  (`upgrade.sh:426`).

**Reachability.** Both preconditions are allowed by the guard
(`probe_376r2_guard_rerun.txt`: `stamp rm` allow, `venv mv aside` allow,
`Write HOOKS-DAEMON.md` allow). `HOOKS-DAEMON.md` is an ordinary tracked
project file an agent edits routinely. This is the same failure the plan's goal
and review-1's BLOCKER 1 are about: a non-interactive agent deploys a MAJOR and
the owner is never asked.

**Directions** (the first closes it; the others are defence in depth):

1. Apply the MAJOR 1 rule to every FROM source. Whenever the resolved FROM is
   > = the target and the source is not a stamp backed by a matching
   > `gated-install.json`, treat the range as unknown and send it to the owner.
2. Use the doc marker only to widen the range, never to narrow it. Layer 1
   already hands over `_PREVIOUS_REF`. FROM should be the lower of
   (stamp or doc) and the pre-checkout clone release. A doc claiming a version
   newer than the clone is evidence of tampering or drift, not a shortcut.
3. Add a RED test: stamp absent, doc marker == target, clone on an older tag
   → exit 3 or 4, nothing deployed.

The docs currently state the opposite of this behaviour:

- `LLM-UPDATE.md:208-211` ("a fresh clone, a manual checkout and a re-run
  therefore all see the real range");
- release note `60-…md:20`.

## MAJOR 1: "Nothing in the caller's environment steers the gate" overstates what was built

`LLM-UPDATE.md:215` and PLAN.md decision (e) (`PLAN.md:341-346`) say the gate
no longer depends on the caller's environment, so Layer 1 need not be
re-launched clean. That is true of the **gate subprocess** (`env -i`, `-I -S`,
fixed PATH; confirmed: the gate ran on `/usr/bin/python3.11` in every rerun
scenario). It is not true of the **process that reads the verdict and
deploys**. Layer 2 is started as `bash "$LAYER2_SCRIPT"` (`upgrade.sh:721`),
with `bash` resolved from the caller's `PATH` and the caller's full environment
inherited. It then trusts its own shell state to parse the verdict file
(`upgrade_version.sh:462-485`).

So beyond the gate subprocess, the only barrier against a steered Layer 1 or
Layer 2 is `upgrade_approval_guard`'s recognition of the command. That
recognition is heuristic by construction (code reading,
`upgrade_approval_guard.py:300-420`):

- it parses shell segments, the `_SHELL_HEADS` shells and the
  `_WRAPPER_HEADS` wrappers;
- a launch through any other program, or a steering variable set in an earlier
  tool call rather than on the same command, is outside what it parses.

This does not reopen review-1's BLOCKER 1. That exact route is now denied and,
independently, the gate no longer resolves its tools from `PATH`. But the docs
assert a guarantee the design does not provide.

**Directions:**

- Scope the sentence to the gate subprocess, and state the threat model
  plainly: the approval gate is a procedural control against an agent following
  the documented route, backed by a best-effort guard. It is not a boundary
  against a same-user process determined to install by hand, which no
  in-process check can be.
- Optionally narrow the gap cheaply: have Layer 1 start Layer 2 through
  `/usr/bin/env -i` with an explicit allowlist and `/bin/bash --noprofile --norc`. The allowlist would carry the handoff path, `UPGRADE_FLAGS`,
  `HOOKS_DAEMON_PYTHON` for the venv build, proxy variables, `HOME` and `LANG`.
  This keeps what decision (e) wanted to preserve and removes the inherited
  shell environment from the deploying process. Layer 1 itself stays exposed,
  which is inherent.

## MAJOR 2: GATE_SAFE_PATH is trusted without checking who can write it

`GATE_SAFE_PATH` (`upgrade_version.sh:222`) and `TRUSTED_TOOL_PATH`
(`upgrade_tasks.py:131`) are fixed strings. `_gate_tool` (`:226-236`) and
`find_latest_python` under that `PATH` accept the first executable found, with
no ownership or mode check. Code reading plus host facts:

- On macOS with Homebrew, `/opt/homebrew/bin` (Apple Silicon) and
  `/usr/local/bin` (Intel) are owned by the user by default. That is the same
  user an agent runs as. The gate's Python would typically come from there.
- In this project's own container the agent is `uid=0` (`id` → `root`), so
  every listed directory is agent-writable. On this host
  `/usr/bin`, `/usr/sbin` and `/usr/local/bin` are `root:root 755`, and `/bin`
  and `/sbin` are symlinks to them.

So "a fixed system location" stops a caller-supplied `PATH`, which was
review-1's finding. It does not stop a tool placed in a listed directory, which
needs no environment variable and so never reaches the guard.

**Directions:**

- Accept a directory, and the resolved binary, only if it is root-owned and
  not group- or world-writable. Skip it otherwise, and fail closed if nothing
  qualifies.
- Say in LLM-UPDATE that a Homebrew-only Python needs the user.
- Record the resolved interpreter and `timeout` paths in the verdict file and
  `gated-install.json`, so an audit can see what answered.
- State that an agent running as root is outside what the gate can defend.

## MINOR

- **M1 — verdict file placement and nonce visibility (code reading).**
  `mktemp -d` (`upgrade_version.sh:424`) honours an inherited `TMPDIR`. The
  guard denies `TMPDIR` only on the same command as the upgrade. The nonce
  travels on the gate's argv (`:442`), readable by any same-uid process via
  `/proc`. The O_EXCL/0600 file with the `-f`/`! -L`/`-O` checks
  (`upgrade_gate.py:820-825`, `upgrade_version.sh:462`) defeats a stale or
  replayed file. That is what it is for. It does not authenticate against a
  concurrent same-user process, and the docs' "a wrapper … cannot pass for the
  gate" (`LLM-UPDATE.md:229-231`) should say "a stdout-printing wrapper".
  Direction: `mktemp -d -p /tmp` (or a directory under the daemon's own
  untracked dir) instead of `$TMPDIR`; pass the nonce on an inherited file
  descriptor or stdin rather than argv.
- **M2 — the clone's persistent config is outside route 5 (code reading).**
  `_HEAD_MOVING_GIT_SUBCOMMANDS` (`upgrade_approval_guard.py:207-209`) covers
  ref moves, not `remote`/`config` writes on `.claude/hooks-daemon`. Layer 1's
  `fetch --tags --force` (`upgrade.sh:541`) correctly resets locally re-pointed
  tags, but only to whatever `origin` names. The gate code that runs is the
  target's own (`upgrade_version.sh:410`), so the origin URL decides which gate
  runs. Direction: add clone `remote`/`config` writes to route 5, and/or have
  Layer 1 compare `origin`'s URL with the canonical one (the same value
  `HOOKS_DAEMON_CLONE_URL` would override, which the guard already treats as
  steering) before fetching.
- **M3 — the receipt is exactly as strong as a marker.** `gated-install.json`
  is unsigned JSON with no FROM version, protected only by the
  `upgrade-approvals/` path predicate (`upgrade_approval_guard.py:480-481`).
  The rerun shows that predicate's known gaps are unchanged (`marker via variable dir`, `marker via tar -x`: allow). This is no new class, since a
  forged marker already grants approval. The docs call it what "the gate itself
  recorded", which is fine, but it should not be cited as proof in future
  reasoning (see BLOCKER 1 direction 1, which should not rely on it alone).
- **M4 (review-1 D8, not fixed).** `upgrade-template/README.md:405-409`
  (rollback Option A) still instructs `cd .claude/hooks-daemon` then
  `git checkout vX.Y`. That is now denied twice: by R-DAEMON-DIR-CD and by
  this branch's route 5, which treats a `git checkout` after a `cd` into the
  clone as moving it. Lines `:29`, `:34` and the other `cd` sites have the same
  problem. Every future guide is copied from this template.
