## MAJOR 1: `_script_carries_the_upgrade` is the N29 shape, and it fails OPEN

`upgrade_approval_guard.py:359-368` assigns `content = None` in the handler and
returns `None` after it. That is exactly the evasion Plan 00466 N29 records.
Behaviour is unchanged by the commit, but this is a security guard, and `None`
does not mean "deny". It means "judge by argument shape" (`_script_run_is_upgrade`,
`:371-386`). Arguments passed through variables have no shape.

**Observed:**

- `probe_376r3_guard_steered_out.txt`: `PATH=/x:$PATH bash <Layer 2 copy>` is DENY
  when the script is readable. When the read fails it is **allow**.

- `probe_376r3_guard_steered2_out.txt`: with `BASH_ENV=/x/evil.sh` and the
  arguments in `"$p" "$d" "$v"`, readable is DENY and read failing is **allow**.
  This includes the non-root dance `chmod 644 copy && BASH_ENV=… bash copy …`
  run on a file that was mode 000 at guard time.

- As root, `open()` never fails on mode 000 (`uid=0 chmod 000 -> True`). But the
  same fallback is reached with no mocking at all
  (`probe_376r3_guard_steered3_out.txt`, all **allow** with
  `BASH_ENV=/x/e.sh` and variable arguments):

  - `bash /dev/stdin … < copy`;
  - `bash <(cat copy) …`;
  - `cat copy | bash -s …`;
  - `s=copy; bash "$s" …`.

  The control, with literal arguments, is DENY.

**Why it matters:** `BASH_ENV` runs inside Layer 2 before `_sanitise_layer2_env`
(MAJOR 2). The guard's same-command steering deny is the only barrier, and
release note 67 claims it "recognises the upgrade however its script is named".

**Direction:** fail closed. A shell run whose script the guard cannot read or
resolve should count as an upgrade when the same command carries a steering
assignment, export or function export. That covers:

- a read failure;
- a `$`-path;
- `/dev/stdin`, `/dev/fd/*`, `<(…)`;
- `-s` or stdin.

Keep the argument heuristic only for the unsteered case. Also add a RED test
for each of the four steered3 shapes.

## MAJOR 2: the trusted-bash launch closes PATH only; `BASH_ENV` and `BASH_FUNC_*` still reach Layer 2

`probe_376r3_layer1_out.txt`:

| Scenario                                                       | Result                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| hostile `bash` first on PATH                                   | **held**: Layer 2 on `/usr/bin/bash`, nothing hostile ran                                                                                                                                                                                                                                           |
| `ENV=evil`                                                     | **held**: bash is not in posix mode                                                                                                                                                                                                                                                                 |
| exported `_gate_tool` only                                     | **held**: the drop loop removed it                                                                                                                                                                                                                                                                  |
| `BASH_ENV=evil`                                                | **ran in Layer 1 and again in Layer 2** (`$0=…/upgrade_version.sh BASH=/usr/bin/bash`)                                                                                                                                                                                                              |
| exported `unset` (a no-op function)                            | **defeats the drop loop in both layers** (`upgrade.sh:26-28`, `upgrade_version.sh:29-31`). It also neuters `_sanitise_layer2_env`: the hostile `unset` received `-v BASH_ENV ENV CDPATH GLOBIGNORE NODE_OPTIONS` and `-v GIT_EDITOR`, so the `GIT_*`/`PYTHON*`/`LD_*` families survive into Layer 2 |
| exported `unset` + `source`                                    | hostile `source` runs inside Layer 2 on every library it loads                                                                                                                                                                                                                                      |
| `ENV_SANITISE_SH_LOADED=1` + exported `unset` and `_gate_tool` | **Layer 1 launches the PATH-planted bash** (`PATH-bash argv=…upgrade_version.sh …`). The inherited include guard skips the file, so the imported `_gate_tool` answers                                                                                                                               |
| `ENV_SANITISE_SH_LOADED=1` alone                               | fails closed (exit 1), but with a misleading "No trusted bash found"                                                                                                                                                                                                                                |

**Scope, stated fairly:**

- Every one of these also runs code in Layer 1 first. They are therefore no new
  capability over a caller who already controls Layer 1, and this review does
  not rank them as a blocker.
- The guard denies the same-command forms: `BASH_ENV` prefix/export,
  `env 'BASH_FUNC_unset%%=…'` and `export -f` are all DENY
  (`probe_376r3_guard_out.txt`).
- The persistent forms are all **allow**, and they reach every later Bash call:
  `echo 'export BASH_ENV=…' >> ~/.bashrc`, the same for `PATH`, and an exported
  function in `.bashrc`.

**What is wrong today is the claims:**

- `PLAN.md:317-320` decision (b): "Layer 1 and Layer 2 drop every imported
  shell function before anything runs". This is false against an imported
  `unset`, and no in-bash loop can make it true, since any builtin, including
  `builtin`, can be shadowed.
- LLM-UPDATE `:261-271` and decision (e) present the trusted bash as closing the
  "what launches Layer 2" gap. It closes PATH only.

**Direction:**

- Launch Layer 2 through the trusted `env`, which is already resolved by
  `_gate_tool env`. Drop `BASH_ENV`, `ENV` and every `BASH_FUNC_*` at minimum
  (`env -u …`), or use review-2's `env -i` allowlist. This is the only way to
  stop function import, because the importing shell cannot undo it.
- Ignore an inherited `ENV_SANITISE_SH_LOADED`: unset it before `source`, or key
  the guard on a non-exported variable.
- Correct decision (b) and LLM-UPDATE to say Layer 1 is caller-controlled by
  construction, and that persistent profile changes (`~/.bashrc`) are outside
  the guard.
