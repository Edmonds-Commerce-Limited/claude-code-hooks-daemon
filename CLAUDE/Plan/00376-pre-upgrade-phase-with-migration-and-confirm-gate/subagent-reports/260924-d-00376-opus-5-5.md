## Per-task outcomes

### Task 4.3 — fixed

The defect was in three places, not one:

1. `upgrade.md` reached post-upgrade tasks only through the step 5
   migration-Note clause.
2. `scripts/upgrade.sh` printed truth-changes and config-changes summaries
   but never the tasks.
3. The "MANDATORY" tasks section in `CLAUDE/LLM-UPDATE.md` sat under "Upgrade
   Path Determination", which only the manual sequential path reaches. Its
   glob also listed every guide ever shipped, not the ones crossed.

The fix:

- `src/claude_code_hooks_daemon/install/upgrade_guides.py` is a new resolver.
  It finds every `v{A}-to-v{B}` guide directory under any `v{major}/` in
  `(from, to]`, reads the tasks, and adds `UNRELEASED/` tasks for a branch
  install (`None` asks the install stamp).
- `hooks-daemon check-post-upgrade-tasks --from --to` is a new command. It
  exits 0 when there are no tasks, 1 when there are tasks, and 2 on a bad
  range, the same as `check-truth-changes`.
- `upgrade.md` has a new **mandatory step 6** (the old steps 6-8 are now
  7-9, and every reference is renumbered). The dogfood copy under
  `.claude/skills/` is kept identical.
- `LLM-UPDATE.md` has a new section, "Post-Update: Carry Out Post-Upgrade
  Tasks (MANDATORY)". The old subsection now points to it.
- `scripts/upgrade.sh` prints the list before the metadata block.

Tests:

- `tests/integration/test_post_upgrade_tasks_are_reachable.py` checks that
  the skill has exactly one numbered, mandatory step that runs the command,
  that `LLM-UPDATE` runs it in a mandatory Post-Update section, and that
  Layer 1 runs it before the sentinel. It also checks that every task file on
  disk is listed for an upgrade that crosses it. That covers 13 released
  tasks plus the UNRELEASED `01-remove-vendor-...` task this release ships.
- RED at HEAD, checked with the same helpers against `git show HEAD:` for
  each file: no skill step ran the command, no `LLM-UPDATE` section did, and
  Layer 1 never ran it.
- Unit tests are in `tests/unit/install/test_upgrade_guides.py` and
  `tests/unit/daemon/test_cli_check_post_upgrade_tasks.py`.

### Task 4.2 — fixed

I reproduced it on the real tree before changing anything.
`CompatibilityChecker("3.62.1", "3.66.0").suggest_upgrade_guides(repo)`
returned `[]`, although that range crosses three main guides. The function
had two problems:

- It matched only `v{M}.{m}-to-v{M}.{m+1}` names inside `v{target_major}/`,
  so 9 of the 14 v3 guide directories were invisible. That covers every
  patch-numbered guide and `v2.32-to-v3.0`, whose guide is a README.
- It never read `UNRELEASED/`.

It now resolves guides through `upgrade_guides`, falls back to `README.md`,
and appends every staged `UNRELEASED/` document (not READMEs) when
`include_unreleased` holds.

Tests: `TestSuggestUpgradeGuidesSeesTheWholeTree` in
`tests/unit/install/test_upgrade_compatibility.py` has five tests, all RED
before the fix.

### Task 1.1 — fixed (the defect found while doing 4.2)

**The defect.** On the supported route, the Layer 2 compat check and the
Step 5a reading list never ran. Layer 1 checks the target out before it
calls Layer 2, so the "already at target" test was always true, and the
idempotent path exited before both. Invoked directly, both read the
pre-checkout tree, which holds no guide for the version being installed.

**RED first.** `tests/integration/test_upgrade_pre_deploy_phase_runs_on_layer1.py`
(marked `slow`, needs `uv`) builds a scratch daemon origin from the working
tree:

- tag `v{current}`;
- tag `v{next minor}`, which adds a guide and a post-upgrade task;
- a branch off `v{current}` that stages an `UNRELEASED/` task.

It installs nothing ahead of time. It runs the working tree's real Layer 1
against a project whose clone sits on `v{current}`, once as a release
upgrade and once as a branch install. On the old scripts both upgrades
succeeded and "Checking config compatibility" never appeared. After the fix
both pass (about 60s together). The test checks that:

- the check and the list come before "Deploying hooks to project";
- the list names the target's guide, and names the staged task only on the
  branch route;
- the post-upgrade list names the guide's task and the staged task.

**The fix: the smallest move that covers every route.**

- The check and the list now live in one function, `run_pre_deploy_phase`,
  in `scripts/upgrade_version.sh`. It is called in two places:

  - on the idempotent path, right after the target's venv verifies (every
    Layer 1 upgrade);
  - on the direct path, after Step 7.

  On both, that is before the first deploy.

- FROM is `CURRENT_VERSION`, which Layer 1 hands over. TARGET is the release
  part of `INSTALL_STAMP`, so a branch install uses its pyproject version.
  `include_unreleased` comes from `BRANCH_INSTALL_STATE`, not from the stamp
  of the running venv.

- An exported sentinel stops a direct call's second pass from running it
  twice.

- The old pre-checkout blocks are removed, with pointer comments in their
  place.

- `tests/integration/test_upgrade_pre_deploy_phase_placement.py` pins the
  placement cheaply, so it still runs when slow tests are deselected. It was
  RED against HEAD.

- Two line-keyed error-hiding exclusions moved with the code and were
  realigned: 514 to 641, and 876 to 796.

**A design decision you may want to reverse: the phase reports, it does not
block.** The removed pre-checkout check ran `fail_fast` on incompatibility
unless `--force` was given. I did not carry that over, for three reasons:

- On the idempotent path an abort lands after the checkout and the venv
  rebuild, and what that must undo is Task 1.2, which is still open.
- The gate that acts on this report is Phase 3, which I was told not to
  build.
- A check that has not run on the real route for many releases would start
  blocking every upgrade whose config has a key the target no longer
  registers.

For the same reasons the interactive "have you read the guides?" prompt is
removed, not moved. It could never fire, because it read the old tree.
Task 3.1 now names `run_pre_deploy_phase` as the gate's site.
`upgrade_version.sh` still ignores `--skip-reading-confirmation` without
error. If you want blocking now, it is one `fail_fast` in the function, but
it needs a Task 1.2 answer first.
