## Per-task outcomes

### Task 4.3 — fixed

The defect was in three places, not one:

1. `upgrade.md` reached post-upgrade tasks only through the step 5
   migration-Note clause.
2. `scripts/upgrade.sh` printed truth-changes and config-changes summaries
   but never the tasks.
3. The "MANDATORY" tasks section in `CLAUDE/LLM-UPDATE.md` sat under "Upgrade
   Path Determination", which only the manual sequential path reaches. Its
   glob also listed every guide ever shipped, not the ones crossed.

The fix:

- `src/claude_code_hooks_daemon/install/upgrade_guides.py` is a new resolver.
  It finds every `v{A}-to-v{B}` guide directory under any `v{major}/` in
  `(from, to]`, reads the tasks, and adds `UNRELEASED/` tasks for a branch
  install (`None` asks the install stamp).
- `hooks-daemon check-post-upgrade-tasks --from --to` is a new command. It
  exits 0 when there are no tasks, 1 when there are tasks, and 2 on a bad
  range, the same as `check-truth-changes`.
- `upgrade.md` has a new **mandatory step 6** (the old steps 6-8 are now
  7-9, and every reference is renumbered). The dogfood copy under
  `.claude/skills/` is kept identical.
- `LLM-UPDATE.md` has a new section, "Post-Update: Carry Out Post-Upgrade
  Tasks (MANDATORY)". The old subsection now points to it.
- `scripts/upgrade.sh` prints the list before the metadata block.

Tests:

- `tests/integration/test_post_upgrade_tasks_are_reachable.py` checks that
  the skill has exactly one numbered, mandatory step that runs the command,
  that `LLM-UPDATE` runs it in a mandatory Post-Update section, and that
  Layer 1 runs it before the sentinel. It also checks that every task file on
  disk is listed for an upgrade that crosses it. That covers 13 released
  tasks plus the UNRELEASED `01-remove-vendor-...` task this release ships.
- RED at HEAD, checked with the same helpers against `git show HEAD:` for
  each file: no skill step ran the command, no `LLM-UPDATE` section did, and
  Layer 1 never ran it.
- Unit tests are in `tests/unit/install/test_upgrade_guides.py` and
  `tests/unit/daemon/test_cli_check_post_upgrade_tasks.py`.

### Task 4.2 — fixed

I reproduced it on the real tree before changing anything.
`CompatibilityChecker("3.62.1", "3.66.0").suggest_upgrade_guides(repo)`
returned `[]`, although that range crosses three main guides. The function
had two problems:

- It matched only `v{M}.{m}-to-v{M}.{m+1}` names inside `v{target_major}/`,
  so 9 of the 14 v3 guide directories were invisible. That covers every
  patch-numbered guide and `v2.32-to-v3.0`, whose guide is a README.
- It never read `UNRELEASED/`.

It now resolves guides through `upgrade_guides`, falls back to `README.md`,
and appends every staged `UNRELEASED/` document (not READMEs) when
`include_unreleased` holds.

Tests: `TestSuggestUpgradeGuidesSeesTheWholeTree` in
`tests/unit/install/test_upgrade_compatibility.py` has five tests, all RED
before the fix.

## Finding that reshapes Task 1.1 (not fixed; it is the feature)

On the supported route, the Layer 2 compat check and the Step 5a reading list
never run. Layer 1 checks the target out before it calls Layer 2, so the
"already at target" test at `scripts/upgrade_version.sh:339` is always true,
and the idempotent path exits at `:509`, before `:511+`. Invoked directly,
both read the pre-checkout tree, which holds no guide for the version being
installed. So Task 4.2's module fix is correct and tested, but its only
caller is unreachable until Task 1.1 moves the phase. When Task 1.1 moves
it, it must pass `include_unreleased` from `BRANCH_INSTALL_STATE`: the venv
running at that point belongs to the previous install. This is recorded in
PLAN.md under Task 1.1, and callout 56 says it plainly.
