## 12:47 · decision · — — owner ruled against deprecation windows

The owner's words: "i dont like delay - its over complex … lets have proper
semver and lets have a pre upgrade process so agents can properly understand
what is going to happen and what they need to do, and also give them ability to
confirm (with owner if needs be) that the upgrade should proceed."

The reasoning that survived scrutiny, recorded because a future agent will be
tempted to reintroduce a window as "the safe option":

- A window substitutes for being unable to reach your consumers. This daemon IS
  installed inside the consumer's repository and upgraded by an agent with
  write access to it, so the substitute is strictly worse than the thing it
  substitutes for.
- For a rename specifically, a window makes the defect — two live names for one
  concept — correct by policy for a release, and invites a new reader to key on
  the spelling about to disappear. It ADDS a failure mode.
- It does not avoid the break. Under `CLAUDE/development/RELEASING.md:966`
  ("Breaking API changes, removed features" = MAJOR) the version owed is the
  same whenever the removal lands. The window buys delay and nothing else.

## 12:48 · finding · P1 — the existing gate is inert, and three surfaces are broken

Surveyed the upgrade pipeline before designing. The gap is not documentation:
the machinery is missing, and what looks like a gate does not fire.

- `scripts/upgrade_version.sh:733-861` — Step 5a prints "REQUIRED READING" and
  asks yes/no, but `:808` tests `[ ! -t 0 ]` and falls through at `:814` to
  "Review upgrade guides after upgrade". **Every agent-driven upgrade takes
  that branch.** The gate protects a human at a terminal and nobody else.
- It would not be pre-install regardless: `scripts/upgrade.sh:550` checks the
  new version out, then delegates to Layer 2 at `:608-629`. Step 5a runs with
  the new code already on disk.
- `CLAUDE/UPGRADES/UNRELEASED/post-upgrade-tasks/README.md:20` — "There is no
  runner. Nothing executes these tasks automatically." Nothing in the upgrade
  path reads the directory, `.claude/skills/hooks-daemon/upgrade.md` never
  mentions it, and it has no schema test (contrast
  `tests/integration/test_pending_release_notes_holding_area.py`). Plans are
  REQUIRED to write there as part of their definition of done, and those files
  are read by nobody.
- `install/upgrade_compatibility.py:351-373` scans only
  `CLAUDE/UPGRADES/v{major}/`, never `UNRELEASED/`.
- The only thing that scans the project at all is `check-worktree-seed`
  (`scripts/upgrade.sh:870-891`); it reports and never writes. There is no
  "this project uses X" detection anywhere.

Takeaway shaping the plan: Phase 4 exists because a surface plans are obliged
to feed and nothing reads is worse than no surface — it manufactures the
appearance of a safety net.

## 12:49 · thought · T1.1 — the bootstrapping constraint is why this does not already exist

Pre-upgrade instructions ship WITH the incoming version but must run BEFORE it
is installed. `post-upgrade-tasks/` has no such problem, which is the most
likely reason it exists and a pre-upgrade peer does not. Task 1.1 is that
problem, and it should be settled before any of the surface is built —
constructing `pre-upgrade-tasks/` first and then discovering it cannot be read
in time would waste the whole phase.
