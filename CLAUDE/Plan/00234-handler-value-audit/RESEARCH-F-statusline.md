### git_branch cache-miss-rate derivation (the headline number)

Render-TTL is `2.0s` (`_DEFAULT_RENDER_TTL_SECONDS`, `git_branch.py:71`); the measured render interval is `~1.15s`. Because `1.15s < 2.0s < 2×1.15s (2.30s)`, the cache provably settles into an exact **alternating hit/miss steady state**: a miss at render `k` caches at `t_k`; the next render (`t_k + 1.15`) is within the 2.0s window (hit, cache untouched); the render after that (`t_k + 2.30`) exceeds the 2.0s window (miss, cache refreshed) — and the cycle repeats. That is a **50% miss rate**, not an occasional one.

Applied to the measured count: **3,383 renders in 65 minutes ⇒ ~1,691 cache misses ⇒ up to 4 git subprocess spawns per miss ⇒ ~6,700 git subprocess spawns in the same 65-minute window (~6,200/hour)** — from this ONE handler. That is very likely the single largest source of subprocess-spawn load anywhere in this cohort's enabled set, and plausibly in the daemon's whole `status_line` chain, given every other handler in the cohort spawns 0 subprocesses per render. This is a sharper, quantified version of what the original dossier flagged qualitatively as "up to 4 spawns on a cache miss."

**`daemon_stats` — explicitly checked and cleared on subprocess grounds**: confirmed **0 subprocess spawns/render**. `psutil.Process().memory_info()` reads `/proc/<pid>/stat` directly via the OS, it does not fork/exec a `ps` or similar external tool. `get_controller().get_stats()` and `get_data_layer().history.count_blocks()` are both in-memory (`controller.py:828-834`, `handler_history.py:126-132`). The only real per-render cost is the internal `/proc` read `psutil` performs, which is cheap kernel I/O, not a process spawn. Named by the team lead as one to check first — it checks out cheap.

## multithread_indicator

1. **CLAIM**: shows this thread's rank (`🧵 Y/X`) among live Claude Code sessions sharing one daemon — answers "which backgrounded thread am I looking at" (Agent View has no field for this itself).
2. **RENDER COST**: 0 subprocess. Every render, unconditionally, no cache: 1 write (`upsert_heartbeat` — reads prior heartbeat file if present [1 read], writes tmp, `Path.replace()`) + 1 directory scan (`read_live_entries` iterates `registry_dir`, one JSON read per live entry, N ≈ 1-2 typical — agent/subagent sessions are excluded from N entirely, `agent_type` truthy → no heartbeat written) — `multithread_indicator.py:106-117`, `thread_registry.py:73-154`. At the measured ~3,130 renders/hour this is ~3,130 read-modify-write cycles/hour, bounded by small N but genuinely uncached (no TTL, no mtime-gate — every render re-does the full scan even if nothing changed).
3. **WIDTH**: 0 when alone (the common case — silent), else `🧵 Y/X` ≈ 8 cols, prefixed `| `.
4. **STALENESS RISK**: reads its own registry (not a foreign sidecar); entries aged out after 45s (`_FRESH_WINDOW_S`, `thread_registry.py:55`) so a closed thread's stale entry self-heals within one window. Fail-open on any I/O error → silent (`multithread_indicator.py:118-123`).
5. **DUPLICATION**: none — no other segment shows thread count.
6. **CONFIG**: enabled, priority 2 (first segment) — `.claude/hooks-daemon.yaml`.
7. **HISTORY**: Plan 00158, 2 commits (`64a91dd4`, `1c75c2b9`) — introduced specifically to fix a Agent-View ambiguity bug (Truth #1/#5 in the module docstring), not speculative.
8. **CONSUMER**: n/a (self-contained; writer and reader are the same handler across sessions).

**SIGNAL: KEEP** — cheap in absolute terms (bounded by small N), self-limiting (silent when alone), fixes a real documented UX gap. The uncached-every-render pattern is real but low-severity given the small, bounded registry size.

**SIGNAL: KEEP** — zero display cost, confirmed consumer, opt-in by design, write cost is small and unavoidable given the sensor's job.

## git_branch

1. **CLAIM**: current git branch + magicmonty-style ahead/behind/staged/changed/conflict/untracked/stash icons, plus worktree marker.
2. **RENDER COST**: **heaviest handler in the cohort, and quantified sharper by the live firing data.** On a cache miss: up to 4 subprocess spawns per render — `git rev-parse --show-toplevel` (`git_branch.py:175-181`), `git branch --show-current` (`193-199`), `git status --porcelain=v2 --branch` (`380-386`), `git stash list` (`492-498`) — plus a conditional 5th (`git symbolic-ref`/`show-ref` for default-branch detection, cached per-repo after first call, `340-362`), plus 1 filesystem read for worktree detection (`.git` file). Mitigations: a 2.0s render-TTL cache keyed by cwd (`_DEFAULT_RENDER_TTL_SECONDS`, `git_branch.py:71`, `139-166`) and a 300s background-fetch TTL run in a daemon thread off the render path (`_DEFAULT_FETCH_INTERVAL_SECONDS`, `64`, `269-330`).
   **Cache-miss-rate derivation (new, from the live render interval)**: the measured render interval is ~1.15s; the render-TTL is 2.0s. Since `1.15s < 2.0s < 2×1.15s`, the cache provably settles into an exact alternating hit/miss steady state — a **50% miss rate**, not an occasional one. Applied to the measured 3,383 renders/65min: **~1,691 misses ⇒ ~6,700 git subprocess spawns in that same 65-minute window (~6,200/hour)**, from this ONE handler — see the "Per-handler I/O counts" section above for the full derivation. Without the TTL cache this would be ~4× higher (~13,500/hour); the cache is real and load-bearing, but it is only cutting the cost in half, not eliminating it, because the TTL sits just inside one render-interval "notch" above the render rate.
3. **WIDTH**: variable, ~10 (short branch, clean) to 45+ cols with a long branch name and several non-zero icon counts (`| ⎇ 🌳 feature/some-long-branch-name ↑2 ↓1 ●3 ✚5 …2 ⚑1`).
4. **STALENESS RISK**: ahead/behind counts are bounded by the 300s fetch TTL — module comment explicitly acknowledges "a long-lived daemon that never fetches would show 'in sync' forever" and designed the background fetch specifically to bound that (`git_branch.py:59-64`). The 2s render cache can show up-to-2s-stale icon counts, low risk.
5. **DUPLICATION**: none — nothing else surfaces branch/status.
6. **CONFIG**: enabled, priority 20, `auto_fetch: true`, `fetch_interval_seconds: 300` set explicitly in this repo's config.
7. **HISTORY**: 17 commits, oldest core handler (`6cc2f0ae`), continuously extended (worktree colour, background fetch, render-TTL cache per Plan 00155 T4).
8. **CONSUMER**: n/a.

**SIGNAL: SUSPECT** — not for pointlessness (it's clearly wanted and well-engineered with two independent TTL caches), but the live-data-derived ~50% cache-miss rate makes this, on current evidence, the single largest subprocess-spawn source in the whole `status_line` chain (every sibling handler in this cohort spawns 0 subprocesses per render). Worth either widening the render-TTL (e.g. to 3-5s, which the ahead/behind staleness tolerance already accepts far worse via the 300s fetch TTL) or re-examining whether all 4 git calls are needed on every miss.

## startup_cleanup

3. **WIDTH**: 0 after 30s (the vast majority of a session's lifetime); ~5-12 cols during the window.
4. **STALENESS RISK**: none — `timestamp`/`count` are read fresh every render and the display window is self-expiring; a stale file simply stops being SHOWN after 30s regardless of content (but is still read).
5. **DUPLICATION**: none.

## supervisor_indicator

1. **CLAIM**: top-hat (🎩) showing whether the ccy PTY supervisor is watching this session, colour-coded armed/dry-run/down, plus transient warning messages (e.g. Ctrl+Z-ignored notice).
2. **RENDER COST**: two-tier cache. **In THIS repo's steady state (ccy armed, cache warm)**: the fast path is 1 cheap `os.kill(pid, 0)` liveness probe only (`supervisor_indicator.py:292-298`) — **0 file reads for state, 0 subprocess**. Every render still does one ADDITIONAL, unconditional check for the transient-message channel: `_active_message` → `_read_message` does a `path.exists()` (1 stat, always) and a conditional `read_text()` only if a message file is actually present (rare/transient) — `supervisor_indicator.py:247-282`. **Cold-start or negative-cache-miss path (not the steady state here, but the real cost profile for a non-ccy project or right after a supervisor restart)**: reads the status file (1 read) AND, if that doesn't resolve, a **full `/proc` scan** — `list(proc_root.iterdir())` then `read_bytes()` on `/proc/{pid}/cmdline` for every numeric pid on the box (`supervisor_indicator.py:365-395`) — the single most expensive per-op cost anywhere in this cohort when it fires. A 5s negative-cache TTL (`_NEGATIVE_CACHE_TTL_SECONDS`, line 100) bounds how often that walk repeats for a project that never runs the supervisor, but 5s against a ~1.15s render interval still implies a walk roughly every 4-5 renders (~20% of renders) until/unless the project simply never installs ccy and the human never notices the cost. **In this repo specifically, because ccy is confirmed armed, the positive cache holds and this expensive path is not being paid on the measured renders** — it only recurs if the cached supervisor pid dies (rare).
3. **WIDTH**: 0 when `NOT_CONFIGURED` (silent by design); ~5 cols (`| 🎩 `) for the plain state; up to ~40 cols when a transient message is attached.
4. **STALENESS RISK**: explicitly engineered against staleness — the module docstring documents a real observed bug (status file going missing while the supervisor was still alive, which used to make the icon vanish) and the fix grounds truth in the live PID via `/proc`, not just the file (`supervisor_indicator.py:29-35`). This is the cohort's best example of "truthfulness" being taken seriously rather than trusting a cache blindly.
5. **DUPLICATION**: conceptually adjacent to `environment_indicator` (both are "context about the running environment") but answers a genuinely different question (is a safety net watching vs where am I running).
6. **CONFIG**: `get_default_enabled() -> True` upstream (safe because NOT_CONFIGURED renders nothing); explicitly re-enabled here for "this repo's always-armed ccy sessions."
7. **HISTORY**: Plan 00168/00171/00173, 4 commits, most recent (`9849d19b`) attaching supervisor messages to the top hat — actively maintained, bug-driven (not speculative).
8. **CONSUMER**: n/a (reads the supervisor's output; the supervisor is `.claude/ccy/claude-supervise.py`, confirmed present in this repo).

**SIGNAL: SUSPECT** — not for pointlessness (well-justified, actively bug-fixed) but purely on render-cost grounds: the `/proc` walk is the heaviest single operation any handler in this cohort can trigger, and while the design correctly memoises the common case, a project that installs the handler (it's on-by-default upstream) but never runs ccy pays a `/proc` walk roughly every 4-5 renders indefinitely, at the same ~3,130 renders/hour rate measured here. This repo's own numbers do NOT show that cost (ccy is armed), which is worth being explicit about so the judge doesn't read "cheap here" as "cheap everywhere."

## Notable cross-cutting finding: `usage_tracking` + `stats_cache_reader`

These two files are a matched pair worth calling out together for the judge: `usage_tracking.py`'s `matches()` has been hardcoded `False` since commit `71593163` (8 commits ago, well before this cohort's newest work), with a documented architectural reason. That is a defensible disable — but it leaves ~165 lines of handler code, ~117 lines of a support module only it calls, a config block that reads as `enabled: true`, and a full acceptance-test entry that will trivially "pass" without exercising any real behaviour. This is not the same defect class as `transcript_archiver` (which had NO reader ever) — `usage_tracking` has a stated, honest reason for its dormancy — but it is the same *shape* of risk: code that looks live from the config file and passes CI while doing nothing, and whose hardcoded model-ID table (`stats_cache_reader.py:13-16`) has since drifted further out of date (pre-dates the Claude 5 family). **This is now corroborated by live production data**: the verdict log's 43,929 status-handler records divide cleanly across exactly 13 firing handlers, with zero contribution from `usage_tracking`.

## Notable cross-cutting finding: the "uncached forever" group

Four handlers in this cohort — `account_display`, `upgrade_notifier`, `startup_cleanup`, and (bounded by small N) `multithread_indicator` — read (or read+write) a small file on **every single render, unconditionally, for the life of the daemon**, with no mtime-gate or TTL of any kind, even though in three of the four cases the underlying data changes far less often than it's read (account username: effectively never; upgrade cache: ≤once/24h; cleanup status: once per daemon restart). Individually each is cheap (small files, no subprocess), but at the measured ~3,130 renders/hour this is collectively ~9,000-12,500 avoidable file operations per hour across the enabled set, for values that are almost always unchanged between reads. `model_context`'s `settings_reader.py` already demonstrates the fix pattern in this exact directory (mtime-cache, ~20 lines) and could be trivially reused by the other three.
