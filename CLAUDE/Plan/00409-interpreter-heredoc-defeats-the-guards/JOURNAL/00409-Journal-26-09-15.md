## 00:40 · finding · T2.1 — the first fix was incomplete: a sink can FEED an interpreter

Found by probing the fix after it was committed and green, not by reading it.
`cat <<'EOF' | bash` passes the receiver check — the receiver genuinely IS
`cat` — and then hands the body straight to bash, which runs it. Three more
holes, all of which v3.63.0 denied:

```
allow body_blanked=True  cat heredoc, no pipe (should blank)
allow body_blanked=True  cat heredoc piped to bash               <== HOLE
allow body_blanked=True  cat heredoc piped to sh                 <== HOLE
allow body_blanked=True  tee then bash                           <== HOLE
allow body_blanked=True  cat heredoc piped to grep (still data)
```

The lesson is uncomfortable and worth writing down plainly: the receiver check
was correct, fully tested, QA-green and pushed — and still wrong, because
"receiver" was the wrong unit. The right unit is the PIPELINE. A guard that
stops looking at the first stage lets a sink be used to smuggle a body to the
next one.

`curl_pipe_shell` already had a local check for this (`_PIPE_INTO_INTERPRETER_
PATTERN`, "a sink's output can itself be piped into an interpreter"), which is
the second time in this plan that handler turned out to have reasoned its way
to something the shared util lacked. That is now two for two, and is itself the
finding: the knowledge was never missing from the codebase, only from the place
that needed it.

The fix keeps the allowlist direction rather than copying the local check,
which is a denylist of interpreter names. `_downstream_is_all_data_sinks`
requires EVERY piped-on stage to be a recognised sink, so `| ssh host` and
`| python3` withhold the exemption too — neither is in `_PIPED_INTERPRETERS`,
so the denylist would have missed both.

`|` extends the pipeline; `&&`, `||`, `;` and `&` end it. That distinction is
load-bearing in the other direction: without it,
`cat <<'EOF' > notes.md || echo failed` would have its prose body scanned
because of a fallback branch that never sees the body. Pinned by its own test.

## 00:43 · finding · T2.1 — third pass, third hole: a substitution in command position

Kept probing rather than declaring victory, using Plan 00335's own enumeration
of execution channels as the checklist — the one written for `curl_pipe_shell`
and never applied to the shared util. Nine channels tested; two more were open:

```
DENY  eval of a substituted cat heredoc

allow backtick substitution  <== HOLE
DENY  source /dev/stdin
DENY  source builtin
DENY  bash -s

```

`$(cat <<'EOF' ... EOF)` standing alone as a command: the receiver is `cat`,
nothing is piped on, so both existing checks answer "prose" — and bash
substitutes the output and then RUNS it. The `eval` spelling was already caught
only because `eval` is the segment's command word and is not a sink; the bare
form has no such word.

The root cause is a good intention one layer down. `command_word` deliberately
STRIPS `$(` and a backtick to find the command inside, which is exactly right
for naming a receiver and exactly wrong for deciding whether an exemption is
safe — the stripping discards the very fact that matters.

Fixed with `_SUBSTITUTION_OPENER_PATTERN`, matched against the receiving
segment before the command word is resolved. It deliberately does NOT match a
bare `(` or `{`: those GROUP rather than substitute, so
`( cat <<'EOF' ) > notes.md` sends the body to a redirect and never to command
position. Withholding there would scan every grouped prose write for nothing,
so that case has its own test in the opposite direction.

Three passes, three holes, every one found by probing and none by reading —
including two found AFTER the previous fix was committed, green and pushed.
Worth recording as a pattern rather than three incidents: each fix was correct
about the case in front of it and wrong about the unit of judgement. Receiver,
then pipeline, then command position. The probe is what moved each time; the
reasoning never would have.

All nine execution channels now DENY, all four inert controls still ALLOW, and

## 00:48 · finding · T2.1 — fifth pass: `2>&1` contains an ampersand

The fourth pass probed CHANNELS. This one probed the fix's own parsing, which
is a different question, and found a hole I had introduced myself two commits
earlier.

`_PIPELINE_TERMINATORS` included a lone `&`, so the opener tail was cut at the
first ampersand — and a stderr redirect contains one. `cat <<'EOF' 2>&1 | bash`
was cut at the `&` in `2>&1`, the pipe was never seen, no downstream stage was
found, and the body bash runs was blanked:

```
blank 2>&1 then bash (must KEEP)          <== WRONG
blank 2>&1 then ssh (must KEEP)           <== WRONG
```

Not an exotic spelling. `2>&1` is what anyone writes to merge stderr, and the
pipeline fix was specifically about pipes — so the hole sat exactly where the
previous commit claimed to have looked.

Fixed by dropping the lone `&` from the terminator list. `&&` and `||` stay
(they are matched whole, longest-first). The cost is over-withholding: a `|`
belonging to something after a background `&` now reads as downstream, which
SCANS a body rather than exempting one. That is the safe direction, and
`cat <<'EOF' & bash` is pinned by a test asserting it still blanks, because
bash there never receives the body.

Five passes now, four of them finding something. The pattern has shifted: the
first three were about the unit of judgement (receiver, pipeline, command
position); this one was about whether my own parser could be fooled by ordinary
shell punctuation. Both kinds need probing and neither is visible by reading.

## 00:50 · finding · T2.1 — sixth pass: the SAME ampersand on the other side

Having found the `&` hazard in the pipeline split, asked the obvious follow-up:
the receiver resolution splits on a lone `&` too. It does, and it is fooled the
same way — but the consequence is the opposite one, which is why it needed
finding separately rather than assuming.

`cat 2>&1 <<'EOF'` splits at the redirect's `&`, so the receiver resolves to
`'1'`:

```
KEPT  receivers=['1']  cat with stderr redirect      <== false positive
KEPT  receivers=['1']  git commit with redirect      <== false positive
KEPT  receivers=['2']  cat with fd dup only          <== false positive
```

`'1'` is on no allowlist, so the exemption is WITHHELD and the body is scanned.
That is the safe direction — no guard is lost — which is exactly why it would
have survived every hole-hunting probe I had written. It is a FALSE POSITIVE,
and a consequential one: `git commit -F - 2>&1 <<'EOF'` describing a
destructive command is denied again, which is precisely the report that
produced release note 29. My fix would have re-opened it in a narrow spelling.

`_FD_REDIRECT_PATTERN` blanks fd redirects out of the segment before it is
split — `2>&1`, `>&2`, `1>&2`, `&>log`, `&>>log`, `2>&-`. Blanked rather than
removed, so nothing else on the line shifts.

Note this one is PRE-EXISTING: `_receiving_segment` and `_RECEIVER_SEPARATORS`
are older than this plan, and `quoted_heredoc_receivers` has been returning
`['1']` for these shapes to `curl_pipe_shell` all along (withholding there too,
also safely). What changed is that this plan made that parser load-bearing for
a new decision, which turned a dormant imprecision into a live false positive.

Lesson worth keeping separate from the other five: probing only for HOLES finds
only holes. This pass looked for surprises in both directions, and the thing it
found was a guard being too eager, not too lax.

## 00:53 · decision · T2.1 — eighth pass: one safe imprecision, left alone deliberately

Line continuations. `_downstream_is_all_data_sinks` reads only the opener TAIL,
which is the rest of that PHYSICAL line, so a backslash-newline could in
principle put an interpreter where the tail never reaches.

It does not produce a hole. `cat <<'EOF' | \` + newline + `bash` keeps its
body, because the tail's last stage resolves to the bare continuation
backslash, `command_word` strips it to the empty string, and an unnameable
stage withholds. The allowlist's default carries the case its author never
considered — which is the argument for an allowlist, arriving unprompted.

It does produce one FALSE POSITIVE: the same shape piped to `grep` also keeps
its body, where it could have been blanked.

Left unfixed, deliberately. The gain is cosmetic — a prose body gets scanned
rather than exempted, in a spelling (a continuation immediately after a pipe on
a heredoc opener) that is rare and whose exact body-start semantics are murky
enough that I would be guessing at what bash does. Chasing it means touching
the tail parser again, and the last two passes both found that touching this
parser is how holes appear. A recorded imprecision that fails safe beats an
unrecorded change that might not.

Eight passes: six found something, two were clean, and the two clean ones are
recorded precisely because "probed and clean" is a different fact from "did not
probe".
