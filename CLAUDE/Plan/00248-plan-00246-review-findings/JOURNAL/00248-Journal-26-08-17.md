## The findings arrived after the plan they are about had shipped

`review-round-2` was dispatched during Plan 00246 and then vanished without
reporting; I closed 00246 having said plainly in its PLAN.md that the
self-review was weaker evidence than the peer review would have been. The agent
then reported an hour later, after 00246 was archived and pushed, with six
findings.

Two of them are regressions 00246 introduced. That is worth sitting with,
because it is a specific and generalisable failure of centralising work:

`run_git` exists so that two properties — the declined optional lock and a
timeout — hold by construction rather than per call site. But a call site that
had DELIBERATELY chosen a different value for one of those properties loses that
choice silently when it is migrated. `branch_safety._git` passed no timeout at
all, deliberately: it runs `git bundle create`, which packs objects. After the
migration it runs on `Timeout.GIT_CONTEXT = 5`, a budget named for hook context.

So the migration inverted the defect it was fixing. Before, a property was
missing at thirty sites and had to be remembered individually. After, a property
is present at thirty sites and its VALUE is now assumed uniform — and the one
site where it was not uniform is the human-gated branch-deletion safety command.
Nothing in the plan's own test suite could see this: every test passes, because
every test uses a small repository where five seconds is plenty.

## Verifying rather than trusting

A peer's report is not an oracle. Earlier in this same repository an agent
reported a live ruff rule as stale, and I nearly accepted it. So each finding was
re-derived:

- F1: `git show 013b48e7~1:...branch_safety.py` — the old `_git` passed no
  `timeout=`. Regression confirmed from history, not inference.
- F2: built a throwaway repo, committed a file containing `\xff\xfe`, and ran
  `git show HEAD:./bad.txt` through the exact `subprocess.run` keywords
  `run_git` uses. It raises `UnicodeDecodeError`, and I checked the class
  hierarchy in the same script: not an `OSError`, not a `SubprocessError`, so
  `run_git`'s except clause cannot catch it while its docstring says "Never
  raises". With `errors="replace"` the same call returns cleanly.
- F3, F4, F5, F6: read the code. All four match the report exactly, including
  F5's specific AST predicates (`func.value.id == "subprocess"` and
  `call.args[0]`), which is why an alias import, a from-import and an `args=`
  keyword each walk straight past the guard.

Six findings, six confirmed. No corrections to make to the report.

## What I am not doing

F5 lists six escape shapes; I am closing three. `asyncio.create_subprocess_exec`
and `shutil.which("git")` are not idioms this codebase uses, and an absolute
`/usr/bin/git` is not either. The guard's own docstring commits it to
unambiguous shapes, on the same reasoning `check_magic_values.py` uses: a check
that guesses gets disabled, and a disabled check protects nothing. The three I
am closing are ordinary idioms that a future author would reach for with no
intent to bypass anything, which is exactly the case a guard has to cover.

## Phase 1–3 delivered

All six fixed, each with a test that fails first where a failing test was
meaningful.

**F2** was the satisfying one: one keyword at the chokepoint (`errors="replace"`)
makes the docstring true for all thirty-odd callers at once. The RED test builds
a real repo, commits a file containing `\xff\xfe`, and reads it back with
`git show` — the exact production path, since `claude_md_injector` does precisely
that during daemon startup.

**F1** needed a judgement about what to assert. The honest test of "5s is too
short for `git bundle create`" is a repository large enough to take longer than
five seconds — which would add minutes to the suite to demonstrate what a named
constant already states exactly. So the tests assert the BUDGET (not
`GIT_CONTEXT`, at least `GIT_BRANCH_SAFETY`, bundle strictly greater still), and
a third asserts the CLI turns a git failure into a refusal rather than a
traceback. The last one is the behaviour a human actually meets.

**F3** could have been `except OSError` around the call. Passing the filesystem
root instead removes the question entirely: `ls-remote` talks to a URL and never
reads the cwd, so asking `Path.cwd()` for a value nothing uses — and inheriting
its ability to raise — was the actual defect. While there I added the argv
assertion the review noted was missing: with `subprocess.run` patched
process-wide, every test in that file would pass if the handler stopped calling
git at all.

**F4** exposed a gap in the test I had written during Plan 00246. It asserts the
commit's budget and the status's budget, and I read that as covering the
function — but `git add` runs ONLY for an untracked CLAUDE.md, and that fixture
commits one first. So the call the review flagged was invisible to the test that
looked like it covered the area. It has its own test now, with an explicit
precondition assertion so it cannot quietly stop reaching the staging branch.

**F5**: four shapes, all RED first. Bindings are now collected per module from its
own imports rather than matching the name `subprocess`, which keeps the negative
cases honest: a project-local `run(["git", ...])` is not flagged, because
inferring from a bare name is exactly the guessing the guard's docstring rules
out. I deliberately did NOT chase `shutil.which("git")`, `/usr/bin/git` or
`asyncio.create_subprocess_exec` — the first two are genuinely ambiguous in an
AST and the third is not an idiom this codebase uses.

**F6** got a test file of its own, with the fixture as the subject rather than as
a tool. A guard whose own anti-vacuity measure can silently stop working needs
one. Both helpers now fail loudly on a repo that cannot support the assertion —
no tracked files, or no index yet — rather than passing or raising a bare
`FileNotFoundError` that reads as a bug in the test.
