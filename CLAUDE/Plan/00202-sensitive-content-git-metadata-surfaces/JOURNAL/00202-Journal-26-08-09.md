## 10:41 · finding · — — why this plan exists: 00201 guarded 2 of 7 surfaces

Plan 00201 shipped believing "sensitive content" meant file *content*. It does
not. The evidence was already sitting in the rewrite built to clean this repo's
own history: `git-filter-repo --replace-text` alone was nowhere near enough —
four distinct mechanisms plus two manual steps were needed, across seven
surfaces. Two are now guarded. Five are not, and all five enter through
`Bash`, which `matches()` rejects before it looks at anything:

```
def matches(self, hook_input):
    tool_name = hook_input.get(HookInputField.TOOL_NAME)
    if tool_name not in (ToolName.WRITE, ToolName.EDIT):
        return False
```

The concrete failure: force-push the cleaned history, then make one
`git commit -m "<term>"`. The repo is contaminated again and BOTH guards
report all-clear — the scanner because it reads `git ls-files` blob contents,
the handler because it never saw the call.

That is the DBF question answered honestly. The defect was never "165 places
carried the term". It was "nothing could see them", and that fix is only
finished when the guard sees every surface the rewrite had to touch.

## 10:41 · decision · — — extend the handler, do not add a second one

A `sensitive_git_metadata` handler would fork the secret-list loading, the
exclude-path logic and the non-disclosure contract across two files. 00201's
own post-mortem was exactly that failure: a second implementation of the same
rule drifted from the first and reported clean while the tree was dirty. The
rule here is identical ("does this text carry a listed term") — only the
haystack differs, and `fb91d81f` already made the handler take a *list* of
haystacks. Recorded as Decision 1 in PLAN.md.

## 10:41 · finding · — — two lessons carried in from the path fix (`fb91d81f`)

Both are in PLAN.md Context because they are the expensive kind to re-learn:

1. **Never reimplement the match test.** The 00201 scanner hand-rolled
   lowercase substring containment and so could not see a path term's
   venv-slug spelling — it reported a clean tree over a contaminated one.
   Everything now routes through `utils.secret_redaction.term_matches`.
2. **The deny reason is itself an output surface.** The path fix had to redact
   `file_path`, because the reason echoed it verbatim — the non-disclosure
   contract was being broken by the very message announcing the block.

## 10:41 · finding · — — my own guards fired on me twice, both correctly

Recording these because each is the system working, and neither needed a fix:

- `error_hiding` (the QA gate **and** its unit test, independently) rejected
  the first relative-name draft, which fell back to a basename on `ValueError`.
  That fallback would have silently stopped the scanner seeing DIRECTORY names
  — precisely half the surface I was adding. Replaced with a lexical
  computation that cannot raise, invariant written down in the source.
- `lint_on_edit` (ARG001) caught me deliberately sabotaging the source to
  prove a negative control could fail. That forced a better method: call
  `scan_file` directly from a scratchpad harness with a wrong scan root, no
  source edit at all. Correct root → 0 violations, wrong root → 1. The
  assertion is load-bearing rather than vacuously green.
