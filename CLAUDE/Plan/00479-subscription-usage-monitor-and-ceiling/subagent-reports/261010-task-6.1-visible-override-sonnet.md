# Task 6.1 report: make the usage-pause owner override visible

Branch: agent-ab61c4fa2ab46feb5-04518b37. No decision changed: the override still suppresses every pause, and no backstop was added (Task 6.2).

## What was built

1. One accessor for the marker. `utils/usage_pause.py` gains `UsageOverride(until)` and `read_usage_override(dir, session, now=)`, the only reader of the `<session>.usage-override` marker. `usage_override_active` is now `read_usage_override(...) is not None`, so start_pause and the new signals cannot disagree. An unreadable marker still counts as an override (fails toward not pausing) but has `until=None`; a malformed, foreign-session or expired marker is no override. The read goes through a private list-returning helper so the error-hiding audit does not flag new `return None` handlers.
2. Per-prompt context. `utils/usage_pause_gate.py` gains `override_notice(hook_input, env)` and `override_end_text(until, now=)`. The notice reuses `current_breaches` (the same usage reading the pause uses) and is emitted only when the override has a known end AND at least one window is over its ceiling. Text starts `USAGE CEILING SUPPRESSED:`, names each window with its floored percentage and ceiling, the end as `HH:MM UTC` (`YYYY-MM-DD HH:MM UTC` when not today, UTC), and says the session is NOT paused and that HTTP 429 can follow. Silent on no data, no ceiling, no session id, no project context, an unreadable marker, or synthetic traffic (a probe's exemption is an override too, and its verdict must not gain context). `UsagePauseGateHandler.handle` attaches it to the ALLOW when `try_start_pause` returns None. Its resident guidance (`get_claude_md`) mentions it.
3. Status chip. `UsageIndicatorHandler._override_chip` shows `override until HH:MM` (local time, `MM-DD HH:MM` when not today), leading the segment after the failure and pause chips, even with no usage snapshot. `explain_segment` and the module docstring describe it.

## Chip decision

The chip shows whenever the override is valid, not only when over the ceiling. Reason: the override is what switches the guard off, and the 10-08 incident was an override written at 80% with the breach arriving later inside it. A chip tied to the breach would be absent at the moment the owner most needs to remember the guard is off. Colour carries the extra: red when a window is already over its ceiling, yellow otherwise. The model-facing line is the opposite, breach-only, because it costs context on every prompt and "override active, usage fine" gives it nothing to act on.
