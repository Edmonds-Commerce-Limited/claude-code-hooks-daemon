> **Append-only activity log** for plan 00479. One file per day
> (`00479-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM, ONLY with
> `mkplan.bash --journal <plan-number> <category> <body-file>` (it stamps the
> real UTC time; a hand-written entry is denied); NEVER edit earlier entries
> (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff` | `correction`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - A `correction` corrects an earlier entry without touching it. Its `REF`
>   (`--ref`, required) names that entry: `HH:MM` in this file, or
>   `YY-MM-DD/HH:MM` in an earlier one. An entry a correction names in this
>   file no longer counts for time order, so a future-dated stamp can be
>   corrected at the honest time.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 12:30 · finding · —

The pause gate reached its third and last review round (head 563b78f2a). The review requests changes.

- **Round 2**: N1-N6 are all resolved, and the round-1 fixes still hold.
- **Blocking, R3-1**: a subagent over the ceiling is never paused. This is a regression from the coordinator's round-2 ruling ("subagents never start a pause"). A subagent's call should write the record and get the plain "stop now" deny.
- **Blocking, R3-2**: the resume cron is written in UTC. The CronCreate tool schema, loaded through ToolSearch in this session, says: "Uses standard 5-field cron in the user's local timezone ... '0 9 * * \*' means 9am local". It also says `recurring: false` fires "once at the next match, then auto-delete". So on a host whose zone is not UTC, a pinned UTC one-shot lands hours off or a year late. The fix the reviewer prefers is zone-independent: a recurring `*/10 * * * *` resume cron, whose early ticks the prompt gate drops at no cost. A recurring job auto-expires after 7 days, which covers the longest pause (the 8-day cap may need to become 7).
- **Follow-up-OK**: R3-3 (the override cap is only enforced on write), R3-4 (the matches-to-handle state is keyed by session under parallel calls), R3-5 (the 2-minute floor is tight), R3-6 (concurrent read-back can delete a record), and a narrow except around `clear`'s usage read.
