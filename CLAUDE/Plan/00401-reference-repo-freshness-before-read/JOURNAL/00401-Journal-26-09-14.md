## 12:35 · decision · P1 — started building rather than waiting for a confirmation

The owner's three rulings are recorded, and the one open question — "PreToolUse
performs no network I/O" — is not a preference to be ruled on. It is forced:
`Timeout.GIT_FETCH_SESSION` and `GIT_PULL_SESSION` are 30s each against a 30s
hook socket budget, so one repo can consume the whole budget. There is no
version of this design where PreToolUse fetches. Proceeding under that stated
assumption rather than blocking on a question with one possible answer.

## 12:40 · action · T1.1 — discovery.py, 23 tests, 100% coverage

Two boundaries carry the design, and both were written as tests first:

- A checkout is a `.git` of EITHER kind. A worktree and a submodule carry a
  `.git` FILE, so an `is_dir()` test would silently skip exactly the checkouts a
  multi-worktree workflow produces.
- The walk is depth-bounded and a non-positive bound finds NOTHING. A root is
  configuration and configuration can say `/`; failing closed on a nonsense
  value is what keeps a typo from becoming a filesystem-wide walk.

## 12:55 · decision · T1.2 — three small deviations from the drafted task, each deliberate

1. **`inspection.py`, not `inspect.py`.** The draft named it after the concept,
   but that filename shadows a standard-library module much of the ecosystem
   imports. Matching a draft filename is not worth that.
2. **`RepoState` carries no enforcement policy.** Three surfaces consume it and
   only ONE of them blocks, so a `should_block` property would bake the
   PreToolUse handler's configurable mode into a value the CLI and the sweep
   also read. It exposes facts and derived predicates; policy lives in Phase 4.
3. **`git_sync._remotes` promoted to public `remotes()`.** Needed to separate
   `NO_REMOTE` from `NO_UPSTREAM`. Both are uncomparable in an ahead/behind
   sense, so it would have been easy to collapse them — but the remedies differ
   (`git remote add` versus `git branch -u`), and a report that conflates them
   tells the reader to run the wrong command. Only two call sites, both inside
   `git_sync`, so the rename was contained; four tests cover the new contract.

## 13:00 · finding · T1.2 — the architecture is now a test, not a comment

`test_inspection_never_performs_network_io` patches `fetch_all` and
`pull_ff_only` to raise, so any future change that "helpfully" adds a fetch to
the inspection path fails there and nowhere else. A paired test asserts the
consequence honestly: a commit pushed to origin is INVISIBLE until something
fetches, so freshness means "fresh as of the last fetch". That is why the cache
feeding PreToolUse needs a TTL and why a missing or expired entry must read as
NOT VERIFIED rather than as fresh (Task 1.4).

The canary case is covered too: an origin set to `https://invalid.invalid/` still
classifies as CHECKABLE and demands no attention, because nothing contacts it.
A design that reached out would stall there for the whole fetch timeout.

## 12:46 · action · P1 — Phase 1 complete: 123 tests, 100% package coverage

`cache.py` and `report.py` close the phase. Both were shaped by asking what the
SILENT failure would be, rather than what the happy path needs.

For the cache that meant: every unusable shape reads as NOT VERIFIED, including
two that would otherwise pass quietly — a FUTURE timestamp (a naive `age > ttl`
never fires on a negative age, so clock skew would pin a stale reading in place
forever) and a partially-readable file (returning the readable remainder
silently drops a repo, and a dropped repo is indistinguishable from one that was
never governed). `None` and `{}` are kept as different answers throughout.

For the report it meant listing ONLY repos needing attention. A report reciting
every healthy repo is one a reader skips, and the uncheckable canary would head
that list in perpetuity.

## 12:46 · finding · P1 — coverage keeps finding the branches I did not think about

Three times now the 95% gate has pointed at a real gap rather than a formality:
