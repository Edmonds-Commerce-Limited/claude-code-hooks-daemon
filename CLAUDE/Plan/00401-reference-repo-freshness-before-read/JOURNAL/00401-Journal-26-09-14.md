## 12:40 · action · T1.1 — discovery.py, 23 tests, 100% coverage

Two boundaries carry the design, and both were written as tests first:

- A checkout is a `.git` of EITHER kind. A worktree and a submodule carry a
  `.git` FILE, so an `is_dir()` test would silently skip exactly the checkouts a
  multi-worktree workflow produces.
- The walk is depth-bounded and a non-positive bound finds NOTHING. A root is
  configuration and configuration can say `/`; failing closed on a nonsense
  value is what keeps a typo from becoming a filesystem-wide walk.

## 12:55 · decision · T1.2 — three small deviations from the drafted task, each deliberate

1. **`inspection.py`, not `inspect.py`.** The draft named it after the concept,
   but that filename shadows a standard-library module much of the ecosystem
   imports. Matching a draft filename is not worth that.
2. **`RepoState` carries no enforcement policy.** Three surfaces consume it and
   only ONE of them blocks, so a `should_block` property would bake the
   PreToolUse handler's configurable mode into a value the CLI and the sweep
   also read. It exposes facts and derived predicates; policy lives in Phase 4.
3. **`git_sync._remotes` promoted to public `remotes()`.** Needed to separate
   `NO_REMOTE` from `NO_UPSTREAM`. Both are uncomparable in an ahead/behind
   sense, so it would have been easy to collapse them — but the remedies differ
   (`git remote add` versus `git branch -u`), and a report that conflates them
   tells the reader to run the wrong command. Only two call sites, both inside
   `git_sync`, so the rename was contained; four tests cover the new contract.

## 13:00 · finding · T1.2 — the architecture is now a test, not a comment

`test_inspection_never_performs_network_io` patches `fetch_all` and
`pull_ff_only` to raise, so any future change that "helpfully" adds a fetch to
the inspection path fails there and nowhere else. A paired test asserts the
consequence honestly: a commit pushed to origin is INVISIBLE until something
fetches, so freshness means "fresh as of the last fetch". That is why the cache
feeding PreToolUse needs a TTL and why a missing or expired entry must read as
NOT VERIFIED rather than as fresh (Task 1.4).

The canary case is covered too: an origin set to `https://invalid.invalid/` still
classifies as CHECKABLE and demands no attention, because nothing contacts it.
A design that reached out would stall there for the whole fetch timeout.

## 12:46 · action · P1 — Phase 1 complete: 123 tests, 100% package coverage

`cache.py` and `report.py` close the phase. Both were shaped by asking what the
SILENT failure would be, rather than what the happy path needs.

For the cache that meant: every unusable shape reads as NOT VERIFIED, including
two that would otherwise pass quietly — a FUTURE timestamp (a naive `age > ttl`
never fires on a negative age, so clock skew would pin a stale reading in place
forever) and a partially-readable file (returning the readable remainder
silently drops a repo, and a dropped repo is indistinguishable from one that was
never governed). `None` and `{}` are kept as different answers throughout.

For the report it meant listing ONLY repos needing attention. A report reciting
every healthy repo is one a reader skips, and the uncheckable canary would head
that list in perpetuity.

## 13:11 · finding · — — the correction above was itself estimated; here are the measured numbers

The `12:46` correction entry claims the two entries above it were written "at
roughly 12:20". That was another estimate, and it was also wrong. Git knows:

| Entries          | Commit     | Real commit time |
| ---------------- | ---------- | ---------------- |
| `10:26`          | `a06bd799` | 10:29            |
| `12:35` → `12:45`| `9e399219` | 12:28            |
| `12:55`, `13:00` | `63acb7c2` | 12:34            |
| `12:46` ×4       | `d5a2e618` | 12:47            |

So SIX labels are ahead of the commit that carried them, not the two the earlier
correction identified — the whole upper block was estimated, and the `12:45`
entry was committed at 12:28. Only the `12:46` run and `10:26` are true.

I started re-labelling all six to git-bounded windows and the `journal-append-only`
check stopped me mid-edit: corrections are additions, never rewrites. It is
right, and the reasoning is worth keeping. A false label is not evidence of the
mistake — this entry is. Rewriting the headings would have destroyed the only
proof that the estimates ever happened while making the file *look* disciplined,
which is precisely backwards.

The standing `journal-entry-ordering` advisory on this file is therefore accepted
and permanent, not a defect to clear. That the check is `advise` rather than
`block` is the project having already made this trade.

The method, for next time: `git log --format='%h %ad' --date=format:'%H:%M' -- <file>`
attributes every entry to a real commit time. A timestamp is a fact to look up,
and there were two lookups available here — `date` before writing, and git
afterwards — neither of which I used until the linter forced it.

## 13:40 · finding · P4-P6 — the two defects only RUNNING it could find

Both were invisible to a green test suite, and both were found by pointing the
finished thing at reality rather than at a fixture.

**1. A failed fetch read as an all-clear.** Ran the new CLI against this repo's
own canary, whose origin is `https://invalid.invalid/canary.git`. Output:

```
📚  reference repos: all 1 up to date
```

The fetch fails with exit 128. The local refs say "not behind", so the repo was
counted as fresh. `refresh_repo` already KNEW — it returns `fetched=False` with
a `_FETCH_FAILED` detail — but all three consumers keep only `.state` and drop
the outcome, so the knowledge died at the call site. Fixed by carrying it on
`RepoState` (`fetch_failed`, plus a `verified` property) so it survives into the
cache and reaches every surface.

The interesting part was where NOT to put it. Folding it into `needs_attention`
was the obvious move and is wrong: the canary is *checkable* (it has a remote
and an upstream), so every session would have opened with a complaint about a
remote that is unreachable **by design**. That is precisely what the model
docstring keeps un-checkable repos out of the way for. It belongs in the
counting, not in the nagging.

**2. The handler denied the commit that shipped its own documentation.**

```
reference repo freshness NOT VERIFIED: no in-date reading exists for untracked/repos
```

…on a `git add -A && git commit -F - <<'MSGEOF'` whose MESSAGE mentioned
`untracked/repos/php-qa-ci`. `_CHAIN_SEPARATORS` includes `"\n"`, so every line
of the heredoc body became its own "segment", and a line of prose naming a repo
parsed as a command reading it. Nothing was being read at all.

The fix was already sitting in the codebase: `strip_quoted_heredoc_bodies` and
`strip_message_bodies` in `utils/shell_segmentation.py`, which `pipe_blocker`
uses for this exact class of false positive. I segmented a raw command string
without them. Worth remembering that "is this text a command?" is a solved
problem here, and reaching for the solved version is cheaper than rediscovering
why it exists.

Both now have regression tests. Neither would have been caught by more unit
tests of the kind I was already writing — the first needed a repo with a
genuinely unreachable remote, and the second needed a real commit message.
