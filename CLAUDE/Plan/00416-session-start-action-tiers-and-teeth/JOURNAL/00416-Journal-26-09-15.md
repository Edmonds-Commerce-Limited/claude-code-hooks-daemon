## 19:20 · finding · T2.1 — Task 2.1 cannot be built, and Task 1.1 is the proof

Phase 2's first task says to point `persistent_cron_assertor` at the cron
checker as its verifier. It cannot be done, and the reason is already written
into this plan: `session_crons` is not delivered to `SessionStart`. That is the
entire justification for Task 1.1 existing at `Stop` rather than earlier.

A SessionStart verifier would therefore have no input. Worse than useless: a
verifier that can never fail can never compute `ACTION_REQUIRED`, so the wiring
would yield a permanently-`INFO` advisory that LOOKS like it participates in
the tier system while being structurally incapable of doing so. That is the
tier inflation problem in reverse and just as misleading.

Rewritten as a decision rather than an attempt. Either the cron case stays out
of the computed tier — defensible, since the tier system is for conditions
checkable at session start and this one provably is not — or the assertor gets
a different verifier, which requires finding some SessionStart-visible signal
about crons, and none is known to exist.

Noted because the failure is only visible if you hold Task 1.1's constraint and
Task 2.1's instruction in mind at once, and they sit in different phases. The
next agent would have started building before hitting it.

I had told the owner 2.2 and 2.3 "hang off" 2.1's restatement. That was wrong

Caught by applying the lesson from N5 an hour earlier — I had asserted a thing
was blocked without testing it, twice in one evening. The second time I looked

Both verifiers are RED-first, 9 tests. The one worth keeping is
`TestTheVerifierNeverMutates`: `hook_registration_checker.handle()` self-heals
(settings migration, then registration repair) before reporting, so the obvious
implementation — reuse the audit path — would rewrite `settings.json` every
time a tier was computed. Tiers are computed by `session-actions`, which a
human runs to INSPECT. The verifier runs the validators alone and the test
pins the file byte-identical afterwards.

The honest consequence is written into the docstring: the verifier reports what
is broken right now, and `handle` may then repair some of it, so a tier can be
momentarily pessimistic. That is the safe direction and cheaper than the
alternative.

Also fixed a mistake of my own making on the way: switching to explicit
two-parent `__init__` calls, I wrote `SessionStartHandlerBase.__init__(` without
`self`. Tests went 8-failed to 9-failed rather than improving, which is the
signal worth trusting — a change that makes things worse is not a partial fix.

Verified live: `session-actions` reports no ACTION_REQUIRED on this session,
which is correct (handlers loaded, wiring sound) and shows the mechanism does
not false-alarm on a healthy session.

## Task 2.3 — the supervisor directive, shipped as a sixth signal family

Task 2.3 was the last item under the goal condition I had not examined, and I
had already told the supervisor it was owner-gated because "the wording is the
owner's call". That was wrong for the same reason 2.2 was wrong: the plan
already SAYS what the directive says, and the owner already proved the line
works. Nothing was waiting on anyone.

Built the whole path rather than a nudge-shaped stub:

- `utils/session_actions_signal.py` — the sensor. One JSON file per session in
  the shared context-sidecar directory.
- `handlers/session_start/session_actions_directive.py` — priority 72, last.
- `.claude/ccy/claude-supervise.py` — loader, fixed renderer, a sixth injection
  family below even the standing-auth reminder, the reaper glob and a runaway
  cap.

Three decisions worth recording, because each had a cheaper wrong answer.

**The payload carries no text.** I could have copied `goal-intent`, which
carries daemon-composed lines and defends itself with a verbatim-header check.
Copied `operator-signal` instead: a positive integer count, and every word the
agent reads composed by the supervisor from a fixed template. `operator-signal`
earned that shape because it is reachable from outside the container; this one
has a different reason. A nudge whose entire message is "go read what you were
already told" never needed to carry prose, and a channel that cannot carry
prose cannot be widened into one later by someone with a good reason. A test
writes a signal carrying forged `message` and `rendered_lines` fields and
asserts the render is byte-identical to the template.

**Priority 72 is load-bearing, not tidiness.** `hook_registration_checker`
SELF-HEALS in its `handle()`. Counting anywhere but last would nudge the agent
about a problem the session had already repaired — the mirror image of the
mutation bug 2.2 had to avoid, and found by asking the same question.

**One collector, not two.** The directive says "run `session-actions`". If the
two answers could diverge, the first divergence would teach the agent that the
directive lies, which is precisely the failure this plan exists to fix. So the
CLI's private collector moved to `utils/session_action_items.py` and a test
pins that the CLI has no collector of its own.

Also gated the write on `armed_supervisor_live`: with no supervisor nothing
ever reads the file, so writing one is litter rather than a nudge.

Five test failures came out of the full suite afterwards, all mine and all
structural rather than behavioural: the opt-in drift guard, the reference
config completeness check, and the error-hiding audit — which caught something
I would not have: moving the collector left a line-keyed exclusion for
`daemon/cli.py::_collect_session_action_entries` pointing at nothing. A stale
exclusion is worse than a missing one, because it silently exempts whatever
drifts under it. Deleted rather than repointed: the extracted code returns `{}`
on a bad config instead of logging and continuing, so it is no longer a finding
in its new home at all.

Fixed a stale claim in `test_cli_session_actions.py`'s docstring while there —
it still said none of the shipped SessionStart handlers implements a verifier,
which Task 2.2 made false. The baseline is still an empty list, but now for the
stronger reason that two verifiers exist and are passing.
