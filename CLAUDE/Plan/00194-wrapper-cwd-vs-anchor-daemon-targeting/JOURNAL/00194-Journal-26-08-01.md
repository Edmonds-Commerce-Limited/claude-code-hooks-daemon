## 06:40 · finding · — how this was found, and the exact reproduction

Found during Plan 00193 Phase 4, by executing the installer's own printed
commands verbatim from the client fixture — the Plan 00192 standard that a
command is fixed when it RUNS, not when it looks right.

Isolating CWD as the only variable, with the SAME wrapper binary each time:

```
W=/workspace/untracked/dummy-client-repo/.claude/hooks-daemon/bin/hooks-daemon

cwd=/workspace
  Socket: /workspace/untracked/daemon-d8b8f32bb3db.sock (exists)     ← MAIN daemon
cwd=/workspace/untracked/dummy-client-repo
  Socket: …/dummy-client-repo/.claude/…/daemon-d8b8f32bb3db.sock     ← fixture's
cwd=/
  (exit 1 — no project root found)
```

The damage is not hypothetical: running `"$W" restart` from `/workspace`
restarted the DOGFOOD daemon (PID 1186876 → 1203331) while I believed I was
exercising the fixture. It reported "Daemon already running" and then
"Daemon started successfully" — both true statements about the wrong daemon.
Nothing indicated a cross-project action.

Why the interpreter and the target disagree: the wrapper computes `DAEMON_DIR`
from `$0` and uses it ONLY for `resolve_venv_python`. It then does

```
exec "$PYTHON" -m claude_code_hooks_daemon.daemon.cli "$@"
```

and the CLI discovers its project root from CWD. So `$0` picks the interpreter;
CWD picks the daemon.

## 06:40 · decision · — documentation half fixed in 00193, behaviour tracked here

The wrapper's DESIGN NOTE 1 read "It anchors to its OWN location (not the
caller's CWD)" — which a reader reasonably takes to cover the whole wrapper. It
is true of the interpreter only. That is precisely the "docs assert something
untrue" defect Plan 00193 exists to remove, so the comment was corrected there
(in BOTH `bin/hooks-daemon` and the `install/templates/hooks-daemon` source —
they are byte-identical and `test_bin_wrapper.py` enforces that).

The behaviour change is NOT being slipped into 00193: project-root resolution is
the entry point every hook forwarder, script and skill wrapper goes through, so
changing it needs the caller enumeration in Phase 1 before any code moves.
