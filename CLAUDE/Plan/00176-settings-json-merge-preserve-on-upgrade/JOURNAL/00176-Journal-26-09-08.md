# Plan 00176 Journal — 2026-09-08

## Task 2.0 shipped, and it was filed against the wrong site

The plan's backup table said the upgrade path took no backup — "**no** — bare
`cp`" — reasoning from the copy at `:865` alone. Two things turned out to be
wrong with that, and the second inverts the risk model.

**First: Step 9 is covered.** `upgrade_version.sh:544` creates a full state
snapshot at Step 3, `install/rollback.sh:162` captures `settings.json` in it,
and `cleanup_old_snapshots "$DAEMON_DIR" 3` at `:1192` keeps the last three. So
a recoverable copy survives a successful upgrade, and the "cheap mitigation" of
backing it up first would have added a second one.

**Second, and worse: the site that runs most often is the uncovered one.** The
idempotent fast path at `:307` copies `settings.json` and prints *nothing*, and
`exit 0`s at `:439` — before Step 3 at `:539` — so no snapshot stands behind it
either. The script's own comment about that branch:

> Layer 1 (upgrade.sh) ALWAYS checks out the target tag before invoking this
> script, so `ROLLBACK_REF` always equals `$TARGET_VERSION` here — this branch
> is the effective single deployment path for every client upgrade.

So the silent, unbacked, unannounced copy is the one on the effective single
deployment path, and the plan's table pointed at its safer sibling.

**The fix is one function, not two patches.** Two sites doing one job
differently is what produced the gap in the first place, so
`scripts/install/settings_deploy.sh` now serves both. Its three properties, each
chosen against a specific failure:

- Acts only when the file actually **differs**. Warning on every upgrade trains
  people to ignore the warning, and a `.bak-` per upgrade of an identical file
  is litter that makes the real one harder to find.
- Takes a backup only when nothing else holds a copy; points at the snapshot
  when one exists. One copy, never two.
- **Aborts** if the backup cannot be written, leaving the client file
  untouched. Losing it is the one outcome worth failing a deploy for.

Tested by sourcing the real library and calling it, plus assertions that both
sites go through it and that no raw `cp "$SETTINGS_JSON_SOURCE"` survives — a
helper only helps if the sites that had the bug actually call it.

I deleted `test_upgrade_sh_settings_replacement_warning.py`, written an hour
earlier against an inline version of this. It extracted the Step 9 block and
stubbed its callees; once the block called the helper, stubbing would have
tested the stub.

with `Path("/").stat().st_uid == 0` — which asks who owns `/`, not who is
running, and is therefore constant `True`. CI's skip list confirms it: it
skipped on a runner, where the process is not root and the stated reason is
false. I cannot verify the fix locally (this container IS root, so the test
cannot exercise its own assertion), so guessing at it would push an unverified
change. Filed as Plan 00351.

**Two error-hiding exclusions drifted.** My five inserted lines pushed the
pinned exclusions at 444 and 798 off their targets, and QA reported both the
"new" findings and the stale entries. Exactly what Plan 00220's stale-exclusion
check is for, and it worked. Realigned rather than re-justified — same lines,
same reasons, five lines lower.
