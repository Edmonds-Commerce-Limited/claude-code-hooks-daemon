# Plan 00377 — Journal 26-09-11

> **Append-only activity log** for plan 00377. One file per day
> (`00377-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM; NEVER edit earlier
> entries (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` local 24h (the date is in the filename); times increase down the file.
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 14:12 · decision · N1 — two blind spots, both deliberate, both guarded

The first sweep reported only ARCHIVED plans. Those cannot be fixed:
`archive-immutability` forbids editing a plan under `Completed/`. Reporting a
finding nobody is permitted to act on is worse than not reporting it — it
trains the reader to skim the check. So the sweep is scoped to plans in the
plan ROOT, with its own iteration rather than the shared
`journal_tree_targets` (which deliberately walks the archive for the naming
check).

That left one LIVE finding: `00163-Journal-26-07-14.md`. I nearly "fixed" it by
reordering, then checked `git blame` first — every entry was committed on
2026-07-14, so they are same-day entries whose sequence by PHASE (P1 → P2 → P3
→ P4 → delivery) is monotonic and correct while the clock readings are not.
Reordering would have scrambled the true work order to satisfy wrong
timestamps, in a record that is append-only by contract.

So: no backfill, mirroring Plan 00163 Decision 7. The sweep ignores day-files
NAMED before the rule shipped. The sweep still earns its registration after
that cutoff — it is the only half that sees a file written by something the
EDIT hook never observed: a Bash heredoc, a merge, an external tool.

Both exclusions have a test, because both are decisions a later reader could
reasonably mistake for oversights and "fix".

## 14:14 · finding · N1 — the cutoff silently did nothing on its first run

Wrote the cutoff as `(26, 9, 11)` to match the day-file name's `YY`.
`parse_journal_dayfile_name` expands it: `.year` is `2026`, so
`(2026, 7, 14) < (26, 9, 11)` is False and every file stayed in scope. The
sweep output was identical to before the guard existed, which is exactly the
shape of bug that gets shipped — a filter that matches nothing looks the same
as a filter that was never reached. Verified the parse rather than re-reasoning
about it; the constant is now four-digit with a comment saying why.
