# Plan 00377 — Journal 26-09-11

> **Append-only activity log** for plan 00377. One file per day
> (`00377-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM; NEVER edit earlier
> entries (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` local 24h (the date is in the filename); times increase down the file.
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 14:12 · decision · N1 — two blind spots, both deliberate, both guarded

The first sweep reported only ARCHIVED plans. Those cannot be fixed:
`archive-immutability` forbids editing a plan under `Completed/`. Reporting a
finding nobody is permitted to act on is worse than not reporting it — it
trains the reader to skim the check. So the sweep is scoped to plans in the
plan ROOT, with its own iteration rather than the shared
`journal_tree_targets` (which deliberately walks the archive for the naming
check).

That left one LIVE finding: `00163-Journal-26-07-14.md`. I nearly "fixed" it by
reordering, then checked `git blame` first — every entry was committed on
2026-07-14, so they are same-day entries whose sequence by PHASE (P1 → P2 → P3
→ P4 → delivery) is monotonic and correct while the clock readings are not.
Reordering would have scrambled the true work order to satisfy wrong
timestamps, in a record that is append-only by contract.

So: no backfill, mirroring Plan 00163 Decision 7. The sweep ignores day-files
NAMED before the rule shipped. The sweep still earns its registration after
that cutoff — it is the only half that sees a file written by something the
EDIT hook never observed: a Bash heredoc, a merge, an external tool.

Both exclusions have a test, because both are decisions a later reader could
reasonably mistake for oversights and "fix".

## 14:52 · finding · N7 — the commit describing N4's fix was denied as a force-push

Dogfooding caught its own guard. The commit-and-push for N4/N5 was denied:

```
BLOCKED [R-GIT-PUSH-FORCE]: `git push --force` / `git push <remote> +<refspec>`
This command PERMANENTLY DESTROYS data with NO recovery possible.
```

The command was `git commit -F - <<'EOF' … EOF && git push origin main`. No
force anywhere — the only `--force` was PROSE in the commit message, describing
the flag N4 had just added, inside a heredoc with a QUOTED delimiter that the
shell expands nothing in. The guard saw `git push` and `--force` in one command
string and joined them.

Recorded as N7 rather than just worked around, because the precedent for the
fix already exists in this codebase: `sed_blocker` exempts a `git commit`
message mentioning `sed`, and `pipe_blocker` exempts a quoted-delimiter heredoc
outright for exactly this reason. `destructive_git` lacks the equivalent.

The part that makes it more than an annoyance: the deny text asserts the
command "PERMANENTLY DESTROYS data with NO recovery possible" about a command
that does nothing of the kind. A guard that is confidently wrong about prose
teaches an agent to route around it, which is the opposite of what it is for.

Workaround used: commit and push as two separate calls. That is also mildly
against the standing cadence of committing AND pushing in one step, so the
inconvenience is real rather than cosmetic.

## 15:06 · decision · N6 — the hard part dissolved on inspection

N6's own text worried that a drift check cannot tell "the user edited this"
from "the template moved on". That is true for AGENTS, and is already solved
there: `classify_agent` resolves it with `historic_md5s`, so a deployed file
whose digest is a previously shipped revision is provably pristine (`OUTDATED`,
safe to refresh) and anything else is `CUSTOMISED`.

For the other two surfaces the question does not arise at all, which I had
assumed rather than checked:

```
core_docs.deploy_core_docs   "core documents are overwritten unconditionally"
plan_workflow._deploy_mkplan "Daemon-owned tooling, so it is overwritten on every upgrade"
plan_workflow._deploy_planlib "Daemon-owned tooling, like mkplan.bash: overwritten on every run"
```

Nothing protects a local edit to those files, so there is no customisation to
preserve and no ledger to build: deployed ≠ template IS drift, full stop. That
removes the only part of N6 that looked like it deserved its own plan.

Inventory for the check: agents (via `classify_agent`), the three
`CLAUDE/core/*.core.md`, `mkplan.bash`, `_planlib.inc.bash`. Client-owned
assets — `_TEMPLATE_.md`, `_JOURNAL_TEMPLATE_.md`, `PlanJournalling.md`,
README/CLAUDE.md, the core-doc overrides — are excluded by construction, not by
a list that can rot. Two false-positive traps to test: a core document whose

report, not this one's.

## 15:09 · finding · N7 — wider than it was reported

Reading `destructive_git` to fix N7: `matches()` tests the raw command against
every pattern, so the false positive is not specific to `--force`. A commit
message mentioning `--amend`, `reset --hard` or `clean -f` is denied the same
way; push-force is just the one I happened to hit.

The fix is therefore at the scan target, not the push pattern — blank the inert
spans once and run every pattern against the result, which is exactly what
`pipe_blocker.matches` already does via `_strip_inert_spans`. Checked the
existing suite first: no test asserts that a destructive flag inside a message
SHOULD block, and `git commit --amend -m 'fix typo'` stays blocked because the
`--amend` sits outside the message value. So the change subtracts false
positives without subtracting coverage.
