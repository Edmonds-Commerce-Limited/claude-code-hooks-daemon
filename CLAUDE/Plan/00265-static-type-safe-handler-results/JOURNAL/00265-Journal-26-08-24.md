## 10:14 · finding · — — the design was verified before the plan was written

The plan arose from a question during the response-contract work: whether Python
can do what PHP does with a wide interface type narrowed by each implementation.
Rather than answer from memory, two probes were run under this project's strict
mypy — one generic, one against the real `HookResult` and `Handler`.

Every deliberate violation was caught:

```
probe:28: error: Argument "decision" to "AdvisoryResult" has incompatible type
          "Literal[Decision.DENY]"; expected "Literal[Decision.ALLOW, Decision.CONTINUE]"  [arg-type]
probe:65: error: Return type "HookResult" of "handle" incompatible with return
          type "AdvisoryResult" in supertype "SessionStartHandler"  [override]
probe:69: error: "type[AdvisoryOnly]" has no attribute "deny"  [attr-defined]
probe:46: error: Incompatible return value type (got "WideResult", expected "AdvisoryResult")  [return-value]
```

The correct handler compiled clean with **nothing extra declared** — it inherits
the constraint from its event base. That is what separates this from the
AST-based guards shipped earlier today: those detect a bug someone already
wrote; this makes it unwritable.

## 10:16 · finding · P4 — Pydantic makes this stronger than the PHP equivalent

`validate_assignment` is already `True` on `HookResult`, so an out-of-tier
decision raises `ValidationError` on **both** construction and mutation:

```
validate_assignment: True
construct: rejected -> ValidationError
mutate:    rejected -> ValidationError
```

Consequence for Phase 4: `merge_pseudo_results` writes
`real.result.decision = Decision.DENY` directly. Under narrowed types that is a
type error AND a runtime raise — correct, since it is an unchecked path that can
write a decision the trigger's event cannot carry, but it means Phase 4 must
land BEFORE the trigger events are reparented. Otherwise dispatch starts raising
where it previously degraded silently.

## 10:18 · decision · — — per-event bases, not `Handler[ResultT]`

Both encodings type-check. They differ in what happens when a developer forgets:
a generic parameter must be declared per handler, so a forgotten declaration
silently loses protection — the exact failure mode this plan exists to remove. A
per-event base is inherited, so it cannot be forgotten, only actively overridden
(which mypy rejects as `[override]`).

## 10:41 · finding · P1 — `Decision.CONTINUE` is vestigial

While deciding which decisions belong in each tier, checked whether CONTINUE is
deliverable rather than assuming. It is — valid on all 31 events — but the
reason is that it does nothing:

- `grep -rn "Decision.CONTINUE" src/` returns **only** its own definition in
  `hook_result.py`. Every other `CONTINUE` hit in `src/` is either a comment or
  the unrelated `AUTO-CONTINUE` prose in the stop handler.
- No formatter branches on it, so it serialises to `{}` on every event.
- No response schema has a `continue` key, so it has no wire representation at
  all.
- `chain.py` and `verdict_log.py` both already class it with ALLOW as
  "lax"/"advisory".

So it is ALLOW-equivalent in practice. Included it in all three tiers: it IS
deliverable everywhere, and excluding it would break nothing today while being a
gratuitous incompatibility for any client handler that names it. Recorded here
rather than acted on — removing a public enum member is a separate decision.

## 10:52 · decision · P1 — `result_type_for_event` FAILS FAST on an unknown event

First implementation returned the advisory tier for an unrecognised event name,
because an unknown event resolves to `{ALLOW, CONTINUE}` which matches
`AdvisoryResult` exactly. The RED test caught it.

That default is the worst possible one: the wrong answer is indistinguishable
from the right one. A typo for a refusal-capable event would silently forbid
every handler built on it from denying. Now raises.

Deliberately the OPPOSITE policy to
`decision_capability.undeliverable_decisions`, which returns nothing for an
unknown event. That one is a diagnostic run against a CLIENT's handlers, where
refusing to judge is the safe failure; this one picks the type a handler is
built on, where guessing is not. Both docstrings say so, so the asymmetry does
not read as an inconsistency.

## 12:58 · action · P2 — Phase 2 complete: the constraint is now inherited

`core/handler_bases.py` adds three abstract tier bases (`AdvisoryHandler`,
`BlockingHandler`, `GatingHandler`) that re-declare `handle()` with the narrowed
return type, plus one alias per wired event. 113 unit tests, QA 23/23, daemon
RUNNING.

The measured payoff is that a handler now inherits the constraint with NOTHING
declared. Three new fixture cases prove it — all reported by a real mypy run:

```
decisions.py:71: error: Argument "decision" to "AdvisoryResult" has incompatible
  type "Literal[Decision.DENY]"  [arg-type]
decisions.py:86: error: Return type "HookResult" of "handle" incompatible with
  return type "AdvisoryResult" in supertype
  "claude_code_hooks_daemon.core.handler_bases.AdvisoryHandler"  [override]
decisions.py:103: error: Argument "decision" to "BlockingResult" has
  incompatible type "Literal[Decision.ASK]"  [arg-type]
```

The `[override]` line is the important one: it is the escape hatch closing. A
handler cannot widen its way back to plain `HookResult`.

### Decision: per-event names are ALIASES, not classes

Verified mypy enforces a narrowed return type identically through an alias —
the `[override]` error above was produced through `SessionStartHandlerBase`, and
mypy even names the real base (`AdvisoryHandler`) in the message. So an event
costs one line rather than a class body.

The aliases add no type-level strictness over the three tier classes. They exist
so a handler author never has to know which tier their event is in — precisely
the knowledge this plan removes the need for. Package-to-tier correctness is
enforced by the sweep in `test_handler_bases.py`, not by the naming.

`{Event}HandlerBase` rather than `{Event}Handler` because `WorktreeCreateHandler`
and `WorktreeRemoveHandler` are already concrete handler class names; a test
asserts no base name collides with a shipped handler, so the reason cannot be
quietly undone later.

### Finding: `[type-abstract]` rejects a container, not a return

The first cut of `handler_base_for_event` used a `dict[type[HookResult],
type[Handler]]` lookup and mypy reported three `[type-abstract]` errors — it
refuses an ABSTRACT class placed into a `type[X]` container literal. Probed the
exact boundary rather than guessing: RETURNING an abstract class from a function
annotated `-> type[Handler]` is fine; only the container is rejected.

These bases must stay abstract (a concrete `handle` stub would let a subclass
forget to implement it and silently inherit the stub), so the table is simply
not available. Rewrote as three direct returns and recorded why in the
docstring, so nobody "tidies" it back into a dict.

### Coverage the sweep adds

`TestEveryWiredEventHasABase` is parametrised over EVENT metadata, not over
existing handler packages — so an event that gains its first handler later
already has a correctly-tiered base waiting, rather than the gap being noticed
when someone writes the handler.

Next: **Phase 4, not Phase 3.** `merge_pseudo_results` mutates
`real.result.decision`; once trigger-event handlers are reparented that becomes
both a mypy error and a runtime `ValidationError`, so dispatch would start
raising where it previously degraded silently.

## 13:16 · action · P4 — the mutation path is closed

`merge_pseudo_results` now takes the REAL event name, clamps to what that event
can carry, and CONSTRUCTS the merged result instead of mutating one. QA 23/23,
daemon RUNNING, no errors in the log.

### `event_name` is required, not defaulted

The merge cannot be done correctly without it: a pseudo-event has no response of
its own, so its decision is delivered under the real event's, and triggers are
per-project CONFIG. The same handler is deliverable under one project's config
and dropped under another's.

Derived the deliverable set via `decisions_of(result_type_for_event(name))`
rather than calling `decisions_carried_by` directly — same answer, but that
route RAISES on an unknown event. `decisions_carried_by` resolves an unknown
name to `{ALLOW, CONTINUE}`, which is indistinguishable from a correct advisory
answer, so a typo would have clamped every refusal in silence. Same trap Phase 1
documented on `result_type_for_event`; worth writing down that it bites twice.

### Decision: clamp, don't discard

A clamped refusal keeps its message. The reason is appended to context — which
is exactly what an advisory event CAN deliver — and the clamp is logged at
ERROR naming the event and the decision.

The ERROR matters *because* nothing visibly breaks: the guidance still reaches
Claude, so a misbound refusing handler would otherwise look like it was working.
Deliberately did NOT invent a promotion (ASK→DENY on an event with no `ask`):
nothing else in the system does that, and inventing one here would make the
clamp stronger than what the handler asked for.

### Finding: the controller test could not have caught this

`test_pseudo_event_context_merged_into_result` built the chain result from a
`MagicMock`. A mock absorbs any operation the merge performs, so it could not
distinguish a working merge from a broken one — and when the merge switched from
mutating to constructing, the mock swallowed the `TypeError` into
`process_event`'s broad `except`, surfacing as a daemon-error result rather than
a merge failure.

Rebuilt it on a real `ChainExecutionResult`, and added a second test asserting
the CONTROLLER hands the merge the event it will serialise under. That pairing
is invisible in unit tests of the merge itself — only the controller can get it
wrong — and it now also asserts the result carries no daemon-error context, so a
swallowed crash cannot read as a successful clamp.

### API note for Phase 5

`merge_pseudo_results` is exported from `core`, so the required third argument is
a signature change to a public name. Nothing outside this repository is known to
call it (it is dispatch plumbing, not a project-handler extension point), but it
belongs in the truth-changes manifest with the rest of Phase 5.

Phase 3 is now unblocked: reparenting the trigger events can no longer make
dispatch raise.

## 13:35 · finding · — the sweep was blind to the commonest refusal shape

Found while working out what Phase 3 has to change: `decisions_referenced_by`
only recognised `Decision.DENY` as an attribute reference. It never saw
`HookResult.deny(...)` — which names neither the enum nor the member, and is
how most handlers actually refuse.

Measured before fixing, across this repository's 84 concrete handlers: exactly
one refused that way and the scan saw nothing (`PlanNumberHelperHandler`). It
cost nothing here only because that handler is on `PreToolUse`, which can deny.

**The gap that matters is the client's.** `validate-project-handlers` shares
this primitive, so a project handler refusing on `SessionStart` through the
factory passed the pre-flight check in silence — and a project handler is
exactly the population with no other guard.

DBF: the defect worth fixing was the blind guard, not the one handler. The scan
now recognises `<Something>Result.allow|deny|ask(...)`, matched by the `Result`
SUFFIX rather than a fixed class list, so the narrowed tiers, a future tier, and
a client's own `HookResult` subclass are all covered. `error` and
`configuration_error` are deliberately excluded — both are fail-open ALLOW, so
naming them would add noise and never a finding.

The sweep still passes with the wider detection, which is the useful part: it
now sees 39 of 84 handlers refusing, and none of them refuses on an event that
cannot carry it.

A `self.policy.deny(...)` lookalike does not match, because the receiver is an
Attribute rather than a Name — asserted, since a diagnostic a client is asked to
trust must not report a defect that is not there.

## 14:05 · decision · P3 — the factories decide whether Phase 3 is writable at all

Started Phase 3 and immediately hit the thing that decides its whole shape:
handlers build results with `allow`/`deny`/`ask`, not `__init__`. Those
classmethods construct via `cls(...)`, so `AdvisoryResult.allow()` has ALWAYS
returned an `AdvisoryResult` — but they were ANNOTATED `-> "HookResult"`, so
mypy typed the result as the wide class and rejected it from a handler declared
`-> AdvisoryResult`.

Probed the options against real mypy before choosing, and the probe changed the
answer:

- Annotating all three with `Self` makes the tiers usable, but
  `AdvisoryResult.deny(...)` then type-checks — the inherited method returns
  `Self` = `AdvisoryResult` — and only Pydantic stops it, at runtime, when that
  handler first executes.
- Leaving all three wide catches that, but breaks `allow` for every tier.

**So they are split deliberately.** `allow` returns `Self` on the base (safe:
ALLOW is deliverable on every event). `deny` and `ask` stay WIDE on the base,
and only the tiers that can actually refuse override them with a `Self` return.
`AdvisoryResult.deny(...)` therefore yields a `HookResult` and is rejected by the
handler's own return annotation. Recorded as an assertion, not a comment —
widening the base back would silently delete the static half while every runtime
test kept passing.

That last point is the reason for a second fixture file, `factory_forms.py`. It
pins BOTH directions: marked lines must error, and every unmarked line must NOT.
A violations-only fixture cannot express "this must compile", and that is exactly
the half that would otherwise be discovered by 84 handlers failing at once.
Every runtime assertion in `test_result_types.py` passed before this change and
after it, which is precisely why it could not have caught any of it.

### Finding: the pilot reparent broke two tests, and both were DRY debt

Reparenting the single `pre_compact` handler made two unrelated tests fail:
`test_all_pre_compact_handlers_in_config` and
`test_all_production_handlers_are_enabled`. Both reported a phantom handler
called `advisory`.

Cause: the four-condition "is this a discoverable handler?" predicate was
hand-copied FIVE times — three in `handlers/registry.py`, twice more in test
helpers — and the two copies in tests had drifted:

- one omitted `inspect.isabstract` entirely;
- the other substituted `"Base" not in attr.__name__`, which **cannot** work,
  because a per-event alias shares the class object: `PreCompactHandlerBase`
  reports its `__name__` as `AdvisoryHandler`.

Neither cost anything until a handler module first imported another `Handler`
subclass — which is exactly what reparenting does, 84 times over. Production
discovery was correct throughout (it has the abstract check), which is why the
daemon started fine while the tests failed.

Fixed at the root: one `is_discoverable_handler` TypeGuard in `registry.py`, used
by all five sites, with its own unit tests including the aliased-base case. Doing
this now rather than after the bulk reparent means the remaining 83 handlers
cannot re-trip it.
