## 07:32 · decision · P4 — backoff must have a cap, not silence

Considered making the cron back off indefinitely after N unproductive ticks.
Rejected: the cron exists to recover a session interrupted by a rate limit or
an API error, and in that case a LATER tick genuinely does help once the limit
lifts. Unbounded backoff would remove the feature's reason to exist. Exponential
with a ceiling (~4h) cuts the waste while preserving recovery, and a real user
message resets it — mirroring how a user message already clears the marker.

## 08:30 · decision · P4 — the ledger is the authority on "done", not the agent

Owner steer mid-session: should the cron stop once we hit a human blocker, or
once work is completely done? With the crucial caveat — "the completely done
bit is tricky because agents stop randomly all the time, why we have so many
stop systems" — and the observation that the `/goal` system is effective at
keeping agents running.

The two cases separate, and giving them the same answer would be a mistake:

- **Blocked on human** — safe to suppress. Terminal until input arrives, and a
  user message already clears the marker.
- **Work complete** — must NOT suppress on the agent's word. A false "done" is
  the commonest way an agent stops wrongly, and the cron is the net that
  catches it. Suppressing on self-report disables the net precisely when it is
  needed.

Verified before relying on it: `_goal_ledger_challenge()` (auto_continue_stop.py
:633) calls `GoalLedger.live_plan_numbers(plan_dir)`, which derives what is
owed from plan **Status on disk** — daemon-side state, not self-report, and it
names displaced goals the single-slot upstream `/goal` has forgotten. This
session is the demonstration: the stop hook blocked a stop and named Plan 00336
while it was In Progress.

So the cron should ask the LEDGER whether work is owed, not the agent whether
it is finished. Task 4.1 now carries the resulting truth table. This supersedes
the original Phase 4 framing, which keyed backoff on "consecutive unproductive
ticks" — that is a heuristic; the ledger is a state signal.

Recorded limit (Task 4.1b): the ledger tracks PLAN goals, so non-plan work is
invisible to it and "no goals owed" is not proof of idleness. Hence the
no-owed/no-declaration case backs off rather than silencing.

## 16:00 · thought · P3/P4 — the precedent is real but it does not transfer whole

Task 3.3 asks for `ASKING BECAUSE:` to be cited as the in-project precedent
for an explicit agent-facing declaration. Read rather than assumed, and it
supports the principle while breaking on the mechanism.

`ask_user_question_blocker` (Plan 00108) requires the prefix on every
`question` string and DENIES the tool call without it, with a `strict` /
`advisory` mode pair so a project can dogfood the convention before turning on
hard blocking. Its own docstring says it "mirrors the Stop handler's
`STOPPING BECAUSE:` convention", so the family already exists.

Where it does not transfer: `ASKING BECAUSE:` is a **gate**. The agent wants
something (to ask a question), and the declaration is the price. Phase 3's
token is a **state marker** — the agent gains nothing by declaring, and the
daemon cannot deny a stop for failing to declare a state the agent may
genuinely not be in. So the token can never be mandatory the way the precedent
is; it will always be opt-in.

That has an ordering consequence worth stating before anyone builds it: Phase
3 makes arming RELIABLE for an agent that co-operates, and does nothing at all
for one that does not. Phase 4 — the ledger-driven backoff — is the half that
needs no co-operation, which is what makes it the load-bearing fix and Phase 3
the optimisation on top. The plan's Goals already say this ("even when the
agent declares nothing"); this is the argument for why the phase ORDER should
not be read as a priority order.

The `strict`/`advisory` rollout, on the other hand, transfers directly and is
worth reusing: ship the token recognised-but-unadvertised first, confirm it
arms, then document it.

## 16:15 · decision · T4.4 — the backoff folds into the suppressor, on position

Task 4.4 asks whether a third state-holder is justified against folding the
backoff into `failsafe_cron_blockage_suppressor`. Read both, and the answer is
not a preference — it falls out of where each handler sits in the event flow.

A backoff has to do four things: see every delivered tick, see every real user
prompt (to reset), hold a counter across ticks, and be able to drop a tick.
`failsafe_cron_blockage_suppressor` already does all four:

- `matches()` fires on the canonical cron prompt AND on any real prompt while
  a marker exists, so both edges of the reset are already on its path.
- `handle()` already branches on `is_cron_prompt`, already clears state on a
  genuine prompt, and already returns DENY to erase a tick before the model.
- It has an injectable clock (`self._clock`), which a backoff needs and which
  tests already substitute.
- It is fail-open throughout, which a cadence controller must be — a backoff
  bug that suppressed everything would silently disable recovery.

`recovery_cron_advisor` owns the cron's LIFECYCLE (create, reuse, delete
advice). It never sees a delivered tick as a prompt, so it cannot count them.
A third handler would have to re-derive the tick-recognition and the
prompt-reset that already exist here.

One thing that does NOT fold, and should be designed rather than assumed: the
backoff counter cannot live in the existing marker. The marker is cleared on
any real prompt and is absent whenever the agent has declared nothing — and
the truth table's bottom row ("no goals owed, no declaration → back off hard")
is precisely the case with NO marker. So the counter needs its own persistence
with its own lifetime; sharing the file would make the state vanish exactly
when it is needed.

## 16:30 · finding · T4.1 — the ledger answers a narrower question than the plan assumes

Read `live_plan_numbers` rather than trusting the summary in Task 4.1, and it
is narrower in two ways that both bias it towards "nothing owed" — the
direction that makes the cron back off.

```python
live = {
    e.plan_number
    for e in entries
    if e.retired_at is None and states.get(e.plan_number) == _STATE_IN_PROGRESS
}
```

**It only knows LEDGERED plans.** `entries` is the ledger's own contents, so a
plan is visible only if a `/goal` was ever set for it. Work on a plan that
never got one is invisible.

**Only `In Progress` counts.** The state resolver maps `Not Started` to
`_STATE_OTHER`; only `PlanStatus.IN_PROGRESS` yields `_STATE_IN_PROGRESS`.

Those combine into a concrete failure the truth table would walk straight
into, and it is the same rot Plan 00341 was just filed for: a plan being
ACTIVELY WORKED whose header still reads `Not Started` is not counted as owed.
The cron would read "no goals owed", find no declaration either, and take the
bottom row — back off hard — on a session that is working normally. That is
the opposite of what the row is for.

Two consequences for Phase 4, both recorded rather than fixed here:

- Task 4.1b's stated limit ("the ledger tracks PLAN goals, so non-plan work is
  invisible") is real but understates it. Even PLAN work is invisible if the
  plan was never ledgered or its header has rotted.
- This is a dependency on Plan 00341, not a coincidence. 00341 makes
  `Not Started` falsifiable; until it lands, the ledger's "owed" signal has a
  known blind spot that Phase 4 would inherit and amplify — a stale header
  currently costs a reader some confusion, and under Phase 4 it would cost the

## 17:25 · decision · T3.1 — the bracketed token, and one alternative is not ours to choose

Task 3.1 asks for the three candidates to be compared and the winner argued.
One of them turns out not to be on the table at all.

**A structured hook field is not available.** The Stop hook's input schema is
Claude Code's, not the daemon's — `HookInputField` documents the fields the
host SENDS (`session_id`, `transcript_path`, `prompt`, …) and the daemon reads
them. There is no mechanism for us to add a field an agent could populate.
This would be an upstream change, so it is out of scope rather than rejected
on merit.

**A dedicated tool is real but costs more than it saves.** A tool call is
unambiguous and visible to `PreToolUse` with no text matching at all, which is
genuinely better on precision. Against it: it adds permanent surface to the
tool inventory, which this project is actively trying to SHRINK (Plan 00293),
and — the decisive part — a tool call is not a stop. The agent would have to
call the tool AND then stop, so a declaration that exists to describe a stop
would be split across two acts, with the failure mode of one happening without
the other.

**The bracketed token wins on composition.** `STOPPING BECAUSE: [awaiting-human]
…` rides a line the agent already emits, is matched by exact string rather
than by NLP, adds no surface, and reads acceptably to a human. Anchoring it
directly after the prefix is deliberate: the position is unambiguous to match
and is not something prose produces by accident.

The comparison is also settled by Task 3.3's conclusion. The token is a state
marker, so it is permanently opt-in — and for an OPTIONAL declaration, minimum
friction is the dominant criterion. That is exactly what the tool option
fails: nobody makes an extra tool call to volunteer information.

## 18:30 · decision · P4 — the cadence algorithm, written out before it is built

Phase 4 is the load-bearing half (Task 3.3), so the algorithm is settled here
rather than discovered during implementation. Everything below follows from
Task 4.1's truth table plus the two constraints already established: the
counter cannot share the marker file (Task 4.4), and the ledger's "owed"
signal has a known blind spot (Task 4.1b).

**Inputs, both already reachable inside the suppressor.**

- `declared` — a valid marker for this session, which is exactly what
  `marker_is_valid(...)` already computes in `handle()`.
- `owed` — `GoalLedger.live_plan_numbers(plan_dir)` being non-empty.

**The rows, and what each does.**

| owed | declared | action                                        |
| ---- | -------- | --------------------------------------------- |
| yes  | no       | ALLOW every tick, reset cadence to hourly     |
| yes  | yes      | back off, capped                              |
| no   | yes      | DENY — today's behaviour, reset cadence       |
| no   | no       | back off, capped                              |
Row 1 is the net doing its job: work is owed and the agent has not said it is
blocked, so it most likely stopped wrongly and the tick is the correction. It
must never be backed off — that is the case the cron exists for.

Row 3 stays exactly as it is today. Suppression there is already correct and
already tested; Phase 4 must not perturb it.

**The backoff, for rows 2 and 4.** State is a separate file under the daemon's
untracked dir, session-scoped like the marker but with its own lifetime:

```
{"session_id": ..., "dropped_since_allowed": int, "cadence_hours": int}
```

On a tick in a backoff row: if `dropped_since_allowed + 1 < cadence_hours`,
DENY and increment. Otherwise ALLOW, reset `dropped_since_allowed` to 0, and
double `cadence_hours` capped at 4. So the tick pattern is hourly, then every
2h, then every 4h, and never sparser — Task 4.2's ceiling, never silence.

**Resets.** Any genuine (non-cron) prompt resets `cadence_hours` to 1 and the
counter to 0, in the same branch that already clears the marker (Task 4.3).
Rows 1 and 3 also reset, so a session that starts producing again, or that
declares a real blockage, does not carry stale backoff into its next phase.

**Two things to be careful about when building it.**

- Fail-open, like every other path in this handler. If the state file is
  unreadable or the ledger raises, ALLOW the tick. A cadence bug that denied
  everything would silently disable recovery, which is worse than a wasted
  turn — and would be invisible, because the symptom is nothing happening.
- Row 4 must never become row 3. "No goals owed and nothing declared" is the
  case where the ledger's blind spot bites (a plan never ledgered, or one
  whose header has rotted to `Not Started`), so it backs off rather than
  suppressing. That is the whole reason the bottom row is not "silence".

## 18:40 · finding · P4 — the suppressor cannot reach the ledger yet

Traced the exact call the suppressor will have to make, because "consult the
ledger" is one line in the plan and two prerequisites in the code.

`auto_continue_stop._goal_ledger_challenge()` does:

```python
ledger_path = ProjectContext.daemon_untracked_dir() / LEDGER_FILENAME
plan_dir = resolve_plan_dir(ProjectContext.project_root(), self._track_plans_in_project)
live = GoalLedger(ledger_path).live_plan_numbers(plan_dir)
```

`self._track_plans_in_project` is not something a handler declares — the
registry injects it, and the injection is gated:

```python
if plan_workflow is not None and "planning" in instance.tags:
```

`FailsafeCronBlockageSuppressorHandler` is tagged `WORKFLOW`, `AUTOMATION`,
`NON_TERMINAL`, `BLOCKING` — **no `PLANNING`**. So today it would read an
attribute that was never set.

Two ways out, and the choice is not obvious:

- Add `HandlerTag.PLANNING`. Semantically honest once the handler reads plan
  status, and it inherits the whole injected bundle. But tags drive filtering
  and reporting elsewhere, so this is a behaviour change beyond the one line
  and needs its own check.
- Resolve the plan dir independently and leave the tags alone. Narrower, but
  duplicates a resolution the registry already performs — the kind of second
  copy that drifts.

Recorded now rather than met mid-implementation. Either way Phase 4 must keep
its fail-open promise: if the attribute is missing, `resolve_plan_dir` falls
back to `PlanWorkflowConfig().directory`, so the failure mode is "wrong
directory, no goals found, back off" — which is the WRONG direction, since
backing off is what a missing signal biases towards. So the ledger consult
needs an explicit "could not determine" state distinct from "nothing owed",
and "could not determine" must behave like row 1 (tick), not row 4.

## 18:55 · decision · T5.0 — the discriminator is the transcript's size, not a turn id

Task 5.0 says "add a session/turn discriminator". Looked at what
`_log_stop_event` can cheaply reach, and there is a better answer than the
obvious one.

`session_id` is free — already in `hook_input` — and worth adding, but on its
own it only separates SESSIONS. It cannot tell two stops within one session
apart, which is precisely the ambiguity Task 5.1 is stuck on: is a pair of
records three seconds apart one stop logged twice, or a fast text-only turn
that stopped again?

**The transcript's byte size settles it.** The transcript is append-only, so
its size is monotonic within a session and reachable in O(1) via `stat` — no
parsing, no read. Two records with the SAME size are the same logical stop
re-fired, because nothing was appended between them. A larger size means the
model genuinely produced something.

So the entry gains `session_id` and `transcript_bytes`, and Task 5.1's
classification becomes arithmetic over the ledger rather than a transcript
correlation:

- equal size → a hook re-fire, not a turn (today's 43 sub-second pairs, and
  probably much of the 50 sub-ten-second bucket)
- grew a little → a text-only turn that stopped again — the actual waste
- grew a lot → work happened, so the DENY was productive

Cheap, and it makes the measurement repeatable instead of a one-off audit.
Both fields must keep the existing failure contract: `_log_stop_event`
swallows its own errors, so a missing transcript or a failed `stat` leaves the
field out rather than breaking the log line.
