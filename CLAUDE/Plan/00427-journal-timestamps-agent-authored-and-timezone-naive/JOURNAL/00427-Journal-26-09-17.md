## 09:38 · finding · — — the reported mechanism is not the implemented one

Issue #45 states the check "judges each writer against that writer's own
clock", so both writers pass. The check runs in `PlanQaEditHandler`, a
`PreToolUse` handler — it executes in the DAEMON process. One clock judges
every writer.

Measured against the real check with a one-hour offset:

```
tolerance = 30 min, future direction only

daemon UTC  vs agent BST (10:35): ahead=+59min  fires=True
daemon UTC  vs agent UTC (09:35): ahead=-1min   fires=False
daemon BST  vs agent BST (10:35): ahead=-1min   fires=False
daemon BST  vs agent UTC (09:35): ahead=-61min  fires=False
```

The consequence the reporter cares about survives — an agent BEHIND the daemon
is silent and its entry lands out of order — but via a different route, and
there is a second symptom they did not report: an agent AHEAD of the daemon is
flagged for a timestamp that is correct in its own zone.

This matters for remedy selection. "The check is blind" invites fixing the
check; "the check is blind in one direction because the entry and the clock are
in different zones and nothing records which" points at the grammar.

The reporter's own fixture reproduces exactly as described — 59.99 minutes
apart for a single instant.

## 11:57 · finding · —   — UTC stamps judged by a local clock: the check fires west of UTC

Success criterion 4 asked for the opposite-direction symptom to be checked
too, "not just the silent direction". Checking it turns up a regression
Phase 2 introduces, and the tests cannot see it because this container runs
UTC.

`--journal` now stamps entries in UTC. `journal_entry_future_dated._now()`
still returns `datetime.now()` — a naive LOCAL clock — and the entry time is
rebuilt naive from the UTC day-file name. So the check compares a UTC reading
against a local one. Measured at one instant, tolerance 30 minutes:

```
UTC-stamped entry: 2026-09-17 11:56
host zone             local now          ahead (min)   fires?
UTC                   2026-09-17 11:56            -1   no
Europe/London         2026-09-17 12:56           -61   no
Europe/Berlin         2026-09-17 13:56          -121   no
America/New_York      2026-09-17 07:56          +239   YES
America/Los_Angeles   2026-09-17 04:56          +419   YES
Asia/Tokyo            2026-09-17 20:56          -541   no
```

Every host WEST of UTC now gets the advisory on every scaffolded entry — a
permanently-firing finding on correct data, which is precisely the failure
mode this check's own docstring says it was designed around when it declined
to dual-register.

Before Phase 2 this was rare (it needed a genuinely cross-zone pair). After
Phase 2 it is deterministic for a whole class of hosts, so the plan is not
complete: Phase 2 shipped a correct writer and left the reader judging it by
the wrong clock.

The fix the sentinel already makes available: the day-file says which clock it
was written by. A file carrying `timestamps in this file are UTC` should be
judged against a UTC now; a file without it is legacy-local and keeps the
local clock. That is the sentinel earning its keep rather than being merely
informational, and it needs no migration.

Not built yet — the full QA suite is mid-run and mutating `src/` under it
would make its result unreadable.

## 12:01 · action · —   — Phase 3: the reader now uses the writer's clock

Phase 3 built: the check now picks its clock from the day-file.

`_utc_now()` alongside `_now()`, and `_is_utc_dayfile()` looking for
`timestamps in this file are UTC`. Sentinel present ⇒ UTC; absent ⇒ the
existing local clock, because a legacy file's times really are local. No
migration, no existing day-file touched.

RED was genuine — `AttributeError: ... has no attribute '_utc_now'` on all
three new cases before the source existed.

to DISAGREE (local 14:00, UTC 20:00, entry 16:44) so that reporting the finding
