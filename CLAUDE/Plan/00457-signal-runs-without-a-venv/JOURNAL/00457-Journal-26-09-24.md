>   one-line takeaway above the fence.

## 09:48 · decision · T1.2 — extracted `is_self_install_mode`/
`get_untracked_dir` to `daemon/paths.py`; loaded by file path, not import

Found a pre-existing near-duplicate: `daemon/paths.py::_get_untracked_dir`
already computed the identical self-install/untracked-dir logic
independently of `ProjectContext.initialize`'s inline copy — two
definitions of one rule, not the plan's fault but exactly what it asked
to fix. Added a public `is_self_install_mode()`, refactored
`_get_untracked_dir` to call it, and refactored
`ProjectContext.initialize()` (deferred import, matching the existing
`_get_git_repo_name` circular-import pattern — `daemon/server.py` imports
`ProjectContext` back) to call both instead of its own inline check. Both
now share ONE definition; `tests/unit/core/test_project_context.py` and
the new `tests/unit/daemon/test_paths_untracked_dir_resolution.py` both
green.

**The real obstacle, discovered empirically**: `operator_signal.py` is
stdlib-only, but `import claude_code_hooks_daemon.utils.operator_signal`
still executes `claude_code_hooks_daemon/__init__.py` first (Python
always initialises a dotted import's parent packages) —
`core/front_controller` -> `core/acceptance_test` ->
`core/hook_result` -> `from pydantic import ...`, confirmed by running it
under `/usr/bin/python3` with `PYTHONPATH=src`: `ModuleNotFoundError: No
module named 'pydantic'`. "The writer only needs the stdlib" (the
proposal's and the triage's framing) is true of the FILE, not of
importing it by its real dotted name.

Fix: `daemon/signal_standalone.py` loads `temp_names.py`,
`operator_signal.py` and `daemon/paths.py` directly by file path
(`importlib.util.spec_from_file_location`), registering each under its
REAL dotted name in `sys.modules` BEFORE executing it — so
`operator_signal.py`'s own `from
claude_code_hooks_daemon.utils.temp_names import ...` resolves from that
cache (Python checks `sys.modules` for the full dotted name before ever
touching a parent package) rather than triggering a real package import.
`paths.py` needed no such pre-caching (no `claude_code_hooks_daemon`
imports of its own at module scope — confirmed by grep; its two
package-internal imports, `process_verification` and `retention`, are
both function-local and never called by the two functions this module
uses).

Reused, not re-implemented: `operator_signal.py` gained
`validate_signal_request()` and `run_signal_cli()` (the full
validate-target-write body, extracted from `cmd_signal`); `cmd_signal`
(`daemon/cli.py`) now calls `validate_signal_request` first (preserving
its fail-fast-before-`ProjectContext` ordering) and delegates to
`run_signal_cli` for the rest, so the two entry points share one
function and cannot drift. `daemon/signal_standalone.py:main()` is a thin
adapter: parse args (`--project-root` REQUIRED — the CWD walk-up needs
the full config-loading path this module exists to avoid, documented in
its module docstring), resolve `untracked_dir` via the loaded
`paths.get_untracked_dir`, call the same `run_signal_cli`.

**Minimum Python version: 3.10**, not the project's stated 3.11 floor —
the binding constraint is `daemon/paths.py`'s bare `X | Y` return/param
annotations with no `from __future__ import annotations`, evaluated at
function-definition time. `operator_signal.py`/`temp_names.py` both defer
annotations and need nothing past ~3.8 (`typing.Final`) on their own.
Pinned by `tests/unit/daemon/test_signal_standalone.py::TestSyntaxFloor`
(`ast.parse(..., feature_version=(3, 10))` over all four files: the entry
point itself, `paths.py`, `operator_signal.py`, `temp_names.py`).

## 10:48 · decision · T1.2 — team-lead review: floor lowered to 3.8 via a
new tiny `install_layout.py`, not `daemon/paths.py`

Team-lead review (relayed, not a plan change): loading all of
`daemon/paths.py` to reach two small functions cost two things worth
fixing before acceptance -- (1) it set the floor at 3.10 purely because
of `paths.py`'s OWN bare `X | Y` annotations, unrelated to the two
functions actually used, and 3.10 is above what common host distros ship
(Debian 11: 3.9, Ubuntu 20.04: 3.8) -- exactly the "silently cannot run
on the host" failure #55 exists to fix; (2) any future third-party import
landing anywhere in `paths.py`'s 1,800+ lines would break host
signalling, guarded only by one syntax test.

Fix: extracted `is_self_install_mode`/`get_untracked_dir` out of
`daemon/paths.py` into a NEW module, `daemon/install_layout.py` --
standard-library-only, `from __future__ import annotations`, ZERO
`claude_code_hooks_daemon` imports of its own. `daemon/paths.py` now
loads it by FILE PATH too (not a dotted import) and delegates
`is_self_install_mode`/`_get_untracked_dir` to it, keeping its existing
public names working. This was necessary, not optional: `paths.py` is
ITSELF run standalone by `resolve_venv.sh`
(`python3 paths.py resolve-venv ...`) during fresh-clone bootstrap with
no venv and nothing on `sys.path` -- a plain
`from claude_code_hooks_daemon.daemon.install_layout import ...` at
paths.py's own top level would have broken THAT bootstrap path exactly
the way this plan exists to fix for `signal`. `ProjectContext.initialize`
now imports `install_layout` directly (still a deferred/function-local
import -- the `daemon/server.py` circular-import concern is about the
`claude_code_hooks_daemon.daemon` PACKAGE, not which submodule inside it,
so it applies regardless of target). `signal_standalone.py` loads
`install_layout.py` instead of `daemon/paths.py`.

**Re-derived floor: Python 3.8**, not 3.10. Driven by
`operator_signal.py`'s `from typing import Final` (added 3.8) -- `Final`
is used only inside deferred (string) annotations thanks to
`from __future__ import annotations`, but the IMPORT STATEMENT itself
still executes eagerly at module load and needs the name to exist.
`temp_names.py` and the new `install_layout.py` both need nothing above
~3.6 (f-strings) on their own. Re-pinned across all four files signal_standalone.py
now loads (itself, `install_layout.py`, `operator_signal.py`,
`temp_names.py`) via `TestSyntaxFloor`.

Added `_check_python_version()` (parameterised on `version_info`, default
the real interpreter) as the FIRST thing `signal_standalone.py` does at
module scope, before the `operator_signal.py` load that would otherwise
raise a confusing `ImportError` deep in a file the caller never asked to
look at -- prints a clear message naming both versions and exits 1.
Parameterised specifically because `sys.version_info` is a read-only
structseq and cannot be monkeypatched for a black-box test; new
`TestVersionFloorEnforcement` in `tests/unit/daemon/test_signal_standalone.py`
calls it directly with synthetic `(3, 7)`/`(3, 8)`/`(3, 11)` tuples via
`runpy.run_path`.
