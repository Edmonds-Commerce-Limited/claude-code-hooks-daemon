## 12:10 · decision · T1.1 — the chain key is an explicit `id`, not semantic matching

Delivered under Plan 00362 Task 2.7 (ledger item D13), which owns the
supersession half of this plan. The `was`/`now` schema carries nothing that
identifies a truth across releases — `was` text is by construction the
PREVIOUS `now` reworded, so no field is stable — so the schema gains an
optional `id: kebab-slug` naming the truth. Entries sharing an `id` across
the loaded range form a chain; `collapse_superseded` surfaces the
highest-version link, marked `(v3.26.0, revised in v3.23.0, v3.25.0)
[plan-creation]`, and the report header tells the agent to reconcile any
earlier form to the same `now`. Both text and JSON formats collapse.

Rejected: semantic/text matching (non-deterministic, and the LLM would then be
asked to trust a machine's guess about which of its own instructions to skip);
a `supersedes: <version>` pointer (works, but every link must know its
predecessor's version, so a back-fill touches N files instead of tagging N
entries with one slug, and a chain that skips a release needs the author to
look it up). `topic:` as the plan suggested is the same thing as `id`; `id`
was chosen because a slug names ONE truth, whereas a topic invites grouping
several truths under one key and collapsing entries that do not supersede
each other.

## 12:12 · decision · T1.2 — un-keyed entries pass through untouched

An entry with no `id` is surfaced as before, never collapsed (not even two
with identical text), and never interferes with a keyed neighbour. A blank
`id`, or the same `id` twice in one file, is a load error — one release
revises a truth at most once, and "stands alone" must be written as an absent
key so the choice is visible.
