## 22:30 · finding · T0.2 — what Claude Code does with an oversized result

Checked first for a vendored copy: this repo has no `remote-docs/` tree yet
(`R-REMOTE-DOCS-VENDORED-COPY` has nothing to point at). Then the public
docs, then the installed binary, then a direct probe. Three sources agree.

**Source 1 — Claude Code docs, "Bash tool behavior › Output limits"**
(https://code.claude.com/docs/en/tools-reference, fetched today):

> Valid — Inline up to roughly 30,000 characters by default; past that, the
> path of a file saved to the session directory and truncated past 64 MiB,
> plus a short preview from the start, and Claude reads or searches the file
> when it needs the rest.
> Failure — Inline up to roughly 10,000 characters; past that, a
> head-and-tail excerpt of that size cut from the read-back window, with no
> file path.
> A command that exits 1 counts as a valid result for the Bash tool only when
> Claude Code recognizes exit code 1 as a benign outcome for that command:
> `grep`, `rg`, `egrep`, `fgrep`, `find`, `diff`, `test`, and `[`, plus
> `git diff` and `git grep`. Every other command that exits 1 counts as a
> failure.

`BASH_MAX_OUTPUT_LENGTH` (default 30,000, ceiling 150,000) sizes only the
read-back window; `bashOutputMaxChars` (v2.1.261+, up to 128,000) sizes the
inline ceiling too. Neither changes the failure-path shape.

**Source 2 — the installed binary**, `@anthropic-ai/claude-code` 2.1.267
(`/usr/local/lib/node_modules/@anthropic-ai/claude-code/bin/claude.exe`),
string-searched: the valid-path wrapper is a `<persisted-output>` block —
`Output too large (N). Full output saved to: PATH` then `Preview (first
2000):` — with the preview constant hard-coded at 2,000 characters, and the
settings-schema text "Output past this is saved to a file and Claude
receives a short preview plus the path" (default 30000, clamp 4000–128000).
MCP results are a different mechanism again: `[OUTPUT TRUNCATED - exceeded N
token limit]` under `MAX_MCP_OUTPUT_TOKENS` (default 25,000 tokens).

**Source 3 — a direct probe in this session.** A command printing 700
numbered 51-byte lines (35,700 bytes) and exiting 1 came back as lines
1–98, then `... [20012 characters truncated] ...`, then lines 492–589. No
file path. Lines 590–700 were never read back at all (the 30,000-character
window), and lines 99–491 were cut from what was.

**What this means for the two reports.** Both `check-truth-changes` and
`check-config-migrations` exit 1 precisely when they have something to say,
and neither is on the benign-exit-1 list, so their output takes the
FAILURE path: ~5 KB head, ~5 KB tail, the middle silently DROPPED, no file
to go back to. On the full span that is 90 KB in, ~10 KB out — roughly 60
of 71 truth-change entries never reach the agent, and there is no marker in
the delivered text saying which ones. That is truncation, not skimming; the
plan's Task 0.2 remedy split resolves to "instructions are dropped".

`upgrade.sh` itself exits 0, so its 143 KB takes the VALID path: persisted
to a file, with a 2,000-character preview from the START. The
`UPGRADE_METADATA` block that step 2 of the skill parses is the last 713
bytes — the preview never contains it. An agent following the skill
literally must read the persisted file to find `from_version`/`to_version`,
and the file it is pointed at is 143 KB.

## 22:40 · decision · P2,P3 — the bound, and the shape of the fix

- **The bound is 8,000 bytes of stdout per report command**, a constant in
  code and pinned by test. It sits under the ~10,000-character failure-path
  ceiling with headroom (the docs say "roughly"), so the bounded form
  survives whichever path the harness takes and regardless of
  `BASH_MAX_OUTPUT_LENGTH`/`bashOutputMaxChars`. The exit-code contract (0
  nothing / 1 entries / 2 error) is unchanged: every caller — the skill,
  `upgrade.sh`, `optimise-invoke.sh` — keys on it, and a bounded result
  under 10 KB is delivered whole on either path.
- **Full report to a file, summary to stdout** — the `echd-capture` /
  `subagent_report_size_blocker` idiom. Default location
  `<project_root>/untracked/truth-changes/` (and `untracked/config-changes/`
  for the advisory); `untracked/` is what the installer git-ignores in a
  client. `--report-dir` overrides; `--full` restores the whole report
  inline for a human or a pipeline that asked for it.
- **Both commands get the offload.** Phase 0 showed `check-config-migrations`
  is the larger of the two on a routine hop (38 KB vs the 30-ish KB a hop of
  truth-changes runs to) and is truncated by the same path.
- **Chunks are files, one per topic**, written next to the full report,
  each self-contained: the reconciliation rules, the entries, and the
  return contract ("report the files you changed, one line each — not the
  entries you read"). The summary lists the chunk files, so the coordinator
  never holds an entry — only paths and counts.
- **The chunk key is a `topic:` on the entry, falling back to its `id`.**
  `id` names ONE truth (Plan 00362's decision stands: an `id` shared by two
  entries means "the later supersedes the earlier"), so it cannot also mean
  "these entries edit the same documents" — that is a coarser grouping, and
  it needs a key that never collapses. `topic` is that key. A keyed entry
  with no topic is its own chunk (the plan's "keyed by the id slug"). An
  entry with neither goes into a single `unassigned` chunk that the summary
  marks SEQUENTIAL: its documents are unknown, so it must run alone, after
  the topic chunks return, never alongside them.
- **The corpus gets `topic:` back-filled**, all 74 entries. Without it every
  entry lands in the sequential chunk and Phase 3 delivers nothing; with it
  the parallel dispatch is real. This is additive (no `was`/`now` text
  changes) and, unlike an `id` back-fill, a wrong topic cannot drop an
  instruction — the worst case is two subagents editing one file, and an
  `Edit` whose `old_string` has moved fails loudly rather than corrupting.
  The Non-Goal about rewriting the corpus was written for Phase 1's key;
  Phase 1 did not need it, Phase 3 does.

## 23:10 · decision · T3.3 — what "disjoint in the documents they touch" can and cannot mean

A client's documents are not visible to the daemon, so disjointness cannot
be computed; it is a CONTRACT the manifest author makes when choosing a
topic, stated in the schema README ("two truths that could edit the same
project document must share a topic"). What the code proves is the
structural half: every surfaced entry lands in exactly one chunk, chunk
keys are unique, and the shipped corpus has no unassigned entry
(`TestRealCorpusTopics`). The failure mode if an author gets a topic wrong
is two subagents editing one file, and the tools make that loud rather than
silent: an `Edit` whose `old_string` has moved fails. The skill's dispatch
rules and the SEQUENTIAL chunk are the second line of defence.
