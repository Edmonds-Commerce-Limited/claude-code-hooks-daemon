## 19:40 · finding · T2.1 — settings.json fails on an unmeasured premise

Evaluated `~/.claude/settings.json` as Task 2.1 asked. It holds the family and
the daemon already has an mtime-cached reader for it
(`handlers/status_line/settings_reader.py`), so the plumbing would be nearly
free — and it is still the wrong signal. Three defects, written up in
`DETECTION-CHANNELS.md`; the third is disqualifying.

The reproduction's own evidence turns out not to support what it was cited for.
It read settings.json mtime 07:58:56 as the human's pick landing. But `/effort
low` was injected at 07:58:56 and effort writes the same file (`effortLevel`
plus the per-model `modelSettings` block), so that timestamp attributes to
either cause. Only a change in the `model` VALUE is usable, not the mtime.

And the value cannot discriminate unless the automatic downgrade does not write
`model`. Nothing measured says it does not. Both candidate causes predict
`opus`, which is what the file held. The product behaviour argues for it — the
key is "your default for new sessions", and silently rewriting a persisted
default off one downgraded request would be a real bug — but that is an
argument, and this repo has been burned twice this fortnight substituting one
for a measurement (00341's replay found a 25% false-positive shape, 00343's
found 7 of 18).

If the premise is false, settings.json reports "the human chose opus" for every
automatic downgrade, the auto-restore quietly becomes dead code, and it looks
like success from the outside.

## 19:46 · finding · T2.1 — Claude Code already writes the automatic downgrade down

Looking for a way to measure the premise, found the thing the premise was a
proxy for. Claude Code emits the safety downgrade into the session transcript
as a structured record, and this daemon **already parses that exact shape** in
`handlers/session_start/model_fallback_detector.py`. It was simply never wired
to the supervisor.

Scanned all 25 transcripts under `~/.claude/projects/-workspace/`. 25 genuine
records, three sessions, 2026-08-26 to 2026-09-02, every one the fable security
downgrade this plan exists for:

```json
{"originalModel": "claude-fable-5", "fallbackModel": "claude-opus-4-8",
 "apiRefusalCategory": "cyber", "scope": "session",
 "ts": "2026-08-27T09:34:10.341Z"}
```

Uniform across all 25 — same pair, same category, same scope. Two shapes per
event: a `fallback` content block in the assistant message, then a standalone
`subtype` record 7–90s later (13 blocks / 12 subtypes, so they pair but not
exactly; a consumer takes either and dedupes).

## 19:52 · decision · T2.2/T2.3 — arm positively, and the question changes shape

The plan has been asking the harder question. Everything built so far tries to
recognise the HUMAN so the restore can be suppressed — a negative inference
("the family changed and I did not cause it, so a human did") that needs the
set of non-human causes to be closed and observable. That is why it keeps
failing: 00316 inferred it from keystrokes the picker never emits, and both
`note_model_reading` and `downgrade_state.py` infer it from a high-water mark
that a human picking opus reproduces exactly.

The owner's scope ruling makes the positive form available: the restore
counteracts the automated fable security downgrade and nothing else. Arm on the
transcript record and a human change needs no recognition at all — it emits no
such record.

That reorders Phase 2. Old 2.2 (delete the keystroke machinery *if* 2.1 is
sound) becomes new 2.3 and gets bigger: the typed parser, stem match, picker
wildcard, its session key and the restore-steal guard all answer "was that the
human?", and that question stops being asked, so they are redundant rather than
replaced. Old 2.3 (fall back to Phase 1 only) is dropped — it was the branch
for "no sound channel exists", and one does.

Two constraints on the build, both recorded on the task so they are not
rediscovered:

- The status-line event does NOT carry `transcript_path` — nothing under
  `handlers/status_line/` references it — so the sidecar the supervisor reads
  cannot be the producer as it stands. `PostToolUse`/`Stop` do carry it.
- The largest transcript here is ~100 MB. `model_fallback_detector` reads whole
  files because it runs once at SessionStart; a per-event consumer must scan
  the tail from a recorded offset.

The supervisor must not read transcripts itself — Plan 00317's audit keeps the
PTY host thin, and the daemon already sees `transcript_path` on every hook
event and already owns the parser. Producer in the daemon, consumer in the
supervisor, over the file channel they already share.
