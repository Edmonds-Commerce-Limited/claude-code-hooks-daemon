# Callout: a `github.com-<suffix>` ssh host alias remote is read as GitHub

**Plan**: 00474
**Audience**: everyone

A remote cloned through an ssh config host alias, the common multi-key idiom `git@github.com-<suffix>:owner/repo.git` (or `ssh://git@github.com-<suffix>/owner/repo.git`), now names `github.com`. Before, `branch-reject request <name> --remote-only` passed the alias to `gh -R` as the host and always refused ("error connecting to github.com-<suffix>"), and the upstream issue filing gate did not recognise such a clone of this repository, so a bare `gh issue create` from it was not gated. Only the ssh-style forms are mapped, and only a suffix of letters, digits, `.`, `-` and `_`: an `https://github.com-<suffix>/...` URL, an enterprise host, and an empty or odd suffix are left as written, so gh still refuses a host it cannot reach. GitHub's documented ssh-over-443 address `ssh://git@ssh.github.com:443/owner/repo.git` also names `github.com`, and it is the one non-default port the remote route accepts; every other port is still refused, and its owner/repository checks are unchanged. Host names are matched case-insensitively and the slug's host is lowercased, as gh lowercases it. The issue filing gate is also stricter: it now recognises GitHub in an ssh or scp URL with any user part or none (`github.com-lts:owner/repo`, `me@github.com-lts:...`, `ssh://u@github.com/...`), in an https URL carrying a user or a port, and through any port. **Limit:** only the `github.com-<suffix>` idiom is recognised. Any other ssh config alias (`git@github-work:...`, `git@work:...`) names whatever its `HostName` says, which only reading ssh config could tell, and the daemon does not read it. Such a remote is therefore not recognised as GitHub: the remote route refuses it (gh cannot reach the host), and the issue filing gate does not take it for this repository. Use the `github.com-<suffix>` form for an alias that should be recognised.
