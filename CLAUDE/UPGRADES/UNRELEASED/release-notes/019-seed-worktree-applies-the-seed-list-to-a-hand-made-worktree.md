# Callout: new command `seed-worktree` applies the configured seed list to a worktree made by hand

**Plan**: 00613
**Audience**: client projects

New: `hooks-daemon seed-worktree <worktree>` places the `worktree_create` `seed` entries into a worktree that was made with a hand-run `git worktree add`, which never fires the creation hook and so is otherwise left without the project's git-ignored files. It takes exactly one argument, the worktree, and no options: what is placed, and in which mode, comes only from the project's config. The worktree must be a linked worktree git lists for THIS project's repository (not a worktree of another clone, not the main checkout, not a subdirectory, not prunable); the main checkout's config (`.yaml`, else `.yml`) is read strictly and fresh from disk, and an unreadable one, or a disabled `worktree_create` handler, refuses. A destination whose parent inside the worktree is a symlink refuses. The same checks as at creation apply: a protected file in `mode: copy` is refused, each protected link is logged to `worktree-seed-protected-links.jsonl` (verb `seed-worktree`), and an existing destination is never touched, so running it twice places nothing the second time. A link entry whose source is, holds or links to a protected path is placed only when the config committed at `HEAD` of the main checkout lists the same entry, so an uncommitted edit to the seed list cannot link a protected path; commit the config change first. The creation hook applies the same check, so a worktree Claude Code creates after a daemon restart on an uncommitted seed edit is refused too. A filesystem error part-way through is a refusal that lists what was placed and what was not. Exit 0 on success, 1 when refused.

A file the `secret_file_guard` protects, such as a vault password file, may be seeded in `mode: symlink`. The link makes no second copy, and the guard judges a read through it as a read of the file. That now includes a recursive read that follows links below its root (`grep -R`, `rg -L`, `find -L`, `find -exec`, `zip`, `diff -r`, `tar`, `cp`, `xargs`): what lies behind each link is judged as the direct path would be, and a link the guard cannot resolve is denied. `grep -r`, `rg` and `git grep`, which follow no link below their root, are not affected unless handed a glob (`grep -r x *`), whose expansion they do follow. The guard also judges `fd -x`/`-X` and `bfs -exec` as readers of every file they walk, brace operands of a recursive search (`grep -r x {conf,docs}`) as each spelling, a `link/..` root that leaves the project as an unvouched read, and a link made earlier in the same command (`ln -s <main>/conf conf2 && cat conf2/vault.txt`, `hooks-daemon seed-worktree wt && grep -R x wt`) as a read of where it leads; a link to a place outside the project then fails closed. No configuration changes are required.
