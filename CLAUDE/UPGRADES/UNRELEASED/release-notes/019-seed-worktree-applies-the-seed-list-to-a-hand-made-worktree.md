# Callout: new command `seed-worktree` applies the configured seed list to a worktree made by hand

**Plan**: 00613
**Audience**: client projects

New: `hooks-daemon seed-worktree <worktree>` places the `worktree_create` `seed` entries into a worktree that was made with a hand-run `git worktree add`, which never fires the creation hook and so is otherwise left without the project's git-ignored files. It takes exactly one argument, the worktree, and no options: what is placed, and in which mode, comes only from the project's config. The worktree must be a linked worktree git lists for THIS project's repository (not a worktree of another clone, not the main checkout, not a subdirectory, not prunable); the main checkout's config (`.yaml`, else `.yml`) is read strictly and fresh from disk, and an unreadable one, or a disabled `worktree_create` handler, refuses. A destination whose parent inside the worktree is a symlink refuses. The same checks as at creation apply: a protected file in `mode: copy` is refused, each protected link is logged to `worktree-seed-protected-links.jsonl` (verb `seed-worktree`), and an existing destination is never touched, so running it twice places nothing the second time. A link entry whose source is, holds or links to a protected path is placed only when the config committed on the repository's default branch lists the same entry, and only while the main checkout is on that branch: commit the config change to the default branch first. A main checkout with a detached HEAD, or on any other branch (a feature branch included), has no committed baseline, so every protected link entry is refused there until it is back on the default branch; unprotected entries are unaffected. The default branch is read from git (`origin/HEAD`, else a local `main` or `master`), not from the config. The creation hook applies the same check, with the same config source (the main checkout's config on disk), so a worktree Claude Code creates after a daemon restart on an uncommitted seed edit is refused too, and both routes refuse an entry the committed list does not name when the main checkout's config, or its `secret_file_guard` options, cannot be read. A filesystem error part-way through is a refusal that lists what was placed and what was not. Exit 0 on success, 1 when refused.

A file the `secret_file_guard` protects, such as a vault password file, may be seeded in `mode: symlink`. The link makes no second copy, and the guard judges a read through it as a read of the file. That now includes a recursive read that follows links below its root (`grep -R`, `rg -L`, `find -L`, `find -exec`, `zip`, `diff -r`, `tar`, `cp`, `xargs`): what lies behind each link is judged as the direct path would be, and a link the guard cannot resolve is denied. `grep -r`, `rg` and `git grep`, which follow no link below their root, are not affected unless handed a glob (`grep -r x *`), whose expansion they do follow. The guard also judges `fd -x`/`-X` and `bfs -exec` as readers of every file they walk, brace operands of a recursive search (`grep -r x {conf,docs}`) as each spelling, a `link/..` root that leaves the project as an unvouched read, and a link made earlier in the same command (`ln -s <main>/conf conf2 && cat conf2/vault.txt`, `hooks-daemon seed-worktree wt && grep -R x wt`) as a read of where it leads; a link to a place outside the project then fails closed. That covers every way of making the link (`ln` and `link` with any flags, `busybox`/`toybox ln`, `cp -s`, `install -l`, a `mv` of an existing link, an interpreter one-liner that names a link call) and every reader the direct path is judged on (a leading or attached `<` redirect, `$(<file)`, `dd if=`, interpreter literals, `file://` URLs). A `mv` of a link or a directory into another directory, followed in the same command by a reader of where it landed, is denied whenever the project holds a protected file. No configuration changes are required.
