# Callout: owner_wait_stop_guard judges each stop chain on its own

**Plan**: 00636
**Audience**: operators

Three narrowings of `owner_wait_stop_guard`, no config change. The refusal carries the stand-in cron requirement only where `auto_continue_stop` would ask for it (the declaration sits on a `STOPPING BECAUSE:` line and the stop has a session id). The one-shot pass after the guard's own refusal now needs the guard's own refusal in the current stop chain (after the last real prompt, including a prompt the human typed mid-continuation), with no non-daemon block after it. An earlier chain's refusal, or a refusal followed by a goal continuation, no longer lets a new unposted wait through; the guard refuses it once more, and that refusal earns the next re-stop's pass. Another daemon handler's deny after the refusal still keeps the pass, so the two handlers cannot refuse each other in turn. Residual: a compaction summary is not a prompt, but task notifications, bus deliveries and other `isMeta` entries still start a new chain, which costs at most one extra refusal. A stop whose message cannot be read is still refused where the bus reports notify flags, but on pingbus v1 it no longer gets the "this stop waits on a human" advisory, since nothing showed it did.
