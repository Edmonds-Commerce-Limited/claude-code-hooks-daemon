# Callout: upgrades stop before deploying until you have read what they list, and a breaking one waits for the owner

**Plan**: 00376
**Audience**: operators

Every upgrade now runs a pre-deploy gate once the target is checked out and before anything reaches your project. When it lists something (the upgrade guides you cross, a pre-upgrade task that found call sites in your project, the tasks a branch install stages), it deploys nothing and exits `3` until you re-run with the `--skip-reading-confirmation=<digest>` it printed. A breaking upgrade (a MAJOR version, a crossed `breaking: true` manifest such as v3.58.0's, a detected `critical` task, or an installed version the gate cannot read) exits `4` until the project owner types the approval phrase in their own terminal, which an agent cannot record: an upgrade from v3.64.x or later stops only for reading, one from v3.57.x or earlier needs the owner, and the stop prints an approval command that runs from the new release's code for daemons that predate `approve-upgrade`. Post-upgrade tasks are now a mandatory step (`hooks-daemon check-post-upgrade-tasks --from <previous> --to <new>`; run it once over your whole upgrade history if you have upgraded before); `scripts/upgrade.sh` exits with the version-specific script's own code instead of `0`, and refuses to fetch when git configuration rewrites origin to a different repository (an https-to-ssh rewrite of the same repository is fine; point origin at a mirror directly rather than through `insteadOf`); and the best-effort `upgrade_approval_guard` denies an agent approving, forging the approval, moving the daemon clone or writing into its `.git/`, or steering an upgrade with environment variables, and it is the only barrier on a direct call of `scripts/upgrade_version.sh`, which skips the cleared environment `scripts/upgrade.sh` launches it in. The full procedure is "The pre-deploy gate" in `CLAUDE/LLM-UPDATE.md`.
