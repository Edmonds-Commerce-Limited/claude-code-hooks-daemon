# Callout: agents may now upgrade the daemon on their own, and only one upgrades at a time

**Plan**: 00625
**Audience**: client projects

**On by default, including on your install after this upgrade:** a new standing authorisation, `daemon-auto-upgrade`, lets an agent upgrade the hooks daemon to the latest published release without being asked. When the session-start version check finds a newer release, it tells the agent to run the hooks-daemon skill's upgrade with `--unattended`. That mode only adds refusals. It never upgrades across a MAJOR version, past anything the pre-deploy gate lists under `READ THIS FIRST`, while a release is in progress, with uncommitted changes, or to a version whose unattended attempt already failed: those wait for a human, and a failed version is not retried until a newer one is published. If the new daemon does not start or fails its post-upgrade checks, an unattended upgrade rolls back to the previous one. Tag signatures are not verified, so an unattended upgrade trusts GitHub and the origin URL, as a manual upgrade does. To switch it off, add `{id: daemon-auto-upgrade, enabled: false}` to `handlers.user_prompt_submit.standing_authorisations.options.authorisations` in `.claude/hooks-daemon.yaml`.

Every upgrade and every `provision.sh` sync now takes one upgrade lock, a file in the repository's git directory. When several containers or the host share one checkout, the first to start upgrades, and the others stop with exit `75` (or wait, with `--lock-wait=SECONDS`) and change nothing. A lock is taken over only when its holder is provably dead (same kernel and PID namespace) or has sent no heartbeat for 10 minutes. The lock is safe on local disks, bind mounts and volumes shared on one host, and NFSv3 or later. Across hosts, their clocks must agree. The background sync's old lock judged a holder in another container as dead and could take it over mid-sync; that is fixed.
