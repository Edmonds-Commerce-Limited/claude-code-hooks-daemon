# Callout: the secret file guard's exemptions no longer skip options they do not know

**Plan**: 00474
**Audience**: operators

`secret_file_guard` exempts a few read-only shapes (a `grep` that only names a protected file as its search pattern, `git rm --cached`, git or file commands over a confirmed-encrypted file, allowlisted consumers such as `ansible-playbook`). Their option parsers skipped any option they did not recognise, so a command could carry one the guard did not understand and still be judged exempt: `grep --rege=. <key>` (GNU grep accepts `--rege` as `--regexp`), ugrep `--and=.`, and `git -c core.fsmonitor=<command> rm --cached <key>` all printed or executed against the protected file. The parsers now accept only a closed list of known-safe options, matched by full name, so an unknown option or any abbreviation of one voids the exemption and the command is judged normally. `git -c`, `--config-env` and every other git global option except `-C <dir>` and a few harmless flags void the `rm --cached` exemption; consumer option words are judged for protected paths; and a denied subcommand (`view`, `decrypt`) anywhere in a consumer command voids it. The documented exempt shapes stay exempt. Cost: a `grep` that passes a long option's value as a separate word (`--max-count 3`), or uses an option outside the GNU grep set, is now judged like any other command naming the file.
