# Callout: declared crons are held by a session's initial thread only

**Plan**: 00470
**Audience**: operators

A thread opened later in a Claude Code session (left arrow, then a new thread) is a separate session to the hooks, with its own empty cron list and a `SessionStart` that reports `source: "startup"`. So `cron_stop_enforcer` demanded the declared `persistent_crons` at every thread's stop, and each thread ran its own copy of every job. Now only the initial thread of a session is required to hold them. The daemon tells the threads apart by process ancestry: all threads of one session run under one `claude daemon run --spawned-by` process, and the first `session_id` seen under it is the initial thread. A later thread is told by `persistent_cron_assertor` that it holds none and which thread does, and `cron_stop_enforcer` and `cron_subagent_stop_enforcer` do not demand them from it. The grouping reads only `/proc` (bounded depth, a deadline, no signal sent) and the group-to-holder map persists across a daemon restart. Where no such ancestor is found, or `/proc` is unreadable, every session holds the crons exactly as before. The option `persistent_crons.initial_thread_only` (default `true`) turns this off. The daemon learns the hook's pid from the event socket, so the behaviour applies on the byte-pump relay path; the legacy `init.sh` socket path does not carry it and keeps the old behaviour.
