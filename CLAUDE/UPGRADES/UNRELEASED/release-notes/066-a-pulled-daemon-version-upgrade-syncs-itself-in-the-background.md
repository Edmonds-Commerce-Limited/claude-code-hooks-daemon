# Callout: a pulled `daemon.expected_version` upgrade now syncs the daemon clone in the background, and a failed sync is reported at every session start

**Plan**: 00477
**Audience**: operators

When someone else upgrades the project and commits, this checkout's pull changes `daemon.expected_version`, but the gitignored clone under `.claude/hooks-daemon/` stays at the old version. The SessionStart `version_check` drift notice used to name `bash .claude/provision.sh` and wait for a person to run it. For an UPGRADE the sync now starts itself. The tracked session-start forwarder (`.claude/hooks/session-start`) starts `bash .claude/provision.sh --background` detached at every session start, so it never runs inside the hook's time budget. It sits above the relay hot path, so it runs with the relay enabled too. The sync does nothing when the clone already matches. Otherwise it waits for the running daemon, then runs provision's own steps (release note 031). The target is fetched, gated and built in a stage beside the running daemon, which keeps serving, untouched, until the switch. The switch stops it, swaps the stage in by renames, keeps the old clone until the new daemon answers, and swaps it back if the new one does not. A failure before the switch never stops it. A switch a killed sync left half-done is undone by the next session start's run, and recorded as failed. The forwarder and `provision.sh` are tracked files, so the commit that moved `daemon.expected_version` brings them with it, and the very pull that changes the version is enough.

- The output goes to `.claude/hooks-daemon/untracked/background-sync/v<version>.log`. The outcome is recorded in `v<version>.state` beside it. That file is also the marker that the target was attempted, so each target version is synced in the background at most once. A lock stops two syncs from overlapping.
- A failure leaves the previous version in place, as a manual provision does: a refused clone, an unfetchable tag, a failed venv build, or a target whose pre-deploy gate wants its reading list confirmed. Every later session start then shows `BACKGROUND SYNC TO vX.Y.Z FAILED` (or `STOPPED`) to the human and the agent, with the reason, the log, `bash .claude/provision.sh` to run by hand, and the state file to delete to have it retried in the background.
- A DOWNGRADE is never synced in the background. Nor is a fresh checkout provisioned, or a project without the tracked `.claude/provision.sh` synced. The notice for those still names the command, and a person or agent runs it. The daemon's own repository never syncs.
- With no daemon running from the clone after 30 seconds, the sync changes nothing and claims nothing, and a later session start tries again. A clone too broken to start keeps the existing `init.sh` message naming provision.
- The `version_check` notice reports the sync's state: started, under way, or its outcome. Only an installed daemon at this version or later knows to read that state. On the first move onto this release, the sync still runs, but the notice keeps its older wording.
