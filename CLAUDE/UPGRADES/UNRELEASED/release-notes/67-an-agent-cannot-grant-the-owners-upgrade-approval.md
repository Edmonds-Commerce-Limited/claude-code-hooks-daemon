# Callout: an agent cannot grant the owner's upgrade approval

**Plan**: 00376
**Audience**: operators

The new `upgrade_approval_guard` handler closes the routes an agent could use to grant its own breaking-upgrade approval instead of waiting for the owner: running `approve-upgrade` itself, forging the `upgrade-approvals/` marker or a venv's `.daemon-version` stamp, or setting `HOOKS_DAEMON_UPGRADE_HANDOFF` to impersonate the upgrade's Layer 1. On a command that runs the upgrade, it also denies setting a variable that picks the upgrade's interpreter, venv, flags, git view or code (`HOOKS_DAEMON_PYTHON`, `HOOKS_DAEMON_VENV_PATH`, `PATH`, `HOSTNAME`, `GIT_*` and the rest `hooks-daemon explain-rule R-UPGRADE-APPROVAL-ENV-BYPASS` lists). The pre-deploy gate itself never runs on `HOOKS_DAEMON_PYTHON` and never reads the installed version from `HOOKS_DAEMON_VENV_PATH`: an interpreter that only printed the gate's verdict, or a venv stamped with the target, could otherwise answer for it. If an upgrade genuinely needs one of these (an interpreter that is not on PATH, say), the agent asks you to run it. The approval itself now needs a terminal and a typed phrase naming both versions, and its marker is bound to that upgrade, so the guard is a second line: an agent's shell has no terminal to answer with. The owner's route is `hooks-daemon approve-upgrade <version> --from <installed>`, or the command the gate's stop prints to run the approval from the new release's own code.
