# Callout: `bash .claude/provision.sh` now syncs a daemon clone that is at another version than the project expects, and the drift notices name it instead of `upgrade`

**Plan**: 00477
**Audience**: operators

When a pull changes `daemon.expected_version`, the gitignored clone under `.claude/hooks-daemon/` is left behind (or ahead). `provision.sh` used to refuse a clone that was already there; it now brings it to the expected version. A clone already at that version is left alone ("already at vX.Y.Z", exit 0). Otherwise it refuses, changing nothing, when the clone is not a git checkout, its `origin` is not the fixed trusted URL, or it has tracked changes or files outside `untracked/` (gitignored files do not count). When it may go on it fetches exactly the tag (depth 1) from the fixed URL, checks that the tag's `version.py` names the version, checks the tag out, runs the target release's own pre-deploy gate (the one upgrade runs; a target that predates the gate has none to run), rebuilds the venv through the clone's `scripts/venv_bootstrap.sh repair` and restarts the daemon with the clone's `bin/hooks-daemon restart`. When the gate wants its reading list confirmed it prints the listing, puts the clone back and stops; re-run with `--skip-reading-confirmation=<digest>`, as with upgrade. A failure after the checkout puts the previous commit and its venv back, restarts the old daemon and says that the previous version is in place. A sync writes no tracked file, runs no config migration and regenerates no docs: moving a PROJECT to a new version is still `upgrade`.

The version-drift notices now name `provision` for this case: the `init.sh` stale-clone message, the SessionStart `version_check` drift notice, and `daemon_sync_after_merge` after a pull that changed `daemon.expected_version`. Each also says that `upgrade` remains the route for moving the project to another version (reported as issue #78).
