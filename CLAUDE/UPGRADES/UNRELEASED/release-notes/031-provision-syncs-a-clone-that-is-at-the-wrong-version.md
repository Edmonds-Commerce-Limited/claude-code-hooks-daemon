# Callout: `bash .claude/provision.sh` now syncs a daemon clone that is at another version than the project expects, and the drift notices name it instead of `upgrade`

**Plan**: 00477
**Audience**: operators

When a pull changes `daemon.expected_version`, the gitignored clone under `.claude/hooks-daemon/` is left behind (or ahead). `provision.sh` used to refuse a clone that was already there; it now brings it to the expected version. A clone already at that version is left alone ("already at vX.Y.Z", exit 0). Otherwise it refuses, changing nothing, when the clone is not a git checkout, its `origin` is not the fixed trusted URL, or it has tracked changes or files outside `untracked/` (gitignored files do not count). When it may go on, it first works in a stage under the clone's `untracked/`, writing nothing else of the live clone (its git directory included) while the old daemon serves. It fetches exactly the tag (depth 1) from the fixed URL into a clone of its own there and checks that the tag's `version.py` names the version. It runs the target release's own pre-deploy gate from the stage (the one upgrade runs; a target that predates the gate has none to run). It builds the target's venv there with the target's own `scripts/venv_bootstrap.sh`, then rebinds it to the live path: the venv is renamed for the live path and every text file in it that names the stage names the live path instead. Only then does it switch. It stops the old daemon, moves the daemon's state under `untracked/` into the stage, swaps the stage in by renames, keeps the old clone at `untracked/sync-previous`, and starts the daemon with `bin/hooks-daemon restart`. The old clone is removed once the new daemon answers. During the switch, a hook that would start a daemon answers "the daemon is starting; retry" instead. When the gate wants its reading list confirmed, it prints the listing and stops with nothing changed; re-run with `--skip-reading-confirmation=<digest>`, as with upgrade. A failure before the switch changes nothing and never stops the old daemon. A failure during it swaps the old clone, its venv and the daemon's state back, starts the old daemon again and says that the previous version is in place. A switch that a killed run left half-done is undone the same way by the next run of `provision.sh`, which prints `RECOVERED`. A sync writes no tracked file, runs no config migration and regenerates no docs: moving a PROJECT to a new version is still `upgrade`.

The version-drift notices now name `provision` for this case: the `init.sh` stale-clone message, the SessionStart `version_check` drift notice, and `daemon_sync_after_merge` after a pull that changed `daemon.expected_version`. Each also says that `upgrade` remains the route for moving the project to another version (reported as issue #78).
