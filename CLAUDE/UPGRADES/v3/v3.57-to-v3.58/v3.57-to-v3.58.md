# Upgrade Guide: v3.57 → v3.58

## Summary

This upgrade completes the hard cutover to **declared, not inferred, project
boundaries**: a monorepo now declares its sub-projects via the top-level
`projects:` config block (Plan 00296), and the older
`monorepo_subproject_patterns` regex-pattern alias for `markdown_organization`
is removed outright (Plan 00300, owner ruling) — there is no fallback and no
override. A zero-config repository (no `projects:` declared) behaves exactly
as before: single root project, byte-identical behaviour. Alongside the
cutover this release also adds per-project `layout:` blocks, zero-absolute-
paths-in-config enforcement plus the portable `{REPO_ROOT}` path token, a
degraded-mode safety net for destructive-git protection, a failsafe-cron
blockage suppressor, multi-plan combined `/goal` rendering, and a supervisor
DROP ANCHOR safety net.

**This upgrade is only breaking for a project that actively set
`monorepo_subproject_patterns` to a non-empty pattern list.** Everyone else
upgrades with no config changes.

## Version Compatibility

- **Source Version**: v3.57.0
- **Target Version**: v3.58.0
- **Minimum Claude Code Version**: Any
- **Supports Rollback**: Yes
- **Breaking Changes**: Yes (see below — narrowly scoped)
- **Config Migration Required**: Only if `monorepo_subproject_patterns` is set to real patterns

## Pre-Upgrade Checklist

Before starting the upgrade:

- [ ] Backup `.claude/hooks-daemon.yaml`
  ```bash
  cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
  ```
- [ ] Check whether you use the removed option
  ```bash
  grep -n "monorepo_subproject_patterns" .claude/hooks-daemon.yaml
  ```
  If this prints nothing, or the value is `null`/an empty list, you are not
  affected — skip straight to "Step-by-Step Upgrade Instructions".
- [ ] Check for uncommitted changes
  ```bash
  cd .claude/hooks-daemon
  git status
  ```
- [ ] Read "Breaking Changes" below if the grep above found real patterns.

## Changes Overview

### New Features

- **Declared `projects:` config (Plan 00296)** — a shared `Workspace.for_path`
  resolver (manifest walk-up + git-root fallback) lets a monorepo declare
  each sub-project's root explicitly. `markdown_organization`,
  `tdd_enforcement`'s `test_path_map`, `npm_command`, `lint_on_edit` and
  `eslint` all resolve against the declared workspace first. A new
  SessionStart `monorepo_detector` advisory flags a likely-monorepo layout
  with no `projects:` declared (advisory only, never decides for you), and
  `hooks-daemon check` surfaces downgraded enforcement status when workspace
  resolution degrades.
- **Per-project `layout:` blocks (Plan 00300/00301)** — a declared
  `projects:` entry may carry its own `layout:` block (same shape as the
  top-level `layout:`) governing only that project's own source/test/
  config/vendor directory names. A project without one uses built-in
  defaults and never inherits the root project's layout.
- **REPO vs PROJECT handler `workspace_scope` taxonomy (Plan 00301)** — every
  handler now declares whether it operates repo-wide or per-declared-project.
- **Zero-absolute-paths-in-config enforcement + `{REPO_ROOT}` token (Plans
  00302, 00303)** — several config path fields now hard-error or fail open on
  an absolute value; the literal token `{REPO_ROOT}` is accepted as portable
  notation for "the repository root". See `config-changes/v3.58.0.yaml` for
  the full per-field breakdown.
- **Degraded-mode safety net (Plan 00304)** — `DestructiveGitHandler` runs
  config-independently while degraded; degraded mode is now visible on
  `hooks-daemon status`/`check`/`config-validate`.
- **Failsafe-cron blockage suppressor (Plan 00298)** and **multi-plan
  combined `/goal` rendering (Plan 00299)** — supervisor-side improvements,
  no config action needed.
- **Supervisor DROP ANCHOR safety net (Plan 00297)** — the ccy supervisor
  read-back-verifies its effort/model invariant on escalation.

### Modified Handlers

- **`markdown_organization`**
  - What changed: sub-project resolution now prefers declared `projects:`
    config; `monorepo_subproject_patterns` is a removed, non-functional key.
  - Why: Plan 00300 hard cutover — declared config is unambiguous, a regex
    pattern list is not.
  - Migration: see "Breaking Changes" below.
- **`tdd_enforcement`**
  - What changed: in a declared `projects:` monorepo, `test_path_map`
    resolves a relative `test_dir` against the source file's declared
    workspace ONLY — the second, repository-root-anchored candidate that
    used to be searched is gone.
  - Why: Plan 00300 — a workspace-anchored resolver should not silently fall
    back to a different root.
  - Migration: only relevant if you both declare `projects:` AND have a
    `test_path_map` entry whose test file lives at the project-root-anchored
    path rather than the workspace-anchored one. Move the test file, or split
    the `test_path_map` entry per declared project.

### Removed Handlers/Options

- **`handlers.pre_tool_use.markdown_organization.options.monorepo_subproject_patterns`**
  - Deprecation reason: superseded by declared `projects:` config
    (Plan 00296); the regex-pattern alias created ambiguity a declared block
    does not have.
  - Alternatives: declare `projects:` entries directly.
  - Migration: see "Breaking Changes" below.

### Configuration Changes

#### New Config Fields

```yaml
projects:
  - name: api
    root: packages/api
    layout: # optional, per-project
      source_dirs: [src]
      test_dirs: [tests]
```

#### Removed Fields

- `handlers.pre_tool_use.markdown_organization.options.monorepo_subproject_patterns`
  → removed (no replacement key; use `projects:` at the top level instead)

#### Path fields now repository-relative only (hard error on absolute)

- `plan_workflow.directory`
- `plan_workflow.workflow_docs`
- `documentation.trees.agent`
- `documentation.trees.human`

#### Path fields that now fail open (log + default) on absolute instead of using it verbatim

- `handlers.pre_tool_use.sensitive_content.options.secret_word_list_path`
- `daemon.payload_capture.dir`
- `handlers.session_start.model_fallback_detector.options.snapshot_dir`

Full field-by-field detail (with `migration_note` for each) is in
`CLAUDE/UPGRADES/config-changes/v3.58.0.yaml`.

### Dependency Changes

None.

## Step-by-Step Upgrade Instructions

### 1. Update Daemon Code

```bash
cd .claude/hooks-daemon
git fetch origin
git checkout v3.58.0
```

### 2. Update Dependencies

```bash
bash .claude/hooks-daemon/scripts/upgrade_version.sh \
  "$PWD" "$PWD/.claude/hooks-daemon" v3.58.0
```

### 3. Update Configuration File (only if affected)

**File**: `.claude/hooks-daemon.yaml`

If your pre-upgrade grep above found `monorepo_subproject_patterns` set to a
non-empty pattern list:

1. Run the daemon (or `bin/hooks-daemon config-validate .claude/hooks-daemon.yaml`)
   and read the printed error. For every LITERAL (non-wildcard) pattern it
   prints a paste-ready `projects:` block, e.g. `packages/api` becomes:
   ```yaml
   projects:
     - name: api
       root: packages/api
   ```
2. For any pattern the error could not auto-translate (it contained a regex
   wildcard, e.g. `packages/[^/]+`), declare one `projects:` entry per real
   sub-project directory by hand.
3. Delete the `monorepo_subproject_patterns` key from
   `.claude/hooks-daemon.yaml` entirely.
4. Restart the daemon and confirm it starts cleanly.

See `config-before.yaml` / `config-after.yaml` in this directory for a
concrete before/after example.

If your `monorepo_subproject_patterns` was `null`, an empty list, or absent:
no action needed — it is auto-cleaned with an advisory log line only.

### 4. Update Hook Scripts (if needed)

```bash
bash .claude/hooks-daemon/scripts/install_version.sh \
  "$PWD" "$PWD/.claude/hooks-daemon"
```

No hook script changes shipped in this release; only needed if prompted.

### 5. Restart Daemon

```bash
cd .claude/hooks-daemon
.claude/hooks-daemon/bin/hooks-daemon restart
```

## Breaking Changes

### Breaking Change 1: `monorepo_subproject_patterns` removed outright

**What broke**: the `markdown_organization.options.monorepo_subproject_patterns`
regex-pattern list for declaring monorepo sub-projects no longer exists. A
non-empty value now fails daemon startup with a hard config-validation error.

**Why**: Plan 00300 (owner ruling) — declared `projects:` config
(Plan 00296) is the only sub-project resolution mechanism from this release
on. Two competing mechanisms (a declared block and a regex-pattern alias)
created ambiguity about which one wins for a given file; removing the alias
outright removes that ambiguity permanently rather than deprecating it in
place.

**Who is affected**: only projects that explicitly set
`monorepo_subproject_patterns` to a non-empty list. A `null`/empty/absent
value (the shape an older daemon version's own default config template
writes, with nothing actually configured) is NOT affected — Plan 00304
tolerates that shape silently (an advisory log line only).

**Migration Steps**:

1. Run `bin/hooks-daemon config-validate .claude/hooks-daemon.yaml` (or start
   the daemon) and read the printed error — it contains a paste-ready
   `projects:` YAML block for every literal (non-wildcard) pattern.
2. For any wildcard pattern the error could not auto-translate, declare one
   `projects:` entry per real sub-project directory by hand.
3. Delete the `monorepo_subproject_patterns` key.
4. Restart the daemon and confirm it starts cleanly.

**Example**:

Before (v3.57, real usage):

```yaml
handlers:
  pre_tool_use:
    markdown_organization:
      options:
        monorepo_subproject_patterns:
          - "packages/api"
          - "packages/web"
```

After (v3.58):

```yaml
projects:
  - name: api
    root: packages/api
  - name: web
    root: packages/web

handlers:
  pre_tool_use:
    markdown_organization:
      options: {} # monorepo_subproject_patterns key removed
```

**Rollback**: there is no in-place rollback for this option — it is gone,
not deprecated. If migration is not ready, stay on v3.57.x until it is; that
is the documented backward-compat path.

### Breaking Change 2: `test_path_map` loses its repository-root-anchored fallback

**What broke**: in a declared `projects:` monorepo, `tdd_enforcement`'s
`test_path_map` used to search TWO candidates for a relative `test_dir`
(workspace-anchored, then repository-root-anchored). Only the
workspace-anchored candidate is searched now.

**Why**: Plan 00300 — a workspace-anchored resolver should not silently fall
back to a different root; that ambiguity is the same class of problem the
`projects:` cutover exists to remove.

**Who is affected**: only a project that BOTH declares `projects:` AND has a
`test_path_map` entry whose test file happens to live at the
project-root-anchored path rather than the workspace-anchored one. A
single-project repo (no `projects:` declared) is unaffected — the workspace
IS the repository root, so behaviour is byte-identical.

**Migration Steps**:

1. Move the test file to `{declared project root}/{test_dir}/`, or
2. Split the `test_path_map` entry into one per declared project, each with
   its own `test_dir`.

**Rollback**: stay on v3.57.x, or remove the `projects:` declaration for the
affected source glob until the test files are relocated.

## Additional Notes

- The `{REPO_ROOT}` path token (Plan 00302 extension) is purely additive
  sugar — adopt it in new/edited config where it reads more clearly than a
  bare relative path, or where a plugin/project-handler path previously
  needed a machine-specific absolute value.
- Per-project `layout:` blocks (Plan 00300/00301) are opt-in and dormant by
  default — a repository with no `projects:` declared, or `projects:`
  entries with no `layout:` of their own, behaves exactly as before.
