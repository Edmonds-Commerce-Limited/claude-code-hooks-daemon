# Callout: remote branch deletes are proven against the remote's default only, and interleaved cherry-picks now prove

**Plan**: 00626
**Audience**: operators

**Safety fix.** `R-GIT-PUSH-DELETE-REMOTE` (an agent's `git push --delete`) and `branch-sweep --clean --remote` proved a remote branch "merged" against the LOCAL default branch as well as the remote one. A branch merged only into a local default whose push had not landed (waiting on CI, say) was therefore listed as proven and deletable on the remote, although the remote held that work nowhere else. Every remote-delete proof now judges the remote-tracking default (`refs/remotes/<remote>/<default>`) alone, and confirms in the same `git ls-remote` it already made that the remote's live default, and the integration line that proved a branch by ancestry, are at the shas the proof read. A missing tracking default, a tracking ref moved locally (`git update-ref`), a remote default that moved since the last fetch, or a failed listing all refuse the delete with a "run `git fetch` and retry" reason. With `branches.default: auto`, the remote default is read from `refs/remotes/<remote>/HEAD` only: the local `main`/`master` fallback is no longer used for a remote delete, because on a repository whose default has another name it can be a stale old branch. A clone without that ref (for example one built with `git remote add` rather than `git clone`) has its remote deletes refused until `git remote set-head <remote> --auto` is run or `branches.default` is set. A cached proof result no longer authorises a remote delete: the cache is a plain file in the working tree, so a positive result is recomputed every time; only a cached refusal is reused. Remote deletes of proven branches therefore cost a little more git work on each run. Local deletes (`delete-branch`, `git branch -d`) are unchanged.

**Over-refusal fix.** A branch whose commits were cherry-picked onto the default, with the default changing one of the same files between the picks, was refused as "not merged" even though `git cherry` marked every commit `-` (park and unpark markers on top included). No single commit of the default held the branch's whole result, and that was the only content proof. Such a branch is now proven `patch-equivalent` when BOTH hold: `git cherry` finds every non-park commit's patch in the remote default with no merge commit in the range, AND every path the branch changes is held at its exact bytes and mode (a deletion: absent) by some first-parent commit of the default after the merge base. The exact-bytes check closes the hole that kept patch-ids from proving a branch alone (a patch-id ignores whitespace), and a branch with no merge base is never proven this way. The proof cache key version moved, so earlier refusals are judged afresh after the upgrade.
