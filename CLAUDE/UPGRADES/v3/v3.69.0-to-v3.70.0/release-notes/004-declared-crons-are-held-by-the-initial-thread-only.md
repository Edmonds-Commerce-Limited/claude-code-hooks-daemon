# Callout: declared crons are held by a session's initial thread only

**Plan**: 00470
**Audience**: operators

A thread opened later in a Claude Code session (left arrow, then a new thread) is a separate session to the hooks, with its own empty cron list and a `SessionStart` that reports `source: "startup"`. So `cron_stop_enforcer` demanded the declared `persistent_crons` at every thread's stop, and each thread ran its own copy of every job. Now only the initial thread of a session is required to hold them. The daemon tells the threads apart by process ancestry: all threads of one session run under one `claude daemon run --origin transient --spawned-by` process, the initial thread's worker carries `--fork-session --resume`, and a thread opened later is a `bg-spare` worker. The holder is chosen by that worker shape, not by which hook arrived first, and it is a live process: if the initial thread exits the next thread takes over, and a `/clear` in the initial thread keeps holding. A later thread is told by `persistent_cron_assertor` that it holds none, and `cron_stop_enforcer`, `cron_subagent_stop_enforcer` and the `usage_pause_gate` lift directive no longer ask it for them. The grouping reads only `/proc` (bounded depth, a deadline, no signal sent) and the group-to-holder map persists across a daemon restart. Whenever the placement is unsure (no such ancestor, an unreadable `/proc`, a worker of an unrecognised shape) every session holds the crons exactly as before. The daemon reads the hook's pid from the connection on both the event sockets and the legacy `init.sh` socket, replacing any pid a payload carries. The option `persistent_crons.initial_thread_only` (default `true`) turns this off.
