# Directory Roles — what belongs where

**This file is the canonical home for directory-role rules**: for each
directory role in a project, what the directory is for, what markdown belongs
in it, and which enforcement covers it. The shipped `.claude/rules/` pointer
files route here; they never restate these rules. The documentation-SSoT
ruleset itself (R1–R13) is owned by
[DocumentationStrategy.md](DocumentationStrategy.md) — this document applies
those rules per directory role and adds nothing normative to them.

**Directory NAMES are project configuration, not truths of this document.**
Roles are stated generically with the defaults in parentheses. The names come
from the project's configured layout: `documentation.trees.agent/human` for
the two doc trees, `plan_workflow.directory` (plus
`plan_workflow.qa.completed_dir/cancelled_dir`) for the plan directory, and
the top-level `layout:` block (`source_dirs`, `test_dirs`, `config_dirs`,
`vendor_dirs`) for the rest — schema, defaults and the handlers that consume
it:
[docs/guides/HANDLER_REFERENCE.md § Directory Layout](../docs/guides/HANDLER_REFERENCE.md#directory-layout-layout).

## The rule in one sentence

Durable documentation lives in the two doc trees; every other directory holds
at most **routing markdown** (`CLAUDE.md`, `README.md`) or content that is not
documentation at all (fixtures, vendored bytes, scratch) — anything else
found there is promoted into a doc tree with a pointer left behind.

## Per-role rules

### Source directories (default inference `src/`, `lib/`, `app/`, per-language conventions; declare via `layout.source_dirs`)

Production code. Markdown here is limited to **routing**: a collocated
`CLAUDE.md` is allowed as a module doc — either a pure routing table or a
registered module-local canonical home, per R7d and the `module-doc-budget`
check — and `README.md` is allowed in place as the conventional package entry
point. Any other markdown is a defect: promote its content into the agent or
human tree and leave a pointer, convert it to a routing `CLAUDE.md`, or
delete it. Enforcement: `markdown_organization` gates new writes;
`module-doc-budget` (docs_qa, edit + sweep) polices `CLAUDE.md` shape; the
`source-tree-markdown` docs_qa sweep check flags non-`CLAUDE.md` markdown
already on disk.

### Test directories (default inference `tests/`, `test/`, `__tests__/`, `spec/`; declare via `layout.test_dirs`)

Tests mirroring source. The same markdown rules as source directories apply,
with one addition: markdown under fixture directories (`tests/fixtures/`-style
paths) is **test data, not documentation**, and is exempt from documentation
checks. Enforcement: as for source directories.

### Human docs tree (default `docs/`; configured via `documentation.trees.human`)

Terse, digestible, human-register documentation. It may summarise and point
into the agent tree for depth; a human-tree file restating agent-tree content
at length violates R3. Enforcement: `markdown_organization` allows writes
here; the docs_qa catalogue (edit, commit gate, sweep) applies in full.

### Agent docs tree (default `CLAUDE/`; configured via `documentation.trees.agent`)

Verbose, information-dense agent-register documentation — this tree **owns the
depth for every fact** (R2). Every satellite surface points here. Enforcement:
`markdown_organization` allows writes here; the docs_qa catalogue applies in
full.

### Plan directory (default `CLAUDE/Plan/`, a subdirectory of the agent tree; configured via `plan_workflow.directory`)

Numbered development plans: each plan folder holds a lean `PLAN.md`, unbounded
supporting docs, and an append-only `JOURNAL/`. The three files obey different
write/read contracts — see [PlanWorkflow.md](PlanWorkflow.md) (workflow,
templates, completion checklist) and [PlanJournalling.md](PlanJournalling.md)
(journalling). A plan folder is a drafting ground, not a documentation home:
at terminal status every supporting doc gets a promote/historical/delete
disposition (R8). Enforcement: the plan_qa catalogue (`plan_qa_edit`,
`plan_qa_commit_gate`, `plan_qa_sweep`) plus `plan_time_estimates`.

### `.claude/rules/`

Path-glob-scoped rule files loaded on demand when matching files are touched.
**Pointers only** (R7a): frontmatter, a trigger statement, the rule in ≤2
imperative lines, and link(s) to a canonical doc — no fences, tables,
procedures, or quotes, within a 15-line body budget. If the substance has no
canonical home yet, create the home first. Enforcement: `rules-file-shape`
(docs_qa, edit + sweep).

### `.claude/skills/`

Intent-triggered skills: thin shims that carry their own invocation mechanics
and point at a canonical doc for the procedure body (R7b). Enforcement: the
docs_qa catalogue indexes this tree (pointer resolution, duplication).

### `.claude/agents/`

Sub-agent definitions: role framing, role-unique behavioural instruction, and
pointers — no engineering-principle restatements or remediation cookbooks
(R7c). Project-level handler development, by contrast, lives in
`.claude/project-handlers/` and is code, not docs — see
[PROJECT_HANDLERS.md](PROJECT_HANDLERS.md). Enforcement: the docs_qa
catalogue indexes this tree.

### Remote docs tree (default `remote-docs/`; configured via `documentation.trees.remote`)

Documentation **captured from upstream**, never authored here. Every file
carries provenance frontmatter recording its source URL, fetch time, content
hash, fidelity, licence and freshness window. Top-level rather than a `docs/`
subdirectory on purpose: the human-docs role rule would otherwise instruct
"keep it terse, summarise" over verbatim upstream prose, and rule globs cannot
be negated.

Deliberately **outside the docs-QA corpus** — our documentation rules do not
apply to someone else's prose. Enforcement: `remote_docs_provenance` denies a
write without valid provenance; `remote_docs_routing` routes a `WebFetch` to a
fresh vendored copy; `remote_docs_staleness` reports stale documents at session
start. Capture with `hooks-daemon remote-docs add <url>` — see
[RemoteDocs.md](RemoteDocs.md).

### Vendor and build directories (built-in set, e.g. `vendor/`, `node_modules/`, build outputs; extend via `layout.vendor_dirs`)

Third-party and generated bytes. Nothing here is authored in this project, so
no documentation rule applies and no doc check looks inside; content-guard
handlers skip these paths by default. Never edit vendored files — regenerate
or re-vendor upstream.

### Untracked/scratch space (gitignored working dirs, e.g. `untracked/`)

Runtime files, virtualenvs, captured output, transient reports. Nothing
durable belongs here: a write-up worth keeping is promoted into a doc tree or
a plan folder and committed; everything else is cleaned up once acted on.
This space sits outside the documentation corpus entirely.

### Project root

The root `CLAUDE.md` is resident in every session, so it stays lean: stable
instructions and the shortest possible summaries, each pointing at its
canonical home (R11). `README.md` is the human entry point. Ephemeral or
session-specific content in either is a defect (`validate_instruction_content`
enforces this).
