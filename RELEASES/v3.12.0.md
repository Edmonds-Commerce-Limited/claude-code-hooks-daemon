# Release v3.12.0 - Batch Backlog Delivery + Security Hardening

**Type:** Minor Release

## Summary

This is the Plan 00107 batch-delivery release — a six-wave audit-and-close of the v3.x backlog. Most of the bundled plans had already shipped in prior releases (00063, 00077, 00089, 00096, 00099) or were superseded by other work (00081 → 00082); their PLAN.md status records have been reconciled in this release. **Two source-code changes ship**: a security-tightening fix to `auto_approve_reads` (only auto-approves in `bypassPermissions` mode now), and a behaviour fix to `markdown_organization` so plan-redirect writes actually take effect. One plan (00085, reminder pseudo-event system) is deferred to a future release with documented rationale.

## What's New

### Fixed (Plan 00106 — security)

- **`auto_approve_reads` only auto-approves in `bypassPermissions` mode**. The handler previously auto-approved Read/Glob/Grep permission requests **regardless of the active permission mode**. This meant that in `default`, `plan`, `acceptEdits`, and `dontAsk` modes — where the user has NOT opted out of per-tool approvals — the daemon was silently approving on their behalf. The handler now defers in every mode except `bypassPermissions`, so users running in `default` mode get Claude Code's normal approval prompts for filesystem reads.
  - **Security impact**: read-only operations previously bypassed user approval regardless of permission mode. Users who never enabled YOLO mode were not getting the approval prompts they expected.
  - **Behaviour change**: in `default` mode, Claude Code will now show its normal approval prompt for Read/Glob/Grep — approve it as you would any other tool request. In `bypassPermissions` mode the auto-approve behaviour is unchanged.
  - **New utility**: `utils/permission_mode.py` provides a typed predicate for `bypassPermissions` mode, reused by `auto_approve_reads` and available for future handlers that need the same gate.

### Fixed (Plan 00086 — plan-redirect path)

- **`markdown_organization` plan-redirect path now returns `Decision.ALLOW`**. `_handle_plan_write` previously returned the wrong decision type when redirecting a plan-mode write to `CLAUDE/Plan/`. The redirect annotation was set on the result but the decision did not actually allow the write through, so the user-visible behaviour was a silent failure. The handler now correctly returns `ALLOW` with the redirect annotation, so plan files land in their proper destination.

### Changed (Plan 00107 — batch reconciliation)

- **Plan 00107 batch-delivery meta-plan executed across six waves**: Plans 00063, 00077, 00081, 00086, 00089, 00096, 00099, 00101, 00106 reconciled — each marked Complete (Already Shipped), Cancelled (Superseded), or moved to `Completed/` with disposition evidence cited (file/line references in source). Plan 00100 marked Residue Scope (Phases 0–3.9 shipped; Phases 3.5/4/5/6 deferred). Plan 00085 deferred to a future release with documented rationale (8-phase fresh-TDD scope qualitatively different from the audit-and-close pattern that closed the rest of the batch). See `CLAUDE/Plan/Completed/00107-batch-delivery-meta/PLAN.md` for the full disposition table.
- **`CLAUDE/Plan/README.md` index reconciled**: Active/Completed/Cancelled sections updated to reflect the batch outcome and statistics updated accordingly.
- **Plan workflow standard — no completion dates in plan index**: Plan index entries no longer carry completion dates; commit hashes recorded in the plan's "Notes & Updates" section are the authoritative "when". The `validate_instruction_content` blocking handler enforces this on `CLAUDE.md` and `README.md` by blocking ephemeral ISO-date content. Documented in `CLAUDE/PlanWorkflow.md`.

## Breaking Changes

None. This is a MINOR release. The `auto_approve_reads` behaviour change is a **security tightening**, not a breaking change: the previous behaviour was a silent over-approval bug, and the new behaviour matches the documented intent of YOLO-mode-only auto-approval. Users running in `bypassPermissions` mode (YOLO containers, the documented opt-in path) see no change. Users running in `default` mode will see Claude Code's normal approval prompts for Read/Glob/Grep where previously these were silently approved.

## Install / Upgrade

### Upgrading Existing Installations

No manual steps required. Run the upgrade skill from any Claude Code session in your project:

```
/hooks-daemon upgrade
```

Or directly from the daemon directory:

```bash
cd .claude/hooks-daemon
./scripts/upgrade.sh
```

The skill's self-bootstrap stanza fetches the latest `upgrade.sh` body from this release, sha256-verifies it against `bootstrap-checksums.txt`, and re-execs the fresh body before proceeding.

### New Installations

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon/main/install.sh)
```

Or clone a specific tag:

```bash
git clone -b v3.12.0 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon
cd .claude/hooks-daemon && ./install.sh
```

### Verify

```bash
/hooks-daemon health
# Expected: "Daemon: RUNNING" with no errors
```
