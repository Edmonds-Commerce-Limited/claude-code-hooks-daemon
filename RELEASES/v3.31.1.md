# v3.31.1 — Patch: fix Sev-1 Stop/SubagentStop infinite loop regression from v3.31.0

**Release date**: 2026-07-01
**Type**: PATCH release
**Urgency**: Upgrade immediately if you are on v3.31.0

## Summary

v3.31.1 fixes a Sev-1 regression introduced in v3.31.0: a genuine infinite loop on
Stop/SubagentStop events that could hang or require killing a live Claude Code session.
v3.31.0's fix to `HookResult._format_stop_response()` started emitting
`hookSpecificOutput.additionalContext` for Stop/SubagentStop ALLOW decisions whenever
`context` was non-empty. Claude Code treats any non-empty `additionalContext` on
Stop/SubagentStop as "continue the conversation," regardless of decision — and because
unconditional advisory Stop handlers (e.g. `hello_world_stop`) contribute non-empty
context on every single Stop event, this created an unbounded re-entry loop with no
natural termination. This release restores correct behaviour: advisory context now
surfaces only on the first stop check of a run; any re-entry goes silent so control
actually returns to the user. DENY behaviour is unchanged.

## Fixed

- **Stop/SubagentStop infinite advisory-context loop (Sev-1 regression from v3.31.0)** — v3.31.0's fix to `HookResult._format_stop_response()` started emitting `hookSpecificOutput.additionalContext` for Stop/SubagentStop ALLOW decisions whenever `context` was non-empty (previously it silently returned `{}` for anything but DENY). Claude Code treats any non-empty `additionalContext` on Stop/SubagentStop as "continue the conversation," regardless of decision. Because `hello_world_stop` (and other unconditional advisory Stop handlers) always contribute non-empty context on literally every Stop event, this created a genuine infinite loop: once one ALLOW-with-context response went out, the daemon kept re-triggering "continue" on every subsequent Stop check forever — confirmed directly in `untracked/stop-events.jsonl`, which showed `stop_hook_active=true`/`decision=allow` repeating with no bound until the session had to be killed. `auto_continue_stop`'s existing re-entry guard (`has_recent_stop_hook_block`) only recognised re-entry after a DENY/block marker, so it never caught this class of loop. Fixed by making advisory (ALLOW) context on Stop/SubagentStop surface only on the first stop check of a run (`stop_hook_active` falsy); any re-entry (`stop_hook_active=true`) with a non-DENY decision now returns an empty response so Claude Code can actually return control to the user. DENY is unchanged — it always surfaces regardless of re-entry. Implemented via a new `stop_hook_active: bool = False` keyword parameter on `HookResult.to_json()`, threaded through from the three dispatch call sites that have access to the raw hook input (`core/front_controller.py`, `daemon/server.py`, `daemon/controller.py`). Verified live against the running daemon socket for both Stop and SubagentStop, and pinned with 4 new regression tests in `test_hook_result.py`.

## Upgrade

**This is an urgent fix. If you are running v3.31.0, upgrade immediately** — the
regression can hang or require force-killing a live session.

```
Use the hooks-daemon upgrade skill (Skill tool: skill=hooks-daemon, args=upgrade).
```

No config migration is required. No handler behaviour changes other than the loop fix
itself — DENY responses on Stop/SubagentStop are completely unaffected, and ALLOW
advisory context still reaches the user on the first stop check of each run exactly as
v3.31.0 intended, it just no longer re-fires forever on subsequent re-entries.

## Installation

### New Installations

```bash
mkdir -p .claude && cd .claude
git clone https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git hooks-daemon
cd hooks-daemon
git fetch --tags && git checkout v3.31.1
python3 -m venv untracked/venv
untracked/venv/bin/pip install -e .
untracked/venv/bin/python install.py
cd ../..
```

### Upgrading Existing Installations

```bash
cd .claude/hooks-daemon
git fetch --tags
git checkout v3.31.1
untracked/venv/bin/pip install -e .
untracked/venv/bin/python -m claude_code_hooks_daemon.daemon.cli restart
```
