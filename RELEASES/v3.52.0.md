# Release v3.52.0 - Defence Before Fix

**Release Date**: 2026-08-12
**Type**: Minor
**Previous Version**: v3.51.0

## ⚠️ Read this first: published history was rewritten

**This repository's `main` branch and every tag were rewritten** to remove
identifiers that should never have been committed. This is the release in which
you receive that rewritten history.

| You have                           | What to do                                                                                        |
| ---------------------------------- | ------------------------------------------------------------------------------------------------- |
| A daemon installed in a project    | **Nothing.** Upgrade normally with `scripts/upgrade.sh` — it already force-fetches tags.          |
| A clone or fork you commit to      | **Do NOT `git pull`.** Realign your branch onto its upstream, then `git fetch --tags --force`.    |
| A branch that diverged from `main` | Rebase or cherry-pick onto the rewritten `main`. A merge would republish the pre-rewrite history. |

### Why a pull is the wrong move

A rewrite gives every commit a new sha. Your local `main` and the new
`origin/main` therefore share **no commits at all** — git sees a divergence and
offers to merge. Merging would pull the entire pre-rewrite history back in and
republish exactly what the rewrite was run to remove.

The giveaway is that the two sides resolve to the **same tree**: identical
content, different shas. There is nothing to merge; there is only history to
republish.

### Tags need `--force`

A rewrite moves every tag to a new sha, and a plain `git fetch --tags` will
**not** clobber a tag you already have — it silently keeps the old one. Use:

```bash
git fetch --tags --force
```

`scripts/upgrade.sh` has done this since v3.51.x, so an ordinary upgrade needs
no intervention. Only manual clones do.

### The daemon now warns you

`git_upstream_checker` detects this exact shape — a divergence whose two sides
share no shas yet resolve to the same tree — and **overrides every pull mode**,
including `auto-pull`. Instead of advising a pull in any wording, it asks a
human to realign the branch and re-fetch tags with `--force`.

## Summary

A minor release carrying two new handlers, a whole-tree QA backstop, and the
closure of a bypass class that ran through five existing blocking handlers.

The organising principle is now written into `CLAUDE.md` as Core Standard 15:

> **DBF — Defence Before Fix.** When a defect is found, the defect is the
> *symptom*. The bug worth fixing is the missing or blind guard that failed to
> catch it. A defect fixed by hand recurs; a defect fixed by making the guard
> see it cannot.

Its corollary drove most of the work: **a guard that only fires at write time
does not cover what is already on disk.** A PreToolUse handler sees the next
`Write`; it has never seen the 40,000 files that were there before it existed.
So every write-time rule in this release ships with a batch equivalent, or it is
not finished.

## Why this release exists

### A handler that only matches the spelling you expect is not a guard

Five blocking handlers were bypassable by respelling the command. Not by
obfuscation — by *ordinary* alternative spellings a well-intentioned agent types
by accident:

| Spelling                                    | Was     | Now     |
| ------------------------------------------- | ------- | ------- |
| `git reset --hard`                          | blocked | blocked |
| `git -C /path reset --hard`                 | ALLOWED | blocked |
| `git -c core.x=y stash`                     | ALLOWED | blocked |
| `sudo -H pip install x`                     | ALLOWED | blocked |
| `sudo /usr/bin/pip install x`               | ALLOWED | blocked |
| `curl URL \| /bin/bash`                     | ALLOWED | blocked |
| any of the above, split with a trailing `\` | ALLOWED | blocked |

Ten distinct bypasses in total, found by probing the **live daemon** rather than
by reading the regexes — reading code finds the bugs you already suspect.

The fix is structural, not per-handler. A single
`utils/command_evasion.py` module holds the invocation grammars, and shell line
continuations are normalised **once**, where a command enters the daemon, so
every command guard — including ones written later — sees the joined form.

The most consequential of the ten was in `sensitive_content` itself: it read
`tokens[position + 1]` as the git subcommand, so `git -C /path commit -m "…"`
was classified as *not* a metadata-writing command and allowed straight through.

### The guard for the guards

Closing ten bypasses by hand is a DBF failure — the eleventh would arrive with
the next handler. So the release also ships a completeness-gated test that
discovers every PreToolUse handler by `pkgutil` and **requires each one to be
classified**: hardened against evasion, not command-anchored, or command-anchored
but not unit-testable. A new handler cannot silently escape triage.

That test also requires every hardened handler to carry **false-positive**
cover, and that requirement immediately earned its place: a widened `sudo_pip`
pattern made `sudo` optional, which would have blocked **every ordinary
`pip install` in every project**. The evasion table alone would never have
caught it — it only asks what *should* be blocked.

### What this release does *not* close

All ten bypasses were **invocation** respellings — the same command, dressed
differently. A **synonym** respelling, where a *different* command reaches the
same destruction, is a separate axis and is still open. Two are known:
`git update-ref -d refs/heads/<name>` deletes a branch with no merge check
exactly as `git branch -D` does, and `git push origin +main:main` force-pushes
exactly as `git push --force` does, because the `+` refspec prefix carries the
force rather than a flag.

Both predate this release, so nothing regressed — but naming them matters more
than closing them quietly would, for the reason the section below spells out:
a protection believed to exist is worse than one known to be absent. Tracked in
Plan 00205.

### Seven places a secret can enter a repository, and guards for two of them

`sensitive_content` began as a content check on `Write`/`Edit`. File contents and
file *paths* are only two of the seven surfaces; the other five are git metadata
— commit messages, tag names and messages, branch names, author identity, merge
messages — and **none of them is a file write**. A handler watching file writes
is structurally blind to all five.

All seven now carry a guard. Read-only commands stay allowed even with a term
sitting on the command line (`grep`, `git log --grep=`, `git branch --list`,
`git tag -l`), because searching for a term and removing it are exactly the work
of cleaning a repository.

And per the DBF corollary, the write-time handler is paired with
`scripts/qa/check_sensitive_content.py`, which enforces the same two sources
against **every git-tracked file** — covering everything that never passed
through a tool call: `git mv`, external editors, other agents, and the entire
history of the repository before the handler existed.

### A guard that claimed more than it did

Found during this release's own acceptance gate, by writing a string-built SQL
query at the live daemon and watching it through.

`security_antipattern`'s guidance told every client project that **SQL
injection**, **weak cryptography** and **path traversal** were blocked. Not one
of the eleven language strategies has a pattern for any of the three.

They were absent for a structural reason rather than by oversight. Every
pattern the handler owns matches a **construct** — `eval`, `shell_exec`,
`pickle.load`, `innerHTML`. All three missing categories are properties of how
a value **flows**: a concatenated query is only a vulnerability if the
concatenated part is attacker-controlled, and `md5()` is only weak when it is
hashing a password. A regex sees the shape, never the provenance.

This is the worst shape a guard can have. `get_claude_md()` is inlined into the
resident `CLAUDE.md` and read in full every session, so an agent treats it as
the authoritative statement of coverage — and relaxes its own vigilance about
a class of bug that nothing is watching for. **A protection believed to exist
but absent is worse than a known absence.**

The guidance now names the five categories that genuinely exist and states
outright what it cannot see. A completeness gate requires every claimed
category to be evidenced by a real registered pattern, so the claim cannot
drift back. Implementing the three is tracked in Plan 00204 — with the
false-positive rate measured *before* any pattern is written, because the naive
form of each fires on the overwhelmingly common safe case, and a rule that
cries wolf gets disabled, taking the five working categories with it.

## What's New

### `sensitive_content` — PreToolUse, blocking, dormant by default

Two independently configurable sources:

- **`options.public_patterns`** — named regexes, safe to name. The deny reason
  shows the pattern name and the exact matched text, so you can fix it.
- **`options.secret_word_list_path`** — default `.claude/block-words.secret`,
  gitignored, one term per line, matched literally and case-insensitively.

**A secret-list match is never disclosed anywhere.** Not in the deny reason, not
in any daemon log, not in payload capture, not in a PreCompact transcript
archive. The deny reason names only a 1-based index — `entry N of M in the secret word list` — which is meaningless without the gitignored file.

Only *added* text is checked on an `Edit` (`new_string`), so removing sensitive
content is never blocked.

Both sources are inert by default (`public_patterns` is an empty list; a missing
secret file is a silent no-op), so the handler ships dormant. See
`.claude/block-words.secret.example` for the file format. `*.secret` and
`*.secrets` are now gitignore defaults, and `gitignore_safety_checker` warns
when they are missing.

### `hooks-daemon delete-branch` — a deletion you have to earn

Found the way most gaps are: by hitting it. `destructive_git` blocks
`git branch -D`, and `git branch -d` refuses every branch after a history
rewrite, because a rewrite stops their commits being ancestors of `main`. The
seven stale branches in this repository were therefore undeletable by any
sanctioned route, and this release sat blocked on a human for two days.

The guard was not wrong. The gap was that its only outcome was **escalation, on
every branch, forever** — the project offered no deterministic path to a
provably safe deletion.

This is that path, and it is deliberately not an escape hatch. An escape-hatch
variable would have unblocked the release while proving nothing; the checks are
the entire value. Four tiers, cheapest-first:

| Tier                | Proof                                                                                 |
| ------------------- | ------------------------------------------------------------------------------------- |
| `merged`            | Tip is an ancestor of the protected ref — what git's own safe delete proves           |
| `patch-equivalent`  | Every commit is already upstream by patch-id — the shape a rewrite produces           |
| `content-preserved` | Every file version is byte-identical to a blob still reachable from the protected ref |
| `unproven`          | Everything else — refused, with the files whose content exists nowhere else named     |

The design is evidence-led rather than imagined. Probing the seven real branches
showed neither obvious proof sufficed: none was an ancestor, yet 925–1408
commits each **were** patch-equivalent (a rewrite preserves patch-ids while
changing shas), with 57–65 residual. A single-check design would have refused
everything or approved on a proof that did not hold.

**The proof is blob identity, never path presence.** A path existing upstream
says nothing about the content at that path, so a path-level tier could approve
a deletion that destroys the only copy of a file version. That distinction is
not academic: on these branches a path-level view reported 21 alarming "unique"
paths, of which 20 were byte-identical to blobs already in `main` — merely
sitting where `main` no longer keeps them.

Deletion is all-or-nothing and writes a recovery bundle first unless you pass
`--no-bundle`. Blocking preconditions — the current branch, a branch checked out
in any worktree, a protected name — refuse absolutely and `--allow-unproven`
cannot override them.

**Abandoning unproven work is human-gated.** Every tier above is a *proof*, so
the command can act on it unattended. `unproven` is the opposite: it means the
branch holds the only copy of real work, and discarding that is a judgement, not
a fact. So `--allow-unproven --reason "..."` is necessary but **not sufficient**
— the command also requires a human to type `abandon` at an interactive
terminal. The flags declare *intent*; the prompt asks for *consent*, and the
party that wants the deletion cannot grant its own consent. An agent's shell has
no TTY, so it is refused there with a message telling it to hand the decision
back to you rather than hunt for a way around. Provably-safe tiers never prompt,
so nothing about the automatic path gets slower.

**`git branch -d` remains the first thing to reach for**, and this command is
the fallback for when it has actually refused — not a replacement. `-d` is
battle-tested and this is new. That is also why the `merged` tier *delegates*
to `git branch -d` instead of forcing: git then re-runs its own ancestry check
independently, so a bug in our classifier cannot cause a silent loss on that
tier — git refuses and the command fails loudly. The force flag is used only
where git would refuse no matter what, which is precisely where the extra proof
has to earn its keep.

Squash merges land in that territory too: squashing N commits into one changes
every patch-id, so `-d` and `patch-equivalent` both fail — while
`content-preserved` proves the branch safe and deletes it with no flags.

```bash
git branch -d <name>                          # ALWAYS TRY THIS FIRST
hooks-daemon delete-branch --dry-run <name>   # only if -d refused
hooks-daemon delete-branch <name>             # deletes only if provably safe
```

### `agent_isolation_advisor` — PreToolUse, advisory, on by default

When more than one agent thread is live in a checkout, spawning another `Agent`
without isolation is flagged. Agents sharing one working tree share a single
`.git/index`, so a peer's bare `git commit` can silently absorb another agent's
staged work.

It never blocks, and it deliberately does **not** advise isolation for agents
that need the real project root — daemon restart verification and client-mode
testing do not work in a worktree.

### `journal-dayfile-is-today` — plan QA, edit-time, block by default

A `Write`/`Edit` targeting a plan `JOURNAL/` day-file dated anything other than
today is blocked, and the message names the exact today-dated filename to write
instead. The previous rule tolerated a yesterday-dated file as a "legitimate
midnight rollover"; that tolerance was precisely the mis-filing it now closes.

Unlike the rest of the journalling feature this does **not** ship advise-first,
because the failure mode is silent mis-filing rather than a rollout risk.
Controlled independently via `plan_workflow.qa.journal.today_only_mode`
(`advise` | `block` | `off`; default `block`), and still subordinate to
`plan_workflow.qa.edit_mode`.

### Continuous integration and drift guards

CI now runs on every push, along with the fixes for the two things that would
have made it report green while blind. A **handler-reference truth check** fails
when `docs/guides/HANDLER_REFERENCE.md` drifts from the handler code.

## Upgrade Notes

**No configuration changes are required.** Both new handlers are either dormant
(`sensitive_content`) or advisory (`agent_isolation_advisor`).

**One behaviour change to be aware of**: commands that previously ran will now
be denied — `git -C /path reset --hard`, `git -C /path stash`,
`sudo -H pip install`, `sudo /usr/bin/pip install`, `curl URL | /bin/bash`, and
any of these split across lines with a trailing backslash. If a script of yours
relied on one of those spellings, use the documented escape hatch for that
handler or set its `enabled: false` — do not respell the command.

Projects with `plan_workflow` enabled and the default `edit_mode: block` will
find stale journal day-file edits blocked immediately; set
`plan_workflow.qa.journal.today_only_mode: advise` if you need scripted backfill.

### Installation

```bash
mkdir -p .claude
git clone https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon
git -C .claude/hooks-daemon fetch --tags --force
git -C .claude/hooks-daemon checkout v3.52.0

# The installer builds the venv, installs the package and starts the daemon.
# Never hand-build the venv: it is fingerprint-keyed, and a hand-made
# untracked/venv/ is the retired pre-v3.7.0 layout the resolver refuses.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
curl -fsSL https://raw.githubusercontent.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon/main/scripts/upgrade.sh -o /tmp/upgrade.sh
less /tmp/upgrade.sh          # review before running
bash /tmp/upgrade.sh --project-root /path/to/your/project v3.52.0
rm /tmp/upgrade.sh
```

Verify afterwards:

```bash
.claude/hooks-daemon/bin/hooks-daemon status     # expect: RUNNING
```

If your daemon directory has diverged from the rewritten upstream, the upgrade
script now reports it rather than merging.
