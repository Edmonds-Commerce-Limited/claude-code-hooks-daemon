# Release v3.76.0 - Remote-Delete Proofs Judged Against the Remote Default, Long Project Paths, and a Harder Secret Guard

**Release Date:** 2026-11-20
**Type:** Minor Release

## Summary

This release fixes how a remote branch delete is proven (against the remote's default branch only, with a new cherry-pick route and empty-commit tolerance), adds a warning ladder to the three branch pools, stops a long project path from denying every tool call, moves the supervisor's idle compaction to the orange context tier, and hardens `secret_file_guard` and the quarantine guard against links, computed `cd` moves and scans that stop early. Seven release-note callouts are folded into Highlights below, in the authors' own words.

## Read this first

- **Several denials get stricter and several proofs change; no command is removed and no config key is renamed.** The config-changes manifest is not marked breaking.
- **Restart the daemon once after upgrading.** The socket fallback directory changed (private, mode 0700), so a host that relied on the bare `/tmp` fallback gets its socket in a new place.
- **Remote deletes need a tracking default.** A clone without `refs/remotes/<remote>/HEAD` has its remote deletes refused until `git remote set-head <remote> --auto` is run or `branches.default` is set.
- **No pre-upgrade or post-upgrade task.**

## Highlights
### Audience: operators

#### branch pools now warn well before they refuse a new branch

_Plan 00619 · Audience: operators_

Each branch pool (open work, parked, merged) now warns as it fills: at 60 percent of the point where creating a branch is refused, more firmly at 80 percent, and at 90 percent on every tool call and every prompt until the pool drops below it. Session start and the main thread's stop report the same ladder. The warning names the pool, its count, the first branch to finish or remove and its command; the percentages are `branches.wip.ladder`, `branches.parked.ladder` and `branches.merged.ladder`. The block at the limit is unchanged and has no exemption, and no guard denies or allows anything it did not before.

#### empty commits on a merged branch no longer block its delete

_Plan 00622 · Audience: operators_

A branch whose work is already in the default branch, with one or more empty commits on top (a hand-written `Unpark branch`, a note, any commit that changes no file), was refused by `R-GIT-PUSH-DELETE-REMOTE`, `branch-sweep --clean --remote` and `delete-branch` as "not merged". It is now proven with the new evidence tier `empty-commits-only`: every commit the default lacks has exactly one parent and that parent's tree. The commit message plays no part. A commit that changes any file, a merge commit (even one with its first parent's tree), and a root commit still count as content, so no branch carrying content the default lacks gains a pass. What a delete of such a branch loses is the empty commits themselves and their messages; `delete-branch` still prints a `git branch <name> <sha>` restore line. A branch made only of empty commits off the default is deletable on the same rule. An empty commit is never excused by patch-id equivalence alone, because a patch-id ignores whitespace: a cherry-picked branch with an empty commit on top is still refused on the hook-path cleanup, which has only patch-ids, and passes `delete-branch` and the remote proofs only when the default holds its exact net change. Every git call the daemon makes now reads the stored objects: replace refs (`git replace`) and a legacy `.git/info/grafts` file are ignored, so neither can make a content commit look empty or make the default look as if it holds a branch. Whether a commit is empty is decided from the stored commit objects themselves, read with `git cat-file`: the commit-graph cache (the repository's own, or one in an alternate object store) is turned off for that walk and never trusted, so a hand-edited graph cannot make a content commit read as empty either. Any failure to read a commit object leaves the branch unproven, which refuses the delete. The cached remote-delete proofs are recomputed once after the upgrade (the cache key version moved), so a branch refused before the upgrade is judged afresh.

#### remote branch deletes are proven against the remote's default only, and interleaved cherry-picks now prove

_Plan 00626 · Audience: operators_

**Safety fix.** `R-GIT-PUSH-DELETE-REMOTE` (an agent's `git push --delete`) and `branch-sweep --clean --remote` proved a remote branch "merged" against the LOCAL default branch as well as the remote one. A branch merged only into a local default whose push had not landed (waiting on CI, say) was therefore listed as proven and deletable on the remote, although the remote held that work nowhere else. Every remote-delete proof now judges the remote-tracking default (`refs/remotes/<remote>/<default>`) alone, and confirms in the same `git ls-remote` it already made that the remote's live default, and the integration line that proved a branch by ancestry, are at the shas the proof read. A missing tracking default, a tracking ref moved locally (`git update-ref`), a remote default that moved since the last fetch, or a failed listing all refuse the delete with a "run `git fetch` and retry" reason. With `branches.default: auto`, the remote default is read from `refs/remotes/<remote>/HEAD` only: the local `main`/`master` fallback is no longer used for a remote delete, because on a repository whose default has another name it can be a stale old branch. A clone without that ref (for example one built with `git remote add` rather than `git clone`) has its remote deletes refused until `git remote set-head <remote> --auto` is run or `branches.default` is set. A cached proof result no longer authorises a remote delete: the cache is a plain file in the working tree, so a positive result is recomputed every time; only a cached refusal is reused. Remote deletes of proven branches therefore cost a little more git work on each run. Local deletes (`delete-branch`, `git branch -d`) are unchanged.

**Over-refusal fix.** A branch whose commits were cherry-picked onto the default, with the default changing one of the same files between the picks, was refused as "not merged" even though `git cherry` marked every commit `-` (park and unpark markers on top included). No single commit of the default held the branch's whole result, and that was the only content proof. Such a branch is now proven `patch-equivalent` when BOTH hold: `git cherry` finds every non-park commit's patch in the remote default with no merge commit in the range, AND every path the branch changes is held at its exact bytes and mode (a deletion: absent) by some first-parent commit of the default after the merge base. The exact-bytes check closes the hole that kept patch-ids from proving a branch alone (a patch-id ignores whitespace), and a branch with no merge base is never proven this way. The proof cache key version moved, so earlier refusals are judged afresh after the upgrade.

#### a long project path no longer denies every tool call

_Plan 00628 · Audience: operators_

**Live defect fix.** In a project whose absolute path is long enough that the daemon's natural socket path (`<project>/.claude/hooks-daemon/untracked/daemon-<hostname>.sock`) exceeds the 104-byte AF_UNIX limit, every tool call was denied with `daemon_startup_failed`. The hook started the daemon with its own computed socket path forced through `CLAUDE_HOOKS_SOCKET_PATH`, the daemon used a forced path verbatim, and the bind failed (`AF_UNIX path too long`), while `status`, which shortens the path itself, could report a daemon RUNNING that no hook could reach. A start that failed this way also deleted a running daemon's socket discovery file, so the hooks lost a healthy daemon too.

Now one function (`paths.fit_socket_path` / `fit_pid_path`) decides the socket and PID path for every caller: the default, `CLAUDE_HOOKS_SOCKET_PATH` / `CLAUDE_HOOKS_PID_PATH`, the `--socket` / `--pid-file` flags and `daemon.socket_path` / `daemon.pid_file_path` in the config. A requested path that fits is honoured verbatim; one over the limit is replaced by the project's short fallback, the same one `status` computes. The hook's start wait now follows the discovery file, so the hook that starts the daemon also reaches it. The discovery file is written only once the daemon has bound its socket, and removed only by the daemon that wrote it.

**Security tightening.** The short fallback directory must now be a real directory (not a link) owned by the daemon's user and closed to group and others (mode 0700, as `$XDG_RUNTIME_DIR` and `/run/user/<uid>` normally are). A runtime directory that fails this, for example `$XDG_RUNTIME_DIR` inherited from another user, is skipped. With neither available the daemon uses `/tmp/hooks-daemon-<uid>`, created with mode 0700, instead of `/tmp` itself; if that directory exists and is not private (another user's, a link, or open to others) the start fails closed with a message naming it, rather than placing the socket somewhere another user could reach. A host that relied on the bare `/tmp` fallback, or on a non-private runtime directory, places its socket in a new location after the upgrade; restart the daemon once after upgrading.

### Audience: client projects

#### the supervisor's idle compaction now keys on the orange context tier after ten minutes idle

_Plan 00603 · Audience: client projects_

The ccy supervisor's own idle compaction (shipped in dry-run by default) changed its two main defaults. It now fires when the session's context tier is ORANGE or higher, instead of at a fixed 30 percent, and only after the true idle has held unbroken for 600 seconds, instead of 60. The tier is the daemon's own classification, the same one the status line colours, so the gate follows the window size: orange starts at 30 percent of a 1M-token window and 51 percent of a 200k one. A 200k session at 35 percent (yellow) is therefore no longer a candidate, and a 1M session behaves as before apart from the longer wait.

New setting `CCY_IDLE_COMPACT_TIER` (`yellow`, `orange` or `red`; anything else is `orange`). `CCY_IDLE_COMPACT_PCT` is now unset by default; setting it replaces the tier gate with that percentage, so a project that pinned a percentage keeps it. A sidecar tier the supervisor does not recognise never fires.

The idle compaction also now waits for queued supervisor work: when a standing-authorisation reminder, a session-actions directive or a cron-reconcile prompt is pending, that goes first and the compaction is reconsidered after.

The mode default is unchanged (`dry-run`: a `would idle-compact` line in `decision.log`, nothing typed); set `CCY_IDLE_COMPACT=on` in `.claude/ccy/ccy.env` to arm it. The decision half hot-reloads with the worker; no relaunch is needed for the new defaults. See [CLAUDE/development/CcySupervisor.md](../../../development/CcySupervisor.md).

#### the secret guard judges a link from the command's own directory

_Plan 00614 · Audience: client projects_

A symlink with an innocuous name that points at a protected file was denied when spelled as an absolute path, but three spellings reached the file's content past `secret_file_guard`:

- A relative Bash word naming the link (`cat link`, `cat < link`, an interpreter one-liner's `open('link')`). The daemon runs from `/`, so the link was looked up there instead of in the command's working directory. It is now resolved from the hook's `cwd` (and every literal `cd` target), and a link anywhere on the path counts, not only the last component. A relative `Read` or `Grep` path is judged the same way.
- A recursive search (the Grep tool, `grep -r`, `rg`) rooted at a directory link that leads out of the project, typically into another checkout from a worktree. The protected-file index lists only the project, so such a search is no longer vouched for and is denied.
- A glob under a directory link (`cat dlink/*`) that leads out of the project. Plan 00612 already matches such a glob with its literal directory resolved; a target outside the project is now denied too.
- A `cd` the command makes anywhere bash runs it: in a subshell `( )`, a brace group, after `if`/`while`/`then`, in a `$( )` or backtick substitution, in a quoted `bash -c` body, and `env -C`/`--chdir` and `git -C`. All of these now move where a relative link is read, for both the text scan and a recursive search.
- A glob whose wildcard sits in the component that names the directory link (`cat dl*/*`, `cat pl*/sub/*`, `grep -r x dl*`). The matching links in the literal parent are listed and judged. A glob whose first component is wildcards only (`*/*`) still names no place and is allowed.
- A command an exemption clears (an allowlisted consumer such as `ansible-playbook` with the protected path in flag position, a grep whose protected mention is only its pattern, or one naming an encrypted-at-rest file) no longer clears a relative link to a protected file beside it.

Behaviour change: a recursive search or a glob through a link from inside the project to a directory outside it is denied even when that directory holds no protected file. The deny message now says that a link to a directory outside the project is the cause, names the link, and says to run the command from the checkout that holds the target. It also names the first configured protected glob, because no particular file matched.

- A `cd` spelled `builtin cd`, `command cd`, or with a redirection before it or before its operand (`>/dev/null cd x`, `cd 2>/dev/null x`), and the chdir options `sudo -D`/`--chdir` and `tar -C`/`--directory`. All of these now move where a relative word is read.
- A glob with no slash (`*`, `i*`, `*/*`) read after a `cd` into a directory link that leads out of the project. It is now denied like `./*`.

Behaviour change: a `cd` whose target bash computes (`cd "$D"`, `cd $(pwd)/x`, `cd -`, a bare `cd`) now makes relative words and search roots be read from the project root, and from every project directory that holds a link, as well as from the hook's `cwd` and every literal target. Before, they were dropped. So `cd "$D" && grep -r foo .` is now judged over the project root. A variable the same command assigns literally (`D=x; cd "$D"`) is put in, in addition to those directories rather than instead of them. A globbed target (`cd inn?r`) is expanded on disk, listing at most 512 directories; a wider glob is judged like a computed target. A wrapper before a command with a chdir option (`sudo tar -C d`, `nice git -C d`, `nohup env -C d`) no longer hides the option. The directories that hold a link are found by a scan of at most 512 directories (see the next-but-one change for what happens past that).

Behaviour change: if working out where a command's paths lead raises an error, the call is now denied rather than allowed with an advisory. This covers placing a directory it moves to, a link or a glob. Before the fix, a `cd` to a single name over 255 bytes made every protected read in the same command go unjudged. A failed `cd` (to a name that is not a directory) keeps the directory a recursive search was already in, as bash does for a command after `;` or `||`.

Behaviour change: when a command moves into more than 16 existing directories, a relative word that could pass through a link in one of them is denied rather than resolved from each, and the deny message says to split the command. The same rule applies to the quarantine-artefact guard, which shares the index. A path that is outside the project as spelled is judged as before, and an ordinary relative word that is not a link behaves as before.

Security fix: when the scan of a Bash command stopped early (a brace expansion past the enumeration cap, the scan deadline, a word it could not read, or an internal error), only the literal paths in its text were judged, so a recursive search in the same command (`echo {a..z}{a..z}{a..z}; grep -r x dir`) was allowed with the not-judged advisory. Such a command is now denied whenever it holds a recursive search or a glob, and the deny says the scan stopped before it finished. A command with neither keeps the advisory. A Grep tool call whose check stopped early is denied the same way.

Behaviour change: any Bash command holding a glob character (`*`, `?`, `[`) or a recursive search whose scan stops early is now denied, where it was allowed with the not-judged advisory. Split a command that trips this, or drop the large brace expansion beside it.

Behaviour change: after a `cd` whose target bash computes (`cd "$(pwd)/x"`), or a globbed `cd` that matches nothing, a glob read (`ls *.md`) is denied in a project that holds a directory link leading out of the project, because the shell could be inside that link. A plain relative path is still judged as before. Spell the directory literally to avoid it.

A `cd`, `env -C`, `sudo -D`, `tar -C` or `git -C` named by its path (`/usr/bin/env -C d`) is now read like the bare command.

A command with many `cd`s to directories that do not exist no longer makes the search check's cost grow without bound: past 64 candidate directories every later read is judged over every indexed file and over every directory link a move could reach.

A `cd` operand that is an extended glob (`@(x)`, `+(x)`), a relative `cd` in a command that names `CDPATH`, and `eval cd x` are now judged like a computed `cd`.

A globbed `cd` that matches more than 16 directories is judged like a computed `cd` rather than followed match by match, which keeps the guard's cost bounded (`cd */*/*` over a wide tree no longer takes seconds).

A computed `cd` is now also judged from inside each directory link in the project, not only from the directories that hold a link, so `cd $(echo link) && cat .e*` is denied when `link` leads out of the project. At most 512 directory links are considered.

Behaviour change (fail closed): the link scan behind a computed `cd` now reports whether it finished. It does not finish when the project has more than 512 directories (most real repositories), more than 512 directory links, or a link whose target cannot be stat-ed for a reason other than a loop. Then any relative word after the computed `cd`, and any recursive search or directory reader after it, is denied, because the shell may be in a directory the scan never reached. Before, the scan logged that it stopped and the call was allowed; one link loop early in the project could also end the scan silently. In a large project, `cd "$D" && make test` or `cd $(pwd)/x; ls` is therefore denied; spell the directory literally instead. `cd "$(git rev-parse --show-toplevel)"` (or the backtick form) is not a computed move: it is placed at each ancestor of where the command is, up to the project root, and needs no scan. A command that names a `GIT_` variable is still judged as computed. The unquoted `$( )` form placed before a recursive search (`cd $(git rev-parse --show-toplevel) && grep -r x d`) is still denied in a large project; quote it. A quoted `bash -c` body holding `&&` or `;` after a `cd` (`bash -c 'cd sub && cat f'`) is read as a computed move and is denied in a large project too.

After a computed `cd`, a relative word of several components (`cat a/late`) is also resolved from each directory above a scanned link that its leading components lead into, so a link one or more levels below where the shell may be is judged. Behaviour change: a recursive search or directory reader after a computed `cd` is now judged as reading every directory link in the project too, so in a project holding a directory link out of the project, `cd "$D" && grep -r x sub` is denied.

The scan is reused only within one tool call. Before, it was kept for 5 seconds, so a link made by one call could be read through by the next.

A chdir option inside a short-option cluster (`env -iC d`, `sudo -nD d`, `env -iCd`) or abbreviated (`env --chd=d`, `env --ch d`, `sudo --chd=d`) now moves where a relative word is read, as does `exec` before the command (`exec env -C d`, `exec -a name env -C d`).

A Grep tool call with no `path` is judged at the hook's `cwd` when that directory passes through a link, so a session whose directory is a link out of the project is denied a search there. A pathless Grep from an ordinary directory is judged as before.

`cd "$(git rev-parse --show-toplevel)"` is not trusted when the command defines a function or alias, changes `PATH`, sets `core.worktree` or names a `GIT_` variable; it is then judged as computed. Otherwise it is judged as computed too, with each ancestor added, but a link scan that did not finish does not deny it. The quarantine-artefact guard now denies a call whose paths could not be placed, as the secret guard does, instead of allowing it with an advisory.

Upgrade: nothing to do.

#### computed `cd` moves in large projects are judged from a link index

_Plan 00623 · Audience: client projects_

Behaviour change (usability): release note 003 made a `cd` whose target bash computes (`cd "$D"`, `cd -`, a bare `cd`, `cd ~/x`, `cd "$TMPDIR"`) deny any later relative word once the project held more than 512 directories, because the per-call link scan could not finish. That was most real repositories. The daemon now keeps an in-memory index of the project's directories and links. It is built in the background when the daemon starts and checked against the filesystem before each use, so such commands are judged on what the project really holds: allowed when no link reaches a protected path, denied when one does. Until the index is built (the first seconds after a restart), the old bounded scan is used and may still deny.

The index is never written to disk, so no file in the project can forge it. It fails closed: a project past 200,000 directories, a check that has to re-list more than 4,096 changed directories or that runs past 2 seconds, a project root that cannot be stat-ed, a directory anywhere in the project that cannot be listed, or a link whose target cannot be told all deny the computed move followed by a reader, and a rebuild starts in the background. `.git` directories are indexed too. A project past 200,000 directories (for example a checkout that holds many other worktrees or large scratch trees) therefore denies every computed move followed by a reader.

When the index names more than 512 link-holding directories and directory links together (a `node_modules/.bin` in every package), a word read after a computed move is judged by link name instead of from each directory: it denies when any leading part of it spells the end of a link path anywhere in the project (`cat .bin/tool`, `cat l*` when a link `late` exists), or when it holds `..`. Words that name no link (`cat README.md`, `ls -la`, `npm test`) are allowed. A relative or globbed `cd` after such a move, a relative glob, and a recursive search that could reach a protected file anywhere in the project still deny. The move still denies when the project holds more than 512 links to directories or more than 65,536 links in all.

Behaviour change: a move to `~`, `$HOME` or `$TMPDIR` (with an optional literal path after it) that lands outside the project is placed there, using the daemon's own value of the variable, instead of being judged as an unknown move. It is placed only when the command names the variable nowhere else. Placement does not excuse a link scan that stopped: until the index is built, or when it fails closed as above, such a move followed by a reader still denies. The same holds for `cd "$(git rev-parse --show-toplevel)"`.

Security fixes, each of which was allowed before:

- A bracket glob that bash expands to exactly a link to a protected file (`cat dir/[l]ink`, `cat d[i]r/link`) is now denied, as the literal spelling was. Each finite bracket expansion is checked for links like a plain word.

- After a computed `cd`, a word that steps back with `..` (`cat .bin/../dir/link`, `cat ../dir/link`) is now judged from every project directory it could be read in, so a link on its collapsed path to a protected file is denied.

- A relative word that fits PATH_MAX on its own but not once joined to the project directory (`cat plain/../plain/../…/link`) is now denied when it cannot be stat-ed.

- A path through the daemon's own process view (`/proc/self/…`, `/proc/thread-self/…`, `/dev/fd/…`) is now denied in Bash, Read and Grep, because the daemon would resolve it from its own working directory rather than the shell's. Behaviour change: ordinary reads such as `cat /proc/self/status` and `ls /dev/fd` are denied too.

- `cd "$(git rev-parse --show-toplevel)"` is no longer placed at an ancestor of the command's directory when git config in the repository, user or system config names a worktree or an include, or a `GIT_` relocating variable is set for the daemon.

- A recursive search or a directory change nested more than four `bash -c` levels deep is now denied when the nested body could read or move; a harmless nested body is still allowed.

- A globbed or relative `cd` taken from more than 17 directories, and a wildcard whose parent directory exists but cannot be listed, now deny instead of dropping the directories not looked at.

- The quarantine-artefact guard, the flaggable-content guard and payload capture now treat a command whose words cannot be placed as a finding (deny, or excluded from capture) instead of an unjudged allow.

## Security

- **Remote delete proofs no longer trust an unpushed local default** (Plan 00626): `R-GIT-PUSH-DELETE-REMOTE` and `branch-sweep --clean --remote` judge the remote-tracking default alone. See the callout above.
- **`secret_file_guard` and the quarantine-artefact guard deny more** (Plans 00614, 00623): links, computed `cd` moves, `/proc/self` paths and early-stopped scans. Every change denies more, never less, except where a computed move in a large project is now judged from the link index instead of denied outright. See the callouts above.
- **The daemon's socket fallback directory is private** (Plan 00628): it must be owned by the daemon's user with mode 0700, or the start fails closed.

## Upgrade Instructions

No pre-upgrade or post-upgrade task and no breaking change. Config keys are added (`branches.wip.ladder`, `branches.parked.ladder`, `branches.merged.ladder`), all optional with defaults of 60, 80 and 90; see `CLAUDE/UPGRADES/config-changes/v3.76.0.yaml`. Restart the daemon once after upgrading (the socket fallback location may change), and run `git remote set-head <remote> --auto` in any clone whose remote deletes are refused for a missing tracking default.

## Installation

### New Installations

```bash
mkdir -p .claude
git clone -b v3.76.0 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon

# The installer builds the fingerprint-keyed venv, installs the package and
# starts the daemon. Never hand-build a venv: the resolver refuses the
# retired pre-v3.7.0 layout.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
git -C .claude/hooks-daemon fetch --tags

# Rebuilds the venv and reinstalls the package for the target version. Runs the
# target's own upgrade.sh: the installed one may predate the pre-deploy gate.
tmp="$(mktemp)"
git -C .claude/hooks-daemon show "v3.76.0:scripts/upgrade.sh" > "$tmp"
bash "$tmp" --project-root "$PWD" "v3.76.0"

.claude/hooks-daemon/bin/hooks-daemon restart
```
