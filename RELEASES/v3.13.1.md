# Release v3.13.1 — Niggles + Plan 00101 Phases 9/10

**Type:** Patch Release

## Summary

This patch release ships seven bug fixes against v3.13.0: three field-reported niggles (boot-race false alarm, health-check handler count, CWD-relative log paths), Plan 00101 Phases 9 + 10 (Stop hook hard-block via exit-code-2 + asyncio readline buffer lift), and the plan-folder close-out reconciliation. No new features, no breaking changes.

Five of the seven commits address bugs surfaced by dogfooding the daemon in its own repo. All fixes are TDD-verified (RED before fix, GREEN after) and the full QA suite is green: 15/15 gates, 8226 tests / 0 failed, 94.97% coverage.

## What's Fixed

### SessionStart `daemon_startup_failed` boot race (`init.sh`)

Three-prong fix for the false-alarm "daemon failed to start" message that fired even when the daemon was up within ~1s:

- `DAEMON_STARTUP_TIMEOUT` raised from 50 to 150 deciseconds (5s → 15s), matching the python-side `Timeout.DAEMON_RESTART_VERIFY_TIMEOUT_SEC` that Plan 00100 Task 0.2 already aligned for `daemon_control.sh::restart_daemon_verified`.
- Polling loop now combines `is_daemon_running` AND socket-file existence so a transient socket from `enforce_single_daemon` doesn't trigger a false-positive readiness signal.
- Final retry probe after the loop closes the boundary race where the daemon binds on the same tick `elapsed < TIMEOUT` flips false.
- Removed the destructive `rm -f "$PID_PATH"` on timeout that was killing the genuinely-coming-up daemon's PID slot.

New regression test: `tests/integration/test_init_sh_start_daemon_boot_race.py` (4 static-analysis checks, RED before fix, GREEN after).

### `health-check.sh` reports correct handler count (niggles Issue 2)

`health-check.sh:186` scraped the human-formatted output of `daemon.cli handlers` with `grep "^  -"` expecting a leading dash; the actual display format is `"  [T] 10 name"` / `"  [-] 23 name"` where the dash is bracketed and never appears at the literal start of the line. The grep matched zero lines and the silent `|| echo "0"` fallback returned `0` for every install since the bracketed-flag column was added.

Fix: expose a machine-readable count via `daemon.cli handlers --count` so the shell script never has to scrape display format. Dropped the silent fallback — if the count query fails, the script now prints a visible failure rather than masking it as 0 (same antipattern that caused the v3.9.0 field bug).

### Logger and cleanup handlers resolve untracked path via `ProjectContext` (niggles Issue 3)

Three handlers (`notification_logger`, `subagent_completion_logger`, `cleanup_handler`) wrote/read a CWD-relative `untracked/...` path. When the daemon's CWD is `/` (typical for a daemonized process), `untracked` resolved to `/untracked` → `Permission denied`, and notification logs and subagent completion logs were silently dropped; `CleanupHandler` silently no-op'd because the target dir never existed at that path.

Fix: every log/temp path now resolves against `ProjectContext.daemon_untracked_dir()` so they land in the project's untracked dir regardless of process CWD. `test_cleanup_handler.py` rewritten to use real filesystem operations instead of brittle `Path` mocking.

### Stop hook hard-block via exit-code-2 wrapper contract (Plan 00101 Phase 9)

Claude Code v2.1.114 silently downgrades JSON-stdout `{"decision":"block"}` for Stop/SubagentStop events to suggestion-level (`level: suggestion`, `preventedContinuation: false`); the documented alternative per `CLAUDE/Code/HooksSystem.md` is exit code 2 + stderr explanation, which the daemon Python process cannot emit directly because the wrapper subprocess controls the exit code.

Solution: bash wrapper `forward_stop_event` shared helper in `init.sh` (DRY across Stop + SubagentStop) detects `{"decision":"block","reason":"..."}` in the daemon response and re-emits the reason to stderr with exit 2. Installer regenerates wrappers via `_STOP_EVENT_NAMES` branch in `create_forwarder_script`. Daemon JSON output unchanged (back-compat).

Three new acceptance tests in `tests/acceptance/test_stop_hook_hard_block.py` wired into RELEASING.md Step 12.0 H-1 gate (now 22 tests total).

### asyncio readline buffer lifted to 16 MiB (Plan 00101 Phase 10)

Root cause of the dogfooded `LimitOverrunError("Separator is found, but chunk is longer than limit")` PostToolUse output: `asyncio.start_unix_server` defaulted the `StreamReader` buffer to 64 KiB. A single PostToolUse `Edit` on this repo's own `cli.py` (102,927 bytes; `old_string + new_string` roughly doubles that) sends a JSON request well above that ceiling, `readline()` raises `LimitOverrunError`, the bare except in `_handle_client` returns `{"error": "Separator is found..."}` as the daemon response — and the PostToolUse advisory context the model would have seen is silently dropped.

Fix: new `SocketLimit.REQUEST_BUFFER_BYTES = 16 MiB` constant in `constants/protocol.py` passed as the `limit=` kwarg to `asyncio.start_unix_server`. 16 MiB sits above any realistic full-file Edit hook payload while bounding per-connection memory. RED test in `tests/daemon/test_server.py` reproduces the exact `LimitOverrunError` with a 200 KiB request payload and asserts the daemon responds normally instead of returning `{"error": ...}`.

## What's Changed

- **`daemon.cli handlers --count` machine-readable output** — New flag on the existing `handlers` subcommand prints only the loaded-handler count as a single line, used by `health-check.sh` so it never has to scrape display-formatted output.
- **Plan 00101 closed (Phases 9 + 10 delivered post-v3.13.0)** — Plan moved to `CLAUDE/Plan/Completed/`. `CLAUDE/Plan/README.md` index updated — Active Plans count 4 → 3, Completed Plans count 90 → 91.

## Breaking Changes

None. This is a PATCH release. Daemon JSON output is unchanged; the only externally observable change is that Stop/SubagentStop wrappers now emit exit code 2 + stderr on hard-block decisions (the documented Claude Code contract), where v3.13.0 wrappers emitted JSON-via-stdout that Claude Code v2.1.114 silently demoted to suggestion-level. Consumers that parse wrapper exit codes should already handle exit 2 as a hook block per the Claude Code hook spec.

## Install / Upgrade

### Upgrading Existing Installations

```bash
curl -fsSL https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon/releases/latest/download/upgrade.sh \
  | bash -s -- 3.13.1
```

The skill upgrade.sh self-bootstrap path verifies the v3.13.1 manifest (`bootstrap-checksums.txt`) against the published sha256 for every bootstrappable script before executing.

### Fresh Installations

```bash
git clone -b v3.13.1 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git
cd claude-code-hooks-daemon
./scripts/install.sh
```

## Verification

After upgrading, verify the daemon is healthy:

```bash
$PYTHON -m claude_code_hooks_daemon.daemon.cli status
# Expected: Daemon: RUNNING

bash .claude/hooks-daemon/scripts/health-check.sh
# Expected: "Loaded handlers: N" where N matches `daemon.cli handlers --count`
# (Prior to v3.13.1 this reported 0 on every install since the bracketed-flag column was added.)
```
