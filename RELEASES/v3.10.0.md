# Release v3.10.0 - venv resolver DRY consolidation + 2026-05-01 field-report fixes

**Release Date:** 2026-05-01
**Type:** Minor Release

## Summary

v3.10.0 closes the structural cause of the v3.9.x field-report regression series. Where v3.9.1 fixed each of five resolver sites independently, v3.10.0 collapses all of them to a single canonical resolver library at `scripts/lib/resolve_venv.sh` — the four resolver concerns (`resolve_existing_venv_python`, `verify_venv`, `venv_lock_hash_matches`, `read_metadata_field`) now have exactly one implementation in the repo. Every shell caller delegates to it.

The release also fixes the six issues reported in the 2026-05-01 field report (Issues #1, #3, #4, #6 — Issues #2 and #5 were duplicates), adds a static-check QA gate that prevents future drift, and introduces an H-1 acceptance gate that mandate-tests the production diagnostic scripts end-to-end before any release can ship.

The 2026-05-01 field report (`CLAUDE/Plan/00104-v3.10.0-venv-resolver-dry-consolidation/context/2026-05-01-field-report-upgrade-issues.md`) is the verbatim primary source for this release. Every fix in this changelog corresponds to an issue number in that report.

## Highlights

- **One resolver, one implementation**: The five resolver sites that v3.9.1 fixed independently are now thin shims over `scripts/lib/resolve_venv.sh`. Future drift is impossible by construction.
- **12th QA gate — canonical-callers static-check**: Any new caller of the four canonical resolver functions that does not source the canonical library fails QA. Catches drift at QA time, not in field reports.
- **H-1 acceptance gate (BLOCKING release)**: `tests/acceptance/test_diagnostic_scripts.py` mandate-tests the production diagnostic scripts end-to-end against a fixture project. Wired into `RELEASING.md` as Step 12.0 — v3.10.0 cannot ship without these passing, and neither can any future release.
- **Issue #4 root cause fixed**: `cli.py:1415`'s `.resolve()` was recording `python_path` as the system Python (`/usr/bin/python3.11`) instead of the venv's `bin/python` whenever the venv used a symlinked interpreter. Every downstream `ModuleNotFoundError` traced back to this single line. Fixed.
- **Skill `upgrade.sh` self-bootstrap with sha256 verification**: The skill now fetches the latest `upgrade.sh` body from the GitHub release, verifies it against the published `bootstrap-checksums.txt`, and re-execs the fresh body. Aborts loudly on network failure rather than silently using the stale local copy. Closes Issue #1.
- **Multi-host NFS fail-fast and `requires-python` cross-check**: The resolver refuses to use a venv whose `.daemon-metadata.json` was written on a different host, and validates the venv's Python against `pyproject.toml`'s `requires-python` constraint at resolution time.
- **Hot-path cache restored**: `init.sh::_resolve_python_cmd` caches the resolved Python path in a per-shell-process variable, so the canonical-library indirection costs nothing on the hot path.

## Changes

### Added

- **Canonical resolver library `scripts/lib/resolve_venv.sh` (Plan 00104 Phase 4)**: Single source of truth for the four shell-side resolver concerns. Every shell caller delegates to this library; the previous five independent reimplementations are now thin shims that source it. Closes the structural cause of the v3.9.0 field-report regression series.
- **Canonical-callers static-check (12th QA gate, Plan 00104 Phase 6)**: New QA check `scripts/qa/run_canonical_callers_check.sh` scans every shell script in the repo and asserts that any caller of `resolve_existing_venv_python`, `verify_venv`, `venv_lock_hash_matches`, or `read_metadata_field` either *is* `scripts/lib/resolve_venv.sh` or sources it. Integrated into `run_all.sh` as check 12.
- **Multi-host NFS fail-fast and `requires-python` cross-check (Plan 00104 Phase 7)**: The canonical resolver refuses to use a venv whose `.daemon-metadata.json` was last written by a different host, and validates the venv's Python interpreter against `pyproject.toml`'s `requires-python` constraint at resolution time. Both produce a clear non-zero exit with a directive rather than silently using an incompatible environment.
- **Hot-path cache for `_resolve_python_cmd` (Plan 00104 Phase 8)**: `init.sh::_resolve_python_cmd` now caches the resolved Python path in a per-shell-process variable, so repeated invocations within the same shell session pay the resolution cost only once. Restores hot-path latency to pre-resolver-library levels.
- **Skill `upgrade.sh` self-bootstrap with sha256 verification (Plan 00104 Task 5.1, Decision 3.C)**: The hooks-daemon skill's `upgrade.sh` now fetches the latest `upgrade.sh` body and `bootstrap-checksums.txt` from the GitHub release, verifies the body against the published sha256, and re-execs the fresh body before invoking the rest of the upgrade. Aborts loudly on network failure rather than silently falling back to the stale local copy. Closes Issue #1 from the 2026-05-01 field report.
- **H-1 acceptance gate `tests/acceptance/test_diagnostic_scripts.py` (Plan 00104 Phase 9)**: Five deterministic acceptance cases that mandate-test the production diagnostic scripts end-to-end against a fixture project. Wired into `RELEASING.md` as Step 12.0 (BLOCKING) — v3.10.0 cannot ship without these passing.
- **`upgrade_version.sh` tolerates fresh-clone no-venv state (Plan 00104 Task 5.2)**: When invoked on a fresh clone before the first `install.sh`, `upgrade_version.sh` now exits with a clear "run install.sh first" directive instead of crashing inside the version-bump path.

### Fixed

- **Issue #4 — `cli.py:1415` `.resolve()` recorded `python_path` as `/usr/bin/python3.11` instead of the venv's `bin/python` (Plan 00104 Task 2.1)**: The `write-venv-metadata` CLI subcommand applied `Path.resolve()` to the input path, which on systems where the venv's `bin/python` is a symlink to the system interpreter resolved to the system path. The metadata file then recorded the system Python rather than the venv Python, causing every downstream consumer to invoke `/usr/bin/python3.11` (no daemon site-packages → `ModuleNotFoundError`). The `.resolve()` call has been dropped; the input path is recorded verbatim. Reported in `context/2026-05-01-field-report-upgrade-issues.md` as the root cause of all six observed failures.
- **Issue #6 — `health-check.sh` phantom `ModuleNotFoundError` (Plan 00104 Task 2.2)**: A regression test confirms that the Issue #4 fix also resolves the phantom `ModuleNotFoundError` in `health-check.sh`. Both bugs share the same root cause: a corrupted `python_path` in `.daemon-metadata.json`.
- **Issue #3 — stray `uv.lock` accumulated under `untracked/` (Plan 00104 Task 2.3)**: `untracked/` was missing from `.gitignore`'s explicit `uv.lock` rules, allowing stray `uv.lock` files generated by ad-hoc `uv sync` runs to accumulate and pollute the worktree. The skill `upgrade.sh` now cleans stray `uv.lock` files under `untracked/` before invoking `uv sync`, and `.gitignore` is updated to exclude them.
- **Silent-fallback antipattern removed from `create_venv_at_path` (Plan 00104 Task 5.3.A)**: The function previously caught venv-creation failures and silently fell through to a default path, masking the real failure. The fallback has been removed; failures now propagate with a clear directive.
- **`venv_lock_hash_matches` delegates to canonical lib (Plan 00104 Task 5.8)**: The lock-hash comparison function in `venv.sh` now delegates to `scripts/lib/resolve_venv.sh::venv_lock_hash_matches` instead of carrying its own implementation. Eliminates a sixth resolver-site that v3.9.1 had not consolidated.

### Changed

- **All five resolver sites collapsed to canonical shims (Plan 00104 Phase 5)**: `_resolve-venv.sh` (Task 5.4), `venv-include.bash` (Task 5.5), `venv_resolver.sh` (Task 5.6), `init.sh::_resolve_python_cmd` (Task 5.7), and `venv.sh::venv_lock_hash_matches` (Task 5.8) are now thin shims that source `scripts/lib/resolve_venv.sh` and delegate. There is exactly one resolver implementation in the repo.
- **`RELEASING.md` Step 12.0 added — H-1 diagnostic-script gate (BLOCKING)**: The release pipeline now runs the H-1 acceptance gate before any other acceptance testing. Any failure aborts the release immediately.

## Breaking Changes

None. This is a MINOR release. No API or configuration changes. No handler additions or removals. No user-facing behavioural changes — every change is internal consolidation, a new QA gate, or a fix for a field-reported bug.

Users on v3.9.1 who applied any of the workarounds in the 2026-05-01 field report may remove them — the underlying issues are now fixed at the source.

## Upgrade Instructions

### Upgrading Existing Installations

```bash
/hooks-daemon upgrade
```

Or, from the daemon directory:

```bash
cd .claude/hooks-daemon
./scripts/upgrade.sh
```

No manual configuration changes required. The skill `upgrade.sh` self-bootstraps the latest body from the v3.10.0 release with sha256 verification.

### New Installations

```bash
git clone -b v3.10.0 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon
cd .claude/hooks-daemon && ./install.sh
```

### Verify

```bash
/hooks-daemon health
# Expected: "Daemon: RUNNING" with no "venv not found" or "ModuleNotFoundError" errors

/hooks-daemon status
# Expected: clean status output, no phantom errors
```
