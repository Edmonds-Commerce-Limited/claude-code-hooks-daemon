# v3.31.0 — Minor: loud project-handler load-failure alert + status-line fixes

**Release date**: 2026-07-01
**Type**: MINOR release

## Summary

v3.31.0 closes a silent fail-open on the observability axis for project-level handlers
(Plan 00143): the daemon has always safely skipped a project handler that fails to
load, but previously that skip was only a `logger.warning` line nobody reads. A whole
session could proceed under the false assumption that all custom guardrails were
active. This release persists the running daemon's actual load failures and surfaces
them loudly — a new SessionStart alert, a degraded signal in `status`/`health`/`check`,
and an upgrade-time validation gate. It also fixes a status-line dogfooding bug where
the effort bars ignored session-only `/effort` overrides, retires the now-tautological
`thinking_mode` status-line segment, and — found during this release's own mandatory
acceptance-testing gate — fixes a core bug in `HookResult`'s Stop/SubagentStop response
formatting that made 4 advisory handlers silent no-ops in production, plus 4 other
handlers that put user-facing guidance in the wrong field.

## Highlights

- **`project_handler_load_checker` SessionStart handler (Plan 00143)** — Loud
  "PROJECT PROTECTION DEGRADED" alert at every session start when a
  `.claude/project-handlers/` handler failed to load, listing the handler, its failure
  reason, and the fix-then-restart remediation. Silent when everything loads cleanly.
  Shipped ENABLED BY DEFAULT (opt-out).
- **Degraded-protection signal in `status`/`health`/`check` (Plan 00143)** — All three
  CLI surfaces read the same persisted state: `status` prints a DEGRADED block,
  `health` returns non-zero, `check` includes a project-handler-health section.
- **Upgrade-time validation gate (Plan 00143)** — `upgrade_version.sh` now runs
  `validate-project-handlers` post-upgrade and warns loudly (without failing) if the
  upgrade dropped a previously-working project handler.
- **Status-line effort bars fixed** — `model_context` now reads the live
  `hook_input["effort"]["level"]` Claude Code sends on every Status event, so a
  session-only `/effort` override is reflected immediately instead of showing the stale
  `~/.claude/settings.json` value. The bar scale also expands from 3 to the full 5-tier
  `low`/`medium`/`high`/`xhigh`/`max` scale.
- **Stop/SubagentStop advisory context was silently dropped for ALL handlers** —
  `HookResult` never implemented Claude Code's documented
  `hookSpecificOutput.additionalContext` mechanism for these two event types, making
  `task_completion_checker`, `hedging_language_detector`, `dismissive_language_detector`,
  and `remind_prompt_library` complete no-ops whenever they tried to advise (not block).
  Fixed at the core formatter, so all four now work correctly.
- **5 more handlers put ALLOW-decision advisory text in `reason` instead of `context`**
  — silently dropped by `HookResult.to_json()`, which only surfaces `reason` for
  DENY/ASK. Fixed in `npm_command`, `lsp_enforcement`, `task_tdd_advisor`,
  `validate_eslint_on_write`, and `lint_on_edit`.
- **`thinking_mode` status-line segment removed** — Tautological (always-on, zero
  information value) now that "always thinking on" is enforced separately. Backwards
  compatible — see Removed section below.

## Changes

### Added

- **`project_handler_load_checker` SessionStart handler — loud project-handler degraded-protection alert (Plan 00143), shipped ENABLED BY DEFAULT (opt-out)** — When a project handler under `.claude/project-handlers/` fails to load (e.g. a daemon upgrade introduced a required method like `get_claude_md` that an older handler does not implement), the daemon has always safely skipped the broken handler and kept the rest running — but previously this was only a `logger.warning` line nobody reads, so a whole session could proceed under the false assumption that all guardrails were active. The running daemon now persists its actual load failures (filename + reason) to a state file on every startup via a new `daemon/project_handler_health.py` module, and this new priority-50 handler reads that state and injects a loud, recurring alert at the start of every session listing each skipped handler, its failure reason, and the fix-then-restart remediation. It stays completely silent when all project handlers load cleanly.
- **CLI degraded-protection signal across `status`/`health`/`check` (Plan 00143)** — `status` prints a loud DEGRADED block when project-handler load failures are persisted; `health` returns a non-zero exit code (with detail) when degraded; `check` includes a project-handler-health section. All three read the same single source of truth as the SessionStart alert.
- **Upgrade-time project-handler validation gate (Plan 00143)** — `upgrade_version.sh` now runs `validate-project-handlers` post-upgrade (Step 16.5) and prints a loud (non-fatal) warning with restart guidance if the upgrade caused a previously-working project handler to stop loading, so regressions are caught immediately instead of silently at the next session.
- **`discover_handlers_with_failures()` in `project_loader.py` (Plan 00143)** — Returns a `ProjectHandlerDiscovery` dataclass (`handlers` + `failures: list[ProjectHandlerLoadFailure]`) capturing load-failure reasons that were previously logged and discarded. `discover_handlers()` delegates to it and keeps its existing signature, so no caller changes are required.
- **`config-changes/v3.31.0.yaml` manifest** — Documents the new `project_handler_load_checker` handler for the upgrade advisory; ships on by default so no `recommended` promotion is needed.

### Changed

- **Status-line effort bars now expand to the full 5-tier scale** — `model_context` (status line) previously rendered a fixed 3-bar scale and collapsed `xhigh` (and anything above `high`) into `high`. It now renders the full `low`/`medium`/`high`/`xhigh`/`max` tier list Claude Code exposes.

### Fixed

- **Status-line effort bars stuck on stale `settings.json` value** — `model_context` (status line) read `effortLevel` only from `~/.claude/settings.json`, which is never updated by a session-only `/effort` slash-command override (only the persisted default is written there). Switching effort mid-session left the bars showing the old tier indefinitely. The handler now reads the live, authoritative `hook_input["effort"]["level"]` that Claude Code sends on every Status event first, falling back to `settings.json` only when that field is absent.
- **`root_recursion_guard`'s own acceptance tests never exercised its real detection logic** — Found during this release's acceptance testing: 2 of 3 `get_acceptance_tests()` commands wrapped the dangerous scanner invocation in `echo "..."`, which defeats this handler's `shlex`-based tokenization (unlike most blocking handlers, which do raw substring matching and are safely tested via `echo`-wrapping). Production `matches()`/`handle()` were never affected — always correctly covered by direct unit tests. Fixed the 3 test commands to use the `false && <real command>` short-circuit pattern instead, and added a regression test that round-trips every acceptance test through `matches()`.
- **`global_npm_advisor`'s own acceptance test asserted a message pattern absent from the real advisory** — `"local install"` never appears in the actual `handle()` output; fixed to `"npx"` and added a regression test pinning the real output.
- **`HookResult`'s Stop/SubagentStop formatting silently dropped ALL non-blocking advisory context (4 handlers affected)** — Claude Code's hooks documentation states that Stop and SubagentStop accept `hookSpecificOutput.additionalContext` for non-blocking advisory feedback, alongside the top-level `decision`/`reason` blocking mechanism. `HookResult._format_stop_response()` never implemented this: it returned `{}` for any ALLOW decision regardless of `context`. This silently made `task_completion_checker`, `hedging_language_detector`, `dismissive_language_detector`, and `remind_prompt_library` (which also had a second, separate bug — see below) complete no-ops in production for as long as they have existed. Fixed the formatter to emit `hookSpecificOutput.additionalContext` whenever `context` is non-empty, updated the Stop/SubagentStop JSON schemas to allow the new field, and added regression tests pinning the documented contract.
- **5 handlers put ALLOW-decision advisory text in `reason` instead of `context`, so it was silently dropped** — `HookResult.to_json()` only copies `reason` for DENY/ASK decisions (PreToolUse, PostToolUse, Stop, SubagentStop alike); only `context` reaches the user for ALLOW. Found via a full audit triggered by discovering the `npm_command` instance. Fixed by moving the content to `context` (merging with any pre-existing terse `context` summary) in `npm_command` (PreToolUse — the entire "consider `llm:` wrappers" advisory, likely seen by most new adopters, was silently lost), `lsp_enforcement` (PreToolUse — LSP guidance lost in both `advisory` mode and the post-`block_once` allow path), `task_tdd_advisor` (PreToolUse — the full RED/GREEN/REFACTOR walkthrough was lost, leaving only a terse summary), `validate_eslint_on_write` (PostToolUse — the detailed `llm:lint` recommendation was lost), and `lint_on_edit` (PostToolUse — the lint-timeout advisory was lost). Added `to_json()` round-trip regression tests for each.

### Removed

- **`thinking_mode` status-line handler** — Removed the `ThinkingModeHandler` segment (source, tests, `HandlerID`/`Priority` constants, config templates, example config, and docs). The daemon enforces "always thinking on" via `optimal_config_checker`, so the segment displayed the same On state on every render — a tautology with zero information value. **Backwards-compatible**: the config registry silently ignores unknown handler keys during actual handler registration, so an existing `handlers.status_line.thinking_mode:` block in your `.claude/hooks-daemon.yaml` does not break anything and the daemon still starts fully with all other handlers working normally. You may see a harmless advisory warning from `ConfigValidator` (surfaced in logs and `daemon status`) noting `"Unknown handler 'thinking_mode' at 'handlers.status_line.thinking_mode'..."` until you delete the block — delete it at your convenience; no restart-blocking action is required.

## Upgrade

```
Use the hooks-daemon upgrade skill (Skill tool: skill=hooks-daemon, args=upgrade).
```

No hard config migration is required. The new `project_handler_load_checker` handler
is active automatically after upgrade and stays silent unless a project handler
actually failed to load. If you maintain project handlers in
`.claude/project-handlers/` and a required method was introduced in this or a prior
release that they do not implement, you will see a degraded-protection alert at
session start after upgrading — fix the handler(s), then restart the daemon to clear
it. If you have a `handlers.status_line.thinking_mode:` block in your
`.claude/hooks-daemon.yaml`, it is now inert; delete it at your convenience (harmless
advisory warning until you do).

## Installation

### New Installations

```bash
mkdir -p .claude && cd .claude
git clone https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git hooks-daemon
cd hooks-daemon
git fetch --tags && git checkout v3.31.0
python3 -m venv untracked/venv
untracked/venv/bin/pip install -e .
untracked/venv/bin/python install.py
cd ../..
```

### Upgrading Existing Installations

```bash
cd .claude/hooks-daemon
git fetch --tags
git checkout v3.31.0
untracked/venv/bin/pip install -e .
untracked/venv/bin/python -m claude_code_hooks_daemon.daemon.cli restart
```
