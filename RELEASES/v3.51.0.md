# Release v3.51.0 - Scope Is Part of the Contract

**Release Date**: 2026-08-02
**Type**: Minor
**Previous Version**: v3.50.0

## Summary

v3.50.0 fixed a real defect: every daemon-CLI instruction the daemon emitted was
written as `$PYTHON -m …daemon.cli`, a variable that is never set in an agent's
shell. It shipped a `bin/hooks-daemon` wrapper to replace that form, and a QA
gate to stop the old form returning.

Both had a hole, and the holes were the same shape: **each was scoped narrower
than the defect it existed to prevent.**

This release closes them. Nothing here changes configuration or handler
behaviour, and no action is required on upgrade. It is versioned minor rather
than patch solely because of one new CLI flag, `init-config --stdout`;
everything else is a fix or a documentation correction.

## Why this release exists

### A gate only ever checks what you point it at

The `python_var_guidance` gate shipped scoped to `src/` only, with **no test
file** — so nothing asserted where it pointed. It reported clean through a
release that was specifically about this bug, while 297 occurrences of the exact
pattern sat in `CLAUDE/`, `docs/` and `examples/`.

Scope was wrong in three dimensions at once, and each was invisible from inside
the others:

| Dimension     | Was                            | Missed                                                           |
| ------------- | ------------------------------ | ---------------------------------------------------------------- |
| Scan roots    | `src/` only                    | 297 occurrences in living docs shipped into every client project |
| File suffixes | `.py`, `.md`                   | 9 commands **printed at runtime** by `.sh` scripts               |
| Pattern       | `$PYTHON` and `-m …daemon.cli` | 65 references to the retired `untracked/venv/` layout            |

The retired-layout group was the largest and the last to be found, precisely
because it names a real-looking path rather than an obviously-unset variable.

Widening the gate then uncovered a second layer that no pattern would have
caught: docs were teaching **superseded procedures**. Hand-rolled venvs that the
canonical resolver now *rejects*. The self-deprecated `install.py`. A `cd` into
the daemon directory that `daemon_location_guard` **blocks**. An agent that
follows those instructions concludes its install is broken and starts repairing
something that was never wrong.

### The wrapper had the same asymmetry, in code

`bin/hooks-daemon` resolved its *interpreter* from its own location, but the
daemon it *managed* from the working directory. Its own design notes asserted
the opposite — "It anchors to its OWN location (not the caller's CWD)" — which
was true of the interpreter only.

This was observed live, not theorised. A client project's wrapper, invoked by
absolute path from a different project's directory, restarted **that other
project's** daemon and reported success. Silent, and indistinguishable from
working.

## Changes

### Fixed

- **`bin/hooks-daemon` managed the wrong project's daemon.** The wrapper now
  derives its own project root from its location and passes `--project-root`,
  so it acts on *its* project's daemon from any working directory. The daemon
  root is `<project>/.claude/hooks-daemon` in a client install and `<project>`
  itself in self-install, so the layout alone distinguishes them — no mode flag
  needed. A caller's explicit `--project-root` still wins, because argparse
  takes the last occurrence and the derived anchor is injected first.
- **The working directory is no longer an input to daemon selection.** The
  wrapper has no fallback: a layout it cannot anchor exits 5 with a diagnostic
  naming the root it derived and the two layouts it expects. The only possible
  fallback would be to exec unanchored and let the CLI walk up from `$PWD` —
  and that walk-up *is* the defect above. Falling back to it would have kept
  the silent-wrong-target behaviour alive in exactly the case where no other
  check can catch it, and a wrong target that exits 0 is worse than a refusal.
- **Daemon start could duplicate buffered output.** `cmd_start` forked without
  flushing, so anything already sitting in the stdout/stderr buffers was written
  twice — once by the parent, once by the daemonised child.
- **`init-project-handlers` scaffolded a handler its own validator rejects.**
  The generated example omitted `get_claude_md()`, required since v2.30.0, so
  the very next `validate-project-handlers` failed on freshly-scaffolded code.
- **`test-project-handlers` crashed instead of explaining.** It now checks for
  `pytest` up front and says so when it is absent.
- **Documentation taught commands that do not exist.** 297 unrunnable
  invocations plus 65 references to the pre-v3.7.0 `untracked/venv/` layout,
  corrected across 30 files — including five shell scripts that *printed* the
  bad form at runtime, a spelling that lived in no document at all.
- **Client-fixture teardown reported success while orphaning a daemon.**
  `dummy-client-repo.sh destroy` stopped the daemon using the caller's working
  directory, so run from the daemon repo it targeted the wrong project,
  announced "Daemon not running", and deleted the fixture out from under a live
  process. Teardown now anchors explicitly and fails loudly rather than
  orphaning.

### Changed

- **Silent fallbacks to the retired venv layout are now fail-fast.** Seven call
  sites — the QA runner, the strategy-pattern check, `debug_hooks.sh`,
  `validate_worktrees.sh`, `detect_location.sh` (twice), `install/rollback.sh`
  and `install/project_detection.sh` — degraded to
  `untracked/venv/bin/python` when the canonical resolver was unavailable.
  Venvs have been fingerprint-keyed since v3.7.0, so that path exists on no
  current install: the fallback could never succeed and only converted "the
  resolver is missing" into a confusing "no such file" against a path that was
  never there. Each now names the real problem.

### Added

- **`init-config --stdout`** — print the configuration template for review
  instead of writing it. This is the only reason the release is minor rather
  than patch. Reviewing the available handlers is the common case on an
  *existing* install, where `init-config` previously refused with "already
  exists, use `--force` to overwrite" — pushing anyone who merely wanted to
  *read* the template toward a destructive flag. `--stdout` is checked before
  the exists test, because printing cannot destroy anything.
- **The `python_var_guidance` gate covers shell assignments, not just printed
  guidance.** It previously inspected only `echo`/`printf` lines, so a hardcoded
  retired venv path in an assignment or conditional was structurally invisible —
  which is how six of the seven fallbacks above survived. The new rule flags the
  path anywhere in a shell file. Genuine dual-layout probers (the skill
  installer's health check, which lists the old path on purpose so a working
  pre-v3.7.0 install is left alone rather than re-cloned over) declare
  themselves with an inline, reasoned exemption marker that appears in the diff.
- **Scope is now pinned by test.** The gate's roots include `.claude/`, and
  `TestRepositoryIsClean` runs it against its real default roots — so narrowing
  `_DEFAULT_SCAN_ROOTS` is a *test failure*, not a silent loss of coverage.
  25 tests, up from none at v3.50.0's ship.

## Upgrade Instructions

Drop-in and non-breaking. No configuration migration is required; no config keys
were added, renamed, or removed.

Two behaviour changes worth knowing, both confined to `bin/hooks-daemon`:

1. **It targets the daemon belonging to the wrapper you invoked**, not the one
   belonging to your current directory. If you had a script that relied on the
   old behaviour — running one project's wrapper from another project's
   directory to act on the latter — pass `--project-root` explicitly, which
   still takes precedence.
2. **A wrapper that cannot anchor to a project now exits 5** instead of
   silently falling through to the working directory. This only affects a
   wrapper copied outside a valid install layout; a normal client or
   self-install is unaffected, and the fallback it replaces existed only in
   v3.50.0. The error names the root it derived and the two layouts it expects.

Both are covered by `CLAUDE/UPGRADES/truth-changes/v3.51.0.yaml`, so if your
project's own docs assert the old behaviour, reconcile them:

```bash
.claude/hooks-daemon/bin/hooks-daemon check-truth-changes --from 3.50.0 --to 3.51.0
```

## Installation

### New Installations

```bash
mkdir -p .claude
git clone https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon
git -C .claude/hooks-daemon fetch --tags
git -C .claude/hooks-daemon checkout v3.51.0

# The installer builds the venv, installs the package and starts the daemon.
# Never hand-build the venv: it is fingerprint-keyed, and a hand-made
# untracked/venv/ is the retired pre-v3.7.0 layout the resolver refuses.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
curl -fsSL https://raw.githubusercontent.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon/main/scripts/upgrade.sh -o /tmp/upgrade.sh
less /tmp/upgrade.sh          # review before running
bash /tmp/upgrade.sh --project-root /path/to/your/project v3.51.0
rm /tmp/upgrade.sh
```

Verify afterwards:

```bash
.claude/hooks-daemon/bin/hooks-daemon status     # expect: RUNNING
```

## Testing

- **Tests:** 10,800+ passing
- **Coverage:** 95.2%
- **Type Safety:** MyPy strict mode compliant
- **Security:** Bandit scan clean (zero issues at every severity)
- **QA:** 14/14 gates passing

Every fix followed TDD, full QA, and a verified daemon restart. The wrapper fix
is covered by a test that runs the **real** wrapper against a stub resolver and
an argv-echoing stub interpreter — client install, self-install, invocation from
an unrelated directory, git worktree, explicit-override precedence, unanchorable
layout, and byte-identity between the deployed copy and its template.

Because self-install mode cannot exercise this class of bug at all, the
documentation and path fixes were additionally verified in a real client install
provisioned by the production installer (`scripts/dummy-client-repo.sh`), with
commands copied verbatim from the client's own generated `CLAUDE.md`.
