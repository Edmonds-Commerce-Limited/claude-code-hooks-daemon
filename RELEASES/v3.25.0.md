# v3.25.0 — Minor: deploy mkplan.bash on upgrade (config-driven), colour-coded environment indicator

**Release date**: 2026-06-23
**Type**: MINOR release

## Summary

v3.25.0 fixes a field bug present in v3.24.0 and earlier: the `mkplan.bash`
plan-scaffolding script (Plan 00130) was only ever deployed by the installer
behind the opt-in `PLAN_WORKFLOW=yes` env var, and was **never deployed by the
upgrade path at all** — yet the daemon's own `plan_number_helper` guidance told
agents to run `CLAUDE/Plan/mkplan.bash`. Every upgraded project that used the
plan workflow was pointed at a script that did not exist. Reported by downstream
client `client-a-infra` (v3.22.0 → v3.24.0).

The fix makes the **config the single source of truth** for whether the plan
workflow deploys (`config.plan_workflow.enabled`), via one
`deploy_plan_workflow_if_enabled` entrypoint called identically by
`install_version.sh` and **both** `upgrade_version.sh` paths. The orthogonal
`PLAN_WORKFLOW` env var — a second, never-agreeing switch — is deleted entirely.

It also colour-codes the status-line environment indicator so the runtime
(desktop / docker / podman / lxc) is identifiable at a glance.

## Changes

### Fixed

- **`mkplan.bash` is now deployed on upgrade, driven by config (Plan 00136)** —
  The plan-scaffolding script was only written by `install_version.sh` behind the
  opt-in `PLAN_WORKFLOW=yes` env var, and was never deployed by the upgrade path —
  so any upgraded project was told by `plan_number_helper` to run
  `CLAUDE/Plan/mkplan.bash`, a file that did not exist. Deployment is now derived
  from `config.plan_workflow.enabled` via a single `deploy_plan_workflow_if_enabled`
  entrypoint, called identically by `install_version.sh` and **both**
  `upgrade_version.sh` paths (full + idempotent fast path). Two end-to-end
  acceptance gates assert `mkplan.bash` is present and mode `0o755` after a real
  shell install and upgrade. The `bootstrap_plan_workflow` docstrings are
  reconciled with the wired behaviour.

### Changed

- **`PLAN_WORKFLOW` env var removed entirely — config is the single source of
  truth (Plan 00136)** — The install-time `PLAN_WORKFLOW=yes` switch was a
  second, orthogonal source of truth for "is the plan workflow on" that never
  agreed with the config and never ran on upgrade. It is deleted outright (gate,
  install-summary line, and customisation hint). Whether the plan scaffold +
  `mkplan.bash` deploy is now decided solely by `config.plan_workflow.enabled`.

### Added

- **Colour-coded environment indicator in the status line** — The
  `environment_indicator` segment now renders each runtime in a distinct colour:
  💻 desktop = red, 🐳 docker = blue (Docker brand), 📦 podman = bright
  magenta/purple (Podman brand, lightened for legibility on black terminals),
  🧊 lxc = cyan, generic/unknown container = grey. Brand-relevant where a brand
  colour exists, non-semantic and distinct otherwise; every segment colour-resets.

## Behaviour change — plan-workflow deploy default

Because `config.plan_workflow.enabled` defaults `true`, install **and upgrade**
now deploy the `CLAUDE/Plan/` scaffold + `mkplan.bash` by default (previously a
fresh install required `PLAN_WORKFLOW=yes`, and upgrades never deployed it). The
scaffold is non-destructive — `README.md`/`CLAUDE.md` are only created if absent;
the daemon-owned `mkplan.bash` is overwritten on every run. To opt out, set in
`.claude/hooks-daemon.yaml`:

```yaml
plan_workflow:
  enabled: false
```

A follow-up release (Plan 00137 — install/upgrade SSoT + KISS audit) will
reconcile the shipped example-config default with the opt-in plan handlers so
that deployment becomes opt-in rather than default-on.

## Upgrade

```
Use the hooks-daemon upgrade skill (Skill tool: skill=hooks-daemon, args=upgrade).
```

No config migration is required. The deploy-default behaviour is reversible via
`plan_workflow.enabled: false`.

