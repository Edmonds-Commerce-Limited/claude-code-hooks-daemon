# Release v3.50.0 - Commands That Actually Run

**Release Date:** 2026-07-31
**Type:** Minor
**Previous Version:** v3.49.1

## Summary

Two themes.

**The daemon was generating instructions that cannot be executed.** Every
daemon-CLI command it emitted — in block reasons, in `get_claude_md()` guidance,
and in the resident `CLAUDE.md` block it writes into your project — took the
form `$PYTHON -m claude_code_hooks_daemon.daemon.cli …`. `$PYTHON` is never
exported in an agent's shell. Only the daemon's own bash entry points set it,
internally. The instruction therefore expanded to `-m: command not found`.

**Plan size is now enforced.** v3.49.1 established the PLAN-vs-JOURNAL contract
and explicitly shipped no thresholds. This release adds the tiered enforcement
that contract described.

## READ THIS FIRST: your CLAUDE.md will change

On the first daemon restart after upgrading, the `<hooksdaemon>` block in your
project's `CLAUDE.md` will be regenerated with different commands. **This is the
fix, not a regression.** Every command in it is now an absolute path to a
wrapper that runs as printed.

If your own project docs, notes or memory repeat the old `$PYTHON -m …` form,
update them. An agent that follows the old form concludes the daemon is not
installed — see below for why that is worse than a command that merely fails.

## Why this release exists

### The failure is silent-by-confusion, not loud

A command that fails with a clear error gets fixed. This one fails with
`ModuleNotFoundError`, which is a *misleading* error: it says the package is not
installed. It is installed — it lives in an isolated fingerprint-keyed venv that
the PATH `python3` cannot see.

So the agent does what the error implies. It runs `pip install claude-code-hooks-daemon` (wrong environment, blocked by PEP 668), edits the
container Dockerfile, or builds a new venv. **All of which damage a working
installation whose venv was never broken.** This release exists because exactly
that recovery path was started in a real project before someone caught it.

### It fired hardest when you were already in trouble

Two of the affected messages appear precisely when something has gone wrong:

- `daemon_location_guard` — redirects an agent that has `cd`'d into the daemon
  directory. All three of its remedy commands failed.
- `project_handler_load_checker` — reports **degraded security protection**,
  then prints a diagnostic command that also fails. A real, security-relevant
  degradation could not be investigated by following the printed instructions.

### It was install-independent

Diagnosed in this repository, then independently corroborated by a field report
from a **separate client install** — different layout, different Python version,
different venv fingerprint, same root cause.

### The scope was larger than first estimated

The initial assessment was 17 source locations. The field report said 29 files.
Measured: **77 occurrences across 29 files.** The report was right.

## Highlights

### A wrapper that works from anywhere

`bin/hooks-daemon` resolves the daemon's venv through the canonical resolver and
forwards every subcommand. Critically, it anchors to its **own** location rather
than the working directory.

That fixed a second, separately-reported bug for free. Worktrees are a common
agent workflow, and `.claude/.gitignore` ignores `hooks-daemon/`, so the daemon
library exists only in the main checkout. Verified A/B from an unrelated
directory: the previous `daemon-cli.sh` exits 1 with "Not in a hooks daemon
project"; `bin/hooks-daemon` resolves and reaches the CLI.

### The fix reaches projects that already have the daemon

Wrapper deployment is wired into **both** the install path and the **upgrade**
path. That distinction matters: every project affected by this bug already has
the daemon installed, so an install-only fix would have reached nobody.

### A guard that only stops you growing the problem

The `plan-doc-size` block tier denies an edit **only when it grows the file**.
Shrinking is silent and a same-size edit such as ticking a checkbox only
advises. Measuring the corpus showed 6 of 187 plans already over the block tier —
without this asymmetry, a checkbox tick would have trapped them permanently.

### Testing against a real client install

Self-install mode is not representative of a client install, and this entire bug
class is invisible without one. `scripts/dummy-client-repo.sh` now provisions a
real client-mode install through the **production** installer — never synthesised
state, which is how a previous SEV-1 escaped. The fix was verified there:
the fresh client's generated `CLAUDE.md` went from **9 unrunnable commands to 0**,
and commands copied verbatim out of it return real CLI output.

## Changes

### Added

- `bin/hooks-daemon` deployed CLI wrapper; deployed on install **and** upgrade.
- `plan_workflow.qa.plan_doc_size` — tiered plan-document limits (advisory
  18,000 B / 350 L, warning 25,000 / 500, block 35,000 / 900).
- `plan-shrink-without-journal` commit check.
- `plan-qa.md` in the deployed skill — the skill previously had no plan-QA
  coverage, so client projects had no discoverable way to run it.
- `python_var_guidance` QA gate (14 gates total).
- `scripts/dummy-client-repo.sh` client-mode acceptance fixture.

### Changed

- All 77 emitted daemon-CLI commands are now absolute wrapper paths.
- `daemon.sh` deprecated to a forwarding shim; notice on stderr only.
- Journal exemption is by **location**, not just filename.
- Shipped plan docs no longer teach patterns the daemon itself blocks.

### Fixed

- `daemon_location_guard` shipped a hardcoded interpreter path — this
  repository's own path, and the legacy pre-v3.7.0 venv — to every client.
- `plan_number_helper` matched an `echo` across a newline into an unrelated
  command. Its patterns used `[^;&|]*` to stop exactly that, but a negated
  character class matches newline by default.
- `markdown_table_formatter` silently rewrote mis-named journal files.
- `background_process_tracker` fired on literal `&` and on keywords inside
  quoted strings and heredoc bodies.
- Chain attribution named the wrong handler in the "To disable" footer.
- `plan_workflow.get_claude_md()` returned `None`.

## Post-Upgrade Tasks

After upgrading, review
`CLAUDE/UPGRADES/v3/v3.49.1-to-v3.50.0/post-upgrade-tasks/` — it contains one
**recommended** task: audit your plan documents against the new size tiers
before the block tier applies to them.

## Upgrade Instructions

No configuration changes are required. `plan_doc_size` is on by default with
sensible tiers; the post-upgrade task explains how to audit first if you have
large plans.

```bash
/hooks-daemon upgrade
```

Then restart and confirm:

```bash
.claude/hooks-daemon/bin/hooks-daemon restart
.claude/hooks-daemon/bin/hooks-daemon status
```

Expect your project `CLAUDE.md` block to change on that restart. That is the fix
landing.

To defer the new size enforcement:

```yaml
plan_workflow:
  qa:
    plan_doc_size:
      enabled: false
```
