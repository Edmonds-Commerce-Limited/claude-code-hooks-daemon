# Release v3.75.0 - Branch Pools Counted Per Owner, A Model Ownership Statement, and `session-state`

**Release Date:** 2026-11-16
**Type:** Minor Release

## Summary

This release finishes the branch-pool work of Plan 00594: a squash-merged or cherry-picked branch now counts as merged, pools are counted per owner, pressure lands at session start and stop instead of at creation, `branch-preflight` lists every blocker, and `branch-sweep --clean` previews before `--apply` deletes in resumable batches. It also adds a model ownership statement to the injected CLAUDE.md block (on by default), the `session-state` command with versioned JSON Schemas, an opt-in long-running-command guard, supervisor idle compaction (dry-run by default), hook wrappers with no machine-specific path, and a run of secret-guard, `destructive_git` and `pipe_blocker` fixes. Fifty release-note callouts are folded into Highlights below, in the authors' own words.

## Read this first

- **Two operator CLI changes break scripts.** `branch-sweep --clean` is now a dry run (add `--apply`), and `delete-branch` lost `--allow-unproven`, `--reason`, `--bundle` and `--no-bundle`. See "BREAKING CHANGES" below. Hooks, handlers and existing config keys are not removed or renamed.
- **Two new defaults change behaviour on upgrade, with no config edit.**
  - `claude_md.ownership` defaults to `own`: the CLAUDE.md block gains a leading sentence and handlers drop short hints. It measurably lengthens output; set `claude_md.ownership: off` to keep the old block.
  - `branches.wip.creation_grace` defaults to `2`: creating a branch when the open work branches are already at `branches.wip.cap` now only warns, and is denied two branches later, at `cap + 2`. Set `branches.wip.creation_grace: 0` to keep the old deny at the cap.
- **No pre-upgrade or post-upgrade task.** The config-changes manifest is not marked breaking. A truth-changes manifest (`CLAUDE/UPGRADES/truth-changes/v3.75.0.yaml`) records the `branch-sweep --clean`, `delete-branch` and creation-cap changes so the upgrade can reconcile your project's own docs.
- **Upgrade guide:** `CLAUDE/UPGRADES/v3/v3.74.0-to-v3.75.0/v3.74.0-to-v3.75.0.md`.

## Highlights

### Audience: everyone

#### the injected CLAUDE.md block now tells the model the codebase is its own, and a setting turns it off

_Plan 00599 · Audience: everyone_

The block the daemon injects into `CLAUDE.md` now leads with "This codebase is yours: what it's for and how it's built are your call, and you'll keep building on it.", and existing handlers drop one-line ownership hints (tidy plan and ledger files, fix the cause of a lint failure in code just written, clean or keep your own branches, the sub-agent brief), plus a counter-hint wherever foreign branches are listed saying they are not the model's to change. It is on by default; `claude_md.ownership: off` removes the sentence and every hint, and `custom` with `claude_md.ownership_text` (one line, no `**`) uses your own wording (for example to name paths that are not the model's) and keeps every hint silent, so no fixed hint contradicts a carve-out. Each hint speaks at most once per session, the owned-branch hint once across the whole SessionStart report.

Know the costs before keeping it on, as Anthropic measured them: the sentence made the model merge repeated code in about half of tries (under a tenth without it) and fix nearby problems rather than only report them, but output rose about 1.5 times, it made several unrequested changes (mostly new tests and docs), an existing feature's behaviour changed in one try in six to ten, and the closing summary omits small changes, so review the diff, not the summary. A scope rule such as "no drive-by refactors" does not cancel it. Where you own the code and want minimal change, set `ownership: off`. Details: `docs/guides/CONFIGURATION.md`.

### Audience: client projects

#### pipe_blocker reads heredoc bodies and `py.test`; `${x:-a}` operands are read as words

_Plan 00478 · Audience: client projects_

`pipe_blocker` allows an unknown producer (`docker ps | tail -1`) with an advisory only when no blacklisted command is named anywhere in the command. That check now also reads **heredoc bodies**: quoted (`<<'EOF'`, `<<-'EOF'`) or not, and whether or not the command then runs the body. So `cat > t.sh <<'EOF'` holding `pytest`, followed by `bash t.sh | tail`, denies. One exception: a quoted-delimiter body that reaches only a markdown file (`cat > notes.md <<'EOF'`) or a git/gh message (`git commit -F -`, `gh pr create --body-file -`) is prose and is not read; so is a quoted-delimiter body read by a text reader (`cat`, `grep`, `wc`) that prints to stdout. `py.test` is now blacklisted like `pytest`, including through `env`, a path (`.venv/bin/py.test`) and `bash -c`.

The shell word reader shared by the safety guards no longer stops at a `${...}` operator form (`${x:-a}`, `${HOME#x}`, `${x:+a}`, `${#x}`). It reads the whole brace-balanced expansion as one word, an unresolved expansion like `$NAME`, so the words after it are still judged. A command substitution (`$(...)`, backticks) or an unclosed brace still stops it. For `write_protected_paths` under a glob such as `protected/**`:

- `awk '{print > FILENAME}' "${IN:-a.txt}" protected/x` now denies.
- `rm`, `cp`, `mv`, `tee`, `>`, `truncate` and `sed -i` judge an operand like `${PWD:-.}/protected/x` the same way they judge `$PWD/protected/x`.
- `${PWD:-w}`, `${PWD-w}`, `${PWD:=w}`, `${PWD=w}`, `${PWD:?w}` and `${PWD?w}` are read as the working directory, exactly as `$PWD` is.

#### a squash-merged or cherry-picked remote branch now counts as merged

_Plan 00594 · Audience: client projects_

The proof that a remote branch is merged used to be ancestry only, so a branch merged by squash (several commits into one), by a renamed pull request, or by cherry-pick stayed "open" and its remote delete was refused. The proof now tries ancestry, then one net-change check, all offline. The branch's NET change is its diff against `merge-base(default, tip)` with rename detection off. The branch counts as merged when SOME commit on the default branch's first-parent line, after that merge base and up to the default's tip, has a tree that holds the net change: every path the branch adds or modifies has the same blob and mode, and every path it deletes is absent. The content is then permanently in the default branch's history, so deleting the remote branch loses nothing, even if the default has since changed those files again or reverted the work. The candidates are the default's tip plus the first-parent commits that touched the branch's changed paths, checked with one batched lookup each and stopping at the first match; more than 50 candidates is unproven, never proven. Ancestry is sufficient on its own; patch-id (`git cherry`) only labels how the change arrived, and never proves a branch by itself. A branch whose net change is empty (only empty commits, or changes that cancel out, such as a park branch) is unproven, as is one that only deletes (while the default still has the file), renames, copies or changes the mode of a file, reverts the default's change to an older version, changes a path whose name is not valid UTF-8, or whose change no default commit ever held. The proof runs every git call from the repository top level, so a command typed in a subdirectory is judged the same. The `git push --delete` guard, `branch-sweep --clean --remote` and the branch-creation cap all read the same proof, so an agent may delete such a branch, `branch-sweep --clean --remote --apply` deletes it (printing a restore line), and it no longer counts against the open-branch cap once the proof has run (branch creation reads cached proofs only and never computes one). A branch with even one change the default branch never took stays unproven. Results are cached by algorithm version (v3), tip and default sha in `untracked/branch-inventory/cache.json` (new `proofs` key; entries written by an earlier algorithm are ignored and pruned on the next save). The local `delete-branch` command is covered separately below: in this release it lost its recovery bundles and its unproven-delete flags.

#### a branch install knows the ref it tracks, notices when it moves, and has a one-step way back

_Plan 00594 · Audience: client projects_

A guarded branch install now records the exact tracked ref (slashes kept), the full commit and the release installed before it in the venv's `.daemon-metadata.json`; a release install of this version onward clears them (returning to an older release leaves the record in place, which that release ignores). At session start a branch install makes one cached, time-bounded listing of that branch on the remote and, when the tip differs from the installed commit, says `tracked ref <ref> moved <old7>..<new7>; re-run the upgrade to follow it` with the command to run. A full-sha pin never moves and makes no network call; a listing that fails or times out says "not checked", never "current" (and is remembered for an hour so an offline machine does not wait at every start); a ref that is a tag is named as a tag. A release install makes no such call. `upgrade.sh --release` (or the hooks-daemon skill with `args=upgrade --release`) returns to the release recorded before the branch install, or the latest release when none was recorded, with no `HOOKS_DAEMON_UNSAFE_*` variables. Following a moved ref still goes through the same guarded upgrade; the stop, checkout, build and start handover order is owned by Plan 00535.

#### branch-sweep prints a remote delete only when the guard would allow it

_Plan 00594 · Audience: client projects_

`hooks-daemon branch-sweep` and `branch-sweep --clean` used to print a `git push <remote> --delete <name>` line for any merged or patch-equivalent branch whose remote copy it saw, using its own inventory test, and the remote-delete guard (`R-GIT-PUSH-DELETE-REMOTE`) could then refuse that very command, for example when the remote branch had moved after your last fetch or the shared proof could not establish the merge. The sweep now asks the same proof the guard uses (`core/remote_branch_proof.py`) before it prints a delete: a branch the proof accepts gets the runnable line, and any other branch gets owner-only wording ("remote delete of <remote>/<name> is for the owner: <reason>") that is advice, not a command. Both the report's remote-only entries and the `--clean` follow-up commands (including `--dry-run`) follow this rule, and the `--json` `action` field carries the same text. The proof contacts the remote with one bounded `git ls-remote`, only when a branch with a remote copy is being judged. The `--clean --remote` deletion itself is unchanged.

#### branch-park says plainly when the push was refused, and a merge clears the park visibly

_Plan 00594 · Audience: client projects_

`hooks-daemon branch-park` writes the park first (the trailer commit, plus a local record in git config under `branch.<name>.hooksDaemonParked*` holding the commit, reason, time and owner), then pushes. A project pre-push gate may refuse that push, for example one that wants a fresh full-QA verdict. The park then stands locally and the command now prints `WARNING: parked locally, not pushed`, git's own reason, and the exact `git push <remote> <name>` to run later. It exits with status 3 instead of 0, so a script can tell a half-done park from a full one. A branch that only the remote holds is kept the same way: the refused park is held on a new local branch at the park commit.

A merge of a parked branch ends its park. `branch-park --clear`, the post-merge cleanup, `branch-sweep --clean` and the worktree-removal cleanup now remove the local record and print `Park cleared: <name> (<reason>)` (`Park record cleared: ...` for `--clear`), so a park never ends silently. Pool caps are unchanged.

#### branch_creation_guard advises on recovery-copy branch names and nested worktrees

_Plan 00594 · Audience: client projects_

`branch_creation_guard` now adds an advisory, never a deny, in two cases. A branch created with a recovery-copy name (`rescue/*`, `recovery/*`, `backup/*`, `*-rescue`, `*-backup`) is told to keep the copy as `refs/archive/<name>` or a `git bundle` instead, because the branch pools count only branches and a recovery copy kept as a branch counts as open work. A `git worktree add` whose target is inside another linked worktree is told that worktrees are created from the main checkout, never nested, and is given the main checkout's path. The patterns are a fixed list, not configurable. The three habits (archive instead of branching, create from the main checkout, remove an agent's worktree after the agent) are written once under "Branch Practice" in `CLAUDE/core/Worktree.core.md`, which refreshes on upgrade.

#### secret_file_guard no longer denies a git search string, a grep filter value or bold markdown

_Plan 00595 · Audience: client projects_

`secret_file_guard` (R-SECRET-BASH-MENTION) judged three kinds of text as protected paths although none opens a file (GitHub #200). All three are now allowed:

- The value of a git search option, `-S`, `-G`, `--grep`, `--author`, `--committer` and `--grep-reflog`, in both the separate (`-S x`) and attached (`-Sx`, `--grep=x`) spellings. `git log -S org.freedesktop.secrets` is a search for a string.
- The attached value of a grep/rg filename filter (`--include=*`, `--exclude=`, `--exclude-dir=`, `--glob=`, `--iglob=`) when the command names search paths and none of them holds a protected file. A filter over a directory that does hold one, or a command that names no path (so the cwd is searched), is still denied.
- A colon split of a word no longer yields a wildcard-only part, so bold markdown such as `**Option 2:** build` in a Python heredoc is not read as the glob `**`.

A protected path that is genuinely named still denies: `git log -- <path>`, `git show HEAD:<path>`, `host:<path>`.

#### branch-preflight lists every blocker to creating a branch, and the creation deny prints the same report

_Plan 00594 · Audience: client projects_

`hooks-daemon branch-preflight [name]` is a new read-only command that answers "can I create a branch now?". It lists every pool that refuses a creation (the open-work cap, dormant branches at the block stage, the parked pool, the merged pool), not only the first rule that trips, and gives each one the exact command that clears it (`branch-park ... --reason`, `branch-park ... --clear`, `delete-branch`, `branch-sweep --clean`, `branch-keep`). It exits 0 when a branch may be created and 4 when one is refused (1 when the directory is not a git repository); `--json` prints `{may_create, blockers: [{rule_id, refuses, fixes, lines}], notices}`. A pool in `warn` mode is listed but does not refuse.

The creation deny (R-BRANCH-WIP-CAP, R-BRANCH-DORMANT, R-BRANCH-PARKED-POOL, R-BRANCH-MERGED-POOL) now renders the same report from the same function, so the two cannot disagree, and ends with a pointer to the command. No verdict changed: what is allowed and what is denied is exactly as before. Two listings gained fix commands they lacked: each open branch in the cap deny now names a command (the snapshot's suggested action, otherwise `branch-park <name> --reason ...`), and each dormant branch names its park and delete commands.

#### branch-sweep --clean now previews; --apply deletes, in resumable batches

_Plan 00594 · Audience: client projects_

`hooks-daemon branch-sweep --clean` used to delete at once. It is now the dry run: it prints the whole plan, each local and remote branch with its proof (`would delete <name> (proven merged)`, `would delete remote <remote>/<name> (tip <sha>, proven merged into <default>)`), deletes nothing, and ends with the exact command that applies it. Add `--apply` to delete (`--clean --remote --apply` for remote copies too). `--apply` cannot be combined with `--dry-run`. Every command the daemon prints for a one-step cleanup already names `--apply`; a script of your own that ran `branch-sweep --clean` must add it. The `branch-sweep-clean` step of `/hooks-daemon housekeeping` already does.

`--apply` works in batches of 50 (`BULK_BATCH_SIZE`): a `git branch <name> <sha>` restore line per deleted branch (no recovery bundle is written), and one `git push --delete` per batch for the remote copies, each under a lease on its proven tip. Remote deletes use the same proof as the remote-delete guard, unchanged. A run that is interrupted (Ctrl+C), a batch that fails, or a push the remote refuses stops cleanly: the report lists what was deleted, what remains, and `Resume with: <command>`. Resuming is running the same command again, because the repository is the only state: a deleted branch is no longer a candidate, and a branch gone since the plan was made is skipped as `already deleted`, not an error.

`--clean` no longer runs on the hook-sized inventory time budget (`branches.sweep.budget_ms`, 3 seconds by default). On a repository with hundreds of branches that budget could run out before the keep notes were read, so a branch kept with `branch-keep` looked deletable. The sweep now allows itself ten minutes.

#### branch-park writes a signed commit when the repository requires signing

_Plan 00594 · Audience: client projects_

`hooks-daemon branch-park` (and `--clear`, and the park a sub-agent makes before it stops) wrote its trailer commit with `git commit-tree`, which does not read `commit.gpgsign`. In a repository that requires verified signatures the park commit was therefore unsigned and the host refused the push of it; a client report found every sub-agent branch ending in one. The park now asks for a signature (`commit-tree -S`, so `user.signingkey`, `gpg.format` and `gpg.program` apply) whenever `git config --type=bool commit.gpgsign` is true. A repository that does not ask for signing behaves as before.

If signing is required but fails (no key, the signing program missing), the park stops with git's own reason and a hint naming the settings to check. It does not write an unsigned commit and it does not move the branch: the branch, its park record and the remote are left exactly as they were.

#### branch-pool pressure lands at session start and stop; creation is only a backstop

_Plan 00594 · Audience: client projects_

Branch-pool pressure used to land almost entirely at creation, which is the worst moment: an urgent fix could not get a branch because of other work. It now lands where it can be acted on.

- **Session start** lists every full pool with its exact fix commands (the same report as `branch-preflight`), under a `BRANCH POOLS` heading.
- **Stop** (`branch_stop_guard`, `branch_subagent_stop_guard`) adds two checks for the stopping session's OWN touched open branches: `dormant past the block stage` and `open pool over cap`. Branches this session never touched are never judged, and the deny offers only finish (merge) or `branch-park <name> --reason ...`, never a rename or the deletion of someone else's branch. In `branches.stop_guard.mode: warn` they are context only; `wip.mode: off` and `dormancy.mode: off` switch the matching check off. A hard-context handoff and a sub-agent stop do not run them.
- **After a merge**, `cleanup_after_merge` names the single `branch-sweep --clean` command when the merged pool is full.
- **Creation** is a backstop. New option `branches.wip.creation_grace` (default `2`, `>= 0`): the open-work cap denies a creation only at `cap + creation_grace` open branches, and warns (with the full report) between `cap` and that. Set `creation_grace: 0` to keep the old deny at the cap. The dormant, parked and merged pools are unchanged and still deny at their own limits.

`branch-preflight` follows the same rule: it exits 0 below `cap + creation_grace` and lists the cap as a warning.

#### branch pools count only this clone's branches; others are listed as Foreign

_Plan 00594 · Audience: client projects_

A client report showed the branch pools filling with branches that other people's clones, earlier containers or bots had pushed, so the creation guard and the stop guard pressed one clone to finish work it never started. Pools are now counted per owner.

A branch is **mine** when, in this order:

1. this clone holds a `hooksDaemonCreator` record for it (the daemon wrote it when the branch was created here);
2. otherwise it has a local ref, or its remote tip's author email equals `git config user.email` (compared without regard to case).

Anything else is **foreign**. A foreign branch:

- is listed in a new `Foreign` group of `branch-sweep` (and `group: "foreign"` in `--json`, with new `author` and `author_email` keys), with its age and author;
- is counted in no pool (open, parked, merged, dormant), so it never fills a cap, never blocks a creation, and is never judged at stop;
- is never cleaned automatically. `branch-sweep --clean --remote` still deletes a foreign branch whose merge is PROVEN, because proof matters more than ownership;
- is never offered as something to rename or delete by any deny or report.

The email check is weak evidence when several seats share one identity, so such seats see each other's pushed branches as mine. `branches.bot_owned` is unchanged; foreign is the general case of it. With no `user.email` set, a remote-only branch without a creator record is foreign.

#### a refused park push is kept for a remote-only branch too, stops counting as open, and an ended park is announced

_Plan 00594 · Audience: client projects_

Three gaps left by the earlier `branch-park` change are closed.

1. **A branch only the remote holds** now behaves like a local one when the push is refused. `hooks-daemon branch-park <name> --reason ...` keeps the park in a new local branch at the park commit, writes the same git-config record, prints `WARNING: parked locally, not pushed` with git's reason and `git push <remote> <name>`, and exits 3. A push that succeeds still leaves no local branch.
2. **A rejected park push no longer counts as open work.** When the local park record still holds and the remote copy sits behind the park commit, the branch is counted in the parked pool, not the open one, so it stops filling `branches.wip.cap`. A remote tip that is not behind the park keeps the branch open.
3. **A park that ends is announced.** When a branch gains new work or its ref disappears, the next session start and the next `hooks-daemon branch-sweep` print `Park cleared: <name> (<reason>)` once, and the record is then removed. A merge keeps printing the same line as before.

#### destructive_git no longer denies printed git text that is captured or reformatted

_Plan 00596 · Audience: client projects_

`destructive_git` denied commands that only PRINT the words of a destructive git command when the printed text was captured or reformatted. Two shapes are now data:

- **A print-only capture.** `msg=$(printf '%s\n' 'then git push origin --delete b'); echo "$msg"` and `echo "$(printf ...)"`. A substitution whose body is one `printf`/`echo` of literal words is no longer a "substitution that can run a delete" when the WHOLE command only prints: every segment is a plain `NAME=$(...)` assignment of it, an `echo`/`printf` (not `printf -v`) of literal words or of that variable with no redirect, or a data-sink pipe stage given options only. Anything else anywhere in the command (another command, a redirect, `declare -n`, `${!r}`, a variable in command position) keeps the original verdict.
- **A text formatter.** `printf '...git reset --hard' | fold -w 40`. `fold`, `fmt`, `nl`, `expand`, `unexpand`, `paste`, `rev` and `tac` join `tr`, `cut` and `column` as pipeline stages that only reshape text.

Text that may be executed keeps its verdict: a substitution in command position, `eval "$(...)"`, `bash -c "$(...)"`, `source <(...)`, a pipe into `sh`, `bash`, `xargs` or any program the guard cannot classify, a body that runs git, and a captured variable later run (`$msg`, `eval "$msg"`, `bash -c "$msg"`).

Newly denied, because they run the written text: a script written earlier in the command and fed to a shell on stdin (`echo '...git reset --hard' > s.sh; sh < s.sh`, `cat s.sh | sh`, including through `exec`/`env`/`command` and a `cp`/`mv` copy), and a `printf -v n '...git reset --hard'` whose `$n` is later expanded outside a plain print.

#### plan_number_helper no longer denies a content search inside an echo's substitution

_Plan 00597 · Audience: client projects_

`plan_number_helper` (R-PLAN-NUMBER-DISCOVERY) denied `echo "found: $(grep -rl takeover CLAUDE/Plan/00001*/subagent-reports/)"`, a content search of ONE plan, because its echo/printf glob rule read the `*` of the grep's path as an echoed plan-folder glob. Two changes:

- **A substitution is opaque to the echo/printf rule.** The rule steps over `$(...)`, backticks and `<(...)` instead of reading into them. A glob inside belongs to the inner command, which is judged by its own rules, so `$(ls -d CLAUDE/Plan/* | tail -1)` still denies while `$(grep -rl x CLAUDE/Plan/00001*/)` does not.
- **A glob opening with a full plan number names one plan.** `echo CLAUDE/Plan/00001*/PLAN.md` and `echo CLAUDE/Plan/00001-*` are lookups, as they already were for `ls`. `echo CLAUDE/Plan/*`, `echo CLAUDE/Plan/0*` and `printf '%s\n' CLAUDE/Plan/*/` still deny.

#### the venv resolver probes this path's venv first and no longer warns about a sibling view's

_Plan 00598 · Audience: client projects_

When one checkout is visible at two paths (for example a container bind mount of the host checkout), each path builds its own venv under `untracked/`, and both carry the same `lock_hash`. The resolver's scan ranked them equal, so the other path's venv could be probed first and, when another Python built it, print `resolve_venv: candidate ... interpreter drift ... -- skipping` on every interpreter-cache miss before choosing the right venv (GitHub #199). Two changes, in `scripts/lib/resolve_venv.sh` and its mirror in `daemon/paths.py`:

- **Own-slug first.** Among candidates of equal rank, the venv whose slug names THIS project path is probed first.
- **A sibling view's failure is not reported.** A candidate slugged for a different path that fails the usable probe is skipped silently; it belongs to that view. A failing venv slugged for this path, or a legacy un-slugged one, still warns as before.

The venv chosen is unchanged; only the spurious warning and the probe order differ.

#### new `hooks-daemon session-state` command, and versioned JSON Schemas for machine-read output

_Plan 00601 · Audience: client projects_

A tool that supervises several sessions can now read one session's state through a documented interface instead of the daemon's internal files:

- `hooks-daemon session-state --json --session ID` prints one JSON line: the session's modes, its last turn edge (`start`, `stop` or `stop_failure` with the error), account usage (`five_hour` and `seven_day` with `used_percentage` and `resets_at`), `limit_reset` and the usage pause. A session with no records gets `null` fields, not an error.
- `hooks-daemon session-state --watch --session ID` prints one JSON line per change, so the consumer does not poll.
- `limit_reset` answers when a rate-limited session can continue. A `rate_limit` stop is recorded without a reset time, so the daemon joins it to the usage window that is at its limit; it is `null` when no live usage reading exists (a plan that reports no usage, or a window that has already rolled over) rather than guessed.
- Every `--json` document, including `mode-history --json`, now carries `schema_version` (semver). `mode-history --json` keeps every field it had.
- JSON Schema 2020-12 files for `mode-history`, `session-state` and the `--watch` line ship inside the package (`claude_code_hooks_daemon/schemas/`), each with a versioned `$id`. Pin the major version and refuse an unknown one; a breaking change is a new major. The daemon's own tests validate its output against these schemas.
- The contract is documented in one place: [docs/guides/SESSION_STATE_CONTRACT.md](../docs/guides/SESSION_STATE_CONTRACT.md) (versioning rule, schema location and loading, the optional `limit_reset`/`resets_at` rule, the `--watch` line format, a consumer example). Consumers ignore unknown fields within a pinned major.

#### new opt-in `long_running_command_guard` keeps long commands out of the foreground

_Plan 00602 · Audience: client projects_

A command run in the foreground of the main thread blocks the session: messages from the owner and from other agents wait until it ends. The new `long_running_command_guard` PreToolUse handler denies a foreground Bash call that looks long and gives the exact `run_in_background` form, with a pointer to the Monitor tool for waiting on a condition.

- A `timeout N` wrapper with N above `threshold_seconds` (default 30) is the main flag, since a timeout of minutes means the command runs for minutes. A wait loop (`until`/`while` with `sleep`), `sleep N` above the threshold, and a known-slow program (test suites, QA runs, builds, installs, `gh run watch`) are denied too.
- A foreground command that is not known to be fast and carries no timeout gets an advisory (`R-LONG-RUNNING-NO-TIMEOUT`), never a deny.
- Never judged: a call with `run_in_background: true`, a command ending in `&`, a `timeout` at or below the threshold, short commands, and every sub-agent call.
- Ships **off**. Enable it with `handlers.pre_tool_use.long_running_command_guard.enabled: true`; options are `mode` (`deny`, `advise`, `off`), `threshold_seconds`, `extra_slow_patterns`, `extra_fast_programs` and `exempt_patterns`.
- One call that must block opts out with `MUST_RUN_FOREGROUND_BECAUSE="reason"; <command>`; a placeholder reason is not honoured.

Rule IDs: `R-LONG-RUNNING-WAIT-LOOP`, `R-LONG-RUNNING-TIMEOUT`, `R-LONG-RUNNING-SLEEP`, `R-LONG-RUNNING-SLOW-COMMAND`, `R-LONG-RUNNING-NO-TIMEOUT` (see `explain-rule`). Details: [Handler Reference](../docs/guides/HANDLER_REFERENCE.md#long_running_command_guard).

#### the supervisor can compact on its own at a true idle once context reaches 30 percent

_Plan 00603 · Audience: client projects_

The ccy supervisor used to compact only when the context reached the RED tier. It can now also inject ONE armed `/compact`, followed by the usual post-compaction `continue`, when the session is in a true idle and the context is at or above a percentage you choose (default 30). This supplements Claude Code's own `idleCompaction`, which waits about an hour and needs the one-hour prompt cache; the daemon's optimal-config check and SessionStart sync for `idleCompaction` are unchanged.

A true idle means: the screen shows the main prompt, its footer names no background task, sub-agent, shell or running turn, the input box is empty, the focus hold is clear, nothing is streaming, no injection is pending, and that state has held for a settle period (default 60 seconds). A cooldown after any compaction (default 30 minutes) and an absolute token floor (default 100000) stop a small window being compacted at 30% of nothing. The RED and CRITICAL tiers and the status-line colours are unchanged.

**Default for clients: `dry-run`.** Nothing is typed; each time the trigger would have fired, `decision.log` gets a `would idle-compact` line with the percentage and token count. That gives you the firing rate before the behaviour, and a `/compact` rewrites context, so it is armed only on request. Set `CCY_IDLE_COMPACT=on` in `.claude/ccy/ccy.env` to arm it (the supervisor's own dry-run, when it is not started with `--arm`, still types nothing), or `off` to remove it.

Tunables, all optional: `CCY_IDLE_COMPACT_PCT`, `CCY_IDLE_COMPACT_SETTLE_SECONDS`, `CCY_IDLE_COMPACT_COOLDOWN_SECONDS`, `CCY_IDLE_COMPACT_MIN_TOKENS`. See [CLAUDE/development/CcySupervisor.md](../CLAUDE/development/CcySupervisor.md).

The "no background task or sub-agent" test reads Claude Code's own session records (the documented `status` in `~/.claude/sessions/`, the sub-agent `finished` flag and the background-task exit line, the last two internal to Claude Code and checked on 2.1.322) and the footer of the rendered screen; the screen part needs the `hooks-screen` binary. Any missing or unreadable signal means not idle, so the feature goes quiet rather than firing wrongly. The host half (the screen read) takes effect on the next ccy relaunch; the decision half hot-reloads with the worker.

#### removing a worktree no longer blocks on a symlink seed that points at the main checkout

_Plan 00474 · Audience: client projects_

`git worktree remove` was denied by R-GIT-WORKTREE-REMOVE-FORCE ("holds 1 path(s) the removal would lose") when the only content of an ignored directory in the worktree was a `worktree_create` symlink-mode seed. The rule already recognised a copy-mode seed identical to its source, but not a link whose target is the main checkout's own file, and removing such a link loses nothing.

A symlink inside an ignored directory now counts as losing nothing when it resolves to an existing path inside the main checkout and outside the worktree being removed. A dangling link, a link pointing elsewhere, a link into the worktree itself, and any real file beside the link still protect the directory, so the denial is unchanged for them.

The merged-branch cleanup after a pull-request merge is a separate matter: `branches.default` (or `branches.integration_lines`) must name the real integration branch for the daemon to treat a merge into it as safe. See the `branches:` block in your `.claude/hooks-daemon.yaml`.

#### the no-timeout advisory of the long-running guard no longer names plan and bus helpers

_Plan 00474 · Audience: client projects_

R-LONG-RUNNING-NO-TIMEOUT, the advisory `long_running_command_guard` gives for a foreground command of unknown length, fired on ordinary quick helpers such as `mkplan.bash` and `pingbus`, which trained readers to skip it. Both are now on the built-in known-fast list, next to `git`, `gh`, `ls`, `cat`, `grep`, `rg`, `jq`, `awk` and `hooks-daemon`.

Network and object-store git verbs (`clone`, `fetch`, `pull`, `push`, `gc` and the like) and programs on no list still draw the advisory. The deny rules are unchanged: a `timeout` above the threshold, a long `sleep`, a wait loop and a known-slow command are denied whatever else is listed. To silence the advisory for a quick project command, add its name to `handlers.pre_tool_use.long_running_command_guard.options.extra_fast_programs`. The handler ships off, so nothing changes unless you enabled it.

#### branch-park can park with no commit and no push, and a standing park hands the branch over at stop

_Plan 00594 · Audience: client projects_

`branch-park` always added an empty trailer commit at the branch tip, which invalidated any QA already run on that tip, and always pushed, which a sub-agent told not to push cannot do. Two new switches change that per call: `--no-commit` records the park in git config only, leaving the tip untouched and pushing nothing, and `--no-push` writes the commit but does not push. `branches.park.commit` and `branches.park.push` set the same choice for every call. Both default to `true`, so nothing changes unless you set them.

The inventory and the pools read the park record rather than the trailer commit, so a no-commit park counts as parked and ages from the record. A no-commit park is local to the clone that made it: other checkouts cannot see it and read the branch as open work.

The branch stop guards (`R-BRANCH-STOP-GUARD`, `R-BRANCH-SUBAGENT-STOP-GUARD`) also stopped reporting the unpushed tip of a branch the stopping agent had parked with a reason. A park that is still recorded and uncleared counts as a handover; a commit after the park ends it and the checks resume.

#### the ccy supervisor no longer disables a plugin because the host was busy, and says why when it does

_Plan 00603 · Audience: client projects_

On a heavily loaded host the policy worker can go unscheduled for longer than a plugin hook's time budget plus grace. The supervisor read the stale in-hook marker as a plugin stuck inside a hook and disabled the plugin for the rest of the session, with nothing in `claude-supervise-worker.err.log` and a notice saying no action was needed. For `ccy-lifecycle` that silently switched off the relaunch on a team join, the max-age restart and the deadline notice.

A wedge is now declared only when the same marker is seen at two consecutive silent ticks and the worker's CPU time did not advance between them. A plugin disabled for an exception, a bad result, an overrun or a wedge comes back at the next worker restart after the one the failure caused, or after 120 ticks the worker answered cleanly (`CCY_PLUGIN_REENABLE_CLEAN_TICKS` changes the count). A load refusal, a repeated unhonoured exit request and a host fault still keep the plugin off. Every disable now writes a line to `claude-supervise-worker.err.log` with the marker's age and the host load averages, and the notice names the cause, the log path and what is off while the plugin is disabled.

`PluginTestHarness` also no longer writes to the live worker error log: a hook that raises under it is logged under the harness's `work_dir`.

The host-side parts take effect when the ccy session is next started; the notice text reloads with the policy worker.

#### daemon.omit_permission_surface drops the PermissionRequest hook and deny rules that keep the rm prompt on in bypass sessions

_Plan 00474 · Audience: client projects_

Claude Code keeps its critical-path removal prompt on, even with `CLAUDE_CODE_EVEN_MORE_DANGEROUSLY_SKIP_PERMISSIONS=1`, when a `PermissionRequest` hook or a Bash, Edit or Read deny rule exists. The daemon wrote both. The new `daemon.omit_permission_surface` key (default `false`, so nothing changes unless you set it) makes the daemon register no `PermissionRequest` hook and write no `permissions.deny` rules, and removes only the entries it wrote earlier, never your own. Turning it on lowers defence in depth for sessions that are not in bypass mode.

`hooks-daemon permission-surface` prints those entries as JSON for a user-level `settings.json`, and writes nothing.

Separately, in a project that sets `daemon.omit_permission_surface: false` explicitly, a settings merge now appends any missing daemon deny rules to an existing `permissions.deny`, where before they returned only when the whole `permissions` key was absent. A config without the key merges exactly as before. Your own rules are kept.

#### a branch park and the plan counter now wait for a held git config lock instead of failing at once

_Plan 00474 · Audience: client projects_

Git does not retry `.git/config.lock`, and every checkout and parallel agent of a repository shares that one config file, so a park record or the plan counter written while another git process held the lock failed immediately. `branch-park` (the park record and its clear) and the plan counter now wait for the lock for a few seconds, longer on a loaded host, and fail with an error that names the lock file when it stays held. A lock more than a minute old with no git process running is reported as stale, with the command to remove it; the daemon never deletes it for you.

#### a worktree add that times out under host load is retried once, and its budget is configurable

_Plan 00474 · Audience: client projects_

On a heavily loaded host `git worktree add` could still time out even on its load-scaled budget, and the agent dispatch then failed outright with no retry. The handler now undoes the timed-out add and, when the undo left nothing behind, attempts the add once more on a budget scaled from a fresh load reading. Only a timeout is retried; an existing branch or path, a refused hook or any other git error is deterministic and fails at once. If the retry fails too, the deny says that one automatic retry was already made.

Because the event can now make two adds and two undos, the `WorktreeCreate` event deadline grows and the client wait in `init.sh` moves from 230 to 450 seconds. The hook is registered without a short timeout, so nothing else changes.

The `worktree_create` handler gains two options, `add_base_seconds` (default 30) and `add_ceiling_seconds` (default 120). Both are positive numbers, the base may not exceed the ceiling, and the ceiling may not exceed 120 because the event deadline is sized for it. The defaults are the previous constants, so behaviour is unchanged until a project sets them. An invalid value is reported at session start and that option runs on its default.

#### the symbol-lookup guard no longer mistakes a grep option value for a searched file

_Plan 00474 · Audience: client projects_

A `grep` that filters another command's output was still treated as a symbol lookup when it carried an option that takes a value, such as `-A 3`, `-m 2` or `-e PATTERN`, because the value was read as a file name. The guard now knows which options consume a value, so those output filters are left alone, while a grep that really names a file is still judged.

#### the merged-branch pool message says a branch is unkept, not that it is old

_Plan 00474 · Audience: client projects_

A merged branch that was neither deleted nor kept was reported as stale "past" the age limit even when it was days old. The branch-creation block and the sweep report now say "neither deleted nor kept" for that case, and mention the age limit only for a keep that has lapsed.

#### a finished agent whose report quotes a usage-limit sentence is no longer reported as killed

_Plan 00474 · Audience: client projects_

The prompt-time check for agents killed by a usage limit searched the whole task notification, so a completed agent whose report quoted the limit text drew a "re-brief it" notice. A notification whose status is completed is now ignored, and the limit sentence is looked for outside the agent's own result.

#### a skipped venv of unknown ownership no longer prints an interpreter-drift line on every run

_Plan 00474 · Audience: client projects_

When the venv scan passed over a legacy, un-slugged venv whose interpreter had drifted, it printed a warning on every command even though another venv was then used. That warning is now printed only when no venv turns out usable; a venv built for this checkout still warns at once.

#### worktree creation no longer loses its creator record to a held git config lock, and its branch checks follow host load

_Plan 00474 · Audience: client projects_

When a session creates a worktree, the daemon checks the branch cap and then records which session created the branch in the repository's git config. Both steps used a fixed 5 second budget, so on a heavily loaded host a timed-out check was read as a failed judgement, and a creator record written while another git process held `.git/config.lock` was silently lost. The branch checks now scale their budget with host load (up to 10 seconds each), and each creator-record write waits for the lock for up to 10 seconds, then logs and carries on without blocking the worktree. The WorktreeCreate event budget grows from 440 to 500 seconds to cover this, and the shell client's default wait for that event grows from 450 to 510 seconds. A client project that overrides the wait in its own `init.sh` copy should refresh it by upgrading the daemon.

#### a worktree add on a heavily loaded host is given longer, and a timed-out one is cleaned up and explained

_Plan 00474 · Audience: client projects_

Creating a worktree for an `isolation: "worktree"` agent or a `--worktree` session used to give `git worktree add` a fixed 30 seconds. On a host busy with something heavy, such as a QA run, git needed longer, the creation was denied as a handler crash, and the cleanup, on 5-second calls of its own, could not remove the half-populated checkout directory it left behind. That directory had no registered worktree and no branch, so `git worktree remove` did not know it.

The add now runs on a budget scaled to host load: the 30-second base on an idle host, growing with the load average per CPU up to a ceiling of 120 seconds. The cleanup calls scale the same way, up to 10 seconds each. If the add still times out, the handler undoes it, deleting the partial directory itself when git does not own it, and the deny names the cause, the load average and the safe action, which is to retry once the load drops. The timeout and the load average are also logged as a warning. The slowest case the event can now take is longer, so the `WorktreeCreate` client wait in `init.sh` moves from 90 to 230 seconds; the hook is registered without a short timeout, so nothing else changes. `worktree remove` in `branch-sweep --clean` and `worktree-reap` scales its 300-second budget the same way, up to 20 minutes.

A new QA check, `fixed_worktree_budget`, fails the build when a function that writes a worktree runs a git call on a fixed budget.

#### the declared dependency floors now match what the daemon imports (jsonschema 4.18 or newer)

_Plan 00474 · Audience: client projects_

The daemon imports `referencing` (schema validation) and `pydantic_core` (config error reporting) directly, but declared neither, and its `jsonschema>=4.0` floor admitted releases that do not depend on `referencing` at all. The package now requires `jsonschema>=4.18`, `referencing>=0.28.4` and `pydantic-core>=2.14`. A client environment already on current releases changes nothing; one pinned to an older jsonschema is upgraded on the next install or upgrade.

#### the generated hook wrappers name no machine-specific path

_Plan 00609 · Audience: client projects_

The relay hot-path block the daemon generates into each `.claude/hooks/*` wrapper embedded the absolute checkout path (the `BASH_SOURCE` prefix test, the untracked directory, the relay binary default and the daemon root passed to the relay). On a deeply nested checkout it also embedded the short fallback events directory, a path made of a runtime directory, a uid and two hashes. A project that tracks its wrappers therefore got a dirty checkout whenever another machine or root regenerated them. The nc rung's trailing events-directory argument carried the same fallback path.

The wrappers are now byte-identical in every root on every machine. The checkout root is derived at run time from `${BASH_SOURCE[0]}` (which must be an absolute path ending in `/.claude/hooks/<name>`; anything else takes the legacy transport as before), and only the layout below the root (`untracked` or `.claude/hooks-daemon/untracked`) is written. No extra process is spawned on the hot path.

When the natural events directory overflows the AF_UNIX path limit, the daemon binds in its short fallback root and now publishes where, in `untracked/events<host-suffix>.location` (two lines: the untracked dir it was written for, then the events dir). The wrapper and `init.sh`'s nc rung read it back with the `read` builtin and trust it only when it names their own untracked dir. `HOOKS_DAEMON_EVENTS_DIR` still wins over everything.

Behaviour change: a copy of a wrapper (a git worktree inherits the tracked file) now dials its own checkout's socket instead of skipping the hot path, and finds none unless that checkout runs a daemon.

Upgrade: the next converge or upgrade rewrites each wrapper that still carries the old embedded block once; a second regeneration is a no-op. A project that tracks its wrappers should expect exactly one diff to commit. A daemon running an older release does not publish the location file, so on an overflowing layout the wrapper falls through to the legacy transport until the daemon is restarted.

#### the venv start diagnosis no longer trusts an ambient PYTHONPATH

_Plan 00609 · Audience: client projects_

When the daemon fails to start, it runs the venv's own interpreter to report why (version, `site-packages` on `sys.path`, whether the daemon package imports). That probe inherited the caller's `PYTHONPATH`, so a shell that exports `PYTHONPATH=<checkout>/src` made a venv with no daemon package report `importable: yes` and `healthy`, hiding a broken venv. The probe now runs without `PYTHONPATH`, so it judges the venv itself.

Nothing to do on upgrade. The start-failure message may now name a venv problem that was previously masked.

#### WorktreeRemove and other hard-failing git calls now wait longer on a loaded host

_Plan 00474 · Audience: client projects_

`git worktree remove` inside the WorktreeRemove event ran on a fixed 30 s budget. On a host at a load average near 70 that killed the removal part way and left a half-deleted `prunable` worktree. The removal now runs on a 30 s base scaled by host load, bounded by a 120 s ceiling, and the handler's other git calls (worktree list, containment check, creator record, merge probe, prune) are scaled the same way as the WorktreeCreate metadata calls, up to 10 s each.

Behaviour change: the WorktreeRemove event budget grows from 60 s to 170 s, and the client wait that mirrors it (`init.sh` `_event_socket_wait`, the relay guard) from 70 s to 180 s. An idle host is unaffected: every base is the floor and scaling only lengthens a budget.

The same treatment covers the other git calls that treat a timeout as a hard failure with no retry: the CLAUDE.md auto-commit (30 s base, 120 s ceiling), the fetches and pushes of `branch-park`, `branch-keep` and `branch-sweep --clean` (30 s base, 120 s ceiling), the branch-safety proof walks (120 s base, 480 s ceiling) and the protected-file index build (120 s base, 480 s ceiling). On an idle host each keeps its old budget.

Upgrade: nothing to do; the next converge or upgrade rewrites `init.sh` and the relay wrapper with the new wait.

### Audience: operators

#### branch-sweep classifies branches that share no history with the default branch

_Plan 00605 · Audience: operators_

A branch with no merge base against the default branch (an orphan branch, or any branch left behind when the default branch's history was rewritten) used to come back `UNCLASSIFIED` with a reason blaming the sweep budget, and so counted toward `branches.wip.cap` with no way to clear it. It is now measured and classified as unmerged work (never merged, contained or patch-equivalent, even when its commits repeat patches the default branch holds), with its whole tip counted as its lines. In a shallow clone whose fork point was not fetched it stays unclassified, with a reason saying the history was not fetched. An unclassified branch's reason now names its real cause (the budget ran out, git failed, or history not fetched), and `branch-sweep --budget-ms N` overrides `branches.sweep.budget_ms` for that run only.

#### delete-branch no longer deletes unproven work, and its proof target is not caller-chosen

_Plan 00594 · Audience: operators_

`delete-branch` removed the `--allow-unproven` and `--reason` flags: a branch whose content no machine-checked tier proves recoverable is never deleted by the command, whatever is declared or confirmed. Finish the work (merge it) or let the human who owns the branch decide. `--protected-ref` now accepts only the default branch or a declared integration line (local or remote form); any other ref, including the branch's own tip or a sha, is a usage error, because a caller that names its own proof target proves its own deletion. A project that scripted `delete-branch ... --allow-unproven --reason ...` must drop those flags.

#### recovery bundles are gone; delete commands print a restore line instead

_Plan 00594 · Audience: operators_

`delete-branch`, `branch-sweep --clean --apply` and `worktree-reap --reap-branches` no longer write recovery bundles under `untracked/deleted-branches/` or `untracked/branch-cleanup/`. A delete is permitted by the machine proof alone, never by a copy. The `--bundle` and `--no-bundle` flags of `delete-branch` are removed, so a script that passes them must drop them. Each command now prints one `git branch <name> <sha>` restore line per deleted branch (remote deletes print `git push <remote> <sha>:refs/heads/<name>`), naming the tip the proof was made against. The JSON output of `delete-branch --format json` replaces its `bundle` key with a `restore` list. Bundles already on disk are untouched and can be deleted by hand.

#### the daemon's remote git calls use the session's SSH agent

_Plan 00594 · Audience: operators_

A daemon started by an upgrade or restart outside the session shell has no `SSH_AUTH_SOCK`, so its `git fetch`, `git push` and `git ls-remote` calls to an ssh remote could not authenticate. The daemon now reads `SSH_AUTH_SOCK`, and only that variable, from the connecting hook process's `/proc/<pid>/environ` when a remote git call is made, and passes it to that one git subprocess. The value is used only when it is an absolute path to a socket owned by the daemon's own uid; otherwise the daemon's own environment applies. It is never logged and never stored on the payload. `GIT_SSH_COMMAND`, `GIT_SSH`, `GIT_ASKPASS`, `SSH_ASKPASS` and `SSH_AGENT_PID` are never taken from a peer. The "daemon has no SSH_AUTH_SOCK" hint on a failed `ls-remote` is no longer shown when a socket was forwarded. No configuration is needed. The status-line background fetch and the version check are unchanged.

#### finished issues leave the workable cache, and setup_worktree.sh obeys the branch pools

_Plan 00606 · Audience: operators_

`work-queue done` no longer lists the issue it just finished as the next workable one: the issue number in the entry's branch or name is kept out of the workable-issues cache even while GitHub still shows the issue open, so the stop gate stops naming a finished issue. `branch_creation_guard` now treats `scripts/setup_worktree.sh <name>` as a branch creation (it runs `git worktree add` itself), so the branch pool caps apply to it exactly as they do to a direct `git worktree add`. The acceptance-test socket discovery also asks the daemon's own resolver, so a runner whose hostname pushes the socket to the `/tmp` fallback no longer errors every acceptance test.

#### provision.sh puts the relay binary in place, as install and upgrade do

_Plan 00608 · Audience: operators_

A checkout provisioned with `bash .claude/provision.sh` now gets the relay binary, not only the venv and the daemon. Until now only install and upgrade ran that step, so a freshly provisioned clone had the relay switched on by default but no binary, and ran every hook on the slower fallback transport. The foreground run now builds or downloads the binary for the tag after the venv is built, through the same `scripts/install/relay_provision.sh` step install and upgrade use, and regenerates the forwarders for the transport. A clone already at the expected version gets it only when its binary is missing or defective (`relay_deploy --check`), and a synced clone gets it for the new tag. A failure prints the banner and the provision still succeeds, because the bash transport enforces every rule; `daemon.transport.relay_enabled: false` does nothing. A `--background` run never builds or downloads: it reports a missing relay and names `hooks-daemon transport on`. The regenerated forwarders under `.claude/hooks/` are tracked files, so the closing lines say so instead of claiming nothing tracked changed when the step rewrote them.

#### a relay repair that cannot create its state file is logged

_Plan 00608 · Audience: operators_

When the session-start relay repair could not create its state directory or file, it returned the reason into that one session's start-up context only and wrote nothing to the daemon log, so the failure left no trace afterwards. It now also logs an error naming the binary and the reason. The repair is still not started in that case, and nothing else changes.

#### the relay repair also starts when the daemon starts

_Plan 00608 · Audience: operators_

An unusable relay binary was repaired in the background only by the session-start check. A clone provisioned after its session began, or a session whose start-up hook never reached the daemon, therefore stayed on the slower fallback transport until the next session start. The daemon now judges the configured relay binary at its own start-up, as a deferred step after its socket is bound, and starts the same detached repair. It is once per cause, shared with the session-start check through one claim file, so the two triggers never build twice, and a failed attempt stays failed until `transport on` is run by hand. The step never delays or stops daemon start-up: a failure to judge or start the repair is logged at ERROR in the daemon log. A relay disabled in config, or a usable binary, starts nothing.

The repair the daemon starts is owned by the daemon: stopping the daemon ends it (its whole process group, SIGTERM then SIGKILL, bounded to a few seconds) and waits for it, so nothing writes under the project after `stop` returns. A repair interrupted this way has its unfinished claim withdrawn, so the next daemon start retries it; a recorded result is kept. The repair the SessionStart check starts stays detached on purpose, because its parent is a hook that exits at once. A daemon killed with SIGKILL cannot end its repair, which then finishes on its own.

#### `hooks-daemon status` shows the relay repair state beside its relay WARNING

_Plan 00608 · Audience: operators_

When `hooks-daemon status` warns that the configured relay binary is missing or cannot run, it now also prints what the background repair of that cause recorded: `Relay repair: <status> - <detail>` and `Relay repair log: <path>`, or `Relay repair: no attempt recorded for this cause` naming the state file that is absent. That tells a repair that failed apart from one that was never attempted. The lines are read from the repair's own state file in the daemon's untracked directory, in both the running and not-running outputs, and the exit code is unchanged (liveness only). Nothing is printed when the relay is disabled or its binary is usable.

#### the last venv build result is recorded per view

_Plan 00608 · Audience: operators_

`untracked/.venv-bootstrap.result` was one file written by every view of a checkout (a host and a container mounting the same tree), so the last writer replaced the other view's record. The result is now one file per view, `untracked/.venv-bootstrap-<fingerprint>.result`, keyed by the venv fingerprint exactly as the build log `untracked/.venv-bootstrap-<fingerprint>.log` is. The bash build paths (`venv.sh`, `venv_bootstrap.sh`) and the Python repair write it; the format and keys are unchanged.

The readers that run without a venv (`hooks-daemon status`, the wrapper's `diagnose` and failure output, the stop hook, the `probe` state) cannot cheaply tell which view they are, so they show the newest record of any view; its `log=` line names the fingerprint of the view it belongs to.

Upgrade: the old single `.venv-bootstrap.result` is neither written nor read any more, and no fallback read is kept. It is a diagnostic of the last build only, the next build in each view writes its own record, and reading a file that either view might have written is the defect this removes. A leftover old file is harmless and can be deleted.

#### a park marker over work the default already holds is in no pool, and its delete is proven

_Plan 00594 · Audience: operators_

A branch whose only commits beyond the default are empty `Parked-*` park markers (the work under the marker is already in the default, for example carried by a merged release line) used to be judged three ways: the branch-creation guard counted it as parked, `branch-sweep` called it merged, and the remote-delete guard refused it as unmerged. A clone could read `Parked: 4 of 10` in the sweep while creation was refused at `Parked branches: 10 (cap 10)`, and the refs had no route out.

There is now one rule (`branch_inventory.is_park_residue`, every commit in `default..tip` is a park marker) and one pool function (`pool_for_ref`) used by the sweep, the creation guard and the remote-delete proof. Such a ref has the status `park-carried`: it counts in no pool, so it blocks no creation; `branch-sweep` lists it under "Park-carried" with its park reason and, when the remote-delete proof accepts it, the runnable `git push <remote> --delete <name>` line; `branch-sweep --clean --remote` deletes it under a lease on its tip. The proof tier is `park-carried`; a park over work the default does NOT hold stays parked and its remote delete stays refused, and an empty change that is not a park marker is still unproven. A ref with a local copy is reported the same way but gets no `--clean` local delete.

The merged-pool deny text now says an unkept merged branch is stale from day 0 whatever its age (its age is the tip commit date); only a keep is aged against `branches.merged.max_age_days`.

#### the secret guard judges a trailing-slash glob as directories

_Plan 00610 · Audience: operators_

`secret_file_guard` denied `ls -d */` (R-SECRET-BASH-MENTION) whenever the project root held a protected file, while `ls -d docs/` was allowed. The glob was matched like `*`, against files at its own level, because the trailing `/` was dropped.

A glob ending in `/` now expands only to directories, as in the shell, and never matches a file at its own level. A recursive reader (`grep -r x */`, `rg x d*/`) is judged over each directory the glob expands to, exactly as it is for the literal directory (`grep -r x dir/`): it is denied when a protected file lies below a matching directory. Other glob shapes, protected patterns and config defaults are unchanged.

#### the secret guard no longer misses POSIX classes and symlinked directories in a glob

_Plan 00612 · Audience: operators_

`secret_file_guard` allowed two recursive reads that reach a protected file. `grep -r x [[:alpha:]]*/` was allowed because POSIX bracket classes (`[[:alpha:]]`, `[[:digit:]]`, `[[:space:]]` and the rest) were passed to `fnmatch` untranslated and matched nothing. `grep -r x l*/` was allowed when `l` is a symlink to a directory holding a protected file, because the index holds real paths.

Glob components are now matched with the POSIX classes translated, for file globs and directory globs alike (`[^x]` and `[!x]` still both negate). A trailing-slash glob also matches a symlink to a directory holding a protected file, found by listing the single directory the glob's literal parent names; a symlink matched only below a wildcard directory (`*/l*/`) is still not judged, which keeps the cost independent of tree size. Protected patterns and config defaults are unchanged.

## ⚠️ BREAKING CHANGES

### Command-line changes that need a script update

- **`hooks-daemon branch-sweep --clean`** - Changed in v3.75.0

  - **Why**: `--clean` deleted at once, which is the wrong default for a command that can remove hundreds of branches. It is now the dry run and prints the whole plan with each branch's proof.
  - **Migration**: add `--apply` to delete (`--clean --remote --apply` for remote copies). The `branch-sweep-clean` step of `/hooks-daemon housekeeping` already does.
  - **Guide**: [v3.74.0-to-v3.75.0](../CLAUDE/UPGRADES/v3/v3.74.0-to-v3.75.0/v3.74.0-to-v3.75.0.md)

- **`hooks-daemon delete-branch --allow-unproven`, `--reason`, `--bundle`, `--no-bundle`** - Removed in v3.75.0

  - **Why**: a branch whose content no machine-checked tier proves recoverable is never deleted by the command, and recovery bundles are gone. A caller that names its own proof target proves its own deletion, so `--protected-ref` now accepts only the default branch or a declared integration line.
  - **Migration**: drop the removed flags from any script. Each delete prints a `git branch <name> <sha>` restore line (`git push <remote> <sha>:refs/heads/<name>` for a remote delete); `delete-branch --format json` replaces its `bundle` key with a `restore` list.
  - **Guide**: [v3.74.0-to-v3.75.0](../CLAUDE/UPGRADES/v3/v3.74.0-to-v3.75.0/v3.74.0-to-v3.75.0.md)

- **`hooks-daemon delete-branch --protected-ref` and `worktree-reap --base-branch`** - Narrowed in v3.75.0

  - **Why**: the ref a deletion is proved against must not be caller-chosen.
  - **Migration**: pass only the default branch or a declared integration line (local or remote form); any other ref, including a sha, is now refused with a usage error.
  - **Guide**: [v3.74.0-to-v3.75.0](../CLAUDE/UPGRADES/v3/v3.74.0-to-v3.75.0/v3.74.0-to-v3.75.0.md)

### Default behaviour changes

- **`claude_md.ownership`** - New key, default `own`, in v3.75.0

  - **Why**: the ownership sentence and hints change what the model does (see the callout above for the measured costs).
  - **Migration**: set `claude_md.ownership: off` to restore the previous block.

  ```yaml
  claude_md:
    ownership: off
  ```

  - **Guide**: [v3.74.0-to-v3.75.0](../CLAUDE/UPGRADES/v3/v3.74.0-to-v3.75.0/v3.74.0-to-v3.75.0.md)

- **`branches.wip.creation_grace`** - New key, default `2`, in v3.75.0

  - **Why**: branch-pool pressure now lands at session start and stop, so creation is only a backstop. A creation at `branches.wip.cap` open branches warns (with the full report) instead of being denied; the deny comes at `cap + 2`. The dormant, parked and merged pools still deny at their own limits.
  - **Migration**: set `creation_grace: 0` to keep the old deny at the cap.

  ```yaml
  branches:
    wip:
      creation_grace: 0
  ```

  - **Guide**: [v3.74.0-to-v3.75.0](../CLAUDE/UPGRADES/v3/v3.74.0-to-v3.75.0/v3.74.0-to-v3.75.0.md)

## Security

- **Fixed false allows in `secret_file_guard`** (Plan 00612): a recursive read through a POSIX bracket class (`[[:alpha:]]*/`) or through a symlink to a directory holding a protected file was allowed. Both are now judged. See the callout above.
- **`destructive_git` denies more** (Plan 00596): a script written earlier in the command and fed to a shell, and a `printf -v` variable later expanded outside a plain print, now deny.
- **The daemon reads one variable from the hook process** (Plan 00594): `SSH_AUTH_SOCK`, from `/proc/<pid>/environ`, used only when it is an absolute path to a socket owned by the daemon's own uid, never logged or stored. No other variable is taken from a peer.
- **`daemon.omit_permission_surface` lowers defence in depth** when set to `true` (default `false`): it removes the daemon's `PermissionRequest` hook and `permissions.deny` rules for every session, not only bypass sessions. Turn it on only where every session runs in bypass mode.

## Upgrade Instructions

No pre-upgrade or post-upgrade task. Config keys are added (`claude_md.ownership`, `claude_md.ownership_text`, `daemon.omit_permission_surface`, `branches.wip.creation_grace`, `branches.park.commit`, `branches.park.push`, and two `worktree_create` options), all optional; see `CLAUDE/UPGRADES/config-changes/v3.75.0.yaml`. Two of them change behaviour when left unset: `claude_md.ownership` (default `own`) and `branches.wip.creation_grace` (default `2`); the upgrade's config advisory lists both under "Recommended" so you decide deliberately. The truth-changes manifest `CLAUDE/UPGRADES/truth-changes/v3.75.0.yaml` lists the documented commands that changed (`branch-sweep --clean`, `delete-branch`, the creation cap); reconcile your project's own docs against it. Several worktree-event callouts above each quote one step of a wait that moved more than once in this release: the net change from v3.74.0 is that the `init.sh` client wait for `WorktreeCreate` goes from 90 to 510 seconds and for `WorktreeRemove` from 70 to 180 seconds. The next converge or upgrade rewrites each generated hook wrapper once, so a project that tracks its wrappers should expect exactly one diff to commit. See `CLAUDE/UPGRADES/v3/v3.74.0-to-v3.75.0/v3.74.0-to-v3.75.0.md`.

### Upgrading Existing Installations

```bash
cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
git -C .claude/hooks-daemon fetch --tags

# Rebuilds the venv and reinstalls the package for the target version. Runs the
# target's own upgrade.sh: the installed one may predate the pre-deploy gate.
tmp="$(mktemp)"
git -C .claude/hooks-daemon show "v3.75.0:scripts/upgrade.sh" > "$tmp"
bash "$tmp" --project-root "$PWD" "v3.75.0"

.claude/hooks-daemon/bin/hooks-daemon restart
```
