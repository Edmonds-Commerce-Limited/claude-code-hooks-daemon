# v3.58.0 — Declared Monorepo Projects, Zero-Absolute-Paths Config, and a Degraded-Mode Safety Net

**Release Date:** 2026-09-01
**Type:** Minor Release (with narrowly-scoped breaking changes)

## Summary

This release completes the hard cutover to **declared, not inferred,
monorepo project boundaries** (Plan 00296/00300/00301): a top-level
`projects:` config block is now the only sub-project resolution mechanism,
each declared project may carry its own `layout:` block, and the older
`monorepo_subproject_patterns` regex-pattern alias is removed outright. It
also delivers a zero-absolute-paths-in-config audit with a portable
`{REPO_ROOT}` path token (Plan 00302/00303), a degraded-mode safety net that
keeps destructive-git protection alive config-independently (Plan 00304), a
zero-token failsafe-cron blockage suppressor (Plan 00298), multi-plan
combined `/goal` rendering (Plan 00299), and a supervisor DROP ANCHOR safety
net (Plan 00297). Two false-positive fixes round out the cycle: the Go
error-hiding check and the quarantine artefact read guard.

## Highlights

- **Declared `projects:` config is the only monorepo sub-project mechanism**
  (Plan 00296/00300) — a repository with no `projects:` declared behaves
  exactly as before.
- **Per-project `layout:` blocks** (Plan 00300/00301) let each declared
  project override its own source/test/config/vendor directory names.
- **Zero-absolute-paths config enforcement + `{REPO_ROOT}` token** (Plan
  00302/00303) hard-errors or fails open on an absolute config path,
  depending on the field's existing contract.
- **Degraded-mode safety net** (Plan 00304) — destructive-git protection now
  runs config-independently while the daemon is degraded, with visibility on
  `status`/`check`/`config-validate`.
- **Failsafe-cron blockage suppressor** (Plan 00298) and **multi-plan
  combined `/goal` rendering** (Plan 00299) — zero-token cron ticks while
  blocked on human input, and one combined goal view across every live plan.
- **Supervisor DROP ANCHOR safety net** (Plan 00297) — read-back-verified
  Fable-above-low-effort invariant, with an owner-approved ESC interrupt on
  escalation.

## ⚠️ BREAKING CHANGES

### Configuration Changes

- **`handlers.pre_tool_use.markdown_organization.options.monorepo_subproject_patterns`** — Removed in v3.58.0

  - **Why**: Plan 00300 hard cutover (owner ruling). Declared `projects:`
    config (Plan 00296) is now the ONLY sub-project resolution mechanism —
    two competing mechanisms created ambiguity about which one wins for a
    given file, so the regex-pattern alias is removed outright rather than
    deprecated in place. A non-empty pattern list is real usage and is now a
    hard config-validation error at daemon startup; the error message prints
    a paste-ready `projects:` block for every literal (non-wildcard)
    pattern. A `null`/empty/absent value — the shape an older daemon
    version's own default config template writes, with nothing actually
    configured — is tolerated silently (Plan 00304; an advisory log line
    only, no error).
  - **Migration**: run `bin/hooks-daemon config-validate .claude/hooks-daemon.yaml`
    (or start the daemon) and read the printed error for a paste-ready
    `projects:` block; declare any wildcard pattern's real sub-project
    directories by hand; delete the `monorepo_subproject_patterns` key.
  - **Guide**: [v3.57-to-v3.58 Upgrade Guide](../CLAUDE/UPGRADES/v3/v3.57-to-v3.58/v3.57-to-v3.58.md)

- **`tdd_enforcement`'s `test_path_map`** — Behaviour changed in v3.58.0

  - **Why**: Plan 00300. In a declared `projects:` monorepo, a relative
    `test_dir` now anchors against the source file's declared workspace
    ONLY — the second, repository-root-anchored candidate that used to be
    searched is gone. A single-project repo (no `projects:` declared) is
    unaffected: the workspace IS the repository root.
  - **Migration**: only relevant if you both declare `projects:` AND have a
    `test_path_map` entry whose test file lives at the project-root-anchored
    path. Move the test file to `{declared project root}/{test_dir}/`, or
    split the entry per declared project.
  - **Guide**: [v3.57-to-v3.58 Upgrade Guide](../CLAUDE/UPGRADES/v3/v3.57-to-v3.58/v3.57-to-v3.58.md)

## Changes

See [CHANGELOG.md](../CHANGELOG.md) for the full categorized entry. Summary:

### Added

- Declared `projects:` config + shared `Workspace.for_path` resolver, with
  `markdown_organization`, `tdd_enforcement`, `npm_command`, `lint_on_edit`
  and `eslint` all workspace-aware (Plan 00296).
- Per-project `layout:` blocks with DRY registry helpers (Plan 00300/00301).
- REPO vs PROJECT handler `workspace_scope` taxonomy (Plan 00301).
- Zero-absolute-paths config enforcement and `{REPO_ROOT}` path token (Plan
  00302/00303).
- Degraded-mode safety net: config-independent `DestructiveGitHandler`, and
  DEGRADED-mode visibility on status/check/config-validate (Plan 00304).
- Failsafe-cron blockage suppressor — zero-token ticks while blocked on
  human input (Plan 00298).
- Multi-plan combined `/goal` rendering with a thrash guard (Plan 00299).
- Supervisor DROP ANCHOR safety net with owner-approved ESC interrupt on
  escalation (Plan 00297).
- `php-qa-ci` canary workflow documentation.

### Changed

- Removed the erroneous secondary publish-confirmation gate from the release
  process (owner ruling): `/release` is the sole authorisation.

### Fixed

- Go error-hiding false positive: a blank identifier in the FIRST tuple
  position (`_, err := f()`, which captures the error) was wrongly denied;
  only a blank in the LAST position is the real error-hiding shape.
- `quarantine_artefact_read_guard` false positive on unexpanded shell globs:
  an ordinary `grep -c pattern docs/*.md` was denied even with no
  `*-opus-security-DETAIL*` artefact on disk, because the glob token
  fnmatched the seed literal's stem regardless of the filesystem. A strict
  glob-expansion check now requires the token to actually expand to a real
  matching file.

### Removed

- `handlers.pre_tool_use.markdown_organization.options.monorepo_subproject_patterns`
  (see BREAKING CHANGES above).

## Installation

### New Installations

```bash
mkdir -p .claude
git clone -b v3.58.0 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon

# The installer builds the fingerprint-keyed venv, installs the package and
# starts the daemon. Never hand-build a venv — the resolver refuses the
# retired pre-v3.7.0 layout.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
git -C .claude/hooks-daemon fetch --tags

# Rebuilds the venv and reinstalls the package for the target version.
bash .claude/hooks-daemon/scripts/upgrade_version.sh \
  "$PWD" "$PWD/.claude/hooks-daemon" "v3.58.0"

.claude/hooks-daemon/bin/hooks-daemon restart
```
