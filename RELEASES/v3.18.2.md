## Summary

v3.18.2 is a single-fix patch. `restart_daemon_verified` in `scripts/install/daemon_control.sh` previously treated the daemon starter process's exit code as the authoritative signal for "did the daemon start". Under single-daemon enforcement (container mode), a concurrent daemon start — for example, a live hook-triggered auto-start arriving during an upgrade — SIGTERMs the in-flight `cli start` parent, causing it to exit 143. The old code reported "Daemon failed to start (exit code 143)" even when the winning daemon came up healthy. The fix makes `start_daemon_safe` expose its result via `DAEMON_START_EXIT_CODE` / `DAEMON_START_OUTPUT` (with a quiet mode to suppress interleaved output) and `restart_daemon_verified` always defers the start/no-start decision to an authoritative status poll, reporting failure only when the poll confirms no daemon is running, and surfacing the captured starter output at that point for diagnostics. This was field-observed twice across consecutive upgrade runs.

**Note on delivery**: `daemon_control.sh` is part of the install/upgrade script bundle copied into each project's `.claude/hooks-daemon/scripts/install/` during `install.py` or `upgrade.sh`. It is NOT delivered via the Plan 00109 thin-shim (which only covers `scripts/upgrade.sh`). Existing installations receive this fix on their next upgrade run that executes `untracked/venv/bin/python install.py` or the equivalent versioned checkout-and-install step.
