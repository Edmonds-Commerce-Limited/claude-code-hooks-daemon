# Release v3.66.0 - Scoped Handlers, Verified Reports, a Run of Layering Fixes

**Release Date:** 2026-09-21
**Type:** Minor Release

## Summary

Plan 00423 gives any handler a `scope: ALL | MAIN | SUB` config key, decided
from whether the triggering event carries a subagent id rather than
guesswork, and ships `subagent_cron_delete_blocker` so a subagent can no
longer delete the session's own recovery cron — both close a reported
incident where a finished subagent was nudged to continue plans that were
never its assignment and then deleted the cron doing the nudging. Plan 00427
makes `mkplan.bash --journal` stamp journal timestamps in UTC and teaches the
future-dated check to read a day-file's own clock rather than a naive local
one. Plan 00446 ships `subagent_report_path_verifier`, blocking a subagent
stop that claims to have written a file that is not on disk. The rest of this
cycle is a run of smaller correctness and layering fixes surfaced by the
00422 niggles ledger — `remote-docs`, `format-markdown`, `block-report`, the
worktree socket-path pre-flight, scoped QA output, the harvester's kill
suggestion, persistent-cron prompt matching, the two link-resolution checks,
and a shared locked counter behind two advisory handlers — plus two internal
moves (the fence splitter and the read-only git-facts core) into `utils`.
`breaking: false` — no config keys renamed or removed this cycle, so no
upgrade guide is needed.

## Highlights

### Everyone

- **Handlers can declare whether they run for the coordinator, subagents, or
  both (Plan 00423).** Any handler may set `scope: ALL | MAIN | SUB`, and
  `ALL` stays the default so nothing changes unless you set it — the role is
  decided by whether the event carries a subagent id, never by guesswork.
  This closes a reported problem where a finished subagent was told, on every
  failsafe tick, to continue plans from the coordinator's goal ledger that
  were never its assignment. **Three stop-time nudges now ship scoped to the
  coordinator and therefore stop firing inside subagents on upgrade** —
  `auto_continue_stop`, `cron_stop_enforcer` and `teammate_reap_advisor`.
  Each advises on state only the coordinator owns, so this is the intended
  fix, but it is a change of default behaviour rather than an opt-in: set
  `scope: ALL` on any of the three to restore what they did before.
  Relatedly, a
  subagent can no longer delete a session cron — the incident behind the
  report was one deleting a shared recovery cron to stop the nudges, leaving
  a live session with no recovery path — so if you disabled a stop handler
  outright to work around this, you can stop doing that and scope it
  instead.
- **`mkplan.bash --journal` stamps journal entries in UTC (Plan 00427).**
  `mkplan.bash` now accepts `--journal <plan-number> <category> <body-file> [--ref R] [--title T]` to append a journal entry to an existing plan. The
  script reads the clock itself and normalises it to UTC, so the agent never
  types (or estimates) a timestamp — closing the first of two failure modes
  measured on issue #45, an agent's guessed time drifting from real elapsed
  time. The second (a naive future-dated check misreading an entry written in
  a different zone) needed the reader to change too — see below.
  A day-file the scaffolder creates carries one sentinel line in its preamble
  naming the writer and the zone; a day-file with no sentinel predates this
  system and is left exactly as it is — no migration, no rewrite of the
  existing 2,207 entries across this project's own history. Hand-authored
  entries (`Write`/`Edit`/a heredoc) are unaffected and still carry no zone.
- **`journal-entry-future-dated` judges a day-file by the clock that wrote it
  (Plan 00427).** `journal-entry-future-dated` compared every journal entry
  against a naive local clock. Once `mkplan.bash --journal` began stamping
  entries in UTC, that made the check wrong on correct data for a whole class
  of hosts — measured at one instant against the check's 30-minute tolerance,
  a `America/New_York` host false-fired at +239 minutes and
  `America/Los_Angeles` at +419 minutes, while `UTC` and `Europe/London`
  stayed silent. The check now picks its clock from the day-file itself: a
  file carrying the scaffolder's sentinel is judged against UTC, a file
  without one is legacy and keeps the local-clock behaviour unchanged.
  Nothing is migrated, and no existing day-file is touched. If you saw this
  advisory on entries that looked perfectly correct, that was this defect,
  and it is gone.
- **The dedupe scout's plan count is now checked from outside the agent (Plan
  00434).** `hooks-daemon-plan-dedupe-scout` reports `Checked N live plans.`
  so a caller can tell a real check from a guess. Until now the only thing N
  could be reconciled against was the scout's own enumeration — which is no
  check at all when the enumeration is what went wrong. Measured on this
  agent across real dispatches: 34, then 32, then 17 plans reported for the
  same unchanged tree of 34. `mkplan.bash` now prints the number of plan
  folders in the plan root beside the reminder to dispatch the scout, and
  says what to do when the report disagrees: re-dispatch rather than act on
  the verdict. The agent itself is redeployed at v1.2.0, with its
  archived-plan step now written in terms of the Grep and Glob tools it
  actually has.
- **The two link checks now agree, and one stops crying "archived" (Plan
  00441).** Docs QA's `pointer-resolves` and plan QA's `plan-link-resolves`
  both answer "does this markdown link point at a file that exists", but were
  written months apart and disagreed three ways: a live plan was reported as
  archived when `PlanLinkResolver` found it live but the finding's wording
  didn't say so; a document naming the same dead link three times produced
  three identical findings instead of one; and a repo-root-relative link that
  `pointer-resolves` has always accepted was rejected by
  `plan-link-resolves`. All three now share one rule in
  `utils/link_resolution.py`. Nothing here changes which links are legal —
  it changes which findings you see, and all three changes remove noise
  rather than adding it.

### Operators

- **`remote-docs add` refuses an existing capture (Plan 00424).**
  `remote-docs add <url>` now refuses when a capture of that URL already
  exists, naming the existing file's `fetched_at` and `source_sha256` and
  pointing at `refresh` or `--force` rather than silently overwriting it. If
  you relied on a bare `add` to re-derive frontmatter after declaring
  `documentation.remote.known_sources`, use `add --force` instead, which
  replaces the capture and prints both the old and new `source_sha256`.
- **`remote-docs check` reports a stale generated index (Plan 00425).**
  Deleting a vendored capture with `rm` never regenerated
  `.claude/REMOTE-DOCS.md` — it kept naming a file that was gone, and `check`
  said everything was fresh. `check` now compares the index against the tree
  and reports a disagreement as a finding, with exit `1`, the same as
  staleness and licence drift. This can turn a previously-green CI run red
  the first time it runs after a deletion. The fix is the new `remote-docs index` command, which re-renders the file without touching the network.
  The generated index's own header text changed too, so **every existing
  project's index will report as stale once**, on the first `check` after
  upgrading, even with no tree changes — run `remote-docs index` once to
  clear it.
- **The documented `plugins:` examples were unloadable (Plan 00426).** Every
  `plugins:` example this project ships has been corrected, and a test now
  validates them against the model that has to accept them. If you copied a
  `plugins:` block from the configuration guide, the basic-setup example, or
  the commented example in `.claude/hooks-daemon.yaml.example`, it would have
  been rejected at config load: the config template showed a shape that
  predates the current schema, and the guide/example both omitted
  `event_type`, which is required and has no default. Nothing about the
  plugin system itself changed — only the examples were wrong. If you have a
  working `plugins:` block, no action is needed.
- **`format-markdown` no longer crosses repository or exclusion boundaries
  (Plan 00429).** `hooks-daemon format-markdown <dir>` (write and `--check`
  modes both) now skips any directory below the walk root that is itself a
  git repository, and honours `daemon.exclude_paths` the same way the docs-qa
  and plan-qa CLIs do. Previously, running it from a project root that
  vendors dependencies as real git checkouts could rewrite and leave
  uncommitted changes inside a repository you do not own. A file you name
  directly is still formatted regardless of exclusions, because naming it is
  explicit consent. Exclusions resolve against the enclosing project root
  rather than the directory you point the command at.
- **`block-report` now attributes denies from every `ProjectContext`-reading
  handler (Plan 00430).** `hooks-daemon block-report` now initialises
  `ProjectContext` before scanning transcripts, the same way `explain-rule`,
  `explain-handler`, `status-line --explain`, `session-actions` and
  `routine-qa` already do. Previously it never did, so five handlers whose
  constructors read `ProjectContext.project_root()`
  (`validate_eslint_on_write`, `markdown_organization`, `npm_command`,
  `plan_number_helper`, `remote_docs_provenance`) could not be constructed
  during handler discovery and were silently skipped — every deny they had
  produced was counted as unattributed instead of attributed to its handler.
  A project with no discoverable `hooks-daemon.yaml` still produces a report
  exactly as before; only a project with a working config sees attribution
  improve.
- **The worktree socket-path pre-flight now works without a venv (Plan
  00431).** `scripts/setup_worktree.sh` refuses to create a worktree whose
  prospective daemon socket path would exceed the AF_UNIX cap, because
  exceeding it is silent — the daemon still starts, relocates its runtime
  files to `/tmp`, and the acceptance gates then fail with a restart
  instruction that cannot fix it. That check used to resolve a virtualenv
  Python to call the daemon's own measurement helpers, and stood down when it
  could not — so it never ran in a worktree created from inside another
  worktree, exactly where the path gets long enough to matter. It now
  measures under the system `python3`, loading `daemon/paths.py` by file
  rather than by package path.
- **A scoped QA scan no longer overwrites the repository's artefact (Plan
  00432).** Seven `llm_qa` checkers wrote their JSON artefact to a fixed path
  inside the checkout whenever `--json` was passed, even when the scan had
  been pointed somewhere else with `--path`, `--root` or `--repo` — so a
  scoped run could replace a repository-wide PASS with a scoped FAILURE, or
  mask a real repository-wide defect behind a scoped PASS. `check_git_history.py`,
  `check_skill_references.py`, `check_python_var_guidance.py`,
  `check_github_urls.py`, `check_security_downgrade_flags.py`,
  `check_eacces_safe_predicates.py` and `check_authored_path_stat.py` now
  write their verdict beside what they scanned; three more
  (`check_fail_open_inventory.py`, `check_dangerous_invocation_corpus.py`,
  `check_declared_invariant_pairs.py`) do the same for a file override. An
  unscoped run — which is every run `llm_qa` itself makes — is unchanged.
- **`setup_worktree.sh` refuses to create a worktree inside a worktree (Plan
  00433).** `PROJECT_ROOT` comes from the script's own location, so running
  the copy inside an already-isolated worktree checkout nested a second
  worktree inside the first — overlong socket paths (caught by the AF_UNIX
  pre-flight above) were only the visible half of the cost; the expensive
  half was work committed in a tree the coordinator may later reap. The
  script now detects this before creating anything, refuses, names the
  enclosing checkout, and prints the command to run there instead. The
  documented child-worktree workflow is unaffected.
- **The harvester's suggested kill can no longer name a protected group (Plan
  00438).** `hooks-daemon harvest-background` prints a ready-to-run `kill -- -<pgid>` per breaching process group. Callers can declare groups
  off-limits (`exclude_pgids`); that exclusion was honoured when deciding
  what counts as a breach, but not when building the kill command itself, so
  a breaching process with a descendant inside an excluded group could have
  that group rendered into the suggestion. Both halves now use the same
  excluded set.
- **The cron enforcers stop re-parsing your config on every turn (Plan
  00440).** `Config.load_or_default` parses the whole pydantic model on every
  call — measured at 76.3ms median on this repository's own config —
  and `cron_stop_enforcer` called it from both `matches()` and `handle()`,
  with `matches()` running on every Stop event; the SubagentStop twin did the
  same. Those handlers, and `remote_docs_routing`, now read through a shared
  cache keyed on the file's modification time and size, cutting the
  per-event cost from roughly 150ms to about 0.05ms on an unchanged config.
  Editing your config still takes effect on the next event — the cache
  invalidates on `(st_mtime_ns, st_size)` rather than caching for the process
  lifetime.
- **A subagent's claimed report path must exist (Plan 00446).** A new
  SubagentStop handler, `subagent_report_path_verifier`, ships enabled at
  priority 8. When a subagent's final message says it wrote a file and that
  file is not on disk, the stop is blocked and the missing path is named —
  the incident behind it was a dedupe scout report ending with a
  well-formed, plausible path to a file nobody had created. Built to
  under-fire: a claim is only recognised when a past-tense or passive write
  verb governs a `.md` path inside the project root; fenced blocks are
  stripped first, and a message that merely mentions a path it read is not a
  claim. The deny offers two equal routes — write the file at the named
  path, or stop without naming one — and explicitly rules out creating an
  empty file to clear the check. Disable with
  `handlers.subagent_stop.subagent_report_path_verifier.enabled: false`.
- **The session advice counter is shared and locked (Plan 00437).**
  `teammate_reap_advisor` and `background_process_tracker` each carried their
  own unlocked copy of the counter that rate-limits their advisory. The
  daemon dispatches hook handling through a `ThreadPoolExecutor`, and
  handlers are daemon-lifetime singletons, so two concurrent hook requests
  could share one counter map across two worker threads — the eviction that
  bounds the map could raise `KeyError` or `RuntimeError` when two threads
  raced it, surfacing as an advisory handler failing on an unrelated hook
  request. Both handlers now use one locked `SessionAdviceCounter`; nothing
  about either advisory's wording, interval or eviction bound changes.

### Handler Authors

- **The documented priority bands now match the shipped constants (Plan
  00435).** The priority band table said two things that were no longer
  true, on every surface that quotes it — the agent guide, `CONTRIBUTING.md`
  and the configuration guide. The `0-9` band is not empty: three built-in
  Stop handlers (`cron_stop_enforcer`, `cron_subagent_stop_enforcer`,
  `teammate_reap_advisor`) sit there deliberately, below the terminal
  handlers that would otherwise stop them from running on the common path. And
  the Advisory band is `56-73`, not `56-69` — `PriorityRange.ADVISORY_MAX`
  has been 73 since the session-actions directive shipped. A test now
  compares the table against `PriorityRange` and checks every shipped
  handler priority falls inside a documented band.
- **The fence splitter moved out of plan QA, and the import direction is now
  checked (Plan 00439).** The fenced-code-block splitter — the primitive
  every line-oriented markdown check starts with — was written for
  `plan_qa.model` and acquired callers elsewhere. It now lives at
  `claude_code_hooks_daemon.utils.markdown_fences`, with every caller
  importing it from there; no re-export was left in `plan_qa.model`. **If you
  import `lines_outside_fences` from `plan_qa.model`, repoint it** — that
  name is gone from there. Behaviour is unchanged, and the splitter has
  direct unit tests for the first time. A new
  `tests/integration/test_qa_package_dependency_direction.py` checks the
  claimed layering rather than trusting the docstring, against a declared
  allowlist of the edges that remain.
- **Read-only git facts moved into `utils`, and two declared edges are gone
  (Plan 00444).** Following on from the callout above, two of the four
  allowlisted dependency-direction edges were `docs_qa` importing
  `plan_qa.gitfacts` for read-only git plumbing that has nothing to do with
  plans. `claude_code_hooks_daemon.utils.git_facts` now holds
  `GitFactsBase` and `StagedChange` — staged changes with rename detection,
  staged/HEAD file contents, and last-commit dates — and
  `plan_qa.gitfacts.GitFacts` subclasses that base and adds only
  `plan_counter()`, the one member that genuinely belongs to plan QA. No
  plan-QA caller changes: `from claude_code_hooks_daemon.plan_qa.gitfacts import GitFacts, StagedChange` still resolves. **If you monkeypatch
  `run_git` for a test, patch it on `utils.git_facts`** — that is where the
  name the code calls now lives.

### Client Projects

- **A truncated-to-nothing cron prompt no longer asserts every job (Plan
  00436).** If your project declares `persistent_crons`, the Stop-event
  enforcement compares each declared job against what `session_crons`
  actually delivers, and a delivered prompt that is cut short is matched by
  prefix. A delivered prompt consisting of nothing but the truncation marker
  strips to an empty prefix, which every declared job on the same schedule
  starts with — so a cron that was never created could be reported as live,
  the expensive direction of failure: a session with no recovery cron and
  nothing saying so. Prefix matching now requires a non-empty prefix; real
  truncated deliveries still match exactly as before.

## Installation

### New Installations

```bash
mkdir -p .claude
git clone -b v3.66.0 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon

# The installer builds the fingerprint-keyed venv, installs the package and
# starts the daemon.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
git -C .claude/hooks-daemon fetch --tags

bash .claude/hooks-daemon/scripts/upgrade.sh --project-root "$PWD" "v3.66.0"

.claude/hooks-daemon/bin/hooks-daemon restart
```

**Use `upgrade.sh` (Layer 1), not `upgrade_version.sh` (Layer 2) directly** —
Layer 1 is the documented entry point; invoking Layer 2 on its own skips
steps Layer 1 is responsible for sequencing.

No config keys were renamed or removed this cycle (`breaking: false`), so no
upgrade guide is required. Three new config keys ship — `scope` on any
handler, `subagent_cron_delete_blocker` and `subagent_report_path_verifier`
— all additive and on by default where applicable; see
`CLAUDE/UPGRADES/config-changes/v3.66.0.yaml` for the full manifest.

## Release Review

The code review for this release ran across two parallel reviewers (the
handler subtree and the rest of `src/`), plus a separate documentation
review, per RELEASING.md's "Review Early, Never Drop Findings" rule. Both
code reviewers returned **PROCEED with 0 blocking findings**; between them
they raised 6 non-blocking defects, and the documentation review raised 6
more.

Eleven are fixed in this release rather than deferred, per that rule's "a
release carries no known defect" requirement — "non-blocking" is a reviewer's
estimate of urgency, not permission to ship a defect. Four were code defects
this release introduced:

- the extracted advice counter's eviction had silently inverted FIFO to LIFO,
  so a session arriving after the 256-session cap re-advised from event 1 on
  every subsequent new session — the exact spam the interval prevents;
- `format-markdown --check <dir>` exited 1 on a dangling `.md` symlink, where
  v3.65.0 exited 0, failing a QA gate with an error no formatting can fix;
- the new report-path verifier read a NEGATED claim ("No report was written
  to `<path>`") as a claim — which is the sentence its own deny message asks
  the agent to write;
- and it resolved relative claims against the daemon's startup root rather
  than the event's own `cwd`, so a subagent in another checkout had an honest
  stop denied.

One finding is recorded rather than fixed: unifying the two link-resolution
rules adopted the more permissive of them, so `plan-link-resolves` now
accepts a repo-root-relative link that renders dead from its own document.
That is deliberate — tightening instead would have changed docs QA across the
whole corpus — and it is now stated as a known false-negative class in
`utils/link_resolution.py` rather than left for the next reader to
rediscover.

One is filed as follow-up Plan 00449 rather than fixed here: the unlocked
select-then-delete that this release's own counter work documents survives in
at least six other handlers, including the safety-band `write_clobber_guard`,
which claims to fail closed and does not under contention. It is pre-existing
and this release does not make it worse, so it is a follow-up and not a
blocker — but it is filed, not dropped.
