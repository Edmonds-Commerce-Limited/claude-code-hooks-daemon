# Release v3.15.0 — Skill thin-shim + atomic upgrade commit

**Type:** Minor Release

## Summary

This minor release ships Plan 00109: the skill-pushed `scripts/upgrade.sh` becomes a thin curl-and-exec shim that fetches the canonical upgrade script from `main` HEAD, and the in-repo Layer 1 `scripts/upgrade.sh` emits a machine-parseable `UPGRADE_METADATA` block on success. The project agent parses the block and writes one atomic `hooks daemon upgrade: vX → vY` commit recording the version transition.

The motivation is hot-patchability. The v3.9.x `write-venv-metadata` field bug and the v3.10.0 `print_info` stdout-corruption SEV-1 both happened because the skill carried frozen-at-release-time logic that no in-repo fix could rescue. With the thin shim, every entry point pulls live from `main`, so bug fixes reach every client on the next `/hooks-daemon upgrade` invocation without re-installation.

Backwards-compatible: clients invoke `/hooks-daemon upgrade` exactly as before.

## Highlights

- **Thin-shim skill `upgrade.sh`** — Collapses from ~280 lines of logic in the client repo to a ~23-line shim that walks for the project root, fetches the canonical script from `main` HEAD via `curl`, and execs it. Env overrides allow paranoid users to pin via `HOOKS_DAEMON_UPGRADE_REF=v3.15.0` and tests to point at `file://` fixtures via `HOOKS_DAEMON_UPGRADE_BASE_URL`.
- **`UPGRADE_METADATA` contract** — Layer 1 emits 10 `key=value` lines between `<<<UPGRADE_METADATA` and `UPGRADE_METADATA>>>` sentinels: `from_version`, `to_version`, `python_version`, `python_path`, `venv_path`, `host`, `daemon_dir`, `project_root`, `modified_files`, `config_diff_summary`. The project agent parses the block and writes one atomic commit covering ONLY daemon-owned paths — no `git add .`.
- **Skill `upgrade.md` rewritten as agent workflow** — 5 numbered steps: run upgrade, parse metadata, verify daemon RUNNING, stage daemon-owned paths only, commit with metadata in body. Closing caveat: do NOT commit if daemon is not RUNNING.
- **Four new acceptance gates** — Cover Layer 1 alone, the shim with a stand-in, the metadata-contract symmetry between script and `upgrade.md`, and the full end-to-end pipeline against an installed daemon.

## Changes

### Added

- **Thin-shim skill `scripts/upgrade.sh`** (Plan 00109 Phase 2): Replaces the legacy ~280-line skill script with a ~23-line shim. Detects `PROJECT_ROOT` by walking up for `.claude/hooks-daemon.yaml`, fetches `${HOOKS_DAEMON_UPGRADE_BASE_URL}/${HOOKS_DAEMON_UPGRADE_REF}/scripts/upgrade.sh` (defaults to `raw.githubusercontent.com/.../main`), aborts loudly on `curl` failure, and execs the fetched script with `--project-root "$PROJECT_ROOT"` and any forwarded args.
- **`UPGRADE_METADATA` block emission in Layer 1** (Plan 00109 Phase 1): After a successful upgrade Layer 1 prints a machine-parseable block on stdout with 10 fields. The block goes to stdout AFTER all human-readable progress output so it is the last thing the agent sees.
- **Skill `upgrade.md` rewritten** (Plan 00109 Phase 3): Old 89-line user-facing guide replaced with a 56-line agent-facing workflow.
- **`tests/acceptance/test_upgrade_metadata_emission.py`**: Layer 1 alone emits the contract correctly against a fixture project.
- **`tests/acceptance/test_skill_upgrade_shim.py`**: Shim fetches and execs a stand-in script via `file://` fixture; aborts non-zero on fetch failure.
- **`tests/acceptance/test_upgrade_md_metadata_contract.py`** (4 tests): Symmetry between Layer 1 emission and `upgrade.md` references — every emitted field is mentioned in `upgrade.md`; every snake-case reference in `upgrade.md` exists in the contract; both sentinels mentioned; both files exist. Cheap (~0.03s, no subprocess).
- **`tests/acceptance/test_skill_upgrade_end_to_end.py`**: Full pipeline gate — shim → real Layer 1 → metadata against an installed daemon. Sets up fixture project, clones daemon, runs `install_version.sh`, builds `file://` fixture tree seeded from the cloned daemon dir (hermetic), invokes the shim, asserts exit 0, both sentinels on stdout, all 10 fields populated, `metadata["project_root"]` matches the shim's detected root (proves `--project-root` forwarding), `python_path` not `/usr/bin/`.

### Changed

- **`uv.lock` cleanup migrated upstream as git-aware block**: The skill's old indiscriminate `rm -f $DAEMON_DIR/uv.lock` is gone; the equivalent logic lives in Layer 1 and only removes untracked `uv.lock` files. In self-install mode (where `uv.lock` IS tracked), the tracked lockfile is preserved. Closes a footgun where the upgrade silently dropped a tracked lockfile.
- **`HOOKS_DAEMON_UPGRADE_REF` / `HOOKS_DAEMON_UPGRADE_BASE_URL` env vars**: New supported overrides for the shim. Defaults pull from `raw.githubusercontent.com/.../main/scripts/upgrade.sh`. Set `HOOKS_DAEMON_UPGRADE_REF=v3.15.0` to pin to a specific tag. Test suites use the base-URL override for `file://` fixtures.
- **`CLAUDE/development/RELEASING.md` Step 14 documents the inert `upgrade.sh` artifact**: The published `upgrade.sh` release asset is functionally inert (clients run the canonical script from `main` HEAD via the shim) but stays in `bootstrap-checksums.txt` for cross-symmetry with the three sibling self-bootstrap scripts. Plan 00109 Decision 4 records the rationale.
- **`markdown_organization` allows skill-source markdown**: Added `^src/claude_code_hooks_daemon/skills/.*\.md$` to `allowed_markdown_paths` so the handler stops blocking legitimate edits to skill source markdown.

### Fixed

- None.

### Removed

- **Six legacy skill-side integration tests**: `test_skill_python_version_precheck.py`, `test_skill_upgrade_aborts_on_network_failure.py`, `test_skill_upgrade_checksum_mismatch.py`, `test_skill_upgrade_handles_stale_uv_lock.py`, `test_skill_upgrade_recursion_guard.py`, `test_skill_upgrade_self_bootstraps.py`. These exercised behaviours that lived in the old skill `upgrade.sh` (self-bootstrap with sha256, Python pre-check, recursion guard). With the shim those either moved upstream (`find_compatible_python` in Layer 1; git-aware `uv.lock` cleanup) or no longer apply (no self-bootstrap on the shim — by design). Coverage restored with two additions to `tests/unit/install/test_upgrade_compatibility.py`.

### Security

- **`HOOKS_DAEMON_UPGRADE_BASE_URL` is a test override, not a production knob**: The default base URL is over HTTPS. Users overriding it bypass that trust boundary; the env var exists for the `file://` fixture pattern. The longer-term review of whether `raw/main` itself remains the right source (vs `releases/latest/download` with sha256, vs a pinned tag) is tracked in [gh issue #31](https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon/issues/31).

## Breaking Changes

None. This is a MINOR release. The user-facing CLI (`/hooks-daemon upgrade`) is identical. The only behavioural change downstream is that clients now pull the upgrade script from `main` HEAD on every invocation instead of running their frozen-at-release-time copy — which is the entire point of the refactor and the same flow `version_check` has been suggesting since v3.10.x.

The retired six skill-side integration tests covered internal behaviour of the OLD skill `upgrade.sh` (sha256 self-bootstrap, recursion guard, Python pre-check). No public API; no client-visible scriptable contract. Coverage restored elsewhere.

## Install / Upgrade

### Upgrading Existing Installations

```bash
/hooks-daemon upgrade
```

Or via the canonical hot-patch flow:

```bash
curl -fsSL https://raw.githubusercontent.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon/main/scripts/upgrade.sh -o /tmp/upgrade.sh
less /tmp/upgrade.sh
bash /tmp/upgrade.sh
```

After upgrade, parse the `<<<UPGRADE_METADATA` block from the output and write one atomic commit covering only daemon-owned paths. See `src/claude_code_hooks_daemon/skills/hooks-daemon/upgrade.md` for the 5-step agent workflow.

### Fresh Installations

```bash
git clone -b v3.15.0 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git
cd claude-code-hooks-daemon
./scripts/install.sh
```

### Pinning to v3.15.0 (paranoid users)

If you want every `/hooks-daemon upgrade` to fetch the upgrade script from a specific tag rather than `main` HEAD:

```bash
export HOOKS_DAEMON_UPGRADE_REF=v3.15.0
/hooks-daemon upgrade
```

**Step 12.1–12.5 skip rationale**: Per RELEASING.md Step 12 scope table, MINOR releases nominally require the full interactive suite. The skip here is justified because Plan 00109 contains **zero changes** in `src/claude_code_hooks_daemon/handlers/` — the entire refactor lives in shell scripts (`scripts/upgrade.sh`, `src/.../skills/.../scripts/upgrade.sh`), skill markdown (`src/.../skills/.../upgrade.md`), tests, and `CLAUDE/development/RELEASING.md`. No PreToolUse/PostToolUse/Stop/SessionStart handler dispatch logic changed, so the interactive playbook tests (which exercise hook dispatch via dangerous commands and verify deny/allow contracts) cannot regress.

- `test_upgrade_metadata_emission.py` — Layer 1 contract end-to-end.
- `test_skill_upgrade_shim.py` — shim fetch + exec + fetch-failure abort.
