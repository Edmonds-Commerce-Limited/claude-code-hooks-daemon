# Release v3.73.1 - Branch Pools, Admin-Seat Issue Takeover, arm64 Release Assets

**Release Date:** 2026-11-09
**Type:** Patch Release

## Summary

A patch release on the branch-hygiene line. Branches now sit in three pools (open, parked, merged) with their own caps and ages, a repository admin seat is no longer locked out by a non-admin's issue assignment, and releases ship attested arm64 relay and hooks-screen binaries. A run of field-report fixes (supervisor FIFO hang, all-digit SHA upgrade stop, `modified_files` scope, branch-creation guard, worktree-reap) rides along. Nine release-note callouts are folded into Highlights below, in the authors' own words.

## Read this first

- **No breaking change.** The release adds config keys only: `branches.parked.cap`, `branches.parked.max_age_days`, `branches.parked.mode`, `branches.merged.cap`, `branches.merged.max_age_days`, `branches.merged.mode` and `branches.bot_owned`. All have working defaults; no existing key changes meaning. There is no pre-upgrade task and no post-upgrade task, so the pre-deploy gate adds no stop of its own.
- **Config-changes:** `CLAUDE/UPGRADES/config-changes/v3.73.1.yaml` lists the seven new `branches.*` keys (parked and merged pools: `cap`, `max_age_days`, `mode`; and `bot_owned`, default `["dependabot/*"]`).
- **Truth-changes:** `CLAUDE/UPGRADES/truth-changes/v3.73.1.yaml` revises four statements in project docs:
  - **issue-sdlc:** an issue assigned to someone else is never claimed holds for a non-admin seat, and for any seat when the assignee is a repository admin. A repository admin seat may work an issue held only by non-admins (`issue-validity N` exits 0 with an advisory; `--claim` is a recorded takeover). If your project's docs say "never claim an issue held by someone else", make that conditional on the seat not being a repository admin.
  - **git-safety (parked):** a parked branch is in its own pool and no longer counts against `branches.wip.cap`.
  - **git-safety (merged):** a merged, undeleted branch is in the merged pool, and an unkept one denies branch creation until `branch-sweep --clean` removes it.
  - **git-safety (bot-owned):** branches matching `branches.bot_owned` are in no pool and are never cleaned.
- **Upgrade guide:** `CLAUDE/UPGRADES/v3/v3.73.0-to-v3.73.1/v3.73.0-to-v3.73.1.md`.

## Highlights

### Audience: client projects

#### a repository admin seat is no longer locked out by a non-admin's issue assignment

_Plan 00573 · Audience: client projects_

The assignment guard and `issue-validity` used to block any work tied to an issue assigned to another account, which also locked out a repository admin seat (an inactive non-admin assignee left an issue uneditable until a human reassigned it by hand). Now, when the signed-in account is a repository admin (read from GitHub) and every other assignee is a non-admin, the guard allows the work with an advisory naming the assignee and the takeover command, and `issue-validity N --claim` performs a recorded takeover: it switches the assignee to the admin, re-reads to verify the admin is the only assignee, and posts one short comment naming the previous assignee(s). The duplicate-work protection is unchanged for non-admin seats, an admin still respects another admin's assignment, and a permission that cannot be read never grants the override.

#### worktree-reap deletes merged branches safely, and running-agent holds match however the path is written

_Plan 00571 · Audience: client projects_

Two defects in v3.73.0's branch cleanup, both found in that release's own review and shipped as accepted known defects.

`worktree-reap --reap-branches` deleted a merged branch with a plain `git branch -d`, which refuses a branch merged into the default branch but never pushed to its own upstream, so that branch was skipped without explanation and the command still exited zero. It now deletes through the same path as `delete-branch`: the branch's containment is proven, its tip goes into a recovery bundle under `untracked/deleted-branches/`, and a branch it keeps is reported `KEPT` with the reason and makes the command exit non-zero.

The running-agent protection added in v3.73.0 (`branch-sweep --clean` and `worktree-reap` skip a worktree a `running` work-queue record names) compared worktree paths as written. A record holding a relative path, a trailing separator or a symlinked route to the same directory did not match, so that worktree could be cleaned while its agent was running. Paths are now compared after resolving them against the project root.

#### releases now ship attested arm64 relay and hooks-screen binaries

_Plan 00572 · Audience: client projects_

Each release now carries the relay and hooks-screen for both x86_64 and aarch64 (`hooks-relay-<triple>`, `hooks-screen-<triple>`), built natively on each architecture's GitHub runner, covered by one `SHA256SUMS` and attested with GitHub build provenance (`gh attestation verify <file> --repo Edmonds-Commerce-Limited/claude-code-hooks-daemon`). With `daemon.transport.relay_source: download` (or `auto` without a musl toolchain), an arm64 Linux host now downloads its own digest-verified relay instead of having to build it from source; any other architecture is still refused before anything is fetched. Building from source remains the first-class route.

#### branches now sit in three pools (open, parked, merged), each with its own cap and age

_Plan 00571 · Audience: client projects_

Parked and merged-but-undeleted branches no longer count against `branches.wip.cap`: each is its own pool with a cap (`branches.parked.cap`, `branches.merged.cap`, both defaulting to `wip.cap`) and a maximum age (defaulting to the dormancy preset's `block_days`), and branch creation is denied while a pool is full or holds a stale member (`R-BRANCH-PARKED-POOL`, `R-BRANCH-MERGED-POOL`), naming that pool's own way out. An unkept merged branch is cleanup debt at once; `branch-sweep --clean` clears it, and the new `branch-keep <name> --reason "<text>"` keeps one you still need for the merged pool's age, as a git note every clone sees. `branch-sweep --clean --remote` fetches those keeps first and refuses the remote half if it cannot, re-parking needs a new reason, and `branches.bot_owned` (default `dependabot/*`) branches are never counted or cleaned (reported as issue #165). A merged branch whose worktree is under `.claude/worktrees/` (Claude Code's own) is still skipped by `--clean`; its skip line now names `worktree-reap --reap --only <name>`, which removes the worktree first.

The creation guard makes one more git call to find merged branches, so the client-side wait `init.sh` allows a WorktreeCreate hook is now 90 seconds (was 85); a project that pins or wraps that wait should allow the extra five seconds.

#### the upgrade's `modified_files` lists only the files the upgrade changed

_Plan 00474 · Audience: client projects_

`UPGRADE_METADATA`'s `modified_files` used to name every uncommitted file in the project, so an upgrade run while another agent had work in progress listed that work too, and a gate that exempts listed paths as daemon-owned exempted it silently. The upgrade now records which files were already uncommitted, with a hash of each one's content, before it writes anything, and lists only paths it created, modified or deleted, including a pre-existing uncommitted file it then changed again. If you have been trimming `modified_files` by hand before pasting it into the upgrade commit, you can stop.

#### the ccy supervisor no longer hangs on a FIFO in a signal directory

_Plan 00474 · Audience: client projects_

The ccy supervisor globs its signal directories (goal, compaction, usage-pause, session-modes, standing-auth, session-actions, model-switch, model-downgrade, operator and context sidecars) and `/proc`, then reads each entry it finds. A FIFO there made the read block in `open` for ever, hanging the supervisor tick. Socket and device entries were opened the same way. Every such read now opens non-blocking and reads only when the descriptor is a regular file. Anything else is treated as an unreadable entry, as a malformed file already was. A client QA rule that flags directory walks opening non-regular files (fedora-desktop's walk-opens-non-regular-file, their issue #191) no longer finds instances in the deployed `.claude/ccy/claude-supervise.py`.

#### creating the default branch (or an exempt or protected name) is never denied by the branch cap

_Plan 00474 · Audience: client projects_

The branch creation guard allowed a name already in `refs/heads` (a reset or a checkout), but treated any other name as new open work. A checkout with no local copy of the default branch (a detached CI pull-request checkout, or a clone that deleted its local `main`) was therefore denied `git branch main origin/main` or `git checkout -b main` whenever the repository sat at `branches.wip.cap` or held a dormant branch. The default branch and any name matched by `branches.exempt`, `branches.integration_lines` or `branches.protected_names` are never counted as work, so creating one cannot raise the count the cap and dormancy judge, and it is now allowed.

#### upgrading to a commit whose short SHA is all digits is no longer stopped as a "MAJOR version change"

_Plan 00474 · Audience: client projects_

An upgrade that names a commit rather than a tag records the commit's short SHA as its target. When that SHA happened to contain only decimal digits (about 1.5% of nine-character SHAs, for example `965951009`), `upgrade_version.sh` and the pre-deploy gate read it as release 965951009, reported "MAJOR version change: v3.x -> v965951009.x" and stopped the upgrade with exit 3 until the reading was confirmed. A release is now recognised only when it is `v`-prefixed (`v4`, `v3.74.0`) or dotted (`3.74.0`); an all-digit ref is a commit ref like any other, and the gate reads the target's version from the checkout as it already did for a SHA with letters in it.

#### on an arm64 host, the transport probe now checks for the arm64 musl target

_Plan 00572 · Audience: client projects_

The transport probe's "musl toolchain present" answer asked `rustc` for the x86_64 target whatever the host was, so on an aarch64 Linux host it reported the toolchain missing when the aarch64 target was installed, and present when only the x86_64 one was. It now checks the host's own relay target (`aarch64-unknown-linux-musl` on arm64), the same target the build route already used. Found by the new non-blocking arm64 test job in CI.

## Installation

### New Installations

```bash
mkdir -p .claude
git clone -b v3.73.1 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon

# The installer builds the fingerprint-keyed venv, installs the package and
# starts the daemon. Never hand-build a venv: the resolver refuses the
# retired pre-v3.7.0 layout.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
git -C .claude/hooks-daemon fetch --tags

# Rebuilds the venv and reinstalls the package for the target version. Runs the
# target's own upgrade.sh: the installed one may predate the pre-deploy gate.
tmp="$(mktemp)"
git -C .claude/hooks-daemon show "v3.73.1:scripts/upgrade.sh" > "$tmp"
bash "$tmp" --project-root "$PWD" "v3.73.1"

.claude/hooks-daemon/bin/hooks-daemon restart
```
