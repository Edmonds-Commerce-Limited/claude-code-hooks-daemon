# v3.54.0 — The Daemon Stops Fighting Your Working Tree

Two defects in this release had the same shape: the daemon reaching into the
user's own working tree and taking something it did not need — a lock, or the
last word on a file's contents. Both are fixed. Alongside them,
`hooks-daemon delete-branch` gets four plans' worth of hardening from a client
field report, and `tdd_enforcement` finally gains a way to be told where a
project's tests actually live.

No breaking changes. No handlers added or removed (still 85 handlers across 13
event types).

## Fixed: the daemon no longer discards a concurrent `CLAUDE.md` edit

Observed in this repository. `CLAUDE.md` was written byte-identical to a
snapshot taken three minutes earlier, discarding a line added in between — and
the line was **outside** the generated `<hooksdaemon>` block, which a block
update has no business touching at all. The auto-commit then committed the
clobbered state, so the loss left no trace.

The existing `_is_user_content_preserved` check could never catch this. It
compares the snapshot the injector is holding against an updated value derived
from that *same* snapshot, so it validates the transformation while staying
structurally blind to the file moving underneath. The defect is the whole-file
read-modify-write, not the transformation.

Two writers had that shape and both are fixed:

- **`ClaudeMdInjector`** re-reads immediately before writing and, when the
  content has changed, recomputes the block replacement against what is on disk
  *now* — leaving every byte outside the block untouched. After three
  unreconcilable attempts it **declines to write**: a stale generated block is
  recoverable on the next restart, a discarded edit is not.
- **`markdown_table_formatter`** re-reads before its write and skips the
  rewrite rather than reverting newer content. No formatting is lost, because
  that newer write raises its own PostToolUse event.

## Fixed: the daemon no longer takes the git index lock it does not need

`git status` refreshes and **rewrites** `.git/index`. Three daemon paths were
therefore contending with your own git commands for the index lock:
`git_context_injector` on every user prompt, the `git_branch` status-line
handler on every status refresh, and the `CLAUDE.md` injector on every daemon
start.

Every git spawn now routes through one `run_git` in `utils/git_repo.py`, which
sets `GIT_OPTIONAL_LOCKS=0` and always carries a timeout. The `CLAUDE.md`
auto-commit stages with `git add` only when the file is untracked — one lock
instead of two in the normal tracked case. Lock contention is now logged at
WARNING with git's own stderr rather than at debug, so the next occurrence is
visible. An AST guard now covers all of `src/`, closing the 24 direct git
spawns across 12 files that previously bypassed the facade.

If you have seen stale `.git/index.lock` files in a project running the daemon,
this is why.

## Fixed: `delete-branch` hardening

Reported from a client repo against v3.53.1: `hooks-daemon delete-branch`
crashed with a raw traceback on a branch fully merged into `main` but one commit
ahead of its own remote-tracking ref — and `--dry-run` reported "merged —
nothing can be lost" while the real run deleted nothing.

The two halves were answering different questions. `classify_branch` proves
**ancestry to the protected ref** (is this recoverable?); `git branch -d`
enforces **merged into its own upstream, if it has one** (is this published?).
Rather than widen `merged` to force-delete, the release adds distinct tiers so
the verdict names which situation you are in:

| Tier                 | Meaning                                                                   |
| -------------------- | ------------------------------------------------------------------------- |
| `merged-unpushed`    | Merged into the protected ref, but ahead of its own upstream              |
| `merged-not-in-head` | Merged into the protected ref, no upstream, and not an ancestor of `HEAD` |

Both carry the *identical* ancestry proof to `merged` and both delete. Three
further fixes land alongside:

- **Object walks are no longer capped at the 5-second hook budget.** The
  `run_git` centralisation had imposed `Timeout.GIT_CONTEXT` on
  `git bundle create` and two `rev-list --objects` walks, so on a real repository
  the command raised a traceback instead of refusing. Now
  `Timeout.GIT_BRANCH_SAFETY` for walks and `Timeout.GIT_BUNDLE_CREATE` for the
  pack, and a git failure is reported as a refusal quoting git's own stderr.

- **A proof can now expire.** If a peer advances a branch between
  classification and deletion, the recovery bundle predates the new commit and
  does not cover it — so the command refuses that branch and names both shas.
  Re-run to reclassify against the current tip.

- **A same-named tag can no longer make the proof describe the wrong object.**
  A bare refname is ambiguous: git resolves `refs/tags/<name>` ahead of
  `refs/heads/<name>`, warning only on stderr. There are three refs the engine
  measures — the branch under test, `git_sync`'s merge base, and the protected
  ref itself — and all three are now qualified. The protected ref was the
  serious one, and it was found by this release's own review gate: with a tag
  named `main` present, every proof described the **tag** while the command
  acted on the **branch**, and a branch holding the only copy of a file was
  deleted. `--dry-run` reported the same wrong verdict, so the preview a human
  would check agreed with it.

  Read the severity carefully if you use `delete-branch` in a repository that
  tags releases with names that can collide with a branch. The mis-verdict is
  older than this release, but until now it produced tier `merged`, which
  delegates to `git branch -d` — and git's own ancestry check refused, quietly
  containing it. The two new tiers above return `--force` precisely to bypass
  that refusal, so **this release would have removed the net that was catching
  it**. The reproduction now reports `unproven`, refuses, and names the file
  whose content exists nowhere else.

## Added: three new config options

All opt-in. Nothing changes for a project that configures nothing.

Reported from a client monorepo whose PHPStan rules under a QA-tooling directory
are correctly classified production source, but whose test root is a flat PSR-4
namespace with no `src/` segment. Both mirror resolvers and the lowercase
`tests/` fallback missed it, so the deny message listed three locations none of
which was real — and no amount of moving the test could satisfy the gate.

```yaml
handlers:
  pre_tool_use:
    tdd_enforcement:
      options:
        # Declare where the tests live. test_dir is project-root-relative
        # (or absolute) and FLAT — the filename goes directly in it.
        test_path_map:
          - source_glob: "**/qaConfig/PHPStan/Rules/**"
            test_dir: "apps/app/qaConfig/Tests"
        # Or exempt paths entirely (prefer test_path_map — it keeps the gate ON)
        exclude_paths:
          - "generated/**"
  post_tool_use:
    lint_on_edit:
      options:
        exclude_paths:
          - "vendor/**"
```

`test_path_map` candidates are searched **first**, ahead of every inferred one,
and are deliberately not gated by `test_locations` — otherwise setting
`test_locations: ["collocated"]` would silently discard your own declared root.
A malformed entry is logged and skipped rather than raised, so one bad line
cannot disable TDD enforcement wholesale.

## ⚠️ Changed: `daemon.exclude_paths` now reaches two more handlers

**If your project already sets `daemon.exclude_paths`, this changes behaviour on
upgrade with no config edit of your own.** The project-wide glob list is now
honoured by `tdd_enforcement` and `lint_on_edit` as well as the content-scanning
blockers that already read it — so paths you excluded from content scanning now
also skip the TDD gate and lint-on-write.

For the usual contents of such a list — `vendor/`, generated code, build output
— that is the intended reading and needs no action. It is worth one look if any
glob was added for a narrow reason, because its exemption is now broader than it
was when written. To narrow it again, remove that glob from
`daemon.exclude_paths` and set it on the specific handlers that should still
skip it; every one of them keeps its own `exclude_paths`, and the sources are
additive with none overriding another.

## Also fixed

- **`recovery_cron_advisor` stacked a new hourly cron for every plan.** The
  creation advisory said "create a cron NOW" unconditionally, so a session
  touching several plans accumulated identical hourly crons. Both it and
  `background_process_tracker`'s watchdog advisory are now CronList-first:
  reuse an existing cron, delete extras, create only when none exists.
- **`run_git`'s "never raises" contract was false.** `text=True` decodes
  strictly, so a single invalid byte raised an uncaught `UnicodeDecodeError`
  that could fail daemon startup. Now decodes with `errors="replace"`.
- **A same-named tag could flip the gone-branch advisory's merged/not-merged
  verdict.** The base of the merged comparison was a bare refname, so a tag
  named after the default branch made git answer about the tag — and a branch
  holding unique commits was reported safe to delete. The advisory also named
  branches as `heads/<name>`, a string no git command accepts, so the
  `git branch -d` it offered failed as typed. A semgrep rule now flags
  `%(refname:short)` in git format strings.
- **`RELEASES/v3.53.0.md` documented a CLI subcommand that does not exist**
  (argparse rejects it with exit 2). Upgrading is reachable through the skill,
  so the words were right and only the form was wrong. A new
  `cli-subcommand-unknown` doc guard reads the live argparse registry to stop
  that class recurring.
- **CI is green on Python 3.11, 3.12 and 3.13 again** after 25+ consecutive red
  runs. Repository infrastructure only.

## Truth-changes

Three statements that were true at v3.53.1 and are false now. If your project's
own docs assert any of them, correct them:

1. `delete-branch` classifies into **four** tiers — it is now six.
2. Once a branch is proved safe, `delete-branch` deletes it — a proof can now
   expire, and an expired proof refuses.
3. `daemon.exclude_paths` exempts paths from **content scanning** only — it now
   also exempts them from the TDD gate and lint-on-write.

Run `hooks-daemon check-truth-changes --from 3.53.1 --to 3.54.0` for the full
`was → now` text.

## Upgrade

**In the Claude Code chat:**

```claude-code
/hooks-daemon upgrade
```

Optionally pass a target tag: `/hooks-daemon upgrade v3.54.0`. The default is
latest.

**From a terminal:**

```bash
.claude/skills/hooks-daemon/scripts/upgrade.sh
```

If the skill is not deployed in your project, fetch the canonical upgrader —
inspect before running, never pipe it to a shell:

```bash
curl -fsSL https://raw.githubusercontent.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon/main/scripts/upgrade.sh -o /tmp/upgrade.sh
less /tmp/upgrade.sh
bash /tmp/upgrade.sh --project-root /path/to/your/project
```

No config changes are required. Three new options are available (see above) —
check `hooks-daemon check-config-migrations --from 3.53.1 --to 3.54.0`. The
`daemon.exclude_paths` reach change is deliberately not a config migration
(there is no value to recommend); it ships as a truth-change — run
`hooks-daemon check-truth-changes --from 3.53.1 --to 3.54.0`.
