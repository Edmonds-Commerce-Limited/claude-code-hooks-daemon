# v3.26.0 — Minor: install/upgrade SSoT + KISS audit; plan workflow now opt-in

**Release date**: 2026-06-23
**Type**: MINOR release

## Summary

v3.26.0 remediates an Opus-run SSoT/KISS audit of the install/upgrade/deployment
system (Plan 00137), spawned after the v3.25.0 `mkplan` fix to hunt for
structural twins of the deleted `PLAN_WORKFLOW` bug: env-var gates orthogonal to
config, install-vs-upgrade asymmetries, and duplicated sources of truth.

The headline is the **promised follow-up to v3.25.0**: the plan workflow is now
**opt-in by default**. v3.25.0 made deployment derive from config but left the
model default `true`, so a stock install/upgrade scattered `CLAUDE/Plan/` +
`mkplan.bash` even though the plan handlers ship disabled. The default is now
`false`, matching the opt-in handlers — opting in is a single field. The rest of
the audit collapses duplicated authorities (Python floor, plan directory,
profile lists) to one source each.

## Highlights

- **Plan workflow is opt-in (Plan 00137, F-PLANDEF)** — `plan_workflow.enabled`
  defaults `false`; one field (`plan_workflow: { enabled: true }`) turns on both
  the planning handlers' directory feed and the `CLAUDE/Plan/` + `mkplan.bash`
  deploy. Legacy per-handler opt-in is preserved by config migration.
- **`plan_workflow.directory` is the single plan-directory SSoT (F-PLANDIR)** —
  dead duplicate `track_plans_in_project` entries removed from the example config.
- **Profiles documented as an install-time seed (F-PROFILE)** — the seed survives
  upgrade via the config-merge; no upgrade path re-applies a profile.
- **Python floor derives from `pyproject.toml` during install (F-PYFLOOR)** — no
  more hardcoded `3.11` that would silently accept a too-old interpreter at the
  next floor bump.
- **Install summary prints the real `$VENV_PATH` (F-VENVSUM)**; **profile lists
  validated against config keys (F-PROFLIST)**.

## Changes

### Changed

- **`plan_workflow.enabled` now defaults to `false` — opt-in (Plan 00137,
  F-PLANDEF)** — Matches the opt-in plan handlers; a stock install/upgrade no
  longer scatters `CLAUDE/Plan/` + `mkplan.bash`. Opting in is a single field
  (`plan_workflow: { enabled: true }`) that enables BOTH the directory feed and
  the deploy. Legacy clients that opted in via a per-handler
  `track_plans_in_project` option (no top-level block) are preserved by the
  config migration. The deploy is non-destructive — disabling never removes an
  existing `CLAUDE/Plan/`. Carries `config-changes`/`truth-changes` manifests.
- **`plan_workflow.directory` is the single source of truth for the plan
  directory (Plan 00137, F-PLANDIR)** — The registry already injects
  `track_plans_in_project` into planning-tagged handlers from the top-level
  `plan_workflow.directory`. The now-dead duplicate per-handler entries (one
  annotated "Must match markdown_organization setting") were removed from the
  example config; an integration guard forbids their reintroduction.
- **Handler profiles documented as a one-shot install-time seed (Plan 00137,
  F-PROFILE)** — `HANDLER_PROFILE` seeds the per-handler `enabled:` flags once;
  the yaml is the SSoT thereafter and no upgrade path re-applies a profile. A
  regression test proves a profile-seeded `enabled: true` survives the upgrade
  config-merge.
- **Python minimum derives from the `pyproject.toml` SSoT during install (Plan
  00137, F-PYFLOOR)** — `check_python3` raises the floor from `requires-python`
  and derives the `(X.Y+)` diagnostic from it; the bare `3.11` is only the
  floor-of-last-resort.

### Fixed

- **Install summary prints the real venv path (Plan 00137, F-VENVSUM)** — was the
  deleted legacy `untracked/venv/` literal; now the fingerprint-keyed
  `$VENV_PATH`.
- **Handler-profile lists validated against config keys (Plan 00137, F-PROFLIST)**
  — `apply_profile` warns on profile handlers absent from the target config, and
  a guard test asserts every profile handler name exists in the shipped example.

## Behaviour change — plan workflow is now opt-in

This is the follow-up announced in v3.25.0. `plan_workflow.enabled` now defaults
`false`, so a stock install/upgrade does **not** deploy the `CLAUDE/Plan/`
scaffold or `mkplan.bash`. To use the plan workflow, opt in with a single field
in `.claude/hooks-daemon.yaml`:

```yaml
plan_workflow:
  enabled: true
  directory: "CLAUDE/Plan"   # optional; this is the default
```

This one field enables BOTH the planning handlers' directory feed and the
deploy. If you opted in the **legacy** way — a per-handler
`track_plans_in_project` option under `markdown_organization` with no top-level
`plan_workflow` block — you are unaffected: the config migration still promotes
that into an enabled `plan_workflow`. Disabling is non-destructive; an existing
`CLAUDE/Plan/` directory is never removed.

## Upgrade

```
Use the hooks-daemon upgrade skill (Skill tool: skill=hooks-daemon, args=upgrade).
```

No config migration is required. If you relied on v3.25.0's deploy-by-default
behaviour, add `plan_workflow: { enabled: true }` to keep the plan workflow on.

## Installation

### New Installations

```bash
mkdir -p .claude && cd .claude
git clone https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git hooks-daemon
cd hooks-daemon
git fetch --tags && git checkout v3.26.0
python3 -m venv untracked/venv
untracked/venv/bin/pip install -e .
untracked/venv/bin/python install.py
cd ../..
```

### Upgrading Existing Installations

```bash
cd .claude/hooks-daemon
git fetch --tags
git checkout v3.26.0
untracked/venv/bin/pip install -e .
untracked/venv/bin/python -m claude_code_hooks_daemon.daemon.cli restart
```
