# Release v3.74.0 - The CLAUDE.md Block Stays on Its Home Branch

**Release Date:** 2026-11-10
**Type:** Minor Release

## Summary

The daemon now writes and commits the CLAUDE.md block only while HEAD is attached to a home branch, instead of onto whatever branch or detached HEAD the checkout happened to be on. Two optional config keys, `branches.home` and `branches.home_commit`, say which branches those are and whether the daemon may commit there. The release also carries a run of fixes from release-candidate field use: worktree removal beside regenerable dependency directories, `branch-keep` for same-tip siblings, a re-stamped reused venv, no stray settings backup, and a narrower `lsp_enforcement` match. Seven release-note callouts are folded into Highlights below, in the authors' own words.

## Read this first

- **No breaking change.** The two new config keys are optional and the config-changes manifest is not marked breaking. There is no pre-upgrade task and no truth-change.
- **One recommended post-upgrade task.** A project whose main checkout lives on a branch other than the default branch, or whose default branch only accepts pull requests, should set `branches.home` or `branches.home_commit`. See "Post-Upgrade Tasks" below.
- **Upgrade guide:** `CLAUDE/UPGRADES/v3/v3.73.2-to-v3.74.0/v3.73.2-to-v3.74.0.md`.

## Highlights

### Audience: client projects

#### the CLAUDE.md block is written and committed only on a home branch

_Plan 00594 · Audience: client projects_

At daemon start the main checkout used to write the `<hooksdaemon>` block into
CLAUDE.md and auto-commit it onto whatever HEAD was: a feature branch, a
detached HEAD (leaving a dangling commit), or a branch made only to get a
worktree removed. That is how the daemon created stray branches and commits on
its own.

The block is now written and committed only while HEAD is attached to a home
branch. By default that is the repository's default branch. On any other
branch, or on a detached HEAD, the daemon writes nothing, commits nothing and
logs at info level why, naming `regenerate-docs`. If HEAD or the default
branch cannot be named by git, it falls back to `init.defaultBranch` (only when
that branch exists or HEAD is unborn on it), then the
branch of an unborn HEAD (the block is written, no root commit is made), then a
sole local branch. If none resolves to a local branch, nothing is written and
the SessionStart notice tells the agent to set `branches.home`.

If a checkout lives on an environment, release or production branch for weeks,
declare it, because a configured list replaces the default:

```yaml
branches:
  home: [release-x]
```

`home` takes exact branch names; a glob such as `release/*` is rejected at load.

`regenerate-docs` still writes the block on request from any branch, but it
commits only on a home branch. Off home, the file is left modified for you to
commit deliberately. Linked worktrees are still left alone at startup.

For a home branch that only accepts pull requests, set `home_commit: false`.
The daemon then never writes CLAUDE.md on a home branch: a modified file there
would make the next `git pull` fail whenever an upstream change touches
CLAUDE.md. A stale block is reported at every SessionStart (recomputed each
time, so the notice goes once the block is current); run `regenerate-docs` in a
pull-request worktree or branch and commit the result there. On a home branch
under `home_commit: false`, `regenerate-docs` itself refuses and exits non-zero.

#### dependency directories beside a lock file no longer block worktree removal

_Plan 00594 · Audience: client projects_

Removing a merged branch's worktree was refused when it held a package
manager's install directories (`vendor/`, `node_modules/` and similar),
particularly ones nested several levels below the repository root beside
their manifest. They can be rebuilt, but a root-level name list could not
describe them.

An ignored directory now counts as regenerable when it sits beside a
manifest and lock file that are both committed at that location:

| Manifest         | Lock file                                          | Directory                                                                           |
| ---------------- | -------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `composer.json`  | `composer.lock`                                    | `vendor/`, `vendor/bin/` (or the manifest's `config.vendor-dir` / `config.bin-dir`) |
| `package.json`   | `package-lock.json`, `yarn.lock`, `pnpm-lock.yaml` | `node_modules/`                                                                     |
| `Gemfile`        | `Gemfile.lock`                                     | `vendor/bundle/`                                                                    |
| `Cargo.toml`     | `Cargo.lock`                                       | `target/`                                                                           |
| `pyproject.toml` | `uv.lock`, `poetry.lock`                           | `.venv/`                                                                            |

Only ignored, untracked content qualifies: a directory holding a committed
file, an unignored file, or no committed lock file still blocks, and
`untracked/scratch/` is never regenerable. The configurable list
`branches.cleanup_after_merge.regenerable` is unchanged and additive.

#### lsp_enforcement no longer reads `semgrep <name>` as a grep for a symbol

_Plan 00594 · Audience: client projects_

A Bash command that merely named a tool ending in `grep` or `rg` followed by an identifier-shaped argument, for example `llm_qa.py ... semgrep shell_check`, could be denied as a symbol search, even when the command's only real grep searched a text file. The pattern is now taken only from a `grep` or `rg` that starts a word, so an argument list is no longer mistaken for a search.

#### `hooks-daemon status` names the live commit after a branch install moves

_Plan 00594 · Audience: client projects_

When a guarded branch install moved to a newer commit whose `pyproject.toml` and `uv.lock` were unchanged, the existing venv was reused but kept the install stamp of the older commit, so `hooks-daemon status` and the version check reported a commit that was no longer live. Every venv reuse now rewrites the stamp with the version being installed, without rebuilding, and a stamp that cannot be written fails the install the same way a failed build does.

#### a branch keep lifts the merged-pool block for every branch at that tip

_Plan 00594 · Audience: client projects_

`branch-keep` records the keep as a note on the branch's tip commit, so every
branch name at that tip is kept, and `branch-sweep` reports them all kept. The
creation guard (`R-BRANCH-MERGED-POOL`) reads a per-name snapshot, though, and
`branch-keep` cleared the stale mark only for the name it was given. A
same-tip sibling, for example a `-parked` twin, stayed stale to the guard and
went on denying branch creation. Re-keeping the sibling with the same reason
was refused before the mark was cleared. Now a keep clears the stale mark of
every name at the kept tips, and so does a re-keep refused for repeating its
reason.

Workaround on earlier versions: re-keep the sibling with a new reason.

#### the worktree-removal deny says to delete ignored content in a separate command

_Plan 00594 · Audience: client projects_

When `git worktree remove` is denied because the worktree holds ignored content such as `untracked/scratch/`, the deny now says to look at those paths first: move anything worth keeping to a tracked home, delete what is disposable in a separate command, then retry the removal. The command is judged before any of it runs, so a delete chained in front of the removal (`rm -rf <worktree>/untracked/scratch && git worktree remove <worktree>`) never counts and stays denied; when the command does chain such a delete, the deny says that the chained delete is not counted. Modified and untracked files get no delete advice.

#### no stray `settings.json.bak-*` file when the merge changed nothing

_Plan 00594 · Audience: client projects_

The installer and upgrader copy `.claude/settings.json` to `.claude/settings.json.bak-<timestamp>` before merging it. When the merge then changed nothing, that backup was byte-identical to the live file yet stayed behind, showing up as an untracked path that blocked clean-tree checks and worktree removal. A backup identical to the merged result is now deleted; a merge that changes the file still keeps its backup exactly as before.

## Installation

### New Installations

```bash
mkdir -p .claude
git clone -b v3.74.0 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon

# The installer builds the fingerprint-keyed venv, installs the package and
# starts the daemon. Never hand-build a venv: the resolver refuses the
# retired pre-v3.7.0 layout.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
git -C .claude/hooks-daemon fetch --tags

# Rebuilds the venv and reinstalls the package for the target version. Runs the
# target's own upgrade.sh: the installed one may predate the pre-deploy gate.
tmp="$(mktemp)"
git -C .claude/hooks-daemon show "v3.74.0:scripts/upgrade.sh" > "$tmp"
bash "$tmp" --project-root "$PWD" "v3.74.0"

.claude/hooks-daemon/bin/hooks-daemon restart
```
