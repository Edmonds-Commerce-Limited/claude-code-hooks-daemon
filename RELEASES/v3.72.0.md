# Release v3.72.0 - Branch Hygiene, the Rust Relay by Default, Hardened Recovery

**Release Date:** 2026-11-04
**Type:** Minor Release

## Summary

A branch-hygiene, relay-by-default and hardening release. A new `branches:` config block and nine handlers keep branch work from piling up (a repository-wide WIP cap, a dormancy block, lossless forced removal, an evacuate-then-destroy deny, creator and touch records, a stop guard, post-merge cleanup and a `branch-sweep` report); the Rust relay is the default hook transport on Linux; a drifted venv is rebuilt and a daemon that cannot start no longer locks the session out; and `mkplan.bash` reads remote plan numbers before allocating. 33 release-note callouts are folded into Highlights below, in the authors' own words.

## Read this first

- **No breaking change.** `CLAUDE/UPGRADES/config-changes/v3.72.0.yaml` has `breaking: false`, so the pre-deploy gate adds no stop of its own for upgrades that cross this release. The manifest does carry `renamed` and `changed` entries, but each keeps working on an existing config: the renamed `branch_count_advisor` options are still read for one release, and an explicit `relay_enabled: false` is kept. No pre-upgrade task and no post-upgrade task ships.
- **Check for dormant branches before you upgrade.** A repository that already holds a branch idle for 30 days or more is blocked from the first session start after the upgrade: no new branch and no agent worktree until each such branch is merged, parked or deleted. Run `bin/hooks-daemon branch-sweep` first, or set `branches.dormancy.mode: warn`.
- **Declare `branches.integration_lines` and `branches.exempt`** (for example `release/*`, `users/*`, `gh-pages`) before the branch guards fire, or those branches are counted as work.
- **Two defaults change.** The Rust relay is the default transport on Linux (opt out with `daemon.transport.relay_enabled: false`), and `goal_loop_detector` defaults to `mode: act` (opt out with `mode: observe`). See the callouts below.
- **Commit the new `.gitattributes`** that install and upgrade write.
- **Upgrade guide:** `CLAUDE/UPGRADES/v3/v3.71.0-to-v3.72.0/v3.71.0-to-v3.72.0.md`.

## Highlights

Each change is described below in the words of the plan that made it. The branch-hygiene set (Plan 00558) is the largest part: the remote-delete guard, `branch-sweep`, post-merge cleanup, integration lines, WorktreeRemove, the creation guard, forced-removal and evacuation judgement, creator and touch records, dormancy and the stop guard.
#### the goal-loop detector no longer mistakes journal commits for progress, and reports a loop that persists

_Plan 00501_

The detector's repository fingerprint now hashes the committed tree by content, so a commit that touches only plan journals (or no file) no longer re-arms a loop; before, a stand-in's journal-only commit split one long goal loop into many `would-enter` records and, in `act` mode, would have ended the block. In `act` mode a loop is now entered once per fingerprint instead of on every threshold crossing (one goal clear and one notice, not several). A loop that stays latched or blocked now logs a `loop-persisting` transition every `persist_every_crossings` further crossings (new option, default 5) carrying its cycles, crossings and first-seen time, and the first one queues one line telling the agent to run `bin/hooks-daemon clear-goal`, journal why, and stop with the real blocker stated. Thresholds and the goal text are unchanged.

#### the goal-loop detector now acts by default, agents clear their own stuck goal, and a Blocked plan leaves the goal

_Plan 00501_

**Behaviour change: `goal_loop_detector` now defaults to `mode: act` (it was `observe`).** When a session keeps stopping on a goal the evaluator keeps rejecting, the detector now enters the `goal-blocked` session mode for `blocked_hours` and clears the goal (the ccy supervisor types `/goal clear` at its next idle), instead of only logging `would-enter`. The owner accepted a 64-hour, 1446-evaluation main-session loop as the trigger. To keep the old logging-only behaviour set `mode: observe` under `handlers.stop.goal_loop_detector.options`. Thresholds are unchanged. Without the ccy supervisor nothing types the clear, so a human must type `/goal clear`.

An agent may now run `bin/hooks-daemon clear-goal` itself when its goal cannot be satisfied: the first `loop-persisting` line and act mode's entry notice tell it to run that command, journal why, and stop with the real blocker stated. `clear-goal` retracts only that session's own goal; it ends no session mode and touches no plan.

A plan that moves to `Blocked` now drops out of the session's combined goal the way a retired plan does, and a goal whose plans are all Complete or Blocked is cleared. This is for the goal only: nothing is archived and the plan-QA terminal-status rules are unchanged.

#### a merge conflict can no longer brick a session through the daemon's hook files

_Plan 00552_

A merge, rebase or stash pop that conflicted on a hook stub or `.claude/init.sh` used to leave `<<<<<<<` markers in a bash script. The script failed to parse and exited 2, which Claude Code reads as a block, so every event was blocked, including UserPromptSubmit, and the session could not take a prompt.

Two changes close this, and both reach an existing client on its next upgrade:

- **Stubs fail open when `init.sh` does not parse.** Each deployed stub now runs a `bash -n` check on `init.sh` after the relay hot path and before sourcing it. If the file is broken, the stub exits 0 with a non-blocking message naming the file (JSON events carry it in `systemMessage`; the status line prints a display line; worktree-create writes it to stderr and exits 1). The check costs about 10 ms against a 3 ms bash spawn floor, and only hooks that miss the relay pay it. A stub that itself holds markers still cannot parse; the next change prevents that.

- **A managed `.gitattributes` block.** Install and upgrade now write (or update in place) a block in the project root `.gitattributes` that sets `-merge` for `.claude/hooks/**` and `.claude/init.sh`. A conflict on those files then keeps your side of the file intact with no markers, and git still reports the conflict. The block sits between `# BEGIN claude-code-hooks-daemon managed block` and `# END claude-code-hooks-daemon managed block` comment lines; your own lines outside it are never touched and a re-run changes nothing. **Commit the new `.gitattributes`.** `.claude/settings.json` is deliberately not covered, because it holds project-owned entries and `-merge` would silently drop a side of a real edit; use `reconcile-settings` to re-add missing registrations. The daemon repository's own self-install does not get the block.

- **New verb `repair-install`.** `.claude/hooks-daemon/bin/hooks-daemon repair-install` restores a broken install from a terminal, with no Claude session and no running daemon. It redeploys the hook stubs and `.claude/init.sh` from the installed daemon's templates (the installer's own generator, so the parse guard is included), runs `bash -n` on every one and reports each `OK` or `BROKEN`, and checks that `.claude/settings.json` parses. It exits non-zero while anything is still broken. `--check` reports without writing. `settings.json` is only ever rewritten with the explicit `--reconcile-settings` flag, and a file carrying conflict markers is never overwritten: resolve it by hand. The stub parse-guard message now names this command. See the recovery section of `docs/guides/TROUBLESHOOTING.md`.

If a conflict does leave a kept-ours stub or `init.sh` that is older than the merged branch, run `repair-install` (or re-run the upgrade) to redeploy them.

#### the supervisor top hat is green only for a session the supervisor oversees

_Plan 00553_

The status-line `supervisor_indicator` used to turn green for every session of a project as soon as any `claude-supervise` process was visible, so a session with no supervisor claimed an auto-compact safety net it did not have (reported as issue #140). A supervisor now counts for a session only when that session's id is in the environment of a process in the supervisor's own descendant tree, the same rule the supervisor applies to its own sessions. The status-file pid and the `/proc` scan are both held to it, and each session keeps its own cache. A session with no id, or whose ownership cannot be read, renders orange (a status file exists) or nothing, never green.

#### the automatic relay repair now starts when the daemon runs on a uv-managed Python

_Plan 00474_

When `daemon.transport.relay_enabled` is on and the relay binary is missing or cannot run, the session-start relay check starts a detached repair in the background. It started that process with `os.posix_spawn(..., setsid=True)`.

CPython builds installed by `uv python install` (python-build-standalone) lack `POSIX_SPAWN_SETSID`, so on those interpreters that call raised `NotImplementedError: posix_spawn: setsid unavailable on this platform`. Builds from the operating system's packages do not have this problem. The error was not an `OSError`, so the repair never started and the session-start check failed instead of reporting.

The repair process is now started through `subprocess.Popen` with `start_new_session=True`, which gives it its own session on every CPython build. Nothing to do on upgrade: a missing relay binary is repaired at the next session start.

#### probing a venv interpreter no longer leaves a stray `sleep` process behind

_Plan 00474_

When the daemon's launcher has no cached venv interpreter, it probes each candidate under a watchdog. The watchdog waits out a timeout with `sleep` and is cancelled as soon as the candidate answers.

About one probe in 25 could cancel the watchdog too early, after it had started its `sleep` but before it had recorded that process. The `sleep` then outlived the watchdog and stayed attached to PID 1 for the whole timeout, which can be many hours when `HOOKS_DAEMON_VENV_PROBE_TIMEOUT` is set high.

The watchdog now finds its `sleep` through the shell's job table, which holds it from the moment it starts, so no `sleep` survives. Nothing to do on upgrade. A stray `sleep` left by an earlier version can be killed safely.

#### the ccy supervisor's main-thread focus hold is now off by default

_Plan 00474_

The ccy supervisor has a focus hold. It stops typing anything while the main prompt may not have focus, for example after an Up arrow that could have moved into the sub-agent panel. The hold judges this from your keys alone, so it cannot tell a history recall (Up, then Enter at the main prompt) from panel navigation, and only Esc ends it. In live use one history recall left the supervisor holding every send for more than fifteen hours while the main thread plainly had focus.

The hold is now off unless you set `CCY_FOCUS_HOLD=1` in the ccy environment. It is host code, so relaunch ccy to pick up the change. A host started before the upgrade keeps holding until it is relaunched; press Esc to release a hold in the meantime.

#### the ccy supervisor can now read the screen to decide its focus hold

_Plan 00538_

With `CCY_FOCUS_HOLD=1`, the supervisor's focus hold used to rely on your keystrokes alone, so one history recall could hold every send for hours. A keystroke latch now only asks a new small Rust helper, `hooks-screen`, to render the terminal output and say which view is showing. Only a `transcript` or `panel-selected` verdict holds. A missing helper, a timeout or an `unknown` screen lets sends through.

Until real screen captures exist the helper recognises nothing, so the hold stays effectively off. To help build the recognisers, set `CCY_SCREEN_CAPTURE=1` alongside `CCY_FOCUS_HOLD=1`, open a sub-agent transcript once, and keep `untracked/supervise/screen-capture/`. Build the helper with `bash screen/build.sh`. Its renderer is the vendored `vt100` crate (checked into `screen/vendor/`, built offline and locked), because terminal emulation is a correctness problem; the relay stays std-only. This is host code, so relaunch ccy to pick it up.

#### the Rust relay is now the default hook transport on Linux

_Plan 00554_

Hooks now travel through the compiled Rust relay by default instead of the bash and python3 forwarder, which cuts the per-hook cost from tens of milliseconds to a few. The default depends on the host. A config with no `daemon.transport.relay_enabled` key resolves to relay ON where the host can run it and to the legacy transport everywhere else:

| Host            | Default | How the binary arrives                                 |
| --------------- | ------- | ------------------------------------------------------ |
| Linux x86_64    | relay   | downloaded from the matching release (digest-verified) |
| Linux aarch64   | relay   | built from source (needs a musl-capable `rustc`)       |
| macOS and other | legacy  | none; the relay is never built or downloaded           |

The install or upgrade provisions the binary (`relay_source` now defaults to `auto`: build when a musl toolchain is present, otherwise download where a release binary exists). The fallback ladder is unchanged: if the binary is missing or unusable, the call falls through to the legacy transport and the session-start check warns and starts a repair. On a host that cannot run the relay, an explicit `relay_enabled: true` is still honoured and warns, with `bin/hooks-daemon transport off` as the fix.

To keep the legacy bash and python3 transport, set `daemon.transport.relay_enabled: false` in `.claude/hooks-daemon.yaml`, or run `bin/hooks-daemon transport off`; an explicit `false` is always respected. Only `true` and `false` are valid values: `relay_enabled: null` is a config validation error. A config file the loader cannot read also falls back to the legacy transport. If the relay misbehaves on your host, opt out as above and report it on the issue tracker.

Two fixes ship with this change and also apply to clients who had already opted in to the relay:

- **bash 3.2 safety**: the generated forwarders and the relay guard no longer use bash 4-only constructs (`${v,,}` lower-casing, `read -N`), so they run on the bash 3.2 that macOS ships.
- **wrong-platform binaries**: a relay binary built for another OS or architecture (for example one copied from a different machine) is now detected as defective and removed, rather than left in the exec path; the install then provisions the right one or reports why it cannot.

#### a venv whose Python changed underneath it is now rebuilt instead of trusted

_Plan 00555_

A host or image update can change the system Python, for example from 3.11 to 3.13. The daemon venv's `bin/python` then runs the new version and can no longer see its own installed packages. Earlier versions still judged that venv usable because its interpreter ran, so every daemon start failed with `ModuleNotFoundError` and the automatic rebuild never fired.

Every venv check, Python and shell alike, now compares the `major.minor` recorded in the venv's `pyvenv.cfg` with the interpreter that will actually run. A venv that differs is treated as stale, so the normal hook bootstrap builds a fresh one for the current Python with no command needed. A new QA check, `venv_interpreter_trust`, blocks any code that trusts a venv interpreter without that comparison.

A daemon that cannot start no longer locks the session out.

- `hooks-daemon diagnose` runs with no venv and no daemon. It names any interpreter drift, the last build result and the fix, and prints the last 20 lines of that build's log.
- `hooks-daemon status` reports any stop that was let through while the daemon was down, giving the count, the most recent entry and the path of `untracked/.daemon-down-stops.log`.
- While the daemon cannot be reached, the fail-closed guard now allows a small read-only set:
  - Read of a project file;
  - plain `ls`, `cat`, `head -n`, `tail -n`, and `git log` (`git status` is excluded: it can rewrite the index and run a configured fsmonitor program);
  - `hooks-daemon diagnose`.
- Protected and quarantined files stay refused. So do the daemon's runtime outputs: payload captures, the verdict and stop-event logs, and `untracked/hook-errors.log`.
- A Stop blocked because the daemon is down is allowed on the third consecutive block, or at once when the stop declares `[awaiting-human]`. The same applies to a daemon that accepts the connection but then fails, and each sub-agent keeps its own count.

Nothing to do on upgrade. If a drifted venv from an earlier version is still in place, the first hook after upgrading replaces it. `bin/hooks-daemon repair` forces the rebuild if needed. The troubleshooting entry "Interpreter changed under the venv" in `CLAUDE/SELF_INSTALL.md` gives the manual diagnosis.

#### the config check now reports when idle compaction is switched off

_Plan 00557_

Claude Code 2.1.290 and later compacts a long idle interactive session just before its one-hour prompt cache expires, so the next turn does not re-read the whole context uncached. `hooks-daemon check` gains an "Idle Compaction" line that fails and names the cause when `idleCompaction` or `autoCompactEnabled` is false, or when `DISABLE_AUTO_COMPACT`, `DISABLE_COMPACT` or `FORCE_PROMPT_CACHING_5M` is set, in the shell or any settings file's `env` section.

At session start the daemon now also writes `idleCompaction: true` to `~/.claude/settings.json` when the key is absent, and announces it in the `CONFIG SYNC` line. An explicit `false` is your choice: it is reported by the check and never overwritten.

#### secret_file_guard no longer denies bare dotted words that are not files

_Plan 00556_

Addresses #145 and #143. The default `*.secret*` pattern matched any Bash token or authored-script word that merely contained `.secret`, so a setting key such as `app.secret.key` or a module-name string such as `logging.getLogger("pkg.x_secret_guard")` was denied as a read of a protected file.

A BARE dotted word (letters, digits, `_` and `-`, with at least one `.` and no `/`, and not starting with `.`, `~` or `$`) now counts as a mention only when one of these holds:

- it names a file that exists (relative to the command's working directories or the project root);
- it is in the protected-file index (a glob match, or the basename of an indexed file);
- it is the operand of a file-opening command or call: `cat`, `less`, `cp`, `source`, a redirect target, a `git` or `python`/`ansible` command, `open(...)`, `Path(...)`, and a module-shaped string passed to a call that opens files.

Newly allowed:

- a bare dotted token that is not a path, does not exist, is not indexed and is not a file-opening operand (for example `echo app.secret.key`, or `grep app.secret.key notes.txt`, where the first grep operand is a pattern);
- a module-name string handed to `import_module`, `find_spec`, `run_module`, `patch(` or `getLogger` in an authored script.

Still denied:

- any path (`./app.secret`, `conf/app.secret`, `~/x.secret`), any glob that reaches a protected file, and any variable;
- a bare name of an existing or indexed protected file, such as `cat app.secret`;
- a file-opening operand, including `open("app.secret")`, `Path("x.secret").read_text()` and a redirect target.

Residual risk, accepted by the owner: a file that does not exist, is not indexed and is read by a command outside the file-opening list is allowed.

Nothing to do on upgrade.

#### write_protected_paths no longer denies read-only commands under a wildcard-only glob

_Plan 00556_
_Reported as issue #141_

Three faults combined to deny read-only commands as "writes" when a `write_protected_paths` glob ended in a wildcard-only component, such as `protected/**`:

- **awk programs:** a comparison (`>=`, `>`), a regex alternation (`/a|b/`), `||` or a quoted `|` inside an awk program was read as an output redirect or pipe. Only real awk output now counts as a write:
  - `print`/`printf` to `>`, `>>` or `|`;
  - `"cmd" | getline`;
  - `system(...)`;
  - `-i inplace`.
- **Wildcard-only globs:** text the guard could not read precisely was reported as naming `protected/**` whatever it said. Such a glob now names text only when the text mentions its literal directory (`protected/x`, `./protected/x`, or an absolute path under it). A glob with no literal directory at all, such as a bare `**` or `*`, stays fail-closed.
- **Heredoc bodies:** brace enumeration ran over heredoc bodies, which bash never brace-expands, and a body with nested quoted braces overflowed it. A body that a data consumer reads (`cat > notes.txt <<'EOF'`) is now skipped. A body fed to a shell or an interpreter is still judged in full: `bash <<'EOF'`, `cat <<'EOF' | sh`, `python3 - <<'EOF'`.

Real writes still deny, including `echo hi > protected/x`, `cp a protected/x`, `awk '{print > "protected/x"}'` and a shell heredoc that writes into `protected/`.

Nothing to do on upgrade.

#### a trusted consumer command that redirects stderr with `2>&1` is no longer denied

_Plan 00556_
_Reported as issue #146_

`secret_file_guard` lets a trusted consumer name a protected file in flag position, because the tool reads the file itself and never prints it. An example is `ansible-playbook ... --vault-password-file <path>`. That exemption is voided when the command is compound.

Until now, any `&` counted as making the command compound, including the `&` inside a redirection operator. So the same command was allowed with `> out.log` and denied with `> out.log 2>&1`.

Redirection operators no longer void the exemption: `2>&1`, `>&2`, `&>file`, `&>>file`, `>&file` and `<&0`. The redirection's target is still judged, so these are still denied:

- `&> <protected path>`;
- `2> <protected path>`;
- a real background `&` followed by another command;
- `&&`, `;` and pipes.

Nothing to do on upgrade.

#### deny messages and advice name the daemon wrapper that exists in a client install

_Plan 00556_
_Reported as issue #147_

A client install keeps the daemon's command-line wrapper at `.claude/hooks-daemon/bin/hooks-daemon`, and has no `bin/` directory at the project root. Many deny reasons, fix lines, advisories and CLI hints named `bin/hooks-daemon`, the self-install form, so the command they told the reader to run did not exist on a client install. Examples:

- the secret guard's `secret-meta` suggestion;
- the "Full detail" pointer on every rule;
- the generated CLAUDE.md block;
- `clear-goal`, `usage-pause clear` and the remote-docs fix lines.

Every runtime message now names the wrapper for the install mode in use:

- `.claude/hooks-daemon/bin/hooks-daemon` on a client install;
- `bin/hooks-daemon` on a self-install.

A test now fails on any new bare `bin/hooks-daemon` string in runtime code outside a short allowlist of self-install-only sites. The messages baked into the generated hook forwarder are unchanged, because no install mode is known when they run.

Nothing to do on upgrade. The generated CLAUDE.md block picks up the client form at the next daemon restart.

#### a pattern-only grep is no longer denied just because another statement follows it

_Plan 00556_
_Reported as issue #144_

`secret_file_guard` already let a grep-family search through when the protected name was only the search pattern, because searching for a name does not open the file. That exemption was lost as soon as the grep was one statement of a compound command, so a search that was allowed alone was denied once `; echo done` followed it.

A compound command is now judged statement by statement. It is allowed only when every statement either carries no protected mention or is itself a grep search whose file arguments are not protected. `;`, `&&` and `||` separate statements, and so does a newline, provided the command has no heredoc.

Everything that could read the file is still denied:

- a later statement that names a protected file;
- a pipe into a reader, a background `&` or a subshell;
- a redirect into a protected path;
- a `-f` or `--file` pattern file;
- a pattern assigned in one statement and expanded in another, since expansion characters are still refused across the whole command;
- a multi-line command with a heredoc, or a newline inside quotes.

Nothing to do on upgrade.

#### a `sensitive_content` public-pattern deny no longer shows the matched text

_Plan 00514_
_Reported as issue #92_

A deny from a `public_patterns` entry used to end with `Matched: <the matched text>`. The reason is written to the session transcript, so a pattern written to catch a value by its shape (a labelled sort code, a reference number) repeated that value into the transcript.

The deny reason now names only the pattern and where it matched:

- `Write` and `Edit`: the file path and the line number;
- git metadata: the field (commit message, tag name, branch name, author identity, merge message);
- `gh`: the inline body, or the body-file path;
- a staged file at commit time: the path, as before.

The matched text, a snippet of it and the raw command line are no longer in the reason, and no log record holds the match. The secret word list already worked this way.

This reverses the earlier rule that public patterns are safe to name. Nothing blocks differently: every pattern that denied before still denies. Nothing to do on upgrade, but a pattern's `description` is still shown, so keep it generic.

#### a bare `**` is no longer denied as a recursive, dot-matching glob when your shell does not expand it that way

_Plan 00556_
_Reported as issue #142_

`secret_file_guard` used to read a bare unquoted `**` as a recursive glob that also matches hidden names. So `ls **` was denied whenever a protected file existed anywhere below the working directory, hidden directories included. Bash does not expand it that way unless `globstar` (recursion) and `dotglob` (hidden names) are on.

The guard now reads the Bash tool's shell snapshots in `<Claude config dir>/shell-snapshots/`. When EVERY readable snapshot records both options as off, a bare `**` is judged as bash's default expansion: like `*`, one level deep, no dot names.

The conservative reading stays in force when any of these holds:

- a snapshot records `globstar` or `dotglob` as on;
- a snapshot cannot be read, or does not record both options;
- there is no snapshot;
- the command itself runs `shopt` or `set -O`.

A literal protected path, and a glob that spells a protected file name, are denied as before. At most the 200 newest snapshots are read, and the verdict is cached until the directory or a snapshot changes.

Nothing to do on upgrade. If your profile turns `globstar` or `dotglob` on, nothing changes for you.

#### a stop that only mentions "waiting on the owner's decision" no longer declares you blocked on the human

_Plan 00474_
_Reported as issue #149_

The Stop handler's last legacy prose pattern used to arm the awaiting-human mode on any "waiting on/for the owner's (user's, human's) decision, input, response or answer". A stop that merely noted parked issues while other work remained (for example a CI run still going) was read as blocked-only-on-human, was denied for the missing stand-in cron, and would have silenced the failsafe and declared crons.

The pattern now requires "only", before or after the target: `waiting only on the user's decision`, or `waiting on human response only`. The advertised example in the generated guidance is `waiting only on the user's decision`.

Nothing to do on upgrade unless you relied on the bare phrase to arm the mode. In that case write `[awaiting-human]` after `STOPPING BECAUSE:`, which is the supported declaration and is unchanged.

#### the sub-agent context budget no longer doubles the context on a turn that used the advisor

_Plan 00474_
_Reported as issue #150_

On an assistant turn that used a server-side tool (the advisor), the transcript's top-level usage is the sum of the executor requests in `usage.iterations`. The context reader counted that sum, so a sub-agent at about 229k tokens was told it was at 456k, past the 300k soft budget, and handed off early.

Context is now read from the last `message` entry of `usage.iterations`; `advisor_message` entries are never counted. A turn without `iterations`, or with none of type `message`, is read from the top-level fields as before. The fix is in the shared reader, so `subagent_context_budget`, `resume_guard`, the session-load view and the spend ledger's context figures all get it. Spend totals (summed tokens) still use the top-level fields.

The soft advisory also stops saying "then stop" when `hard_tokens` is off: it now states that continuing is permitted and the handoff is advised, not required. With `hard_tokens` set the wording is unchanged.

Nothing to do on upgrade.

#### two `mkplan.bash` runs can no longer get the same plan number (Ubuntu 25.10+, and interrupted runs)

_Plan 00474_

`mkplan.bash` (and the repository's own `mkroutine.bash`) serialise plan-number allocation with a lock. Two defects let two runs hold it at once and get the same plan number.

**On Ubuntu 25.10 and later**, the lock was taken by running `mkdir` and trusting it to fail when the lock already existed. Those releases ship the Rust uutils coreutils as `mkdir`, and under a race two `mkdir` calls on the same path can both report success. Two agents running `mkplan.bash` at the same moment then both took the lock and both created the same plan number. The lock is now a file created by bash itself with an exclusive create (`set -C`, which opens with `O_CREAT|O_EXCL`), so it no longer depends on which `mkdir` is installed. The same fix covers the venv build lock's non-`flock` fallback in `scripts/install/venv.sh` (and its Python side in `hooks-daemon repair`) and the background-sync lock in `provision.sh`.

**On any system**, a run holding the lock that received Ctrl-C (SIGINT) or SIGTERM released the lock and then carried on: it created the plan folder, advanced the counter and exited 0, with no lock held. An interrupted run now releases the lock and exits (130 for SIGINT, 143 for SIGTERM) without creating anything after the signal.

The deployed `CLAUDE/Plan/mkplan.bash` is refreshed by the upgrade.

Nothing to do on upgrade. A lock left as a directory by the previous version is still honoured as held, so an old and a new run cannot both get in. If a timed-out run names a lock that no running `mkplan.bash` holds, remove it. If two plans already share a number, renumber one; if an interrupted run left a numbered folder with no `PLAN.md`, remove it. The next run takes the number after the highest folder on disk either way.

#### listing inside an existing plan folder is no longer denied as plan-number discovery

#### deleting many merged remote branches in one push is now judged within the dispatch budget

_Plan 00558_

`destructive_git` confirms each branch of `git push <remote> --delete a b c ...` against the remote's live tip with `git ls-remote`. It made one call per branch, so a 37-branch delete at about a second a call exceeded the handler's 20 s dispatch budget and was not judged at all (#153).

#### `hooks-daemon branch-sweep` reports every branch, and the SessionStart branch line now names unpushed work

_Plan 00558_

`bin/hooks-daemon branch-sweep` lists every local and remote branch by state, the actionable groups first: CONTAINED NOWHERE (commits no remote ref holds, with the `git push -u` that secures them), merged but not deleted (with the `bin/hooks-daemon delete-branch` command, which proves the merge again before it deletes), patch-equivalent, dormant (with age and where the commits live), live work, parked, and not yet classified (with the reason). It is a report: exit 0 whatever it finds, 1 only when it cannot run (not a git repository).

The `branch_count_advisor` SessionStart line is replaced by `branch_sweep`. It names a branch contained nowhere on every session start (new, resume, compact), and on a new session the dormant branches, the merged-not-deleted count and the open-work count when it reaches the cap. It is silent when there is nothing to report. The old key still works: `enabled: false` under `branch_count_advisor` silences the new summary, and its `max_open_branches` / `behind_main_threshold` options are read for one release while `branches.wip.cap` / `branches.sweep.behind_threshold` are unset, with a deprecation line until you move them.

#### a merged branch is cleaned up after the merge, and `branch-sweep --clean` deletes the rest behind a bundle

_Plan 00558_

A new PostToolUse handler, `cleanup_after_merge`, runs after a `git merge` into the default branch or an integration line. Each local branch named on the merge command is handled per `branches.cleanup_after_merge.mode`. The default `advise` prints the `bin/hooks-daemon delete-branch` command. `act` deletes the branch when the target holds every one of its commits and prints `git branch <name> <sha>`, the line that restores it. `off` is silent. It never removes a worktree: a branch checked out in one gets the `git worktree remove` and delete commands printed for you to run. A patch-equivalent branch is not deleted after a merge; it is pointed at `branch-sweep --clean`. The remote delete is printed, never run. A `--squash`, `--no-commit`, `--abort` or `--continue` merge is ignored.

`bin/hooks-daemon branch-sweep --clean` deletes every merged and patch-equivalent local branch in one batch, behind a recovery bundle under `untracked/branch-cleanup/`, and prints the `git fetch <bundle> ...` line that restores each branch. A linked worktree holding one of those branches is removed first, without `--force`, and only when it is clean and every ignored path in it matches `branches.cleanup_after_merge.regenerable`. That list defaults to the venvs, QA output, caches, `.claude/hooks-daemon/`, `*.egg-info/`, `untracked/.venv-bootstrap*` and `untracked/lsp-venv/`. `untracked/scratch/` always blocks the removal, and a config list that would cover it fails the load. `--clean --dry-run` prints what would happen and changes nothing.

On upgrade: run `bin/hooks-daemon branch-sweep --clean --dry-run` to see what a clean would remove. Set `branches.cleanup_after_merge.mode: act` when you want merged branches deleted automatically. If your worktrees hold other rebuildable ignored stores, add them to `regenerable`.

#### the remote-branch delete guard accepts branches merged into an integration line, and never deletes a line

_Plan 00558_

`destructive_git` allows `git push <remote> --delete <name>` only for a branch it can prove merged. It now also counts a branch whose remote-tracking tip is an ancestor of any `refs/remotes/<remote>/<line>` for a `branches.integration_lines` glob (for example `release/*`), not only of the default branch; the proof is one `git for-each-ref --merged` per target over all the named branches, so a 40-branch delete costs a fixed handful of local calls plus the single `git ls-remote` (#153).

It also refuses outright, whatever the proof and with a reason naming which, the default branch, an integration line itself, a `branches.exempt` name and a `branches.protected_names` name. The handler reads the top-level `branches:` block; with none, the model defaults apply (no lines, no exemptions, protected `main`, `master`, `develop`, `trunk`), so a remote `develop` that was deletable when merged is now refused.

#### WorktreeRemove no longer force-removes a worktree, and deletes its branch once merged

_Plan 00558_

The `worktree_remove` handler used to run `git worktree remove --force` on the path Claude Code named, which deleted every ignored file in it, `untracked/scratch/` notes included (#155), and it never deleted the branch. It now:

- removes only a path `git worktree list` names as a linked worktree, and only when nothing would be lost: no modified or untracked file and no ignored path outside `branches.cleanup_after_merge.regenerable`. Otherwise the worktree is left and the blocking paths are written to the daemon log;
- adds `--force` only when the worktree's HEAD is also held by another ref;
- then deletes the branch when it has the WorktreeCreate `<slug>-<8 hex>` name and the default branch or an integration line holds every commit, logging the `git branch <name> <sha>` restore line. Any other branch is left for `bin/hooks-daemon branch-sweep --clean`;
- skips and logs the remaining steps when its event budget runs out.

`worktree-reap`'s orphan pruning now also covers `<slug>-<8 hex>` branches, not only `agent-*`.

`branch-sweep --clean` and this handler share three fixes found by running the sweep on this repository: an empty directory (an empty `untracked/scratch/` included) is never a blocker, a `store/` glob also matches a symlink of that name (`untracked/lsp-venv`), and the `regenerable` default now lists `untracked/repair.log`, `untracked/repair.txt`, `.coverage`, `untracked/.python-cmd-cache`, `untracked/context-sidecar/`, `untracked/logs/`, `untracked/acceptance/` and `.CLAUDE.md.pre-inject`.

The SessionStart branch summary again names, on a new session, each work branch more than `branches.sweep.behind_threshold` (default 50) commits behind the default branch, within its existing line cap.

Nothing to do on upgrade.

#### a new branch is denied while the open work branches are at the cap

_Plan 00558_

The new `branch_creation_guard` PreToolUse handler (rule `R-BRANCH-WIP-CAP`) judges every git command that creates a branch (`switch -c/-C/--orphan`, `checkout -b/-B/--orphan`, `branch <name> [start]`, `worktree add -b/-B`, and a bare `worktree add <path>`) and every Agent dispatch with `isolation: "worktree"`. When the open work branches already number `branches.wip.cap` (default 10), the creation is denied; `branches.wip.mode: warn` only warns and `off` stops counting.

- Local and remote refs of one name, and branches at one tip, count once. The default branch, integration lines, protected and exempt names never count.
- A name already in `refs/heads` is a reset or a checkout, never a creation, so `checkout -B`, `branch -f` and switching to an existing branch are never denied. A name the shell builds (`$NAME`) cannot be read and is allowed.
- The deny lists every open branch with its age and worktree, merged and patch-equivalent branches first with their `bin/hooks-daemon delete-branch` command, ordered from the labels the SessionStart branch summary now writes to `untracked/branch-inventory/labels.json`.
- A new name that shares a stem or an issue number with an existing branch draws a warning naming that branch (`branches.duplicates.mode`); it never denies.
- WorktreeCreate applies the same verdict before its `git worktree add` and refuses the creation at the cap. Its event budget grows by two short git calls, so the `.claude/init.sh` client wait for WorktreeCreate is now 70 seconds.
- A git failure allows the creation with a "could not judge" line.

Enable it with `handlers.pre_tool_use.branch_creation_guard: {enabled: true, priority: 40}`.

#### a forced branch delete or worktree removal is allowed only when nothing is lost, and copying work out before destroying it is denied

_Plan 00558_

`destructive_git` now judges what a removal would lose instead of trusting a remote alone.

- `git branch -D` and `git update-ref -d refs/heads/<name>` are allowed when every named tip is reachable from ANY surviving ref: another local branch, a tag or a remote-tracking ref. Refs the same command deletes do not count. One `git rev-list <tips> --not --glob=...` call proves every tip at once. A denial names each branch with the number of commits it would lose. `branches.force_removal.mode: off` restores the remote-tracking-only check.
- `git worktree remove` is judged under the new rule R-GIT-WORKTREE-REMOVE-FORCE, with or without `--force`, because git deletes ignored files either way. It is allowed when every ignored entry matches `branches.cleanup_after_merge.regenerable`. A forced removal must also have a clean status and a HEAD that a surviving ref holds. A denial lists the paths that would be lost. With `branches.force_removal.mode: off` it is not judged.
- New rule R-GIT-EVACUATE-THEN-DESTROY: one command that writes a worktree's or branch's work to a file nothing tracks, then destroys that same worktree or branch, is denied. The copy is made with `git diff`, `format-patch`, `stash show -p` or `show`, through a redirect, `tee` or `-o`. The destruction is `worktree remove`, `branch -d/-D`, `update-ref -d` or `rm -r` of the worktree. The deny says to commit or push on the lane's branch, or to ask a human. `branches.evacuation.mode` is `block` (the default), `warn` (allow with the same text as context) or `off`.
- The same rule covers the destruction in a LATER command of the same turn. A new PostToolUse handler, `evacuation_recorder` (priority 41), records the worktree and branches of each evacuation in the session's spend-ledger state; `destructive_git` denies a `worktree remove`, `branch -d/-D`, `update-ref -d` or `rm -r` of recorded work under the same rule and mode. The main thread's turn is a counter that a new UserPromptSubmit handler, `evacuation_turn_marker` (priority 43), advances at each prompt, so a patch exported in an earlier turn never blocks later cleanup; a sub-agent's turn is its lifetime. The record keeps the current turn only, at most 50 evacuations.

Every one of these denials ends with the shared branch-limit principle.

Nothing to do on upgrade. Commands that used to be allowed and are now denied are commands that would have lost work.

#### branches record who created and who touched them, and WorktreeRemove trusts the record

_Plan 00558_

The new `branch_touch_recorder` PostToolUse handler writes two records into the repository's git config.

- **Creator**: after a git command creates a branch (`switch -c`, `checkout -b`, `branch <name>`, `worktree add`), once the ref exists and only when no creator is recorded yet, it writes `branch.<name>.hooksDaemonCreator` (`<session>:<agent>`, the agent empty on the main thread), `hooksDaemonCreated` (unix time) and `hooksDaemonRoute`. The WorktreeCreate event writes the same record itself with route `worktree_create`. An agent's first touch of a branch its own session's main thread made through WorktreeCreate binds the creator to that agent.
- **Touches**: a `commit`, `merge`, `rebase`, `cherry-pick`, `am`, `revert`, `reset`, `switch`, `checkout` or `pull`, and any Write/Edit/NotebookEdit, adds the session and agent to the checked-out branch's `hooksDaemonTouchedBy`, once per branch per session. A failed write is logged and never blocks.
- **WorktreeRemove** now deletes a merged branch when its creator route is `worktree_create`. Only a branch with no record at all is still judged by its `<slug>-<8 hex>` name, and a branch recorded with any other route is kept.
- The WorktreeCreate budget grows by three short git calls, so the `.claude/init.sh` client wait for WorktreeCreate is now 85 seconds.

Enable it with `handlers.post_tool_use.branch_touch_recorder: {enabled: true, priority: 40}`.

#### dormant branches now block new branches, and `branch-park` exempts one

_Plan 00558_

The branch creation guard now also enforces dormancy. While an unmerged, unparked branch is at the block stage (30 days idle under the default `standard` preset), creating a branch is denied with rule `R-BRANCH-DORMANT`; the deny lists the branches and the three ways out: finish and merge, park, or delete. A branch at the noisy stage (14 days) adds a context line to every allowed creation. `branches.dormancy.mode: warn` stops at the noisy stage and `off` disables the stages. Nothing else is denied, so commits, merges, pushes and deletes stay open.

- **Check before you upgrade.** A repository that already holds a branch idle for 30 days or more is blocked from the first session start after the upgrade: no new branch and no agent worktree until each such branch is merged, parked or deleted. Run `bin/hooks-daemon branch-sweep` first; anything listed as `block` under "Dormant" needs a decision. Set `branches.dormancy.mode: warn` if you cannot decide straight away.
- `bin/hooks-daemon branch-park <name> --reason "<text>"` writes an empty `Parked-Reason` commit at the branch tip without a checkout and pushes it with a plain fast-forward. A parked branch never trips a stage. `branch-park --clear <name>` writes an `Unparked` commit.
- `branches.dormancy.preset: strict` warns from 3 days and blocks at 7. It is never applied for you: `bin/hooks-daemon optimise-checklist` prints a non-scoring OPTIONAL line suggesting it to a project on the defaults, and the score is unchanged.
- The stages come from the SessionStart labels snapshot (`untracked/branch-inventory/labels.json`), so a branch ages as of the last session start; `branch-park` updates the snapshot at once.

#### stopping with branch work unfinished is now denied, three times at most

_Plan 00558_

Two new non-terminal handlers, `branch_stop_guard` (Stop, priority 9) and `branch_subagent_stop_guard` (SubagentStop, priority 12), judge the branches the stopping session or sub-agent touched, using the touch records.

- **Checks**: a dirty worktree, commits no remote holds, and a branch merged but not deleted. The deny names the branch, the failed check and the exact commands. The default branch and integration lines are skipped unless `branches.stop_guard.include_default` is set. A branch that has not moved since it was created (a sub-agent's worktree before its first commit) is not reported as merged.
- **Scope**: a sub-agent answers for its own branches. The coordinator answers for its own and for its sub-agents' unpushed and merged-but-present branches, not their dirty worktrees. `branches.stop_guard.unpushed_subagent` (`block`, `advise`, `off`) sets how a sub-agent's unpushed commits are treated.
- **Gives way**: after three denied stops the guard allows the stop and records the branches as abandoned in the session's spend-ledger state. A live usage pause, a recorded release, or a git failure also allows the stop. An agent past its hard context budget skips the merged check and the deny lists each branch with its tip sha for the handoff.
- **Noisy line**: at a main-thread stop, at most once an hour per session, a non-blocking line lists branches at the noisy dormancy stage or later.
- `branches.stop_guard.mode` is `block` (default), `warn` or `off`.

Enable them with `handlers.stop.branch_stop_guard: {enabled: true, priority: 9}` and `handlers.subagent_stop.branch_subagent_stop_guard: {enabled: true, priority: 12}`.

#### mkplan now fetches before allocating, so two clones stop taking the same plan number

_Plan 00562_

`mkplan.bash` and the daemon's plan numbering now consider the plan folders other clones have pushed, not just the local counter and disk.

- **What changes**: before allocating, `mkplan.bash` fetches the default remote (`origin`, else the first remote) within the 30 second fetch budget, reads the plan folder names on every remote branch (the plan root, `Completed/` and `Cancelled/`) without a checkout, and allocates above the highest of counter, disk and remote.
- **Read-only**: it never pushes. The fetch happens before the scaffold lock is taken.
- **Offline**: with no remote, a failed fetch, or a timeout, allocation falls back to the local answer and prints `remote could not be checked` on stderr once.
- **Only mkplan fetches**: hooks run under a 5 second handler budget and perform no network I/O. The daemon's `next_plan_number_for_target` applies the same rule by reading the remote-tracking refs already fetched (by `mkplan.bash`, a session-start sweep or your own `git fetch`), never fetching itself. The check that validates a hand-created `PLAN.md` stays local.
- **Unchecked remote**: on the daemon side the fallback and its reason, including git's own error text, are logged as a warning. If any remote branch's tree cannot be listed, both scanners treat the remote as unchecked.
- **Known limit**: nested archive folders below `Completed/` and `Cancelled/` are not read on the remote.

Run `bin/hooks-daemon upgrade` (or redeploy plan workflow) to refresh the deployed `CLAUDE/Plan/mkplan.bash`.

This release is not breaking (`breaking: false`, no pre-upgrade task, no post-upgrade task). Its `renamed` and `changed` manifest entries all keep working on an existing config, and the manifest sets `breaking: false` so the pre-deploy gate lists nothing under `READ THIS FIRST` for upgrades that cross this release. See `CLAUDE/UPGRADES/v3/v3.71.0-to-v3.72.0/` for the upgrade guide and the callouts behind the Highlights, and `CLAUDE/UPGRADES/config-changes/v3.72.0.yaml` for the added, renamed and changed keys. Before upgrading a repository with old branches, run `bin/hooks-daemon branch-sweep` (see "Read this first").

## Installation

### New Installations

```bash
mkdir -p .claude
git clone -b v3.72.0 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon

# The installer builds the fingerprint-keyed venv, installs the package and
# starts the daemon. Never hand-build a venv — the resolver refuses the
# retired pre-v3.7.0 layout.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
git -C .claude/hooks-daemon fetch --tags

# Rebuilds the venv and reinstalls the package for the target version. Runs the
# target's own upgrade.sh: the installed one may predate the pre-deploy gate.
tmp="$(mktemp)"
git -C .claude/hooks-daemon show "v3.72.0:scripts/upgrade.sh" > "$tmp"
bash "$tmp" --project-root "$PWD" "v3.72.0"
# Exit 3: read what it lists, then re-run with the --skip-reading-confirmation=<digest> it printed.

.claude/hooks-daemon/bin/hooks-daemon restart
```
