# Release v3.70.0 - Faster Start-up, Venv Hygiene, Sharper Guards, No Upgrade Approval Stop

**Release Date:** 2026-10-17
**Type:** Minor Release

## Summary

A start-up-speed, venv-hygiene and guard-precision release. The pre-deploy upgrade gate loses its project-owner approval stop, the daemon binds its socket before non-essential start-up work and parses its config once, venvs are judged by one staleness rule and the ones it cannot prove stale are surfaced, sub-agent spend and model tiers are measured and advised on, and a new opt-in `write_protected_paths` handler keeps listed files read-only for agents. 82 release-note callouts are folded into Highlights below, in the authors' own words.

## Read this first

- **The upgrade owner-approval stop is gone.** There is no exit 4, no `approve-upgrade` command and no `upgrade_approval_guard` handler. What used to need approval is listed first under "READ THIS FIRST" in the reading the gate already stops on. See [BREAKING CHANGES](#%EF%B8%8F-breaking-changes) and the upgrade guide.
- **`prune-venvs --all-except-current` is removed.** Use `prune-venvs --stale`.
- **Config-changes manifest.** `CLAUDE/UPGRADES/config-changes/v3.70.0.yaml` has `breaking: false`, so the pre-deploy gate adds no stop of its own for upgrades that cross this release. No pre-upgrade task ships. A truth-changes entry, `CLAUDE/UPGRADES/truth-changes/v3.70.0.yaml`, records the changed upgrade-gate description.
- **Start-up budget gate (Step 8b) passed:** median 0.74 s of CPU before the socket binds, against a 2 s budget.

## Post-Upgrade Tasks

After upgrading, review `CLAUDE/UPGRADES/v3/v3.69.0-to-v3.70.0/post-upgrade-tasks/` - it contains 3 tasks that may require action in your project: clear unproven venvs (recommended), commit `daemon.expected_version` and `.claude/provision.sh` (recommended), and tune the plan fact-checker (optional).

## Highlights

Each change is described below, grouped by audience.

### Everyone

#### The defences listing carries defect classes, and more denials print an identifier (Plan 00484)

`hooks-daemon defences --json` now lists only the content and commit gates, which are the Defence Before Fix Defences, with a `defect_class` on every row, so the row count drops sharply (about 135 rows to about 30 in this repository) and a script that counted rows or looked a rule up there must use `explain-rule --list` for the full set. A project handler drops out of the listing unless it declares a `defect_class`, a member of the closed `DefectClass` enum (see CLAUDE/HANDLER_DEVELOPMENT.md); the post-write linters (`lint_on_edit`, `validate_eslint_on_write`) and `tdd_enforcement` are not Defences, while `staged_lint_gate` and `github_auto_close_keywords` are. `explain-rule` and `explain-handler` say whether a rule is a Defence or a guardrail instead of calling every rule a defence. Five more handlers (`dispatch_declaration` in strict mode, `subagent_report_size_blocker`, `subagent_report_path_verifier`, `cron_stop_enforcer`, `cron_subagent_stop_enforcer`) print a `BLOCKED [R-...]` identifier, as do the fail-closed denies of `destructive_git` (new `R-GIT-DESTRUCTIVE-UNREADABLE`), `sensitive_content`, `staged_lint_gate`, `conflict_marker_commit_gate`, the three remote-docs gates, `usage_pause_stop_gate` and the `auto_continue_stop` stand-in block (new `R-STOP-STAND-IN-MISSING`). `explain-rule` resolves the plan-QA and docs-QA check IDs such as `plan-doc-size`, and `explain-rule --list` ends with a line pointing at `explain-rule <ID>`, so a script that reads that listing as tab-separated rows should skip its last line. The generated CLAUDE.md block also ends each promoted handler's section with an `IDs:` line.

#### The QA runner checks suppression reasons, runs detectors first and explains rule IDs (Plan 00484)

`llm_qa.py` gains a gate, `inline_suppressions`, that fails any inline `nosec`, `noqa` (including the file-wide `ruff: noqa` and `flake8: noqa`), `type: ignore`, `nosemgrep`, `pragma: no cover`, `shellcheck disable`, `pyright: ignore`, `mypy: ignore-errors`, `mypy: disable-error-code` or `pylint: disable` that carries no reason (on the line, in the same comment, or in the comment block directly above that names the suppression's rule code or tool, or opens with `SECURITY:`), so a contributor who keeps a suppression must now say why; there is no baseline file. The `qa_suppression` write-time guard now also blocks `mypy: disable-error-code`. Every static detector now runs before the test suite and the other runners, and a runner that passes after a detector has failed is marked `NOT MEANINGFUL: detector failed` and left out of the pass count (every tool still runs; a runner that failed stays a failure), so a green `tests` line beside a red detector no longer reads as a pass. A failing tool's summary now names its first five findings with their rule IDs and the absolute path of the full report, `llm_qa.py --explain <ID>` prints what any `scripts/qa` rule ID means and how to fix it (`--explain` alone lists them), and `check_magic_values.py`, `audit_error_hiding.py` and `audit_shell.py` accept `--path FILE` to judge one file.

#### Fewer false denies from guards that matched text a command only mentions (Plan 00483)

The threat-model conformance audit checked every blocking guard against the careless-not-hostile threat model and narrowed the ones that denied ordinary commands. `destructive_git` and `git_stash` now judge each command segment by its own tokens, so a quoted search pattern, a `gh` body heredoc or a printing `while read` loop that names a destructive git command is read as data. `curl_pipe_shell` and `worktree_file_copy` judge what actually runs, reading shell wrappers word by word, and `root_recursion_guard` judges a command's scan root rather than every word in it. A git global option (`-C`, `-c`) with a quoted or escaped value no longer hides the subcommand after it.

The false positives the audit found but did not fix here are open entries in the niggles ledger (Plan 00474). Nothing to do on upgrade.

#### An upgrade keeps running the opt-in handlers that were running before it (Plan 00474)

When a rule change would stop opt-in handlers that your project was running, `upgrade.sh` now writes `enabled: true` for each of them into `.claude/hooks-daemon.yaml`. It edits the file as text (comments, layout and line endings are kept) and replaces it atomically; the summary then names each restored handler, says why, and how to undo it: set the handler's `enabled: false`, or delete its block.

**The restored handlers do not run until the daemon is restarted.** This step runs after the upgrade has already restarted the daemon, so the running daemon and the guidance it generated at that start still have them off. The summary prints a `RESTART THE DAEMON` warning with the command (`.claude/hooks-daemon/bin/hooks-daemon restart`); run it, then review the handlers it kept and disable any you did not want.

Nothing is written, and the summary prints the YAML to add by hand as before, when the file cannot be edited safely: an unusual layout, a permission error, a failed write, or a config you list under `write_protected_paths`. An older target that does not know `--apply` produces the same report without the write.

Also: `.claude/fake-values.yaml` is pre-filled with visibly fake examples for the kinds docs are likely to need, and the docs QA check `unlisted-fake-value` reports any registry entry that does not look obviously fake.

#### A `$` spend-limit chip, and an opt-in commit block for the fake-values registry (Plan 00474)

Behind a Claude apps gateway that sets you a spend limit, Claude Code's Status payload carries `rate_limits.spend_limit`. The status-line usage segment now shows it as a `$` chip beside the 5h and 7d chips (`$5%`, or `$ 62% 3h 0m` once it passes the warning level), in the same colour bands. The percentage is not capped at 100, so an exceeded limit reads `$ 140%` on red; a value above 10000 is treated as malformed. The chip is hidden when the field is absent or malformed, and the usage ceiling and pause gates still look only at the 5h and 7d windows.

The docs QA check `unlisted-fake-value` now also runs at the commit gate. It denies a commit that adds a `.claude/fake-values.yaml` entry which is not visibly fake (the word `fake`, or one character repeated eight times), or that stages a registry which cannot be parsed. Entries already in HEAD are not blamed on the commit.

**Other projects must opt in to the block.** The check ships advisory. To get the denial, set it in `.claude/hooks-daemon.yaml`:

```yaml
documentation:
  qa:
    check_modes:
      unlisted-fake-value: block
```

This repository sets it already. Without the key the same finding is shown as advisory context at commit time.

#### Stop re-entry with an unreadable transcript is allowed, and fewer inline-code advisories (Plan 00474)

Three guard changes from the niggles ledger. A Stop on a re-entry whose transcript cannot be read (no path, a missing file, a directory or a permission error) is now allowed by auto-continue, instead of being treated as a fresh stop and blocked again; this keeps the daemon to one block per chain and below Claude Code's 8-continuation cap (N411). A readable transcript with no block marker is still treated as a fresh stop.

The sub-agent full-QA guard no longer raises the unrecognised-interpreter inline-code advisory for `ps -e`, `file -e`/`-c`/`-r`, or `docker run -e`/`podman run -e` (and `exec`, `create`) when the flag comes before the image. Words after the image are still judged, so `docker run IMG sh -c '...'` is still flagged (N419).

The conflict-marker commit gate stays fail-closed when it cannot place the repository, and its deny now names the forms it accepts for reaching the project root: `cd "$(git rev-parse --show-toplevel)"`, `cd "$PWD"` and `cd "$(pwd)"` (N402). Nothing to do on upgrade.

#### A substituted test interpreter no longer trips the upgrade guard, and retiring an archived plan keeps the live goals (Plan 00474)

The upgrade-approval guard (`R-UPGRADE-APPROVAL-ENV-BYPASS`) denied a plain test run whose interpreter was a command substitution, such as `PYTHONPATH=<src> $(ls -d venv-*/bin/python) -m pytest tests/...`. It split the substitution at its spaces, took the tail for a script it could not read, and counted that as the upgrade because `PYTHONPATH` steers. The program word is now read whole. A substituted interpreter given `-m <module>` (attached, as in `-mpytest`, or separate) is judged by the module, as a `$PY` variable already was, and the command inside the substitution is checked for the upgrade as well. Real bypasses stay denied: an upgrade script run through a shell, a substituted program that is itself the upgrade, a computed script, module or `-c` program, and the daemon's own `-m claude_code_hooks_daemon...`.

When a plan's PLAN.md sits under `Completed/`, the goal handler now reads the live plans from the plan root, not from `Completed/`. Previously a retirement refresh given an archived path found no live plan and cleared every owner's `/goal`. Writes under `Completed/` are not matched by the handler, so this closes a latent path rather than a reproduced one.

`TeammateIdle`, `TaskCreated` and `TaskCompleted` are now events on which a handler `scope` of `MAIN` or `SUB` is accepted, as their contracts declare `agent_id`. No handler changes behaviour: the default scope is still `ALL`.

#### An upgrade no longer waits for the project owner's approval, and a large jump gets advice to go in phases (Plan 00503)

The pre-deploy upgrade gate had two stops: the reading confirmation (exit 3) and, for a breaking upgrade, the project owner's approval (exit 4), given in their own terminal with `hooks-daemon approve-upgrade`. The owner ruled the second one friction with no safety value: the threat model is a careless agent, not a hostile one, and an installed daemon older than the gate has no `approve-upgrade`, so a project could be stuck behind a long pipeline command just to say yes.

The approval tier is removed. There is no exit 4, no `upgrade-approvals/` marker, no `approve-upgrade` command (and no `approve` form of the standalone gate), and no `upgrade_approval_guard` handler with its rules `R-UPGRADE-APPROVAL-AGENT` and `R-UPGRADE-APPROVAL-ENV-BYPASS`. A config that still names `upgrade_approval_guard:` keeps validating; the key is retired, so it is accepted silently. Delete it when convenient.

What used to need approval - a MAJOR bump, a crossed config-changes manifest declaring `breaking: true`, a `critical` pre-upgrade task found in the project, or an installed version the gate cannot read - is now listed first, under "READ THIS FIRST: this upgrade is likely to break the project", in the same listing the reading confirmation already stops on. Read it, carry out the pre-upgrade tasks it names, and re-run the upgrade with `--skip-reading-confirmation=<digest>`; that is the whole gate. The reading confirmation itself is unchanged.

A large jump - one that crosses a MAJOR boundary, or spans more than ten minor releases - now also prints `ADVICE:` to upgrade in phases, naming an intermediate release (the last release of the current major, or one near ten minors ahead). It is advice only: it never stops the upgrade, changes the digest or sets an exit code.

An upgrade runs the gate from the TARGET release's code, not from the installed daemon's, so a project upgrading from 3.68 or 3.69 to this release meets no approval stop. Only an upgrade whose target is still 3.68.0 or 3.69.0 prints the old approval stop; move the target to this release or later instead of running `approve-upgrade`.

The gated-install receipt now lives in `untracked/upgrade-gate/gated-install.json` (it was under `upgrade-approvals/`). A project that had one is asked for the reading once on a same-version re-run that claims the target is already installed; its first upgrade through this gate records the new receipt.

#### The markdown formatter honours `exclude_paths` and leaves nested git checkouts alone, and its advisory no longer understates what it changed (Plan 00509)

The PostToolUse handler `markdown_table_formatter` formats the whole of every `.md` file it is given, and that does not change. What changes is its reach and its report. It now honours its own `handlers.post_tool_use.markdown_table_formatter.options.exclude_paths` and the project-wide `daemon.exclude_paths`, so generated or hand-formatted markdown can be opted out. A `.md` file inside a nested, separately versioned git checkout below the project root (a vendored clone or a submodule) is no longer rewritten, as `format-markdown` already did since Plan 00429; a linked worktree of the same repository is still formatted. The advisory used to say "aligned table pipes" even when bullet markers, blank lines or escaping had changed too: it now names the known changes only when they account for the whole diff, and otherwise says "Reformatted the whole file (mdformat)" (reported as issue #79).

#### The docs QA edit-time lint skips nested git checkouts and gitignored files (Plan 00510)

The write-time docs QA lint (`docs_qa_edit`) and `docs-qa --lint` now leave out two kinds of file they used to judge. A `CLAUDE.md` inside a nested, separately versioned git checkout below the project root (a vendored clone, a submodule, or a linked worktree of another repository) is no longer held to this project's module-doc budget, and neither is a file the project's `.gitignore` excludes, which is what the sweep already did. `docs-qa --lint` now refuses such a file as "not a documentation file". This repository's own linked worktrees stay in scope, and so does any file git cannot judge (the project is not a git repository, or git is unavailable). The cost is one `git check-ignore` for the one path per documentation edit, about 2 ms (reported as issue #80).

#### The deny text no longer claims batched tool calls were cancelled (Plan 00511)

Every PreToolUse denial used to end with "Any tool calls batched with this one were CANCELLED", and the `lint_on_edit` and `validate_eslint_on_write` guidance said the same about sibling calls. That has been false since Claude Code 2.1.161, which answers each parallel tool call on its own: a denied Write sat beside a Bash call that ran. An agent that believed the text re-issued work that had already happened, such as a commit. The suffix now says batched calls "may ALREADY HAVE RUN" and to check their results before re-issuing anything, and it still ends with "adapt and continue". The two linter handlers' guidance and the handler-development guide say the same (reported as issue #81). No handler's decision changed.

#### The worktree events get a budget longer than their git call (Plan 00512)

A `git worktree add` that took more than about 20 seconds, for example behind a slow `post-checkout` hook, used to get no path back: the chain deadline (20s) and the client's socket wait (30s) were both shorter than the handler's own 30s git budget, so Claude Code saw a failed worktree creation while git went on to create the worktree and branch as orphans. WorktreeCreate and WorktreeRemove are not guards, so they now have their own budget in `Timeout.EVENT_HANDLER_BUDGET`, `EVENT_CHAIN_DEADLINE` and `EVENT_CLIENT_WAIT`: the chain deadline is 55s for create and 65s for remove, and the client (`init.sh` and the relay forwarder) waits 60s and 70s. A failed or timed-out add is also undone: the worktree and the branch that call created are removed, and a branch that already existed is left alone. Every guard event keeps the 20s deadline, and `daemon.chain.deadline_seconds` still sets it (reported as issue #82).

#### The conflict-marker gate scans only what the commit records (Plan 00474)

On a large repository under load, the conflict-marker commit gate could deny a clean commit as `R-CONFLICT-MARKER-SCAN-TIMED-OUT`. It ran `git grep` over the whole tree (the index, or the working tree for `commit -a`) and only afterwards dropped every file the commit did not record, so on a repository of about 5,800 files each grep took 4 to 7 seconds against a 5 second limit. Both `git grep` passes now name the paths the commit records, as literal pathspecs in chunks of 256, so the scan costs what the commit changes rather than what the repository holds. A recorded file whose name holds `*`, `?` or `[` is read as that file and nothing wider. The verdicts are unchanged: the same markers are found, a marker in a file the commit does not record never denies, and the timeout limit and its fail-closed rule are as before (reported as issue #83).

#### The venv scan prefers the venv built for this source (Plan 00474)

After an interpreter patch update the current interpreter fingerprint matches no venv, and both venv resolvers fell back to a scan that returned the lexically-first `untracked/venv-*`. A legacy un-slugged `venv-py311-<hex>` sorts ahead of a slugged `venv-<slug>-py313-<hex>`, so a stale legacy venv with old metadata won: `daemon_upgrade_detector` reported a false downgrade on every turn, and the shell side ran the upgrade gate under the legacy interpreter. Both scans (`resolve_existing_venv_python` in `paths.py` and `_rv_pick_python` in `scripts/lib/resolve_venv.sh`) now rank the candidates: a venv whose `.daemon-metadata.json` `lock_hash` matches the current `pyproject.toml` and `uv.lock` first, other slugged venvs next, legacy un-slugged venvs last, with ties kept in name order. The ranking uses stdlib hashing (a `sha256sum` or `shasum` call on the shell side) and one JSON read per candidate, with no Python spawn, so the per-turn hot path costs what it did. The override and the exact-fingerprint steps, the slug rule and the shell run-probe are unchanged, and an install with only a legacy venv still resolves it (reported as issue #84).

#### Opening the compact summary no longer defers the post-compact resume (Plan 00474)

The ccy supervisor tracks the human's input box from the keystrokes it forwards, and every injection (including the resume after a compact) waits until the box is empty. `HumanInputLine` counted every control byte it did not recognise as typed content, so one Ctrl+O (Claude Code prints "ctrl+o to see full summary" right after a compact) left the box looking non-empty until the human pressed Enter, Ctrl-U or Ctrl-C, and the resume was deferred meanwhile. Ctrl+O and Ctrl+T (the transcript/summary and todo-list view toggles) are now consumed as no-ops: they neither mark the box non-empty nor change its content, and they do not start the abandoned-box clock. Ctrl+V and Ctrl+R stay counted as content because they can fill the box, and any other unrecognised control byte keeps the conservative rule.

#### A quoted heredoc fed to git merge is read as data (Plan 00474)

`git merge` was missing from the set of git subcommands whose heredoc body is read as data, although `git commit` and `git tag` were in it. A quoted heredoc fed to `git merge` (`git merge topic -F - <<'EOF'`) was therefore tokenised as shell, and an apostrophe in the body ended the read: `project_containment` then allowed the call but printed "could NOT fully judge this call ... report it". `merge` is a git built-in that no alias can shadow and it never runs its stdin, so it now joins the data subcommands. An unknown or aliasable subcommand with the same body is still scanned.

#### `issue_filing_gate` reads gh flags from shell words (Plan 00474)

`issue_filing_gate` read `--repo`/`-R` and `--body-file`/`-F` (and `--web`) by regex over the raw command text, so text inside a quoted argument counted as a flag. A title such as `'git merge -F - reads stdin'` made a valid generated report look like a stdin body and refused it. Worse, a title such as `'see -R someone/else'` placed before the real `--repo` made the gate read the wrong target and stand down for a real filing against the public hooks-daemon tracker; a quoted `--web` in a title likewise opened the browser-fallback exemption. The flags are now taken from the segment's shell words, so only a real flag counts. A segment that cannot be split into words (an unterminated quote, `$(...)`) is still read from the raw text as before, except that `--web` is never granted there. Any `--repo` value naming the tracker engages the gate, because `gh` honours the last of a repeated flag.

#### The Effort Source OK line reports what modelSettings actually holds (Plan 00474)

The Effort Source check passed with the text "per-model levels come from settings.json modelSettings" whenever nothing pinned effort, without reading `modelSettings`. With no `modelSettings` entries anywhere, that sentence was false. The check now reads `modelSettings` from the user, project and local settings files: it names each model ID that carries an `effortLevel` (and the file it came from), or, when none does, says that no model has an explicit effort level so each runs at its own default. An entry without an `effortLevel` key is not counted. A top-level `effortLevel` in the user file (the legacy form: not a pin, and applying only to Opus 5, Fable 5.1 and earlier, while Opus 5.5 and later run at their own default) is named too with that exception, and the text only says "each runs at its own default" when no such level is set. The verdict is unchanged (passed when nothing pins effort) and the check still recommends no level.

#### Plan QA's "no README index row" finding states the accepted row forms (Plan 00474)

The plan index reader only accepts top-level bullet rows, so a markdown table row such as `| [00001](00001-x/PLAN.md) | Title | Not Started |` was silently ignored and every plan was reported as having no README index row, with a remediation that named no grammar. The `row-folder-bijection` finding now states both accepted forms (`- [NNNNN: Title](NNNNN-name/PLAN.md) - status` and `- **NNNNN** - status`, under a `##` section heading), and when the README holds a table row for the plan it says so and that table rows are not read as index rows. Table rows still do not satisfy the check, and the finding's level is unchanged.

#### An upgrade now removes stale venvs, and only those it can show are stale (Plan 00474)

A normal client upgrade checks the target out first, so it always took the already-at-target path in `scripts/upgrade_version.sh`, which never cleaned up old venvs; installs kept a `venv-*` directory per past version. That path now calls `eager_cleanup_stale_venvs` after the verified restart and the post-install checks. The cleanup no longer removes every venv except the current one: a `venv-*` directory is removed only when its `.daemon-metadata.json` `lock_hash` is readable and differs from the current source's, and its name carries this checkout view's path slug or no slug. Another view's slugged venv (a host and a container sharing one checkout), a venv whose `lock_hash` matches, and a venv with missing or unreadable metadata are kept, each with a `Kept venv:` log line giving the reason. When the current `lock_hash` cannot be computed, nothing is removed. The decision lives in `paths.py list-stale-venvs`.

### Operators

#### The plan fact-check feed names real files, checks only what changed, and no longer loses a check (Plan 00474)

If you enabled `plan_fact_check_feed`, its owed-check instructions are now trustworthy. Edits inside a sub-agent's worktree no longer feed your session's debouncer, a plan archived to `Completed/` is named at its new path (or dropped if gone), and a plan's first sighting records a baseline instead of diffing the whole folder. The content counts as checked only once the session is seen dispatching `plan-fact-checker` with the diff path in its prompt; an unacted offer is re-offered after five minutes, up to three times. A small edit (20 lines or fewer) within ten minutes of a confirmed check is taken as a correction and absorbed, so fixing a finding no longer owes another check.

#### `write_protected_paths` keeps listed files read-only for agents, by any tool or Bash route (Plan 00499)

A new opt-in PreToolUse handler, `write_protected_paths`, takes a list of repository-relative path globs (`options.paths`) that agents may read but never create, change, move onto or delete. It denies `Write`, `Edit` and `NotebookEdit` on a listed path, and a Bash command that writes it (redirect, `tee`, heredoc, `sed -i`, `dd of=`), copies, moves, installs or links onto it, touches it, or deletes or truncates it (`rm`, `unlink`, `truncate`, `: >`), including a directory that holds it. The denial says the file is maintained outside the agent (infrastructure-as-code or a human) and to ask the human for any change. The Bash check is a read-only allowlist: a command naming a listed path is denied unless its verb is known only to read (`cat`, `grep`, `sort`, `awk`, `diff` and the like); wrappers (`env`, `flock`, `timeout`, `xargs`), `bash -c`/`sh -c`/`eval` bodies, brace lists, `for` loops, `find -delete`/`-exec` and absolute command paths (`/bin/rm`) are read through to the command they run. Deliberately hostile respellings are out of scope and named as known gaps in the handler's guidance. It ships disabled and does nothing without `paths`, so existing projects behave exactly as before. Claude Code's own `permissions.deny` with `Edit(...)` misses every Bash route; this handler covers them. For handler authors: `scan_bash_write_targets` takes `include_mutations=True` to also report the files a command changes without authoring (`sed -i`, `ln`, `rm`, `truncate`, and the source of `mv`); callers that do not pass it see no change.

#### Declared crons are held by a session's initial thread only (Plan 00470)

A thread opened later in a Claude Code session (left arrow, then a new thread) is a separate session to the hooks, with its own empty cron list and a `SessionStart` that reports `source: "startup"`. So `cron_stop_enforcer` demanded the declared `persistent_crons` at every thread's stop, and each thread ran its own copy of every job. Now only the initial thread of a session is required to hold them. The daemon tells the threads apart by process ancestry: all threads of one session run under one `claude daemon run --origin transient --spawned-by` process, the initial thread's worker carries `--fork-session --resume`, and a thread opened later is a `bg-spare` worker. The holder is chosen by that worker shape, not by which hook arrived first, and it is a live process: if the initial thread exits the next thread takes over, and a `/clear` in the initial thread keeps holding. A later thread is told by `persistent_cron_assertor` that it holds none, and `cron_stop_enforcer`, `cron_subagent_stop_enforcer` and the `usage_pause_gate` lift directive no longer ask it for them. The grouping reads only `/proc` (bounded depth, a deadline, no signal sent) and the group-to-holder map persists across a daemon restart. Whenever the placement is unsure (no such ancestor, an unreadable `/proc`, a worker of an unrecognised shape) every session holds the crons exactly as before. The daemon reads the hook's pid from the connection on both the event sockets and the legacy `init.sh` socket, replacing any pid a payload carries. The option `persistent_crons.initial_thread_only` (default `true`) turns this off.

#### Agent dispatch branches now count as work branches (Plan 00474)

`branch_count_advisor` and `merge_qa_advisor` used to recognise a work branch only by the `worktree-` prefix. A sub-agent dispatched with `isolation: worktree` works on an `agent-<hex>-<hex>` branch, so those branches were left out of the open-branch count, and merging one drew no advice about recorded QA. Both handlers now treat `agent-*` branches as work branches too. A session that keeps many old agent branches will see the branch-count advisory name them until they are merged or deleted.

#### `/hooks-daemon optimise` no longer recommends the `daemon_stats` status-line handler (Plan 00474)

The config-optimisation review used to treat `handlers.status_line.daemon_stats` (the daemon health line: uptime, memory, log level, error count) as relevant to every project, so it recommended enabling it everywhere. That health line is a diagnostic for people developing the daemon itself. It now reports as "not applicable here" in every project except the daemon's own repository. If you enabled it because the review recommended it, you can set `handlers.status_line.daemon_stats.enabled: false` (or remove the entry, since it ships disabled) and restart the daemon. Nothing else changes, and the separate daemon-upgrade notifier (`version_check`) stays on by default.

#### A venv cache miss no longer costs the probe's full timeout (Plan 00500)

When the hook's venv resolver had to probe a candidate interpreter (a cache miss), every probe used to cost the whole watchdog bound, about 5 seconds, even when the candidate answered at once. The watchdog held the caller's output pipe until its `sleep` ended. It now detaches its input and output and kills its own `sleep` when the candidate answers, so a good candidate costs milliseconds. A hanging candidate is still killed at the bound. Nothing to do on upgrade.

#### The host status-line segment shows the session's role as `role@host` (Plan 00474)

When a session sets a hostname override (`HOOKS_DAEMON_HOSTNAME`, the role that `persistent_crons` `hosts:` entries match against), the opt-in `host_hostname` segment now shows it before the `@`. For example, it renders `sdlc-runner@build-box` instead of `@build-box`. A role longer than 15 characters is cut to its first 10 characters followed by `...`, so a long alias cannot crowd out the host name. When no override is set, or the override equals the host's own name (as it does when only `CCY_HOST_HOSTNAME` is set), the segment is unchanged. The role is read on every render from the session's payload, while the host name is still resolved once per daemon start. No configuration change is needed. The segment remains disabled by default.

#### List every exception, probe one handler alone, and the disable footer asks why (Plan 00484)

Three small changes to how exceptions to a guard are handled.

`hooks-daemon exceptions [--json]` lists what exempts something from a guard, with the reason each carries: `exclude_paths` and `extra_whitelist` entries (a reason is read from the raw config, because loading drops it), handlers set to `enabled: false` or `mode: warn`, `MUST_EXCEED_*_BECAUSE` hatches in tracked files, and the QA exception files. An entry with nowhere to write a reason shows `(no reason)`.

`hooks-daemon probe <event> --only <handler>` runs that one handler instead of the whole chain, so a detector can be exercised alone. It is honoured only for a probe-class source; a name that is not an enabled bundled, project or plugin handler of that event is refused rather than answered with an allow.

Every deny now carries one `To disable:` footer, the router's (five handlers used to print a second one of their own), and it reads `(set enabled: false and record why beside it)`. Reasons on config exceptions stay optional, and under `daemon.strict_mode` a plain string is a warning, not an error. Nothing to do on upgrade.

#### The usage-pause owner override is now visible to the session and the status line (Plan 00479)

`bin/hooks-daemon usage-pause clear` records an override that suppresses the usage pause until the latest reset among the windows over the ceiling. Until now it was silent: usage could climb from the ceiling to the account's hard limit with nothing telling the model or the person watching. Two signals now show it, and neither changes any decision (the override still suppresses every pause).

While an override is in force and at least one usage window is over its ceiling, each prompt carries a `USAGE CEILING SUPPRESSED` line naming each over-ceiling window, its percentage, the ceiling and the override's end time in UTC (with the date when it is not today). The status line's usage segment shows `override until HH:MM` (local time, with the month and day when it is not today) whenever the override is valid: red while a window is over the ceiling, yellow otherwise. Missing or stale usage data says nothing, and a failure reading usage never affects the prompt.

An override marker that exists but cannot be read is still treated as an override, as before, but is no longer silent: every prompt says the ceiling is suppressed by a marker that cannot be read (naming its path) and that its end is unknown, and the chip reads `override (end unknown)` in red. Existing behaviour worth knowing: such a marker never expires on its own, because only the marker's content carries an end time, so it holds until the file is made readable (it then ends at its recorded time) or deleted. No configuration change is needed.

#### Defences lists a runnable probe command for project handlers, and one more checker takes a file (Plan 00484)

`hooks-daemon defences` now gives a project handler of yours the same `--only` probe command as a bundled one. `scripts/qa/check_british_english.py --path FILE` judges one document as the whole-tree run would and writes no artefact. A file the tree run skips (a plan, a release record, a fixture) is refused rather than passed. Nothing to do on upgrade.

#### The idle housekeeping report also names old scratch files and changed-green refs of deleted branches (Plan 00470)

`idle_housekeeping_advisory` (beta, opt-in, off by default) now has two more report-only sections. Neither deletes anything; each prints the command a person may choose to run.

#### Defences lists three batch checkers beside the handlers (Plan 00484)

`hooks-daemon defences` now also lists the `scripts/qa` checkers that are the whole-tree form of a Defence handler: `audit_error_hiding.py`, `check_sensitive_content.py` and `check_inline_suppressions.py`. #### `verdicts.jsonl` now records the rule ID of a handler's decision (Plan 00474)

The `rule` field of each line in `verdicts.jsonl` was null for most handlers, including the usage-pause gate and the failsafe-cron suppressors, so a dropped tick (`R-FAILSAFE-CRON-SUPPRESSED`, `R-DECLARED-CRON-SUPPRESSED`, `R-FAILSAFE-CRON-BACKED-OFF`, `R-USAGE-PAUSE-PROMPT`) could not be counted from the log.

#### The status line no longer goes blank while the daemon is down, and names the outage (Plan 00488)

Claude Code renders nothing for a status line command that exits non-zero. The status-line forwarder printed its daemon-down marker and then exited 1, so the bar was blank for the whole outage, including the first minutes of a fresh checkout whose venv is building. The forwarder now exits 0 on that path (a per-event `daemon_down_exit_code` in the event catalogue); the `WorktreeCreate` forwarder keeps exit 1 because its stdout is a value and non-zero there means "not handled". `init.sh` also names each daemon-down state it can tell apart, instead of the generic `DAEMON FAILED`: `VENV BUILDING` while the self-heal build runs, `VENV MISSING` when a clone or leftover venv exists but nothing builds, `VERSION MISMATCH` for a stale clone, and the existing `NOT PROVISIONED`. The list is in `CLAUDE/Architecture/StatusLine.md`.

`mkplan.bash` already advances a lagging plan counter to the highest plan on disk instead of refusing; a regression test now pins that for a fresh clone far behind the disk. No configuration change is needed.

#### While a fresh checkout's venv builds, the hook message says what to avoid (Plan 00488)

On a fresh checkout the daemon cannot answer until the background venv build finishes, so no guard judges tool calls meanwhile. That stays as it was: PreToolUse keeps allowing, since denying would wedge the agent (even `sleep` would be denied) and waiting cannot fit inside the hook timeout. What changes is the message the agent sees on every hook event during the build: it now adds a line telling it to keep to reads and ordinary edits, and not to commit, push, delete branches or touch protected files until the status line clears. The failed, refused and disabled states do not carry the line. No configuration change is needed.

#### A raw clone of the daemon's repository builds its venv with no manual step, and the build's first moments read as building (Plan 00488)

Two gaps in the first-session venv build are closed. A fresh `git clone` of this repository has no `.claude/hooks-daemon.env` (it is gitignored), so `init.sh` looked for the daemon in `.claude/hooks-daemon/`, found nothing, and the status line read "DAEMON FAILED" while SessionStart advised installing, which is wrong for this repository. `init.sh` now recognises the daemon's own source tree and uses the project itself as the root, so the first hook starts the background venv build with no step from you. `scripts/bootstrap-self-install.sh` still works for a foreground build. A client project is never matched.

Separately, for the first sub-second to few seconds of a build, uv has made the interpreter but not yet installed the package. A hook arriving then used to read "DAEMON FAILED" and PreToolUse denied the call. A held venv build lock now marks the whole window as "venv building", and tool calls fail open with the announcement, as the rest of the window does. No configuration change is needed.

#### `remote-docs refresh` re-fetches each document in the fidelity it recorded (Plan 00504)

`remote-docs refresh` used to pick one fetcher from the command line and use it for every document, so a plain `refresh --all` turned a document captured with `add --verbatim` into an extraction, and `refresh --all --verbatim` turned converted documents into verbatim ones. Refresh now reads each document's recorded `fidelity` and re-fetches a `verbatim` document verbatim and any other document with the default fetcher, so a mixed corpus keeps every document's mode with no flag. An explicit `--verbatim` still forces verbatim for every target. A document whose provenance cannot be read is still reported unreadable and left untouched. No configuration change is needed; to deliberately change a document's fidelity, re-capture it with `add --force`.

#### `tdd_enforcement` checks a worktree's own test against a declared `test_path_map` (Plan 00505)

A source file written inside a git worktree nested in the project (`untracked/worktrees/<name>/`) was checked against the main checkout's `test_path_map` directory, so the test written in the worktree was never searched and the write was denied with R-TDD-TEST-FIRST. A declared `test_dir`, flat or `mirror: true`, and the `source_glob` that selects it are now anchored at the checkout that holds the source file, so the worktree's own test satisfies the gate and the deny names the worktree's locations. A source in the main checkout resolves exactly as before, and `layout.test_dirs` mirror roots were already worktree-anchored. No configuration change is needed (reported as issue #74).

#### `comment_size` and `comment_changelog` no longer read an unclosed `/*` as a comment running to the end of the file (Plan 00506)

A block or doc opener with no closing delimiter later in the content used to be closed at the end of the file, so a `/*` inside a string literal (the glob `"src/*.rs"`) made `comment_size` deny a file that held no comment at all. Such an opener now yields no comment and scanning resumes on the next line as code. A terminated block comment is read as before, a marker in a string whose closer does appear later is still read up to that closer, and no configuration change is needed (reported as issue #75). This applies to whole-file content (`Write`). An `Edit` is judged on its `new_string`, a fragment whose closer may lie in the untouched file, so there an opener with no closer inside the fragment is read as a comment running to the end of the fragment, unless the opener sits inside a string literal on its line.

#### `lint_on_edit` checks a Rust file as a module of its own crate, so valid modules of an edition-2024 crate are no longer denied (Plan 00507)

`lint_on_edit` compiled every `.rs` file as a standalone edition-2021 library, so a let chain, a `use crate::sibling`, or an integration test importing its crate was denied with `R-LINT-FAILURE` although the code was valid. `rustc` now runs from the nearest `Cargo.toml` with that crate's edition (`package.edition`, the workspace's `[workspace.package].edition`, or Cargo's default of 2015); a file with no `Cargo.toml` keeps edition 2021. An unresolved import, path, crate or module file (`E0432`, `E0433`, `E0463`, `E0583`) now ALLOWs with an advisory that the file was not checked when every error in the output is of that kind; syntax errors and other compiler errors still deny, including when they appear alongside an unresolved import. A `command_overrides` template may use `{edition}` as a whole argument; one without it runs as written, and no configuration change is needed (reported as issue #76, duplicate #89).

#### A host reboot or shutdown warning now reaches an agent in the middle of a long turn, through the new default-enabled `operator_signal_notice` handler (Plan 00508)

`hooks-daemon signal` writes a per-session warning that the host will reboot or shut down, or that a warned reboot is cancelled. The ccy supervisor types it into the session only when the session is idle with an empty input box, so an agent in a long turn was told after the stated minutes could already have run out. The new PostToolUse handler `operator_signal_notice` (priority 38, enabled by default) adds the same rendered warning as hook context at the next tool call, once per signal in each agent thread (the main thread and every sub-agent are each told once). It reads one known file per event, ignores a malformed, expired, unknown-kind or other-session file with a logged reason, and never deletes or rewrites the file, so the supervisor's idle-time injection is unchanged and the agent may see the same warning a second time when it goes idle. Opt out with `handlers.post_tool_use.operator_signal_notice.enabled: false` (reported as issue #77).

#### `bash .claude/provision.sh` now syncs a daemon clone that is at another version than the project expects, and the drift notices name it instead of `upgrade` (Plan 00477)

When a pull changes `daemon.expected_version`, the gitignored clone under `.claude/hooks-daemon/` is left behind (or ahead). `provision.sh` used to refuse a clone that was already there; it now brings it to the expected version. A clone already at that version is left alone ("already at vX.Y.Z", exit 0). Otherwise it refuses, changing nothing, when the clone is not a git checkout, its `origin` is not the fixed trusted URL, or it has tracked changes or files outside `untracked/` (gitignored files do not count). When it may go on, it first works in a stage under the clone's `untracked/`, writing nothing else of the live clone (its git directory included) while the old daemon serves. It fetches exactly the tag (depth 1) from the fixed URL into a clone of its own there and checks that the tag's `version.py` names the version. It runs the target release's own pre-deploy gate from the stage (the one upgrade runs; a target that predates the gate has none to run). It builds the target's venv there with the target's own `scripts/venv_bootstrap.sh`, then rebinds it to the live path: the venv is renamed for the live path and every text file in it that names the stage names the live path instead. Only then does it switch. It stops the old daemon, moves the daemon's state under `untracked/` into the stage, swaps the stage in by renames, keeps the old clone at `untracked/sync-previous`, and starts the daemon with `bin/hooks-daemon restart`. Before that start, the moved venv must pass init.sh's own pre-start check (`validate_venv`), resolve as the live venv and import the package from the live `src`. If it does not, it is rebuilt in place through the clone's `scripts/venv_bootstrap.sh repair` while the daemon is down, and the outcome records that and why; if the rebuild fails too, the old clone is swapped back. The old clone is removed once the new daemon answers. During the switch, a hook that would start a daemon answers "the daemon is starting; retry" instead. When the gate wants its reading list confirmed, it prints the listing and stops with nothing changed; re-run with `--skip-reading-confirmation=<digest>`, as with upgrade. A failure before the switch changes nothing and never stops the old daemon. A failure during it swaps the old clone, its venv and the daemon's state back, starts the old daemon again and says that the previous version is in place. A switch that a killed run left half-done is undone the same way by the next run of `provision.sh`, which prints `RECOVERED`. A sync writes no tracked file, runs no config migration and regenerates no docs: moving a PROJECT to a new version is still `upgrade`.

The version-drift notices now name `provision` for this case: the `init.sh` stale-clone message, the SessionStart `version_check` drift notice, and `daemon_sync_after_merge` after a pull that changed `daemon.expected_version`. Each also says that `upgrade` remains the route for moving the project to another version (reported as issue #78).

#### Venvs are judged by one staleness rule, and the ones it cannot prove are surfaced (Plan 00517)

`prune-venvs`, `disk-usage`, the upgrade cleanup and the daemon-start advisory now share one definition of a stale venv: the legacy `untracked/venv/`, or a venv of this checkout view whose readable `lock_hash` differs from the current source's. The venv the running daemon or the resolver uses is never selected, and `prune-venvs --all-except-current` is removed with a message (`--stale` is the replacement). Daemon start, restart and `provision` now remove every venv proven stale. A venv the code cannot prove stale (missing or unreadable metadata, or another view's slug) is never removed automatically: `list-venvs`, `prune-venvs --dry-run` and the new `unproven_venv_advisor` SessionStart handler list each with the processes using it, its interpreter and version, its age and its view, and `prune-venvs --unproven <path> --force` removes one once you have confirmed it is unused. Daemon start also removes other hosts' dead per-host runtime sets (`daemon-<id>.{sock,pid,sock.start.lock,socket-path}` and `events-<id>/`) when every socket in the set refuses a connection and its pid is not a live daemon.

#### A pulled `daemon.expected_version` upgrade now syncs the daemon clone in the background, and a failed sync is reported at every session start (Plan 00477)

When someone else upgrades the project and commits, this checkout's pull changes `daemon.expected_version`, but the gitignored clone under `.claude/hooks-daemon/` stays at the old version. The SessionStart `version_check` drift notice used to name `bash .claude/provision.sh` and wait for a person to run it. For an UPGRADE the sync now starts itself. The tracked session-start forwarder (`.claude/hooks/session-start`) starts `bash .claude/provision.sh --background` detached at every session start, so it never runs inside the hook's time budget. It sits above the relay hot path, so it runs with the relay enabled too. The sync does nothing when the clone already matches. Otherwise it waits for the running daemon, then runs provision's own steps (release note 031). The target is fetched, gated and built in a stage beside the running daemon, which keeps serving, untouched, until the switch. The switch stops it, swaps the stage in by renames, keeps the old clone until the new daemon answers, and swaps it back if the new one does not. A failure before the switch never stops it. A switch a killed sync left half-done is undone by the next session start's run, and recorded as failed. The forwarder and `provision.sh` are tracked files, so the commit that moved `daemon.expected_version` brings them with it, and the very pull that changes the version is enough.

- The output goes to `.claude/hooks-daemon/untracked/background-sync/v<version>.log`. The outcome is recorded in `v<version>.state` beside it. That file is also the marker that the target was attempted, so each target version is synced in the background at most once. A lock stops two syncs from overlapping.
- A failure leaves the previous version in place, as a manual provision does: a refused clone, an unfetchable tag, a failed venv build, or a target whose pre-deploy gate wants its reading list confirmed. Every later session start then shows `BACKGROUND SYNC TO vX.Y.Z FAILED` (or `STOPPED`) to the human and the agent, with the reason, the log, `bash .claude/provision.sh` to run by hand, and the state file to delete to have it retried in the background.
- A DOWNGRADE is never synced in the background. Nor is a fresh checkout provisioned, or a project without the tracked `.claude/provision.sh` synced. The notice for those still names the command, and a person or agent runs it. The daemon's own repository never syncs.
- With no daemon running from the clone after 30 seconds, the sync changes nothing and claims nothing, and a later session start tries again. A clone too broken to start keeps the existing `init.sh` message naming provision.
- The `version_check` notice reports the sync's state: started, under way, or its outcome. Only an installed daemon at this version or later knows to read that state. On the first move onto this release, the sync still runs, but the notice keeps its older wording.

#### The plan fact-check feed now names an agent that clients actually have (Plan 00474)

The opt-in `plan_fact_check_feed` handler tells the session to dispatch a plan fact-checker agent, but no client project had one: the only definition lived in the daemon's own repository. The daemon now ships it as `hooks-daemon-plan-fact-checker`, a project-neutral template deployed into `.claude/agents/` like the other daemon-owned agents. #### The upgrade restores dropped opt-in handlers before it restarts the daemon (Plan 00474)

When an upgrade would switch off an opt-in handler that was running, the upgrade writes `enabled: true` for it so the project keeps what it ran before. That edit used to happen after the upgrade had restarted the daemon, so the restarted daemon ran without those handlers until someone restarted it again, and the upgrade printed RESTART THE DAEMON. The upgrade now makes the edit inside the version-specific step, after the new virtual environment is verified and before hooks are deployed and the daemon is restarted, so the restarted daemon already has the restored handlers on. The restored-handler report and the upgrade summary still list them, and no restart is asked for. If the restore cannot run (a target without the step, or an error), the upgrade continues and falls back to the earlier behaviour: the outer script applies the restore and asks for the restart.

#### A git failure at daemon start is reported as a git failure, not as an invalid configuration (Plan 00474)

When git failed at daemon start (for example `git rev-parse` exiting 128 because the installed git is too old for the repository's format), the daemon printed "Invalid configuration" and "Fix the configuration file and try again", and dropped git's own error. No edit of the configuration could fix it. The daemon now raises a dedicated error (a `ValueError`, so existing handling still works) that says which git step failed, its exit code and git's stderr, for three cases: `rev-parse` failed, there is no `origin` (or its URL is empty), or the toplevel could not be determined. The failure is logged at WARNING with git's stderr. The CLI start-up check names the project root and git, and suggests checking the repository or the git version. A genuinely invalid configuration still reports "Invalid configuration".

#### Error hiding now blocks a `suppress()` that names Exception or BaseException (Plan 00474)

`error_hiding_blocker` blocked `except Exception: pass` but allowed `with contextlib.suppress(Exception):`, which discards every error in the same way. A Python `Write`/`Edit` is now denied when a `suppress(...)` call (through `contextlib.suppress` or a bare imported `suppress`) names `Exception` or `BaseException` as a whole name, alone or among other exceptions (`suppress(OSError, Exception)`). A narrow `suppress(OSError)` names the exception it accepts and stays allowed, as do `ExceptionGroup`, `MyException` and `asyncio.CancelledError`. The deny says to suppress only the specific exception you expect, or handle it. The matching is textual, so a string literal that holds the broad form is judged like code; a trailing comment that mentions it is not. The `audit_error_hiding.py` QA audit reports the same form as the new `broad-suppress` rule. A client whose code already uses the broad form is not affected until it next writes that code.

#### The merge QA report places a merge by the directory it runs in (Plan 00474)

`merge_qa_report` decided whether a `git merge`, `git pull` or `git rebase` belonged to the project by the session's working directory alone. A merge run as `cd <nested repo> && git merge ...` or `git -C <nested repo> merge ...` was therefore read against the project, and the report described an operation that never happened there. The handler now places the merge the way `daemon_sync_after_merge` already did: by the `cd`, `pushd` or `git -C` in effect at the merge, falling back to the session directory when the target cannot be worked out statically (`cd $DIR`). A merge inside a nested or vendored checkout is left alone, and a plain merge at the project root is reported as before. Both handlers now share one function, `merge_directory` in `utils/merge_scope.py`.

#### A full_words-only full_qa_patterns entry judges operands as words only (Plan 00474)

A `subagent_full_qa_blocker` entry that declared `full_words` and no `full_args` also ran the path rules on every operand, so `{command: php, full_words: [bin/qa]}` denied `php probe.php .`, `php probe.php ..` and `php probe.php <nested repo root>` although no full word was present. Such an entry now judges operands as words only: a word in `full_words` makes the run full, and no operand is judged as a repository root or as at or above the start directory. An entry that declares `full_args`, even `full_args: []`, behaves exactly as before, as do `bare_is_full`, `read_only_flags` and `value_flags`. If you relied on a words-only entry denying `.` or a repository root, declare `full_args` for it.

#### `subagent_worktree_write_guard` binds an agent on a first write made from outside the repository (Plan 00474)

`subagent_worktree_write_guard` bound a sub-agent to the linked worktree of its first write only when the payload cwd was a checkout of the same repository. A first write made while the shared cwd was outside any git checkout, or in a different repository, was allowed but bound nothing, so a later write by the same agent into that same worktree was judged by whatever cwd the session then had: with the cwd in a sibling worktree it was denied naming the sibling, and the identical write from another cwd was allowed. Such a first write now binds the agent to the target's linked worktree exactly as a same-repository first write does, so later writes are judged against that binding. A first write with no `agent_id`, into a main working tree, or outside any checkout still binds nothing, and an unreadable git marker still fails open.

#### `prune-venvs` never selects the venv the daemon is running from (Plan 00517)

The live-venv guard behind `prune-venvs`, `list-venvs` and `disk-usage` took the live venv from the resolver's `bin/python` after following its symlink, which for a real venv is the system interpreter, so the guard compared against `/usr` and never matched the venv. A running venv whose fingerprint differed from the current one was therefore listed by `prune-venvs --all-except-current --dry-run` and removed by `--force`. The guard now identifies the live venv by its directory: the venv the resolver selects (without resolving the `bin/python` symlink) and the running interpreter's `sys.prefix`. No `prune-venvs` mode (`--all-except-current`, `--stale`, `--legacy`) can select either, and both are reported as current by `list-venvs`.

#### `subagent_full_qa_blocker` can exempt a dedicated QA agent type, one run at a time (Plan 00518)

A project that runs its full QA gate through a dedicated agent no longer has to leave `subagent_full_qa_blocker` off. The new option `exempt_agent_types` lists exact agent definition-type names (the `name` in `.claude/agents/<name>.md`); a sub-agent of a listed type is allowed to run a declared full-suite command, with an advisory naming the entry that exempted it. The exemption comes with one run at a time: while another full run holds the host-wide full-QA lock the call is denied, and a holder that ended or died never blocks. A sub-agent whose `agent_type` is missing or empty is never exempt, the match is exact (no globs, no case folding), and the default is an empty list, which changes nothing.

A named agent's `agent_type` in the hook payload is its dispatch `name`, not its definition type, so the new silent handler `agent_dispatch_recorder` records `name -> subagent_type` when it sees the dispatch and the blocker reads the type back from that record. A teammate named like a listed type is therefore not exempt. Keep `agent_dispatch_recorder` enabled (it ships on) if you list a type. The payload `agent_id` tells named from unnamed: an id of the unnamed shape (`a` plus 16 hex digits) means `agent_type` is trusted as the type and no record is read; any other id is a named teammate whose type must come from its record, and with none it is not exempt. The payload offers nothing to check an unnamed agent's type against.

The `optimise` review now looks for a dedicated full-QA runner agent under `.claude/agents/` (a name carrying `full`, `runner` and one of `qa`, `pipeline`, `gate`, `suite`, such as `php-qa-ci_full-pipeline-runner`) and, when it finds one, recommends enabling `subagent_full_qa_blocker` with `exempt_agent_types: [<that agent type>]` instead of leaving it off.

#### The installed daemon version comes from version.py, not from venv metadata (Plan 00517)

The running daemon's upgrade notice (`daemon_upgrade_detector`) took the installed version from the selected venv's `.daemon-metadata.json`, a copy written when the venv was built, so a venv whose metadata disagreed with the source it served reported a version that was not installed. It now reads the `__version__` literal in the installed source tree's `version.py`, as text and fresh on every prompt, so a source upgraded underneath a running daemon is reported and a venv with different metadata is not. The metadata keeps only what tells venvs apart (`lock_hash`, `python_path`) and the version that built the venv.

#### A wrapped status line no longer loses the context figure (Plan 00474)

On a narrow terminal the status line showed an ellipsis where the context percentage should be. The daemon packed each row to the full terminal width, but Claude Code renders the status line inside its own spacing and shares the row with notifications, so it cut the end of the row, which is where the context figure sits. Rows are now packed 8 columns narrower than the terminal (`STATUS_WRAP_MARGIN`), so the figure stays visible and the line wraps one segment earlier instead.

#### `tdd_enforcement` finds the Maven/Gradle test source set (Plan 00520)

A Java or Kotlin file under `src/main/<lang>/<pkg>/` could never satisfy the TDD gate in a conventionally laid-out Maven or Gradle project: the gate searched `tests/...` mirrors but never the sibling `src/test/<lang>/<pkg>/<Name>Test.<ext>`. That location is now searched too, anchored on the first `src` segment, and it is listed in the deny message. The change is additive; every location searched before is still searched in the same order.

#### `tdd_enforcement` no longer gates a Write over an existing file (Plan 00521)

`tdd_enforcement` is about creating a production source file, but it denied a `Write` that overwrote an existing source file with no test, even though an `Edit` to the same file was allowed and can rewrite it wholesale. A `Write` whose target is an existing regular file is now treated like an `Edit` and passes. A `Write` that creates a new path is judged exactly as before. A symlink, a directory or a dangling path at the target counts as not existing, so the gate still applies. Read-before-overwrite (`R-WRITE-CLOBBER`) is a separate guard and is unchanged.

#### `staged_lint_gate` vets Go from its module root (Plan 00525)

`staged_lint_gate` ran `go vet <file>` from the daemon's working directory, so a Go file in a nested module (a `go.mod` in a subdirectory, importing its own module's packages) could not resolve its imports. Depending on the Go version that either denied a correct commit (`package ... is not in GOROOT`) or let the file through unchecked. The gate now finds the nearest `go.mod`, runs `go vet` from that directory on the file's package, exactly as `lint_on_edit` does, through one shared resolver. A correct nested-module package commits and a real `go vet` finding still blocks. The finding line in the message now skips the `# <package>` banner so it names the file. The same module-root working directory now also applies to Ansible (`ansible.cfg`) and Rust (`Cargo.toml`) files checked by the gate.

#### An idle stop with a workable issue is refused (Plan 00470)

A coordinator that closed an issue and then stopped with "the next issue is for the hourly tick" was let through on the `STOPPING BECAUSE:` prefix, although workable issues existed and nothing was in flight. The new Stop handler `idle_workable_issue_stop_gate` (rule `R-STOP-IDLE-WITH-WORKABLE-ISSUE`) refuses that stop on facts: the `issue-sdlc` job is declared for this host and thread, the work queue has no `running` entry, and a fresh workable-issues cache lists an issue. The deny names the issue and says the cron is a safety net, not a scheduler. It stands aside for a sub-agent stop, a usage pause, a non-holder thread, a live or just-declared `[awaiting-human]`, a stale or missing cache, and a stop that re-enters after its own deny. It reads a local file and never calls GitHub.

`work-queue done NAME` now prints `next workable issue: #N - start it now` (or `no workable issue`, or that the next issue is unknown when GitHub could not be asked; the close never fails on that), and `issue-validity --list-eligible` also writes the cache. Workable means eligible and not labelled `agent-needs-human`. The handler is on by default and inert in any project that does not declare an `issue-sdlc` job; `options.job_id`, `options.max_cache_age_hours` (default 2) and `options.marker_expiry_hours` tune it.

#### `lint_on_edit` no longer denies the first half of a Go change (Plan 00527)

`lint_on_edit` ran `go vet` on the edited package after every Edit, so a change that needs two edits (add a call, then its import) was denied after the first: `vet: x_test.go:48:12: undefined: syscall`. Now:

- `go vet` findings in the unresolved-name class on the edited file (`undefined:` / `undeclared name:`, `imported and not used` / `imported but not used`, `declared and not used` / `declared but not used`) are an advisory ALLOW that shows the finding. Genuine findings (printf misuse, unreachable code, a syntax error, a missing return) still deny.
- A `go vet` finding located only in a sibling file is an advisory, not a deny of the file you just wrote.
- `build constraints exclude all Go files` (every file in the package carries a build tag) is an advisory, not a deny.
- A `gofmt -l -e` syntax check now runs first on the edited file and denies a syntax error. An unformatted file is not denied (formatting is left to the autofix step, as for other languages). It needs only the Go toolchain; `golangci-lint` stays an optional extended tier.

The commit-time `staged_lint_gate` is unchanged: a half-made change is still refused at commit.

#### Go development gets six smaller handler fixes (Plan 00527)

- `qa_suppression` also blocks gosec's `//nosec` and `#nosec`. `//nolint` stays blocked even with a stated reason: a suppression is a human's conscious decision.
- `comment_size` treats a Go package doc comment (the comment block directly above the `package` clause, usually in `doc.go`) as API documentation, so it is exempt from the size limit. Every other Go comment keeps the limit, and `comment_changelog` still reads the package doc.
- `auto_continue_stop` recognises Go test failures (`--- FAIL: TestX`, `FAIL`, `FAIL<TAB><pkg>`) wherever it recognises pytest's.
- `lsp_enforcement` treats `func Name` as a definition search, like `def name`.
- `lsp_enforcement`'s one-named-file exemption no longer exempts a bare directory target such as `rg x src/pkg`: rg searches it recursively, so it is judged like any directory search.
- The `llm-command-wrappers` guide uses golangci-lint v2's `--output.json.path` (v1's `--out-format json` was removed in v2) and says golangci-lint is optional; `gofmt -l`, `go vet` and `go test -json` are the baseline.

#### Go TDD gate works per package, and error_hiding_blocker stops flagging comma-ok forms (Plan 00527)

Two Go handlers fired on ordinary, idiomatic Go. `tdd_enforcement` demanded one `_test.go` per new file although Go tests per package, and only looked in `src/`, `cmd/`, `pkg/` and `internal/`. It now passes a new `.go` file when its directory already holds any `*_test.go`, exempts generated files (the `// Code generated ... DO NOT EDIT.` header, `*.pb.go`, `*_gen.go`, `zz_generated*`), `doc.go` and `cmd/<name>/main.go`, and enforces every other `.go` file inside a module (a `go.mod` at or above it), including root-level and `api/`-style packages. A `.go` file with no `go.mod` above it is no longer gated. `error_hiding_blocker` now ignores `v, _ := m[k]`, `x, _ := y.(T)`, `for i, _ := range xs`, `_, _ = fmt.Fprintf(...)` and anything inside comments or string literals, still blocks a blank last value from a function call (`n, _ := strconv.Atoi(s)`), and newly blocks an `if err != nil` whose body is only a comment.

#### The sub-agent worktree guard forgets a worktree that has been removed (Plan 00528)

`subagent_worktree_write_guard` binds each sub-agent to the linked worktree of its first `Write`/`Edit`/`NotebookEdit`. A sub-agent working in the main checkout that made a scratch probe worktree, wrote a test file in it and removed it again stayed bound to the deleted probe, so its report write into the main checkout was denied with R-SUBAGENT-CROSS-WORKTREE-WRITE. A binding whose worktree is no longer on disk is now dropped and the write is judged as if unbound. A probe that still exists keeps the binding, so sub-agents should not `Write`/`Edit` inside a worktree they made themselves; the resident guidance now says so.

#### `worktree-reap` gives the removal time to finish and no longer calls a failure a dry run (Plan 00474)

`hooks-daemon worktree-reap --reap` ran `git worktree remove` under the 5 second timeout meant for git metadata queries. Removal deletes the whole tree, and an agent worktree carries its own venv, so git was killed mid-delete. That left a half-deleted worktree with its `.git` file already gone, which git then refused to remove ("validation failed"). The removal now has its own limit (`Timeout.GIT_WORKTREE_REMOVE`, 300 seconds). If even that is exceeded, the report says the removal was interrupted and may be partial, and names the recovery: `git worktree prune`, then `git branch -d <branch>`.

The same command printed `DRY-RUN` for any worktree it did not remove, including a git refusal or failure under `--reap`. Under `--reap` that line now reads `FAILED`; a run without `--reap` still reads `DRY-RUN`. The safety contract is unchanged: removal never uses `--force` and the branch delete never uses `-D`.

#### A restart that regenerates an identical CLAUDE.md block no longer runs the markdown formatter (Plan 00495)

Every daemon start regenerated the `<hooksdaemon>` block in `CLAUDE.md` and ran the markdown formatter over the whole file, about 0.2 s of CPU on a 114 KB `CLAUDE.md`. The injector now records, inside the repository's git directory (`hooks-daemon-claude-md-format`), a fingerprint of the last text it formatted and the file it produced. When the next start would format the same text and `CLAUDE.md` is still exactly that output, the formatter is skipped and the file is left as it is. Any change to the generated block, or any edit anywhere else in `CLAUDE.md`, runs the formatter exactly as before and produces the same result. Outside a git repository nothing is recorded and every start formats.

Nothing needs to be done on upgrade, and no file is added to the working tree or needs a `.gitignore` entry.

#### The docs and plan QA session-start sweeps are cached and no longer hold up the chain (Plan 00495)

`docs-qa-sweep` and `plan-qa-sweep` re-ran their whole check catalogue on every new session. On a repository with a large documentation tree that is several CPU-seconds, enough to overrun the SessionStart dispatch budget so that handlers behind them were dropped.

Each sweep now keeps its last result in `<daemon untracked dir>/sweep-cache/<sweep>.json`, keyed by a fingerprint of everything that can change a finding: the stat of every file git lists for the project (tracked, plus untracked and not ignored, so gitignored trees such as `target/` or `dist/` are never enumerated; a directory walk outside a git repository), minus dependency and cache directories and the daemon's own runtime directory, the policy, the daemon version, the date and, for the plan sweep, the HEAD commit and plan counter. A session with an unchanged fingerprint reports the cached result. Any change is a miss: the sweep runs on a background thread and the handler waits at most one second for it. A sweep that finishes in that time is reported as before. One that does not is reported as "still running in the background" with the previous result labelled as possibly out of date, and its result is cached for the next session. Nothing is dropped and no check is skipped; `hooks-daemon docs-qa --sweep` and `plan-qa --sweep` still run in the foreground against the live tree.

No configuration change is needed. Deleting the `sweep-cache/` directory forces a full sweep at the next session start.

#### The daemon parses its config once per start, on the C YAML parser (Plan 00495)

The daemon start read `.claude/hooks-daemon.yaml` four times with PyYAML's pure-Python `SafeLoader`: once to load the config, once in the controller's config validation, and once in each of the two config-driven asset syncs (agent assets, directory-role rules), which each rebuilt the whole config model as well. The file is now parsed once and the loaded config is reused by all four steps. Config validation still runs on the parsed document, so a config the validator rejects still starts the daemon in degraded mode exactly as before.

The parse uses PyYAML's `CSafeLoader` where PyYAML was built with libyaml, and falls back to `SafeLoader` where it was not. Both are safe loaders; the unsafe loader is never used. Start-up CPU on this repository's own 87 KB config fell from about 1.9 s to about 1.2 s (median of 6 interleaved runs). A config nested deeply enough to overflow libyaml's C stack (thousands of brackets, or a line led by thousands of indentation columns or `-`/`?`/`:` indicators) is parsed by the pure-Python loader instead and reported as an invalid config rather than crashing the daemon. Nothing needs to change in your config.

#### Handler registry discovery runs once per daemon process (Plan 00495)

`HandlerRegistry.discover` imports and inspects every handler module. The daemon start ran it twice, once inside the config model's handler-dependency validation and once in the controller (four times before the config is parsed once, see the config-parse callout). The result for a package is now kept for the life of the process, and later registries take it instead of scanning the package again.

The measured saving is small: with the handler modules already imported, a repeated scan cost about 6 ms; nearly all the cost of discovery is the first scan's imports, which cannot be skipped. The change removes redundant work and has no effect on which handlers are found, how they are configured or what they do. A package that fails to import is not remembered, so it is retried.

#### The daemon binds its socket before the non-essential start-up work (Plan 00495)

The daemon start used to finish everything before it bound its socket: the `<hooksdaemon>` block regeneration in `CLAUDE.md`, the agent-asset and directory-role-rules syncs, and the guard-index pre-warm all ran first, so the status line and the first hook waited on work that has no bearing on how a request is judged. The socket is now bound as soon as the handlers are registered and the config is validated, and those four steps run in a worker thread behind it.

On this repository's own config, in a throwaway project, the first request was answered after a median of 1.94 s before and 1.51 s after (8 interleaved starts each), and the `start` command returned after 2.12 s and 1.68 s. The deferred work finished about 0.5 s after the first answer.

A request that arrives while the deferred work runs is answered exactly as it would be afterwards: the config validation that decides degraded mode, and the handler registration, are not deferred. A deferred step that fails is logged at ERROR and the remaining steps still run. For about half a second after a start, `CLAUDE.md`, `.claude/agents/` and `.claude/rules/` may therefore still show the previous start's content. Nothing needs to change in your config.

#### The secret-file guard judges a large script Write faster (Plan 00474)

`secret_file_guard` shell-tokenised every line of an authored script to look for a `cd` or `pushd` whose target a later relative path would be read from. It now tokenises only a line that could start with one of them, and a non-shell source file (`.py`, `.js` and the rest), whose scan never uses those directories, skips the step entirely. Every verdict is unchanged: the guard's tests and a pinned corpus of protected-path spellings give the same answer before and after.

Measured on the same host with the shipped protected patterns, a benign `.sh` Write took 376 ms before and 205 ms after at 120 KB, and 4.6 s before and 2.5 s after at 1.2 MB; a `.py` Write took 944 ms before and 740 ms after at 120 KB. A large Write still costs more than the 100 ms the daemon aims for, because the guard's brace-word and Python string-literal scans still read the whole file. Nothing needs to change in your config.

#### `lsp_enforcement` judges a bare directory search by the files it holds (Plan 00527)

`lsp_enforcement` decides whether an enabled language server can answer a search from the file type it names (a glob, an rg type, a file path). A search naming only a directory, such as `rg -n "agent_bus_lxc_bridge" playbooks`, names no type, so any enabled server counted as covering it. A snake_case Ansible variable searched in a YAML-only tree drew the `block_once` deny and was pointed at a Python language server that cannot read YAML. Now, when every target is an existing directory and no type is named, a bounded survey of the files those directories hold decides: no file a served language handles means advice, not a deny. A survey that cannot decide (over 2000 entries, or an unreadable directory) keeps the previous answer.

#### A valid Ansible task or handler file is no longer denied by the lint check (Plan 00474)

The Ansible lint strategy checked every claimed YAML file with `ansible-playbook --syntax-check`, which parses each top-level item as a Play. A role's `tasks/main.yml` or `handlers/main.yml` is a list of tasks, so every valid one was denied (`'ansible.builtin.debug' is not a valid attribute for a Play`) by `lint_on_edit` and by `staged_lint_gate`, and no edit could clear it (GitHub issue 121).

A file in a `tasks` or `handlers` directory is now checked through a generated one-play wrapper that imports it by absolute path. A valid task or handler file passes, and a YAML error or an unknown module in it is still reported, naming the real file. Playbooks are checked as before. The wrapper is written to the daemon's private lint output directory, never beside your source.

Two behaviour changes to know about:

- The default command template is now `ansible-playbook --syntax-check {playbook}`. `{file}` still means the real file, so a `command_overrides` entry for Ansible that uses `{file}` (and `ansible-lint {file}`) is unaffected. An override that spells the old default is unaffected too, but will keep the old failure on task files.
- A `roles/` directory no longer claims a file by itself. A role's `defaults`, `vars` and `meta` YAML (data, neither plays nor tasks) are not linted; files under `tasks/`, `handlers/` and `playbooks/`, and any file whose content has a top-level `hosts:` or `import_playbook:`, still are.

#### `list-venvs` and `prune-venvs` name the venv that is actually in use (Plan 00474)

`list-venvs` printed a "Current Python-env fingerprint" and `prune-venvs` printed "Current venv:" and "Current venv preserved:", all computed from the PROJECT root. Venvs are keyed on the daemon directory (`.claude/hooks-daemon/` in a client install), so the printed name belonged to no venv, and the venv the daemon was running from was not marked `current` by its name (GitHub issue 120). The same split showed in this project's own self-install, where the header named one fingerprint and the table marked another.

Both commands now ask the one resolver that the bootstrap and `ensure_venv` use. The first line of `list-venvs` reads `Current venv (the one the resolver selects): <fingerprint>` and names a venv that exists; the row for that venv carries the `current` marker. When a venv built now would get a different fingerprint (for example after a Python upgrade), `list-venvs` says so on a second line. `prune-venvs` reports the same name, and never selects the venv the resolver uses in either install mode.

The output text changed: anything that parses the old `Current Python-env fingerprint:` line needs updating. `list-venvs --json` is unchanged.

#### The markdown formatter no longer escapes GitHub footnotes (Plan 00474)

`markdown_table_formatter`, `format-markdown` and the CLAUDE.md injector share one mdformat transform, and it did not understand footnotes. A footnote definition such as `[^one]: The source.` was rewritten to `\[^one\]: The source.`, so GitHub showed it as literal text and the reference `[^one]` as plain brackets (GitHub issue 122). A reference starting a wrapped line was escaped the same way.

The transform now enables the `footnote` extension alongside `gfm`, so references and definitions pass through a format unchanged. Files that never used footnotes format exactly as before.

**New dependency**: `mdformat-footnote>=0.1.1` (pure Python; it pulls in only `mdformat` and `mdit-py-plugins`, both already installed). A client install picks it up on upgrade: the upgrade rebuilds the daemon venv, because the venv's recorded hash of `pyproject.toml` and `uv.lock` (and its version stamp) no longer match. A `restart` alone never installs it; if the daemon is running from a venv built before this change, run `bin/hooks-daemon repair`. Until then the formatter still works: it enables footnote support only when the plugin is installed, logs one WARNING when it is not, and formats tables and the rest of GFM as before. A footnote already escaped by an earlier format stays escaped until you remove the backslashes by hand.

#### A daemon venv built for an older dependency lock is rebuilt by every build, and named when it still runs (Plan 00474)

A venv records the hash of the `pyproject.toml` and `uv.lock` it was built for. Every venv build (the upgrade, `install`, provisioning and the automatic first-venv build) now rebuilds a venv whose recorded hash differs from the current one, even when its daemon-version stamp matches. Before, a matching stamp let it be reused without a dependency the source had just added.

`restart` and a daemon started by a hook still do not build a venv. When the venv the daemon runs from was built for another lock, or records none, session start, `restart` and `status` now say so and name the fix: `bin/hooks-daemon repair`. `repair` also records the lock it synced for, so the daemon starts from the repaired venv and the notice clears.

#### Subagent spend is measured, and large subagents are told to hand off (Plan 00471)

Subagents were most of a coordinated session's token spend (86.5 % in the measured run), much of it from agents re-reading contexts above 200k on every call and from finished agents resumed cold. The daemon now measures that spend and advises on it:

- **`hooks-daemon spend [--session ID | --transcript PATH] [--by agent|plan] [--json]`** prints a session's subagent ledger: per agent or plan, requests, largest and mean context, input-token equivalents, compactions and inbound messages, plus the `compact_boundary` distribution and the count of gate calls that could not measure. It exits 1 when the session's agent directory exists but cannot be listed, rather than reporting an empty session. The ledger is also written per agent at each SubagentStop (`subagent_cache_aggregator`, now reading only the bytes appended since the agent's last stop).
- **`subagent_context_budget`** (on): a subagent past `soft_tokens` (300000) is told once to write a handoff file, commit, and message the lead. Its hard band (`hard_tokens`, shipped null) allows only the handoff steps and pairs with **`subagent_handoff_gate`**, which holds the stop until the handoff exists. A `budget: <N>k` line in a named dispatch's prompt raises one agent's budget, up to `max_override_tokens`.
- **`resume_guard`** (on, advisory): a SendMessage that would cold-resume a stopped agent at 250000 tokens or more says to spawn a fresh agent from its report instead. `mode: deny` makes it a refusal; `RESUME-LARGE: <reason>` overrides. A structured message (a plan approval, a shutdown request) is never gated, even under `mode: deny`.
- **`spawn_rate_advisor`** (on): at 80 % of the five-hour usage limit a spawn draws "serialise now" with the reset time, read from the same usage snapshot the status line's usage chip shows; a live-agent cap (`max_concurrent`) is available and off by default. **`background_task_recorder`** keeps the live count honest from each Stop.
- **`review_round_advisor`** (opt-in) and the **`spend_meter`** status segment (`Σ⚙ <ite> · N live · max <ctx>`).

None of these can lose work. Every gate that cannot measure an agent allows the call and records one `unmeasured` verdict: a transcript that cannot be read, one with no usage in its last 4 MiB (a likely format change, read in bounded time), or a failure inside the gate itself. Nothing denies by default. Each per-agent ledger row also records the five-hour usage percentage at the agent's stop (`five_hour_pct`, null when unknown), so the relationship between cache reads and the five-hour limit can be read off later. The ledger lives in `spend-ledger/<session>/` and, for the per-agent rows, `cache-sidecar/<session>/` under the daemon's untracked directory. The new `daemon.spend_ledger_retention_days` (default 90) sets how long the start-up cleanup keeps both; `cache-sidecar/` session directories previously went after `stale_file_days`. The `spend-offsets/` cache still ages out after `stale_file_days`.

#### Which model each subagent runs on is measured, and a cheaper tier is suggested (Plan 00472)

A subagent nobody picks a model for runs on its spawner's. In the measured run, 36.5 % of agents never had a model chosen and almost all of them ran on Opus; a `Workflow` script's `agent()` calls do the same unless they pass `model`. The daemon now records the choice and advises on it. Nothing here denies.

- **Every `Agent` dispatch gets a tier row** in the spend ledger (`spend-ledger/<session>/dispatches/`): how its model was chosen (`fork`, `explicit`, `definition`, `env`, `inherited-capped`, `inherited`), the family that predicts, a role label and any `tier: <reason>` line. `agent_dispatch_recorder` now writes a row for unnamed dispatches too, and the new **`dispatch_model_recorder`** (PostToolUse) adds the model that actually started. Each per-agent ledger row also gains `tool_use_id` and a `downgraded` flag when the safety fallback swapped its model.
- **`hooks-daemon tiers [--session ID | --transcript PATH] [--by type|role|source] [--json]`** prints agents and spend by source, model and role, whether `CLAUDE_CODE_SUBAGENT_MODEL` is set in `.claude/settings.json`, and every agent whose model was swapped mid-run.
- **`subagent_tier_advisor`** (on): a dispatch that inherits Opus or above, or passes a `model` above its definition's own, gets a two-line note naming the cheaper tier, once per session, type and source. A `tier: <reason>` line in the prompt keeps the tier silently. Security, adversarial, decision and review work is never nudged. Ceilings and floors per agent type are configurable and ship empty.
- **`workflow_fanout_advisor`** (on): a `Workflow` call gets a note with the agent count, the `agent()` sites with no `model`, and whether the count is over the ceiling for the session's tier (fable 10, opus 25, sonnet 60, haiku 60). The first call of each session records the call's key names and value types (never values or the script) in `payload-capture/workflow-shape.json`.

**Recommended, not applied:** `CLAUDE_CODE_SUBAGENT_MODEL=sonnet` in `.claude/settings.json` moves every inherited subagent off the main model. Pin reviewers and security checks to `model: opus` (or configure floors) first. See `docs/guides/SUBAGENT_MODEL_TIERS.md`.

#### Four fixes found by CI after the subagent-tier release work (Plan 00474)

- **A deeply nested config no longer kills the daemon.** libyaml composes nested collections by C recursion with no depth limit, so a flow document nested tens of thousands deep overflowed the C stack. A document with more than 1000 opening brackets is now parsed by the pure-Python loader, which raises `RecursionError`, reported by `Config.load` as a `ValueError`. Real configs are far below the threshold and keep the fast loader.
- **The installer emits the SessionStart background-sync block.** `install.py` generated a `session-start` forwarder without the block that syncs in the background, so a fresh install differed from the tracked hook. Re-run the installer (or an upgrade) to get it.
- **Protected files are left out of the sweep fingerprint.** `tree_fingerprint` stated every tracked path, including ones the project marks as protected, so editing a protected file moved the fingerprint. Protected paths are now skipped.
- **Go 1.20+ `declared and not used: x` is allowed mid-edit.** `lint_on_edit` for Go treated the newer message, which appends the variable name, as a genuine finding and denied; it now shows it as an advisory like the older spelling.

#### Tune the plan fact-checker for your project, and be told when the template moves (Plan 00531)

The generic `hooks-daemon-plan-fact-checker` knows nothing of your codebase's layout, test commands or vocabulary, so it checks less well than it could. It can now be tuned the way the daemon's other deployed Claude Code config is managed: the daemon ships the generic agent, you keep a tuned copy, and the copy records which shipped version it started from.

- **The feed dispatches your tuned copy.** Set `handlers.post_tool_use.plan_fact_check_feed.options.tuned_agent` to the name of an agent under `.claude/agents/`. While it is set and the file exists, the feed's instruction names it and a dispatch of it counts as the check being taken up. Unset, or naming an agent that is not deployed (a warning is logged), the generic agent is used.
- **You are told once how to tune it.** While the generic agent is in use, the first fact-check instruction also says how: copy the shipped file to a name of your own, add what the checker should know, set `tuned_agent`. The shipped template's header says the same. Template version 1.1.0; a pristine 1.0.0 deployment is refreshed on upgrade.
- **A copy records where it started.** Replace the copy's `hooks-daemon-agent-version` line with an HTML comment holding `hooks-daemon-derived-from: hooks-daemon-plan-fact-checker 1.1.0`. When a newer template ships, `deployed_artefact_drift` reports the copy at session start, names the shipped file to compare with, and says to update the marker once you have ported what helps. The daemon never edits your copy.

#### `remote-docs refresh` says why a document failed, retries once, and stops closing every browser (Plan 00474)

`hooks-daemon remote-docs refresh` printed `<path>: failed` with no reason, and nothing retried. On a large refresh about half the documents failed that way and each succeeded when refreshed alone.

- **The cause is printed.** A failed document now has an indented line under it naming the cause (the fetcher's own error text, or the file it could not write).
- **A failed fetch is retried once**, after a two second pause. A document that recovers reports its normal outcome.
- **The race is fixed at its source.** Each browser read now runs in its own named agent-browser session and closes only that session. It used to run `agent-browser close --all` after every read; that returns before the shared browser daemon has exited, so the next read reached the dying daemon and got an empty response (7 of 15 back-to-back reads failed that way, none did with one session per read). `close --all` also ended every other agent's browser on the machine. Nothing needs to change in your config.

### Handler authors

#### A deliberate log-and-continue is one named, reasoned helper (Plan 00474)

The error-hiding audit now flags any `except` body that only logs and then continues, returns a fallback or passes, not just a lone inline log call. The one accepted form is `claude_code_hooks_daemon.utils.deliberate_swallow.log_and_continue(logger, exc, reason=...)`, whose required `reason` states why swallowing is correct. The daemon's own swallow sites were converted to it, so a failure that is deliberately skipped is now recorded with its reason and traceback. Project handlers that log and carry on should use the helper.

#### The vendored hooks contract matches the current upstream hooks doc again (Plan 00474)

`contracts/claude-code-hooks/META.json` now records the upstream hooks page as fetched on 2026-10-12 (268811 bytes), still audited at Claude Code 2.1.296, so `bin/hooks-daemon contract-status` reports `unchanged` again. The refresh changed what the contract says about: the `agent_id` input field, which upstream now describes as identifying the subagent or in-process teammate the hook fires in and no longer states is absent from a main-thread call; the `Elicitation` and `ElicitationResult` exit-2 and output behaviour (an exit-2 decline shows no dialog, an `Elicitation` answer skips `ElicitationResult` hooks) and the `ElicitationResult` example, which no longer carries `elicitation_id`; the extra triggers of `WorktreeCreate` and `WorktreeRemove` (`EnterWorktree`, `ExitWorktree`, `claude remote-control`); the `PreToolUse` `allow` exception for reads from network paths; and the `SessionStart` PowerShell and plugin caveats. The vendored copy of the page under `remote-docs/` was refreshed with it. The daemon's own behaviour is unchanged.

## ⚠️ BREAKING CHANGES

### Handler Removals

- **`upgrade_approval_guard`** (PreToolUse) - Removed in v3.70.0
  - **Why**: The owner ruled the approval tier friction with no safety value: the threat model is a careless agent, not a hostile one, and an installed daemon older than the gate has no `approve-upgrade`, so a project could be stuck behind a long pipeline command just to say yes. Its rules `R-UPGRADE-APPROVAL-AGENT` and `R-UPGRADE-APPROVAL-ENV-BYPASS` and the `hooks-daemon approve-upgrade` command, exit code 4 and `upgrade-approvals/` markers go with it.
  - **Migration**: Delete the `upgrade_approval_guard:` block from `.claude/hooks-daemon.yaml` when convenient; a config that still names it keeps validating. Remove any `approve-upgrade` step or exit-4 branch from your upgrade runbook, read the "READ THIS FIRST" listing, and re-run with `--skip-reading-confirmation=<digest>`.
  - **Guide**: [v3.69.0-to-v3.70.0 Upgrade Guide](../CLAUDE/UPGRADES/v3/v3.69.0-to-v3.70.0/v3.69.0-to-v3.70.0.md)

### Command and File Changes

- **`prune-venvs --all-except-current`** - Removed in v3.70.0
  - **Why**: It removed every venv except one computed from the project root, which could be neither the venv in use nor provably stale.
  - **Migration**: Use `prune-venvs --stale` (preview with `--dry-run`), and `prune-venvs --unproven <path> --force` for a venv `list-venvs` reports as unproven.
  - **Guide**: [v3.69.0-to-v3.70.0 Upgrade Guide](../CLAUDE/UPGRADES/v3/v3.69.0-to-v3.70.0/v3.69.0-to-v3.70.0.md)
- **The gated-install receipt** - Moved in v3.70.0 from `upgrade-approvals/` to `untracked/upgrade-gate/gated-install.json`
  - **Why**: The approval markers directory no longer exists.
  - **Migration**: None. A project that had a receipt is asked for the reading once on a same-version re-run; its first upgrade through the gate records the new receipt.
  - **Guide**: [v3.69.0-to-v3.70.0 Upgrade Guide](../CLAUDE/UPGRADES/v3/v3.69.0-to-v3.70.0/v3.69.0-to-v3.70.0.md)

## Installation

### New Installations

```bash
mkdir -p .claude
git clone -b v3.70.0 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon

# The installer builds the fingerprint-keyed venv, installs the package and
# starts the daemon. Never hand-build a venv — the resolver refuses the
# retired pre-v3.7.0 layout.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
git -C .claude/hooks-daemon fetch --tags

# Rebuilds the venv and reinstalls the package for the target version. Runs the
# target's own upgrade.sh: the installed one may predate the pre-deploy gate.
tmp="$(mktemp)"
git -C .claude/hooks-daemon show "v3.70.0:scripts/upgrade.sh" > "$tmp"
bash "$tmp" --project-root "$PWD" "v3.70.0"
# Exit 3: read what it lists, then re-run with the --skip-reading-confirmation=<digest> it printed.

.claude/hooks-daemon/bin/hooks-daemon restart
```
