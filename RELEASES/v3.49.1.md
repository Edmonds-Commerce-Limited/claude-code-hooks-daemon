# Release v3.49.1 - The PLAN-vs-JOURNAL Contract

**Release Date:** 2026-07-31
**Type:** Patch
**Plan:** [00190](../CLAUDE/Plan/00190-plan-journal-separation-and-size-enforcement/PLAN.md)

## Summary

This release establishes the **PLAN-vs-JOURNAL contract** and fixes five bugs
where the two rule-sets had bled into each other.

`PLAN.md` and `JOURNAL/` are governed by near-**opposite** rules. Applying the
wrong set to a file is a defect in either direction — and every bug fixed here
is an instance of exactly that, including one that blocked the journal entry
documenting it.

**No enforcement thresholds ship in this release.** This is the contract and
the groundwork. Tiered plan-size enforcement is designed and tracked in Plan
00190 Phases 2-5, not yet built. Do not go looking for size limits — they are
not live.

## READ THIS FIRST: the contract

Every file in a plan folder is exactly one of these. **Applying the wrong
column's rules is a defect in either direction.**

|                 | `PLAN.md` — the plan document                                                                                                                                          | `JOURNAL/NNNNN-Journal-YY-MM-DD.md`                                        |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| **Answers**     | What are we building, and where does it stand *now*?                                                                                                                   | What happened, in order?                                                   |
| **Read**        | **In full, every session.** It is your grounding.                                                                                                                      | **Never in full.** Grep it, tail the newest day-file, or send a sub-agent. |
| **Write**       | Rewrite freely — curate, delete, restructure.                                                                                                                          | **Append only.** Never edit or remove an earlier entry.                    |
| **Corrections** | Fix the text in place.                                                                                                                                                 | Add a new, later entry that corrects it.                                   |
| **Size**        | **Bounded** — *because* you read it in full. (By discipline; no threshold ships yet.)                                                                                  | **Unbounded** — safe *because* you never read it in full.                  |
| **History**     | In git, not in the file body.                                                                                                                                          | In the file body. That is the point.                                       |
| **Workflow**    | Commit if dirty → edit → commit, so each change lands as an isolated, reviewable, revertable diff — which is *why* nothing needs keeping in the file "for the record". | Append → commit.                                                           |

### The size rules are consequences of the read rules

This is the ethos, and it is why the rules are not arbitrary hygiene:

- `PLAN.md` must stay lean **because** it is re-read whole every session. Its
  size limit is *derived from its read cost*.
- A journal may grow forever **because** it is never read whole. Unbounded
  growth is safe *only* under a bounded read discipline.

Break one rule and the other stops making sense.

### Supporting docs

`BRAINSTORM-*.md`, `AUDIT-*.md`, `CRITIQUE-*.md`, field reports — any other
`.md` in the plan folder — follow **neither** column: written once, revised
freely, read on demand when their subject comes up. When you want to write
narrative, move it OUT of `PLAN.md` into one of these or into `JOURNAL/`.
Never leave it in the plan.

### Reading a journal without flooding your context

Three bounded moves, cheapest first. All are permitted by this daemon's own
handlers — verified, not assumed:

1. **Where did we leave off?** — `ls <plan-folder>/JOURNAL/` (day-file names
   sort chronologically, so the last line is newest), then
   `tail -n 40 <newest day-file>`. Run `tail` **directly on the file** — with no
   pipe, `pipe_blocker` never applies.
2. **What did we decide about X?** — `grep -n "X" <plan-folder>/JOURNAL/*.md`.
3. **Reconstruct a whole thread of work** — dispatch a sub-agent to read the
   `JOURNAL/` and report back: it absorbs the volume; your context receives the
   conclusions, not the log. (`Explore` is the right agent type — read-only,
   returns conclusions rather than file dumps.)

Two pipe rules worth knowing precisely, because the loose version of each is
wrong:

- `pipe_blocker` denies a pipe into `tail`/`head` **only when the source command
  is not whitelisted**. `pytest … | tail -20` is denied; `cat file | tail -40`
  and `grep … | tail -20` are allowed, because `cat`, `grep` and `rg` are on the
  universal whitelist. It is *not* true that every `… | tail` is blocked.
- `ls … | sort … | tail -1` **is** denied — not by `pipe_blocker` but by
  `plan_number_helper`, which treats a sorted-and-tailed listing of the plan
  directory as plan-number discovery. Use plain `ls` instead; day-file names
  already sort chronologically.

## Why this release exists

### The problem

Agents conflate `PLAN.md` with `JOURNAL/`. They append narrative progress —
session logs, findings, dead-ends, pasted output — into the plan document
instead of the journal. The plan then grows monotonically and is never curated,
until it is too expensive to read and too tangled to trust.

### The evidence

This repo holds **187** `PLAN.md` files (active + `Completed/`). Churn was
measured with `git log --numstat --follow` over the **183** of them with enough
history to measure:

- median `del/add` ratio: **0.077**
- **15.8%** have never deleted a single line
- PLAN.md editing is **~92% additive**

A genuinely curated specification shows substantial deletions as resolved
material is condensed away. These files are appended to, not curated — they are
being edited *as journals*.

Meanwhile the existing plan-QA sweep reported the whole tree as essentially
clean (2 advisory findings, neither about size). **No check measured size,
growth, or curation**, so the drift was not merely unenforced — it was
*invisible* to the tooling that exists to catch plan rot.

### Journalling amputates the tail, it does not shrink the median

Comparing only **mature** plans — those with ≥300 cumulative added lines, so
that short or barely-started plans (small in both groups) cannot drag the
medians together — those **with** a `JOURNAL/` sit at a median of 16.6 KB
against 17.3 KB without. Statistically indistinguishable. But p90 is 23.4 KB
vs 36.4 KB, max is 25.8 KB vs 57.2 KB, and **zero** journal-era plans exceed
35 KB.

(Across the *whole* corpus, mature and immature together, the median plan is
~9.3 KB. That figure and the 16.6/17.3 KB pair above describe different
populations — do not compare them directly.)

A plan's irreducible content — overview, goals, task tree, decisions, success
criteria — is ~10-20 KB regardless, and journalling neither can nor should
touch it. Everything beyond ~25 KB is accreted narrative, and that is exactly
what the journal absorbs. Journalling and size discipline are **complementary,
not redundant**.

## Two hazards this design guards against

These shaped every fix in this release, and they will shape the enforcement
that follows.

### 1. Delete-instead-of-relocate

Telling an agent only *"your plan is too big"* invites it to **delete** content
to satisfy the check — destroying the record while passing. Every message about
plan size must name `JOURNAL/` as the destination and state that the journal
grows freely.

There is a second remedy that must also be named. Analysis of this repo's six
worst offenders found that **only one is a journalling failure**: plan 00101
collapses from 45.6 KB to ~9.5 KB (the whole-corpus median, ~9.3 KB) once its dated incident
blocks move out. The other five are **over-scoped, not journal-polluted** —
after perfect curation, plan 00100 is still 45.8 KB because its task tree alone
is 28.5 KB. Naming only "move it to `JOURNAL/`" to such a plan is actively
harmful: with no narrative left to relocate, the only remaining lever is
deleting genuine task content. The correct second remedy is **split the plan**.

### 2. Scope-dependent signals

Dated headings, `## HH:MM ·` entries, past-tense narrative and pasted
tracebacks are **correct journal content**. They are only a defect signal when
found in a *plan document*. Any content-shape detector needs an explicit
file-scope predicate, or it will fire on exactly the files that are behaving
properly.

The corollary drives the fix style in this release: these are **location
rules, not content-quality rules**. Phrase everything as *"this belongs in the
journal"*, never *"this is bad"*. An agent told "wrong place" relocates; an
agent told "bad content" deletes.

## Highlights

### The bug that reproduced itself

While the audit was being written up, `plan_time_estimates` **blocked the
journal entry documenting it** — because the entry quoted the bug's own
symptom. The handler blocked the journal entry about the handler blocking
journal entries.

Its `matches()` gated on `"/Plan/" in file_path` plus an `.md` suffix, which
matched all 187 `PLAN.md`, 107 supporting docs, **and** all 28 journal
day-files. A plan-document rule enforced on an append-only log: the exact
bleed, shipped and live.

### An injected instruction outranks a doc

`recovery_cron_advisor` carried the only *injected* instruction in the daemon
telling an agent to write the activity stream into `PLAN.md`
(*"Record the cron ID in this plan's Notes & Updates section"*). It contradicted
`CLAUDE/PlanWorkflow.md`, which says record it in the `JOURNAL`.

An instruction injected into the session beats a doc an agent may never open.
This is worth internalising when auditing guidance: **check what the handlers
inject, not just what the docs say.**

### A scaffolder that contradicted itself in one run

`mkplan.bash` wrote a `## Notes & Updates` heading pre-seeded with a dated
entry — a worked example of the anti-pattern — *while the same script
scaffolded* `JOURNAL/`. That fallback path is reached whenever `_TEMPLATE_.md`
is absent, i.e. every drop-in deployment before `deploy-plan-workflow` has run,
so it shaped first impressions in client projects.

### Config demarcation

`plan_workflow.qa.journal.mode` is a **ceiling, not a guarantee**. Surface
modes (`edit_mode`, `commit_gate_mode`, `sweep_mode`) are document-type
*agnostic* gates; `journal:` is a document-type sub-block **subordinate** to
them. `journal.mode: block` only denies when the surface mode is also `block`,
and `edit_mode: off` disables both journal edit checks regardless of
`journal.enabled`. The behaviour is correct; only the documentation was wrong,
so only the documentation changed — and two regression tests now pin the
semantics so the next person gets a failing test, not a stale sentence.

## Changes

### Fixed

- `plan_time_estimates` no longer fires on journal day-files. Exemption keys on
  the day-file **grammar** (config-independent, matching
  `markdown_table_formatter`) so disabling an unrelated knob cannot re-open the
  bleed.
- `recovery_cron_advisor` no longer instructs writing into the retired section
  (four sites: runtime guidance, two `get_claude_md()` rows, progress
  detection).
- `journal-append-only` remediation now states the journal is unbounded by
  design and must not be tidied.
- `mkplan.bash` fallback emits the `## Delivery & Milestones` stub instead of
  pre-seeding the retired section.

### Changed

- `journal.mode` subordination documented in `config/models.py`,
  `docs/guides/HANDLER_REFERENCE.md`, and both `PlanJournalling.md` copies.
- `plan_time_estimates` guidance now states its true scope
  (`CLAUDE/Plan/**/*.md` except journal day-files).

### Not shipped (tracked in Plan 00190)

- Tiered plan-size enforcement (advise → warn → block)
- The `PlanFileKind` SSoT path classifier
- `docs/PLAN_SYSTEM.md` corrections (it still teaches dated logs inside
  `PLAN.md` — the largest remaining doc contradiction)

## Upgrade Instructions

Drop-in, non-breaking. No configuration migration required. No config keys were
added, renamed, or removed.

**One behaviour change to be aware of:** editing a `## Notes & Updates` section
in a `PLAN.md` no longer counts as a "progress" signal for the recovery-cron
advisory. Task-status icons (⬜/🔄/✅) still do, and every genuine progress
edit touches one under the plan template's task grammar.
