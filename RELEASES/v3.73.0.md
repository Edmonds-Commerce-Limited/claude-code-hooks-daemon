# Release v3.73.0 - Remote Branch Cleanup, Accumulating Recovery Bundles, arm64 hooks-screen

**Release Date:** 2026-11-07
**Type:** Minor Release

## Summary

A minor release on the branch-hygiene line. `branch-sweep --clean --remote` clears merged branches on the remote, recovery bundles accumulate instead of overwriting each other, branch containment sees a branch a remote keeps outside `refs/heads`, and the ccy supervisor finds `hooks-screen` by host architecture. Two guard fixes (`gh` view guards, `lsp_enforcement`) and CI sharding ride along. Five release-note callouts are folded into Highlights below, in the authors' own words.

## Read this first

- **No breaking change.** No config-changes manifest, no pre-upgrade task and no post-upgrade task ships, so the pre-deploy gate adds no stop of its own.
- **Truth-changes:** `CLAUDE/UPGRADES/truth-changes/v3.73.0.yaml` revises what project docs say about reading a `gh` issue or pull request (use `--json title,body,state,comments`, not `--comments`) and about where `delete-branch` recovery bundles live (one per call under `untracked/deleted-branches/`).
- **Upgrade guide:** `CLAUDE/UPGRADES/v3/v3.72.1-to-v3.73.0/v3.72.1-to-v3.73.0.md`.

## Highlights

#### gh issue/pr view guards now suggest a command that returns the body

_Plan 00565 · Audience: client projects_

The `gh_issue_comments` and `gh_pr_comments` guards used to tell an agent to append `--comments`, but without a terminal `gh ... view --comments` prints only the comments and drops the body (and prints nothing for an item with no comments). They now suggest `--json title,body,state,comments` (plus `author` for pull requests), which returns both, and their guidance says `--comments` alone omits the body in non-interactive output. What the guards match and block is unchanged, and `--comments` is still allowed (reported as issue #158).

#### lsp_enforcement no longer denies a grep over extensionless files no language server serves

_Plan 00567 · Audience: client projects_

A symbol-like `grep` that names two or more existing files with no suffix (for example `grep -n foo_bar bin/tool1 bin/tool2` over shell scripts) was denied whenever any language server was enabled, while the same search over their directory was only advised. Named files are now judged by their own suffix, and an extensionless file counts as unserved, so both forms get the same advisory. A named file with a served suffix is still enforced, including in a mixed list, and targets that cannot be judged (missing paths, a file list piped through `xargs`) keep the cautious answer that an enabled server covers the search (reported as issue #162).

#### the ccy supervisor finds hooks-screen by host architecture

_Plan 00569 · Audience: client projects_

The ccy supervisor used to look for the `screen/build.sh` output under a name pinned to `x86_64-unknown-linux-musl`, whatever the CPU. It now derives the target from the host architecture: x86_64/amd64 and aarch64/arm64, both on musl. An unsupported architecture skips that candidate (the `CCY_HOOKS_SCREEN` override and `untracked/bin/hooks-screen` still apply), and the fail-open note in the supervisor log names the architecture and the build it searched for. `screen/build.sh` defaults `SCREEN_TARGET` from `uname -m` the same way and refuses an unknown architecture. A client that excluded the deployed supervisor from its QA because of the pinned triple can drop that exclude (reported as issue #174).

#### branch containment sees what the remote holds outside refs/heads

_Plan 00570 · Audience: operators_

A remote can keep a finished branch under a namespace the clone never fetches, such as `refs/archive/<name>`. The sweep used to report that branch CONTAINED NOWHERE ("no remote ref holds its commits"), advise a `git push -u` that re-creates it on the remote, and `delete-branch` refused it as content found nowhere. The explicit commands `branch-sweep` and `delete-branch` now make one bounded `git ls-remote` (only when a branch would otherwise be unproven) and accept a remote ref at, or descending from, the branch tip as proof the remote holds it. They name the ref they relied on (`delete-branch` calls the new tier `remote-held`), and the sweep no longer advises pushing such a branch. A failed or timed-out listing falls back to the offline answer and says the remote could not be checked; it is never proof. The session-start summary and the branch creation guard stay network-free, and their text now says what was checked: no fetched remote-tracking ref of the remote holds the commits, with a pointer to `branch-sweep` for the remote check (reported as issue #166).

#### recovery bundles accumulate, and one command clears merged branches locally and remotely

_Plan 00571 · Audience: client projects_

`delete-branch` used to write every call into the same `untracked/deleted-branches.bundle`, so only the last deleted branch could be restored. Each call now writes its own bundle under `untracked/deleted-branches/`, named by UTC time plus a random suffix, and prints one exact `git fetch <bundle> refs/heads/<name>:refs/heads/<name>` restore line per deleted branch. `branch-sweep --clean` uses the same naming. An explicit `--bundle PATH` that already exists is refused rather than overwritten. An existing `untracked/deleted-branches.bundle` is left in place; it still holds the last branch deleted before the upgrade.

`branch-sweep --clean --remote` is new. It also deletes merged branches on `branches.remote`, using the proof the remote-delete guard already applies to an agent's `git push --delete` (the tip is an ancestor of the default branch or an integration line, and `ls-remote` confirms the live tip). Each delete carries a lease on that tip, and the remote tips go into the same recovery bundle. Every report that lists a merged branch (the sweep, the WIP-cap deny, the stop guard) now names `branch-sweep --clean` as the one-step fix, and `worktree-reap --reap-branches` prints each merged branch it skipped because it is not agent-owned (reported as issue #165).

`branch-sweep --clean` (with or without `--remote`) leaves running agents' worktrees alone. A worktree and its branch are skipped, with a `Skipped <name>: ...` reason, when a `running` work-queue record names them, when the worktree lives under `.claude/worktrees/` (Claude Code's own agent worktrees), or when git reports it `locked`. A freshly spawned agent's branch sits at the default branch's tip, so it used to look merged and removable. `worktree-reap` also keeps work-queue-running and locked worktrees.

#### Maintenance

CI is sharded by wall-clock time: one reusable shard workflow shared by `release-gate.yml` and `qa.yml`, a QA gate aggregator job, rebalanced integration and handler shards, and the release slate check now recognises the sharded full tier. This changes nothing for an installed project.

## Installation

### New Installations

```bash
mkdir -p .claude
git clone -b v3.73.0 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon

# The installer builds the fingerprint-keyed venv, installs the package and
# starts the daemon. Never hand-build a venv — the resolver refuses the
# retired pre-v3.7.0 layout.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
git -C .claude/hooks-daemon fetch --tags

# Rebuilds the venv and reinstalls the package for the target version. Runs the
# target's own upgrade.sh: the installed one may predate the pre-deploy gate.
tmp="$(mktemp)"
git -C .claude/hooks-daemon show "v3.73.0:scripts/upgrade.sh" > "$tmp"
bash "$tmp" --project-root "$PWD" "v3.73.0"

.claude/hooks-daemon/bin/hooks-daemon restart
```
