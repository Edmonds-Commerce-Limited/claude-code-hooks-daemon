# v3.19.1 — Host/Container venv Isolation Fix

**Type**: Patch release (bug fix)
**Previous**: v3.19.0

## Summary

A desktop-level Claude Code session and a containerised (ccy/Podman) session that open the **same bind-mounted project** are designed to each get their own Python virtual environment. On a machine where the desktop host and the container run the **same Python** (same `sys.version`, `sys.base_prefix`, and architecture) they were instead sharing **one** venv and fighting over it. This release restores the intended isolation.

## Root Cause

`ensure_venv` (`scripts/install/venv.sh`) computed the venv fingerprint with:

```bash
fingerprint=$(python_venv_fingerprint "$python_bin")   # project root never passed
```

`python_venv_fingerprint` only prepends the **project-path slug** (`venv-{slug}-py{MM}-{hash}`) when given a root. `ensure_venv` already had the root — its first argument, `daemon_dir` — but never passed it. The result: the venv was keyed by the bare, slug-less `venv-py{MM}-{hash}`.

The bare hash is `md5(sys.version | sys.base_prefix | platform.machine())`, which is **identical** for a host and a container that share the same Python. Because the project's `untracked/` directory is bind-mounted into the container, both views resolved to the **same** `venv-py{MM}-{hash}` directory and collided. The project-path slug (introduced in Plan 00100) is exactly the discriminator meant to keep a host view (`/home/user/project`) and a container view (`/workspace`) apart — and it was being dropped.

The Python resolver (`paths.py`) already passed the root and looked for the slugged name first, so this was also a silent disagreement between bash venv **creation** (slug-less) and Python venv **resolution** (slugged), masked by the resolver's broad `venv-*` scan fallback.

### Why it only surfaced recently

On a machine where the desktop Python differs from the container Python (different version / base prefix / arch), the bare hashes differ and the two coincidentally land on separate venvs even without the slug. The collision only manifests when the host and container Pythons match — the slug would have isolated them in either case.

## Fix

- **`scripts/install/venv.sh`** — `ensure_venv` now passes `$daemon_dir` to `python_venv_fingerprint`, so the venv is keyed by the project-path slug, matching the Python resolver's keyed lookup.
- **`scripts/upgrade.sh`** — the venv-discovery glob used for upgrade metadata was broadened from `venv-py*` to `venv-*py3*` so it matches both the new slugged names and legacy bare names.
- **Tests** — added a slug-isolation regression test to `test_ensure_venv.py`; updated install/upgrade acceptance tests to the slugged venv naming.

## Impact on Existing Installs

The change is backwards-compatible and self-healing. On the next daemon start after upgrading, `ensure_venv` creates the correctly-slugged venv and the daemon runs from it. The old slug-less `venv-py{MM}-{hash}` directory is harmlessly orphaned under `untracked/` — it is never selected again and may be deleted at leisure:

```bash
# Optional: remove the orphaned pre-3.19.1 slug-less venv
rm -rf untracked/venv-py*[0-9a-f]   # only the bare 'venv-py{MM}-{hash}' form
```

No config changes are required.
