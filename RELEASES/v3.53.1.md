# v3.53.1 — Generated Docs Stop Naming the Rendering Machine

A small release: 10 commits since v3.53.0. Two field-reported defects in
generated, tracked documentation, and one installer permissions bug.

## Fixed: generated tracked docs no longer name the rendering machine

`get_claude_md()` handler bodies and the docs generator built their example
commands from the runtime path builder, whose ABSOLUTE output the injector
writes verbatim into the tracked `<hooksdaemon>` block of `CLAUDE.md` (and the
header of `.claude/HOOKS-DAEMON.md`) and auto-commits. On a client install that:

- published the developer's home directory into a committed — sometimes
  public — file
- named a directory that exists on no other clone
- rewrote itself per machine whenever two developers, or a host and a
  container view of one bind-mounted repo, regenerated it

A new `daemon_cli_command_for_docs()` builder emits a project-root-relative
command instead — `.claude/hooks-daemon/bin/hooks-daemon status` in a client
install, `bin/hooks-daemon status` in self-install — routed through 11
tracked-doc call sites. **Runtime output is untouched**: block reasons and
advisory context stay absolute and copy-paste runnable from any working
directory, per Plan 00192's existing contract. Only the tracked destination
moved. Reported from a client install against v3.51.0.

A second, related defect: `absolute_path` and `root_recursion_guard` both had
this repository's own self-install root, the literal `/workspace`, hard-coded
into their worked examples — so every client install was told to prepend or
scope to a directory that does not exist on their machine. `absolute_path` now
resolves the real project root for its example (and omits the example rather
than guessing if the root can't be resolved); `root_recursion_guard` now also
offers a plain `rg -l "x" .` alongside the `$CLAUDE_PROJECT_DIR` form.

### ⚠️ Expect one-time churn on your next daemon restart

The `<hooksdaemon>` block in your `CLAUDE.md` is regenerated and auto-committed
on daemon restart. The next restart after upgrading will rewrite the absolute
paths your repository already has committed, in a single diff — this is
expected, not a bug. Nothing about runtime behaviour changes.

## Fixed: installer deployed hooks at a umask-dependent mode

`set_hook_permissions` and `ensure_echd_capture_executable` in
`scripts/install/hooks_deploy.sh` used `chmod +x`, and a `+x` with no "who"
clause is masked by the caller's umask — the same installer produced `0755`
under the common umask `022` but `0744` under `077` (hardened images, many
containers). Every Python deploy path already applied an explicit
`Path.chmod(0o755)`, which ignores umask entirely, so bash was the outlier.

At `0744` the owner can still execute, so this only bites when the installing
user differs from the user running Claude Code — a root install run by a
different user, or a host/container pair sharing a bind-mounted project —
where the hook wrappers become silently non-executable and hooks stop firing.
The existing permissions test asserted `0755` but inherited the test runner's
own umask, so it only caught the bug where the umask was already restrictive;
it now pins a deliberately hostile umask `077` so it fails on any machine.

## Also fixed

- **Daemon auto-commit no longer describes a hand edit as a regeneration.**
  `ClaudeMdInjector._auto_commit_if_dirty` swept any uncommitted `CLAUDE.md`
  change — including genuine hand-written documentation sitting alongside the
  generated block — into a commit labelled
  `Auto: hooks daemon regenerated CLAUDE.md handler guidance`. The sweep-up
  itself is deliberate and unchanged (it exists so an agent doesn't see a
  dirty `CLAUDE.md` after a restart and try to revert or stash it); only the
  message was wrong. It now reports whether the commit changes content
  outside the generated block, without asserting that such content is
  necessarily hand-written.

## Added

- **`scripts/qa/check_doc_snippets.py` — a QA check guarding Python code
  examples in tracked docs against the live package.** Ground truth is
  introspected from the package at check time, never restated, so a renamed
  field changes what the check enforces in the same commit that renames it.
  Found and fixed 8 real defects across `CLAUDE/ARCHITECTURE.md`,
  `CLAUDE/SELF_INSTALL.md`, `CLAUDE/development/QA.md`,
  `docs/QA-RUNNER-SETUP.md`, `CLAUDE/DEBUGGING_HOOKS.md`, and the handler
  skeleton in `CLAUDE.md` itself — including a documented
  `HookResult(modified_input=...)` example that Pydantic silently discards
  rather than raising on, producing a handler that looks like it works and
  does nothing.

## Upgrade

**In the Claude Code chat.** This is a skill invocation you type into Claude
Code — it is NOT a shell command and will not run in a terminal:

```text
/hooks-daemon upgrade
```

Optionally pass a target tag: `/hooks-daemon upgrade v3.53.1`. The default is
latest.

**From a terminal**, run the deployed skill script instead:

```bash
.claude/skills/hooks-daemon/scripts/upgrade.sh
```

If the skill is not deployed in your project, fetch the canonical upgrader —
inspect before running, never pipe it to a shell:

```bash
curl -fsSL https://raw.githubusercontent.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon/main/scripts/upgrade.sh -o /tmp/upgrade.sh
less /tmp/upgrade.sh
bash /tmp/upgrade.sh --project-root /path/to/your/project
```

No config changes are required. No handlers were added or removed (still 85
handlers across 13 event types).
