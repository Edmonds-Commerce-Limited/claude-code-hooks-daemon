# v3.19.2 — Quiet uv copy mode in containers

**Type**: Patch release (bug fix)
**Previous**: v3.19.1

## Summary

Every daemon install/upgrade inside a container printed the alarming
`⚠ uv hardlink failed (likely overlay-fs) — retrying with UV_LINK_MODE=copy`
warning, wasted a first `uv sync` attempt, then retried with copy mode. This
release detects the container environment and picks copy mode up front — one
clean sync, no failed attempt, no warning.

## Root Cause

`create_venv_at_path` (`scripts/install/venv.sh`) already chose copy mode
proactively on hardlink-hostile filesystems — but only by probing the **target**
filesystem type (`overlay`/`nfs`). In a typical container the project (and its
`untracked/` directory) is bind-mounted from the host, so the venv target sits
on the host filesystem (ext4/xfs/btrfs) while `uv`'s cache lives on the
container's overlay filesystem. The two are **cross-device**, so `uv` hardlink
fails even though the target filesystem type is not overlay/nfs. The type probe
could not see this, so the warn-then-retry fallback fired on every container
install/upgrade.

## Fix

- Added a `_uv_in_container` helper to `scripts/install/venv.sh`. Detection
  signals: the `container` env var (Podman/systemd set `container=podman`),
  Podman's `/run/.containerenv`, and Docker's `/.dockerenv`.
- Wired it into the `first_link_mode` decision: when no explicit `UV_LINK_MODE`
  is set and the filesystem-type probe did not already pick copy, a detected
  container selects `UV_LINK_MODE=copy` before the first sync.

### Unchanged behaviour

- An explicit `UV_LINK_MODE` from the environment always wins (escape hatch).
- Normal-disk installs stay hardlink-first.
- The overlay/nfs filesystem-type probe is preserved (the container check is
  purely additive), as is the warn-then-retry fallback for genuine hardlink
  failures detection did not anticipate.
