# v3.24.0 — Minor: promote dormant opt-in features on upgrade + block untracked Claude memory by default

**Release date**: 2026-06-23
**Type**: MINOR release

## Summary

v3.24.0 makes upgrades **actively promote dormant opt-in features** instead of shipping them inert, and — using that revived mechanism — **flips the `allow_untracked_claude_memory` default to `false`** so untracked Claude auto-memory is blocked by default and durable knowledge is steered into tracked, reviewed project docs.

The motivating problem: this project ships behaviour-changing features as opt-in so an upgrade never silently changes a client's behaviour. The side effect is that those features arrive **dormant** — the client gets the code but never the protection unless something tells them the capability exists. v3.24.0 revives, strengthens, backfills, and wires up the previously-abandoned config-changes advisory so every upgrade surfaces a recommendation-grade prompt for each dormant opt-in feature in the version range crossed. The first feature to benefit is the v3.23.0 memory policy, whose default now flips to the safer value.

It also removes a long-standing niggle: the daemon's CLAUDE.md injector now formats the file after writing its block, so the next edit no longer churns the injected guidance.

## Highlights

- **Upgrades recommend enabling dormant opt-in features (Plan 00133)** — config-changes manifests gain `recommended` / `dormant` / `recommended_value`; a `changed` entry compares the client's actual value and surfaces a `🆕 Recommended — enable these` section. `check-config-migrations` is wired into the upgrade flow (and a bare `scripts/upgrade.sh` run).
- **Untracked Claude memory blocked by default (Plan 00133)** — `allow_untracked_claude_memory` now defaults to `false`. Memory writes are blocked (tool + bash side-doors); reads stay allowed. Opt out with `allow_untracked_claude_memory: true`.
- **`Handler.get_default_enabled()`** — a code-level opt-in/opt-out single source of truth, with a drift-guard test against the config template.
- **No more CLAUDE.md formatter churn (Plan 00134)** — the injector writes formatter-canonical content via a shared `format_markdown_text` SSoT.

## Changes

### Changed

- **`allow_untracked_claude_memory` now defaults to `false` (Plan 00133)** — The daemon BLOCKS untracked Claude auto-memory writes (`~/.claude/projects/*/memory/*.md`, via `Write`/`Edit` and bash `>`/`>>`/`tee`) **by default**, routing durable knowledge into tracked project docs (`CLAUDE.md`, `.claude/rules/*.md`, thin skills, `docs/`). **Reads are always allowed** so existing memory can be migrated. This is a behaviour change for projects that relied on the old default — it is **opt-out** (`allow_untracked_claude_memory: true` restores the previous behaviour). A `critical` post-upgrade task guides migration; existing memory files are never modified or deleted by the daemon. A single source-of-truth constant (`DEFAULT_ALLOW_UNTRACKED_CLAUDE_MEMORY`) backs both the handler default and the `optimal_config_checker` reconciliation, so the SessionStart advisory never contradicts the block.
- **Upgrades actively recommend enabling dormant opt-in features (Plan 00133)** — The config-changes advisory is revived, strengthened, and wired into the upgrade flow. Per-version manifests (`CLAUDE/UPGRADES/config-changes/v{X.Y.Z}.yaml`) gain `recommended` / `dormant` / `recommended_value`; a `changed` entry now compares the client's value against `recommended_value` and surfaces a recommendation-grade `🆕 Recommended — enable these` section distinct from the quiet `💡 New Options Available` list. `check-config-migrations` is invoked from `skills/hooks-daemon/upgrade.md` and `scripts/upgrade.sh`. v3.x manifests are backfilled, and an `UNRELEASED/config-changes/` staging directory plus RELEASING.md governance prevents future rot.

### Added

- **`Handler.get_default_enabled()` — code-level opt-in/opt-out SSoT (Plan 00133)** — A concrete base method (default `True` = opt-out) modelling whether a handler ships enabled. Opt-in handlers (e.g. `lsp_enforcement`) override to `False`. A drift-guard test asserts the template's `enabled: false` set equals the set of handlers declaring `get_default_enabled() -> False`.

### Fixed

- **No more CLAUDE.md formatter churn from the daemon injector (Plan 00134)** — The mdformat+gfm transform behind `markdown_table_formatter` and `format-markdown` is extracted into one shared `format_markdown_text` (SSoT), and the CLAUDE.md injector formats the file after writing its `<hooksdaemon>` block (fail-safe; the content-loss guard runs on the pre-format result). The on-disk block is already formatter-canonical, so the next CLAUDE.md edit no longer produces a spurious reformat diff. Note: the injector now runs the formatter over the whole CLAUDE.md (the same transform the PostToolUse formatter already applies on any `.md` edit), so a project's CLAUDE.md may get a one-time canonical reformat on the first daemon restart after upgrade; content is preserved (a content-loss guard runs before writing) and the result converges immediately.
- **`version_check` upgrade notice points to the skill, agent-safely** — The SessionStart "update available" notice now instructs using the hooks-daemon upgrade skill (`Skill tool: skill=hooks-daemon, args=upgrade`) instead of the old manual curl/less/bash steps, phrased so an agent will not run a bare slash command as bash.

## Post-Upgrade Tasks

After upgrading, review `CLAUDE/UPGRADES/v3/v3.23.0-to-v3.24.0/post-upgrade-tasks/` — it contains a **critical** task (`migrate-untracked-claude-memory`) for the `allow_untracked_claude_memory` default flip: decide whether to keep the new default (recommended) or opt out, and migrate any existing untracked Claude memory into tracked project docs. Existing memory files are left untouched; deletion is your call.

## Opting out of the memory policy

If you want the previous always-allow behaviour, in `.claude/hooks-daemon.yaml`:

```yaml
handlers:
  pre_tool_use:
    markdown_organization:
      options:
        allow_untracked_claude_memory: true
```

Restart the daemon.

## Upgrade

```
Use the hooks-daemon upgrade skill (Skill tool: skill=hooks-daemon, args=upgrade).
```

No config migration is required to upgrade. The memory default flip is opt-out and reversible; no data is lost (the policy only blocks new writes).

## Installation

### New Installations

```bash
mkdir -p .claude && cd .claude
git clone https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git hooks-daemon
cd hooks-daemon
git fetch --tags && git checkout v3.24.0
python3 -m venv untracked/venv
untracked/venv/bin/pip install -e .
untracked/venv/bin/python install.py
cd ../..
```

### Upgrading Existing Installations

```bash
cd .claude/hooks-daemon
git fetch --tags
git checkout v3.24.0
untracked/venv/bin/pip install -e .
untracked/venv/bin/python -m claude_code_hooks_daemon.daemon.cli restart
```
