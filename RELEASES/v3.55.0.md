# v3.55.0 — Ten New Handlers, Two of Them On by Default, and a Type-Safe Handler Contract

This is a broad release — around ten new handlers land across PreToolUse,
PostToolUse and SessionStart. Two brand-new PreToolUse safety handlers ship
**enabled by default** — `github_auto_close_keywords` and `secret_file_guard`
— alongside an opt-in skill-opportunity scanner, a new goal-injection
mechanism for Claude Code's `/goal` command, a verification-result gate and
an Ansible lint tier, a type-safety upgrade that makes an undeliverable
handler decision a compile-time error instead of a silent runtime no-op, and
a batch of fixes closing Bash-authored write blind spots across several
existing content guards.

No breaking changes. No handler was removed or renamed, and no
`@abstractmethod` was added to the `Handler` base class — every project
handler continues to work unmodified.

## Added: `github_auto_close_keywords` — enabled by default

A new PreToolUse handler denies a `git commit` (or `git merge -m` /
`git tag -m`, or a `gh pr create`/`gh pr edit` body) whose message contains a
GitHub closing keyword followed by an issue reference — `Fixes #NNN`,
`closes owner/repo#NNN`, `Resolved GH-NNN`. These keywords auto-close the
referenced issue or PR the instant the commit reaches the default branch (or
the PR merges), with **no repository-side switch to disable that behaviour**,
and agents write commit messages like this routinely without realising the
side effect.

There is deliberately **no escape hatch** — unlike most of this daemon's
guards, there is no `MUST_..._BECAUSE` declaration that lets an agent bypass
it in the moment. If a project genuinely wants auto-close commits as a
deliberate part of its workflow, a human disables the handler outright:

```yaml
handlers:
  pre_tool_use:
    github_auto_close_keywords:
      enabled: false
```

Use a non-closing reference instead — `Addresses #123`, `Refs #123`,
`See #123` — and GitHub still links them without closing anything.

## Added: `secret_file_guard` — enabled by default

A terminal PreToolUse handler that absolutely prevents the CONTENTS of
configured secret files from ever entering context, across every route the
daemon can see: `Read`, `Write`, `Edit`, `NotebookEdit`, `Grep`, and any
`Bash` command whose text mentions a protected path — `cat`, interpreter
one-liners, `cp`/`mv` relocation, command substitution, sourcing. Default
globs cover `*.secret*`, `.vault-pass*`, `*.vault-password`, `*vault_pass*`,
`id_rsa`, and `id_ed25519`; a project extends or replaces the list via
`handlers.pre_tool_use.secret_file_guard.options`.

Like the handler above, there is no escape hatch and no self-declared-intent
override — only a human editing config can lift it. A file's PRESENCE and
safe metadata remain visible: a new `secret-meta` CLI subcommand exposes a
keyed HMAC digest and a bucketed size for tooling that needs to reason about
a protected file without ever reading it.

## Added: `skill_opportunity_detector` — ships disabled, opt-in

A SessionStart advisory that surfaces, at most once per `check_interval_days`
(default 7), a suggestion to run the new `bin/hooks-daemon skill-scan` CLI
when repeated near-identical requests or recurring points of confusion show
up in this machine's own Claude Code session transcripts. The scan runs
entirely outside the hook path: a two-layer noise filter, token-set Jaccard
clustering, normalisation placeholders, and secret-word-list redaction
condense the evidence deterministically before a single bounded headless
`claude -p --model haiku` call turns it into skill-creation suggestions,
written to `untracked/reports/`. It is report-only — no skill is ever
auto-created — and every failure mode (no CLI, no auth, offline, timeout,
garbage output) is fail-open. `--dry-run` prints exactly what would be sent
to the model, for a privacy check before ever enabling it.

Enabling this handler is an explicit opt-in to transcript mining: only
extracted HUMAN prompt text is ever read (never tool results or assistant
output). Recommended for development-heavy projects where the same requests
recur across sessions.

## Added: `goal_injection` and goal-stack concurrent tracking

**New in this release, ships DISABLED (Plan 00269).** Claude Code's new
`/goal` slash command gives a session one persistent Stop-hook condition.
`goal_injection` is a PostToolUse advisory that, when a `PLAN.md` flips to
`**Status**: In Progress`, writes a `<session>.goal-intent` signal; the ccy
PTY supervisor — if armed and watching — consumes it to type a
machine-marked `/goal` message into the foreground chat. It is opt-in
**twice over**: the handler itself, and an armed ccy supervisor to act on the
signal. A new `hooks-daemon inject-goal NNNNN` CLI subcommand is the manual
fallback/debug tool.

Because Claude Code holds only one goal at a time, a second plan starting
mid-session would otherwise silently clobber the first plan's goal with no
record that anything had been displaced. Plan 00276, landing in this same
release, closes that gap: `goal_injection` now maintains a goal ledger and
advises when an injection is about to displace a still-live goal, and
`auto_continue_stop` defends any live ledgered goal at Stop time.

## Added: type-safe handler results (no more silently dropped refusals)

`HookResult` used to be one event-agnostic type serving all 31 wired events,
so a handler on `SessionStart` could construct
`HookResult(decision=Decision.DENY)` and mypy stayed silent — the wire
response then silently dropped the refusal, because `SessionStart` cannot
express one. New per-event abstract handler bases
(`PreToolUseHandlerBase`, `SessionStartHandlerBase`, `StatusLineHandlerBase`,
…) narrow `handle()`'s return type to exactly what the event can deliver, so
that mistake is now a mypy `[arg-type]`/`[override]` error at write time
instead of a production no-op. Every built-in handler has been reparented
onto its event's base; a coverage test enforces this for every handler under
`src/`. Project handlers keep working via the existing `Handler` ABC —
migrating onto the new bases is recommended, not required.

## Added: verification-result enforcement and an Ansible lint gap closed

Prompted by a client field report: an `ansible-lint` failure was printed,
diagnosed correctly on stderr, and then ignored by a `git commit` that
followed on the very next line of the same Bash invocation — an unloadable
playbook reached the default branch. Two new guards close this:

- **`verification_result_gate`** (warn-first) flags a verifier
  (`ansible-lint`, `shellcheck`, `pytest`, `ruff`, `mypy`, `go vet`, …)
  followed by a mutator (`git commit`/`push`/`tag`, `gh pr create`, a real
  `ansible-playbook` run) with nothing consuming the verifier's exit status —
  including across a bare newline, not just `;`. Set
  `options.mode: block` to deny instead of advise.
- **`lint_on_edit` now covers Ansible YAML** (playbook/role task files,
  identified by directory convention or a top-level `- hosts:` line): a
  cheap `ansible-playbook --syntax-check` tier catches a play that will not
  load, with full `ansible-lint` as the extended tier. CI workflow files,
  `docker-compose*`, inventories and vault files are left untouched.
- **`staged_lint_gate`** (warn-first) runs the same cheap syntax check across
  every staged file at `git commit` time, catching a file that reached the
  index by a route other than `Write`/`Edit` — `git add` of something written
  earlier, a merge, pre-existing changes.

## Also added

- **`bash_safe_mode`** (ships disabled, opt-in): requires a declared safety
  prelude (`set -e`/`set -o pipefail`, optionally `set -u`) on multi-statement
  Bash invocations, with an in-content `MUST_SKIP_SAFE_MODE_BECAUSE=` escape
  hatch for commands that must run every statement regardless.
- **`contract_staleness`** (SessionStart advisory): flags when the running
  Claude Code version has moved on from the one the daemon's vendored hooks
  contract fixtures were captured against.
- **`write_clobber_guard`**: denies a `Write` to an existing, unread file —
  restoring the `Write` tool's own documented contract after a clobbering
  write destroyed a tracked file in this repository under
  `bypassPermissions`.
- **`artifact_publish_blocker`** (enabled by default, no escape hatch): denies
  `Artifact` tool publishing; enumeration (`action: "list"`) stays allowed.
- **Worktree seeding**: a fresh git worktree now inherits configured
  git-ignored local files at creation instead of starting from a silently
  different configuration; `hooks-daemon check-worktree-seed` suggests
  entries by scanning the repository.
- **Hook contract alignment**: an audit against the raw Claude Code hooks
  documentation found 21 drifts. `PermissionRequest` and `UserPromptSubmit`
  move to the documented blocking tier; `PreToolUse` gains expressible
  `Decision.DEFER` and `updatedInput`; `SessionStart` context now uses the
  documented `hookSpecificOutput.additionalContext` channel.
- **Input-payload validation**: a new `input-contract` QA check validates
  hook input payloads against a superset schema, the companion to the
  daemon's existing response-contract validation.

## Fixed

- **A Bash write side-door across content-guard handlers.** Several
  handlers keyed on the `Write`/`Edit` tools missed files authored via Bash
  redirects, `tee`, and heredocs; `lint_on_edit` and the stream-editor
  (`sed_blocker`) guidance now correctly describe and, where applicable,
  cover the Bash-authored write surface through one shared write-target
  accessor.
- **A Bash tokeniser phantom-target bug.** `get_bash_write_targets` used
  non-POSIX `shlex`, which does not process backslash escapes — so an
  escaped double-quote inside a quoted argument prematurely terminated the
  quote, causing everything after it (including unrelated redirects) to be
  misread as a write target. Fixed and differential-tested against a real
  shell.
- **QA runs were not isolated from each other.** A second concurrent
  `llm_qa.py`/`run_all.sh` run contended over the same coverage file and test
  tree, so either run's verdict could be wrong in either direction. QA runs
  are now serialised.
- Five blocking handlers advertised themselves as advisory in resident
  guidance — corrected.
- A client hanging up was reported as a daemon error, with two tracebacks.
- The duplicate-registration check was blind to actual duplicates.
- Several response-contract gaps closed as part of the type-safety work: a
  refusal an event cannot carry no longer vanishes without a trace, a
  `PermissionRequest` refusal now explains itself, and the constants module
  no longer published a PostToolUse field name that is always absent.

## Post-Upgrade Tasks

After upgrading, review
`CLAUDE/UPGRADES/v3/v3.54.0-to-v3.55.0/post-upgrade-tasks/` — it contains two
tasks that may require action in your project:

- **Recommended**: re-check any `.claude/project-handlers/` for a refusal the
  event cannot deliver via the `HookResult.deny(...)` factory form (the
  detection gap this release closes) — most notably if you copied the
  `branch_naming_enforcer` example handler, which shipped with exactly this
  defect and has never actually blocked anything.
- **Optional**: replace any reference to the removed
  `HookInputField.TOOL_OUTPUT` constant (it named a field no real event ever
  carries) with `HookInputField.TOOL_RESPONSE`.

## Upgrade

**In the Claude Code chat:**

```claude-code
/hooks-daemon upgrade
```

Optionally pass a target tag: `/hooks-daemon upgrade v3.55.0`. The default is
latest.

**From a terminal:**

```bash
.claude/skills/hooks-daemon/scripts/upgrade.sh
```

If the skill is not deployed in your project, fetch the canonical upgrader —
inspect before running, never pipe it to a shell:

```bash
curl -fsSL https://raw.githubusercontent.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon/main/scripts/upgrade.sh -o /tmp/upgrade.sh
less /tmp/upgrade.sh
bash /tmp/upgrade.sh --project-root /path/to/your/project
```

**Two new handlers ship enabled by default** (`github_auto_close_keywords`,
`secret_file_guard`) — if either surprises you on upgrade, disable it in
`.claude/hooks-daemon.yaml` and read its `CLAUDE.md` guidance section for the
non-escape-hatch reasoning before doing so. Check
`hooks-daemon check-config-migrations --from 3.54.0 --to 3.55.0` for the full
set of newly available options, including `skill_opportunity_detector`
(recommended, ships disabled).
