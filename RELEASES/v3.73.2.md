# Release v3.73.2 - Journal Entries Survive Markdown Formatting (Hotfix)

**Release Date:** 2026-11-10
**Type:** Patch Release (hotfix fast path)

## Summary

A hotfix for a deadlock on plan journal entries: a markdown formatter could rewrite a journal entry, the commit gate treats an entry as immutable, and the rewritten file could then be neither committed nor restored. Three fixes close it. The release also carries every other change merged since v3.73.1, chiefly guards that warn instead of deny when they cannot decide. Twenty release-note callouts are folded into Highlights below, in the authors' own words.

## Read this first

- **No breaking change.** No config key is added, renamed or removed. There is no pre-upgrade task, no post-upgrade task and no truth-change.
- **Upgrade guide:** `CLAUDE/UPGRADES/v3/v3.73.1-to-v3.73.2/v3.73.1-to-v3.73.2.md`.

## Highlights

### Audience: client projects

#### a markdown formatter can no longer strand a journal entry

_Plan 00594 · Audience: client projects_

A QA pipeline that ran `hooks-daemon format-markdown <dir>` rewrote plan journal entry headings. The commit gate (`journal-dayfile-is-today`) treats an entry as immutable, so the rewritten file could be neither committed nor restored by an agent, and every later run reformatted it again. Two fixes:

- `format-markdown` now skips plan journal files. A directory walk passes over them, and an explicitly named entry is reported as skipped. The edit-time formatter already did this.
- The journal immutability check, at both edit and commit time, no longer blocks a change that is whitespace-only: the same words in the same order. Any added, removed or changed word is still blocked.

If one of your entries is already stuck with a whitespace-only change, you can now commit it.

#### a titled journal heading is single-spaced, so formatters leave it alone

_Plan 00594 · Audience: client projects_

`mkplan.bash --journal ... --title T` used to put three spaces before the title (`## HH:MM · category · REF   — T`). A markdown formatter in the project's own format check (prettier, for example) collapses that run of spaces. The commit gate treats a journal entry as immutable, so the collapsed version could never be committed and the format check stayed red. The scaffolder now writes `## HH:MM · category · REF — T`, which is already in collapsed form. Existing entries are not touched.

If your format check covers plan files, also exclude `**/JOURNAL/**` from it. Journal entries are append-only, and the daemon's own markdown formatter already skips them.

#### commit gates warn instead of deny when they cannot decide

_Plan 00478 · Audience: client projects_

The owner's ruling is "warn dont block": a safety guard that cannot tell whether a commit is dangerous allows it, with an advisory. A positively recognised finding (a conflict marker, a secret term, a public pattern, a lint failure, a missing provenance block, a docs or plan QA finding) still denies. Eight routes that used to deny because the gate had no verdict now allow, with an advisory naming the guard, the cause and how to rephrase:

- `conflict_marker_commit_gate`, git ran out of time reading the commit (`R-CONFLICT-MARKER-SCAN-TIMED-OUT`, now an advisory only; the rule ID stays so the explanation and the advisory still cite it).
- `conflict_marker_commit_gate`, a commit it cannot place or read (`cd` through a variable, `--git-dir`, `GIT_INDEX_FILE`, `--pathspec-from-file`, `git am <patch>`, a directory outside a repository, a git failure). A marker found in another commit of the same command still denies.
- `sensitive_content`, a secret word list that exists but cannot be read. The advisory names the configured path and never a term. A public-pattern match still denies.
- `sensitive_content`, a staging simulation that fails. The command text (a commit message, a `gh` body) is still scanned, so a term written in it still denies.
- `staged_lint_gate`, a staging simulation that fails (in block mode as well as warn).
- `remote_docs_commit_gate`, a staging simulation that fails.
- `docs_qa_commit_gate` in block mode, a staging simulation that fails.
- `plan_qa_commit_gate` in block mode, a staging simulation that fails.

Every one of these writes one log line starting `UNKNOWN-VERDICT <handler> <cause>` (WARNING), so a field report can count how often the guards fell back to warning. A command written to defeat the reader can force an unknown verdict and so run with only a warning; the ruling accepts that cost.

#### six more guards warn instead of deny when they cannot decide

_Plan 00478 · Audience: client projects_

The owner's ruling is "warn dont block": a safety guard that cannot tell whether something is dangerous allows it, with an advisory. A positively recognised finding still denies, and it still denies when the same command also holds a part the guard could not judge. Six more routes that used to deny because the guard had no verdict now allow, with an advisory naming the guard, the cause and how to rephrase:

- `flaggable_content_channel_guard`, a recursive search whose roots or exclusions cannot be placed (a shell expansion such as `$DIR`, unparseable quoting, `git -C` with a relative or built value, `--git-dir`, unknown pathspec magic, a relative root with no working directory). A literal absolute `git -C /path` is placed as the working directory and still denies when it reaches the flagged directory. A root that positively contains the flagged directory still denies.
- `plan_journal_guard`, a Bash write whose destination is built at run time, or text the write analysis could not read, that could name a journal day-file or `JOURNAL/` directory. A destination with a literal day-file name, or a literal `JOURNAL/` before its first run-time part, still denies; only one unknown all the way through warns.
- `release_merge_freeze` (a project handler), a release state file that cannot be read, is not a JSON object, or has no positive `ci.pr_number`. A positively open release still denies.
- `reference_repo_freshness`, a governed clone with no in-date freshness reading (`R-REFERENCE-REPO-NOT-VERIFIED`, now an advisory only in every `mode`). A clone known to be stale (`R-REFERENCE-REPO-STALE`) still follows `mode`, also when another path in the same call is unverified.
- `curl_pipe_shell`, a download piped into python, perl, ruby or node with an argument that cannot be resolved. A pipe into a shell, into an interpreter that reads stdin, or into one whose unresolved word is an option's value (`python3 -W $W`) still denies, as does a shell behind a wrapper with an unresolved argument (`sudo $FLAG bash`).
- `root_recursion_guard`, a recursive scan of a path under `/proc` or `/sys` that cannot be stat'ed. A catastrophic root still denies.

Every one of these writes one log line starting `UNKNOWN-VERDICT <handler> <cause>` (WARNING), so a field report can count how often the guards fell back to warning. A command written to defeat the reader can force an unknown verdict and so run with only a warning; the ruling accepts that cost.

#### validate_eslint_on_write warns instead of denying when ESLint cannot run

_Plan 00478 · Audience: client projects_

Under the owner's "warn dont block" ruling, `validate_eslint_on_write` no longer denies when it has no verdict. If ESLint does not finish within its timeout (`R-ESLINT-TIMEOUT`) or cannot be launched (`R-ESLINT-RUN-FAILURE`), the write is now allowed with an advisory that says plainly the file was NOT linted, and one log line starting `UNKNOWN-VERDICT validate_eslint_on_write` is written. Both rule IDs stay, as advisory-only rules, so `explain-rule` and the advisory still cite them. ESLint errors that were actually reported still deny (`R-ESLINT-ERRORS`). A TypeScript file written while ESLint is hung or missing is therefore no longer stopped: run ESLint by hand when you see the advisory.

#### generated forwarder stubs pass shellcheck

_Plan 00577 · Audience: client projects_

Every generated `.claude/hooks/*` forwarder stub assigned `HOOKS_DAEMON_RELAY_UNUSED` in its relay hot path without `export`. `shellcheck --severity=warning` reported SC2034 (appears unused) on it, once per stub, so a client that lints its shell scripts failed after every upgrade, and the stubs are regenerated on every upgrade, so the client could not fix it locally. The assignment is now `export HOOKS_DAEMON_RELAY_UNUSED=...`, the form shellcheck treats as used externally. Behaviour is unchanged: `init.sh` reads the variable and unsets it before the stub starts the daemon. A test now shellchecks the stub generated for every event. GitHub #163.

#### optional seed entries are not reported as MISSING

_Plan 00580 · Audience: client projects_

`hooks-daemon check-worktree-seed` listed a configured seed entry under MISSING whenever its source was absent, even when the entry was marked `optional: true`. Creation-time seeding already skips an absent optional source, so the report claimed that the next worktree creation would abort and told the reader to remove an entry that was working as designed. The report now lists only absent required entries under MISSING. An absent optional entry is no longer reported, a present one is unchanged, and creation-time seeding is unchanged. GitHub #167.

#### provision repairs a stale venv

_Plan 00581 · Audience: client projects_

`bash .claude/provision.sh` reported "nothing to do" whenever the daemon clone was already at the expected version, even when a pull had changed `pyproject.toml` or `uv.lock` and left the venv built for the old lock. The restart path warned "DAEMON VENV NOT BUILT FOR THIS SOURCE" while provisioning said all was well. A foreground run now checks the venv's lock hash; a stale (or unreadable) one is rebuilt through the existing bootstrap repair, and the output says so. A `--background` run never rebuilds: it reports the stale venv and names `hooks-daemon repair`. A venv that matches is unchanged, and the version-mismatch sync and fresh provisioning are unchanged. GitHub #168.

#### branch guard notices state intent and action

_Plan 00583 · Audience: client projects_

The surfaces that name idle branches read as a status report, so unfinished work branches were left in place across many stops. The main-thread Stop context line for idle branches and the `branch-sweep` "Dormant:" section now state the branch-limit principle (work must finish, not disappear), tell the session to take that work on, and give each branch its next step: finish and merge it, `branch-park <name> --reason ...`, or `delete-branch <name>` when the guard proves nothing is lost. The `R-BRANCH-WIP-CAP` deny no longer offers "continue in one of them" as a way past the cap; it demands finishing (merging), parking or proven-safe deletion first. Thresholds, caps and which branches are judged are unchanged. GitHub #192.

#### a merged branch's remote delete is no longer denied when chained after its worktree removal

_Plan 00474 · Audience: client projects_

(Ledger item N578.) `git worktree remove <wt> && ... && git push origin --delete <b>` was denied by the destructive_git guard (R-GIT-PUSH-DELETE-REMOTE) even when `origin/<b>` was merged into the default branch, because the worktree removal also matched a rule and the remote delete was then never judged on its own proof. The remote delete is now judged the same alone or chained after a worktree removal or local branch delete, and every denial of it names the branch and why it is not proven merged. Unmerged branches, tags, `--mirror` and `--prune` stay denied.

#### the project-root write guard follows a cd into loop, if, group and subshell bodies

_Plan 00587 · Audience: client projects_

(GitHub #195.) `project_containment` (R-WRITE-OUTSIDE-PROJECT-ROOT) judged a relative redirect inside a `for`, `while`/`until`, `if` or `( )` body from the starting directory as well as the directory a preceding `cd ... &&` reached, so `cd sub && for x in a; do echo hi 2>>../f; done` was denied with a target joined to the repository root. The body is now read from the directory the `&&` chain reached, as a top-level step is. A `cd` outside the project, a target that climbs out of the root, a `cd` inside the body and a target before the `cd` stay denied. Only this guard changed; the git gates read the command as before.

#### lsp_enforcement no longer judges a grep that filters stdin, or `git grep`

_Plan 00588 · Audience: client projects_

(GitHub #169.) `lsp_enforcement` (R-LSP-SYMBOL-LOOKUP) treated `printf ... | grep -v some_name` as a project-wide symbol lookup, because a grep with no file target was read as "the whole project", and it picked up the `grep` inside `git grep -lF some_name HEAD -- dir` the same way. Neither searches a file a language server indexes, so neither is denied or advised any more: a grep or rg fed by a pipe, a `<` redirect or a `<<<` here-string and naming no file, and every `git grep` (with or without a ref or pathspec, `git -C dir grep` included). A `grep -r` stage still searches the working directory and stays judged. `grep -rn some_name src/`, `rg some_name`, a grep with no target as the first command, the Grep tool, and which patterns look like identifiers are unchanged. A command mixing a skipped grep with a real one is judged as before.

#### destructive_git no longer denies git text printed by a single-quoted awk program

_Plan 00478 · Audience: client projects_

(GitHub #170.) `printf 'x\n' | awk '{print "git worktree remove " $1}'` was denied under R-GIT-WORKTREE-REMOVE-FORCE ("This delete could not be verified as safe: no forced branch delete or worktree removal could be read") although it runs no git. The `$1` made `destructive_git` keep the awk program as command text, its raw-text patterns matched `git worktree remove`, the parser read no removal, and the fail-closed unreadable branch denied. A single-quoted awk program is now data for awk, `$` included, so `print`/`printf` of `git worktree remove ...` or `git branch -D ...` (with `-F`, `BEGIN` blocks and so on) is allowed. Anything that may run the text is judged as before: a pipe into `sh`/`bash`/`xargs`, `eval "$(...)"`, `source <(...)`, `bash -c "$(...)"`, an awk `system(...)`, an awk `| "sh"` or `> "file"` redirect (a script a later command can run), and a real `git worktree remove` beside the print. The unreadable-command verdict itself is unchanged.

#### explain-rule and explain-handler now resolve handlers loaded through `plugins:`

_Plan 00589 · Audience: client projects_

(GitHub #171.) Every deny ends with "Full detail: `hooks-daemon explain-rule <ID>`", but for a rule declared by a handler registered under the `plugins:` config section the command answered `unknown rule ID`; `explain-handler <name>` had the same gap. The lookup read the library handlers and the `project_handlers:` directory and never the plugin loader. It now also loads the `plugins:` entries through the same `PluginLoader` the daemon uses, so a plugin handler's rules and docs resolve, and a disabled entry contributes nothing. A plugin that fails to load is logged and left out; library and project lookups still answer. The block-report fingerprint index is unchanged (library handlers only).

#### R-DAEMON-DIR-CD no longer denies a quoted search pattern that names `cd`

_Plan 00590 · Audience: client projects_

(GitHub #194.) `daemon_location_guard` denied commands that change no directory, such as `grep -c "cd " .claude/hooks-daemon/CLAUDE.md`, because the quoted pattern's `cd ` was joined to grep's file argument once quotes were removed. The text of a `grep`/`egrep`/`fgrep`/`rg` command is now ignored when nothing could run it (no expansion in it, and its output is not piped to a shell). Every executing form still denies: `bash -c`/`sh -c` bodies, `eval`, `$( )`, backticks, `( )`, an executing heredoc, `echo "cd ..." | sh`, and a real `cd` after the grep. `echo`/`printf` are still judged as before.

#### the CLAUDE.md auto-commit waits for uncommitted plugin and project handler files

_Plan 00591 · Audience: client projects_

(GitHub #172.) On restart the daemon regenerates the CLAUDE.md handler block and commits it. If a `plugins:` or `project_handlers:` handler file was still untracked or modified, that commit recorded a rule row no committed code declared. The commit is now held back while any such source file is untracked or modified: CLAUDE.md stays dirty and one log line names the file. Commit the handler and the next restart commits the block. Library handlers, sources outside the repository, and projects with no plugin or project handlers behave as before.

#### a failed worktree creation no longer leaves a locked worktree and branch behind

_Plan 00592 · Audience: client projects_

(GitHub #173.) A `git worktree add` that was killed (for example by its timeout) leaves the worktree locked with the reason `initializing`, so the handler's cleanup could neither remove the worktree nor delete its branch. The cleanup now releases a lock whose reason is exactly `initializing`, then removes the worktree and the branch it created as before. A worktree locked for any other reason is never touched. Whatever the cleanup still cannot remove is named (path and branch) in the error the handler raises.

#### a seeded copy identical to its source no longer blocks a worktree removal

_Plan 00579 · Audience: client projects_

The worktree-removal check (`R-GIT-WORKTREE-REMOVE-FORCE`, also used by `branch-sweep --clean` and the `WorktreeRemove` handler) now reads the `worktree_create` seed list directly. A copy-mode seeded file, or a seeded directory, that is byte-identical to its source in the main checkout can no longer be lost, so it no longer blocks the removal and needs no `branches.cleanup_after_merge.regenerable` entry. A copy that differs from its source, or whose source is gone, still blocks, and the deny names it as differing from its source. Symlink seeds, `regenerable` globs (which add to the seed list) and every other ignored entry behave as before. If you repeated seed paths in `regenerable` only to get past this, you can remove them.

#### pipe_blocker and write_protected_paths warn instead of denying when they cannot decide

_Plan 00478 · Audience: client projects_

Under the owner's "warn dont block" ruling, two more guards allow with an advisory (and one log line starting `UNKNOWN-VERDICT <handler>`) where they used to deny for lack of a verdict.

`pipe_blocker`: a pipe to `tail`/`head` whose producer is on neither the whitelist nor the blacklist is allowed with an advisory **only when no blacklisted command is named anywhere in the command**. The advisory names `bin/echd-capture` for an expensive command and `extra_whitelist` for a cheap one. For example, `my_report --all | tail` and `docker ps | tail -1` warn. These still deny:

- A known expensive producer (`pytest`, `npm test`, `cargo`, `make`, ...) feeding the pipe, including through a wrapper or runner the guard reads through (`VAR=x`, `env`, `timeout N`, `sudo`, `uv run`, `npx`, `xargs`, `python3 -m`, a `bash -c '...'` body, `.venv/bin/pytest`).
- Any pipe whose producer is unknown, when a blacklisted command appears anywhere in the command text: in another statement, a substitution, a `-c` body or a here-string. The match is per word: as written, as a path's basename (`scripts/qa/run_all.sh`) and with a glued `-m` removed (`-mpytest`). Whole words only, so `pytester` does not count. This is the rule that catches `unbuffer pytest | tail`, `sleep 1 & pytest | tail` and `bash -euo pipefail -c 'pytest' | tail`, whatever wrapper is in front. The deny names the command and says the guard could not tell which pipe it feeds; if it feeds none, run it as a separate command.
- A prose-shaped match, and a pipe fed by a whole loop, `if`, `case` or group.
- Every pipe in a command is judged, and a single `&` ends a statement. An unknown pipe never excuses another one: `docker ps | tail -1 && pytest | tail -5` denies on `pytest`.

An expensive command that is on no list (a project script such as `run_all.sh`) now only warns. Add it to `extra_blacklist` to keep the deny. An entry is matched against every word of the command and its basename, so `'^run_all\.sh(\s|$)'` covers `./scripts/qa/run_all.sh`, `bash scripts/qa/run_all.sh` and `timeout 600 scripts/qa/run_all.sh`. End an entry with `(\s|$)` rather than `\b` if a longer file name (`run_all.sh.bak`) must not match.

`write_protected_paths`: when a command cannot be read (unclosed quote, brace group past the spelling cap, text too deep or large to scan) and no listed path is literally named in it, the command is now allowed with an advisory. A protected-path glob with no literal part (such as `**`) used to turn this case into a deny.

An awk program that writes is handled by where it writes:

- **Only to string literals** (`print > "/tmp/out"`, `print | "sort"`): its file operands are only read. It is judged by its program text, as before.
- **To a computed destination** (`print > FILENAME`, `> $1`, `| cmd`, `system()`): it denies when a file operand names a listed path (`awk '{print > FILENAME}' protected/x`). An operand built from an expansion (`$PWD/protected/x`, `~+/protected/x`) counts when its literal part names a listed path or directory, and always counts under a glob with no literal part.
- **Run inside a listed directory** (`cd protected && awk '{print > $1}' ...`): it denies whatever its destination.
- **Otherwise**: it is allowed with the advisory, unless the program names a listed path.

Wherever a listed path IS named in the command, an unknown verb or unreadable text still denies. If you relied on that deny as a backstop, list a literal path to keep it.

### Audience: everyone

#### `/release hotfix` fast path, and advisories no longer fail QA

_Plan 00576 · Audience: everyone_

`/release hotfix` (or `/release X.Y.Z hotfix`) cuts an emergency patch release on a shorter path: in-flight plans no longer stop it at the slate gate (the report still prints), the housekeeping phase, the Claude Code changelog review and the documentation review are skipped, the code review covers only the hotfix commits, and acceptance testing is the deterministic gates plus targeted tests for the handlers the fix changed. The release pull request, the full CI gate, the merge freeze, CI verification, tagging and publishing are unchanged. Separately, an advise-severity `plan_qa` or `docs_qa` finding is now reported without failing the check; only block-severity findings fail QA and CI.

### Audience: operators

#### a shell file test no longer reads as an interpreter running inline code

_Plan 00576 · Audience: operators_

`subagent_full_qa_blocker` judges a program it does not recognise as UNSEEN when it is run with `-e`, `-E`, `-c`, `-r` or `--eval`, the flags that hand code to an interpreter. The shell file tests `[ -r FILE ]`, `[[ -e FILE ]]` and `test -e FILE` matched that shape, though there `-r` means "readable" and `-e` "exists". A sub-agent running a script that holds such a test, such as `hooks-daemon status`, got an advisory saying it ran inline code. `[`, `[[` and `test` are now among the programs whose own flags are never read as inline code. Found during Plan 00576's close-out configuration review.

## Installation

### New Installations

```bash
mkdir -p .claude
git clone -b v3.73.2 https://github.com/Edmonds-Commerce-Limited/claude-code-hooks-daemon.git .claude/hooks-daemon

# The installer builds the fingerprint-keyed venv, installs the package and
# starts the daemon. Never hand-build a venv: the resolver refuses the
# retired pre-v3.7.0 layout.
bash .claude/hooks-daemon/scripts/install_version.sh "$PWD" "$PWD/.claude/hooks-daemon"
```

### Upgrading Existing Installations

```bash
cp .claude/hooks-daemon.yaml .claude/hooks-daemon.yaml.backup
git -C .claude/hooks-daemon fetch --tags

# Rebuilds the venv and reinstalls the package for the target version. Runs the
# target's own upgrade.sh: the installed one may predate the pre-deploy gate.
tmp="$(mktemp)"
git -C .claude/hooks-daemon show "v3.73.2:scripts/upgrade.sh" > "$tmp"
bash "$tmp" --project-root "$PWD" "v3.73.2"

.claude/hooks-daemon/bin/hooks-daemon restart
```
